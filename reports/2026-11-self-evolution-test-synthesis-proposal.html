自进化瓶颈突破方案
从"人工造数据集"到"Bad Case 自动沉淀为可回归测试资产"

调研范围：SWE-bench / SWE-smith / SWE-Gym · Agent-as-a-Judge · AgentDebug / TRAIL / Who&When · AgentEvolver / R-Zero / Absolute Zero · tau-bench / tau2-bench · CheckEval / metamorphic testing · OpenAI Agent Improvement Loop / LangSmith / DeepEval · ExpeL / AgentLoop 经验库 · specification mining（Prometheus / SpecFirst / TrajSpec）· On Randomness in Agentic Evals / Miller Error Bars · Silent Regressions（NeurIPS 2026 WS）· 生成与裁决分离验收闭环

一句话方案

在现有 probe_reports（归因）与六步聚类之后，新增一条 「轨迹 → 回归案件（Case）→ 三级验证器 → 回归门禁」 的自动沉淀管线：每个分析出来的 bad case 不再只是"一条归因记录"，而是被自动合成为一份最小复现输入 + 三级验证器（程序化断言 → checklist 评审 → 变换不变量）的可回归案件，进入 FAIL_TO_PASS / PASS_TO_PASS 双集回归门禁，替代人工构造的评测数据集。

一、我们卡在哪：现状与瓶颈

当前自进化闭环（M5）的链路是：bad_cases（外部只读表）→ probe_reports 归因（model / prompt / error）→ 占位聚类 → git candidate → 占位评测。整条链路上有两个断点：

图 1 · 当前闭环与两个断点（红色）

断点①：bad case 分析完就"沉库"了。 probe_reports 记录了归因类型与描述，但它只是一段文字，没有变成"可以重新执行、可以判定通过/失败"的东西。下一轮进化无法回答"上一轮修的那个问题，现在真的修好了吗"。

断点②：评测集靠人工构造。 eval_config 由人工在向导里配置，评测证据从哪来是人工成本大头；且人工构造的集合是静态的，覆盖不到线上真实失败的长尾。

charter 明确约束 "没有评测证据的自动改代码"不做——所以断点②不解决，整个闭环只能停在占位评测，进化就不是"进化"，是"换运气"。

二、业界是怎么做的：五条路线与适用性判定

两条调研线（失败轨迹转测试、自构造数据与验证器）合计覆盖 20+ 个项目/论文。逐条判定是否适用我们的场景：

路线 / 代表项目核心机制适用性判定理由
SWE-bench 抽测试 从真实 PR 中抽取"人已写好的测试 diff"作为 FAIL_TO_PASS / PASS_TO_PASS 回归集 不适用 前提是"修复者写了测试"。我们的 harness 目标对象（skill / agent 配置）没有自带测试套件，无 diff 可抽。但其 FAIL_TO_PASS / PASS_TO_PASS 双集语义被我们保留（见第四节）。
SWE-smith bug 注入 LM 自动注入合成 bug，用仓库原有测试当验证器，批量造可执行任务 部分适用 思想可借鉴："验证器可以复用、只有触发条件需要合成"。但注入对象是代码，我们进化的是prompt/skill/agent 配置，不能直接搬。其"合成样本不过就回炉"的自反馈环被吸收。
Agent-as-a-Judge（Meta） 把完整轨迹喂给 judge agent，输出结构化判决（met / unmet + 证据定位） 部分适用 轨迹评审形式与我们 probe 归因天然契合，可当 L2 验证器；但纯 LLM 判决方差大、不可当 CI 门禁，必须降级为"软验证层"并与程序化断言组合。
AgentDebug / TRAIL / Who&When 失败归因 层级错误检测 + 根因聚类，输出 (step, agent, error_type, root_cause) 已具备 / 直接复用 我们的 probe_reports.attribute_type + probe_analysis 就是这个三元组的简化版。关键洞察：归因输出的"出错步骤"恰好是构造最小复现测试的归约（shrinking）锚点——复现输入 = 固定出错步骤之前的最小上下文。
AgentEvolver（阿里） Self-Questioning：从失败/存疑轨迹自动提出带可验证答案的新任务；Self-Attributing 过程奖励 适用（思想层） 证明"失败轨迹本身就是新任务的矿"。我们吸收其"从失败生成新任务"的思想，但不需要其 RL 训练部分——我们是 harness 层进化，不是模型权重进化。
R-Zero / Absolute Zero 自博弈 Challenger-Solver 互相出题；自生成可执行验证程序，解释器判定，零人工数据 部分适用 Absolute Zero 的"验证器与任务同步自生成"是'轨迹→测试'的最纯形态，启发我们的 L1 程序化断言生成。但纯自博弈会reward hacking（论文已观察到奖励退化），所以必须加"验证器自身被校验"环节，不能裸跑。
tau-bench / tau2-bench user simulator + 程序化终态断言（DB 状态 / 动作集比对）+ passk 显式建模 flaky 适用（L1 范式） 最有用的工程范式：验证器不必判"过程对不对"，只需判终态可程序化比对的不变量。passk 直接解决 LLM 系统"这次过下次不过"的回归噪声问题。tau2 的 JSON domain spec 可直接作为我们 case 卡的存储格式参考。
CheckEval / G-Eval rubric 把"好不好"拆成 yes/no 原子断言 checklist，一致性远超 1-5 打分；多 judge + 基线对照消噪 适用（L2 范式） 凡程序化断言覆盖不到的质量维度（措辞、合规、风格），用 checklist rubric + "基线版本 vs 新版本"对照判定，judge 噪声被两侧抵消。
Metamorphic / property-based（metamorph、CheckList） 不判绝对对错，判变换不变量（换文件名/换顺序/加干扰，结果语义应等价）；违规样本自动 shrink 成最小失败 case 适用（L3 范式） 零 oracle、零 token 回归成本，且天然从 bad case 泛化出"一簇"变体（bad case 只是一簇的特例），正好补"人工数据集覆盖窄"的短板。
OpenAI Agent Improvement Loop / LangSmith 动态 dataset / DeepEval Synthesizer trace 打标 → LLM 聚类归纳 failure taxonomy → 每类自动生成 eval case + grader → 重跑；动态 dataset = 持久化查询 适用（管线骨架） 这就是"断点①②"的标准工业解法，且与我们"probe → 聚类 → 评测"六步结构同构，挂接成本低。
ExpeL / AgentLoop 经验库 轨迹压缩成经验/insight 检索复用；阿里 AgentLoop：经验先跑消融（带/不带回归对比）收益为正才入库 部分适用 "消融验证后才入库"是全方案最重要的防污染机制，直接移植到我们的 patch 与 case 验证器的准入判定；经验库本身不是当前瓶颈，暂不引入。
Spec mining（Prometheus / SpecFirst / TrajSpec） 从轨迹反向归纳"场景 spec（前置条件+期望+禁止行为）"，编译成可执行断言 远期 是 L1/L2 资产的终态形态（反复出现的 rubric 升级为持久 spec），有价值但有"把观察到的 bug 固化成规范"的幸存者偏差风险，放二期。
结论：没有任何单一项目能直接搬进来。SWE 系假设"有代码测试"，纯 judge 系不可当门禁，纯自博弈系会 reward hacking，tau 系需要重写领域。但把它们按层拼装，恰好补齐我们两个断点。

三、推荐方案：「回归案件（Regression Case）」自动沉淀管线

核心动作只有一个：给 probe_reports 的每条归因，追加一个自动合成阶段，把"一段归因文字"升级为"一份可执行的案件卡"。案件卡由三部分组成：

案件卡（Case Card）的三要素 —— 用一个例子说明

假设线上分析出这样一个 bad case：

probe_id:      pr-20261104-017
probe_object:  skill/pdf-export  (v1.3)
attribute_type: error
probe_analysis: 用户要求导出"季度报告-2026Q4.pdf"，agent 调用导出工具时
                文件名未做编码处理，遇到中文与连字符导出静默失败，
                会话内无报错提示，用户重试 3 次后放弃。

自动合成阶段把它升级为：

要素内容（本例）来源机制
① 最小复现输入归约后的会话上下文：同一句用户指令 + 中文文件名环境 + 导出工具可用。只保留出错步骤之前的必要状态，剥掉无关历史（长对话、无关子任务）AgentDebug / Who&When：归因的出错步骤 = 归约锚点
② 三级验证器L1 程序化断言：导出产物存在、文件名经编码比对一致、无静默失败标记。L2 checklist 评审：失败时是否有用户可见报错提示（yes/no 原子断言 × N，双 judge 对照）。L3 变换不变量：换成纯英文名 / 换成日文 / 加空格，导出均应成功且语义等价tau-bench 终态断言 / CheckEval / metamorphic
③ 准入记录合成后先自证：在旧版本（v1.3）上必须失败、在人工确认的修复版上必须通过，两条都成立才准许入集；judge 生成的断言需双 judge 共识 + 采样一致性SWE-smith 回炉 / R-Zero 共识 / AgentLoop 消融入库

图 2 · 管线全景：从轨迹到回归门禁（六步）

为什么是"三级验证器"，而不是只靠 judge？

L1 程序化断言（门禁主力）

判终态事实：产物存在性、工具调用参数、数据库/状态比对。确定性、零 token、可当 CI 硬门禁。来源：tau-bench 范式 + LLM 从轨迹归纳 likely invariants（自动导出不变量）。

L2 checklist 评审（软层）

判质量与体验：报错是否可见、回答是否合规。CheckEval 式 yes/no 原子断言 + 异构双 judge + "基线 vs 新版"对照判定，judge 噪声被对照抵消，只做加分/降级不单独否决。

L3 变换不变量（泛化层）

一个 bad case 往往是一簇问题的特例。对复现输入做自动变换（换语言、换格式、加干扰、重排序），断言"语义等价"仍然成立——不用人工补数据，就把 1 个 case 扩成 1 组回归，且 L3 是零 judge 成本的可重复执行。

防作弊与防污染（业界踩过的三个坑，逐一设防）

坑1 · 生成测试本身是错的（reward hacking）：Absolute Zero 已观察到自博弈奖励退化。设防 = 第④步"旧版必败 + 修复版必过"双向自证 + 断言生成的双 judge 共识；自证不过的案件回炉，重合成 2 次仍不过则降级为"仅观察"不入集。
坑2 · 把观察到的行为固化成规范（幸存者偏差）：spec mining 系的通病。设防 = 案件卡区分 verified（经过第④步双向自证）与 observed（仅来自轨迹观察），只有 verified 才能进 FAIL_TO_PASS；L2 rubric 由"期望行为"而非"实际行为"生成。
坑3 · LLM 系统回归 flaky（这次过下次不过）：设防 = tau-bench 的 passk：每个案件独立重放 k 次（如 k=3）全过才算通过，门禁比较新旧版本的通过率而非单次结果。

四、怎么落到我们的代码上

方案对现有架构是增量插入，不推翻任何既有模块。复用现有的事实：六步状态机（state.py 单游标）、job 队列与事件总线（job_runs + run_events）、外部网关模式（eval_poller 冻结网关）、双方言存储与契约门禁。

新增/改造点位置与做法对齐的架构约束
案件卡存储 regression_cases 新表（Alembic 双方言迁移）：输入快照引用（复用 raw payload 按 (root_session_id, agent_id) 唯一保存的事实）、三级验证器定义（JSON）、准入状态 verified / observed / rejected、归属 probe_id / cluster_id / run_id 存储隔离在 db/ 接口与 repository 后；一个事实一个 home
合成服务 service/evolution/case_synthesis/ 三步：归约（按 probe_analysis 定位步骤截断会话树，复用既有树组装）、验证器合成（LLM 生成 L1 断言表达式 / L2 checklist / L3 变换表）、自证准入（对基线 ref 与修复 ref 各跑一遍） 业务规则进 service/；LLM 调用放 third_party_api/ 出站边界
挂接六步状态机 在「聚类」与「迭代」之间插入案件合成子阶段（cluster_only 引擎可跳过）；合成任务走既有 job 队列 + run_events，事件序列号机制原样沿用 单一 m5-01 unit-cursor 状态机，不另起状态副本
评测执行器（替换占位评测） eval_poller 的冻结外部网关语义不变：网关收到的不再是人工 eval_config，而是 regression 双集引用；执行器按案件重放输入、执行 L1 断言、收集 L2 判决，返回 passk 统计 出站用版本化 contract；CI 只用 mock；packages/contracts 先行
门禁判定（增强 apply_final.py） 接受条件从占位改为：FAIL_TO_PASS 配对统计显著翻绿（McNemar）且 PASS_TO_PASS 通过率配对不降（n 由功效分析定，见"随机性修正"一节）；判决证据（哪个案件、哪级验证器、judge 意见）写进 round 快照，满足 charter"评测证据"要求 charter：无评测证据不自动改代码；评测器改动单独实验
评测集不再人工构造 向导第 2 步的 probe 预览保持不变；新增"案件预览"：展示合成出的 L1/L2/L3 与自证结果，人工只做抽查否决，不做构造 admin 可写、成员只读的既有权限模型

分阶段推进（每步独立可验收）

1
先做 L1 + 自证准入（价值最大、风险最小）：只合成程序化断言，先把"旧 bad case 可重放、可判定"打通，评测占位符即可下线。
2
补 passk 与 PASS_TO_PASS：接入门禁判定，替代占位评测，进化闭环拿到真实评测证据。
3
补 L2 checklist + 双 judge 对照：覆盖体验/合规类归因（prompt 型 probe 的主场景）。
4
补 L3 变换泛化：从单案扩为案件组，数据集规模开始自增长。
5
远期：rubric 升格为持久场景 spec（spec mining 形态），反复出现的 checklist 沉淀为对象级规格。

补充：随机性与可复现性——"跑 3 次必失败"成立吗？（修正后的口径）

不成立，方案在此处修正。实证依据：KTH《On Randomness in Agentic Evals》（6 万条 SWE-bench 轨迹）测得——温度 0 也不确定（推理引擎浮点/并行/批处理引入非确定性），同配置 10 次独立评测单次成功率波动 2.2–6.0 个百分点，pass^5 与 pass@1 最大差 24.9 个百分点。agent 的成败是伯努利事件，不是确定性事件。Miller《Adding Error Bars to Evals》(arXiv 2411.00640) 给出正确统计口径；Anthropic 官方指引：客户侧 agent 用 pass^k，"demo 看 pass@k、产品看 pass^k，两者之差就是 flakiness"。业界已有可借鉴实现：Anthropic skill-creator 的 test/measure/refine、社区 agent-regression-evals（flake_detector + regression_gate）、regressgate。

修正一：案件先分类——很多 skill 问题冻结输入后其实是确定性的

以"步 50 触发 skill、步 90 出错"为例：随机性只存在于 agent 构造输入的决策过程（步 1–89）；前缀冻结、指令固定后，步 50 之后的工具调用路径（skill 代码 + 工具）往往是确定性代码。据此分类：

类别失败位置复现预期自证判据（旧版跑 n 次）
D 类（确定性）工具/代码层（如文件名编码 bug）10/10 复现失败 ≥10/10，按传统测试对待
S 类（统计性）LLM 决策层（如该触发未触发）以失败率复现失败率显著高于阈值（Wilson 区间下界 > 30%），n 由功效分析定，通常 ≥ 20

归约（shrink）的真正目的由此改写：不是"保证复现"，而是把"30% 的玄学失败"放大成"可检测的高频失败"——逐条裁剪前缀摘要、重测失败率，留下抬升失败率的条目。达不到统计判据的案件降级 observed，不进门禁。

修正二与修正三：统计口径的门禁

  • 准入（修正"旧版必败+修复版必过"）：旧版跑 n 次（D 类 10、S 类 ≥20），Wilson 区间估计失败率；修复版同理验证通过率显著上升。单次或 3 次的结论一律不算数。
  • 门禁（修正"pass^3 全绿"）：新旧版在同一案件上各跑 n 次，做 per-case 配对差值 + McNemar 翻转检验（只看翻绿/翻红案件，配对消掉案件难度噪声）；同时报告 pass@k 与 pass^k 两个口径，gap 作为 flakiness 指标持续监控。多案件不做逐案显著性检验（避免多重检验误报），关键案件按策略规则"一票否决"。
  • k 与 n 的确定：按 Miller 功效公式 n ≈ ((1.96+0.84)·σ/δ)² 由期望检测的效应量决定，不拍脑袋。
结论修正：随机性不能被"消除"，也不能被"3 次"采样消除，只能被冻结输入（提高复现概率）+ 足量重复（估准失败率）+ 配对比较（消掉案件难度与 judge 偏置）三层统计机制所"度量与约束"。门禁回答的问题从"这个版本过没过"改为"这个版本在此案件上的失败率是否显著下降、其他案件是否显著变差"。

维度现状预期

为什么这套方案成立：它没有发明新科学，而是把四个已被验证的机制按我们的架构缝隙拼装——tau-bench 的"程序化终态断言"解决"判什么"，CheckEval 的"checklist + 对照"解决"判不了怎么办"，SWE-bench 的"FAIL_TO_PASS / PASS_TO_PASS"解决"怎么算回归"，AgentLoop 的"消融通过才入库"解决"生成的测试可不可信"。而我们的 probe_reports 归因结构恰好已具备这一切需要的输入。

六、场景深化：四类对象的复现与回归难度与形态

前述管线在不同被测对象上难度不同，逐一看清"复现什么、回归什么"。

6.1 检视类 skill（误报/漏报）

先分清三个层次：病（"检视 skill 有误报漏报"，不可测试）、病例（"第 3 次会话把正常 try-except 报成缺陷"，可测试）、案件（冻结输入 + 判定标准，回归对象）。要点：

  • 每个 bad case 独立成案件、按病根组成案件组，不合并——误报组与漏报组是两个独立指标，合并会看不见此消彼长。
  • 检视类输入是代码（确定性），误报案件多为 D 类（确定性复现）；输出是结构化 findings 列表，L1 断言 = 集合比对（"findings 不得含 X"/"必须含 Y"）。
  • oracle 来源 = 归因报告本身：probe_analysis 里"该处符合规范、属误报"的确认结论与证据链，就是案件标签——归因时已付过人工确认成本，转化近乎免费。
  • 检视类专属陷阱（二维门禁的原因）：修复 prompt 时最经典失败是"改保守了——误报没了但漏报更多（学会装死）"。门禁必须二维：误报组不回升 + 漏报组检出率不降。若某病根只有单侧病例，标注"单侧验证"并借其他病根的常驻集补位。
  • L3 变换防两个方向作弊：换代码写法后"仍应检出"（防背答案）、"误报不应回来"（防文件名黑名单式假修复）。

6.2 超长程任务 skill（Superpowers / OpenSpec 类）

三个变化：错误暴露点离根因远（归因要找最早显著偏离点而非最晚出错点）；判定对象从单点变成"过程轨迹 + 中间产物"；中间有人工交互点。关键洞察与对策：

  • 过程类 skill 的典型 bad case 是"流程没走对"（跳过 TDD、没等批准就动手、没跑测试就宣称完成），而这类错误是事件流断言，可程序化检查——比结果质量好判。
  • OpenSpec 有免费 oracle：spec/tasks/验收标准在仓库里，验证器直接从 spec 编译（SpecFirst 结论：有显式 spec 的流程验证器生成成本最低）。
  • 验证器从单点断言升级为检查点链（C1 过程断言：测试文件创建早于实现修改；C2 产物断言；C3 终态断言；C4 rubric）。
  • 人工交互点提取为用户应答表（tau-bench user simulator 最小化），脚本按表应答；交互分支变体留给 L3。
  • 里程碑级重放控制成本：检查点产物落盘为中间工件，回归可从"卡住点之前的状态"起跑，不必全流程重放。
  • 按检查点分层统计：全程 pass^k 在长轨迹下低到不可用；"流程合规率"与"终态成功率"分开报，修复哪类病根看哪层。

6.3 链式方案：检视正报 → 上游工作流的 bad case（自增长数据源）

思路：Superpowers/OpenSpec 执行中调用检视 skill，检视的正报（真缺陷）直接当作上游工作流的 bad case——即把检视器当上游的外部验证器，用其输出当免标注 oracle。实证支持：

  • Silent Regressions（NeurIPS 2026 workshop，2750 条 SWE-bench 轨迹）：完成信号几乎无效（返回 patch 率仅差 1.2pp，实际解决率差 22.2pp）；agent 自己写测试自证无效；把验证预算花在外部提供的 FAIL_TO_PASS 测试上，带静默回归的补丁占比从 18.8% 降到 4.8%（随机选测试只降到 10%）——"验证器不能瞄准，跑多少都没用"，而检视正报天然有瞄准。方差 62–76% 在任务之间而非运行之间——按案件/任务簇组织回归集比按多跑几次更有效。
  • 验收闭环工程范式（生成与裁决分离）：任务契约（allowed_paths + 验证命令）、隔离 worktree、确定性门禁优先、模型复核非阻塞、验收测试防篡改（agent 不可写目录 / CI 注入隐藏测试）。

转化三步：

1
确认归属：正报只说明"代码有缺陷"，根因可能是上游流程漏环节、模型能力问题或检视口径问题——复用 probe_reports 归因层判定，决定案件挂哪个回归集。
2
编译成案件：finding 是判断文本不是可执行资产。编译产物 = 冻结被检视代码段 + 任务上下文 + L1 断言（该缺陷复现断言，SWE-bench 语义的外部验证命令）+ L3 注入写法变体。
3
双回归集挂载（最大红利）：同一条正报同时进上游流程案件集（FAIL_TO_PASS：修复后这类缺陷不应再产出）与检视器案件集（PASS_TO_PASS：检视 skill 迭代后必须"仍然报出来"，防止升级时把能抓的缺陷抓丢）。零人工构造、双向夹板。
两个偏差要诚实面对：① 幸存者偏差——检视器报不出的缺陷永远进不了该数据集，靠漏报案件 + L3 泛化补位；② 正报 ≠ 免费午餐——每条仍需归属确认与断言编译，只是人工成本从"构造数据集"（天级）降到"确认+编译"（秒级）。

6.4 代码首次生成类（纯 S 类）

"复现那次特定的坏生成"这个目标应直接放弃：坏代码是模型能力 × 采样运气的产物，同输入同版本也会时好时坏。回归对象换成："同样输入契约下，产出坏代码的概率是多少，修复后降了多少"。代码生成的独特红利是产出物可执行——oracle 就是断言，不需要 judge（SWE-bench / SWE-Gym 全套形态照搬）。案件形态：任务契约（冻结需求 + allowed_paths + 环境快照）+ 从检视正报编译的 L1 断言集 + n≥20 次独立生成的断言通过率。预期通过率从 30%→85% 而非 100%——门禁回答"显著改善且其他簇不退化"，不要求全绿。

真正难的三点与对策：

难点说明对策
oracle 覆盖窄检视正报只是缺陷总体的一个采样；单输入案件只守住一个坑L3 输入变体扩成案件组；按能力簇（边界条件/错误处理/并发/注入安全）归组，门禁看簇级通过率——Silent Regressions"方差在任务间"的发现支持以任务簇为稳定观测单位
病可能修不动怎么改 prompt 通过率都在 30% 附近 → 不是 prompt 病，是模型能力边界案件的价值从"验收修复"扩展为"诊断病因"：区分流程病（好修）与能力病（换模型/加生成后自检/约束解码），为归因层 attribute_type 提供量化依据
组合空间爆炸案件永远只是真实输入空间的采样无银弹：靠检视正报链路持续供料（唯一能自动跟上真实分布的来源）+ 簇级看趋势而非绝对值
