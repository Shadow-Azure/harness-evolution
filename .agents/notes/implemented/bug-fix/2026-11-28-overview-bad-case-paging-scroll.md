# Agent Note: 总览 bad case 列表翻页保持阅读位置

Status: implemented

[English](2026-11-28-overview-bad-case-paging-scroll.en.md) | 中文

## Problem

总览页的 bad case 列表点击「下一页」时，首次进入未翻过的页会出现刷新感并跳到页面顶部；返回后再次进入已翻过的页则正常（[GitHub #670](https://github.com/Shadow-Azure/harness-evolution/issues/670)）。用户报告没有现场测量，因此这里用合成数据复现。

`BadCaseTable.vue` 的加载分支在 `loading` 时用 4 行骨架替换整张表和分页条；`useOverviewCases` 又以 `page` 为查询键，未访问页没有缓存，必然经过这段加载态。合成 20 条 bad case（每页 8 条，共 3 页）、1500×837 视口，先把列表滚到底部：点击下一页前 `scrollTop` 461、内容高 1242；加载期间表格与分页条消失，骨架只剩 984 的内容高，浏览器把 `scrollTop` 夹到 203。视口更矮或内容更短时内容高度低于一屏，夹紧结果就是 0，即页面顶部。已访问页有缓存，数据同步就绪，不经过这段收缩，所以不复现。

## Decision

查询层：`useOverviewCases` 增加 `placeholderData`，在同一工作空间内把上一有效列表结果保留到新查询返回；占位数据用查询键里的 `workspaceId` 校验，切换空间时不显示其它空间的数据。这与 `08 §6.2` 已写明的「把上一有效结果保留到新查询返回」一致。

组件层：`BadCaseTable` 只在「首次加载且没有任何行」时显示骨架；已有数据时翻页或改筛选继续渲染旧行，列表根节点标记 `aria-busy`，并在分页条信息里追加「加载中…」提示。分页条在加载期间保持可见与可操作，方便快速连续翻页。数据层仍按 URL `page` 与查询键隔离页数据，晚到的旧页响应只写回自己的缓存键，不会覆盖当前页。

## Alternatives considered

- **加载期间禁用分页按钮**：能让当前页停在原地，但用户无法快速连续翻页，且分页控件在请求期间变得不可操作；拒绝。
- **给列表写死最小高度**：能为当前页保留空间，但末页不足一页时会留下一大片空白，且只掩盖高度收缩，不解决加载态替换整张表的问题；拒绝。
- **请求完成后恢复 `scrollTop`**：能抹平观感，但用户可能在加载期间滚到别处，恢复会抢走滚动控制，也把「加载态移除内容」的根因留在原地；拒绝。
- **骨架用绝对定位覆盖旧表**：需要额外定位与遮罩，仍会暂时遮住可读的旧数据，复杂度高于保留旧行；拒绝。

## Consequences

- 首次访问与缓存命中两条翻页路径都保持列表滚动位置；加载期间旧行、分页条与页码保持可见，不再出现整页刷新感。
- 末页不足一页时列表会按真实行数变矮，浏览器可能把 `scrollTop` 夹紧一段，但不会跳回顶部；不用虚假空白撑高。
- 请求失败仍以块级错误态替换列表，重试成功后恢复；失败页没有可保留的当前页数据，该路径不承诺保持行内容。
- 不改 API、契约、排序、分页大小或服务端缓存，也不改变总览其余区块与工作空间壳层的滚动归属。
