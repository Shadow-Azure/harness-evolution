# Agent Note: 归因置信度改为证据完整度规则分

Status: implemented

[English](2026-11-22-attribution-rule-confidence.en.md) | 中文

## Problem

归因写入时的 case 级置信度是引擎里的三个常量（自报 0.8、对象之后发现 0.6、非目标 0.7），不代表证据强弱：同一份证据确实同分，但分数与「这条结论有多少直接证据」无关，步骤 4 的置信度无法解释，也无法给后续低置信门槛提供依据。[#491](https://github.com/Shadow-Azure/harness-evolution/issues/491) 与设计 [07 §5.5.2](../../../../plans/fullstack-design/07-backend-implementation.md) 决定 case 级置信度不上模型，改为规则可判定的证据完整度；模型评分只放在聚类后的簇级。

## Decision

- 三信号计票：时间序可比（`order=comparable`）、失败签名匹配（bad case 声明的对象身份与归因对象一致）、版本直证（bad case 声明的版本或 revision 命中 run 解析出的 revision 身份或其裸 body hash）。
- 区间：三票 0.9；两票 0.8；一票 0.5；零票 0.3；版本直证但对象身份不一致视为信号矛盾，0.2。
- 非目标结论的置信度取证据完整度的补数：归因证据越充分，「非该对象问题」越不确定；因此顺序未知但对象与版本都命中的 case 为 0.2，完全没有信号时为 0.7。
- 信号只取已持久化、重试仍能重建的数据：`order_state` 来自候选快照，对象身份与版本来自 `bad_cases` 行，目标身份与 revision 来自 run；不新增表列、不改 cache key、不改 API 字段，引擎名仍是 `rule-v1`。
- 版本直证只认解析后的 revision（`tag:` / `digest:` / `provider:`），不认 run 的选版本：选版本不在缓存键里，把它纳入信号会让同一缓存键在不同选版本下得到不同分数却仍共用缓存。
- 「低置信不入簇」只落两个常量（开关 `False`、阈值 0.5），本 issue 不接线；启用时需要同时改聚类输入查询。

## Alternatives considered

- **逐 case 模型置信度**：与归因缓存天然契合，但单条盲评丢掉跨 case 佐证且成本 O(N)，被 #487 否决；簇级直评留给 bugfix-19。
- **用 matcher 的 session 级版本匹配作为版本直证**：session 关联本身就要求版本命中，信号会恒真而无法区分 case；且 prepare 重试不重跑 matcher，只重读候选与证据，会破坏「同证据同分」。
- **用历史 case 的失败签名做「对象已知失败签名」**：需要新增跨 case 查询与新的持久面，超出本 issue 只改写入路径置信度产出的边界；先把失败签名定义为 bad case 声明的对象身份，后续要更细的错误指纹可在同一信号函数内扩展。
- **非目标沿用固定 0.7**：与「置信度即对结论的把握」冲突，同样不可解释；改为补数后语义一致。

## Consequences

- 步骤 4 新产生的归因行置信度从常量变为 0.1–0.9 的规则值；历史缓存行保留旧值，不做回填（缓存键未变）。
- 失败签名目前是对象身份，不是错误文本指纹；跨对象但版本相同的 case 会落到矛盾带（0.2），这是有意的保守取值。
- 低置信门槛仍是关闭常量，当前没有消费方；这是设计留下的开关位，不是本 issue 的缺陷。
- 单测矩阵钉住 0/1/2/3 票与矛盾信号；引擎与 runner 各有一条集成断言。
