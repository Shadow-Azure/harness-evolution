# Agent Note: edit unifies the insert_after anchor contract as cross-line text blocks

Status: implemented

English | [中文](2026-11-25-edit-insert-anchor-multiline.md)

## Problem

The production full run `01M885592456VVK5B68DSMRKTE` failed at turn 3/10 of step 6/7 ("iterative optimization") in the patch stage: `claude-code edit submission failed validation`. The submission file had been parsed normally (`submissionParsedBy=json5`, `submissionParseFailures=0`), but `EditPlan.model_validate()` rejected edit 7 (0-based `edits.6`), an `insert_after`, with `target must be a single-line substring`. That target was the 4-line text block of the `### 验收与回归` template (158 characters), occurring exactly once in the target `SKILL.md` — the model did the right thing by the contract it was told (prompt and derived schema only say "anchor text must exist and be unique"), while the validator enforced a stricter, unpublished rule that contradicts design doc 07 §5.5.4. Edit is a single call with no retry on validation failure, so this hidden rule living only in the validator killed the whole turn; edits 1 and 2 on the same release succeeded, showing this was model output variance hitting a contract mismatch, not a deployment regression.

## Decision

The `insert_after` anchor contract is unified as "a text fragment that exists exactly once in the file and may span lines". On the model side, `EditOp._validate_op_fields()` no longer rejects targets containing `\n`/`\r` (the single-line rule introduced in #494); all other constraints (append forbids target, delete forbids content, non-blank and line-capped content, etc.) stay as they are. On the applier side, `_insert_after_text()` is rewritten as "match the unique whole fragment, insert after the block's last line": the insertion point sits after a trailing newline of the target itself (`\r\n`/`\n`/`\r`), otherwise after the next line terminator of the line holding the matched block's final character, or a synthesized `\n` at EOF; inserted lines reuse that terminator's style (`\r\n` stays `\r\n`; a bare-`\r` anchor line keeps its bytes and inserts with `\n`). The `text.count(target)` branches stay untouched — 0 occurrences → `skipped_anchor_missing`, more than 1 → `error` (ambiguous) — with uniqueness counted as non-overlapping matches (the semantics `replace`/`delete` already use). An unterminated final line is the end of the file, so the insertion point is EOF and no text between the match and EOF is dropped. Single-line targets reproduce the old output byte for byte in `\n`, `\r\n`, and bare-`\r`-only files; mixed bare-`\r`/`\n` files and the extra Unicode line separators (`\v`, `\f`, `\x85`, `\u2028`, ...) that the old `splitlines` folded are outside that promise. The contract also enters the model-visible surface: `_edit_prompt()`'s anchor line becomes "anchor text must be a fragment that occurs exactly once in the file and may span lines; insert_after inserts content after that fragment's last line", with 07 §5.5.4's execution bullet and json5 example comment updated to match. Regression tests cover validation and application of a 4-line block anchor, single-line byte-for-byte cases (mid-line / line-end / EOF without terminator / bare-`\r` / CRLF), missing and ambiguous block anchors, CRLF block insertion, and a synthetic replay of a production-shaped 8-edit plan (no production text).

## Alternatives considered

- **Add a field-level feedback retry for edit**: analyze has the `feedback_prompt()` retry, edit does not; adding one would change `edit_workspace()`'s single-call semantics and the run state machine, a cost far beyond this defect's surface — and the correct contract should not be hidden inside a validator in the first place. Rejected.
- **Explain "target must not contain newlines" in the prompt**: publishing the hidden rule instead of removing it. A multi-line block is a natural, unique, legitimate anchor choice for the model; suppressing it via prompt only pushes toward more fragile workarounds while the contract keeps contradicting 07 §5.5.4. Rejected.
- **Allow multiple anchors (take the first match)**: it breaks the deterministic "anchor exists and is unique" contract held since #494; the result would depend on match order and resist audit. Rejected; the uniqueness check stays untouched, and a cross-line target does not bypass it.
- **Only fix observability (pass `AgentProviderError.detail` through `ConfigError`)**: the run page could then show `edits.6`'s field-level cause, but "a valid plan gets rejected" remains unfixed; the observability gap is recorded as debt instead of widening this change. Rejected.

## Consequences

- A production-shaped plan (8 edits, a 4-line block anchor, per-edit content ≤ 28 lines) now passes `EditPlan.model_validate()`, applies all edits to the target file only, and leaves single-line `insert_after` unchanged — the four-op exact-content test and `test_insert_after_last_line_without_newline` keep their byte-for-byte assertions.
- Conditional constraints a schema cannot express must go into the prompt: a derived JSON Schema cannot state "when one field takes value X, another must look like Y", so the Pydantic validator is the only enforcement point and the caller's prompt must state every semantic constraint as a positive contract — otherwise a "rule that lives only in the validator" gap reappears.
- The observability gap where the `ConfigError` conversion drops `AgentProviderError.detail` remains: `_fail_patch_generation()` only receives `str(error)`, so the run page and job show a generic message and the field-level cause must be reproduced from the leftover `edits.json5`; fixing it is a separate small change, out of scope here.
- The three anchored ops (`replace`/`insert_after`/`delete`) now share one anchor semantic: a unique whole-text substring match, with no single-line special case in `insert_after`; a multi-line anchor turned from "illegal" into "a legitimate anchor", while bad plans still fail before any write and application stays deterministic and replayable.
