# Agent Note: Job execution and SSE replay boundary

Status: implemented

English | [中文](2026-10-25-jobs-sse.md)

## Problem

M1 needs durable job state, serial in-process execution, restart recovery, and page-level notifications, while the parent table and business write lifecycle for `evolution_run_events` belong to m5-08.

## Decision

`job_runs` is the task source of truth. `JobRunner` serializes execution with a global lock and preserves queued/running/terminal audit rows; startup reschedules durable queued rows, marks residual running jobs interrupted, and only sync retains that audit row before being queued again. Every prepare/advance/apply/finalize/retry stage for one run shares one active-stage constraint and conflicts with `RUN_BUSY`. The EventBus gives each connection one queue capped at 100 items; overflow evicts the oldest `run.progress`, while a queue containing only critical events closes the slow connection so reconnect replay can restore history. An M1 ticket authorizes exactly one `run:{rid}` because browser reconnect carries one integer `Last-Event-ID`; multiple topics require a future per-topic compound-cursor contract. SSE pages `seq > cursor` through an injectable `RunEventReplay` boundary before switching to live events; subscriptions precede replay, and cursor filtering removes handoff duplicates. Restart and graceful-shutdown interruptions both pass through `RunEventRecorder` to persist a legal stage and job ID before notification. Migration `0003` creates the authoritative event projection, and `SqlRunEventStore` provides SQL replay and recording; m5-08 creates the evolution parent and adds relationships and resource authorization.

## Alternatives considered

Requiring an absent evolution parent would prevent the M1 job foundation from migrating independently, so the event projection lands with its authoritative columns while m5 owns the parent, relationship constraints, and real resource authorization. Retaining all history in the EventBus would lose events across restarts and cannot satisfy `Last-Event-ID`. Allowing multiple topics would force one integer cursor to represent several sequences and silently skip history, so M1 rejects multi-topic tickets and leaves compound cursors to a later contract.

## Consequences

The SQL store can page replay and record interruptions after migration, and explicitly exposes empty history when a deployment has no event table rather than inventing events. M1's topic authorizer is an injection seam only; m5-08 must enforce run existence and completion state. The `evolution_run_events.run_id` foreign key is added after the parent table exists. A slow connection still receives already-queued critical terminal events before closing and reconnecting for persisted replay; revocation and tickets remain process-local state, so multi-instance deployment requires shared storage first.
