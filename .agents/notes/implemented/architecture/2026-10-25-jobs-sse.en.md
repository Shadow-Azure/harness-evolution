# Agent Note: Job execution and SSE replay boundary

Status: implemented

English | [中文](2026-10-25-jobs-sse.md)

## Problem

M1 needs durable job state, serial in-process execution, restart recovery, and page-level notifications, while the parent table and business write lifecycle for `evolution_run_events` belong to m5-08.

## Decision

`job_runs` is the task source of truth. `JobRunner` serializes execution with a global lock and preserves queued/running/terminal audit rows; startup reschedules durable queued rows, marks residual running jobs interrupted, and only sync retains that audit row before being queued again. Every prepare/advance/apply/finalize/retry stage for one run shares one active-stage constraint and conflicts with `RUN_BUSY`. The EventBus gives each connection one bounded queue spanning its authorized topics, dropping the oldest notification instead of blocking producers. SSE pages `seq > cursor` through an injectable `RunEventReplay` boundary before switching to live events; subscriptions precede replay, and per-topic cursor filtering removes handoff duplicates. `RunEventRecorder` persists restart interruptions before notification. Migration `0003` creates the authoritative event projection, and `SqlRunEventStore` provides SQL replay and recording; m5-08 creates the evolution parent and adds relationships and resource authorization.

## Alternatives considered

Requiring an absent evolution parent would prevent the M1 job foundation from migrating independently, so the event projection lands with its authoritative columns while m5 owns the parent, relationship constraints, and real resource authorization. Retaining all history in the EventBus would lose events across restarts and cannot satisfy `Last-Event-ID`. A queue per topic would complicate ordering and cleanup for multi-topic connections, so each connection owns one queue.

## Consequences

The SQL store can page replay and record interruptions after migration, and explicitly exposes empty history when a deployment has no event table rather than inventing events. M1's topic authorizer is an injection seam only; m5-08 must enforce run existence and completion state. The `evolution_run_events.run_id` foreign key is added after the parent table exists. Revocation and tickets remain process-local state, so multi-instance deployment requires shared storage first.
