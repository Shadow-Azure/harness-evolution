# Agent Note: SkillOpt-style baseline gate and test-set final

Status: implemented

English | [中文](2026-11-25-baseline-gate-test-final.md)

## Problem

The real evaluation platform supplies measurements and metric directions, not an accept/reject verdict. HE previously trusted the gateway's `externalVerdict` for every turn, and its final evaluation only rolled per-turn validation scores into `init_score` and `best_score`. There was no "evaluate the initial version once as the baseline" and no independent held-out test-set acceptance. Under score noise a candidate could be accepted, and the final conclusion could not answer whether the final version is better than the initial one.

## Decision

Gateway `get_result` returns only an `EvalMeasurement` (primary metric value, metric direction and raw items). The decision lives in the service layer at `service/evolution/eval_gate.py`: turn N's baseline is the latest accepted turn's candidate score, or the run-level `validation_baseline` score when no turn has been accepted; a candidate is accepted only when it is strictly better than the baseline under the metric direction, and ties reject. Acceptance naturally advances the baseline to that turn's candidate score; rejection leaves both the run branch and the baseline untouched.

Run-level evaluations live in the new `evolution_evaluations` table with `kind` values `validation_baseline`, `test_baseline` and `test_final`, mirroring the turn evaluation columns. `evolution_advance` submits only the validation baseline before publishing turn 1; the test baseline and test final both wait for `evolution_finalize` after every turn is terminal, where they are concurrently in flight. `evolution_apply` returns "not applied" until the validation baseline completes and the poller re-enqueues it, never deciding early. After the last iteration terminates, `evolution_finalize` submits both test-set evaluations and only writes `evolution_finals` once both complete: `init_score` is the test-baseline score, `best_score` the test-final score, and `verdict` requires an accepted turn and a test-final score strictly better than the test baseline.

Without an accepted turn, `test_final` no longer falls back to `base_commit`. Finalization first creates an empty result commit on the run branch that changes no skill file, with `Harness-Run-Id`, `Harness-Verdict: no-acceptance`, the validation initial/best scores, metrics and per-turn decisions in its message; it is pushed and then used as the test-set final target. Its hash is stored in `evolution_runs.result_commit`, and retries reuse the same commit. The poller re-enqueues `evolution_finalize` only when neither test-set evaluation is in flight.

Platform errors distinguish retryability: 401/403/404/422 are final and enter `blocked(stage=eval)` with the platform error code; 5xx, 429 and network errors are retryable, so the poller only defers the next poll, still capped by the 2h timeout. A failed baseline or test final also takes `blocked(stage=eval)`; `/retry` clears the failed row and resubmits without rerunning accepted iterations.

The launch `asset_override` names the platform's runtime-generated asset path, not the HE target repository's source path. OpenSpec snapshots keep objects under `skills/`, `agents/` and `commands/`, while the platform publishes them under `.claude/skills/`, `.claude/agents/*.md` and `.claude/commands/` after `codespec init`; the gateway maps the target type through that layout and sends explicit `asset_types`, so the platform can infer the type and does not collide source and generated file maps.

## Alternatives considered

Keep the platform verdict: the platform contract does not provide one, and it would re-couple acceptance rules into every platform subclass. Store baselines on `evolution_rounds`: baselines and the final belong to no turn, and reusing the turn table would break the `(run_id, seq)` uniqueness and turn lifecycle. Decide as soon as the candidate result lands: an incomplete baseline would force a guessed score, treating observation timing as a conclusion. Enable baselines and final only on the real platform: fake mode would then take a different decision path from production and tests could not cover the real gate. Compute the test-set final from per-turn validation scores: it cannot answer the held-out test-set acceptance question. Keep the test baseline on the startup path: a cancelled run, a run with no accepted turn, or an early failure still consumes test-set capacity, and test-set failures get coupled into turn 1. Keep falling back to `base_commit` without an accepted turn: the final target is identical to the initial version, so "the run produced no change" cannot be distinguished from "the final version is the initial version".

## Consequences

`evolution_finals.best_score` changes meaning from "highest per-turn validation score" to "test-set final score"; frontend fields stay the same but the value's semantics change, a direct consequence of the SkillOpt comparison. Run-level evaluation needs migration `0033` and dual-dialect repository coverage; the no-acceptance result commit needs migration `0036` for `evolution_runs.result_commit`. An old run submits baselines on its first advance or finalize after deployment, and already completed turns are unaffected. The test set now only appears at finalization, so the startup path no longer consumes platform capacity; `/retry` resubmits only failed test-set evaluations and never resets completed ones. The platform `partial` status is completed or failed against a 50% minimum-completion guard, and `paused_budget` fails immediately with actionable information. The per-turn idempotency key includes the attempt count, so a retry after a platform-side failure cannot replay the same evaluation.
