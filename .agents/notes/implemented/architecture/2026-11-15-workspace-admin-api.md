# Agent Note: 空间管理、成员与上报凭据 API

Status: implemented

[English](2026-11-15-workspace-admin-api.en.md) | 中文

## Problem

m7-03 给了每个业务请求空间门禁与 `auth/session` 聚合，但空间本身仍只能由迁移播种：没有创建、改额度、任命管理员的入口，也没有成员与上报凭据的生命周期。若把成员规则分散到路由，空间管理员“只能授 member/viewer、不能改 space_admin 行、不能移除最后一个空间管理员”三条边界会各写一遍；凭据若在列表响应或数据库里出现明文，泄漏面就不止一个端点。

## Decision

- `WorkspaceService` 独占管理规则，路由只做鉴权与 DTO 转换：创建空间要求至少一个已存在的初始空间管理员；`PUT` 对空间管理员只开放 `quota`，改 `name/mark` 返回 `403 WORKSPACE_FORBIDDEN`；额度低于实时 `used` 返回 `422 QUOTA_INVALID` 并携带 `{quota, used}`。
- 成员写操作要求 `space_admin` 及以上。空间管理员授 `space_admin` 返回 `403`；修改或移除已有 `space_admin` 行、以及移除/降级最后一个空间管理员返回 `409 ROLE_LOCKED`。全局管理员可任命/撤销空间管理员，但不能让空间失去最后一个管理员。“自任空间管理员”仅全局管理员可调用，并写入真实成员行。
- 成员候选搜索在服务端按用户名/显示名匹配、排除已有成员、限制 `limit ≤ 20`；空查询直接返回空页，不把全局用户目录当默认列表下发。
- 凭据使用 `whk_` + 32 字节随机串，库里只存 SHA-256 十六进制与 12 字符前缀；明文只在创建响应返回一次，列表只给 `id/prefix/createdAt/lastUsedAt/revokedAt`。每个空间最多 3 条有效凭据；撤销是幂等置 `revoked_at`，撤销后哈希查询不再命中。
- `POST /api/workspaces` 仍是全局管理员专属，但中间件用“精确路径”规则而不是前缀规则，否则同一前缀下的成员与凭据 POST 也会被误伤。

## Alternatives considered

- **把成员规则下放给路由**：每个端点都要重复角色判断与 404/403 语义；集中到 service 后测试只覆盖一张权限矩阵。
- **空间管理员也能改空间名/说明**：设计只允许空间管理员调额度；放开会让空间标识与审计归属漂移。
- **凭据明文存库或列表回显**：轮换窗口方便，但数据库或响应一旦泄漏就是长期可用的上报凭据；拒绝。
- **候选搜索直接在浏览器加载全局用户表**：会向空间管理员暴露全局用户目录；改为服务端搜索并排除成员。
- **用前缀规则拦截 `POST /api/workspaces`**：路径前缀会连成员、凭据、自任管理员一起变成全局管理员专属；改为精确匹配。

## Consequences

- m7-06/m7-07 的空间读写路由直接复用 `require_workspace_role`；成员变更下一次请求立即生效。
- 凭据认证接缝 `verify_credential` 已按哈希与撤销状态实现，m8-01 的上报端点只消费它，不再重复解析。
- 空间创建、成员与凭据写操作各多一次读后写；并发下“最后管理员”与“3 条有效凭据”仍存在窄窗口，后续如需强一致要在事务里锁空间行。
- 凭据 `last_used_at` 的 60 秒节流更新属于上报路径，本轮只保留字段。
