# Agent Note: workspace bad-case overview aggregation API

Status: implemented

English | [中文](2026-11-16-workspace-overview-api.md)

## Problem

m8-01 let workspace credentials report bad cases into `bad_cases`, and m8-02 let the workspace Session list read through a workspace projection. The workspace overview page needs neither a single session nor a single case: it needs "how many bad cases this workspace produced in a window, which objects they came from, how they spread over time, and a filtered paged list". Those numbers must be comparable within one request: the strip, the trend, the source distribution, and the list must agree on the same window, or a page that says "6 bad cases, 5 trend bars, 7 list rows" is impossible to debug. They must also count only the workspace in the path — bad cases are written by external reports, so a cross-workspace leak is a security incident, not a display bug.

## Decision

- Add four read-only endpoints, all behind `require_workspace_role(wid, "viewer")` and all pinned to the path workspace: `GET /api/workspaces/{wid}/overview/summary`, `/overview/trend`, `/overview/sources`, and `GET /api/workspaces/{wid}/bad-cases`. An invisible or missing workspace keeps answering `404 WORKSPACE_NOT_FOUND` (anti-enumeration), matching the m7/m8 read paths.
- The window is an **inclusive local-date range**: both `from` and `to` are used as given, and a leftover `range` is then ignored and **not validated** (`from/to/range=0` is legal); without either boundary, `range` (default 90, only 7/30/90) yields `[today-range+1, today]`; a single boundary requires an explicit `range`, anchors the window, and derives the other side from the range (`from=X&range=7` → `[X, X+6]`, `to=Y&range=7` → `[Y-6, Y]`). That keeps "window length == range" true on every entry point and removes the ambiguity of "from plus range but still ending today". `from > to`, a single boundary without `range`, a span over 366 days, a `range` that participates in deriving a boundary but is outside 7/30/90, or a boundary outside `1970-01-01..2999-12-31` (including `date ± timedelta` overflow) answer `422 WINDOW_INVALID` rather than 500.
- `grain` is declared as `Literal["day","week","month"]` in the route signature, so OpenAPI publishes the allowed values and generated TS clients get the union. FastAPI validates it before the handler, and a route wrapper maps a `grain` `RequestValidationError` back to the dedicated `422 GRAIN_INVALID`, so an invalid value never becomes generic `VALIDATION_INVALID`. `range` keeps `int|None` validation because an explicit boundary pair must accept any ignored leftover value; its OpenAPI schema declares `7/30/90` through `json_schema_extra`.
- Boundaries and buckets are Asia/Shanghai: SQL expresses the inclusive date range as `created_at >= start 00:00+08` and `created_at < (end+1) 00:00+08`, so a `00:30+08` report belongs to that day and never to the previous UTC day. A day bucket is the local day; a week bucket starts on the ISO Monday and may precede the window start; a month bucket starts on the 1st. The trend returns only buckets intersecting the window and **fills zeros** — a day/week/month without cases still appears with zero counters.
- `grain=day` downgrades to `week` when the inclusive span exceeds 92 days (93 downgrades, 92 stays daily), and the response carries a `grain` field that reports the **effective** grain, so the client never re-derives the downgrade rule. `week` and `month` never downgrade.
- Bucketing happens in Python: SQL only selects `(created_at, bad_case_type)` inside the window (capped at 366 days, row count bounded by workspace quota) and `window.py` maps each row to its bucket. That keeps "Monday start", "first of month", and zero filling in one implementation that unit-tests without a database; putting `strftime`/`date_trunc` in SQL would duplicate the same rules per dialect.
- `summary` counts: `badCases` = rows in the window, `self`/`discovery` = the two type counts in the window, `sessions` = `COUNT(DISTINCT bad_case_session_id)` in the window, `sources` = `COUNT(DISTINCT object_name)` in the window. Both type counts and both distinct counts come from one aggregate row so the predicate set is written once.
- Every overview read path shares one `bad_case_type IN ('self','discovery')` predicate: the legacy catalog sync can store a type outside the report contract (the writer only enforces column length), and those rows are excluded from `badCases/self/discovery/sessions/sources/objects` and the trend while still counting toward the workspace-wide `used`. That keeps `badCases = self + discovery`, the trend total, and the list `total` consistent and stops one malformed row from turning the list into a 500.
- `sessions` counts **reported roots** in the window, including pending roots with no normalized trace: the overview answers "how many sessions had a reported problem in this period", not "how many can be opened". It is not 06 §7.5's workspace Session set (the `session_families` join) and not the Session page's `total`, and it is not additive with `pendingSessions`; those three definitions live in 06 §7.5, 05 §3.10/§4.18, and the OpenAPI field description.
- `quota`/`used` are workspace-wide with **no window and no object/type filter**: `quota` reads `workspaces.quota`, `used` counts that workspace's `bad_cases`. Quota is the credential-report admission limit, so the overview must show real occupancy (which the legacy catalog sync can push past `quota`) rather than the window count; out-of-contract types count only here.
- The `objects` option list is the distinct `object_name` in the window **ignoring the `objects` filter** (otherwise selected options would disappear and could not be re-selected), ordered by `lower(object_name)`; the case-insensitive alphabetical order is exactly `deep-research / Explore / workflow` in the design example.
- `sources` has one row per object with `total`, `self`, `discovery`, and `sessions` (distinct roots for that object), ordered `total DESC, object ASC`; the name tie-break keeps pages and assertions independent of implicit row order.
- List parameters: `from/to`/`range`, `objects`, `badCaseType` (`all|self|discovery`, default `all`), `page` (>= 1, default 1), `pageSize` (1..50, default 8). `objects` accepts repeated parameters and comma-separated values: both forms are split on commas, trimmed, emptied parts dropped, and deduplicated by first occurrence; an empty selection adds no object predicate, and only more than 50 names **after dedupe** raise `422 OBJECT_FILTER_TOO_LARGE` (so `?objects=a&objects=a,a` is legal).
- The list order is fixed at `created_at DESC, bad_case_id ASC`, so several reports in the same millisecond still sort deterministically. `total` shares the page predicates and `page`/`pageSize` only bound `items`.
- `attributionCount` counts **distinct `(probe_type, probe_object, object_version)` triples** reached through `bad_case_analysis JOIN probe_reports`, computed once for the current page's case ids. Today `bad_case_analysis` is unique per `bad_case_id`, so the real value is only 0 or 1, but the query is shaped as "distinct triples then group by case" so m10's one-to-many schema needs no code change. SQLite lacks `COUNT(DISTINCT a, b, c)` and the MySQL dialect must not leak into the repository, so a distinct subquery plus an outer `COUNT(*)` serves both dialects with one statement.
- `badCaseTypeLabel` comes from the server (`self → 自身存在问题`, `discovery → 发现前置步骤问题`) as in the 05 §3.10 DTO, so the list never re-derives the label per rendering language.
- `triggerAt` temporarily equals `createdAt`: object trigger coordinates arrive in m9-04, so this issue invents no schema field and does not join `agents`/`agent_events` to guess a trigger time. The field exists per the contract, the 05 §3.10 example, its OpenAPI description, and this note all state the temporary equivalence, so the client never treats it as a real trigger instant.
- External-table probes are cached per repository instance: only a **first probe** that finds the table missing degrades — without `bad_cases` the summary is all zeros (`quota` still comes from the workspace row), `objects` is empty, the trend has only zero buckets, and sources/list are empty; without `bad_case_analysis` or `probe_reports` the list still works and only `attributionCount` becomes 0. Because the cache is process-wide, a table created or dropped at runtime is not re-probed: the overview may keep returning zeros/empties, or raise a database error on the next query, until the process restarts. This mirrors m8-02's `_scoped_reads_available` and is not a promise that no 500 can ever happen.
- `main.py` only gains one composition-root wiring line and one router registration; `errors.py` only gains `WINDOW_INVALID`, `GRAIN_INVALID`, and `OBJECT_FILTER_TOO_LARGE`. Contracts come from `pnpm contract:generate` (`packages/contracts/openapi.json` and `api.d.ts`), and `test_openapi.py` pins parameter names, defaults, enums, and error codes.
- 05 §3.10/§4.18 and 06 §7.5 record the window and list parameters (including `range` being ignored with explicit boundaries, the default 90, and `pageSize` 1..50), bucket label formats, the reported-root `sessions` definition, the temporary `triggerAt` equivalence, the canonical `attributionCount` definition, and the out-of-contract `bad_case_type` exclusion.

## Alternatives considered

- **Conditional counts with `FILTER (WHERE …)`**: rejected. SQLite 3.30+ supports it and MySQL does not, which would drag dialect branching into the repository; `SUM(CASE WHEN … THEN 1 ELSE 0 END)` runs on both.
- **Split the summary into four `COUNT` queries**: rejected. Four queries would each repeat the window/object predicates, and one missed edit would make the strip internally inconsistent; one aggregate row yields both type counts and both distinct counts.
- **Generate the bucket series in SQL (recursive CTE / `date_trunc`)**: rejected. Monday starts, first-of-month, the downgrade threshold, and zero filling all differ between SQLite date functions and MySQL `DATE_FORMAT`, and are not fully equivalent; the pure Python functions hold one implementation and unit-test the 92/93 boundary, leap day, and year rollover.
- **Count only normalized roots in `sessions` (JOIN `session_families`)**: rejected. The overview answers "how many reported sessions had a problem in this period", and pending roots are still incidents in the workspace; filtering by join would make "6 reports, 4 sessions" look like data loss. Pending sync has its own metric on the Session page.
- **Window `quota`/`used`**: rejected. Quota is workspace admission state; letting it follow the window would make "quota 60, used 3" jump with filters and could not explain a 409 rejection.
- **Let object options follow the `objects` filter**: rejected. Unselected objects would vanish from the dropdown and could not be re-selected; options describe "which objects exist in this window", independent of the current selection.
- **Order tied `sources` by name descending or by database row order**: rejected. Paging and assertions would drift with the plan; a fixed `total DESC, object ASC` is reproducible.
- **Accept only repeated `objects` parameters**: rejected. Frontend URLs and curl debugging both write `?objects=a,b`; accepting both costs one split and unifies trimming and dedupe.
- **Truncate past 50 objects**: rejected. Silent truncation returns a subset the user did not select and looks like a broken filter; `422 OBJECT_FILTER_TOO_LARGE` tells the caller to narrow the selection.
- **Write `COUNT(DISTINCT probe_type, probe_object, object_version)` directly**: rejected. MySQL supports it and SQLite does not; a distinct subquery is equivalent on both and survives m10's one-to-many change.
- **Return `triggerAt` as `null` or join trigger points now**: rejected. `null` forces the client to branch on a field that is supposed to exist, and joining `agents`/`agent_events` to guess a trigger instant would pre-empt m9-04's coordinate semantics. Returning `created_at` with an explicit temporary-equivalence statement is more honest than a pretending guess.
- **Express the object ceiling as a FastAPI constraint like `pageSize`**: rejected. The count must be computed after dedupe (repeated parameters must not trip the limit), which requires custom validation and therefore the documented dedicated code instead of generic `VALIDATION_INVALID`.
- **Reuse the problems module's `BadCaseListResponse`**: rejected. The session-scoped problem list is `{items:[BadCase]}` without pagination while the overview list is `{items,total,page,pageSize}`; sharing the name makes OpenAPI emit the module-qualified `app__service__overview__schemas__BadCaseListResponse`. `OverviewBadCaseListResponse` is the envelope, and `BadCaseListItem` keeps the 05 §3.10 name.

## Consequences

- One overview first paint issues four requests: summary (one aggregate + one quota pair + one object-option query), trend (one windowed row query plus Python bucketing), sources (one grouped aggregate), and list (one count + one page + 0/1 attribution count). All read through `ix_bad_cases_workspace_created` / `ix_bad_cases_workspace_object` / `ix_bad_cases_workspace_type`, bounded by the workspace's case count.
- The response is not a snapshot: the four endpoints open their own read sessions, so a case reported between two calls can be present in the summary and absent from the list for milliseconds. Same tradeoff as m8-02's list/counter split; reads dominate writes and this issue adds no snapshot or transactional consistency layer.
- `sessions` includes pending roots and is not the same set as the Session page's `pendingSessions` or `total`; page copy must not add the three together. This is a deliberate split of definitions, recorded in 06 §7.5, 05 §3.10/§4.18, and the OpenAPI description.
- `used` can exceed `quota` (the legacy catalog sync may push past it) and can exceed the windowed `badCases`; the client must not assume `used <= badCases`.
- `attributionCount` can only be 0 or 1 today (one analysis row per case). Tests cover 0, 1, and an `object_version IS NULL` triple; the distinct-triple dedupe path cannot be falsified by an integration test until m10 relaxes `uq_bad_case_analysis_case` (a fixture with two probes on one case cannot be built yet), so the current guarantee is that the SQL shape is ready. m10 must add the reverse case: one case with two probes sharing a triple counts once.
- `triggerAt == createdAt` is a transition fact: once m9-04 adds object trigger coordinates the same field starts returning a real trigger time and stops matching `createdAt`; the client must not use it as a sort key or equality basis.
- The list pages with `OFFSET`, which degrades linearly on very deep pages; workspace quota (tens to hundreds of cases) makes this a non-issue, and keyset paging can replace it if a workspace ever grows past ten thousand rows.
- Table-presence probes are cached per repository instance, so creating or dropping a table at runtime needs a process restart before it is noticed, matching the existing Session read path; only a missing table at first probe degrades, and dropping a table at runtime can raise a database error, so there is no absolute "no 500s" guarantee.
- MySQL is verified by CI's mysql lane, which runs the `@pytest.mark.mysql` cases in `test_database.py`; a new overview repository case covers `SUM(CASE)`, `COUNT(DISTINCT)`, and the distinct subquery through summary/trend/sources/list. Without a local MySQL service that case is skipped, and only SQLite ran locally.
- This issue excludes the target view (`/overview/targets*`), chart components, and the frontend page, and adds no migration; those land in m11, m8-04, and follow-up issues.
