# Agent Note: 自进化真实模型化的四项结构性取舍

Status: implemented

[English](2026-11-22-evolution-real-ai-design.en.md) | 中文

## Problem

自进化的聚类、置信度、严重度与 patch 生成是占位实现（词面聚类、固定置信度、常量公式、placeholder patch），要接入真实模型能力时必须在四个结构问题上做决定：模型出站调用收口在哪；聚类的模型介入放在哪一层、如何随归因报告量扩展；结构化 JSON 结论如何可靠回收；编辑 patch 用什么表示。2026-11-22 的定稿设计（[07 §5.5.1–§5.5.4](../../../../plans/fullstack-design/07-backend-implementation.md)）锁定了四个答案，本文记录为什么以及放弃了什么。

## Decision

- **模型出站收口到 `third_party_api/ai_agent` 的父类接口**：`analyze` / `edit_workspace` 两个能力面 + 工厂按 `AI_AGENT_PROVIDER` 选择子类（当前仅 claude-code 与 fake）；接口按能力而非厂商划分，换后端只新增子类。它不是早期「统一 Provider 层」的复活——只服务模型出站一个接缝。
- **聚类分三层，LLM 输入输出与归因报告总量 N 解耦**：分组层 O(N) 无 LLM（lexical 首实现、向量化升级位）；审查层 O(K×s) 只做合并/命名（草稿键引用 + 草稿划分完整性硬闸）；评分层 O(K×s) 簇置信度直评 + 严重度维度分。case 级置信度保持规则信号不上模型——逐条盲评丢掉跨 case 佐证且成本 O(N)。
- **结构化回收走自建提交通道**：agent 写 `result.json5`（JSON5 宽松字面量），`submission.py` 确定性解析 + 校验 + 失败回喂重试；不依赖任何 CLI 内部机制（Claude Code 的 `--json-schema` 降为可选快路径，默认关）。「用 JS 生成 JSON」的价值被提炼为字面量容错 + 确定性序列化，且不执行模型代码。
- **patch 用 SkillOpt 式 Edit 指令**：agent 只读探索后提交 EditPlan（op/file/target/content/rationale），锚文本必须存在且唯一（多义回喂），`edits.py` 确定性应用，`git diff` 为唯一真值；`edit_budget` 双重执行（prompt 约束 + 硬截断）；`EditRequest` 带 `session_id`、`EditResult` 回传 `EditPlan`；评测 reject 即结束该轮，不做 round 级自动重试、`--resume` 反馈或 rejected-edit buffer（2026-11-23 决定）。agent 工具面收敛为只读 + 写一个 json5，无需文件编辑权限。

## Alternatives considered

- **逐 case 模型置信度（聚类前）**：与归因证据缓存天然契合，但单条盲评丢掉佐证效应、成本 O(N)；被「规则信号 + 簇级直评」取代，逐条模型分留作预算开关。
- **依赖 `--json-schema` 原生通道为主路径**：Claude Code 上免维护且可靠，但属于 CLI 内部机制，换 opencode 等后端时层 1 强度骤降且要重写回喂闭环；降为 env 开关的快路径。
- **agent 直改文件（agentic editing）收 diff**：复杂重构能力更强，但意图不可计数、需要 acceptEdits 权限面；目标对象是技能/配置文档，指令式主场，直改留作未来开关位。
- **让 agent 调 JS 脚本生成 JSON**：数据仍需以参数或文件形态由模型手写，或需执行模型代码；被「写宽松字面量 + 确定性解析」取代，脚本仅保留为内容计算工具的形态。

## Consequences

- 设计已落 `plans/fullstack-design`（07 §5.5.1–§5.5.4、04 目录树与接缝表），后续实现 issue 以其为设计依据；本文随实际落地同步状态与事实。
- 实现按阶段推进（骨架 → 聚类三层 → 可选向量化 → 指令式 patch），每步 env 可回退（fake / placeholder），最坏情况等于今天的行为。
- 新增纯 Python 依赖 `json5` 与 `json-repair`；`edit_workspace` 语义从「直接编辑」变为「提交计划 + 确定性应用」，round 内无试错循环，由 round 级迭代闭环补偿。
- 声明（EditPlan）与实际（git diff）的对照成为每 round 的审计信号；两者不一致即质量报警。
- 2026-11-22 骨架已落地（bugfix-15）：`ai_agent` 四模块、Settings 仅两个配置项、确定性的 `fake` 与 `claude-code` 占位；真实 CLI 子类与业务接入仍在后续 issue。
- 2026-11-22 提交通道已落地（bugfix-16）：`third_party_api/ai_agent/submission.py` 以一次性任务目录收货，唯一工具白名单为 `Write(./result.json5)`；解析顺序为严格 JSON → JSON5 → json-repair（仅兜底），结果交 Pydantic `model_validate`，失败文案经 `feedback_prompt` 回喂重试一轮。
- 2026-11-22 提交通道是当前默认且唯一路径：`HE_AI_AGENT_NATIVE_SCHEMA` / `--json-schema` 仅是设计文档中的可选快路径，刻意不实现，待真实需求出现再评估；`SubmissionOutcome.parsed_by` 与有界 `repair_log` 是层 5 的出处字段，记录由哪层解析、修复器改动过什么；结果文件名与工具白名单暂不参数化，`edits.json5` 的复用推迟到 bugfix-21（届时需要文件名/路径参数与后端特定工具覆盖）。
- 2026-11-23 EditPlan 机械层已落地（bugfix-20）：`third_party_api/ai_agent/edits.py` 以 Pydantic 定义四类 op 与跨字段校验（`EDIT_BUDGET=8`、单条 400 行、路径必须为规范相对 POSIX 路径、`.harness-evolution/**` 与 `.git/**` 拒绝），`apply_edit_plan` 按序重读文件并原子写盘；逐条 `applied / skipped_anchor_missing / error` 报告，单条错误记录后继续（原子替换保证文件停在上一次一致状态）。`PatchBundle.sha256` 在单文件时与 `Patch.sha256` 逐字节一致，多文件按排序后的 `(path, content)` 对哈希；`PatchSource.build_bundle()` 默认把旧 `build()/change_note()` 包成单文件 bundle，placeholder 与 minimal-config 行为不变。`agent-edit` 已注册为保留模式，工厂明确报 bugfix-21 未实现；workspace 的 `create_candidate_bundle` 按 bundle 多文件 add、默认排除 `.harness-evolution/**`，并回填 `git diff` 作为 `CandidateWorkspace.unified_diff`。
- 2026-11-23 聚类三层已接入 prepare（bugfix-19）：在词面分组之后先做一次 `analyze(task="cluster.review")`——输入是每草稿约 60 tokens 摘要 + 3–5 条按 case id 确定性抽取的代表样本 + 类型/成员数/签名重合/时间跨度统计，成员列表由代码持有、不进 prompt（N=200 与 N=50 同三草稿的 review prompt 等长）；输出用草稿键 `{"from": ["D1","D2"], "title": …}`，成员由代码按 `from` 展开，硬闸是草稿划分完整性（每个键恰好一次、无未知键、不跨类型合并），违反即整批降级回草稿。随后评分层恰好两次批量调用、覆盖全部最终簇（`C1..Cm`）：`cluster.score`（0–1 直评 + `evidence_refs` 只能引用同簇 prompt 样本 id）与 `severity.score`（overall 决策分 + 五个固定维度名 `impact/scope/reproducibility/evidence_directness/blast_radius` + CVSS 3.1 向量串）；两次调用相互隔离，任一失败按任务整体降级——所有簇置信度回 `TYPE_CONFIDENCE`、所有簇严重度回 `cluster_severity()`——每 run 恰好 3 次有界 analyze（审查 1 次 + 评分 2 次）且与簇数无关。公式分仍以 `severityFormula` 与决策分同列进 `clusters_created` payload 供对照，维度与向量留在审计 payload 而 DB 列仍只有 `confidence/severity/rank`（零迁移）。接入 agent 后算法标识固定 `hybrid-lexical-llm-v1`——该标识描述管线，不描述模型实际贡献了多少；降级不改标识，但每次降级把任务键写进 `clusters_created.payload.degraded`（没有降级时不写该键），所以全降级 run 可与模型参与的 run 区分。无 agent 时逐字节保持 `lexical-jaccard-v1`；每次调用记 `ai_agent_call`（task/provider/model/tokens/cost/latency/outcome/sessionId，level=info），每次降级记 `degraded`（level=warn，task/reason），两个事件类型沿用 `String(48)` 列。合并簇的 `signatureOverlap` 按合并后成员标题重算平均两两 Jaccard，仅在 evidence 缺失时回退草稿加权均值；prompt 标签 `reportedSpanDays` 明确跨度来自 `bad_cases.created_at`（上报时间）。`claude-code` 占位仍抛 `NotImplementedError`，三层各自降级后 run 照常完成，最坏情况等于词面路径。
- 2026-11-23 Claude Code 真实子类已落地（bugfix-17）：`third_party_api/ai_agent/claude_code.py` 以 `create_subprocess_exec` + `start_new_session=True` 调用 `claude --bare -p <prompt> --output-format json --permission-mode dontAsk --allowed-tools <派生写工具>`，analyze 追加 `--no-session-persistence` 且仅在 `~/.claude/settings.json` 存在时传 `--settings`，edit 保留会话并只允许写 `.harness-evolution/edits.json5`（只收货不应用，bugfix-21 接入）；超时/取消对进程组先 SIGINT、宽限 5 秒后 SIGKILL，退出码 143 与 `cancelled` 均归一为 `detail="cancelled"`、`retryable=False`；提交失败只做一次无状态反馈重试——重发原 prompt 加 `feedback_prompt` 的校验反馈、不带 `--resume`，因为真实 CLI 2.1.278 的 `--no-session-persistence` 明确写着会话「cannot be resumed」，实测对无持久化会话执行 `--resume` 退出 1 并报 `No conversation found with session ID`，所以 issue 字面要求的 `--resume` 不可行而「回喂一次」的设计意图保留；`total_cost_usd` / `usage` 与真实 CLI 的 camelCase `modelUsage`（条目内 `inputTokens`/`outputTokens`/`costUSD`）都映射进 `AgentUsage`，两种拼写都接受，有 per-model 明细时不再累加 aggregate，`model` 取 per-model 键（顶层 `model` 优先），避免 token 双计与模型身份丢失；`session_id` 缺失允许为空；health 以 10 秒超时的 `--version` 探测且绝不抛异常，成功时只报认证来源（`ANTHROPIC_API_KEY` / `apiKeyHelper`）或「no bare-mode auth configured」，从不读取或打印密钥值；特性探测只读 `system/init.capabilities` 并存入私有字段，不做版本号比较、不实现 `--json-schema` 快路径。`submission.prepare` 新增 `directory` / `filename` 覆盖：显式 workspace 不写 `schema.json`，把同一 Pydantic 派生 schema 内联进 prompt，唯一写工具由文件名派生；`SubmissionPrep.owned` 区分渠道铸造目录（`discard` 可删）与调用方目录（`discard` 为 no-op，避免对称 `finally` 删 workspace）；`schema_reference` 让重试文案在一次性目录指向 `./schema.json`、在显式目录指向「上方 prompt 内联的 schema」；结果路径在删除/读取前按 `Path.resolve()` 做目录内包含校验，符号链接不能把删除或读取带出提交目录；默认路径（一次性任务目录 + `result.json5` + `schema.json`）的输出保持逐字节不变。已知边界：stdout 无大小上限（`communicate` 先全量缓冲，运行时仅由进程超时约束）；opt-in 真实 CLI e2e 仍只覆盖 happy path（模型身份与 token 断言已收紧，反馈重试路径由单测覆盖，未引入独立 marker/lane）；edit 的迭代闭环仍待 #488——`EditRequest` 没有 `session_id`，`EditResult` 也不返回 plan，拒绝缓冲需要这两项先落地。`AI_AGENT_PROVIDER=claude-code` 现在产出真实子类，失败统一折叠为 `AgentProviderError`，诊断经 `sanitize_detail` 脱敏并限长。
- 2026-11-23 agent-edit patch source 已落地（bugfix-21）：`AgentEditPatchSource` 收取 `EditPlan`（`EditResult.plan` 回传意图），只把计划目标文件镜像到临时目录并在那里跑 `apply_edit_plan`，仓库字节在候选提交前从不被写脏——越界/失败编辑不会泄漏，因此不需要 `git checkout -- .` 回滚；计划一条都没应用即本轮失败，不做第二次模型调用。`publish` 改走 `build_bundle()` + `create_candidate_bundle`，单文件哈希与旧 `Patch.sha256` 逐字节一致，多文件按排序 `(path, content)` 哈希；round 的 `patch` JSON 新增 `files` / `intent` / `report`（保留单文件旧键），`candidate_committed` 事件落 intent、逐条 report 与有界 `unifiedDiff`（候选 commit 的真实 git diff）。`--max-turns` 常量 40 与超时一起约束单次调用；provider 可重试失败落 `blocked(stage=patch)`，不可重试失败终态失败。按维护者 2026-11-23 决定：评测 reject 即结束该轮，不做 round 级自动重试、`--resume` 反馈或 rejected-edit buffer，避免 round 生命周期与进度游标的跨模块改造；相关 issue 与设计文档已同步。
- 2026-11-23 观测与常驻文档收尾（bugfix-22）：`ai_agent_call` 统一由 `service/evolution/ai_observability.py` 生成 payload，新增 `totalTokens`（输入+输出）、`attempts`、`feedbackRetries` 与 `submissionParsedBy`/`submissionRepaired`/`submissionParseFailures`/`submissionValidationFailures`；三次 analyze 与 agent-edit 的每次出站调用（含失败）各记一条，提交文件解析失败率可从事件序列统计。新增 `docs/ai-agent.md` 记录出站层、提交通道与观测契约；`HE_PATCH_SOURCE_MODE` 的 `agent-edit` 通过配置校验可启动。
