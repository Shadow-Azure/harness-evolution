# Agent Note: Evolution-target overview aggregation API

Status: implemented

English | [中文](2026-11-17-target-overview-api.md)

## Problem

The workspace overview also needs an object-centric view: for each evolution target, which Sessions it appeared in, how many potential bad cases it owns, and how those potential cases split into "is this object", "not this object", and "unanalyzed". The frontend cannot assemble this from independent lists: the potential set must come from the same matcher as the wizard and runs, the three states must come from the same deduplicated attribution rows, the trend has to use attribution time for analyzed rows and report time for unanalyzed ones, and skill, agent, and knowledge revisions all have to work. A read path that forgets the workspace predicate leaks objects, cases, or attributions from another space.

## Decision

- Add four read-only endpoints, all behind `require_workspace_role(wid, "viewer")`: `GET /api/workspaces/{wid}/overview/targets`, `/targets/trend`, `/targets/cases`, and `/targets/{targetId}/detail`. Every query is pinned to the path workspace: targets come from that space's `evolution_targets`, cases from its `bad_cases`, and attributions must also match `probe_reports.workspace_id`. Missing or invisible spaces keep `404 WORKSPACE_NOT_FOUND`; missing, disabled, or foreign targets answer `404 TARGET_NOT_FOUND`.
- The window is the existing `service/overview/window.py` one: explicit `from`/`to` win, a single boundary needs `range`, no boundary defaults to the last 90 days, and `range` is validated only when it derives a boundary. Invalid/oversized/out-of-range dates answer `422 WINDOW_INVALID`; trend grain stays `day|week|month` with the >92-day day-to-week downgrade. The target endpoints also accept `range`, matching design 05 §4.18.
- Versions are not limited to `defaultRef`. The service reads every `agent_events.object_version`/`object_revision` for the target kind and name in the window's reported Sessions, strips a `tag:` prefix, deduplicates, adds the configured `defaultRef`, and sorts the result newest-first. Each version builds one `MatchCondition` and calls the shared `PotentialMatcher.associated_sessions` and `potential_cases`, so "potential matches the wizard/run" holds per `(target, version)`; the object-level `potential` is the sum of those version rows.
- One potential row is `(badCaseId, targetVersion)`, not a deduplicated case. The same case may appear under multiple versions of one target or under several targets; this follows 05 §3.10's one-attribution-per-version rule and the prototype note that one case may be potential for several targets. Object `potential = attributed + nonTarget + unanalyzed`, `evolvable = attributed + unanalyzed`, and the list sorts by `evolvable DESC, potential DESC, objectName ASC`. Detail exposes `distinctCases` separately.
- The three states read only `bad_case_analysis JOIN probe_reports`: `probe_type = target.objectType`, `probe_object = target.objectName`, the probe's `object_version` stripped of `tag:` equals the current version, and `conclusion ∈ {attributed, non_target}`. A case/version may have several historical conclusions (for example a legacy key and a V2 revision key); the newest by `updated_at DESC, probe_id DESC` wins. `attributed` maps to `attributed`, `non_target` to `nonTarget`, and no readable row to `unanalyzed`, so one row can never carry two states and an old non-target conclusion cannot double-count a newer attributed one. `category` is exposed only for attributed rows from the closed `model|prompt|error` set.
- Target trend buckets analyzed rows by the attribution's `created_at` and unanalyzed rows by `bad_cases.created_at`; `meta.bucketPolicy` returns that rule verbatim. The window itself filters by case report time, so an attribution created outside the requested window does not appear in a bucket. That is an inherent consequence of separate bucket times and is declared through `bucketPolicy`; attribution times are not clamped to the window edge.
- Target-list `sessions` is the union of the object's associated Sessions across versions; the summary's `sessions` sums those per-target counts, so a Session containing two targets counts once per target. Summary `potential` and state counts are likewise sums of object rows, not cross-object dedupes.
- The case list sorts by `createdAt DESC, badCaseId ASC, objectName, version, targetId` and defaults to 8 rows per page; the target list defaults to 5 and only the items page. `objects[]` filters the bad-case source `bad_cases.object_name`, `targets[]` filters target ids, `states[]` accepts only the closed three-state vocabulary, and empty selections mean all. After deduplication `targets[]` and `versions[]` allow at most 50 values; unknown states or oversized selections answer `422 VALIDATION_INVALID`.
- Detail version scope: explicit `versions[]` keeps the requested order and intersects with known versions (unknown values are ignored); otherwise `versionLimit` takes the newest N versions, `0` meaning all, restricted to `0|5|10|20`. `stats.versions` counts selected versions, `stats.sessions` unions the selected versions' associated Sessions (including associated Sessions with no potential case), `stats.potential` counts rows, and `stats.distinctCases` dedupes cases. `byVersion` zero-fills every selected version; `bySource` aggregates reported sources by total and distinct cases, sorted by total and then source.
- Knowledge shares the same coordinate as skill and agent: `kind=knowledge` events usually carry only `object_revision=digest:...`, version discovery keeps `digest:...`, and the matcher matches on revision; `probe_type=knowledge` attributions enter the same state math. There is no knowledge-specific branch.
- The read boundary is split: `db/crud/overview_targets.py` only performs batched fact queries (window cases with titles, object version events, attribution links), while `service/overview/targets.py` merges versions, calls the matcher, projects states, buckets, and pages. `main.py` only adds the composition-root wiring and `app.state.target_overview`; there is no migration, new error code, or frontend change.
- This issue adds no UI. The `TargetsOverview.vue`, TargetSideList, TargetDetailCard, and prototype-aligned visual work belong to m11-04; m11-03 delivers the API and contracts that the frontend will consume.

## Alternatives considered

- **Analyze only `defaultRef`**: simplest, but historical versions disappear from the object view and detail's `versions[]`/`byVersion` have no data source. Rejected in favor of evaluating each version actually observed in the trace.
- **Discover versions from remote git tags**: the overview would depend on network and each target repository's availability, so one page load could be taken down by a 422 or timeout. Trace events record what the space actually saw, so they are the first-version source; remote tags were rejected.
- **Reimplement potential matching in SQL**: that creates a second decision engine next to the wizard and runs, while the issue requires one source. Calling the shared `PotentialMatcher` per version is the accepted cost.
- **Deduplicate object potential by case**: `attributed + nonTarget + unanalyzed = potential` needs exactly one state per row. Cross-version dedupe would erase real differences such as "attributed for v1, unanalyzed for v2" and break trend/list agreement. Keep row counts and expose `distinctCases` separately.
- **Add all attribution rows for one case/version**: that would count an old conclusion and a new one as two states. Take the newest row so each potential row lands in exactly one state.
- **Clamp attribution times to the window edge**: it would make trend totals equal potential while lying about when analysis happened. Rejected; keep the real time and declare that out-of-window attributions are not bucketed.
- **Use `updated_at` as trend attribution time**: cache reuse refreshes `updated_at`, so the trend would drift with reuse counts. Use `created_at` for conclusion time and keep `updated_at` only for selecting the newest row per case/version.
- **Deduplicate summary Sessions across targets**: then a target's `sessions` would no longer match the summary when one Session contains several objects. The summary sums per-target counts to keep the per-object analysis explainable.
- **Apply target/state filters to the target list**: the list endpoint has no such parameters and its summary is workspace-wide. Filters apply only to trend, cases, and detail so the header numbers do not jump when the side selection changes.
- **Reuse the target list's version scope for detail**: the single-object card needs independent version and time filters, so explicit `versions[]` and `versionLimit` are parsed separately and the window is passed independently.

## Consequences

- The first target-overview load grows linearly with enabled objects times observed versions: each version runs one matcher pass (batched window cases, Session metadata, object events, agents, anchor events, cache keys), plus one version query and one attribution query per object. Current workspaces configure a small set of objects and each has single-digit versions. If a future space has dozens of objects and dozens of versions each, the matcher's window/metadata loading must be hoisted across versions or the target analysis must become an asynchronous snapshot.
- The list, trend, case list, and detail are four independent reads without a shared snapshot, so millisecond-level inconsistency is possible while a report or attribution is being written, consistent with the existing overview endpoints.
- The trend window filters by case report time while analyzed rows bucket by attribution creation time; rows attributed outside the window are absent from the trend. The frontend must not assume the trend sum equals `summary.potential`; `meta.bucketPolicy` is the single machine-readable statement of the difference.
- The same case counting under several objects/versions is intentional. Only detail's `distinctCases` dedupes cases; the page must not substitute `potential` for it or vice versa.
- Knowledge versions are displayed as raw `digest:...`, not human-friendly tags; the UI must render revision text and must not assume semantic versions.
- No new error code: missing targets reuse `TARGET_NOT_FOUND`, while filter/version-limit failures reuse `VALIDATION_INVALID`; window and grain failures still use `WINDOW_INVALID` and `GRAIN_INVALID`.
- No migration was added. The three states are derived entirely from existing `bad_case_analysis`/`probe_reports`, so historical data and legacy V1 probe rows display whenever their object/version identity matches.
- This issue contains no frontend implementation or screenshots; m11-04 owns the target view components, dual tabs, single-object card interactions, and visual E2E.
