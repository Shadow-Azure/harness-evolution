# Agent Note: 向导下一步的点击校验与 409 空命中映射

Status: implemented

[English](2026-10-29-wizard-step1-validation.en.md) | 中文

## Problem

「启动自进化」向导第一步的必填反馈完全寄托在「下一步」按钮的禁用态上：缺什么、为什么不能点，界面一个字不说；时间段标了必填 `*` 却不参与禁用判断，规则自相矛盾。条件填齐而命中为零时，`probes/query` 返回的 `409 NO_PROBES_MATCHED` 被当成普通错误，把内部英文文案直接甩给用户并终止在第一步——零命中是"查询成功但没有结果"，不是异常终点。

## Decision

「下一步」按钮恒可点，校验移到点击时做字段级反馈：对象/版本/时间段缺失时对应输入框标红（`aria-invalid`）并在框下显示红色缺失提示，字段修正即时清错，不通过不发请求。`probes/query` 的 `409 NO_PROBES_MATCHED` 由前端映射为空结果：进入 Step2 渲染未命中空态与调整条件引导，两个出口按钮禁用（launch 同口径必然 409）；其余错误维持 Step1 提示。后端契约、OpenAPI 与 launch 的 probe>0 前置校验一律不动——空态是前端对既有 409 的解释，不是新的接口语义。

## Alternatives considered

后端把零命中改成 `200` + 空结果被否：跨栈契约与 openapi 都要动，且 launch 仍会 409，"空结果"出现两套口径。保留禁用态、用 tooltip 解释原因被否：触屏与键盘路径上 tooltip 不可靠，点击后的逐字段反馈才可执行，原型 `wz-query` 本也无 disabled 态。把 409 留在 Step1、仅本地化文案被否：产品上零命中必须进入下一步查看与调整，停在第一步只是把英文换成了中文，流程仍死在那。

## Consequences

`NO_PROBES_MATCHED` 从纯错误码变成前端实际消费的"空命中信号"，错误码字符串进入事实上的前端契约（已在 openapi `ErrorCode` 枚举内，但前端从此依赖它做分支）；其他调用 `probes/query` 的界面若存在，需要自行决定是否复用同一映射。空态下两个出口被禁用是冗余防御——后端 launch 本会拒绝，但禁用让用户不必点了一次才碰壁。本 Note 已随实现同步。
