# Agent Note: Evolution-target overview page

Status: implemented

English | [中文](2026-11-17-target-overview-ui.md)

## Problem

The overview page used to have only the bad-case view: sources, trend, and list were organized around reported sources, and `?tab=targets` was explicitly downgraded to `tab=cases` with a "coming in M11" notice. m11-03 delivered four read-only target endpoints, but the page still lacks a prototype-aligned view: target counters, a three-state trend, two distributions, a five-per-page target side list, a single-target analysis card with independent version and time filters, and a potential-case list filtered by target/source/state/time. The hard part is not drawing more components; it is keeping the shared time window and the single-target independent filters in one URL state while keeping the numbers consistent with the API's `(badCaseId, targetVersion)` row counting.

## Decision

- Both views share `tab`, `range`/`from`/`to`, and `grain`; switching tabs only resets `page`, never the window or grain. `?tab=targets` is now a valid state, so the old downgrade notice and disabled "coming in M11" state are removed. The target view additionally owns `targets` (trend target multi-select), `states` (trend states), `tpage` (side-list page), `ctarget`/`csource`/`cstate`/`cfrom`/`cto`/`page` (potential-case list), and `dtarget`/`dversions`/`dfrom`/`dto`/`dlimit` (single-target card). All are parsed and canonicalized in `overviewUrl.ts`, invalid values fall back, refresh restores them, and the existing canonical form of `overviewQuery("cases")` stays unchanged.
- The side list needs the complete ordered set while a list page holds at most 50 rows. `listAllOverviewTargets` first requests `pageSize=50` and follows `total` for remaining pages; the page then paginates the result at five rows in the client. The side list, target multi-select, and single-target selector share one evolvable-sorted set instead of mixing the `/evolution/targets` configuration list into display data. Trend, list, and detail still issue their own requests, preserving m11-03's four independent reads.
- The three trend chips are toggled in the client and `states` is not sent to `/targets/trend`: the API filter zeroes the unselected states, so the chip totals would change with the filter. The client keeps the full buckets and derives bar heights from the selected states, so each chip always shows the total for that state in the current target and time window. At least one state stays selected; selecting all writes an empty `states` so the URL stays canonical. The potential-case list's `cstate` is an independent server filter and does not affect the trend selection.
- Both distributions are derived from existing responses without new requests. The associated-Session distribution uses each complete target's `sessions` (the tooltip says one Session may contain several targets); the potential distribution sums the trend buckets' `byTarget` per target and splits it by state. Bars normalize by the largest Session count and the largest potential count. The list's source options reuse the bad-case summary's `objects`, which both tabs keep fetching, so the page does not run the matcher again just to fill a few dropdowns.
- The single-target card passes its own filters to the detail endpoint: explicit versions come from `dversions`, otherwise `dlimit` maps `5|10|20|0(all)`; `dfrom`/`dto` fall back to the shared window and show "follow the overview" to clear them once set. The card only changes its own query key, so the trend and list do not move with its versions or time; switching targets clears explicit versions so version names cannot leak across targets.
- Target maintenance reuses `TargetFormDialog` and `useEvolutionTargets`. Permission uses the workspace role through `canManageWorkspace` (global/space admin), not the global user role. Successful create/edit/remove invalidates the `["ws", wid, "overview"]` prefix and removes the deleted target from `targets`/`ctarget`/`dtarget` in the URL. Removal still surfaces the server's 409 (active run) inside the block.
- A potential-case row shows `badCaseId`, `objectName@version`, source, state, report time, Session, attribution report ID, and category. The ID opens the error detail at `?case=&tab=desc`; the attribution ID opens `?case=&tab=attr&at=`. Category exists only for attributed rows; unanalyzed and non-target rows show `—`, and "unanalyzed" is never rendered as "not this object".
- The workspace shell fixes `main` to the viewport height and clips overflow, so the overview page becomes its own scroll container (`height: 100%; overflow-y: auto`). Without it, taller content pushes the analysis card and potential-case table below the viewport with no way to scroll there. Mobile keeps document-flow scrolling.
- The visual layout follows the object view in `plans/ui-prototype-v2/harness-evolution.html`: `TargetsOverview` composes the stat strip, filter bar, trend card, side list, analysis card, and potential-case table. The state colors keep the prototype's green/orange/faint; bars and distributions use the in-house SVG and the pure `stackSegments` helper, with no third-party chart library.

## Alternatives considered

- **Make the target view a separate route**: the prototype makes it a secondary tab of the overview, and a separate route would lose the shared window and browser back semantics. Rejected; keep `?tab=` and one page state.
- **Let the server filter trend `states`**: fewer requests and simpler, but chip totals would change with the filter; toggling "unanalyzed" off would zero that chip and make it impossible to toggle back. Rejected. The server `states` filter remains for the potential-case list.
- **Fetch only five side-list rows and join the configuration list for names**: that creates two orderings (evolvable vs configuration), so the side list and multi-select disagree. Rejected; follow pages once and paginate in the client.
- **Reuse the shared window and target selection in the single-target card**: the prototype explicitly requires independent target, version, and time, otherwise the card cannot answer "how this version behaved in that period". Rejected; the detail endpoint already supports independent windows and versions.
- **Add a chart library or Element Plus chart components**: violates the m11-04 non-goal and bundle constraints. Rejected; keep the overview's SVG pure functions and add unit tests for the new three-segment `stackSegments`.
- **Derive source options from the current list page**: the dropdown would drift as pages change. Rejected; reuse the summary's workspace-wide source set.
- **Refresh the list after removing a target without fixing the URL**: `targets`/`ctarget`/`dtarget` would point at a missing id, leaving the trend and detail at 422/404. Rejected; clean the URL immediately after a successful delete.

## Consequences

- The first target-view paint issues four overview reads (complete target list, trend, potential cases, single-target detail) plus the shared summary. The target-side matcher cost remains m11-03's linear cost, and the client caches nothing across pages. Switching tabs disables trend/list/source requests so the bad-case view does not keep computing target analyses.
- The side list's five-per-page is client pagination; `tpage` only slices, it does not reduce the complete target request. If a future space has many targets, the side list must move back to server pagination and the complete set must become a separate options endpoint.
- The URL has many keys, but each appears only when non-default. `page` is shared by both tabs and resets on tab switch; the side list has its own `tpage`, so the two pagers cannot fight.
- Client-side trend chip filtering means the bar sum does not equal the list total (the list also has source, state, and independent time filters). The page explains this in copy and tooltips instead of forcing the numbers to agree.
- Source options come from the bad-case summary and may include sources that cannot appear under the current target filter. That accepts stable options over exact ones; selecting one may show the filtered empty state.
- Target maintenance reuses the target configuration form, so the overview page loads that form's Element Plus dependencies. Vite already splits it into a shared chunk outside the synchronous entry, and `verify:bundle` covers that boundary.
- The side list shows `versions[0]`: the API returns observed versions plus `defaultRef` in natural descending order and does not expose `defaultRef` separately, so the page cannot guarantee the configured baseline. The newest observed version is the explainable approximation.
- The target list API returns no case description, so the last table column uses the attribution category instead of the prototype's "problem description"; the title remains in the first column. This is a data-contract boundary, not a visual gap.
