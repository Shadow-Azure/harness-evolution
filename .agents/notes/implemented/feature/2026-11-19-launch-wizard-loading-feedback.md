# Agent Note: 启动向导预览显示阶段进度与超时反馈

Status: implemented

[English](2026-11-19-launch-wizard-loading-feedback.en.md) | 中文

## Problem

「启动自进化」第 1 步点击「下一步：关联 Session」会同步调用 `preview/sessions`。服务端在匹配 Session 之前先把所选版本解析成 body hash：本地 mirror 缓存为空时，`SubprocessGitContent` 对目标仓库执行 `git clone --mirror`，整个过程受 20 秒上限约束；因此冷缓存或 GitHub 访问慢时，这一步会等待到超时。2026-11-19 18:38 的部署 #388 把 `HE_DATA_DIR` 切到全新的 `/var/lib/harness-evolution/data`（部署日志显示该目录此前不存在），旧 `target-content` 缓存没有迁移；#385 修好缓存目录不可写之后，这是第一次真正走到 clone。用户 19:26 点击下一步时，看到的只有置灰的按钮和约 20 秒的静默等待，随后版本字段下出现「读取目标文件超时」。

前端 `LaunchWizard.vue` 在 `pending` 时只禁用按钮，既不说明当前在解析版本还是关联 Session，也不显示已等待时间；用户无法区分「正在 clone」和「页面卡死」。超时也只落在版本字段的红字里，缺少原因、重试和「不是 Session 数据为空」的解释。这个问题不能靠后端提速完全消除，因为首次读取远程仓库天然慢；入口必须把等待过程说清楚。

## Decision

- V2 原型在预览等待期间显示一张只读进度卡，位于步骤条与表单之间：
  - 第 1 步列出「读取目标版本 → 关联 Session」，第 2 步列出「筛选潜在 bad case」，第 3 步列出「检查归因缓存」；已完成阶段打勾，当前阶段高亮，未开始阶段置灰。
  - 显示已等待秒数，并写明「通常 2–5 秒；首次读取需要先克隆仓库，服务端单次读取上限约 20 秒，超时会给出重试」「缓存为空时会从远程仓库克隆」；不使用假进度条或倒计时，也不承诺超过上限的等待会成功。
  - 主按钮立即改成当前阶段文案（如「正在读取目标版本…」）并带 spinner；表单保留但整体置灰，避免等待中改动条件。
  - 等待中提供「取消等待」，回到原步骤并保留已填条件；生产请求可能继续，前端丢弃结果。
- 超时状态复用同一张卡：说明服务端读取达到上限、未能读完目标文件、这不是 Session 数据为空，并提供「重试解析」与「返回修改条件」；版本字段同时标红，与生产 `TARGET_CONTENT_UNRESOLVED` 的字段级反馈一致。`repo_unreachable`、`ref_not_found` 等其他 reason 仍保留字段级红字。
- 可访问性：等待卡 `role=status`，超时卡 `role=alert`；每秒变化的 elapsed 加 `aria-hidden`，不放进 live region；主按钮 disabled 时仍显示阶段文案；生产在 `prefers-reduced-motion` 下停止 spinner 动画。
- 原型用 `wzsim=loading` / `wzsim=timeout` 查询参数固定等待与超时状态，便于同一场景截图；正常点击会在 4 秒后自动进入下一步。
- 生产 `LaunchWizard.vue` 已按同一交互落地：`previewBusy` 状态 + 每秒计时器 + 请求代际；步骤前进的预览显示进度卡，表单 `inert`/locked；超时（`content_timeout` / `timeout`）显示失败卡与重试/返回；取消递增代际并丢弃 late result，不修改 `http.ts`、不引入 AbortController。服务端未上报子阶段，因此第 1 步只把「读取目标版本」标为进行中、「关联 Session」保持等待，不伪造完成。

## Alternatives considered

- **整窗只放一个居中 spinner**：拒绝。它抹掉了选择范围和已填条件，用户在 20 秒里无法确认自己做对了什么；进度卡保留上下文。
- **只给按钮加 spinner，不显示阶段**：拒绝。用户仍然不知道慢在读取版本还是关联 Session，也不知道首次 clone 可能更慢；阶段列表直接回答「这一步在做什么」。
- **用假进度条或倒计时营造「快好了」**：拒绝。服务端没有可报告的百分比，假进度会在超时时打脸，也会让后续真实进度失去可信度。
- **只把超时红字写得更长**：拒绝。超时发生在 20 秒之后，用户在前 20 秒仍然没有任何反馈；原因、重试和「不是 Session 数据为空」需要和等待过程放在一起。
- **自动重试**：拒绝。冷 clone 重试会重复等待，且掩盖了「目标仓库不可达/太慢」这个需要用户或运维处理的事实；保留显式重试。
- **把 clone 改到后台并让前端轮询**：这是更彻底的后端方案，但会改变 `preview/*` 的同步契约、任务状态和缓存语义，超出本次原型范围；在 issue 中作为后续选项记录。

## Consequences

- 原型能在同一场景清楚展示慢在哪、等了多久、失败后做什么；等待中仍可取消，表单内容不丢。
- 生产实现已落地并通过真实浏览器冒烟：等待卡、阶段按钮、表单锁定、取消、20 秒超时状态、重试/返回都可用；等待中仍可取消，表单内容不丢。冒烟使用本地 SQLite fixture，并以 CDP 在 20 秒后注入 422 模拟 `content_timeout`，不是真实 GitHub 延迟或真实后端超时。这次变更不改变 20 秒超时、不改 `preview/*` 契约、不减少任何一次真实网络读取。
- 前端不设独立 watchdog：若请求因代理/网络挂起而不 settle，等待卡会一直显示，用户只能用取消等待退出；504/非 JSON 会落到通用 `requestError`，不会进入超时卡。只有服务端返回 `content_timeout` / `timeout` 时才会卡片化。
- 服务端没有子阶段进度，所以生产第 1 步的「关联 Session」始终保持等待，不会像原型演示那样自动切到第二行；这是有意的诚实降级，不是实现遗漏。生产另补了原型没有的 `prefers-reduced-motion` 处理。
- 取消只丢弃前端结果，不 abort 已发出的请求；late response 由请求代际拦截，不会推进步骤。步骤内分页和第 4 步缓存刷新不套用这张进度卡。
- 超时卡只覆盖 `content_timeout` / `timeout`；`ref_not_found`、`repo_unreachable` 等仍保留字段级红字，避免把所有内容错误都说成超时。文案把「首次 clone」作为常见原因，但不应声称它是唯一解释。
- 后端仍可继续优化：单文件直读、单 ref shallow fetch、后台 mirror 预热、请求异步化；这些与前端进度反馈是互补的，不应互相替代。
- 原型演示态由查询参数固定，不能作为真实耗时或真实超时的证据；生产证据来自真实浏览器冒烟（本地 fixture + CDP 注入 422）和真实应用截图，真实后端/GitHub 延迟仍需部署后观察。
