# Agent Note: Body-hash attribution identity and post-process anchors

Status: proposed

English | [中文](2026-11-18-body-hash-attribution-post-process.md)

## Problem

In the 2026-11-18 production case the `systematic-debugging` target is a skill. The trace only exposes `definitionHash=8e54…` and `objectRevision=digest:3643…`; the revision combines a runtime-injected source path with the body hash. That path is a plugin-cache path such as `.../claude-plugins-official/superpowers/6.4.1/skills/systematic-debugging/SKILL.md`, is not a stable relative path, and is not persisted on `agent_events`; a target therefore cannot reconstruct the same revision from `repoUrl/subDir/ref`. In practice tag `v6.4.1` associates zero Sessions: all four normalized Sessions are skipped and eighteen are pending, so attribution cannot start. The same `sha256(normalized_body)` file-matching need applies to agents (`AGENT.md`) and knowledge (document file reads): they must share the same body hash instead of retaining source/raw-content identities.

At the same time, a bad case whose reported object cannot be found uses `eventIndex=-1`; the current design degrades it to the reporting Agent's birth point (the Session start for a main Agent), so these post-processed reports always fall before the target object and potential stays at zero. In the current docs `eventIndex=-1` means "missing/abnormal anchor", not "post-process"; the two meanings are conflated and the data cannot be explained or matched under a post-process rule.

## Decision

- The **file-matching key** for skill/agent/knowledge is `sha256(normalize_definition_body(body))`: skill uses `SKILL.md`, agent uses `AGENT.md`, and knowledge uses the document content from file reads. Skill identity uses that body hash; an agent `object_revision` keeps `agentType + isBuiltIn + body hash` as evidence identity, but target matching uses `definition_hash`; knowledge file-read `document_revision`/`object_revision` also use the normalized body hash, while the Provider revision remains `provider:`. `source_path` remains evidence and does not participate in revision, cache keys, or matching. An explicit tag/version still has the highest priority; the body hash is used only when no tag exists (knowledge uses `defaultRef` as the document revision).
- Selecting a tag in the evolution wizard means selecting the target version: for skill/agent the server reads `repoUrl/subDir/SKILL.md`/`AGENT.md` at that tag, and for knowledge it reads the document at its revision. All are normalized with the same `normalize_definition_body` as the parser and hashed with sha256; the resolved `targetRevision=digest:<bodyhash>` is used for session association and cache keys, while the tag remains the version/display and code baseline. A content-read failure must return a stable error and must not silently fall back to `tag:` matching. Knowledge targets remain API-configured and API-launched; the wizard has no knowledge selector yet.
- The target content must come from the same artifact/version and the same body extraction and normalization as the trace; agreement between the skill/agent tag-to-body hash, the knowledge document-revision body hash, and a known trace `definitionHash`/`documentRevision` is an acceptance test. In the current example, `obra/superpowers` v6.4.1 has a normalized file hash of `9080…`, not the trace's `8e54…`; the source/version or body extraction still has to be aligned. This is a prerequisite, not a reason to guess by name or default branch.
- When the reported object cannot be found, skill/agent anchors become post-process anchors: `eventIndex=2147483647` (INT_MAX), `anchorKind=post_process`, and `triggeredAt=bad_case.created_at`. They sort after every resolvable object; `-1` remains only for "the reporting Agent itself cannot be resolved" (unknown). The tree/API expose `anchorKind`; candidate rows record `case_anchor_kind=post_process`, and potential rows expose `anchorSource=post_process`, so the reason is auditable.
- Compatibility boundary: bump the parser version and replay stored claude-code Sessions. Legacy path+body revisions remain historical and are not the identity for new runs; new runs write body-only revisions. Old cache keys are not reused and may be cleaned separately. The knowledge UI selector, private-repository credentials, and rule-v1 categories are out of scope.
- This Note is design only; implementation (parser, target-content resolution, matcher, contract/UI, migration, tests) follows in a code PR after review.

## Alternatives considered

- **Keep path + body hash and normalize the path to a relative form**: the runtime path is a plugin-cache path, not a stable repository-relative path, and it is not persisted; the target still cannot reproduce it. Supporting it would require a new path-normalization contract and persistence, still bound to the plugin cache shape; body-only is simpler.
- **Use body hash only for target matching while keeping path+body as the object identity**: this creates two identities and doubles cache keys, attribution rows, and evidence semantics. It may serve as a transitional compatibility mode, but not as the long-term design. This decision chooses a single body-only identity.
- **Keep `agentType + isBuiltIn + body hash` as the target matching key for agents**: type/builtin are evidence, not the file-matching key; otherwise the same body would fail to match when type or builtin markers differ. Target matching uses `definition_hash`.
- **Keep the raw content hash for knowledge**: it would diverge from the skill/agent `sha256(normalized_body)`; file reads use the normalized body hash, while the Provider revision stays `provider:`.
- **Keep the tag as the revision**: a tag names a version but says nothing about the content hash of that version; a content mismatch cannot be detected, and the current example already shows a tag-file hash different from the trace. The tag should select content, not be the final revision.
- **Only change `eventIndex` to MAX**: comparison looks at `triggered_at` first, and the main Agent's birth point carries `session_started_at`; MAX only affects the coordinate fallback. The matcher also re-resolves the anchor and does not read the display anchor. A post-process trigger time (`created_at`) and `anchorKind` are required, or MAX has no effect.
- **Keep -1/birth fallback**: it treats a post-process case as "before the object", so explainable post-process data never enters potential, and "object not found" cannot be distinguished from "reporting Agent unresolved". Explicit post-process semantics are more explainable, but need a policy decision to avoid over-attribution.

## Consequences

- A parser version bump and replay are required for skill/agent/knowledge; legacy path+body revisions, cache keys, and attribution rows keep their historical meaning, while new runs use the normalized body hash. The 96-character column still fits the 71-character `digest:<sha256>`.
- The target side needs content read/normalization/cache and timeout boundaries for skill `SKILL.md`, agent `AGENT.md`, and knowledge documents. Target configuration currently uses credential-free HTTPS/SSH; private-repository content reads are out of scope. Read failures need stable error codes and must not fall back to tag guessing.
- Using `created_at` as the post-process trigger means "post-process report" is interpreted as "after the target". This is intentional product semantics but widens `after_object` inclusion; it needs `anchorSource` auditing and a policy switch if necessary.
- The tree/API gain `anchorKind`; the frontend must render MAX as "post-process" rather than a huge number. `BadCaseAnchor.event_index`'s `ge=-1` does not reject INT_MAX, but contracts and tests must cover the value.
- The current production example's tag-file hash differs from the trace body hash; the real source/version and body extraction must be settled first. Otherwise even body-only may still associate zero targets. Design docs and acceptance tests must make this prerequisite explicit and must not guess by name or default branch.
