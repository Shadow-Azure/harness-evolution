## 1. 一页速览

一句话：测试集不再在运行启动时被“预支”，而是和终评一起只在全部轮次结束后出现；无接纳轮时用一个不碰 skill 文件的空 commit 代表“本次运行的终态”，让测试集终评仍有明确的评测对象。

比喻：以前一开工就把期末试卷先考一遍留底；现在先只做随堂测验（验证集）决定每一轮去留，等所有轮次结束才把期初卷和期末卷一起发下去，并且如果这学期没有任何改动被采纳，就补一张“本学期无改动”的说明纸作为期末卷的答题人，而不是把开学时的空白卷再交一次。

| 交付块 | 内容 | 验证 |
|---|---|---|
| 启动/迭代 | 只提交 `validation_baseline` | `test_startup_submits_only_the_validation_baseline` |
| 终评编排 | `test_baseline` + `test_final` 并发在途，都完成才写 finals | `test_finalize_submits_both_test_evaluations_for_the_terminal_row`、`test_finalize_waits_for_both_test_evaluations` |
| 无接纳 | 空结果 commit、推送、持久化、复用作 `test_final` 对象 | `test_no_acceptance_run_uses_one_result_commit_as_the_test_target`、`test_result_commit_is_empty_pushed_and_reused` |
| 旧 run | 已有 test final 复用；旧失败经 finalize 补建结果 commit | `test_legacy_completed_test_final_is_reused_without_a_result_commit`、`test_legacy_failed_test_final_routes_through_finalize` |
| poller | 两项测试集评测未完成不入队 finalize | `test_poller_waits_for_both_test_evaluations_before_finalize` |
| 前端 | 文案区分「测试集基线（初始版本）」与「测试集终评」 | Before/After 截图 + `StepContent.test.ts` |

## 2. 架构导览

### 2.1 提交入口拆分

`EvolutionEvalSubmitter` 原先一个 `submit_baselines` 同时提交验证集与测试集基线，终评再单独提交 `test_final`。现在拆成：

- `submit_validation_baseline`（`eval_poller.py:180`）：只服务启动路径。
- `submit_test_evaluations`（`eval_poller.py:191`）：终评路径一次提交 `test_baseline`（`base_commit`）与 `test_final`（最终 commit），两者都通过 `_submit_run_evaluation` 的 `ensure_run_evaluation` 幂等落行。
- `submit_test_final`（`eval_poller.py:208`）：先返回已有 external id 的行，避免旧 run 已存在的终评被改目标；否则解析最终 commit。

“并发”在这里指两次平台提交都已在途，而不是同一 Python 调用内并行 await；poller 对两行分别轮询，因此无需引入并发控制。

### 2.2 终评编排与结果 commit

`EvolutionFinalizeService.handle`（`apply_final.py:290`）：

1. 只确保验证集基线（旧 run 兼容）。
2. 没有接纳轮时，若 `test_final` 尚无 external id，调用 `_ensure_result_commit`（`apply_final.py:370`）。
3. 提交两项测试集评测；`_test_evaluations_completed`（`apply_final.py:406`）要求两行都 completed，否则提前返回。
4. 写 `evolution_finals`、发布 run 分支、完成 run。

结果 commit 由 `GitWorkspaceManager.ensure_result_commit`（`workspace.py:918`）创建：

- 切到 run 分支并校验工作区干净；
- 若 HEAD 已是同一 run 的 `Harness-Verdict: no-acceptance` commit，直接复用；
- 否则 `git commit --allow-empty` 生成空提交；
- 用 `_push_run_branch(require_trailer=True)` 先推送，再返回哈希；
- 服务层用 `record_result_commit` 写入 `evolution_runs.result_commit`，重试直接复用。

空提交保证树与 `base_commit` 完全一致，因此不修改任何 skill 文件；同时因为哈希不同，`test_final` 的对象能明确区别于初始版本。

### 2.3 轮询与重试

`EvolutionEvalPoller._test_evaluations_ready`（`eval_poller.py:585`）只在两项测试集评测都 completed（或行尚不存在，允许 finalize 去补交）时重新入队 finalize。缺失行被视为“可推进”，这样 finalize 首次运行、崩溃后补交、旧 run 缺失基线都能继续。

重试侧 `EvolutionRetryService._legacy_no_acceptance_final`（`retry.py:290`）识别“无接纳轮 + 无 result_commit + 失败项含 test_final”的旧 run，改为调用 finalize 补建结果 commit；新 run 已有 result_commit，走原有按 kind 重提路径。

### 2.4 前端

`StepFinal.vue:109` 把“测试集得分 vs 初始”改为“测试集终评得分 vs 测试集基线（初始版本）”，表头与等待文案同步（`StepFinal.vue:157`、`:203`）。DOM 结构、间距和控件不变，因此与原型保持同一版式；原型自身仍使用旧文案，这是本 issue 要求“用文案区分两条评测”带来的有意差异。

## 3. 数据流走查

```text
advance(job)
  └─ submit_validation_baseline(run)
       └─ evolution_evaluations(validation_baseline, base_commit)

round publish → candidate submit → poller → apply
  └─ 每轮仍以 validation_baseline / 最近接纳轮为基线

finalize(job)
  ├─ submit_validation_baseline(run)            # 旧 run 兼容
  ├─ no accepted?
  │    ├─ test_final 已有 external id → 保留旧目标
  │    └─ 否则 ensure_result_commit
  │         ├─ commit --allow-empty
  │         ├─ push run branch
  │         └─ evolution_runs.result_commit = hash
  ├─ submit_test_evaluations
  │    ├─ test_baseline(base_commit)
  │    └─ test_final(last accepted commit / result_commit)
  ├─ both completed?
  │    ├─ no → return finalized=false
  │    └─ yes → write evolution_finals
  └─ publish run branch → complete run
```

关键不变量：

- 启动与迭代阶段不产生 `test_baseline` / `test_final` 行；
- `test_baseline` 的 commit 永远是 `base_commit`；
- 有接纳轮时 `test_final` 是最后一个接纳 commit，无接纳轮时是结果 commit；
- `evolution_finals.init_score` / `best_score` / `verdict` 口径不变；
- 结果 commit 的树与 `base_commit` 相同，且带 `Harness-Run-Id` 与 `Harness-Verdict: no-acceptance`。

## 6. 讨论点

### D1 结果 commit 记录的是验证集分数，不是最终测试集分数

- **位置**：`apps/api/app/service/evolution/git_candidate.py:155`
- **现象**：结果 commit 的「分数（验证集）」与 trailer 记录 `Harness-Init-Score` / `Harness-Best-Score`，而 issue 文本写的是“verdict、初始与终评分、指标与各轮决策”。
- **问题**：`test_final` 必须指向结果 commit，但提交 `test_final` 时测试集终评分尚不可知；commit 推送后不可变，不能事后补写最终分。
- **预判**：当前实现把提交前已知的验证集结论写入不可变 commit，把测试集 init/best 写入 `evolution_finals`，避免在 commit 里伪造未知分数；如果维护者要求 commit 必须包含测试集分数，就需要改变“先建 commit 再评”的顺序，属于设计变更。
- **结论**：（留空，待维护者拍板）

### D2 前端文案与原型文字不完全一致

- **位置**：`apps/web/src/pages/evolution/components/StepFinal.vue:109`
- **现象**：原型写“测试集得分 80.4 vs 初始 v1.5.0 81.2”，实现写“测试集终评得分 … vs 测试集基线（初始版本） …”。
- **问题**：issue 要求“用文案区分测试集基线与测试集终评”，原型没有这条区分；两者只能取其一。
- **预判**：保留原型的结构与视觉层级，只替换文案，以满足 issue 的验收标准；如果维护者认为原型文字优先，可回退这四处文案，但“区分两条评测”的验收项会失去。
- **结论**：（留空，待维护者拍板）

### D3 旧 run 失败的 test_final 通过 finalize 补建结果 commit

- **位置**：`apps/api/app/service/evolution/retry.py:242`
- **现象**：旧 run 无接纳轮、无 `result_commit` 且 `test_final` 失败时，直接重提会因缺少最终 commit 再次阻塞。
- **问题**：修复前的旧 run 的 `test_final` 目标是 `base_commit`；本 PR 要求无接纳时不再回退，因此需要先补建结果 commit。
- **预判**：实现选择让 retry 分流到 finalize，由 finalize 创建并推送结果 commit 后再提交终评；这会让一次 retry job 返回 `finalized=false`，由 poller 继续推进，语义与现有“重提后等 poller”一致。
- **结论**：已按此实现并新增 `test_legacy_failed_test_final_routes_through_finalize`（2026-11-27）。

### D4 两项测试集评测是顺序发起、并发在途

- **位置**：`apps/api/app/service/evolution/eval_poller.py:191`
- **现象**：`submit_test_evaluations` 先 `await` test_baseline 提交，再 `await` test_final 提交。
- **问题**：issue 说“两者可以并发在途”，并不要求同一事件循环内并行 HTTP；但 reviewer 可能期待 `asyncio.gather`。
- **预判**：两次提交都只写数据库与平台 launch，顺序发起不会让任一评测等待另一评测完成；poller 独立轮询两行，因此“在途并发”成立。改成 gather 会引入部分成功时的错误合并，收益低。
- **结论**：（留空，待维护者拍板）

### D5 结果 commit 的迁移 downgrade 未纳入测试

- **位置**：`apps/api/alembic/versions/0036_run_result_commit.py:26`
- **现象**：`downgrade` 直接 `op.drop_column`，没有像部分迁移那样加降级测试。
- **问题**：SQLite 需要较新版本才支持 `DROP COLUMN`；生产使用 MySQL，风险主要在本地旧 SQLite。
- **预判**：当前 CI 的 SQLite 版本支持该语法；若维护者要求所有新迁移都有降级测试，可补 `test_migration_0036`。
- **结论**：（留空，待维护者拍板）

### D6 poller 把“已建行但未提交”误判为在途

- **位置**：`apps/api/app/service/evolution/eval_poller.py:585`
- **现象**：原条件只要 `eval_status != "completed"` 就阻止 finalize 入队，`pending` 且 `eval_external_id IS NULL` 的行永远不会被 `list_run_eval_due` 扫到。
- **问题**：崩溃/关闭落在 retry 的 run-eval 重提之间时，run 可能永远停在 running，没有 job、没有错误、没有 due poll。
- **预判**：没有 external id 的行不可能在平台侧在途，应允许 finalize 入队并由其幂等重提。
- **结论**：已修复为“有 external id 且未 completed 才视为在途”，新增 `test_poller_resumes_a_pending_test_evaluation_without_external_id`（2026-11-27）。

### D7 recovery 路径漏掉旧 run 结果 commit

- **位置**：`apps/api/app/service/evolution/retry.py:355`
- **现象**：`_recover_running` 直接重提 pending 的 test_final，旧 run 无 result_commit 时会命中 `_test_final_commit` 的 RunBlocked。
- **问题**：下一次 `/retry` 找不到 failed run eval 或 failed round，run 永久停在 blocked(eval)。
- **预判**：与主 retry 路径使用同一分流：无接纳、无 result_commit 时先走 finalize。
- **结论**：已修复，新增 `test_recovery_pending_test_final_routes_through_finalize`（2026-11-27）。

### D8 结果 commit trailer 的分数口径不够显式

- **位置**：`apps/api/app/service/evolution/git_candidate.py:200`
- **现象**：`Harness-Init-Score` / `Harness-Best-Score` 实际是验证集分数，与 finals 的测试集同名字段可能被误读。
- **问题**：不可变 commit 是长期证据，字段名应自解释。
- **预判**：改名为 `Harness-Validation-Init-Score` / `Harness-Validation-Best-Score`，并在 verdict 值里标注 `validation`。
- **结论**：已改名，集成测试断言新 trailer（2026-11-27）。

### D9 accepted 谓词两处不一致

- **位置**：`apps/api/app/service/evolution/apply_final.py:292` / `eval_poller.py:228`
- **现象**：finalize 用 `any(round_.accepted)`，`_test_final_commit` 用 `accepted and commit_hash`。
- **问题**：理论上 accepted 但 commit_hash 为空的轮会让 finalize 跳过结果 commit，再由提交器抛 RunBlocked。
- **预判**：统一为 `accepted and commit_hash`，finalize 与提交器使用同一最终 commit 集合。
- **结论**：已统一（2026-11-27）。

### D10 owning Note 的旧 run 时机描述过期

- **位置**：`.agents/notes/implemented/architecture/2026-11-25-baseline-gate-test-final.md:29`
- **现象**：Note 仍写旧 run 在首次 advance 或 finalize “补交基线”，未区分验证集与测试集。
- **问题**：与实现和新决策不一致。
- **预判**：改为“advance 补交验证集基线，缺失的测试集评测在 finalize 补交”。
- **结论**：已更新中英两侧并重录 i18n（2026-11-27）。

## 9. 文件级分析

### 9.1 `apps/api/app/service/evolution/apply_final.py`

职责：终评编排。变更形态 M。

旧实现：`submit_baselines` + `submit_test_final`，只看 test_final 是否 completed。
新实现：只确保验证集基线；无接纳轮先建结果 commit；提交两项；两项都 completed 才写 finals。错误处理抽成 `_raise_push_failure` / `_raise_final_failure`，避免结果 commit 与最终 push 两条路径重复 30 行错误落库逻辑。

实现思路：把“评测对象解析”放在“评测提交”之前，把“等待条件”放在“写 final”之前；三件事各自幂等，重试只需从 handle 重新进入。

发现：结果 commit 的创建与测试集提交之间没有事务边界；如果进程在推送后、持久化前退出，下一次 `ensure_result_commit` 会通过 HEAD trailer 复用，不会重复 commit。已覆盖。

### 9.2 `apps/api/app/service/evolution/eval_poller.py`

职责：评测提交与轮询。变更形态 M。

旧实现：一个 `submit_baselines` 循环两个 kind；poller 只看 test_final。
新实现：启动入口只提交 validation；终评入口提交 test_baseline + test_final；`submit_test_final` 先复用已有 external id；poller 用 `_test_evaluations_ready` 同时检查两行。

实现思路：把“提交哪些评测”从调用方下沉为两个命名入口，避免 advance 与 finalize 共享一个含义模糊的方法；poller 的等待条件与 finalize 的等待条件使用同一组 kind。

发现：`_test_evaluations_ready` 对缺失行返回 true，允许 finalize 补交；这与“缺失即补交”的兼容边界一致。

### 9.3 `apps/api/app/service/evolution/git_candidate.py`

职责：commit message builder。变更形态 M。

新增 `build_no_acceptance_message`、`_round_decision_lines`、`_metric_lines`、`_eval_scores`。消息结构沿用 candidate/accepted 的“人读叙事在上、trailer 在下”：结论 → 分数（验证集）→ 指标 → 各轮决策 → 追溯 → trailer。主体使用 `_safe_single_line`/`_bounded_subject`，避免把外部文本原样写入不可变 commit。

发现：消息中的“候选最佳分”来自验证集，已在标题与正文显式标注，避免与 `evolution_finals` 的测试集 best 混淆。

### 9.4 `apps/api/app/third_party_api/git/workspace.py`

新增 `ensure_result_commit` 与 `_is_result_commit`：校验 run 分支名、切分支、要求工作区干净、复用已有 no-acceptance HEAD、`--allow-empty` 提交、trailer 校验、`_push_run_branch` 推送。推送复用现有 fast-forward 校验与 lease 语义，不引入 force push。

### 9.5 `apps/api/app/service/evolution/retry.py`
