## 1. 一页速览

一句话：**把根会话 ID 从“藏在 DOM 属性里的暗号”变成页面上的门牌号，并让搜索框认这个门牌号。**

## 2. 架构导览

### 2.1 后端：一个 `OR` 条件，不新增契约

`SessionRepository.list_sessions` 是会话列表唯一的 SQL 读路径。改动把原来的单列 `LIKE` 拆成 `pattern` + `or_`：

- `apps/api/app/db/crud/sessions.py:217`：`pattern` 只构造一次，两列共用同一转义结果。
- `apps/api/app/db/crud/sessions.py:220`：`or_(search_text LIKE, lower(id) LIKE)`。
- `apps/api/app/db/crud/sessions.py:222`：`func.lower(id)` 让 SQLite 与 MySQL 对大小写的行为一致；`_escape_like` 继续把 `%`、`_`、`\` 当字面量。

选择“查询时匹配主键列”而不是“把 id 写进 `search_text`”的原因在 Agent Note 里：`search_text` 的写入路径在归一化侧，改它要动写入、回填和 fixtures；id 不可变，重复存储没有收益。读路径一处 `OR` 的代价是 `%...%` 全表扫描，但 `session_families` 是根会话粒度，和现有标题搜索同一量级。

### 2.2 前端：四个展示点共用同一文案

四个组件都采用“根会话 ID · <完整 UUID>”的文本结构，不新增请求：

- 错误页左栏：`ErrorSidebar.vue:38` 把原来的 `session · <id>` 换成带标签的 ID 行，`title` 保留完整值。
- 错误页右栏：`errors/Index.vue:331` 在 `time` 之后、repo 之前插入 meta 片段，`ErrorSidebar` 与 meta 使用同一个路由解析后的 `sessionId`。
- 会话卡：`SessionCard.vue:60` 在 repo/时长/工具/子 agent 行之后、统计条之前插入 ID 行，使用 `item.id`。
- 会话概览：`SessionOverview.vue:191` 在 `time` 之后插入 ID 片段，使用 `item.id`。

样式层面：

- 错误页与概览的 ID 片段使用 `overflow-wrap: anywhere`，窄屏可折行（`errors/Index.vue:582`、`SessionOverview.vue:392`）。
- 会话卡 ID 行使用 `text-overflow: ellipsis` + `title`，保持卡片高度可控（`SessionCard.vue:198`）。
- 两处 `.root-session-id` 样式各自 scoped，未抽公共类；这是有意的局部重复，避免为一个 10 行样式新增共享层。

## 6. 讨论点

### 6.1 精确 ID 也走 `%...%`，没有利用主键索引

- **位置**：`apps/api/app/db/crud/sessions.py:220-223`
- **现象**：`q` 无论是否是完整 UUID，都走 `lower(id) LIKE '%q%'`；完整 UUID 也无法用主键索引。
- **问题**：`session_families` 当前是根会话粒度，行数不大；但若未来会话量到百万级，每次搜索都全表扫描，p95 可能回退。
- **预判**：V1 可接受，和现有 `search_text LIKE '%q%'` 同量级；若要优化，先加 `id = q` 的精确快路径，再考虑前缀索引/全文方案，不在本 PR 扩大范围。
- **结论**：__________

### 6.2 E2E 没有覆盖“与完整 ID 不同的前缀”

- **位置**：`apps/api/tests/m2-06-session-query-api/test_sessions_api.py:142-165`、`tests/e2e/m3-session-browser.test.mjs:513`
- **现象**：API 测试覆盖完整 ID、子串 `0001`、大写与不存在；E2E 用完整 ID。fixture 的 4 个会话 ID 共享 `10000000-0000-4000-8000-...` 前缀，无法用现有数据断言“唯一前缀”。
- **问题**：前缀行为依赖 `LIKE '%q%'` 的 SQL 语义，没有直接断言一个“短于完整 ID 但唯一”的输入。
- **预判**：低风险；若要补，加一个合成 ID 的 repository 测试或 E2E fixture，而不是改现有会话 ID。
- **结论**：__________

### 6.3 会话卡多一行后，列表更早出现滚动条、标题更容易省略

- **位置**：`apps/web/src/pages/sessions/components/SessionCard.vue:60-68`、`:198`
- **现象**：每张卡高度增加约 15–18px；4 张卡在 900px 高视口下已经出现滚动条，滚动条占宽后卡标题比改动前更早省略（对比图 `screenshot-root-session-id-compare-browser.png`）。
- **问题**：这是“每张卡都显示完整 ID”的直接代价；信息更全，但视觉密度变高。
- **预判**：符合“每张卡都显示”的产品选择；若觉得拥挤，可压缩 ID 行上下 margin 或把 ID 放到 hover/focus 展开，但那会牺牲常驻可见性。
- **结论**：__________

### 6.4 两处 `.root-session-id` 样式重复

- **位置**：`apps/web/src/pages/errors/Index.vue:582`、`apps/web/src/pages/sessions/components/SessionOverview.vue:392`
- **现象**：两处 scoped 样式几乎相同（颜色、`overflow-wrap`、内层 mono）。
- **问题**：未来改样式要改两处；但抽公共类需要新增共享样式层或全局类，收益不大。
- **预判**：保留局部重复，等第三处出现再抽；当前 10 行重复可接受。
- **结论**：__________

### 6.5 短数字片段会命中大量 ID

- **位置**：`apps/api/app/db/crud/sessions.py:218`
- **现象**：`q=1` 会匹配所有含 `1` 的 UUID，也可能匹配标题/仓库里的 `1`。
- **问题**：这是模糊搜索的自然结果，但与“按 ID 精确过滤”的直觉有差距；用户可能预期输入 `1` 不会返回一堆。
- **预判**：与现有标题/仓库模糊搜索一致；不加最小长度限制，避免破坏既有搜索习惯。若产品要求“ID 模式才走 ID 匹配”，另立需求。

## 9. 文件级代码分析

### 9.1 `apps/api/app/db/crud/sessions.py`（M）

职责：会话列表的唯一 SQL 读路径。变更形态：修改 `list_sessions` 的 `q` 条件。

旧代码：

```python
conditions.append(
    session_families.c.search_text.like(
        f"%{_escape_like(query.lower())}%",
        escape="\\",
    ),
)
```

新代码：

```python
pattern = f"%{_escape_like(query.lower())}%"
conditions.append(
    or_(
        session_families.c.search_text.like(pattern, escape="\\"),
        func.lower(session_families.c.id).like(pattern, escape="\\"),
    ),
)
```

这在做什么：把“搜索词”同时拿去比标题/仓库列和根会话主键列；`pattern` 只构造一次，避免两处转义不一致。`func.lower(id)` 是跨库一致性的保险：SQLite 的 `LIKE` 对 ASCII 大小写不敏感、MySQL 取决于 collation，显式转小写让两边结果一致。

实现思路总结：不新增字段/索引/契约，只在读路径扩一个 `OR`；转义复用现有 `_escape_like`。

检视发现：6.1 的全表扫描是已知代价，设计文档已写明；无正确性发现。

### 9.2 `apps/api/tests/m2-06-session-query-api/test_sessions_api.py`（M）

职责：会话查询 API 的 HTTP 契约与搜索/排序/校验回归。变更形态：新增一个测试函数。

新增测试 `test_list_search_matches_root_session_id`：

- 完整 ID：`q=SESSION_1` → 只返回 SESSION_1。
- 子串：`q=0001` → SESSION_1。
- 大写：`q=SESSION_2.upper()` → SESSION_2。
- 不存在：`q=...0009` → 空。

为什么这么写：用真实 HTTP + 真实 SQLite fixture，不 mock repository；断言 ID 列表而不是整个响应，聚焦“命中范围”这一个行为。测试先红后绿，红灯是 `[] != [SESSION_1]`，说明它确实覆盖了新增分支。
