## §1 一页速览

一句话：把 case 级归因置信度从「按命中路径写死的 0.8 / 0.6 / 0.7」改成「三份独立证据到了几份」的规则分，步骤 4 的数字第一次能解释「为什么是这个把握」。

比喻：置信度像体检报告的三项指标——时间序、对象身份、版本身份。三项都合格是 90 分；缺一项是 80 分；只有一项在 50 分上下；一项都没有是 30 分；如果版本指标说「就是这台机器」，身份指标却写着「另一台」，这是互相矛盾的证据，只能给 20 分，比「没查出来」还低。

## §2 架构导览

### 2.1 置信度是纯函数，不碰数据库也不碰模型

`attribution_confidence.py:43-66` 定义 `EvidenceSignals`，只装三个布尔；`extract_signals()`（`:125-164`）把已持久化的原始字段折成这三个布尔；`evidence_score()`（`:167-186`）做区间映射；`attribution_confidence()`（`:189-205`）决定是取分数还是取补数。整条链路没有 I/O，同一输入永远同一输出，单测可以只构造 dataclass 就把 0/1/2/3 票和矛盾信号全部钉住。

这与旧的引擎写法形成直接对照：旧代码在 `attribution.py` 的三个分支里分别写 `confidence=0.8/0.6/0.7`，分数是「走到哪个分支」的函数；新代码的分数是「证据有几份」的函数，分支只决定分类。

### 2.2 三个信号各自的来源与边界

| 信号 | 来源 | 判定 | 边界 |
| --- | --- | --- | --- |
| 时间序可比 | 候选快照 `order_state` | 等于 `comparable` | `unknown` 不加分，也不扣分 |
| 失败签名匹配 | `bad_cases.object_type` / `object_name` vs run 目标 | 归一化后 `(type, name)` 全等 | 只比对象身份；不做错误文本指纹 |
| 版本直证 | `bad_cases.object_version` vs run 解析出的 revision | revision 的带前缀形式或裸形式命中 | 不认 run 的选版本，理由见 §2.3 |

`failure_signature()`（`:69-89`）做 `strip().casefold()`，空值返回 `None`，避免把空字符串当成一个「匹配」。`version_identity_forms()`（`:108-122`）只接收一个 revision，展开 `tag:` / `digest:` / `provider:` 的前缀与裸形式；例如 `tag:v2.0.0` 接受 `v2.0.0`，`digest:<sha>` 接受裸 `<sha>`，这样 trace parser 里常见的裸 body hash 也能命中。

### 2.3 为什么版本直证不认「选版本」

run 同时有 `target_version`（人选的 tag）和 `target_revision`（解析后的 `tag:` / `digest:` 身份），但 cache key 只含 `target_revision`，不含 `target_version`。如果把选版本也纳入版本直证，同一个 case + 同一个 revision 在两个选版本下会算出不同分数，却共用同一行缓存：缓存命中时显示旧分数，缓存未命中时显示新分数，违反「同证据同分」。`version_identity_forms()` 因而只接受解析后的 revision；这在语义上也更贴 issue 的「body 哈希 / revision 精确命中」。

### 2.4 非目标结论取补数

`attribution_confidence()`（`:189-205`）对 `attributed` 返回完整度分数，对 `non_target` 返回 `1 - 分数`。原因不是数学游戏：非目标结论的把握与「归因证据有多强」相反。一个 order unknown、但对象和版本都写着的 case，说「不是这个对象」只有 20% 把握；一个什么信号都没有的 case，才有 70% 把握。旧实现两种情况都写 0.7，等于把两种完全不同的证据强度抹平。

### 2.5 低置信门槛是一个关闭的开关，不是死代码的借口

`LOW_CONFIDENCE_CLUSTER_GATE_ENABLED = False` 与阈值 0.5 在 `:31-40`，本 issue 不接线。原因在 issue 的交付边界里：门槛要生效必须同时改聚类输入查询，否则会出现「常量打开了但查询没过滤」的假生效。两个常量把语义与默认值固定下来，后续 bugfix-19 接线时不需要重新发明阈值。

## §3 数据流走查

一条主线：创建一个 full run → prepare 产出候选 → 归因 runner 写 probe → 步骤 4 读出 confidence。

1. `PotentialMatcher` 产出候选：`order_state` 由 `compare_triggers()` 算出，随候选快照落库；`bad_cases` 行保留 bad case 自己声明的 `object_type/object_name/object_version`。
2. `AttributionRunner.run()`（`attribution.py:431-434`）先把本次归因的 revision 定下来：显式 `target_revision` → run 快照 `target_revision` → 历史 NULL 回退 `resolve_legacy_target_version()`。
3. runner 调用 `load_bad_case_evidence()`（`crud/attributions.py:512-551`），一次批量读回 `object_name/object_type/object_version/title/description/meta_data`。重试时 prepare 不重跑 matcher，但这一步仍从同一批行读出同样字段，所以信号可重建。
4. `_build_input()`（`attribution.py:504-547`）把候选 `order_state`、证据对象身份/版本、run 的 revision 装进 `AttributionInput`；`case_object_*` 三个字段默认 `None`，只有 runner 的生产路径会填。
5. `RuleBasedEngine.attribute()`（`attribution.py:150-152`）先算 `signals = item.evidence_signals()`，再按命中原因分类；分类逻辑本身没变。
6. `_attributed()` / `_non_target()` 用 `attribution_confidence()` 写分数（`:217`、`:238`），`AttributionResult` 的 `__post_init__` 仍校验 0–1 与闭集分类。
7. `ProbeWrite` 把分数写进 `probe_reports.confidence`；cache key 仍由 workspace、case、对象、revision、policy、engine 七段生成。命中旧缓存时走复用分支，不重算、不改分数。
8. 步骤 4 的 API 把 probe 的 `confidence` 原样投影为 0–1 float；前端 `StepAttribution.vue` 仍是 `(value * 100).toFixed(0)%`，零改动。
9. 误差与边界：证据行缺失时 `_build_input` 抛 `LookupError`，runner 转成 retryable `RunBlocked`；对象身份为空时签名信号为 false，不把空串当匹配。

## §6 讨论点

### D1 失败签名取对象身份，而不是错误文本指纹

- **位置**：`apps/api/app/service/evolution/attribution_confidence.py:69-89`
- **现象**：issue 写的是「错误签名匹配（与对象已知失败签名重合）」，实现把「失败签名」落成 bad case 声明的 `(object_type, object_name)`，与归因对象身份全等即得分。
- **问题**：这比「错误文本指纹」粗。两个不同错误只要都指向同一个对象，就会被视为同一个签名；跨对象但错误文本相同的 case 反而不得分。
- **预判**：本 issue 的交付边界是只改写入路径的置信度产出，没有新的「对象已知失败签名」持久面。先在对象身份这一层落地，能保证规则确定、可单测、零额外查询；更细的指纹需要历史 case 的跨行查询或新的持久字段，适合另开 issue。
- **结论**：保留对象身份定义并写入 owning Note 的 Consequences；若维护者要求错误文本级签名，另开 issue 扩展 `failure_signature()`，不影响本 PR 的区间与缓存契约。

### D2 版本直证但对象身份不一致时给 0.2

- **位置**：`attribution_confidence.py:58-66`、`:178-179`
- **现象**：`version_proof=True` 且 `failure_signature_match=False` 时，分数固定 0.2，低于「零票」的 0.3。
- **问题**：跨对象归因（`same_object_only=false` 的 after_object 路径）本来就是合法策略，若两个对象恰好共用同一个版本 label，会被判成矛盾证据并压低到 0.2。这是否过严？
- **预判**：跨对象归因的证据本来就弱于「对象自报」；版本命中却指向另一个对象，确实是冲突而不是单纯缺证据。0.2 是保守值，只影响展示与未来的低置信门槛，不影响结论是否入簇（门槛关闭）。
- **结论**：保留；若产品认为跨对象归因应更高，调 `_CONTRADICTION_SCORE` 即可，属于后续策略决定，不是本 PR 的缺陷。

### D3 非目标结论的补数会显示 10%

- **位置**：`attribution_confidence.py:189-205`
- **现象**：一个对象与版本都命中、但正文为空的自报 case 会得到 non_target 结论、confidence 0.1。
- **问题**：步骤 4 的「置信度」列没有额外的语义提示，用户可能把 10% 理解成「10% 相信它不是该对象」，而不是「只有 10% 把握断言它不是该对象」。
- **预判**：分类 chip 同一行显示「非该对象问题」，语义上「置信度」修饰的是结论；数学上补数是正确的。真正需要提示时应该改 UI 文案，不在本 issue 的写入路径里做。
- **结论**：保留数值语义；UI 文案若需要澄清，另开前端 issue，本 PR 不动展示组件。

### D4 低置信门槛只有常量，没有消费方

- **位置**：`attribution_confidence.py:31-40`
- **现象**：`LOW_CONFIDENCE_CLUSTER_GATE_ENABLED=False` 与阈值 0.5 已定义，但聚类查询没有引用。
- **问题**：读者可能认为开关是死代码或「忘了接线」。
- **预判**：issue 明确要求「设计为常量开关，默认关闭，不在本 issue 启用」。接线需要同时改聚类输入查询，否则开关打开也不会过滤，属于 bugfix-19 的范围。
- **结论**：保留；在 Note 与 PR 描述中写明「预留开关，非本 issue 缺陷」。

### D5 历史 probe 不回填

- **位置**：`attribution.py:449-461`（runner 的缓存复用分支）
- **现象**：改动前写入的 probe 仍保留 0.8/0.6/0.7；只有新写入或 cache-off 重算的行才用规则分。
- **问题**：同一个页面上可能同时出现旧常量与规则分，用户会看到不一致。
- **预判**：issue 验收写明「历史缓存不受影响」，回填会改写外部拥有表的结论字段，且没有证据快照可重算。保持现状是契约要求；需要统一时应在下一轮全量重算/迁移里做。
- **结论**：保留；不写迁移、不回填。

## §9 文件级代码分析

### 9.1 `apps/api/app/service/evolution/attribution_confidence.py`（A）

**职责**：把「证据完整度」落成纯函数，给 rule-v1 引擎提供 case 级置信度。变更形态是新增文件，没有前身。

**关键依赖**：只用标准库 `dataclasses`。这不是为了炫技，而是让整个模块没有任何 I/O 依赖：数据库、模型、时间都不进来，测试可以只构造三个布尔。

**变更块分析**：

- `:14-27` 五个区间常量。旧实现把 0.8/0.6/0.7 直接写在引擎分支里，数字与含义脱节；这里把每个数字背后的证据状态写成 docstring，调值时只改一处。
- `:31-40` 低置信门槛常量。`ENABLED=False` 是设计开关位；阈值 0.5 与「一票 0.5」的边界对齐，语义是「低于一票的完整度算低置信」。
- `:43-66` `EvidenceSignals`。`votes` 用三个 `int(bool)` 相加，避免 if/else 链；`contradictory` 单独表达「版本命中但身份不符」，让区间函数先处理矛盾再数票。
- `:69-89` `failure_signature()`。归一化只做 `strip().casefold()`，不做别名映射：对象名在 catalog sync 与 run 快照里应已经是同一规范名，擅自做模糊匹配会把不同对象合并。
- `:92-105` `_identity_forms()`。只剥离一个前缀，不做递归；revision 前缀是封闭集合 `tag:/digest:/provider:`，多层前缀没有现实来源。
- `:125-164` `extract_signals()`。三个参数组分别对应候选快照、bad case 行、run 快照；`order_state` 用字符串比较而不是 `Literal`，让纯函数不依赖 `potential.py` 的类型。
- `:167-186` `evidence_score()`。先判矛盾，再按票数；这样「两票但其中一票是矛盾」不会误落 0.8。
- `:189-205` `attribution_confidence()`。`conclusion` 只区分 attributed 与其它；非目标取补数。`AttributionResult` 的闭集校验仍在，坏值进不了写路径。

**实现思路总结**：先定义证据，再定义票数，最后定义区间；顺序反过来就会把区间写成 if/else 分支的副产品。

### 9.2 `apps/api/app/service/evolution/attribution.py`（M）
