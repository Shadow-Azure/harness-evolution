## §2 架构导览

### 2.1 四层职责刻意分开

`contracts.py` 只放值对象和错误，不认识任何后端；`base.py` 只放 ABC 和三个代码常量（`base.py:24-31`）；`factory.py` 只负责「字符串 → 类 → 实例」；`fake.py` 是唯一实现。这样 bugfix-17 加真实子类时只改 `factory.py:58-61` 的注册项，业务侧不出现厂商分支。

`AIAgentProvider.__init__` 接收可选 `Settings`（`base.py:39-46`），工厂统一调用 `implementation(settings)`（`factory.py:102`）。fake 不需要配置，因此构造参数可省略；真实 CLI 子类可以直接从 `self.settings` 取 `ai_agent_claude_bin`。

### 2.2 默认值必须能启动

`Settings.ai_agent_provider` 默认 `claude-code`（`config.py:158-161`），而真实 claude 子类要到 bugfix-17 才存在。若「只注册 fake、校验器只认注册表」，零配置启动会直接红——与「默认 claude-code、零配置可跑」冲突。因此 `factory.py:26-55` 放了一个显式占位：`provider_id="claude-code"`、`health_check` 返回 `healthy=False`、`analyze`/`edit_workspace` 抛带 bugfix-17 指针的 `NotImplementedError`。它不会静默降级，也不会让应用起不来。

校验器只认注册表（`config.py:326-339`），错误文案固定含 `unknown AI agent provider`；`AI_AGENT_PROVIDER` 与 `HE_AI_AGENT_PROVIDER` 两个别名都通过 `AliasChoices` 接收。

### 2.3 装配与健康事件

`create_app` 在数据库之前构建单例（`main.py:195`），挂到 `app.state.ai_agent`（`main.py:614`）。lifespan 一开始调用 `_record_ai_agent_health`（`main.py:521`）：成功时按 `healthy` 选 INFO/WARNING，失败时只记 `error_type`，永远不把 provider 的内部细节写进启动失败路径（`main.py:140-166`）。健康事件是结构化日志字段 `event='ai_agent_health'`，因为启动阶段还没有 run，不能写 run events。

### 2.4 fake 先行的边界

`fake.py:32-42` 给三个已知 task 键固定输出，未知键返回 `{"task": ...}`；调用方可传 `outputs` 覆盖。`fake.py:77-85` 用调用方的 Pydantic 模型验证输出，失败折叠为 `AgentProviderError(retryable=False, provider_id="fake", detail=...)`。fake 不碰网络、不碰文件系统，`edit_workspace` 返回固定「无改动」结果（`fake.py:94-104`），这是后续业务单测全走它的前提。

## §3 数据流走查

一条主线：进程启动 → 环境变量 → Settings → 工厂 → provider 单例 → 健康事件。

1. 部署注入 `AI_AGENT_PROVIDER=fake`（或留空走默认 `claude-code`）。
2. pydantic-settings 按 `AliasChoices` 取值；`validate_ai_agent_provider` 归一化大小写/空白并查注册表（`config.py:326-339`）。未知值在构造 Settings 时抛 `ValidationError`，服务不会带错配置启动。
3. `create_app` 调 `build_agent_provider(resolved_settings)`（`main.py:195`）；工厂按注册表实例化具体类（`factory.py:93-102`）。
4. provider 挂到 `app.state.ai_agent`（`main.py:614`），后续 service 只从 state 取，不自行读 env。
5. lifespan 启动先 `health_check()`（`main.py:521`），记录 `provider_id / healthy / detail / latency_ms`；健康 false 只告警，不阻断数据库初始化。
6. 业务调用 `analyze(request)`：request 带 `task`、`prompt`、调用方 `output_model`；fake 按 task 取固定输出，`model_validate` 成功后转成 JSON 兼容 dict 返回 `AnalysisResult`（`fake.py:70-92`）；失败抛归一化错误，调用方按 `retryable` 决定是否重试。

## §6 讨论点

### 讨论点 1：注册表里同时有 `fake` 与 `claude-code` 占位

**位置**：`apps/api/app/third_party_api/ai_agent/factory.py:58-61`

**现象**：issue 的实现内容写「本 issue 仅注册 fake」，实际注册表有两个键；`claude-code` 指向一个健康 false、能力调用抛 `NotImplementedError` 的占位。

**问题**：这是否偏离「仅注册 fake」？占位是否会在业务层造成「看起来可用」的误解？

**预判**：不偏离。issue 同一段明确允许「以显式占位抛 NotImplementedError」，而默认值就是 `claude-code`、验收要求零配置可启动，两者只有占位能同时满足。占位把 `healthy=False` 与 `NotImplementedError` 都做得显式，不会静默降级；bugfix-17 落真实子类时只替换注册项。

**结论**：（留空给维护者）

### 讨论点 2：`output_model` 用 Pydantic 模型而非裸 JSON Schema

**位置**：`apps/api/app/third_party_api/ai_agent/contracts.py:88-99`

**现象**：`AnalysisRequest.output_model` 的类型是 `type[BaseModel]`，设计文档 §5.5.1 的注释写的是「调用方传入的 JSON Schema」。

**问题**：是否需要支持 `Mapping[str, Any]` 形态的裸 JSON Schema？两种调用方会不会分裂？

**预判**：暂不需要。07 §5.5.3 把 Pydantic 定为单一事实源，后续 submission 通道也是 `model_validate`；Pydantic 模型需要时可用 `model_json_schema()` 导出 JSON Schema，不需要为此引入 `jsonschema` 运行时依赖。若未来出现只提供裸 schema 的调用方，再把字段扩成联合类型即可，当前没有这样的消费方。

**结论**：（留空给维护者）

### 讨论点 3：fake 的默认输出刻意最小

**位置**：`apps/api/app/third_party_api/ai_agent/fake.py:32-42`

**现象**：`cluster.review` 默认返回空 `clusters`，`severity.score` 只含 `overall` + `vector`；这些结构不一定满足 bugfix-19 将要定义的完整任务模型。

**问题**：默认值是否应该直接对齐设计里的完整任务结构？还是让业务测试自行覆盖？

**预判**：当前空结构是安全的：它不会伪造业务结论，且 `FakeAIAgentProvider(outputs=...)` 已提供覆盖入口；bugfix-19 引入任务模型时，同一 PR 内补默认值或测试覆盖即可。现在就猜完整字段，反而容易和后续模型漂移。

**结论**：（留空给维护者）

### 讨论点 4：健康事件只落结构化日志

**位置**：`apps/api/app/main.py:140-166`

**现象**：`ai_agent_health` 通过 `logger.log(..., extra=...)` 记录，没有写数据库事件表。

**问题**：issue 写「lifespan 启动时 `health_check` 记事件」，是否应写入 `evolution_events` 或 `EventBus`？

**预判**：启动阶段没有 run，`evolution_events` 需要 run 身份；`EventBus` 是进程内 SSE，启动时没有订阅者。仓库对启动/运维事件本来就用结构化日志（`app/logging.py` 的 `KeyValueFormatter`），这里沿用同一约定，测试也按日志字段断言。

**结论**：（留空给维护者）

## §9 文件级代码分析

### `contracts.py`

职责：定义 provider 的输入、输出、用量、健康与错误，不依赖任何具体后端。关键依赖只有 `pydantic.BaseModel`，用于表达「调用方的 schema」；它在本文件只做类型与 `issubclass` 校验，不参与运行时序列化。

- `AgentUsage`（`contracts.py:44-69`）：model / input_tokens / output_tokens / cost_usd；`tokens` 属性返回总量。设计只要求 model/tokens/cost_usd，拆成双向是为了接 Claude CLI 的 `model_usage`。
- `AnalysisRequest`（`:88-99`）：task、prompt、output_model；三个字段都做非空/类型校验。
- `AnalysisResult` / `EditResult`（`:102-160`）：统一携带 usage、session_id、latency_ms、retryable，调用方不需要知道后端。
- `ProviderHealth`（`:163-174`）：health_check 的返回值，detail 由 provider 负责脱敏。
- `AgentProviderError`（`:177-196`）：message + retryable + provider_id + detail；message 不承载 prompt/token，detail 可放有界诊断。

### `base.py`

职责：唯一父类契约与三个代码常量。`analyze`/`edit_workspace`/`health_check` 都是抽象方法；`provider_id` 是 `ClassVar`，注册表用它对齐键。300s/1800s/dontAsk 放在模块级，避免变成子配置项。

### `factory.py`

职责：字符串到实例的唯一入口。注册表是模块级 dict；`_PendingClaudeCodeProvider` 承担默认值可启动的职责；`register_provider` 校验 id 与声明一致，防止「设置值、注册键、结果字段」三处漂移；`build_agent_provider` 再做一次未知值保护，覆盖绕过 Settings 的调用方。

### `fake.py`

职责：CI 与业务测试的确定性后端。默认输出按 task 键固定；构造时深拷贝覆盖项，避免测试间共享可变状态；`model_validate` 失败折叠为归一化错误；`edit_workspace` 不碰文件系统；`health_check` 恒 healthy。没有网络、没有时钟、没有随机数。

### `config.py`

两个字段与两个校验器：provider 走 `AliasChoices`，校验器查注册表并归一化；claude_bin 只做非空裁剪。校验器内部延迟 import 工厂，避免 `config` 与 `factory` 的模块级循环依赖。

### `main.py`

`_record_ai_agent_health` 是一个独立的启动探针：成功按健康状态选日志级别，异常只记类型；lifespan 在建库前调用，保证 provider 问题不会伪装成数据库问题；`app.state.ai_agent` 是业务唯一取用点。

### `test_ai_agent_factory.py`

22 项测试覆盖：默认值、工厂选择与归一化、两种 env 别名、未知值启动红、空 CLI 路径、工厂自保护、四个 task 的 fake 输出、覆盖项、schema 失败归一化、固定 EditResult、错误字段、契约非空/负值校验、占位行为、`app.state` 装配、lifespan 日志、注册表一致性。没有网络调用。

### 流程与 Note

flow issue 只改 `status: ready → in-progress`，中英与配对记录同步；设计 Note 在 Consequences 追加骨架落地事实，中英同步并重录配对。没有新增 Agent Note，因为该变更正是既有设计的实施，更新 owning Note 已满足仓库规则。
