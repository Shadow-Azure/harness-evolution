## 1 一页速览

**一句话**：把「凭旧 probe 报告两步起跑」的向导换成「先看对象版本在哪些 Session 出现，再看哪些 bad case 属于潜在，再看归因缓存能复用多少，最后才启动」的四步向导。

**一个比喻**：像机场值机。第 1 步选航班和日期；第 2 步柜台只核对「这趟航班到底有没有这位乘客」；第 3 步按签证/行李规则筛出真正能登机的人；第 4 步确认哪些人已经有过安检结果（缓存）、哪些要重新安检。柜台不自己重新算签证规则，只读系统给的名单——这就是本 PR 让所有计数由服务端 summary 提供的理由。

| 交付块 | 内容 | 验证 |
|---|---|---|
| 四步状态机 | 范围 → Session → 潜在 → 归因 | 15 条 VTU + 1 条 E2E |
| 服务端口径 | 三段 preview summary/分页 | API 测试与真实 E2E |
| 启动快照 | `policy` / `cacheEnabled` 进 run | 3 条 API 测试 |
| focus case | `?case=` 预选对象/版本 | Index + Wizard 单测 |
| 视觉对齐 | 720px、radio 策略、switch 缓存 | 前后截图 + prototype 对比 |

**验证基线**：真实 API + SQLite + fixture corpus + 无头 Chrome；截图 1408×960，场景固定为 `synthetic-review@synthetic-1`、2026-10-20 ~ 2026-10-25。

## 2 架构导览

### 2.1 前端：单组件、单状态机、单向依赖

`LaunchWizard.vue:61` 只有一个 `step`（1|2|3|4）。第 1 步的表单直接驱动条件对象，第 2–4 步是只读投影：

```text
step 1 表单 ──条件──► preview/sessions ──summary──► step 2
                                          └─page──► preview/sessions(page)
              ──条件+policy──► preview/potential ──summary──► step 3
                                          └─page──► preview/potential(page)
              ──条件+policy+cache──► preview/attribution ──4 数──► step 4
              ──条件+policy+cache──► runs / cluster-previews ──202──► 路由
```

- 条件变化通过 `resetDownstream()`（`LaunchWizard.vue:306`）清空第 2–4 步；分页函数（`:464`、`:535`）只重发当前端点。
- 策略在 `currentPolicy()`（`:385`）集中构造；`custom` 至少一条规则的本地校验在 `validateStep1()`（`:398`），后端 `resolve_policy` 用同一规则兜底。
- `focusCase` 的预选在 `applyFocusCase()`（`:273`），只改对象/版本与提示，不碰时间段/策略。

### 2.2 服务端：preview 只读，launch 才写

三段预览共用 `PotentialMatcher` 的关联/潜在/缓存键逻辑；`preview/attribution` 只读取 `probe_reports.cache_key`，不写 probe、analysis 或候选。启动时 `launch.py:128` 先 `resolve_policy`，再把 `policy.snapshot()` 与 `body.cache_enabled` 写进 `evolution_runs`（`:234`）。这样第 4 步看到的是「这份策略和缓存开关」，而不是 prepare 阶段再读请求方的当前值。

### 2.3 契约：先有 generated 类型，再有前端别名

`ProbeQueryRequest` 新增 `policy`/`cache_enabled` 后运行 `pnpm contract:generate`；`packages/contracts/src/index.ts` 只加类型别名，没有手写业务字段。前端 `api/evolutionRuns.ts:130` 起三个函数直接消费生成类型。

### 2.4 可访问性

对话框保留既有语义：`role="dialog"`、`aria-modal="true"`、标题 `aria-labelledby`、Escape 关闭、关闭后焦点回到触发元素。字段错误通过 `aria-invalid` + `aria-describedby` 指向自己的错误文本；两个空态是页面内区块，不是 toast。

## 3 数据流走查（一条真实剧本）

1. 管理员从 `/workspaces/ws-default/evolution` 点「启动自进化」；`Index.vue:144` 挂载向导。
2. 若 URL 带 `?case=...`，`Index.vue:23` 读出并传给 `focusCaseId`；向导 `getBadCase` 成功后预选 `synthetic-review` 与 `synthetic-1`（`LaunchWizard.vue:273`）。
3. 填 `2026-10-20 ~ 2026-10-25`，点下一步。`goToSessions()`（`:431`）POST `preview/sessions`，服务端返回 `reported=4 / associated=1 / skipped=3 / versionUnresolved=0 / pending=0`。
4. 第 2 步显示「示例会话三：技能分叉」，4 条/页；点下一页只重发 `page=2`。
5. 点下一步。`goToPotential()`（`:487`）带 `{preset:"default"}` POST `preview/potential`；服务端返回 1 条 `badcase-synthetic-0003`，命中原因 `self_report`。
6. 点下一步。`goToAttribution()`（`:551`）带 `cacheEnabled:true` POST `preview/attribution`；服务端返回 `{potential:1,reused:0,fresh:1,nonTargetKnown:0}`。
7. 关闭缓存开关，`refreshAttribution()`（`:580`）重发一次 `cacheEnabled:false`；数字更新但步骤不倒退。
8. 点「仅聚类」，`launch("cluster_only")`（`:598`）POST `cluster-previews` → 202 → `emit("launched")`；`Index.vue` 路由到 `/evolution/cluster/:runId`。
9. 重开向导点「启动自进化」，POST `runs` → 202 → `/evolution/runs/:runId`。

## 6 讨论点

### D1 · `policy`/`cacheEnabled` 与并行的 m10-04 重复

- **位置**：`apps/api/app/service/evolution/launch.py:128`、`:234`；`probe_query.py:44-46`
- **现象**：m10-04 的 worktree 也在改同一组字段（并且把 `_require_hits` 换成潜在校验）。本 PR 为了向导 E2E 与「启动快照」先在 m10-05 里落了最小改动。
- **问题**：两 PR 谁先合入、是否产生无意义重复？
- **预判**：字段语义一致，冲突只是同一段代码；m10-04 合入后应以它的版本为准，本 PR 的 `launch.py`/`probe_query.py` 改动可整体让位。
- **本 PR 处理**：保留到 m10-04 合入；若 m10-04 先合入，rebase 时删除本 PR 的重复后端改动，仅保留前端契约消费。最终以两 PR 的合入顺序为准，待维护者确认。

### D2 · 启动仍用旧 probe 命中做前置校验

- **位置**：`apps/api/app/service/evolution/launch.py:145`（`_require_hits`）
- **现象**：第 3 步可能显示有潜在 case，但库里没有已分析的 probe 时，启动会 409 `NO_PROBES_MATCHED`；这是旧 prepare 的入口条件。
- **问题**：m10-05 是否应该顺手替换？
- **预判**：替换前置校验等于把七步 prepare 的状态机与聚类输入一起改掉，属于 m10-04 的交付边界；在 m10-05 做会与并行工作直接冲突。
- **本 PR 处理**：不修复；PR 描述与 Agent Note 已明确「旧 prepare 的 probe 前置条件仍在」，m10-04 接管后重跑冒烟。最终边界待维护者确认。

### D3 · 第 2 步「潜在数」与后端契约不一致

- **位置**：`plans/fullstack-design/08-frontend-implementation.md:627`；`SessionPreviewItem` 契约
- **现象**：设计原文第 2 步表格含「潜在数」，但 `preview/sessions` 只做关联，不返回潜在数；如果前端硬算就会破坏「不自行重算口径」。
- **问题**：改实现还是改文档？
- **预判**：契约是服务端事实，文档是笔误；应以契约为准。
- **本 PR 处理**：已把 08 §9.2 改为「对象出现标记 / 触发点时间 / bad case 数」，并在第 3 步保留潜在数。**已修 2026-11-17**，措辞待维护者确认。

### D4 · 删除 V1 两步 E2E

- **位置**：`tests/e2e/m5-05-launch-wizard.test.mjs`（删除）
- **现象**：该用例断言 `wizard-cluster` 在第 2 步出现，而四步向导把出口移到第 4 步；保留会稳定失败。
- **问题**：应该改旧用例还是删？
- **预判**：旧用例描述的是被本 PR 删除的 V1 页面，改造成四步只是复制新用例；新 `m10-05` 用例已覆盖两个出口与完整四步。
