## §1 一页速览

一句话：这个 PR 把原型里的“横条 Agent + 压缩触发链 + 正交父子边”从浏览器脚本提炼成可单测的纯函数，并加了一个真实 Vue Flow 视觉夹具。

生活化比喻：`buildGraph` 像先在草稿纸上排好整张地铁线路图，确认每根线从哪里出发、在哪里拐弯、哪些站合并显示；Vue Flow 最后只负责把这张图纸画出来。这样布局不依赖浏览器何时完成测量，也能在数据打乱时复现同一张图。

## §2 架构导览

### 2.1 输入与不可变副本

`buildGraph` 先把 Agent 与 events 复制到内部数组，再做父边修补和缺失事件合成，见 `layout.ts:361-366`、`layout.ts:444-458`。这层复制把调用方数据与一次布局尝试隔开，避免重试或第二个消费者看到被改写的 `parentAgentId/toolUseId`。

### 2.2 触发链与条宽

`chainOf` 按 `messageOffset → line → 原数组顺序` 排序触发事件，生成触发药丸与 `×N` 间隔，见 `layout.ts:127-185`。返回的 `width` 取“链宽”和“按 JSONL 行数缩放宽度”的较大值，因此无触发事件的短/长 transcript 仍有不同的横条长度。

### 2.3 递归布局与 trunk

当前实现按父 Agent 分桶、按父事件位置排序子节点，再以 DFS 放置，见 `layout.ts:467-500`、`layout.ts:518-689`。触发点只在相邻 X 差不超过 24px 时聚合；超过八个直接子节点且未展开时替换成一个 collapse 节点。

### 2.4 渲染边界

`AgentTree.vue` 只消费 `SessionTree`，不请求 `/tree`，也不渲染问题卡。Vue Flow、Background、Controls 都由该组件动态引入；生产路由不注册隐藏 demo 页，见 `router/index.ts:31-40`。这符合 m3-02 与 m3-03/m4 的边界。

## §3 数据流走查

场景：用户打开 DEV 视觉夹具，查看四节点 nested 树。

1. `agent-tree-demo/Index.vue` 把 `demoCoreTree` 传给 `AgentTree`，初始展开 main 与 A。
2. `AgentTree` 用 canvas 测量文本宽度，调用纯 `buildGraph`，同时保留折叠集合，见 `AgentTree.vue:49-81`。
3. `buildGraph` 为 main/A/B/C 计算横条、触发药丸、三个父边与 anchor 描述。
4. VueFlow 渲染自定义 Agent 节点和 OrthEdge；节点初始化完成后执行 `fitView({padding: 0.12})`，见 `AgentTree.vue:106-131`。
5. 点击 collapse 节点时，组件更新本地 expanded Set 并发出事件；父级可用事件同步自己的展开状态，见 `AgentTree.vue:84-104`。

## §6 讨论点

### D1 普通子 Agent 的未知 toolUseId 会误挂到第一个 Workflow

**位置**：`apps/web/src/components/agent-tree/layout.ts:188-196`

**现象**：`agentEventIndex` 在 child 带有非空 toolUseId、但父事件中找不到它时，直接返回父 Agent 的第一个 `workflow` 事件。由 Node type-stripping 探针构造“main 有一个 Workflow 事件、普通 child 的 toolUseId 不匹配”后，输出 edge `sourceHandle=h0` 且 diagnostics 为空。

**问题**：普通子 Agent 的父边会从错误 Workflow 触发点出发，排序也会借用该事件的位置。设计只允许 workflow-subagent 使用 Workflow 关联；普通/未知 ID 应降级到 main 并产生 `MISSING_PARENT_EVENT`。

**预判**：建议把 Workflow fallback 限定为明确的 workflow-subagent 语义，其余未知 ID 直接返回 `-1` 进入现有合成边路径；补一个与上面探针等价的回归测试。

**结论**：已修复（2026-10-26）。普通和未知父调用降级到 main 的合成 agent 事件，Workflow fallback 仅限 workflow 类型。

### D2 超长触发链会缩扁药丸，但 handle 仍按未缩放坐标摆放

**位置**：`apps/web/src/components/agent-tree/layout.ts:638-646`、`apps/web/src/components/agent-tree/nodes/AgentNode.vue:151-174`

**现象**：子节点 `boxW` 被封顶 520px，但 `data.w/chain.offsets` 保留完整链宽。20 个长触发事件的探针得到 `chainWidth=4390`、`boxW=520`，最后一个 handle 的 `left=4309px`。CSS 的 `.rf-cnode` 又没有 `flex-shrink: 0`，药丸会被 flex 压低宽度，而 handle 使用原始 offsets。

**问题**：长链 Agent 的边缘会落到节点外，药丸上的可见触发点与实际 source handle 不再对齐；在后续 m3-03 接真数据时会让树边看起来从错误位置出发。原型药丸显式设置 `flex-shrink: 0`，不会出现这种静默错位。

**预判**：应明确选择“节点随链扩展”还是“节点内横向滚动/折叠”；无论哪种，handle 必须使用最终渲染坐标。至少先恢复药丸 `flex-shrink: 0`，并增加宽链的真实 handle 对齐测试。

**结论**：已修复（2026-10-26）。节点随长触发链扩展，药丸禁止 flex 压缩，handle 使用最终布局坐标。

### D3 四节点视觉夹具仍显示两个无对应节点的触发药丸

**位置**：`apps/web/src/components/agent-tree/fixtures/demo-nested.ts:23-56`、`apps/web/src/components/agent-tree/fixtures/demo-nested.ts:232-236`

**现象**：`demoCoreTree` 只过滤 Agent 列表到 main/A/B/C，但 main 的 events 仍保留 Workflow 和 forked-skill 两个触发点。真实截图里主链出现“批量处理 workflow”“forked-skill”两个药丸，却没有对应的 Workflow/fork 子节点或边。

**问题**：视觉验收页标题声明“核心四节点”，却展示两个悬空触发点；读者会误以为这两个分支应存在但未画出。E2E 只断言 4 节点/3 边，没有检查主链药丸是否都有落点。

**预判**：让 `demoCoreTree` 同步剔除没有对应 Agent 的 main events，或让视觉夹具完整渲染六个节点；前者更适合“最小 nested 四节点”验收。E2E 可增加 `source handles == edges + intentionally-terminal markers` 的结构断言。

**结论**：已修复（2026-10-26）。核心视觉夹具同步剔除没有落点的 Workflow/fork 触发。

### D4 collapse 分支没有进入 branchSegments，问题卡侧向判断会漏掉它

**位置**：`apps/web/src/components/agent-tree/layout.ts:543-585`、`apps/web/src/components/agent-tree/layout.ts:676-682`

**现象**：普通子 Agent 会同时写入 `branchSegments` 供 `pickFindingSide` 做碰撞检测；collapse 节点只写 edge，没有写入 `branchSegments`。10 个子节点 + main finding 的探针中，edges 有 `main-group`，但 `branchSegments=[]`。

**问题**：m4 消费 anchor 时，问题卡可能被放在 collapse 竖线经过的右侧，违反原型“问题卡不穿过兄弟分支”的要求。

**预判**：collapse edge 也应按相同 trunk/y-range 记录分支段，并增加 collapse + anchor 的侧向测试；这属于 anchor 描述自身的完整性，不提前实现问题卡。

**结论**：已修复（2026-10-26）。collapse 竖段进入 `branchSegments`，问题卡侧向判断可感知。

### D5 节点标题用 10px 字体测量，实际 CSS 为 11px

**位置**：`apps/web/src/components/agent-tree/layout.ts:55-58,638-646`、`apps/web/src/components/agent-tree/nodes/AgentNode.vue:122-131`

**现象**：布局用 `FONT_PILL`（10px）测量 `item.agent.label`，节点标题实际以 11px 渲染；原型单独使用 11px 的 `agentLabelW`。长标题在 box 宽度封顶前后会比预期提前省略，`visualW` 也不会为问题卡保留真实空间。

**问题**：普通英文标签差异较小，但中文长标签或高 DPI 字体测量会放大误差；会让“节点宽度至少容纳标题”的边界失真。

**预判**：增加独立 `FONT_AGENT_LABEL`（11px）并在 label 宽度计算中使用；补浏览器 computed 宽度与 mock measure 的字体断言。

**结论**：已修复（2026-10-26）。标题按实际 11px CSS 字体测量。

### D6 真实 E2E 没有覆盖 390px 与折叠点击

**位置**：`tests/e2e/m3-agent-tree.test.mjs:144-150,198-218`

**现象**：浏览器测试只设置 1408px，没有验证 390px 下画布、header、controls 的布局；collapse 仅在 mock 单元测试中触发 `$emit`，真实 DOM 的 button 点击没有 E2E。

**问题**：当前原型要求有窄屏一致性，且折叠是图的直接交互；两个路径都没有真实浏览器证据。现有截图只证明四节点主图。

**预判**：补 390×844 的 computed/overflow 检查，并点一次真实 collapse 按钮后验证节点从 2 变 13、控制台保持干净。

**结论**：已修复（2026-10-26）。真实 Chrome E2E 覆盖 collapse 2→13 与 390px。

### D7 OrthEdge 缺少原型边的 arrow marker

**位置**：`apps/web/src/components/agent-tree/edges/OrthEdge.vue:25-37`、原型 `harness-evolution.html:1241-1245`

**现象**：原型 edge 使用 `MarkerType.ArrowClosed`；当前 OrthEdge 只画 `<path>`，没有 marker definition 或 `marker-end`。

**问题**：截图中父边方向只能从几何推断，原型则在末端有箭头。对当前四节点图影响较小，但属于可观察的原型偏离。

**预判**：若项目已决定不使用箭头，应更新原型或 Agent Note；否则复用 SVG marker，并补 E2E `marker-end`/可见箭头断言。

**结论**：已修复（2026-10-26）。父边使用单根 `<g>` 内的闭合 SVG marker。

## §9 文件级代码分析

### `agent-tree/layout.ts`（A）

职责：把 `SessionTree` 变成无 DOM 依赖的 Vue Flow 节点、边、诊断和 anchor 描述。

关键机制：

- `orthPath` 在 `721-743` 生成圆角正交路径。

### `agent-tree/AgentTree.vue`（A）

职责：真实 Vue Flow 薄渲染层，管理展开集合、控件、节点选择事件和 fitView。

实现思路：每个非 gap item 生成一个 `h{eventIndex}` source handle；位置使用纯布局 offsets。左侧 target handle 与父边相连。
