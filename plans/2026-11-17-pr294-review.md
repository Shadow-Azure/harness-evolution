## §1 一页速览

**一句话**：把「对象在哪些 Session 出现过、哪些 bad case 算潜在、哪些归因能复用缓存」收进一个只读的 `PotentialMatcher`，并用三条 `preview` 端点把向导第 2–4 步的数字提前算出来；本 PR 不写候选行、不执行归因、不接 run。

**一个比喻**：`PotentialMatcher` 像一名**只查目录、不写卡片的图书馆员**。第 2 步先按「书名 + 版次」（target + version）找出哪些读者借过这本书（Session 关联），并把读者分成「借到了」「版本不明」「借的是别的版」「还没登记」四类；第 3 步按借阅规则挑出「可能和这本书有关」的借阅记录（policy），并给每条记录标「自报 / 在借书之后 / 两者都是 / 被规则排除 / 顺序不可比」；第 4 步只翻历史书评卡片（既有 cache key）数「能复用几张、要新写几张、历史上判过非本书的几张」，全程不往卡片盒里放新卡片。

## §2 架构导览

这一层的核心是四个决定：**谁拥有匹配规则**、**用什么身份判定「同一个对象」**、**五个计数怎么分区**、**预览如何只读**。

### 2.1 单一 matcher + 只读 repository，预览 service 只做壳

设计把「规则」和「查询」拆成两层：`PotentialMatcher` 只接 `MatchCondition`，不接 run；`PotentialRepository` 只做 `select`，所有方法按 500 个标识分块（`crud/potential.py:29-35`）。三段预览 service（`potential.py:746-903`）只做 target/窗口归一化、分页和 DTO 映射，不复制策略。

这个分层的好处是 m10-04 的 run prepare 可以直接构造同一个 `MatchCondition` 调 matcher（Note:33），不会出现「向导算 7 条、run 算 5 条」。代价是：**预览没有 run 级快照**，所以它不能保存「这次为什么排除」的行；被排除的行只进 summary（`potential.py:690-698`），m10-04 才落 `evolution_run_candidates`。这与 07 §5.10「读路径只读已落库事实」一致，但也意味着预览数字在两次调用之间可能因并发上报而漂移（只读但不保证跨查询的单一快照；当前无实害，见 §6 D6 的量级讨论）。

### 2.2 版本身份：代码只比较 `object_version`，设计里还有 `object_revision`

这是本 PR 最需要先讨论的一层。先看数据是怎么写进来的：

- 对 **skill / agent**，parser 只在工具入参显式带 `skillVersion` / `agentVersion` / `objectVersion` / `version` 时写 `object_version`；`tag` 只写 `object_revision=tag:<tag>`，不写 `object_version`；没有任何显式版本就留 NULL（`claude_code.py:53-81`、`:526-539`）。
- 同一时刻，parser 一定写 `object_revision`，词汇是 `tag:<tag>` / `digest:<sha256>` / `provider:<raw>` / `unknown`（`base.py:686-699`、`:756-767`）。例如只带 `tag: "release-7"` 的 Skill，`object_version=None`，但 `object_revision="tag:release-7"`（`tests/m9-04.../test_object_revision.py:251-264`）。
- 对 **knowledge**，`record_knowledge_event` 只接收 `document_revision` 与 `object_revision`，**从不设置 `object_version`**（`base.py:462-501`；`claude_code.py:542-597`）。实测：一次文件读的 knowledge 事件是 `object_version=None`、`object_revision="digest:…"`。
- matcher 的查询只 select `agent_events.object_version`（`crud/potential.py:198-213`），`ObjectEventRecord` 里也没有 revision 字段（`crud/potential.py:61-71`）；关联时只做 `event.object_version == condition.target_version`（`potential.py:551-582`）。

后果分三档：

1. **knowledge 永远不关联**。当前 parser 下所有 knowledge 事件的 `object_version` 都是 NULL，所以每个知识 Session 都会进 `versionUnresolved`；`associated=0`，第 2 步直接 409。实测（用 support 的播种 helper 复现真实 parser 形状）：`reported=1, associated=0, versionUnresolved=1, skipped=0, pending=0`。
2. **只有 tag 没有 version 的 skill/agent 被当成「版本不明」**。它明明有 `object_revision=tag:release-7`，却因为 `object_version=NULL` 被跳过。
3. **`targetVersion → objectRevision` 没有落实**。15 §9.2 明确写「API 的 `targetVersion` 保留为选择入口，服务端必须解析为规范化 `objectRevision` 后再做 Session 关联与缓存键计算」（`15-v1-v2-gap-analysis.md:158`）；实现和本 PR 修改后的 05/06/07 都改成「只与 `object_version` 精确比较」（`05:1241`、`06:901`、`07:1153`），15 没有同步。这不是「按名称猜版本」的替代方案问题：`object_revision` 是已经落库的规范化身份，不是猜测。

Agent Note 的已知限制写的是「knowledge 关联依赖 `agent_events.object_version`；当前 M9 parser 只保证 `document_revision`」（Note:34）。这句话把「没有 object_version」与「没有规范化 revision」混在一起：M9 parser 其实保证 `object_revision`，knowledge 也有 digest/tag/provider 三种身份。Review 时建议把这一句改成「knowledge 有 object_revision，但没有 object_version；当前 matcher 不用 object_revision」。

### 2.3 策略真值表：优先级、排除原因与 `orderState`

`resolve_policy`（`potential.py:115-157`）把策略收敛成四个开关：

- `None` 或 `preset=default`：两条规则都开、`sameObjectOnly=false`；只要携带任一开关就 422。
- `preset=custom`：三个开关必须都给；两条匹配规则不能同时关；否则 422 `POLICY_INVALID`。
- `sameObjectOnly` 是最后一道过滤，不是匹配规则。

`evaluate_hit`（`potential.py:419-452`）的顺序是：

```
sameObjectOnly 不满足            → policy_excluded
self_hit = self_match && includeSelf
after_hit = after_match && order==comparable && includeAfter
both                            → both
self_hit                        → self_report
after_hit                       → after_object
includeAfter 且 order==unknown   → order_unknown
其余                             → policy_excluded
```

举例：target 是 skill `deep-research` v2，Session 在 10:00 第一次触发 `deep-research`，10:30 出现一个 `other-skill` 的 discovery case。

- 默认策略：`other-skill` 的触发点 10:30 > 10:00 → `after_object`，纳入。
- custom 只开 `includeSelfReport`：同样的 case 不满足 self，`after_hit=false` → `policy_excluded`。
- custom 只开 `includeAfterObject`：如果 case 是 `deep-research` 的 self 报告，`self_hit=false`，若触发点可比且更晚 → `after_object`；否则 `policy_excluded`。
- `sameObjectOnly=true`：`other-skill` 先被名称过滤成 `policy_excluded`，即使它在对象之后。
- 上报 agent 解析不到：`case_trigger=None` → `order_unknown`，不纳入；如果它同时是 self 报告，仍按 `self_report` 纳入（`potential.py:440-449`）。

`order_unknown` 只在 `includeAfterObject=true` 时出现；如果策略只开 self 规则，未知顺序会落成 `policy_excluded`。这是有意的：`order_unknown` 表达「本该比较但比不了」，而不是「任意排除」。测试 `test_policy_truth_table.py:141-280` 把这条真值表基本钉全了。

### 2.4 锚点：self/agent、skill、discovery/agent、出生点

`_resolve_case_trigger`（`potential.py:930-971`）按 06 §7.4 做四件事：

| case | 锚点 | 代码 |
|---|---|---|
| `self + agent` | 上报 agent 的出生点（主 agent=Session `started_at`；子 agent=父节点 `tool_use_id` 匹配的 `agent` 事件） | `_birth_point`（`:974-997`） |
| `self + skill` | 上报 agent 中该 skill 的**最后一次**触发（按 `event_index`） | `:941-955` |
| `discovery + skill` | 同上 | `:941-955` |
| `discovery + agent` | 父节点中调用该 subagent 的 `agent` 事件（按 `tool_use_id`，不按名称） | `_parent_call_event`（`:1000-1013`） |

几个边界：

- skill 找不到同名事件 → 退化成出生点（主 agent 是 Session 开始，子 agent 是父调用）。测试 `test_skill_anchor_uses_the_last_named_trigger` 的 `case-skill-missing` 就是这条。
- `discovery + agent` 的父节点存在但 `tool_use_id` 对不上 → `_birth_point` 返回 `None`（`:988-991`），保持 unknown，不降级到主 agent。
- `bad_case_agent_id` 为空 → 用该 Session 的 main agent（`_reporter_for`，`:919-927`）；`bad_case_agent_id` 指向不存在的 agent → 直接 `None`，不猜测。
- `discovery + agent` 的 reporter 是 main（异常数据）→ 没有父节点，退化成 main 的出生点（Session 开始），等价于 06 §7.4 的「锚 main、eventIndex=-1」。

一个值得注意的边界：`_birth_point` 把 `reporter.parent_agent_id is None` 也当成 main 处理（`:981`）。如果一条 subagent 的父关系是 unresolved（parent 列 NULL），它会被当成「主 agent 从 Session 开始就存在」，而不是 unknown；这会把很多 case 误判成「在对象之后」。见 §6 D10。

### 2.5 比较：时间优先，坐标兜底，strictly after

`compare_triggers`（`potential.py:382-416`）的规则与 06 §7.5 一致：

1. 双方 `triggered_at` 都非空 → 只比时间，严格大于才算 after；相等算 comparable 但 after=false。
2. 否则，双方 `(tree_index, event_index)` 都齐全 → 字典序比较。
3. 任一侧缺锚点或坐标不全 → `unknown`，after=false。

这里有一个隐含前提：对象进入点来自 DB，`tree_index/event_index` 一定齐全；case 锚点来自 `_birth_point` 或事件，可能缺。因此 unknown 基本只来自「上报 agent 解析不到」或「子 agent 的父调用找不到」。

### 2.6 五项分区与三层 summary：数字关系是自洽的

Session 段（`potential.py:548-594`）：

```
reported = associated + versionUnresolved + skipped + pending
```

- `pending`：窗口内有 case、但没有 `session_families` 行的上报根。
- `versionUnresolved`：在没有版本匹配事件的前提下，Session 有同名对象事件且至少一条事件 `object_version` 为 NULL；若存在匹配事件则优先算 associated，不因同 Session 另有 NULL 事件而降级。
- `skipped`：其余已归一化但没有任何版本匹配的根（包括「根本没有同名事件」）。
- `associated`：存在 `object_version == target_version` 的同名事件；只有它进 `items`。

潜在段（`potential.py:690-698`、`:815-837`）：

```
sum(byReason) = badCases
potential = self_report + after_object + both
badCases = potential + policy_excluded + order_unknown
```

`badCases` 是**关联 Session 内**的候选数，不是整个空间窗口的 case 数；`byReason` 五键零填充；items 只含 included。

归因段（`potential.py:700-743`）：

```
reused + fresh = potential
```

`reused` 是 included 集合中既有 `probe_reports.cache_key` 的精确数；`cacheEnabled=false` 时 `reused=0`、`fresh=potential`。`nonTargetKnown` 是**历史参考值**，不是本次潜在集合的子集，也不是与 `reused` 互斥的第四块——同一个历史 case 可能既在 `reused` 里，又被算进 `nonTargetKnown`。UI 不能把四个数相加。见 §6 D9。

### 2.7 只读与批量：没有 per-case N+1，但有「全量搬运」

`PotentialRepository` 的每个方法都先按 500 个标识分块，再 `IN` 查询（`crud/potential.py:29-35`、`:160-180`、`:182-235`、`:237-275`、`:277-325`、`:327-340`）；没有任何「循环里按 case 查一次」的路径。七个查询分别是：窗口 case、Session 元数据、对象事件、agents、锚点事件、既有 cache key、历史 non_target（`07:1151`）。

但批量不等于有界：

- `list_window_cases` 没有 SQL `LIMIT`，窗口最长 366 天（`potential.py:53`），最多把整个空间的窗口 case 拉进 Python。
- `list_object_events` 按 session 拉**所有同名事件**（不过滤版本），`list_agents` 拉**关联 Session 的全部 agents**，`list_anchor_events` 拉**所有 involved agent 的所有 `kind=agent` 事件 + 指定 skill 事件**（`crud/potential.py:182-325`）。
- 第 2 步为了给 4 行 Session 算 `potentialCount`，会对全部关联 Session 跑一遍完整 `potential_cases`（`potential.py:769-773`），等于「为了看 4 本书的封面，把整个图书馆的书搬到桌上」。
- 三段预览各自独立重算，没有按条件缓存；窗口/目标不变时，第 2、3、4 步会重复同样的重查询。

当前没有生产真实数据，所以无实害；一旦空间有大量 Session/agent/事件，这是内存和延迟的第一风险。见 §6 D6。

### 2.8 target 类型扩 knowledge：契约宽了，配置路径仍按 git 对象走

`EvolutionObjectType` 扩为 `skill|agent|knowledge`（`crud/evolution_targets.py:21`），`EvolutionTargetWrite` 与 record 同步（`targets.py:35`）。但：

- `bad_cases.object_type` 与上报契约仍是 `skill|agent`（`ingest.py:72`；06:902），`probe_reports.probe_type` 的首版归因引擎也仍限 `skill|agent`。
- `create` / `update` 仍然对所有对象类型执行 `_validate_remote`（`targets.py:309`、`:454-459`），也就是必须是一个能通过 `git ls-remote` / ref 校验的仓库；`versions` 也仍然返回 git tags（`:390-410`）。如果 knowledge 对象不是 git 仓库，配置时就会 422 `REPO_INVALID`。
- 向导目录 `CatalogService.targets` 在 DB 查询后按 `row.object_type in {"skill","agent"}` 过滤（`catalogs.py:68-87`），所以 knowledge target 不会出现在向导第 1 步；target 管理页仍会列出来，但表单没有 knowledge 选项。
- run 侧 `ProbeQueryRequest.target_type`、`stages.py` 的 `EvolutionTargetRun`、`runs.py` 的 `RunTarget.type` 仍是 `skill|agent`（`probe_query.py:35`、`stages.py:63`、`runs.py:55`），在能通过 git 校验的前提下，knowledge target 目前**只能配置和预览，不能启动 run**。这与 PR 的「m10-04 接 run」一致，但需要在文档里明确「可配置 ≠ 可启动」。

15 §9.3 允许 `object_type` 只在知识事件、target 配置与 PotentialMatcher 同一切片内扩展，§9.5 要求 M10 消费 M9 证据且不得对 `unknown` revision 做名称级猜测。本 PR 的 target/PotentialMatcher 类型扩展符合 §9.3 的切片，但 §9.5 的「消费 M9 证据」只做到 `object_version`，没有用 `object_revision`（D1）；15 §9.4 的完成状态/任务快照与本 PR 无直接关系，未改动是合理的。

### 2.9 API、鉴权与错误矩阵

## §3 数据流走查

主线用向导第 2–4 步的一个具体场景：workspace `ws-a`，target `deep-research`（skill，`defaultRef=v2.0.0`），窗口 2026-11-01..2026-11-30。Session `S1` 在 10:00 第一次触发 `deep-research@v2.0.0`，10:30 有一个 `other-skill` 的 discovery case；Session `S2` 只有 `deep-research` 事件但 `object_version=NULL`；Session `S3` 只有 `v1.0.0`；Session `S4` 有窗口 case 但没有 `session_families`。

### 3.1 第 2 步：条件归一化

`preview_sessions` → `PotentialPreviewService.sessions`（`potential.py:758-798`）：

1. `_condition` 调 `enabled_config`，在 URL 空间内找 enabled 的 `(skill, deep-research)`；找不到 → 409 `TARGET_NOT_CONFIGURED`（`targets.py:412-452`）。
2. 没带 `targetVersion` → 取 `defaultRef=v2.0.0`；空版本 → 422 `VALIDATION_INVALID`（`potential.py:887-893`）。
3. `resolve_window`：没带 `from/to` → 今天往前 89 天（inclusive 90 天）；`from > to` 或 >366 天 → 422；再转成 Asia/Shanghai 半开区间（`potential.py:455-487`、`crud/potential.py:371-376`）。
4. 得到 `MatchCondition(workspace_id, target_type, target_name, target_version, window_start, window_end)`（`potential.py:277-287`）。

### 3.2 第 2 步：Session 关联与分区

`associated_sessions`（`potential.py:511-594`）：

1. `list_window_cases` 取窗口内 `bad_case_type IN ('self','discovery')` 的 case（`crud/potential.py:109-158`），按 `created_at, bad_case_id` 排序；这里只取 `ws-a`。
2. `session_ids` 去重排序；`list_sessions` 取 `session_families` 元数据（`crud/potential.py:160-180`）。
3. `list_object_events` 对已归一化的 Session 取 `kind=skill, name=deep-research` 的全部事件（`crud/potential.py:182-235`）。
4. 逐个 Session 判断：
   - `S1` 有 `object_version=v2.0.0` → associated；`object_entry` 取最早匹配事件（10:00）。
   - `S2` 有同名事件但 `object_version=NULL` → versionUnresolved。
   - `S3` 只有 `v1.0.0` → skipped。
   - `S4` 不在 metas → pending。
5. 返回 `reported=4, associated=1, versionUnresolved=1, skipped=1, pending=1`，`sessions=[S1]`，`cases` 是所有四条 case 的快照。

然后 service 用默认策略再跑一次 `potential_cases`，只为给 S1 算 `potentialCount`（`potential.py:769-773`）；第 2 步返回 4/页。

**如果把这个场景换成 knowledge target、且 S1–S4 的命中事件都是 knowledge 读事件**：parser 写的 `object_version` 都是 NULL，`object_revision` 是 `digest:…`；分区结果就是 `associated=0, versionUnresolved=4`，`sessions` 为空，service 在 `:766-768` 直接抛 409 `NO_ASSOCIATED_SESSIONS`。用户看不到 `versionUnresolved=4` 这个最有用的解释。

### 3.3 第 3 步：策略与命中原因

`preview_potential` → `_condition` → `resolve_policy` → `associated_sessions` → `potential_cases`（`potential.py:800-837`）。

用 §2.3 的 S1 例子，四条 case：

| case | 类型 | 名称 | 触发点 | 默认策略结果 |
|---|---|---|---|---|
| `case-self-early` | self | deep-research | 09:00（skill 最后一次） | self_report |
| `case-after-other` | discovery | other-skill | 10:30 | after_object |
| `case-before-other` | discovery | early-skill | 08:30 | policy_excluded |
| `case-after-self-other` | self | other-skill | 10:30 | after_object（self 名称不匹配，但 after 成立） |

`potential_cases` 先按关联 Session 过滤 case，再取 agents、main、锚点事件（`potential.py:612-688`）；对每条 case：

1. `_reporter_for` 解析上报 agent（`bad_case_agent_id` 为空 → main）。
2. `_resolve_case_trigger` 取锚点/出生点。
3. `compare_triggers` 得到 `comparable/unknown` 与 `after`。
4. `evaluate_hit` 得到 `hit_reason` 与 `included`。
5. `trigger_at`：有锚点时间用锚点时间，否则用 `created_at`。

summary：`badCases=4, potential=3, byReason={self_report:1, after_object:2, policy_excluded:1, both:0, order_unknown:0}`；items 按 `trigger_at` 倒序、`badCaseId` 升序分页，5/页。

### 3.4 第 4 步：只读缓存预览

`preview_attribution` → `_condition` → `resolve_policy` → `associated_sessions` → `potential_cases` → `attribution_preview`（`potential.py:839-873`）。

对 3 条 included case：

1. 用 `attribution_cache_key(workspace, case_id, target_type, target_name, target_version, "v1", "rule-v1")` 算 3 个 key（`crud/attributions.py:39-64`）。
2. `existing_cache_keys` 查既有 probe 的 `cache_key IN (...)`，返回 2 个 → `reused=2`。
3. `count_non_target_cases` 查该对象·版本历史 `conclusion='non_target'` 的去重 case 数，假设 1 → `nonTargetKnown=1`。
4. 返回 `potential=3, reused=2, fresh=1, nonTargetKnown=1`；不写 probe、不写 `bad_case_analysis`、不写候选行。

**只读证据**：matcher 测试和 API 测试都在调用前后对 `probe_reports`、`bad_case_analysis`、`evolution_run_candidates`、`bad_cases` 计数（`test_matcher.py:673-703`、`test_preview_api.py:581-621`），结果不变。

### D1 版本关联只比较 `object_version`：knowledge 真实数据永远不关联，15 §9.2 的 `targetVersion → objectRevision` 未落实

- **位置**：`apps/api/app/service/evolution/potential.py:551-582`（只比较 `event.object_version`）、`apps/api/app/db/crud/potential.py:198-213`（只 select `object_version`，不 select `object_revision`）、`apps/api/app/service/acquisition/parsers/base.py:462-501`（knowledge 事件只写 `document_revision/object_revision`，`object_version` 默认 NULL）、`apps/api/app/service/acquisition/parsers/claude_code.py:526-539`（skill/agent 只有显式版本才写 `object_version`）、`plans/fullstack-design/15-v1-v2-gap-analysis.md:158`（要求解析为 `objectRevision`）、`plans/fullstack-design/05-api-design.md:1241`、`06:901`、`07:1153`（本 PR 改成只与 `object_version` 比较）
- **现象**：
  1. knowledge 事件在当前 parser 下 `object_version` 恒为 NULL；实测一次文件读事件：`object_version=None, object_revision="digest:…"`。用 support 的播种 helper 复现同样形状后，matcher 输出 `reported=1, associated=0, versionUnresolved=1`。

  3. MCP knowledge 事件可以带 `object_revision="tag:v9"` / `"provider:…"`（`tests/m9-05.../test_knowledge_mcp.py:379-426`），同样不可见。
  4. 测试 `test_knowledge_target_uses_the_same_entry_point_and_order`（`test_matcher.py:450-504`）与 `test_knowledge_target_is_configurable_and_previewable`（`test_preview_api.py:529-578`）直接给 knowledge 事件播种 `object_version="rev-1"`——这是生产 parser **不会产生**的行，测试因此通过。

  当前把 15 §9.2 留成旧文本、05/06/07 改成只比 `object_version`，等于让同一份设计语料互相打架；无论选 A 还是 B，都要把 15 的 §9.2 改到与实现一致。
- **结论**：

### D2 knowledge target 仍走 git 对象校验，且向导/run 都不接受它：可配置 ≠ 可启动

- **位置**：`apps/api/app/service/evolution/targets.py:32-39`（`object_type` 扩 knowledge）、`:290-323`（`create`）、`:454-459`（`_validate_remote` 对所有类型执行 git validate）、`:390-410`（`versions` 返回 git tags）；`apps/api/app/service/catalogs.py:68-87`（catalog 过滤 knowledge）；`apps/api/app/service/evolution/probe_query.py:35`（run 请求仍 `skill|agent`）；`apps/api/app/service/evolution/stages.py:63`、`runs.py:55`（run DTO 仍 `skill|agent`）；测试 `tests/m10_02_potential_support.py:403-413`（`FakeGitRemote` 接受任意 URL）
- **现象**：`POST /targets` 接受 `objectType=knowledge`，但 `_validate_remote` 仍要求 `repoUrl/defaultRef` 通过 git 校验；如果 knowledge 对象不是 git 仓库，配置直接 422 `REPO_INVALID`。`GET /targets/{id}/versions` 也仍拉 `git ls-remote` 的 tags，而不是文档 revision。向导 catalog 明确过滤 knowledge，target 表单也没有 knowledge 选项，run 的 `ProbeQueryRequest` 仍拒绝 knowledge。测试用 `FakeGitRemote` 让 knowledge 创建通过，掩盖了真实校验。
- **问题**：设计 06 §7.5 说「knowledge target 通过既有 target CRUD 配置」（`06:902`），但既有 CRUD 的字段语义是 git 对象（repo/subDir/defaultRef）；knowledge 的 M9 证据是 `source_path`/`document_revision`/`object_revision`，两者没有映射。PR 的「可配置」在真实环境可能意味着「必须给它编一个能过 git 校验的仓库」，而不是配置知识对象。另一方面，target 管理页会显示 knowledge target，但表单无法新建/切换，管理员只能走 API；这作为 m10-04 前的过渡可以接受，但需要写明。
- **预判**：建议在本 PR 或 m10-04 前定一件事：knowledge target 的 `repoUrl/subDir/defaultRef` 到底代表什么。若 knowledge 文档也在 git 仓库里，`defaultRef` 是仓库 tag，则 `_validate_remote` 可保留，但 `versions` 与 `object_revision` 的映射要写清楚；若 knowledge 是本地/Provider 文档，则 knowledge 分支应跳过 git 校验，`versions` 返回可用的 revision 列表（或明确 422 不可用），并在 target 表单/catalog 里给出说明。至少要把测试从 `FakeGitRemote` 换成能区分「knowledge 不该走 git」的断言。
- **结论**：

### D3 第 2 步在 `associated=0` 时返回 409：05 §4.20 却写「仍返回 200」，而且 `versionUnresolved` 被错误信息吞掉

- **位置**：`apps/api/app/service/evolution/potential.py:766-768`（`if not association.sessions: raise _no_associated_sessions()`）、`:810-811`、`:856-857`（三段都抛）；`plans/fullstack-design/05-api-design.md:1248`（同一行既写「无关联 Session（三段都触发）→ 409」又写「第 2 步仍返回 200，由 `associated=0` 表达空态」；§4.9 的 `05:929` 又写「向导把 409 映射为空态」）；`plans/fullstack-design/07-backend-implementation.md:1190`（「无关联 Session → 409（三段都触发）」）
- **现象**：代码在三段都先判 `association.sessions`，空就 409；05 §4.20 同一节里既有「三段都触发 409」又有「第 2 步仍返回 200」。这不是文案小错：在 knowledge 场景下，`versionUnresolved` 是唯一能解释「为什么没有关联」的数字，但 409 响应只有 code/message，没有 summary；用户/向导只能看到「no session is associated」，看不到「有 4 个 Session 命中了名称但版本为空」。测试 `test_no_associated_sessions_returns_409` 把三段 409 固化了（`test_preview_api.py:439-471`），与 05 的 200 句直接冲突。
- **问题**：第 2 步的产品职责是「展示关联/跳过/待同步」，空态本身也是信息；把它变成 409 会让「空态」和「调用出错」不可区分，尤其 `versionUnresolved` 全部命中时。若坚持 409，至少应在 error details 里带 `summary`（reported/associated/versionUnresolved/skipped/pending），否则第 2 步的数字永远无法送达。05 §4.9 还说「向导把 409 映射为空态并禁用出口」（`05:929`），说明 UI 确实需要空态；这与 §4.20 的 200 句也不一致。
- **预判**：建议第 2 步在 `reported>0` 时返回 200 + summary（`associated` 可为 0），只有 `reported=0`（窗口内完全没有 case）才考虑 409；潜在段/归因段仍按设计在 `potential=0` 时 409。若维护者认为「无关联就 409」是既定契约，则改 05 §4.20 的 200 句，并给 409 加 summary details。两种都能接受，但不能同时保留。
- **结论**：

### D4 `engineKey` 校验的是 run engine 注册表（full/cluster_only），缓存 key 却固定 `rule-v1`：参数语义含混

- **位置**：`apps/api/app/service/evolution/potential.py:185-189`（`AttributionPreviewRequest.engine_key`）、`:848-854`（`EngineFactory.is_registered`）、`:717-731`（cache key 固定 `ATTRIBUTION_ENGINE="rule-v1"`）；`apps/api/app/service/evolution/engine/factory.py:14-24`（注册表只有 `full` / `cluster_only`）；`plans/fullstack-design/05-api-design.md:1247`（「engineKey 只做已注册校验」+「缓存键仍按 rule-v1」）；`plans/fullstack-design/07-backend-implementation.md:1155`（policy v1 + rule-v1）
- **现象**：`EngineFactory` 是 **run engine** 注册表（`full` / `cluster_only`，用于启动完整 run 或仅聚类），不是归因引擎注册表。预览传 `engineKey="rule-v1"`（05/07 里说的归因引擎）会 422 `ENGINE_INVALID`；传 `engineKey="full"` 会通过校验，但 `attribution_preview` 完全不使用它，cache key 仍按 `rule-v1` 算。`cacheEnabled` 本身是自洽的：false → `reused=0`、`fresh=potential`。
- **问题**：一个「可选 engineKey」同时承担两种可能语义：run 的调度引擎，或归因引擎。当前实现选择了前者，但文档把它写在「归因预览」行里，并说缓存键固定 rule-v1；调用方按文档传 `rule-v1` 会失败，传 `full` 又没有效果。将来新增归因引擎 `rule-v2` 时，预览仍只能数 `rule-v1` 的键，无法预览新引擎的复用率；这与 07 §5.13「换归因引擎只注册新 key，缓存键自动隔离」的扩展路径不匹配。
- **预判**：需要拍一个语义并改名/改校验：
  - 如果它确实是 run engine（为 m10-04 预留）：文档应写「run engineKey，仅校验注册，不参与预览」，测试补 `engineKey="full"` 通过、`"rule-v1"` 422，并说明预览固定 rule-v1。
  - 如果它应是归因引擎：新建 `AttributionEngineFactory`（或 registry）校验 `rule-v1`，cache key 用传入的 key；这样 `rule-v2` 可预览。
  当前两者混用，至少应删掉「归因预览 + engineKey」的歧义，否则 m10-04 接线时容易把 run engine 当成归因引擎。
- **结论**：

### D5 `self` 与 `sameObjectOnly` 只按名称：同名 skill/agent、跨版本 self 报告会被误纳

- **位置**：`apps/api/app/service/evolution/potential.py:661-667`（`same_object = case.object_name == condition.target_name`）、`:440-449`（`self_hit = self_match && includeSelf`）、`:634-636`（只有 skill 名称参与锚点）；`plans/fullstack-design/06-database-design.md:896`（默认策略 `object_name == target.name AND bad_case_type='self'`；`sameObjectOnly` 再按名称过滤）、`Note:17`；测试 `test_matcher.py:156-176`（self 忽略 case 的 `object_version`）、`:314-374`（sameObjectOnly 只按名称）
- **现象**：`bad_cases.object_type` 仍只有 `skill|agent`，所以「同名不同类」是可能的：一个名为 `Explore` 的 skill 自报问题，会满足 agent target `Explore` 的 `object_name == target.name`，被算成 self_report；`sameObjectOnly` 也不会挡住它。另一个例子：target `deep-research@v2.0.0`，一条 `self` case 的 `object_version=v1.0.0`，仍会被算进 v2 的潜在集（测试明确锁定了这一点）。当前文档把原因写成「bad_cases.object_type 没有 knowledge，所以不比较类型」，但 skill/agent 类型是存在的，这个理由不足以解释跨类型误纳。
- **问题**：策略语义是「潜在 bad case 是否可能由该对象引起」；同名不同类、同名不同版本的 self 报告是否应算，是产品判断，不是实现细节。若保持名称-only，建议在文档和 UI 里明确「self 报告按名称，不区分类型/版本」；若要收紧，可在 `bad_cases.object_type != 'knowledge'` 时比较类型（skill/agent），而 knowledge 继续只按名称；版本是否参与 self 规则需要单独拍（当前明确不参与）。这不会破坏 custom 真值表，只影响 `self_match` 与 `same_object` 的输入。
- **预判**：建议至少把「同名不同类/跨版本」写成已知语义，并补一条测试断言当前行为；如果维护者认为这是误纳，再改 `self_match`/`same_object_only` 的判定。不要在没有产品结论前默默改，因为 `sameObjectOnly` 的现有测试和 06 §7.5 都写的是名称-only。
- **结论**：

### D6 性能：没有 per-case N+1，但全量 case/agents/events 进 Python，第 2 步为 4 行算全量 potential

- **位置**：`apps/api/app/db/crud/potential.py:109-158`（窗口 case 无 LIMIT）、`:182-235`（同名事件全量）、`:237-275`（关联 Session 全部 agents）、`:277-325`（involved agent 的全部 agent 事件 + skill 事件）；`apps/api/app/service/evolution/potential.py:511-594`（全部分区）、`:596-698`（全部 case 评估）、`:769-773`（第 2 步为 potentialCount 跑全量 potential）、`:815-837`（排序后切片，不是 SQL 分页）
- **现象**：七个批量查询都按 500 分块，没有 per-case 查询，这点做得对。但窗口最长 366 天，`reported` 可能是几千个 Session；每个 Session 的全部 agents、所有 involved agent 的 `kind=agent` 事件、同名 skill 事件都会成为 Python 对象。第 2 步只显示 4 行，却要为所有关联 Session 计算 `potentialCount`；第 2/3/4 步各自重算，没有条件级缓存。最坏情况是「大空间 + 366 天 + 多 agent 树」，内存和延迟会随 Session 数线性甚至超线性增长，而 API 的 `pageSize` 最大还允许 50（`potential.py:169/181`），大页会放大单次成本。
- **问题**：设计 07 §5.12 要求「一次取…不做 per-case 查询」，但没有要求「有界」。预览是向导的交互路径，用户在第 2 步只等 4 行；为 4 行搬全量数据不划算。当前没有生产真实数据，所以无实害；一旦接上真实空间，这会先于功能问题暴露。
- **预判**：建议至少做一件低成本的事：① 第 2 步只对当前页的 Session 计算 `potentialCount`（或把 potentialCount 改成按 Session 的聚合查询），避免为 4 行算全量；② 给 `list_window_cases`/`list_object_events` 加窗口内上限或按 Session 分页；③ 按 `(workspace, target, version, window)` 做短 TTL 缓存，三步共享；④ 用真实量级做一次 `performance:report` 或合成基准。若维护者认为 m10-04 的 run prepare 也需要同一份全量数据，至少把「预览全量」与「run 全量」区分开，不要让向导为 run 的量级买单。
- **结论**：

### D7 测试的真值表很扎实，但 knowledge 用例播种了生产不会出现的行，且缺 defaultRef/tag-only/engineKey 正例

### D9 summary 数字关系自洽，但 `nonTargetKnown` 与 `potential/reused` 不是互斥集合，UI 不能相加

- **位置**：`apps/api/app/service/evolution/potential.py:700-743`（`reused` / `fresh` / `nonTargetKnown`）、`:690-698`（`byReason`/included）、`:815-837`（`badCases`/`potential`）；`plans/fullstack-design/05-api-design.md:1246`（`nonTargetKnown` 是参考值）、`06:899`（历史 `conclusion='non_target'` 去重数）
- **现象**：三段 summary 的内部关系是自洽的：`reported = associated + versionUnresolved + skipped + pending`；`sum(byReason) = badCases`；`potential = self_report + after_object + both`；`reused + fresh = potential`。但 `nonTargetKnown` 是「该对象·版本历史 non_target 去重 case 数」，不按窗口、不按本次 potential 集合过滤；同一个历史 case 可能既在本次 `reused`（已有 cache key）里，又被算进 `nonTargetKnown`。所以四个数不是四块互斥饼图，UI 若画成「potential + reused + fresh + nonTargetKnown」会重复。
- **问题**：文档已经写「参考值，不是本次预计结果」，但没有给前端一个「不能相加」的显式提示；API 字段名 `nonTargetKnown` 也容易被读成「本次已知非目标数」。另外 `byReason` 的 `policy_excluded` 把「before object」「sameObjectOnly 过滤」「规则未启用」混成一类，排除行又不在 items 里，用户只能看到总数，无法解释具体原因；这是设计选择的封闭集合，不是 bug，但 UI 需要文案。
- **预判**：建议在 05 §4.20 或前端文案里明确「`reused + fresh = potential`；`nonTargetKnown` 是历史参考，可能与之重叠」；如果要做更可解释的第 4 步，可把 `nonTargetKnown` 拆成「其中本次也在潜在集」/「仅在历史」两个数，或至少加 tooltip。当前 API 不改也能用，属于口径/文案问题。
- **结论**：

### D10 小语义缝隙：targetName 不 trim、defaultRef 128 对 64、空 agent id、unresolved 父关系、混合时间戳、显示回退

- **位置**：`potential.py:164`（targetName）、`targets.py:37` + `potential.py:165` + `domain.py:247` + `claude_code.py:64-70`（defaultRef 128 vs 64）、`potential.py:925-927`（空 agent id）、`:981`（unresolved 父关系）、`:1016-1020`（混合时间戳）、`:565-569`（显示回退）、`:185-189`（无用分页）、`crud/potential.py:128`（未用字段）。
- **现象**：
  1. **targetName 不 trim**：preview 的 `target_name` 只有 `min_length=1/max_length=128`（`potential.py:164`），而 target 配置写入时 `_normalize_text` 会 strip（`targets.py:231-247`）；用户从别处粘贴带前后空格的名称，会在 target 查找时 409，而不是归一化后命中。
  2. **defaultRef 128 vs targetVersion/object_version 64**：`EvolutionTargetWrite.default_ref` 允许 128（`targets.py:37`），`SessionsPreviewRequest.target_version` 只允许 64（`potential.py:165`），`agent_events.object_version` 是 `VARCHAR(64)`（`domain.py:247`），parser 的 `_bounded_version` 还会截到 64（`claude_code.py:64-70`）。超过 64 的 defaultRef 既不可能匹配事件，也不会有 422；用户只会看到 409 无关联。
  3. **空字符串 agent id 不当作缺失**：`_reporter_for` 只判 `is not None`（`potential.py:925-927`），而 bad case 读取层 `_text` 把空串归一为 None（`bad_cases.py:164-166`）；legacy 行如果是 `""`，会被当成「指向不存在的 agent」→ unknown，而不是回退 main。
  4. **unresolved 父关系的 subagent 被当 main**：`_birth_point` 的条件是 `reporter.kind == "main" or reporter.parent_agent_id is None`（`potential.py:981`）；如果 subagent 的父关系是 unresolved（parent 列 NULL），它会拿到 Session `started_at` 作为出生点，而不是 unknown，可能把很多 case 误判成「之后」。15 §9.1 要求 unresolved 节点保留，06 §7.5 要求不猜测；这里与「不猜测」有张力。
  5. **混合时间戳的进入点排序**：`_entry_order_key` 把所有有 `triggered_at` 的事件排在所有无 `triggered_at` 的事件之前（`potential.py:1016-1020`）。如果同一 Session 的进入点既有带时间又有不带时间的事件，`min` 可能选到「时间更晚但带时间」的事件，而不是按 `(tree_index,event_index)` 更早的无时间事件；设计只说「triggered_at 优先，缺失时按坐标」，没有定义混合场景。
  6. **objectTriggerAt 显示回退**：`SessionPreviewItem.object_trigger_at` 在 `entry.triggered_at is None` 时回退 `session.started_at`（`potential.py:565-569`），但比较仍用坐标；UI 会把 Session 开始时间显示成对象进入时间，和实际比较口径不一致。
  7. **attribution 请求带无用分页**：`AttributionPreviewRequest` 继承 `page/pageSize`（`potential.py:185-189`），OpenAPI 里也暴露了它们，但响应没有分页；这是契约噪音，容易让前端误以为第 4 步可分页。
  8. **未使用的字段**：`WindowCaseRecord.object_version` 被 select 但 matcher 从不使用（`crud/potential.py:128`）；`PotentialCase.object_type/created_at` 仅存储不参与 DTO；`ResolvedPolicy.snapshot` 目前无调用方（`potential.py:95-102`）。这些不影响正确性，但会让读者以为「case 的 object_version 参与了匹配」。
- **问题**：单条都不改变主流程，但 2、4、5 会在真实边界上产生「看起来是 after，其实不确定」的结论；1 是常见的输入归一化问题；3 是 legacy 数据兼容问题。它们都适合趁 m10-04 接线前顺手定口径。
- **预判**：低成本修法：targetName 复用 `_normalize_text` 的 trim（或 preview 自己 strip）；defaultRef 与 targetVersion/object_version 统一到 64，或在 create 时拒绝 >64；`_reporter_for` 用 `case.bad_case_agent_id or None`；`_birth_point` 只把 `kind=="main"` 当主 agent，parent 缺失的 subagent 返回 None；混合时间戳时先按「双方都有时间才比时间，否则按坐标」统一到比较口径（选择进入点时也用同一规则）；`object_trigger_at` 在无时间时直接回退 `started_at` 但在 DTO 里标注 `estimated` 或保留 NULL；删除 attribution 的无用分页；删除/使用未读字段。若维护者认为这些是 m10-04 的范围，至少把 2/4/5 写成已知边界。
- **结论**：

## §9 文件级代码分析

> 每个文件：职责一句 + 变更形态 + 关键依赖 + 变更块（旧 vs 新）+ 检视发现。A 文件无旧版；M 文件用 `git diff main...HEAD` 对照。

### 9.1 `apps/api/app/service/evolution/potential.py`（A，1050 行）

**职责**：单一 `PotentialMatcher`（Session 关联、潜在策略、锚点/比较、归因缓存预览）+ 三段预览 service（条件归一化、分页、DTO）。

**关键依赖**：`pydantic`（请求/DTO，`IdentityModel` 的 camelCase alias 与 `extra=forbid`）、`app.db.crud.attributions.attribution_cache_key`（缓存指纹）、`EngineFactory`（engineKey 注册校验）、`EvolutionTargetService`（target enabled/defaultRef）。没有第三方匹配库；策略和坐标比较全是标准库/Python 逻辑。

**9.1.1 DTO 与常量（`:35-275`）**

- `OrderState`、`HitReason` 是封闭 Literal；`REASONS` 五键零填充。
- `PotentialPolicy` 用三个 `bool | None` 表示「是否携带开关」，`ResolvedPolicy` 才是物化后的四开关；`snapshot()`（`:95-102`）给 m10-04 落 `evolution_runs.potential_policy` 用，本 PR 无调用方。
- 请求模型：`SessionsPreviewRequest`（4/页）、`PotentialPreviewRequest`（5/页 + policy）、`AttributionPreviewRequest`（+cacheEnabled/engineKey）。`target_version` 空白 → None（`:171-175`）；`target_name` 不 strip（见 D10）。
- 响应模型：Session 五数 + items；Potential 三数 + byReason + items；Attribution 四数无 items。数字都有 `ge=0`，但 summary 之间的一致性由构造保证，不由模型保证。

**9.1.2 策略与真值表（`:105-157`、`:419-452`）**

- `resolve_policy` 的三种 422：default 携带开关、custom 缺开关、custom 两规则全关。`preset` 省略时默认 default，所以只传开关不传 preset 会 422（不是 custom）——这是一个值得知道的输入契约。
- `evaluate_hit` 的优先级是 `sameObjectOnly` 过滤 → `both` → `self_report` → `after_object` → `order_unknown` → `policy_excluded`；`order_unknown` 只在 `includeAfterObject` 时出现。
- 测试 `test_policy_truth_table.py:141-280` 覆盖了 default/custom 的组合矩阵，包括 `sameObjectOnly` 与 unknown 的交叉；这块是本 PR 质量最高的部分。

**9.1.3 窗口与比较（`:382-487`）**

- `compare_triggers` 时间优先、坐标兜底、unknown 不满足 after；`resolve_window` 支持单边界补齐到 90 天、拒绝倒置/超 366 天/越界日期。测试覆盖默认、单边界、越界；没有测「恰好 366 天」和「混合时间戳」。
- `MIN_SUPPORTED_DATE`/`MAX_SUPPORTED_DATE` 是为了避免 `end + 1 day` 溢出；`MAX_SUPPORTED_DATE=2999-12-31` 留了半开区间余量。

**9.1.4 Session 关联（`:511-594`）**

- 先取窗口 case，再取 session 元数据，再取同名对象事件；分区五项互斥。`associated` 用 `min(matching, key=_entry_order_key)` 取最早进入点。
- **核心问题**：`matching` 只按 `object_version` 过滤（`:551-557`），`version_unresolved` 只按 `object_version is None` 判断（`:579`）；不读 `object_revision`。这是 D1 的代码锚点。
- `object_trigger_at` 在 `entry.triggered_at is None` 时回退 `session.started_at`（`:565-569`），只影响显示/排序，不影响比较；见 D10。

**9.1.5 潜在评估（`:596-698`）**

- 先按 associated Session 过滤 case，再一次性取 agents、main、锚点事件；对每条 case 解析 reporter/trigger/compare/evaluate。没有 per-case DB 查询。
- `same_object` 只比名称（`:661`）；`self_match` 只比名称 + `bad_case_type='self'`（`:663`）；`bad_cases.object_type/object_version` 不参与。见 D5。
- `trigger_at` 用锚点时间，否则 `created_at`；`by_reason` 在全部 evaluated 上计数，included 只收 `included=True`。数字关系自洽。

**9.1.6 归因预览（`:700-743`）**

- `cache_enabled=False` 直接跳过 key 查询，`reused=0`；`non_target_known` 始终查历史。cache key 七元组固定 `POLICY_VERSION/ATTRIBUTION_ENGINE`；`engineKey` 不参与。见 D4。
- `existing_cache_keys` 只查 key 是否存在，不校验 probe 的 conclusion；因此历史 `non_target` 的 key 也会计入 `reused`，这是「复用结论」的语义，不是 bug，但会与 D9 的 `nonTargetKnown` 重叠。

**9.1.7 三段 service（`:746-903`）**

- `sessions` 在 `associated=0` 时 409（`:766-768`），即使 `versionUnresolved>0`；见 D3。`potential` 在 `included=0` 时 409（`:813-814`），`byReason` 被丢弃；`attribution` 同。
- `_condition` 的顺序是 target → version → window → policy（policy 在调用方）；`target_version` 为空时 422 `VALIDATION_INVALID`，没有走 `TARGET_NOT_CONFIGURED`。
- `attribution` 的 engineKey 校验在 association 之前（`:848-854`），但与 cache key 无关；见 D4。

**9.1.8 锚点辅助（`:906-1050`）**

- `_reporter_for`：`bad_case_agent_id is not None` 才查 agents；空串不会回退 main（D10）。
- `_resolve_case_trigger`：skill 取 reporter 的最后一条同名事件；`discovery+agent` 取父调用；其余出生点。
- `_birth_point`：main 或 `parent_agent_id is None` → Session start；子 agent 父调用找不到 → None；`parent_agent_id is None` 的 subagent 被当 main（D10）。
- `_entry_order_key`：有 timestamp 的一律排在无 timestamp 前，混合场景未定义（D10）。
- `_associated_order_key` 注释写「nulls last」，但 `object_trigger_at` 永远非空（有回退），注释略过时；无实害。

**检视发现**：D1（核心）、D3、D4、D5、D6、D9、D10；真值表与只读实现质量好。

### 9.2 `apps/api/app/db/crud/potential.py`（A，376 行）

**职责**：matcher 的只读仓储；七个批量查询 + 窗口日边界。

**关键依赖**：SQLAlchemy Core（`select/join/func`）、`Database.session()`、`as_shanghai`、domain 表。没有 ORM 关系加载，全部显式 select。

**变更块**：

- `_QUERY_CHUNK=500` + `_chunks`（`:29-35`）：所有 `IN` 查询按 500 分块，避免 SQLite/MySQL 参数上限；这是「无 per-case N+1」的基础。
- `list_window_cases`（`:109-158`）：`workspace_id`、`created_at` 半开窗口、`bad_case_type IN ('self','discovery')`；选择 `bad_cases.object_version` 但 matcher 不用（D10）。
- `list_sessions`（`:160-180`）：按 root 取 `session_families.id/title/started_at`。
- `list_object_events`（`:182-235`）：`agent_events JOIN agents`，按 `root_session_id IN`、`kind == object_type`、`name == object_name`；**只 select `object_version`，不 select `object_revision`**（D1）。
