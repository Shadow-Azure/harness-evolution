## §2 架构导览

### 2.1 渲染链路：从数据库列到 DOM

数据流只有一条主线，改动集中在最后一跳：

```text
bad_cases.bad_case_description（TEXT NOT NULL）
  → crud/bad_cases.py:191  reason=mapping["bad_case_description"]
  → schemas.py:140         reason: str（BadCase 必填字段，契约不区分格式）
  → ProblemDescription.vue:15  props.problem.reason
  → ProblemDescription.vue:50  reasonHtml = computed(() => renderMarkdown(props.problem.reason))
  → utils/markdown.ts:33-35    markdown.render(source)
  → ProblemDescription.vue:123 v-html="reasonHtml"
  → :176-256                   .problem-detail.markdown :deep(...) 排版
```

关键点：渲染发生在**展示层**，DB 与 API 仍按自由文本原样存储/返回；06:466 明确写了“HE 不校验、不改写、不对历史纯文本做迁移”。这避免了“入库时改写上游权威数据”的不可逆问题（Note 的 Alternatives 也记录了这一点）。

### 2.2 `renderMarkdown` 的安全配置与链接加固机制

`markdown.ts:4-8` 的 markdown-it 实例配置：

- `breaks: true`：单个 `\n` 变成 `<br>`。这是“历史多行纯文本立即按行显示”的唯一来源。
- `html: false`：原始 HTML 标签被转义成文本，而不是 DOM 节点。
- `linkify: true`：裸 `https://…` 与邮箱自动变成 `<a>`。

`markdown.ts:10-25` 的 `link_open` 覆盖是“包一层而不是换掉”的写法：先取出默认规则或手写 `renderToken`，再在 token 上 `attrSet("target", "_blank")` 与 `attrSet("rel", "noopener noreferrer")`，最后调用默认规则渲染。这样既拿到默认的 `href` 转义，又保证所有链接（显式 Markdown 链接、linkify 自动链接、mailto）都带安全属性。

实测探针结果：

| 输入 | 输出 | 说明 |
| --- | --- | --- |
| `<img src=x onerror=alert(1)><script>alert(2)</script>` | `&lt;img …&gt;…` 纯文本 | 原始 HTML 不生成节点 |
| `[x](javascript:alert(1))` | `[x](javascript:alert(1))` 纯文本 | markdown-it 的 `validateLink` 拒绝危险 schema，链接根本不生成 |
| 裸 `https://example.com/report` | `<a href="https://example.com/report" target="_blank" rel="noopener noreferrer">…</a>` | linkify 链接也吃到 `link_open` 加固 |
| `第一行\n第二行` | `<p>第一行<br>\n第二行</p>` | 单换行保留 |
| `![x](https://x/y.png)` | `<p><img src="https://x/y.png" alt="x"></p>` | **未被禁用**，见 §6.1 |
| `\| a \| b \|` + 分隔行 | `<table>…</table>` | **无对应排版**，见 §6.2 |

### 2.3 为什么 scoped CSS 必须用 `:deep()`

Vue 的 scoped CSS 会给组件模板里的元素加 `data-v-xxx` 属性，但 `v-html` 生成的内容是运行时字符串，没有这个属性。直接写 `.problem-detail p { … }` 编译成 `.problem-detail[data-v-x] p` 时，`p` 没有 `data-v-x`，规则不会命中。`:deep(p)` 编译成 `.problem-detail[data-v-x] p`（`p` 侧不带属性要求），专门解决这个问题。PR 在 `:176-256` 全部使用 `:deep()`，写法与本页已有的 `AttributionReport.vue:602-613` 一致。

### 2.4 数据侧约定与展示契约

- 05 §3.4（`:232`）：`reason` 是描述正文，按 Markdown 渲染，并列出 `html:false` / `breaks:true` / `linkify:true` 与外链加固。
- 06 §4.1（`:450` 表格、`:466` 说明）：`bad_case_description` 是自由文本，允许并鼓励 Markdown；不迁移历史纯文本。
- 08 §7（`:584`、`:587`）：问题描述正文的排版与归因文本边界。
- design-v2（`:217`）：原型侧同一约定。

### 2.5 组件结构没有变

模板层级仍是：标题行 → 元信息 → 正文块 → 事实 chips → 关联行 → 降级诊断。唯一变化是正文块从文本插值变成 `v-html`，并多了一个 `markdown` 类；`data-testid="problem-detail"` 保留，E2E 选择器不受影响。

## §6 讨论点

### 讨论点 1：Markdown 图片语法绕过了“禁用原始 HTML”的边界

- **位置**：`apps/web/src/utils/markdown.ts:4-8`、`apps/web/src/pages/errors/components/ProblemDescription.vue:123`
- **现象**：`html:false` 只转义原始 HTML；markdown-it 默认的 image 规则仍然生效。实测 `renderMarkdown("![x](https://x/y.png)")` 输出 `<p><img src="https://x/y.png" alt="x"></p>`，`v-html` 会把它插进 DOM。新增的原始 HTML 测试（`ProblemDescription.test.ts:239-257`）只覆盖 `<img src=x onerror>` 这种裸标签，冒烟里“0 script/img/iframe”也只对该 fixture 成立。
- **问题**：`BadCase.reason` 是外部上报文本，等于让上游可以借 Markdown 图片触发任意外部请求（跟踪像素、泄露 IP / Referer），并让“禁用原始 HTML、不引入额外加载面”的表述比实际更宽。它不构成脚本执行面（`img` 不能执行脚本），所以不是 XSS。
- **预判**：如果产品意图是“只排版文本、不加载远端资源”，在 `markdown.ts` 初始化后 `markdown.disable("image")`（或渲染后过滤 `<img>`），并补一条 `![...]` 测试；如果接受 Markdown 图片（例如贴截图链接），就把 05/06/08 与 PR 描述的边界改成“允许 Markdown 图片，仅禁用原始 HTML”，并给 `:deep(img)` 补 `max-width: 100%`。同页 `reasoning` 早就允许 Markdown 图片，所以当前无实害；但这是把渲染器接给更不受控输入后最值得先拍板的一条。
- **结论**：已修（2026-11-18）：问题描述关闭 Markdown 图片，图片语法降级为 alt 文本；新增组件/工具测试，避免外部请求。默认 `renderMarkdown` 仍保留图片，归因推理行为不变。

### 讨论点 2：渲染器输出面大于排版面，table / blockquote / hr / img 没有样式

- **位置**：`apps/web/src/pages/errors/components/ProblemDescription.vue:176-256`、`apps/web/src/utils/markdown.ts:4-8`、`plans/ui-prototype-v2/harness-evolution.html:465-476`
- **现象**：`:deep()` 只覆盖 p / ul / ol / li / code / pre / strong / a / h1–h6。markdown-it 还会产出 `table`、`blockquote`、`hr`、`img`、`em`；实测 `| a | b |` 两行会生成 `<table>`，`> quoted` 生成 `<blockquote>`，`---` 生成 `<hr>`。这些节点没有对应的间距、边框、宽度约束，`table` 与 `img` 可能把卡片撑出横向溢出。

## §9 文件级代码分析

### `apps/web/src/pages/errors/components/ProblemDescription.vue`（M）

职责：错误详情「问题描述」tab 的卡片。改动形态：M；前身用 `{{ problem.reason }}` 纯文本插值。

旧代码（`git show origin/main:apps/web/src/pages/errors/components/ProblemDescription.vue:117-122`）：

```vue
<div
  class="problem-detail"
  data-testid="problem-detail"
>
  {{ problem.reason }}
</div>
```

新代码（`:119-125`）：

```vue
<!-- eslint-disable vue/no-v-html -- MarkdownIt raw HTML is disabled and links are hardened. -->
<div
  class="problem-detail markdown"
  data-testid="problem-detail"
  v-html="reasonHtml"
/>
<!-- eslint-enable vue/no-v-html -->
```

`reasonHtml` 在 `:50` 用 `computed` 派生，因此 `problem.reason` 变化时会重渲染；不会把 HTML 缓存进 props 或跨组件状态。

为什么这么写：复用同页已验证过的 `renderMarkdown`，不新增依赖，也不把“是不是失败清单”的判断塞进组件；`eslint-disable` 注释与 `AttributionReport.vue:287-292` 保持同一套说明，读者能立刻知道这里的 `v-html` 是有意为之。

排版层（`:176-256`）用 `.problem-detail.markdown :deep(...)`，逐类补间距与色彩：`p` 7px 下距、`ul/ol` 18px 左缩进、`li` 1px、`code` 10.5px `--mono` + `--bg-inset` chip + `overflow-wrap:anywhere`、`pre` 横向滚动、`strong` 650、`a --blue`、`h1–h6` 统一 12px/700。`.problem-detail` 本身的 12.5px / 1.7 / `--text-dim`（`:169-174`）没变，所以“普通文本不变、只有 Markdown 结构获得层级”的目标成立。

检视发现：安全与排版主体没问题；渲染器输出面大于排版面（§6.2），Markdown 图片未被禁用（§6.1），标题保留 h1–h6 会污染文档大纲（§6.5）。逻辑上无缺陷。

### `apps/web/src/utils/markdown.ts`（M）

职责：全站唯一的 Markdown → 安全 HTML 渲染器。改动形态：M，只改 JSDoc（`git diff` 显示 `+7 −3` 中仅注释与两行 docstring）。

```ts
/**

```

新注释（`:27-35`）：

