## §2 架构导览

### 2.1 兼容面为什么单独成页

`docs/compatibility.md:7-17` 用一张表把端点、路由、run schema、可空列、内联字段、深链和目录同步放在同一坐标系里。每一行都是“现状 → 删除条件”，不是“以前如何”。这样删除 PR 只需按表逐行关闭，避免在 architecture、Note 和 plans 之间找散落的条件。

`docs/compatibility.md:21` 把“下个大版本”落成 V3，并明确“至少覆盖一个已发布 V2 版本”。这是本 PR 唯一新增的产品/流程命名，理由见 §6 讨论点 1。

`docs/compatibility.md:23-32` 是机械清单：先搜索残留，再删前端、后端/契约、数据库、数据、测试、文档，最后删重定向。顺序有意把“确认无调用”放在删除之前，把“回填列”放在收紧 NOT NULL 之前。

### 2.2 architecture 如何保持“现状地图”

`docs/architecture.md:27-31` 只保留请求链路和页面壳的关键事实：谁能进、空间路由怎么收口、Session/错误详情/运行详情各自的事实。`docs/architecture.md:35-44` 按数据层分组：空间三表、凭据上报、多归因、证据、知识触发、任务/重放、上游/normalize、兼容边界。

证据门禁写到 `docs/architecture.md:39`：关系置信度四级、`execution_outcome` 独立于解析状态、未知 revision 不猜名。知识触发写到 `:40`：只认空间知识根或 Provider/Collection 返回的文档，存身份与来源，不存全文。两处都是 M9 的实现事实，不是未来计划。

### 2.3 为什么 development 只加一句

`docs/development.md` 是步骤型 home。这里只加“删除兼容层前按 compatibility 清单执行”的入口，不复制 8 步；architecture 只链接兼容页，也不复制清单。符合“现状 → docs、步骤 → development、理由 → Agent Note”的分层。

### 2.4 设计 Note 的同步不是改历史

旧 Note 的正文保留原决策，只把“m11-06 退役”改成“V3 退役并指向 compat”。`workspace-shell-routing` 还修正了三处已落地事实：默认落地页是 `overview`、错误详情用空间归因端点、四步向导用空间 preview。这是 Note 规则要求的“随实际落地保持同步”，不是重写决策。

## §3 文档流走查

一个后来者问“`/api/probes/{id}` 能不能删”，理想路径是：

1. 打开 `docs/README.md` 地图，看到 `compatibility.md` 的“V1 兼容面、触发版本与机械退役清单”。
2. 进入 `docs/compatibility.md:11`，确认该端点属于 V1 读端点，删除条件是 V3 且无调用。
3. 需要理由时点开 `docs/compatibility.md:5` 的 Agent Note，看到“现在删会破坏旧书签、外部客户端和兼容页”的取舍。
4. 真要删除时回到 `docs/compatibility.md:25`，按 8 步执行；第 1 步的 `rg` 会同时扫 apps、packages、tests、fixtures、docs。
5. 删除 PR 完成后，按同页第 7 步更新 architecture 与 owning Note，并跑 `verify:docs`、`verify:flow`。

这条路径保证“条件、理由、步骤”各有一个 home，读者不需要在 architecture 里读长清单。

## §6 讨论点

### D1 触发版本命名

**位置**：`docs/compatibility.md:21`

**现象**：全库此前只有“下个大版本”的自然语言，没有 V3 的机读定义。

**问题**：新增 V3 命名是否越权或与 roadmap 冲突？

**预判**：issue 明确要求“记录下个大版本移除条件”，不命名就无法机械判断；V3 是 V2 之后第一个主版本的直白定义，且只写在本页与 Note，不新增 milestone。

**结论**：已决（2026-11-17）——接受 V3；若未来 roadmap 采用别的命名，同 PR 替换本页、Note 与 plans 的链接即可。

### D2 architecture 压缩丢失旧事实

**位置**：`docs/architecture.md:41-42`

**现象**：初稿压缩时删掉了 `sync_runs` 先终结再释放、重放按 root 原子重写两条既有事实。

**问题**：更新现状不等于删旧现状；这两条仍是任务/重放边界。

**预判**：恢复为一条紧凑的任务/重放 bullet，不增加新页。

**结论**：已修复（2026-11-17）——`:41` 恢复单飞、`sync_runs` 终结、payload 唯一键与原子重放。

### D3 内联归因的现状被写窄

**位置**：`docs/compatibility.md:15`

**现象**：初稿写 `BadCase.analysis` “只服务 V1 列表与兼容读”，实际列表卡仍读它。

**问题**：这会让删除 PR 误以为 V2 列表已不依赖该字段。

**预判**：按实际行为改写，并把删除条件写成“列表卡不再读取”。

**结论**：已修复（2026-11-17）。

### D4 legacy 目录同步是否属于兼容面

**位置**：`docs/compatibility.md:17`

**现象**：主通道是凭据上报，但 `HE_BAD_CASE_CATALOG_SYNC_ENABLED` 仍保留历史导入。

**问题**：不登记就会在 V3 漏掉一条默认关闭的写路径。

**预判**：登记为独立兼容面，条件写成“默认空间不再需要历史导入”。

**结论**：已补充（2026-11-17）。

### D5 预算提高

**位置**：`scripts/doc-budgets.manifest.json:7-8`

**现象**：architecture 960 → 1080，compatibility 新增 780。

**问题**：是否用提预算代替压缩？

**预判**：退役步骤已搬到新页，architecture 新增六类 V2 事实且压缩了旧 UI 细节；compatibility 承载完整清单，780 词仍低于其信息密度。提预算在 PR 描述说明，符合“搬层 → 压缩 → 提预算”。

**结论**：接受（2026-11-17），PR 描述已说明理由。
