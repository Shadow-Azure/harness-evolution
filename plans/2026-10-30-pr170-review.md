## §1 一页速览

**一句话**：向导第一步从「按钮替人判断能不能点」改成「点击后告诉用户哪个框错在哪里」，同时把 `409 NO_PROBES_MATCHED` 解释为查询成功但结果为空，让用户进入第二步看到空态并只能返回调整条件。

**一个比喻**：旧按钮像不开门的办事窗口，用户只能猜缺哪份材料；新按钮像先收表单的窗口，逐项指出缺什么；如果材料齐全但系统回复“没有匹配记录”，它不再把这句系统话当成事故，而是带你到下一页的结果栏，明确显示空结果。

## §2 架构导览

### 2.1 向导是唯一前端消费点

`LaunchWizard.vue` 用 `step` 表达两步，用 `preview` 表示有命中，用新增 `emptyResult` 表示“查询成功但零命中”，用 `fieldErrors` 表达四个可定位字段（`LaunchWizard.vue:47-66`）。这四个状态互斥地组合出 Step1、命中 Step2 和空命中 Step2：`resetPreview()` 把后两者清回 Step1（192-198），Step2 渲染条件是 `step === 2 && (preview || emptyResult)`（369）。

### 2.2 校验从按钮属性迁到点击入口

旧实现在模板层用 `:disabled="!selectedTarget || !targetVersion || windowInvalid()"`，且 `runQuery()` 只拦截对象缺失和倒挂区间；新实现把按钮 `disabled` 完全移除，`runQuery()` 先调用 `validateCondition()`，四个字段全部写回 `fieldErrors`，失败时清查询状态并停在 Step1（旧 `LaunchWizard.vue:196-209`、新 `218-256`、`740-748`）。字段 watch 在值变化时清各自错误（136-147），这是“修正后立即消失”的直接机制。

### 2.3 409 不是新的后端语义

`queryProbeHits()` 仍调用既有 `POST /api/evolution/probes/query`（`apps/web/src/api/evolutionRuns.ts:83-90`）；`request()` 把带 `error.code` 的失败统一解码成 `ApiError`（`apps/web/src/api/http.ts:101-113`）。后端在 probe 数为 0 时已经返回 `409 NO_PROBES_MATCHED`（`apps/api/app/service/evolution/probe_query.py:272-278`）。因此本 PR 只新增前端解释层：`error.status === 409 && error.code === "NO_PROBES_MATCHED"` 才置 `emptyResult` 并进 Step2（`LaunchWizard.vue:244-252`）。

### 2.4 空态出口是冗余防御

空态渲染在主体区域（504-518），两个启动按钮都加 `:disabled="launching || emptyResult"`（721-738）；`launch()` 也再次检查 `emptyResult`（272-275）。后端 launch 本会拒绝空命中，这里的双层禁用不是安全边界，而是减少一次注定失败的点击；Agent Note 已明确记录这个取舍（`Agent Note:19-21`）。

### 2.5 错误反馈分层

每个控件包在 `.wz-field` 内，红框 class 和 `aria-invalid` 绑定字段错误，红字是控件后的下一个兄弟节点，并带 `role="alert"`（544-573、597-606、639-679）。版本列表加载失败使用独立 `wizard-version-load-error`（608-624），因此不会再挤占旧实现里同名的 `wizard-version-error`，后者现在专指“用户没有选版本”（597-605）。

## §3 数据流走查

### 场景 A：空表单点击

1. 向导打开后加载对象和模型目录；对象未选时 `selectedTarget` 为 null，版本也被 watch 成空字符串（`LaunchWizard.vue:95-110`、`125-147`）。
2. 用户点击恒可点的「下一步」，事件进入 `runQuery()`（740-748）。
3. `validateCondition()` 计算四个布尔值：对象、版本、from、to 全部失败（218-226）。
4. 失败路径清空 `preview / emptyResult / previewError`，`page=1`，`step=1`（229-237），因此不发网络请求。
5. 模板按字段渲染红框、`aria-invalid` 和框下红字（544-606、638-680）；单测断言 `bodies` 为空且错误是控件下一个兄弟节点（`LaunchWizard.test.ts:362-400`）。

### 场景 B：区间倒挂

1. 用户先选对象和版本，填 `from=2026-08-31`、`to=2026-08-01`。
2. `windowInvalid()` 用 ISO 日期字符串做字典序比较，得到 `from > to`（214-216）。
3. `validateCondition()` 把两端都标错（220-224），两端文案都是「起始时间不能晚于结束时间」（656、677）。
4. E2E 在真实浏览器里点击后等待两端同一文案且没有 `.wz-stats`（`m5-05-launch-wizard.test.mjs:382-388`）。

### 场景 C：零命中

1. 条件通过后 `queryProbeHits()` 发请求；后端查得 probe 数为 0，返回 `409 NO_PROBES_MATCHED`（`probe_query.py:272-278`）。
2. `catch` 同时检查 status 和 code（`LaunchWizard.vue:245`），避免把其他 409 误当成空命中。
3. 前端清 `preview`、置 `emptyResult=true`、清错误、`page=1`、`step=2`（246-251）。
4. Step2 保留条件摘要（369-388），主体渲染空态标题和调整条件引导（504-518），两个出口禁用（721-738）。
5. 点击「修改条件」调用 `resetPreview()`，`emptyResult` 归 false，流程回 Step1（381-387、192-198）；单测和 E2E 都覆盖恢复命中（`LaunchWizard.test.ts:429-455`、`m5-05-launch-wizard.test.mjs:453-470`、`482-501`）。

## §6 讨论点

### 6-1 空态的「修改条件」按钮数量与原型不一致

- **位置**：`plans/14-15-ui-prototype/harness-evolution.html:3305-3313`；`apps/web/src/pages/evolution/components/LaunchWizard.vue:381-387`、`504-518`。
- **现象**：原型的空态有两个返回入口——条件摘要条右侧一个「← 修改条件」，空态面板内容底部还有一个「← 修改条件」；生产实现只保留条件摘要条里的返回按钮。
- **问题**：功能等价，但按“UI 与原型一致”的口径这是可见差异；空态卡片中央少了一个原型里显式引导用户返回的按钮。
- **预判**：倾向删掉原型 3313 的重复按钮，让“条件摘要条返回”成为唯一规范入口；这比在生产 UI 里复制两个语义相同的按钮更干净。若维护者认为空态中央按钮是必要引导，则应改生产实现。
- **结论**：2026-10-30 判定意见成立；已删除原型空态面板内的重复「← 修改条件」按钮，保留条件摘要条中的唯一返回入口。该差异已修复。

### 6-2 flow issue 的根因与设计依据仍描述已被 #167 更新的旧现状

- **位置**：`.agents/flow/issues/m6-wizard-validation-empty-state.md:46,62-65`；`.agents/flow/issues/m6-wizard-validation-empty-state.en.md:46,62-65`。
- **现象**：中文根因段写 `05 §4.9` 有“前端停在 Step1”的现行表述，设计依据写 `08 §9.2`“现为『无匹配时后端 409』”；但当前被链接的 `08-frontend-implementation.md:482` 与 `05-api-design.md:753` 已经表达空态映射。英文侧同样写 `currently` / `current`。
- **问题**：issue 是本 PR 的执行依据，正文却引用了过时描述；后来读者可能误以为设计文档尚未同步。
- **预判**：把两处括号改成目标口径（例如“字段级点击校验 + 409 映射空态”），去掉 `current/currently` 的旧现状叙事；同时重录双语 hash。属于低风险文档修正。
- **结论**：2026-10-30 判定意见成立；中英 issue 根因与设计依据已改为现行设计行为——点击时字段级校验，`409 NO_PROBES_MATCHED` 映射到 Step2 空态，并已重录双语哈希。该差异已修复。

### 6-3 对象目录加载失败会显示“请选择进化对象”

- **位置**：`LaunchWizard.vue:95-103`、`218-226`、`554-573`、`608-624`。
- **现象**：版本列表失败有独立错误与重试；对象目录失败没有等价的错误/重试 UI。此时用户点击「下一步」只会看到「请选择进化对象」，但下拉里可能只有占位项。
- **问题**：错误原因“目录读取失败”和用户动作“没选择”被合并成同一个提示，定位效率低于版本错误。
- **预判**：这是既有目录加载能力的缺口，不是本 PR 引入的回归；也不在 issue“不改配置页与目录失效语义”的边界内。建议另开小 issue，不阻塞本 PR。
- **结论**：2026-10-30 判定意见成立；作为后续独立 issue 处理，不在 #161 边界内，不阻塞合并。

## §9 文件级代码分析

### 9.1 `apps/web/src/pages/evolution/components/LaunchWizard.vue`（M）

职责：承载启动自进化两步向导的状态、查询与启动动作。变更形态：核心交互重写加模板结构调整；无新依赖。关键依赖：Vue `watch/reactive/ref` 负责本地状态总线，`ApiError` 是统一 API 失败信封，像一张同时写着 HTTP 状态和业务代码的回执。

旧核心：

```ts
function runQuery(): Promise<void> {
  if (!selectedTarget.value || windowInvalid()) {
    return;
  }
  try {
    preview.value = await queryProbeHits(condition());
    step.value = 2;
  } catch (error) {
    preview.value = null;
    previewError.value = error instanceof Error ? error.message : String(error);
  }
}
```

新核心：

```ts
function validateCondition(): boolean {
  const rangeInvalid = windowInvalid();
  fieldErrors.target = !selectedTarget.value;
  fieldErrors.version = !targetVersion.value;
  fieldErrors.from = !windowFrom.value || rangeInvalid;
  fieldErrors.to = !windowTo.value || rangeInvalid;
  return !fieldErrors.target && !fieldErrors.version && !fieldErrors.from && !fieldErrors.to;
}

async function runQuery(): Promise<void> {
  if (!validateCondition()) { /* 清查询状态并停留 Step1 */ }
  try {
    preview.value = await queryProbeHits(condition());
    emptyResult.value = false;
    step.value = 2;
  } catch (error) {
    if (error instanceof ApiError && error.status === 409 && error.code === "NO_PROBES_MATCHED") {
      preview.value = null;
      emptyResult.value = true;
      previewError.value = "";
      page.value = 1;
      step.value = 2;
      return;
    }
    preview.value = null;
    emptyResult.value = false;
    previewError.value = error instanceof Error ? error.message : String(error);
  }
}
```

这里把“入口能不能点”改成“入口给出定位”，把“所有失败都是异常”拆成“业务空结果 vs 真失败”。`resetPreview()` 同步清 `emptyResult`，避免从空态返回后残留禁止启动的旧状态。模板把四个控件包进 `.wz-field`，红字成为控件兄弟节点；版本加载失败改用独立 testid，避免语义撞车。

检视发现：核心实现与设计和 issue 一致；未见校验绕过或空态误启动路径。组件 diff 较大主要来自模板重排，逻辑增量集中在上述状态机。
