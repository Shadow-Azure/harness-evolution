## §1 一页速览

一句话：让每条 bad case 上报自己带一份“去哪里取会话”的地址，root-sync 第一次 claim 时把地址冻住，之后按 envelope 回报的 runtime 选 adapter 和 parser。

比喻：以前所有包裹都送回同一个总仓库；现在上报单上写了收件地址，调度员第一次上门时把地址抄在工单上，后面再送只认这张工单，不会因为上报单更新而改地址。

| 交付块 | 内容 | 验收 |
|---|---|---|
| 上报契约 | `sessionSource` 可选、模板严格校验 | 旧 body 不变；坏模板 422 |
| envelope | 单接口返回 runtime/父子/agentMeta/轨迹 | 版本、回显、parent、NDJSON、lineCount 均有稳定码 |
| adapter | 工厂 + 自注册 + Claude closed schema | 新 runtime 只加 adapter/parser 文件；未知 runtime 不回退 |
| 来源选择 | report 优先、global 回退、快照冻结 | 重试不换源；只有 report 源也能调度 |
| 持久化 | 新列 + 迁移 0017 | SQLite/MySQL head 一致；存量 root 回填 global |
| 文档 | Agent Note + 05/06/07/11 | 双语与 docs 门禁全绿 |

## §2 架构导览

### 2.1 上报与持久化

`BadCaseSessionSource`（`service/workspaces/ingest.py:26`）把模板校验收在模型层：恰好一个 `{sessionId}`、http(s)、无 userinfo/fragment、长度上限；`extra="forbid"` 拒绝 headers/token。`BadCaseIngest.session_source`（`:79`）可选，旧 body 不传时落 NULL。写入侧把 `session_source` 放进 `_UPSTREAM_COLUMNS`（`db/crud/bad_case_ingest.py:35`），重报时随其它 upstream 字段一起替换。

### 2.2 取数与校验

`HttpSessionSourceClient.fetch`（`session_source/client.py:66`）先渲染模板（`:108`），在进程级 `asyncio.Lock` 内 GET，再按 `:117` 的 closed envelope 校验 schemaVersion、sessionId、agentKind/parent、轨迹与 lineCount（`:145`）。HTTP 细节集中在 `_request`（`:171`）：超时/连接/429/5xx 重试，401/403 与最终失败分别是 `SESSION_SOURCE_*`。校验通过后由 envelope 的 `runtime` 调 `SessionSourceFactory.create`，未知 runtime 或 adapter 没有对应 parser 时抛 `UnsupportedTraceRuntime`。

### 2.3 adapter 工厂

`BaseSessionSourceAdapter.project`（`base.py:102`）只做 runtime 无关投影；`parse_agent_meta` 是子类唯一实现点。`ClaudeCodeSessionSourceAdapter`（`claude_code.py:58`）用 closed `ClaudeAgentMeta` 解释 `agentMeta`，未知字段直接拒绝。`SessionSourceFactory.register`（`factory.py:18`）同时要求 parser 已注册，保证 adapter 与 parser 的 runtime 词汇表不分叉。

### 2.4 root-sync 来源选择

`BadCaseRootSyncService._select_source`（`bad_case_sync.py:255`）只在首次 claim 编排来源：已有快照直接用；无快照但已尝试过（存量行）按 global；否则查 `latest_report_source`。`claim` 在同一事务里写 `source_kind/source_snapshot`，已有快照不覆盖（`db/crud/bad_case_sync.py:377`）。`_selection`（`bad_case_sync.py:271`）用 closed snapshot 校验读回值，坏快照让 root 失败而不是静默回退。

### 2.5 遍历与 payload

`_sync_report_root`（`bad_case_sync.py:384`）复用现有 BFS 的 visited/深度/数量/时间预算，只是把 children 换成 envelope 的 `childSessionIds`，把 payload 的 runtime/agentKind/agent_meta 换成 `SessionInfo` 投影；`_sync_global_root`（`:331`）保持原两接口路径。两者最后都走 `write_local_payloads` 和一次 replay。

### 2.6 迁移

`0017`（`alembic/versions/0017_per_report_session_source.py:60`）先给 `bad_cases` 加 `session_source`，再给 `bad_case_root_sync` 加 `source_kind/source_snapshot` 并回填 `global`。external `bad_cases` 不存在时跳过，配合运行时 `bootstrap_external_tables=False` 的启动顺序。

## §3 数据流走查

1. 上报方 POST `sessionSource`；`BadCaseIngest` 校验后写入 `bad_cases.session_source`，同事务插入 pending root。
2. coordinator 发现全局未配置但存在 report source，仍提交 root-sync job。
3. service 读取 pending root，选择最新上报源并 claim，写入 `source_kind=report` 与快照。
4. `HttpSessionSourceClient` 代入根 sessionId 取 envelope，校验后由 Claude adapter 投影出主 agent 的 `SessionInfo`（runtime/agentKind/children/trajectory）。
5. 写 payload（`runtime_key=claude-code`，`source_type=http_api`），对每个 child 重复，父 id 来自遍历父节点。
6. replay 用 runtime_key 选择 parser，组装 Session/Agent 树；`source_records` 与 `session_families` 带 runtime。
7. 状态 API 返回 `badCaseSync.synced=1`；失败 root 保留稳定 `last_error` 与退避时间。

## §6 讨论点

### 6.1 重试不换源会阻止上报方修正 URL

- **位置**：`apps/api/app/service/acquisition/bad_case_sync.py:255`、`apps/api/app/db/crud/bad_case_sync.py:377`
- **现象**：root 首次 claim 后快照冻结；后续重报带新模板不会改变已 failed root 的下一次重试来源。
- **问题**：如果上报方第一次给错 URL，修好后只能等运维清理状态行，重报无法自愈。
- **预判**：这是 issue 明确的“快照落表，重试不换源”语义，优先保证一次同步内来源不漂移；若要支持修正，应增加显式 reset 入口而不是在 claim 时比较 `created_at`。
- **结论**：

### 6.2 仅有上报源时的调度可用性查询

- **位置**：`apps/api/app/service/acquisition/bad_case_sync_coordinator.py:77`、`db/crud/bad_case_sync.py:275`
- **现象**：全局查询未配置时，每一次 status/trigger 都会查一次 `bad_cases.session_source IS NOT NULL LIMIT 1`。
- **问题**：状态接口高频轮询时会多一次 DB 查询；当前表有 workspace/session 索引但没有 session_source 索引。
- **预判**：低频状态弹层可接受；若后续出现性能问题，可缓存或加部分索引，不在本 issue 引入。
- **结论**：

### 6.3 per-report URL 是上报方可控的出站请求

- **位置**：`apps/api/app/third_party_api/session_source/client.py:171`
- **现象**：服务端会 GET 上报方给的任意 http(s) URL，当前没有内网地址/域名白名单。
- **问题**：持有上报凭据的调用方可以让服务访问内网地址（SSRF 面）；设计文档把授权交给模板签名，但没有限制目标。
- **预判**：本 issue 的契约要求按上报路由到上游，内网 trace 服务是预期用法，不能简单封私网；若要收紧，应在部署层增加 allowlist 或单独出站代理，作为后续安全项。
- **结论**：

### 6.4 Claude `agentMeta` 是 closed schema

- **位置**：`apps/api/app/third_party_api/session_source/claude_code.py:17`
- **现象**：上游 meta.json 新增字段会被 adapter 拒绝，root 失败并记 `SESSION_SOURCE_INVALID_RESPONSE`。
- **问题**：provider 元数据可能漂移，closed schema 需要跟随升级。
- **预判**：与 m9-06 parser 的 meta 解释边界一致；比静默丢弃/落库未知字段更安全。新增字段时只改 Claude adapter 的 schema 与测试。
- **结论**：

## §9 文件级代码分析

### 9.1 `third_party_api/session_source/client.py`（A）

职责：把一次 envelope GET 变成 `SessionInfo`。依赖 `httpx` 做传输、`pydantic` 校验、共享 trajectory 模块做 NDJSON 规范化和 `SessionSourceFactory` 做 runtime 分派。

旧代码：无；新代码拆成 `fetch` → `_render_url` / `_parse_envelope` / `_validate_identity` → `canonicalize_ndjson` → adapter。实现思路：HTTP 与协议校验固定在共享层，子类只解释 runtime 元数据；错误只用稳定码，不把上游正文带进 `AppError.message`。

检视发现：`_request` 的重试分支覆盖了超时/连接/429/5xx；响应体先整体读入再限长，极端大响应会多占一次内存，但 96 MiB 的 envelope 上限对当前上游可接受。

### 9.2 `third_party_api/session_source/base.py` + `claude_code.py`（A）

职责：定义 envelope 的 closed 模型、来源快照模型、`SessionInfo` 与投影模板。Claude 子类把 `agentMeta` 的已知字段映射成 camelCase，未知字段拒绝。

实现思路：`project` 只处理“主/子 agent 元数据合并”，把 `parentAgentId` 固定在 adapter 层，避免每个调用点重复拼装。`SessionSourceSnapshot` 用 `kind` 区分 report/global，report 必须带模板。

检视发现：`promptSnapshot`/`agentListingDelta` 用 `Any` 保留结构，未限制嵌套大小；它们来自上报方可信上游，当前没有独立大小门禁。

### 9.3 `service/acquisition/bad_case_sync.py`（M）

前身：单一全局 `SessionQuerySource` 的 BFS。新代码把循环拆成 `_sync_global_root` 与 `_sync_report_root`，共享 `_check_deadline` / `_check_limits` / `_enqueue_children`；`run` 在 claim 前选源、claim 后读回冻结快照。

检视发现：两条路径都保留“失败即停”和部分 payload 保留；report 源失败不会降级 global，符合 issue 的显式来源语义。

### 9.4 `db/crud/bad_case_sync.py` + `0017`（M/A）

职责：持久化来源快照与最新上报源。claim 的写路径只在快照为空时写，保证同一 root 首次选择是吸收态；迁移对 absent external 表跳过。

检视发现：`latest_report_source` 的并列裁决用 `bad_case_id` 字符串降序；`bad_case_id` 列是 VARCHAR(64)，与设计里的“最大 bad_case_id”一致，不依赖数字排序。

### 9.5 `service/workspaces/ingest.py` + `db/crud/bad_case_ingest.py`（M）

职责：新增可选字段与持久化。模板校验在 Pydantic model validator 内完成；upsert 把 `session_source` 当普通 upstream 字段替换。

检视发现：`source` 和 `sessionSource` 的命名只差大小写，OpenAPI 生成 `sessionSource` 明确；`extra="forbid"` 已覆盖旧调用方的未知字段拒绝。
