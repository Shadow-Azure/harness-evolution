## §1 一页速览

**一句话**：这个 PR 把执行流图里的触发 pill 从“只负责装饰的标签”变成真正的连线插座，所有子 Agent 和错误卡都从对应的 pill 插口出发；多个错误卡则像同一根立管上的楼层，按上/下方向逐张串联。

**生活化比喻**：旧实现像先在所有墙上预留了一排假电线，再把真正电线从房间外墙接进去；用户看到的墙内短线和墙外长线是两段拼起来的。现在每个 pill 是唯一插座：有设备才拉线，线从插座的准确位置出发，错误卡则顺着插座的竖直轨道排队。

## §2 架构导览

### 2.1 布局阶段决定“有没有线”，组件不自行猜测

`buildGraph()` 先照常生成 Agent 节点、分支边和问题卡 overlay，再遍历所有真实边，从 `sourceHandle` 的 `h{i}` / `rep{i}` 命名中抽取 pill 事件下标，写入 `triggerConnections`（`layout.ts:1046-1075`）。

这一步是架构关键：节点组件只消费“是否占用”，不再从“是否存在 skill pill”推断“是否应该有竖线”。因此无子 Agent、无问题卡的 pill 不会生成 handle，也就没有可被 Vue Flow 连接的入口。

### 2.2 问题卡列由布局纯函数生成

`buildBadCaseOverlay()` 以 `hostAgentId + eventIndex + side` 分组纵向问题卡（`layout.ts:542-621`）。同一组第一张仍由 Agent pill 连接，后续边把 source 改成前一张卡，并选择 `card-stack-top` 或 `card-stack-bottom`；这让 SVG 连线不会同时叠在同一段竖直区间上。

以 `deep-research` 的两张 self-skill 卡为例：

```text
skill pill --h0--> 第一张卡顶部
第一张卡底部 --card-stack-bottom--> 第二张卡顶部
```

向上 discovery 卡则反向：

```text
第一张卡顶部 --card-stack-top--> 第二张卡底部
第一张卡底部 --rep0--> skill pill 顶部
```

### 2.3 问题卡节点提供方向明确的双端口

`BadCaseNode.vue` 在原有左右、顶部、底部 target handle 之外，增加顶部和底部 source handle（`BadCaseNode.vue:63-74`）。左右端口继续服务 self-agent/fallback；上下端口只服务触发点问题和其堆叠链，避免改变旧侧向布局。

### 2.4 边层必须跨过 Agent 盒背景

`AgentNode.vue` 的自定义 handle 位于 pill 内部，而 Agent 节点自身有实色背景。若 edge 仍是常规的低层 SVG，pill 到盒边这一段会被背景覆盖。`AgentTree.vue:443-448` 将 edge 提到节点层上方，同时关闭整个 edge 层的指针事件，使缩放、节点点击和问题卡点击仍由节点层接收。

## §3 数据流走查

1. `AgentTree.vue:107-113` 用 `buildGraph()` 从 `SessionTree` 计算节点、Agent 分支边、问题卡节点与问题卡边。
2. `layout.ts:864-1023` 排布父 Agent 与子 Agent；子分支的 `sourceHandle` 仍是 `h{i}`，但此时只是语义标识，最终位置由后面的连接占用决定。
3. `layout.ts:301-405` 根据 bad-case anchor 选出 above/below/left/right；skill 问题进入竖直组，agent 问题进入侧边组。
4. `layout.ts:473-654` 计算问题卡坐标、同列顺序和卡到卡边；`stackedSourceById` 将后续卡的 source 改成上一张卡。
5. `layout.ts:1046-1075` 汇总真实 Agent 边与首张问题卡边，把 `above` / `below` 写回 Agent 节点 data。
6. `AgentNode.vue:17-35` 只遍历已占用方向，生成 `h{i}` / `rep{i}` handle；`AgentNode.vue:115-147` 将其定位在 pill 下沿 `53px` 或上沿 `31px`。
7. `AgentTree.vue:114-137` 合并 Agent edge 与 bad-case edge，交给 Vue Flow 渲染；edge 类型决定使用 `OrthEdge`、`TriggerEdge`、`DiscoveryEdge` 或 `BadCaseEdge`。
8. `AgentTree.vue:438-448` 把 edge SVG 放到节点背景之上，用户能看到 pill 到目标之间的完整路径。

## §6 讨论点

### 6-1 [P1] discovery 路径在 pill 与卡片同 x 时会留下横向回钩

**位置**：`apps/web/src/components/agent-tree/layout.ts:1191-1203`；对应测试只覆盖横向错位场景 `layout.test.ts:1019-1051`。

**现象**：本 PR 把 discovery/self-skill 问题卡的 x 坐标改成以 pill 中心对齐（`layout.ts:593`），但 `discoveryPath()` 仍固定生成“先向下/上、再横向圆角、最后横线到 targetX”的路径。sourceX 与 targetX 相等时，它仍先弯到 `sourceX + 7`，随后再水平返回 `targetX`。按当前公式，`(100,100) → (100,20)` 会得到 `M 100 100 V 27 Q 100 20 107 20 H 100`，卡片底边会出现一个 7px 的横向回钩。

**问题**：大部分新布局正好是同 x 的竖直连接，这个回钩与原型中的纯竖线不一致；多张 discovery 卡串联时同样存在。当前测试没有覆盖 sourceX == targetX，因此没有捕获。

**预判**：优先在 `discoveryPath()` 对同 x 情况直接返回 `M sourceX sourceY V targetY`，并补一个纯竖直路径断言；若保留横向偏移路由，也应让半径受水平差约束，避免反向水平段。

**结论**：2026-10-28 确认为真实缺陷并修复。`layout.test.ts` 先增加同 x 断言并观察到 RED（旧结果为 `M 100 100 V 27 Q 100 20 107 20 H 100`）；`discoveryPath()` 随后对同 x 返回纯竖线，相关 35 项布局测试转绿。横向错位路由保持不变。

### 6-2 [P2] 原型只演示了向下多卡，正式实现却包含向上多卡

**位置**：原型 `plans/14-15-ui-prototype/harness-evolution.html:1533-1557`、`:1707-1712`；正式实现 `layout.ts:581-621`、`BadCaseNode.vue:63-74`。

**现象**：正式代码为 discovery 卡增加 `card-stack-top`，布局也会把同一锚点的多张 discovery 卡向上串联；原型的问题卡只有一个 `stack-out` 底部 source handle，且主会话上报型问题每次只生成一张卡，没有“第二张 discovery 卡继续向上”的可运行示例。

**问题**：PR 声称原型与设计同步，但多张 discovery 卡这一条只能从正式代码和设计文档推断，无法通过原型直接验收。若产品预期“上、下都可多卡”，原型缺少关键视觉证据；若原型只要求下方多卡，则应明确它是简化演示，而不是完整交互契约。

**预判**：补一个双 discovery 卡原型场景及顶部 stack handle，成本很低，也能让“上方错误框底边→pill 顶部”与“后续卡继续向上”两个交互同时可验。

**结论**：2026-10-28 确认原型应补齐并已修复。原型现在为同一 `deep-research` pill 生成两张 discovery 卡，近卡底边连接 pill 顶部，远卡由近卡顶部继续向上串联；问题卡增加顶部 `stack-top` source handle，Computer Use 已验证两卡同列且连线完整可见。

### 6-3 [P2] 合并后还需要明确的 issue/flow 收口动作

**位置**：`.agents/flow/issues/m6-agent-tree-trigger-edges.md:11` 当前 `status: in-progress`；PR 描述没有 `Closes #149` / `Fixes #149`。

**现象**：PR 标题包含 `(#149)`，但 GitHub #149 当前仍是 open；合并 PR 不会自动关闭 issue，本地 flow issue 也会继续保持 `in-progress`。仓库此前的 milestone issue 采用合并后再提交 `chore(flow): close ...` 的收口模式。

**问题**：如果第 11 步直接合并就结束，用户会看到 PR 已合并但 issue 仍打开、本地流程状态仍未 done。若加入关闭关键字但不更新本地状态，也会产生 GitHub 与 flow tree 的状态漂移。

**预判**：保留“实现的 PR”和“合并后的 flow close PR”两阶段，或在同一交付流程中明确安排合并后的 `status: done`、双语重录和 `flow:sync`；不要让合并动作成为未登记的半完成状态。

**结论**：2026-10-28 确认 PR 正文应加入 `Closes #149`，但本地 flow issue 必须保持 `in-progress` 到 PR 合并，否则远端 issue 仍为 open 时 `flow-online` 会失败。PR 合并并自动关闭 #149 后，再通过独立 flow close 变更将 `m6-08` 改为 `done`、重录双语并同步。

### 6-4 [P3] edge 整体高于节点是一个有意但需长期约束的取舍

**位置**：`apps/web/src/components/agent-tree/AgentTree.vue:443-448`。

**现象**：当前把整个 `.vue-flow__edges` 放到 `.vue-flow__nodes` 上方，解决 pill 到盒边被背景遮挡的问题；`pointer-events: none` 只保证交互不被拦截，不保证视觉上永远不会压住文字。

**问题**：当前布局与路径测试表明分支不会穿过兄弟节点，因此暂无实害；但未来新增交叉路由、节点内浮层或更大的问题卡时，edge 可能压在文字上。Agent Note 已记录这条边界，属于可接受的长期约束。

**预判**：本轮无需为潜在几何变化重构边层；未来若出现交叉，可考虑只给 pill 到盒边的内段单独升层，而不是让全部 edge 永久高于全部节点。

**结论**：2026-10-28 接受当前取舍。指针事件已关闭，现有路径与布局测试未发现 edge 压住节点内容；未来若新增交叉路由或节点内浮层，再按预判拆分层级。

## §9 文件级代码分析

### 9.1 `types.ts`

**职责与变更**：M；为 Agent 节点 data 增加 `triggerConnections`，值按事件下标记录 `above` / `below`。这把“视觉连线是否存在”从组件内推断改成布局输出，类型边界清楚。

**实现思路**：`Record<number, TriggerConnection>` 运行时会落成字符串 key，`AgentNode` 用 `Object.entries()` 再转回数字，当前没有排序或查找歧义。可继续观察到更严格的事件下标类型收益有限。

**检视发现**：无独立问题。

### 9.2 `layout.ts`
