## §1 一页速览

**一句话**：给三张“别人家的”外部问题表装上定期体检与读失败分诊台——按 06 §4 图纸比对列/类型/可空性，把“缺表、缺列、权限不足、一般读失败”翻译成稳定错误码与结构化日志，让线上从“未分类 500 + 只在单次请求里飘过的 warning”变成“可查询的漂移事件 + 稳定 503”。

**比喻**：服务只是这三间仓库的租客。本 PR 请了一个“巡检员”，每 5 分钟拿房东给的图纸核对门牌（表）、货架（列）与货架规格（类型/长度/可空），发现差异就写巡检记录（`external.contract_check` / `external.contract_drift`）；同时给每次取货加了“分诊台”，取不到货时先判断是“没钥匙（`EXTERNAL_READ_FORBIDDEN`）”“货架不在了（`EXTERNAL_SCHEMA_DRIFT`）”还是“运输出错（`EXTERNAL_READ_FAILED`）”，再回稳定 503。巡检员只在门口看图纸、从不搬货（巡检与读路径都只发 SELECT）；用户能看到的只是“数据降级”小标签，巡检结论只进运维日志。

## §2 架构导览

### 2.1 契约是一张“图纸表”：`ColumnContract` / `TableContract` / `EXTERNAL_TABLES`

`ColumnContract` 只记四件事：列名、逻辑类型族、是否可空、最小长度（`external_contract.py:74-81`）；`TableContract` 是一张表的列集合（`:84-88`）；`EXTERNAL_TABLES` 是三表 40 列的元组（`:95-151`）。没有数据库连接、没有 ORM 查询，纯数据，所以可以被巡检、被测试直接 import。

这张图纸与 06 §4 的对照是逐列核过的：`bad_cases` 15 列、`bad_case_analysis` 6 列、`probe_reports` 19 列，长度（64/36/128/255/96 等）、可空性（`bad_case_analysis.probe_id` 与 `probe_reports.cache_key` 可空是 06 §4.2 的兼容例外）、`CHAR(64)` 缓存键、`DOUBLE` 置信度都一致；也与 `app/db/models/domain.py:294-416` 的查询模型一致。这说明“图纸”本身没有抄错。真正的风险在“拿图纸对实物”的比较逻辑（D1/D2）。

### 2.2 巡检怎么跑：`inspect_external_contract` 与 `_inspect_schema`

巡检入口是 `inspect_external_contract`（`external_contract.py:387-435`）：取 `database.engine`，`connect()` 后把同步回调 `_inspect_schema` 丢给 `run_sync`。`_inspect_schema`（`:222-283`）对三张表各自：

1. `inspector.has_table(name)` 判表是否存在，缺表直接记 `missing_table`；
2. `get_columns(name)` 拿实际列，构造 `{name: column}` 映射；
3. 按图纸逐列比对：找不到 → `missing_column`；`_type_drift`（`:208-219`）比较 `_family` 与最小长度，不一致 → `type_mismatch`；`nullable` 不一致 → `nullability_mismatch`；
4. 实际列比图纸多 → `extra_column`。

状态判定在 `:415-433`：只要出现 `missing_table` / `missing_column` / `type_mismatch` 就 `unavailable`（这些会让真实 SELECT 失败或截断）；只有额外列或可空性差异则 `degraded`（读仍可用）；全对则 `ok`。这个分级是合理的：把“读不了”和“能读但有噪音”分开。

`_family`（`:180-198`）用 `isinstance` 判断 SQLAlchemy 反射类型的逻辑族：`JSON`→json、`CHAR`→char、`Text`→text、`String`→varchar、`DateTime`→datetime、`Float/Numeric/Double`→float、`Integer`→integer，其余用类名小写兜底。**这里按“名义类型”而不是“行为兼容性”比较**，是 D1 的根源。

### 2.3 读失败分诊：`classify_external_read_error` 与 `read_only_guard`

`_classify_failure`（`external_contract.py:321-333`）先取驱动错误码 `_db_error_code`：`exc.orig.args[0]` 为 int 时即驱动码（MySQL 常见形态）。然后按顺序：

- `PermissionError` 或驱动码 ∈ {1044,1045,1142,1143,1227} 或消息含 “access denied / permission denied / readonly database / read-only database / not authorized” → `EXTERNAL_READ_FORBIDDEN`；
- 驱动码 ∈ {1054,1146} 或消息含 “no such table / no such column / unknown column / doesn't exist / does not exist” → `EXTERNAL_SCHEMA_DRIFT`；
- 其余 → `EXTERNAL_READ_FAILED`。

三个码统一构造 503 `AppError`，文案是固定英文短句（`:336-341`），不带异常文本。`_log_read_failure`（`:300-317`）只写 `event/table/dialect/error_class/db_code/code`，不写 `str(exc)`——这是“日志不泄漏 SQL/参数”的关键实现。

`read_only_guard(table)`（`:355-383`）是一个装饰器工厂，包一层 `guarded`：先 `except AppError: raise`（业务错误不被改写，`test_app_error_is_not_rewrapped` 覆盖），再 `except (OperationalError, ProgrammingError, DBAPIError)` 转分诊；repository 从 `args[0]._database` 取 dialect。最终提交 `2839c47` 补了 `@functools.wraps(operation)`（`:366`），方法名与 docstring 不再丢失。注意：名字叫“guard”，但它不强制只读，只是**错误边界**；只读是仓库既有行为，由测试断言证明（见 §2.7 / §3.6）。

### 2.4 监控生命周期：`ExternalContractMonitor`

`ExternalContractMonitor`（`external_contract.py:481-565`）持有 `Database`、`asyncio.Lock`、最近一次 report、`time.monotonic` 时间戳与 task。

- `start()`（`:522-531`）：先 `await refresh()`（失败只 `logger.exception`，**绝不阻断启动**），再 `create_task(_loop())`；重复 `start()` 直接 return。
- `refresh()`（`:515-520`）：加锁 → 检查 → 记录 report/时间。
- `_loop()`（`:557-565`）：`sleep(interval)` → `refresh()`；`CancelledError` 原样抛，其余异常记 `logger.exception` 后继续下一轮。
- `stop()`（`:533-540`）：取走 task → cancel → 吞掉 `CancelledError`；未启动时 no-op。
- `report()`（`:507-513`）：TTL 缓存（`_is_stale`，`:542-545`），超过 interval 才重查。

装配在 `main.py:146-149`，启动放在 lifespan 的 `external-contract-monitor` 阶段（`main.py:445-446`，在 catalog sync 之后、job dispatch 之前），关闭在 finally 第一句（`main.py:466`）。因此启动顺序上它晚于迁移与身份种子，早于 job 派发；即使巡检异常也只影响监控自身，不会把 `database_start_error` 打出来（除非 `BaseException`，正常不会）。

一个设计观察：`report()` / TTL / `interval_seconds` 属性目前**没有产品消费者**（全仓 grep 只有测试调用；`_loop` 直接走 `refresh()`）。也就是说缓存/锁语义目前是“为未来准备”的死代码；不会出错，但也没有被产品路径证明（D7）。

### 2.5 行级漂移：`_log_drift_summary` 与 `merge_snapshot` 汇总来源

问题列表的既有字段校验在 `BadCaseService._case_model` / `_analysis_model` 里产生 `ExternalReadWarning` 并逐条 `logger.warning`；本 PR 新增 `_log_drift_summary`（`bad_cases/service.py:80-96`），在“一次读取”结束时额外打一条 `external.row_drift`，只带 `scope/warning_count/codes`，不重复外部正文。

调用点四处：`get_probe_result`（`:199-204`，scope=probe_detail）、`merge_snapshot` 的空结果（`:228-231`）与正常结果（`:259-263`，scope=bad_case_list）、`merge_probe_rows`（`:286`，scope=probe_list）。`merge_snapshot` 的旧实现已经在循环里 `warnings.extend(model_warnings)`，列表 DTO 本来就包含 `_case_model` 的 warning；本 PR 只是把构造改成“身份 warning + 所有 `item.warnings`”并让汇总日志用完整集合。集合不变，顺序从“按行交错”变成“身份级在前、逐项在后”；消费方只有测试，无 UI 依赖。PR 描述把它说成“列表 DTO 现在包含 `_case_model` 追加的 warning”是与 base 不符的（D9）。

### 2.6 会话树降级：`_session_bad_case_fields`

会话树走的是另一条读模型：`SessionBadCase.bad_case_type/object_type` 是 `Literal`，之前直接把外部值 `cast` 进去（`service/sessions/service.py` 旧代码），外部值越界时 Pydantic 校验失败 → 整棵 `/tree` 500。本 PR 在最终 head 里加了 `_session_bad_case_fields`（`:205-240`）：

- 值在闭集内 → 用原值；越界 → 回退 `self` / `agent`，并把字段名收进 `drifted`；
- 只要有回退，打一条 `external.row_drift`（`scope=session_tree`、`bad_case_id`、`codes=['EXTERNAL_FIELD_INVALID']`、`fields`、`warning_count`）；
- `_bad_case` 用回退后的值去 `resolve_problem_anchor` 并填 DTO（`:243-292`）。

它解决的是“一个坏行炸整棵树”的真实问题，回归用例 `test_session_tree_degrades_invalid_external_enums`（`test_read_only_boundary.py:105-133`）与冒烟 `/tree 200` 都验证了。代价是：**回退值会改变语义**（一个 discovery 问题被展示成 self），而 `SessionBadCase` DTO 不带 `degraded` 标记（06 §4 明确该卡不承载降级），用户侧只能靠日志发现（D6）。

### 2.7 测试基座：受控 SQLite、假 DB、SQL 录制与 opt-in

- `conftest.py` 的 `external_database`（`:66-82`）只建三张外部表；`seeded_environment`（`:85-113`）用 fixture corpus 种子 + 真实 `create_app` lifespan + 管理员登录（含改密），并把 `sync_*_interval_seconds` 置 0，避免后台任务干扰。

## §3 数据流走查

### 3.1 启动：`database.start` → 迁移 → 巡检 → 任务

1. `create_app` 先建 `ExternalContractMonitor(resolved_database, interval_seconds=settings...)`（`main.py:146-149`），此时不连库。
2. lifespan：`database.start()`（只建 engine）→ `upgrade_database(..., bootstrap_external_tables=False)`（不建外部三表）→ 种子/恢复/各调度器（`main.py:429-444`）。
3. `external_contract.start()`（`:446`）：`refresh()` → `inspect_external_contract` → `engine.connect()` → `_inspect_schema` → `_log_report`；成功/失败都返回 report，失败只记 exception，不抛给 lifespan（`:522-531`）。
4. `asyncio.create_task(_loop())`；之后每 300s 一次 refresh；`stop()` 在 finally（`:466`）取消，任务不泄漏（`test_monitor_start_and_stop_cancel_the_loop`、`test_start_and_stop_are_idempotent` 覆盖）。

**关键结论**：巡检不可能因自身异常把应用启动打挂；启动成本只是多一次元数据查询（连接已由迁移建立，MySQL pool 复用），没有新增“启动必须外部表存在”的约束。

### 3.2 一次“体检”：三种输出

以 `external_database`（SQLite，由模型建表）为例：

1. 正常：三表 40 列全匹配 → status=ok，`external.contract_check` INFO（`test_schema_contract.py:53-61` 覆盖）。
2. 加一列 `upstream_note`：`extra_column` → status=degraded → WARNING 汇总 + 一条 `external.contract_drift(table='bad_cases', kind='extra_column', field='upstream_note')`（`:63-82`）。
3. 删 `source`：`missing_column` → status=unavailable（`:84-92`）；把 `source` 改成 INTEGER：`type_mismatch`（`:94-106`）；DROP 一张表：`missing_table`（`:108-115`）。
4. 空库（三表都不存在）：三条 `missing_table`，但 `_log_report` 的 `only_missing_tables` 分支改打 INFO“not provisioned yet”，不刷 drift warning（`:132-145`）；这是给“新部署尚未建外部表”的正常状态留的静音。
5. 权限失败：`engine.connect()` 抛 DBAPI 错误 → `_classify_failure` 给 FORBIDDEN → report.status=forbidden，`_log_read_failure` 一条 ERROR（`external.read_failed`），`_log_report` 走 `forbidden` 分支打 ERROR“unreadable”（`:457-459`），不再说 drift（最终 commit 修复）。

### 3.3 一次问题列表读：成功路径与行级漂移

## §6 讨论点

### D1 类型族按“名义类型”比较，MySQL 的 `LONGTEXT`/`MEDIUMTEXT` 会被当成 varchar

**位置**：`apps/api/app/db/external_contract.py:180-219`（`_family` / `_type_drift`）、`:95-151`（`TEXT` 列的契约）

**现象**：`_family` 用 `isinstance` 判族，而 SQLAlchemy 2.1.9 的 MySQL 反射类型里 `TEXT` 同时是 `sqltypes.Text`，但 `MEDIUMTEXT` / `LONGTEXT` 只继承 `sqltypes.String`（不是 `Text`）。我用仓库 venv 实测：`_type_drift(ColumnContract('bad_case_description','text',False), mysql.types.LONGTEXT())` 返回 `varchar`，即类型不匹配。若外部所有者把 `bad_case_description` / `probe_analysis` 放宽成 `LONGTEXT`/`MEDIUMTEXT`（对“问题正文”很自然），巡检会报 `type_mismatch` → status `unavailable` + 每 5 分钟告警，而真实读路径完全正常。`CHAR` vs `VARCHAR`（`cache_key`）、SQLite 用 `TEXT` 承载 JSON 也有同类偏差；注释“broader columns are compatible”（`:91-93`）与实现对不上。

**问题**：巡检的误报会训练运维忽略 `external.contract_drift`；它把“更宽的列”判成“漂移”，与契约声明的兼容策略矛盾。

**预判**：把逻辑族比较改成“可承载性”比较（text 兼容 `TEXT/MEDIUMTEXT/LONGTEXT`；varchar 与 char 可互认，长度只对有限长类型检查；SQLite 的 text 可承载 json 文本），并补 MySQL 类型族的单测（不需要真实 MySQL，直接构造 mysql 反射类型）。若认为“名义一致才算契约”，则把注释与文档的“broader compatible”改掉，别让两套语义并存。

**结论**：

### D2 列名精确匹配：大写/混合大小写的外部 DDL 会产生整表假漂移

**位置**：`apps/api/app/db/external_contract.py:235-241`（`observed.get(column.name)`）、`:274-281`（额外列差集）

**现象**：`observed` 用反射列名原样做 key，图纸列名是小写。MySQL/SQLite 的列名在 SQL 里大小写不敏感（MySQL 列名本身不区分大小写；SQLite 也不区分），所以外部 DDL 写成 `BAD_CASE_ID` 时应用查询仍然工作，但巡检会认为 15 列全缺、再报 15 列全多。我用 SQLite 建了全大写列名的同构三表实测：`_inspect_schema` 返回 80 条 drift（40 missing + 40 extra），status 直接 `unavailable`。表名同理：SQLite 的 `has_table` 与反射名大小写敏感，MySQL 在 Linux 上表名敏感（那种情况下应用查询也会坏，算真漂移）。

**问题**：这是“监控自身把可用部署判成不可用”的假阳性；一次 80 条 `contract_drift` 还会刷日志。

**预判**：比较前把表名/列名统一 casefold（或按 `lower()` 建映射），并按“规范化名”输出 field；同时补一条“外部 DDL 大写列名仍为 ok”的用例。若坚持列名大小写也是契约，应在 06 §4 写明，并让应用查询也显式引用大小写（目前做不到）。

**结论**：

### D3 读失败边界没有覆盖全部公开外部读，且 `analysis_progress` 用消息启发式

**位置**：`apps/api/app/db/crud/bad_cases.py:274-309`（`analysis_progress`）、`apps/api/app/api/acquisition.py:242`、`apps/api/app/db/crud/attributions.py:763-779,874-889`、`apps/api/app/db/crud/overview.py:122-186,405-430`

**现象**：PR 声明“`ProblemRepository`、`BadCaseRepository`、`AttributionRepository` 的公开读方法统一加边界”，实际 `analysis_progress` 未加，且保留旧启发式：`except (OperationalError, ProgrammingError)` 后仅当 `"bad_cases" in str(exc).lower()` 才降级为 0，否则 re-raise。用测试假 DB 实测：权限错误（1142）也被判成“`bad_cases` is not provisioned”并返回 0，`/api/acquisition/status` 静默显示 0 进度；而如果异常消息里不含 `bad_cases`（例如连接级 1044 “Access denied for user...”），就会变成未分类 500。`list_run_attributions`（演进 run 详情）与 overview 的外部读同样没有新边界，权限不足时仍是 500——用户会看到“问题页 503、总览/run 页 500”的不一致。

**问题**：新错误码只覆盖“被装饰的方法”；而 `analysis_progress` 的降级条件不是“表不存在”，是“异常文本里恰好有 bad_cases（通常是 SQL 文本）”，既会把权限问题误诊成未建表，也会在消息变化时漏判。命名上的“统一边界”与实际覆盖不一致。

**预判**：给 `analysis_progress` 选择明确语义：要么加 `@read_only_guard('bad_cases')` 并让浮层显示降级（不再静默 0），要么显式区分 `EXTERNAL_READ_FORBIDDEN`（503/告警）与“未建表”（0）；把 `list_run_attributions` 与 overview 的读路径纳入同一守卫或写明“本 issue 不做”。另建议守卫只包住“外部表查询段”，避免 `session_families` 等核心表的故障被贴上 `table='bad_cases'` 的标签（`problems.py:77-99` 的 guard 覆盖了整个快照，包括 `_family/_agents/_events`）。

**结论**：

### D4 巡检“不可读”与“字段漂移”的日志语义：已修一半

**位置**：`apps/api/app/db/external_contract.py:436-479`（`_log_report`）、`:387-435`（`inspect_external_contract`）、`.agents/notes/.../2026-10-26-external-read-models.md:15`

**现象**：`409ab89` 之前的版本在权限失败时会打 `WARNING external problem table contract drift detected` 且 `drift_count=0`；最终 head 的 `2839c47` 已加 `if report.status == "forbidden"` 分支，改打 `ERROR external problem tables are unreadable` 并 return（`:457-459`）。但**非 DBAPI 的 `SQLAlchemyError` 分支**（`:410-417`）仍返回 `unavailable` + 空 drifts，随后 `_log_report` 仍会打“contract drift detected”（drift_count=0）；另外该分支用 `logger.exception` 输出原始异常文本，和 Note 的“日志只写表名、列名、漂移种类与计数、不写 SQL”并不完全一致（当前实测没有 SQL 泄漏，但断言是“消息里没有 SQL”，不是“结构上不可能”）。

### D5 契约测试是“自证”，且没有 MySQL 覆盖

**位置**：`apps/api/tests/m12-02-external-contract-live/test_schema_contract.py:53-61`（用 `DOMAIN_METADATA.create_all` 建表）、`:230-234`（只断言表名在 metadata 里）、`test_live_external_tables.py:46-87`（skip）

**现象**：`test_contract_accepts_provisioned_external_tables` 用 `domain.py` 的模型建表，而 `EXTERNAL_TABLES` 正是照着这个模型写的——它只能证明“契约与模型自洽”，不能证明“外部所有者的真实 DDL 与 06 §4 一致”。`test_schema_can_be_recreated_from_the_published_model` 只检查 `DOMAIN_METADATA.tables` 含三个表名，几乎空转。新增套件没有一条 MySQL 用例（`grep` 无 `mysql` marker），而 D1 的两类假阳性恰好都发生在 MySQL 反射类型上；唯一能验证真实 schema 的 live 用例被 skip。PR 描述/Note 说“默认套件用受控 SQLite/MySQL 与只读 SQL 断言覆盖”，与事实不符。

**问题**：本 PR 的核心承诺是“按 06 §4 巡检”，但默认证据是“契约 vs 同一个模型”；一旦外部 DDL 与模型在类型/大小写上有差异，测试不会发现（D1/D2 就是例子）。

**预判**：把 06 §4 的列签名落成一份可独立比对的 fixture（或生成表格），让测试对“规范”而不是对模型断言；至少加一个 MySQL 类型族单测（构造 mysql 反射类型跑 `_family/_type_drift`，无需服务）和一条大写列名用例；PR 描述把“SQLite/MySQL”改成“SQLite 默认 + MySQL 待 CI 服务覆盖”，别把待办写成已完成。

## §9 文件级代码分析

### `apps/api/app/db/external_contract.py`（A，565 行）

**职责**：外部三表的只读契约与诊断层：契约数据、schema 巡检、读失败分诊、读方法装饰器、周期监控。变更形态：新增。

**关键依赖**：SQLAlchemy 的 `inspect/get_columns`（反射，运行时读元数据）、`AsyncEngine.run_sync`（把同步 inspector 塞进异步连接）、标准库 `logging` / `asyncio` / `functools`。比喻：inspector 是“拿图纸的验房师”，`run_sync` 是“把验房师送进异步电梯”，`logging extra` 是“巡检单的勾选框”，`read_only_guard` 是“分诊台”。

**分段理解**：

1. 契约数据（`:95-151`）：40 列手写镜像；与 06 §4 / `domain.py` 逐列一致（我对照过）。这是“单一事实”的薄弱点：三处（06 §4、domain 模型、本文件）需要人工同步，本 PR 只靠测试对模型自证（D5）。
2. 类型族（`:180-219`）：`_family` 的 `isinstance` 顺序（JSON→CHAR→Text→String→DateTime→Boolean→Float/Numeric/Double→Integer）本身正确；问题在“名义族”不等于“行为兼容”（D1），以及 `_type_drift` 只在 `length` 是 int 时检查最小长度（`length=None` 视为兼容，对 MySQL 无长度类型合理，但对 SQLite 的 `VARCHAR` 反射同样是 None，属于宽松策略）。
3. 巡检（`:222-283`）：单连接、单事务、只读；`has_table` 先判表，因此不会用 `NoSuchTableError` 当控制流。额外列按 `sorted` 输出，日志稳定。
4. 分诊（`:286-352`）：`_db_error_code` 从 `orig.args[0]` 取 int；`_error_text` 只用驱动消息（用于 marker），不写日志；`_FAILURE_MESSAGES` 固定文案。风险是 marker 匹配（“does not exist”等）依赖驱动文本，跨驱动可能误判，但当前只支持 sqlite/mysql，可接受。
5. 守卫（`:355-383`）：`functools.wraps` 已在最终 head 补上；`except AppError: raise` 保业务错误；`args[0]._database.dialect` 取方言，测试 double 也满足。它不强制只读，名字略宽。
6. 巡检入口（`:387-435`）：DBAPI 错误分诊后返回 report（forbidden/unavailable），非 DBAPI `SQLAlchemyError` 记 exception 后返回 unavailable；最终 head 删掉了“drift→READ_FAILED”的改写，让 1146/1054 仍能落到 `EXTERNAL_SCHEMA_DRIFT`（语义更准，但 `_log_report` 的 message 仍可能说 drift，见 D4）。
7. 日志（`:436-479`）：ok → INFO；forbidden → ERROR“unreadable”（新）；全缺表 → INFO“not provisioned”；其余 → WARNING + 每 drift 一条。`external.contract_check` 的 `extra` 含 status/dialect/tables_checked/drift_count/duration_ms/error_code，都是受控值。
8. 监控（`:481-565`）：start/refresh/loop/stop/TTL；`stop` 先置 `_task=None` 再 cancel+await。缓存 API 无消费者（D7）。

**检视发现**：D1、D2、D4、D7 的源头；类型族单测缺失（未覆盖 192/197/217 行，覆盖率 95%）。无写入路径，`engine.connect()` 不写。

### `apps/api/app/service/sessions/service.py`（M，ad2e182 新增）
