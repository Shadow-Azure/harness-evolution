## §1 一页速览

一句话：把 bad case 列表从“图表筛选的附属品”改成“自己的查询”，并用一个可选布尔参数让“空日期 = 不限时间”在服务端成立。

比喻：以前列表和图表共用一根水管，关小图表的水阀，列表也跟着变小；现在给列表接了独立水阀，还新装了一个“全开”档位——空日期不是“回到 90 天”，而是真正不设时间闸门。

| 交付块 | 内容 | 验证基线 |
| --- | --- | --- |
| URL 状态 | `lfrom/lto/lobject` + 既有 `page/type` | `overviewUrl.test.ts`、深链 E2E |
| 查询独立 | 列表只读列表状态；空日期发 `allTime=true` | Index 单测、API 测试、E2E 请求断言 |
| 控件与错误 | 日期/来源/类型/重置；单边或倒置日期就地提示且不发请求 | 组件单测、E2E 03 |
| 分页与空态 | 列表筛选重置 `page=1`；过滤空态与空间空态分离 | Index 单测、E2E 04/05 |
| 契约扩展 | 列表端点一个可选布尔 `allTime` | OpenAPI 测试、`contract:check` |

## §2 架构导览

### 2.1 URL 是唯一事实源

`overviewUrl.ts:28` 把列表日期和来源加入 `OverviewUrlState`，与既有 `page`/`type` 并列。解析在 `:233` 用同一个 `validWindow` 处理 `lfrom/lto`：只要不是“完整且有序”的一对就丢弃，而不是回落到图表的窗口；这样旧 URL 里的残缺日期不会悄悄把列表变窄。序列化在 `:293` 只为 cases Tab 写 `lfrom/lto/lobject`，并保留旧键 `type`/`page` 的含义。`:473` 的 `overviewListWindow` 把“成对才有限制”固化成可测试的纯函数。

### 2.2 列表查询与图表查询分叉

`Index.vue:66` 的 `caseFilters` 只从 `state.listFrom/listTo/listObject/type/page` 组装：有完整日期就发 `from/to`，否则发 `allTime: true`。`summaryFilters`/`trendFilters` 仍然从全局 `range/objects/grain` 组装，两者互不读取。`Index.vue:215` 的全局清除只重置时间、粒度和来源；`:227` 的列表清除才重置列表四项和页码。`:260` 的桶点击把桶窗口写进 `listFrom/listTo`，不再改 `range/from/to`。

### 2.3 服务端的“真正不限”

`service.py:265` 在 `all_time` 为真时完全跳过 `query.window.window()`，把 `start/end` 留空；`crud/overview.py` 的 `_case_conditions` 只有在两端都存在时才追加日期谓词。`api/overview.py:366` 只把这个参数暴露给列表路由，其余三个总览读端点不变。这样既没有扩大 366 天的窗口限制，也没有让前端用 `1970..今天` 之类的假窗口绕过校验。

### 2.4 控件的本地草稿

`BadCaseTable.vue:89` 用 `draftFrom/draftTo` 保存输入中的值，`:106` 计算错误文案：成对且有序才合法，单边提示补全，倒置提示“开始日期不能晚于结束日期”。`:126` 只在合法时 `emit('update:filters')`；两个都清空时立即恢复不限。这样“非法日期不发请求、保留上一个有效结果”不是靠父组件猜，而是组件的输入约束。`:119` 还会把 URL 里已选但 summary 选项里暂缺的来源补进下拉，避免 summary 失败时控件显示空白。

## §3 数据流走查

一条端到端主线：

1. 用户打开 `/workspaces/:wid/overview`。`parseOverviewQuery` 得到默认 `range=90`、列表日期/来源为空（`overviewUrl.ts:233`）。
2. `Index.vue:66` 组装列表 filters：`{allTime: true, objects: [], badCaseType: "all", page: 1, pageSize: 8}`；`useOverviewCases` 以该对象作为 query key。
3. `api/overview.ts:194` 把 `allTime` 写成 `allTime=true`，不发送 `from/to/range`；`listOverviewBadCases` 仍发送 `page/pageSize`。
4. 后端 `list_workspace_bad_cases` 收到 `allTime=true`，`OverviewService.list_cases` 跳过窗口解析，repository 只按 workspace、来源、类型过滤并分页（`service.py:265`）。
5. 用户选 `lfrom/lto`：组件先写草稿，合法后 emit；`Index.applyListFilters` 把 `from/to` 映射到 `listFrom/listTo`、`page=1`，`router.replace` 写 URL；query key 变化触发新请求，请求携带 `from/to`，不再带 `allTime`。
6. 用户把 `from` 改到 `to` 之后：组件只更新草稿并显示错误，URL 和 query key 不变，上一页结果继续显示；修正或清空后才重新请求。
7. 用户翻到第 2 页：`setPage` 用 `router.push` 写 `page=2`，保留列表筛选；浏览器后退回到第 1 页并恢复筛选。
8. 点击趋势桶：`selectBucket` 只写 `lfrom/lto` 和 `page=1`；图表的 `range/from/to` 不变，summary/trend 不重新取数。

## §6 讨论点

### 6.1 `allTime` 布尔是否应改为窗口哨兵

- **位置**：`apps/api/app/service/overview/service.py:265`
- **现象**：列表“无日期限制”由新增布尔参数表达，其他总览读端点不识别它。
- **问题**：一个只服务单端点的布尔参数会让契约出现不对称；另一种做法是给 `range` 增加 `all` 值，让窗口模型统一表达。
- **预判**：布尔更窄，不影响既有窗口校验和其余三个端点；`range=all` 会迫使窗口解析、粒度和 422 语义认识特殊值，代价更大。当前选择合理。
- **结论**：（留空）

### 6.2 旧 URL 的 `objects` 不再收窄列表

- **位置**：`apps/web/src/pages/overview/Index.vue:66`
- **现象**：旧 URL `?objects=alpha&page=2&type=self` 仍解析，`objects` 只作用于图表/统计，列表只受 `type/self` 和 `page` 约束。
- **问题**：这是用户可感知的行为变化；书签里的列表范围会变大。
- **预判**：列表独立正是本 issue 的目标，`page/type` 保持旧义已覆盖分页和类型；只有来源需要用户重新在列表头选择。可接受，但应在发布说明中提一句。
- **结论**：（留空）

### 6.3 日期是“成对”语义，原型允许单边

- **位置**：`apps/web/src/pages/overview/components/BadCaseTable.vue:106`
- **现象**：只填一侧时组件提示补全，不发请求；原型对 `from`/`to` 各自判空，支持单边开放。
- **问题**：这是与原型的一处能力差异；若产品要求单边开放，现有 API 无法表达“只限开始”或“只限结束”。
- **预判**：本 issue 的验收与“非法日期区间”措辞都按成对理解，单边开放需要新的窗口契约（例如 `allTime` 配合单边），不宜在本 PR 私自扩展；建议另开切片。
- **结论**：（留空）

### 6.4 `page`/`type` 与进化对象视图共用 URL 键

- **位置**：`apps/web/src/pages/overview/overviewUrl.ts:293`
- **现象**：cases Tab 的 `page` 是列表页，targets Tab 的 `page` 是潜在 bad case 页；`type` 只在 cases Tab 序列化。
- **问题**：同名键在不同 Tab 含义不同，切换 Tab 时既有逻辑重置 `page`，可能让列表页码丢失。
- **预判**：这是 m8-04 以来既有的 URL 结构，本 PR 保持兼容；若要拆成 `listPage`/`casePage` 会破坏旧链接。保留现状，不扩大改动面。
- **结论**：（留空）

### 6.5 全量列表的计数成本

- **位置**：`apps/api/app/db/crud/overview.py:352`
- **现象**：默认列表会对整个空间的 bad case 做一次 `count(*)` 再取 8 行。
- **问题**：大空间下 `count(*)` 是否成为首屏瓶颈。
- **预判**：`bad_cases` 有 `workspace_id` 索引，计数与分页都只扫该空间；当前生产规模（个位数到千级）无实害。若未来到十万级，再考虑近似计数或游标分页。
- **结论**：（留空）
