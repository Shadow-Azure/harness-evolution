## §1 一页速览

一句话：聚类的「分组」仍由词面 Jaccard 在本地算，但「这些 case 是不是同一根因」「这个簇多可信、多严重」两件事改由模型判断——为了不让 prompt 随 case 总量 N 膨胀，代码只把**草稿键**（`D1..Dk`）、每草稿 3–5 条代表样本和几个确定性统计量递给模型，模型只能回答「哪几个 D 合并、叫什么、多可信、多严重」，成员列表始终留在代码里。

比喻：这像**法院的案卷分案**。书记员（词面分组）先把案卷按相似度码成若干摞，每摞只贴一张标签（`D1`）；法官（`cluster.review`）只看标签、每摞抽三到五份样卷和一张统计卡片，然后裁定「第 1、2 摞是同一个案子，叫『检索索引问题』」——法官从不接触全部案卷，所以案卷再多，法官的工作量也不变。随后两个评分员分别只回答两个问题：`cluster.score` 打「这个案子合并得对不对」的可信度（0–1，且引用的样卷必须来自本案卷袋），`severity.score` 打「这个案子多严重」（0–10 决策分 + 五维 + 一张 CVSS 式向量）。任何一个评分员缺席，就用桌上的**旧表格**（类目常量 / 公式分）顶上——案子照样结，只记一笔 `degraded`。

## §2 架构导览

### 2.1 三层与依赖方向

`cluster_llm.py` 刻意只依赖三样东西：`pydantic`、`time/logging` 等 stdlib，以及 `cluster.py` 的纯值对象（`ClusterDraft`/`ClusterType`/`TYPE_CONFIDENCE`/`TYPE_IMPACT`/`cluster_severity`）与 `ai_agent` 的契约（`cluster_llm.py:28-43`）。它不知道数据库、不知道 git、不知道 prepare。这带来一个好处：`enhance_clusters` 可以在 1.7 秒内被 26 个测试反复驱动，而真实的 `AIAgentProvider` 由调用方注入（`:787-795`）。

prepare 这一侧把「读库 → 统计 → 调模型 → 落库 → 记事件」全部收进 `_build_clusters`（`prepare.py:469-539`），并抽出一个可序列化的结果包 `_ClusterBuild`（`prepare.py:133-139`）：`clusters`（已落库的行）、`fingerprint`（审计 hash）、`algorithm`（算法标识）、`severity_comparison`（公式分对照行）。这个包是「本次聚类做了什么」的唯一事实，`handle` 只负责把它写进 `run.stats` 与 `clusters_created`（`prepare.py:348-377`）。

### 2.2 审查层：只合并不拆分的构造性守恒

审查的接口设计是「用键说话」：prompt 里每个草稿是一个块 `[D1] type=prompt members=18 signatureOverlap=0.42 reportedSpanDays=21`，加一行 `summary:` 和 3–5 行 `- <case-id> | title: … | text: …`（`cluster_llm.py:434-452`）。模型输出 `{"clusters":[{"from":["D1","D2"],"title":"…"}]}`，成员由代码按 `from` 展开（`:1009-1029`）。**输出量因此是 O(K)，与 N 无关**——这是设计里「守恒是构造性的」那句话的实现。

硬闸在 `validate_review_partition`（`:573-624`）：先按输入草稿生成期望键集 `D1..Dk`（`:597`），再逐项检查标题非空、键必须能映射回草稿（`_draft_index`，`:603-604`）、同一键不得出现在两个 item（`:605-611`，同时也就禁止了「把一个草稿拆成两个簇」）、一个 item 内的草稿类型必须一致（`:612-617`），最后报告缺失键（`:618-623`）。任何一条违反都抛 `ClusterContractError`，`_review` 捕获后整批回退到词面草稿（`:925-931`）——不做部分接受，因为部分接受会破坏「划分完整性」这个不变量。

一个容易忽略的细节：prompt 规则 3 与规则 4 把「每个键恰好一次」和「merge-only」写成了两条自然语言规则（`:417-425`），而 validator 用同一个 `seen` 字典同时实现两者。也就是说「模型违规」与「代码不变量」是同一件事的两种表述，不是两套逻辑。

### 2.3 评分层：两次批量调用与三层校验

两次评分调用的 prompt 结构相同：开关是 rubric/维度锚点（`:480-501`、`:534-560`），主体是每个最终簇的 header + 最多 5 条样本（`:503-507`、`:561-565`）。`_render_cluster_header` 把 `type / title / description / members / signatureOverlap / reportedSpanDays` 压成一行（`:1128-1137`），所以评分员看到的输入形状与审查层一致，只是键从 `D` 换成了 `C`。

校验分成三层：

1. **模型校验**：`ClusterScoreItem.confidence` 0–1（`:195`）、`SeverityScoreItem.overall` 0–10 与五维 0–10（`:220-221`）、`vector` 必须匹配 `^CVSS:3\.1(/[A-Z]{1,3}:[A-Z])+$`（`:143`、`:222`）。
2. **覆盖校验**：每个 `C` 键恰好出现一次，多、少、重复都拒（`:653-699`、`:702-743`）。
3. **引用校验**：`evidence_refs` 必须是**同一簇** prompt 样本 id 的子集（`:627-650`，`validate_cluster_scores` 在 `:689` 传入 `by_key[item.cluster].members`）。

三层任何一层失败都走同一个出口：整批降级。这是本 PR 最值得讨论的设计点（§6 点 1、2）。

### 2.4 降级矩阵与「观测不阻塞业务」

三条降级路径在代码里是三个独立的 `try/except` 段，形状完全对称（`:916-933`、`:948-965`、`:985-1002`），都是「先构造 fallback 字典，再请求，再 `model_validate` + 语义校验，成功返回结果、失败记两条事件后返回 fallback」。fallback 的来源分别是：审查 → `_fallback_groups`（`:1032-1043`，原样使用草稿，`fallback=True` 用来在描述拼装上跳过 LLM 组合）；置信度 → `TYPE_CONFIDENCE`（`:943-945`）；严重度 → `cluster_severity(type, member_count)`（`:975-982`）。

观测侧用两个回调 `RecordCall` / `RecordDegraded`（`:351-355`），`_notify_call`/`_notify_degraded` 吞掉回调异常并 `logger.exception`（`:1223-1240`）——「记事件失败不能把业务带崩」。prepare 把两个回调实现成两次 `_record`（`prepare.py:584-612`），`_record` 本身也是 best-effort（`prepare.py:824-848`）。

### 2.5 prepare 的双分支：lexical 与 hybrid

`_build_clusters` 在词面草稿产出之后分流（`prepare.py:503-511`）：`agent is None` 走 `_lexical_writes`（`prepare.py:980-1016`），否则走 `_enhance_clusters` + `_enhanced_writes`（`prepare.py:1019-1044`）。两条分支最终都交给同一个 `replace_prepared_clusters(run.id, writes)`，写出同一组 `ClusterWrite` 字段——这正是「零迁移」的实现方式：DB 列没变，变的是值的来源。

hybrid 分支的 fingerprint 是对**增强后**的簇（type + LLM description + probes）算的 `cluster_hash`（`prepare.py:522-531`）；lexical 分支仍是对草稿算的（`:509`）。也就是说 `clusters_created.payload.clusterHash` 在两分支下含义都是「本次持久化簇的规范摘要」，但输入文本不同，跨分支不可比。

### 2.6 统计量：把 N 压成几个数字

`_enhance_clusters` 在调模型前做三件事（`prepare.py:556-582`）：

- 把 `BadCaseEvidenceRecord` 转成 `ClusterCaseEvidence`（带 title/description/reported_at）；
- 按草稿聚出 `case_ids`（bad case 维度，不是 probe 维度）；
- 算 `signature_overlap`（词面紧密度）与 `time_span_days`（上报时间跨度）。

三个统计量最终都只以「一个数字」进 prompt，所以 prompt 长度与 N 无关（§1 实测 1831/1866/2190 字符三份 prompt 在 N=50 与 N=200 下逐字符等长）。

### 2.7 描述拼装与支撑件

- `_compose_description`（`:1116-1125`）：`"{type} 类问题 · {title} · {summary}"`，title 上限 120、summary 上限 200；若模型标题已带 `{type} 类问题 · ` 前缀则先剥掉，整体再由 `DESCRIPTION_MAX_CHARS=300` 截断。因为 06 §5.3 没有 title 列，LLM 的标题只能折进 `probe_cluster_description`。
- `_render_span`（`:1148-1150`）：没有时间戳时渲染字符串 `unknown`，而不是编一个 0。
- `_evenly_spaced_indexes`（`:1153-1162`）：`round(position * (total-1) / (count-1))`，等距取点；`count==1` 时取中点，避免除零。
- `_bounded`（`:1243-1248`）：折叠空白 + 截断 + 省略号，所有进 prompt/model 的外部文本都过它。
- `_draft_index`（`:1100-1113`）：拒绝 `D01`、`D0`、`D999` 之类非法键，把「键解析」也纳入契约。

## §3 数据流走查

一条 cluster-only run 的端到端剧本（实测，含真实事件序列）：

1. **进入 prepare**。`handle` 按 `progress_unit` 走七步；到第 4 步（attribution 完成）后进入聚类（`prepare.py:345-377`）。
2. **读归因行**。`_build_clusters` 调 `list_clusterable_probes` 拿到 `(probe_id, attribute_type, bad_case_id)` 三元组，装出 `cases_by_probe` / `type_by_probe`（`prepare.py:478-483`），再用 `load_bad_case_evidence` 批量读标题、描述与 `created_at`（`prepare.py:484-485`、`attributions.py:512-551`）。
3. **词面分组**。`cluster_probes` 按 `model/prompt/error` 顺序、类内单链连通分量合并（`cluster.py:80-126`），产出 `ClusterDraft`（type + 描述 + 成员 probe id）。
4. **统计**。每个草稿算 `case_ids`、`signature_overlap`（成员标题两两 Jaccard 均值）、`time_span_days`（最早/最晚 `bad_cases.created_at` 之差，进入 prompt 时标签为 `reportedSpanDays`）（`prepare.py:565-582`）。
5. **审查调用**。`build_review_request` 把草稿渲染成 `[D1]…[Dk]`（`cluster_llm.py:434-452`），`agent.analyze` 一次；实测 N=50 与 N=200 的 review prompt 都是 1831 字符、15 条样本行，且 `case-0150` 不出现（§1 探针 P1）。输出经 `ClusterReviewOutput.model_validate` + `validate_review_partition`，通过则 `_groups_from_review` 按最小草稿下标排序（`:1009-1029`）。
6. **建评分计划**。`_build_plans` 把每个 group 展开成 `ClusterPlan{C1..Cm}`，合并统计量、重新抽样 3–5 条（`:873-900`）。**从此之后所有调用都只看 C 键。**
7. **批量置信度**。一次 `cluster.score`；`validate_cluster_scores` 同时校验覆盖与同簇引用（`:653-699`）。
8. **批量严重度**。一次 `severity.score`；`validate_severity_scores` 校验覆盖（`:702-743`）。
9. **组装与排序**。`enhance_clusters` 用 `zip(groups, plans, strict=True)` 把两组值装回 `EnhancedCluster`（`:842-864`），`_enhanced_writes` 再按 `(-severity, -member_case_count, type)` 排序并编 `rank`（`prepare.py:1019-1044`）。
10. **落库**。`replace_prepared_clusters` 写 `probe_clusters` 与 `probe_cluster_probes`，`confidence`/`severity`/`rank` 用增强值，`impact` 仍是类目常量（`prepare.py:520-521`）。
11. **记审计**。`run.stats.clusterAlgorithm` + `clusters_created.payload{algorithm, clusterHash, similarityThreshold, severityFormula?, degraded?}`（`prepare.py:348-377`）；`severityFormula` 每行含 `clusterHash`（单簇摘要）、`severityFormula`、`severity`、`dimensions`、`vector`（`prepare.py:1068-1093`）；有降级时 `degraded` 按任务顺序列出任务键，全部成功则不写该键。
12. **事件序列（实测，默认 `claude-code` 占位）**：`prepare_started → sessions_linked → potential_computed → attribution_created → ai_agent_call(cluster.review) → degraded(cluster.review) → ai_agent_call(cluster.score) → degraded(cluster.score) → ai_agent_call(severity.score) → degraded(severity.score) → clusters_created`，其中 `degraded` 为 `level=warn`。run 最终 `completed`，簇描述回到词面文本，置信度 0.74/0.74，严重度 5.7/5.2（公式分），算法标识仍为 `hybrid-lexical-llm-v1`。

## §6 讨论点

> 每条固定五段；**结论**记录维护者拍板结果（日期、决定与理由），未拍板的讨论点保持空。

### 讨论点 1：批量评分是「全或无」——一个簇的非法值让所有簇的置信度一起降级

**位置**：`apps/api/app/service/evolution/cluster_llm.py:936-965`（置信度批次）、`:968-1002`（严重度批次）、`:653-699` 与 `:702-743`（覆盖校验）；批量化的提交是 `0e7cce91`

**现象**：实测两个最终簇、`cluster.score` 返回 `C1=0.93, C2=1.4`（越界）时，落库置信度是 **0.74 / 0.74**（两簇都回 `TYPE_CONFIDENCE["prompt"]`），degraded 理由 `output failed schema: scores.1.confidence`；同一批的严重度 8.5/4.0 不受影响。更常见的模型错误——百分比尺度（`93`/`61`）——同样让两簇一起回 0.74，理由指名 `scores.0.confidence, scores.1.confidence`。测试 `test_cluster_score_batch_coverage_violation_degrades_every_confidence`（`test_clustering_three_layers.py:613-634`）把「少一个键 → 全部降级」钉成了契约。

**问题**：issue 与设计里的「失败隔离」（07 §5.5.2：「两次调用失败隔离」）说的是**任务之间**（置信度失败不影响严重度），这一点实现是对的。但把 1+2K 次调用压成 3 次（`0e7cce91` 的成本形态修复）顺带把「簇之间」的隔离也取消了：一个簇的格式错误会连坐所有簇。真实模型最容易犯的恰恰是尺度/范围/漏字段这类**局部**错误，代价却由整批承担。反过来看，批量也有硬收益：成本形态降到 3 次、可观测事件固定 6 条、prompt 有全局上下文可做相对校准。

**预判**：不建议退回 1+2K。可考虑「批量优先 + 单簇重试」的两段式：整批失败后，对每个 `Ci` 单独补一次小批量（或只对失败簇重试），把连坐面缩到真正坏的簇；或者保留批量但在 `cluster.score` 上放宽为「逐项丢弃坏项、其余保留」，把「覆盖完整性」从硬闸降级为可降级信号（`degraded` 里记哪几个簇缺失）。前者多花调用（失败时最多 +K），后者不改成本但削弱「每簇恰好一次」的守恒。取舍点：本 PR 的 3 次成本形态是设计红线，任何重试都必须不改变成功路径的调用数。

**结论**：已决 2026-11-22：保持批量全或无（理由：3 次调用是设计红线，issue 的失败隔离指两个评分任务之间，这一点已实现；「单簇重试」若做也不得改变成功路径的调用数，留作后续 issue）。

### 讨论点 2：`extra="forbid"` + 必填 `vector` 让一个多余/缺失字段毁掉整批

**位置**：`cluster_llm.py:170`（`ClusterReviewItem`）、`:192`（`ClusterScoreItem`）、`:217`（`SeverityScoreItem`）、`:222`（`vector` 必填 + 正则）、`:926-931`、`:958-963`、`:995-1000`

**现象**：实测 `{"clusters":[{"from":["D1","D2"],"title":"…","confidence":0.9}]}` → `ValidationError`，整批审查回退（两簇描述变回词面）；而**顶层**多一个键（`{"clusters":[…],"note":"ignored"}`）被静默忽略——同一个模型里 `extra` 策略上严下松。严重度侧：C2 漏写 `vector` → 两簇严重度一起回公式分（5.7/5.2），哪怕 C1 的 8.5 完全合法。CVSS 串大小写写错（`cvss:3.1/av:n`）同样整批失败——正则只认大写（`:143`）。

**问题**：`extra="forbid"` 的动机写在 docstring 里（`:163-168`）：「多一个字段说明模型没遵守契约，整批降级而不是猜」。这在「契约即事实源」的立场上自洽，但对真实模型过于刚硬：模型多写一个 `"reason"` 或 `"confidence"` 字段是极常见的「善意越权」，代价是整批审查作废、6 条事件、run 的簇描述退回词面。设计文档 07 §5.5.3 的六层防线里，第 2 层是「服务端校验」、第 4 层是「有限重试与降级」，第 5 层还要求把「解析失败率、回喂重试次数」记进 `ai_agent_call`——说明设计预期的是「回喂重试」，而本 PR 只实现了「直接降级」。

**预判**：两条路。① 保持严格但补回喂：审查失败时把 `_contract_reason` 作为反馈再请求一次（provider 层的 `feedback_prompt` 已有现成通道，见 Note `:33`），仍失败才降级；② 放松为 `extra="ignore"`，用 validator 只校验语义（划分、范围、引用），把「多余字段」降为日志/事件里的观测项。我倾向 ①：既不放弃契约，也不让一次善意越权毁掉整批；成本是失败路径多一次调用，成功路径不变。另外顶层 `ClusterReviewOutput` 也应该与子项同策略，避免「顶层宽松、子项严格」的意外。

**结论**：已决 2026-11-22：保持 `extra="forbid"` 严格校验（理由：六层防线的第 4 层由 bugfix-17 的一轮 `--resume` 回喂补齐；放宽为 `extra="ignore"` 会放弃「契约即事实源」，而回喂只影响失败路径）。

### 讨论点 3：`main.py` 注入默认 `claude-code` 占位，生产每次 prepare 付 3 次失败调用 + 3 条 degraded

**位置**：`apps/api/app/main.py:195`（`build_agent_provider`）、`:408`（`agent=ai_agent_provider`）；`apps/api/app/config.py:158-161`（默认 `claude-code`）；`apps/api/app/third_party_api/ai_agent/factory.py:26-46`（占位 `analyze` 直接 `raise NotImplementedError`）；`prepare.py:512-520`

**现象**：用真实的 `_PendingClaudeCodeProvider`（即 `main.py` 在零配置下注入的实例）跑 cluster-only prepare，实测 run `completed`，事件计数 `{'ai_agent_call': 3, 'degraded': 3}`，三条 call 的 `outcome` 全是 `error`、`model` 全是 `unknown`、tokens/cost 全 0，degraded 理由全是 `NotImplementedError raised during analysis`；落库结果与旧词面路径**取值完全相同**（描述=词面、置信度 0.74/0.74、严重度 5.7/5.2），但 `run.stats.clusterAlgorithm` 与 `clusters_created.algorithm` 都是 `hybrid-lexical-llm-v1`。`m5-05` 的 launch 集成用例（`test_launch_api.py:465-479`）今天走的就是这条路径。

**问题**：这是「接线已通、后端未到」的中间态（真实 `claude-code` 子类是下一步 #492/#17）。问题不是它错，而是**代价被默认配置静默承担**：每个 run 多 6 次事件写入（含 6 次 SSE 发布）、3 次必然抛异常的调用，日志与 UI 里出现 3 条 `error` 级别的调用记录（虽然事件 level 是 info，见点 12），而数据库里的算法标识声称这次聚类「用了 LLM」。对运维来说，这是「每个 run 都报警一次」的噪声；对审计来说，这是「标识说 hybrid、实际全降级」的失真。设计也确实预期占位存在（Note `:35`：「三层各自降级后 run 照常完成，最坏情况等于词面路径」），但那条事实记录的是「行为等价」，没记「每次都产生 3 条失败事件」的成本。

**预判**：三种收窄方式。① 在 prepare 装配处判断 `provider.health_check()` 或一个能力标志，未实现的 provider 直接走 `agent=None` 的 lexical 分支（最干净：没有调用就没有失败事件，算法标识也诚实）；② 保留调用但只在 `AI_AGENT_PROVIDER=fake` 或真实 provider 注册后才注入 `agent`，默认零配置不接线；③ 维持现状，但在 `run.stats`/事件里把「全部降级」标成一个显式的 `clusterDegraded=true`，让 UI 能区分「hybrid 成功」与「hybrid 全降」。①的成本是一次健康检查（`health_check` 已在启动时调用，见 `main.py:522`），收益是默认配置零噪声；缺点是健康检查与真实可用性可能不一致。归属：在真实 provider 合并前决定，否则这段噪声会成为默认体验。

**结论**：已决 2026-11-22：保持默认占位接线，推迟到 #492（理由：provider 必须走真实装配才能验证接线与降级；占位必须触发降级而不是被静默跳过；#492 用真实 `claude-code` 子类替换后这 3 次失败调用与 3 条 warn 事件自然消失）。

### 讨论点 4：降级矩阵有一个洞——provider 返回非 Mapping 输出时 `ValueError` 逃逸，run 直接失败

**位置**：`cluster_llm.py:926`、`:958`、`:995`（三处 `dict(result.output)`）；契约 `apps/api/app/third_party_api/ai_agent/contracts.py:86-99`（`output: Mapping[str, Any]` 只是类型标注，运行时无校验）

**现象**：构造一个返回 `AnalysisResult(output="not-a-mapping", …)` 的 provider，`enhance_clusters` 抛 `ValueError: dictionary update sequence element #0 has length 1; 2 is required`，**degraded 列表为空**（一条降级都没记），异常一路穿出 `_build_clusters` → prepare 失败。`_review`/`_score_confidences`/`_score_severities` 的 `try` 只包住 `model_validate` + validator，`dict(...)` 在 try 内但 `except` 只捕获 `(ValidationError, ClusterContractError)`（`:928`、`:960`、`:997`）。

**问题**：这与「任一违反 → 整批回退、run 不阻塞」（Note `:35`、07 §5.5.2）的承诺直接冲突。今天不会触发（`fake` 返回 dict，占位在 `analyze` 里就抛异常被外层 `except Exception` 捕获），但真实 CLI 子类（#492）要经过 JSON5 解析、`json-repair`、`model_validate` 三道，最可能的失败形态恰恰是「解析出一个列表/字符串而不是对象」。类型标注不是运行时不变量，provider 是第三方边界，这里应该按不可信输入处理。严重度：中低（潜在；一旦真实 provider 上线就变成「模型吐一次坏 JSON，整个 run failed」，而不是「降级到词面」）。

**预判**：在 `cluster_llm` 里加一个边界函数：

```python
def _output_mapping(result: AnalysisResult) -> Mapping[str, Any]:
    output = result.output
    if not isinstance(output, Mapping):
        raise ClusterContractError(f"provider returned {type(output).__name__}, not an object")
    return output
```

三处调用改成 `ClusterReviewOutput.model_validate(dict(_output_mapping(result)))`，并把 `ClusterContractError` 纳入现有 `except`。这样「provider 吐坏形状」与「模型吐坏字段」走同一条降级路径，且 `degraded.reason` 仍是脱敏的（`_contract_reason` 只输出类型名/字段路径）。成本约 10 行 + 3 个参数化用例。

**结论**：已决 2026-11-22：修复（理由：provider 是第三方边界，`output` 的类型标注不是运行时不变量；非 Mapping 输出必须与字段违约走同一条降级路径，不能以 `ValueError` 逃逸把 run 打失败）。实现：新增 `_output_mapping`，三处 `dict(result.output)` 统一改用，并把 `TypeError`/`ValueError`/`ClusterContractError` 纳入降级 `except`。

### 讨论点 5：三层全降级时算法标识仍是 `hybrid-lexical-llm-v1`

**位置**：`cluster_llm.py:829-835`（空草稿也返回 `HYBRID_ALGORITHM`）、`:865-870`（返回值恒为 `HYBRID_ALGORITHM`）；`prepare.py:532-539`（hybrid 分支固定写 `HYBRID_ALGORITHM`）

**现象**：`_FailingProvider`（等价占位）下实测 `run.stats.clusterAlgorithm == hybrid-lexical-llm-v1`、`clusters_created.payload.algorithm == hybrid-lexical-llm-v1`，而簇描述、置信度、严重度全部来自词面/常量/公式，与 `lexical-jaccard-v1` 路径逐值相同（§3 第 12 步）。零草稿 run（attribution 后没有可聚类 probe）也会写 hybrid，尽管一次调用都没发生（`:829-835` 直接返回）。

**问题**：算法标识的用途是「回放时知道这批簇是怎么来的」（07 §5.5.2：「随 run 快照可回放」）。三点值得讨论：① 标识回答的是「用了哪条管线」还是「这条管线真的产出了什么」？如果前者，hybrid 是对的；如果后者，全降级的 hybrid 与 lexical 的产物不可区分，标识就失去了区分力。② 零草稿的 hybrid 更极端——没有任何 LLM 参与，却是 hybrid。③ `run.stats.clusterAlgorithm` 只落在 DB JSON 里：`EvolutionRunStats`（`runs.py:115-125`）是固定字段模型，`_stats()`（`runs.py:258-298`）只挑白名单键，所以 **API 消费者看不到这个标识**，能看到的只有 `clusters_created` 事件的 payload。

**预判**：标识本身保留「管线」语义是合理的（同一份代码、同一组任务），但建议同时落一个可判别的降级事实，例如 `clusters_created.payload.degraded = ["cluster.review","cluster.score",...]`（或 `algorithm` 变为 `hybrid-lexical-llm-v1+degraded`），并在 `EvolutionRunStats` 增一个可选 `clusterAlgorithm` 字段让 UI 能显示。这样「管线」与「实际贡献」两个事实都有 home，回放时不至于把一次全降级 run 误读成模型参与过的 run。若维护者认为「degraded 事件已经足够」，至少应在 Note 里写清「算法标识描述管线，不描述产出」。

**结论**：已决 2026-11-22：接受并修复为「标识描述管线 + payload 记录实际贡献」（理由：`hybrid-lexical-llm-v1` 回答的是用了哪条管线，降级不改它是自洽的；实际贡献由 `clusters_created.payload.degraded` 的任务键列表回答，全降级 run 因此可判别。Note 已写明算法标识不描述模型贡献）。

### 讨论点 6：合并簇的 `signatureOverlap` 是「草稿均值的加权平均」，不是成员两两均值——实测虚高一倍

**位置**：`cluster.py:129-152`（`signature_overlap` 的定义：给定文本的平均两两 Jaccard）、`cluster_llm.py:1046-1090`（`_merged_stats` 用 `weighted/weight` 合并）、`prepare.py:578-581`（草稿级计算）；注入 prompt 的位置 `cluster_llm.py:445-447`、`:1133-1137`

**现象**：两个草稿合并后的簇，`signatureOverlap` 由 `_merged_stats` 用 `Σ(overlap_i × member_i) / Σ member_i` 计算（`:1072-1073`、`:1088`）。实测：草稿 A 两名成员、标题两两 Jaccard = 0.5556；草稿 B 一名成员（单成员草稿恒为 0）。合并后 `_merged_stats` 给出 **0.3704**，而对三个成员标题直接重算的真实两两均值是 **0.1852**——虚高一倍。这个数字随后作为 `signatureOverlap=0.37` 进入两个评分 prompt 的簇 header（`:1133-1137`）。

**问题**：`signature_overlap` 的 docstring 明确定义为「mean pairwise lexical similarity of one draft's member titles」，评分 prompt 的置信度 rubric 也用「cases share one signature」作为 0.9/0.7 锚点（`:121-141`）。也就是说，模型被要求按「样本是否共享签名」打分，却被喂了一个在合并簇上偏高的统计量——而合并恰恰是 review 层的主要动作。单成员草稿的 `overlap=0.0`（`cluster.py:144-145`）在加权平均里被「稀释」而不是「补齐」，方向也不一致（一个单成员草稿不该把整簇紧密度拉低，也不该被忽略）。这不影响落库契约，但影响「置信度是否反映真实紧密度」这一层的质量。

**预判**：`_merged_stats` 已经拿到了合并后的 `case_ids` 与 `evidence`（`evidence[case_id].title` 就是成员标题），可以直接按合并后的文本重算 `signature_overlap`，只在 evidence 缺失时退回加权平均。成本是合并簇多一次 O(k²) 计算（§6 点 7 有实测：200 成员约 10ms）。另一个可选口径是把「单成员草稿」的 `0.0` 改成 `None` 并在加权时跳过，但那样统计量在 prompt 里出现 `unknown`，可读性更差。建议重算，并把「统计量必须能从持久化的成员集合复算」写进 Note。

**结论**：已决 2026-11-22：修复（理由：`signature_overlap` 的文档语义是簇内成员标题的平均两两 Jaccard，评分 rubric 也按「共享签名」打分；合并后必须按 `evidence[case_id].title` 重算，实测 0.1852 而非加权平均的 0.3704。仅当 evidence 缺失时回退加权平均，作为已文档化的降级口径）。

### 讨论点 7：`signature_overlap` 是 O(k²)，但真正的超线性在词面分组层——「分组 O(N)」的前提不成立

**位置**：`cluster.py:129-152`（两两循环）、`cluster.py:178-189`（`_connected_components` 按 posting list 两两比较）、`cluster_llm.py:578-580`（每草稿一次）、`prepare.py:565-582`

**现象**：本机实测（同一份合成文本，`N` 个成员聚成一簇）：`signature_overlap` N=200 → **10.1ms**、N=500 → 67.1ms、N=1000 → 238ms、N=2000 → 974ms、N=4000 → 4.2s（配对数 N(N−1)/2 从 1.99 万到 800 万）。同一批输入下 `cluster_probes`（词面分组）N=200 → 62–125ms、N=500 → 429–832ms、N=2000 → **8.1–12.9s**。也就是说：200 case 的簇上 `signature_overlap` 约 10ms，完全可接受；但分组层在共享 token 多时已经比 `signature_overlap` 贵 6–13 倍，且同样是近似二次的。

**问题**：任务描述与设计都写「分组层 O(N)、允许；LLM 层与 N 解耦」。前半句在**共享 token 稀疏**时成立，在「大量标题共享少数 token」时不成立：posting list 的笛卡尔积把 `_connected_components` 推到 O(Σ|posting|²)。这不是本 PR 引入的（分组层是既有实现），但本 PR 在它之上又加了一个 O(k²) 统计量，并把它写进「与 N 解耦」的叙事里——实际是「prompt 与 N 解耦，计算与 N² 相关」。对于今天 200 例量级的真实数据，实测开销可忽略；对于「一个簇囊括几百上千条 case」的极端 run，最坏会到秒级。

**预判**：本 PR 不需要改。但建议在 Note/设计里把「分组 O(N)」改成「分组在 posting 稀疏时近似线性、最坏 O(N²)」，并把 `signature_overlap` 的成本与上界（例如 k ≤ 采样上界时直接算，超过则降采样）写成已知项，避免后续以「O(N)」为前提做容量规划。若未来真的遇到千级簇，优化点应在 `_connected_components`（用 MinHash/LSH 或限制 posting list 长度）而不是 `signature_overlap`。

**结论**：已决 2026-11-22：记录设计措辞事实，不改代码（理由：分组层在共享 token 多时最坏 O(N²)，本 PR 新增的 `signature_overlap` 也是 O(k²)；200 例量级开销可忽略，但容量规划不能以「分组 O(N)」为前提，已在 §7 留档）。

### 讨论点 8：`select_samples` 等距取样——确定但不稳定，且「看了哪几条」没有落库

**位置**：`cluster_llm.py:758-784`（选择逻辑）、`:1153-1162`（等距索引）；调用点 `:439-443`、`:892-896`；样本未进入任何持久化字段（对照 `prepare.py:1068-1093`）

**现象**：实测 10 个成员 `c-0..c-9` 选出 `c-0,c-2,c-4,c-7,c-9`；增加一个 `c-10` 后变成 `c-0,c-10,c-4,c-7,c-9`（5 个里换了 1 个）。原因是 ① 先按字符串排序（`c-10` 排在 `c-1` 之后、`c-2` 之前），② 索引由 `total` 决定：10 成员取 `0,2,4,7,9`，11 成员取 `0,2,4,7,10`。同一个输入重放（同成员集合、同 evidence）结果稳定；但**数据增长一条就可能换掉一条样本**，且换掉的是哪条无法从落库数据反推——`evidence_refs` 校验完就被丢弃（点 13），样本 set 只在 prompt 里活过一次。

**问题**：三个层面。① 确定性够用（重放同一 DB 快照结果一致），但「跨 run 对比同一簇的置信度」时，样本不同会让分数漂移，审计时无法归因到「模型变了」还是「样本变了」。② 等距取点的语义在字符串序上并不等于「时间均匀」或「严重度均匀」——bad case id 是 ULID（`apps/api/app/utils/ids.py:6-8`，按时间可排序），所以排序≈上报时间序，等距≈时间均匀，这一点是巧合而非契约；若 id 换成 uuid，等距就变成任意位置。③ 未持久化样本集意味着「模型看到的输入」不可回放——对一个以「可审计」为卖点的三层设计，这是明显的缺口。

**预判**：① 若目标是「可回放」，最小改动是把选中的样本 id 写进 `clusters_created.payload`（与 `severityFormula` 同一层，K×5 个 id，体积可控），或者写进 `ai_agent_call` 事件（但事件按调用记，样本按簇分，结构更绕）。② 若要稳定性，改用「按 id 的哈希前缀排序后取前 s 条」（一致性抽样：插入新元素只影响落在窗口内的那条），代价是样本不再在时间上均匀。③ 若两者都要，可以「哈希分层 + 时间分位」组合，但对 200 例量级属于过度设计。我倾向先做 ①，把「模型看过什么」变成事实；② 等出现跨 run 对比需求再谈。

**结论**：已决 2026-11-22：推迟（理由：等距取样确定且可重放，但样本集未落库；把选中样本 id 写进 payload 属 bugfix-22 的可观测性范围，本 PR 不改成本形态与 payload 结构）。

### 讨论点 9：`time_span_days` 用的是上报时间（`bad_cases.created_at`），不是故障发生时间

**位置**：`apps/api/app/db/crud/attributions.py:512-551`（新增 `created_at` 读取，`:534`、`:550`）；`prepare.py:1057-1064`（`_time_span_days`）；`cluster_llm.py:1076-1085`（合并后重算）

**现象**：`bad_cases` 表没有「故障发生时间」列，只有 `created_at`（`apps/api/app/db/models/domain.py:295-320`，`nullable=False`）；`_time_span_days` 用 `evidence[case_id].created_at` 的 max−min。真实故障发生时间在候选表上有 `case_trigger_at`（`apps/api/app/db/models/evolution.py` 的 candidates 列；`prepare.py:735` 用它构造 `PotentialCase.case_trigger_at`），但 `list_clusterable_probes` 不返回它。docstring 诚实地写成「reported time span」（`prepare.py:1062`），prompt 里只显示 `timeSpanDays=21` 这样的数字，不带语义。

**问题**：「时间跨度」作为评分统计量的意图是「这个问题持续了多久 / 是否长期存在」——那应该用**发生**时间。用上报时间度量的是「报告渠道的活跃窗口」：一个 30 天前发生、今天才补报的故障与今天发生的故障在统计上无差别；批量导入的历史 case 会让跨度虚高。设计（07 §5.5.2）只写了「时间跨度」四个字，没有规定来源，所以这是实现层的口径选择，不是违约。但它会被模型当作「持续时长」读，从而影响 `scope`/`reproducibility` 的评分。

**预判**：短期内接受现状（零迁移是明确约束，`case_trigger_at` 需要扩 `list_clusterable_probes` 的返回列，属于小改但会动归因查询）。可选的最小改进：在 prompt 里把标签写成 `reportedSpanDays=`（一个词的改动），让模型知道这是上报跨度；或者在 Note 里记一句「时间跨度≡上报时间跨度」的取舍。若要真正改为发生时间，建议在后续 issue 里把 `case_trigger_at` 加进聚类查询并保留 `timeSpanDays` 作对照。

**结论**：已决 2026-11-22：修复为 `reportedSpanDays`（理由：值来自 `bad_cases.created_at`，是上报时间而非故障发生时间；零迁移不改查询，重命名标签并在 docstring 写明口径即可让模型正确理解）。

"·"` 回退、直接显示 `event.eventType` 原文，没有穷举 switch。所以「新增枚举值会不会炸消费者」的答案是**不会**。但两件事值得记录：① `degraded` 是一个与域无关的泛名，未来任何阶段（patch/eval/push）的降级都会复用这个名字，消费方无法只靠 `eventType` 区分「聚类的降级」与「patch 的降级」，必须读 `payload.task`；② 所有 `degraded` 与失败的 `ai_agent_call` 都以 `level="info"` 落库（`prepare.py:842`），而 UI 按 level 上色（`EventList.vue` 的 `:class="event.level"`）、API 支持 `level` 过滤——也就是说「模型三次全挂」在事件流里显示为三行普通信息，不会进入 warn/error 视图。

**问题**：① 泛名是可演化性的问题，不是当下缺陷；但既然这是第二个「跨阶段通用」事件类型（第一个是 `degraded` 自身），建议现在就把 `payload.task` 的取值空间当契约写进 Note，避免以后各阶段各造字段。② level 的选择更像一个疏漏：`eval_poller.py` 里同类失败用的是 `warn`/`error`（`:121`、`:471`、`:510`），而 prepare 的 `_record` 是固定 `info`——本 PR 没有改 `_record` 的签名，所以降级事件跟着 info 走。运维过滤 `level=warn` 时会漏掉「三层全降级」这种本该被看见的状态。

**预判**：① 保留 `degraded`（泛名有利于后续阶段复用），但在 Note/设计里固定 `payload = {task, reason}` 的跨阶段契约，并要求 `task` 带域前缀（本 PR 已经是 `cluster.review` 等带点前缀的形式）。② 给 `_record` 加可选 `level` 参数（默认 `info` 保持旧行为），degraded 传 `warn`、`ai_agent_call` 且 `outcome=error` 传 `warn`；这是 1 个参数 + 2 处调用，风险低，收益是「降级在 UI 里可见」。若维护者认为 prepare 的事件级别应保持一致，则至少在 degraded 事件的 message 里加一个视觉前缀。

**结论**：已决 2026-11-22：修复 `degraded` 为 `level=warn`（理由：`_record` 增加可选 `level`，默认 `info` 保持其他事件不变；降级是运维需要看见的状态，应在 warn 过滤中可见。`degraded` 的泛名保留，`payload.task` 的域前缀继续作为跨阶段契约）。

### 讨论点 13：`evidence_refs` 校验完就丢——「模型引用了哪几条样本」没有落库

**位置**：`cluster_llm.py:843`（取出）、`:860`（装进 `EnhancedCluster`）、`:627-650`（校验）；持久化侧 `prepare.py:1068-1093`（`severityFormula` 行不含 refs）与 `:1019-1044`（`ClusterWrite` 没有 refs 列）

**现象**：`evidence_refs` 从 `cluster.score` 输出解析、经 `validate_evidence_refs` 做子集校验、装进 `EnhancedCluster.evidence_refs`（测试 `test_review_merge_names_expands_members_and_scores` 断言 `("c-1","c-2")`），然后**没有任何消费者**：`_severity_comparison` 不写它，`ClusterWrite` 没有对应列，事件 payload 里也没有。实测默认占位的 `severityFormula` 行只含 `clusterHash / severityFormula / severity / dimensions / vector`。

**问题**：设计的意图是「引用校验」作为反幻觉闸（模型必须能指出证据），这一点已实现。但「审计」的下一半——「模型当时到底引了哪几条」——丢失了：事后无法判断一个 0.9 的置信度是建立在「三条样本都指向同一签名」还是「只引了一条」。这与 PR 的卖点（`dimensions` 与 `vector` 都留在审计 payload）不对称：同为模型产出，五维和向量留了，引用没留。也可能是刻意为之——`evidence_refs` 只是校验中间量，持久化会暴露 case id 与簇的映射（但 `probes` 已经暴露了成员），所以「怕泄露」不是理由。

**预判**：低成本补齐：`_severity_comparison` 的行里加 `evidenceRefs: list(cluster.evidence_refs)`。体积是每簇 ≤5 个 id（约 130 字节/簇），与现有 `vector` 同量级；`dimensions` 为空时仍会写 `{}`，说明 payload 本来就不追求极简。另一个选择是只在 `degraded` 时记（用于解释降级原因），但那恰好是最不需要引用的场景。建议补进 `severityFormula` 行，并在 Note 里把「引用校验 + 引用留档」写成一对。

**结论**：已决 2026-11-22：推迟（理由：`evidence_refs` 的子集校验已实现，反幻觉闸有效；把模型引用写进 `severityFormula` 行属 bugfix-22 的可观测性补全，当前 payload 体积不是阻塞项）。

### 讨论点 14：`description` 拼装 `type 类问题 · title · summary` 会前缀重复，且长度到 330 字符

**位置**：`cluster_llm.py:1116-1125`（`_compose_description`）、`:846-850`（调用）；落库列 `prepare.py:1036`；UI 展示 `apps/web/src/pages/evolution/components/StepClusters.vue:150-155`（`cluster.description`）；标题来源 `apps/api/app/service/evolution/stages.py:1015-1028`（`title = cases[0].title`）

**现象**：`_compose_description` 无条件加前缀 `"{type} 类问题 · "`。而审查 prompt 的样本摘要本身就是词面描述（含同样的前缀，`cluster.py:236-254`），prompt 又要求 title「用样本的语言」——模型很容易照着抄。实测把 title 设为 `"prompt 类问题 · 检索索引失败"`，落库描述变成 **`prompt 类问题 · prompt 类问题 · 检索索引失败`**。长度方面：title 上限 120 + summary 上限 200 + 分隔符，最长可到 133 字符（实测长标题用例）；`probe_cluster_description` 是 `TEXT`，DB 无压力，UI 在簇详情里整段展示（`StepClusters.vue:150-155`），折叠行用的是 `cases[0].title`（`stages.py:1020`）所以不受影响。

**问题**：① 前缀重复是可预期的小概率外观问题（依赖模型抄不抄前缀），但一旦发生会进 DB 与 UI，且无法在事后区分「模型写的」与「代码加的」。② 组合后的字符串把「标题」和「摘要」揉进一个列，是因为 06 §5.3 没有 title 列（零迁移约束）——这是合理的妥协，但代价是「标题」不再是独立字段，未来若要单独展示标题只能再解析 `·`。③ 长度上界（≈330）没有在任何常量里表达，`_bounded(title,120)` 与 `_bounded(summary,200)` 两个魔数是分散的。

**预判**：① 在拼装前去前缀：若 `title` 以 `f"{type} 类问题 · "` 开头则剥掉，再拼；或更稳妥地在 prompt 里明确「title 不要包含『N 类问题』前缀」（一句话，成本最低）。② 给组合长度定义一个常量（如 `CLUSTER_DESCRIPTION_MAX_CHARS = 320`）并在 `_compose_description` 末尾整体 `_bounded` 一次，让上界可被测试断言。③ 不建议为标题单开一列（零迁移是明确约束，解析成本不高）。这些都属于「外观与文档」，不阻塞合并。

**结论**：已决 2026-11-22：修复（理由：模型可能照抄样本摘要里的类目前缀，拼装前剥掉 `{type} 类问题 · ` 可消除重复；最终描述由单常量 `DESCRIPTION_MAX_CHARS=300` 兜底截断，上界可被测试断言）。

## §9 文件级代码分析

### `apps/api/app/service/evolution/cluster_llm.py`

**职责**：把「审查 / 置信度 / 严重度」三个 LLM 任务定义成可校验的 Pydantic 契约，并把三者的调用、校验、降级串成一个确定性的编排函数。**变更形态**：A，纯新增（`git show origin/main:apps/api/app/service/evolution/cluster_llm.py` 不存在）。

**关键依赖解读**：只依赖 `pydantic`、`time/logging` 与 `cluster.py` / `ai_agent` 的项目内契约，不依赖数据库或 HTTP。Pydantic 在这里承担「模型输出即不可信输入」的边界：`model_validate` 是唯一入口，`extra="forbid"` 是刻意的严格策略（见讨论点 2）。`Literal["ok","degraded","error"]`（`:293`）让可观测记录自带状态机，不需要额外的布尔字段。

**变更代码块分析**（纯新增，按数据流讲「在做什么、为什么这么写」）：

- **常量层**（`:47-143`）：三个任务键是字符串而不是 enum，因为 provider 的 `output_model` 与事件 payload 都按字符串传，enum 只会多一次转换；采样上界（3–5）与字符上界（240/120/240/300）集中在一处，所有 prompt 渲染都引用它们，保证「prompt 大小是常量与 K 的函数」。
- **契约层**（`:160-234`）：`ClusterReviewItem` 用 `from` 别名（Python 关键字冲突），`from_keys: list[str]` 的语义是「合并来源」，不是「成员」；`ClusterScoresOutput` 用 `scores: list[...]` 包一层而不是直接 `list[...]`，是为了让输出是一个对象（JSON5/JSON 通道与 `model_validate` 都更稳）。`SeverityScoreItem.dimensions` 用 `dict[str, Annotated[float, 0..10]]` 而不是五个具名字段——省掉一版 prompt 与 schema 的同步成本，代价是维度名不受约束（发现 1）。
- **值对象层**（`:237-348`）：全部 `frozen=True, slots=True`。`ClusterDraftStats` 把「成员 id（代码持有）」「紧密度」「时间跨度」装在一起，是「N 不进 prompt」的载体；`EnhancedCluster` 同时保留 `severity`（决策分，落库）与 `formula_severity`（公式分，对照），这两个值必须成对出现，否则审计断链。
- **prompt 构造**（`:369-570`）：三个 builder 结构对称——头部规则、主体块、尾部 return。审查 prompt 的规则 3/4（划分完整性、merge-only）与规则 6（不跨类型）是把 validator 的不变量**提前**告诉模型，属于「可被测试的自然语言契约」（`test_review_prompt_uses_draft_keys_and_bounded_samples` 断言了 `members=18`、`signatureOverlap=0.42` 等字面量）。
- **validator 层**（`:573-743`）：四个 validator 的返回类型不同——划分返回 item 元组、引用返回去重后的 id 元组、两个批量返回 `dict[key, value]`。这个设计让编排层不需要再遍历查找，`confidence_by_key[plan.key]` 是 O(1)。错误信息全部是「人话 + 具体键名」，因为它们会进 `degraded.reason` 被运维读（例：`cluster.score [C1]: cluster.score cited 1 evidence_ref(s) outside the prompt samples`）。
- **编排层**（`:787-870`）：`calls`/`degraded` 两个 list 与两个 sink 并行维护（`:821-827`），所以返回值（`EnhancedClusters.calls`）与回调收到的记录**逐条相等**（测试 `assert result.calls == tuple(calls)` 钉住了）。三个阶段的调用顺序写死在 `:837-840`，没有并行化——串行是刻意的：后一阶段依赖前一阶段的簇划分。
- **统计与拼装**（`:1046-1162`）：`_merged_stats` 是唯一「跨草稿」的合并逻辑，成员 id 用集合并、重叠度用加权平均（发现见讨论点 6）、时间跨度优先用 evidence 重算（`:1076-1085`）——三个统计量用了三种合并口径，这是本文件最「不统一」的地方。
- **失败记录**（`:1170-1220`）：`_failure_record`（调用抛异常）与 `_result_record`（调用返回但内容违约）是两条独立路径，前者 `model="unknown"`、tokens/cost 为 0，后者沿用 provider 报告的用量——这个区分让「模型没回答」与「模型答错了」在事件里可分辨。

**实现思路总结**：用「键引用 + 有界样本 + 确定性统计」把 N 从 prompt 里彻底移除；用「三个独立 try/except + 统一 fallback 词典」把失败变成值而不是异常；用「Pydantic 边界 + 语义 validator 双层」把模型输出当不可信输入。

**检视发现**：

1. `SeverityScoreItem.dimensions` 不校验维度名集合（`:221`）：prompt 规则 3 要求「exactly these dimension keys」（`:549`），但模型返回 `{"impact":9,"made_up":3}` 能通过（实测），并原样进 `severityFormula.dimensions`。属契约松（低），修法是在 `SeverityScoreItem` 加一个 `field_validator("dimensions")` 限定 `SEVERITY_DIMENSIONS`（或至少记录未知名的数量）。
2. `_evenly_spaced_indexes(total, count)` 在 `count == 1` 且 `total > 1` 时除零（`:1159`）：`count >= total` 的分支只兜住 `total == 1`。默认路径不可达（`_sample_target` 只会返回 0/1/3/4/5，返回 1 时成员数必为 1），但 `select_samples` 是导出 API，`select_samples(ids, evidence, limit=1)` 实测抛 `ZeroDivisionError`。属潜在 bug（低），修法是循环前补 `if count == 1: return (total // 2,)` 或直接用 `index = round(position * (total - 1) / max(count - 1, 1))`。
3. 同一 item 内重复 `from` 键的理由误导（`:605-611`）：`{"from":["D1","D1"]}` 被拒是对的，但文案是「…so splitting a draft is impossible; D1 appears in items 0 and 0」——把「同一 item 重复」说成了「跨 item 拆分」，而 `splitting` 恰恰不是发生的事。属文案 bug（低），修法是把「键在本 item 已出现」先判出来并给独立理由（`duplicate draft key D1 inside one item`），再判跨 item。
4. `DRAFT_SUMMARY_TOKENS`（`:69`）只被导出、没有被任何代码读取（grep 全库只有 `__all__` 与文档引用）；它是「字符上界 ≈ 60 tokens」的说明性常量。无实害，但会让人误以为有 token 级截断。
5. `MAX_REASON_CHARS` 的截断发生在 `ClusterContractError.__init__`（`:156`）与 `_provider_reason`/`_contract_reason`，所以「降级理由」始终 ≤300 字符；这与事件 payload 的 sanitize 叠加，安全性足够。
