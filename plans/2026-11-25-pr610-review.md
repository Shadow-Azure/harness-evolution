## §1 一页速览

**一句话**：这个 PR 把「换一个 AI Agent 后端」从口号变成可验收的接口——技能怎么铺、怎么调用从服务层搬进 provider（`stage_skill`），能力面从"猜你实现了没有"升成"你自己声明"，配置从 Claude 专属名升成通用名。

**一个比喻：换快递承运商。**

平台以前把包裹按某一家承运商的仓库形状码放（`.claude/skills`），还在运单上手写这家的内部单号（`/{name}`）。换一家承运商，平台得跟着改，否则新公司拿不到货。现在平台只按标准箱码放（`work/skills/<name>/`），并在单子上写"照箱里的说明单操作"；承运商自己在 `stage_skill` 里决定要不要再摆一份到自家货架、要不要贴自家面单。Claude 这家要求两份都要（`.claude/skills` 链接 + `/{name}` 前缀），一个通用后端可以不摆、返回空串——这就是 PR 描述的"零适配"。

**交付块**：

| 块 | 解决的问题 | 关键改动 |

| 契约 | 能力靠隐式推导、鉴权不在契约里 | `capabilities` 声明、`ProviderHealth.auth`、`stage_skill` 钩子、`from_settings` 钩子 |

## §2 架构导览

### 2.1 契约层：三个新钩子与一个"带上下文的默认值"

**`capabilities` + `_declared_capabilities`（`base.py:44`, `base.py:80-91`, `base.py:142-155`）**

父类给了 `capabilities` 一个默认值 `frozenset({"analyze","edit"})`，但 `supports_skills` 不能直接读它——否则"没声明"会被读成"声明了没有 skill"。实现用 MRO 走查来区分：

```python
for klass in owner.__mro__:
    if klass is AIAgentProvider:      # 走到父类就停，父类的默认值不算声明
        return None
    if "capabilities" in klass.__dict__:   # 只看类自己写的，不看继承来的
        return frozenset(klass.__dict__["capabilities"])
```

白话：`hasattr` 会告诉你"这个类有 capabilities"，但它分不清是子类自己写的还是从父类继承的；这里用 `__dict__` + 在父类处截断，等价于问"往上数，第一个自己写了 capabilities 的是谁"。中间的 mixin 自己写了也算——这是注释里明确要的行为。

`supports_skills`（`base.py:80-91`）：声明存在则以声明为准，否则回落到"`run_skill` 是否被覆盖"的历史推导。这样 `AgentBackend`（legacy 插件基类，没声明、覆盖了 `run_skill`）保持原行为。

**`stage_skill`（`base.py:114-127`）**：默认实现抛 `AgentProviderError("provider does not support Skill staging")`。契约是"把冻结文件铺成自己的形态，返回可选原生前缀；空前缀=不需要前缀"。

**`from_settings`（`base.py:58-65`）**：默认 `cls(settings)`；需要自己命名空间的后端覆盖它。工厂只认这一个装配点（`factory.py:70`）。

**`ProviderHealth.auth`（`contracts.py:23-29`, `contracts.py:235-257`）**：`ok`/`missing`/`unknown` 三态，`__post_init__` 做闭集校验。默认 `unknown`，所以所有"探测没走完"的分支天然落在未知态。

**`EDIT_PLAN_FILENAME`（`contracts.py:31-37`）**：从 `claude_code.py` 提到包里，`claude_code` re-export 保留旧导入路径，`patch_source.py:533` 改为引用常量。

### 2.2 配置层：用 `None` 而不是默认值来区分"没设置"

`config.py:176-187` 三个字段并存：

```python
ai_agent_claude_bin: str = "~/.local/bin/claude"   # 旧名，有默认值
ai_agent_claude_settings: str | None = None
ai_agent_bin: str | None = None                     # 新名，None 表未设置
ai_agent_settings: str | None = None
```

`effective_ai_agent_bin`（`config.py:460-471`）就是一句"新名非 None 就用新名，否则用旧名"。看起来过于简单，但这是 Agent Note 里明确讨论过的选择：新名若也带默认值，就只能靠"值是否等于默认值"判断是否设置，而旧名默认值恰好相同，无法区分"显式设成默认"与"没设置"。

校验沿用旧规则（`config.py:408-425`）：空 bin 抛 `ValueError`（启动红），空 settings 归一成 `None`（视为未设置）。

### 2.3 装配与观测：一个装配点、两条观测线

- 装配：`main.py:216` → `factory.build_agent_provider`（`factory.py:55-70`）→ `implementation.from_settings(settings)`。
- 观测 1：启动时 `main.py:593` 调 `_record_ai_agent_health`，事件 extra 新增 `auth`（`main.py:180-186`）。
- 观测 2：发布预检 `preflight.py:23-30`：先 `health_check()`（≤10s），再用 `health.auth` 推 `bin`，打印 `skills=/auth=/bin=`。

### 2.4 服务层：只留"平台自己的三件事"

`local_attribution.py:489-520` 现在的职责恰好三件：校验冻结文件 checksum、把文件交给 `provider.stage_skill`、把平台 writer shim 换进去（外加写 case 输入）。任务文本由 `_skill_prompt`（`:86-98`）生成：

```
使用 {name} skill：读取 skills/{name}/SKILL.md 并严格遵循其中的全部指令，分析本目录的 input_badcase.json 并生成归因报告。
```

对比旧文本 `/{name} input_badcase.json，请分析并生成归因报告`——旧文本的"斜杠命令"隐含了两件事：Claude 的技能发现目录、Claude 的调用语法。新文本只说"去读哪份说明"，调用形态交给 provider 加前缀。

### 2.5 平台 writer shim：不再数目录层级

旧 shim 用 `Path(__file__).resolve().parents[3]` 硬编码"我是从 `.claude/skills/<name>/` 被复制的"，铺盘深度一变就错。新实现（`writer_entrypoint.py:15-17`）向上找"含 `.platform` 的祖先"：

```python
staged = Path(__file__).resolve()
work = next((p for p in staged.parents if (p / ".platform").is_dir()), staged.parents[-1])
```

`.platform` 是平台自己的标记目录（原 writer 与 receipt 都在这），所以这个定位与 provider 的铺盘形态无关。找不到时回落到文件系统根，随后调 writer 会失败并返回非零——兜底不优雅，但不会静默成功。

### 2.6 case-tools 与反软链守卫

`claude_skill.py:167-175` 与 `attribution_case_tools.py:47-63` 都改从 `work/skills` 读指南，并且都保留"必须解析到自身（即不是链接）、必须是真实文件"的检查。这正是 `.claude/skills/<name>` 不能再作为读取源的原因：它是链接（复制回退时是另一份实体），而守卫要求真实文件。守卫本身没有被削弱。

## §6 讨论点

> 每条固定五段：位置 / 现象 / 问题 / 预判（供拍砖，不拍板）/ 结论（留空给维护者）。

### D1 重放时"铺盘用部署 provider、执行用冻结 provider"

**位置**：`apps/api/app/service/evolution/local_attribution.py:512`（`prefix = self.agent.stage_skill(...)`）与同文件 `:588`（`provider = self._skill_provider(manifest["agent"])`）。

**现象**：`_stage_attempt` 从 `@staticmethod` 变成实例方法后，铺盘与原生前缀由**当前部署的** provider 产生，但真正执行 `run_skill` 的是 manifest 里**冻结的** provider。正常路径两者相同（`freeze` 把 `agent=self.agent.provider_id` 写进 manifest），只有"部署换过后端再重放旧快照"时分离。

**问题**：issue 要求"存量快照的重放不得因本次改造破坏"，而 `tests/attribution/test_runtime_boundaries.py:144` 恰好守的就是这个场景（部署切到 `fake` 后旧 `claude` 快照仍解析到 `ClaudeCodeProvider`）——但该用例只断言了 `_skill_provider` 的解析，没有走到铺盘。具体后果：部署切到另一个技能后端、但旧 claude 二进制仍留在默认位置（只改 `AI_AGENT_PROVIDER`、不改 bin）时，旧 claude 快照的铺盘由新后端完成：没有 `.claude/skills` 链接、没有 `/{name} ` 前缀；而 claude CLI 照冻结说明单执行 `.claude/skills/...`（见 D3）→ 找不到脚本 → case 失败。改动前铺盘是静态的（与 provider 无关），这条路径能过。

**预判**：先记"回归风险"而不是"阻断"：issue 字面验收只要求"别名映射 + `skill_model_identity` 相等校验"不变（这两条确实没变），回归发生在更下面一层——铺盘由谁做。触发它需要"部署切换 + 旧快照补跑"同时成立；另外要提醒：即便修好铺盘，"冻结的 agent + 当前 settings 重建 provider"仍可能指向新部署的二进制（只改 provider 名、不改 bin 时恰好不受影响），这是改动前就存在的洞，不是本 PR 引入，但重放故事要真正成立，迟早要面对（例如冻结时记录 provider 的解析结果）。修法很小：把 `_stage_attempt` 里的 `self.agent.stage_skill` 换成先解析 `self._skill_provider(manifest["agent"])` 再调它的 `stage_skill`，并补一条"部署切换后重放旧快照"的端到端用例。

**结论**：（留空）

### D2 复制回退分支里，`.claude/skills` 别名持有的是**没换写**的旧 writer

**位置**：`apps/api/app/third_party_api/ai_agent/claude_code.py:226`（`_link_or_copy(staged, work/".claude"/"skills"/name)`）与 `apps/api/app/service/evolution/local_attribution.py:512-517`（`stage_skill` 之后才 `rename` + `copyfile` 换写 shim）。

**现象**：顺序是"铺中立 → 建别名 → 把中立路径的 `make_probe_report.py` 挪进 `.platform/` → 在中立路径放 shim"。软链时别名与中立路径是同一个目录，shim 自动可见；**复制回退**时别名是换写**之前**的快照，里面仍是冻结的原稿 writer。

**问题**：默认技能包 `attribute-badcases/SKILL.md:354` 的指令是 `python3 .claude/skills/attribute-badcases/make_probe_report.py …`。在复制回退的主机上，CLI 从 `.claude/skills` 发现技能、照说明单执行——执行到的是原稿：它直接写 `probe_report.json`，**不写 `.platform/receipt.json`**，于是 `_read_emission`（`local_attribution.py:523-530`）报 "Skill did not invoke the platform report writer"，整个 case 失败。`_link_or_copy` 的 docstring 说回退后"still gets a working skill layout"，这个分支在当前顺序下并不等价。

**预判**：判为 bug，但触发面窄（需要"无符号链接权限 + 真 Claude CLI"同时成立；CI Linux 与生产部署不受影响，本机 Windows 无 CLI 也不受影响）。修法比"调换顺序"更稳：让 shim 字节直接进传给 `stage_skill` 的 `files` 映射（`files["make_probe_report.py"] = writer_entrypoint 字节`），冻结原稿单独写到 `.platform/`。这样软链与复制两种形态天然一致，也顺带消掉 D4 的硬假设。测试补一条"复制回退 + shim 真正生效"的用例（现有 `test_ai_agent_claude_code.py:1724` 只断言了 `SKILL.md` 被复制过去）。

**结论**：（留空）

### D3 冻结技能包仍写 `.claude/skills/...`，"零适配"只在钩子 API 层成立

**位置**：`attribute-badcases/SKILL.md:354`；对照 `apps/api/tests/attribution/test_portable_backend.py:224`（stub 的 agent 脚本直接调 `skills/<name>/make_probe_report.py`）。

**现象**：服务层与 prompt 都中立了，但**技能包正文**（被 checksum 冻结、原样交给任何 provider 的那份说明单）里仍写着 `python3 .claude/skills/attribute-badcases/make_probe_report.py`。PR 的零适配 stub 用例没有暴露这一点：它的 `_AGENT_SCRIPT` 是测试自己写的，直接挑中立路径调用，从不读那份说明单（脚本甚至断言 `not (work/".claude").exists()`）。

**问题**：把这样一个 stub 换成真实 CLI agent（比如将来接 Codex/Gemini），agent 会照着说明单去执行 `.claude/skills/...`——这个路径在新后端下不存在。也就是说"只加一个子类与一个注册项"在 API 层成立，在"默认归因技能真的能跑"这一层还不成立。`docs/ai-agent.md:11` 的承诺读者会按后者理解。

**预判**：不算本 PR 的代码 bug（issue 明确只改任务文本、"上游技能 prompt 改路径引用"，技能包正文属于包内容），但它是"可替换"承诺的最大缺口，建议开 follow-up（不改本 PR）：把默认包 `SKILL.md` 的调用路径改成 `skills/<name>/make_probe_report.py`——Claude 同样能读中立路径，软链只是它的发现入口；默认包 `content_hash` 会变，但旧快照读自己的冻结副本，不受影响。另一个可选方向是在 provider 契约里写明"agent 必须能按中立布局读说明单，指南中的厂商路径由 `stage_skill` 负责兼容"。

**结论**：（留空）

### D4 `stage_skill` 契约的 "or beyond" 与服务的硬编码路径冲突

**位置**：`apps/api/app/third_party_api/ai_agent/base.py:114-121`（"lays them out in its best form under ``work/skills/<name>/`` or beyond"）与 `local_attribution.py:513`（`staged = work / "skills" / name / "make_probe_report.py"`）。

**现象**：契约允许 provider"铺到中立布局之外的自有形态"，服务却硬取中立路径下的 `make_probe_report.py` 来换写 shim。

**问题**：一个合法实现（例如只铺 `.codex/skills/`，或把文件重命名/编码成自有格式）会在 `staged.rename(...)` 处以 `FileNotFoundError` 失败；报错落在服务层，看不出根因是契约与实现不一致。这也是 D2 的结构性根源：平台 writer 的换写点被钉死在一个"约定路径"上。

**预判**：二选一——要么把契约改成"必须保留 `work/skills/<name>/` 的中立布局（可以额外再铺）"，要么让 `stage_skill` 返回 staged 目录/让平台自己写中立布局、provider 只做额外适配。倾向后者（D2 的修法顺带解决），并同步 07 §5.5.1 与 `base.py` docstring。

**结论**：（留空）

### D5 preflight 的 `bin` 由 `auth` 推导，两个正交事实被合成一个 token

**位置**：`apps/api/app/third_party_api/ai_agent/preflight.py:24`（`binary = "missing" if health.auth == "unknown" else "present"`）。

**现象**：能力行里的 `bin` 不是"二进制文件是否存在"，而是"这次探测有没有走到可用部署"。举例：① 二进制存在但 `--version` 退出非零（坏安装/缺动态库）→ `bin=missing`；② `fake` 根本没有二进制概念 → `bin=present`（因为 `auth="ok"`）；③ 将来某个 provider 主动声明 `auth="unknown"`（"凭据是否有效不知道"）→ 被读成二进制缺失。

**问题**：`bin=` 这个名字会让人按"文件存在性"理解，而它实际编码的是"可用部署"。部署契约脚本（`verify_provisioning_contract.sh:71,90`）已经把 `ready=True bin=missing` 这一组合固化成期望值——对写脚本的人自洽（这是安装 CLI 之前的预检），对值班的人读起来是自相矛盾。

**预判**：无实害（Agent Note 写明 `bin=present ⇔ auth ∈ {ok, missing}`，单测与部署脚本都自洽），不改也能用。建议要么把 token 改名（如 `usable=`），要么真探一次二进制存在性并把两个事实分开；改的话要同步三处部署脚本期望行与两条 preflight 单测。

**结论**：（留空）

### D6 `ProviderHealth.auth` 的三态其实是"凭据来源是否已声明"

**位置**：`apps/api/app/third_party_api/ai_agent/contracts.py:23-29`（docstring）与 `claude_code.py:554-559`。

**现象**：成功分支的判定是"环境有 `ANTHROPIC_API_KEY` 或 settings 里有 `apiKeyHelper` → `ok`，否则 `missing`"；`fake` 恒 `ok`。

**问题**：① `contracts.py` 的注释 "``missing`` means a usable deployment runs without credentials" 字面读像"没有凭据也能跑"（那应该是 ok），与实现相反；② 用 OAuth/keychain 登录的 Claude 实际能调用，但这里报 `missing`（`_bare_mode_auth_hint` 自己说明 bare 模式只认这两种来源）；③ 环境里有 key 但走的是非 bare 通道时也会报 `ok`。字段叫 `auth`，语义是"bare 模式凭据来源是否存在"。

**预判**：无实害（观测字段；preflight 只用 `unknown` 区分"没到可用部署"，启动事件只是多一个字段），但这是契约层的语义债：建议把 `ProviderAuth` 的 docstring 改成可执行的判定描述（例如"`ok` = 检测到已配置的凭据来源；`missing` = 该后端没有配置可用的凭据来源；`unknown` = 探测未完成"），并在 `docs/ai-agent.md` 的配置表旁点一句。

**结论**：（留空）

### D7 `capabilities` 声明不可验证，且与推导双轨导致 `provider.capabilities` 会"说谎"

**位置**：`apps/api/app/third_party_api/ai_agent/base.py:88-91`、`base.py:142-155`；例证 `tests/test_ai_agent_factory.py:301-305`（只声明 `skill`、不实现任何技能方法的后端也被判 `supports_skills=True`）。

**现象**：① 声明是自我声称，没有闭集校验；② 未声明的旧子类，`.capabilities` 仍返回父类默认值 `{"analyze","edit"}`，而 `supports_skills` 可能是 True——同一个对象上两个公开事实互相矛盾（`test_ai_agent_factory.py:308-317` 只断言了 `supports_skills`，没断言 `.capabilities`）。

**问题**：`capabilities` 拼错（`{"skills"}` / `{"skill "}`）会静默降级为 cache-only，只在 preflight 的 `skills=no` 上可见——这正是 issue 想消灭的"静默失败"，只是从运行期挪到部署期；② 声明 `skill` 但没有实现 `stage_skill`/`run_skill` 的后端能通过 `require_skill_support()`，到每个 case 才炸（且错误来自 `stage_skill` 默认抛错，信息不指向"你少实现了一个方法"）。

**预判**：无实害（目前生产代码没有读者读 `.capabilities`，只有 `supports_skills` 被 `main.py:715` 与 preflight 使用），但 docs 已把它当"能力面"对外承诺。建议两小步：给 members 加闭集校验（非法值装配即红），并在 `require_skill_support` 或装配处补"声明 skill ⇒ 两个钩子都已实现"的校验；`.capabilities` 若要当公开事实，应改成"声明 ∪ 推导"的计算属性。

**结论**：（留空）

**旧 → 新**：

```python

def stage_skill(self, work, name, files) -> str:
    staged = work / "skills" / name
    for relative, content in files.items():
        (staged / relative).parent.mkdir(parents=True, exist_ok=True)
        (staged / relative).write_bytes(content)
    _link_or_copy(staged, work / ".claude" / "skills" / name)
    return f"/{name} "

def _link_or_copy(source, link):
    try: link.symlink_to(source, target_is_directory=True)

```
