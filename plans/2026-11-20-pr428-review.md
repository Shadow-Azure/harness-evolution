## §1 一页速览

**一句话**：把「每次 run 把整座图书馆搬回家」改成「按书签只借那一本」，并给每次借书/还书贴上可查询的快递面单。

| 交付块 | 内容 |
|---|---|
| 单 ref 缓存 | `data/repos/<target>/<sha256(ref)[:16]>`，tag/分支全历史，完整 commit depth 1，不再 `--mirror` |
| 工作区 | 从缓存 `git clone --no-checkout` → 建 `evo/...`；远端已有 run 分支先 fetch 再 track |
| 推送 | `HE_GIT_PUSH` + 可选 `HE_GIT_PUSH_URL`；写 fork、读 origin |

## §2 架构导览

### 2.1 缓存层：按 (target, ref) 借书

`GitWorkspaceManager.prepare`（`workspace.py:167`）先算规范化 ref 与缓存路径 `_ref_cache_path`（`workspace.py:886`），再在 `_ensure_ref_cache`（`workspace.py:900`）的进程内锁里判断缓存是否可用、origin 是否仍匹配。可用但 origin 变了就 `_remove_cache`（`workspace.py:1025`）；新建失败删半成品，已有缓存刷新失败保留完整对象。

`_fetch_ref`（`workspace.py:950`）只有两条路：完整 40 位 commit 用 `fetch --depth 1`；其他 ref 用 `fetch --no-tags origin <ref>`，把解析出的 commit 写到 `refs/heads/harness-target`（`workspace.py:990`）。这个 synthetic ref 是给本地 clone 看的：clone 只复制被 advertise 的 refs，单纯 fetch 到 `FETCH_HEAD` 不会被复制。

### 2.2 工作区与恢复：不要把「对象缺失」误判成非快进

新工作区从缓存 clone 后由 `_select_or_create_run_branch`（`workspace.py:811`）决定：本地有 run 分支就切；远端有就 `_fetch_remote_branch`（`workspace.py:854`）显式 fetch 再 `switch --track`；都没有才从 base commit 建。已有工作区走 `_reuse_or_reject`（`workspace.py:752`），同样补上「分支不存在时先 fetch 或从 base 重建」。

`_push_run_branch`（`workspace.py:685`）在 `merge-base --is-ancestor` 前用 `_commit_present` 确认远端 commit 在本地；不在就先 fetch 该分支。单 ref 缓存不含 run 分支，这一步是恢复确定性的关键。

### 2.3 推送目标：读 origin，写 fork

`_ensure_push_remote`（`workspace.py:1036`）在配置了 `HE_GIT_PUSH_URL` 时维护独立 `push` remote；`push_candidate`、`_push_run_branch`、候选 tag 的 `ls-remote` 与删除都用它。未配置时仍是 `origin`。fetch 始终走 `origin`，避免把 fork 当成目标内容源。

### 2.4 可观测：两层记录

`observability.py` 定义 `GitOperationRecord`（`observability.py:36`）与 `GitOperationCollector`（`observability.py:63`）。`git_operation_scope`（`observability.py:103`）用 contextvar 绑定一次 prepare；`emit_git_operation`（`observability.py:129`）把 ls-remote/clone/fetch/push 收进列表、把每个子进程写日志；`emit_proxy_probe`（`observability.py:137`）只写日志且 runId=null。`bounded()` 截到 20 条并返回截断标记。

`ProxyAwareGitRunner.run`（`proxy.py:552`）记录代理前后状态、是否实际走代理、回退原因、耗时、exitCode、host；`is_proxy_traffic`（`observability.py:157`）把「本地缓存 clone」判为 false。`probe_once`（`proxy.py:428`）单独记录探测，不混入 run 流量。

`EvolutionPrepareService._prepare_workspace`（`prepare.py:457`）在作用域内调用 workspace，事后把 `collector.bounded()` 投影到 `workspace_prepared`（`prepare.py:488`）。

## §3 数据流走查

1. prepare 进入 `_prepare_workspace`，建立 `git_operation_scope`（`prepare.py:457`）。
2. `prepare` 算缓存路径 → `_ensure_ref_cache`（`workspace.py:900`）→ `git fetch` 只拉目标 ref（`workspace.py:950`）。
3. `git update-ref refs/heads/harness-target` 让后续 `git clone` 能看到对象（`workspace.py:990`）。
4. `git clone --no-checkout` 到 `data/workspaces/<runId>`，`remote set-url origin <repo_url>`，再按本地/远端/base 三种情况建 run 分支（`workspace.py:811`）。
5. `validate_for_push` 校验分支名、base、clean、trailer；`_push_run_branch` 先 `ls-remote`，必要时 fetch remote commit，再 `merge-base`，最后非 force push（`workspace.py:685`）。
6. 每个 git 子进程走 `ProxyAwareGitRunner.run`（`proxy.py:552`）：健康时带代理环境，代理层失败直连重试一次并记 fallbackReason。
7. prepare 成功写 `workspace_prepared` payload（`prepare.py:488`），前端/API 可读；日志按 runId 过滤 `git.proxy.operation`。

## §6 讨论点

### D1：`HE_GIT_PUSH` 默认仍为 true，第三方只读仓库靠配置关闭

- **位置**：`apps/api/app/config.py:133`、`docs/git-workspace.md`
- **现象**：默认配置仍会向 `origin` 推 run 分支；对无写权限的公共仓库，失败按 `blocked(push)` 暴露，而不是提前拒绝。
- **问题**：验收要求「默认不向无写权限的第三方仓库推分支」。当前实现依赖操作者设置 `HE_GIT_PUSH=false` 或 `HE_GIT_PUSH_URL`，系统无法自动判断目标是否可写。
- **预判**：在没有 per-target 写权限元数据的前提下，自动判断需要额外 API/契约；当前用「显式开关 + 失败不静默」兑现策略，并在文档与部署模板写清。是否要改为默认 false 或增加 target 级 push 配置，留给维护者拍板。
- **结论**：

### D2：仓库缓存不参与工作区保留策略

- **位置**：`workspace.py:1025`、`docs/git-workspace.md`
- **现象**：`cleanup_workspaces` 只清 `data/workspaces`；`data/repos` 的 per-ref 缓存不随 run 清理。
- **问题**：访问过的 ref 越多，磁盘占用越大；目前没有自动回收。
- **预判**：本 issue 只要求「缓存按 target + ref 命中与刷新」，未要求清理；新增自动清理会扩大状态机与数据目录语义。先文档化、人工清理，后续可加 retention。
- **结论**：

### D3：`cloneSeconds` 在缓存命中时包含刷新 fetch 的耗时

- **位置**：`workspace.py:172`、`prepare.py:498`
- **现象**：字段名沿用 issue 的 `cloneSeconds`，但缓存命中时实际测量的是「确认缓存 + 刷新目标 ref」的时间。
- **问题**：名字容易被读成「本次 clone 耗时」。
- **预判**：字段名是 issue 明确要求；语义在文档中写为「目标 ref 进入缓存的时间」。无实害，若要更精确可改名为 `cacheSeconds`，但会偏离契约。
- **结论**：

## §9 文件级代码分析

### `workspace.py`：从 mirror 到 per-ref cache

旧代码 `_ensure_mirror` 对目标仓库执行 `git clone --mirror --no-hardlinks`，每次 run 都下载全部 refs。新代码把缓存键拆成 target + ref，并把「只 fetch 目标 ref」作为唯一入口；`_fetch_ref` 的完整 commit 分支保留 depth 1，tag/分支保留全历史，因为 patch/commit/ancestry 需要完整树与父链。

变更块（语义）：

```text
old: clone --mirror repo_url repos/<target>; git remote update --prune
new: git init --bare repos/<target>/<refhash>
     git fetch --no-tags origin <ref>
     git update-ref refs/heads/harness-target <commit>
```

`_push_run_branch` 的变化是把「远端 commit 一定在本地」这个旧 mirror 假设显式化：先 `cat-file -e`，缺失就 fetch 分支，再 `merge-base`。`_ensure_push_remote` 把 push 目标与 fetch 目标解耦，避免 fork 覆盖目标内容源。

### `observability.py`：记录的是「事实」，不是「结论」

`GitOperationRecord.as_payload` 只输出 operation、viaProxy、前后状态、fallbackReason、durationMs、exitCode、targetHost；没有 URL、stderr、凭据。`target_host_for` 只取 host；`is_proxy_traffic` 把本地 clone 判 false，避免把「进程带了代理环境变量」误报成「走了代理」。`GitOperationCollector.bounded` 用 20 条上限防止事件膨胀。

### `proxy.py`：一次逻辑操作一条记录

`run` 在 `finally` 里发记录，保证成功、失败、异常都有 exitCode（异常为 null）。代理层失败时先 `report_failure`，记录 fallbackReason，再直连重试；最终记录 `viaProxy=false`。`probe_once` 走 `emit_proxy_probe`，不经过 run 收集器，保证 probe 与业务流量分离。

### `prepare.py`：把上下文绑定到一次 prepare

`git_operation_scope` 包住 `workspaces.prepare`，让 workspace 内部的 git 调用自动进入同一个收集器；成功后把 `collector.bounded()`、`proxy_state` 与 `PreparedWorkspace` 的 cache 字段写进事件。失败不写事件，保持既有失败路径。

### 测试与文档

`test_single_ref_workspace.py` 覆盖 tag/分支/完整 SHA、argv 无 `--mirror`、缓存复用/刷新、transient 保留、缺失 ref 清理、远端 run 分支恢复、push URL 全写入 fork、事件 payload、代理 fallback、probe 分离与 20 条上限。`docs/git-workspace.*` 与 Agent Note 记录现状与取舍；旧 Note 的 mirror 句子就地更新为 per-ref cache 事实。
