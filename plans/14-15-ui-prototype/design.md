# #14/#15 前端原型 UI 设计方案（讨论稿）

> 配套可点击原型：同目录 `index.html`（入口）、`session-explorer.html`（#14）、`timeline.html`（#15）、`evolution.html`（自进化，见 §10）。
> 本稿只用于 UI 讨论，全部数据为打桩样例，不进入产品代码。

## 1. 需求回顾

- **#14 Session 浏览器与家族摘要**：顶层只列 4 个 root session；摘要卡展示 turn / agent / command / failure / skill / finding 聚合数；支持按仓库、时间、状态、问题密度筛选；URL 保存 root session + 选中 agent + 证据位置；空列表 / 未选中 / 加载失败三态明确。
- **#15 Turn 时间线核心渲染**：按 turn 分组；为用户、Agent、推理、工具调用、工具输出、文件变更、错误、token 提供专门卡片；call_id 配对调用与输出；长文本折叠 / 复制 / 看原始载荷；用户消息与最终回复在长轨迹中易定位。

## 2. 调研结论（同类产品的成熟做法）

| 来源 | 值得借鉴的点 |
|---|---|
| [FutureAGI Observe 重设计](https://futureagi.com/blog/redesigning-observe-ui/) | "Triage-first"：列表页直接把错误密度、失败率做成一眼可扫的指示，先分诊再下钻 |
| [LangSmith View traces](https://docs.langchain.com/langsmith/view-traces) | trace 列表 + run tree 双视图；每个节点带状态色、耗时；thread 视图按对话轮次组织长轨迹 |
| Langfuse Sessions | session 是一等单位，列表直接展示聚合指标（turn 数、token、成本），不在列表混进子 trace |
| [claude-code-log](https://pypi.org/project/claude-code-log/) / [claude-log-viewer](https://pypi.org/project/claude-log-viewer/) | JSONL 轨迹 → 聊天式卡片流；thinking / tool_use / tool_result 各自一种卡片，长输出默认折叠 |
| [Superset #5056](https://www.cubic.dev/pr/superset-sh/superset/pull/5056) | 把一个 assistant turn 内的多个步骤折叠成 "step view"，turn 成为天然的折叠边界 |
| [GitLab Session List Redesign](https://gitlab.com/gitlab-org/gitlab/-/work_items/612102) | 会话列表的搜索 + 状态过滤 + 密度信息排版 |

提炼出的通用方法：

1. **列表即分诊**：root session 卡片上直接放聚合数字 + 问题密度条，用户不点进去就能排序出"最值得看的会话"。
2. **turn 是时间线的唯一分组边界**：turn 头吸顶，带序号 / 时刻 / 耗时 / 事件数 / token，长轨迹里永远知道自己在哪一轮。
3. **事件类型 = 卡片类型 = 色彩编码**：每种事件一种卡片、一种主题色，扫读时靠颜色而不是读文字。
4. **默认折叠，按需展开**：推理和长工具输出默认只露摘要，展开后才能复制 / 看原始 JSON。
5. **调用配对要"看得见"**：工具调用与输出用同一条左侧竖线 + 相同 call_id 徽章连成一组，失败输出红色并带退出码。
6. **状态入 URL**：选中项、过滤条件写进 hash/query，刷新可恢复（#14 验收硬要求）。

## 3. 布局方案

三栏壳（M1 阶段右栏留空，后续 #12 问题面板 / #8 执行流图再填）：

```text
┌──────────────┬───────────────────────────────────────────┐
│ Session 浏览器│  主区（两种状态）                           │
│  (#14)       │  A. 家族摘要（未进入时间线时的落地页）        │
│  搜索+筛选    │  B. Turn 时间线（#15，含 agent 切换条）      │
```

### 3.1 #14 Session 浏览器（见 `session-explorer.html`）

- 每张家族卡：任务标题、启动时刻（20:05 / 17:32 / 08:46 / 12:34 即四类场景的识别符）、仓库、总耗时、后代 agent 数、聚合统计行（turn / 交互次数 / 工具失败 / skill / 问题）、**两条独立密度线**：工具失败密度（红）与问题密度（橙），各自 ÷ 交互次数换算成「每百次交互」（见 §5.2）。
- 筛选：搜索框（标题/仓库）、状态 chips（全部/完成/部分失败/失败）、排序（最新 / 问题最多）。4 个 session 一屏必放得下，筛选主要是验证交互模型。
- 主区家族摘要：顶部只留标题 + 单行紧凑统计条（Turn / Agent / 交互 / 工具失败 / Skill / 问题 / 两条密度值），把纵向空间让给下面的家族成员树 +「打开 Turn 时间线」入口。
- URL 状态演示：`#/session/<id>` 写入 hash，刷新恢复选中（agent 与证据位置同理，原型里先演示 session 一级）。
- 三态演示：右上角可切换「正常 / 空列表 / 加载失败 / 未选中」。

### 3.2 #15 Turn 时间线（见 `timeline.html`）

- 顶部：面包屑（Session 20:05:12 › agent 选择器，下拉内按深度缩进展示家族成员 + 各自状态/问题数）。
- 工具条：事件类型过滤 chips（带计数）、「仅用户消息与最终回复」开关、全部展开/折叠、turn 跳转下拉。
- turn 头吸顶：`Turn 3 · 20:07:41 · 耗时 42s · 8 个事件 · 12.4k tok`。
- 卡片类型与色彩：

| 事件 | 色 | 默认状态 |
|---|---|---|
| 用户消息 | 蓝 | 展开，置顶易定位 |
| Agent 回复 | 绿 | 展开 |
| 推理 | 紫 | 折叠为一行摘要 |
| 工具调用 | 青 | 展开（标题行=工具名+关键参数+状态徽章） |
| 工具输出 | 灰 | 与调用配对；>15 行折叠 + 渐隐遮罩 |
| 文件变更 | 橙 | 展开，diff 统计 |
| 错误 | 红 | 展开，退出码显眼 |
| token 用量 | 灰 chip | 收在 turn 头 |

- call_id 配对：调用卡与输出卡共用一条左侧竖轨，两张卡都带 `call_xxxx` 徽章，点击徽章互相高亮。
- 每张卡右上角：复制 / 查看原始 JSON（打桩弹层）。

## 5. 我的判断（未经你确认，标出来供推翻）

1. ~~暗色 devtool 风格~~ → **亮色系**（已由你拍板：白底卡片 + 浅灰面板 + 高对比类型色）。
2. 密度**拆成两条线，不合并**（已由你拍板）：工具失败密度 = 工具失败 ÷ 交互次数（红条，3 次/百次满格）；问题密度 = 问题数 ÷ 交互次数（橙条，同样 3 次/百次满格，两条线共用一把尺）。分母用交互次数而非 turn——turn 颗粒度不稳定：1 个复杂 turn 可能含上百次交互，10 个简单 turn 可能只是 10 次模型直回。失败是客观发生的执行信号，问题依赖诊断器质量，两者量纲不同，合并会互相污染。
3. **agent 切换放在时间线顶部下拉**而不是左侧树——树留给 #8 执行流图，避免两处维护层级。
4. **家族摘要作为选中 session 后的落地页**，而不是直接进时间线——先给家族全貌再下钻，符合 ADR 的演示链路「搜索 → 执行流 → …」的第一步。
5. **事件过滤 chips 带计数**，因为长轨迹里用户靠计数判断"这个 session 有没有 MCP / 文件变更"。

## 7. 数据源变更：改用 Claude Code 会话（2026-10-19）

原型不再基于 Codex rollout，改为 `~/.claude/projects/<project>/<sessionId>.jsonl` + `<sessionId>/subagents/*.jsonl`。样本取 llm-wiki 的 4 条会话，见 `claude-code.html`。

### 结构差异（原型必须处理）

| 事实 | 处理方式 |
|---|---|
| JSONL 里**没有 turn 字段**，`promptId` 只按 `/clear` 分段（14 次提问仅 3 个 promptId），不能当轮次键 | 轮次由「真实人类提问」派生：`type=user` 且不含 `tool_result`、且不是 skill 注入/中断/命令回显 |
| 工具结果以 `type=user` 记录内联返回，与提问同形 | 按 `tool_use_id` 回填到对应工具卡，不参与轮次切分 |
| 元记录：`queue-operation` / `attachment` / `file-history-snapshot` / `last-prompt` / `mode` | 不进时间线；`attachment` 里的 SessionStart hook（superpowers 注入）只作诊断线索 |
| Skill 注入以「Base directory for this skill…」伪提问出现；中断以「[Request interrupted…]」出现 | 不算轮次，降级为轮内 `metacard`（技能注入 / 中断） |
| 子 agent 转录在独立文件，meta 记录 `agentType` 与 `toolUseId`（对应主会话 Agent 调用） | 家族成员 = 主会话 + 子转录；Agent 工具调用卡直接显示子 agent 类型与描述 |
| assistant 每条记录带 `message.id` 与 usage | 步骤 = `message.id`；token 按步骤聚合到轮次头 |
| 2f5e7ae8 时间跨度 145h（跨 6 天、多次重启） | 时间线展示每步的绝对时刻与轮次内耗时，不做连续时长假设 |

### 派生模型

- **轮次（Round）**：人类提问边界。轮次头 = 提问预览 + 起始时刻 + 步骤数 + 工具数 + 子 agent 数 + token。
- **步骤（Step）**：一次 assistant 响应（`message.id`），含思考 / 正文 / 工具调用 / Agent 调用。
- **轮次长度分布条**：摘要页把各轮步骤数画成段宽成比例的色条（含失败的轮次标红），一眼看出「1 个巨型轮次 + 若干轻量问答」的形状。

### 样本真实统计

| 会话 | 轮次 | 步骤 | 工具 | 失败 | 子 agent | Skill | Token |
|---|---|---|---|---|---|---|---|
| 研究用户数据驱动自进化方法 | 5 | 73 | 39 | 6 | 6 | deep-research、dispatching-parallel-agents | 7.0M |
| AI agent + 视频播放调研 | 12 | 375 | 197 | 4 | 0 | deep-research | 58.4M |
| 学习 DeepSeek Harness | 6 | 117 | 65 | 2 | 4 | — | 11.8M |
| Obsidian 插件机制分析 | 6 | 193 | 97 | 6 | 2 | — | 19.2M |

密度口径沿用 §5.2，分母由「交互次数」改为「步骤数」：失败/百步、问题/百步，两条线共用 3/百步满格。


## 8. 家族树图（替换轮次分布条 / 家族成员 / Skill 列表）

### 实现思路

1. 数据：每个 agent 一条横条，长度 ∝ 该 agent 的 JSONL 行数；Skill / Agent 触发点按 `行号 / 总行数` 定位到条上（例：172 行日志，L27 触发 skill → 条上 15.7% 处）。
2. 布局：主会话在左上；子 agent 节点按触发点的 x 对齐、纵向逐行堆叠（行高 118px），从父条触发点画折线（垂直→水平）连到子节点左侧中点。
3. 视图：React Flow 画布 + `fitView`（padding 0.15），滚轮缩放、拖拽平移，MiniMap 定位；「适应」不再手写包围盒计算。
4. 交互增强：节点 `<title>` 悬浮提示行号与事件名；顶栏图例区分 Skill / Subagent / 问题；子 agent 超过 8 个时折叠为「N 个子 agent · 点击展开」。

### 嵌套示例 `demo-nested`

用一张最小树验证「问题归属」和「子 agent 内触发」两件事，不混入真实会话的批量打桩：

```text
主会话 100 行 ──L20──> 子任务 A 60 行 ──L30──> 子任务 C 20 行（左侧 1 条问题）
      └────────L80──> 子任务 B 40 行（L15 触发 review-changes）
```

- **C 发现问题**：问题由数据里的 `findings` 显式声明，渲染时锚在 C 的横条上，而不是按「最后一个 agent」猜测归属。
- **B 触发 skill**：skill 事件写在 B 自己的转录里，药丸挂在 B 的条上；主会话 JSONL 里没有这条记录。

### 打桩时暴露的问题

1. **「最后一个 agent」不能作为问题归属**：布局是深度优先（A→C 循环在 B 之前），`[main, A, C, B]` 的最后一个 agent 是 B，不是 C；当初用「取 agentNodes 最后一个」打桩时，C 的问题被错挂到了 B。问题归属必须由证据里的 agent path / target 决定。
2. **父子回查依赖 `toolUseId`**：C 的合成数据一开始漏了 `toolUseId`，`childEventIndex` 找不到父条上的 L30 触发点，连线回落到 45% 处、标签也丢了 L30。子转录必须保留父调用的 `toolUseId`，否则树会「连得上但连错位置」。
3. **问题卡会横穿兄弟分支**：C 的右侧正好是 main→B 的竖直通道，问题卡无脑放右边时，红色连接线穿过灰色分支。现在记录每条父→子连线的竖直段，放卡前检测是否与问题堆相交；C 的卡因此换到左侧。Agent 节点也需要补一个 `in-left` target handle。
4. **子 agent 的 skill 不在主会话事件流里**：B 的 `review-changes` 只存在于 B 的转录。若家族摘要的 Skill 数只统计主会话事件，这个触发会整条丢失；聚合口径必须递归到每个成员。
5. **长标签会盖住右侧问题卡**：0 行的 workflow 节点只有 120px 条宽，但「workflow · 56 个 workflow 子 agent」这类标签会溢出到条外，正好压住右侧问题堆。问题卡的锚点因此改为 `max(条宽, 标签宽 + 60px)`，连接线的竖直通道也移到标签尾部右侧；标签本身保持完整、不再截断。
6. **连续触发把多条边叠成灰带**：主会话的 L70~L73 四个 subagent 触发点只差几像素，每条边各自竖直下落时会在同一条主会话横条下面叠成一条灰色长条。现在 24px 内的兄弟共用一个竖直 trunk，边从同一触发点下落，只保留一根细线；`fitView` 也改为等节点测量完成后再执行，避免首屏缩放跑偏。
7. **节点 class 与页面布局撞名**：主会话节点最初生成 `class="rf-agent main"`，命中了页面右栏的 `.main { overflow-y: auto; }`，节点内部因此出现一条可拖动的横向滚动条。改为 `class="rf-agent root"` 后滚动条消失；节点自身的 class 必须与页面布局 class 隔离。

### 集成到 `claude-code.html`

`claude-code.html` 的「执行流与触发时序」已换成同一套 React Flow 家族树：左侧选择 session 后重新挂载 React 岛，右侧面板固定 720px 高（嵌入页行高 108px，独立原型为 118px）。问题卡数量对齐 `SESSIONS.findings`（技能问题在左、上报型问题在 main 上方、剩余挂最后一个 agent），不再使用独立实验页的批量打桩。面板不显示 MiniMap，避免盖住右上角的上报型问题卡；缩放/适应由 React Flow Controls 提供。

问题卡文案约定：目标自身的问题用 `skill出现问题：…` / `subagent出现问题：…`；目标发现前置步骤的问题用 `<finder> skill发现前置步骤存在问题：…` / `<finder> subagent发现前置步骤存在问题：…`，finder 取实际 skill 名或 agent 任务名。

执行流下方的问题列表：按序号从小到大的顺序纵向渲染 N 张问题卡（N 与 `SESSIONS.findings` 对齐），每张卡显示 `#N`、问题文案、关联目标；点击卡片会滚动到执行流，并高亮、聚焦对应的问题框。

问题卡内容分层：执行流里只保留 `#N + 短标签`；列表卡展示短标题（如 `执行时间过长`）、统一的「错误」标记、详情，以及关键事实（文件路径 / 行号 / 错误、预期 / 实际 / 超出倍数、缓存命中等）和关联目标。当前阶段不区分告警与错误，所有问题卡都按错误处理。代码类问题必须能落到文件与行号；耗时类问题必须同时给出预期与实际时间。

### 可选技术方案（供后续正式实现）

| 方案 | 适用 | 代价 |
|---|---|---|
| 手写 SVG + transform（本原型采用） | 节点 < ~200、事件标记密集、需完全自定义 | 缩放/命中测试要自己实现 |
| D3（d3-hierarchy + zoom/drag） | 同一棵树要支持动态展开/折叠、动画 | 依赖 d3，样式自己写 |
| AntV G6 / X6 | 需要内置小地图、连边路由、导出 | 包体大，定制节点仍要写 React/Vue 渲染 |
| React Flow | 节点即 React 组件，交互态丰富 | 面板内嵌需 React 运行时，轨迹数据量大时性能要调 |
| Perfetto / Jaeger 式瀑布（行 + 缩进） | 只要"深度缩进 + 时间轴"，不需要连线 | 表达父子触发点不如树直观 |

参考：[Perfetto UI](https://perfetto.dev/docs/visualization/perfetto-ui)（track + slice 的执行流表达）、[AntV G6 自定义节点](http://www.chinadongda.com/j/?weixin_44827945/article/details/125861041)、[Jaeger trace 视图](https://raw.githubusercontent.com/wso2/docs-api-platform/main/en/docs/api-gateway/next/observability/tracing/viewing-traces-in-jaeger.md)、[React Flow](https://github.com/push-forward/react-flow)。

## 9. 错误详情与归因（新原型）

入口：Session 浏览器标题栏的「打开错误详情」按钮，位于「打开时间线」右侧；新增第三个页面「错误详情」，复用同一套 React Flow 执行流与问题打桩数据。

布局：左栏改为错误卡，不再放 session 列表，每卡显示 `#N`、标题、分析状态和关联目标，顶部有「全部错误」；右上是执行流，未选错误时显示该 session 的完整执行流，选中某个错误时只保留该错误的问题卡，其他错误卡及对应连线隐藏，agent/skill 横条保留；右下是 tab 卡片，当前为「问题描述」「归因分析」两页，未选错误时为空态。

状态枚举（左栏错误卡与归因结论共用）：

| 状态 | 含义 |
|---|---|
| 未分析 | 尚未产生归因报告 |
| 已分析 | 已收集证据，结论待确认 |
| 非问题 | 判定不是问题 |
| 是问题-模型问题 | 归因到模型规划 / 决策 |
| 是问题-prompt缺失某些提示词 | 归因到 prompt 缺失约束 |
| 是问题-错误 | 归因到代码 / 运行时错误 |

归因报告结构：先给结论（问题 / 非问题；未分析为空态；已分析但未归类时显示待确认）。非问题给非问题原因与分析推导过程；问题给分类（模型问题 / prompt缺失某些提示词 / 错误，后续可扩充）、定位到的问题对象（未知 / `skill:xxx` / `agent:<type> · <agent 名>`）、分析出的问题描述、分析推导过程。agent 类型取 `TREE` 里该子 agent 的 `type`，例如 `general-purpose`、`Explore`、`workflow`；左栏错误卡的关联目标同样带类型。「问题描述」tab 展示标题、状态、详情、关键事实（文件 / 行号 / 错误、预期 / 实际等）和关联目标。

原型打桩映射：自进化——重复加载=未分析，输出缺少来源校验=非问题，检索索引读取失败=是问题-错误，执行时间过长=是问题-模型问题（`agent: general-purpose · 检索EverMind与Hermes`）；视频——重复加载=已分析，检索结果反序列化失败=是问题-错误（`skill: deep-research`），执行时间过长=是问题-模型问题（`agent: workflow · 56 个 workflow 子 agent`）；DSH——会话快照读取越界=是问题-prompt缺失某些提示词（`agent: Explore · 分析 agent loop 与 LLM 层`），执行时间过长=是问题-模型问题（`agent: Explore · 分析自进化与协调面`）；Obsidian——插件清单解析失败=是问题-错误，执行范围越界=非问题，子任务重复抓取=未分析。状态与归因内容均为打桩，真实分析器接入后替换 `analysisFor` 的数据即可。

交互：点击左栏错误卡后，执行流只保留该问题卡，tab 回到「问题描述」；再次点击已选中的错误卡保持选中，不取消，也不切换当前 tab；取消选择统一用「全部错误」。点「全部错误」恢复完整执行流和空态详情。归因 tab 按「结论 → 非问题原因 / 问题分类 → 定位对象 → 问题描述 → 推导过程」的顺序展开。

## 10. 自进化页面（evolution.html）

入口与 session 页面分离：`index.html` 上的独立卡片，顶栏只保留「← 原型入口 / Session 浏览器 →」的弱导航，不与 session 浏览器共用侧栏。

### 10.1 入口页三大功能

- **历史流程查看 / 正在执行进展查看**：同一列表分两组。运行卡展示对象 chip（`skill:deep-research@v2.0.0`）、时间段、模型 chips、聚合数字（session / 问题报告 / 用于进化 / 聚类 / 已跑轮次 / 已接纳）；正在执行的卡带脉冲点 + 进度条 + 当前阶段文案，历史卡带终评结论（best vs 初始得分、Δ、接纳 patch 数、有效/无收益徽章）。
- **启动自进化**：右上角主按钮打开两步向导。第一步筛选——对象类型（skill/agent 切换）+ 对象 + 版本、时间段（session 启动时间）、模型多选；点「查询匹配报告」后给出命中摘要（session 数、报告数、已分析/未分析、可作为输入的「是问题」数）与前 8 份报告预览。第二步两个出口：「仅聚类分析」与「启动自进化」。

### 10.2 流程在打桩中的落点

筛选 → 聚类（M 类，不同类型不混聚，每簇记录来源报告 id 列表）→ 拉取对应版本对象由 LLM 归因判定问题是否真实存在并给置信度 → 综合置信度/影响面/报告频次得严重程度 → 按严重程度降序逐轮：生成 edit patch → candidate 与 current 评测 → 有收益则接纳（commit 携带聚类问题、来源报告 id、问题现象）→ M 轮后 best skill 与初始版本在测试集终评，判定自进化是否有效。详情页顶部的六段 stepper 与该流程一一对应；**已完成 / 进行中的节点可点击**，下方内容区随之切换为该步骤的产出（第 1 步筛选条件与命中报告明细表、第 2 步聚类结果、第 3 步归因判定与置信度、第 4 步严重程度排序表、第 5 步逐轮 patch/评测/接纳、第 6 步测试集终评），选中节点蓝色高亮并在面板标题标注「当前查看：第 N 步」，未到达的节点不可点击；「模拟推进一轮」后选中节点自动跟随最新进度。

### 10.3 详情页信息组织（对应需求的 4 项）

1. **目标基本信息**：对象 / 版本 / 时间段 / 模型 + session 数、报告数、已分析/未分析、用于进化数；已分析部分用堆叠条 + 图例展示「非问题 / 是问题-错误 / 是问题-prompt缺失某些提示词 / 是问题-模型问题」的数量分布，并注明用于进化数 = 三类「是问题」之和（非问题剔除）。
2. **聚类问题**：按严重程度降序的簇列表，每簇显示类型 chip、来源报告数与 id  chips、置信度、严重程度条。
3. **每轮迭代**：簇展开后含生成的 edit patch（diff 着色）、candidate vs current 评测对比条与 Δ、接纳/未接纳徽章；接纳时展示 commit 块（hash + cluster + reports + phenomenon 三行打桩），未接纳时说明 current 不变。
4. **最终结果**：有效性判定横幅（best 版本号、双方得分与 Δ）、best skill 修改点清单（逐条 commit hash + 簇 + 来源报告数）、测试集对比表（总体得分 / 成功率 / 引用准确率 / 复现率 / 平均轮数）。

### 10.4 打桩与交互约定

- 3 条预置 run：deep-research v2.0.0（运行中，第 3/5 轮评测中）、deep-research v1.9.0（已完成·有效）、Explore v1.0.1（已完成·无收益）。「模拟推进一轮」按预定结局推进运行中的 run，用于演示进展查看。
- 启动向导与「仅聚类」的命中数字按筛选条件哈希生成，对象类型决定聚类模板（skill / agent 两套）；新建 run 进入列表顶部并可模拟推进。
- 聚类页与详情页的簇默认展开当前轮；URL hash（`#/runs` / `#/run/<id>` / `#/cluster`）保持与 session 原型一致的可恢复约定。
