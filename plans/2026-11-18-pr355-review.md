## §1 一页速览

**一句话**：把 refresh Cookie 的 `Secure` 从“部署阶段决定”改成“这次请求实际是不是 HTTPS 决定”，让先用 IP + HTTP 上线的生产实例也能把 refresh token 存进浏览器。

**一个比喻**：原来的逻辑像“只要是正式演出就锁门”，可场地还是露天（HTTP）；观众（浏览器）看到“锁门”标记就不把票（Cookie）带进来。现在改成“看到雨棚（HTTPS）才锁门”，露天场地照常收票，搭了雨棚后再恢复锁门。

| 交付块 | 内容 |
|---|---|
| 核心判定 | `cookie_secure_for(request)`：显式开关优先，否则 `request.url.scheme == "https"` |
| 覆盖范围 | 登录、刷新、IdP 回调清理、登出四处共用 |
| 配置 | `HE_COOKIE_SECURE`（留空自动，true/false 强制） |
| 部署配套 | nginx `X-Forwarded-Proto $scheme`；生产模板登记开关 |
| 文档 | Agent Note（决策）+ postmortem（事故）+ flow issue（实施契约）+ 架构现状 |
| 验证基线 | API 单测 4 条路径；生产构建 HTTP 浏览器冒烟 7 场景 |

**代价**：HTTP 下 refresh token 明文传输（issue #348 明确接受的过渡风险）；TLS 代理终止时依赖 `X-Forwarded-Proto` 或显式开关，否则会退回非 Secure。

## §2 架构导览

### 2.1 判定层：一个函数，四个调用点

`apps/api/app/api/auth.py:43` 新增 `cookie_secure_for(request)`：

- 第 46–47 行：`settings.cookie_secure` 非 None 时直接返回，给运维一个显式开关。
- 第 48 行：未设置时读 `request.url.scheme`。Starlette/uvicorn 在信任代理头时会把 `X-Forwarded-Proto` 反映到 scheme；nginx 配置新增的第 23 行负责提供这个头。

四个调用点：

| 位置 | 场景 | 作用 |
|---|---|---|
| `auth.py:58` | `set_refresh_cookie` | 登录与刷新共用，决定新 Cookie 是否 Secure |
| `auth.py:140` | IdP 回调清理 state Cookie | 与写入侧（`state_challenge`）目前仍不完全一致，见讨论点 D2 |
| `auth.py:160` | 登出删除 refresh Cookie | 删除属性与写入侧保持一致 |

这个函数把原先散落在四处的 `settings.is_production` 收成一个来源，避免“登录改了、登出没改”的半修复。

### 2.2 配置层：可选布尔与空值

`apps/api/app/config.py:25` 的 `_parse_optional_bool` 把空字符串转成 `None`。原因是生产模板习惯把未启用项写成 `HE_COOKIE_SECURE=`，而 pydantic 的 `bool` 解析会拒绝空串；如果不处理，模板照抄会启动失败。

`config.py:50` 定义 `CookieSecure = Annotated[bool | None, BeforeValidator(...)]`，`config.py:147` 落到 `Settings.cookie_secure`。没有设置时是 `None`，与“自动”语义一致；显式 `false` 也能和“未设置”区分开。

### 2.3 部署层：为什么还需要 nginx 头

后端只听 `127.0.0.1:8787`，公网流量经 nginx。如果未来 TLS 在 nginx 终止，而 nginx 不传 `X-Forwarded-Proto`，后端看到的是 `http`，就会再次省略 Secure。`deploy/nginx-harness.conf:23` 补上头；`deploy/env.production.example:27-29` 登记 `HE_COOKIE_SECURE` 作为代理不传头时的兜底。

注意：该 nginx 文件在仓库里，但现有 `release.sh` 只重启 API，不会自动把 `deploy/` 下的 nginx 配置安装到 `/etc/nginx`。当前 HTTP 修复不依赖它；HTTPS 上线时需要在下一次 nginx 配置安装中带上，见讨论点 D1。

## §3 数据流走查

以“生产 HTTP 登录 → 刷新 → 空闲过期”为主线：

1. **登录**：浏览器 POST `/api/auth/login`。`login` 调 `set_refresh_cookie`（`auth.py:76` → `:51`）。`request.url.scheme` 是 `http`，`cookie_secure_for` 返回 `False`，响应下发无 `Secure` 的 `refresh_token`。浏览器接受并存储。
2. **整页刷新 / 新标签**：前端 `bootstrapApp` 先 `auth.tryRefresh()`（`apps/web/src/bootstrap.ts`），走 `POST /api/auth/refresh`。浏览器自动带 Cookie；`identity.refresh` 校验并轮换 refresh token，`set_refresh_cookie` 再次下发无 Secure 的新 Cookie。前端拿到 access token 后 `loadSession`，路由守卫放行。
3. **空闲过期**：access token 30 分钟后过期，`/api/acquisition/status` 轮询得到 401。`http.ts` 的 `execute` 只重试一次，先 `refreshOnce()`；refresh 成功后重放原请求，页面不跳登录。只有 refresh 也失败才触发 `authExpiredHandler`。
4. **主动退出**：`POST /api/auth/logout` 撤销 refresh token，`delete_cookie` 用同一判定删除 Cookie；前端清 query cache 并 `router.push("/login")`。
5. **未来 HTTPS**：浏览器请求 `https://…`；若 nginx 传 `X-Forwarded-Proto: https`，uvicorn 把 scheme 还原为 https，`cookie_secure_for` 返回 `True`，Cookie 带 Secure。若代理不传头，运维显式设 `HE_COOKIE_SECURE=true`。

## §6 讨论点

### D1. 存量服务器不会自动获得 `X-Forwarded-Proto`

- **位置**：`deploy/nginx-harness.conf:23`、`apps/api/app/api/auth.py:43-48`
- **现象**：仓库模板已补代理头，但 `deploy/release.sh` 只重启 `harness-api`，不重装 `/etc/nginx` 配置；现有服务器若直接启用 HTTPS，后端仍可能看到 `http`。
- **问题**：自动判定会静默省略 Secure，属于“安全属性悄悄降级”。当前 HTTP 生产不受影响，但 HTTPS 切换时容易踩。
- **预判**：接受当前取舍——本 PR 的核心目标是恢复 HTTP 登录；HTTPS 上线应在运维步骤里显式安装 nginx 配置或设 `HE_COOKIE_SECURE=true`，并复跑冒烟确认 Set-Cookie 带 Secure。可考虑后续在启动日志里对“production + http + 未设开关”打一条 warning。
- **结论**：

### D2. `callback.state_challenge()` 仍用 `is_production`

- **位置**：`apps/api/app/service/identity/callback.py:135-140`（未改），`apps/api/app/api/auth.py:140`
- **现象**：IdP state Cookie 的写入侧仍固定 `self._settings.is_production`，而删除侧已改用 `cookie_secure_for`。OIDC 当前返回 501，属于未启用路径。
- **问题**：未来接入 OIDC 时，HTTP 生产会写入 Secure state Cookie 并被浏览器丢弃，回调校验失败；两侧属性也不一致。
- **预判**：当前无实害，不在本 PR 扩大范围；OIDC 落地时应让 `state_challenge` 接收请求或显式开关，并复用同一判定。已在 Agent Note 的 Consequences 记录。
- **结论**：

### D3. `HE_COOKIE_SECURE=false` 可显式关闭 HTTPS 的 Secure

- **位置**：`apps/api/app/config.py:147`、`apps/api/app/api/auth.py:46-47`
- **现象**：显式 `false` 会覆盖协议判定，即使请求是 HTTPS 也不加 Secure。
- **问题**：这是给“内网 HTTP/特殊代理”留的逃生门，但也可能被误用成永久降级。
- **预判**：保留；生产模板注释已把它限定为“TLS 在代理层终止且未传 X-Forwarded-Proto”时用 `true`，没有鼓励 `false`。若要更稳，可在 HTTPS 请求 + `cookie_secure=False` 时打 warning，属于后续增强。
- **结论**：

### D4. CI 仍无法自动复现“非 loopback HTTP + Secure Cookie”

- **位置**：`apps/api/tests/identity/test_auth.py:461-503`、`tests/e2e/*`
- **现象**：单测覆盖了 ASGI 层的 scheme 分支；真实浏览器冒烟使用非 loopback 地址，能在本地/手工复现，但 CI 的 E2E 仍跑 `127.0.0.1`，Chrome 把它当可信源，会接受 Secure Cookie。
- **问题**：同类回归（把判定改回 `is_production`）只能靠单测兜住，浏览器级 CI 不会红。
- **预判**：单测已经能精确锁住判定函数；把非 loopback 浏览器冒烟做成 CI 门禁成本高（需要额外网卡/主机名与端口）。建议保留“发布后生产/IP 冒烟”清单，并把本次报告作为基线。是否要把它升级为自动化门禁，交给维护者拍板。
- **结论**：

### D5. 生产 bug 报告与 flow issue 的正文归属

- **位置**：`.agents/flow/issues/m12-14-auth-session-persistence.md:58`
- **现象**：issue #348 是生产直接创建的 bug 报告，本地 flow issue 用同一编号接入；两者正文不同，`pnpm flow:sync` 会用本地正文覆盖远端。
- **问题**：若无人合并正文，`flow:sync` 会丢掉 #348 的截图、时间线和复现细节。
- **预判**：本 PR 在 flow issue 与 PR 描述里都写了“sync 前人工合并正文”的提示；长期看，流程需要一条“从外部 bug 报告接入”的规则，明确保留证据段。
- **结论**：

## §9 文件级代码分析

### 9.1 `apps/api/app/api/auth.py`（M）

**职责**：鉴权 HTTP 适配层，负责 Cookie 的下发/清理与错误码映射。
**变更形态**：新增一个纯函数；三处 `secure` 参数改为调用它。

```python
# 旧
secure=settings.is_production

# 新
secure=cookie_secure_for(request)
```

`cookie_secure_for` 的逻辑是“显式开关 > 请求协议”，把安全属性从部署阶段解耦到传输层。这样 HTTP 生产可用，HTTPS 仍安全；代价是 HTTP 下 refresh token 明文传输（见 D6/Agent Note）。实现无 I/O、无状态，容易测试。四个调用点共享同一函数，避免遗漏登出或回调清理。

**检视发现**：无阻塞问题。唯一值得记录的是 `callback.state_challenge` 未同步（D2，未启用路径）。

### 9.2 `apps/api/app/config.py`（M）

**职责**：环境变量配置的单一入口。
**变更形态**：新增 `_parse_optional_bool`、`CookieSecure` 类型别名与 `cookie_secure` 字段。

空字符串 → `None` 的处理是必要的：生产模板用 `HE_COOKIE_SECURE=` 表示“自动”，若直接交给 pydantic 的 bool 解析会启动失败。该函数只处理 `str`，其他类型原样交给 pydantic，边界清楚。字段默认 `None` 保持向后兼容：未配置时行为等同“按协议自动”。

**检视发现**：无。覆盖测试见 `test_empty_cookie_secure_environment_value_is_auto`。

### 9.3 `apps/api/tests/identity/test_auth.py`（M）

**职责**：鉴权端到端行为测试。
**变更形态**：原 `test_production_refresh_cookie_is_secure` 改名为 `test_https_refresh_cookie_is_secure`；新增 3 条测试。

四条路径分别锁住：HTTPS 加 Secure、HTTP 生产不加且 refresh 能成功、显式 true 覆盖 HTTP、空环境值解析为自动。第 476 行的 `refreshed = await client.post("/api/auth/refresh")` 特别关键：只断言 Set-Cookie 不够，还要证明 HTTP 下 refresh 链路真的可用。
