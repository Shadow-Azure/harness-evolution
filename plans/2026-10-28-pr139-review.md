## §1 一页速览

**一句话：** 这个 PR 给自进化 run 装入一台持久“飞行记录仪”：过程事件先落数据库，REST 按游标回放，SSE 只发“有新记录”的通知，详情页再用日志 tab 把失败和阶段过程展示出来。

**比喻：** `run.event` 是机场公告，`evolution_run_events` 才是飞行记录仪本体。乘客错过广播、连接断开或页面重开时，仍然从黑匣子按序号补读；PR 的核心价值是保证广播丢失也不会丢事实。

## §2 架构导览

### 2.1 一次写入：先脱敏，再分配 run 内序号，再通知

`EvolutionRunEventService.record()` 是写入主入口。它先校验 event type、level、stage、step 范围，再递归脱敏 payload，压缩消息与错误详情，最后调用存储层（`apps/api/app/service/evolution/events.py:216-273`）。

存储层在同一写事务中读取当前 `max(seq)` 并插入下一号；`UNIQUE(run_id, seq)` 冲突时最多重试五次（`apps/api/app/db/crud/run_events.py:99-157`）。这像餐厅取号：先看柜台最后一张号，冲突就重取，而不是依赖一个可能跨 run 共享的全局计数器。

持久化成功后，服务才发布 `run.event`，并在通知数据里补 `runId`（`events.py:274-282`）。REST/SSE 共享同一事件 DTO，避免两套字段随时间漂移。

### 2.2 一次读取：level 是筛选器，不是第二套游标

`read_page()` 始终使用 `run_id` 和 `seq > afterSeq` 限定范围，再可选追加 `level` 条件，最后按 `(run_id, seq)` 排序并多取一行判断 `hasMore`（`run_events.py:159-193`）。

例如库里依次有 `info#1, error#2, info#3, error#4`，`afterSeq=2&level=error` 返回 `4`，不会因第二条是 info 而把游标停在 2。页面 `nextSeq` 取实际返回的最后一条；没有匹配项时保持请求游标（`events.py:285-312`）。

### 2.3 状态通知：历史事件与生命周期广播分开发

`record_failed()`、`record_blocked()`、`record_resumed()` 都先写 `run.event`，再更新 run 状态并发 `run.failed/blocked/resumed`（`events.py:314-470`）。任务边界捕获 `RunBlocked` 时把 job 记为 failed，但把 run 记为 blocked；普通异常才把 run 记为 failed（`jobs.py:240-301`）。

这区分了两件事：job 是本轮 worker 的尝试，run 是用户看到的业务对象。一次 push 可重试失败结束的是 job，不是整个 run。

### 2.4 日志 tab：REST 分页快照，加本地过滤/滚动状态

`useEvolutionRunEventLog()` 首次请求 `afterSeq=0&limit=100`，加载更多时复用最后 `nextSeq`，合并时按 `seq` 去重排序（`useEvolutionRunEventLog.ts:16-104`）。`RunLogPanel` 管理全部/错误/警告筛选、自动滚动开关、刷新和加载更多；`EventList` 只在目标 step/cluster 可点击时给跳转入口（`RunLogPanel.vue:27-172`；`EventList.vue:43-107`）。

`ErrorDetail` 使用原生 `<details>` 默认折叠，复制内容只来自已经脱敏的服务端 `error` 对象（`ErrorDetail.vue:9-48`）。

### 2.5 RunDetail 用 tab 避免日志挤压六步布局

`RunDetail.vue` 新增 `?tab=logs` 派生状态；错误横幅和失败/阻塞 banner 可直接切日志。日志事件跳 step 时删掉 `tab`，切簇时写 `step=clusters&cluster=…`（`RunDetail.vue:19-168`）。这条路由规则把“查看日志”和“继续定位到步骤/簇”串成一个可刷新深链。

## §3 数据流走查

### 场景 A：运行创建并准备

1. `EvolutionLaunchService` 创建 run 后追加 `run_created`，payload 只保留 mode/target 等非敏感事实（`launch.py:114-131`）。
2. service 对 payload、message、error 递归脱敏，再追加到事件表（`events.py:244-273`）。
3. 存储层分配 `seq=1` 并持久化，发布 `run.event`（`run_events.py:119-142`；`events.py:274-282`）。
4. detail 读取时用 `max_seq` 回填 `lastEventSeq=1`（`runs.py:352-411`）。

### 场景 B：用户打开运行详情并切到执行日志

1. 页面读取 run shell 和当前 step。
2. 用户点击“执行日志”，URL 变为 `?tab=logs`。
3. `RunLogPanel` 拉取 `afterSeq=0&limit=100`。
4. 用户选择“错误”，hook 重新从 0 拉 `level=error`。
5. 事件带可点击 step/cluster 时，点击后回到六步详情对应位置。

### 场景 C：push 可重试失败

1. engine 抛 `RunBlocked(stage="push")`。
2. job 边界把 job 标记 failed，但调用 `record_blocked()`。
3. 事件表写 `run_blocked`，run 变 `blocked`，`blockedStage=push`；随后发 `run.event` 和 `run.blocked`。
4. UI 顶部显示阻塞阶段、重试次数与下一次时间；用户可跳日志看已脱敏错误。

### 场景 D：致命评测异常

1. worker 抛普通异常。
2. job 边界把 `traceback.format_exc()` 交给事件 service。
3. service 压缩控制字符、脱敏后按 UTF-8 8KB 截断，落 `error_detail`。
4. run 状态更新为 failed，UI 横幅和日志都能直接定位失败阶段。

## §6 讨论点

### D1：常见裸凭据仍可原样进入持久事件

**位置：** `apps/api/app/utils/redaction.py:9-28,55-84`；`apps/api/app/service/evolution/events.py:249-273`

**现象：** 当前规则覆盖 `HE_*`、password/token/secret/api_key 等带标签值、URL userinfo 和 Bearer/Basic。`AWS_ACCESS_KEY_ID=AKIA…`、`AWS_SECRET_ACCESS_KEY=wJal…`、裸 `sk-proj-…`、裸 `ghp_…` 与 JWT 不会命中。直接调用 `record()` 可看到这些值原样进入存储层 append 参数。

**问题：** issue 明确要求“密钥样例被替换，不得把原始 token / 环境变量 / 未脱敏 stderr 入库”。真实 CLI 错误输出经常只打印 token 本身，或打印 AWS 的双字段，不一定有本 redactor 认识的键名。

**预判：** 这是必须修复的安全缺陷。建议同时增加常见凭据前缀/格式（AWS access key、`sk-`、`ghp_/github_pat_`、JWT、private-key block）和更完整的 AWS/environment 键识别，并用 service→DB→API/SSE 的完整链路测试断言原值不出现。

**结论：**

2026-10-28 已修复。统一脱敏器增加 AWS access/session 字段、OpenAI/GitHub token、JWT 与 PEM/OpenSSH 私钥块识别，并由真实 service→DB→API/SSE 测试证明原值不会进入事件、run 状态或通知。

### D2：评测阻塞恢复后保留 `evalStatus=failed`

**位置：** `apps/api/app/db/crud/evolution.py:151-193`；`apps/api/app/service/evolution/events.py:434-470`

**现象：** eval 阻塞时 `mark_blocked()` 设置 `eval_status="failed"`；`record_resumed()` 调用 `mark_resumed()` 后只把 `status` 恢复为 `running`，没有重置 `eval_status`。独立 SQLite 复现得到 `blocked / failed / eval`，恢复后为 `running / failed / None`。

**问题：** RunDetail 会在“正在执行”的 run 上继续展示“评测失败”，后续轮询/恢复也会面对互相矛盾的状态字段。

**预判：** 在恢复 evaluator 时把 `eval_status` 推回 `pending`（或该阶段真正开始后的 `evaluating`），并新增 `blocked at eval → resumed` 回归测试；如果由 m5-11 承担恢复动作，m5-08 的 `record_resumed()` 也不能发布自相矛盾状态。

**结论：**

2026-10-28 已修复。`mark_resumed()` 将 `eval_status` 恢复为 `pending`；新增 eval blocked→resumed 回归，覆盖 `running / None / pending`。

### D3：切换 run 或筛选时日志 hook 保留上一页事件

**位置：** `apps/web/src/composables/useEvolutionRunEventLog.ts:44-64,88-94`

**现象：** `refresh()` 开始新请求时只设置 `isPending`，不清空 `items/nextSeq/hasMore`。同一详情路由从 run A 切到 run B、或从“全部”切到“错误”时，新请求返回前仍渲染 A/全部过滤结果。

**问题：** 用户会在新 run 标题下短暂看到上一条 run 的事件；慢请求、失败或快速筛选时更容易造成误判。当前组件测试只验证成功响应，没有覆盖请求挂起时的切换。

**预判：** 在 runId/level 键变化时同步清空列表和游标，或按 key 创建独立状态；新增延迟响应测试，断言切换后旧 seq 立刻消失、旧请求返回不能覆盖新 key。

**结论：**

2026-10-28 已修复。runId 或 level 身份变化时同步清空 items、游标与错误并提升请求代际；延迟响应测试证明旧 run/filter 数据不会在新 key 下短暂出现或被旧请求恢复。

### D4：加载更多失败会抹掉已读日志

**位置：** `apps/web/src/composables/useEvolutionRunEventLog.ts:66-85`；`apps/web/src/pages/evolution/components/RunLogPanel.vue:128-143`

**现象：** `loadMore()` 失败写入同一个 `error`，模板随后用 `ErrorState` 替换整个 `EventList`。

**问题：** 用户已经加载的前 100 条日志因下一页失败而消失，无法继续查看已知错误；错误态虽然“明确”，但不应牺牲已有事实。

**预判：** 区分首屏错误与追加错误；追加失败保留列表并在底部显示可重试提示。若无历史事件后再走整块错误态。

**结论：**

## §9 文件级代码分析

### `apps/api/app/utils/redaction.py`（A）

**职责：** 所有 evolution event、job error 和敏感 payload 的集中安全边界。

**关键依赖：** Python 标准库 `re`；没有第三方运行依赖。正则像机场安检机，所有字符串先过同一组识别规则，再由 `sanitize_value()` 递归检查对象键。这个设计比在每个调用点手写脱敏可靠，但安检规则漏掉的证件类型仍会通过。

**变更代码块分析：** 旧逻辑散落在 `service/jobs.py`，只覆盖少数后缀键；新文件把规则集中在 9–52 行，并加入 URL userinfo、Basic Authorization、`HE_*`、JSON key 和 8KB UTF-8 截断。`truncate_utf8()` 在 120–127 行用字节切片，避免多字节字符导致上限被突破。

**实现思路总结：** 一处定义规则、一处递归应用、一次字节级截断。

**检视发现：** D1；其余已知键、URL userinfo、Authorization 和详情截断路径实现清晰。

### `apps/api/app/service/evolution/events.py`（A）
