## §1 一页速览

**一句话**：给总览页补上“按进化对象看”的后端：每个对象在窗口内出现在哪些版本、产生多少潜在 bad case、这些 case 是三态中的哪一种。

**一个比喻**：潜在匹配器像一位熟悉案卷的档案员，能判断“这份 case 是否属于这个对象的这个版本”；本 PR 不是再写一位档案员，而是给档案员配一张按对象、版本、状态排好的目录柜。目录柜只负责把档案员已经判好的案卷归档、编号、分页，不重新判断案卷归属。

**交付块**：

| 块 | 内容 |
|---|---|
| 对象列表 | 三态统计 + `evolvable` 降序 + 5 条/页 |
| 趋势 | 对象/状态多选，零填充，analyzed 用归因时间、unanalyzed 用上报时间 |
| 潜在 case 列表 | 对象/来源/状态过滤，8 条/页，带归因 ID 与 category |
| 单对象分析 | 独立时间窗 + `versions[]`/`versionLimit`，byVersion/bySource |
| 契约 | 4 个 GET 路径、15 个 schema、TS 类型 |
| 边界 | 只读、空间隔离、知识库 revision 同一坐标、无迁移/无前端 |

## §2 架构导览

### 2.1 HTTP 层：只做参数解析与鉴权

`apps/api/app/api/overview.py:204` 新增 `target_overview_from` 从 `app.state` 取服务；`_target_query`（`:209`）把 `from/to/range/grain/targets/objects/states/versions/versionLimit/page/pageSize` 归一成一个 `TargetOverviewQuery`。窗口解析复用既有 `OverviewQuery.window()`，因此目标端点与 bad case 总览共享同一套 `WINDOW_INVALID`/`GRAIN_INVALID`/降级规则。

四个路由都在 `require_workspace_role("viewer")` 之下：

- `/overview/targets`（`:375`）：默认 `pageSize=5`。
- `/overview/targets/trend`（`:406`）：`targets[]`、`states[]`、`grain`。
- `/overview/targets/cases`（`:436`）：增加 `objects[]`，默认 `pageSize=8`。
- `/overview/targets/{targetId}/detail`（`:473`）：`versions[]` 与 `versionLimit`。

`versionLimit` 故意写成 `int + ge/le + json_schema_extra enum`，而不是 `Literal`：FastAPI/Pydantic 对查询串里的 `Literal[int]` 不做字符串→整数转换，实测会返回 “Input should be 0, 5, 10 or 20”；改成整数后由服务层 `parse_version_limit` 做封闭集合校验（`targets.py:228`），OpenAPI 仍暴露枚举。

### 2.2 服务层：把 matcher 当唯一判定器

`TargetOverviewService`（`service/overview/targets.py:324`）持有 `EvolutionTargetRepository`、`TargetOverviewRepository` 与共享 `PotentialMatcher`，默认策略固定为 `resolve_policy(None)`（`targets.py:337`）。

核心方法是 `_analyse_target`（`targets.py:577`）：

1. `list_object_versions` 取窗口内实际出现的 `(object_version, object_revision)` 去重集合。
2. `_ordered_versions`（`targets.py:281`）把 `tag:` 前缀去掉、与 `defaultRef` 合并、按自然版本降序。
3. 每个版本调 `_evaluate`（`targets.py:640`）一次，得到 `SessionAssociation` 与 `PotentialMatch`。
4. 对 `match.included` 用 `list_attributions`（`overview_targets.py:166`）取归因链接，按 `updated_at DESC, probe_id DESC` 选每个 case/版本最新一条。
5. 投影成 `TargetCaseEntry`，同时记录每个版本的关联 Session 集合。

这样“潜在数”只有 matcher 一份实现；服务层不复制 `include_self_report / include_after_object / same_object_only` 或触发点比较。

### 2.3 数据读取层：三组批量查询，全部空间固定

`apps/api/app/db/crud/overview_targets.py` 只做三件事：

- `list_window_cases`（`:77`）：窗口内 self/discovery case，带 title；与 matcher 的 case 集合同谓词。
- `list_object_versions`（`:121`）：`agent_events JOIN agents`，取 `kind=object_type AND name=object_name` 的 distinct 版本/修订对。
- `list_attributions`（`:166`）：`bad_case_analysis JOIN probe_reports`，固定 `workspace_id/probe_type/probe_object`，只读 `conclusion ∈ {attributed, non_target}`。

所有查询都分块 500，避免一次 IN 过长；没有 per-case 查询。

### 2.4 契约与装配

`main.py:277` 构造 `TargetOverviewService(target_repository, TargetOverviewRepository(db), potential_matcher)`，`main.py:517` 挂到 `app.state.target_overview`。没有新增迁移、错误码或全局配置。

DTO 在 `target_schemas.py`：`TargetOverviewItem`（`:40`）明确写出“一行 = `(badCaseId, targetVersion)`，所以 `attributed + nonTarget + unanalyzed = potential`”；`TargetTrendMeta`（`:112`）把分桶时间策略作为机器可读字段返回；detail 把 `target/versions` 与 `byVersion/bySource` 分开，便于前端做独立筛选。

## §3 数据流走查

以 `GET /api/workspaces/ws-a/overview/targets?from=2026-11-01&to=2026-11-30` 为例：

1. `require_workspace_role("viewer")` 解析 `wid`，不可见空间返回 404（`overview.py:379`）。
2. `_target_query` 解析窗口，`OverviewQuery.window()` 得到 `[2026-11-01, 2026-11-30]`、grain=day。
3. `TargetOverviewService.list_targets`（`targets.py:339`）调用 `_analyses`（`:527`），先取该空间所有启用 target。
4. `list_window_cases` 取窗口内 case facts；`session_ids` 来自这些 case 的根 Session。
5. 每个 target：`list_object_versions` 发现版本；假设 skill `deep-research` 发现 `v2.0.0/v1.9.0/v1.8.0`，加上 `defaultRef` 后自然降序。
6. 对 `v2.0.0`：`MatchCondition` 用 `resolve_target_revision("v2.0.0") → ("v2.0.0","tag:v2.0.0")`；matcher 关联含该 revision 的 Session，并按默认策略筛出潜在 case。
7. `list_attributions` 取这些 case 的链接；`_newest_link_by_case`（`:295`）只保留当前 display version 的最新一条；`_state`（`:315`）映射 `attributed/nonTarget/unanalyzed`。
8. 汇总成 `TargetAnalysis`（`:125`）：`sessions` 是版本关联 Session 并集，`potential` 是行数，三态计数；`list_targets` 按 `(-evolvable, -potential, name)` 排序并分页。
9. `trend`（`:373`）复用同一批分析：analyzed 取 `attribution.created_at`、unanalyzed 取 `case.created_at`，落到 `bucket_starts` 的零填充桶；`meta.bucketPolicy` 返回 `BUCKET_POLICY`（`:81`）。
10. `cases`（`:432`）在行级再过滤 target/state/source，按 `createdAt DESC` 分页。
11. `detail`（`:464`）只分析请求的 `target_id`（修复后），按显式 `versions[]` 或 `versionLimit` 选版本，再算 `sessions/potential/distinctCases/versions` 与 `byVersion/bySource`。

边界：归因创建时间落在窗口外的 analyzed 行不会进入 trend 桶；这是分桶策略的直接结果，已由 `meta.bucketPolicy` 声明，不是漏算。

## §6 讨论点

### D1 每个对象版本都跑一次 matcher，首屏查询量随“对象×版本”增长

- **位置**：`apps/api/app/service/overview/targets.py:527`、`:577`、`:640`
- **现象**：`_analyses` 对每个启用 target 调 `_analyse_target`，后者对每个发现版本调一次 `associated_sessions + potential_cases`；每次 matcher 又会批量查窗口 case、Session、对象事件、agents、锚点事件。
- **问题**：当前空间对象是人工配置的小集合、版本通常个位数，页面可接受；若未来单空间几十个对象、每对象几十个版本，首屏会退化成数百次查询。
- **预判**：本 issue 的正确性优先于查询次数；先把 matcher 的窗口/metadata 装载提升为跨版本复用，或把目标分析做成异步快照，再谈优化。
- **结论**：（留空）

### D2 趋势总和可能小于 summary.potential

- **位置**：`apps/api/app/service/overview/targets.py:394`、`:429`
- **现象**：trend 对 analyzed 行用 `attribution.created_at` 落桶，窗口按 case `created_at` 筛选。若一条历史 case 在窗口结束后才被归因，它会计入 summary/detail 的 potential，但不落入任何 trend 桶。
- **问题**：前端若假设“趋势柱总和 = summary.potential”会看到差；`meta.bucketPolicy` 目前只是字符串说明，前端需要读它或接受差异。
- **预判**：这是“归因时间 vs 上报时间分开落桶”的必然结果，设计已明确要求；不要为了等式把归因时间夹到窗口边界，否则会谎报归因发生日。
- **结论**：（留空）

### D3 detail 原实现会计算所有对象，已改为只算请求对象（已修）

- **位置**：`apps/api/app/service/overview/targets.py:464`、`:471`
- **现象**：修复前 `detail` 调 `_analyses(workspace_id, query.window, ())`，先分析全部启用对象再按 id 找目标；对一个对象的详情卡来说，其他对象的 matcher 开销和潜在异常都白付。
- **问题**：详情页性能和行为隔离都不对；其他对象的数据异常不应影响当前对象。
- **预判**：把 target 过滤提前到 `_analyses`，是局部、无契约变化的安全修复。
- **结论**：已在 `c142f5d` 修复为 `_analyses(..., (target_id,))`；目标测试通过。

### D4 版本顺序用自然版本降序，而不是“最近出现时间”

- **位置**：`apps/api/app/service/overview/targets.py:281`、`target_schemas.py:52`
- **现象**：`_ordered_versions` 用数字分段自然排序；`v2.0.0-rc1` 这类预发布标签会排在 `v2.0.0` 之前，且与“最近 N 个版本”的日常语义不完全一致。
- **问题**：如果产品把 `versionLimit` 理解为“最近活跃的 N 个版本”，自然排序会选错；如果理解为“最高的 N 个版本”，当前行为正确。
- **预判**：首版按“最高版本”解释并在字段描述里写明“descending natural version”，比引入 semver 依赖或额外记录时间更简单；若前端需要“最近活跃”，再按事件时间排序。
- **结论**：（留空）

### D5 窗口 case 谓词在 overview repository 与 matcher repository 各有一份

- **位置**：`apps/api/app/db/crud/overview_targets.py:77`、`apps/api/app/db/crud/potential.py:130`
- **现象**：两处都写 `workspace_id + created_at 半开窗口 + bad_case_type IN ('self','discovery')`；本 PR 的新查询只多了 title 投影。
- **问题**：谓词漂移会让 target 视图的 case facts 与 matcher 的 case 集合不一致。
- **预判**：这是两个不同投影（一个带 title、一个给 matcher），共享底层 SQL 需要把 title 加进 matcher 的 dataclass，跨 issue 改动；当前谓词很稳定，先保留并在 Note 里记录。
- **结论**：（留空）

### D6 新增服务单测覆盖率 97%，总体 91%

- **位置**：`apps/api/tests/m11-03-target-overview/test_target_overview_units.py:82`
- **现象**：`coverage` 报告 `app/service/overview/targets.py` 97%，只剩少量错误分支；总体 91% 满足门禁。
- **问题**：单模块覆盖率偏低，未来改分桶/排序时回归保护弱。
- **预判**：新增的解析、版本归一、状态投影、属性单测覆盖了最容易漂移的纯函数；matcher 分支已被 matcher 自己的测试覆盖。若维护者要求单模块阈值，再补 trend 边界与空目标用例。
- **结论**：（留空）
