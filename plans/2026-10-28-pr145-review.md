## §1 一页速览

**一句话**：给“卡住的自进化 run”装了一只闹钟和一个手动开关——瞬时推送故障按 1/5/15 分钟自己再试，评测与补丁故障只等人点按钮，重启后只认数据库里的到期时间，页面靠 SSE + 轮询把“第几次、几点再试”如实显示出来。

**一个比喻**：这套机制像病房里的**候诊叫号**。`evolution_runs.retry_attempts`/`next_retry_at` 是贴在墙上的号票（唯一可信），`blocked_sweeper` 是每 30 秒巡一次墙的护士（只看号票，不记得上次叫过谁），`evolution_retry` job 是叫号广播（同一 run 只挂一个，重复按铃会被合并），`EvolutionRetryService` 是进诊室后的分诊台（按“你卡在哪一步 + 你手上已有的检查单”决定下一步，而不是从头再查一遍）。进程重启相当于换班：上一班的未完成动作作废（标 interrupted），但墙上的号票继续有效。

## §2 架构导览

### 2.1 状态事实只有一个家：`evolution_runs` 三列

退避语义完全落在 `blocked_stage`（patch/push/eval）、`retry_attempts`（已用掉几次自动重试）、`next_retry_at`（下次自动尝试的绝对时刻）上（列定义在 base 已有，本 PR 未加迁移）。这条约束决定了后面所有设计：sweeper 不需要内存状态、重启不需要重建计时器、前端刷新后拿到的一定是当前事实。

- `mark_blocked` 每次写 `status=blocked` + 阶段 + 错误 + `next_retry_at`（`crud/evolution.py:151-186`）；`retry_attempts` 传 `None` 时保持原值，于是“谁负责计数”变得很关键——本 PR 统一为“自动重试执行前 +1”（`crud/evolution.py:205-219`）。
- `mark_resumed` 清 blocked 并 **把 `next_retry_at` 置空**（`crud/evolution.py:188-203`）。这就是“恢复动作一开始就不再排队”的开关。

### 2.2 退避阶梯是纯函数，边界被显式拒绝

`next_retry_delay(attempts)`：`0→1min、1→5min、2→15min、≥3→None`（`backoff.py:11-24`）。三处刻意设计：

1. `MAX_RETRY_ATTEMPTS = len(RETRY_BACKOFF_MINUTES)`（`backoff.py:8`），阶梯与封顶同一个常量，改表就改上限。
2. 拒绝 `bool`（Python 里 `True` 是 `int`）与负数（`backoff.py:18-21`），防止损坏的计数“发明”出一个排期。
3. 绝对值换算 `next_retry_at(now, attempts)`（`backoff.py:27-30`）把“相对延迟”和“落库时刻”分开，调用方必须显式给 `now`，测试因此可注入固定时钟。

**语义要点**：`attempts` 的含义是“已经完成过几次自动重试”，不是“即将做第几次”。所以首次 block 写 `attempts=0, next=now+1min`（`git_candidate.py:315`），第 1 次自动重试失败后写 `attempts=1, next=now+5min`（`retry.py:186-189` + `_with_backoff`）。

### 2.3 sweeper 只做一件事：把“到期的号票”变成一个 job

`EvolutionBlockedSweeper.run_forever`（`blocked_sweeper.py:81-94`）循环体只有 `run_once()` 与可中断等待；异常被 `logger.exception` 吞掉但循环继续（`blocked_sweeper.py:86-87`），这是它能长期存活的关键。`run_once`（`96-107`）查一批到期 run，逐个 `_schedule_retry`：

- 只投 `evolution_retry`，`payload={"runId", "automatic": True}`，`ref_id=run.id`（`blocked_sweeper.py:112-117`）；
- `RUN_BUSY` 静默跳过并返回 False（`118-120`），因为下一轮扫描还会再来；
- `reused=True` 也算“没新增”（`132`），于是同一 run 不会因两轮扫描堆两个 job。

**stage 过滤在数据库层**：`list_blocked_due` 的 where 里写死 `blocked_stage == "push"`（`crud/evolution.py:253`，整段条件 `250-262`），不是靠 sweeper 过滤。这一点常被误读为“sweeper 管所有阶段”，其实 eval/patch 的 blocked 永远不在候选集里——Note 的描述（`2026-10-28-evolution-recovery.md:13`）与代码一致。

### 2.4 retry 是一个“分诊台”，不是“重跑器”

`EvolutionRetryService.handle`（`retry.py:164-233`）的骨架值得单独记：

```
读 run → 不是 blocked 就直接返回（165-177）
automatic 且 stage != push → 直接返回（179-185，双保险）
automatic → attempts+1 并落库（186-189）
eval → 先清空失败轮次的 external id（194-202）
_resume：先写 run.resumed + mark_resumed（203）
按现场事实分发（207-218）
任何 RunBlocked/异常 → _with_backoff 补上退避事实后抛给 JobRunner（219-226）
```

“先恢复状态再执行动作”的顺序是有意的：`write_final`/`_apply` 都要求 `run.status=running`（见 `apply_final.py:84`），所以必须先 `mark_resumed`；反过来说，动作失败后必须重新写回 blocked，这一棒由 JobRunner 的 `RunBlocked` 分支接住（`jobs.py:240-256`）。

分发判据（`retry.py:235-261`）不是阶段名，而是**耐久事实的优先级**：

| 现场事实 | 动作 | 锚点 |
|---|---|---|
| 已有 `evolution_finals` | 继续 finalize（不重跑迭代） | `247-249` |
| 有 `evaluating/deciding` 且 `eval_result` 已落库 | 交给 apply（不重复评测） | `250-252` → `403-411` |
| 有活动轮次且状态 `pushing/evaluating` | 只重推已持久化 candidate 并补交评测 | `253-256` → `285-301` |
| 有活动轮次且其它非终态 | 重新生成 patch（走标准 publish） | `257` → `303-322` |
| 无活动轮次但仍有 pending | 排 `evolution_advance` | `366-401` |
| 所有轮次终态 | 排 `evolution_finalize` | `377-378` |

### 2.5 失败分类：`retryable` 是唯一进入自动阶梯的闸门

`GitOperationError.retryable` 由 transient markers 判定（`third_party_api/git/workspace.py:1077-1078`，markers 在 `121-130`），`classify_git_failure` 只决定是“blocked 还是 failed”、以及 blocked 落在哪个阶段（`git_failures.py:23-41`）。本 PR 把 `retryable` 一路带进 `RunBlocked`（`engine/contracts.py:31-48`），于是三处调用点能各自决定要不要排期：

- 候选推送失败：`next_retry_at = now+1min if retryable else None`（`git_candidate.py:315-321`）；
- 通用 git 失败：只有 `blocked_stage == "push"` 且 `error.retryable` 才排期（`git_candidate.py:632-640`）；
- finalize 的 write_final 失败被判定为永久（`apply_final.py:214-226` 传 `retryable=False`），分支推送失败按 `exc.retryable`（`238`）。

`_with_backoff`（`retry.py:480-485`）是最后一层兜底：`exc.retryable and exc.stage == "push"` 才算延迟，且 `retry_attempts = max(attempts, exc.retry_attempts)` 保证计数只增不减。

### 2.6 幂等：三个不同层次的去重

1. **队列层**：`JobRunner.submit` 对 `_REUSABLE_DUPLICATE_KINDS`（含 `evolution_retry`，base 已有 `jobs.py:29`）按 `(kind, ref_id)` 复用活动 job，返回 `reused=True`（`jobs.py:135-138`），API 直接把它翻译成 202（`retry.py:159-162`）。
2. **状态层**：`mark_round_pushing` 要求 `status ∈ {patching,pushing}` 且 candidate 已存在（`crud/evolution.py:855-869`）；`mark_round_push_succeeded` 要求 `status=pushing` 且 rowcount=1（`872-905`）；`accept`/`reject` 对已决策轮次直接早返回（`git_candidate.py:461-462`、`541-542`），apply 服务同样早返回（`apply_final.py:76-83`）。
3. **git 层**：`push_candidate` 先比较远端 tag 指向，若已等于本次 commit 直接返回（`workspace.py:353-359`）——“推成功但没来得及写库”的重放不会变成冲突；`create_candidate` 会先删同名本地分支再重建（`workspace.py:285-301`），patch 阶段重复重生成不会撞名。

### 2.7 SSE：本 PR 没有改协议，只改了“喂给协议的事实”

`record_blocked`/`record_resumed` 在 base 就已带 `blockedStage/retryAttempts/nextRetryAt/message` 与 `stage/retryAttempts`（`events.py:380-473`；`git show 888c93f:...events.py` 对照确认两处均存在），订阅面也早已限定 `preparing/running`（`events.py:93`）。本 PR 的实际贡献是：让 `RunBlocked` 第一次真的带上了 `next_retry_at/retry_attempts`，于是事件与 REST 快照不再出现“有阶段没时间”的空洞；前端第一次真的用上了这条通道。

## §3 数据流走查

主线剧本：一次瞬时推送故障 → 自动恢复 → 前端如实显示。锚点全部来自实际阅读。

1. **失败发生**。`EvolutionCandidateService.publish` 的 `attempt_push` 经 `retry_push` 试满 `push_attempts` 后仍失败（`git_candidate.py:255-293`），进入 `except GitOperationError`：写 `push_failed` 事件（`301-314`）、算 `retry_at`（`315`）、`mark_blocked(stage="push", retry_attempts=0)`（`316-322`）、抛 `RunBlocked("candidate push failed", stage="push", next_retry_at=retry_at, retryable=exc.retryable)`（`323-329`）。

## §6 讨论点

### 6-1 JSON `None` 修好了新写入，但旧行没有回填

**位置**：`apps/api/app/db/crud/evolution.py:1588-1590`（`_nullable_json`）、`679`、`695`、`1069`、`1350`；受影响的判据是 `crud/evolution.py:1257`（`eval_result.is_(None)`）与 `1155`（`is_not(None)`）。

**现象**：base 版本用 `deepcopy(round_.get("eval_result"))` 与 `eval_result=None` 写 JSON 列；SQLAlchemy `JSON` 默认 `none_as_null=False`，Python `None` 会落成文本 `'null'` 而不是 SQL NULL。本次实测（临时 SQLite，走真实 `EvolutionRepository`）：

```
raw: [('old', "'null'", 0), ('new', 'NULL', 1)]      # 旧写法 / 新写法
save eval_result (stored 'null'): False              # 守卫 eval_result IS NULL 不命中
save eval_result (stored NULL)  : True
```

于是 base 版本里 `save_eval_result` 永远返回 False，`eval_poller._poll_round` 返回 False（`eval_poller.py:399-400`），轮次停在 `evaluating`、`eval_next_poll_at` 仍是过去时间 → `list_eval_due` 每 30 秒再取一次、每次重试同样失败。PR 描述把这条列为“latent bug fixed，被真实闭环冒烟暴露”，修复对**新写入**是完整的（`insert_rounds` 的 `patch`/`eval_result`、`mark_eval_submitted` 的清零、`reset_round_for_eval_retry` 的清零），`_nullable_json` 在 executemany 下也实测可用（`insert(evolution_rounds), values`，`737`）。

**问题**：修复没有覆盖**已存在的行**。任何在升级前创建、且当时 `eval_result` 写成 `'null'` 的轮次，升级后仍然命中不了 `IS NULL` 守卫，会继续无限轮询；`list_eval_followups` 的 `is_not(None)` 在旧行上反而是 TRUE（`'null'` 非 NULL），但它的 `eval_status='completed'` 条件不成立，所以不会误发 apply——症状是“卡住”，不是“做错”。仓库已有数据迁移先例（`apps/api/alembic/versions/0007_evolution_target_history.py:41` 直接 `op.execute`）。

**预判**：要修，但属于“升级路径”而非“功能正确性”。两种收法：① 加一条迁移把历史 `'null'` 归零（SQLite/MySQL 各一句，`WHERE eval_result = 'null'` 或 JSON 类型判空）；② 把判据放宽成“NULL 或 JSON null”。①更干净且与既有迁移风格一致；②会把 SQL 谓词复杂化并扩散到两处。建议在本 PR 内补①（含一条断言语义化 NULL 的回归测试），或明确记进 follow-up issue 再合。另：这条修复目前**没有进 owning Note**（`2026-10-28-evolution-recovery.md` 全文未提），按“每个非平凡变更至少一条 Note”的规则，建议在 Note 的 Consequences 补一句，或另开 `bug-fix` Note。

**结论**：已修（2026-10-28）。新增 `apps/api/alembic/versions/0009_eval_result_null_backfill.py`：MySQL 走 `WHERE JSON_TYPE(eval_result) = 'NULL'`，SQLite/其它走 `WHERE eval_result = 'null'`，downgrade 写 no-op 并注明数据修复不可逆；`test_database.py` 两处 alembic head 断言改 `0009`；`test_full_placeholder_loop.py` 补 SQL 级断言（真实 `insert_rounds` 后 `eval_result IS NULL` 为真，`435-436`）与一条真实迁移用例（旧文本 `'null'` 经 `0009` upgrade 归零、真实 JSON 结果不被误改，`672-712`）；Note 的 Consequences 补一句并重录 i18n。锚点：`apps/api/alembic/versions/0009_eval_result_null_backfill.py:16`、`apps/api/tests/test_database.py:494`、`apps/api/tests/test_database.py:761`、`apps/api/tests/m5-11-evolution-recovery/test_full_placeholder_loop.py:672`。

### 6-2 前端「已提交重试」不会回收：一次快速失败会把按钮永久禁用

**位置**：`apps/web/src/pages/evolution/RunDetail.vue:54`、`76-81`（watch）、`262-278`（`retryBlockedRun`）、`367-371`（按钮 `:disabled`）。

**现象**：点击重试成功后 `retryAccepted=true`，按钮变成“已提交重试”并禁用；只有 `run.status` **变化且不等于 blocked** 时才清回（`76-81`）。但 blocked 页面的快照是 5 秒轮询（`useEvolutionRunDetail.ts:38-40`），而 retry job 的“running 窗口”可能远短于 5 秒（eval 重提是纯 DB 操作）：`mark_resumed` 写 running → 评测重提失败 → 又写回 blocked，轮询一次都没采到 running。状态始终是 `blocked → blocked`，watch 不触发，按钮保持禁用、banner 持续显示“重试任务已受理，等待运行推进”，而 `nextRetryAt`/`retryAttempts` 已经更新——用户看到“已受理”却无法再点，只能刷新页面。

**问题**：这是“受理态”与“事实态”的耦合错误。`retryAccepted` 应该表达“这一个 job 还在途”，而现在它只靠一个粗粒度的状态跃迁来回收。

**预判**：建议在本 PR 内修，成本很小，且不改契约：可以在轮询拿到**新快照**时（`watch(run, …)`，或直接 `watch(() => run.value?.error?.at)` / `nextRetryAt`）把 `retryAccepted` 清回；也可以给它加一个与轮询周期同量级的自动回收（例如 10 秒）。前者更“以 REST 快照为准”，与 Note 的表述一致（`2026-10-28-evolution-recovery.md:21`：blocked 页展示的阶段/次数/时间以 REST 为准）。

**结论**：已修（2026-10-28）。`RunDetail.vue` 在受理成功的首个 REST 快照上记录 `error.at`/`nextRetryAt` 作为基准（`retryAcceptedFacts`，从 query cache 读，避开 observer 批次延迟），watch 同时盯状态与这两个字段：非 blocked 或无变化的 blocked 快照保持受理态，一旦事实不同立即回收；另加 10 秒兜底定时器，组件卸载与状态变化时清理。文案改为 `运行在{{ blockedStageLabel }}阻塞`，已知阶段自带“阶段”后缀，默认“未知阶段”不再拼出“未知阶段阶段”。新增 2 条组件测试：`RunDetail.test.ts:746`（10 秒兜底恢复为“重试”可用）、`RunDetail.test.ts:792`（新 blocked 快照事实不同即回收），既有 202/409/404 用例保持通过。锚点：`apps/web/src/pages/evolution/RunDetail.vue:56`、`RunDetail.vue:89`、`RunDetail.vue:187`、`RunDetail.vue:399`。

### 6-3 退避事实在“内层服务”会写一次 0/1 分钟，靠外层覆盖纠正

**位置**：`apps/api/app/service/evolution/git_candidate.py:504-509`（`accept` 调用 `_handle_git_failure` 未传 `retry_attempts`）→ `619-651` 以默认 `retry_attempts=0` 写 `mark_blocked`；纠正发生在 `retry.py:219-226` 与 `jobs.py:240-256`。同类现象也在 `apply_final.py:206-226`（最终以 `_job_retry_attempts(job)` 传入的值为准）。

**现象**：自动重试进入 `_apply → candidates.accept` 时，若 amend/fast-forward 的 push 失败，内层 `_handle_git_failure` 会先用 `retry_attempts=0, next_retry_at=now+1min` 写一次 blocked，随即被 `_with_backoff(attempts=2)` 与 JobRunner 的 `record_blocked` 覆盖成正确值。最终事实正确，但中间存在一个毫秒级的错误窗口；如果进程恰好在这个窗口内崩溃，落库的就是“计数归零 + 1 分钟后重试”，阶梯被重置。

**问题**：分层责任不清——`accept` 不知道自己处在恢复链路里。另一种表现是 `_dispatch` 的 `pushing/evaluating` 分支（`retry.py:253-256`）理论上会把 `evaluating` 轮次交给 `repush_existing`，而 `mark_round_pushing` 只接受 `patching/pushing`（`crud/evolution.py:855-869`），最终会在 `mark_round_push_succeeded` 抛 409，被 `retry.py:221-226` 转成永久 blocked。按现场事实推演这条路走不到（`evaluating` 意味着 push 已成功），但它是“关不上”的。

**预判**：可以不修，但值得记录取舍。若要修，最小改动是给 `apply`/`_handle_git_failure` 一条显式的 attempts 传递（`apply` job payload 已带 `retryAttempts`，见 `retry.py:332-341`，`accept` 只需透传），并把 `_dispatch` 的 `evaluating` 分支改成“回退到 `_apply` 或 `_schedule_next`”，避免走到必然 409 的路径。建议归入本 PR 的后续清理，或下一个恢复相关切片；不值得为毫秒级窗口单独发版。

**结论**：已修（2026-10-28）。`accept` 新增 `retry_attempts` 关键字参数并原样传给 `_handle_git_failure`，`EvolutionApplyService.handle` 用 `_job_retry_attempts(job)` 注入，于是 accept 的 fast-forward 失败落库时就是正确档位，不再依赖外层 `_with_backoff`/JobRunner 覆盖那个毫秒级窗口；新增用例直接跑真实 apply 服务，断言失败后 `retry_attempts=2`、`next_retry_at=now+15min`（`test_retry_dispatch.py:777`）。同段的 `_dispatch` 的 `evaluating → repush_existing` 分支**不修**：按耐久事实推演不可达（`evaluating` 意味着 push 已成功），改动会牵动分发优先级，记录为已知不可达路径留后续切片。锚点：`apps/api/app/service/evolution/git_candidate.py:449`、`git_candidate.py:504`、`apps/api/app/service/evolution/apply_final.py:98`。

### 6-4 关键幂等路径用替身覆盖，真实 apply/finalize 的“重入”没有被测到

**位置**：`apps/api/tests/m5-11-evolution-recovery/test_retry_dispatch.py:402-408`（finalize 用 `RecordingStage`）、`426-432`（apply 用 `RecordingStage`）、`512-517`/`538-543`（candidate 用桩）。

**现象**：分发决策（“该走 apply 还是 finalize”）测得很好，但被分发的真实服务没有被组合进恢复路径测。于是以下三条声明缺乏证据：① 重复 `apply`（例如 accept 成功后进程崩溃、再次 retry）不会二次 push／二次写 final；② 重复 `finalize`（final 已存在）不会重写 final；③ `write_final` 要求 `status=running`，所以 `_resume` 必须先行——目前只有 `retry.py:203` 的顺序能保证，没有任何测试会在顺序被改动时报警。真实闭环冒烟（`test_full_placeholder_loop.py`）覆盖了正常闭环，但没有“恢复重入”的变体。

**问题**：这是“测试真实性与盲点”里最值得补的一块，而且补起来不贵——把 `EvolutionApplyService`/`EvolutionFinalizeService` 接进 dispatch 测试，让同一个 `handle` 跑两次并断言 `evolution_finals` 只有一行、candidate 只 push 一次。

**预判**：建议在本 PR 内补 1 条“apply 重入幂等”用例（最高价值）与 1 条“`retry.handle` 先 mark_resumed 再分发”的顺序断言；`JobRunner` 的真重放测试可留待后续。注：手动/自动并发（`reset_manual_retry` 与 sweeper 同拍）也只是靠 `submit` 的锁推断，没有并发用例——但这条更接近“已由 JobRunner 单写者串行化保证”，可只在 Note 记一句。

**结论**：已修（2026-10-28），补了最有价值的两条。① 真实 apply 重入：`test_full_placeholder_loop.py:564` 在真实 accept 之后用同一个 `evolution_apply` job 重放，断言 `applied=False`、`status=accepted`、`commit_hash`/`progress_unit` 不变、candidate tag 仍被清理，且事件序列里 `cluster_accepted` 仍只有一条（`test_full_placeholder_loop.py:659`）。② 顺序：`test_retry_dispatch.py:734` 在 apply 阶段入口读 run 与事件表，断言 `status=running`、`blocked_stage=None`、已有 1 条 `run_resumed`——即 `_resume` 必然先于分发，顺序被改动时该用例会红。仍未覆盖、保留为后续：真实 `finalize` 重放、`JobRunner` 真重放、手动/自动并发。

### 6-5 `evolution_retry` 被中断时，事件阶段记成 `step`

**位置**：`apps/api/app/service/jobs.py:31-37`（`_KIND_TO_STAGE["evolution_retry"] = "step"`，base 已有，本 PR 未改）；计划 Task 3 把“确保 evolution_retry 的 interrupted 记录 stage 正确”列为待办且未勾选。

**现象**：一个 push 重试 job 在重启时被打断，`run_interrupted` 事件与 `evolution_runs.error_stage` 都写 `step`（`test_process_recovery.py:173` 断言的正是 `"step"`），而这次中断真实发生在 push 阶段。页面中断 banner 只显示“任务被中断，可查看最后事件”（`RunDetail.vue:394-396`），用户无法从 run 上看出中断前卡在哪个阶段。

**问题**：不是错误，是信息损失；且是计划里明确列出却未落地的项。要修的话，静态映射满足不了（retry 可能是 patch/push/eval），正确做法是在写 interruption 时读 run 的 `blocked_stage`（JobRunner 已有 `ref_id` 与 run_events 依赖）。

**预判**：可不在本 PR 修，但应把计划里的这条待办改成“记录为已知取舍”，否则计划与实现会长期不一致（计划另有多处 `- [ ]` 未勾）。如果维护者希望中断信息完整，一行改动是把 `_KIND_TO_STAGE` 的 `evolution_retry` 改成 `"push"` 是**错的**，不要这么做。

**结论**：不修（2026-10-28）。`_KIND_TO_STAGE["evolution_retry"] = "step"` 是 base 行为，本 PR 不动；retry 可能发生在 patch/push/eval 任一阶段，静态映射无法表达真实阶段，正确修法要在写 interruption 时读 run 的 `blocked_stage`，属于 JobRunner 的独立改动，超出本 PR 范围。按“现状偏差”保留，计划里标注为已知取舍；**不要**把它改成 `"push"`（那会给出错误事实）。锚点：`apps/api/app/service/jobs.py:32`、`apps/api/tests/m5-11-evolution-recovery/test_process_recovery.py:173`。

### 6-6 本轮明确保持现状的三处取舍

- **多实例 sweeper 会重复入队**：`EvolutionBlockedSweeper` 是进程内循环，V1 明确以单进程为前提；跨实例单飞要等 JobRunner 支持 `SKIP LOCKED`，本 PR 不引入分布式锁（`blocked_sweeper.py:81-107`、Note 的 Consequences 已记）。
- **`finalize` 的 `write_final` 外层是 `except Exception`**：一次数据库抖动会被判成“永久、不排期”。写 final 是幂等 upsert、失败后仍可手动重试，自动重试次数不该被非网络原因吃掉；收紧成“业务异常永久、其余可重试”要先区分异常类型，留后续（`apply_final.py:206-226`）。
- **`_dispatch` 的 `evaluating → repush_existing` 分支**：按耐久事实不可达（`evaluating` 意味着 push 已成功），真的走到只会在 `mark_round_push_succeeded` 抛 409 再被转成永久 blocked；改动会牵动分发优先级，留后续切片（`retry.py:253-256`、`crud/evolution.py:855-869`）。

## §9 文件级代码分析

### 9.1 `apps/api/app/service/evolution/backoff.py`（A）

**职责**：把 1/5/15 分钟阶梯做成无副作用的整数→延迟映射，供 sweeper 与 retry 共用。**变更形态**：新文件，38 行，无第三方依赖（只用 `datetime`）——这是刻意的“零依赖叶子”，所以它能在纯函数测试里被钉死（`test_backoff_sweeper.py:141-165`），也能被两个调用方同时引用而不形成环。

**变更块**：整文件即变更。三处写法值得说明为什么：

```python
RETRY_BACKOFF_MINUTES: tuple[int, ...] = (1, 5, 15)
MAX_RETRY_ATTEMPTS: int = len(RETRY_BACKOFF_MINUTES)   # 上限与阶梯同源

if isinstance(attempts, bool) or not isinstance(attempts, int):
    raise TypeError("retry attempts must be an integer")
if attempts < 0:
    raise ValueError("retry attempts must not be negative")
if attempts >= MAX_RETRY_ATTEMPTS:
    return None
```

第一块让“封顶 3 次”不可能与阶梯脱钩；第二块把 `bool` 单独拎出来，是因为 `isinstance(True, int) is True`，若不挡，损坏的计数会被当成 1 并给出 5 分钟排期；第三块返回 `None` 而不是抛异常，使“用尽”成为正常返回值而不是错误路径。`next_retry_at` 只做“基准时刻 + 延迟”的换算，把 `now` 变成必填参数，避免隐式调用系统时钟。

**实现思路总结**：阶梯是数据，上限由数据推导，非法输入拒绝而非钳制，绝对时间由调用方给基准。

**检视发现**：无缺陷。唯一可讨论点是 `next_retry_at` 与 `backoff.next_retry_at` 名字重复（`git_candidate.py:315` 等处局部变量同名），阅读时有轻微歧义，不影响行为。

### 9.2 `apps/api/app/service/evolution/blocked_sweeper.py`（A）

**职责**：进程内的 30 秒扫描循环，把“到期且未超限的 push blocked run”变成一个 `evolution_retry` job。**变更形态**：新文件，135 行。依赖 `EvolutionRepository.list_blocked_due`、一个 4 参数 `submit` 协议与 `now_shanghai`。比喻：只巡墙、不记人的护士——所有记忆都在数据库。

**变更块一：循环的存活策略**

```python
while not self._stop.is_set():
    try:
        await self.run_once()
    except Exception:
        logger.exception("blocked sweeper scan failed")
    try:
        await asyncio.wait_for(self._stop.wait(), timeout=self._scan_interval_seconds)
    except TimeoutError:
        continue
```

先扫后等、异常只记日志、用 `wait_for` 让 stop 立即生效而不是睡满 30 秒——这三点合起来才使它“既能长期活、又能优雅停”。`test_sweeper_survives_a_failing_scan`（`test_backoff_sweeper.py:246-267`）正是钉这条。

**变更块二：入队与去重的三种结果**

```python
except AppError as exc:
    if exc.code == ErrorCode.RUN_BUSY:
        return False
    ...                    # 其它 AppError 记日志后 False
return not bool(getattr(submission, "reused", False))
```

`RUN_BUSY` 静默、其它错误记日志、`reused` 不计入“新入队”。用 `getattr(..., False)` 而不是要求协议里必须有 `reused`，让 fake 队列能只实现 `id`——这在 `test_backoff_sweeper.py` 的 `JobCapture` 与 `test_process_recovery.py` 的同名替身上都能看到。

**实现思路总结**：循环体只承担“扫描 + 入队”，异常不逃逸，去重依赖队列与 `reused` 两个既有语义。

**检视发现**：

1. `RetryJobSubmitter` 协议在本文件（`19-30`）与 `retry.py:41-52` 里各定义了一次，字段完全一致；`sweeper` 版本返回值写成 `object`，`retry` 版本写成 `JobSubmissionView`。属于可合并的重复（一行 import 即可），无实害。
2. `list_blocked_due` 的 `max_attempts=MAX_RETRY_ATTEMPTS`（`98-102`）把“封顶”同时写进了 SQL 与 Python 阶梯，二者必须一致；因为同源（`backoff.py:8`），这一点是安全的。
3. 观察：sweeper 没有“本轮已尝试过这个 run”的内存去重，靠的是 `next_retry_at` 在失败时被推后、成功时被清空。这是正确的最小设计，但也意味着**如果 retry job 执行后没有写回任何一种状态**（例如 handler 提前 return 且未改 run），下一轮会立刻再入队。当前所有 return 分支都不会留下“到期但状态未变”的组合（`retry.py:171-185` 的早返回要求 run 已不是 blocked），因此无实害。

### 9.3 `apps/api/app/service/evolution/retry.py`（A）

**职责**：恢复链的分诊台——手动受理（`request_retry`）+ 自动/手动共用的执行分发（`handle`）+ 退避事实兜底（`_with_backoff`）。**变更形态**：新文件 491 行，依赖 `EvolutionRepository`、`EvolutionCandidateService`、`EvolutionRunEventService`、可选的 apply/finalize/advance/eval-submitter/probes（测试可只注入用到的部分）。

**关键依赖解读**：`JobRunRecord` 是本文件与 JobRunner 之间的唯一数据面——`handle` 从 `job.ref_id`/`job.payload` 取 runId 与 `automatic`，并用 `dataclasses.replace` 伪造下游 job 的 payload（`332-341`、`355-363`），从而在不改下游签名的前提下把 `retryAttempts` 传进 apply/finalize。比喻：分诊台在转诊单上补写“这是第几次复诊”，诊室不用知道病人怎么来的。

**变更块一：先清 blocked，再分发**

```python
await self._resume(run.id, stage=event_stage, job_id=job.id)
refreshed = await self._runs.get_run(run.id)
if refreshed is not None:
    run = refreshed
```

顺序是硬约束：`mark_resumed` 把 `next_retry_at` 清空（`crud/evolution.py:195-202`），既保证扫描不再命中，也满足下游 `write_final`/apply 的“必须 running”前置。重新 `get_run` 是为了拿到 `retry_attempts` 的最新值——自动重试在 `186-189` 先 +1，若不刷新，后面 `_republish_push` 传下去的计数会是旧值。

**变更块二：分发按耐久事实而不是阶段名**

```python
final = await self._runs.get_final(run.id)
if final is not None: return await self._finalize(run, job)
evaluated = await self._undecided_evaluated_round(run.id)
if evaluated is not None: return await self._apply(run, evaluated, job)
active = await self._active_round(run.id)
if active is not None:
    if active.status in {"pushing", "evaluating"}: return await self._republish_push(...)
    return await self._regenerate_round(...)
```

这是本 PR 最值得保留的设计：恢复动作的判据是“磁盘/库里已经有什么”，因此**不需要在阻塞时把恢复计划序列化下来**，也不怕计划与现场漂移。代价是每个分支都必须自己保证不重复副作用，于是有了 `repush_existing` 的单次推送与 apply/finalize 的早返回。

**变更块三：退避事实的最后一道闸**

```python
delay = next_retry_delay(attempts) if exc.retryable and exc.stage == "push" else None
exc.next_retry_at = None if delay is None else self._now() + delay
exc.retry_attempts = max(attempts, exc.retry_attempts)
```

三重限定的意义：非 push 阶段一律不排期（eval/patch 只手动）、非瞬时错误一律不排期（永久错误交人）、计数只增不减（内层服务写下的 0 覆盖不了外层已知的 2）。`max(...)` 正是对 §6-3 那个“内层写 0”的兜底。

**实现思路总结**：先恢复状态再动作、按现场事实选一个动作、退避事实在离开服务前统一裁决。

**检视发现**：

1. `__init__` 接收 `prepare`（`113`、`126`）但全文件没有使用；`_schedule_next` 走的是 `jobs.submit("evolution_prepare")`（`374`）。`main.py:245` 仍在注入 → 死参数，建议删除（§7）。
2. `now: Any = now_shanghai`（`117`）与 `blocked_sweeper.py:41` 的 `Callable[[], datetime]` 相比丢了类型；mypy 能过是因为 `Any`。建议统一为 `Callable[[], datetime]`。
3. `_BLOCKED_STAGE_TO_EVENT_STAGE`（`33-37`）与 `jobs.py:38-42` 同表重复；两处必须同步，属可合并的重复。
4. `_failed_eval_round` 只找 `status=evaluating` 且 `eval_status ∈ {failed,timeout}` 的轮次（`413-421`）。`mark_eval_failed` 同时把 run 置 blocked（`crud/evolution.py:1312-1325`），轮次状态仍是 `evaluating`，因此一致；但若未来有人在 blocked 后改写轮次状态，这条恢复会退化成 `RuntimeError("blocked evaluation round not found")` → 永久 blocked（`196-197`、`221-226`）。记录为脆弱点，非缺陷。
5. `request_retry` 先 `reset_manual_retry` 再 `submit`（`152-158`）：若 `submit` 抛 `RUN_BUSY`，接口返回 409 而计数已被清零。改动成本极低（把 reset 移到 submit 成功之后，或先查 `find_active`），但触发条件罕见（blocked run 上存在另一类活动 job），归入清理。

### 9.4 `apps/api/app/db/crud/evolution.py`（M）

**职责**：所有 evolution 数据事实的唯一写入口。**变更形态**：+140/−3，四个新方法 + JSON NULL 修复。前身对照（`git show 888c93f:`）确认改动只在这几处，没有顺手改到无关语句。

**变更块一：自动计数的原子性边界**

```python
await session.execute(
    update(evolution_runs)
    .where(evolution_runs.c.id == run_id, evolution_runs.c.status == "blocked")
    .values(retry_attempts=evolution_runs.c.retry_attempts + 1),
)
```

`retry_attempts = retry_attempts + 1` 是数据库端自增，不是“读-改-写”，因此无需乐观锁；`status == "blocked"` 的条件把“已经恢复的 run”挡在外面（并发下手动/自动同时到时，只有仍在 blocked 的那次会计数）。缺点是没有返回 rowcount——0 行也会被当成成功并返回刷新后的 run；在“另一路已经把 run 推出 blocked”的场景下，`handle` 后续的 `run.status != "blocked"` 判定（`retry.py:171`）会在下一次读到时兜住，所以无实害。

**变更块二：到期查询把语义压进 SQL**

```python
.where(
    evolution_runs.c.status == "blocked",
    evolution_runs.c.blocked_stage == "push",
    evolution_runs.c.next_retry_at.is_not(None),
    evolution_runs.c.next_retry_at <= now,
    evolution_runs.c.retry_attempts < max_attempts,
)
.order_by(next_retry_at, created_at, id).limit(limit)
```

`blocked_stage == "push"` 写死在这里，是“自动退避只覆盖 push”的唯一强制点（§2.3）；`next_retry_at IS NOT NULL` 与 `<= now` 合起来就是“有号票且到点”；`limit` 与三级排序保证批量扫描确定性、便于测试。`max_attempts < 1` 与 `limit < 1` 提前抛 ValueError（`242-245`），避免“上限 0 导致永远不扫”的静默失效。

**变更块三：eval 重试的“一次性清零”**

```python
.where(
    evolution_rounds.c.id == round_id,
    evolution_rounds.c.run_id == run_id,
    evolution_rounds.c.status == "evaluating",
    evolution_rounds.c.push_status == "succeeded",
)
.values(status="evaluating", eval_status="pending", eval_external_id=None, ...)
```

**变更块四：JSON `None` → SQL NULL**

```python

+  "patch": _nullable_json(round_.get("patch")),
```

**检视发现**：

### 9.12 `apps/web/src/composables/useRunEvents.ts`（A）

**职责**：页面级 SSE 客户端：取 ticket（带游标）→ 开流 → 追加/失效 → 终态关闭 → 断线 3 秒重连 → `reset` 交回 REST。**变更形态**：新文件 234 行。依赖原生 `EventSource` 与 vue-query，全部通过 options 注入（`eventSource`/`requestTicket`/`setTimeoutFn`/`clearTimeoutFn`），所以测试不需要真网络（`useRunEvents.test.ts` 用 `FakeEventSource` + 手动 timer 队列）。

**变更块一：`generation` 世代号**

```ts
let generation = 0;
async function connect() {
  if (closed || !toValue(isActive) || source !== null) return;
  const attempt = ++generation;
  try { ticket = await requestTicket([`run:${runId}`], loadedSeq.value); }
  catch { scheduleReconnect(attempt); return; }
  if (closed || attempt !== generation || !toValue(isActive) || source !== null) return;
  ...
}
```

`generation` 解决“异步取票返回时状态已变”的竞态：取票期间页面被卸载、run 变终态或再次触发 watch，`attempt !== generation` 就让这次连接作废，避免旧票开出多余连接。这是把“取消”实现为“结果作废”，比 AbortController 更适配 `EventSource` 这种无取消语义的对象。比喻：取号后如果广播已经换了场次，这个号直接作废，不去检票口闹。

**变更块二：生命周期监听器的三档行为**

```ts
function registerLifecycle(target, type, callback, terminal) {
  target.addEventListener(type, (event) => {
    if (terminal) closed = true;
    closeSource();
    invalidateRun();
    callback?.(parseLifecycleNotice((event as MessageEvent).data));
  });
}
```

`run.blocked` 传 `terminal=false`：关流、失效、回调，但 `closed` 保持 false，于是状态从 blocked 回到 running 时 watch 还能重新订阅（`useRunEvents.test.ts:381-395` 的测试正是这个语义）；`completed/failed/interrupted` 传 true，永久关闭。

**变更块三：`reset` 与 `onerror` 的分工**

```ts
next.addEventListener("reset", (event) => { closeSource(); handlers.onReset?.(...); });
next.onerror = () => { closeSource(); if (closed || !toValue(isActive)) return; scheduleReconnect(generation); };
```

`reset` 是“服务端说游标无意义”，处理方式是交回 REST（`RunDetail.resetRunSnapshot` 清 liveEvents、`logResetToken++`、`refetchRun`），**不重连**；`onerror` 是“连接掉了”，3 秒后重新取票（新票带新游标）。`closeSource()` 在 `onerror` 里是必须的：它会抑制浏览器 `EventSource` 的原生自动重连（原生重连会复用已消费的一次性 ticket，必然 401 并形成无意义重试风暴）。

**实现思路总结**：一个流一个世代，票即授权、关即取消，blocked 半关闭、终态永久关闭、错误重连、reset 交回 REST。

**检视发现**：

1. `reset` 之后该页面不再有实时流，只能靠 15 秒轮询（`useEvolutionRunDetail.ts:41-45`）。这与设计样例一致（`08-frontend-implementation.md:209` 同样是「close + reload snapshot」，`05-api-design.md:913` 只要求重拉 REST），**不是缺陷**；写进 §7 作为已接受的取舍。
2. `RunLifecycleNotice` 没有 `onResumed` 回调；`run.resumed` 帧会被静默丢弃。因为 blocked 期间不订阅（`_ACTIVE_SSE_STATUSES` 排除 blocked，`events.py:93`），页面本来收不到 resumed，只能靠轮询发现 running——自洽，但若将来允许 blocked 页订阅，这里会成为缺口。
3. `handleEventMessage` 只做 `seq` 类型校验（`58-70`），不做 schema 校验；恶意/异常帧可能带着错误字段进入日志渲染。事件由自家后端产生，且 `EventList` 按字段读，风险低；记录为可接受。
4. `onUnmounted` 里 `closed = true` 且 `generation += 1`（`226-231`），保证卸载后迟到的取票不会开流；测试覆盖了“卸载取消重连”（`useRunEvents.test.ts:397-412`）。

```html
<button :disabled="isRetrying || retryAccepted" @click="retryBlockedRun">…</button>
```

四件事同时可见：阶段（patch/push/eval 中文化，`138-151`）、脱敏错误、已用次数、下次时间（或“已用尽”）。`nextRetryAt` 用 `v-if` 而不是“时间 + 已用尽”并列，避免永久错误（`nextRetryAt=null` 且 `attempts<3`）与“用尽”被混为一谈——永久错误时两者都不显示，只剩错误与按钮，语义正确。

**变更块三：中断态独立 banner**

```html
<div v-else-if="run.status === 'interrupted'" data-testid="interrupted-banner" role="status">
  <span class="blocked-title">任务被中断，可查看最后事件</span>
```

与设计 `08:552` 的文案一致，且**不提供重试**（interrupted 不是 blocked，`request_retry` 也会 409），避免给用户一个必然失败的按钮。E2E 只断言 blocked 的重试按钮，中断态由组件测试覆盖（`RunDetail.test.ts` 新增“explains an interrupted run without offering a retry”）。

**检视发现**：

1. **`retryAccepted` 不回收**（§6-2，`54`/`76-81`/`368`）：本文件唯一有实际用户影响的问题。
2. `retryErrorMessage`（`248-260`）按 `error.code` 分支覆盖 `RUN_NOT_RETRYABLE`/`RUN_NOT_FOUND`，其余落到通用文案；`RUN_BUSY` 没有专门文案（会显示“重试请求失败，请稍后再试”），可接受。
