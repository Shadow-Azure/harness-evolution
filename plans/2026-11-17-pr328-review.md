## §1 一页速览

**一句话**：把“真实上游轨迹接入”从只能 mock 的客户端契约，推进到有结构化健康/漂移信号、有真实 loopback HTTP 验收、并在拿到凭据时可以手动跑一次实联的生产化状态。

## §2 架构导览

### 2.1 出站客户端的分层：协议、实现、注入

`TrajectorySource` 是一份 Protocol，只声明 `fetch` / `list_window` / `fetch_many` / `close`（`apps/api/app/third_party_api/trajectory/source.py:13-31`）。真正的 HTTP 实现在 `HttpTrajectorySource`（`apps/api/app/third_party_api/trajectory/http.py:33-55`），它不自己创建客户端，而是接收一个 lifespan 拥有的 `httpx.AsyncClient`；这使测试可以换 transport，也保证真实 socket 的生命周期只有一个 owner。

生产装配在 `create_app`：当 `Settings.upstream_configured` 为真时创建 `AsyncClient`，把 `Authorization: Bearer {token}` 放在客户端默认 header 上（`apps/api/app/main.py:153-171`），再注入 `HttpTrajectorySource`；`upstream_configured` 同时要求 base URL 与 token 非空（`apps/api/app/config.py:232-240`）。因此凭据只出现在客户端 header，不进入本 PR 的任何日志字段。

### 2.2 日志分支：`event` + `extra` 的七条记录

本 PR 的日志写法统一是“消息给人看，字段给机器读”：消息是短句，所有可查询值放在 `extra` 的 `event` 与同名字段里。六类事件名、七条记录（`upstream.health` 在客户端与 pull 层各一条）及触发点：

| event | 级别 | 位置 | 字段 |
|---|---|---|---|
| `upstream.version_observed` | INFO | `http.py:248-252` | `api_version`（已过 `_VERSION_PATTERN`，只可能是 `major.minor`） |
| `upstream.version_drift` | WARNING | `http.py:234-242`、`:253-262` | `reason=missing/unparseable/incompatible/version_changed`；`expected_major` / `observed_major` 或 `previous_version` / `current_version` |
| `upstream.contract_drift` | WARNING | `http.py:319-329`（调用点 `:65-69`、`:219`、`:270-274`） | `model=package/window`、`reason=session_mismatch/schema_mismatch/invalid_json`、`error_count` |
| `upstream.request_retry` | INFO | `http.py:281-298` | `model`、`reason=timeout/transport/http_status`、`attempt`、`status_code` |
| `upstream.request_failed` | WARNING | `http.py:300-317` | `model`、`reason=http_status/retry_exhausted/timeout/transport`、`attempts`、`status_code` |
| `upstream.health`（客户端批次） | INFO | `http.py:148-157` | `status=ok/degraded`、`sessions_requested/fetched/isolated` |
| `upstream.health`（pull job） | INFO / WARNING | `upstream_pull.py:187-202` / `:127-138` | 成功：ok/degraded + `payloads_inserted/updated/unchanged`、`replayed`、`failed`、`duration_ms`；失败：`status=failed`、`sessions_requested`、`duration_ms`、`error_code` |

这套拆分是“客户端记录单次 HTTP 语义，pull job 记录批次结果”的两层结构。好处是客户端单元测试可以精确断言；代价是同一事件名在两层重复出现（§6 D7）。

### 2.3 版本状态机：观察一次、变化告警、不兼容批次失败

`_observed_version` 是 source 实例上的状态（`http.py:55`），只在响应头通过校验后更新（`:263`）。`_validate_version` 先分类：

- 没有 header → `reason=missing`，`observed_major=None`；
- header 形状不匹配 `major.minor`（如 `v1`）→ `reason=unparseable`；
- 形状匹配但 major 不是 1（如 `2.0`）→ `reason=incompatible`，`observed_major=2`；
- 以上都 raise `UPSTREAM_VERSION_INCOMPATIBLE`（`:243-247`），`fetch_many` 对它是整批 re-raise（`:121-126`），pull job 最终记失败健康。

通过校验后：第一次记 `version_observed`；之后值变化记 `version_changed` 但**不**失败（`:253-262`）。所以“同一进程内 1.0 → 1.1”是告警，“1.x → 2.0”是批次失败，两种语义不同。

### 2.4 失败分类与隔离矩阵

`_get_json` 把失败分成三类（`http.py:164-221`）：

1. **可重试**：429 或 5xx，最多 `max_retries` 次，指数退避；每次补试记 `request_retry`，用尽后记 `request_failed(reason=retry_exhausted)` 并抛 `UPSTREAM_REQUEST_FAILED`；
2. **不可重试的 4xx**：记 `request_failed(reason=http_status)` 后抛 `UPSTREAM_REQUEST_FAILED`；
3. **契约失败**：无效 JSON / 重复 key 记 `contract_drift(reason=invalid_json)`，模型校验失败记 `contract_drift(reason=schema_mismatch)`，session 回显不一致记 `contract_drift(reason=session_mismatch)`，统一抛 `UPSTREAM_INVALID_RESPONSE`。

`fetch_many` 对每条 `AppError` / `ValidationError` / `httpx.HTTPError` 做逐会话隔离（`http.py:114-146`），唯一例外是 `UPSTREAM_VERSION_INCOMPATIBLE`。这个矩阵决定了“窗口枚举失败整批失败、包请求失败按条隔离”的实际行为（§6 D8 与 05 §10.4 的字面差异）。

### 2.5 pull job 的批次健康

`UpstreamPullService.handle` 在进入枚举/抓取前启动 `time.monotonic()`（`upstream_pull.py:104`），把“枚举 + 抓取”包在 try 里（`:112-138`）：任何异常先记一条 `upstream.health(failed)`（含 `error_code`），再原样 re-raise，交给 JobRunner 标失败。成功路径在写 payload、重放、写 sync errors 之后记一条 `upstream.health`（`:187-202`），字段来自 `LocalImportWriteResult` 与 `ReplayResult`，耗时由 `_elapsed_ms` 取整（`:217-219`）。`_error_code` 只返回 `ErrorCode.value` 或异常类名（`:222-226`），不拼接异常文本。

因此健康日志的位置有一个天然边界：它只覆盖“上游枚举/抓取”这一段；`write_local_payloads` 或 replay 失败不会产生 `upstream.health`，因为那已不是上游健康（§9 记为已知弱点）。

### 2.6 测试基座：真实 socket 与可注入的 app

`LocalUpstream` 是测试内的真实 HTTP 服务：`ThreadingHTTPServer(("127.0.0.1", 0), _Handler)` 拿临时端口（`apps/api/tests/m12_01_support.py:139-147`），`base_url` 返回 `http://127.0.0.1:<port>`（`:123-129`）。它按 05 §10 实现：`/trajectories` 窗口枚举（`:193-200` 用 `cursor` 偏移分页）、`/trajectories/{id}` 包、`Authorization` 校验（`:171-173`）、可选 503 故障（`:175-187`），并把每个请求的 path/query/authorization 记录在 `requests`（`:161-170`）。

app 侧用 `create_app(upstream_settings(...))` 装配真实 `httpx.AsyncClient`；测试自身访问 API 用 `ASGITransport`，但 API 访问上游走真实 TCP，所以“真实 HTTP”只指上游这一段，恰好也是本 PR 要验证的边界。`upstream_settings` 把 `sync_interval_seconds=0`，避免后台 sync 干扰断言（`:235-254`）。

## §3 数据流走查

### 3.1 成功路径：窗口 pull

以一个真实测试输入为例：`{"window": {"from": "2026-11-01", "to": "2026-11-30"}}`，上游有 `ROOT` 和 `ROOT_2` 两个会话，`page_size=1`。

1. 管理员 `POST /api/acquisition/pull` 入队 pull job（`test_controlled_upstream.py:55-61`）；JobRunner 调到 `UpstreamPullService.handle`。
2. `handle` 校验 `PullJobPayload`，进度更新为 `fetching`（`upstream_pull.py:105-111`）。
3. 走窗口分支：`source.list_window(...)`（`upstream_pull.py:119-124`）。客户端第一次 `GET /trajectories?from=...&to=...&problemOnly=true`，响应头 `X-Trajectory-Api-Version: 1.0` 通过校验并记 `version_observed`；`nextCursor="1"`，第二次带 `cursor=1`，拿到 `ROOT_2` 后 `nextCursor=null` 结束（`http.py:91-107`；测试断言 `test_controlled_upstream.py:72-75`）。
4. `fetch_many([ROOT, ROOT_2])`（`upstream_pull.py:126`）逐个 `GET /trajectories/{id}`，每个都走版本校验与 JSON 解析；两次成功，记一条客户端 `upstream.health(ok)`（`http.py:148-157`）。测试断言所有请求都带 `Authorization: Bearer controlled-upstream-token`（`test_controlled_upstream.py:76-78`）。
5. `package_to_payloads` 把包转成原始 JSONL 行，`write_local_payloads(source_type="http_api")` 写入 `trajectory_payloads`（`upstream_pull.py:146-155`）；测试断言插入 2 条（`test_controlled_upstream.py:67,70`）。
6. `replay_pending_payloads` 归一化并写入 `session_families`（`upstream_pull.py:167-172`）；测试断言 replayed=2、failed=0、families=2（`:68-69,71`）。
7. 最后记 pull 层 `upstream.health(ok)`，包含请求/抓取/隔离/写入/重放/耗时（`upstream_pull.py:187-202`）；测试断言该记录 `status=ok`、`sessions_requested=2`、`sessions_isolated=0`（`test_controlled_upstream.py:79-87`）。

### 3.2 逐会话失败与手动重拉

1. 上游把 `ROOT` 配成 503（`test_controlled_upstream.py:96`）。`_get_json` 在默认 3 次重试后记 `request_failed(retry_exhausted)` 并抛 `UPSTREAM_REQUEST_FAILED`；`fetch_many` 把它转成一条 `UpstreamItemIssue`，继续处理其他会话（`http.py:114-146`）。
2. pull job 仍完成，结果 `upstreamIssues=1`，没有写 payload（`test_controlled_upstream.py:111-115`）；pull 层健康为 `degraded`，客户端批次也是 `degraded`。
3. 管理员清掉故障后 `POST /api/acquisition/pull` 传 `sessionIds=[ROOT]`（`:117-122`），第二次抓取成功，插入 1 条、replayed 1（`:124-129`）；两条 pull 健康记录状态依次为 `degraded`、`ok`（`:131-136`）。
4. 手动 `POST /api/acquisition/sync` 的重放路径由 `test_manual_sync_replays_stored_payload` 单独覆盖：先直接写一条本地 payload，再触发 sync，断言 imported=1、families=1（`test_controlled_upstream.py:139-158`）。

### 3.3 上游故障不阻塞 payload 路径

1. 先写入一条脚本 payload（`test_controlled_upstream.py:180`）。
2. 上游窗口配 `fail_window=True`，并设 `upstream_retry_attempts=0`（`:166-171`）。`list_window` 的 503 不重试，记 `request_failed` 后抛 `UPSTREAM_REQUEST_FAILED`；pull job 失败，pull 层健康记 `failed`、`error_code=UPSTREAM_REQUEST_FAILED`（`upstream_pull.py:127-138`；测试 `:194-201`）。
3. `POST /api/acquisition/sync` 照常重放已落库 payload，imported=1、families=1（`:188-193`）。这说明上游故障只让 pull job 失败，`trajectory_payloads` 的脚本路径不被阻塞。

这条剧本正是 issue #242 的验收标准“上游故障不阻塞 payload 表路径”。

## §6 讨论点

### D1 结构化日志在生产入口没有输出通道

**位置**：`apps/api/app/__main__.py:16-23`、`deploy/harness-api.service:15`、`apps/api/app/third_party_api/trajectory/http.py:148-157`、`apps/api/app/service/acquisition/upstream_pull.py:187-202`、`docs/deployment.md:51`

**现象**：新代码把可查询字段放进 `logging` 的 `extra`，测试用 `caplog` 能读到 `record.status` 等属性。但生产入口是 `python -m app`（systemd `ExecStart` 同）→ `uvicorn.run(..., log_level=...)`；uvicorn 默认 `LOGGING_CONFIG` 只给 `uvicorn*` logger 装 handler，不给 root 装，`log_level` 也只设置 `uvicorn.error/access/asgi`。实测在该配置下：应用 logger 的 **INFO 记录被直接丢弃**；**WARNING 只输出 message**（如 `upstream trajectory API version drift`），`event`、`reason`、`expected_major` 等字段全部丢失。

复现（在 `apps/api` 下用仓库 venv）：

```sh
.venv/bin/python - <<'PY'
import logging, logging.config
import uvicorn.config

logging.config.dictConfig(uvicorn.config.LOGGING_CONFIG)
log = logging.getLogger("app.service.acquisition.upstream_pull")
log.info("upstream pull health", extra={"event": "upstream.health", "status": "ok"})
log.warning("upstream trajectory API version drift",
            extra={"event": "upstream.version_drift", "reason": "missing"})
PY
# stdout: （无输出，INFO 被丢弃）
# stderr: upstream trajectory API version drift   ← event/reason 均未出现
```

**问题**：PR 的核心交付“结构化健康/漂移日志”在当前部署形态下不可观测；`docs/deployment.md:51` 说“pull 输出……结构化日志”并不成立。这不是字段泄漏或分支错误，而是输出层缺失，且 caplog 测试天然掩盖了它。

**预判**：在 `app/__main__.py`（或一个幂等的 `configure_logging(settings)`）加 `logging.config.dictConfig`：root/`app` handler + 能渲染 `event` 与 other extras 的 formatter（JSON lines 或 `key=value`），level 取 `settings.log_level`；或者在部署命令明确传 `--log-config` 并在 deployment 文档写清。补一个“格式化后的整行包含 `event=upstream.health` / `status=degraded`”的测试，不要只断言 `LogRecord` 属性。注意多 app 实例（测试）重复配置 handler 的幂等性。

**结论**：待维护者拍板。

### D2 `live_upstream` marker 不是门禁，Note 的“只有 -m 才访问真实上游”不成立

**位置**：`apps/api/tests/m12-01-real-trace-upstream/test_live_upstream.py:19,28-33`、`apps/api/pyproject.toml:63`、`.agents/notes/implemented/architecture/2026-10-26-upstream-trace-contract.md:21`、`docs/development.md:61-64`

**现象**：marker 只在 `pyproject.toml` 注册，`pytestmark` 只提供元数据；用例的 skip 条件仅是 `HE_UPSTREAM_BASE_URL` / `HE_UPSTREAM_TOKEN` 存在。实测把两个变量指向一个关闭的 loopback 端口、**不带** `-m` 运行该文件，测试会执行并因连接失败而失败，说明“只有 `-m live_upstream` 才访问真实上游”不成立。今天的 CI 确实 1 skipped，因为 CI 没有这两个变量；但这是环境事实，不是机械门禁。另有一个细节：测试读 `os.environ`，而 app 的 `Settings` 还会读 `.env`（`config.py:71-76`），所以 `.env` 里的凭据不会触发 live 测试，导出的 shell 变量会。

复现（在 `apps/api` 下）：

```sh
HE_UPSTREAM_BASE_URL=http://127.0.0.1:9 HE_UPSTREAM_TOKEN=dummy \
  .venv/bin/python -m pytest tests/m12-01-real-trace-upstream/test_live_upstream.py -q
# FAILED ... ConnectError → 重试耗尽 AppError；不是 skipped
```

**问题**：任何在 shell 里 `export` 了凭据的人跑全量 `pnpm test:api` 都会访问真实上游；未来 CI 若把 secrets 注入 env，也会破坏 hermetic。Note 与文档把“默认不访问”写成了比实现更强的保证。

**预判**：增加显式开关（例如 `HE_UPSTREAM_LIVE=1` 才运行，或 conftest 在未显式选择时 skip），CI 命令加 `-m "not live_upstream"`，并把 Note/development 的措辞改成“变量存在时运行；`-m` 只是筛选”。如果保留 `HE_UPSTREAM_LIVE_SESSION_ID`，一并写进 development 文档。

**结论**：待维护者拍板。

### D3 失败健康日志的 `sessions_requested` 在窗口 pull 下不可信

**位置**：`apps/api/app/service/acquisition/upstream_pull.py:112-138`（具体值在 `:133`）

**现象**：失败分支写 `sessions_requested=len(payload.session_ids or ())`。窗口 pull 在枚举成功后、`fetch_many` 因 `UPSTREAM_VERSION_INCOMPATIBLE` 抛错时，`session_ids` 已经知道，但日志写 0；枚举本身失败时也写 0，与“确实请求了 0 个会话”同形。

**问题**：排障时无法从失败健康日志区分“窗口枚举失败（数量未知）”和“窗口 0 条/版本不兼容（数量已知）”；这是本 PR 新增的字段，应该可信。

**预判**：在 try 前初始化 `requested = len(payload.session_ids or ())`，窗口枚举成功后更新为 `len(session_ids)`，日志统一用 `requested`；必要时再加 `sessions_enumerated`。补一个“枚举成功、`fetch_many` 版本不兼容”的用例，覆盖当前未测到的路径。

**结论**：待维护者拍板。

### D4 deployment 文档说“调度重试逐会话失败”，但调度器不会重拉上游

**位置**：`docs/deployment.md:51` / `docs/deployment.en.md:51`；对照 `apps/api/app/service/acquisition/sync.py:80-100,234-249`

**现象**：文档说逐会话失败留在 `sync_runs.errors`，“由调度或手动重放重试”。但 `SyncScheduler` 的 `run_once()` 只重放 `trajectory_payloads` 中待归一化的 payload；上游抓取失败根本没有 payload 可重放。真正重试上游抓取的入口是 `POST /api/acquisition/pull` 带 `sessionIds`。

**问题**：运维会以为调度器会自动补拉失败会话，实际不会；pull 健康日志里的 `replayed` / `failed` 也是归一化计数，不是上游重试。

**预判**：按实际行为改写为“逐会话失败留在 `sync_runs.errors`；已落库 payload 由调度或手动 `sync` 重放；上游抓取失败需手动 `pull(sessionIds)` 重拉”。中英两页同步。

**结论**：待维护者拍板。

### D5 泄漏断言的测试防线是假阴性

**位置**：`apps/api/tests/m12-01-real-trace-upstream/test_health_and_drift.py:124,148,174,199,227,250`、`test_controlled_upstream.py:202`

**现象**：这些断言用 `"must-not-leak" not in caplog.text` / `ROOT not in caplog.text`。pytest 的 `caplog.text` 是 handler 用默认 formatter 渲染的文本，默认格式只含 `%(levelname)s ... %(message)s`，**不含 `extra`**；而本 PR 的数据恰好都在 `extra`。当前逐项核对没有泄漏，但测试并没有证明这件事。

**问题**：将来若把 session id、响应正文或 token 加进 `extra`，这些断言仍会通过；这是对 PR 安全声明的“纸面防线”。

**预判**：断言改为遍历 `record.__dict__` 的非标准字段（或把全部 extras 序列化）后检查敏感值；或配置一个包含 `event` 与全部 extras 的 formatter，对整行断言。至少加一条“响应正文含 token / sessionId”的用例。

**结论**：待维护者拍板。

### D6 逐会话 4xx 被记成 WARNING `upstream.request_failed`

**位置**：`apps/api/app/third_party_api/trajectory/http.py:196-210`

**现象**：所有 `>=400` 且不可重试的状态（400/401/403/404）都会 WARNING `upstream.request_failed(reason=http_status)`；随后 `fetch_many` 把它按条隔离，`upstream.health` 只记 degraded。大窗口里已删除会话（404）或错误凭据（401）会按会话重复刷 WARNING；每次可重试失败还会先来一条 INFO `request_retry`。

**问题**：隔离是设计的正常路径，却用了“请求失败”的告警语义，容易触发噪声告警和误判；对窗口型 pull，日志量可能随会话数线性放大。

**预判**：非重试 4xx 用 INFO（或加 `isolated=true`，401/403 单独 reason），WARNING 只留给重试耗尽、传输/超时和 5xx；补 404 的级别断言。这是告警策略取舍，故列为决策点。

**结论**：待维护者拍板。

### D7 同名 `upstream.health` 在客户端与 pull 层重复，schema 还不一致

**位置**：`apps/api/app/third_party_api/trajectory/http.py:148-157`、`apps/api/app/service/acquisition/upstream_pull.py:187-202`

**现象**：一次成功的 degraded pull 会产生两条 `event=upstream.health`：客户端批次那条只有 `sessions_*`；pull job 那条多出 `payloads_*` / `replayed` / `failed` / `duration_ms`，但没有客户端字段。失败时只有 pull 层一条。按 event 计数的看板会把一次 pull 算两次，按字段消费则 schema 不同。

**问题**：`event` 是事实上的日志契约，重复与不一致会让告警/指标长期漂移；Note 目前只说“客户端与 pull job 都输出”，没有说明两者关系。

**预判**：给记录加 `component=client|pull` 并在文档列出两套 schema；或只保留 pull 层（信息更全），客户端层降到 DEBUG/删除。若保留两层，字段命名与状态枚举应统一。

**结论**：待维护者拍板。

### D8 设计文档与实现字面不一致：版本“拒绝启动”、类名/路径、5xx 隔离范围

**问题**：PR 以 05 §10 为设计依据，但实现与文档字面冲突；后来者按 05 会预期启动失败或找不到文件。这些是 pre-existing 偏差，但本 PR 既然补了版本日志，正是对齐的时机。

## §9 文件级代码分析

### `apps/api/app/third_party_api/trajectory/http.py`（M）

**职责**：出站轨迹查询的 HTTP 实现，负责版本头、JSON/模型校验、重试、逐会话隔离与本次新增的健康/漂移日志。变更形态：M，base 版本已有 `fetch` / `list_window` / `fetch_many` / `_get_json` / `_validate_version`，本 PR 增补日志与 `label` 参数。

**关键依赖**：`httpx`（第三方、运行时）提供客户端与 `MockTransport`；`pydantic`（第三方、运行时）做模型校验；`logging`（标准库）承载 `extra`。比喻：`httpx.AsyncClient` 是接进来的水管，`HttpTrajectorySource` 是水表，`extra` 是水表读数，但读数要有人抄（见 D1）。

**变更代码块**：

旧：

```python
payload = await self._get_json(f"trajectories/{quote(session_id, safe='')}")
...
payload = await self._get_json("trajectories", params=params)
```

新：

```python
payload = await self._get_json(
    f"trajectories/{quote(session_id, safe='')}",
    label="package",
)
...
payload = await self._get_json("trajectories", params=params, label="window")
```

`label` 不是 URL 的一部分，只是日志里的 `model` 字段；它让“窗口失败”和“包失败”在同一事件名下可区分。`_get_json` 的签名加必填 keyword，两个调用点都更新，避免默认值掩盖调用方。

旧 `_get_json` 的失败分支只 `raise`；新版本在 timeout/transport 重试前记 `request_retry`，耗尽记 `request_failed`，5xx/429 补试同样记，4xx 记 `http_status`，无效 JSON 记 `contract_drift`。实现思路：**在唯一的重试循环里埋点**，保证每条失败路径只在一个地方分类，不会因子类重复记录；`attempt+1` 表示“已尝试次数”。

旧 `_validate_version` 只 raise；新版本先算 `observed_major` 与 `reason`，再 WARNING + raise；通过后记录首次版本或变化告警。这里有意只写 `observed_major`（int）而不是原始 header，满足“不泄漏不受控字符串”。

旧 `fetch_many` 直接返回 `FetchManyResult`；新版本先构造 `result`，再 INFO `upstream.health`，最后返回。`sessions_isolated` 用 `len(issues)`，`sessions_fetched` 用成功包数；状态只有 ok/degraded，不在这层判 failed（失败会 raise，到 pull job 层记 failed）。

**检视发现**：

- 字段面：逐项核对 `extra` 的所有 key（`event/status/sessions_*/api_version/reason/expected_major/observed_major/previous_version/current_version/model/attempt/attempts/status_code/error_count`），没有响应正文、URL、session id、Authorization 或 token；`api_version` 在记录前已过 `^[1-9][0-9]*\.[0-9]+$`，`reason/model/status` 是闭集，`attempts/status_code` 是整数。**当前没有泄漏**。
- 日志输出层缺失（D1）：记录存在，但生产 formatter 不渲染 `extra`，INFO 还被丢。
- 逐会话 4xx WARNING 噪声（D6）。
- 同名 health 重复（D7）。
- 覆盖率缺口：`_get_json` 的 timeout/transport 耗尽分支（`http.py:181-182`）没有被测试覆盖；窗口校验 `:83`、分页上限 `:108`、循环末尾不可达 `:221` 也未覆盖。建议补一个 `httpx.ConnectTimeout` 的 `MockTransport` 用例，直接验证 `reason=timeout` 的 `request_failed`。
- `version_observed`/`version_changed` 只按 source 实例记录；并发 pull 共用同一个 source 时，`_observed_version` 的读写发生在同步的 `_validate_version` 内，asyncio 单线程下不会交错，当前无实害。

### `apps/api/app/service/acquisition/upstream_pull.py`（M）

**职责**：pull job 的编排：枚举/抓取、写原始 payload、重放、写 sync errors，并记录批次健康。变更形态：M，base 是直线流程；本 PR 加 stopwatch、try/except、成功/失败两条 health，以及 `_elapsed_ms` / `_error_code`。

**关键依赖**：无新第三方依赖；`time.monotonic()` 提供不受系统时钟回拨影响的耗时，`logging` 承载事件。

**变更代码块**：

旧：

```python
if payload.session_ids is not None:
    session_ids = list(payload.session_ids)
else:
    ...
    enumerated = await source.list_window(...)
    session_ids = [item.session_id for item in enumerated]
fetched = await source.fetch_many(session_ids)
```

新：

```python
try:
    if payload.session_ids is not None:
        session_ids = list(payload.session_ids)
    else:
        ...
        enumerated = await source.list_window(...)
        session_ids = [item.session_id for item in enumerated]
    fetched = await source.fetch_many(session_ids)
except Exception as exc:
    logger.warning(
        "upstream pull failed",
        extra={
            "event": "upstream.health",
            "status": "failed",
            "sessions_requested": len(payload.session_ids or ()),
            "duration_ms": _elapsed_ms(started),
            "error_code": _error_code(exc),
        },
    )
    raise
```

这段的意图是“失败也要留下可聚合的健康记录”，同时保持原异常语义（`raise` 不改栈）。catch 用 `Exception` 而不是 `BaseException`，`CancelledError` 不会被吞成健康失败，这是对的。

成功路径在 replay 与 append sync errors 之后记：

```python
logger.info(
    "upstream pull health",
    extra={
        "event": "upstream.health",
        "status": "degraded" if issues else "ok",
        "sessions_requested": len(session_ids),
        ...
        "replayed": replay.imported,
        "failed": replay.failed,
        "duration_ms": _elapsed_ms(started),
    },
)
```

这里把“上游隔离数”和“归一化失败数”放在同一条记录里；`status` 只看 `issues`（上游），`replay.failed` 不参与 degraded 判定。

**检视发现**：

- 失败分支的 `sessions_requested` 在窗口 pull 下是 0（D3），是本次新增字段里最明显的值语义 bug。
- `status="ok"` 可能在 `replay.failed > 0` 时出现（记录里同时有 `failed` 字段）。若“pull 健康”包含归一化，建议把 `replay.failed` 也算进 degraded；若只指上游，字段名与文档应说明。当前无实害，因为 `upstreamIssues`/`failed` 分开返回，但对看板是歧义。
- 失败分支只覆盖“枚举 + 抓取”；`write_local_payloads` / replay / append sync errors 失败不会产生 health（见 2.5）。若希望失败也有可观测记录，需要把 try 扩大到整个 handle，或单独记 job 失败原因。
- `_error_code` 对非 `AppError` 返回 `type(exc).__name__`，是受控短字符串；但该分支在覆盖率里是 `:226`，没有测试。若未来把异常 message 拼进去，会破坏“无上游文本”的承诺，建议加一条非 AppError 的单测锁定行为。
- `_elapsed_ms` 的 `max(0, ...)` 防御时钟/浮点异常，成本可忽略。
