## §1 一页速览

一句话：列表翻页时不再把整张表换成骨架，而是保留上一页的行和分页条，查询在后台换成新页；滚动容器高度不变，`scrollTop` 不再被夹回顶部。

比喻：原来的翻页像把整面书架先清空再摆新书，书架一空，房间里的阅读位置就被拉回门口；现在新书到之前旧书留在架上，读者站在原地等替换。

| 交付块 | 内容 |
| --- | --- |
| 查询层 | `placeholderData` 只在同一 `workspaceId` 内复用上一次成功结果 |
| 组件层 | `initialLoading = loading && items.length === 0`；加载中 `aria-busy` + 分页条「加载中…」 |
| 数据一致性 | 页码仍来自 URL `page`；查询键按页隔离，旧响应只写自己的缓存键 |
| 回归 | 组件单测、页级单测、三页真实浏览器（首次请求 / 缓存命中 / 失败重试 / 末页 / 快速翻页） |
| 证据 | PR 描述中的同视口前后截图、原型对照、7 场景冒烟报告 |

## §2 架构导览

总览页在 [Index.vue:66](../apps/web/src/pages/overview/Index.vue#L66) 派生列表查询参数，`page` 来自 URL；[useOverview.ts:118](../apps/web/src/composables/useOverview.ts#L118) 的 `placeholderData` 只在目标查询还没有数据、且上一次有数据的查询属于同一工作空间时返回旧结果。Vue Query 把占位结果标记为 `isPlaceholderData`，查询本身仍在后台请求新页。

[Index.vue:571](../apps/web/src/pages/overview/Index.vue#L571) 把 `isPending || isPlaceholderData` 传给表格，区分「完全没有数据」与「有旧结果、正在换成新页」。表格在 [BadCaseTable.vue:175](../apps/web/src/pages/overview/components/BadCaseTable.vue#L175) 用 `initialLoading` 把骨架限定到前者；[BadCaseTable.vue:246](../apps/web/src/pages/overview/components/BadCaseTable.vue#L246) 在列表根节点暴露 `aria-busy`；[BadCaseTable.vue:485](../apps/web/src/pages/overview/components/BadCaseTable.vue#L485) 起分页条只要不是首次加载就保持渲染，并在信息行 [BadCaseTable.vue:491](../apps/web/src/pages/overview/components/BadCaseTable.vue#L491) 显示加载提示。

滚动归属不变：`.overview-page` 仍是总览页自己的滚动容器，[Index.vue:614](../apps/web/src/pages/overview/Index.vue#L614) 的 `height: 100%` 与 [Index.vue:616](../apps/web/src/pages/overview/Index.vue#L616) 的 `overflow-y: auto` 没有改动。修复只是阻止内容高度在加载期间收缩。

## §3 数据流走查

主线：位置栏 `page=2` → `casesQuery` 的查询键从第 1 页切到第 2 页 → 目标键无缓存，`placeholderData` 返回同空间第 1 页数据 → 表格渲染旧 8 行、`aria-busy=true`、分页条显示「第 2 / 3 页 · 加载中…」 → 第 2 页请求返回后查询键写入数据，旧行原位替换 → `aria-busy=false`，滚动位置保持。

失败支线：第 3 页请求连续返回 5xx（查询层默认重试两次）→ 查询进入 error，占位数据不再适用 → 表格显示块级错误态与重试 → 重试成功写入第 3 页 4 行。

快速翻页支线：第 2 页请求被延迟，用户立刻翻到第 3 页 → 第 3 页先返回并写入自己的缓存键 → 第 2 页晚到，只写第 2 页键，当前页仍是第 3 页。

## §6 讨论点

**位置**：`BadCaseTable.vue:337` 与 `:485` 的加载态条件。

**现象**：目标页在加载时，分页条已经显示目标页码（如第 2 / 3 页），但行内容仍是第 1 页。

**问题**：短暂出现「页码与行内容不同页」，完全依赖 `aria-busy` 与「加载中…」提示表达过渡状态。

**预判**：可接受。页码代表 URL 目标而不是已渲染数据；若改成显示已渲染页会与浏览器地址栏不一致。两种选择都需要过渡提示，当前提示同时服务视觉与读屏。

**结论**：（留空）

**位置**：`BadCaseTable.vue:337` 的失败路径（错误态仍替换整表）。

**现象**：第 3 页请求失败后列表内容消失，`scrollTop` 398 → 199；重试成功后回到 255。

**问题**：失败路径仍会收缩列表，观感与本次修复目标相近。

**预判**：保持现状。失败页没有「当前页数据」可以保留，展示错误态是诚实状态；冒烟把失败与重试单列为场景，并在 PR 边界中写明。后续若要彻底消除收缩，可给错误态加与表格同高的占位，但那是独立的视觉决策。

**结论**：（留空）

**位置**：`tests/e2e/m8-04-overview.test.mjs:1470` 附近的失败注入。

**现象**：为了等到错误态，测试连续注入 3 次 500，对应查询层默认重试两次。

**问题**：测试与 `createAppQueryClient` 的重试策略耦合；策略变化时断言会先失败。

**预判**：可接受。断言失败会直接指向重试次数变化，属于有意义的提示；若未来策略可配置，测试可从查询客户端读取次数而不是写死 3。

**结论**：（留空）

## §9 文件级代码分析

### `apps/web/src/composables/useOverview.ts`

职责：总览所有读接口的查询封装。变更形态 M。

新增 `placeholderData: (previousData, previousQuery) => ...`：没有旧数据或旧查询不存在时返回 `undefined`，让表格回到骨架；旧查询的工作空间与当前不一致时也返回 `undefined`，避免跨空间串数据；否则复用旧结果。

检视发现：查询键结构是 `["ws", workspaceId, "overview", "cases", filters]`，索引 1 稳定；若未来键前缀调整，这里要同步，目前由 `queryKeys` 单点定义。

### `apps/web/src/pages/overview/Index.vue`

职责：总览页状态、查询与模板编排。变更形态 M。

`loading` 从单一 `isPending` 扩展为 `isPending || isPlaceholderData`：首次加载与占位加载都让表格知道正在换页，但表格自行区分有无旧行。后台 refetch 当前页不会进入这两个状态，因此不会闪加载提示。

检视发现：无。`isPlaceholderData` 只在占位结果上为真，不会影响其它区块。

### `apps/web/src/pages/overview/components/BadCaseTable.vue`

职责：bad case 列表、列表级筛选、分页与状态渲染。变更形态 M。

`initialLoading` 把骨架限定为「加载中且没有行」；分页条从 `!loading` 改为 `!initialLoading`，加载中继续显示；分页信息追加 `role="status"` 的「加载中…」；列表根节点加 `aria-busy`。加载提示放在分页信息里，避免在列表头新增一行改变卡片高度。

检视发现：在极慢请求期间用户仍可连续点击下一页，页码按 URL 前进；这是有意保留的能力，查询键隔离保证晚到响应不会覆盖当前页。

### `apps/web/src/pages/overview/Index.test.ts`
