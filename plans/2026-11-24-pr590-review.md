## §1 一页速览

一句话：让服务在重启后不只接管「崩溃时仍是 `running`」的 job，也接管「优雅停机已经写成 `interrupted`」的 job，使跨发布的 prepare 与归因批次自动续跑。

一个比喻：原来的恢复像保安只检查还亮着「占用」灯的房间；部署重启会先把房间灯改成「已中断」，保安就以为这里没人了。现在保安同时翻「已中断」登记簿，按房间号只认最新一条记录，把还没人接手的房间重新排进队列。

| 交付块 | 用户可见结果 |
|---|---|
| `evolution_prepare/advance/apply/finalize/retry` 恢复 | 部署重启后 run 自动续跑，事件流出现 `job_recovered`，不再永久停在 interrupted |
| `attribution_batch` 恢复 | 归因批次原地回到队列，保留 9/22 进度，只补未完成 case |
| 护栏 | pause/blocked/completed run、attempt 用尽的批次、已过归因阶段的旧批次都不恢复；连续重启不重复入队 |
| 可观测性 | 启动日志汇总恢复数量、kind 与 run id；不写 Session 内容或凭据 |

验证基线：focused/related API 测试 85 passed；全量 `test:api` 仅 1 个 macOS 路径规范化用例失败（与改动无关）；`test:db`、`typecheck:api`、`lint:docs`、`verify:docs`、`test:gates`、`verify:flow(--diff)` 全绿。

## §2 架构导览

### 2.1 数据层：只认「最新一行」

`JobRepository.latest_interrupted()`（`apps/api/app/db/crud/jobs.py:438`）用 `row_number() over (partition by kind, ref_id order by created_at desc, id desc)` 给可恢复 kind 的 job 排序，只留下每组第一行，再过滤 `status=interrupted`、未取消、`attempt < max_attempts`。这解决两个问题：

- 同一 run 同一 kind 只恢复一条，不会把历史上多次中断的行全部重排；
- 一旦恢复流程插入了新的 replacement，旧 interrupted 行就不再是「最新」，第二次重启自然跳过。

`requeue_interrupted()`（`jobs.py:466`）把单行从 `interrupted` 原地改回 `queued`，清 lease/error/finished_at，保留 `progress`、`attempt`、`result`。这是归因批次「保留批次身份与 9/22 进度」的落点。

### 2.2 服务层：先 running，后 interrupted

`JobRunner.recover()`（`apps/api/app/service/jobs.py:156`）保持原有顺序：

1. `requeue_running_kind("attribution_batch")` 释放仍在 running 的归因批次；
2. `mark_running_interrupted("process restarted")` 把崩溃遗留的 running 行写成 interrupted，记录 `run_interrupted`，再走原有 `_requeue_interrupted()`；
3. 新增：`latest_interrupted(_RECOVERABLE_INTERRUPTED_KINDS)`（`jobs.py:196`）接管优雅停机已写好的行。

第 3 步先处理 `attribution_batch`，再处理 evolution job（`jobs.py:203`）。归因批次先行保证父 prepare 恢复后 `run_for_prepare()` 能 join 到同一个批次，而不是再开一批。

### 2.3 evolution 的栅栏复用

evolution job 不直接改行，而是复用 `EvolutionControlRepository.requeue_interrupted()`（`jobs.py:271`）：`control_state != running`、run 已 completed/failed、blocked 暂不放行、已有活跃 job、`resumed_at >= finished_at` 都跳过。成功后写 `job_recovered`（payload 带 `previousJobId` 与 `source=process-restart`），原 `run_interrupted` 保留。

### 2.4 归因批次的额外护栏

`_recover_attribution_batch()`（`jobs.py:236`）只在该 run 仍处于 `progress_unit == 3`、`control_state == running`、状态为 `preparing/running/interrupted` 时恢复（`jobs.py:249`）。这三种状态覆盖了「优雅停机把 run 标 interrupted」与「崩溃后 run 仍 active」两种现场；`blocked`、`completed` 与已推进到后续阶段的旧批次都不重跑。

## §3 数据流走查

以生产事故的现场为例：run 在 prepare 的归因步骤，prepare job 与 attribution batch 都被停机写成 interrupted。

1. 部署重启，新进程启动 `JobRunner.start()` → `recover()`（`jobs.py:156`）。
2. `mark_running_interrupted` 没找到 running 行；`requeue_running_kind` 也没找到 running 批次。
3. `latest_interrupted` 取到两条：prepare 与 batch（`jobs.py:196`）。
4. 先恢复 batch：`_attribution_run_active` 看到 run `progress_unit=3`、control running、status interrupted → `requeue_interrupted` 把同一行改回 queued（`jobs.py:236`、`db/crud/jobs.py:466`）。
5. 再恢复 prepare：`_requeue_interrupted` 走 control 栅栏插入新的 `evolution_prepare`，写 `job_recovered`（`jobs.py:261`）。
6. `start_queued()` 按 created_at 调度：batch 的 `created_at` 仍是停机前的时间，先于新 prepare。
7. prepare handler 读到 run interrupted → `mark_recovered` 把 run 拉回 running；随后 `run_for_prepare()` 提交归因，`find_active` 命中刚恢复的 batch 并复用。
8. 9/22 批次只对未链接 probe 的 13 个 case 调用归因；全部完成后 prepare 继续后续步骤。

## §6 讨论点

### D1 启动查询会扫描可恢复 kind 的全部历史行

- **位置**：`apps/api/app/db/crud/jobs.py:438`
- **现象**：窗口函数在分组前对所有 `kind in (...)` 的行排序，不只排序 interrupted 行；这样才能判断「旧中断行是否已被更新的 replacement 超越」。
- **问题**：job 历史无限增长时，启动恢复的这条查询会随历史线性变慢。当前索引是 `(kind, created_at desc)` 与 `(ref_id)`，没有 `(kind, ref_id, created_at)` 复合索引。
- **预判**：单实例、启动时执行一次，当前数据量下无实害；若未来 job 行数到百万级，再补复合索引或把查询收窄到「有 interrupted 行的 ref」。
- **结论**：本轮接受，不加迁移；记录为潜在优化点。

### D2 9/22 续跑测试直接写 probe，而不是先真实跑到 9 个

- **位置**：`apps/api/tests/bugfix-49-shutdown-recovery/test_attribution_resume.py:64`
- **现象**：测试先通过仓储写入 9 个已完成 probe，再调用真实 `AttributionJobService.handle` 补剩余 13 个。
- **问题**：没有复现「引擎跑到第 10 个时进程被 kill」的中间态。
- **预判**：恢复路径只负责把 job 放回队列；「跑过的 case 不重跑」由 `AttributionRunner` 的 `linked_probe_ids` 跳过逻辑保证，已有 `tests/attribution/test_m10_03_runner.py` 覆盖。两层分开测更稳定，也未伪造外部模型。
- **结论**：接受；若未来要覆盖「写入过程中 kill」，应放到归因 runner 的故障注入测试，而不是恢复测试。

## §9 文件级代码分析

### 9.1 `apps/api/app/db/crud/jobs.py`（M）

职责：job 行的方言中立持久化。新增两个方法，不改变已有方法语义。

关键依赖：SQLAlchemy Core 的窗口函数 `row_number()` 同时被 SQLite 3.25+ 与 MySQL 8 支持；`record_from_row` 只读取已知列，`ranked` 子查询多出的 `recency` 列不影响映射。

变更块：

```python
ranked = select(*job_runs.c, recency).where(job_runs.c.kind.in_(tuple(kinds))).subquery()
statement = select(ranked).where(
    ranked.c.recency == 1,
    ranked.c.status == "interrupted",
    ranked.c.cancel_requested.is_(False),
    ranked.c.attempt < ranked.c.max_attempts,
)
```

这在做什么：先按 `(kind, ref_id)` 找每组最新行，再只保留其中仍是 interrupted 且可再试的行。为什么这么写：如果只按 `status=interrupted` 分组，旧中断行永远是最新中断行，恢复一次后会再次入队。

实现思路总结：分组取最新 → 过滤可恢复 → 交给 service 决定 evolution 或 batch 的恢复方式。

检视发现：启动历史扫描（D1，接受）。

### 9.2 `apps/api/app/service/jobs.py`（M）

职责：JobRunner 的启动恢复编排。原有 running 路径不变；新增 interrupted 路径。

变更块：

```python
shutdown_interrupted = [
    job for job in await self.repository.latest_interrupted(_RECOVERABLE_INTERRUPTED_KINDS)
    if job.id not in restarted_ids
]
```

这在做什么：排除本次启动刚中断的行，只接管启动前已写成 interrupted 的行，避免同一次启动对同一行既走 running 路径又走 interrupted 路径。

`_recover_attribution_batch` 与 `_attribution_run_active` 把「批次是否值得恢复」收敛成三个条件：run 存在、control running、`progress_unit == 3`、状态未完成。`_requeue_interrupted` 保持原有 evolution 栅栏与 sync 特例。

检视发现：命名已修；阶段护栏已补（见 §7）。
