## §1 一页速览

一句话：把 Web 端所有业务页从“默认某个空间”搬到显式 `/workspaces/:wid`，并让缓存、页面状态和旧链接都遵守这个空间。

一个比喻：V1 的缓存像一个没有写名字的公共储物柜，谁先来谁放；这个 PR 给每个空间发了一个带锁的柜子（`["ws", wid]`），换柜子时把旧柜子里的东西标记失效，并且把手里旧柜子的钥匙（`sessionId`/`runId`）丢掉。

| 缓存隔离 | `["ws", wid]` 前缀、切空间失效旧树、RouterView key | `queryKeys.test.ts`、`WorkspacePicker.test.ts`、E2E |

## §2 架构导览

### 2.1 路由壳：名称即上下文

`router/index.ts:40` 把原先散在顶层的业务路由收进 `/workspaces/:wid` 父路由，子路由名统一以 `workspace-` 开头。默认子路由 `workspace-root` 重定向到 `sessions`（`router/index.ts:42` 起的 children）。选择 `sessions` 而不是设计里的 `overview` 是阶段决定：总览页属于 m8-04，壳先落在一个已存在的页面，避免为占位新建一个空页。

旧路径不再注册为路由记录，而是由 `beforeEach` 按路径前缀识别（`router/index.ts:124`）。这样旧路径不需要各自的组件，也不会在异步组件加载后才决定去向；一次 `replace` 完成重定向并保留 query/hash。

### 2.2 守卫：三种失败各自有出口

`router/index.ts:102` 起的守卫顺序是：

1. 未 bootstrap → `tryRefresh()`；
2. 未登录且不是登录/改密页 → `/login?redirect=…`；
3. 已登录访问 `/login` → `safeRedirect(query.redirect, defaultLandingPath)`；
4. 强制改密 → `/change-password?redirect=…`；
5. 旧路径 → `resolveLegacyWorkspace()`；解析不到进选择页 `reason=select`；
6. 带 `wid` 的新路由 → 可见性检查，不可见进选择页 `reason=forbidden`。

第 6 步与后端 `require_workspace_role` 是两层护栏：前端只负责体验，直连 API 仍会被后端 404/403 拦住。

### 2.3 最近空间解析：不静默选第一个

`router/workspace.ts:68` 的 `resolveLegacyWorkspace()` 只接受两种确定答案：localStorage 里仍可见的空间，或当前用户唯一可见的空间。多个空间且没有记忆时返回 null，由守卫送去选择页。这是 m7-08 验收“旧链接不静默选择任意空间”的核心。

`switchableWorkspaceChild()`（`router/workspace.ts:105`）负责切空间时丢弃旧空间拥有的资源 id：`/sessions/:sid` 与 `/evolution/runs/:rid` 都退回各自列表；`/evolution/targets` 这种无资源 id 的分区保留。

### 2.4 缓存：key 是隔离边界

`api/queryKeys.ts:17` 起，Session 列表、详情、树、问题、bad case、运行、step、事件、对象、catalog 全部以 `["ws", wid, …]` 开头。`WorkspacePicker.vue:61` 的切换流程先 `invalidateQueries({queryKey: ["ws", oldWid]})`，再 `rememberWorkspace(newWid)` 并 `router.push`。`App.vue:16` 把 `RouterView` 的 key 设为 `wid`，因此页面内 `ref`（搜索词、展开节点、滚动记忆）会随空间重建，不需要每个页面手写重置。

### 2.5 启动：一个 payload 决定“我是谁、我能去哪”

`stores/auth.ts:134` 的 `restoreSession()` 先 refresh 再 `GET /auth/session`，`setWorkspaceSession()`（`stores/auth.ts:51`）同时写入 `user`、`workspaces`、`truncated`。登录和改密成功后也走同一 `loadSession()`。这样守卫拿到的可用空间与用户身份来自同一响应，不会出现“用户已登录但空间列表还是空的”中间态。

### 2.6 组件补 wid：显式优于全局

页面通过 `useWorkspaceId()`（`composables/useWorkspaceId.ts`）读 `route.params.wid`，再把 `wid` 传给 composable 和需要生成链接的子组件（`SessionOverview`、`ErrorSidebar`、`BadCaseList`、`ProbeSourceTable`、`RunLogPanel`、`LaunchWizard`、`TargetConfigEntry`）。选择显式 props 而不是在组件里偷偷读路由，是为了让组件测试能明确指定空间，避免新页面漏传时静默生成全局链接。

## §3 数据流走查：从旧深链到新空间页

剧本：已登录用户打开旧书签 `/sessions/<sid>/errors`。

1. 浏览器加载 SPA；`bootstrapApp()` 先装 Pinia/Query/Router，再 `tryRefresh()`。
2. `restoreSession()` 调 `/auth/refresh`，拿到新 access token，再 `GET /auth/session`（`stores/auth.ts:134`）。
3. `router.isReady()` 触发守卫；`isLegacyWorkspacePath("/sessions/…")` 为真（`router/workspace.ts:136`）。
4. `readLastWorkspaceId()` 读浏览器记忆；若该空间仍在 `auth.workspaces` 中则选它，否则看是否只有一个可见空间（`router/workspace.ts:68`）。
5. 命中后 `legacyWorkspaceTarget()` 生成 `/workspaces/<wid>/sessions/<sid>/errors`，守卫返回 `{path, query, hash, replace: true}`；浏览器历史只替换当前项，不追加（`router/index.ts:124`）。
6. 页面挂载时 `useWorkspaceId()` 得到 `wid`，`useSessionBadCases` / `useSessionSummary` / `useSessionTree` 用 `["ws", wid, …]` 取数（`composables/useSessions.ts`）。
7. bad case 详情走 `/api/workspaces/{wid}/bad-cases/{id}`；返回的 `sessionId` 与路由不一致时，页面显示“问题不属于当前 Session”（`pages/errors/Index.vue:175`）。
8. 顶栏 `WorkspacePicker` 展示当前空间与角色；切换到另一个空间时失效旧 `wid` 缓存并在同一分区打开新空间（`components/layout/WorkspacePicker.vue:42`、`:61`）。

## §6 讨论点

### D1 默认落地页暂时不是总览

- **位置**：`apps/web/src/router/workspace.ts:105`、`apps/web/src/router/index.ts:46`
- **现象**：`/workspaces/:wid` 默认子页是 `sessions`；设计 08 §1 的默认落地页是 `overview`。
- **问题**：空间壳的“入口语义”与目标态不一致；如果把会话列表当作临时入口，用户会形成错误习惯。
- **预判**：这是依赖顺序造成的阶段差异，不是实现遗漏；m8-04 交付总览后改一个常量与守卫默认值即可。
- **结论**：待维护者确认是否接受“先 Session、后 overview”的过渡；当前按 m8-04 依赖保留。

### D2 归因/探针仍是可见空间并集

- **位置**：`apps/web/src/api/badCases.ts:41`、`apps/web/src/pages/errors/Index.vue:175`
- **现象**：bad case 详情已走空间端点，但 `/api/bad-cases/{id}/analysis` 与 `/probes/{id}` 仍是 m7-06 的兼容端点；前端只能按 `wid` 隔离缓存，并额外比对 `sessionId`。
- **问题**：同一 bad case 被两个可见空间引用时，归因投影仍可能在“另一个可见空间”的上下文中被打开；这是后端端点缺口，不是前端能独立关死的。
- **预判**：m7-08 的验收边界是壳与缓存，不扩到空间级归因；但 Agent Note 必须保留这个欠账，后续补 `/workspaces/{wid}/.../analysis` 时一并收紧。
- **结论**：接受为已知限制，记入 Note 的 Consequences。

### D3 `auth/session` 依赖外部引导表

- **位置**：`apps/web/src/stores/auth.ts:134`；E2E 适配见 `tests/e2e/m1-shell.test.mjs:102`
- **现象**：启动改走 `auth/session` 后，`used` 聚合会读 `bad_cases`；m1 这类原来不 seed 外部表的 E2E 会停在登录页，因此测试补了 `fixtures/m1-shell.json` 的 seed。
- **问题**：全新部署若尚未初始化外部 `bad_cases` 表，空间壳会启动失败；这不是本次引入的后端查询，但被新的启动路径放大了。
- **预判**：生产部署本来要求先初始化外部表；可在部署文档/启动检查里明确，而不是让前端回退到 `me`。
- **结论**：接受；已写入 Note 的 Consequences，建议部署 issue 跟进启动检查。

### D4 切换空间时旧缓存是“失效”不是“删除”

- **位置**：`apps/web/src/components/layout/WorkspacePicker.vue:61`
- **现象**：切换时 `invalidateQueries(["ws", oldWid])`，旧空间数据仍在内存，切回时重新拉取。
- **问题**：如果空间数据量大，保留旧树会增加内存；如果要求“切走即释放”，应使用 `removeQueries`。
- **预判**：设计 03 §7 的原文是“失效旧前缀（切回时重拉）”，失效语义足够；删除会让切回变慢，且不利于快速对照。
- **结论**：按设计保留失效语义，待维护者确认是否有内存上限要求。

### D5 选择页不自动进入唯一空间

- **位置**：`apps/web/src/pages/workspaces/Chooser.vue`
- **现象**：用户直接访问 `/workspaces` 时，即使只有一个可见空间也展示选择页。
- **问题**：多一次点击；但自动进入会让“选择页”这一 URL 失去意义，也会掩盖旧链接解析失败。
- **预判**：登录与旧链接已经有“唯一空间自动落地”的路径；直接访问选择页保留手动选择是合理的。
- **结论**：保持现状；如维护者希望直达，只需在选择页挂载时复用 `resolveLegacyWorkspace`。

## §9 文件级代码分析

### `apps/web/src/router/index.ts`（M）

职责：路由表与唯一全局守卫。变更形态：把 V1 顶层业务路由收进 `/workspaces/:wid`，旧路径改由守卫按前缀处理。

关键依赖：`vue-router` 的 `beforeEach` 返回值机制——返回 location 会中止当前导航并开始新导航；`replace: true` 让重定向替换当前历史项，而不是追加。

变更代码块：

```ts
// 旧：{ path: "/sessions", component: SessionsPage }
// 新：/workspaces/:wid 父路由 + children
{ path: "/workspaces/:wid", component: Shell, meta: { workspace: true },
  children: [{ path: "sessions", component: SessionsPage }, …] }
```

```ts
// 旧：root redirect "/sessions"
// 新：守卫按路径解析
if (isLegacyWorkspacePath(to.path)) {
  const workspaceId = resolveLegacyWorkspace(readLastWorkspaceId(), auth.workspaces);
  if (!workspaceId) return { path: "/workspaces", query: { reason: "select" }, replace: true };
  return { path: legacyWorkspaceTarget(workspaceId, to.path), query: to.query, hash: to.hash, replace: true };
}
```

思路总结：路由表只描述“正常入口”，迁移期的旧入口集中在守卫一处，删兼容时只动一个分支。

检视发现：`isLegacyWorkspacePath` 未覆盖 `/evolution/` 这种尾斜杠写法；实际浏览器/Vue Router 会归一化，暂不修，记作已知弱点。

### `apps/web/src/router/workspace.ts`（A）

职责：不依赖 Vue 的纯路由函数，便于单测。`resolveLegacyWorkspace` 的“只接受确定答案”是本 PR 最重要的不变量；`switchableWorkspaceChild` 把“页面状态隔离”具体化为“丢弃跨空间资源 id”。

检视发现：`rememberWorkspace` 的存储失败被吞掉，符合“存储不可用不阻塞导航”的取舍；代价是同一浏览器在禁用 storage 时每次旧链接都会走“唯一空间/选择页”分支。

### `apps/web/src/api/queryKeys.ts`（M）

职责：集中缓存 key。变更后所有空间资源首段是 `"ws"`，`["ws", wid]` 可直接作为前缀失效。

检视发现：`badCase` 与 `badCaseAnalysis` 仍保留 `sessionId` 尾段，因为页面需要区分“同 case 不同 Session 的归属校验”；这不影响前缀失效。

### `apps/web/src/stores/auth.ts`（M）
