## §1 一页速览

一句话：给每个业务请求一个统一的空间门禁，并让前端启动时一次拿到“我是谁 + 我能去哪些空间”。

比喻：`require_workspace_role` 是门口查工牌的保安——工牌不在名单里就当这层楼不存在（404），工牌等级不够才说“你不能进”（403）；`GET /api/auth/session` 是前台，第一次就把你的工牌和可去楼层清单一起交给你，不用再跑两趟。

| 交付块 | 内容 | 关键位置 |
|---|---|---|
| 权限依赖 | `viewer < member < space_admin`；全局管理员直通；每请求现查成员行 | `apps/api/app/api/deps.py:15`、`apps/api/app/service/workspaces/service.py:35` |
| 会话聚合 | user + 可见空间 + 实时 `used`/`memberCount`/`spaceAdminCount` + 200 条截断 | `apps/api/app/service/workspaces/service.py:70` |
| 批量读取 | 一次列表、一次 used 分组、一次成员分组，无 N+1 | `apps/api/app/db/crud/workspaces.py:126`、`:166`、`:182` |
| 契约 | session 两型由 OpenAPI 生成；新错误码 | `packages/contracts/src/workspaces.ts:37`、`:67` |
| 强制改密 | session 与改密/登出/me 同属白名单 | `apps/api/app/middleware/auth.py:14` |

验证基线（本机实跑）：`pnpm test:api` 全绿、覆盖 90%；`pnpm test:db` 20 passed；`pnpm contract:check`、`pnpm typecheck`、`pnpm typecheck:api`、`pnpm lint:api`、`pnpm verify:flow`、`pnpm verify:flow --diff origin/main`、`pnpm test:gates`、`pnpm lint:docs`、`pnpm verify:docs` 全绿。真实 uvicorn 冒烟结果见 PR 描述。

## §2 架构导览

### 2.1 门禁接在已经验过的 principal 上

中间件先解 Bearer 并写入 `request.state.principal`（`apps/api/app/middleware/auth.py:71` 起）；依赖只读这份已验证的上下文，不重新解析 header（`apps/api/app/api/deps.py:28`）。这样“认证”和“授权”各有一个家：认证失败是 401，空间授权失败才可能是 404/403。

依赖是工厂：`require_workspace_role(minimum)` 在路由声明时固定最低等级，返回一个以 `{wid}` 为路径参数的异步函数（`apps/api/app/api/deps.py:15`–`:37`）。`wid` 的 `min_length=1, max_length=36` 由 FastAPI 校验，非法长度在进入业务前就变成 422。

### 2.2 全局管理员直通，但先确认空间存在

`WorkspaceService.authorize` 的第一分支是全局管理员（`apps/api/app/service/workspaces/service.py:50`）：先 `get(wid)`，不存在仍然 404；存在就返回 `global_admin`，不要求成员行。第二个分支查成员行（`:56`），没有行就 404——空间不存在与不可见共用同一个错误，避免调用方枚举别的空间；角色不足才 403（`:59`–`:64`）。

角色比较是封闭集合上的整数序号（`apps/api/app/service/workspaces/roles.py:11`–`:30`）：`viewer=1`、`member=2`、`space_admin=3`；`global_admin` 不属于存储角色，`role_at_least("global_admin", …)` 为假，因此它只能走管理员分支，不能靠伪造成员行提权。

### 2.3 会话聚合只做常数条查询

`session_payload` 先取列表，`limit = 200 + 1`（`apps/api/app/service/workspaces/service.py:72`–`:78`）：多取一条即可判断“是否还有第 201 个”，不需要 `COUNT(*)`；随后对入选的空间批量查 `used` 与成员统计（`:80`–`:81`），最后逐行组装。查询条数固定为 4（用户、列表、used 分组、成员分组），与空间数量无关。

存储层把“可见列表”收敛成一个方法（`apps/api/app/db/crud/workspaces.py:126`）：管理员走 `select(workspaces)`，普通用户走 `workspaces JOIN workspace_members` 并带出 `role`；统一按 `created_at DESC, id` 排序，保证截断边界稳定。`used_counts` 与 `member_counts` 都用 `GROUP BY workspace_id`（`:166`、`:182`），前者计数 `bad_cases`，后者用 `SUM(CASE role='space_admin')` 同时得到成员数与管理员数。

### 2.4 契约从 OpenAPI 出发

`SessionPayload`/`SessionWorkspace` 是 Pydantic 模型，camelCase 由 `to_camel` 别名生成（`apps/api/app/service/workspaces/schemas.py:10`–`:33`）。`contract:generate` 把它们写进 `openapi.json` 与 `api.d.ts`；`packages/contracts/src/workspaces.ts` 中这两个类型从手写接口改为 `components["schemas"][…]` 别名（`:37`、`:67`），其余管理类型等 m7-05 端点落地再替换。

### 2.5 强制改密窗口内的会话恢复

强制改密时中间件只放行改密、登出、`me`；本 PR 把 `session` 加入同一白名单（`apps/api/app/middleware/auth.py:14`–`:19`）。这对应设计 05 §4.1：改密前先恢复用户与空间，改密后再刷新 token。

## §3 数据流走查

### 剧本 A：业务请求访问一个空间（m7-05 起复用）

1. `GET /api/workspaces/ws-harness/members` 带 Bearer → 中间件验签，`request.state.principal = {user_id, role, mcp}`（`apps/api/app/middleware/auth.py:71`）。
2. 路由声明 `Depends(require_workspace_role("member"))` → 依赖取 `wid="ws-harness"`（`apps/api/app/api/deps.py:23`）。
3. `authorize`：普通用户查 `workspace_members(ws-harness, user_id)`（`apps/api/app/service/workspaces/service.py:56`）。
4. 无行 → `404 WORKSPACE_NOT_FOUND`；角色序号不足 → `403 WORKSPACE_FORBIDDEN`；通过 → `WorkspaceAccess{workspace_id, role}` 交给路由。
5. 成员变更在下一次请求立即生效，因为角色不在 token 里。

### 剧本 B：前端启动恢复会话

1. `GET /api/auth/session` → 中间件放行（登录用户，含 `mcp=true`）。
2. `auth.session` 用 principal 读用户行；用户消失返回 401（`apps/api/app/api/auth.py:160` 起）。
3. `session_payload` 取 201 条可见空间（管理员全部、普通用户仅成员空间），判断截断（`apps/api/app/service/workspaces/service.py:72`–`:78`）。
4. 对前 200 个 id 批量取 `used` 与成员统计，组装每项的 `role/quota/used/memberCount/spaceAdminCount`（`:83`–`:97`）。
5. 返回 `{user, workspaces, truncated}`；前端只需一次请求。

### 剧本 C：强制改密

1. 首次登录 seed 管理员，token 带 `mcp=true`。
2. `GET /api/users` → 403 `PASSWORD_CHANGE_REQUIRED`（冒烟实测）。
3. `GET /api/auth/session` → 200，返回 `mustChangePassword=true` 与空间列表（冒烟实测）。
4. 改密 → `POST /api/auth/refresh` 换新 token → 再拉 session。

## §6 讨论点

### 6.1 `used` 依赖外部 `bad_cases` 表的存在

- **位置**：`apps/api/app/db/crud/workspaces.py:166`
- **现象**：本机冒烟第一次请求 `auth/session` 时返回 500，原因是从未建过外部 `bad_cases` 表；执行 fixture 引导后恢复 200。
- **问题**：空间基础表由迁移创建，外部 bad-case 表由上游 schema/fixture 创建；两者不同步时，会话聚合成第一个暴露 500 的读路径。
- **预判**：这是部署前置条件而非本 PR 的语义缺陷；`/api/sessions` 等问题读路径同样依赖该表。可在健康检查或启动期显式提示外部 schema 未就绪，但本轮不扩范围。
- **结论**：留空给维护者拍板。

### 6.2 SQL 条数与设计措辞的对齐

- **位置**：`apps/api/app/service/workspaces/service.py:72`–`:81`
- **现象**：实际为 4 条常数查询：用户、可见列表、used 分组、成员分组；设计 §5.15 写作“3 条 SQL”。
- **问题**：措辞与实现差一条，读者可能误以为成员数和管理员数是分开查的（实际用 `SUM(CASE)` 合并）。
- **预判**：常数条查询满足“不做 N+1”的意图；可只改设计措辞或把用户查询算作会话之外的输入，不建议为凑数字再合并查询。
- **结论**：留空给维护者拍板。

### 6.3 存储角色 `global_admin` 的失败模式不一致

- **位置**：`apps/api/app/service/workspaces/roles.py:33`
- **现象**：若成员行被误写成 `global_admin`，授权路径因等级表缺失而 403，会话组装却会原样输出 `role=global_admin`。
- **问题**：数据库没有角色 CHECK 约束，两个路径对同一脏数据给出不同结论。
- **预判**：当前只有 m7-05 的服务端写成员会落库；在该写路径加角色校验与唯一约束即可。本 PR 的直接风险低，属于应在成员写操作落地时收口的已知弱点。
- **结论**：留空给维护者拍板。

### 6.4 可见空间排序未在设计里固定

- **位置**：`apps/api/app/db/crud/workspaces.py:136`
- **现象**：实现按 `created_at DESC, id` 排序，测试据此断言最新空间在前。
- **问题**：设计 §3.7 没有规定顺序；未来前端可能更希望按名称或“最近访问”。
- **预判**：新建空间靠前符合空间切换器的直觉，且与 `ix_workspaces_created_at` 索引一致；若要改成名称序只动一处。
- **结论**：留空给维护者拍板。

### 6.5 依赖目前只被测试路由消费

- **位置**：`apps/api/app/api/deps.py:15`
- **现象**：生产路由还没有 `{wid}` 业务端点，权限矩阵通过测试挂载的三条探针路由验证。
- **问题**：第一个真实消费者若把路径参数命名为 `workspaceId` 而不是 `wid`，依赖会拿不到值并 422。
- **预判**：设计 §4.16 已把路径参数定为 `{wid}`；m7-05/m7-06 接入时沿用即可，可在那时补一条真实端点的集成测试。
- **结论**：留空给维护者拍板。

## §9 文件级代码分析

### 9.1 `apps/api/app/api/deps.py`（A）

职责：把“空间 + 最低角色”变成一个可声明在路由上的依赖。

关键依赖是 FastAPI 的 `Depends` 与 `Path`：路由声明时调用工厂，请求时执行闭包。它像门口查工牌的保安——不关心你从哪个门进来，只认中间件已经验过的 `request.state.principal`。

```python
def require_workspace_role(minimum: WorkspaceMemberRole) -> WorkspaceRoleDependency:
    async def dependency(
        request: Request,
        wid: Annotated[str, Path(min_length=1, max_length=36)],
    ) -> WorkspaceAccess:
        principal = request.state.principal
        service = cast(WorkspaceService, request.app.state.workspaces)
        return await service.authorize(
            user_id=principal.user_id,
            user_role=principal.role,
            workspace_id=wid,
            minimum=minimum,
        )
    return dependency
```

为什么这么写：`minimum` 在路由声明期固定，避免每个处理函数自己传角色字符串；返回 `WorkspaceAccess` 而不是布尔值，后续端点可直接拿到有效角色做更细的判断。

检视发现：无；已知“路径参数必须叫 `wid`”见 §6.5。

### 9.2 `apps/api/app/service/workspaces/roles.py`（A）

职责：角色封闭集合与等级比较，供依赖与测试共用。

`WORKSPACE_ROLE_RANK` 是唯一排序事实；`role_at_least` 对未知角色返回 `False`（失败关闭），`effective_role` 把存储字符串收窄成契约联合。`_WORKSPACE_ROLES` 与 `WorkspaceRole` 目前是一份手工同步的列表，属于两行常量的轻量重复；若以后角色扩展，两处要一起改，可在契约生成后由类型推导替代。

检视发现：脏角色两路径不一致，见 §6.3。

### 9.3 `apps/api/app/service/workspaces/service.py`（A）

职责：授权规则与会话聚合的唯一业务入口。

旧代码：无。新代码的关键是“先取 201 条再截断”和“聚合只针对入选空间”：

```python
visible = await self._repository.list_visible(
    user_id=user.id,
    include_all=user.role == "admin",
    limit=SESSION_WORKSPACE_LIMIT + 1,
)
truncated = len(visible) > SESSION_WORKSPACE_LIMIT
selected = visible[:SESSION_WORKSPACE_LIMIT]
workspace_ids = [row.workspace.id for row in selected]
used_counts = await self._repository.used_counts(workspace_ids)
member_counts = await self._repository.member_counts(workspace_ids)
```

为什么这么写：用一条 `LIMIT 201` 代替“先 COUNT 再查 200”，既省一条查询，也避免两次查询之间新增空间导致“截断标记与列表长度不一致”。`_not_found()` 把两处 404 收成一个工厂，消息与错误码不会漂移。

检视发现：SQL 条数措辞见 §6.2；外部表依赖见 §6.1。

### 9.4 `apps/api/app/db/crud/workspaces.py`（A）

职责：空间与成员的唯一读取层，负责 SQL 形状。

旧代码：无。记录类型（`WorkspaceRecord`/`WorkspaceMembership`/`VisibleWorkspace`/`WorkspaceMemberCounts`）把行映射挡在服务层之外；`list_visible` 用 `include_all` 分流出管理员全量与成员 JOIN 两条 SQL，排序与截断都在库内完成。

`member_counts` 的 `SUM(CASE …)` 是一个小技巧：

```python
select(
    workspace_members.c.workspace_id.label("workspace_id"),
    func.count().label("member_count"),
    func.sum(
        case((workspace_members.c.role == "space_admin", 1), else_=0),
    ).label("space_admin_count"),
)
```

一次分组同时得到“总成员数”和“空间管理员数”，避免第二条按角色过滤的查询；`or 0` 兜住空分组时 `SUM` 返回 NULL 的方言差异。空 id 列表提前返回，避免生成 `IN ()`。

### 9.6 `apps/api/app/api/auth.py`（M）

职责：在既有认证路由里追加会话聚合端点。

变更前该文件只有 login/refresh/logout/change-password/me；变更后新增 `workspaces_from` 取用函数（`:31`）与 `GET /session`（`:169` 起）。端点先读用户行再组装会话：用户被删除时返回 401，而不是空壳 session。

```python
@router.get("/session", dependencies=[Security(BEARER_AUTH)], ...)
async def session(request: Request) -> SessionPayload:
    principal = request.state.principal
    user = await identity_from(request).get_user(principal.user_id)
    if user is None:
        raise AppError(status_code=401, code=ErrorCode.AUTH_REQUIRED, ...)
    return await workspaces_from(request).session_payload(public_user(user))
```
