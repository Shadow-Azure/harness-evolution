## §1 一页速览

**一句话**：把「近 7 天」这个快捷范围和一个默认粒度绑定起来 —— 选 7 天自动按日看，选 30/90 天自动按周看，用户手点日/周/月仍然优先；URL 里的裸 `?range=7` 同样补齐成 `grain=day`。

**一个比喻**：这像相机的「场景模式」。你选「拍近处」（7 天），相机自动切微距（日粒度）；选「拍远景」（30/90 天），自动切广角（周粒度）。但你之后手动拧到别的档位（点粒度按钮），它不会因为相机测了一次光（数据刷新）就把你的档位抢回去。真正麻烦的是「自定义焦距」：它沿用你当前档位，而不是自己再猜一次。

**交付块**

| 块 | 内容 | 风险 |
|---|---|---|
| URL 模型 | `parseOverviewQuery` 的默认 grain 依赖 `range` | 低；纯函数，有单测 |
| 页面交互 | `setRange` 给快捷范围写显式 grain | 低；与原型一致 |
| 测试 | 单测 15 条 + 组件测 + 1 条 E2E | 低；见 §6 测试质量 |
| 设计基线 | 原型/两份设计文档补规则 | 无运行时影响 |

## §2 架构导览

### 2.1 URL 模型：一个纯函数决定默认粒度

总览页把所有筛选状态放在 URL 里，`parseOverviewQuery` 是唯一入口（`overviewUrl.ts:196`），`overviewQuery` 是唯一出口（`:278`）。页面只读 `parsed.state`，所以默认值的改动必须落在这对函数里。

本次改动只有一处（`overviewUrl.ts:210`–`216`）：

```ts
// 旧
const grain = rawGrain && GRAIN_VALUES.has(rawGrain) ? rawGrain : DEFAULT_OVERVIEW_STATE.grain;
// 新
const grain = rawGrain && GRAIN_VALUES.has(rawGrain)
  ? rawGrain
  : range === 7 ? "day" : DEFAULT_OVERVIEW_STATE.grain;
```

语义是「**显式合法 grain 最高优先；否则 7 天给 day，其余给默认 week**」。因为 `parseRange`（`:154`–`169`）已经把 `range` 归一成 `7 | 30 | 90 | "custom"`，这里只需判 `=== 7`。

注意 `overviewQuery` 无条件输出 `grain`（`:282`），所以任何 URL 规范化后都带显式 grain —— 这让「默认值只影响首次解析」这个边界非常干净：一旦页面跑过一次规范化，后续刷新/前进后退看到的都是显式值，不会再被默认规则二次影响。

### 2.2 页面交互：范围按钮“拥有”默认粒度

`setRange`（`Index.vue:185`–`205`）分两支：

- `custom`：从当前 summary 的服务端窗口预填 from/to，**不动 grain**（注释在 `:188`–`:191`）。
- 快捷范围：`replaceState({ range, from: "", to: "", grain: range === 7 ? "day" : "week" })`（`:199`–`:204`）。

这里用 `router.replace` 而非 `push`（`:171`–`174`），所以点范围不会新增历史条目 —— 与既有筛选行为一致。

`setGrain`（`:215`–`217`）只 patch grain；`clearFilters`（`:223`–`233`）回到 90/week 默认。粒度按钮本身在 `FilterBar.vue:163`–`175`，是独立控件，所以「先手改粒度、后续数据刷新」不会被覆盖 —— 数据刷新只重算 `trendFilters`（`Index.vue:60`–`63`），不写 URL。

### 2.3 URL 规范化 watcher：默认值落地的最后一环

`Index.vue:323`–`334` 的 watcher 在 `route.query` 与 `overviewQuery(parsed.state)` 不一致时 `router.replace` 到规范形式。这是 `?range=7` → `?range=7&grain=day` 真正写回地址栏的地方（`parseOverviewQuery` 的 `sanitized` 标记只用于测试，页面不信它）。

watcher 是收敛的：replace 后 `parsed` 重算、`sameOverviewQuery` 返回 true，不会自激循环；`flush: "post"` 保证首次渲染已挂载。它只在 `route.name === "workspace-overview"` 时工作（`:326`），离开页面不误写。

### 2.4 原型与设计文档是同一事实源

原型的状态默认是 90/week（`harness-evolution.html:5638`–`5642`）。本次在两条路径补默认：点击（`:6837`–`:6846`）和启动解析（`:6964`–`:6967`）。设计文档只加规则句（`design-v2.md:121`、`08:512`），与实现一一对应。

## §3 数据流走查

**主线剧本：默认 90 天/周 → 点「近 7 天」→ 图表出现 7 个日桶**

1. 落地 `?range=90&grain=week`（或由 `WorkspacePicker` 用 `overviewQuery(DEFAULT_OVERVIEW_STATE)` 生成）。`parseOverviewQuery` 得到 `range=90, grain=week`。
2. 点「近 7 天」（`FilterBar.vue:108`–`120` → `emit('update:range', 7)`）。
3. `setRange(7)` 执行 `replaceState({ range: 7, from: "", to: "", grain: "day" })`（`Index.vue:199`）。
4. 路由变成 `?tab=cases&range=7&grain=day`；`parsed` 重算，watcher 比对相等，不再写 URL。
5. `trendFilters` 变成 `{ range: 7, objects, grain: "day" }`（`Index.vue:60`–`63`）；`useOverviewTrend` 以新 key 重取。
6. 服务端 `resolve_window` 得到 `[today-6, today]`（`apps/api/app/service/overview/window.py:103`），`grain=day` 且 span=7 ≤ 92 不降级（`:169`–`170`），返回 7 个连续日桶。
7. `activeGrain = data.grain = "day"`，hint 渲染「按日聚合」（`Index.vue:513`–`516`），`StackedBucketChart.vue:211` 给每个桶挂 `data-bucket="YYYY-MM-DD"`，当天桶出现。

**分支剧本 A：裸 `?range=7`**

1. `parseOverviewQuery` 无显式 grain，`range=7` → `grain="day"`，`sanitized=true`。
2. 首次渲染就用 day 发请求（UI 不闪周桶）。
3. watcher 把地址栏 replace 成 `?range=7&grain=day`。此后刷新仍是显式 day。

**分支剧本 B：显式 `?range=7&grain=week`**

1. `rawGrain="week"` 合法 → grain 保留 week，`sanitized=false`。
2. watcher 无动作，请求 `grain=week`，图表仍是 11-09 / 11-16 两个周桶 —— 旧链接不被静默改写。

**分支剧本 C：30/90 与自定义**

1. 在 7 天/day 下点「近 30 天」：`setRange(30)` 写 `grain=week`，即使之前手选过月也会被覆盖一次（Note 已声明）。
2. 点「自定义」：`setRange("custom")` 用当前 summary 窗口预填，grain 保持 day；URL 带显式 `grain=day`，重新加载仍 day。
3. 手写 `?range=custom&from=…&to=…`（无 grain）：`parseRange` 归为 custom，grain 走默认 week —— 与「自定义沿用当前粒度」不冲突（此时“当前”就是默认）。

## §6 讨论点

### 6.1 点“已选中”的快捷范围也会重置粒度（non-blocking，建议合并前明确）

- **位置**：`apps/web/src/pages/overview/Index.vue:199`–`204`；对照 `setTab` 的早退守卫在 `:176`–`179`，设计文档说法在 `plans/fullstack-design/08-frontend-implementation.md:512`。
- **现象**：`setRange` 只判断是否 `custom`，没有 `if (state.value.range === range) return`。因此当用户手动把粒度改成 day 后，再点一次本来就处于选中态的「近 90 天」，`range` 没变但 `grain` 被写回 week。实测路径：默认 `?range=90&grain=week` → 点「日」得 `?range=90&grain=day`（合法且服务端 90 天 ≤92 天不降级）→ 再点「近 90 天」，URL 变回 `grain=week`。
- **问题**：文档与 Note 把联动描述为「**时间范围变化时**联动」（`08:512`、Note 第 14 行），但这个分支在范围**没有变化**时也触发了，属于文档措辞与实现语义的偏差。它还会让「显式 grain 被尊重」的承诺在一次看似无害的重复点击后失效。原型 `harness-evolution.html:6837`–`6846` 同样无条件重置，所以这不是生产独有的 bug。
- **预判**：加一行 `if (state.value.range === range) return;` 最贴合文档措辞，也与 `setTab` 的写法一致；代价是用户无法靠重复点范围按钮“重置粒度”，但粒度本就有独立按钮。若维护者选择保持原型行为，则把 Note/08 的「时间范围变化时联动」改成「点击快捷范围即联动」即可。功能上无数据损坏，非阻塞。
- **结论**：已按预判采用守卫。生产 `setRange` 与原型点击处理都加了 `if (当前范围 === 目标范围) return;` 早退，并补组件测试覆盖「手动选周后重复点当前范围仍保持周」。检视时那处未提交的原型改动已随本 PR 一起提交，原型与实现不再分叉。

### 6.2 自定义 7 天窗口仍可能按周显示（non-blocking，产品后续）

- **位置**：`apps/web/src/pages/overview/overviewUrl.ts:214`–`216`、`Index.vue:207`–`213`；后端窗口语义 `apps/api/app/service/overview/window.py:103`。
- **现象**：从默认 90/week 进入「自定义」，`setRange("custom")` 按设计保留当前 grain=week；用户在日期框里把窗口收窄到 7 天，仍然按周展示，可能再次出现「当天没有独立柱」的原始症状。相反，从 7 天/day 进自定义则保持 day。
- **问题**：issue 的非目标明确写了「自定义区间保持当前粒度」，所以这是**已声明的取舍**，不是实现错误；但「同一个 7 天窗口因入口不同而粒度不同」对运营来说不易解释，原始反馈（#375）的困惑可能以另一条路径复现。
- **预判**：本 PR 不必扩面；若要收敛，可在自定义窗口 span ≤ 7 时也提示「建议日粒度」，或后续单独讨论「自定义是否也按 span 给默认值」。当前先在 Note 里补一句「自定义沿用进入时的粒度，不按 span 推断」即可，避免未来把它当回归。
- **结论**：接受当前取舍；Agent Note 的 Consequences 已补「自定义窗口沿用进入时的粒度，不按 span 推断，从 90 天/周进入 7 天自定义仍需手动切日」。

### 6.3 E2E 尾部断言是重言式，且未断言当天桶计数（non-blocking，测试质量）

- **位置**：`tests/e2e/m8-04-overview.test.mjs:1161`–`1211`（`waitForDocument` 条件与随后的 `assert`）。
- **现象**：`waitForDocument` 只有在条件为真时才返回（`tests/support/runtime.mjs:114`–`122`，超时直接 throw），而条件里已经要求 `search.get("grain") === "day"`、`buckets.length === 7`、`hint.includes("按日聚合")`、`[data-bucket=day0]` 存在。因此后面 `assert.equal(seven.grain, "day")`、`assert.equal(seven.buckets, 7)`、`assert.match(seven.hint, /按日聚合/)` 以及 30/90 的 `assert.equal(..., "week")` 都不会失败，属于装饰性断言。真正有效的断言是等待条件本身。
- **问题**：这不是假通过（条件真的被轮询验证了），但会给人「有细粒度断言」的错觉；更实质的是验收标准写「当天桶可见且**计数正确**」，而 E2E 只断言桶存在，不断言当天桶的 `total`（种子数据 day0 有 6 条、day1 有 5 条）。如果聚合把当天数据错算进别的桶，现有 E2E 仍会绿。
- **预判**：把 `data-bucket=day0` 的柱文本/数值纳入等待条件并断言为 6（或用 API 返回的桶值），再把尾部重言式断言删掉或改成独立可失败断言。属于测试增强，不阻塞。
- **结论**：已修复。E2E 的等待条件现在从 `data-bucket=day0` 的 `aria-label` 解析自身/前置数量，要求总数等于 6，7 天分支返回后的重复装饰断言已删，30/90 分支保留简单的周粒度确认。

### 6.4 显式 week 的“保留”只测到解析层，没测到页面规范化（non-blocking，测试缺口）

- **位置**：`apps/web/src/pages/overview/overviewUrl.test.ts:38`–`46`（解析层测了 `?range=7&grain=week`）、`apps/web/src/pages/overview/Index.vue:323`–`334`（页面 watcher 未覆盖该输入）。
- **现象**：解析单测证明 `parseOverviewQuery({range:"7", grain:"week"})` 返回 week，但没有组件级用例断言「以 `?range=7&grain=week` 挂载页面后，watcher 不会把 grain 改回 day」。目前 watcher 的比较逻辑确实会保留 week（因为 `overviewQuery` 原样输出 week），C 分支剧本是人工推演。
- **问题**：这是本 PR 最重要的兼容承诺（旧链接不被改写），却缺少端到端断言；未来若有人把默认逻辑挪进 watcher 或 `overviewQuery`，解析层单测仍绿。
- **预判**：在 `Index.test.ts` 加一条 `mountPage('...overview?range=7&grain=week')` 断言 `route.query.grain === 'week'` 且 trend 请求带 `grain=week`。成本很低，建议补。
- **结论**：已修复。`Index.test.ts` 新增页面级深链用例：以 `?range=7&grain=week` 挂载，断言规范 URL 与 trend 请求都保持 week。

### 6.5 原型与实现在非法输入上不完全一致（no-harm）

- **位置**：`plans/ui-prototype-v2/harness-evolution.html:6964`–`6967`。
- **现象**：原型启动逻辑是 `if (q.has('grain')) grain = q.get('grain')`，即 `?range=7&grain=bogus` 会把 `"bogus"` 直接塞进状态；生产 `parseOverviewQuery` 只在 grain 属于 `GRAIN_VALUES` 时才采用，否则 7 天回落 day。另外原型用 `range=0` 表示自定义，而生产 URL 用 `range=custom`，`Number("custom")` 在原型里是 `NaN`。
- **问题**：原型是 `plans/` 下的设计工件，不参与运行时；生产更严格是好事。但「原型与实现默认一致」的表述需要限定为**合法输入**，否则未来用原型做验收会在非法 URL 上得到不同结论。
- **预判**：无需改生产。若要严格对齐，可在原型 boot 里对 grain 做白名单、把 `range=custom` 映射到 0；但这是原型侧的既有欠账，不阻塞本 PR。
- **结论**：标注为原型边界差异，不改。

## §9 文件级代码分析

### `apps/web/src/pages/overview/overviewUrl.ts`（M）

**职责**：总览页 URL 的唯一解析/序列化器；纯函数，无副作用。**前身**用 `git show a849aa7:...overviewUrl.ts` 对照，本次只改 grain 默认分支。

**关键机制**：`parseRange` 先把 `range` 归一成 `7|30|90|custom`（`:154`–`169`），grain 默认才有确定的判断对象。`overviewQuery` 无条件输出 grain（`:282`），保证规范化后的 URL 自描述。

**变更对照**

```ts
// 旧
: DEFAULT_OVERVIEW_STATE.grain;
// 新
: range === 7 ? "day" : DEFAULT_OVERVIEW_STATE.grain;
```

为什么这么写：把「默认粒度」表达为 `range` 的函数，而不是在页面里散落判断；`parseOverviewQuery` 被 `parsed` 计算属性每次路由变化重算，默认逻辑只有一处。

**实现思路**：显式合法值优先 → 否则按 range 给默认 → 其他回落 `DEFAULT_OVERVIEW_STATE`。三行以内。

**检视发现**：无缺陷。边界正确：非法 grain 回落、custom 回落 week、30/90 回落 week。唯一值得注意的语义是「custom 无 grain 时是 week」（见 6.2），与「自定义沿用当前粒度」不冲突。

### `apps/web/src/pages/overview/Index.vue`（M）

**职责**：总览页容器；把 URL 状态翻译成四个 query，并承载所有 URL 写操作。**前身**对照后，本次只改 `setRange` 的 patch 内容。

**变更对照**

```ts
// 旧
void replaceState({ range, from: "", to: "" });
// 新
void replaceState({ range, from: "", to: "", grain: range === 7 ? "day" : "week" });
```

为什么这么写：让「快捷范围」显式拥有默认粒度，而不是依赖 parse 的兜底 —— 否则从 7/day 切到 30 时，旧 grain=day 会被原样保留，30 天窗口就变成 30 个日桶，与「30/90 默认周」的目标相反。显式写入也保证 URL 立即自描述，不依赖 watcher 补写。

**实现思路**：范围按钮 = 「范围 + 该范围的默认粒度」的原子操作；粒度按钮是独立覆盖通道；自定义不动粒度。

**检视发现**：如 6.1，缺少「同值不重置」守卫；与 `setTab` 不一致，但与原型一致。其余无缺陷。
