## §1 一页速览

一句话：这个 PR 给原本只有健康检查的 API 装上一扇真实身份门，用户通过 argon2id 密码换取短命 access JWT 和受限 refresh cookie，所有业务 API 由中央中间件统一验证，SSE 只拿一次性票据。

生活化比喻：access token 像一张 30 分钟有效的门禁卡，refresh cookie 像放在只向 `/api/auth` 开放的保险盒里的续卡凭据；中间件是唯一的门卫，强制首登改密是“临时卡必须先去前台换密码后才能进办公区”；SSE 票据则像只能刷一次、60 秒失效的访客条。

| 交付块 | 结论 |
|---|---|
| users 迁移与 repository | 基本符合设计；SQLite/MySQL CI 均通过 |
| 登录、刷新、登出、改密 | 主链路可用；发现旧密码复用和校验明文回显两个实质问题 |
| 中央鉴权与 admin 边界 | 符合 fail-closed、强制改密和 `/api/users*` 设计要求 |
| 登录限流 | 有并发安全滑动窗口和窗口恢复测试 |
| SSE 票据 | principal/topic/cursor/TTL/单次消费齐全；长期过期错误码存在边界漂移 |

## §2 架构导览

### 2.1 组合根与生命周期

`apps/api/app/main.py:41-62` 在 lifespan 中按 `database → migration → identity-seed` 顺序初始化。初始化异常只记录阶段、方言和异常类型，健康检查改为 503，不把数据库 URL 或驱动上下文暴露出去。

`main.py:74-95` 把 settings、database、identity 和 limiter 放进应用状态，再注册 RequestContext、CORS、限流、鉴权和四个 router。认证逻辑集中在一个门卫，而不是散落到每个 endpoint。

### 2.2 Bearer 门卫

`apps/api/app/middleware/auth.py:25-62` 的流程是：

```text
公开路径放行
  → 非 /api 放行
  → 解析 Bearer
  → 验签并构造 principal
  → 强制改密闸
  → /api/users* admin 闸
  → 写入 request.state.principal
  → 进入 router
```

这意味着未来任何新增 `/api/*` 路由默认受保护；忘记在路由上写 dependency 不会意外公开。OpenAPI 的 `BearerAuth` 是文档声明，真正的强制点在中间件。

### 2.3 Token 与 refresh 旋转

`service/identity/tokens.py:35-69` 签发 access/refresh；`tokens.py:71-123` 用同一 HS256 密钥验签，并通过 `typ` 防止 refresh 冒充 access。refresh grant 还带回签名中的 `exp`，供撤销索引在令牌到期后自动清理。

`service/identity/service.py:79-98` 先重读用户，再在 `revocations.consume_once()` 中原子领取 `jti`。两个并发 refresh 只会有一个进入签发阶段，另一请求得到 `AUTH_EXPIRED`。

比喻：每个 refresh token 像一张只能盖章一次的车票；`asyncio.Lock` 是唯一的盖章窗口，两个请求同时伸手时也只能有一张被盖章。

### 2.4 用户存储与迁移

`db/models/users.py:13-27` 定义跨库表，`db/crud/users.py:20-113` 隔离读写；service 不直接拼 SQL。`alembic/versions/0002_users.py:20-40` 建立同构列、唯一用户名和 `must_change_password DEFAULT true`。

时间戳由 `utils/time.py:9-18` 写为 Asia/Shanghai。DDL 没有时间默认值，符合“数据库不借本地时钟猜业务时间”的规则。

### 2.5 票据状态机

`service/identity/tickets.py:49-61` 把 principal、topics、cursor 和 expiry 封进进程内 grant。`consume()` 同时在锁内完成取出、过期判断和清理，避免两个 SSE 消费者拿到同一张票。

过期 grant 被清理时会保留 60 秒 tombstone，因此“刚过期但已被下一次签发顺手清理”的票仍返回 `TICKET_EXPIRED`。tombstone 到期后会再次被清理，见 §6 的边界讨论。

### 2.6 错误与契约

`app/errors.py:19-34` 把错误码变成闭集，`ErrorResponse` 是统一外壳。OpenAPI 对登录声明 401/403/422/429，对用户创建声明 401/403/409/422，受保护操作统一声明 `BearerAuth`。

生成链路是 FastAPI handler/模型 → `openapi.json` → `openapi-typescript` → `api.d.ts`；`contract:check` 防手改或漏生成。

## §3 数据流走查

### 场景 A：初始管理员登录并完成首登改密

1. 空库启动，`main.py:49-50` 调 `seed_admin_if_empty()`。
2. `identity/service.py:40-53` 只在 users 为空且 env 用户名/密码非空时写入 argon2id 哈希，并把 `must_change_password=true`。
3. `POST /api/auth/login` 在 `api/auth.py:57-72` 验证密码、更新 `last_login_at`、返回 access token 和 refresh cookie。
4. 中间件读取 access 的 `mcp=true`，只允许 `/me`、登出、改密。
5. `POST /api/auth/change-password` 在 `service.py:110-130` 校验旧密码、更新哈希和时间戳、置 `must_change_password=false`。
6. 前端按设计调用 `/refresh`；refresh 重读用户并签出 `mcp=false` 的新 access token。

这里发现一个实际短路：第 5 步没有比较新旧密码是否相同；提交 `oldPassword == newPassword` 会得到 204，并直接解除强制改密。详见 §6 D1。

### 场景 B：access 过期后刷新并拒绝旧 refresh 重放

1. 业务 API 收到过期 access，`middleware/auth.py:39-43` 返回 `AUTH_EXPIRED`。
2. 前端调用 `/api/auth/refresh`，cookie 只作用于 `/api/auth`。
3. `service.py:83-98` 验签、重读用户、原子消费 `jti`，成功后写新 refresh cookie。
4. 旧 cookie 重放时，`revocations.consume_once()` 返回 false，统一报 `AUTH_EXPIRED`。
5. 两个并发重放只有一个成功；测试覆盖在 `test_auth.py:293-318`。

### 场景 C：业务 API 与 admin 边界

1. 任意 `/api/*` 先经过中央门卫。
2. 缺 token → `AUTH_REQUIRED`；过期 → `AUTH_EXPIRED`；非法 → `AUTH_REQUIRED`。
3. `mcp=true` 访问 `/api/users` → `PASSWORD_CHANGE_REQUIRED`。
4. 普通 member 访问 `/api/users*` → `FORBIDDEN`；admin 才进入 router。

### 场景 D：申请一次性 SSE 票据

1. 已登录用户向 `/api/events/ticket` 提交 `topics` 和游标。
2. `api/events.py:27-37` 只接受 `run:{rid}` 形状，并把当前 principal 写入 grant。
3. 响应只返回 opaque ticket、TTL 和 topics，不返回用户身份。
4. 后续 SSE consumer 消费即删除，重放为 `TICKET_INVALID`，超时为 `TICKET_EXPIRED`。

### 场景 E：请求体校验失败

1. Pydantic 发现密码过长、缺字段或类型错误。
2. `errors.py:149-160` 捕获 `RequestValidationError`，把 `validation_error.errors()` 序列化进 `details`。
3. 实测发现该数组包含 `input`，会把用户提交的明文密码原样放回响应。详见 §6 D2。

## §6 讨论点

### D1 首登可通过“改成原密码”绕过

**位置**：`apps/api/app/service/identity/service.py:110-130`、`apps/api/app/db/crud/users.py:92-105`

**现象**：实测用 `oldPassword == newPassword` 调 `/api/auth/change-password` 返回 204；随后 refresh 返回 200，`mustChangePassword` 变为 false，`/api/users` 返回 200。

**问题**：设计要求初始密码“由他人设定且本人尚未更换”，并强制首次登录改密。服务端只验证旧密码正确，没有验证新密码确实不同，因此用户可继续使用管理员给的临时密码。

**预判**：这是服务端可绕过的功能缺陷，应优先级修复。最小修法是在改密业务规则中拒绝新旧密码相同，并用稳定错误码或 422 表达“新密码未变化”；同时补一条端到端测试，证明 204 不会在相同密码时出现。

**结论**：已修复（2026-10-25）。新旧密码相同时返回 `422 VALIDATION_INVALID`，不改密码、不清 `mustChangePassword`；端到端测试确认 refresh 后的 principal 仍被强制改密闸拦截。

### D2 422 响应会回显明文密码

**位置**：`apps/api/app/errors.py:149-160`

**现象**：向 `/api/auth/login` 提交 129 字符密码，422 JSON 的 `details.errors[0].input` 包含完整的 129 字符明文。改密的 `oldPassword`/`newPassword` 或建用户 temporary password 走同一 handler，也有同样风险。

**问题**：issue 明确要求“密码和哈希不进日志或 payload”，数据库设计也要求密码材料不出服务边界。当前行为会把密码放进 API response、浏览器日志和任何采集错误响应的监控系统。

**预判**：这是安全缺陷，应优先修复。修复时应构造不含 `input` 的安全校验错误摘要，只保留 `type/loc/msg`（必要时安全白名单），不要只针对某一个 password 字段做字符串补丁。补回归测试覆盖 login 和 change-password。

**结论**：已修复（2026-10-25）。统一 422 handler 只输出 `type/loc/msg`，不再序列化 `input/ctx/url`；登录和改密的超长密码测试均断言完整响应不含明文密码。

### D3 过期票据的稳定错误码只维持一个 tombstone 窗口

**位置**：`apps/api/app/service/identity/tickets.py:63-99`

**现象**：ticket 在 t=100 秒签发、t=161 秒被下一次签发触发清理后仍返回 `TICKET_EXPIRED`；等到 t=223 秒 tombstone 也已清理，同一张过期票再次 consume 会变成 `TICKET_INVALID`。

**问题**：接口错误码表把“超过 60 秒”定义为 `TICKET_EXPIRED`，没有附加“仅在额外 60 秒内”。bounded tombstone 解决了内存增长，但没有让错误码在任意时间都稳定。

**预判**：无安全影响，但会让客户端诊断和重连日志随等待时间改变。若接口承诺稳定错误码，可把 expiry 编进不可伪造票据或采用有界但更长/可配置的 tombstone；若接受短期区分，应把限制写进契约和 Agent Note，而不是只存在于实现细节。

**结论**：已修复（2026-10-25）。删除固定 tombstone，票据改为携带 HMAC 认证的微秒到期时间；活动 grant 仍只存内存并单次消费，远期过期稳定返回 `TICKET_EXPIRED`，伪造、篡改、非 ASCII 签名和已消费票返回 `TICKET_INVALID`。独立 scoped re-review 已批准。

### D4 JWT 密钥只校验非空，未校验强度

**位置**：`apps/api/app/config.py:41-43,66-70`

**现象**：`HE_JWT_SECRET` 只要非空就可启动；实测短密钥会让 PyJWT 发出 `InsecureKeyLengthWarning`，而应用仍正常签发/验证。

**问题**：当前没有生产事故，但弱 HMAC 密钥会降低 access/refresh token 的离线猜测成本。设计只写了“必填”，没有规定最小字节数。

**预判**：建议至少按 HS256 推荐值强制 32 字节，或把强度要求写成部署决策；这不是本 PR 主链路的阻塞项。

**结论**：延后（2026-10-25）。权威设计只要求 `HE_JWT_SECRET` 必填，没有定义最小长度；32 字节强度需先更新架构/配置决策，不在本 issue 引入未定义的部署破坏。残余风险由后续 Agent Note 与配置变更承接。

### D6 冒烟报告生成嵌套 table

**位置**：`.agents/skills/computer-use-smoke-reporting/scripts/render-smoke-report.mjs:79,86,119`、`.agents/skills/computer-use-smoke-reporting/template/report.template.html:92,107`

**现象**：renderer 返回完整 `<table>`，模板又包一层 `<table>`，最终报告出现 `<table><table>`。

**问题**：HTML 表格结构非法，浏览器会自行纠错，导致报告在不同浏览器中的布局和可访问性树不可预测。

**预判**：应由模板独占 table 边界，renderer 只提供 thead/tbody 片段，并用真实 renderer 测试锁定。

**结论**：已修复（2026-10-25）。renderer 输出片段，新增真实渲染回归测试，重生成报告不再嵌套 table。

### D7 自动化覆盖表丢失全部内容

**位置**：`.agents/skills/computer-use-smoke-reporting/scripts/render-smoke-report.mjs:113-119`

**现象**：coverage schema 的行对象含 `area/coverage/conclusion/recommendation`，renderer 按数字索引读取，报告四列全为空。

**问题**：报告声称覆盖了四个区域，但读者看不到区域、覆盖方式、结论和建议，证据链实际断裂。

**预判**：按 schema 的固定字段顺序映射对象值，并断言四列真实内容进入生成 HTML。

**结论**：已修复（2026-10-25）。覆盖表恢复字段值，重生成报告后测试与人工检查均通过。

## §9 文件级代码分析

### `apps/api/app/service/identity/service.py`（A）

职责：认证业务规则与跨 repository/token/ticket 编排。

依赖解读：`argon2-cffi` 是官方维护的 Argon2 实现，`PasswordHasher.verify(hash, password)` 从 PHC 串读取盐和参数；可把它理解为“把密码和自带配方一起现场重算，再恒定时间比较”。

变更核心：

```text
login:  查用户 → dummy/real argon 校验 → 活跃检查 → 写 last_login → 发 token
refresh: 验 refresh → 读最新用户 → 原子消费 jti → 发 token
change:  读用户 → 验证旧密码 → 更新 hash + 清 mcp
```

实现思路：把 token、用户存储和票据拆成协作对象，service 只连接状态转移。失败统一落在 `AppError`，避免泄露账号是否存在。

检视发现：D1；改密后没有撤销现有 refresh，但这属于设计未要求的 session-wide revocation 扩展，当前不单列缺陷。

### `apps/api/app/service/identity/tokens.py`（A）

职责：30 分钟 access / 14 天 refresh 的签发、验签和 claim 类型检查。

依赖解读：PyJWT 是社区维护的标准 JWT 实现；代码显式 allowlist HS256，避免 `alg=none` 或算法混淆。

变更核心：refresh grant 携带 `sub/jti/exp`，`typ` 必须精确匹配。refresh 失败统一 `AUTH_EXPIRED`，避免区分“格式坏”和“已过期”。

实现思路：token 是短命自包含门禁卡，refresh 的额外价值只是向服务换新 access。

检视发现：D4 指向其密钥来源。正常签发路径始终写入 exp；验签没有 `require=["exp"]`，但只有持有服务密钥的签发者可构造缺 exp token，列为已知硬化空间而非当前可利用缺陷。

### `apps/api/app/service/identity/revocations.py`（A）

职责：原子消费 refresh `jti`，按 expiry 惰性清理。

变更核心：`asyncio.Lock` 把“查重 + 写入”合成一个临界区；`consume_once` 成功一次后返回 false，`revoke` 支持 logout。

实现思路：把 refresh 单次使用做成盖章台；进程重启后章会丢，因此 Agent Note 明确单实例边界。

检视发现：无新增阻塞问题。

### `apps/api/app/service/identity/tickets.py`（A）

职责：60 秒一次性 topic grant、principal 绑定、消费与 tombstone。

变更核心：`_grants` 保存 active grant，`_expired` 保存短期过期身份；`threading.Lock` 确保消费原子性；清理在每次 issue/consume/active_count 时惰性发生。

实现思路：访客条过期后先留一小会儿“作废回执”，让错误码仍能说清是过期还是伪造。

检视发现：D3。

### `apps/api/app/service/identity/principals.py`（A）

职责：把已验签 claims 收窄成 principal。

变更核心：`sub/role/mcp` 缺类型即 `AUTH_REQUIRED`，不把任意 JWT 字典传播进业务。

实现思路：验签只说明“这票是真的”，principal 构造再说明“票上的字段够不够用”。

检视发现：无。

### `apps/api/app/service/identity/schemas.py`（A）

职责：身份请求/响应 DTO，统一 camelCase 与 `extra="forbid"`。

变更核心：密码长度有上限，角色是 admin/member 闭集，列表响应不含密码字段。

实现思路：在进入 service 前先拒绝形状错误；但错误 handler 不应把错误输入再吐回，这正是 D2 的冲突点。

检视发现：D2 的触发面之一。

### `apps/api/app/api/auth.py`（A）

职责：登录、刷新、登出、改密、me 的薄 HTTP 适配。

变更核心：cookie 参数集中在 `set_refresh_cookie()`；受保护端点在 OpenAPI 加 BearerAuth；service 异常交给统一 handler。

实现思路：router 只做协议转换，认证规则不落在 handler。

检视发现：D1 的业务缺口在这里暴露为 204；D2 由全局 handler 产生。

### `apps/api/app/api/events.py`（A）

变更核心：非法 topic 报 `TICKET_INVALID`；不签已完成 run 的检查留给后续 SSE issue。
