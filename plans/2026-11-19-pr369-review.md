## §2 架构导览

### 2.1 两把尺子：raw hash 与 normalized body hash

实现把两个 hash 明确分开：

- `file_read_hash`：文件内容原样 sha256（`claude_code.py:300-302`、`:346`），只作诊断；knowledge 事件落 `file_read_hash`（`base.py:501`），replay 也写回（`acquisition_replay.py:793-794`）。
- `definition_hash`：`sha256(normalize_definition_body(body))`（`utils/definition.py:35-40`），是匹配键。
- `normalize_definition_body`（`utils/definition.py:22-32`）：CRLF/CR→LF、去首尾换行、截断运行时追加的常见尾部（`subagent permissions` / `permission notes` / `agent notes` / `notes` / `token budget`，允许 Markdown 标题前缀），再 `rstrip()`。

这解决了旧 skill revision 的根因：旧实现 `_skill_revision(source_path, body_hash)` 把 provider 注入的 cache path 混进 hash（rebase 前 `base.py:690-695`），target 无法复算；新实现 `_skill_revision(body_hash)` 只返回 `digest:<bodyhash>`（`base.py:673-677`）。

**代价**：normalize 的尾部截断是启发式；如果 `SKILL.md` 自己有一个 `## Notes` 段落，正文从该行起会被截掉。parser 与 target 用同一函数，通常仍能匹配，但两个仅在 Notes 段不同的版本会得到同一个 hash（版本区分度下降）。这是设计继承的取舍，不是本 PR 新引入（`utils/definition.py` 只是从 parser 搬出来），但 target 内容身份现在完全依赖它，值得记录。

### 2.2 parser 6：三类对象的身份

`claude_code.py:394` 将 `parser_version` 从 5 提到 6；存量行会在下一次 replay 时被 `_pending_condition` 判定为 pending（不是升级即自动重放）。

- **skill**：从 `isMeta + sourceToolUseID` 的注入正文取 body（`claude_code.py:222-245`），`TraceEvidence.content_hash = definition_hash(body)`；`_resolve_event_revisions` 用 tool_use 绑定证据，revision 为 `digest:<bodyhash>`（`base.py:728-748`）。显式 tag 仍优先写 `tag:<tag>`；source path 只放 `TraceEvidence.source_path`，不参与 revision。
- **agent**：`object_revision` 保留 `agentType + isBuiltIn + body hash` 的诊断身份（`base.py:680-690`），target 匹配靠 `definition_hash`；子 agent 的定义 hash 由 `_apply_agent_revisions` 挂到父节点的 `kind=agent` 事件（`agent_tree.py:302-343`）。
- **knowledge**：文件读在 `_file_evidence` 同时算 raw `content_hash` 与 normalized `definition_hash`（`claude_code.py:305-352`）；`_record_file_knowledge` 完整读取时 `document_revision=digest:<normalized>`、`object_revision` 同值、`file_read_hash=<raw>`；不完整读取一律 `unknown`（`claude_code.py:556-572`，`base.py:481-508`）。MCP 文档仍保留 provider 原始 revision（`claude_code.py:575-605`）。

一个易误读的点：`ParsedEvent.object_revision` 和 `document_revision` 在 knowledge 文件读里是**同一个归一化 digest**，但 `file_read_hash` 才是原始内容 hash；`document_revision` 的“原始值”语义只对 MCP 成立（06 §3 的表格已同步）。

### 2.3 target content resolver：tag 是入口，body hash 是身份

`target_content.py` 的语义：

- 空白 version → `422 VALIDATION_INVALID`（`:147-153`）。
- 已带 `tag:`/`digest:`/`provider:` → 原样返回 `(value, value)`，**不读内容**（`:154-155`）。这是兼容历史/显式身份的逃生门。
- 裸 version：skill/agent 走 `read_file(repo_url, sub_dir, ref, SKILL.md|AGENT.md)`（`:206-237`）；knowledge 走可选的 `KnowledgeContentSource.read_document`（`:179-204`），生产未注入 → `knowledge_content_source_unavailable`。
- 读取后 `definition_hash(content)`；空正文 → `empty_definition_body`；成功后 `digest:<hash>`。
- 缓存：`OrderedDict[(object_type, repo_url, sub_dir, version)]`，上限 256（`:271-282`）；无 TTL。
- 超时：外层 `asyncio.wait_for(..., 20s)`（`:239-269`）；内层 git 每个进程 20s（`git/content.py:127-138`）。
- 错误：`GitContentUnavailable.reason` 映射到 `TARGET_CONTENT_UNRESOLVED` 的 `details.reason`，不把 stderr/正文/路径回给客户端（`git/content.py:23-33`、`:179-183`）。

`git/content.py` 的读取路径：mirror 目录名 = `sha256(repo_url)[:32]`；不存在则 `git clone --mirror --no-hardlinks -- <url> <path>`；`rev-parse --verify <ref>^{commit}`；ref 不存在时 `remote update --prune` 重试一次；`git show <commit>:<relative>`（`:62-119`）。路径拼接在 `_relative_path`（`:146-154`），拒绝绝对路径与 `..`；git 调用全部 argv 数组、`GIT_TERMINAL_PROMPT=0`、`GCM_INTERACTIVE=Never`、stdin DEVNULL（`:157-183`），没有 shell 拼接。

### 2.4 matcher：候选集与后处理锚点

`MatchCondition.revision_candidates`（`potential.py:345-356`）把 `target_version`、`target_revision`，以及 `tag:`/`digest:` 去前缀后的裸值都放进集合；`_event_matches`（`:1149-1159`）对事件的 `object_version`、`object_revision`、`definition_hash`、`document_revision` 任一命中即算出现。这样 v6 body hash、历史 tag、历史 digest 都能在同一入口比较；source path 不参与。

锚点解析（`potential.py:1021-1093`）：

```text
reporter 解析不到            → (None, unknown)
skill 有同名触发事件          → (last event, event)
skill 无同名触发事件          → (INT_MAX / created_at, post_process)
discovery + agent 有父调用    → (parent call event, event)
discovery + agent 无父调用    → (INT_MAX / created_at, post_process)
其余（self + agent 等）        → (reporter node / -1 / session start, node)
```

`_post_process_anchor` 同时把 `tree_index` 设为 `INT_MAX`（`potential.py:1083-1093`）；`compare_triggers`（`:451-485`）双方都有 `triggered_at` 时按时间严格大于，否则按 `(tree_index, event_index)` 字典序。于是“目标有事件时间、case 用 created_at”时按 created_at；“目标没有 triggered_at”时坐标兜底保证 post_process 排在后面。

## §3 数据流走查

一条端到端主线：生产 Session 入轨 → 目标 tag 解析 → 关联/潜在 → 运行/归因 → 前端展示。

1. **入轨与 parser 6**：`source_records`（JSONL）→ `ClaudeCodeTraceParser.parser_version=6`（`claude_code.py:394`）→ `agent_events` 写入 `definition_hash`、`object_revision`、`document_revision`、`file_read_hash`、`read_complete`（`acquisition_replay.py:789-805`）。旧 v5 行在下一次 sync/replay 时重写（设计 07:1161）。  
   例：skill 注入正文归一化后 `definition_hash=9080…`（假设与 target 文件一致），事件 `object_revision=digest:9080…`；source path 只留在 evidence，不进入 revision。
2. **目标版本解析**：向导提交 `targetVersion=v6.4.1`（裸 tag）→ `PotentialPreviewService._condition`（`potential.py:931-986`）→ `TargetContentResolver.resolve`（`target_content.py:132-237`）→ 读 `repoUrl/subDir/SKILL.md` → normalize → `targetRevision=digest:<bodyhash>` → 预览响应 `targetRevision`（`potential.py:858/898/928`）。launch 同路径（`launch.py:159-161`）并在 run 快照写 `target_revision`（`:275-276`）。
3. **关联**：`associated_sessions`（`potential.py:580-660`）取窗口内 bad cases → 根 Session → `agent_events JOIN agents`；`_event_matches` 用候选集匹配 `definition_hash`/`object_revision`/`document_revision`/`object_version`（`:1149-1159`）；命中事件按时间/坐标取最早作为 `object_entry`；没有命中的 Session 若事件有可用身份 → `skipped`，全无身份 → `versionUnresolved`（`:645-648`、`:1162-1173`）。

### 讨论点 7：git 超时只取消等待、不回收子进程；mirror 无并发锁

- **位置**：`apps/api/app/third_party_api/git/content.py:127-138`（`wait_for(self._runner(...))`，无 kill）、`:87-110`（mirror 检测/克隆/失败 `_safe_remove`）、`service/evolution/target_content.py:239-269`（外层 20s 超时）。
- **现象**：探针 `wait_for(_run_process(("sleep","17")), 0.3)` 超时后 `pgrep` 仍能看到 `sleep 17` 存活；说明 `git clone`/`git fetch` 被 cancel 后进程继续跑。另一个风险：两个并发 preview 同时发现 mirror 不存在，都去 `git clone` 同一路径；失败的一方执行 `_safe_remove(repo_path)`，可能删掉正在被另一方 `git show` 使用的 mirror。当前没有 per-repo 锁或临时目录+原子 rename。
- **问题**：网络挂起时会累积孤儿 git 进程/带宽；并发请求会把彼此的 mirror 删掉，表现为随机的 422，重试又可能恢复。超时虽然返回稳定 422，但资源没有收口。
- **预判**：在 `_git` 的 cancel/Timeout 分支 `process.kill()`（必要时 `start_new_session` + 杀进程组）；mirror 克隆用 `asyncio.Lock`（按 repo hash）或 clone 到临时目录后 `os.replace`；失败清理只删自己创建的临时目录。补 timeout 与并发测试（可用注入 runner 模拟）。
- **结论**：

### 讨论点 8：migration 0023 的 downgrade 在 MySQL 上可能因长数据失败

- **位置**：`apps/api/alembic/versions/0023_target_revision_anchor_kind.py:53-79`（`_alter_target_version`）、`:97-101`（downgrade 先 96→64 再删列）；测试 `tests/m13-01-body-hash-attribution/test_migration_0023.py:58-81`（仅 SQLite）。
- **现象**：新 run 的 `target_version` 通常是裸 tag（≤64），但 knowledge target 允许 `digest:<sha256>` 作为 `target_version`（71 字符，`ProbeQueryRequest.target_version` 上限 96；`resolve` 对 prefixed 值原样返回），长 tag/默认 ref 也可能 >64。MySQL 严格模式下 `ALTER TABLE ... MODIFY VARCHAR(64)` 遇到 71 字符数据会报 data too long（或非严格模式截断）。CI mysql 只跑 upgrade（15 passed），没有跑 downgrade。
- **问题**：这正是回滚时需要的路径，却可能在有数据时失败；SQLite 不校验 VARCHAR 长度，测试给不出保护。
- **预判**：downgrade 前先检查/截断超长值并给出明确策略，或干脆保持 96（downgrade 不缩宽，只删新增列）；补一条 MySQL 0023 downgrade + 71 字符 `target_version` 的测试（可在 CI mysql job 里用临时库）。
- **结论**：
