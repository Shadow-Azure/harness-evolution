## §1 一页速览

一句话：生产页、原型和设计文档是同一份接口说明书的三个告示牌；这次把最后两块仍印着旧版式（`email` 登录、`he_session`、snake_case 上报）的牌子，统一换成当前 OpenAPI 这一版。

最值得先看的一刀：文案不是"改好看一点"，而是把“管理员可以给自己加空间管理员”这个权限事实、以及“登录返回 accessToken 并写 refresh_token Cookie”这个调用事实写回页面。前者影响权限理解，后者影响接入方照抄的请求/响应。

| 交付块 | 内容 |
| --- | --- |
| 空间文案 | 生产与原型统一为“任意用户（包括自己）” |
| 鉴权示例 | `GET /api/auth/session` 的 `PublicUser` + `SessionWorkspace` + `truncated`；`login` 的 username/password、accessToken/expiresIn、refresh_token Cookie；`refresh`/`logout` |
| 演示账号 | 生产页删除“替换演示账号”措辞；原型明确演示账号只存在于原型 |
| 上报示例 | 生产与原型、design-v2 统一为 camelCase `BadCaseIngest`，保留 workspace 422 边界 |
| 防漂移 | E2E 读取 `packages/contracts/openapi.json` 的 required 字段，校验页面、原型、设计文档 |
| 验证 | 组件 3 例、E2E 4/4、contract/typecheck/lint/gates/docs/flow 全绿 |

## §2 架构导览

### 2.1 文案的四个事实源

这组文案有四个会互相影响的位置：`packages/contracts/openapi.json`（接口事实）、`Apps/web` 组件（用户看到的）、`plans/ui-prototype-v2/harness-evolution.html`（设计演示）、`plans/ui-prototype-v2/design-v2.md`（设计说明）。本 PR 只改后三个，不改 OpenAPI；测试把 OpenAPI 当作裁判。

### 2.2 空间页

`SpacesTab.vue:61` 是全局管理员视图的 `sub` 文案，只在 `isGlobalAdmin` 分支渲染。原型 `harness-evolution.html:6440` 本来就写了“包括自己”，所以生产只是追平原型与 08 §4.2 的“默认含自己”，没有改权限判定。

### 2.3 鉴权页

`AuthTab.vue:42-60` 是纯静态模板字符串，不参与任何请求构造。本次把 `email`/`name`/`avatar`/`globalRole` 换成当前 `PublicUser` 的 `username`/`displayName`/`role`/`mustChangePassword`，并把 `SessionWorkspace` 的 `mark`/`memberCount`/`spaceAdminCount`/`truncated` 补全；登录段补 `200 {accessToken, expiresIn, user}` 与 `refresh_token` Cookie，再补 `refresh`/`logout`。页面底部说明从“把演示账号替换成返回值”改为“只依赖 user + workspaces，登录页不渲染账号列表”。

### 2.4 上报页

`IngestTab` 与 `useWorkspaces.ingestExampleBody()` 本来已是 camelCase，本次不改代码；PR 中仍给出上报页截图，作为“文案未回退”的对照。真正需要改的是原型 `v2AdminIngest()`（`harness-evolution.html:6469-6487`）和 `design-v2.md:106`：前者把样例改成与生产相同的静态 camelCase payload，后者把字段清单改成必填/可选两段。

### 2.5 测试分层

- 组件层 `Admin.test.ts:381-431`：断言空间文案、鉴权契约字段与无“演示账号”、上报 camelCase 与 422 说明。
- E2E 层 `tests/e2e/m12-13-admin-copy-contract.test.mjs`：真实 API + Vite + headless Chrome，跑空间/鉴权/上报三个 Tab；第四例是源码级 OpenAPI 对齐检查。
- 第四例直接读 `schemas.PublicUser.required`、`SessionWorkspace.required`、`LoginRequest.required`、`LoginResponse.required`、`BadCaseIngest.required`，避免把字段清单再手写一遍。

## §3 数据流走查

一条“管理员打开空间管理 → 看接入说明”的实际路径：

1. 浏览器带 refresh Cookie 打开 `/workspaces/{wid}/admin`；`useAuthStore` 先 `GET /api/auth/session` 恢复用户与空间。
2. `Admin.vue` 渲染四个 Tab；点击“鉴权接入”切到 `AuthTab`，内容是静态字符串，不产生额外请求。
3. 点击“上报接入”切到 `IngestTab`，读取凭据列表；请求体示例来自 `ingestExampleBody()` 的静态 JSON，同样不构造请求。
4. E2E 在同一页面读取 `innerText`/`textContent` 断言文案；截图只在 `HE_M12_13_CAPTURE_DIR` 设置时落盘，不进入代码仓。
5. 第四例在 Node 侧读 OpenAPI 与三个源文件，把“页面/原型/设计是否覆盖 required 字段”变成确定性断言。

## §6 讨论点

### 6.1 本 PR 携带 m12-10 / m12-11 的状态对齐

- **位置**：`.agents/flow/issues/m12-10-bad-case-trigger-point.md:13`、`.agents/flow/issues/m12-11-login-v2-layout.md:12`、`.agents/flow/issues/m12-13-admin-copy-contract.md:14`
- **现象**：远端 #337、#338 已 CLOSED，本地仍为 `in-progress`/`ready`，导致所有新 PR 的 `flow-online` 红；本 PR 按远端事实把两者标为 `done`，并把 m12-13 推进到 `in-progress`。
- **问题**：这是跨 ticket 的流程对齐，且 #347（close m12-10/m12-05）已开 PR 做同样的事，两个 PR 对 m12-10 的改动会重叠；谁后合谁需要 drop 重复 hunk。m12-13 进入 `in-progress` 依赖 m12-10 已 done（P1 最高未清档只剩 m12-09），否则 `verify-flow` 会红。
- **预判**：对齐是远端事实的机械同步，不改变任何 issue 的交付结论；放在本 PR 能让 CI 恢复，也符合此前 PR #349 对齐 m12-08 的先例。若维护者希望保持“一个 ticket 只改自己的流程文件”，可以拆出独立的 flow PR，但当前没有其他可用合并通道。
- **结论**：

### 6.2 同一段契约文字存在三份

- **位置**：`AuthTab.vue:42-60`、`harness-evolution.html:6515-6547`、`design-v2.md:74-84`
- **现象**：登录/会话示例在生产页、原型、设计文档各写一遍。
- **问题**：三份文字无法共享常量；本次用 OpenAPI required 字段测试锁字段名，但字段顺序、示例值、说明文字仍可能各自演化。
- **预判**：可接受。原型是独立静态 HTML，生产组件也不适合 import 设计文档；把“必填字段必须出现”机械化，已经能拦住最危险的漂移（改 schema 未改文案）。更进一步的共享模板需要构建期生成，成本大于本 issue。
- **结论**：

### 6.3 浏览器测试与源码检查放在同一个 E2E 文件

- **位置**：`tests/e2e/m12-13-admin-copy-contract.test.mjs:368`
- **现象**：前三例启动 API/Vite/Chrome，第四例只读文件和 JSON。
- **问题**：单跑第四例也会启动完整夹具，耗时约几秒；从测试分类看，源码检查更像 gate 而不是 E2E。
- **预判**：可接受。issue 的 scope 只允许改 `tests/e2e/m12-13...` 与现有文件，把源码检查放这里能随 E2E lane 一起执行，避免新增脚本目录；若以后同类检查增多，再抽到 `scripts/gates`。
- **结论**：

### 6.4 “Cookie 会话”仍是概括说法

- **位置**：`AuthTab.vue:71`
- **现象**：页面副标题写“当前使用账号密码与 Cookie 会话”，实际是 access token 走 `Authorization: Bearer`，refresh token 才放 HttpOnly Cookie。
- **问题**：严格说“Cookie 会话”覆盖了 refresh 部分，但没有说清 access token；接入方可能以为所有请求都靠 Cookie。
- **预判**：本次 issue 只要求“页面正文已说明 Cookie 会话现状”，不要求改副标题；下方契约已把 accessToken 与 refresh_token 分开写清。是否把副标题改成“access token + refresh Cookie”留作后续文案统一。
- **结论**：
