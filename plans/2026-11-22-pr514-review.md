## §1 一页速览

一句话：`AI_AGENT_PROVIDER=claude-code` 从「启动安全的占位」变成**真实可用的第一个子类**——它把无头 `claude` CLI 当成一个受管子进程，用一次性任务目录收货结构化结论，超时/取消按进程组先 SIGINT 后 SIGKILL，提交失败时做一次无状态反馈重试（重发原 prompt + 校验反馈，不续 CLI 会话），并把成本、token、模型、session 与健康状态归一化进既有契约。

比喻：这个 provider 像工地上的**包工头**。它不自己干活，把一张写好的任务纸（prompt）与一张「只准写这一个文件」的作业票（`--allowed-tools`）交给工人（`claude` 子进程），让工人单独开一个工棚（`start_new_session=True` 的进程组），自己在门口掐表；超时就先喊停（SIGINT），宽限 5 秒不走就拆工棚（SIGKILL）。工人写完的结论不是靠嘴说（stdout），而是塞进工棚里的收货箱（`result.json5`），包工头只认箱子里的东西（`submission.collect`）。叫回同一名工人接着改（`--resume`）听起来顺理成章——但 analyze 的作业票上恰好写着「干完不留档」（`--no-session-persistence`），所以第二次去叫同一个工人时，档案室只会回答「查无此人」。§6 点 1 讲的就是这张自相矛盾的作业票。

## §2 架构导览

### 2.1 接缝与工厂：三个能力面，两个实现

`third_party_api/ai_agent` 的父类只定义三个能力（`base.py:34-59`）：`analyze`、`edit_workspace`、`health_check`。工厂是「一个 `AI_AGENT_PROVIDER` 字符串 → 一个注册类」的字典（`factory.py:20-24`），本 PR 把占位类 `_PendingClaudeCodeProvider` 整个删掉，换成 `ClaudeCodeProvider`（`factory.py:13`），并把 runner、结果、Protocol 从包入口导出（`__init__.py:4-8`、`:52-58`）。`build_agent_provider` 仍然只做 `implementation(settings)`（`factory.py:55-64`），不认识任何后端细节。

这带来一个直接后果：过去零配置启动时，`claude-code` 只是一个「会抛 `NotImplementedError` 的占位」，启动健康检查必然 unhealthy 且便宜；现在零配置启动会构造真实 runner，`main.py:522` 的 lifespan 会**真的 spawn 一个 `claude --version` 子进程**。这是本 PR 从「零副作用占位」跨到「有外部进程的真实后端」的最大边界变化，§6 点 4 与点 14 都围绕它。

### 2.2 传输层：`ClaudeCliRunner` 与进程组

`ClaudeCliRunner` 是一个 `Protocol`（`claude_code.py:107-119`），只有 `run(argv, cwd, env, timeout_seconds)` 一个方法。默认实现 `AsyncioClaudeCliRunner`（`:152-212`）做四件事：

1. `asyncio.create_subprocess_exec(*argv, cwd=cwd, env=dict(env), stdin=DEVNULL, stdout=PIPE, stderr=PIPE, start_new_session=True)`（`:172-180`）。`start_new_session=True` 让子进程成为新 session 的 leader，其进程组 id 等于 pid——这是「杀整组」而不是「只杀直接子进程」的前提；`DEVNULL` 让 CLI 永远不会等 stdin。
2. `asyncio.wait_for(process.communicate(), timeout=timeout_seconds)`（`:182-185`）一次性收完 stdout/stderr。选 `communicate` 而不是逐行读，是因为 `--output-format json` 只产出一个结果对象，简单、无死锁；代价是输出大小无上界（点 6）。
3. 超时（`:186-187`）与调用方取消（`:188-190`）都进 `_terminate`（`:197-212`）：先对进程组发 `SIGINT`（`:199`），`wait_for(process.wait(), grace_seconds)`（`:201`），仍不退出就 `SIGKILL` 整组（`:203-205`）。宽限期默认 5 秒（`:81-82`）。
4. `_signal_process_group`（`:215-228`）先看 `process.returncode`，已退出就直接返回；POSIX 上 `os.killpg(os.getpgid(pid), sig)`，任何 `OSError` 都吞掉（进程已消失、组已空都算「已经结束」）。这是「SIGINT 打一个已经退出的组」与 `getpgid` 竞态的处理方式。

`ClaudeCliResult`（`:91-104`）把 `cancelled` 与 `returncode` 分开：被自己杀掉的进程在 POSIX 上可能是负信号码，也可能是 shell 风格的 143，单看 returncode 无法区分「被杀」与「真失败」。

### 2.3 analyze：一次性目录 + 结构化收货

`analyze`（`:283-293`）先 `submission.prepare(task, output_model)` 拿一个一次性目录，再 `_analyze_with`，最后 `finally: discard(prep)`。`prepare` 的默认路径（`submission.py:204-214`）会：

- `mkdtemp(prefix="he-ai-submission-")` 造一个唯一目录；
- 写 `schema.json`（Pydantic `model_json_schema()` 的序列化）；
- 生成 prompt 追加段：任务键、只准写 `./result.json5`、形状以 `./schema.json` 为准、JSON5 宽松格式说明。

`_analyze_with`（`:295-345`）把调用方 prompt 与追加段拼成 `prompt`（`:302`），构造 argv（`:304`），调 `_call`（`:305-310`），再 `collect(prep, request.output_model.model_validate)`（`:312`）。`_call` 负责把「取消 / 启动失败 / 非零退出 / 没有 JSON result / is_error」五类失败折叠成 `AgentProviderError`，并只把脱敏、限长的 `detail` 带出去（`:430-484`）。

### 2.4 resume：一个「看起来对称」的失败回喂

当 `collect` 不 ok 且解析出了 `session_id`，`_analyze_with` 用 `feedback_prompt(outcome)` 生成一段中文回喂（`:313-315`），把它拼到原 prompt 后再调一次，argv 多一个 `--resume <session_id>`（`:316-321`）。第二次仍失败就抛 `AgentProviderError`（`:330-337`）。

这段逻辑在 mock 测试里是自洽的：`MockRunner` 第一次返回「写了一个非法 `confidence`」的结果，第二次返回合法结果（`test_ai_agent_claude_code.py:374-400`）。但真实 CLI 的第一步带着 `--no-session-persistence`，session 不落盘，第二步的 `--resume` 只能得到「查无此人」。见 §6 点 1。修复后该分支改为一次性无状态反馈重试：重发原 prompt + `feedback_prompt`，不带 `--resume`。

### 2.5 用量：分支写对了，字段名没对上

`_usage_from`（`:672-711`）的设计意图很清楚：`model_usage` 是 per-model 明细，`usage` 是聚合，两者相加会双计，所以有 `model_usage` 时只用它；`total_cost_usd` 优先于 per-model 成本之和；`model` 优先取顶层字段，否则用 per-model 键排序拼接，最后退回 provider id。

问题在字段名：代码读的是 `model_usage`、`input_tokens`、`output_tokens`、`cost_usd`（`:677`、`:690-692`），真实 CLI 输出的是 `modelUsage`、`inputTokens`、`outputTokens`、`costUSD`。于是 per-model 分支在真实调用上永远不触发；顶层 `model` 也不存在，最终 `AgentUsage.model` 恒为 `"claude-code"`。见 §6 点 2。

### 2.6 edit：只读探索 + 一个写文件，只收货不应用

`edit_workspace`（`:347-382`）用 `prepare(..., directory=request.workspace, filename=".harness-evolution/edits.json5")` 在**调用方工作区**里准备收货点（`:350-355`）。显式目录分支（`submission.py:215-231`）不会写 `schema.json`，而是把同一份 schema 内联进 prompt（`:226-231`）；同时它会先 `unlink` 目标文件（`:223-225`），避免上一轮的 plan 被这一轮误收。

argv 的工具面是 `Read,Grep,Glob,Write(./.harness-evolution/edits.json5)`（`:540-541`），`--settings` 同样只在文件存在时传（`:543-544`）。收到 `EditPlan` 后，provider 只把 `summary` 装进 `EditResult`，`changed_files=()`、`unified_diff=""`（`:373-382`）——它没有应用任何编辑，设计里确定性应用器在 bugfix-20/21。这个「空 diff」是诚实的，但 plan 本身没有随结果返回（见点 9、点 10）。

### 2.7 健康检查与启动

`health_check`（`:384-428`）先 `self._binary()` 解析配置路径（`:547-551`，`~` 展开），未注入 runner 时用 `_binary_available` 做存在性检查（`:575-581`）：含路径分隔符就 `Path(binary).is_file()`，否则 `shutil.which`。不存在就返回 unhealthy（`:388-394`），不 spawn；存在就 `runner.run((binary, "--version"), cwd=Path.cwd(), env=..., timeout_seconds=10)`（`:396-401`），任何异常都变成 unhealthy detail（`:402-408`），非零退出或取消也是 unhealthy（`:410-418`），成功则把版本行脱敏限长后放进 detail（`:419-428`）。

`main.py:140-163` 的 `_record_ai_agent_health` 在 lifespan 里 `await` 它（`main.py:522`），然后才 `resolved_database.start()`。所以「健康检查慢」会直接变成「启动慢」；默认宽限 5 秒意味着 `--version` 挂住时最坏约 15 秒，而不是 10 秒（点 7）。

### 2.8 诊断与凭据

`_environment`（`:559-562`）直接把 `os.environ` 复制给子进程；`_diagnostics`（`:755-761`）只把 `exit_code` 与脱敏后的 stderr 放进 detail；`_error_result_detail`（`:764-768`）只取 `subtype` 与退出码，不回声模型文本；`_bounded_detail`（`:780-785`）统一走 `sanitize_detail` 并限 1000 字符；`_version_line`（`:788-794`）只取第一行非空并限 120 字符。模块头注释（`:16-19`）承诺不读取、不记录凭据，这一条在「不主动读」的意义上成立，但「把整个环境原样交给子进程」是另一件事（点 12）。

### 2.9 提交通道的三个新旋钮

`submission.prepare` 从「只接受 task_key + schema」变成可接受 `directory` 与 `filename`（`submission.py:160-240`）：

- `filename` 走 `_safe_submission_filename`（`:427-456`）：非空、无首尾空白、无 NUL、无反斜杠、无盘符、必须是规范相对 POSIX 路径、无 `.`/`..`/空段、任何段都不能 casefold 成 `.git`；`.harness-evolution/` 明确允许。
- 显式 `directory` 走 `_existing_directory`（`:413-424`）：必须绝对、必须已存在，通道不替你创建。
- `SubmissionPrep.schema_path` 变成 `Path | None`（`:85`）：一次性目录有 schema 文件，显式目录没有（内联进 prompt）。
- `SubmissionOutcome.result_name`（`:116`）让 `feedback_prompt` 能点名 `edits.json5` 而不是默认的 `result.json5`（`:342-362`）。

这三处都是加法，默认路径的输出逐字节不变（测试 `test_prompt_addendum_points_at_result_and_schema` 与 `test_prepare_mints_unique_one_shot_directories` 仍在）。但 `discard` 的语义没有跟着 `directory` 一起更新（点 3b）。

对应代码 `claude_code.py:504-516`。cwd 是 `he-ai-submission-*` 一次性目录（测试断言 `call.cwd.name.startswith("he-ai-submission-")`，`test_ai_agent_claude_code.py:271`），子进程写完 `result.json5`、在 stdout 打一个 `type=result` 的 JSON：

4. `collect` 读 `result.json5` → strict JSON / JSON5 / json-repair 阶梯 → `EditPlan`/调用方模型 `model_validate`（`submission.py:242-328`）。

实测结果：`AgentUsage(model='claude-sonnet', input_tokens=8, output_tokens=3, cost_usd=0.25)`、`session='sess-1'`、wall 0.906s（假 CLI 本身有 0.9s 启动开销）。注意这个 `model='claude-sonnet'` 来自假 JSON 的 `model_usage` 键；真实 CLI 会走另一条路（点 2）。

### 3.2 校验失败 → resume（mock 成功，真实失败）

mock 剧本（`test_ai_agent_claude_code.py:374-400`）：

1. 第一次调用返回 `{"confidence": 2.0}`（越界），CLI stdout 带 `session_id="session-1"`。
2. `collect` 失败（`validation_error` 含 `confidence`）。

### 3.3 一次 edit

4. agent 探索后写 plan；`collect` 校验 `EditPlan`。
5. 返回 `EditResult(summary=plan.summary, changed_files=(), unified_diff="", session_id=…)`（`:373-382`）。工作区里的源文件不动；`.harness-evolution/edits.json5` 留着（测试 `:688-689`）。

### 3.4 启动健康检查

`main.py:522` → `_record_ai_agent_health`（`:140-163`）→ `provider.health_check()`：

## §6 讨论点

> 每条固定五段；**结论**记录维护者拍板结果（日期、决定与理由）。预判是供拍砖的初步看法，不是决定。

### 讨论点 1：`--no-session-persistence` 与 `--resume` 互斥——issue 的失败回喂在真实 CLI 上是死路径

**位置**：`apps/api/app/third_party_api/ai_agent/claude_code.py:515-518`（每个 analyze argv 都加 `--no-session-persistence`）、`:517-518`（resume 追加 `--resume`）、`:312-328`（失败回喂分支）；issue 要求 `.agents/flow/issues/bugfix-claude-code-provider.md:35`（同一条命令同时含两者）、`:37`；设计 07 §5.5.3 的「有限重试」。

**现象**：真实 `claude --help`（2.1.278）对 `--no-session-persistence` 的说明是 “Disable session persistence - sessions will not be saved to disk and **cannot be resumed** (only works with --print)”。实测 `claude --bare -p … --no-session-persistence --resume 00000000-0000-0000-0000-000000000000` 退出 1、stderr `No conversation found with session ID: …`；一次带 `--no-session-persistence` 的真实调用产生的 session id 在 `~/.claude/projects` 下也找不到落盘文件。mock 测试 `test_invalid_submission_resumes_once_with_feedback`（`test_ai_agent_claude_code.py:374-400`）用 `MockRunner` 脚本化了一个「同一 session 第二次成功」的世界，因此掩盖了真实 CLI 的约束。

**问题**：issue 同时要求这两件事，但 CLI 语义上它们不能共存。后果不是「重试少一次」而是「重试必然失败」：第一次提交只是校验不通过（本可修正），第二次 `--resume` 以非零退出，`_call` 在 `:461-467` 抛 `retryable=True` 的 `AgentProviderError`，调用方整批降级。也就是说，六层防线里的第 4 层（有限重试与回喂）在唯一真实后端上没有落地，而 PR 正文的「已知设计张力」只写了「需要部署机验证」，没有给出互斥结论。

**预判**：先修正 issue/设计的措辞，再二选一。① **保留 `--no-session-persistence`，放弃 `--resume`**：第二次调用改成不带 `--resume` 的全新调用，prompt 里带上 `feedback_prompt` 的校验错误与「重写 `./result.json5`」指令。这仍然实现「回喂一次」的业务目标，且不依赖 CLI 会话存储；代价是模型看不到自己上一轮的原文（但收货箱里的字面量才是唯一事实，prompt 已包含任务与错误）。② **放弃 `--no-session-persistence`，保留 `--resume`**：第二次能续上会话，但 `~/.claude` 会留下每轮 transcript，需要额外的清理/保留策略，且与「analyze 不持久化」的隐私意图相反。我更倾向 ①：它把「回喂」从 CLI 内部机制降级为纯 prompt 机制，与 §5.5.3「不依赖任何 CLI 内部机制」的立场一致；② 则把可靠性押在 CLI 的会话文件布局上。无论选哪个，都应把 e2e 冒烟补上 invalid → retry 路径，否则 mock 会继续掩盖。

**结论**：已决 2026-11-22：修复（理由：真实 CLI 2.1.278 的 help 明确 `--no-session-persistence` 的会话 "cannot be resumed"，实测 `--resume` 退出 1 并报 `No conversation found with session ID`，issue 的字面要求不可行；保留 no-persistence 的「analyze 不落盘」意图，把回喂降级为纯 prompt 机制。实现：第二轮改为全新无状态调用，重发原 prompt 加 `feedback_prompt`，不带 `--resume`，重试预算仍恰好一次；`_analyze_argv` 删除 `resume_session_id`，命名统一为 feedback retry；单测断言第二轮无 `--resume`、含反馈文本且仍成功，二次 invalid 仍抛；真实 CLI 证据同步进 ADR Note 与 PR 正文）。

### 讨论点 2：真实 CLI 的 `modelUsage` 是 camelCase——per-model 分支永远不触发，`model` 恒为 `claude-code`

**位置**：`apps/api/app/third_party_api/ai_agent/claude_code.py:672-711`（`_usage_from`），重点 `:677`（`payload.get("model_usage")`）、`:690-692`（`input_tokens`/`output_tokens`/`cost_usd`）、`:699-705`（`model` 回退）；测试 `apps/api/tests/test_ai_agent_claude_code.py:549-574`；Note `.agents/notes/proposed/feature/2026-11-22-evolution-real-ai-design.md:36`。

**现象**：真实 `claude -p … --output-format json`（2.1.278）输出的字段是 `session_id`、`total_cost_usd`、`usage`（`input_tokens`/`output_tokens`/`cache_*` 等 snake_case）与 **`modelUsage`**（camelCase）；per-model 条目内部是 `inputTokens`、`outputTokens`、`costUSD`（CLI 二进制里的 usage 类与 `total*Tokens()` 也证实了这套内部字段名）。本实现读 `model_usage` 与 snake_case 条目，所以真实调用永远走 `else` 分支：tokens 取聚合 `usage`，cost 取 `total_cost_usd`，`model` 回退到 `"claude-code"`。把真实形状喂给 `_usage_from` 实测：`AgentUsage(model='claude-code', input_tokens=11, output_tokens=7, cost_usd=0.25)`——模型身份丢失；若某版 CLI 只给 `modelUsage` 而不给聚合 `usage`，tokens 会是 0。PR 的 `test_usage_maps_model_usage_without_double_counting` 用的是真实 CLI 不会产生的 snake_case payload，因此「不双计」的断言只证明了合成契约，没证明真实映射。

**问题**：`AgentUsage.model` 是 `ai_agent_call` 事件与成本归因的固定字段（`contracts.py:35-73`；`cluster_llm.py` 的记录器），恒为 `"claude-code"` 会让「哪个模型跑了这次 review/score」不可回答，per-model 成本拆分也不存在。设计/Note 写的 `model_usage` 与真实 CLI 的 `modelUsage` 是同一个事实的两种拼写，但实现只支持前者；这属于「集成契约没对齐」，不是风格问题。

**预判**：在 `_usage_from` 同时接受两种拼写：`modelUsage`/`model_usage`，条目内 `inputTokens`/`input_tokens`、`outputTokens`/`output_tokens`、`costUSD`/`cost_usd`；仍保持「有 per-model 明细就不再累加 aggregate」。`model` 的优先级改成：顶层 `model` → per-model 键排序拼接 → provider id。加一份从真实 CLI 输出脱敏来的 golden fixture（至少覆盖 `modelUsage` 与 `usage` 同时存在、二者只有一个、`modelUsage` 为空三种），并把 e2e 的 `assert result.usage.model` 收紧为「不是 `claude-code` 且包含模型名前缀」。若成本核算需要 cache token，另开字段或扩展 `AgentUsage`，不要在 `input_tokens` 里混入 cache。

**结论**：已决 2026-11-22：修复（理由：真实输出是 camelCase `modelUsage`，条目内 `inputTokens`/`outputTokens`/`costUSD`，旧的 snake_case 读取让 per-model 分支永不触发、`model` 恒为 `claude-code`，模型身份与成本归因不可回答。实现：`_usage_from` 同时接受两种拼写，模型名从 `modelUsage` 键派生（顶层 `model` 仍优先），per-model 明细存在时不再累加 aggregate；新增真实形状的 golden fixture 并断言 model/tokens/cost，原 snake_case 用例保持通过；ADR Note 同步改为双拼写）。

### 讨论点 3：`discard(prep)` 在 analyze 的 `finally` 里无条件删目录——失败证据与「collect 不删」的契约相反

**位置**：`apps/api/app/third_party_api/ai_agent/claude_code.py:283-293`（`finally: self._submission.discard(prep)`）、`submission.py:330-340`（`discard` 直接 `rmtree`）、`submission.py:137-147`（类 docstring：「collect never discards, because layer-5 raw evidence may still be wanted」）。

**现象**：成功路径与失败路径都会删。自建探针在 analyze 因「stdout 无 result」失败后检查 `len(provider._submission._temp_directories) == 0`——目录已消失，`result.json5` 与 `schema.json` 都不在了。失败时 `_submission_detail` 只带 `validation_error`/`parse_error` 的文本（`:771-777`），不带原始字面量；`collect` 也不会把 payload 放进 outcome 的 `parse_error` 路径。也就是说，模型写出一个「差一点就对」的 JSON5 时，最需要回看的原始文件被 provider 在抛出前删掉了。

**问题**：组件契约说「collect 不删，因为层 5 原始证据可能还要」，provider 却在每次 analyze 结束时删；两处对「谁拥有生命周期」的理解不一致。PR 正文把这次改动写成「额外加固：释放一次性目录」，出发点是防止长生命周期 provider 累积 schema/result 文件（确实存在），但代价是失败证据永久丢失，且未来若外层想用同一个 `prep` 重试，目录已经不存在。

**预判**：把策略从「总是删」改成「成功删、失败留」（或保留最近 N 个失败目录 + TTL）。失败时在服务端日志/事件里记一个脱敏的目录标识（不要进用户可见的 `detail`），让运维能取到原始字面量；`discard` 仍可由调用方在确认不再重试后显式调用。若要同时防累积，可以给 `StructuredSubmission` 加一个有界保留队列（例如最多 20 个失败目录，超出按时间删），这比「一律删」更符合可观测性目标。成本很小，收益是「模型吐坏 JSON」不再是无证事件。

**结论**：已决 2026-11-22：推迟（理由：失败证据保留需要有界保留队列与目录标识的落库位置，属于可观测性范围；本 PR 保留 provider 在 `finally` 释放自己铸造的一次性目录，避免长生命周期单例累积 schema/result，`collect` 不删的组件契约不变。后续可观测性 issue 再评估「成功删、失败留 + TTL」，当前行为作为已知取舍记录）。

### 讨论点 3b：`discard` 对显式目录是「删工作区」——新 `directory` 旋钮没有同步所有权语义

**位置**：`submission.py:330-340`（`shutil.rmtree(prep.directory)`）、`:215-231`（显式目录分支，`prep.directory == directory`）、`:72-80`（`SubmissionPrep.directory` 的 docstring）、`:330-337`（`discard` docstring 声称「只删 prep 命名的一次性 child，不碰 caller-owned root」）。

**现象**：用 `prepare("edit", EditPlan, directory=workspace, filename=".harness-evolution/edits.json5")` 造一个 prep，再 `discard(prep)`，实测整个 workspace（含 `keep.txt`）被删。`discard` 的 docstring 只对「root + 一次性 child」成立；对 `directory=workspace` 这种新形态，`prep.directory` 就是调用方的工作区。今天 provider 只在 analyze 调 `discard`（prep 一定是 `mkdtemp`），edit 不调，所以**当前无实害**；但 `StructuredSubmission` 是共享组件，未来任何人给 edit 加一个「对称的 `finally: discard(prep)`」就会删库。

**问题**：这是典型的「新参数扩大了输入空间，旧方法的所有权假设没更新」。它不是当前 bug，而是 latent destructive API；测试 `test_discard_removes_the_task_directory_and_is_idempotent` 与 `test_discard_forgets_a_tracked_temp_directory`（`test_ai_agent_submission.py:474-497`）只覆盖一次性目录，没有覆盖显式目录。

**预判**：给 `SubmissionPrep` 加 `owned: bool`（`prepare` 里 disposable 为 True、显式目录为 False），`discard` 只对 `owned` 做 `rmtree`，否则 no-op 或抛 `ValueError`；或者用 `prep.directory in self._temp_directories`（不含 root 子目录时还要看 parent）判断。加一个回归测试：显式目录 prep 调 `discard` 后 workspace 仍在。改动约 10 行，风险极低，建议在本 PR 或紧随的修复 PR 里做。

**结论**：已决 2026-11-22：修复（理由：`directory` 新旋钮扩大了输入空间，`discard` 的「只删一次性 child」假设对显式 workspace 失效，属 latent destructive API，虽然当前调用路径无实害。实现：`SubmissionPrep.owned`（铸造目录 True、显式目录 False），`discard` 对非 owned 直接 no-op；新增回归测试证明显式目录 prep 调 `discard` 后 workspace 与其文件完好）。

### 讨论点 4：健康检查只证明「二进制在」——`--bare` 要求 API key/apiKeyHelper，`--settings` 缺失时静默降级为「无认证」

**位置**：`claude_code.py:384-428`（health 只跑 `--version`）、`:553-557`（默认 `~/.claude/settings.json`）、`:519-520` 与 `:543-544`（`--settings` 仅文件存在时传）；`main.py:140-163` 与 `:522`（启动健康）；`config.py:158-162`（默认 bin）。

**现象**：`claude --help` 对 `--bare` 的说明是 “Anthropic auth is strictly ANTHROPIC_API_KEY or apiKeyHelper via --settings (OAuth and keychain are never read)”。本机 `claude auth status` 是 `loggedIn: true, authMethod: oauth_token`，但 `~/.claude/settings.json` 没有 `apiKeyHelper`、环境里也没有 `ANTHROPIC_API_KEY`；一次真实 `--bare` 调用不可能靠 OAuth 认证（本机非 bare 的真实调用也因 401 失败）。`health_check` 只跑 `--version`，若默认路径存在就会报 healthy；`_settings_file` 不存在时 `--settings` 被静默省略，`--bare` 又没有 OAuth 兜底，于是「启动健康」与「analyze 可用」是两件事。`cluster_llm` 对 analyze 失败是整批降级（`:969-974` 等），所以这种误配表现为「每次 run 静默退回词面 + 3 条 error 调用事件」，而不是启动失败。

**问题**：健康检查的语义是「这个 provider 能否工作」，现在实际是「这个二进制能否打印版本」。对一个默认开启的真实后端，false healthy 比 false unhealthy 更贵：它让部署误以为模型路径已通，直到 run 降级才发现。条件化 `--settings` 还带来一个隐式契约：文件不存在时不是「用默认设置」，而是「没有部署设置」；在 `--bare` 下这几乎必然意味着无认证。

**预判**：分两层。① 健康检查增加「认证前提」的存在性判断，不读任何密钥：若使用 `--bare` 且既没有 `ANTHROPIC_API_KEY` 环境变量、也没有一个带 `apiKeyHelper` 的 settings 文件，就报 unhealthy 并在 detail 里写清缺哪一项；这是存在性检查，不违反「凭据零感知」。② 若不想做认证探测，至少把「settings 文件缺失」从静默省略改成启动 warning，并在 Note/部署文档里写明 `--bare` 的认证要求（`ANTHROPIC_API_KEY` 或 `apiKeyHelper`），不要把 OAuth 当成可用路径。③ 若维护者认为健康检查就该只探二进制，那也应把 detail 改成「binary available（未验证认证）」，避免读者误解为「provider healthy」。

**结论**：已决 2026-11-22：修复（理由：`--bare` 只接受 `ANTHROPIC_API_KEY` 或 settings 的 `apiKeyHelper`，OAuth 不参与；只证明「二进制在」的 false healthy 会让部署误以为模型路径已通。实现：`--version` 成功时在 detail 追加认证来源——环境里有 `ANTHROPIC_API_KEY` 报该项，settings 文件声明非空 `apiKeyHelper` 报该项，否则仍保持 `healthy=True` 并写 `no bare-mode auth configured (ANTHROPIC_API_KEY / apiKeyHelper)`；只判断存在性，从不读取或打印密钥值；三支测试覆盖且断言密钥值不回显）。

### 讨论点 5：工具面：逗号语法成立，但 analyze 的 schema 可见性与 `Write(./…)` 模式仍未验证

**位置**：`claude_code.py:504-520`（analyze 只给 `Write(./result.json5)`）、`:531-545`（edit 给 `Read,Grep,Glob,Write(./.harness-evolution/edits.json5)`）、`submission.py:399-404`（analyze 的 prompt 叫模型看 `./schema.json`）、`:204-214`（schema 写在任务目录里，未内联）。

**现象**：`claude --help` 明确 `--allowed-tools` 接受 “Comma or space-separated list”，所以本实现把多个工具拼成一个逗号字符串（`:540-541`）语法正确，不是「一个工具名」的误传。但 analyze 的工具面只有写工具，prompt 却说「字段形状以当前目录的 ./schema.json 为准」；schema 文件确实写进了任务目录（`:206-207`），但模型是否能 `Read` 它取决于 `dontAsk` 模式下只读工具的默认权限——本 PR 没有把 `Read` 放进 analyze 的 allowlist，也没有把 schema 内联进 analyze 的 prompt（edit 的内联分支在 `submission.py:390-394`）。此外 `Write(./result.json5)` 这种带 `./` 的相对路径 pattern 是否被 CLI 的权限匹配器规范化，没有真实模型调用验证；e2e 只覆盖 happy path（点 13）。

**问题**：如果 `dontAsk` 下未列入 allowlist 的 `Read` 被自动拒绝，模型拿不到 schema，只能靠调用方 prompt 猜字段——这会把「Pydantic 是唯一事实源」变成「模型猜 Pydantic」。如果 `Write(./…)` 不被匹配，agent 根本写不了收货文件，analyze 必然 `missing`。两种失败都会在第一次真实部署时暴露，但单测（mock 直接写文件）都看不见。另一个细节：`--allowed-tools` 是 allowlist，不是工具集；未允许的工具仍出现在模型视野里，`dontAsk` 会把它们自动拒绝，产生 `permission_denials` 与无效轮次。edit 的工具面注解写的是「只读 + 一个写」，但实现上只是「允许这些」，不是「只给这些」。

**预判**：① analyze 要么把 schema 内联进 prompt（和 edit 一致，最稳，代价是几 KB prompt），要么把 `Read` 加入 allowlist；内联更符合「不依赖 CLI 内部机制」的立场。② 用 `--tools` 显式限定工具集（analyze 只 `Write`，edit `Read,Grep,Glob,Write`），与 `--allowed-tools` 配合，避免模型看见不可用工具；注意 `--tools ""` 的语义是「禁用全部」，不要误用。③ 在部署机用真实 CLI 跑一次 `Write(./result.json5)` 的 e2e（或至少把 invalid 回喂路径跑起来），确认权限 pattern；在此之前应把「pattern 未验证」写进 Note，而不是当成已验证。

**结论**：已决 2026-11-22：推迟（理由：`--allowed-tools` 的逗号语法已由真实 help 确认，但 analyze 只给 Write、prompt 让读 `./schema.json` 的可见性，以及 `Write(./…)` 模式是否被权限匹配器规范化，都必须在部署机用真实模型验证；本 PR 不改工具面，避免用猜测定案。记录为已知缺口：内联 schema 或把 Read 加入 allowlist 是后续候选，`--tools` 显式限定工具集留到真实验证后统一处理）。

### 讨论点 6：stdout 无上界——一次 30 MiB 输出 0.066s 处理完，但内存是 `communicate` 先吃下的

**位置**：`claude_code.py:182-185`（`communicate()` 收全部 stdout/stderr）、`:191-195`（`decode(errors="replace")`）、`:594-631`（解析）、`:755-761`（诊断只取 stderr 前 600 字符）、`:468-476`（无 result 时 detail 只有 `stdout_bytes`）。

**现象**：自建假 CLI 输出 30 MiB 的 `x`，`communicate` 全量收下、`decode` 成全量 str，解析在 0.066s 内完成（因为首字符不是 `{`，NDJSON 循环只做一次 `startswith`），最终 detail 是 `stdout_bytes=31457280`。空 stdout → `stdout_bytes=0`；非 UTF-8 → `decode(errors="replace")` 后仍无 JSON，`stdout_bytes=8`（注意这个数字是「替换字符再编码」后的长度，不是原始字节数）；多个 `type=result` 行 → 最后一个胜出（实测 `session_id` 取最后一条）；单对象没有 `type` → 当作 result；单 `system/init` 对象 → 不算 result，最终报「没有 JSON result」。`_parse_cli_stdout` 对坏行静默跳过，对列表/标量顶层返回 None。

**问题**：`--output-format json` 的 result 对象包含模型的 `result` 文本，理论上可以任意大；`communicate` 在解析之前就把全部字节读进内存，进程内没有上限。CLI 是可信二进制，但模型输出不可信、且可能被 prompt 诱导输出大段文本（虽然 `--allowed-tools` 限制写文件，stdout 仍可很大）。30 MiB 在本机只是 0.066s，但 1 GiB 就是 OOM 级事件；`_MAX_DETAIL_CHARS` 只约束错误字符串，不约束缓冲区。次要问题：`stdout_bytes` 不是原始字节数，非 UTF-8 时诊断会偏大；单对象无 `type` 被当作 result 是宽松策略，测试方便，但会接受「任意 JSON 对象」作为结果。

**预判**：短期在 `_call` 里加一个显式的输出大小上限（例如 8–16 MiB），超过就抛一个 `retryable=False` 的 `AgentProviderError`（detail 只写字节数），并把这个上限写进 Note；要真正避免「先分配再检查」，需要把 `communicate` 换成带上限的流式读取（读满上限就 kill 进程组），成本较高，可作为后续加固。`stdout_bytes` 改成在 decode 前记录原始字节长度；单对象无 `type` 的宽松分支保留，但加注释说明「测试夹具兼容，不是 CLI 契约」。对 NDJSON 的「最后一条 result 胜出」补一个显式测试，避免未来改坏。

**结论**：已决 2026-11-22：记录为已知限制（理由：stdout 无大小上限，`communicate` 在解析前先全量缓冲，运行时只由进程超时约束；加流式上限需要改 runner 读取路径与杀组时机，成本高于本次接缝修复。当前不改代码，记录「1 GiB 级输出是 OOM 面」并在 ADR Note 留档；需要时与可观测性 issue 一起加上限/流式读取）。

### 讨论点 7：进程组杀得干净，但健康检查的「10 秒」实际是 15 秒；SIGKILL 后没有第二道超时

**位置**：`claude_code.py:161-212`（runner）、`:215-228`（`_signal_process_group`）、`:75-76`（`HEALTH_TIMEOUT_SECONDS=10`）、`:81-82`（`_GRACE_SECONDS=5`）、`:396-401`（health 用 10s）、`:201-205`（SIGKILL 后 `await process.wait()` 无上限）。

**现象**：自建假 CLI 实测：`timeout=0.5`、`grace=0.2` → `elapsed=0.712s`、`cancelled=True`、`rc=-9`，孙进程（同组）也被杀；调用方取消 → `CancelledError` 在 0.205s 后重抛，组已清理。`_signal_process_group` 先看 `returncode`、再 `killpg(getpgid(pid))` 并吞 `OSError`，所以「进程刚好在超时前退出」「SIGINT 打已退出的组」都由 `returncode` 检查或 `ProcessLookupError` 兜住；macOS/Linux 上 `start_new_session=True` 让 pgid=pid，实测成立。健康侧：把 `HEALTH_TIMEOUT_SECONDS` 临时改成 0.2、用默认 5s 宽限的 runner，实测 **5.211s** 返回 unhealthy `code -9`；生产 10s + 5s 约 15s，而 `main.py:522` 是 `await`，所以启动最坏要多等 15s。`_terminate` 返回的 `ClaudeCliResult` 把 stdout/stderr 置空（`:207-212`），超时前已经打印的诊断被丢掉。

**问题**：① 「HEALTH_TIMEOUT_SECONDS 是上界」的文档语义不成立：它只是 `wait_for` 的等待时间，`_terminate` 的宽限会叠加。② SIGKILL 后的 `await process.wait()` 没有第二道上限；内核一般会很快回收，但 D 状态/NFS 等不可杀进程会让调用方无限等。③ 进程组杀不掉的场景（子进程自己 `setsid` 到新组）没有兜底；CLI 正常不会这么做，属于已知边界。④ 超时丢 stdout 让「它卡在哪」不可诊断，尤其 edit 1800s 超时后。⑤ Windows 分支只 `terminate()/kill()` 直接子进程，没有组语义；若部署只面向 POSIX，应在代码/文档里明说。

**预判**：① 给健康检查单独传一个短宽限的 runner（例如 `grace_seconds=0.5`），或把 detail/文档改成「约 15s」；启动健康可以移到 DB start 之后/后台，避免拖慢 readiness。② SIGKILL 后加 `await asyncio.wait_for(process.wait(), timeout=5)`，超时则记录并返回 cancelled（不要让调用方永远挂）。③ 超时/取消时保留已缓冲的 stdout/stderr（截断到上限）放进 `detail` 或日志，便于定位。④ 补一个 `ProcessLookupError`/`killpg ESRCH` 的单测（现有 `_FakeProcess` 只测 SIGINT→SIGKILL 的正常路径）。⑤ 若确实只支持 POSIX，在模块 docstring 与 Note 里写明，避免 Windows 部署误判。

**结论**：已决 2026-11-22：推迟（理由：健康检查的 10s `wait_for` 之后还会叠加 5s 宽限（实测 5.211s 返回），且 `main.py` 会 await 它；SIGKILL 后的 `wait()` 没有第二道上限、超时会丢已缓冲诊断。这些是真实的启动/诊断成本，但修复涉及 runner 宽限参数、启动顺序与输出保留策略，不与本次「重试/用量/所有权」接缝合并；记录为后续加固项）。

### 讨论点 8：`filename` 只做词法校验——符号链接可以把删除/写入带出工作区

**位置**：`submission.py:427-456`（`_safe_submission_filename`）、`:215-231`（显式目录 `target.unlink()`）、`:282-283`（`collect` 的 `read_text`）、`:330-340`（`discard`）；对照 `edits.py` 的 `_PROTECTED_DIRS` 与 resolved-path 检查（`edits.py:57-61`、`:393-426`）。

**现象**：自建探针：workspace 下建 `.harness-evolution -> /tmp/pr514-probe/outside` 的符号链接，在 outside 里放 `edits.json5`；`prepare("edit", EditPlan, directory=ws, filename=".harness-evolution/edits.json5")` 之后，`outside/edits.json5` **已不存在**（被 `target.unlink()` 穿过符号链接删掉）。`collect` 的 `read_text` 同样会穿过符号链接读外部文件。`_safe_submission_filename` 的拒绝矩阵（`test_ai_agent_submission.py:680-737`）覆盖了 `..`、绝对路径、盘符、`.git`、NUL、反斜杠等词法陷阱，但没有覆盖符号链接。`edits.py` 对应用器有 `_PROTECTED_DIRS` 与 `resolved` 检查（`edits.py:57-61`、`:393-426`），提交通道没有。

**问题**：显式目录模式把「删一个文件 / 读一个文件」带进了调用方的工作区。工作区通常由应用准备（git clone），但 git 可以跟踪符号链接，仓库内容里出现 `.harness-evolution` 符号链接并非不可能；一旦存在，`prepare` 会在 agent 运行前删掉工作区外的同名文件，`collect` 会读工作区外的文件。edit agent 自己不能造符号链接（只允许 `Write` 一个文件），所以攻击面主要是「仓库内容」或「外部写者」，严重度中低；但这是新引入的路径，且 `edits.py` 已经示范了正确做法，提交通道没有对齐。

**预判**：在 `prepare`/`collect` 里做 resolved containment：`root = directory.resolve()`；`target = root.joinpath(*parts)`；`resolved = target.resolve(strict=False)`；要求 `resolved.is_relative_to(root)`，并检查中间组件没有符号链接（或对最终文件用 `os.open(..., O_NOFOLLOW)`，父目录逐级 `lstat`）。删除前同样检查；`discard` 也应只接受 resolved 后仍在 root 下的目录。加两个回归用例：父目录符号链接、结果文件符号链接；它们当前都应被拒绝而不是跟随。词法检查保留为第一道，resolved 检查是第二道。

**结论**：已决 2026-11-22：修复（理由：实测 workspace 下 `.harness-evolution -> outside` 的符号链接会让 `prepare` 的 `unlink` 删掉工作区外文件、`collect` 读工作区外文件，严重度中低但路径是新引入的。实现：新增 `_contained_target`，在 stale-target `unlink()` 之前和 `collect` 读取之前用 `Path.resolve()` 做目录内包含校验；`prepare` 越界抛 `ValueError`，`collect` 返回 `invalid` 且不读文件；新增「符号链接子目录」与「collect 越界」两个测试，证明外部文件未被删除或读取）。

### 讨论点 9：prepare 先删上一轮 plan，而 `EditResult` 不返回 plan——迭代闭环的「拒绝缓冲」没有事实源

**位置**：`submission.py:218-225`（显式目录 prepare 前 `unlink`）、`claude_code.py:350-355`（edit 用该分支）、`:364-382`（`EditResult` 只有 `summary`）；`contracts.py:123-145`（`EditResult` 字段）；设计 07 §5.5.4 的「rejected-edit buffer」。

**现象**：`test_explicit_directory_removes_a_stale_result_before_the_next_round`（`test_ai_agent_submission.py:623-641`）钉住了「prepare 会删掉旧 plan、随后 collect 返回 missing」。这对「一轮一提交」是对的，但设计 §5.5.4 的迭代闭环要求 round 被 reject 后 `--resume` 同一会话并注入「上轮 EditPlan 摘要（已被拒绝的编辑勿重复）」。上一轮 plan 的唯一持久副本就是 `.harness-evolution/edits.json5`；`EditResult` 只带 `summary`，不带 `edits`，`changed_files=()`、`unified_diff=""` 也不含 plan 内容。也就是说：如果调用方在 prepare 前没有自己快照那个文件，拒绝缓冲就没有事实源；而 prepare 恰好会在下一轮开始前删掉它。

**问题**：这是「清理过期文件」与「保留迭代上下文」的冲突。清理本身没错（否则 agent 不写时会把上一轮 plan 当本轮收货，测试钉住了这个 bug），错的是 plan 只存在于一个会被下一轮删掉的文件里。`EditResult` 的「空 diff」是诚实的（没有应用），但消费者拿不到 intent，无法构造 `rejected-edit buffer`；bugfix-21 要么重新读 workspace 文件（但已被删），要么要求调用方在 prepare 前快照，要么扩展契约。

**预判**：给 `EditResult` 增加 `intent: EditPlan | None`（或 `plan`/`edits` 字段），把收货到的 plan 原样带出；这样 #488/#499 的迭代闭环不依赖 workspace 文件，prepare 也可以继续安全地清理过期文件。若担心 `EditResult` 的体积/序列化，至少加一个 `edits_summary: tuple[str, ...]`（每条形如 `op file target`），足够做拒绝缓冲。另一个选择是让 `edit_workspace` 在 prepare 前把旧 plan 复制到调用方指定的保留路径，但那需要新的参数，不如直接返回 plan。归属：本 PR 可以先记录为已知缺口，bugfix-21 接线时必须解决，否则「拒绝缓冲」只能靠重新发明状态。

**结论**：已决 2026-11-22：推迟（理由：`EditResult` 只有 `summary`，不返回 plan，而 prepare 会删掉上一轮的 `edits.json5`，拒绝缓冲缺少事实源；这是 #488 迭代闭环的契约扩展，需与 `session_id` 一起设计，不能在本 PR 单独加字段。记录：#488 必须让 `EditResult` 返回 plan 或等价的编辑摘要，否则拒绝缓冲只能靠调用方在 prepare 前自行快照）。

### 讨论点 10：edit 保留了会话却从不 `--resume`——`EditRequest` 没有 session_id 输入

**位置**：`contracts.py:103-120`（`EditRequest` 只有 workspace/prompt/allowed_paths）、`claude_code.py:347-382`（`edit_workspace` 不读 session）、`:523-545`（`_edit_argv` 没有 `--resume`）；issue `.agents/flow/issues/bugfix-claude-code-provider.md:50`（「edit 路径保留会话（`--resume` 供迭代）」）。

**现象**：edit 的 argv 没有 `--no-session-persistence`（`:531-545`），所以 CLI 会持久化会话；`EditResult.session_id` 也把 id 返回了。但 `EditRequest` 没有 `session_id` 字段，`_edit_argv` 从不加 `--resume`，所以每次 `edit_workspace` 都开新会话。issue 说「保留会话供迭代」，实现只完成了「保留」，没有完成「续上」；迭代闭环要么在服务层重新注入全部上下文（等于没用会话），要么等后续 issue 改契约。另一个副作用：会话持久化了却从不 resume，`~/.claude` 会积累每一轮 edit 的 transcript。

**问题**：这是契约缺口，不是当前 PR 的运行时缺陷（本 PR 明确只收货、不应用、不迭代）。但 issue 的验收标准里写了 edit 保留会话供 `--resume`，实现没有输入通道；如果 bugfix-21 直接在服务层拼 `--resume`，会绕过 provider 的契约。要么现在补 `EditRequest.session_id`，要么在 Note/issue 里把「edit 的 resume 在 bugfix-21 实现」写成明确欠账，避免下游误以为已可用。

**预判**：给 `EditRequest` 加 `session_id: str | None = None`，`_edit_argv` 在非空时追加 `--resume <id>`；第一次调用不带，后续轮次带上一轮 `EditResult.session_id`。同时明确 edit 持久化会话是有意为之（与 analyze 的 no-persistence 相反），并在测试里钉住「带 id 时 argv 有 `--resume`、不带时没有」。如果本 PR 不想动 `contracts.py`，至少在 Note 的 Consequences 里写清「edit 的 `--resume` 尚无输入通道，bugfix-21 补」，并把 issue 的措辞从「保留会话（--resume 供迭代）」改成「返回 session_id，供后续 issue 续用」。

**结论**：已决 2026-11-22：推迟（理由：`EditRequest` 没有 `session_id`，`_edit_argv` 从不 `--resume`，issue 的「edit 保留会话供迭代」只有保留没有续上；扩契约属于 #488。记录：#488 必须给 `EditRequest` 加 `session_id` 并在非空时追加 `--resume`，同时 `EditResult` 目前不返回 plan，拒绝缓冲也需要它；在此之前 edit 的持久化会话只返回 id，不构成可用迭代通道）。

### 讨论点 11：`system/init.capabilities` 在生产路径上不可达——`--output-format json` 不产 init 文档

**位置**：`claude_code.py:594-631`（解析单对象/NDJSON）、`:647-659`（只认 `type=system, subtype=init`）、`:459-460`（记录 capabilities）、`:421-422`（health 里拼 capabilities）、`:504-520`（生产 argv 固定 `--output-format json`）。

**现象**：真实 `claude -p --output-format json` 只输出一个 `type=result` 对象（本机 401 的那次也是），没有 `system/init`；`system/init` 是 `--output-format stream-json` 的事件。生产 argv 固定 `json`，所以 `_parse_cli_stdout` 的 `capabilities` 分支永不进入，`detected_capabilities` 恒为 `()`，health detail 永远不会带 capabilities。测试 `test_analyze_parses_ndjson_last_result_and_capabilities`（`test_ai_agent_claude_code.py:302-354`）手工喂 NDJSON，证明了「解析器能解析」，但没有证明「生产能拿到」；issue 的「特性探测用 `system/init.capabilities`」在代码结构上满足，在真实调用上不成立。

**问题**：这是一个「看起来做了、实际没生效」的特性。今天没有消费者依赖 capabilities（`--json-schema` 快路径刻意不实现），所以无实害；但未来若基于 `supports("json-schema")` 开快路径，会永远得到 false，或者有人误以为已经探测过。更一般地，它给人「版本号比较被替代了」的安全感，而实际探测源根本没接上。

**预判**：两条路。① 暂时删掉 `_capabilities_from`/`detected_capabilities` 与相关测试，等真正需要 `stream-json` 时再加；这最诚实。② 如果保留，就在 Note/代码里写明「capabilities 只在未来 `stream-json` 路径可用，当前 `json` 路径恒为空」，并加一个测试断言「生产 argv 不含 `stream-json` → detected_capabilities 为空」，把「不可达」变成显式事实而不是隐藏分支。我倾向 ①：代码少一个死分支，读者不会被误导；如果维护者想保留结构，② 的成本更低。

**结论**：已决 2026-11-22：记录现状（理由：生产 argv 固定 `--output-format json`，不产 `system/init`，`detected_capabilities` 恒为空；今天没有消费者依赖 capabilities，删除或保留结构都不改变行为。本 PR 保留该分支作为未来 `stream-json` 路径的入口，并在 ADR Note 记录「当前 json 路径恒空」；若后续要基于 `supports("json-schema")` 开快路径，先接上真实探测源）。

### 讨论点 12：prompt 走 argv、整个环境原样传给子进程——「凭据零感知」的边界需要写清

**位置**：`claude_code.py:504-520`（prompt 作为 `-p` 的 argv）、`:559-562`（`dict(os.environ)` 全量转发）、`:755-794`（诊断脱敏/限长）。

**现象**：prompt（含从 bad case 采样来的标题/描述）作为命令行参数传给 `claude`；同一用户下的任何进程可以通过 `ps -ww` 或 `/proc/<pid>/cmdline` 看到它。`_environment` 把服务进程的整个环境复制给子进程，包括 `HE_JWT_SECRET`、数据库口令等与 CLI 无关的变量；`--bare` 不加载 hooks/plugins，降低了子进程被诱导执行命令的风险，但环境本身仍然在子进程里。诊断侧：stderr 经 `sanitize_detail(limit=600)`，detail 再经 `_bounded_detail(limit=1000)`；stdout 不回声，`is_error` 只取 subtype；实测 2 KB 假 stderr 里的 `sk-proj-…` 被脱敏、长度 ≤1000（`test_ai_agent_claude_code.py:476-496`）；真实 CLI 的 stderr 只有模型相关提示。没有发现凭据泄漏到 `detail`。

**问题**：argv 暴露不是新的权限提升（同用户本来就能读父进程内存），但它把「用户日志里的敏感文本」放到了更易被进程列表采集的位置；对多租户/共享机器，这是一个隐私面。环境全量转发则是「最小权限」的反面：CLI 只需要 `PATH/HOME/LANG/ANTHROPIC_*/代理变量`，不需要服务端的 JWT/DB 凭据；模块头注释说「never reads them」，容易被读成「never passes them」，两者不是一回事。诊断的脱敏模式覆盖常见 token/Authorization/URL 凭据，但不覆盖任意 secret；它是有界且 best-effort，不是保证。

**预判**：① 在 Note/模块 docstring 里把「argv 暴露 prompt」「env 全量转发」写成明确的取舍，不要用「零感知」一句带过；② 环境改为最小 allowlist（`PATH`、`HOME`、`LANG`/`LC_*`、`ANTHROPIC_*`、`CLAUDE_*`、`HTTP(S)_PROXY`/`NO_PROXY`），并加一个测试断言 `HE_JWT_SECRET` 不出现在子进程 env 里；③ prompt 若要走 stdin，需要确认 CLI 的 `-p` 无参数时是否从 stdin 读，改动较大，可作为后续安全项；④ 诊断保持现状，但把「best-effort 脱敏」写进 docstring，避免被当成 DLP。

**结论**：已决 2026-11-22：推迟（理由：prompt 走 argv 与 env 全量转发是隐私/最小权限面的真实取舍，但最小 env allowlist 会改变子进程可用变量，stdin prompt 需要确认 CLI 的 `-p` 无参数语义，二者都超出本次接缝修复；诊断侧已脱敏限长且未发现泄漏。记录为后续安全项，当前边界写入 ADR Note）。

### 讨论点 13：opt-in e2e 只覆盖 happy path，且 `usage.model` 断言太弱，抓不到本 PR 的两个真实缺陷

**位置**：`test_ai_agent_claude_code.py:929-971`（e2e）、`:945-948`（skipif）、`:967-971`（断言）、`:934-936`（`_E2E_BIN` 默认值）。

**现象**：e2e 需要 `HE_AI_AGENT_CLAUDE_E2E=1` 且 `Path(_E2E_BIN).is_file()`；`_E2E_BIN` 默认是 `~/.local/bin/claude`，本机这个路径不存在（CLI 在 nvm 路径），所以默认跳过；要跑必须同时设 `HE_AI_AGENT_CLAUDE_E2E=1` 与 `HE_AI_AGENT_CLAUDE_BIN=<nvm 路径>`。它只测 analyze 的 happy path：不测 edit、不测超时/取消、不测 invalid→retry、不测认证失败。断言只有 `dict(result.output) == {"ok": True}`、`result.provider_id == "claude-code"`、`result.usage.model` 为真；真实 CLI 下 provider 会把 `model` 回退成 `"claude-code"`（点 2），这个断言仍然通过——也就是说 e2e 抓不到 usage 映射缺陷。它也没断言 tokens/cost，抓不到 `modelUsage` 分支不触发。PR 正文承认「重试路径由 mock 覆盖」，而重试路径正是点 1 的死路径。

**问题**：e2e 的价值是「真实 CLI 契约」的最后一道闸；现在它只覆盖最不容易坏的一条路，而且断言弱到即使映射错了也绿。跳过条件依赖一个部署路径，CI 不设 env 时这个「e2e」永远不跑；PR 说「串行 lane」，但测试文件没有 marker，也没有 CI 配置强制串行，全靠人记得。若有人在并行 lane 打开它，就是一次真实模型调用（成本/波动）。

**预判**：① 给 e2e 加 pytest marker（例如 `live_claude`），在 CI 的串行 lane 里显式选择；默认 lane 用 `-m "not live_claude"` 排除，而不是靠环境变量跳过。② 补场景：invalid → retry（修好点 1 后）、edit plan 收货、超时杀组（用一个假 CLI 走真实 runner，不必真模型）、`--version` 认证失败。③ 收紧断言：`result.usage.model != "claude-code"` 且包含模型名前缀；`input_tokens + output_tokens > 0`；`cost_usd >= 0`。④ 文档写清认证前提：`--bare` 需要 `ANTHROPIC_API_KEY` 或 `apiKeyHelper`，OAuth 登录不够（本机非 bare 的真实调用 401，`--bare` 更不会读 OAuth）。⑤ 如果短期不补，至少把测试名/注释改成「binary + argv happy path smoke」，不要让读者以为它覆盖了 provider 的全部契约。

**结论**：已决 2026-11-22：推迟（理由：保留 `HE_AI_AGENT_CLAUDE_E2E=1` 的 env-switch skipif 与现有串行约定，不新增 pytest marker/lane；本次只收紧断言（`usage.model` 不再是 `claude-code`、tokens 非零、cost 非负），反馈重试路径由 mock 单测覆盖。记录缺口：e2e 仍未覆盖 invalid→retry、edit、超时/取消与认证失败，live 重试需要确定性夹具，留待后续；ADR Note 已记录）。

### 讨论点 14：默认 bin 是 `~/.local/bin/claude`，PATH 上的 `claude` 会被判「不存在」；启动健康还会 spawn 进程

**位置**：`config.py:162`（默认 `~/.local/bin/claude`）、`claude_code.py:575-581`（含分隔符走 `Path.is_file()`，否则 `shutil.which`）、`:547-551`（`~` 展开）、`main.py:522`（lifespan 里 await health）；`test_ai_agent_factory.py:323-333`。

**现象**：本机 CLI 在 `~/.nvm/.../bin/claude`（PATH 可见），默认配置的 `~/.local/bin/claude` 不存在，health 实测 `healthy=False, detail='claude CLI not found: /Users/zn-ice/.local/bin/claude'`；把 `ai_agent_claude_bin` 设成 `"claude"` 后 health 实测 healthy 2.1.278。`_binary_available` 的规则是「值里有 `/` 就当成字面路径，不做 PATH 兜底」，所以默认值把一个常见安装方式判死。启动侧，零配置 `claude-code` 现在会在 lifespan 里 spawn `--version`；默认路径不存在时 0ms 返回，存在时约 20–120ms，挂住时约 15s（点 7）。

**问题**：默认值是一个部署假设（M15 把 CLI 装到 `~/.local/bin`），但代码没有把这个假设写进配置校验或文档；本地开发/其它安装方式得到的是「provider unhealthy」，而不是「请设置 `HE_AI_AGENT_CLAUDE_BIN`」。`test_default_backend_is_the_real_claude_code_provider` 还把默认字符串钉死，等于把假设固化成契约。启动健康 spawn 进程本身不是错，但零配置默认从「纯 Python 占位」变成「真实子进程」是运维需要知道的行为变化。

**预判**：① 让 `_binary_available` 在字面路径不存在时回退 `shutil.which(Path(binary).name)`，或把默认值改成 `"claude"` 并在文档里写明「PATH 优先，找不到再试 `~/.local/bin/claude`」；两者都保留显式配置的优先级。② 在启动日志里区分「配置路径不存在」与「PATH 上找到的 claude」，避免运维误判。③ 把「零配置启动会 spawn `claude --version`」写进 Note/部署文档；如果健康检查不是 readiness 的硬条件，可以考虑不阻塞 DB start。④ 测试补一个 `ai_agent_claude_bin="claude"` 的 PATH 分支（需要 monkeypatch `shutil.which`），不要让默认字符串成为唯一被测值。

**结论**：已决 2026-11-22：推迟（理由：默认 `~/.local/bin/claude` 是 M15 的部署假设，回退 PATH 会改变部署契约，并需要同步配置校验与启动日志；本 PR 不改默认值，`ai_agent_claude_bin="claude"` 已能走 PATH 分支。记录：默认路径对 PATH 安装判「不存在」，运维需显式配置；零配置启动会 spawn `--version` 的事实保留在 Note）。

## §9 文件级代码分析

### `apps/api/app/third_party_api/ai_agent/claude_code.py`

**职责**：把部署的 `claude` CLI 包成一个可注入、可超时、可取消、可观测的 `AIAgentProvider`：构造 argv、管理进程组、解析 JSON/NDJSON、映射用量、探测健康。**变更形态**：A，纯新增（`git show origin/main:apps/api/app/third_party_api/ai_agent/claude_code.py` 不存在）。

**关键依赖解读**：只用 stdlib 的 `asyncio/os/signal/shutil/json/math`（`:24-35`）、项目的 `submission` 通道、`edits.EditPlan` 与 `redaction` 工具；不依赖数据库/HTTP。`asyncio.create_subprocess_exec` 是「真子进程」而不是 shell，避免引号/注入；`start_new_session=True` 是 POSIX 进程组语义的开关；`sanitize_detail`/`sanitize_message`（`app/utils/redaction.py`）承担「诊断可落库」的边界。`Protocol`（`:107-119`）让单测完全不 spawn，这是本文件 971 行测试能在 0.24s 内跑完的原因。

**变更代码块分析**（纯新增，按数据流讲「在做什么、为什么这么写」）：

- **常量与结果对象**（`:63-104`）：`DEFAULT_CLAUDE_BIN`、`CLAUDE_SETTINGS_FILENAME`、`EDIT_PLAN_FILENAME`、`READ_ONLY_TOOLS`、`HEALTH_TIMEOUT_SECONDS`、`CANCELLED_EXIT_CODE`、`_GRACE_SECONDS`、两个 detail 上限。把「部署默认值」与「时间/长度上界」集中在一处，方便测试与文档引用；`ClaudeCliResult.cancelled` 与 `returncode` 分开是刻意的（见 2.2）。
- **runner 层**（`:152-228`）：`run` 只做「spawn → communicate → 超时/取消 → 杀组」；`_terminate` 把「SIGINT 优雅退出」与「SIGKILL 强杀」写成两段，`_signal_process_group` 把「进程已退出」「组已消失」都当成功。为什么不是 `process.kill()`：CLI 可能自己拉子进程（工具/MCP），只杀直接子进程会留孤儿；组杀是 git workspace runner 已经验证过的姿势。
- **解析层**（`:231-243`、`:594-659`）：`_ParsedCliResult` 把「原始 result 文档」「capabilities」「session_id」「usage」打包；`_parse_cli_stdout` 先试单对象（`--output-format json` 的真实形态），失败再按行扫 NDJSON（测试/未来 `stream-json` 兼容）；`type=system, subtype=init` 是唯一的 feature 源。`_single_json_object` 只接受 `{` 开头的完整对象，避免把日志行当 JSON。
- **provider 骨架**（`:246-282`）：`__init__` 绑定 runner、settings 路径、clock；`_runner_injected` 控制 health 是否做二进制存在性检查（测试注入 runner 时不碰宿主）；`_capabilities` 是实例级缓存，供 health detail 展示。`_submission = StructuredSubmission()` 是每个 provider 一个，生命周期跟随 provider 单例。
- **analyze**（`:283-345`）：`try/finally` 保 `discard`；`_analyze_with` 先 `prepare` 再 `_call` 再 `collect`，失败且有 session 才 resume；成功时 `model_dump(mode="json")` 把 Pydantic 对象变成可序列化 dict。`latency_ms` 用注入 clock 计算，测试可确定。
- **resume 分支**（`:312-328`）：`feedback_prompt` 是 submission 组件生成的「哪个文件、哪个字段、怎么改」的中文文案；把它拼到原 prompt 而不是替换，保留任务上下文。这个分支的错误是「假设 session 可续」（点 1）。
- **edit**（`:347-382`）：与 analyze 共享 `_compose_prompt`/`_call`/`collect`，但目录是调用方 workspace、文件名是 `.harness-evolution/edits.json5`、工具面加只读；不 `discard`，因为 workspace 不是 provider 的。
- **health**（`:384-428`）：先存在性检查（不 spawn），再 `--version`；异常不抛，全部折叠成 unhealthy；detail 带版本/能力。
- **argv 构造**（`:495-545`）：analyze 与 edit 只在「工具面」「settings」「resume」三处不同；`--settings` 条件化是为了「本地没有部署设置也能跑 fake/测试」，但真实 `--bare` 的认证依赖它（点 4）。
- **用量/诊断**（`:672-794`）：`_as_mapping`/`_as_int`/`_as_float` 把不可信 JSON 归一成非负有限值；`_diagnostics` 只取 stderr 前 600 字符并脱敏；`_error_result_detail` 不回声模型文本；`_version_line` 只取第一行。这些函数是本文件「安全落库」的边界。

**实现思路总结**：用「可注入 transport + 真实进程组 runner」把外部 CLI 变成可测试的边界；用「一次性目录 + 收货箱」把模型输出变成可校验的数据；用「统一折叠 + 脱敏限长」把失败变成可观测的值。

**检视发现**：

1. **回喂死路径**（`:515-518` + `:312-328`）：`--no-session-persistence` 让 `--resume` 永远查无此人；真实 CLI help 与实测都确认。见讨论点 1。
2. **用量字段拼写**（`:677`、`:690-692`）：真实 `modelUsage`/camelCase 不被识别，`model` 恒为 `claude-code`。见讨论点 2。
3. **失败证据被删**（`:289-293`）：`finally: discard` 在失败路径也删掉 `result.json5`/`schema.json`。见讨论点 3。
4. **capabilities 死分支**（`:594-659` + `:504-516`）：生产 `--output-format json` 不产 init 文档，`detected_capabilities` 恒空。见讨论点 11。
5. **健康上界不是上界**（`:75-76` + `:396-401` + `:201-205`）：10s `wait_for` 后还会等 5s 宽限，最坏约 15s；`main.py:522` 会阻塞启动。见讨论点 7。
6. **`subtype=success` 文案**（`:764-768`）：真实 CLI 在 `is_error=true` 时仍可能给 `subtype="success"`（本机 401 输出即如此，但该次退出码为 1，走的是 `_diagnostics` 分支）。若某次 `is_error=true` 且退出码为 0，`_error_result_detail` 会写出 `subtype=success`，误导读者。低；建议同时看 `api_error_status`（真实输出有这个字段）或只报 `is_error`。
7. **`stdout_bytes` 非原始字节**（`:468-476`）：`len(result.stdout.encode("utf-8"))` 在 `decode(errors="replace")` 之后计算，非 UTF-8 时会偏大（实测 2 字节坏输入变成 8）。低；记录原始 `len(stdout_bytes)` 需要 runner 返回 bytes 或在 decode 前记。
8. **argv prompt / env 边界**（`:504-520`、`:559-562`）：见讨论点 12；不是缺陷，但需要文档化与最小化。
9. **`--settings` 条件化**（`:519-520`）：issue 要求无条件传；实现只在文件存在时传。见讨论点 4。
10. **`analyze` 只用 `prep.allowed_tools[0]`**（`:514`）：当前 `prepare` 总是返回一个工具，所以无实害；但这是隐式耦合，若未来 `allowed_tools` 允许多个，analyze 会静默丢掉其余。低；可改成 `",".join(prep.allowed_tools)` 或断言长度 1。

### `apps/api/app/third_party_api/ai_agent/submission.py`

**职责**：确定性结构化提交通道——造/复用目录、写/内联 schema、收货并校验一个字面量、生成回喂文案、释放目录。**变更形态**：M；前身 `prepare(task_key, output_schema)` 只造一次性目录并写 `schema.json`（`git show origin/main:apps/api/app/third_party_api/ai_agent/submission.py` 的 `:151-262`），本 PR 增加 `directory`/`filename` 旋钮与 `result_name`。

**关键依赖解读**：`pydantic`（schema 唯一事实源）、`json5`（宽松字面量）、`json_repair`（抢救层）、`tempfile`/`weakref`（一次性目录生命周期）、`PurePosixPath`（跨平台路径校验）。`json5`/`json_repair` 是运行时依赖，不是构建期打包；它们只处理文本，不执行模型代码——这是「用 JS 生成 JSON」的替代方案，安全性来自「不 eval」。

**变更代码块分析**：

- **`SubmissionPrep`**（`:69-88`）：旧字段 `directory/result_path/schema_path/prompt_addendum/allowed_tools`；新加 `result_relative` 与 `schema_path: Path | None`。`schema_path` 可空是「显式目录不写 schema」的类型表达；`result_relative` 让 outcome/feedback 能点名文件。
- **`SubmissionOutcome`**（`:91-121`）：新加 `result_name`（默认 `RESULT_FILENAME`），所有 `collect` 分支都填它；这样 `feedback_prompt` 不再硬编码 `result.json5`。
- **`prepare`**（`:160-240`）：旧版「校验 key/schema → mkdtemp → 写 schema → 拼 prompt」一条直线；新版先算 `result_relative`（`:194-198`）、`schema_json`（`:199-203`），然后分两支：disposable（`:204-214`，行为与旧版逐字节一致）与 explicit（`:215-231`，不写 schema、内联 schema、prepare 前 unlink 目标）。**为什么这么拆**：显式目录是调用方的工作区，不能留下 `schema.json`；但 schema 仍要进 prompt，所以把同一份 JSON 内联。unlink 是为了「一轮一提交」，避免 agent 不写时收货到上一轮。
- **`collect`**（`:242-328`）：旧版已经支持「大小/UTF-8/解析/校验」全套；新版只是把错误文案里的 `RESULT_FILENAME` 换成 `prep.result_relative`，行为不变。读路径仍是 `prep.result_path.read_text`（`:283`），没有 resolved containment（点 8）。
- **`discard`**（`:330-340`）：旧版只对一次性目录调用；新版 `directory` 可能是工作区，但 `discard` 仍是 `rmtree(prep.directory)`（点 3b）。`_temp_directories.remove` 对显式目录抛 `ValueError`，被 `suppress` 吞掉。
- **`feedback_prompt`**（`:342-362`）：新版用 `outcome.result_name` 替换硬编码；`retry` 文案仍写「形状见 `./schema.json`」（`:352-355`），对显式目录不成立（点 9/发现 2）。
- **`_existing_directory`**（`:413-424`）：绝对 + 已存在；不检查可写、不检查符号链接（点 8）。
- **`_safe_submission_filename`**（`:427-456`）：新函数，拒绝绝对/反斜杠/NUL/盘符/非规范/`.`/`..`/空段/`.git`；允许 `.harness-evolution/`。它是词法安全的第一道，不是全部（点 8）。

**实现思路总结**：把「一次性目录」与「显式工作区」统一成同一套 `SubmissionPrep`，用 `schema_path=None` + 内联 schema 保持「不往调用方树里写文件」；用 `result_name` 让反馈文案能点名真实文件；用 prepare 前 unlink 保持「一轮一收货」。

**检视发现**：

1. **`discard` 会删显式工作区**（`:338`）：实测整个 workspace 被删；见讨论点 3b。建议 `owned` 标志或只删 `_temp_directories` 中的目录。
2. **符号链接穿透**（`:223-225`、`:283`）：实测父目录符号链接导致外部文件被删；`collect` 也会读外部文件。见讨论点 8。
3. **feedback 的 schema 路径**（`:352-355`）：显式目录没有 `./schema.json`，但 retry 文案仍指向它；edit 当前不 resume，所以无实害；一旦 edit 加重试就会误导模型。建议把 `schema_file`/`schema_path` 带进 `SubmissionOutcome`，或对显式目录改成「形状见上方 schema」。
4. **过期 plan 被删 vs plan 不返回**：见讨论点 9；`prepare` 的清理逻辑本身正确，但 `EditResult` 没有 intent。
5. **超长 filename 的 OSError**（`:223-225`）：`_safe_submission_filename` 不限长度；`target.unlink()` 可能抛 `ENAMETOOLONG`/`EACCES`，而 `prepare` 只 suppress `FileNotFoundError`，会把 OSError 抛给调用方（不是 ValueError）。低；加长度上限或把 OSError 折成 ValueError。
6. **`_existing_directory` 不查可写**：不可写目录会在 agent 写文件时失败，collect 返回 missing；错误可定位但不够早。低；可在 prepare 时 `os.access(directory, os.W_OK)`（注意 root/ACL 语义）。

### `apps/api/tests/test_ai_agent_claude_code.py`

**职责**：用 `MockRunner` 覆盖 provider 的正常、NDJSON、缺失 session、resume、二次失败、取消、非零退出、is_error、不可解析 stdout、三种 usage、settings 条件、edit、health、默认 runner 杀组/取消，外加一个 opt-in 真 CLI 冒烟。**变更形态**：A，971 行 / 26 项（25 pass + 1 skip）。

**关键依赖解读**：`MockRunner`（`:65-96`）记录 argv/cwd/env/timeout，按脚本返回 `ClaudeCliResult` 或回调；`_FakeProcess`（`:896-926`）只实现 runner 需要的字段，用 `asyncio.Event` 模拟 communicate/wait；`monkeypatch` 替换 `asyncio.create_subprocess_exec` 与 `os.getpgid/killpg`，让默认 runner 的杀组路径可在无真实进程下测。这个设计让 25 个 mock 用例 0.24s 跑完，是本 PR 最扎实的部分。

**变更代码块分析**：

- **成功路径**（`:238-283`）：断言 argv 的每个关键项、cwd 是一次性目录、usage/session/latency；`--settings` 不在 argv（文件不存在）。
- **目录释放**（`:286-299`）：断言调用后 cwd 不存在；没有测失败路径也释放（点 3）。
- **NDJSON**（`:302-354`）：`system/init` capabilities + 两条 result 取最后；这是「解析器能力」的证据，不是「生产可达」（点 11）。
- **resume**（`:374-400`）：脚本化「第一次 invalid、第二次成功」，断言 argv 有 `--resume session-1`、prompt 含 `重新写入`；这是点 1 的盲区。
- **取消/143**（`:447-473`）：参数化 `cancelled=True, rc=-2` 与 `rc=143`，断言 detail `cancelled`、retryable False；覆盖了两种归一。
- **非零退出**（`:476-496`）：2KB stderr + 假 `sk-proj-…`，断言脱敏与 ≤1000 字节；这是诊断边界的证据。
- **is_error**（`:499-529`）：断言不回显 `model secret text`；真实 CLI 的 `subtype` 可能是 `success`（发现 6）。
- **usage**（`:549-615`）：三种合成 payload；`model_usage` 是 snake_case，真实 CLI 不会产生（点 2）。
- **settings 条件**（`:618-637`）：文件存在才传；覆盖了 `--settings` 的条件语义，但没有覆盖「`--bare` 无认证」的后果（点 4）。
- **edit**（`:640-740`）：收货、argv 工具面、settings、空 diff、无效 plan 不重试；覆盖了本 issue 的 edit 边界。
- **health**（`:743-817`）：healthy 版本行、非零、异常、二进制缺失；`MockRunner` 注入时跳过存在性检查，所以 `_binary_available` 只在缺失用例里被真实调用。
- **默认 runner**（`:820-893`）：SIGINT→SIGKILL、CancelledError 清理；`_FakeProcess` 的 `killpg` 由 monkeypatch 驱动，`getpgid` 永远返回 pid，没有覆盖 `ProcessLookupError`/`killpg ESRCH` 的竞态（点 7）。
- **e2e**（`:929-971`）：见点 13。

**实现思路总结**：用「可脚本 transport + 假进程」把进程管理、argv、解析、错误折叠全部放进单测；真实 CLI 只留一个 happy path 的 opt-in。

**检视发现**：

1. resume 用例脚本化了一个真实 CLI 不可能发生的成功（`:374-400`），掩盖点 1。
2. usage 用例的 payload 是 snake_case（`:549-574`），与真实 `modelUsage` 不符（点 2）。
3. e2e 断言 `result.usage.model` 为真即可（`:971`），`claude-code` 也能过；覆盖不足（点 13）。
4. `_FakeProcess`/monkeypatch 没有覆盖 `getpgid` 抛 `ProcessLookupError` 与 `killpg` 抛 `ESRCH` 的路径；`_signal_process_group` 的 `OSError` 分支只靠代码审查（点 7）。
5. 没有「失败也保留目录」的用例（点 3），也没有「显式目录 discard 不删」的用例（点 3b，属 submission 测试）。
