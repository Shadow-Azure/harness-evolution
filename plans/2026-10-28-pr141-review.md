## §1 一页速览

**一句话：** 这个 PR 把“候选改动只存在于 fixture”升级成真实隔离 workspace、真实 candidate commit/ref、真实 push、accept 后快进 run 分支和 reject 后只删临时 ref 的生命周期。

**比喻：** run 分支像已经盖过章的主档案，candidate 是夹在档案外的一张待审草稿。审核通过时，草稿只允许沿主档案往后追加；审核拒绝时，草稿被销毁，主档案一页不动。PR 的关键价值是让“草稿在哪里、是否干净、能否安全追加”都由 git 自己回答。

## §2 架构导览

### 2.1 先建“只读源 + 独立草稿区”

`GitWorkspaceManager.prepare()` 先确保 `data/repos/{target}` 是当前 `repo_url` 的 mirror，再把指定 tag/ref 解析成 40 位 base commit，并通过 `git cat-file` 确认 `sub_dir` 在目标树中存在（`workspace.py:130-166`）。随后 clone 出 `data/workspaces/{run_id}`，把 workspace 的 `origin` 指回真正远端，再从冻结的 base commit 建 run 分支（`workspace.py:168-237`）。

这像先把参考书复印到自己的书桌：后续 patch、commit、force-with-lease 都只碰复印件，不会直接改用户原工作目录，也不会写 `~/.claude`。

### 2.2 candidate 是一个 tag，不是 run 分支的子分支

Git ref 是文件系统式前缀：存在 `refs/heads/evo/x` 时，不能同时创建 `refs/heads/evo/x/candidate/r1`。PR 因此把可见候选名继续保留为 `evo/x/candidate/r1`，实际存入 `refs/tags`；本地工作分支则哈希成 `harness-candidate/<16 hex>`（`workspace.py:986-989`）。

这是必要的设计修正，不是语义缩水：远端身份、评测 ref、lease、删除和追溯仍使用设计中的可见 candidate 名，只是换了 ref namespace。

### 2.3 发布前验证是一道共享闸门

`validate_for_push()` 和 `_push_run_branch()` 最终都调用 `_validate_publication_state()`：检查当前分支、工作区 clean、期望 commit、base ancestry 与 `Harness-Run-Id`（`workspace.py:521-542,722-775`）。candidate 还额外锁定期望 commit 与本地候选分支（`workspace.py:711-720`）。

这像登机口同时检查登机牌、航班、行李和目的地；只看其中一个字段就可能把已验证草稿换成别的 commit。

### 2.4 push 重试只覆盖候选交通拥堵

`retry_push()` 只在错误被标成 transient 时执行最多三次、间隔五秒；认证、分支保护、non-fast-forward 等永久错误立即抛出（`workspace.py:895-914`）。候选服务把最终失败写进 round、`push_failed` 事件与 run blocked（`git_candidate.py:225-293`）。

### 2.5 run 分支只允许向前

接纳时先在 candidate 上 amend，再用 candidate 自己的旧 hash 做 `--force-with-lease`，随后切回 run 分支，只允许 `git merge --ff-only`，最后非 force 推送 run 分支（`workspace.py:369-434`）。拒绝时只删 candidate tag 和本地临时分支，run 分支不 reset（`workspace.py:444-471`）。

### 2.6 prepare/advance 把持久状态串成可恢复流水线

prepare 用 `progress_unit=0..4` 分阶段写聚类、置信度、严重度与 rounds（`prepare.py:162-324`）；terminal hook 在 prepare 成功后排队 `evolution_advance`（`advance.py:156-168`）。advance 先原子 claim 最早 pending round，再构造 trace 并发布 candidate（`advance.py:72-134`；`evolution.py:720-743`）。

### 2.7 引擎选择在写库之前失败

launch 先检查 mode，再检查 `engine_key` 是否注册，然后才查 target、写 run、排队 prepare（`launch.py:100-146`）。未知 engine 返回稳定 `422 ENGINE_INVALID`，不会留下孤立的 preparing run。

## §3 数据流走查

### 场景 A：创建 full run 并 prepare

1. 用户提交 full query；`launch.py:106-113` 拒绝未知 engine。
2. run 以 `preparing/progressUnit=0` 落库，prepare job 带冻结 query 排队（`launch.py:121-146`）。
3. prepare 读取 probe；没有 analyzed probe 在写 workspace 前返回 `NO_PROBES_MATCHED`（`prepare.py:143-150`）。
4. `progressUnit 0→1` 记录 prepare_started；full 模式建立 mirror/workspace/run branch（`prepare.py:162-199`）。
5. clusters 0→1 后 replace，随后 1→2、2→3、3→4（`prepare.py:201-277`）。
6. 按排名建 pending rounds，run 标 running（`prepare.py:279-325`）。
7. job terminal hook 排队 `evolution_advance`（`advance.py:156-168`）。

### 场景 B：发布第一轮 candidate

1. advance 找到最早非终态 round；前序仍 patching/pushing/evaluating/deciding/failed 时不越过（`advance.py:72-86`）。
2. atomic claim pending → patching；并发重复任务只有一个成功（`evolution.py:720-743`）。
3. candidate 服务从 run branch 建哈希本地分支，写占位 patch 并 commit（`git_candidate.py:190-223`；`workspace.py:239-323`）。
4. push 循环每次先写 pushing/attempt/事件，再执行 candidate push（`git_candidate.py:225-263`）。
5. 成功后写 push_succeeded 与 evaluating；失败则保留 candidate、记 push_failed、run blocked(push)。

### 场景 C：评测接纳

1. apply 从 evaluating/deciding 开始，要求 eval_status=completed（`git_candidate.py:331-343`；`evolution.py:858-880`）。
2. 在 candidate 上 amend 成断言式 commit，并把原评测 hash 写入 `Harness-Evaluated-Commit`（`git_candidate.py:356-367`）。
3. 用旧 candidate hash 做 `--force-with-lease`，把 amended candidate 推到同名 tag（`workspace.py:369-415`）。
4. 切回 run branch，只允许 ff，非 force 推送 run branch，删 candidate（`workspace.py:416-442`）。
5. 持久 round accepted、最终 commit/message 与 run push succeeded（`evolution.py:882-926`）。

### 场景 D：评测拒绝

1. round 进入 deciding。
2. 先切回 run branch；只有 candidate 的远端/本地删除是 best effort（`workspace.py:451-471`）。
3. round 记 rejected，run branch HEAD 不变，拒绝理由进 `cluster_rejected` 事件（`git_candidate.py:399-448`）。

## §6 讨论点

### D1：文档化的 `HE_GIT_PUSH=false` 安全开关实际不生效

**位置：** `apps/api/app/config.py:68`；设计与 Note 分别见 `plans/fullstack-design/04-backend-architecture.md:366`、`.agents/notes/implemented/architecture/2026-10-28-git-candidate-workspaces.md:15`。

**现象：** 配置字段名为 `git_push_enabled`，Pydantic 的 `HE_` 前缀因此读取 `HE_GIT_PUSH_ENABLED`。实际运行 `HE_GIT_PUSH=false` 后 `Settings.git_push_enabled` 仍为 `True`；只有未文档化的 `HE_GIT_PUSH_ENABLED=false` 才生效。

**问题：** 文档和 Note 宣称可关闭全部远端写入，但按文档配置时 run branch、candidate tag、accept/reject 删除仍会真实操作远端。这才是安全开关最危险的失败方式：操作者以为在本地模式，系统仍产生外部副作用。

**预判：** 必须修复。让设置读取 `HE_GIT_PUSH`，并增加环境变量解析与 create_app 注入测试；不要静默支持两个名字而不写清兼容策略。

**结论：**

✅ 2026-10-28：已修复。`Settings.git_push` 对应唯一公开变量 `HE_GIT_PUSH`，组合根使用该值构造同一个完整 workspace manager；环境解析与注入测试通过。未承诺未文档化的 `HE_GIT_PUSH_ENABLED` 兼容别名。

### D2：git timeout 被报告为失败后，子进程仍继续执行

**位置：** `apps/api/app/third_party_api/git/workspace.py:842-860,941-967`。

**现象：** `_git()` 用 `asyncio.wait_for()` 包住 runner，但 `_run_process()` 在 `communicate()` 被取消时没有 terminate/kill 子进程或进程组。实际用 `git alias` 延迟写文件，0.1 秒 timeout 返回 retryable 错误后，1.4 秒时子进程仍写出了文件。

**问题：** 一个“已经失败”的 push 仍可能在后台继续更新远端；调用方同时开始下一次重试，可能产生重叠 push、过期 lease、远端已更新但数据库仍 blocked 等不可解释状态。超时边界没有真正封住外部副作用。

**预判：** 必须修复。`_run_process()` 在取消/超时时终止整个进程组并 await 回收，测试验证 timeout 后不会继续写远端；重试只能在前一次确认终止后开始。

**结论：**

✅ 2026-10-28：已修复。默认进程 runner 在取消时先向 Git 进程组发送 TERM、短暂等待后升级 KILL，并回收进程后才返回 retryable 错误；真实 delayed git alias 回归确认超时返回后不再产生延迟副作用。

### D3：accept 不是可重放的，且 candidate 清理失败违反“非阻断”设计

**位置：** `apps/api/app/service/evolution/git_candidate.py:368-380`；`apps/api/app/third_party_api/git/workspace.py:369-442`；设计见 `07-backend-implementation.md:799-804`。

**现象：** accept 先 amend 本地 candidate，再 push。若 candidate push 瞬时失败，本地分支已指向新 hash，但数据库仍保存旧评测 hash；下一次 apply 以旧 hash 构造 `CandidateWorkspace`，`_validate_candidate()` 直接报 “publication commit changed before push”。临时 bare repo 已复现：首次失败后重试无法继续。

同一路径在 run branch 已成功推送后，远端/本地 candidate 删除任一失败都会抛错；服务把整个 accept 标成 blocked(push)，于是远端主档案已前进、candidate 仍存在、数据库却未 accepted。设计明确要求 candidate 删除失败只警告并把 `cleanupError` 写进 `cluster_accepted`，流程继续。

**问题：** 用户会看到一个已经发布到 run 分支却仍 blocked 的 run；m5-11 即使实现自动 retry，也没有可识别状态把 amend 后 hash、旧评测 hash 与远端 tag 对账。accept 的基础幂等性不成立。

**预判：** 必须在 m5-09 修正 accept 的可重放边界：为 amended/final commit 建立可恢复状态，或每次失败把临时 candidate 恢复到可重建基线；candidate 删除拆成 best-effort 并返回 warning。增加 candidate push 各阶段失败、run push 失败、tag/local delete 失败后的重试测试，不许只测 happy path。

**结论：**

✅ 2026-10-28：已修复。accept 会复用已验证同一 tree、Run-Id、Evaluated-Commit 与 accepted verdict 的 amended 本地/run 分支提交，远端 candidate 与 run 分支已完成步骤幂等；process restart 使用同一 workspace 可继续。run 分支发布成功后，candidate 远端/本地删除失败只写入 `cluster_accepted.payload.cleanupError`，接纳保持成功。

### D4：Git 失败分类在 prepare/candidate 边界不一致，retryable commit 会被误判为 run failed

**位置：** `apps/api/app/service/evolution/prepare.py:177-188`；`apps/api/app/service/evolution/git_candidate.py:200-207,248-293`；`apps/api/app/service/jobs.py:369-385`。

**现象：** candidate 的 `create_candidate()`（patch 落盘、commit、切分支）在 push retry 的 try 之外。其 retryable `GitOperationError(stage=patch|commit)` 会直接逃到 JobRunner 通用异常，run 被标 failed；`commit` 还没有被 job stage 映射识别，会退化成 `step`。prepare 的初始 run branch push 只有 `retryable=True` 才转 blocked，认证/分支保护等永久 push 错误反而走 run failed。

**问题：** 设计区分的是“可重试失败 blocked”和“不可恢复 failed”，以及 `error_stage=patch|commit`；当前分类取决于错误发生在哪个 try 块，而不是错误本身的 stage/retryable。这样 m5-11 无法按 blocked_stage 恢复，也无法把 commit 失败定位到正确阶段。

**预判：** 统一 GitOperationError → RunBlocked/failed 的分类器：所有 push 错误进入 blocked(push)，retryable patch/commit 进入 blocked(patch)，永久 patch/commit 进入 failed 且 error_stage 保留 patch/commit；prepare 与 accept 复用同一映射。增加 patch、commit、initial branch push 的 transient/permanent 测试。

**结论：**

✅ 2026-10-28：已修复。新增共享 `classify_git_failure()`：所有 push 进入 `blocked(push)`，retryable patch/commit 进入 `blocked(patch)`，永久 patch/commit 进入 failed；持久状态和 SSE failure payload 同时保留原始 `patch|commit` error stage。

### D5：自定义 workspace 注入与默认 manager 被拆分，测试组合根存在后台竞态

**位置：** `apps/api/app/main.py:144-181`；`apps/api/tests/m5-05-launch-wizard/test_launch_api.py:293-327`。

**现象：** `create_app(git_workspaces=...)` 的 prepare 使用注入实例；若它不是 `GitWorkspaceManager`，candidate 会退回新的默认 manager，lifecycle cleanup 也固定使用默认 manager。launch API fake 只实现 `prepare()`，却仍会触发真实 candidate advance，后台任务随后面对没有 `.git` 的 fake workspace。

**问题：** 依赖注入的替换是不完整的，测试可能先读到一个 running run，后台再把它改成 failed；这是时序相关且会污染共享 temp 目录的组合根缺陷。

**预判：** 若该参数只用于 prepare，就改名为 `prepare_workspaces` 并明确 candidate/lifecycle 仍需要完整 manager；若用于完整替换，则 candidate 与 cleanup 必须使用同一实例，并为注入契约增加测试。没有当前生产实害，但会让本 PR 的 E2E/API 测试不稳定。

**结论：**

✅ 2026-10-28：已修复。prepare、candidate 与 lifecycle retention 使用同一个注入实例；prepare-only fake 显式声明 `supports_candidate_lifecycle=false`，terminal hook 因而不调度候选，避免后台回退到默认真实 manager。

### D6：`HE_GIT_PUSH=false` 被展示为远端 push 成功

**位置：** `apps/api/app/service/evolution/git_candidate.py`、`apps/api/app/db/crud/evolution.py`、`apps/web/src/pages/evolution/components/StepIterations.vue`、`apps/web/src/pages/evolution/runDetail.ts`。

**现象：** Computer Use 使用临时 bare remote 启动真实 full run 并设置 `HE_GIT_PUSH=false` 后，远端 ref 前后完全不变，但 round 持久为 `succeeded` 并进入 `evaluating`；RunDetail 同时显示“candidate 已 push / 推送成功”和 run 级 `pending`。

**问题：** 操作者无法区分本地 candidate 与真实远端发布；这是关于外部副作用事实的错误陈述。

**结论：** ✅ 2026-10-28 已修复。disabled push 现在以 `round.status=skipped`、round/run `push_status=skipped`、`eval_status=pending` 停住；UI 统一显示“本地候选（未推送）/已跳过（本地模式）”。重复 refresh/publish 幂等，远端 ref 不变。

## §9 文件级代码分析

### 9.1 `apps/api/app/third_party_api/git/workspace.py`（A，989 行）

**职责：** 把 mirror、workspace、run branch、candidate tag、push、accept/reject 与保留策略封装在单一 Git boundary 内。

**关键依赖：** 标准库 `asyncio/subprocess` 以 argv 数组调用 git，不经过 shell；`tempfile` 只在测试中提供真实 bare remote。像把命令写成“一个一个信封参数”，远端 URL 中即使有空格或 shell 字符也不会被解释成第二条命令。

**变更代码块：**

- `prepare()` 先解析/刷新 mirror，再 clone workspace、设置真实 origin、恢复或创建 run branch（130-237）。这是“源与草稿分离”的主体。
- `create_candidate()` 校验 ref/run id/ancestry，创建哈希本地分支，写 patch、stage、commit（239-323）。
- `push_candidate()` 先查远端 tag；初推拒绝覆盖他人值，re-push 只用精确 `--force-with-lease`（325-367）。
- `accept_candidate()` amend → lease push candidate → ff merge run → non-force push run → delete candidate（369-442）。
- `reject_candidate()` 先切回 run branch，再 best-effort 删 candidate（444-471）。
- `_validate_publication_state()` 统一校验 selected branch、commit、clean、ancestry、trailer（722-775）。
- `_run_process()` 使用 `GIT_TERMINAL_PROMPT=0`、stdin DEVNULL、start_new_session（941-967）。

**实现思路总结：** 由 Git 自己裁决 ref/提交关系；发布前只接受一个完整快照；run branch 只能 ff，candidate 才可 lease force。

**检视发现：**

- D1 所在配置开关在另一文件，但这里所有 `_push_enabled` 分支都依赖它。
- D2 timeout 取消只停 Python coroutine，没有终止真实 git 进程。
- D3 accept 后续普通删除与显式“best effort”不一致。
- D4 `GitOperationError(stage/retryable)` 已是很好的分类输入，但上层没有统一消费。

### 9.2 `apps/api/app/service/evolution/git_candidate.py`（A，714 行）

**职责：** 生成可追溯 commit message，并把持久 round 接到真实 Git lifecycle。

**关键依赖：** `EvolutionRepository` 是状态事实源，`EvolutionRunEventService` 是过程事实源，workspace manager 是副作用边界。像“舞台监督”同时维护节目单（DB）、广播（events）和道具位置（Git）。

**变更代码块：**

- `build_candidate_message()` 和 `build_accepted_message()` 固定 subject、问题、分析、改动、追溯与 trailers（69-137）。
- `publish()` 依次写 patching、candidate、pushing；push retry 后进入 evaluating 或 blocked（174-317）。
- `accept()` 从 deciding 构造 candidate 快照，amend/ff 后持久 accepted（319-397）。
- `reject()` 只删 candidate 并持久 rejected（399-448）。
- `_record()` 是 best-effort，事件失败不覆盖 git 事务（450-484）。

**实现思路总结：** 先把 Git 产物写进 round，再推进 push/eval；message 的机器 trailer 与人类叙事都可由测试复现。

**检视发现：**

- D3：accept 的失败没有被持久化为可重放状态。
- D4：`create_candidate()` 在 push try 之外，所以 patch/commit 的 retryable 错误无法变成 blocked(patch)。
- accept 的通用 GitOperationError 全被映射成 blocked(push)，即使实际是 amend/切分支/cleanup 失败，错误阶段会误导恢复。

### 9.3 `apps/api/app/service/evolution/prepare.py`（M，500 行）

**职责：** 用冻结 run/query 完成 probe 筛选、确定性聚类、置信度、严重度、rounds 与 workspace checkpoint。

**关键依赖：** `ProbeQueryRepository` 读取归一化事实，`simple_cluster` 是确定性占位算法，`EvolutionRepository` 用 conditional cursor 防越级。

**变更代码块：**

- `handle()` 以 `progress_unit` 分段，重复执行可跳过已完成写入（129-335）。
- full 模式仅在 prepare 阶段建 workspace；cluster_only 不建（177-199）。
- rounds 从 severity rank 排序生成一次，retry 检查已有数量（279-306）。
- `_trace()` 从 probe rows 汇总来源、分析与 bad cases（advance.py:184-216）。

**实现思路总结：** 每段写库都自成一个 checkpoint；重试从当前 cursor 继续，不依赖进程内状态。

**检视发现：**

- D4：initial run-branch push 的永久失败逃到通用 job failure，和 candidate push 的 blocked 语义不一致。
- 当前 checkpoint 测试覆盖 0–4，主路径质量较好。

### 9.4 `apps/api/app/service/evolution/advance.py`（A，222 行）

**职责：** 选择顺序轮次、发出真实 candidate，并提供 job terminal hook。

**关键依赖：** repository 的 conditional update 是并发唯一裁决者，probe reader 补 trace，candidate service 执行副作用。

**变更代码块：**

- `handle()` 遇到前序非终态立即停止，accepted/rejected 才跳过（59-134）。
- `claim_round_for_advance()` 的原子 pending→patching 是防止双发布的关键（evolution.py:720-743）。
- `EvolutionJobLifecycle` prepare 成功后排队 advance，并清理非活动 workspace（156-181）。

**实现思路总结：** 用数据库 CAS 做队列幂等，Git 内不做“猜测下一个轮次”。

**检视发现：**

- D5：lifecycle 固定使用默认 workspace manager，和 create_app 的注入参数不是同一依赖链。

### 9.5 `apps/api/app/db/crud/evolution.py`（M，1107 行）

**职责：** 持久 prepare cursor、clusters、rounds 和 accept/reject 终态。

**变更代码块：**

- `advance_unit()` 用 `WHERE progress_unit=expected` 做 cursor CAS（430-465）。
- `insert_rounds()` 同时检查 run cursor 与 cluster owner（587-662）。
- `claim_round_for_advance()` 只允许 pending round 被一个调用者取得（720-743）。
- `accept_round()/reject_round()` 只接受 deciding，写成吸收态（882-960）。

**实现思路总结：** 同一业务动作尽量用一个条件 UPDATE 决定“谁赢”，避免先读再写。

**检视发现：**

- 终态反向改写已有条件保护；accept 失败后的 Git/DB 对账仍未解决（D3）。

### 9.6 `apps/api/app/service/evolution/launch.py` 与 `engine/factory.py`（M）

**职责：** 在启动写库前校验 mode、engine registry、target 和 probe hits。

**变更代码块：** `is_registered()` 查封闭 registry（factory.py:15-23）；launch 立即返回 `422 ENGINE_INVALID`（launch.py:106-113），之后才 create_run。

**实现思路总结：** 无效 engine 不留下半成品 run，错误码在 OpenAPI 与生成 DTO 中同步。

**检视发现：** 无问题；测试明确断言写前失败。

### 9.7 `apps/api/app/config.py` 与 `apps/api/app/main.py`（M）

**职责：** 暴露 Git push 开关并组装 prepare/candidate/advance/lifecycle。

**变更代码块：**

- config 增加 `git_push_enabled: bool = True`（config.py:68）。
- main 创建默认 manager，并分别接 prepare、candidate、lifecycle（main.py:147-181）。

**实现思路总结：** 组合根应把同一个副作用边界交给所有阶段。

**检视发现：**

- D1：字段名产生 `HE_GIT_PUSH_ENABLED`，和文档 `HE_GIT_PUSH` 不一致。
- D5：candidate/lifecycle 可能与注入的 prepare manager 使用不同实例。

### 9.8 契约与设计文件（M）

**职责：** 为 `ENGINE_INVALID` 和 Git ref namespace 修正提供单一事实。

**变更代码块：**

- ErrorCode 枚举和生成 DTO 同步新增 `ENGINE_INVALID`。
- 06 把 candidate_ref 描述为远端 tag/ref；07 明确 run branch 在 refs/heads、candidate 在 refs/tags、本地分支哈希化。

**实现思路总结：** 设计修正来自 Git 的硬约束，且保留外部可见 ref 名，不改变 API/UI 语义。

**检视发现：** 设计修正合理，未放宽验收；但 env 开关文档与 code 不一致（D1）。

### 9.9 测试文件（A/M）

**职责：** 用真实临时 bare remote 与 SQLite 验证生命周期，而不是只 mock service。

**覆盖优点：**

- mirror repo_url 切换、push disabled 的所有远端 mutation、clean/ancestry/trailer、candidate tag/run branch 关系都有真实断言。
- prepare checkpoint 0–4、并发 advance claim、terminal absorbing state、push_failed 顺序有针对性测试。
- commit message 的 subject、trailers、analysis 截断和 URL 安全性有直接测试。

**检视发现：**

- 缺少 git timeout 后进程终止测试，导致 D2 未被发现。
- 缺少 patch/commit retryable 到 blocked(patch) 和永久 initial push 到 blocked(push) 的 job-level 分类测试，导致 D4 未被发现。
