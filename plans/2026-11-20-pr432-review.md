## §1 一页速览

**一句话**：运行详情页过去像一个装满卡片却没有装轮子的抽屉——内容多出可见区域后，外层柜门（`main.workspace-main`）关着且写着“禁止伸出”，抽屉本身又没有滑轨，于是下半截永远拿不到；这个 PR 给抽屉装上滑轨（`overflow-y: auto`），并把抽屉内容限制在原型规定的 1720px 宽、左右留 24px。

**比喻**：工作区壳层是一张固定高度的桌子，总览、管理页各自在桌面上放了一块可滑动的垫板；运行详情直接把纸铺在桌面上，纸比桌子长就被桌沿裁掉。修复不是把桌子改成无限长（那会影响所有页），而是给运行详情也放一块全宽垫板，让滚动条出现在桌子右缘。

| 交付块 | 内容 | 用户可感知结果 |
|---|---|---|
| 滚动容器 | `.run-detail-page` `height:100%` + `overflow-y:auto` | 滚轮、PageDown、End 可看到第 5 步簇列表与第 6/7 步、日志页签 |
| 页宽 | `padding: 20px max(24px, calc((100% - 1720px)/2 + 24px)) 64px` | 1500 视口左右各 24px；1920 视口内容在 1720px 封顶并居中 |
| 移动端 | ≤640px `height:auto; overflow-y:visible; padding:14px 12px 48px` | 由文档滚动，不出现双层滚动条 |
| 回归 | `m10-06` 新增四视口几何 + 真实输入断言 | 下一次重排把内容推过折叠线时 CI 会红 |

**验证基线**：本地 `m10-06` 3/3、`test:web`、`typecheck:web`、`lint:web`、`build`、`lint:docs`、`verify:docs`、`verify:flow` 全绿；Before/After 截图见 PR 描述与 release evidence。

## §2 架构导览

### 2.1 滚动归属：壳层固定，页面自理

`apps/web/src/App.vue:116-121` 把工作区 `main` 固定为 `height: calc(100vh - var(--shell-header-height))`、`overflow: hidden`，文档本身不滚动。这是全应用约定，不是运行详情的局部选择。

总览页用 `.overview-page` 承担页级滚动：`width:100%; height:100%; overflow-y:auto`，并用对称内边距把 1180px 内容列居中（`apps/web/src/pages/overview/Index.vue:607-615`）。m12-16 的 Agent Note 记录了“全宽滚动容器让经典滚动条落在窗口右缘”的取舍。运行详情此前缺少这一层，是本 issue 的根因。

### 2.2 页宽：1720px 原型口径

V2 原型的 `.evo-app .wrap` 定义 `width: min(100%, 1720px)`、`margin: 0 auto`、`padding: 20px 24px 64px`（`plans/ui-prototype-v2/harness-evolution.html:606`），`evRenderDetail()` 把详情渲染进 `.wrap`（同文件 `5533-5545`）。实现没有引入包装层，而是直接把内边距放在根节点上：

- 左右：`max(24px, calc((100% - 1720px) / 2 + 24px))`。视口 ≤1720 时为 24px；更宽时每侧多出 `(100% - 1720px)/2`，使内容列封顶 1720px 并居中。
- 上下：20px / 64px，对齐原型。
- 根节点保持 `width: auto`（父级 100%），因此滚动条在 `main` 的右缘，而不是内容列右缘。

### 2.3 断点：与壳层同一 640px 分界

`main.workspace-main` 在 `max-width:640px` 改为 `height:auto; overflow:visible`（`apps/web/src/App.vue:133-137`）。运行详情的同一断点把根节点改为 `height:auto; overflow-y:visible`、`14px 12px 48px` 内边距（`RunDetail.vue:1398-1407`），把滚动交还文档。两端使用同一分界，避免 641–1024px 之间出现“壳层已文档滚动、页面还在内滚动”的双层状态。

### 2.4 回归测试

新增用例 `tests/e2e/m10-06-run-detail-v2.test.mjs:664`，在 1500×837、1440×900、1366×768、1920×1080 下断言：

- 根节点 `overflow-y:auto`，`main` 仍 `overflow-y:hidden`；
- 根节点左右边界贴住窗口；左右 padding 为 24/124px；
- 内容列 ≤1720px；根节点与文档都没有横向溢出；
- `scrollHeight > clientHeight`；
- 真实滚轮让 `scrollTop > 0`，再聚焦页内按钮后 PageDown + End 到达底部（差 ≤2px）；
- 640×900 下根节点 `overflow-y:visible`、`main` `overflow:visible`、文档 `scrollHeight > clientHeight`。

登录限流从默认 10 提到 100，避免用例在四个视口回访时收到 429；这与 m8-04/m11-04 等既有套件的做法一致。

## §3 数据流走查

1. 路由进入 `/workspaces/:wid/evolution/runs/:runId`，`RunDetail.vue` 挂在 `main.workspace-main` 内。
2. `main` 的高度由壳层固定为视口减顶栏；`<section class="run-detail-page">` 是唯一根节点，`height:100%` 解析为 `main` 的内容高度（`RunDetail.vue:945-961`）。
3. 根节点成为滚动容器后，内容超过高度时浏览器在 `main` 右缘绘制滚动条；内容盒宽度扣除 15px 经典滚动条与左右 padding。
4. 滚轮落在根节点上，浏览器滚动根节点而不是文档；`window.scrollY` 保持 0，`document.scrollingElement.scrollHeight === clientHeight`。
5. 页内步骤按钮获得焦点后，PageDown/End 的滚动目标是其最近的可滚动祖先——根节点，因此可到达底部。
6. 视口缩到 ≤640px，`main` 改为 `height:auto; overflow:visible`，根节点同时改为 `overflow-y:visible`，文档成为唯一滚动容器。
7. 离开详情页回到列表时组件卸载，滚动状态随 DOM 消失；不存在跨页面残留。

## §6 讨论点

### D1 冷加载后 PageDown/End 不滚动，需要焦点先进入页面

- **位置**：`apps/web/src/pages/evolution/RunDetail.vue:945-961`（`overflow-y:auto` 的根节点）与新增 E2E `tests/e2e/m10-06-run-detail-v2.test.mjs:813-846`。
- **现象**：页面加载后焦点在 `body`，直接按 End/PageDown 不会滚动根节点（实测 `scrollTop` 保持 0）；点击页内步骤按钮或 Tab 到页内链接后，同样的按键可以滚到底。滚轮不依赖焦点，始终可用。
- **问题**：issue 验收写的是“滚轮、PageDown、End 都能到达页面底部”，未限定必须先获得页内焦点。这是内滚动容器相对文档滚动的固有差异；总览页目前也是同一行为。
- **预判**：可接受，不阻塞交付。键盘用户按一次 Tab 即进入页内链接，之后 PageDown/End 生效；E2E 用真实鼠标点击步骤按钮模拟了正常交互路径。若要彻底消除差异，需要把滚动交还文档（影响所有工作区页）或给根节点加 `tabindex`（增加整页焦点停靠点），都应另开 issue。无实害，记录为限制。
- **结论**：

### D2 经典滚动条使 1920 下内容列比原型窄 15px

- **位置**：`apps/web/src/pages/evolution/RunDetail.vue:957`（padding 公式）与 `plans/ui-prototype-v2/harness-evolution.html:606`（原型 `.wrap`）。
- **现象**：1500×837 下实现内容列 1437px，原型同视口也是 1437px；1920×1080 下实现内容列 1657px，原型 1672px。差异来自常显滚动条：实现的 padding 以 `main` 的 1920px 为基准计算（每侧 124px），滚动条又占走 15px；原型把 1720px 的 `.wrap` 居中在 1905px 滚动端口里，滚动条被算在 `.wrap` 之外。
- **问题**：issue 的验收口径同时要求“1920 下内容区在 1720px 处封顶并居中”和“左右留白差异 ≤6px”。实现左右 padding 都是 124px，与原型左边界 122.5px 差 1.5px；但内容列宽度差 15px，严格按内容宽度比较会超出 6px。
- **预判**：可接受。用户看到的左右留白（不含滚动条）都是 124px 左右；内容宽度差异只在常显滚动条的平台上出现，且没有隐藏滚动条或压缩内容。issue 给出的 1920 期望 padding 124–130px 与实现一致。若产品要求内容宽度逐像素对齐，需要把滚动条宽度也纳入公式（例如 `calc(100% + scrollbar)` 方案），但那会让滚动条覆盖内容或改变滚动条归属，代价更大。无实害，记录为限制。
- **结论**：

### D3 1920×1080 从“恰好不溢出”变为可滚动

- **位置**：`RunDetail.vue:957-959`。
- **现象**：Before 内容高 1018px、`main` 可视高 1024px，1920 视口不出现纵向裁切；After 加上 20px 上内边距与 64px 下内边距后 `scrollHeight` 1102px，超过 1024px，1920 也会出现纵向滚动。
- **问题**：这是补齐页容器的直接结果，不是内容变多；但可能被误认为“1920 之前好好的，现在多了滚动条”。
- **预判**：预期行为。原型在 1920 下也是文档滚动（`scrollHeight 1749 / clientHeight 1080`）；64px 底部内边距本来就是设计的一部分。保留，PR 描述已写明。
- **结论**：

### D4 流程 issue 保持 ready 而不能置为 in-progress

- **位置**：`.agents/flow/issues/bugfix-run-detail-scroll-gutter.md:7`（`status: ready`）。
- **现象**：实现期间按流程本应改为 `in-progress`，但 `pnpm verify:flow` 的 P2 跨 milestone 串行规则要求 m22/m23/m24 的同档 issue 全部 done；当前仍有未完成项，改为 in-progress 会红门禁。
- **问题**：流程状态与实现进度不完全一致；issue 本身要求提出人确认后才关闭，PR 也不是最终闭环。
- **预判**：保持 `ready` 是当前门禁下唯一不撒谎又不红门禁的选择；PR 描述已说明。等 m22–m24 的 P2 清零或提出人确认后再由流程 PR 置为 in-progress/done。记录为流程欠账，不在本 PR 修流程规则。

## §9 文件级代码分析

### 9.1 `apps/web/src/pages/evolution/RunDetail.vue`

**职责**：运行详情页组件；本次只改 `<style scoped>` 的根节点与断点。变更形态 M。

**旧代码**：

```css
.run-detail-page {
  display: grid;
  grid-template-columns: minmax(0, 1fr);
  gap: 14px;
  min-width: 0;
}
```

**新代码**：

```css
.run-detail-page {
  display: grid;
  grid-template-columns: minmax(0, 1fr);
  gap: 14px;
  min-width: 0;
  height: 100%;
  padding: 20px max(24px, calc((100% - 1720px) / 2 + 24px)) 64px;
  overflow-y: auto;
}
```

**在做什么**：把页面根节点变成固定高度、可纵向滚动的容器；左右内边距按原型 1720px 页宽计算，上下补原型间距。

**为什么这么写**：壳层已经固定 `main` 高度并隐藏溢出，页面必须自己提供滚动；根节点保持全宽才能让滚动条落在窗口右缘。`height:100%` 依赖父级确定高度，这与壳层契约一致；若壳层改成 `height:auto`，断点样式会同步交接（见 9.2）。

**实现思路总结**：根节点承担滚动，不新增 DOM；页宽用 padding 表达，不引入内容包装层。

**断点新增**：

```css
@media (max-width: 640px) {
  .run-detail-page {
    height: auto;
    padding: 14px 12px 48px;
    overflow-y: visible;
  }
}
```

**在做什么**：壳层在 640px 改为文档滚动后，页面同时交还滚动，内边距回落到 12px，避免双层滚动条与双重留白。

**检视发现**：无代码缺陷。D1/D2/D3 是内滚动容器与常显滚动条带来的已知行为差异，已记录；不新增代码复杂度去消除它们。

### 9.2 `apps/web/src/App.vue`（未改，作为边界）

`main.workspace-main` 在 116-121 行固定高度并 `overflow:hidden`，在 133-137 行的 640px 断点改为 `height:auto; overflow:visible`。新样式与这两个分支一一对应，因此未修改壳层。

### 9.3 `tests/e2e/m10-06-run-detail-v2.test.mjs`

**职责**：运行详情真实浏览器回归；新增第三个用例，并在 before 环境里把登录限流上限设为 100。变更形态 M。

**关键依赖解读**：测试直接通过 CDP 驱动真实 Chrome，不依赖 Playwright 封装；`Input.dispatchMouseEvent` 派发真实滚轮与鼠标点击，`Input.dispatchKeyEvent` 派发 PageDown/End。`createBrowserPage` / `waitForDocument` 来自 `tests/support/runtime.mjs`，负责启动独立 profile 与轮询 DOM。

**新增用例在做什么**：

1. 对四个视口逐一设置 device metrics，重新登录并打开 `?step=clusters`。
2. 读取 `main` 与根节点的计算样式、边界、`scrollHeight/clientHeight`，断言滚动容器贴窗口、padding 为 24/124、内容 ≤1720、无横向溢出。
3. 在 1500 下用真实滚轮滚动，再点击页内步骤按钮获得焦点，按 PageDown/End，断言到达底部。
4. 在 640×900 下断言根节点 `overflow-y:visible`、`main` `overflow:visible`、文档可滚动。

**为什么这么写**：几何断言固化“可滚动 + 页边距”两个回归点；真实输入避免只测 `scrollTop` 赋值而漏掉滚轮/键盘路径；640 断点防止内滚动与文档滚动叠加。
