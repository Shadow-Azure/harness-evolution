## §1 一页速览

**一句话**：把“往哪推、用什么身份推、推之前先 fork 到谁名下”从 `GitWorkspaceManager` 构造时写死的全局 `HE_GIT_PUSH_URL` 抽成一个可插拔的 `GitPushProvider`（工厂按 `HE_GIT_PUSH_PROVIDER` 选 GitHub/GitLab），prepare 时把派生目标写进 `run.push_repo_url`，candidate/final/评测都复用它。

**比喻**：以前公司只有一个固定收货地址（全局 push URL），快递员（workspace）不管发什么货都往那送；现在设了一个总台（工厂）：总台按“目的地城市”叫来对应的平台专员（GitHub/GitLab），专员自己查地址簿（URL/API/fork）并把门禁卡（PAT）交给快递员；快递员只负责跑腿（执行 git），不再背死一个地址。专员换人只换总台登记，不动快递路线。

## §2 架构导览

### 2.1 配置与工厂：一个部署只选一个平台

`Settings` 新增两个字段：`git_push_provider: Literal["github","gitlab"] = "github"` 与 `git_push_token: SecretStr | None`（`apps/api/app/config.py:133-136`）。`Literal` 让非法值在 Settings 解析时直接 `ValidationError`，这是“未知值启动失败”的第一道门；`GitPushProviderFactory.create` 再按 registry 取实现，取不到时抛 `ValueError`（`provider.py:540-554`），这是代码内构造 settings 时的第二道门。

`main.py` 在 composition root 只构造一次 provider（`main.py:161`），把 `provider.auth_environment` 作为回调交给代理感知 runner（`main.py:162-165`），并把同一个 provider 注入 `GitWorkspaceManager`（`main.py:341-348`）。因此 run 执行期不读环境、不新建 provider；新增平台只需 `register()` 一个子类，不改服务层。

一个生活化比喻：工厂是“总台”，registry 是总台桌上的内线表；业务方只说“我要 GitHub”，总台叫对应专员，专员自己知道该平台的地址簿与门禁规则。换平台是换内线表，不是把整栋楼的路线重画。

### 2.2 父类与两个子类：URL、认证、fork 是平台差异

`GitPushProvider`（`provider.py:135`）定义 `remote_url`、`auth_environment`、`ensure_fork`、`open_pull_request` 四个契约，以及公共 `remote_ref`/`push_ref` 模板方法（`provider.py:208-244`）。`GitHubProvider` 用 `https://api.github.com`（自托管用同一 web root 的 `/api/v3`，`provider.py:310-314`）、`Bearer` 头、`x-access-token` 用户名；`GitLabProvider` 用 `/api/v4`、`PRIVATE-TOKEN` 头、`oauth2` 用户名（`provider.py:421-527`）。

`remote_url` 永远返回**无凭据**的 HTTPS URL：`parse_repository` 只保留 scheme/host/port/namespace/name，SSH 与 scp-like 输入一律落回 HTTPS 且丢弃 SSH 端口（`provider.py:74-95`）。这就是“token 不进 URL”的结构性保证：URL 里根本没有 token 的位置。

### 2.3 认证环境与 GIT_ASKPASS：把门禁卡放在子进程环境里

`auth_environment()` 在有 token 时返回四个变量：`GIT_ASKPASS`、`GIT_TERMINAL_PROMPT=0`、`HE_GIT_PUSH_USERNAME`、`HE_GIT_PUSH_TOKEN`（`provider.py:177-192`）。git 在需要用户名/密码时会调用 `GIT_ASKPASS` 指向的脚本；脚本按提示词前缀返回用户名或 token（`deploy/git-askpass.sh:9-20`），token 只出现在 stdout，未知提示词只写固定错误到 stderr 并 `exit 1`（fail closed）。

没有 token 时返回空 mapping（`provider.py:185-186`），保留 ambient credential helper 的旧行为；这是“未配置新字段时行为与今天一致”的落点。

### 2.4 代理感知 runner：凭据环境必须加在进程缝上

`ProxyAwareGitRunner.run` 有两条路径：直连（`proxy.py:572-578`）与代理失败后的直连重试（`proxy.py:603-608`）。两处都调用 `build_git_environment()`，再合并 `extra_environment()`。这样无论走不走代理，`GIT_ASKPASS`/token 都在 git 子进程环境里；如果只在 workspace 的 `_run_process` 注入，生产用 proxy runner 时凭据会丢。

`GitWorkspaceManager` 同时保留一个 `_auth_environment`（`workspace.py:172`），只在没有注入 runner 的本地/测试路径使用（`workspace.py:1336-1339`）；生产 runner 是 proxy runner，凭据由 proxy 层负责，两条路径语义一致。

### 2.5 workspace：一次 run 一个目标，不再有全局 `_push_url`

`PreparedWorkspace` 与 `CandidateWorkspace` 各加一个 `push_url` 字段（`workspace.py:76,113`），`prepare` 在克隆前解析目标（`workspace.py:184`），并把 `push_url` 传给 remote 设置、候选推送、final 发布、`ls-remote` 与 tag 删除（`workspace.py:230,246,250,337,350,471-477,530-538,576,683,720,732,778,793-805`）。

`_resolve_push_url` 的顺序是：`run.push_repo_url` 快照 → provider `ensure_fork`（仅当有 token）→ `HE_GIT_PUSH_URL` 兜底 → `None`（推 origin）（`workspace.py:1071-1089`）。`_ensure_push_remote` 在目标非空时确保名为 `push` 的 remote 存在且 URL 正确，否则返回 `origin`（`workspace.py:1091-1119`）。fetch 仍走 `origin`，写操作与候选 ref 查询走 `push`，因此“读上游、写 fork”是同一工作区里的两条 remote。

### 2.6 run 快照与迁移：空串表示“没有派生目标”

`evolution_runs.push_repo_url` 是 `String(1024)`、`nullable=False`、`server_default=""`（`models/evolution.py:64-67`），dataclass 默认 `""`（`models/evolution.py:353-357`），行映射用 `or ""` 兜底（`models/evolution.py:550-556`）。迁移 0024 只加列、不回填、可重复执行（`0024_push_repo_url.py:22-52`），downgrade 只删列（`0024_push_repo_url.py:55-62`）。

`mark_prepared` 的参数默认 `None`，只有非 `None` 才写（`crud/evolution.py:315-340`）；prepare 只在 full 模式有 workspace 时传 `workspace.push_url`（`prepare.py:315-332`）。空串在 API 与评测两处回退 `repo_url`（`runs.py:489-491`、`eval_poller.py:89-92`），历史行因此可读、可评测。

### 2.7 eval 同源：push 到哪，评测就从哪取

`EvolutionEvalSubmitter.submit` 把 `EvalRequest.repo_url` 从 `run.repo_url` 改为 `run.push_repo_url or run.repo_url`（`eval_poller.py:89-92`）。这是本 PR 修“push 到 fork 但 eval 仍从上游取 commit”的关键一行；如果只改 workspace 不改这里，fork 上的 candidate commit 在评测侧不可 fetch，失败会从 blocked(push) 变成 blocked(eval)。

### 2.8 Deploy：把 token 放进 0600 `.env`，把脚本放到绝对路径

Deploy 从 Environment Secrets 读 `HE_GIT_PUSH_PROVIDER`/`HE_GIT_PUSH_TOKEN`（`deploy.yml:262-263`），先校验 provider 取值，再把 `deploy/git-askpass.sh` 安装到 `/opt/harness/shared/git-askpass.sh`（`deploy.yml:285-288`），把 provider、`GIT_ASKPASS` 与 token 以 `KEY <base64>` 形式经 stdin 交给 `inject-config.py`（`deploy.yml:290-315`）。token 为空时追加 `--unset HE_GIT_PUSH_TOKEN`（`deploy.yml:303-307`）；`inject-config.py` 的 `--unset` 是 `action="append"`，可重复（`deploy/inject-config.py:99-108`），因此与 `HE_GIT_PROXY` 的 unset 可以并存。注入后强制 `chmod 600` 并用 `stat -c '%a'` 复核（`deploy.yml:316-323`）。

## §3 数据流走查

一条从 run 创建到评测的端到端脚本（正常路径 + 失败分叉）：

1. **创建 run**：target 只有 `repo_url`（上游，只读），没有 push 字段；`EvolutionTargetWrite` 仍只有原有字段（`targets.py:45-55`）。run 行的 `push_repo_url` 初始为空串（迁移默认）。
2. **prepare 解析目标**：`EvolutionPrepareService.handle` 在 full 模式调 `_prepare_workspace`（`prepare.py:315-317`），后者 try 包住 `workspace.prepare`（`prepare.py:451-484`）。`GitWorkspaceManager.prepare` 先调 `_resolve_push_url`（`workspace.py:184`）：快照为空 → 有 token → `provider.ensure_fork(run.repo_url)`（`workspace.py:1078-1080`）。
3. **provider 自动 fork（GitHub）**：`ensure_fork` 先 `login`（GET `/user` 取 login 并按 host 缓存，`provider.py:364-380`），若上游 namespace 是自己则直接用上游 URL；否则 `_repo_exists`（GET `/repos/{login}/{name}`，404→None，`provider.py:400-419`），不存在就 POST `/repos/{upstream}/forks`（`provider.py:342-346`），再 `_wait_for_fork` 轮询 6 次×1s（`provider.py:291-301,348-350`）。返回 `https://host/{login}/{name}.git`（无凭据）。
4. **失败分叉（provider API）**：`ensure_fork` 抛 `GitPushProviderError`（401/403 带 status；429/5xx/传输也可能是 status 或 None）。`_resolve_push_url` 转成 `GitOperationError("push fork preparation failed (HTTP n)", stage="push", retryable=status is None or status in {429,500,502,503,504})`（`workspace.py:1081-1088`）。prepare 捕获后 `classify_git_failure` 把 stage=push 判为 `blocked(push)`（`git_failures.py:23-30`），`mark_blocked` 并抛 `RunBlocked`（`prepare.py:467-484`）。

6. **candidate 推送**：`EvolutionCandidateService.publish` 用 `prepared.push_url` 重建 `CandidateWorkspace`（`git_candidate.py:391-401`），`push_candidate` 确保 `push` remote（`workspace.py:350`）并用 `--force-with-lease=<expected>` 推 candidate ref（`workspace.py:340-383`）。
7. **accept / final**：accept 重建 candidate 时继续带 `push_url`（`git_candidate.py:494-504`），删除候选 tag 走同一 `push` remote（`workspace.py:535-538`）；final/apply 阶段 `_prepared_workspace(run)` 用 `run.push_repo_url or None` 重建（`apply_final.py:370-386`、`git_candidate.py:877-892`），发布 run 分支（`workspace.py:662-711`）。
8. **prepare 持久化快照**：prepare 成功时 `mark_prepared(..., push_repo_url=workspace.push_url)`（`prepare.py:320-332`）写入 DB；`mark_prepared` 只在非 None 时覆盖（`crud/evolution.py:339-340`），所以后续重试/非 full 流程不会清空快照。
9. **API/UI 展示**：`EvolutionRunService.detail` 构造 `EvolutionRunWorkspace(push_repo_url=run.push_repo_url or run.repo_url)`（`runs.py:489-491`），契约必填 `pushRepoUrl`（`openapi.json:2785,2849`），页面渲染“推送目标”（`RunDetail.vue:856-869`）。历史 run 空串时显示 `repo_url`。
10. **eval 提交**：`EvolutionEvalSubmitter.submit` 用 `run.push_repo_url or run.repo_url` 作为 `EvalRequest.repo_url`（`eval_poller.py:89-92`），ref/commit 仍取 round 的 candidate 值；于是“候选 commit 在 push 目标上存在”与“评测从同一目标取”成立。

## §6 讨论点

### D1 provider 登录缓存按 host 隔离

**位置**：`apps/api/app/third_party_api/git/provider.py:141-160`（`_logins` 初始化）、`:364-380`（GitHub `login`）、`:481-497`（GitLab `login`）。

**现象**：`_logins: dict[str, str]` 的 key 是 `RemoteRepository.host_and_port`；GitHub/GitLab 的 `login()` 先查缓存，未命中才 GET `/user`。同一 provider 实例服务多个 host（例如 `github.com` 与一台 GHE）时，缓存按 host（含显式端口）分开；同一 host 的不同 namespace 共用一个登录名。

**问题**：同一部署只用一把 PAT，按 host 缓存是正确的；但在并发 prepare 时，两个 run 同时首次访问同一 host 会各发一次 GET `/user`，后写覆盖先写；值相同，只是重复请求。没有锁，也没有缓存过期——token 轮换需要重启进程才会重新取 login（Settings 本身也是启动期快照，符合现状）。

**预判**：安全，不存在跨 host 串用；并发重复请求无实害。可选改进是加一个 per-host in-flight `asyncio.Lock` 去重，但不属于本 issue 的交付边界。

**结论**：接受为无实害（2026-11-21）。同一部署一把 PAT，按 host 缓存不会跨 host 串用；并发首次 GET 只是重复请求，值相同，不加锁。

### D2 `_resolve_push_url` 的兜底顺序与历史行为

**位置**：`apps/api/app/third_party_api/git/workspace.py:1071-1089`；`apps/api/app/third_party_api/git/provider.py:330-352`；`apps/api/app/config.py:222-235`。

**现象**：解析顺序是 `run.push_repo_url` → provider fork（仅 `has_token`）→ `_fallback_push_url`（`HE_GIT_PUSH_URL`）→ `None`，`None` 在 `_ensure_push_remote` 里变成 `origin`（`workspace.py:1097-1098`）。历史部署（无 token、无 URL）推 origin，与旧行为一致；配置了 `HE_GIT_PUSH_URL` 的部署仍可用它兜底。

**问题**：两个语义变化需要明说：① 一旦 deployment 配了 token，`HE_GIT_PUSH_URL` 就不再是“首选”，新 run 会去 fork；已有的手动 fork/收集仓 URL 会被忽略。② provider 的 `parse_repository` 只接受 HTTP(S)/SSH/scp-like remote；若 `repo_url` 是 `git://` 或本地路径，有 token 时 `parse_repository` 抛 `GitPushProviderError` → 直接 blocked(push)，而不是回退 `HE_GIT_PUSH_URL`。旧部署如果靠 `HE_GIT_PUSH_URL` 指向本地/非标准 remote 且上游是 `git://`，升级后会变成硬失败。

**预判**：顺序符合 Note 的“fork 优先、URL 兜底”，也符合“失败要响亮”的设计；但建议在 `docs/deployment.md` 或 `git-workspace.md` 写明“配置 token 后 `HE_GIT_PUSH_URL` 仅作为无 token 时的兜底”，并考虑对不可解析的 `repo_url` 跳过 provider、回退到 `HE_GIT_PUSH_URL`（或给出更具体的错误文案）。是否回退属于产品取舍。

**结论**：采纳预判（2026-11-21）。`docs/git-workspace*` 已写明“有 token 时 fork 优先、`HE_GIT_PUSH_URL` 只作无 token 兜底、provider API 失败不静默回退”；不可解析 remote 属于 target 校验之外的配置错误，保留响亮失败，不做隐式回退。

### D3 provider API 失败到 `blocked(push)` 的映射

**位置**：`apps/api/app/third_party_api/git/workspace.py:1081-1088`；`apps/api/app/service/evolution/git_failures.py:23-40`；`apps/api/app/service/evolution/prepare.py:467-484`；`apps/api/app/service/evolution/git_candidate.py:686-717`。

**现象**：`GitPushProviderError` 被转换成 `GitOperationError(stage="push", retryable=...)`：无 status（传输失败、轮询超时）可重试；429/500/502/503/504 可重试；401/403 等不可重试。`classify_git_failure` 对任何 stage=push 都返回 `blocked(push)`，所以 provider 失败确实进入 blocked，而不是 failed。candidate 路径在 `blocked_stage == "push"` 且 `error.retryable` 时还会算 `next_retry_at`（`git_candidate.py:699-703`）。

**问题**：provider 的错误文案只有 `push fork preparation failed (HTTP 401)`，不带“token 缺失/过期/scope 不足”的区分；用户要靠 status 自己猜。git 自身的 push 403 走 `_error_from_result`，其 retryable 由 `_TRANSIENT_MARKERS` 决定，与 provider API 403 的“不可重试”不是同一套判断。

**预判**：满足 issue 的“明确 blocked、可重试”和“失败文案可定位”；401/403 的文案细分可以后续做，不阻塞。两条失败判定路径可以统一，但会扩大改动面。

**结论**：已修（2026-11-21）。`_provider_failure_detail` 按 401/403/404/429/5xx/传输失败给出可定位且不含凭据的原因；`test_per_run_push_target.py` 用参数化用例覆盖 401/403/404/429/503/None 的 retryable 矩阵。

### D4 `push_repo_url` 的非空默认与“无回填”

**位置**：`apps/api/app/db/models/evolution.py:64-67,353-357,550-556`；`apps/api/alembic/versions/0024_push_repo_url.py:22-52`；`apps/api/app/db/crud/evolution.py:315-340`；`apps/api/app/service/evolution/runs.py:489-491`；`apps/api/app/service/evolution/eval_poller.py:89-92`。

**现象**：列是 `nullable=False, server_default=""`，迁移不做数据回填；`mark_prepared` 只在非 None 时写；API 与 eval 在空串时回退 `repo_url`。因此历史行、`HE_GIT_PUSH=false` 的 run、demo 模式 run 的 `push_repo_url` 都保持空串。

**问题**：回退让旧数据可读，但 UI 的“推送目标”会把 `repo_url` 显示成目标；对 `HE_GIT_PUSH=false` 的 run 实际没有任何 push，这个标签在语义上是“评测取数目标”而非“推送目标”。另外，空串与“未知”不可区分：无法从 DB 判断这一行是“旧版本没写”还是“prepare 时 token 缺失而回退 origin”。

**预判**：迁移安全（加列、空默认、无 backfill）；语义上的小瑕疵可以在 UI 加 tooltip 或在 label 上区分，不阻塞。若未来需要诊断，可再考虑 nullable 或单独的 source 字段。

**结论**：接受预判（2026-11-21），无实害；空串语义与 UI tooltip 留作可选优化，不阻塞。

### D5 target 页面 PAT 状态未实现：显式范围决策

**位置**：`apps/api/app/service/evolution/targets.py:45-55`（`EvolutionTargetWrite` 无 push/PAT 字段）；`apps/web/src/pages/evolution/RunDetail.vue:856-869`；`.agents/notes/implemented/architecture/2026-11-21-git-push-provider.md` 的 Consequences；issue #457“实现内容 / 4. target / run 数据与迁移”要求“target UI 显示 PAT 状态（已配置/缺失/过期）”。

**现象**：target 契约、表单、列表都没有 PAT 状态；target 表单只在文案里提示“不要写 token”（`TargetFormDialog.vue:299`）。设计文档也保持 target 不变：`05-api-design.md:984,1057` 明确 `pushRepoUrl` 是 run 的派生字段、target 不接受 push/eval URL；`06-database-design.md:585,616` 只在 `evolution_runs` 记 `push_repo_url`。run 详情只显示派生后的推送目标。原型工作区块也没有 PAT 行。Agent Note 明确记录“PAT 状态不在 target 页面暴露”。

**问题**：这是 issue 验收项与实现范围之间的显式差异，不是静默遗漏；但缺一个“用户如何知道 token 缺失/过期”的入口——目前只能等 push 失败进 blocked，看 `push fork preparation failed (HTTP 401)`。把 PAT 状态塞进 target 页面又和“凭据属于部署级配置”的模型冲突。

**预判**：接受为显式 scope 决策；更好的去处是部署级诊断（例如 health/部署检查显示 provider 与 token 是否配置、最近一次 fork 失败原因），而不是 target 行。建议在 Note 或 follow-up issue 里登记，不要在本 PR 补 UI。

**结论**：接受为显式范围决策（2026-11-21）。target 契约保持部署级凭据模型；Agent Note 的 Consequences 已记录“PAT 状态不在 target 页面暴露”。部署级诊断作为后续入口，不在本 PR 补 UI。

### D6 Deploy 的 Secrets 注入、覆盖与 unset

**位置**：`.github/workflows/deploy.yml:259-325`；`deploy/inject-config.py:60-108`；`deploy/harness-api.service:15`。

**现象**：每次 Deploy 都用 Secrets 里的值覆盖 `.env` 对应键；`HE_GIT_PUSH_TOKEN` 为空时追加 `--unset HE_GIT_PUSH_TOKEN`；`--unset` 是 `action="append"`，与 `HE_GIT_PROXY` 的 unset 可同时出现；值以 base64 经 stdin 传输，token 不进入 SSH 命令行；注入后 `chmod 600` + `stat` 复核；最后只打印“token 已配置/未配置”。

**问题**：`GIT_ASKPASS` 无条件写入，即使没有 token；这本身无害，但意味着“删除 token”并不会删除 askpass 指向。若用户把 token secret 删掉又忘了重新部署，服务器旧 token 会在下一次部署时被 unset——这是期望行为，但依赖“部署被执行”。已有 `apps/api/tests/deploy/test_inject_config.py` 覆盖单个 `--unset`、原子重写与备份；但“`HE_GIT_PROXY` + `HE_GIT_PUSH_TOKEN` 两个 unset 同时出现”、Deploy workflow 的 `install`/`stat` 失败路径仍只有代码审阅（workflow 本身没有 shell 测试）。

**预判**：注入链路正确，重复 `--unset` 已按 `argparse` 的 `action="append"` 代码确认；建议在部署 playbook 加一条人工检查（“删 token 后部署，`grep -c HE_GIT_PUSH_TOKEN /opt/harness/shared/.env` 应为 0”）。是否给 deploy 脚本加测试取决于成本，不必阻塞本 PR。

**结论**：接受（2026-11-21）。注入/unset/0600 链路按代码与 `inject-config.py` 语义确认；部署 playbook 的人工检查步骤留作运维侧后续，不阻塞本 PR。

### D8 GIT_ASKPASS 的提示词匹配与本地可用性

**位置**：`deploy/git-askpass.sh:9-20`；`apps/api/app/third_party_api/git/provider.py:141-160,177-192`。

**现象**：脚本按 `Username*`/`username*` 与 `Password*`/`password*` 匹配；用户名默认 `x-access-token`，密码从 `HE_GIT_PUSH_TOKEN` 取；未知提示词只输出固定错误并以 1 退出，不泄露 token（测试覆盖）。provider 同时把 `HE_GIT_PUSH_TOKEN` 放回 git 子进程环境，所以本地 pydantic `.env` 里配了 token 也能被 askpass 读到。

### D9 GitHub 已有 fork 的处理、轮询与 GitLab 自托管 base

**位置**：`apps/api/app/third_party_api/git/provider.py:291-301,330-352,400-419`（GitHub）；`:427-429,445-469,513-527`（GitLab）；`:74-95`（`parse_repository`）。

**现象**：GitHub 先 GET `/repos/{login}/{name}`；存在就直接返回该 URL，不校验它是不是上游的 fork（响应里的 `parent` 字段没用）。不存在才 POST fork，再 6 次×1s 轮询。GitLab 同理按 `{login}/{name}` 查项目。`api_root` 对 GitLab 返回 `web_root + "/api/v4"`，`web_root` 只由 scheme/host/port 组成。

**问题**：① 如果 `{login}/{name}` 恰好是一个与上游无关的同名仓（或旧 fork 指向别的上游），push/eval 会落到错误仓；GitHub 生态里同名 fork 很常见，命中错误仓的概率低但存在。② 6 秒轮询对超大仓的 fork 可能不够；失败可重试，但每次重试会重新 GET；若仍 404 会再次 POST fork，对已存在 fork 的响应未在本 PR 测试中覆盖，但请求会被放大。③ GitLab 部署在子路径（`https://host/gitlab/group/repo.git`）时，`web_root` 丢掉 `/gitlab`，`api_root` 变成 `https://host/api/v4`，URL 与 API 都会错；GitHub Enterprise 的路径前缀同样不覆盖。

**预判**：① 建议在 `_repo_payload` 里校验 `parent.full_name` 或至少记录“existing repo 被复用”的日志；② 轮询参数可配置（构造函数已接受 attempts/interval），6 秒对常规仓够用，失败会 blocked 而非静默；③ 子路径自托管是已知边界，建议在 Note/文档明确“只支持根路径部署”，或后续从 `repo_url` 的 path 前缀推导 base。都不阻塞本 PR。

**结论**：部分接受（2026-11-21）。已有同名 fork 的身份校验、子路径自托管 base、6 秒轮询上限留作 follow-up；本 PR 的值是主路径可用且失败响亮，不为低概率边界扩大改动面。

## §9 文件级代码分析

### 9.1 `apps/api/app/third_party_api/git/provider.py`（A，583 行）

**职责**：把“推送到哪个 URL、用什么身份认证、fork 在谁名下、如何查远端 ref”收进一个 provider 缝；平台差异由子类承担，工厂按部署配置选实现。

**关键依赖**：`httpx.AsyncClient`（运行时网络客户端；测试用 `MockTransport` 注入，生产每次请求临时建 client），`pydantic.SecretStr`（token 的 repr 保护），标准库 `urllib.parse` 与 `re`（解析 remote，不引入第三方 URL 库）。比喻：httpx 是专员手里的电话，SecretStr 是只显示“已配置”的封条。

**变更代码块（新旧对照）**：

```python
# 旧：没有 provider；workspace 构造时固化一个全局 push_url
self._push_url = (push_url or "").strip() or None
self._push_remote = "push" if self._push_url is not None else "origin"

# 新：工厂按配置选子类，父类只定义契约
class GitPushProviderFactory:
    _registry = {"github": GitHubProvider, "gitlab": GitLabProvider}
    @classmethod
    def create(cls, settings, *, client=None):
        provider_id = settings.git_push_provider.strip().lower()
        implementation = cls._registry.get(provider_id)
        if implementation is None:
            raise ValueError("HE_GIT_PUSH_PROVIDER must be one of: ...")
        return implementation(token=settings.git_push_token, client=client)
```

`parse_repository`（`:74-117`）把 HTTPS/SSH/scp-like remote 归一成 `RemoteRepository`，丢弃凭据与 SSH 端口；`auth_environment`（`:177-192`）只回四个环境变量，token 不进 URL；`ensure_fork`（GitHub `:330-352`，GitLab `:445-469`）先查再建、失败带 HTTP status；`_wait_for_fork`（`:291-301`）做有界轮询；`GitPushProviderFactory`（`:531-575`）负责选择与注册。

**实现思路**：父类管“问题形状”（URL/认证/fork/PR），子类管“平台答案”；公共 git 执行以模板方法预留；工厂加 registry 让新增平台只需一个子类 + 一行注册。

**检视发现**：主路径与失败脱敏正确（401 测试断言 token/响应体不出现）。两个真实但非阻塞的点：① `push_ref`/`remote_ref` 生产未使用（D10）；② 每次 `_request` 在没有注入 client 时新建 `AsyncClient`（`:265-268`），`ensure_fork` 一次会走 login/存在性/创建/轮询多次请求，连接不复用，属性能小账。源码树 grep 无 `_authenticated_login` 残留。
