## §1 一页速览

一句话：把第 6 步从「拿数据库里的 patch 字典直接做封闭校验」改成「先还原成统一 bundle，再显式投影成读 DTO」，前端相应按文件渲染。

比喻：原来的读路径像 **海关只认旧版护照**——写侧已经给每本护照加了两页（`files`、`overwrite`），边检（`StepRoundPatch` 的 `extra="forbid"`）看到新增页就整本扣下。现在先把护照换成统一的内页格式（`PatchBundle`），边检只核对它要放行的字段。

交付块：

| 块 | 内容 |
|---|---|
| API | `stored_bundle()` 共享还原；`StepRoundPatch` 改 `{files, note?}`；`_round_item()` 明示投影 |
| Web | `DiffView.vue` 按 `files` 逐文件渲染，单文件视觉不变 |
| 契约 | OpenAPI/TS 重新生成，§3.6 示例与说明同步 |
| 测试 | API 三种合法形状 + 损坏降级 + Web 组件 + E2E 双文件/legacy |
| 文档 | flow issue 三件套、Agent Note、设计文档 |

验证基线：`pnpm test:e2e -- --pattern iteration` 在本地 Chrome 通过；截图见 PR 描述；生产 run 需部署后复核。

## §2 架构导览

### 2.1 还原缝：`round_patch.py`

`stored_bundle(raw)`（`round_patch.py:20`）优先读 `files[]`，每个元素交给 `_stored_patch_file()`（`:59`）校验 `file/lines/overwrite`；没有有效 `files` 时回退到顶层 legacy `file/lines`。`note` 缺失时补 `PLACEHOLDER_PATCH_NOTE`，`intent`/`report` 解析失败则降级为空（`:77`、`:87`）。

这层不依赖 HTTP 或 pydantic 响应模型，写侧（`git_candidate._patch_file/_patch_note/_patch_hash`、发布前恢复）与读侧（`stages._round_patch`）共用它。`_patch_note()` 也改为从 `bundle.note` 取事实，避免第二份 note 解析。这样「存储形状」只有一个解析 home。

### 2.2 读模型：`stages.py`

`StepRoundFilePatch`（`stages.py:245`）是单文件 DTO；`StepRoundPatch`（`:253`）只保留 `files` 与 `note`。`_round_patch()`（`:1039`）先调用 `stored_bundle()`，成功后再逐文件构造 DTO；读模型自身仍是 `extra="forbid"`，但输入不再是原始字典。`_round_item()`（`:1062`）在 `:1088` 调用它。

关键边界：还原失败返回 `patch: null`，其余轮次字段照常返回；不再让一个字段把整步打成 500。

### 2.3 渲染：`DiffView.vue`

`:19` 的 `v-for="file in (patch.files ?? [])"` 为每个文件输出一个 `.fhead` 与一组 `.dline`；`:59` 的 `.file + .file` 只在文件之间加分隔线。`?? []` 是部署漂移兜底：新前端先于新 API 上线或回滚时，旧响应没有 `files` 也不会在渲染期抛错。`lineClass()` 与颜色 token 未变，所以单文件视觉与改动前一致。

### 2.4 契约与测试

OpenAPI 由 FastAPI 模型生成，`packages/contracts/src/index.ts` 额外手工导出 `StepRoundFilePatch` 方便前端引用。回归用例把写侧 `_stored_patch()` 的真实输出作为输入（`test_iteration_round_patch.py:139-146`），而不是手写一个「看起来像」的字典；第 4 条 round 用不可还原的 patch 断言 200 + `patch: null`，请求走前端实际使用的 workspace 作用域路由。

## §3 数据流走查

1. 写侧 `git_candidate.publish()` 生成 `PatchBundle`，`_stored_patch()` 落库为 `files/note/intent/report`，单文件时再合并 legacy 三键。
2. 读侧 `GET /steps/iteration` → `EvolutionStageService._iteration()` → `_round_item()` → `_round_patch(round_.patch)`。
3. `_round_patch()` 调 `stored_bundle(raw)`：`files` 优先，legacy 回退，得到 `PatchBundle(files=...)`。
4. 投影成 `StepRoundPatch(files=[StepRoundFilePatch(...)], note=raw.note)`，由 `StepRound` 返回。
5. 前端 `StepIterations.vue` 展开轮次，`DiffView` 遍历 `files`，每个文件输出路径标题和增删/上下文行。
6. 多文件 bundle 的每个路径都出现；legacy 单文件 bundle 只有一个路径，视觉与旧版一致。

## §6 讨论点

### 6.1 响应契约从 `patch.file` 变为 `patch.files`

- **位置**：`apps/api/app/service/evolution/stages.py:253`
- **现象**：旧字段 `file`/`lines` 被 `files[]` 取代，属于破坏性响应变更。
- **问题**：仓库内只有 `DiffView.vue` 消费该 DTO，但外部脚本或未合入的客户端可能仍读 `patch.file`。
- **预判**：接受。问题本身要求读模型对齐多文件 bundle；继续保留顶层 `file` 会让契约出现两套真相。Agent Note 已记录该代价。
- **结论（2026-11-23）**：接受破坏性变更。仓库内唯一消费方 `DiffView.vue` 已同步；`StepRoundPatch` 的契约与设计文档同步更新。外部脚本需要从 `patch.file` 迁移到 `patch.files[0].file`，这一代价写进 Agent Note。

### 6.2 无法还原的 patch 降级为 `patch: null`

- **位置**：`apps/api/app/service/evolution/round_patch.py:20`、`stages.py:1039`
- **现象**：`stored_bundle()` 对损坏字典返回 `None`，第 6 步只少 patch 预览，不再 500。
- **问题**：确定性坏数据不再把整步打红，可能降低可观测性；需要日志或测试兜底。
- **预判**：接受。500 会让「来源 bad case / 评测 / commit」也一起不可见；局部降级更利于诊断。当前未加告警日志，可作为后续观测增强。
- **结论（2026-11-23）**：保留降级为 `patch: null`，并在 `test_iteration_round_patch.py` 增加第 4 条不可还原 round，断言 `200 + patch:null`。当前不加日志：读取路径每次刷新都会重复触发，先由测试与 UI 空白暴露；若生产出现，再加带 roundId 的告警。

### 6.3 `overwrite` 进入读契约但未渲染

- **位置**：`stages.py:245`、`DiffView.vue:19`
- **现象**：DTO 暴露 `overwrite`，UI 只显示路径与 diff 行。
- **问题**：是否存在「字段存在但无人消费」的契约噪音？
- **预判**：接受。该字段决定文件是追加还是整文件覆盖，属于 patch 语义的一部分；按 issue 推荐方案保留，UI 是否展示模式标签可另议。
- **结论（2026-11-23）**：保留字段，不在本 PR 增加 UI 标签。多文件 bundle 的路径与内容已足够回答「改了什么」；模式标签可在后续视觉优化中讨论。

### 6.4 写侧序列化仍留在 `git_candidate.py`

- **位置**：`git_candidate.py` 的 `_stored_patch()`（未移动）
- **现象**：还原逻辑已共享，序列化 `_stored_patch()` 仍私有在发布服务里。
- **问题**：下一次存储形状升级时，写侧和读侧可能再次分叉吗？
- **预判**：风险低于本次。读侧已不依赖写侧字段的封闭集合；后续若新增字段，`stored_bundle()` 会忽略未读字段。真正要同步的仍是 `files` 的构造规则，测试已用 `_stored_patch()` 输出做端到端固定。
- **结论（2026-11-23）**：暂不移动 `_stored_patch()`。写侧序列化与读侧还原的耦合点已由「同一份还原规则 + 真实 writer 输出测试」固定；把序列化也搬进 `round_patch.py` 会扩大本 PR 的改动面，可在下次存储升级时再做。

### 6.5 E2E fixture 用 diff 标记，而真实落库是文件内容

- **位置**：`tests/e2e/support/m10_06_run_detail_fixture.py:716-727`、`apps/api/app/service/evolution/patch_source.py:503-508`
- **现象**：fixture 的 `overwrite: True` 文件里放的是 `-`/`+` 行；真实 `Patch.lines` 存整文件内容或追加文本，不会自带 unified diff 标记。
- **问题**：E2E 的增删行断言只证明 `DiffView` 的前缀着色，不证明真实落库内容已经变成 unified diff；这是既有产品行为，不是本 PR 引入。
- **预判**：不在本 PR 扩展。issue #522 只要求读取契约与多文件渲染；把「文件内容」变成真正的 unified diff 需要新增 diff 字段或后端计算，属于另一个产品决策。
- **结论（2026-11-23）**：保留 fixture 与断言，但在 Agent Note 与 PR 限制中不宣称「真实 diff」。本 PR 的验收点是路径、文件数与内容可见；着色行为沿用既有 `DiffView`。

## §9 文件级代码分析

### 9.1 `round_patch.py`（A）

职责：把持久化 patch 字典还原成 `PatchBundle`，供写侧恢复与读侧投影共用。

旧实现是 `git_candidate.py` 里的 `_stored_bundle()` 及三个私有 helper，逻辑逐字搬移，只把函数名改为公开的 `stored_bundle()`。没有引入新依赖，没有改变解析顺序（`files` 优先、legacy 回退）。

实现思路：让「存储形状」只有一个读取入口；读模型不再知道 `intent/report` 的存在。

已知弱点：`PatchBundle.__post_init__` 会校验 `intent.summary == note`，如果历史数据两者不一致，整个 bundle 还原失败，patch 预览变成 `null`。这与「读路径尽量不失败」的目标有张力，但当前没有这类数据；若后续出现，可在 `stored_bundle()` 里分开校验文件与审计字段。

### 9.2 `stages.py`（M）

旧：

```python
class StepRoundPatch(IdentityModel):
    file: str
    lines: list[str]
    note: str | None = None
...
patch=StepRoundPatch.model_validate(patch) if isinstance(patch, dict) else None,
```

新：

```python
class StepRoundFilePatch(IdentityModel):
    file: str
    lines: list[str]
    overwrite: bool = False

class StepRoundPatch(IdentityModel):
    files: list[StepRoundFilePatch]
    note: str | None = None
...
patch=_round_patch(round_.patch),
```

变更点：读模型描述当前 bundle；投影函数只读它要暴露的字段。`note` 仍从原始字典读取，缺失保持 `None`，避免把 `stored_bundle()` 的占位 note 带进响应。

### 9.3 `git_candidate.py`（M）

删除约 90 行私有还原代码，改为 `from app.service.evolution.round_patch import stored_bundle`，并在三处调用点替换函数名。发布、推送、评测逻辑未改。测试覆盖：现有 git candidate 套件 + 本 PR 的 writer→reader 用例。

### 9.4 `DiffView.vue`（M）

旧模板只有一个 `.fhead` 和 `patch.lines`；新模板外层多一层 `.file`，每个文件独立标题与行集合。`lineClass()` 不变，空 patch 的兜底从 `patch.lines.length === 0` 改为 `patch.files.length === 0`，并保留单文件内空行的提示。

### 9.5 测试（A/M）

- `test_iteration_round_patch.py`：真实 `_stored_patch()` 输出 → seed → workspace 作用域 HTTP `steps/iteration`，断言 200、三组合法 `files` 与第 4 组 `patch: null`。修复前旧读模型会在 bundle 形状上抛 `extra_forbidden`，用例失败。
- `test_iteration_patch_note.py`：改成直接测 `_round_patch()`，覆盖 minimal-config note、legacy 无 note、writer-only 字段被忽略、DTO 仍拒绝未知客户端字段。
- `RunDetailConformance.test.ts`：双文件 `DiffView` 渲染与行着色。
- E2E：fixture 的已接纳轮次改 2 文件 bundle；新增用例断言两个路径、增删行、legacy round 的单文件标题，并输出截图。
