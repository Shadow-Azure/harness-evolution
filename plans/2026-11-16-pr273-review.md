## §1 一页速览

一句话：把 Session 页从“默认拉 100 条、输入即防抖请求”改成“默认只拉最新 10 条、完整 root ID 显式提交”，并把服务端的 `total` / `pendingSessions` 变成标题区的两个可见信号。

一个比喻：以前的搜索像自动门，人一靠近就开，哪怕你只是路过；现在像取号机，按一下（Enter 或放大镜）才出一张号，清空号码再按一次就回到“最近十位”的队列。`total` 是今天已经办完的号数，`pendingSessions` 是还在后台补材料、暂时叫不到的号，两者不能相加。

## §2 架构导览

### 2.1 URL 仍是唯一筛选源

`Index.vue:63-82` 的 `filters` 与 `routeWithFilters` 没变，只把 `limit` 从 100 改成 10。搜索框的 `searchInput` 是**输入草稿**，不是筛选源；`route.query.q` 才是。提交时 `submitSearch` 把草稿 trim 后写回 URL（`Index.vue:286-299`），路由变化再驱动 `useSessionList`（`useSessions.ts:20-32`）。因此“输入不发请求”不是靠取消监听，而是查询键根本不看 `searchInput`。

### 2.2 提交会重置选择，但只重置选择

`submitSearch` 的 `path: sessionPath(null)` + `routeWithFilters(..., false)` 做了两件事：把 `sessionId` 从路径拿掉、丢掉 `agent`/`evidence` 深链参数。于是未命中时右侧 `overviewItem` 立即变 null，不会继续显示旧会话（`Index.vue:144-146`、`:299`）。命中时既有 watcher `[items, selectedId, isListSuccess]` 会自动 `replace` 到第一条（`Index.vue:470-489`），不需要新逻辑。

### 2.3 恢复时主动失效默认列表缓存

应用的 `staleTime` 是 30s（`api/queryClient.ts:30`）。如果用户先看默认列表、再搜一个不存在的 ID、然后清空恢复，默认列表的 query key 仍在缓存里，直接导航会渲染旧数据而不发请求。`forgetCachedLatest`（`Index.vue:274-284`）只删精确匹配的默认 key（`q=""` + 当前 `status/sort` + `limit=10`），比全局 `invalidateQueries` 窄，也避免误伤当前查询。`restoreLatest` 清空全部筛选时删的是 `all/latest` key（`Index.vue:301-309`）。

### 2.4 计数与角标只消费服务端字段

`listTotal` 优先用 `data.total`，缺失时回落当前页条数（`Index.vue:135-137`），这样旧测试桩不会显示 `undefined`。`pendingSessions` 同理（`:138-140`）。角标是按钮但只切换一句说明（`Index.vue:666-690`）：待同步根永远不进入 `items`，所以“只看已归一化”本来就是列表的默认语义，角标的作用是解释而不是再过滤一次。这个解释与 m8-02 Note 的“pending 只贡献计数”一致。

### 2.5 空态分层

`SessionList.vue:132-166` 按 `searchQuery → filterActive → pendingSessions → 无 case` 四级判断。顺序很重要：搜索未命中时即使用户还带着状态筛选，也要先告诉他“这个 ID 没找到”，而不是“筛选无结果”。`SessionOverview.vue:295-309` 只区分搜索态/非搜索态，搜索态文案与原型一致。

## §3 数据流走查

1. 进入 `/workspaces/ws-default/sessions`：`filters` 得到 `{q:"",status:"all",sort:"latest",limit:10}`，`listSessions` 发出 `?status=all&sort=latest&limit=10`。
2. 用户键入 36 位 ID：`updateSearch` 只写 `searchInput`；`route.query.q` 不变，`useSessionList` 的 queryKey 不变，零请求。
3. Enter：`submitOnEnter` 阻止默认行为并 emit `submit`；`submitSearch` trim、比较、push 到 `/sessions?q=<id>`；`useSessionList` 的 key 变化，发出一次请求。
4. 命中：响应 `items=[hit], total=1`；自动选中 watcher 等一帧后 `replace` 到 `/sessions/<id>?q=<id>`；标题显示 `命中 1 个`。
5. 未命中：响应 `items=[], total=0`；列表显示“未找到匹配…”，右侧 `searchActive=true` 显示“未找到该 Session”；旧选中已在上一步清掉。
6. 清空再 Enter：`forgetCachedLatest` 删默认 key，push 到 `/sessions`；列表重新请求，自动选中第一条；标题回到 `最新 4 / 总数 4`。
7. 空间有待同步根：响应 `items=[], total=0, pendingSessions=1`；列表显示“暂无可展示的 Session”，标题出现“1 个待同步”，点击展开说明。

## §6 讨论点

### 6.1 提交查询丢弃 `agent`/`evidence` 深链（decision / 低）

- **位置**：`apps/web/src/pages/sessions/Index.vue:286-299`。
- **现象**：`submitSearch` 用 `routeWithFilters({q}, false)`，`preserveDeepLink=false`，即使查询的是当前会话的同一个 ID（值未变时会提前 return）也不会保留 Agent/证据参数。
- **问题**：从深链进入后修改查询，再按浏览器后退，深链参数是否还能恢复？
- **预判**：新查询意味着新的结果集，保留旧 Agent 参数会指向不存在或不属于新会话的锚点；后退由 history 恢复旧 URL，参数仍在。
- **结论**：保留。值未变时提前 return，不会误伤当前深链；仅在新查询提交时丢弃。

### 6.2 恢复默认列表时删除缓存（decision / 低）

- **位置**：`Index.vue:274-284`、`:293`、`:305`；`api/queryClient.ts:30`。
- **现象**：恢复动作先 `removeQueries` 精确删除默认列表 key，再导航。
- **问题**：删除缓存是否会让返回/前进看到骨架屏，或误删当前正在观察的查询？
- **预判**：目标 key 是默认列表，只有在搜索态（`q` 非空）才会走到这里，因此默认列表不在观察中；删除后重新请求是有意换取“恢复最新”的时效性。
- **结论**：保留。E2E 断言恢复动作恰好 1 次请求，证明缓存失效生效且没有双请求。

### 6.3 待同步角标点击不改变列表（fact / 低）

- **位置**：`Index.vue:666-690`；设计 08 §5.2.1 “点击只看已归一化”。
- **现象**：点击角标只展开说明，不写 URL、不切换筛选。
- **问题**：是否与设计“点击只看已归一化”不一致？
- **预判**：API 明确 pending 永不进入 `items`，列表本来就是“只看已归一化”；再加一个筛选键不会改变结果，只会制造第二个真相。
- **结论**：保留当前交互，说明文案写清 pending 只计数；设计 08 的措辞可理解为对既有列表语义的说明而非新过滤。

### 6.4 E2E 的跨空间用例只覆盖 pending 根（testing / 低）

- **位置**：`tests/e2e/m8-05-session-latest-ten.test.mjs` “isolates workspaces…”；m8-02 的跨空间 SQL 用例。
- **现象**：UI E2E 建第二个空间并上报一个 pending root，验证 ws-default 查不到；没有在第二个空间归一化一条真实会话再查。
- **问题**：跨空间隔离的 UI 结论是否足够？
- **预判**：归一化轨迹需要 replay/seed 第二空间，成本高；空间投影与精确 `q` 的隔离已由 m8-02 的 API 测试覆盖，UI 只需证明“其他空间的 ID 不会出现在当前列表/右侧”。
- **结论**：接受；E2E 已覆盖 pending 根不泄漏，归一化根的隔离由 API 测试承重。

### 6.5 右侧空态与设计表格文案曾不一致（fact / 低）

- **位置**：`SessionOverview.vue:295-309`；`plans/fullstack-design/08-frontend-implementation.md:449`。
- **现象**：设计表格原写“选择左侧 Session 查看详情”，实现按原型写“未找到该 Session”+ 重新查询提示。
- **问题**：以哪个为准？
- **预判**：原型是视觉与交互基线，且“未找到该 Session”对搜索未命中更准确；设计表格该行是概括。
- **结论**：已修（文档）：08 §5.2.1 的右栏文案同步为“未找到该 Session + 重新查询提示”，并删掉“m8-05 之前仍用防抖”的过时现状描述；空空间上报链接改为“上报入口在空间管理页”，与当前实现一致。

### 6.6 侧栏 H1 保留「Session 浏览器」（decision / 低）

- **位置**：`Index.vue:658`；原型侧栏 `h1` 为“Session”。
- **现象**：实现未把 H1 改成原型的两字标题。
- **问题**：这算不算 UI 未对齐？
- **预判**：该文案被 `App.test.ts`、`shell-pages.test.ts`、`m1-shell` E2E 与顶栏导航共同引用；为一个局部交互 issue 改全局文案会把 diff 扩到多个无关测试。
- **结论**：保留，并在 PR 与 Note 中声明为有意差异；如要统一，另开文案 issue 一次改全站。

### 6.7 既有 E2E 仍断言旧空态文案（fact / 中）

- **位置**：`tests/e2e/m1-shell.test.mjs:325`、`:333`；`tests/e2e/m7-08-workspace-shell.test.mjs:301`。
- **现象**：新空态把“没有任何筛选的 workspace”从「没有匹配当前筛选的 session」改成「该工作空间还没有上报 bad case」，两个既有 E2E 仍等旧文案；CI e2e lane 在第一次推送时因此失败。
- **问题**：是保留旧文案还是更新测试？
- **预判**：设计 08 §5.2.1 明确要区分“空间无 bad case”和“筛选无命中”，新文案是需求；旧断言只是沿用了过渡期文案。
- **结论**：已修：两处断言改为新文案，本地 `m1-shell exposes` 与 `m7-08 workspace-shell switches` 均通过。

## §9 文件级代码分析

### 9.1 `apps/web/src/pages/sessions/Index.vue`

职责：页面状态编排（URL、查询、自动选中、滚动记忆）与三块请求的组合。变更形态：M。

关键依赖：`@tanstack/vue-query` 的 `useQueryClient` 用于精确失效默认列表 key；`queryKeys.sessionList` 是 key 工厂，保证删除的 key 与实际查询完全一致。

旧代码：

```ts
function updateSearch(value: string) {
  searchInput.value = value;
  clearTimeout(searchTimer);
  const revision = ++searchRevision;
  searchTimer = setTimeout(() => {
    if (revision !== searchRevision) return;
    void updateFilter({ q: value.trim() });
  }, 300);
}
```

新代码：

```ts
function updateSearch(value: string) {
  searchInput.value = value;
}

async function submitSearch() {
  const nextQuery = searchInput.value.trim();
  searchInput.value = nextQuery;
  if (nextQuery === (filters.value.q ?? "").trim()) return;
  ...
  await router.push({ path: sessionPath(null), query: routeWithFilters({ q: nextQuery }, false) });
}
```

这在做两件事：把“输入”和“导航”解耦；把“新查询”定义成“路径回到列表 + 清空深链”。值未变时提前返回是“回车只触发一次查询”的最后一道保险。实现思路：URL 单源、提交原子化、恢复显式失效。检视发现：无阻断问题；唯一弱点是 `filters.q` 可能带空格时比较用 trim、URL 保留原值，属于人为构造的边缘输入，不处理。

### 9.2 `SearchBox.vue`

职责：受控输入 + 提交入口。变更形态：M。

旧代码把图标当装饰、用 `<label>` 包住输入；新代码把图标变成 `button type=button`，输入 `@keydown.enter` 调 `submitOnEnter`。`event.isComposing` 判断避免中文输入法选词时误触发；`preventDefault` 防止将来包进 form 时双重提交。视觉上按钮无边框/背景，与原型放大镜一致；`focus-visible` 给出键盘焦点。检视发现：按钮没有 `title`，但 `aria-label` 足够。

### 9.3 `SessionList.vue`

职责：列表、骨架、错误、空态与键盘导航。变更形态：M。

新增 `searchQuery` / `filterActive` / `pendingSessions` 三个纯展示输入与 `reset` 事件。空态用 `<template>` 分支而不是字符串拼接，避免用户输入进入 HTML。恢复按钮复用同一事件，父层决定清哪些筛选。检视发现：`role="status"` 容器内含按钮，屏幕阅读器可能把按钮当状态内容播报；这是既有空态结构的延续，未在本 PR 改动 ARIA 模型。

### 9.4 `SessionOverview.vue`

职责：右栏概览、Agent 树、问题列表。变更形态：M。

只加 `searchActive` prop 与搜索态文案。没有改树/问题请求，符合“未命中不保留旧详情”的边界。检视发现：非搜索态把原“从左侧选择一个 Session 查看概览”改成“未选择 Session / 从左侧选择一个会话查看家族树”，与原型一致；不影响既有测试（仅深链无效页断言不出现该文案）。
