## §2 架构导览

### 2.1 token 是唯一颜色源

`apps/web/src/styles/tokens.css:1-16` 原样定义原型页面、面板、卡片、正文和六类业务色；18-38 行再把旧组件的语义变量映射到这些 raw token。这样页面不需要一次性改完所有语义类名，但视觉值已经只有一处来源。

比喻：raw token 是颜料仓库，语义 token 是施工图上的“墙面色”“错误色”标签；组件只能领标签，不能自己兑颜色。

`pnpm verify:web-style` 实测通过，说明 Vue 组件没有重新写死颜色。

### 2.2 共享壳层

`App.vue:52-83` 保留“顶栏 + 健康门 + Router 内容”的结构，但删除了开发态的 API 连接胶囊。`App.vue:86-113` 将 shell 改为浅灰背景和宽 1280px 的内容区；认证页不显示顶栏。

`TopNav.vue:23-93` 对应原型顶栏结构：24px 渐变标记、`Harness Evolution`、三个导航项、demo 状态与用户菜单。`TopNav.vue:146-174` 采用透明下划线而非胶囊选中态，Evolution 单独使用紫色。

健康查询失败仍由 `App.vue:62-80` 进入可重试 `ErrorState`，没有因为删除状态胶囊而牺牲恢复能力。

### 2.3 认证与共享三态

`pages/login/Index.vue` 与 `ChangePasswordCard.vue` 把认证卡统一成原型白卡；`EmptyState.vue`、`ErrorState.vue` 和 `LoadingSkeleton.vue` 分别形成白色普通态、浅红错误态和白色加载壳。

`pages/sessions`、`pages/errors`、`pages/evolution` 只消费这些共享组件，没有新增领域数据或 runtime mock。

### 2.4 真实浏览器验收

`tests/e2e/m1-shell.test.mjs:158-232` 在真实 Chrome 中读取登录和强制改密卡片的计算后背景色；238 行之后的壳层测试读取页面、顶栏、空态和导航激活线颜色；381 行之后切换到 390px，验证无横向溢出和 demo/用户入口。

这比只断言 CSS 文本更可靠，因为它同时经过 Vue 渲染、Element Plus、浏览器布局和 Vite 构建。

## §3 数据流走查

### 场景 A：未登录访问 `/sessions`

1. 浏览器加载 `App.vue`，路由具有认证布局标记时跳过 TopNav。
2. 认证路由守卫把请求送到 `/login?redirect=/sessions`。
3. 登录页在 `#f4f5f7` 上渲染白色 `.auth-card`。
4. 输入提交后仍走既有 auth store 和 HTTP 单飞刷新逻辑。
5. 临时密码账号被守卫送到强制改密卡，视觉继续保持无 TopNav 的白卡。

### 场景 B：登录后的共享壳

1. App 查询 health，成功后才放行 RouterView。
2. TopNav 使用 health 的 `phase` 决定是否显示“演示数据”。
3. Sessions/Errors/Evolution 分别使用共享真实空态。
4. 窄屏隐藏品牌副标题，但链接保留 `aria-label="Harness Evolution"`。
5. 390px 下导航、demo 和用户入口仍在视口内。

### 场景 C：health 503

1. health 请求返回统一错误 envelope。
2. App 隐藏业务路由内容，但保留 TopNav。
3. `ErrorState` 以浅红面和红色左边框显示错误。
4. 点击重试，503→200 后恢复 Sessions。

## §6 讨论点

### D1 认证页缺少 390px 真实浏览器验收

**位置**：`tests/e2e/m1-shell.test.mjs:158-232`

**现象**：登录和强制改密只在 1408×900 下读取 computed style；390×844 只覆盖登录后的共享壳，没有覆盖认证卡片。

**问题**：issue 验收明确要求登录/改密、三入口和空态在 1408px 与 390px 均无横向溢出。当前 CSS 看起来能够收缩，但这一承诺尚未被真实浏览器证明。

**预判**：应补 390px 认证路径的 `scrollWidth === clientWidth` 与卡片宽度断言。它属于测试完整性，不是已确认的产品缺陷。

**结论**：已修复（2026-10-25）。真实 Chrome 在 390×844 下分别验证登录卡与强制改密卡的左右边界均在视口内，且 `scrollWidth === clientWidth`。

### D2 before/after 截图证据尚未随 PR 提供

**位置**：`.agents/flow/issues/m2-ui-prototype-alignment.md:38,59-60,87`；当前 `reports/` 下无本 issue 报告。

**现象**：issue 要求保存 before/after 截图并与原型关键区域对照，但 PR 目前只有 computed-style E2E 和描述，没有可复核截图。

**问题**：计算颜色能证明 token，不足以证明整体密度、卡片比例、留白与原型一致；维护者仍无法在当前 PR 中直接做视觉验收。

**预判**：这不是生产 UI 缺陷，而是验收证据缺口。下一步 Computer Use smoke 应产出暗色 before、亮色 after、原型对照与 390px 截图。

**结论**：待 smoke 阶段补齐。

### D3 1408px 壳层测试仍依赖滚动条不可见的假设

**位置**：`tests/e2e/m1-shell.test.mjs:292-293`

**现象**：该测试要求 `clientWidth` 和 `scrollWidth` 精确等于 1408；认证测试已因纵向滚动条占用 15px 而改成关系断言，但壳层测试仍保留精确视口断言。

**问题**：页面内容一旦高于视口，`clientWidth` 会变成 1393，即使没有横向溢出也会假红。这类失败会把产品正确行为误判为响应式回归。

**预判**：应统一为 `clientWidth > 0`、`clientWidth <= 1408`、`scrollWidth === clientWidth`；390px 的严格视口断言可保留。

**结论**：已修复（2026-10-25）。1408px 壳层断言改为 `clientWidth > 0`、`clientWidth <= 1408`、`scrollWidth === clientWidth`，不再把纵向滚动条占用宽度误判为横向溢出。
