## §2 架构导览

### 2.1 HTTP 只做协议翻译

`api/evolution_targets.py` 的五条路由只做参数抽取、响应码和 openapi 声明，业务对象由应用状态里的 service 提供。

```text
POST /api/evolution/targets
  → EvolutionTargetWrite
  → EvolutionTargetService.create
  → GitRemote.validate
  → EvolutionTargetRepository.insert
  → EvolutionTarget
```

admin 判断没有散落到每个路由，而是集中在认证中间件：

- target `GET` 不在 admin 清单中，成员可读；
- `POST/PUT/DELETE` 命中 `/api/evolution/targets` 规则，成员得到 `403 FORBIDDEN`；
- 既有 `GET /api/users` 仍要求 admin；
- `GET /api/acquisition/status` 仍可由成员读取。

证据：`apps/api/app/middleware/auth.py:19`、`:64`；回归 `test_auth_scope.py:129`、`:160`。

### 2.2 service 是业务规则的唯一入口

`EvolutionTargetService` 负责四类规则：

1. 文本规范化；
2. `sub_dir` 必须是仓库内 POSIX 相对路径；
3. HTTPS、SSH、SCP 远端不得携带密码、query、fragment；
4. 保存前用注入的 `GitRemote` 验证 ref，版本列表用同一 adapter 读取 tag。

证据：`service/evolution/targets.py:102-175`、`:204-292`。

例如输入 `https://user:password@example.com/repo.git` 时，service 在接触 git 和数据库之前就以统一的 `REPO_INVALID` 拒绝；错误里不会回显密码。输入 `skills/../secret` 同理。

### 2.3 git 是独立、可替换的出站边界

`GitRemote` 是窄协议，生产实现 `SubprocessGitRemote` 只在 `third_party_api/git` 中调用进程。它使用 argv 数组而不是 shell，避免把 URL/ref 拼进可执行字符串。

进程约束：

- `stdin=DEVNULL`，不能等待用户输入；
- `GIT_TERMINAL_PROMPT=0`、`GCM_INTERACTIVE=Never`；
- POSIX 使用独立 session；
- 超时后杀整个进程组并 `await wait()` 回收；
- stdout/stderr 不进入用户错误。

证据：`remote.py:53-118`；测试 `test_targets_api.py:609`、`:656`、`:674`。

### 2.4 repository 是数据库不变量层

`EvolutionTargetRepository` 保持五类数据库职责：

- target 列表与 enabled-only 列表；
- 唯一对象对的 insert/update conflict；
- 按 id 查询/更新/删除；
- active run 检查；
- 一条 SQL 聚合 `agents.model`。

模型聚合只读归一化表，不碰 JSONL：

```sql
SELECT model, COUNT(DISTINCT root_session_id), COUNT(id)
FROM agents
WHERE model IS NOT NULL AND trim(model) <> ''
GROUP BY model
```

证据：`crud/evolution_targets.py:244-274`。

### 2.5 删除与历史 run 的生命周期

设计只禁止删除“有进行中 run”的 target；历史 run 必须仍可取回自己的 snapshot。

migration `0007` 因此把 `evolution_runs.target_config_id` 改为 nullable，并将 FK 改为 `ON DELETE SET NULL`。删除 target 后：

- run 的 `repo_url`、`sub_dir`、`target_name`、`target_version` 等快照仍在；
- 只丢失“当前配置行”的软引用；
- active run 仍在 repository 的行锁事务中被拒绝。

证据：migration `0007:18-36`、`models/evolution.py:40-45`、repository `:195-227`。

## §3 数据流走查

### 场景 A：admin 新建 target

1. `POST /api/evolution/targets` 进入路由 `evolution_targets.py:41-58`。
2. middleware 根据方法 `POST` 和路径前缀要求 admin。
3. Pydantic 先拒绝缺失/超长字段。
4. service 规范化名字和路径，校验 remote 语法。
5. `GitRemote.validate(repo_url, default_ref)` 执行 `git ls-remote --exit-code -- <repo> <ref>`。
6. repository 插入并返回生成的 ULID。
7. 路由返回 `201` 和 camelCase DTO。

失败映射：

- 远端/ref 不可用 → `422 REPO_INVALID`；
- 对象对重复 → `409 TARGET_EXISTS`；
- 非 admin → middleware `403 FORBIDDEN`。

### 场景 B：成员读取配置与版本

1. `GET /api/evolution/targets` 返回启用和停用配置，供配置页重新启用。
2. `GET /api/evolution/targets/{id}/versions` 先查数据库，再读远端 tags。
3. 返回 `versions` 排序去重，`defaultRef` 来自保存配置。

成员能读，不能写。disabled target 仍出现在配置列表，但不会进入 catalog。

### 场景 C：向导读取 catalog

1. `GET /api/catalogs/targets` 只查询 `enabled=true`。
2. 每个 target 的 tag 读取通过共享 `Semaphore(4)` 限流。
3. `asyncio.gather` 保持输入顺序，分组为 `skill` / `agent`。
4. 模型列表直接读 `agents` 聚合，主/子 agent 都计入。

证据：`service/catalogs.py:63-99`；测试 `test_catalogs_api.py:178`、`:229`、`:264`。

### 场景 D：删除 target

1. repository 先 `SELECT ... FOR UPDATE` 锁 target 行。
2. 同一事务检查是否存在 `preparing/running/blocked` run。
3. active run 存在 → `TARGET_IN_USE`；不存在 → 删除。
4. 历史 completed/failed/interrupted run 的 `target_config_id` 被 FK 置空，snapshot 保留。

这解决两个问题：历史 run 不会让删除永远 500；检查与删除不是两个可插入新 run 的时间窗。

## §6 讨论点

### D1 target 配置列表是否包含 disabled

**位置：** `service/evolution/targets.py:199-202`、`crud/evolution_targets.py:80-92`。

**现象：** `/api/evolution/targets` 返回全部配置，只有 `/api/catalogs/targets` 过滤 enabled。

**问题：** 如果误把配置页当作向导数据源，会出现已停用对象仍可选。

**预判：** 配置页需要看到并重新启用停用项，向导需要 enabled-only；两个职责不能合并成一个接口。

**结论：** 按 05 §4.11/§4.13 接受当前分工；未来前端必须从 catalog 取向导候选。

### D2 保存与版本读取为什么同步访问 git

**位置：** `service/evolution/targets.py:218`、`:278-280`。

**现象：** 请求会等待一次 `git ls-remote`，最长受 adapter timeout 限制。

**问题：** 慢远端会增加 API 延迟，且 M5-02 不建立 clone/cache。

**预判：** 若把验证延后到 run 创建，用户会保存一个实际不可用的配置；同步校验虽慢，但反馈真实。

**结论：** 按 07 §5.2 接受同步校验；后续若需要缓存，应替换 `GitRemote` adapter，不改 service/API。

### D3 删除 target 时历史 run 为什么允许 FK 置空

**位置：** migration `0007:18-36`。

**现象：** `target_config_id` 从 NOT NULL 改为 nullable，删除 target 不阻止 completed/failed/interrupted run。

**问题：** 有人可能把 `target_config_id` 当作历史事实唯一来源。

**预判：** run 在创建时已快照 `repo_url/sub_dir/target_*`；配置行只是可删除的当前登记，历史事实在 run 快照中。

**结论：** 按 05 §4.11 的“只有进行中 run 阻止删除”接受当前生命周期。migration downgrade 会删除失去 FK 的 run，属于不可逆降级成本；生产回退前必须显式评估。

### D4 为什么 catalog tag 并发设为 4

**位置：** `service/catalogs.py:49-61`、`:88-99`。

**现象：** `asyncio.gather` 仍并行，但 `Semaphore(4)` 限制真正启动的远端读取。

**问题：** 上限过低会拉长 100 个 target 的 catalog 构建；过高会制造大量 SSH/git 进程。

**预判：** 当前单组织规模通常为十几到低百配置，4 是保守且可控的起点。

**结论：** 接受该默认值；若真实 catalog 延迟成为问题，可把并发度配置化，而不是移除保护。

### D5 git adapter 的进程隔离是否足够

**位置：** `remote.py:87-118`。

**现象：** POSIX 独立 session + `killpg`，Windows 只 kill 直接子进程。

**问题：** 未来若加 Windows lane，测试和进程树语义不同。

**预判：** 当前生产与 CI 都是 macOS/Linux；Windows 不是本 issue 的运行时目标。

**结论：** 当前实现与验证边界接受；新增 Windows 支持时必须补 job object/process tree 行为。

## §9 文件级代码分析

### 9.1 `alembic/versions/0007_evolution_target_history.py`（A）

**职责：** 让 target 配置删除后，历史 run 的软引用自动置空。

旧 schema 中 `target_config_id` 非空，target 一旦被历史 run 引用就无法删除。新 migration 使用 batch alter 重建 FK：

```text
today: freeze target row forever
after: keep run snapshot, release only current-config pointer
```

**关键判断：** run 创建期已保存 target 字段快照，因此引用置空不破坏历史可读性。

**检视发现：** nullable/FK/SQLite/MySQL 双库反射有测试；downgrade 删除 null 引用 run 是明确的回退风险，不应在未备份数据上执行。

### 9.2 `db/models/evolution.py`（M）

**职责：** 与 migration 保持模型一致。

变更点：

- `target_config_id` 改 `str | None`；
- converter 从 required text 改为 optional text。

这避免数据库已置空时，ORM record 转换把合法历史 run 判成坏数据。

**检视发现：** 无新增差异。

### 9.3 `middleware/auth.py`（M）

**职责：** 认证后按 HTTP 方法和路径给 admin 边界。

旧实现是“路径集合”，同一路径所有方法统一 admin；新实现把方法和 prefix 绑定：

| 路径 | 方法 | 要求 |
|---|---|---|
| `/api/users` | GET/POST | admin |
| `/api/acquisition/sync` | POST | admin |
| `/api/acquisition/pull` | POST | admin |
| `/api/evolution/targets` | POST/PUT/DELETE | admin |
| `/api/evolution/targets` | GET | 登录即可 |

prefix 后要求 `/` 或完全相同，避免 `/api/users-other` 误伤。

**检视发现：** 既有路径与 target 混合读写的回归齐全。

### 9.4 `db/crud/evolution_targets.py`（A）

**职责：** 唯一的 target 数据库读写层。

关键实现：

- `list` 稳定排序，`enabled_only` 只在 catalog 使用；
- `insert/update` 只把可识别的唯一约束异常映射成 conflict；
- `delete` 在行锁事务内检查 active run 再删除；
- `list_models` 用一条 group-by 查询。

```text
wrong order: check active run → commit → DELETE
correct:   lock target → check active run → DELETE → one commit
```

**检视发现：** `has_active_runs` 仍保留给测试/诊断，但生产删除不依赖先查后删，避免 TOCTOU。

### 9.5 `service/evolution/targets.py`（A）

**职责：** 把 HTTP 输入变成可持久化、可验证的 target。

校验顺序：

1. trim + 长度/控制字符；
2. 名字与 ref 格式；
3. POSIX 路径越界；
4. remote scheme/userinfo/query/fragment；
5. 远端 ref 实际存在。

错误统一收敛到 `AppError`，并映射 `404/409/422`。

**检视发现：** 远端失败和本地语法失败共享安全信息，不泄漏 stderr。同步远端延迟是已知 tradeoff。

### 9.6 `third_party_api/git/remote.py`（A）

**职责：** 所有出站 git 调用的唯一进程边界。

```text
argv array → isolated child → stdout tags
                  ↘ timeout → kill process group → wait
```

不使用 shell，不允许 terminal prompt，远端错误不进入响应。

**检视发现：** `_run_process` 在取消时 kill+wait；Windows 仍只 kill 直接进程，列为平台未来项。

### 9.7 `api/evolution_targets.py`（A）

**职责：** 暴露五条 target API。

状态码：

| 方法 | 成功 |
|---|---|
| GET collection | 200 |
| POST | 201 |
| PUT item | 200 |
| DELETE item | 204 |
| GET versions | 200 |

OpenAPI 显式声明 401/403/404/409/422，避免生成器回落到 `HTTPValidationError`。

**检视发现：** `targetId` 1–36 字符，与 ULID/legacy IDs 一致。

### 9.8 `service/catalogs.py` + `api/catalogs.py`（A）

**职责：** 为向导提供两个只读目录。

target catalog：

- repository 先过滤 enabled；
- 每个 target 的 tags 由同一 `GitRemote` 读取；
- semaphore 限制最多 4 个远端并发；
- zip 保持原配置顺序。

model catalog：

- 不解析 payload；
- distinct session、agent 行计数；
- 空模型排除；
- 返回顺序稳定。

**检视发现：** 单个 enabled target 远端失败会让 catalog 整体 422，这是“目录不提供不可验证版本”的一致性选择；不是静默丢 target。

### 9.9 `main.py`（M）

**职责：** 构造 app 时只创建一份 GitRemote，并注入 target service/catalog。

```text
create_app(git_remote=...)
  → resolved_git_remote
    ├── EvolutionTargetService
    └── CatalogService
```

测试可在不访问网络的情况下覆盖所有业务路径；生产由 `SubprocessGitRemote` 承担。

**检视发现：** 装配顺序不依赖 lifespan，API 路由不会临时创建进程。

### 9.10 `errors.py`（M）

**职责：** 增加四个闭集错误码：

- `REPO_INVALID`
- `TARGET_EXISTS`
- `TARGET_NOT_FOUND`
- `TARGET_IN_USE`

这使前端和后端共享稳定 code，不需要解析英文 message。

### 9.11 测试

定向测试按职责拆成三组：

- `test_auth_scope.py`：认证 + 真实 repository；
- `test_targets_api.py`：HTTP + 校验 + git adapter；
- `test_catalogs_api.py`：catalog + 并发 + agents 聚合。

数据库测试增加：

OpenAPI 测试增加五个 operation、Bearer、请求/响应 `$ref` 和错误状态。

**检视发现：** 测试不是 mock-only；HTTP、SQLite、迁移和 ASGI 都真实执行。git 远端本身通过可注入 adapter 与 fake process 做确定性安全测试。
