## §1 一页速览

一句话：把“空间”从迁移播种的只读行变成可管理对象——全局管理员建空间、空间管理员管额度和成员、空间管理员签发一次性上报凭据。

比喻：空间像一栋公寓，`workspace_members` 是住户名册。全局管理员拿总钥匙，能换楼名、加管理员；空间管理员只有本层钥匙，能调额度、加住户、发门禁卡，但不能把别人的“管理员”胸牌摘掉，也不能让这层楼最后一个管理员离开。凭据像一次性门禁卡：发卡时给你一张，系统只留卡号哈希，丢了/换卡后旧卡立即失效。

| 交付块 | 内容 | 关键位置 |
|---|---|---|
| 空间 CRUD | 列表/创建/部分更新；重名 409、额度低于 used 422 | `apps/api/app/service/workspaces/service.py:144`、`:168`、`:208` |
| 成员规则 | 空间管理员只能授 member/viewer；space_admin 行与最后一个管理员被锁 | `apps/api/app/service/workspaces/service.py:280`、`:308`、`:337` |
| 候选搜索 | 服务端搜索非成员、排除全局目录、limit≤20 | `apps/api/app/service/workspaces/service.py:257`、`apps/api/app/db/crud/workspaces.py:535` |
| 凭据 | 明文只返回一次；SHA-256 入库；最多 3 条有效；撤销后可认证性立即消失 | `apps/api/app/service/workspaces/service.py:364`、`:399`、`:415` |
| 管理员边界 | 只有 `POST /api/workspaces` 走精确全局管理员规则 | `apps/api/app/middleware/auth.py:20` |
| 契约 | 管理类型全部改为 OpenAPI 生成别名 | `packages/contracts/src/workspaces.ts` |

验证基线（本机实跑）：`pnpm test:api` 全绿（覆盖率 90%）；`pnpm test:db` 20 passed；`pnpm lint:api`、`pnpm typecheck:api`、`pnpm typecheck`、`pnpm contract:check`、`pnpm verify:flow`、`pnpm verify:flow --diff origin/main`、`pnpm lint:docs`、`pnpm verify:docs`、`pnpm test:gates` 全绿。真实服务冒烟在 CI 后补充。

## §2 架构导览

### 2.1 认证之后才谈空间权限

中间件仍只做 Bearer 验签与强制改密（`apps/api/app/middleware/auth.py:42` 起）。本 PR 唯一改的中间件行为是新增 `_ADMIN_EXACT_ROUTES`（`:20`），并用 `_requires_admin` 先做精确匹配（`:29`）——因为 `POST /api/workspaces` 是全局管理员专属，而 `POST /api/workspaces/{wid}/members`、`/credentials` 必须对空间管理员开放；若沿用前缀规则，同前缀子路由会被一并锁死。

空间内权限继续复用 m7-03 的 `require_workspace_role`（`apps/api/app/api/deps.py:15`）：不可见空间统一 404，角色不足 403。管理端点只声明最低角色，具体字段级规则在 service。

### 2.2 路由只做四件事

`apps/api/app/api/workspaces.py` 的 12 个处理函数保持同一形状：声明 `Security(BEARER_AUTH)`、声明 `require_workspace_role`、从 `request.state.principal` 取用户、调用 service 并把结果套进列表响应。路径参数 `wid/userId/cid` 都有长度上限（`:24`–`:27`），非法值在进入业务前 422。

`GET /api/workspaces` 是唯一不挂 workspace 依赖的读端点（`:62`）：任意登录用户按 `users.role=admin` 决定看全部还是只看成员行。

### 2.3 service 是规则的唯一家

`WorkspaceService`（`apps/api/app/service/workspaces/service.py:72`）把管理规则集中在一处：

- 空间创建（`:168`）：额度非负、至少一个初始管理员、初始管理员必须是已存在用户；重名由仓储抛 `WorkspaceNameConflict` 转 `409 WORKSPACE_EXISTS`。
- 空间更新（`:208`）：先读实时 `used`；空间管理员带 `name/mark` 直接 403；额度小于 used 或负数 → `422 QUOTA_INVALID`，details 带 `{quota, used}`。
- 成员（`:280`–`:355`）：先查目标用户/成员行；空间管理员授 `space_admin` → 403；改/删 `space_admin` 行 → 409 `ROLE_LOCKED`；最后一个管理员不可降级或移除。全局管理员可任命/撤销，但仍不能留下零管理员的空间。
- 凭据（`:364`–`:423`）：有效凭据上限 3；明文 `whk_` + 32 字节随机串只出现在返回对象里；库里只落 SHA-256 与前 12 字符；撤销是幂等置位；`verify_credential` 按哈希查未撤销行。
- DTO 组装（`:435` 起）：`Workspace`/`WorkspaceMember`/`WorkspaceCredential` 的 camelCase 由 Pydantic alias 统一，路由不再手拼 JSON。

### 2.4 仓储只负责“怎么存”

`WorkspaceRepository`（`apps/api/app/db/crud/workspaces.py:191`）在 m7-03 的 4 个读方法上追加写方法与分组读：

- 创建空间 + 初始管理员在同一事务（`:362`）；唯一冲突只翻译成 `WorkspaceNameConflict`。
- 成员查询 join `users` 取用户名/显示名（`:426`、`:451`），列表按 `space_admin > member > viewer`、再按 `joined_at` 排序（`:426`）。
- 候选搜索用一条 SQL 排除成员子查询并 `lower(username/display_name) LIKE`（`:535`），`autoescape=True` 防止用户输入 `%/_` 变通配符。
- 凭据只回 secret-free record（`:111`、`:704`），`find_active_credential_by_hash` 同时过滤 `revoked_at IS NULL`（`:775`）。

### 2.5 契约从 OpenAPI 出发

管理 DTO 在 `apps/api/app/service/workspaces/schemas.py:39` 起定义，`contract:generate` 产出 `openapi.json` 与 `api.d.ts`；`packages/contracts/src/workspaces.ts` 现在全部是 `components["schemas"][…]` 别名，不再手写字段。这样前端在 m7-09 拿到的请求/响应类型与后端同源。

## §3 数据流走查

### 剧本 A：全局管理员创建一个空间

1. `POST /api/workspaces` 带 Bearer 与 `{name, mark, quota, spaceAdminIds}`。
2. 中间件验签；`_requires_admin` 命中精确规则，非 admin 直接 403（`apps/api/app/middleware/auth.py:29`）。
3. 路由把请求体交给 service（`apps/api/app/api/workspaces.py:80`）。
4. service 校验额度与初始管理员存在性（`service.py:168`），仓储在同一事务写 `workspaces` 与 `workspace_members`（`crud/workspaces.py:362`）。
5. 重名时 DB 唯一约束触发，仓储翻译为 `WorkspaceNameConflict`，service 返回 409 `WORKSPACE_EXISTS`。
6. 响应 `201 Workspace`，`used=0`、`memberCount=len(spaceAdminIds)`、`spaceAdmins` 带显示名。

### 剧本 B：空间管理员改额度、加成员

1. `PUT /api/workspaces/{wid}` 带 `{quota}` → 依赖确认调用者是 `space_admin` 或全局管理员（`deps.py:15`）。
2. service 读实时 `used`（`service.py:208`）；小于 used 返回 422 并带两个数。
3. `POST /api/workspaces/{wid}/members` 带 `{userId, role}`；空间管理员请求 `space_admin` 在 service 被 403（`service.py:280`）。
4. 仓储插入成员；重复触发 PK 冲突 → 409 `MEMBER_EXISTS`（`crud/workspaces.py:572`）。
5. 成员写入立即生效，因为角色不进 token。

### 剧本 C：轮换上报凭据

1. `POST /api/workspaces/{wid}/credentials`；service 先数有效凭据，≥3 返回 409 `CREDENTIAL_LIMIT`（`service.py:364`）。
2. 生成明文 → 计算 SHA-256 → 仓储只写哈希与前 12 字符（`crud/workspaces.py:704`）。
3. 响应把明文放进 `credential` 字段；此后再无任何接口回显它。
4. 调用方切换完成后 `DELETE …/credentials/{cid}` 置 `revoked_at`；`verify_credential` 按哈希查未撤销行，旧卡立即 401 `CREDENTIAL_INVALID`（`service.py:415`）。

## §6 讨论点

### 6.1 最后管理员与凭据上限的并发窗口

- **位置**：`apps/api/app/service/workspaces/service.py:318`、`:364`
- **现象**：“读当前管理员数/有效凭据数 → 再写”是两个事务；并发下两个请求可能同时通过检查，把空间变成零管理员或多出第 4 条有效凭据。
- **问题**：数据库没有对应 CHECK/唯一约束兜底；当前只靠单进程串行与低并发窗口。
- **预判**：管理操作是低频写路径，本 PR 用测试锁住顺序语义；强一致需要在事务内 `SELECT … FOR UPDATE` 锁空间行，或增加“每空间至少一个 space_admin”的触发器。建议作为后续加固项，不在本 PR 扩范围。
- **结论**：已知弱点，记录在 owning Note；待维护者决定是否单开 issue。

### 6.2 `MEMBER_NOT_FOUND` 超出设计错误表

- **位置**：`apps/api/app/errors.py:76`、`plans/fullstack-design/05-api-design.md:1308`
- **现象**：设计 §8 原本没有成员目标不存在的 404 码；PUT/DELETE 一个非成员需要一个稳定错误。
- **问题**：若复用 `WORKSPACE_NOT_FOUND` 会误导客户端把“成员不存在”当成空间不可见。
- **预判**：这是实现补全，不是偏离设计意图；已把 `MEMBER_NOT_FOUND` 补进 05 §8 错误表。
- **结论**：已修复（2026-11-15）。

### 6.3 空 `spaceAdminIds` 的 OpenAPI 约束

- **位置**：`apps/api/app/service/workspaces/schemas.py:65`
- **现象**：请求体用服务端校验返回 `ROLE_INVALID`，因此 schema 没有 `minItems: 1`；OpenAPI 读者看不到“至少一个”的结构约束。
- **问题**：错误码与结构约束二选一：Pydantic 的 `min_length=1` 会先返回 `VALIDATION_INVALID`，与设计“初始管理员列表含不存在用户 → ROLE_INVALID”不一致。
- **预判**：优先稳定错误码；服务端校验已覆盖空数组与不存在用户。若未来要同时表达 `minItems`，需要在请求解析层把该字段的校验错误映射成 `ROLE_INVALID`。
- **结论**：接受当前取舍；待维护者决定是否补解析层映射。

### 6.4 本 issue 没有 UI 可对照

- **位置**：本 PR 文件树
- **现象**：m7-05 只交付 API；空间管理四 Tab 属于 m7-09（`.agents/flow/issues/m7-09-workspace-admin-ui.md`）。
- **问题**：原任务要求将冒烟截图与 `plans/ui-prototype-v2/harness-evolution.html` 对照；本 PR 没有界面改动，无法产出 Before/After UI 截图。
- **预判**：用 API 级冒烟证据替代；UI 原型对照留到 m7-09。PR 描述中已声明该限制。
- **结论**：接受，m7-09 补 UI 对照。

### 6.5 管理列表不封顶

- **位置**：`apps/api/app/service/workspaces/service.py:144`
- **现象**：`GET /api/workspaces` 对全局管理员返回全部空间，没有分页；`auth/session` 仍有 200 条截断。
- **问题**：设计没有为管理列表规定上限；空间数量很大时响应会变大。
- **预判**：V2 初期的空间数量远小于 200；若成为瓶颈，可复用 session 的截断参数或加分页。
- **结论**：待维护者决定。

## §9 文件级代码分析

### 9.1 `apps/api/app/api/workspaces.py`（A）

职责：把 12 个管理端点映射到 service，并声明每个端点的最低空间角色与错误响应。

关键依赖是 FastAPI 的 `APIRouter`、`Depends`、`Security` 与 `Path`。路由像前台窗口：只核对“你有没有这栋楼的钥匙、够不够等级”，不处理额度算术或成员锁。

- 更新空间（`:103`）挂 `space_admin`；成员列表（`:122`）挂 `member`；候选/成员写/凭据（`:143`、`:172`、`:193`、`:216`、`:258`、`:280`、`:304`）挂 `space_admin`。
- `current_user`（`:41`）只用于 `/api/workspaces` 列表；用户行消失返回 401，与 `auth/session` 的失败语义一致。
- `POST /{wid}/members/self-admin`（`:239`）没有请求体，角色判断在 service；路由只把 principal 的 `user_id` 传下去。

检视发现：无功能缺陷；已知“全局管理员精确路径”是刻意设计，见 §2.1。

### 9.2 `apps/api/app/service/workspaces/service.py`（M）

职责：空间可见性、字段级权限、成员锁、凭据生命周期的唯一业务入口。

`authorize` 与 `session_payload` 保持 m7-03 行为不变；本 PR 在其后追加管理方法。关键设计是把“空间管理员不能授/改/删 space_admin”和“最后一个管理员不可移除”放在同一层，而不是让每个路由自己判断。

```python
if member.role == "space_admin" and access.role != "global_admin":
    raise self._role_locked()
if body.role == "space_admin" and access.role != "global_admin":
    raise self._forbidden("space admins cannot grant space_admin")
```

这段的顺序很重要：先判断“目标行是否受保护”，再判断“请求角色是否越权”。空间管理员改自己的 `space_admin` 行时返回 409（行被锁），给普通成员升管理员时返回 403（角色越权）。

凭据生成只把明文放进返回值，日志只记 `credential_id`；`verify_credential` 先校验 `whk_` 前缀再哈希，避免无关 token 进入查询。

检视发现：并发窗口见 §6.1；空数组校验取舍见 §6.3。

### 9.3 `apps/api/app/db/crud/workspaces.py`（M）

职责：空间/成员/凭据的 SQL 读写，并把数据库唯一冲突翻译成稳定的领域异常。

- `create_workspace`（`:362`）在一个事务里写空间与初始管理员；只捕获空间名唯一冲突，其他完整性错误继续上抛，避免把 FK 失败伪装成重名。
- `list_members`（`:426`）用 `CASE` 生成角色序号，避免依赖数据库自己的字符串排序；`joined_at` 作为第二排序键。
- `search_member_candidates`（`:535`）用 `NOT IN (SELECT user_id …)` 排除成员；`autoescape=True` 把用户输入的 `%/_` 当字面量。
- `upsert_space_admin`（`:631`）先查后写，保证重复自任不产生第二行；`revoke_credential`（`:756`）只更新 `revoked_at IS NULL` 的行，重复撤销返回 0 行但不报错。

检视发现：`update_member_role` 与 `remove_member` 的成功路径已由新增测试覆盖；并发语义见 §6.1。
