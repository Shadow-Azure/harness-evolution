## §1 一页速览

**一句话**：edit 通道不再走「`--bare` 拿走 `Write` + 相对 `Write(./…)` 门禁卡」那条注定写不出文件的老路，改为和 analyze 共用一套已在生产验证过的无头调用形状与绝对 `Edit(//abs)` 规则，同时把失败证据从「只有一行 stderr」升级为「CLI 的 result 结构化字段」。

**比喻**：把 Claude Code 想成上门维修师傅。`--tools` 是他允许带的工具箱，`--allowed-tools` 是门禁卡上写的具体房间号。改动前 edit 师傅被要求「只带锤子」（`--bare` 把 `Write` 拿走），门禁卡上还写着「我家」（`Write(./…)` 相对路径），而门禁只认绝对门牌（`Edit(//abs)`）——于是他只能在楼道里敲 644 秒，最后留下一句「模型不认识」的走廊回声（stderr）当作事故报告。本 PR 把两个工种合并成同一份上门规矩，门禁卡改成绝对门牌，并给师傅配了一个行车记录仪（结构化失败证据）。

**但记录仪是到站才取卡**：`AsyncioClaudeCliRunner` 用 `communicate()` 一次性收齐输出（`claude_cli.py:126`），provider 也在进程退出后才解析 `system/init`（`claude_code.py:523`）。所以「缺 `Write` 就在数秒内拦下」这条验收在本 PR 里仍然做不到，详见 §6 讨论点 1。

## §2 架构导览

### 2.1 一个构造函数，两种 profile

改动前 `claude_code.py` 里有两份手拼的 argv：`_analyze_argv()`（main:534，已硬化但自己拼公共段）和 `_edit_argv()`（main:581，还是 `--bare` + `--output-format json` 的老形状）。两份 argv 意味着两套权限面，任何一次修复只落在其中一份上就会漂移——#537 修好 analyze 之后 edit 独自留在 `--bare` 上，正是这个结构后果。

新结构把公共段收到 `_headless_argv(profile, settings_file=…)`（`claude_code.py:594-632`），差异抽进 `_HeadlessProfile`（`:148-154`，四个字段：`prompt`/`tools`/`rules`/`max_turns`）。`_analyze_argv()`（`:655-678`）与 `_edit_argv()`（`:680-705`）退化成一屏内的 profile 装配，差异只剩：

| 差异 | analyze | edit |
|---|---|---|
| `--tools` | `Read,Write` | `Read,Grep,Glob,Write` |
| 读取规则 | `Read(//<task>/schema.json)` | `Read(//<workspace>/**)` |
| `--max-turns` | 不传 | `120` |
| `cwd` | 解析后的任务目录 | 解析后的 workspace |

这个收敛的价值不在于少写几行，而在于**下一次改公共段（比如追加一个 flag）只可能落在唯一一处**。同目录的 `claude_skill.py:228-239` 里还有另一处 `-p` argv，但那是沙箱里的 Skill 执行（`--bare`、`--session-id`、`bypassPermissions`、stdout 取结果），issue 非目标明确把它排除在外，属于有据可查的例外。

### 2.2 规则构造函数：绝对门牌

`_submission_rules()`（`claude_code.py:634-653`）是本次第二处收敛。它把「提交写入」固定为 `Edit(//<abs result_path>)`，把「读取面」按阶段二选一：

```text
analyze: Read(//<task>/schema.json), Edit(//<task>/result.json5)
edit:    Read(//<workspace>/**),     Edit(//<workspace>/.harness-evolution/edits.json5)
```

两点值得记住。其一，`//` 是 Claude Code 的「文件系统根」锚点，单斜杠是「settings 源」锚点；`_permission_rule_path()`（`:1052-1059`）用 `path.resolve().as_posix().lstrip('/')` 保持这条语义，注释也写清了。其二，写入规则在**两个阶段都是 `Edit(...)` 而不是 `Write(...)`**——这不是笔误，Claude Code 的文件写权限只按 `Edit(path)` 匹配，`Write(path)` 规则不参与匹配；PR 描述里被列为根因的 `Write(./…)`（`submission.py:262`）正是踩了这一点。

### 2.3 工具面三常量与 07 §5.5.4

`READ_ONLY_TOOLS`（`:83`）、`ANALYZE_TOOLS`（`:86`）、`EDIT_TOOLS`（`:98`）是一组「能力面常量」。`EDIT_TOOLS` 由 `(*READ_ONLY_TOOLS, SUBMISSION_TOOL)` 拼出，天然保证「只读 + 唯一提交写」这个组合，`Bash` 和 `Edit` 工具永远进不来。

这个组合与 [07 §5.5.4](../plans/fullstack-design/07-backend-implementation.md) 的「agent 以只读工具（Read/Grep/Glob）探索 → 写 `edits.json5`」逐字对应，所以 `EDIT_TOOLS` 含 `Grep`/`Glob` 在**设计依据**上是站得住的；issue 正文那句「`Grep`/`Glob` 只有在 init 工具列表证明存在时才加」是另一层要求（见 §6 讨论点 5）。

### 2.4 失败证据的三个来源

改动前，非零退出的 detail 只有 `_diagnostics()`（main:1019-1025）拼的 `exit_code` + 有界 stderr。本次把它拆成三层：

1. `_failure_detail(result, parsed)`（`:1136-1159`）：`exit_code`、`is_error`、`subtype`、`api_error_status`、`tools`/`stop_reason`/`num_turns`/`permission_denials`（复用 `_cli_result_diagnostics()`，`:1096-1109`），最后才是 stderr。这里刻意不打印 `result.result`（模型正文），测试 `test_edit_nonzero_exit_keeps_the_result_evidence` 用 `"model secret text" not in detail` 钉住了这条。
2. `_submission_denial_detail(parsed)`（`:1087-1093`）：从 result 的 `permission_denials` 里挑第一个写类工具的拒绝，渲染成 `permission denied: Write(<path>)`。edit 的 `collect` 失败时先放它（`:418-425`），否则 detail 只有一个 `missing`。
3. `_cancelled_error()`（`:562-592`）：超时/取消仍保留原逻辑，用 stderr + `_cli_result_diagnostics(parsed)`。这一层的输入见讨论点 2。

`_missing_submission_tool_detail()`（`:1129-1133`）与 `_api_error_status()`（`:1162-1171`）是两个共用小件，前者被三条快速失败路径共享，后者把 `api_error_status` 的类型判断从 `_error_result_detail()` 里提出来复用，避免两处实现走样。

### 2.5 快速失败的边界

「快速失败」在代码里其实是三处不同的触发点，触发时机并不一致：

| 触发点 | 条件 | 位置 | 生效时机 |
|---|---|---|---|
| A | 退出码 ≠ 0 且 init 缺 `Write` | `:530-537` | 进程退出后 |
| B | 退出码 = 0、`is_error=false` 且 init 缺 `Write` | `:405-411` → `:362-372` | 进程退出后，`collect` 之前 |
| C | 超时/取消 | `:511-512` → `:562-592` | 墙钟用尽时 |

三条都在「进程结束之后」，所以这里的「fast」指的是**不重试、不继续 collect**，不是「数秒内停掉进程」。这是本 PR 最容易被读错的一处口径（讨论点 1、2、3 都围绕它展开）。

## §3 数据流走查

一次健康的 edit 调用（部署机 CLI 2.1.325 实测路径）：

1. `edit_workspace()` 起钟（`claude_code.py:381`），`StructuredSubmission.prepare("agent.edit", EditPlan, directory=request.workspace, filename=EDIT_PLAN_FILENAME)` 把 `schema.json` 与指令片段落到 workspace，`result_path` 指向 `.harness-evolution/edits.json5`（`:382-387`）。
2. workspace 解析成物理路径 `directory`（`:392`，`_resolved_directory()` 即 `Path.resolve()`，`:1047-1049`），**同一个值**同时用于 `cwd` 和权限规则。这一步是从 analyze 那边搬过来的：`cwd` 未解析、规则已解析时，符号链接的目录（例如 `/tmp` → `/private/tmp`）会让规则匹配不上（analyze 的注释在 `:236-241`）。
3. `_edit_argv()` 装配 profile（`:393-398`），`_headless_argv()` 拼出完整 argv（`:610-632`），`--max-turns 120` 与 `--settings` 按需追加。
4. `_call("edit", argv, cwd=directory, timeout_seconds=1800)`（`:399-404`）交给 `AsyncioClaudeCliRunner`：`create_subprocess_exec` + `start_new_session=True`，stdout 走 PIPE 由 `communicate()` 收齐，stderr 落到带截断的临时文件（`claude_cli.py:111-150`）。
5. 进程退出后解析 stdout：NDJSON 里第一条 `type=system, subtype=init` 贡献 `tools`（`:833-840`、`:883-894`），最后一条 `type=result` 贡献 `permission_denials`/`stop_reason`/`num_turns`/usage（`:841-852`）。
6. `_ensure_submission_tool()` 检查 `Write` 在不在工具面（`:405-411`）；不在就 `retryable=False` 抛错，detail 带 `tools=`。
7. `collect()` 读 `edits.json5`，走「严格 JSON → JSON5 → repair」的阶梯再 `EditPlan.model_validate`（`submission.py` 通道，本次未改）。
8. 失败时组装 detail：`permission denied: Write(<path>)`（若有拒绝）→ `_submission_detail(outcome)` → `_cli_result_diagnostics(parsed)`（`:418-425`）。
9. 成功时返回 `EditResult(plan=validated, usage=parsed.usage, …)`（`:435-446`）。注意 `changed_files=()`、`unified_diff=""`：edit 只产出计划，确定性应用在 patch source 侧。

失败分支的剧本各走一步就结束：

- **非零退出 + 工具面缺 `Write`**：`:530-537` 直接给「tool set does not include Write」，不再报 `exited unsuccessfully`。
- **非零退出 + 工具面正常**：`:538-543` 给 `_failure_detail()`，`retryable=True`（保持原语义）。
- **退出 0 但缺 `Write`**（CLI 静默收窄工具面的形态）：`:405-411` 拦下，`submission_rounds=0`。
- **退出 0 + `is_error=true`**：`:553-559` 先抛 `reported an error result`，detail 来自 `_error_result_detail()`——**没有 `tools=`**，也走不到 `_ensure_submission_tool()`。这条分支是讨论点 3 的一半。
- **超时**：`:511-512` 抛 `cancelled`，detail 见讨论点 2（实测 stdout 为空，只剩 stderr）。
- **写被拒**：退出 0、`collect` 得 `missing`，`:418-425` 把 `permission_denied` 的路径并进 detail。

## §6 讨论点

### 讨论点 1：「数秒内失败」这条验收在缓冲 transport 上不可达

**位置**：`apps/api/app/third_party_api/ai_agent/claude_code.py:523`、`:526-537`；`apps/api/app/third_party_api/ai_agent/claude_cli.py:126`；`docs/claude-code.md:27`；`.agents/notes/implemented/bug-fix/2026-11-24-claude-edit-tool-surface.en.md:19`；`.agents/flow/issues/bugfix-claude-edit-tool-surface.md:157`

**现象**：`system/init` 那一行在进程启动后很快就写到 stdout，但 `AsyncioClaudeCliRunner.run()` 用 `process.communicate()` 把输出一次性收齐（`claude_cli.py:121-126`），`_call()` 要等 `run()` 返回才 `_parse_cli_stdout(result.stdout, …)`（`claude_code.py:523`）。也就是说，缺 `Write` 这件事只能在**进程结束之后**被发现。如果 CLI 不主动退出（`--tools` 里要的工具不存在时它只是静默少给），edit 会照旧跑满 120 轮或 1800 秒，然后才由 `_call` 给出「tool set does not include Write」。

**预判**：两条路二选一。①把口径改准：文档/Note/验收写「失败原因指向缺失工具，不再让 stderr 冒充原因」，不再承诺秒级；②另开 issue 做流式 fail-fast（transport 加 `on_init` 回调，provider 在回调里判定并终止进程组），本 PR 不扩面。当前实现没有数据错误，实害是「排障预期」与「文档承诺」不一致；但如果按验收标准卡，这是要对齐的。

### 讨论点 2：1800s 墙钟路径仍只有 stderr，而 120 轮让这条路径比改动前更常走到

**位置**：`apps/api/app/third_party_api/ai_agent/claude_cli.py:124-147`；`claude_code.py:511-512`、`:574-586`；`claude_code.py:109`

**现象**：`claude_cli.py:124` 把 `stdout` 初始化成 `b""`，随后 `stdout, _ = await asyncio.wait_for(asyncio.shield(io_task), timeout_seconds)`。超时时这行赋值不会发生，`finally` 里 `io_task.cancel()` 把 `communicate()` 已读到的字节一起丢弃，结果 `ClaudeCliResult.stdout` 是空串。本次实测（子进程先 print init 行再 sleep，timeout 1s）得到 `cancelled=True, stdout='', stderr=''`。于是 `_cancelled_error()` 里的 `_cli_result_diagnostics(parsed)` 恒为空，detail 退化为 `cancelled; stderr=[claude-code:unrecognized_model] …`——恰好是本 PR 判定为「诊断行冒充原因」的那个形态。

**问题**：`.agents/notes/…en.md:17` 的算术是对的：本次事故 644s ≈ 40 轮 × 16s，120 轮 ≈ 32 分钟 > 30 分钟，所以**退化会话会先撞墙钟**。改动前 40 轮总能先于 1800s 触发（644s < 1800s），失败形态是「非零退出 + 结构化证据」；改动后同样的退化会话大概率变成「超时 + 只有 stderr」。也就是说，PR 修好的那条证据路径，被 `EDIT_MAX_TURNS` 的提高推到了更少发生的分支上，而最常发生的分支仍然是空的记录仪。现有单测 `test_cancelled_call_keeps_stderr_and_cli_evidence`（`test_ai_agent_claude_code.py:476-515`）给 MockRunner 塞了一个「`cancelled=True` 但 stdout 有内容」的结果，真实 transport 产不出这种组合，这条测试反而掩盖了缺口。

**预判**：修法都不在本 PR 范围（issue 非目标：不改 `claude_cli.py`）：①transport 保留增量 stdout（读任务把已读块累积到局部变量，取消时交出已读部分），超时 detail 就能带上 `tools=`/`num_turns`；②把 `EDIT_MAX_TURNS` 压到墙钟之内（按 16s/轮，≤100 轮才会先触发轮次上限），让失败形态回到有结构化证据的那条。当前实害是排障成本，不是数据错误；建议至少把这条限制写进 Note 的 Consequences，并让 `test_cancelled_call_*` 用真实 transport 的形状（stdout 空 + stderr 尾）来钉。

### 讨论点 3：缺 `Write` 的三条失败路径证据不齐，其中一条完全绕过工具检查

**位置**：`claude_code.py:526-543`（非零退出分支）、`:544-559`（`is_error` 分支）、`:553-559` 与 `:405-411` 的先后关系；`apps/api/app/third_party_api/ai_agent/contracts.py`（`AgentProviderError` 的 `latency_ms=0`、`trace` 默认空）
