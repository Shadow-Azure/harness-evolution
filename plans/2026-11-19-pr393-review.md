## §1 一页速览

一句话：同一版本的 ref 是“常用名”，digest 是“身份证号”；以前两套名字各算一个版本，现在用身份证号做唯一身份、用常用名做展示，并从 run 里取出当时解析到的 commit。

| 交付块 | 内容 | 证据 |
|---|---|---|
| 版本身份 | 触发记录内的 ref+digest 合并；默认 ref 与 digest 只有 run 关联时也合并；digest 保持规范键 | `targets.py:326`、`:437`、API UT |
| run 证据 | `target_revision` → `base_commit` 前 7 位 | `overview_targets.py:178`、API UT |
| 契约 | `versionOptions`、`byVersion[].ref/commit` | `target_schemas.py:40`、`contract:check` |
| 前端 | 多选与版本行 ref + commit；digest 兜底 | `TargetDetailCard.vue:252`、组件测试 |
| 证据 | Before 3 行（main 0 + 2 digest）/ After 2 行（main 2 + v6.4.1 2）/ 原型对照 | PR 描述与发布资产 |

## §2 架构导览

**数据访问层**（`overview_targets.py:178`）

新增的 `list_target_runs` 只做一件事：按 workspace + 对象类型 + 对象名取最近 200 条 run，返回 `target_version`、`target_revision`、`base_commit`、`created_at`。它不写库、不解析 git，也不改变 matcher 的输入；这样展示证据与匹配语义解耦。

**聚合层**（`targets.py:326`、`:437`）

`_record_identity` 把一条 `agent_events` 记录的 `(object_version, object_revision)` 折成一个 `(canonical_key, aliases, ref, digest)`。`_merge_version_groups` 再把“只有 ref 的默认组”和“只有 digest 的事件组”按 run 的 ref↔digest 证据合并；生产数据里 `main` 仅出现在 run、事件只带 digest，这一步决定最终是 2 行而不是“main 0 + main 2”。`_build_version_labels` 用 digest 做 key、把同一 digest 的多条 ref 合并，再用 run 的 `target_revision` 匹配 commit；最后按展示标签自然序排序。这里有三个边界：

1. 同一 digest 不同 ref：最近 run 的 `target_version` 优先，其次 `defaultRef`，最后自然序；
2. 只有 digest：不反查 git，保留 digest 兜底；
3. 只有 ref：仍以 ref 为 key，run 的 `target_version` 兜底 commit。

**投影层**（`targets.py:793`、`:964`、`:1069`）

`_analyse_target` 对每个规范版本调用一次 matcher；`_newest_link_by_case` 现在接收别名集合，因此 probe 记录的是 `main` 还是 `digest:` 都能命中同一版本。`_selected_versions` 兼容旧 URL 的 ref 值，按别名映射回规范键，但仍保持请求顺序与去重。

**前端**（`TargetDetailCard.vue:67`、`:376`）

`versionMeta` 把 `versionOptions` 转成 `version → {ref, commit}`；多选显示 `versionRef` + `versionCommit`，版本行直接读 `row.ref` / `row.commit`。复选框的 `data-version` 仍是规范键，所以 URL、筛选和统计口径不变。

## §3 数据流走查

一条主线：

1. `agent_events` 的一条 skill 触发记录同时有 `object_version=main`、`object_revision=digest:8e54…`（`targets.py:326`）。
2. 生产同态数据里事件只带 digest，服务先按 digest 建组，再按 run 的 ref↔digest 证据把默认 `main` 组合并进来；key 为 digest，aliases 包含 `main`、`digest:…` 和裸 hash（`targets.py:437`）。
3. run 表有 `target_version=main, target_revision=digest:8e54…, base_commit=10e97a3…`，服务取前 7 位作为展示 commit（`overview_targets.py:178`）。
4. 对 digest 键调用 matcher；`MatchCondition` 的 candidates 同时覆盖 digest、裸 hash，事件按 revision 命中（`targets.py:793`）。
5. probe 的 `object_version=main` 通过别名集合命中同一版本的归因（`targets.py:496`）。
6. 详情响应返回 `versions=[digest]`、`versionOptions=[{version, ref, commit}]`、`byVersion[0]={version, ref, commit, …}`（`targets.py:697`）。
7. Vue 用 `versionOptions` 渲染 `main 10e97a3`，复选框仍提交 digest（`TargetDetailCard.vue:252`、`:376`）。
8. 旧链接 `?dversions=main` 在 `_selected_versions` 里按 alias 映射到 digest（`targets.py:964`）。

## §6 讨论点

**1. `versions` 的 URL 值从 ref 变成规范 digest**

- 位置：`apps/api/app/service/overview/targets.py:964`
- 现象：旧 URL 里的 `dversions=main` 仍能工作，但新生成的 URL 写 `digest:…`；直接读 URL 的人看不到 ref。
- 问题：这是展示层修复带来的可观察变化，是否要保留 ref 作为 URL 值？
- 预判：保留 digest 作为 URL 值更稳，因为 ref 会移动、同一 ref 可能对应多个历史版本；展示由 `versionOptions` 承担。当前实现已在服务端做别名兼容。
- 结论：待维护者拍板。

**2. 同一 digest 对应多个 ref 时只显示一个 ref**

- 位置：`apps/api/app/service/overview/targets.py:437`
- 现象：例如 `main` 与某个 feature 分支解析到同一 body hash 时，卡片只显示最近 run 的 ref。
- 问题：是否需要展示全部 ref，或至少提供 tooltip 说明其他 ref？
- 预判：单标签更接近原型，也不会让同一版本多行；最近 run 优先符合“用户最近选择”的直觉。
- 结论：待维护者拍板。

**3. 潜在 bad case 总数会下降**

- 位置：`apps/api/app/service/overview/targets.py:793`
- 现象：改动前同一 case 在 ref 与 digest 两个版本下各计一次；改动后只计一次。
- 问题：这是 issue 明确要求的“不重复计数”，但会让熟悉旧数字的人以为数据少了。
- 预判：方向正确；发布说明或界面提示是否需要解释“同一版本不再重复计数”？
- 结论：待维护者拍板。

## §9 文件级代码分析

**`targets.py`**

- 职责：对象总览的版本发现、matcher 调用与详情投影。
- 变更：用 `_record_identity` / `_merge_version_groups` / `_build_version_labels` 取代“每个 identity 一个版本”的 `_ordered_versions`；`_newest_link_by_case` 改为别名集合；详情行带 ref/commit。
