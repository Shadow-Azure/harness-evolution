## §1 一页速览

**一句话：** 总览页长出 V2 的两个工作流入口（「上报接入」「启动自进化」）和趋势右侧的运营上下文（额度、上报地址、当前空间），并把来源 × 时间矩阵用“每个时间桶问一次既有 sources 聚合”的方式补回来——不新增 API、数据库字段或第二条写路径。

**比喻：** 这次不是新盖办公室，而是给总览页配了一个值班台：左边公告板（趋势）照旧，右边值班台摆着额度、上报地址和当前空间；页头两个按钮是通往**已有**房间的门（空间管理页、启动向导），门后的事情没有重写。来源 × 时间矩阵像一排按周/日切好的抽屉：要用时才一个个拉开，问服务器“这一格里有谁”，再把 14 张回执拼成一张表。

## §2 架构导览

### 2.1 页头动作与角色门控

页头动作按 `canManageWorkspace(auth.workspaceById(workspaceId)?.role)` 分支（`Index.vue:79-81`、`345-385`）：cases Tab 下管理员看到「上报接入」`RouterLink` 与「启动自进化」按钮，非管理员看到只读提示；targets Tab 仍保留原「+ 新增进化对象」/只读分支。两个入口都复用既有实现：

- 「上报接入」是对象形式的 `RouterLink`，目标为当前空间 `admin` 路径 + `?tab=ingest`（`Index.vue:348-354`）；管理页的 `activeTab` 会校验 `route.query.tab`（`apps/web/src/pages/workspaces/Admin.vue:66-72`）。
- 「启动自进化」打开既有 `LaunchWizard`（`Index.vue:528-533`），`openLaunchWizard` 仍二次检查 `canManage`（`Index.vue:237-240`），属于按钮级门控之外的纵深防御。

门控结论：**前端隐藏不是安全边界**，但服务端本来就是边界——凭据列表/创建都要求 `space_admin`（`apps/api/app/api/workspaces.py:249-299`），启动运行也走既有 API；因此这里没有可绕过的新写路径。唯一的“过期”风险是角色来自登录会话缓存，降权后要等会话刷新按钮才消失（服务端仍会拒绝），见 §9 的 `Index.vue` 发现。

### 2.2 运营上下文的数据拼装

`OverviewOpsContext` 是纯展示组件，自身不发请求（`OverviewOpsContext.vue:11-16`），数据来自两条既有链路：

- `totals`：summary 的 `used/quota/sources`（`Index.vue:487-492` 传入 `summary?.totals`）；`used/quota` 在契约里明确是“忽略窗口与筛选”的工作空间级数字（`apps/api/app/service/overview/schemas.py:30-31` 的 docstring）。
- `workspace`：会话里的 `SessionWorkspace`，取 `spaceAdminCount/memberCount/role`（`OverviewOpsContext.vue:134-154`）；这些字段在契约里是必填（`packages/contracts/openapi.json:5489-5545`）。

派生规则：`percent = workspaceQuotaPercent(used, quota)`、`remaining = max(0, quota-used)`、`hot = percent > 80`（`OverviewOpsContext.vue:21-33`）；上报地址由空间 ID 拼出（`OverviewOpsContext.vue:18-20`），复制按钮只写这段字符串，不读取、不缓存凭据（`OverviewOpsContext.vue:48-62`）。

### 2.3 来源 × 时间矩阵：用“按桶问一次”替代新字段

m8-04 的欠账是“对象 × 桶”交叉计数；本 PR 不新增字段，改为在展开时对趋势返回的每个 bucket 调一次既有 `sources` 聚合（`SourceMatrix.vue:91-157`）：

1. 用当前 sources 行初始化矩阵行（`SourceMatrix.vue:98-107`）。
2. `mapConcurrent` 用 4 个 worker 取桶（`SourceMatrix.vue:58-76`）；每个桶先 `bucketWindow(bucket, grain)` 换出闭区间（`SourceMatrix.vue:108-120`），再 `getOverviewSources(workspaceId, {...filters, from, to})`（`SourceMatrix.vue:113-118`）。
3. 把每个桶的 `{self, discovery}` 写进行单元格并累加总计（`SourceMatrix.vue:121-141`），再按“当前 sources 的顺序 → 合计降序 → 名称”排序（`SourceMatrix.vue:142-150`）。
4. `useQuery` 的 key 包含 workspace、filters、grain、桶 id 列表与 sources 的 `object:total`（`SourceMatrix.vue:161-183`）；折叠时 `enabled=false`，不请求。
5. 渲染层：>31 桶只给“切换周/月粒度”提示（`SourceMatrix.vue:219-225`）；加载、错误、空态仍是区块级 `LoadingSkeleton`/`ErrorState`（`SourceMatrix.vue:226-245`）。

`bucketWindow` 的语义是“桶 start 所在整周/整月/当天”（`apps/web/src/pages/overview/overviewUrl.ts:358-386`），而趋势服务的 `bucket_starts` 返回的是“与窗口相交的桶 start”（`apps/api/app/service/overview/window.py:193-203`），趋势聚合本身只统计 `window.start..window.end`（`apps/api/app/service/overview/service.py:197-210`）。这两个定义在**窗口边缘不重合**，是本 PR 最值得讨论的正确性问题（D1）。

### 2.4 双栏与响应式

`.ov-grid` 桌面为 `minmax(0,1fr) + 282px`（`Index.vue:665-671`），列表 `grid-column:1/-1`（`Index.vue:677-680`）；≤1024px 单列并用 `order` 固定趋势→列表→上下文（`Index.vue:746-763`）。所有新容器都补了 `min-width:0`（`Index.vue:673-684`、`SourceBars.vue:173-190`、`SourceMatrix.vue:303-352`），这是矩阵这类宽内容不把卡片撑破的关键；E2E 在 1440/1024/390 三个宽度断言 `scrollWidth === clientWidth`（`tests/e2e/m12-08-overview-actions-context.test.mjs:744-786`）。

## §3 数据流走查

场景：管理员从登录后默认落地 `/workspaces/:wid/overview?range=90&grain=week`，然后依次点两个入口、展开矩阵。

1. **解析 URL**：`parseOverviewQuery` 得到 `range=90、grain=week、objects=[]`（`apps/web/src/pages/overview/overviewUrl.ts` 的 parser），页面用 `summaryFilters/trendFilters/caseFilters` 派生四条查询（`Index.vue:54-74`）。
2. **确认身份**：`auth.workspaceById(wid)?.role` 为 `global_admin`，`canManage=true`（`Index.vue:79-81`）；页头渲染「上报接入」「启动自进化」（`Index.vue:347-363`）。
3. **读上下文**：summary 返回 `used=7, quota=40, sources=2`；会话 workspace 返回 `spaceAdminCount=1, memberCount=2, role=global_admin`；组件显示 `7 / 40`、`18% 已使用`、`剩余 33`、`2 个` 与上报地址（`OverviewOpsContext.vue:75-162`）。
4. **进管理页**：点「上报接入」push 到 `/admin?tab=ingest`；管理页按 `route.query.tab` 选中上报 Tab（`Admin.vue:66-72`）。浏览器后退恢复 overview 的 `range/grain/objects/page`——E2E 断言 `location.search` 与 4 行列表（`m12-08...test.mjs:456-532`）。
5. **启动向导**：点「启动自进化」→ `wizardOpen=true` → 挂载 `LaunchWizard`（`Index.vue:528-533`）；关闭不写 URL（E2E:500-532）。真正启动成功时 wizard `emit("launched", mode, runId)`（`LaunchWizard.vue:598-619`），页面 `onLaunched` 关闭向导并 `router.push` 到 `evolution/runs/:id` 或 `evolution/cluster/:id`（`Index.vue:242-261`），后退回到原总览 URL。
6. **展开矩阵**：点 `ov-matrix-toggle` → `open=true` → `enabled=true`（`SourceMatrix.vue:45-50`）→ 对每个趋势桶取闭区间 → 4 并发请求 sources → 合并行 → 渲染表格（`SourceMatrix.vue:226-298`）。默认 90 天周粒度今天会得到 14 个桶；每个桶的 `from/to` 是**桶自己的**整周，而不是“桶与页面窗口的交集”。
7. **改筛选**：URL 变 → `summaryFilters/buckets` 变 → `SourceBars` 进入 loading 骨架（`SourceBars.vue:89-101`），矩阵随 `v-else` 分支卸载、`open` 状态丢失；重新加载后需再点一次展开。查询 key 变化保证不会拿旧筛选的数据，但在飞的旧桶请求不会被取消（§9 的 `SourceMatrix.vue` 发现）。
8. **边缘**：若窗口 start 不在周/月边界（默认 90 天几乎总是如此），第一个桶的请求会覆盖窗口外的几天；trend 没统计这些天，矩阵统计了（D1）。

## §6 讨论点

### D1（P2，建议合入前修）来源 × 时间矩阵的桶窗口没有按当前窗口裁剪

- **位置**：`apps/web/src/pages/overview/components/SourceMatrix.vue:108-120`；`apps/web/src/pages/overview/overviewUrl.ts:364-386`；`apps/api/app/service/overview/window.py:193-203`；`apps/api/app/service/overview/service.py:199-210`
- **现象**：趋势返回的首桶 `bucket` 是“包含窗口 start 的那个周/月/日”的 start。例如今天（2026-11-18）默认 90 天窗口是 `2026-08-21 .. 2026-11-18`，首个周桶 start 是 `2026-08-17`（周一）；trend 只统计 `08-21 .. 08-23`，但矩阵用 `bucketWindow` 得到 `08-17 .. 08-23` 并向 sources 请求这段，于是把 08-17..08-20 的数据也算进了首列。同一现象会出现在窗口 end 落在周/月中间时的末桶。
- **问题**：矩阵首列可能大于趋势柱；行的“合计”可能大于来源分布条的总数；如果窗口外那几天有某个来源、而当前窗口没有，矩阵还会多出一行当前来源列表里不存在的来源（因为 `SourceMatrix.vue:124-140` 会为桶返回的 source 建行）。这直接违背 issue 验收“与当前筛选一致”和 Note 第 16 行“合并结果对当前窗口与来源筛选是精确的”。默认落地即触发，不是极端自定义窗口才有。
- **预判**：建议把 `summary.window`（`OverviewSummary.window`，Index 已有 `summary?.window`）或其他权威窗口传给矩阵，在 `bucketWindow` 结果上取交集 `from=max(bucketFrom, window.from)`、`to=min(bucketTo, window.to)`；组件测试补一个“窗口从周三开始”的用例，断言首个请求被裁剪。若维护者决定接受“整桶近似”，则必须改 Note 的“精确”措辞、`08 §6.2` 的“与当前筛选一致”口径，并在 UI 上说明首/末桶是整周/整月。
- **结论**：2026-11-18 已修复。`SourceMatrix` 新增 `window` prop，`clipBucket` 先把桶与 summary 窗口取交集；窗口未就绪时禁用请求并给提示。`SourceMatrix.test.ts` 新增窗口裁剪与 window 未就绪用例。

### D2（P2，建议合入前修）上报地址只复制相对路径，与管理页的完整 URL 不一致

- **位置**：`apps/web/src/pages/overview/components/OverviewOpsContext.vue:18-20`；`apps/web/src/pages/workspaces/components/IngestTab.vue:41-47`；`tests/e2e/m12-08-overview-actions-context.test.mjs:425`；`apps/web/src/pages/overview/Index.test.ts:413`
- **现象**：总览上下文的 `endpoint` 是 `/api/workspaces/:wid/bad-cases`（没有 origin），复制按钮原样复制这段相对路径；而既有管理页的上报地址是 `${location.origin}/api/workspaces/:wid/bad-cases`。E2E 与单测都把相对路径写成了期望值，因此测试通过反而锁定了这个差异。
- **问题**：外部上报方拿到 `/api/...` 不能直接使用，必须自己猜/拼部署域名；“上报接入”上下文的核心动作（复制地址）因此不完整。PR 描述的冒烟场景 01 写“完整上报地址”，与实际行为不符；`08` 与 Note 也只写 `POST /api/...`。这是新功能内的功能性不一致，不是纯文案。

- **结论**：2026-11-18 已修复。`OverviewOpsContext` 改为 `location.origin + /api/workspaces/:wid/bad-cases`，与管理页一致；单测与 E2E 改为断言绝对 URL。

### D3（P3，非阻塞）summary 不可用时上下文显示 `0% 已使用`，与“不伪造额度数字”的文档冲突

- **位置**：`apps/web/src/pages/overview/components/OverviewOpsContext.vue:23-27`, `92-93`；`plans/fullstack-design/08-frontend-implementation.md:521`, `523`；`apps/web/src/pages/overview/Index.test.ts:952-958`
- **现象**：`used`/`quota` 为 `null` 时 `percent` 回退为 `0`，模板仍渲染 `{{ percent }}% 已使用`，于是加载态与 summary 错误态显示 `— / —`、`0% 已使用`、`剩余 —`。设计文档明确写“运营上下文在 summary 失败时显示「—」，不伪造额度数字”。现有错误态测试只断言了 `— / —` 与角色，没有断言百分比，所以测试是绿的。
- **问题**：把“未知”呈现为 0% 会让人误以为额度为零/未使用，是文档承诺之外的自造数字；加载态还会闪一下 0%。
- **预判**：`percent`/`remaining` 在数据缺失时保持 `null`，模板显示 `—%`/`—`，或整块额度用占位骨架；补一条 summary 错误态断言 `0%` 不出现。改动很小，建议顺手修。
- **结论**：2026-11-18 已修复。`percent` 缺失时保持 `null`，UI 显示「—」；summary 错误态测试补断言。
