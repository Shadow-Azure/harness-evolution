## §1 一页速览

**一句话**：这个 PR 把 bad case 的 global 取数线从「两个互不相识的 HTTP 客户端 + `main.py` 里两段复制粘贴的装配 + 服务层 `if kind == "report"` 的两套 BFS」改造成「一个总开关（工厂）→ 一张菜单（父类模板方法）→ 一个厨房（ClaudeUpstream 子类）」，并顺带给 `bad_cases` 办了「房产证」（`origin`），让目录同步再也改不动上报过的行。

**一个比喻**：以前这家店有两条后厨流水线，一条做「上报菜」、一条做「目录菜」，切菜、装盘、上菜各写一遍；客人点菜还得看是哪个厨师值班。现在只留一条传菜带：服务员（服务层）只认菜单上的两道菜（`fetch_bad_case_page` / `fetch_session`），流程由领班（父类）固定——先取轨迹、再取子会话、再拼成统一信封；具体怎么炒（端点、Bearer、超时、重试）全在新来的厨师（子类）脑子里。总闸（`HE_BAD_CASE_SYNC_PROVIDER`）不合上，整条 global 线没电，但上报线照常营业。

**代价**：多了一层抽象和一张 `origin` 列；升级后现网若只配了旧端点、没加总闸，global 线会安静地关掉（装配期 warning 提示）；global 路径改成「先读子会话再落库」，某个 agent 的子会话读失败时它自己的 payload 这一轮不写（Note 已记，重试阶梯会补）。

## §2 架构导览

### 2.1 三个新文件就是「总闸 + 菜单 + 厨房」

新目录只有四个文件，依赖方向是单向的：`service/acquisition → base`（只认类型）、`main.py → factory`、`claude_upstream → base + 既有两个 HTTP 客户端 + SessionSourceFactory`（`third_party_api/bad_case_sync_source/__init__.py:5-10`）。`base.py` 不 import `httpx`，`factory.py` 也不 import，所以「服务层看得到 HTTP」这件事在结构上被堵死了。

这一点值得单独说，因为它是 R1/R5 的验收核心：以前 `main.py` 里两段 `if xxx_configured:` 各建一个 `httpx.AsyncClient`（旧 `main.py:270-286`、`310-325`），服务层同时持有 `SessionQuerySource | None` 和 `SessionSourceFetcher | None` 两个互不相干的取数依赖。现在服务层的构造参数只有一个 `source: BaseBadCaseSyncSource | None`（`bad_case_sync.py:144-168`、`bad_case_catalog_sync.py:84-100`）。

### 2.2 父类模板方法：菜单只有两道菜

父类把「什么时候取」写死，子类只决定「怎么取」（`base.py:29-106`）：

- `fetch_bad_case_page(after_id, offset, limit)`（`base.py:39-47`）只是 `return await self.fetch_page(...)`——听起来像废话，但它的价值是把「一页目录」这个返回类型钉在父类：服务层不再依赖任何具体的 catalog 客户端协议。
- `fetch_session(session_id, expected_parent_id, snapshot)`（`base.py:59-83`）才是真正有流程的一道：先 `fetch_trajectory`（读轨迹）→ 再 `list_children`（读子会话）→ 再 `build_envelope`（拼信封）→ 最后 `SessionSourceFactory.create(envelope.runtime).project(...)`（交给既有投影链）。

举个具体例子：root `01JROOT…` 第一次被领取，服务层喊 `fetch_session(session_id="01JROOT…", expected_parent_id=None)`。父类依次触发子类：`GET …/trajectory`（NDJSON → `SessionTrajectory(line_count=128)`）、`GET …/children`（`["01JCHILD…"]`）、合成信封（`agentKind="main"`、`runtime="claude-code"`），投影后得到 `SessionInfo(runtime_key="claude-code", agent_meta=None, child_session_ids=("01JCHILD…",))`。走到子 agent 时同样的调用只是 `expected_parent_id` 非空，信封变 `agentKind="subagent"`，投影把 `parentSessionId` 合并成 `agent_meta={"parentAgentId": …}`——这正是旧 `_payload()` 手拼出来的形状（旧 `bad_case_sync.py:488-507`）。

签名对照（逐字核对 §3.2）：两个模板方法的参数名、关键字限定、类型与返回类型完全一致；四个抽象钩子 `fetch_page` / `fetch_trajectory` / `list_children` / `build_envelope` / `close` 也一致。**唯一新增**是父类把 `from_settings` 声明成抽象类方法（`base.py:34-37`）——设计 §3.1 把它画在子类一栏、§3.2 的父类代码块里没有它；这是偏紧的加法，见 §6 讨论点 7。

### 2.3 工厂：一个总闸，三种状态

`factory.py:67-88` 是开关的唯一读点（全仓 grep `bad_case_sync_provider` 只有 `factory.py:49` 与 `config.py` 的字段/校验器）：

1. **未配置/空白** → `None`。两个服务拿到 `None`，两个 coordinator 的 `available=False`，状态接口 `unavailable`。如果这时候旧端点凭据还在（`session_query_configured or bad_case_query_configured`），打一条 warning（`factory.py:75-87`），提示升级后要补总闸。
2. **未知值** → `create()` 抛 `ValueError`，消息里列出已注册的值（`factory.py:55-65`），`create_app` 装配期直接起不来。
3. **已知值** → `implementation.from_settings(settings)`，由子类自己解释 settings（`claude_upstream.py:85-122`）。

这个「三态」与设计 §3.5 的开关矩阵一致；`provider_key` 的空白归一（`factory.py:46-53`）与 `Settings` 的字段校验器（`config.py:247-253`）是双保险，幂等。warning 只打一次，因为 `create_app` 只调一次工厂。

### 2.4 `_sync_root`：两条传送带并成一条

旧实现是 `if selection.kind == "report": await self._sync_report_root(...); return` 然后 `_sync_global_root`（旧 `bad_case_sync.py:303-447`，其中两段 BFS 的 deadline/limits/renew_lease/enqueue 逐行近似）。新实现 `_sync_root`（`bad_case_sync.py:370-420`）只有：

```python
fetcher = self._fetcher_for(selection)          # 只决定"谁去取"，不写循环体
queue = deque([(root_session_id, None, 0)])
while queue:
    info = await fetcher.fetch(session_id=..., expected_parent_id=..., snapshot=selection)
    written = await write_local_payloads(...)    # 唯一的 payload 映射 _payload_from_info
    progress.agent_count += 1
    ... renew_lease / _enqueue_children
```

`_fetcher_for`（`bad_case_sync.py:422-438`）用两个 `if` 返回 `ReportSessionFetcher` 或 `GlobalSessionFetcher`——设计 §3.4 的伪码本身就写作 `_fetcher_for(selection)`，所以这不是「偷偷留了分支」，而是把「选谁」与「怎么走」拆开：两个 fetcher 都是 `SessionFetcher` Protocol（`bad_case_sync.py:34-45`）的实现，循环体不知道也不关心来源。

`_payload()` 确实删干净了：全仓已无 `def _payload(`，`_payload_from_info`（`bad_case_sync.py:479-499`）是唯一映射；parity 测试在测试文件里保留了旧实现的参照副本（`test_global_session_contract.py:63-83`），这是设计 §7.3 明确要求的做法。

### 2.5 写者归属：给每行办房产证

`origin` 是房产证：第一次登记是谁，之后谁才能改装修。上报插入时写 `report`（`bad_case_ingest.py:266-270`），重报走 UPDATE 且 `_UPSTREAM_COLUMNS` 故意不含 `origin`（`bad_case_ingest.py:291-298`），所以重报不改房东。目录同步 `commit_page`（`bad_case_catalog_sync.py:252-320`）先读本页已存在 id 的 `origin`：

- 不存在 → INSERT，写 `origin="catalog"`、`workspace_id=默认空间`；
- `catalog` → 条件 UPDATE（`WHERE bad_case_id=:row_id AND origin='catalog'`，`bad_case_catalog_sync.py:401-408`）；
- `report` → 一个字段都不碰，`skipped += 1`。

举个页面级例子（设计 §5 Step 5 的同款）：页里三条 1201（新）、1202（目录自有）、1203（已被 workspace 上报）。旧实现 `ON DUPLICATE KEY UPDATE` 会把 1203 的 title/description/created_at 全改掉还记成 `updated`；新实现返回 `PageCounts(inserted=1, updated=1, skipped=1)`，1203 原样不动。

### 2.6 快照与兼容：登机牌

`SessionSourceSnapshot` 是「登机牌」：第一次领取时打印（`source_snapshot IS NULL` 时写入），之后每次重试都按牌面走。这次牌面多了 `provider` 一栏（`session_source/base.py:58-60`），只允许 global 用；校验器三条拒绝规则在 `session_source/base.py:62-73`：report 带 provider、global 带模板、global 带 runtime。旧牌 `{"kind":"global"}` 仍然合法（`provider` 默认 `None`），旧行不用迁移。

「牌面 provider 有什么用」是本 PR 最值得讨论的一处：`_select_source` 会把它盖进快照（`bad_case_sync.py:331-335`），但 `_fetcher_for` 只看当前装配的 `self._source`，从不核对牌面（详见 §6 讨论点 1）。今天只有一个 provider，看不出差别；一旦出现第二个上游，「牌面写 A、实际从 B 取」的风险就成立了。

## §3 数据流走查

一条端到端主线：**进程启动 → 目录同步 → root 同步（report / global 两条分支）→ 进程关闭**。

1. **启动装配**：`create_app` 先解析 settings，然后 `resolved_bad_case_sync_source = bad_case_sync_source or BadCaseSyncSourceFactory.from_settings(settings)`（`main.py:271-274`）。工厂读总闸：未设置且旧凭据在 → 一条 warning + `None`；未知值 → `ValueError`；`claude-upstream` → 子类 `from_settings` 建两个 `httpx.AsyncClient`（`claude_upstream.py:85-122`）。
2. **装配下游**：root 服务拿到 `source`（`main.py:286-291`），目录服务也拿到同一个 `source`（`main.py:301-305`）；两个 coordinator 分别收到 `available=resolved_bad_case_sync_source is not None`（`main.py:297`、`main.py:311`）。report 路径的 `session_source_http_client` 与 `session_source_fetcher` 仍在（设计 §7.2 明确保留）。
3. **目录同步一页**：调度器 tick → 目录 coordinator `trigger`（`bad_case_catalog_sync_coordinator.py:77-99`）先看 `available`；job 跑 `BadCaseCatalogSyncService.run`（`bad_case_catalog_sync.py:131-213`），每页调父类模板 `fetch_bad_case_page`（`:163-168`）→ 子类转给 `HttpBadCaseCatalogSource.fetch_page` → `BadCasePage` 严格校验 → `_row(item, page_now)` 映射本地列 → `commit_page`（`db/crud/bad_case_catalog_sync.py:252-320`）三分流 → 同事务推进游标与 `synced_count`。
4. **目录同步结果**：`counts.skipped` 累加进 `CatalogSyncResult.skipped`（`bad_case_catalog_sync.py:188-193`、`:205-212`），job 结果多一个 `skipped` 字段（`:118-129`）；状态接口**没有**新增 `skippedBadCases`（按设计留给实现 issue，本 PR 选择不加）。
5. **root 同步领取**：`BadCaseRootSyncService.run` 取候选 → `_select_source`（`bad_case_sync.py:315-329`）：已冻结 → 原样复用；`attempts > 0` → global；有最新 `sessionUrlTemplate` 上报 → report；否则 global。global 分支把当前源 provider 盖进快照（`:331-335`）。
6. **快照校验**：`_selection`（`bad_case_sync.py:337-368`）把 DB 里的 JSON 交给 `SessionSourceSnapshot.model_validate`；`extra="forbid"` + 三条规则。旧行 `{"kind":"global"}` 在这里得到 `provider=None`。
7. **report root**：`_fetcher_for` 返回 `ReportSessionFetcher`（`bad_case_sync.py:68-94`），用快照里的模板调既有 `SessionSourceFetcher.fetch`，错误码与语义不变（模板缺失 → `SESSION_SOURCE_INVALID_RESPONSE`，客户端缺失 → `SESSION_QUERY_UNAVAILABLE`）。
8. **global root**：`_fetcher_for` 返回 `GlobalSessionFetcher(self._source)`；源为 `None` 时抛 `SESSION_QUERY_UNAVAILABLE`（`bad_case_sync.py:432-437`），与旧行为一致（该码在 `_NON_RETRYABLE_ERRORS` 里，配置出现后启动钩子 re-arm）。
9. **单循环落库**：`info` → `_payload_from_info`（`bad_case_sync.py:479-499`）→ `write_local_payloads` → 续租 → 子节点入队；批末只要写过 payload 就跑一次 `replay_pending_payloads`（`:285-293`）。
10. **进程关闭**：lifespan 依次关 `resolved_bad_case_sync_source`（一个源关两个客户端）、`session_source_http_client`、event bus、database（`main.py:664-676`），比旧版少两层 try/finally。

### 讨论点 1：快照冻结了 provider，路由却不看它

**位置**：`apps/api/app/service/acquisition/bad_case_sync.py:331-335`（冻结）与 `:422-438`（路由）；设计 §3.4 第 179 行；`third_party_api/session_source/base.py:58-59` 的注释

**现象**：`_select_source` 把 `self._source.provider` 写进 global 快照，注释说「so a later `.env` edit cannot re-route a root」；但 `_fetcher_for` 只判断 `selection.kind`，global 分支固定用 `self._source`，从不读 `selection.provider`。设计 §3.4 的目标写法是 `BadCaseSyncSourceFactory.create(selection.provider or 当前 provider).fetch_session`；设计 §6 Step 5 又画成 `self._bad_case_sync_source.fetch_session`——设计自己两处不一致，实现选了后者。

**问题**：快照里的 provider 目前是「只写不读」的字段。单 provider 部署看不出差别，但它制造了两个未来陷阱：①出现第二个上游后，老 root 的牌面写 `claude-upstream`，`.env` 改成 `other-upstream` 重启，代码会静默从新上游取同一个 session id，取不到就 404、取到了可能是别的内容，而不是按牌面路由或拒绝；②「provider 冻结」在评审与 Note 里被当成已兑现的兼容保证，实际上只保证了「快照字段被写下来」。

**预判**：这不是本 PR 的实际故障（当前注册表只有 `claude-upstream`，且设计 §7.1 允许 `provider=None` 走当前产物），但它是一个 5 行以内能关掉的洞：在 `_fetcher_for` 的 global 分支加一句「`selection.provider` 非空且不等于 `self._source.provider` → 抛 `SESSION_SOURCE_INVALID_RESPONSE`（或按 §3.4 走工厂）」，再补一例「冻结 A、装配 B」的单测。若决定不做，至少把 `session_source/base.py:58-59` 与 Note 里「cannot re-route」的措辞改成「记录用」。

### 讨论点 2：回滚「停车 + 启动 re-arm」的说法不成立

**位置**：`.agents/notes/implemented/architecture/2026-11-23-bad-case-sync-source-factory.md:34`；设计 §7.1 回滚行（第 508 行）；`apps/api/app/db/crud/bad_case_sync.py:30-42`（`_NON_RETRYABLE_ERRORS`）与 `:296-320`（`reset_deterministic_failures`）

**现象**：Note 与设计都说：旧代码读到新快照 `{"kind":"global","provider":"claude-upstream"}` 会被 `extra="forbid"` 拒绝，以 `SESSION_SOURCE_INVALID_RESPONSE`「确定性失败，停车」，启动钩子 `reset_deterministic_failures` 负责清快照 re-arm。实际 `SESSION_SOURCE_INVALID_RESPONSE` **不在** `_NON_RETRYABLE_ERRORS` 里；`deterministic_failure` 为假，`list_candidates` 不会排除它，`reset_deterministic_failures` 也不会清它。于是这类行会按 1m/5m/15m/1h 阶梯每小时重试一次，永久循环，既不停车也不会被 re-arm。

**问题**：回滚路径的缓解措施是「文档承诺、代码没有」。更麻烦的是设计 §7.2 明确写「`_NON_RETRYABLE_ERRORS` 不改」，所以这不是随手补一个枚举就能解决的——要么承认「回滚后这些 root 会一直按小时重试，人工处理」，要么把 `SESSION_SOURCE_INVALID_RESPONSE` 纳入确定性集合（会牵连「快照损坏」这类本应停车的场景，需要单独评估），要么给回滚场景换一个已在集合内的错误码。

**预判**：我倾向前者（改文档）＋一个小的迁移/运维说明：回滚不是本 PR 要支持的常态，旧代码本来也无法解释新字段；与其动错误集合，不如把 §7.1 与 Note 改成「旧代码会持续按阶梯重试，需人工或回滚后清理该 root 的 `source_snapshot`」。如果维护者希望「回滚即停车」，那应当在本 PR 内把码加进集合并同步改 §7.2 的「不改」表述，同时补一例单测（目前没有任何测试覆盖这条路径）。

**结论**：（留空，待拍板）

### 讨论点 4：provider 配了但凭据不全，两种拼错两种命运

**位置**：`apps/api/app/third_party_api/bad_case_sync_source/claude_upstream.py:93-110`；`apps/api/app/config.py:134`、`:247-253`；12 章 §9 环境变量表（本次改为「provider 启用后缺失即启动失败」）

**现象**：设计 §3.5 只定义了两态（未配置 = 关；未知值 = 启动失败），没有定义第三种「provider 配了、端点凭据没配齐」。实现的实际行为分两种：

- `HE_BAD_CASE_SYNC_PROVIDER=claude-upstream` 且 `HE_SESSION_QUERY_TOKEN`/`HE_BAD_CASE_QUERY_TOKEN` 缺失 → `from_settings` 抛 `RuntimeError("session query configuration lost its token")`，进程起不来——行为算 fail-fast，但消息像内部断言，不像给运维看的配置错误，也没指出是哪个环境变量。
- token 在、`HE_SESSION_QUERY_BASE_URL`/`HE_BAD_CASE_QUERY_BASE_URL` 缺失 → `httpx.AsyncClient(base_url="")` 照建，进程正常启动；第一次同步时请求相对 URL 触发 `httpx.UnsupportedProtocol`（属 `TransportError`），重试预算耗尽后记 `BAD_CASE_QUERY_*_FAILED`，此后每次调度都失败。也就是「拼错变量名」不会在启动时报错，而是带着病跑。

**问题**：12 章刚改的口径是「provider 启用后缺失即启动失败」，对 base_url 这一半不成立；两种拼错命运不同，排障成本也不同。仓库已有 `require_jwt_secret` / `require_valid_job_timing` 这类跨字段 `model_validator`（`config.py:212-233`），完全可以照抄一个「provider 非空 ⇒ 两组端点地址与 token 齐备」的校验器，错误消息直接点名四个环境变量。

**预判**：建议在 `Settings` 加一个 `model_validator(mode="after")`（或让 `from_settings` 抛带变量名的 `ValueError`），并补一例单测（provider 配了但缺 token / 缺 base_url 各一）。这是「运维可诊断性」而不是行为契约，成本很低；不做的话至少把 12 章 §9 的措辞改成「缺 token 启动失败，缺地址会在首次同步失败」。

**结论**：（留空，待拍板）

### `third_party_api/bad_case_sync_source/base.py`（A）

职责：定义 bad case 同步源的父类契约——两个模板方法（取一页目录、取一个 session 投影）与五个抽象钩子。新增文件，无前身。

关键依赖：不依赖第三方库；`SessionSourceFactory`（同仓既有投影链）、`BadCasePage` / `SessionInfo` / `SessionTrajectory`（同仓运行时无关模型）。换句话说，父类只进口「模型」与「下游工厂」，不进口 HTTP。

变更代码块（核心模板方法）：

```python
async def fetch_session(self, *, session_id, expected_parent_id, snapshot) -> SessionInfo:
    trajectory = await self.fetch_trajectory(session_id)
    children = await self.list_children(session_id)
    envelope = self.build_envelope(session_id=..., expected_parent_id=..., children=children, trajectory=trajectory)
    return SessionSourceFactory.create(envelope.runtime).project(envelope, trajectory)
```

实现思路：把「读两端点 → 合成信封 → 投影」的三步固定成模板，子类只提供三个纯取数与一个纯合成；`snapshot` 参数只为与 report fetcher 签名同构。检视发现：签名与设计 §3.2 逐字一致；额外把 `from_settings` 提升为抽象类方法（§6 讨论点 7）；模板方法未加 `@final`（全仓无此惯例，视为文案差异）。
