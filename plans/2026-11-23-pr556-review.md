## §1 一页速览

**一句话**：生产机没有 `bubblewrap`，而 Deploy 用户没有 apt 权限，于是把“装系统包”从日常发布里拆成独立、幂等、可审计的 Provision 入口；同时在 Ubuntu 24.04 上补一层只放行 `/usr/bin/bwrap` 的 AppArmor profile，避免装完包仍然卡在 `ATTRIBUTION_BWRAP_UNUSABLE`。

**比喻**：发布像换轮胎，旧做法是让换轮胎的人自己拆轮毂（给 deploy apt 权限，等于给 root）；本 PR 是配一个独立的千斤顶（Provision workflow），换轮胎的人仍然只干换轮胎的事。Ubuntu 24.04 的 AppArmor 又像小区门禁：不是没买车（没装包），而是车进不了地库；给 `bwrap` 单独办一张门禁卡，而不是把整个小区门禁关掉。

### 交付块

| 块 | 内容 |
|---|---|
| 安装块 | 缺包才 `apt-get update` + install；已装时 no-op，不重复 apt |

| 权限块 | Ubuntu 24.04 AppArmor userns 限制：只给 `/usr/bin/bwrap` 装 `userns,` profile |
| 入口块 | `Provision` workflow：仅 `main`、`workflow_dispatch`、`environment: production`、专用 root key |

| 新机块 | `cloud-init.yaml` 创建阶段安装 `bubblewrap`；bootstrap 仍是包清单 source of truth |
| 文档块 | 中英成对；playbook 记录首次启用/轮换/审计 |

## §2 架构导览

### 2.1 Provision 入口与 Deploy 的边界

`provision.yml:30-33` 把 Provision 放进独立 job，并绑定 `production` 环境；它不参与 `CI` / `Deploy` 的触发链，只有人点 `workflow_dispatch` 才运行。`release.sh` 的 preflight 仍然是发布门禁，`deploy.yml` 只在失败后补一个摘要，不自动安装、不重试、不跳过。

这层边界的价值在于：日常 Deploy 继续用 `deploy` 用户（sudoers 只覆盖 `systemctl`），Provision 失败也不会让发布链路获得 root。代价是存量机需要人先跑一次 Provision；这是 issue 明确选择的方向。

### 2.2 脚本是一个小型状态机

`deploy/provision-bubblewrap.sh:15-20` 固定了退出码；`verify_bubblewrap()`（`:108`）按“找二进制 → `--version` → 服务账号 → 命名空间探针”的顺序检查，`install_bubblewrap()`（`:177`）只在缺包时执行 apt，最后统一走 `probe_or_fix()`（`:139`）。

关键点是 `--check` 与 `--install` 共享同一套验证函数：`check` 只读，`install` 在验证失败且命中 AppArmor 限制时才写入 profile。这样“检查”和“安装”不会出现两套判断标准。

### 2.3 Ubuntu 24.04 的 AppArmor 是隐藏前置

`apparmor_userns_restricted()`（`:74`）只在 `kernel.apparmor_restrict_unprivileged_userns=1` 时动作；`install_apparmor_profile()`（`:81`）写 `/etc/apparmor.d/bwrap-userns-restrict` 并 `apparmor_parser -r`，profile 只给 `/usr/bin/bwrap` 放行 `userns`。

这不是“为了过探针”的临时补丁：Ubuntu 24.04 默认拦截 unprivileged userns，`bwrap` 需要写 `uid_map` 和 `setpcap`；不解决它，装完包仍然会 `setting up uid map: Permission denied`。选择 profile 而不是 `sysctl -w kernel.apparmor_restrict_unprivileged_userns=0`，是为了把放行面收敛到一个二进制。

### 2.4 凭据只给 Provision

`provision.yml:43` 从 `secrets.PROVISION_SSH_KEY` 读取专用 root key，`provision.yml:59` 明确拒绝非 `main` 触发；脚本通过 stdin 执行（`:85`），不在主机留临时文件。密钥在 review 中从 repo Secret 移到了 `production` Environment Secret（见 §6 讨论点 1）：只有带该 environment 的 job 才能读到。

### 2.5 Deploy 失败摘要

`deploy.yml:442` 给 release step 加了 `tee` 与 `PIPESTATUS`，`deploy.yml:455-485` 在失败时读取日志，按 `ATTRIBUTION_BWRAP_MISSING` / `UNUSABLE` / `PROVIDER_UNSUPPORTED` / `CONFIG_INVALID` 输出不同下一步，并链接 Provision 与部署文档。摘要不改变 release 的退出码，也不尝试修复。

## §3 数据流走查

1. 操作者在 Actions 选 `Provision`，`mode=check`；job 进入 `production` 环境，读取 Environment Secret `PROVISION_SSH_KEY`（`provision.yml:43`）。
2. workflow 校验 `GITHUB_REF=refs/heads/main`（`:59`）、配置 SSH、`ssh-keyscan`（`:73`）。
3. 脚本经 SSH stdin 进入 root shell（`:85`），`--check` 只读执行 `verify_bubblewrap()`。
4. 若缺包：输出 `state=missing error_code=ATTRIBUTION_BWRAP_MISSING`，exit 10；workflow 红，summary 指向 `install`。
5. 操作者改 `mode=install`；`install_bubblewrap()` 缺包才 `apt-get update && apt-get install -y --no-install-recommends bubblewrap`（`provision-bubblewrap.sh:177` 起）。
6. 探针若因 AppArmor 失败，`probe_or_fix()` 安装 `/etc/apparmor.d/bwrap-userns-restrict` 并重试；成功输出 `state=ready error_code=NONE`。
7. 之后 Deploy 的 `release.sh` 在迁移/切换前跑 `attribution.preflight`；通过则正常发布，失败则旧 release 继续服务，`deploy.yml` 摘要给出 Provision 入口。

## §6 讨论点

### 讨论点 1：repo Secret 还是 Environment Secret

**位置**：`docs/deployment.md:47`、`.github/workflows/provision.yml:43`

**现象**：初版把 `PROVISION_SSH_KEY` 设为 repo Secret；repo 内任何 workflow 都能读取，而 Provision 只需要在 `production` 环境的 job 里使用。

**问题**：root 私钥的读取面被放大到所有 workflow；一旦其他 workflow 被改动，密钥暴露面大于必要。

**预判**：改为 `production` Environment Secret，并在 review 中删除 repo 级同名 Secret；workflow 已经声明 `environment: production`，读取方式不变。这是本次 review 已修复项。

**结论**：已修复（2026-11-23）：`gh secret set PROVISION_SSH_KEY --env production` 并删除 repo Secret；文档同步为 Environment Secret。

### 讨论点 2：production 环境没有 required reviewers

**位置**：`.github/workflows/provision.yml:32`、`docs/deployment.md:33`

**现象**：`production` 环境目前没有任何 protection rule；`environment: production` 只是命名空间，人工审批取决于仓库设置。

**问题**：root 密钥的使用没有第二个人批准，只有“手动 workflow_dispatch”这一层操作门槛。

**预判**：建议 repo owner 在 Settings → Environments → production 配置 required reviewers；这也会影响 Deploy，属于运维策略，代码侧不能替 owner 决定。若只想约束 Provision，可以另建 `provisioning` 环境，但这会偏离 #553 的“production 审批”表述。

**结论**：（留空，待 owner 拍板）

### 讨论点 3：actionlint 未进入本地/CI 检查

**位置**：`.github/workflows/provision.yml` 全文

**现象**：本次用 Ruby YAML 解析 + 提取所有 `run:` block 做 `bash -n`，但没有 actionlint；CI 也没有 actionlint 或 deploy-contract job。

**问题**：表达式/上下文错误（例如 `secrets` 作用域、`if` 语法）只能靠人工与后续运行发现。

**预判**：#552 已计划把 provisioning 契约接入 PR CI（clean-host 负例/正例 + release 顺序断言）；actionlint 可以作为 #552 的一部分，避免在本 PR 扩 CI 面。

**结论**：（留空，归 #552）

### 讨论点 4：AppArmor profile 只覆盖 Ubuntu 24.04+ 的 abi 4.0

**位置**：`deploy/provision-bubblewrap.sh:81-104`

**现象**：profile 使用 `abi <abi/4.0>`；只在 `kernel.apparmor_restrict_unprivileged_userns=1` 时安装。Ubuntu 22.04 没有该 sysctl，不触发。

**问题**：如果未来某发行版启用 userns 限制但 AppArmor 仍是 3.x，`apparmor_parser -r` 会失败，脚本输出 `ATTRIBUTION_BWRAP_UNUSABLE`。

**预判**：当前生产与新机基线是 Ubuntu 24.04；失败会 fail-closed 并给出错误码，不会静默通过。等出现 22.04/3.x 的同类限制再补 abi 兼容，不在本 PR 猜测。

## §9 文件级代码分析

### `deploy/provision-bubblewrap.sh`（A）

职责：在 Linux 主机上幂等安装并验证 `bubblewrap`，输出稳定错误码，供 Provision workflow 与人工排障共用。新增文件，无前身。

关键依赖：`bwrap`（bubblewrap 包提供的沙箱二进制）、`runuser`（util-linux，用于切换到 `harness` 服务账号）、`apparmor_parser`（Ubuntu AppArmor 用户态工具，仅 24.04+ 需要）。三者都是系统工具，不引入 Python/Node 依赖。

变更代码块（节选）：

```bash
# 旧：Deploy 直接 fail，人工 SSH 装包
# 新：install 模式按需安装，check 模式只读
verify_bubblewrap() { ... }
probe_or_fix() {
  if verify_bubblewrap; then return 0; else status=$?; fi
  if [ "$status" -ne "$EXIT_BWRAP_UNUSABLE" ]; then return "$status"; fi
  if ! apparmor_userns_restricted; then return "$status"; fi
  install_apparmor_profile
  verify_bubblewrap
}
```

实现思路：把“缺包”“不可用”“服务账号缺失”“apt 失败”分成不同退出码；所有验证走同一函数，安装后不重复 apt；只在 AppArmor 限制命中时写 profile。检视发现：`--check` 需要 root 是本实现的取舍（见 §6），无代码缺陷。

### `.github/workflows/provision.yml`（A）

职责：唯一的 Provision 手动入口。关键依赖：`actions/checkout@v6`、OpenSSH client、`ssh-keyscan`、`GITHUB_STEP_SUMMARY`。

变更代码块：

```yaml
environment: production
...
if [ "${GITHUB_REF}" != "refs/heads/main" ]; then exit 1; fi
ssh ... "bash -s -- --$MODE" < deploy/provision-bubblewrap.sh
```

实现思路：只从 main 触发，避免用未合并脚本以 root 执行；脚本经 stdin 传输，不在主机落盘；把脚本的机器可读行解析成 summary，并把 SSH 失败单独映射为 `PROVISION_SSH_FAILED`。检视发现：actionlint 未跑（§6 讨论点 3），无代码缺陷。

### `.github/workflows/deploy.yml`（M）

职责：release 失败后的可观测性。前身是单条 SSH 调用；新实现用 `tee` 保留日志，并用 `if: failure() && steps.release.outcome == 'failure'` 追加 summary。实现思路：不改变 release 的退出码；只在归因错误码出现时给 Provision/runbook 链接。检视发现：无。

### `deploy/release.sh`（M）

职责：preflight 失败文案。前身只说“检查上方错误码”；新文案把 `ATTRIBUTION_BWRAP_MISSING` / `UNUSABLE` 映射到 Provision 与 `docs/deployment.md`。实现思路：只改错误提示，不改变 preflight 顺序。检视发现：无。

### `deploy/cloud-init.yaml`（A）

职责：新机创建阶段安装 `bubblewrap`。关键点：`package_update: true` 让新机第一次启动就拉包；`bootstrap-server.sh` 仍是基础包清单 source of truth。检视发现：无（重复包名一致性由 #552 做契约）。
