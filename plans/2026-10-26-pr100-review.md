## §1 一页速览

一句话：这个 PR 给尚不存在的上游轨迹服务定义了一张可验证的“取件单”，并让管理员可以按 session 或日期窗口取件，把原始 JSONL 放入现有 payload 邮箱，再交给既有归一化流水线。

生活化比喻：`HttpTrajectorySource` 像快递站的分拣员。它会核对运单版本、遇到限流/临时故障重试、把某一件坏包裹单独贴问题单而不丢掉整车货物；`UpstreamPullService` 则是仓管，只把签收的原始包裹放进唯一仓库，再通知既有流水线拆包。

| 交付块 | 结论 |
|---|---|
| 响应契约与 canonical schema | 主体完整；运行时别名/类型宽度与 schema 不完全等价 |
| HTTP 版本、重试、分页、逐会话隔离 | 正确；配置与响应头均限制主版本 `1` |
| pull API 与权限 | 正确：admin-only，selector 互斥，未配置稳定 409 |
| package → payload 映射 | 主/子身份、原始行、hash、line count、`http_api` 正确 |
| 幂等与运行态保护 | 连续 pull 零 payload 变化，保留 processed 字段 |
| UI 原型 | 无前端 diff；当前亮色 `Harness Evolution` 壳未回归 |

## §2 架构导览

### 2.1 两个契约面

inbound API 仍以 FastAPI OpenAPI 为事实源，`POST /api/acquisition/pull` 由 `apps/api/app/api/acquisition.py:173-200` 暴露。上游响应不属于本地 inbound API，因此单独定义在 `trajectory/models.py:12-132`，并由 `export_upstream_contract.py:84-137` 导出 JSON Schema。

这避免了前端生成器把不存在的上游路由混入本地契约，代价是现在有两个独立校验层：Pydantic 负责运行时，Ajv/Schema 负责给未来上游做语言无关约束。两层若不保持等价，就会出现本检视的 D1/D2。

### 2.2 HTTP source

`HttpTrajectorySource` 在 `http.py:30-47` 绑定注入的 `httpx.AsyncClient`。`fetch()` 在 `http.py:49-55` 校验请求 id 与响应 `sessionId` 一致；`list_window()` 在 `http.py:57-96` 跟随 cursor；`fetch_many()` 在 `http.py:98-127` 把普通逐会话失败转成脱敏 issue，但把版本不兼容提升为整批失败。

`_get_json()` 在 `http.py:133-173` 完成版本头、重复 JSON key、gzip/decoding、429/5xx/超时重试。版本通过后才解析 JSON，保证大的原始 body 不会在协议不兼容时进入后续写库。

### 2.3 Pull pipeline

`UpstreamPullService.handle()` 在 `upstream_pull.py:94-179` 执行：

```text
selector → list_window? → fetch_many → package_to_payloads
         → trajectory_payloads/source_records → root replay → sync errors
```

`package_to_payloads()` 在 `upstream.py:13-62` 把 main 映射为 root session id、child 保留 `agentId`，并将 lines 用 LF 拼回 raw JSONL。`write_local_payloads()` 在 `local_sessions.py:36-136` 复用唯一 payload 表和稳定键 upsert。

### 2.4 API、组合根与 UI

`acquisition.py:184-200` 只做管理员 pull 的 HTTP 编排；auth middleware 在 `middleware/auth.py:19,51-60` 对 pull 做 admin 强制。`main.py:61-78` 只在 URL 与 token 同时存在时创建 HTTP source，并把同一 pull handler 注册进 `JobRunner`。

本 PR 没有 `apps/web/**` 或原型文件 diff。真实 Chrome E2E 仍验证 56px 亮色顶栏、三入口、390px 和 console；因此 UI 原型范围为 `ALIGNED FOR IMPLEMENTED SCOPE`，不是跳过 UI 验证。

## §3 数据流走查

### 场景 A：管理员按 session 拉取

1. `POST /api/acquisition/pull` 经中央 admin 中间件后进入 `trigger_pull()`。
2. `PullJobPayload` 强制 `sessionIds` 与 `window` 二选一。
3. source 未配置时，`acquisition.py:186-192` 在创建 job 前返回 409 `UPSTREAM_NOT_AVAILABLE`。
4. 配置存在时创建 queued `pull` job；worker 调 `UpstreamPullService.handle()`。
5. source 对每个 session 发 GET；429/5xx/超时最多补试三次，404/4xx 按条隔离。
6. 成功 package 在写库前先做 Pydantic 校验与请求 id 对照。
7. main/child JSONL 写入唯一 payload 表，hash 和行数由内容派生。
8. 共享 replay 按 root 更新 canonical 树；上游 item issue 追加到 sync audit。

### 场景 B：窗口分页

`list_window()` 先取一页。`nextCursor` 非空则继续；重复 cursor 或超过 `max_pages` 会拒绝。空 cursor 结束。全部枚举完成后才进入 `fetch_many()`，因此枚举失败不会产生 payload 写入。

### 场景 C：版本不兼容

配置只接受 `HE_UPSTREAM_API_MAJOR=1`；成功响应若缺失、畸形或主版本不是 1，`http.py` 抛 `UPSTREAM_VERSION_INCOMPATIBLE`。`fetch_many()` 不把它降级成单条 issue，因此 pull job 在写入 payload 前失败。

### 场景 D：重复 pull

相同 package 再次进入 `write_local_payloads()`。payload 主键与 source 主键稳定；内容不变时 `inserted/updated=0`，`received_at/processed_*` 不被 fixture 或 pull 重跑清空。测试 `test_pull.py:415-467` 覆盖了该行为。

## §6 讨论点

### D1 运行时模型接受 canonical schema 拒绝的输入

**位置**：`apps/api/app/third_party_api/trajectory/models.py:15-19`、`apps/api/app/service/acquisition/upstream_pull.py:26,44`

**现象**：模型启用了 `populate_by_name=True`，所以 `session_id`、`agent_id`、`session_ids`、`problem_only` 这类 snake_case 字段会被接受；Pydantic 默认还会把字符串 `"false"` 强制转成布尔值。独立实测：

```text
TrajectoryPackage(session_id=..., agent_id=...)  → ACCEPT
TrajectoryPackage(problemFlag="false")           → ACCEPT
同一文档交给 canonical Ajv schema                 → REJECT
```

**问题**：PR 宣称运行时模型严格，实际可接受 canonical 契约之外的字段名和类型。未来 M6 的上游若误发 snake_case 或字符串布尔，客户端会悄悄修正，造成“服务看似兼容、发布契约却不兼容”的双标准。

**预判**：应在 outbound/inbound API 模型关闭 `populate_by_name`，并设置 `strict=True`；字段构造代码使用 alias。若为了内部 Python 调用需要 snake_case，应在单独的内部模型转换，不要放宽 wire contract。补 snake_case/字符串布尔拒绝测试。

**结论**：已修复（2026-10-26）。运行模型只接受 canonical camelCase aliases，并使用 `StrictBool` 拒绝字符串布尔；新增负例锁定 snake_case 与 `"false"` 均失败。

### D2 canonical JSON Schema 没有断言日期格式与区间顺序

**位置**：`packages/contracts/upstream/trajectory.schema.json:12-57`、`scripts/gates.spec.mjs:95-100`

**现象**：Schema 对时间字段只有 `"format": "date-time"`，而门禁显式设置 `validateFormats:false`。Ajv 对 `not-a-date`、无时区时间和 `endedAt < startedAt` 三种文档均返回 `valid=true`；Pydantic 对三者均拒绝。测试只验证 identity 约束，没有用 canonical schema 验证这些负例。

**问题**：canonical Schema 是给未来上游和跨语言消费者看的契约，当前它允许运行时明确拒绝的值；同时“区间有序”只存在于 Pydantic validator，没有进入机器契约描述。上游按 Schema 实现时可能通过，却被客户端拒绝。

**预判**：补 Ajv formats 断言或把日期正则写进 Schema；区间顺序若无法用标准 JSON Schema 表达，应明确标注为 runtime-only constraint，并给 Ajv 门禁增加负例测试，不能只检查关键字存在。优先保持 Schema 与运行时至少对 malformed timestamp 一致。

**结论**：已修复（2026-10-26）。Ajv 门禁启用 `date-time` 格式校验并注册 `x-time-range` 扩展；checked-in Schema 现在拒绝 malformed、无时区与倒序时间，正向 fixture 仍通过。

### D3 版本不兼容只在首次请求时报错，没有“拒绝启动”

**位置**：`apps/api/app/third_party_api/trajectory/http.py:33-47,133-182`、`apps/api/app/main.py:61-78`

**现象**：构造 `HttpTrajectorySource` 和应用 lifespan 都不做版本探测；只有调用 `fetch()`/`list_window()` 收到 200 后才校验 `X-Trajectory-Api-Version`。因此配置到主版本 2 的上游时，应用仍正常启动、status 可访问，首个 pull job 才失败。

**问题**：fullstack 05 §10.4 明确要求主版本不兼容时 `HttpApiSource` 拒绝启动并记录明确错误。当前实现把协议兼容性推迟到业务请求，运维会看到应用健康启动，却直到管理员触发拉取才知道不兼容。

**预判**：增加 bounded startup probe（可使用 05 §10 定义的探测响应/首请求缓存），或明确修订设计把版本拒绝下沉到首次业务调用；无论选哪种，都应有 startup 级测试和稳定日志 code。当前不能声称“拒绝启动”。

**结论**：已修复（2026-10-26）。新增 `HE_UPSTREAM_API_MAJOR`，配置装载只接受主版本 `1`；source 逐次仍校验响应头，其他主版本在应用启动前被拒绝。真实上游版本探测留在 M6 联调。

### D4 注入的 source 没有在 lifespan 关闭

**位置**：`apps/api/app/third_party_api/trajectory/source.py:34-35`、`apps/api/app/main.py:59-78,114-122`

**现象**：source 协议定义了 `close()`，`HttpTrajectorySource` 也实现 `aclose()`；组合根只关闭自己创建的 `upstream_client`，没有对 `resolved_source` 调 `close()`。测试注入的 `FakeSource.close()` 从未被调用。

**问题**：当前内置 HTTP source 因 client 单独关闭而不泄漏；M6 若注入自有连接池、缓存或 worker 的 `TrajectorySource`，生命周期会悬空，且接口存在却无人调用会误导实现者。

**预判**：让组合根统一管理 source 生命周期，并在 `finally` 调用 `source.close()`；若 source 拥有 client，则由 source 内部关闭，避免双重关闭。补 injected source close 断言。

**结论**：已修复（2026-10-26）。组合根在 lifespan `finally` 调用 resolved source 的 `close()`，嵌套清理保证 scheduler、jobs、source、event bus 与 database 都得到释放；注入 source 回归验证 close 被调用。

## §9 文件级代码分析

### `apps/api/app/third_party_api/trajectory/models.py`（A）

职责：把 wire JSON 收窄为不可变 Python 对象。`TrajectoryApiModel` 拒绝未知字段，`TrajectoryPackage` 对 main/child 身份做 after-validator，`TrajectoryMetadata` 检查带时区且有序的时间。

实现思路：先让 Pydantic 做字段级校验，再做跨字段身份/时间校验；这是正确的分层。问题在 `populate_by_name=True` 及默认非 strict coercion，使 wire 层比声明宽松。

检视发现：D1。

### `apps/api/app/third_party_api/trajectory/http.py`（A）

职责：真实 HTTP 协议适配器。它统一构造相对 URL、重试、版本头、JSON 重复 key 和逐会话错误隔离。

实现思路：将 HTTP 错误分为可重试的网络/429/5xx 和不可重试的 4xx/version；把无法归属整批的版本错误上抛，把单会话错误转为 issue。这是合理的边界。

检视发现：D3；启动阶段没有版本探测。

### `apps/api/app/service/acquisition/upstream.py`（A）

职责：package → `LocalAgentPayload` 的纯映射。主 Agent 使用 root id，子 Agent 保留 id，content 从 lines 按 LF 重建。

实现思路：不引入第二套 payload 表，source metadata 只用于更新时间和运行态，原始 JSONL 仍是唯一数据面。该决定 M6 可复用。

检视发现：无阻断；package metadata 除 `endedAt` 外的字段目前不进入 canonical 存储，属于已知数据边界，应在 M6 若需要 project/problemFlag 时另立迁移。

### `apps/api/app/service/acquisition/upstream_pull.py`（A）

职责：把 selector 作为 durable job payload，调度 source fetch、raw write、shared replay 和 sync issue。

实现思路：HTTP handler 只负责权限/入队；长操作完全落 JobRunner，复用 m2-05 root 原子 replay。失败项不丢弃成功项。

检视发现：D1 的 inbound alias 宽松同在 `PullJobPayload`/`PullWindow`。

### `apps/api/app/api/acquisition.py`（M）

职责：增加 admin-only pull 端点和响应契约，复用统一 ErrorResponse。

实现思路：未配置 source 时先返回 409，不创建伪 job；配置后返回 durable job id。

检视发现：无新增 API 状态机问题；真实 proxy 测试验证了 409 envelope。

### `apps/api/app/config.py`（M）

职责：新增 URL/token/timeout/retry/page 配置，URL 禁止 userinfo/query/fragment，token 使用 SecretStr。

实现思路：URL 与 token 只在同时配置时启用 source，缺一项按 unavailable 处理，避免半启动。

检视发现：配置本身无泄漏；与 D3 的启动版本探测缺失共同导致“URL 合法但版本不兼容”仍被视为可用。

### `apps/api/app/main.py`（M）

职责：装配 source、pull service 和 job handler，并在 lifespan 关闭 HTTP client。

实现思路：source 是应用级对象，pull job 与 sync 共用 JobRunner；关闭顺序在 DB 之前释放出站连接。

检视发现：D3、D4。

### `apps/api/scripts/export_upstream_contract.py`（A）

职责：将 Pydantic schema 导出为 canonical JSON Schema，并手工补齐 transcript identity/Ajv `$data` 约束。

实现思路：生成物 deterministic sort，fixture 由真实模型 round-trip 得到，保证 schema/fixture 同源。

检视发现：D2 的格式/顺序约束没有在生成后的验证测试中体现。

### `packages/contracts/upstream/trajectory.schema.json`（A）
