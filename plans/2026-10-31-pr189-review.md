## §1 一页速览

**一句话**：给每个进化对象发两张门禁卡——验证集工程卡和测试集工程卡；卡号写进对象档案，开工时再复印一份到本次运行的档案里。

**为什么现在做**：外部测试平台用两个独立工程承载验证集/测试集；配置页之前没有字段记录它们，后续评测接入没有可读的持久化来源。

**交付块**：

| 块 | 结果 |
|---|---|
| 表 | `evolution_targets` / `evolution_runs` 各加 `validation_project_id`、`test_project_id`；历史行空串 |
| API | `POST/PUT /api/evolution/targets` 要求两字段；缺失/空白/控制字符 → `422 PROJECT_ID_INVALID` + `details.field/reason` |
| 前端 | 新增/编辑浮窗两个必填输入；列表合并“测试工程”列 |
| Run | 创建 run 时从 target 快照；run API/详情/评测 gateway 不变 |
| 文档 | 05/06/08/02/09/README 更新；新增 14 章与 Agent Note |

- `web-static`、`api-static`、`unit-tests`、`db-sqlite`、`mysql`、`e2e`、`build-lane`、`docs-flow`、`flow-online`、`ci-ok` 全部成功。

## §2 架构导览

### 2.1 写入路径：模型 → 服务 → 仓储 → 表

`EvolutionTargetWrite` 现在有七个业务字段，其中两个 project ID 是**没有默认值的必填字段**（`targets.py:30-58`）。如果客户端省略字段，`_default_missing_project_ids` 会在校验前补空串（`targets.py:40-56`），让请求仍然进入服务层，最终由 `_validate_project_id` 返回字段级 `PROJECT_ID_INVALID`，而不是 Pydantic 的通用 422。这是“契约 required + 缺字段也要字段级错误”的折中。

`_validate_project_id`（`targets.py:130-143`）只做四件事：trim、非空、长度 ≤128、拒绝任何空白/控制字符；不解析前缀、不查外部平台。`_normalize_write`（`targets.py:200-225`）把结果写回模型；`_public`（`targets.py:228-240`）把仓储记录映射成响应。

仓储层只是老实多搬两列：`EvolutionTargetRecord`、`_record`、`insert`、`update`（`crud/evolution_targets.py:21-31, 60-72, 131-193`）。没有新查询、没有新索引。

### 2.2 Run 快照：复制而不是引用

`LaunchTargetRecord` 协议增加两个只读属性（`launch.py:49-55`），`LaunchService._run_values` 在创建 run 时把 target 的两个值写进 `evolution_runs`（`launch.py:203-204`）。这与 `repo_url` / `sub_dir` 的快照语义一致：之后改 target 不会改历史 run。

`EvolutionRunRecord` 在末尾加两个带默认空串的字段（`models/evolution.py:282-283`），`record_from_evolution_run` 从列里读（`models/evolution.py:447-448`），`create_run` 用 `.get(..., "")` 兼容旧调用（`crud/evolution.py:60-61`）。默认值是为了不破坏既有测试里大量 `EvolutionRunRecord(...)` 构造；生产路径始终显式传入。

### 2.3 前端：表单校验与列表展示

`TargetFormDialog.vue` 的表单模型、reset、submit、emit 都加了两个字段（`TargetFormDialog.vue:53-58, 95-99, 132-166`）。本地校验先 trim，再判空、再判空白/控制字符；`PROJECT_ID_INVALID` 这个谓词用逐字符 code point 判断（`TargetFormDialog.vue:44-49`），避免 ESLint 的 `no-control-regex`。

模板里两个 `ElFormItem` 放在子目录/基线之后、启用之前，带 `required` 星号；下面一条全宽帮助文案（`TargetFormDialog.vue:297-341`）。

`TargetTable.vue` 在“基线”和“状态”之间加一列“测试工程”（`TargetTable.vue:94, 124-146`），每个 ID 一行，空值显示“未填写”。`Index.vue` 的 `targetWrite` 复制两个字段（`Index.vue:65-75`），否则启用/停用会把已保存值清空；`PROJECT_ID_INVALID` 映射为表单底部文案（`Index.vue:123-125`）。

### 2.4 契约与错误码

`ErrorCode` 增加 `PROJECT_ID_INVALID`（`errors.py:40`）。OpenAPI 生成后 `EvolutionTargetWrite.required` 包含两个新字段（重新生成后验证过），`details` 形状由服务层保证。

## §3 数据流走查

### 3.1 新增一个对象

1. 管理员打开“新增进化对象”，表单为空，两个输入显示占位符 `val-2026-q3` / `test-2026-q3`。
2. 填写对象名、仓库、子目录、基线、两个工程 ID；点“新增配置”。
3. 本地校验：空/纯空白 → 字段下红字；含空格/控制字符 → 字段下格式错误；不满足时不发请求。
4. 请求到 API，Pydantic 接受七个字段；服务 trim 后写库；返回 201 与完整对象。
5. 列表刷新，新增行在“测试工程”列显示两行 ID。

### 3.2 编辑一个历史对象

1. 历史行两个 ID 是空串；打开编辑，两个输入为空。
2. 直接保存被本地校验拦住（“请填写…”），不会发出空值请求。
3. 补齐后保存，`PUT` 成功；列表接口返回新值。
4. 若绕过前端直接 `PUT` 空值，服务返回 422 `PROJECT_ID_INVALID`，`details.field` 指向字段。

### 3.3 启动一次 run

1. 启动向导仍只读对象/版本/模型；target 必须 enabled。
2. 创建 run 时 `_run_values` 从 target 复制两个 ID 到 `evolution_runs`。
3. 之后修改 target 的工程 ID，已创建 run 的两列不变；新 run 用新值。
4. run API、详情页与评测 gateway 本切片不读这两个字段。

### 3.4 启用/停用

1. 表格“停用”调用 `targetWrite(target)`，复制两个 ID 后 `PUT`。
2. 若 `targetWrite` 漏字段，`EvolutionTargetWrite` 的 required 会先报 422；本 PR 已复制，测试覆盖。

## §6 讨论点

### 6-1 历史 target 仍可启动 run，快照会是空串

- **位置**：`apps/api/app/service/evolution/launch.py:203-204`（快照）、`apps/api/app/service/evolution/targets.py:130-143`（只在 target 写入时校验）
- **现象**：迁移后历史 target 的两个 ID 为空串；它仍然 enabled，可以在不编辑的情况下启动 run。新 run 的两列也会是空串。
- **问题**：如果后续评测切片假设“新 run 一定有工程 ID”，会遇到空值；本切片选择“启动不额外拦截”，把补齐责任留给管理员。
- **预判**：本切片可以接受，因为需求只要求 target 配置必填；但评测切片提交前应显式拒绝空 ID，或在本切片加 `TARGET_NOT_CONFIGURED`。我倾向前者：启动不阻断，评测入口再校验，避免配置迁移期间无法启动历史对象。
- **结论**：（留空）

### 6-2 超过 128 字符走 `VALIDATION_INVALID`，不是 `PROJECT_ID_INVALID`

- **位置**：`apps/api/app/service/evolution/targets.py:38-39`（`max_length=128`）、`plans/fullstack-design/05-api-design.md` §4.11
- **现象**：129 字符在 Pydantic 层就被拒绝，返回 `VALIDATION_INVALID`；空/空白/控制字符才返回 `PROJECT_ID_INVALID`。
- **问题**：错误码语义不完全统一；issue 最初的描述把“超长”也归到 `PROJECT_ID_INVALID`。
- **预判**：保留 Pydantic 的 128 上限，避免为极端长字符串绕过请求校验；文档已改成“超长 → VALIDATION_INVALID，前端 maxlength 拦截”。若要求统一错误码，可去掉 `max_length` 让服务层判 128，但会把无界字符串带进服务。
- **结论**：（留空）

### 6-3 必填星号只加在两个新字段

- **位置**：`apps/web/src/pages/evolution/targets/components/TargetFormDialog.vue:297-341`
- **现象**：对象名称、仓库、子目录、基线其实也必填，但没有 `required` 星号；只有两个工程 ID 有。
- **问题**：视觉上会让人以为只有新字段必填。
- **预判**：这是本切片“只改需求字段”的取舍；统一给五个旧字段加星号是一次独立的 UI 一致性改动，建议后续做，避免本 PR 原型截图范围扩大。
- **结论**：（留空）

## §9 文件级代码分析

### 9.1 `apps/api/alembic/versions/0013_target_project_ids.py`（A）

- **职责**：给 target 与 run 各加两列，历史行默认空串。
- **变更形态**：新增迁移。
- **关键点**：`op.add_column` 循环两张表，`server_default=""` 同时服务 SQLite 与 MySQL；downgrade 反向删列。CI 的 SQLite/MySQL 双 lane 都验证了 head `0013`。
- **检视发现**：无。回滚会丢已填 ID，Agent Note 已写明导出提醒。

### 9.2 `apps/api/app/service/evolution/targets.py`（M）

旧代码只有六个字段，任何仓库/ref 错误统一 `REPO_INVALID`。新代码：

```python
validation_project_id: str = Field(max_length=128)
test_project_id: str = Field(max_length=128)
```

并在 `_normalize_write` 中调用 `_validate_project_id`。新增的 `_project_id_invalid` 把错误码和 `details` 收口到一个地方：

```python
return AppError(
    status_code=422,
    code=ErrorCode.PROJECT_ID_INVALID,
    message="test project id is invalid",
    details={"field": field, "reason": reason},
)
```

`_default_missing_project_ids` 是本次检视修掉的契约点：字段 required，但缺键时补空串，让服务层给出字段级错误，而不是 Pydantic 的通用 422。
