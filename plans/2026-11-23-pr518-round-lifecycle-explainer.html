1

先认识三个词：簇、轮、候选

自进化的一次运行（run）里，会先归并出若干“问题簇”，每个簇代表一类要修的问题。然后系统为每个簇安排一次“实验”，也就是一轮。

CLUSTER

簇

一组相似的问题，例如“三个 case 都是读索引时没校验字段”。它描述“要修什么”。

ROUND

轮

针对一个簇的一次完整尝试：生成候选 → 推送 → 评测 → 接受或拒绝。它描述“试一次”。

CANDIDATE

候选

这一轮真正提交的代码改动，带独立分支与 commit。它描述“这次改了什么”。

关键关系

今天的代码假设：一个簇 = 一轮 = 一个候选。候选被拒绝，这个簇就结束，接着处理下一个簇。

2

今天一轮的完整流水

准备阶段结束后，run 进入“迭代”阶段。下面的每一步都是代码里真实存在的状态，不是示意。

1

prepare 阶段一次性建好全部轮

prepare._build_rounds 为每个簇插入一行 pending 轮，并校验“轮数 == 簇数”。

2

advance 取下一个 pending 轮

生成候选改动，提交到候选分支，然后推送。

3

提交外部评测

把候选 commit 交给评测平台，轮进入 evaluating，随后轮询结果。

4

apply 做决定

评测为 accept → 把候选合入 run 分支；reject → 删除候选并把这轮标成 rejected。

5

所有轮都结束后 finalize

只要每一轮都是 accepted / rejected / skipped，就写终评、发布 run 分支、把 run 标成 completed。

注意第 4 步

reject 不是“这一轮失败，重来”，而是“这个簇的尝试到此为止”。代码里没有“再来一轮”的动作，只有“标记结束”。

3

issue #488 要求的“拒绝后重试”

#488 希望的不是“把被拒绝的候选再评一次”，而是：同一个簇被拒绝后，保留同一个 agent 会话， 把“差了多少分、为什么失败、上一版编辑为什么被拒”喂回去，让模型改一版，再走一轮完整评测。

今天的 reject

候选 X 被拒 → 本轮 rejected → 换下一个簇。
同一个簇不会再有第二次机会。

→

#488 想要的 reject

候选 X 被拒 → 新建同簇第 2 轮 → --resume 同一会话 + 拒绝缓冲 → 候选 Y → 再评测。

“会话”和“拒绝缓冲”其实已经做完了

PR #518 已经让 patch source 能接收上一轮的分差、失败原因、上一版编辑清单，并把它们交给 --resume。缺的不是“怎么说”，而是“谁来开第二轮、第二轮怎么计数、怎么收尾”。

4

为什么不能只改 agent 代码？五处会一起卡住

现在整套系统是按“每簇恰好一轮”这个前提写的。要加第二轮，就像给一台按固定齿数设计的钟表加一个齿轮： 只换一根指针没用，后面的传动比、刻度盘、归零机构都要跟着改。

卡点 1 轮的数量是写死的

prepare 阶段一次性为每个簇插一行 pending 轮，并明确要求轮数等于簇数。

位置：prepare.py:709 _build_rounds

硬改会怎样：多出来的轮没有地方创建；如果预先生成，接受后又会留下永远 pending 的空轮。

卡点 2 进度条按“簇数”算

总进度 = 准备 5 格 + 簇数 + 终评 1 格；每接受/拒绝一轮，进度游标 +1。

位置：state.py:71 total_units、runs.py:298 validate_cursor

硬改会怎样：多试一轮，游标就会超过总数，打开运行详情直接报错，而不是只多一格。

卡点 3 中途不能插轮

插入轮的仓库方法要求 run 仍在“准备完成”阶段；评测时 run 早已进入迭代。

位置：db/crud/evolution.py:969 _require_run_stage(expected=5)

硬改会怎样：reject 时想插第二轮会被阶段校验拒绝；绕过校验就等于让状态机失去一致性保护。

卡点 4 没有“跳过空轮”的动作

如果某簇第一轮就接受了，预生成的第二轮必须被标成 skipped；但现有“skip”方法只服务推送被跳过的场景，还会改 run 的推送状态。

位置：db/crud/evolution.py:1235 mark_round_and_run_push_skipped

硬改会怎样：要么空轮永远不结束、finalize 永远等下去；要么误改 run 的推送状态。

卡点 5 终评和界面都按“轮=簇”展示

finalize 等待所有轮终止；迭代页按轮渲染；最终指标按轮聚合。多出来的重试轮会改变这些列表的长度和含义。

位置：apply_final.py:211、stages.py:282 StepRound

硬改会怎样：同一簇出现多行、指标重复计数、进度文案“第 X/M 轮”对不上。

已就绪 agent 侧的“重试能力”

会话 id、分差反馈、拒绝缓冲、--resume、候选多文件、审计事件都已在 PR #518 完成，并有真实 git 的端到端测试。

位置：patch_source.py:436、git_candidate.py:723

结论：缺的只是“调度器”，不是模型能力。
用一句话总结这五处卡点

“轮”在这个系统里不只是一个笼统的概念，它是数据库里的一行、进度条上的一格、界面里的一张卡片、终评里的一个数据点。 增加一种轮，就必须同时定义：什么时候创建、算不算进度、不跑时怎么结束、界面怎么显示、终评怎么聚合。

5

“扩到 round 生命周期”具体要改什么

生命周期（lifecycle）指一轮从“创建”到“结束”的全过程。扩它，意味着把“每簇一轮”改成“每簇最多 N 轮”，并让下面这些层同时理解新规则。

层现在要变成
创建 prepare 一次建满，且轮数必须等于簇数 允许在 reject 后为同簇追加一轮；接受后把剩余重试轮标成 skipped
计数 每轮接受/拒绝都推进度 +1；总数按簇数算 进度按“簇的最终结果”推进；重试轮不重复占格，详情页不越界
调度 advance 取下一个 pending 轮（天然是下一个簇） 同簇优先取重试轮；到达上限后终止该簇
收尾 所有轮终止即可 finalize 等待重试轮；跳过空轮；最终指标不重复计数
界面 一轮一张卡，文案“第 X/M 轮” 同簇多轮的分组/标记，进度与轮数解耦
数据 round 表够用，但缺“追加/跳过”操作 新增追加与跳过方法（或等价的状态迁移），并补迁移/测试

所以“扩 scope”扩的是这些目录

当前 #488 的 scope 只覆盖 apps/api/app/service/evolution/**、 third_party_api/ai_agent/**、测试与 .agents/**； 要动 apps/api/app/db/crud/**、进度状态语义与前端 apps/web/**， 必须先把这些写进 issue 的 scope，否则流程门禁会判定改动越界。

6

两个选项：现在扩，还是拆出去

两条路都能把 #488 收好，区别是“这一 PR 的体量/等待时间”和“后续 issue 的独立性”。

A. 授权扩 scope，在本 PR 继续做完

适合“希望 #488 一次闭环、愿意让 PR 变大”的情况。

  • 得到拒绝后自动重试、轮次上限、完整验收项一次到位。
  • 得到source 级能力与调度器在同一 PR 联调，回归面集中。
  • 代价要动 db/crud、进度游标、前端轮次展示，PR 约再增数百行与迁移/界面测试。
  • 代价CI 与检视轮次变长；需要重新做一轮完整回归。

B. 拆成 follow-up issue，本轮先收 #488 的 source 能力

适合“先把可复用的能力落地，调度器单独设计”的情况。

  • 得到PR #518 现在可检视、可合入；agent-edit 模式已能产出真实多文件候选。
  • 得到调度器有独立 issue 承载，能单独讨论 N 轮上限、进度和界面语义。
  • 代价#488 的“reject 后下一轮”验收项暂不满足，需要明确降级或改写。
  • 代价source 级 resume 能力要等后续 issue 才在生产路径可达。

我的建议（供拍板，不是替你决定）

如果 #488 的验收必须包含“自动下一轮”，选 A，并把 scope 明确写成 apps/api/app/db/crud/**、apps/api/app/service/evolution/**、 apps/web/**、测试与流程文件；如果更看重尽快合入已验证的补丁能力，选 B， 另开一个“round 重试调度器”issue，验收单独定义。

两个常见疑问

不能“预先生成第二轮”吗？

能预生成，但第一轮一旦接受，第二轮就必须被标成 skipped；当前没有这个安全的跳过动作， 而且预生成的轮会改变“轮数 == 簇数”的现有校验。结果是要么卡住终评，要么误改进度。

不能只让 reject 之后再“假装没发生过”吗？

那等于把已评测的轮重置回 pending，需要清空候选、评测结果和进度增量；这同样是修改轮的生命周期， 只是把“新增一轮”换成了“重置一轮”，复杂度并没有消失。
