## §1 一页速览

一句话：把评测的「提交即计时」改成「平台真正 running 才计时」，并让验证集与测试集、排队与执行各用各的预算。

比喻：以前只有一个沙漏，从你**把评测递进窗口**那一刻开始漏，排队、叫号、真正办事都算你的时间；现在有两个沙漏——「叫号沙漏」从递材料开始算，只负责防止永远排不上，「办事沙漏」等窗口叫到号（平台 `started_at`）才开始漏；测试集业务更重，给它一个更大的办事沙漏。

## §2 架构导览

### 2.1 网关协议层：把平台的「执行起点」带上来

`EvalStatus` 是 HE 与所有评测平台之间的稳定模型（`contracts.py:215`）。新增的两个字段都有默认 `None`，因此旧网关实现、测试里 `EvalStatus(status="completed")` 的相等断言、以及未升级的平台响应都不受影响。

`ai_eval_platform.py:99` 先做原有的 11 态映射，再把 `started_at` 与 `progress.percent` 一次解析出来，供所有返回分支复用。`_started_at`（`:265`）只在字符串、ISO-8601 可解析且带时区时返回 `datetime`；缺失、格式错误、naive 时间都返回 `None`，由 poller 回退到提交时刻。这与 issue 的「解析失败字段为 None，不改变状态判定」一致。

`fake.py:46` 把 `startedAt` / `progressPercent` 作为测试可配置项暴露；测试可以用它构造「先 queued、再 running」的时间线，而不必起真实平台。非法配置会显式抛 `EvalGatewayError`（`fake.py:117`），避免测试悄悄退化成旧行为。

### 2.2 轮询层：两条时钟 + 一条 kind 分流

`EvolutionEvalPoller` 构造参数新增 `test_timeout` 与 `queue_timeout`（`eval_poller.py:394`）。默认值与 issue 一致：候选 2h、测试集 6h、排队 6h。

轮次候选的 `_expire_if_due`（`:958`）和执行级评测的 `_expire_run_if_due`（`:808`）结构相同：

1. 重新读取持久化行，拿最新的 `eval_started_at` 与 `eval_paused_seconds`（`:816`、`:966`）。
2. 用 `_timing_fields` 计算可观测时间（`:1166`）：
   - `queueSeconds`：`queued` 时从提交算到「现在」；`running` 时从提交算到平台 `started_at`；平台 running 但没给起点时保持 `None`，不猜。
   - `elapsedSeconds`：有 `started_at` 从它算到「现在」；没有则由 running 回退到提交时刻；queued 时为 `None`。
   - 两者都减去 `eval_paused_seconds`，并夹到非负。
3. 先查排队上限（`:826`、`:976`），再按状态分流：`queued` 到此为止，不再看执行预算（`:838`、`:988`）；否则取 `started_at`（缺失回退提交时刻）算执行时长，按 `_execution_budget(kind)` 比较（`:862`）。
4. 超时后走原有的 `_fail` / `_fail_run_evaluation`，把 timing 合并进 `eval_timeout` 事件 payload，并照旧把 run 置 `blocked(stage=eval)`。

这样，排队 100 分钟、执行 20 分钟的候选在旧实现里会在提交 120 分钟时被误杀；新实现只在执行满 2 小时后超时。测试 `:329` 正是这个对照。

### 2.3 事件层：让运维不用再对时间线

`eval_polled` 与 `eval_timeout` 的 payload 现在带 `kind`、`startedAt`、`elapsedSeconds`、`queueSeconds`、`progressPercent`（`eval_poller.py:621`、`:739`、`:680`、`:796`）。排队超时用 `evaluation queue timed out`、执行超时仍用 `evaluation timed out`，配合 `startedAt` 是否为 `null` 就能区分卡在哪个阶段。

## §3 数据流走查

生产场景：测试集基线先被误杀，候选评测排队 100 分钟后刚开始执行。

1. 提交评测：`EvolutionEvalSubmitter` 在提交时刻写 `eval_started_at`（既有行为，本 PR 不改）。此时排队沙漏开始。
2. 第一次轮询：平台返回 `queued`，`get_status` 解析出 `progress.percent`，但没有 `started_at`。`_expire_*` 只比较排队时长；未到 6h 就继续等，`eval_polled` 记录 `startedAt=null`、`queueSeconds≈6000`、`elapsedSeconds=null`。
3. 平台开始执行：下一次轮询返回 `running` 且带 `started_at`。执行沙漏从 `started_at` 起算；排队沙漏冻结在 `started_at - eval_started_at`。若排队已超过 6h，会在这一步以排队超时结束（防止平台偷偷跳过排队上限）。
4. 执行中：每 5 分钟同样记录 `elapsedSeconds` 与 `progressPercent`；测试集基线用 6h 预算，验证集基线与候选仍用 2h。
5. 超时：执行时长达到对应预算，记 `eval_timeout`，payload 同时带排队与执行时长，run 进入 `blocked(stage=eval)`，等待 `/retry`。
6. 旧平台：状态响应没有 `started_at`，执行起点回退到 `eval_started_at`，行为与变更前一致；事件里 `startedAt=null`，可据此判断是平台没报还是真的没开始。

## §6 讨论点

### 讨论点 1：`queueSeconds` 在「平台说 running 但没给 started_at」时保持 `null`

- **位置**：`apps/api/app/service/evolution/eval_poller.py:1166`
- **现象**：此时执行时长回退到提交时刻，但排队时长不猜，事件里 `queueSeconds=null`。
- **问题**：运维修看事件时，无法区分「平台没报起点」和「真的 0 秒排队」。
- **预判**：`startedAt=null` 已经表达「平台没报起点」，`queueSeconds=null` 与之一致；若用当前时间减提交时间填充，会把执行时间伪装成排队时间，反而误导。建议保持现状。
- **结论**：（留空）

### 讨论点 2：暂停发生 execution 开始前时，`eval_paused_seconds` 会被执行预算一并扣除

- **位置**：`apps/api/app/service/evolution/eval_poller.py:845`、`:995`
- **现象**：暂停时长是累计值，没有记录暂停发生的阶段；执行预算减去全部暂停时长。
- **问题**：极端情况下（先暂停 3 小时、再开始执行）执行预算会多出 3 小时，即「少算执行时间」。
- **预判**：只会放宽、不会提前误杀，与 issue 的「不误超时」目标同向；要精确需要按阶段记暂停，属于新事实源，超出本 issue。Agent Note 已把该欠账写明。
- **结论**：（留空）

### 讨论点 3：测试集 6 小时是保守首版值

- **位置**：`apps/api/app/config.py:168`
- **现象**：`HE_EVAL_TEST_TIMEOUT_SECONDS=21600` 与排队上限同为 6h。
- **问题**：如果真实平台吞吐更慢，测试集终评仍可能在 6h 处超时；如果吞吐更快，6h 又偏宽。
- **预判**：issue 明确要求「首版保守值，可按实际平台吞吐调整」，且 env 可覆盖；等生产复验拿到真实 duration 再定值。建议本 PR 不调。
- **结论**：（留空）

## §9 文件级代码分析

### 9.1 `apps/api/app/service/evolution/engine/contracts.py`

职责：定义引擎与网关共享的冻结值对象。变更形态：M（只动 `EvalStatus`）。

旧代码只有 `status` + `message`；新代码追加两个带默认值的可选字段。写法上刻意为「加字段不破坏构造与相等」：所有旧调用点、`EvalStatus(status="completed")` 断言、以及第三方实现都不需要改。`started_at` 的 None 语义写在 docstring 里，调用方（poller）必须回退，而不是把 None 当成「现在」。

### 9.2 `apps/api/app/third_party_api/eval_gateway/ai_eval_platform.py`

职责：把平台 HTTP 协议翻译成 HE 的稳定模型。变更形态：M。

旧 `get_status` 在每个分支里直接 `return EvalStatus(...)`，只有 `partial` 分支读 `progress`。新代码把 `started_at`/`percent` 提到分支之前，所有返回都带上；状态判定顺序完全没动。`_started_at` 是纯函数：空、非字符串、解析失败、naive 时间都返回 `None`，不会把坏数据变成 1970 或本地时区猜测。

### 9.3 `apps/api/app/third_party_api/eval_gateway/fake.py`

职责：离线与测试用的确定性网关。变更形态：M。

`get_status` 从冻结配置读 `startedAt`/`progressPercent`。与真实网关不同，fake 对坏配置**显式报错**，因为测试配置写错时静默回退会让用例假绿。解析逻辑与真实网关同构，但去掉了「非法值容忍」，这是有意的差异。

### 9.4 `apps/api/app/service/evolution/eval_poller.py`

职责：durable 轮询外部评测、推进 run。变更形态：M（核心）。

- 构造：新增 `test_timeout`/`queue_timeout` 与正值校验（`:394`）。
- `_poll_round` / `_poll_run_evaluation`：把本次 `status` 传给 `_expire_*`，并在 `eval_polled` 里合并 timing（`:621`、`:739`）；平台直接返回 failed/timeout 时也把 timing 带进事件（`:680`、`:796`）。
- `_expire_if_due` / `_expire_run_if_due`：双时钟与 kind 分档（`:808`、`:958`）。
- `_fail` / `_fail_run_evaluation`：新增可选 `timing`，只影响事件 payload，不改终态写入（`:899`、`:1049`）。
- `_timing_fields` / `_elapsed_seconds`：纯函数，集中定义字段语义，避免两个 `_expire_*` 漂移（`:1166`、`:1203`）。

实现思路总结：先算「可观测时间」，再用同一个 timing 既做判定又做事件；判定顺序固定为排队 → 状态 → 执行，保证 queued 永远不消耗执行预算。

检视发现：无功能缺陷。已知取舍是暂停累计值与事件字段体积，均已在 Note/PR 描述登记。

### 9.5 `apps/api/app/config.py` / `apps/api/app/main.py`

职责：配置与组合根。变更形态：M。

两个 `Field(default=21_600, gt=0)` 与既有 `eval_timeout_seconds` 同风格；`main.py` 把三项都换算成 `timedelta` 注入。缺省值让旧部署无需改 env 即可启动。
