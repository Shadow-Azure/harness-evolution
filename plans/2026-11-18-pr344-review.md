## §1 一页速览

**一句话：** 总览的「触发点」列不再拿上报时间冒充触发位置；它读一列显式、可空的日志行，有就显示 `L<n>`，没有就诚实显示「—」，并与错误详情执行流用同一套行号坐标。

**比喻：** 旧实现像把快递单上的「寄出日期」当成「货架号」贴在包裹上——看起来有信息，去找货时却永远对不上。新实现是在包裹上写真正的货架号；没有货架号的包裹就空着，不拿日期糊弄。

## §2 架构导览

### 2.1 存储与契约层

`bad_cases` 是外部写入、本服务按主键维护的问题表。新增列只做一件事：保存上报方显式给出的触发日志行。模型声明在 `domain.py:310`，外部契约同步声明为 `nullable integer`（`external_contract.py:108`），所以 m12-02 的契约巡检能发现“读路径期望但库中没有”的漂移，而不是等到查询 500。

迁移 `0022` 的设计点是**对已存在的列幂等**：`_existing_columns()` 先反射 `bad_cases`，列不存在才 `batch_op.add_column`（`0022:42-45`）。这既覆盖“本服务自己迁移出来的库”，也覆盖“外部管理、已经手工加过列”的部署；回滚只在列仍在时删除（`0022:50-53`）。历史行不写默认值，`NULL` 保留“不知道”的语义。

### 2.2 写路径：上报与目录同步

`BadCaseIngest` 增加 `triggerLine?: number`（`ingest.py:75-82`），Pydantic 的 `ge=0` 把负数挡在 422。`_row` 把它送进 `BadCaseIngestRow`（`ingest.py:190`），仓储的 `_UPSTREAM_COLUMNS` 与 `_values` 再落到 `trigger_line`（`bad_case_ingest.py:31,107`）。关键点是**只接受显式字段**：`metaData.line` 仍原样存进 `meta_data`，不会被提升为触发行。测试 `test_ingest_api.py` 的第一个用例专门断言：上报体带 `metaData.line=91` 时，`trigger_line` 仍是 `NULL`。

目录同步走同一条列语义：上游 `BadCaseItem.trigger_line` 可选（`models.py:23`），服务映射到 `CatalogCaseRow`，仓储的 `_UPDATE_COLUMNS` 与 `_values` 包含该列。目录同步默认停用；启用时它按 `bad_case_id` 覆盖上游字段，语义与其它上游列一致。

### 2.3 读路径：总览 repository → service → DTO

`page_cases` 在原有 `select` 里多取一列（`overview.py:391`），row dataclass 多一个 `trigger_line: int | None`（`overview.py:77`），构造时显式做 `int(...)` 或 `None`（`overview.py:448-450`）。这条路径没有新增 join、没有按行查 Session，也没有回退到 `created_at`。

`_item` 把 `row.trigger_line` 原样传给 DTO（`service.py:139`）。`BadCaseListItem.trigger_line` 是必填但可空字段（`schemas.py:131-139`），描述明确写出：它是 root Session 触发点的 1-based 日志行，与执行流 `SessionEvent.line` 同一坐标，不从 `createdAt` 或事件下标推导。`triggerAt` 保留在 DTO 中，描述仍说明它临时等于 `createdAt`，但不再作为「触发点」列的值。

### 2.4 前端：列标题、格式与可访问说明

`BadCaseTable.vue` 把表头从「触发时间」改为「触发点」（`:243`），单元格从 `formatStartedAt(item.triggerAt)` 改为一个带 `aria-label`/`title` 的 span（`:294-301`）。两个纯函数分别负责显示值和说明：`triggerLineLabel`（`:111-115`）对 `null`/`undefined` 返回「—」，否则 `L${n}`；`triggerLineDescription`（`:122-126`）分别给出「该 bad case 没有可用的触发行号」或「触发点：日志行 L<n>」。`undefined` 分支是为旧 API 响应保留的兼容：字段缺失时不会渲染 `Lundefined`。

### 2.5 测试与证据

- API：`test_overview_api.py` 新增整数 58 与 NULL 两行，并保留 `triggerAt == createdAt` 兼容断言。
- 契约：`test_openapi.py` 把 `triggerLine` 加入字段集合，断言 `anyOf integer(min 0)/null` 与描述包含 `log line`、`createdAt`。

- 前端：`BadCaseTable.test.ts` 覆盖 `L0`、`L58`、`null`、`undefined`，并断言表头没有「触发时间」。

## §3 数据流走查

场景：上报一条 `self + skill` 的 bad case，触发点在 root Session 的 L2。

1. 上报方 POST `{ "badCaseId": "...", "triggerLine": 2, ... }`；`BadCaseIngest` 校验非负，`BadCaseIngestRepository.ingest` 把 `trigger_line=2` 写入 `bad_cases`。
2. 总览请求 `GET /api/workspaces/{wid}/bad-cases`；`OverviewRepository.page_cases` 在同一条分页 SQL 里取 `trigger_line`，再批量补 `bad_case_root_sync` 与 `session_families` 存在性（原逻辑），最后组装 `BadCasePageRow(trigger_line=2)`。
3. `OverviewService` 的 `_item` 把 `trigger_line=2` 放进 `BadCaseListItem.triggerLine`；`triggerAt` 仍是 `createdAt`，但 UI 不再用它。
4. 浏览器渲染 `BadCaseTable`：`L2`，`aria-label="触发点：日志行 L2"`。
5. 点击 ID 深链到 `/workspaces/{wid}/sessions/{sid}/errors?case=...&tab=desc`；Session tree 返回 `badCases[].anchor={agentId,eventIndex}`。
6. lane DAG 按 anchor 取 `events[eventIndex].line`，显示 `触发点 L2`；E2E 断言它与总览的 `L2` 相等。
7. 若 `trigger_line` 为 NULL：总览显示「—」；详情仍按 anchor 定位（若 anchor 可解析），不回填、不猜测。

## §6 讨论点

### D1. `triggerLine` 与详情 anchor 是两个证据源

- **位置**：`apps/api/app/service/overview/service.py:139`；`apps/api/app/service/sessions/service.py:282`。
- **现象**：总览读 `bad_cases.trigger_line`，详情按 `bad_cases.bad_case_agent_id + object_name/type` 解析 anchor，再由前端取 anchor 事件的 `line`。两条路径在正常数据上相等，但读取层不做交叉校验。
- **问题**：若上报方给出的 `trigger_line` 与 Session 事件行不一致，总览显示上报值、详情高亮另一行。issue 要求“同一触发行号来源”，当前实现把一致性责任放在写入方。
- **预判**：写入方本来就知道真实行号；读取层若为了“纠正”而重算 anchor，会把总览变成每行一次 Session 事件查询（N+1），且违背 issue 的“从 `bad_cases.trigger_line` 或等价既有列稳定投影”。E2E 用真实 anchor 数据证明预期契约；Agent Note 已写明限制。
- **结论**：留空给维护者拍板——接受“写入方保证一致 + E2E 证明”，还是另开切片做写入时校验/回填。

### D2. 1-based 坐标与原型 `L0` 的差异

- **位置**：`apps/api/app/service/overview/schemas.py:131-139`；`apps/web/src/pages/overview/components/BadCaseTable.vue:111-115`。
- **现象**：契约允许 `0`（`ge=0`），原型截图有 `L0`；执行流 `SessionEvent.line` 是 1-based（`schemas.py` 的 `line: int = Field(ge=1)`），解析器 `enumerate(..., start=1)`。
- **问题**：如果写入方把原型里的 0-based 下标直接当 `triggerLine`，总览会显示 `L0`，详情 anchor 却可能是 `L1`，差一行。
- **预判**：生产解析坐标是 1-based；`triggerLine` 应使用同一坐标。契约保留 0 只为原型/历史展示，不把 0-based 当规范。
- **结论**：留空给维护者拍板——是否把 `ge=0` 收紧为 `ge=1`，或保留 0 作为原型兼容值。

### D3. 目录同步可能覆盖已上报的 `trigger_line`

- **位置**：`apps/api/app/db/crud/bad_case_catalog_sync.py:24-37`（`_UPDATE_COLUMNS`）、`:97-113`（`_values`）。
- **现象**：目录同步按 `bad_case_id` upsert 并更新 `_UPDATE_COLUMNS`；上游 `trigger_line` 缺失时值为 `None`，会把已有行写成 NULL。
- **问题**：同一 case 先经上报写入 `trigger_line`，后经目录同步（若启用且上游不含该字段）会被清空。
- **预判**：目录同步默认停用，主通道是上报接口；上游契约现在也声明了可选 `trigger_line`。若未来重新启用目录同步，应明确“上游缺字段是否等于清空”。
- **结论**：留空给维护者拍板——保持 upsert 全字段覆盖，还是把 `trigger_line` 移出更新列、只在插入时写。

### D4. `triggerAt` 继续留在契约里的兼容成本

- **位置**：`apps/api/app/service/overview/schemas.py:125-130`；`05 §3.10`。
- **现象**：DTO 继续返回 `triggerAt == createdAt`，只是前端不再展示。
- **问题**：新调用方仍可能误用 `triggerAt` 当触发时间或排序键；字段描述和设计文档都写了“临时相等”，但 API 没有弃用标记。
- **预判**：issue 明确要求保留兼容；在真实触发时间事件落地前移除字段会破坏旧客户端。当前用文档和 `triggerLine` 的单一来源降低误用。
- **结论**：留空给维护者拍板——是否在 OpenAPI 标 `deprecated`，或等后续真实时间事件再单独立项。

## §9 文件级代码分析

### 9.1 `apps/api/alembic/versions/0022_bad_case_trigger_line.py`（A）

**职责：** 给 `bad_cases` 加一个可空整数列，并在回滚时删除；对已存在列幂等。

**关键依赖：** Alembic 的 `batch_alter_table` 在 SQLite 上走“建新表/搬数据/换名”，在 MySQL 上走普通 `ALTER TABLE`；本仓库用它处理跨方言列变更已有先例（0010、0018）。

旧代码：无（新迁移）。新代码：

```python
if not _has_bad_cases() or "trigger_line" in _existing_columns():
    return
with op.batch_alter_table("bad_cases") as batch_op:
    batch_op.add_column(sa.Column("trigger_line", sa.Integer(), nullable=True))
```

这段先反射列名，再决定是否加列。好处是外部管理或已手工加列的库不会因重复列失败；代价是多一次 `inspect`。回滚同理，列不存在时直接返回，避免 `DROP COLUMN` 报错。

**实现思路：** 加列不设 server default、不回填；`NULL` 就是“没有触发行”。

**检视发现：** 无阻塞发现。迁移只处理 `bad_cases` 表存在的情况；若表不存在，说明部署还没建问题表，跳过是安全的。
