## §2 架构导览

### 2.1 展示层没有新增层级

`StepIterations.vue:5` 引入既有的 `renderMarkdown`，`:142-159` 只增加三个纯函数和一个小状态集合：

- `commitSubject(message)`：取第一行并 `trim()`，作为标题行；
- `commitBody(message)`：取剩余行并 `trim()`，空字符串代表没有正文；
- `commitBodyHtml(message)`：把正文交给 `renderMarkdown(..., { images: false })`；
- `commitOpen`：`Set<string>`，用 `roundId` 记住每个轮次是否展开。

没有新增组件、没有新的 Markdown 库、没有新的事件总线。commit 的正文仍然是 `finalCommit.message` 这一个字符串，拆分只发生在展示层。这样旧 run 的数据不需要迁移，后端也不需要知道 UI 怎么折叠。

### 2.2 安全边界沿用现有链路

`renderMarkdown` 的配置在 `apps/web/src/utils/markdown.ts`：`html:false`、`breaks:true`、`linkify:true`，链接统一补 `target="_blank"` 与 `rel="noopener noreferrer"`，`images:false` 时图片降级为 alt 文本。`StepIterations.vue:307-311` 的 `v-html` 只接收这个函数的输出，和 `BadCaseList.vue`、`ProblemDescription.vue` 的用法一致。

这意味着 commit message 里的原始 HTML 不会执行、`javascript:` 链接不会成为可点击链接、远程图片不会加载。测试在 `RunDetailConformance.test.ts:535-538` 对 `target` / `rel` 做了断言。

### 2.3 折叠状态属于组件生命周期

`commitOpen` 在组件 setup 时创建一个空 Set（`:18`），默认全部收起；它不写入 URL、不写入后端。轮次卡本身已经用 `expanded` 控制 cluster 的展开，commit 的展开是第二层、更细的开关。两层状态互不影响：收起 cluster 再打开，commit 的展开状态仍保留。

## §3 数据流走查

一条主线：打开已完成 run → 第 6 步 → 已接纳轮次 → 展开 commit。

1. 后端 `build_accepted_message()` 生成 `subject + \n\n + ## 问题/分析/改动/为什么接纳/追溯 + \n\n + ---\nHarness-*`；`stages.py` 把 `round.commit_message` 映射为 `StepFinalCommit.message`。
2. 前端 `StepIterations.vue` 收到 `round.finalCommit`；旧 run 的 message 只有一行，新 run 的 message 是多段 Markdown。
3. `commitSubject()` 取第一行，标题行渲染 12 位 hash + subject（`:282-289`）。subject 放不下时 CSS 省略，`title` 保留全文。
4. 若 `commitBody()` 非空，渲染切换按钮（`:290-304`）。`aria-expanded` 随 `commitOpen` 变化，`aria-controls` 指向正文容器 id。
5. 点击按钮 → `toggleCommit(roundId)` 复制 Set 后替换，触发响应式更新（`:154-159`）。
6. 展开时，`commitBodyHtml()` 调 `renderMarkdown()`，输出标题、列表、链接、代码块、分隔线；`v-html` 写入 `.commit-message.markdown`（`:305-312`）。
7. CSS 在 `:600-700` 给正文加排版：12px/1.7、最大高度 520px、`overflow:auto`、`overflow-wrap:anywhere`；hash 用 `white-space:nowrap` 防止被拆开。
8. 再次点击 → 正文节点从 DOM 移除；hash、subject、`Harness-Evaluated-Commit` 不动。

边界：未接纳轮次走 `:323-330` 的原有拒绝说明，不进入 commit 卡；没有 `finalCommit` 的轮次也不渲染该 section。

## §6 讨论点

### 讨论点 1：`Harness-*` trailer 没有独立视觉样式

**位置**：`apps/web/src/pages/evolution/components/StepIterations.vue:310`（`v-html` 输出）、`:600-700`（正文样式）

**现象**：真实 message 末尾的 `Harness-Evaluated-Commit`、`Harness-Verdict`、`Harness-Decision-Rule` 经 `renderMarkdown()` 后是普通段落（连续行由 `breaks:true` 变成 `<br>`），字体与正文相同；V2 原型曾用 `.commit-trailer` 给它们等宽、弱化色。

**问题**：机器 trailer 与人类正文没有视觉区分，扫读时只能靠 `Harness-` 前缀识别。是否需要在生产里也弱化它们？

**预判**：可以不处理。issue 的实现内容只要求复用现有 renderer 并补标题、列表、链接、代码与分隔线样式；要为 trailer 单独着色，就得在通用 renderer 里加一条针对 commit 结构的特判，或先按 `Harness-` 前缀切段再渲染，复杂度和收益不成比例。当前样式已经能读，且 `Harness-*` 前缀本身足够醒目。

**结论**：（留空给维护者）

### 讨论点 2：520px 正文上限在窄视口会产生嵌套滚动

**位置**：`apps/web/src/pages/evolution/components/StepIterations.vue:600-613`

**现象**：`.commit-message` 设置 `max-height: 520px; overflow: auto`。桌面 1500×900 下大多数 message 不需要滚动；窄视口或极长 message 会在页面滚动容器内再出现一个滚动区。

**问题**：嵌套滚动对触控板和移动端不友好，用户可能误以为正文到底了。是否应该在窄视口取消 max-height，交给页面滚动？

**预判**：当前无实害，且上限与 V2 原型的 520px 一致，本 PR 只对齐原型。若后续真出现移动端反馈，可以在媒体查询里把 max-height 改为 `none`，但那会改变「长消息不把后续轮次推远」的原始目标，需要单独权衡。

**结论**：（留空给维护者）

### 讨论点 3：展开状态在轮次数据刷新时保留

**位置**：`apps/web/src/pages/evolution/components/StepIterations.vue:18`、`:154-159`

**现象**：`commitOpen` 只按 `roundId` 记录，不随 `rounds` 数组刷新而清空。SSE/轮询更新同一 run 时，已展开的 commit 保持展开；如果服务端在同一 `roundId` 下更新了 message，正文会直接换成新内容。

**问题**：这是期望行为还是状态泄漏？

**预判**：是期望行为。用户在阅读长 commit 时后台刷新不应把正文突然收起；`roundId` 在同一个 run 内稳定，跨 run 时组件通常重新挂载，不会串状态。

**结论**：（留空给维护者）

## §9 文件级代码分析

### 9.1 `StepIterations.vue`

**职责一句话**：运行详情第 6 步的轮次卡，展示来源 bad case、patch、candidate、推送、评测与最终 commit。变更形态：M。

**关键依赖**：`renderMarkdown` 是仓库自己的安全 Markdown 入口，构建期由 Vite 打包进产物；它不是运行时远程加载的第三方服务，渲染结果只是一段经过转义与链接加固的 HTML。

**变更代码块分析**：

旧代码（`main` 上的 `:261-264`）：

```html
<div class="commit">
  <span class="hash">{{ round.finalCommit.hash.slice(0, 12) }}</span>
  <span>{{ round.finalCommit.message }}</span>
</div>
```

新代码（`:282-312`）：

```html
<div class="commit">
  <div class="commit-head">
    <span class="hash">{{ round.finalCommit.hash.slice(0, 12) }}</span>
    <span class="commit-subject" :title="...">{{ commitSubject(...) }}</span>
  </div>
  <template v-if="commitBody(...)">
    <button class="commit-toggle" :aria-expanded="..." @click="toggleCommit(...)">…</button>
    <div v-if="commitOpen.has(...)" class="commit-message markdown" v-html="..." />
  </template>
</div>
```

这在做什么：把「一个字符串」拆成「标题 + 可选正文」。标题永远可见，正文按需渲染；按钮只在正文非空时出现，所以旧 run 不会多出无意义入口。

为什么这么写：UI 需要同时满足「紧凑」和「完整信息」两个互相拉扯的目标。默认收起保证卡片高度可控；展开后交给现有 renderer 保证 Markdown 结构与安全边界，不需要自己解析标题或列表。

实现思路总结：状态按轮次 id 记录、拆分函数纯函数化、渲染复用现有安全入口。

**检视发现**：无阻断性缺陷。可讨论项见 §6。
