## §2 架构导览

### 2.1 缺陷层：`gh()` 的返回类型是字符串

`gh(args)` 是 `execFileSync(..., { encoding: "utf8" }).trim()`（`scripts/flow-sync.mjs:84-86`），返回值是字符串。旧实现把它当对象：

```js
// 旧（base 侧）
readMilestoneState(milestone) {
  return gh(["api", `repos/${repo}/milestones/${milestone.data.github.number}`]).state;
},
readIssueState(issue) {
  return gh(["issue", "view", ..., "--json", "state"]).state;
},
```

`String.prototype.state` 恒为 `undefined`，`runSync` 里的 `undefined === desired` 永远为 false（`scripts/flow-sync.mjs:151,160`），于是每个编号对象都进 PATCH 分支。正文读取用 `--jq .body` 拿裸字符串、创建路径用 `JSON.parse`，都不受影响，所以故障面只在状态比较。

### 2.2 修复层：解析、校验、注入缝

- `parseState(output)`：`JSON.parse` 后要求 `state` 是非空字符串，否则抛错（`scripts/flow-sync.mjs:99-103`）。缺字段时若返回 `undefined`，就会退回“永远漂移”的旧行为，所以选择响亮失败。
- `githubStateReaders(repo, run = gh)`：返回两个读取器；`run` 默认是真实 `gh`，门禁可注入“返回原始 JSON 字符串”的假执行器（`scripts/flow-sync.mjs:113-122`）。读取器本身仍只负责“解析 + 取 state”，不知道 PATCH 逻辑。
- `ghJson(args)`：`JSON.parse(gh(args))` 的共用入口，替换创建/retire 两处等价的显式 `JSON.parse`（`scripts/flow-sync.mjs:88-91`）。它不是新机制，只是把同样的解析意图命名并收口。

### 2.3 接线：`main()` 把读取器交给 `runSync`

`main()` 构造 io 时用 `...githubStateReaders(repo)` 提供 `readMilestoneState` / `readIssueState`（`scripts/flow-sync.mjs:216`），`runSync` 契约不变（`scripts/flow-sync.mjs:138-176`）。因此“读 → 比 → 条件 PATCH”的主流程没有改动，只把读取实现换成解析版。

### 2.4 门禁：把“接线正确”变成可回归断言

`scripts/gates.spec.mjs:826-842` 用假 `run` 返回原始 JSON，断言读取器得到 `open` / `OPEN` 且调用参数正确；再用 `"{}"` 断言缺 `state` 抛错。`scripts/gates.spec.mjs:844-867` 用注入 io 跑两次 `runSync`：无漂移 `stateUpdates === 0` 且无 PATCH，单个 milestone + 单个 issue 漂移时 `stateUpdates === 2` 且只记录这两个对象。

### D3 缺 `state` 字段时的失败策略

**位置**：`scripts/flow-sync.mjs:99-103`。

**现象**：旧实现缺字段得到 `undefined`，静默重复 PATCH；新实现直接抛错。

**问题**：抛错会让 `pnpm flow:sync` 整体失败（包括后续正文同步），比“只重复状态 PATCH”更响；这是不是期望的失败边界？

**预判**：是。重复全量 PATCH 会烧配额并掩盖漂移，且 GitHub 的两种读取命令都稳定返回 `state`；异常形状更可能是代码错误，应在第一处暴露。

**结论**：（已按此实现；若维护者希望降级为警告，可改读取器而不动 `runSync`）

**现象**：注入测试验证 `runSync` 的计数逻辑，读取器测试验证解析；没有测试能断言 `main()` 的 io 确实用了 `githubStateReaders`。

## §9 文件级代码分析

### 9.1 `scripts/flow-sync.mjs`（M）

**职责**：流程树写 GitHub 的唯一入口；创建/回填/状态同步/正文同步/retire。

**关键依赖**：`node:child_process` 的 `execFileSync`（唯一的 gh/git 进程边界，非第三方包）、`node:fs` 的同步读取（正文渲染）、仓库内的 `flow-lib` / `translation-pairing-lib`。

**变更代码块**：

```js
// 旧：字符串上取 .state
readIssueState(issue) {
  return gh(["issue", "view", String(issue.data.github.number), "--repo", repo, "--json", "state"]).state;
}

// 新：先解析、再校验、再取 state；run 可注入
export function githubStateReaders(repo, run = gh) {
  return {
    readMilestoneState(milestone) {
      return parseState(run(["api", `repos/${repo}/milestones/${milestone.data.github.number}`]));
    },
    readIssueState(issue) {
      return parseState(run(["issue", "view", String(issue.data.github.number), "--repo", repo, "--json", "state"]));
    },
  };
}
```

实现思路：把“命令参数 + 输出解析”封装在一个小工厂里，`main()` 只负责用真实 `gh` 调用它；解析失败抛错而不返回 `undefined`。

检视发现：无逻辑缺陷；`githubStateReaders` 的 `run` 参数只为测试注入，生产默认绑定 `gh`，与现有导出风格一致（`planSync`、`applyGithubRef` 同样为测试导出）。
