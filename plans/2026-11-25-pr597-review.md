## §1 一页速览

一句话：把「一条公共 badcase 属于哪个空间」从 `bad_cases.workspace_id` 这个单值字段，改成一张按 `assignment_source` 区分来源的多对多关联表；空间管理员配置自己接受的 label，目录同步按 `meta_data.label` 把同一条公共事实同时「抄送」给所有匹配空间，所有列表、Session、统计和自进化取数都改从这张关联表判断可见性。

一个比喻：公共仓库是**总库房**，`bad_cases` 是每件货的**唯一档案**（全局 `bad_case_id` 是档案号，只有一份）；`workspace_bad_case_labels` 是各空间在总库房填的**订阅栏目**（一个栏目可被多个空间订阅）；`workspace_bad_cases` 是各空间的**收货清单**；`bad_cases.catalog_label` 是同步时提前印在档案封面上的**栏目名**（只是投影，便于查表）；`catalog_synced` 是「这件货走过总库房登记」的戳。以前每个空间想把货放进自己仓库，只能改档案上唯一的「归属空间」那一栏，所以一件货不可能同时归两个空间；现在改为按封面栏目名往多个空间的清单上抄，档案本身不动。

## §2 架构导览

### 2.1 数据模型：单份事实 + 三态关联

`bad_cases` 仍是每件货唯一档案：`bad_case_id` 全局主键，`meta_data` 原样保留（`domain.py:296-333`）。新增的两个查询列是 `catalog_label VARCHAR(128) NULL` 与 `catalog_synced BOOLEAN NOT NULL DEFAULT 0`（`domain.py:315-316`），并各配一个索引（`domain.py:332-333`）。为什么要有 `catalog_label` 而不在 SQL 里解析 `meta_data`：SQLite 的 `json_extract` 与 MySQL 的 `JSON_EXTRACT` 语法/索引行为不同，而空间规则重算、每页计数都是热路径；把「验证后的 label」投影成普通列后，两边都只是等值比较，能走索引。代价是同一事实有两处表达（`meta_data.label` 与 `catalog_label`），必须由**唯一写者**同步维护，见 §2.3。

两张新表：规则表 `workspace_bad_case_labels` 主键 `(workspace_id, label)`，label 上另建索引（`domain.py:337-346`），便于「按 label 找所有空间」；关联表 `workspace_bad_cases` 主键 `(workspace_id, bad_case_id, assignment_source)`，`bad_case_id` 外键到 `bad_cases` 并级联删除，`label` 记录命中值，另有 `bad_case_id` 与 `label` 两个索引（`domain.py:349-365`）。主键把「同一空间同一 case 的不同来源」设计成可并存：`direct_ingest` 与 `catalog_label` 可以各占一行，读取用 `DISTINCT` 去重。为什么不是 `(workspace_id, bad_case_id)` 唯一：设计明确允许同一空间既直接上报又因 label 命中，二者删除语义不同（删规则不能删直接上报），必须能分别删。

迁移 `0034` 做四件事（`0034:14-135`）：一是给 `bad_cases` 补两列与两个索引，`catalog_synced` 用 `server_default=0`；二是给同步状态表补 `assigned_count/unassigned_count/invalid_label_count`（`0034:43-62`）；三是建两张新表，`workspace_id` 外键级联到 `workspaces.id`、`bad_case_id` 级联到 `bad_cases.bad_case_id`（`0034:64-120`）；四是把既有 `workspace_id IS NOT NULL` 的每一行回填成 `legacy_owner`（`0034:122-135`）。为什么回填：升级前所有列表都按 `workspace_id` 过滤，上线后读路径只认关联表，不回填会让历史数据瞬间「消失」。`legacy_owner` 是兼容态，后续被直接上报收敛为 `direct_ingest`（`bad_case_ingest.py:338-372`），或被目录页回收（`bad_case_catalog_sync.py:298-307`）。

注意模型与迁移的一处有意分歧：`domain.py` 的两张新表没有声明 `workspace_id` 外键，注释写「The migration owns the cross-metadata workspace foreign key」（`domain.py:340`、`352`）。原因是 `workspaces` 在 `WORKSPACE_METADATA`、`bad_cases` 在 `DOMAIN_METADATA`，外部表 bootstrap 不能依赖跨 metadata；这与 `bad_cases.workspace_id` 一直只做值引用的约定一致（`plans/db-relationship-diagram.md:74-84`）。后果是「用模型 metadata 直接建表」的环境（部分 fixture）没有这条外键，级联行为只在真实迁移后的库成立，测试与生产的 schema 不完全等价。

### 2.2 写侧 A：规则保存是一个「全量替换 + 历史重算」事务

HTTP 入口是 `GET/PUT /api/workspaces/{wid}/bad-case-labels`：读用 `require_workspace_role("viewer")`，写用 `"space_admin"`（`api/workspaces.py:121-155`）；service 只把 items 排序后交给 repository（`service/workspaces/bad_case_labels.py:20-41`）。真正的机制在 `WorkspaceBadCaseLabelRepository.replace()`（`db/crud/workspace_bad_case_labels.py:63-149`）：

1. 在一个 `database.transaction()` 里先 `select workspaces.id ... with_for_update()`；不存在返回 `None`（service 转 404）。
2. `delete` 该空间全部规则，再批量插入新规则（`81-98`）。
3. `delete` 该空间全部 `assignment_source='catalog_label'` 关联（`100-105`）。
4. 用 `INSERT … SELECT` 从 `bad_cases JOIN workspace_bad_case_labels ON label = catalog_label` 重建历史关联（`106-134`）。
5. 在同一事务里数一次 `count(distinct bad_case_id)` 作为 `assignedBadCaseCount`（`136-144`），提交后才返回。

为什么用 `INSERT…SELECT` 而不是先查 ID 再逐条插：历史可能几十万条，一次集合写入避免把 ID 搬进 Python；为什么只删 `catalog_label`：直接上报关联是另一个来源，删规则不应该撤销它（设计 §2.2）。放弃的是「增量 diff」：即使规则完全没变也会全删全建，换来的是实现简单和「规则/关联永远同源」；代价见 D5。

### 2.3 写侧 B：目录同步的单页事务顺序

服务层只负责把上游 item 映射成行，并提取 label：`_catalog_label` 要求 `meta_data` 是 Mapping、`label` 是 `str`、长度 1–128、无首尾空白，否则返回 `None`（`service/acquisition/bad_case_catalog_sync.py:61-74`）；`_row` 把它放进 `CatalogCaseRow.catalog_label`（`84-88`）。注意这里没有 trim、没有大小写折叠——契约就是「精确匹配」，`"Review"` 与 `"review"` 是两个 label。

Repository 的 `commit_page()`（`db/crud/bad_case_catalog_sync.py:251-400`）是这次改造最关键的事务边界，顺序是：

1. 先按 id 查 `origin` 做写者归属判断；新 id 走 `insert`，`origin='catalog'` 的旧行走 `update`，`origin='report'` 的旧行只计 `skipped`、**不覆盖**（`267-297`）。插入用 `session.begin_nested()` 包住，撞主键时回滚 savepoint、重读归属、再试一次（`270-285`）——这就是最新提交 `94c018b9` 要修的 SQLite savepoint 问题的现场。
2. 对本页所有 id 删除 `legacy_owner` 与 `catalog_label` 关联（`298-307`）。
3. `INSERT … SELECT` 从 `bad_cases JOIN workspace_bad_case_labels` 重建本页命中的关联（`308-335`）。
4. 全量算 `synced` / `valid` / `assigned` 三个数并写回状态行，同时推进 `last_bad_case_id`（`336-380`）。

为什么删完再建而不是「按 label diff」：上游重试/冷启动会重复收到同一 ID，删建天然幂等；为什么把删除放在 upsert 之后：只有事实落库并带上最新 `catalog_label`，重建才能读到新 label。放弃的是「单条增量」：每页对整页 ID 做一次删除+重建，页大小 200，写放大可接受。

### 2.4 写侧 C：直接上报与额度

`BadCaseIngestRepository.ingest()` 在原有「锁空间 → 查全局 ID 归属 → 额度检查 → insert/update」中插入了关联逻辑（`bad_case_ingest.py:159-195`）：先算 `already_assigned = _workspace_has_case(...)`（该空间是否已有**任意来源**的关联），只有「尚未关联」才做额度检查（`174-182`），写完事实后 `_assign_direct()` 删除同空间 `legacy_owner` 并确保 `direct_ingest` 存在（`338-372`）。为什么豁免已关联 case 的额度：同一 case 的重复上报不应因为 `used` 已达配额而被拒；为什么不删 `catalog_label`：label 命中的可见性与直接上报是两条独立的来源，删了会让「空间因 label 看到它」这件事被上报副作用撤销。

`_used()` 从「数 `bad_cases.workspace_id = ?`」改为「数关联表里该空间去重 case 数」（`308-317`）。这把额度口径从「我拥有多少行」改成「我能看到多少 case」；公共分配可以让 `used > quota`（设计 §4.1 明确接受），此时新 case 的直接上报继续返回 `QUOTA_EXCEEDED`，而管理页会显示超额的 `used`。

### 2.5 读边界：一个方法收口，两种形态

`WorkspaceReadScope.case_condition()`（`db/crud/read_scope.py:48-75`）把旧的 `condition(column)` 换成一个固定针对 `bad_cases` 的谓词：

- 指定空间：`EXISTS (SELECT 1 FROM workspace_bad_cases WHERE workspace_id = :wid AND bad_case_id = bad_cases.bad_case_id)`——相关子查询，命中主键前缀；
- 旧式 user 范围：`bad_cases.bad_case_id IN (SELECT bad_case_id FROM workspace_bad_cases WHERE workspace_id IN (SELECT workspace_id FROM workspace_members WHERE user_id = :uid))`；
- 全局管理员：`true()`。

`session_condition()` 再用它把 Session 投影成「该范围内 case 的根会话集合」（`77-81`）。另有 `scoped_case_ids(workspace_ids)` 给那些已经拿到「一组显式空间」的旧兼容路由用（`84-92`）。设计上这是一个**必须带 `bad_cases` 进 FROM** 的谓词（见 D6 的 API 形状提醒）；所有当前调用点都满足（`sessions.py`、`problems.py`、`overview.py`、`potential.py`、`overview_targets.py`）。

读路径的替换清单可以对照 `grep "case_condition|scoped_case_ids|session_condition"`：sessions 6 处、problems 6 处、overview 的共享谓词 1 处（被 6 个聚合复用）、overview_targets/potential 各 1 处、bad_cases/bad_case_sync/probe_query/evolution_targets 各 1 处。为什么必须收口到一个方法：可见性是权限边界，散落的 `bad_cases.workspace_id == ?` 只要漏一处，就会让 label 共享的 case 在某个页面「看不见」或让旧默认空间「看得见」。这也是本 PR 最有价值的部分。

### 2.6 前端：查询键、mutation 与「草稿」状态机

- 查询键 `adminBadCaseLabels(id)` 挂在 `["ws", id, "admin", ...]` 下（`api/queryKeys.ts:30-31`），因此保存后 `invalidateQueries({queryKey: queryKeys.workspace(id)})` 一次前缀失效就能覆盖总览、Session、自进化、页签自身（`composables/useWorkspaces.ts:369-383`）；另外还失效 `["ws"]` 与 `auth/session` 并主动 `refreshAuthSession()`，因为工作空间列表的 `used` 也可能变。
- 组件状态机（`BadCaseLabelsTab.vue:27-54`）：`savedItems` 来自服务端，`draft` 是本地副本；`watch(savedItems)` 只在「当前 draft 仍等于上一次服务端快照」时才采纳新快照，所以后台 refetch 不会吞掉用户正在编辑的内容；`watch(workspaceId)` 在切换空间时直接采纳当前快照（丢弃未保存草稿）；`isDirty` 用 `sameLabels` 做顺序敏感比较。这个状态机是提交 `913dd44f` 的主要修复对象——旧实现只「首次同步」，离开页签再回来会保留被遗弃的草稿。
- 校验在前端先做一遍（`62-71`），服务端再做权威校验（`schemas.py:160-171`）；保存失败把 `WORKSPACE_FORBIDDEN` / `VALIDATION_INVALID` 映射成中文（`113-120`），其他错误落入通用文案。

### 2.7 契约、文档与原型

FastAPI 模型是契约源：`WorkspaceBadCaseLabelRequest` 的 items 有 `default_factory=list`，所以生成 schema 里 `items` 不是 required（D6）；`WorkspaceBadCaseLabelConfiguration.assigned_bad_case_count` 有 `ge=0`（`schemas.py:174-179`）。生成链把两个 schema 与两条 path 写进 `openapi.json` 与 `api.d.ts`，`index.ts` / `workspaces.ts` 只做类型再导出（`packages/contracts/src/workspaces.ts:66-73`），符合「契约是唯一事实源」的仓库规则。

文档侧，architecture 只改了一句（`docs/architecture.md:36`）：空间表清单补两张新表、明确「bad case 可见性走关联表」；这是现状 home，措辞准确。设计 17 是理由 home，Note 记录取舍与拒绝的替代方案，flow issue 管流程，ER 图补结构——四个 home 各司其职，没有把决策塞进 `docs/`。

## §3 数据流走查

以一个真实场景走一遍：空间 A、B 都配置了 `review`；上游一页返回 5001（`meta_data.label="review"`）、5002（`label=" review"`，带首空格）、5003（`label="tool-use"`，无人配置）；之后 A 又通过凭据直接上报 5004。

1. **管理员配置规则**：A 的空间管理员在空间管理点「Badcase 类型」（`Admin.vue:47` 的页签定义、`303-308` 渲染），输入 `review` 回车，`addLabel()` 校验后把 `draft` 排序为 `["review"]`（`BadCaseLabelsTab.vue:77-82`）；点保存触发 `replaceLabels({items:["review"]})`（`97-106`），`PUT /api/workspaces/A/bad-case-labels`（`api/workspaces.ts:233-241`）。
2. **服务端原子替换**：路由用 `space_admin` 校验（`api/workspaces.py:148-155`），service 排序后调 repository；repository 在**一个事务**里锁空间、删旧规则、插 `review`、删 A 的 `catalog_label` 关联、`INSERT…SELECT` 重建、数一次 `assigned`（当前为 0）、提交（`workspace_bad_case_labels.py:70-149`）。响应 `{"items":["review"],"assignedBadCaseCount":0}`。
3. **目录同步取页**：调度器触发 `BadCaseCatalogSyncService.run()`；它从状态表读 `last_bad_case_id`，`mark_running`，向公共仓库请求 200 条（`service/acquisition/bad_case_catalog_sync.py:143-224`）。对每条 item，`_row` 调 `_catalog_label`：5001→`review`，5002→`None`（首空格不合法），5003→`tool-use`（合法但与规则无关）。
4. **单页事务落库并路由**：`commit_page()` 先查归属（三条都新）→ `insert` 三行事实，`catalog_synced=True`，`catalog_label` 分别为 `review/None/tool-use`（`bad_case_catalog_sync.py:119-131`、`267-297`）→ 按本页 id 删 `legacy_owner`/`catalog_label`（此时没有）→ `INSERT…SELECT` 连接规则表：只有 5001 命中 A（若 B 也配了 `review`，同一行会为 B 也生成一条）→ 写回 `last_bad_case_id`、`synced=3`、`valid=2`、`assigned=1`、`unassigned=1`（5003）、`invalid=1`（5002）→ 提交（`298-380`）。如果第 4 步任意一句失败（例如触发器拒绝插关联），整个事务回滚：事实、关联、计数、游标都不前进；测试 `test_assignment_failure_rolls_back_fact_and_cursor` 用 SQLite trigger 钉住了这一点（`test_catalog_sync_repository.py:321-375`）。
5. **读侧生效**：用户打开总览，`OverviewRepository` 的共享谓词调用 `WorkspaceReadScope.for_workspace(A).case_condition()`（`overview.py:102-117`），SQL 变成 `EXISTS (workspace_bad_cases WHERE workspace_id='A' AND bad_case_id=bad_cases.bad_case_id)`，A 只看到 5001（以及之后 5004）；B 只看 5001；第三方空间看不到 5001。Session 列表走 `session_condition()`（`sessions.py:247-260`），把「A 可见 case 的根会话」投影成 Session 集合；`used` 也数关联去重（`workspaces.py:268-296`）。
6. **直接上报共存**：A 用凭据上报 5004；`_lock_workspace` 拿锁后 `already_assigned=false`，`used` 未到配额 → 插入事实（`workspace_id=A`）→ `_assign_direct` 插 `direct_ingest`（`bad_case_ingest.py:159-195`、`338-372`）。A 现在有 `direct_ingest`(5004) 与 `catalog_label`(5001)；读取去重后 `used=2`。
7. **删规则只撤销 label 可见性**：A 把规则清空 → `PUT {"items":[]}` → repository 删 A 的 `review` 规则、删 A 的 `catalog_label` 关联、不再重建；A 仍能看到 5004（`direct_ingest` 未被动），看不到 5001；B 的 5001 不受影响（`test_bad_case_labels_api.py:104-166`、`test_scope_associations.py:104-120`）。
8. **升级存量**：升级时迁移把每行既有 `workspace_id` 回填 `legacy_owner`（`0034:122-135`）；老公共 case 因此仍能被旧默认空间看到。但它们的 `catalog_label` 仍是 NULL、`catalog_synced` 仍是 0，游标也不会回头，所以 A 之后配置 `review` 只能覆盖升级后新同步的行——这是 D2 的问题。
9. **前端刷新**：保存成功 → `invalidateQueries(["ws", A])` 前缀失效 → 总览/Session/自进化/页签在重新进入或重新请求时拿到新集合；toast 文案「Badcase 类型已保存，历史数据已重新划分」（`BadcaseLabelsTab.vue:102`）与设计 §7 一致。

## §6 讨论点

### D1 归因进度聚合仍按 `bad_cases.workspace_id` 关联报告，label 共享 case 会算错空间

- **位置**：`apps/api/app/db/crud/bad_cases.py:307`（`select(bad_cases.c.bad_case_id, bad_cases.c.workspace_id)`）与 `340-347`（`probe_reports.c.workspace_id == scope.c.workspace_id`）；调用链 `apps/api/app/api/acquisition.py:243-260` → `apps/api/app/service/problems/service.py:54-58` → `bad_cases.py:303`；`probe_reports.workspace_id` 的写入在 `apps/api/app/service/evolution/attribution.py:900-903`。
- **现象**：本 PR 把 `analysis_progress` 的 case 过滤换成了 `scoped_case_ids(workspace_ids)`（`308-309`），但子查询仍把 `bad_cases.workspace_id` 带出来，并用它去匹配 `probe_reports.workspace_id`。对 label 共享的公共 case，`bad_cases.workspace_id` 恒为 `ws-default`（目录同步写入 `DEFAULT_WORKSPACE_ID`，`bad_case_catalog_sync.py:117`），而报告行记录的是**实际发起归因的运行空间**（`run.workspace_id`）。于是空间 B 打开顶栏同步气泡（`TopNav.vue:107-112` 带 `workspaceId` 每 15s 轮询）时，B 对共享 case 的 v2 报告不会被计入；如果 ws-default 归因过，B 反而会显示「已归因」。legacy 的 `analysis_status` 路径不受影响，所以现有测试（只插 legacy 行）全绿。
- **问题**：这是「读边界收口」的一处漏网：筛选条件换了，join 条件没换，而 `probe_reports` 恰恰是按空间存的。后果是聚合数字错误（不是明细泄露，但会误导排期与验收），且与 PR 声称的「所有空间读路径统一经 `case_condition()`」不一致。它也不属于「已持久化快照不反查」的保护范围——这里查的就是实时报告。
- **预判**：修法很小：`workspace_ids` 非空时把 join 条件改为 `probe_reports.c.workspace_id.in_(workspace_ids)`；`workspace_ids is None`（全局管理员）则不限制报告空间。更彻底的做法是让 `analysis_progress` 接收 `WorkspaceReadScope`，统一从 scope 推导 case 与报告空间。补一个跨栈测试：空间 B 对共享 case 产出 probe 报告后，`GET /api/acquisition/status?workspaceId=B` 的 `analyzed` 为 1、`GET ...?workspaceId=A` 不把 B 的报告算进去。属 correctness，建议在合并前或紧随的修复 PR 处理；不涉及数据结构，风险低。
- **结论**：

### D2 升级不回填存量公共事实的 `catalog_label` / `catalog_synced`，也不回退游标

- **位置**：`apps/api/alembic/versions/0034_workspace_bad_case_labels.py:19-41`（新增列，`catalog_synced` 默认 0）、`122-135`（只回填 `legacy_owner`）；`apps/api/app/db/crud/bad_case_catalog_sync.py:129-131`（只有 upsert 才写 `catalog_synced=True`）、`409-428`（`count_bad_cases` 只数 true）、`335-356`（`synced`/`valid`/`invalid` 都基于 true）。
- **现象**：升级前已存在的公共事实（`origin='catalog'`）在迁移后统一是 `catalog_label=NULL, catalog_synced=0`；`bad_case_catalog_sync` 的游标行原样保留（`0012` 建的表，`initialize` 只在缺行时置 0），服务只从游标往后拉。因此升级后：存量公共 case 永远不会被重新打标；`synced` 从「全表行数」立刻降为「升级后新同步的行数」；`invalid_label_count`/`unassigned_count` 也不含存量。设计 §4.3 写的是「新增规则补齐历史数据」，只有 `catalog_label` 非空的存量才能被补齐。
- **问题**：PR 的动机是「生产 badcase 统一进公共仓库」，即生产形态本来就有存量。升级后管理员配一个 label 只能看到升级之后新同步的 case，历史数据仍只以 `legacy_owner` 留在默认空间；同时顶栏/同步页的 `synced` 数字会「归零」，让运维误以为同步坏了。数据没丢，但功能承诺与可观测性都对不上。
- **预判**：三条路，按成本排序：(a) 迁移或一次性运维步骤把 `last_bad_case_id` 重置为 0，让下一次同步重放全部 ID——upsert 会补 `catalog_synced/catalog_label`，页事务会重建关联，代价是一次全量重拉，且会同时触发 D3（所以两条要一起修）；(b) 迁移内用双方言 JSON 表达式回填 `catalog_label`（SQLite `json_extract` / MySQL `JSON_EXTRACT`），需要重复 1–128/trim 校验，SQL 不可移植风险高，不推荐；(c) 明确接受「只对新数据生效」，在 17 与 Note 写清并提供受控重放脚本。建议至少选 (a) 或 (c)，并补一条「升级前已有 catalog 行」的迁移测试（现在的迁移测试只插了一条 legacy 行，见 `test_migration.py:88-192`）。
- **结论**：

### D3 目录页删除 `legacy_owner` 不区分 `origin`，可能让历史直接上报的 case 失去唯一可见性

- **位置**：`apps/api/app/db/crud/bad_case_catalog_sync.py:298-307`（按本页 `ids` 删除 `legacy_owner`/`catalog_label`，未过滤 `origin`）、`283-297`（`origin='report'` 的行只 skip、不 update）；`apps/api/alembic/versions/0034_workspace_bad_case_labels.py:122-135`（所有 `workspace_id IS NOT NULL` 的行都回填 `legacy_owner`，包括 `origin='report'`）；`apps/api/app/db/crud/bad_case_ingest.py:338-372`（只有再次上报才补 `direct_ingest`）。
- **现象**：一条升级前由凭据直接上报的 case（`origin='report'`、`workspace_id=W`）在迁移后只有 `legacy_owner(W)` 这一条关联。如果同一 ID 之后出现在公共目录的某一页，页事务会删掉它的 `legacy_owner`；由于 `origin != 'catalog'` 不会被 update，`catalog_label` 又是 NULL，所以 `INSERT…SELECT` 也不会为它建 `catalog_label` 关联。结果：W 失去唯一可见性，直到 W 再次上报同一 ID 才补回 `direct_ingest`。这不是数据删除，但列表、Session、总览、额度都会少这一条，且没有任何告警。
- **问题**：迁移回填没有利用已经存在的 `origin` 区分「直接上报」与「公共目录」。设计 §2.2 说移除 `legacy_owner` 的目的是「避免旧默认空间继续看到公共数据」，那针对的是 `origin='catalog'` 的行；这里误伤的是直接上报者的合法归属。同步的 `_ownership` 特意跳过 report 行以保护上报者字段，却在同一页删掉了它的可见性，逻辑上自相矛盾。
- **预判**：首选修法：迁移对 `origin='report'` 回填 `direct_ingest`、对 `origin='catalog'` 回填 `legacy_owner`——语义正好对应 `assignment_source` 的两态，也顺带覆盖「上报过又进目录」的存量窗口。次选：页事务只删 `origin='catalog'` 行的 `legacy_owner`（需要 join `bad_cases` 判断 origin）。补一条测试：report-origin 行被目录页触达后，原空间仍能通过列表/详情读到。若生产不存在「直接上报后又出现在公共目录」的 ID，本条无实害，但仍建议按语义修正，因为代码已经假设它会发生。
- **结论**：

### D4 规则保存的「锁空间」在 SQLite 上是 no-op，与 ingest 的 SQLite 写法不一致

- **位置**：`apps/api/app/db/crud/workspace_bad_case_labels.py:70-77`（`select(workspaces.c.id)...with_for_update()`）；对照 `apps/api/app/db/crud/bad_case_ingest.py:210-230`（SQLite 用一次 no-op `UPDATE` 拿写锁）；`apps/api/app/db/database.py:85-93` 的 `BEGIN` 是 deferred。
- **现象**：MySQL 上 `FOR UPDATE` 会锁住空间行；SQLite 方言忽略 `FOR UPDATE`，而本事务的第一条写语句是 `delete(workspace_bad_case_labels)`（`81-85`）。`transaction()` 里显式 `BEGIN` 也只是开事务，不取 RESERVED 锁。于是两个并发的 `PUT` 会各自读到旧规则再全量替换，最终 last-writer-wins；与 ingest 注释里明确写出的「SQLite 没有行锁，先做无意义写入拿数据库写锁」的模式不一致。
- **问题**：因为替换是幂等的全量操作，且没有像额度那样的「基于锁的决策」，当前**无实害**——最坏情况是两个管理员同时保存，后者覆盖前者，与 MySQL 的行锁语义差别不大（MySQL 也只是串行化，不是合并）。但注释写「one transaction locks the workspace」，会让后来者以为 SQLite 也串行化了；将来如果在这段逻辑里加入「先读后判」的规则（例如配额/审计），这个 no-op 会变成真 bug。
- **预判**：两种处理都行：(a) 把注释改成「MySQL 行锁；SQLite 依赖单写者事务」并保持实现；(b) 对齐 ingest，在 SQLite 分支先 `update(workspaces).values(updated_at=workspaces.c.updated_at)` 取写锁。属加固，可后续 ticket，不必阻塞本 PR。
- **结论**：

### D5 每一页都做三次全量计数，同步热路径从 O(表) 变成 O(页数 × 表)

- **位置**：`apps/api/app/db/crud/bad_case_catalog_sync.py:336-365`；其中 `341`/`351` 依赖 `catalog_synced` 索引（布尔列选择性很低），`360-362` 对 `workspace_bad_cases` 按 `assignment_source` 做 `count(distinct bad_case_id)`（该列没有索引，且关联表行数 ≈ case × 空间）。
- **现象**：改造前每页只有一次 `count(*) from bad_cases`；现在每页再算 `synced`（`catalog_synced=true`）、`valid`（true 且 label 非空）、`assigned`（关联表按 source 去重），全部是全量聚合，和页大小无关。一次 run 最多 100 页（`service/acquisition/bad_case_catalog_sync.py:107-124`），初始化/追赶时成本约 `O(页数 × 表行数)`；`workspace_bad_cases` 在「一条 case 被多个空间订阅」时会比 `bad_cases` 大一个数量级。
- **问题**：这是同步热路径上的写放大，而且每轮 run 都会重复。当前数据量下可能无感，设计只写了「计数针对最近一次完成页提交后的公共事实状态」，没有讨论成本，也没有性能基线。它不属于功能缺陷，但属于这次取舍里被放弃的东西：为了「状态行随时可读」而选择了「每页全量重算」。
- **预判**：最省事的改法是只在 `run()` 结束 `mark_idle()` 时算一次（状态页展示的仍是「最近一次 run 结束后的状态」，语义几乎不变，成本降到 O(表)/run）；若要更细的实时性，再考虑增量计数（复杂，需处理重放与规则变更）。无论改不改，建议跑一次 `pnpm performance:report` 记录基线，把结论写进 Note 的 Consequences。属性能取舍，不阻塞合并。
- **结论**：

### D6 `items` 可以缺省，空 body 会被解释成「清空全部规则」

- **位置**：`apps/api/app/service/workspaces/schemas.py:155-171`（`items: list[str] = Field(default_factory=list)`）；`apps/api/app/api/workspaces.py:148-155`（直接使用 `body.items`）。
- **现象**：`PUT /api/workspaces/{wid}/bad-case-labels` 传 `{}`、或客户端漏字段，会被解析成空列表，进而删除该空间全部 label 规则与全部 `catalog_label` 关联。`[]` 本身是合法的「清空」语义，所以服务端无法区分「显式清空」与「忘了带字段」。
- **问题**：全量替换接口里，最关键字段可缺省会把一次客户端 bug/手写 curl 变成一次可见性清空。回滚只能重新配规则并等历史重建（数据还在，`direct_ingest`/`legacy_owner` 不受影响，但公共可见性会中断）。同文件的 `WorkspaceCreateRequest.space_admin_ids` 是必填，说明仓库并不排斥「关键集合必填」。
- **预判**：把 `items` 改成必填（去掉 `default_factory`）即可让 `{}` 返回 422，`[]` 仍是合法清空；调用方目前只有 Web 与新测试，改动面小。若团队认为「省略=清空」是刻意约定，至少在 17/05 写明并让前端永远显式发送。属 API 契约加固，建议本 PR 改或记录后续 ticket。
- **结论**：

### D7 `assignedBadCaseCount` 统计所有来源，「当前划分」文案容易被读成 label 命中数

- **位置**：`apps/api/app/db/crud/workspace_bad_case_labels.py:49-61`、`136-144`（`count(distinct bad_case_id)` 不限制 `assignment_source`）；UI `apps/web/src/pages/workspaces/components/BadCaseLabelsTab.vue:236-247`；测试已把行为固定成「全部来源」：`apps/api/tests/workspaces/test_bad_case_labels_api.py:145-166`（direct + label 去重后是 2）。
- **现象**：`assignedBadCaseCount` 是该空间所有来源的去重可见 case 数（`direct_ingest`、`legacy_owner`、`catalog_label`），不只是 label 命中。空间清空所有 label 后，如果还有直接上报的 case，页面仍显示「已关联 N 条」；反过来，管理员也无法从这个数字判断「这次 label 配了多少条」。
- **问题**：设计 §6 只定义了字段名，没有定义口径；UI 标题是「当前划分」，语义更接近「由这些 label 划分出的条数」。测试把「全部来源」固定下来，说明实现者有过选择，但产品文案没有跟上。当前无数据错误，属语义歧义。
- **预判**：若意图是「当前空间可见总数」，把文案改成「当前空间共 N 条」并保持 SQL（推荐，改动最小）；若意图是「label 命中数」，SQL 加 `assignment_source='catalog_label'` 过滤，并另加一个 total 字段。两条都合理，需要产品拍板；建议在 17 §6 补一句口径定义。
- **结论**：

### D8 迁移回填不是幂等的，且与 fixture 版回填是两份语义

- **位置**：`apps/api/alembic/versions/0034_workspace_bad_case_labels.py:122-135`（`INSERT … SELECT` 没有 `NOT EXISTS`）；`apps/api/app/db/crud/fixtures.py:153-179`（同样的语义但带 `NOT EXISTS`，注释自称 "Mirror migration 0034"）；对照 `0032` 迁移对表/列都有 `has_table`/`has_column` 守卫，以及仓库已有的 partial-DDL 恢复测试 `apps/api/tests/m9-01-trace-evidence-contract/test_trace_evidence_migration.py:279`。
- **现象**：0034 对表、列、索引都有「已存在就跳过」的守卫，唯独数据回填没有；MySQL 的 DDL 是自动提交的，如果在「建表/加列成功、回填成功、alembic 版本行尚未写入」之间进程崩溃，重跑迁移会在回填处撞主键。另有一份 fixture 版回填（供 corpus/e2e 使用），语义将来容易与迁移漂移。
- **问题**：正常一次成功升级不会触发，当前**无实害**；但仓库专门写过 partial-DDL 恢复测试，说明半应用状态不是纯理论。两份回填也意味着以后改一处忘另一处时，fixture 与生产的可见性会不一致。
- **预判**：给迁移回填加 `WHERE NOT EXISTS`（与 fixtures 完全一致），或把这段 SQL 抽成一个共享常量/helper 供迁移与 fixture 复用（迁移里 import app 代码有耦合风险，抽 SQL 字符串更稳）。再补一个「回填已存在时重跑不报错」的测试。低优先级，可在后续迁移加固 PR 处理。

### 9.3 `apps/api/app/db/database.py`（M）

职责：所有写事务的统一入口。变更形态：`transaction()` 多了 4 行 + 一段 docstring。

旧代码：

```python
        async with self._factory()() as session:
            try:
                yield session
                await session.commit()
            except BaseException:
                await session.rollback()
                raise
```

新代码：

```python
        async with self._factory()() as session:
            try:
                if self.dialect == "sqlite":
                    await session.execute(text("BEGIN"))
                yield session
                await session.commit()
```

这在做什么：SQLite 的 DBAPI（legacy 事务控制）把 `BEGIN` 延迟到第一条 DML；如果先开 `SAVEPOINT`（`commit_page` 的 `begin_nested` 就是这样），savepoint 会自己开一个事务，`RELEASE` 时提交，外层再 rollback 也收不回来——事实和游标就会「半提交」。显式 `BEGIN` 让 savepoint 真正嵌在外层事务里。为什么只对 SQLite：MySQL 的驱动默认不延迟事务，重复 `BEGIN` 反而可能报错。

实现思路总结：用方言判断补一个显式事务起点，成本是多一条语句，换来嵌套 savepoint 的原子性。检视发现：这是提交 `94c018b9` 的核心修复，`test_assignment_failure_rolls_back_fact_and_cursor`（`test_catalog_sync_repository.py:321-375`）是它的证据；没有发现其它方言/连接池副作用（每次 `transaction()` 都用新 session，不会在已有事务上重复 BEGIN）。唯一可讨论的是它把「事务开始」提前到 yield 之前，长事务会多占连接，但本仓库的写事务都很短。
