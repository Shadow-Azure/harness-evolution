## §1 一页速览

**一句话**：把“按标题词法聚类”换成“一条归因结论一个草稿，再由 review 按共同根因合并”。

**比喻**：以前是按信封上的收件人模板把信叠在一起——同一批 SWE-bench 的信封长得一模一样；现在先读信的内容，只有“同一处改动能同时修好”的信才装进同一个文件夹。

**交付块**

| 块 | 结果 |
|---|---|
| 分组输入 | `probe_reports.probe_description`，标题不再参与 |
| review 输出 | 仍是 `D1..DN` 的完整分区，只合并/命名，不拆分 |
| 降级 | 按类目 3 个桶，文案带“聚类降级”，不落 N 个单例 |
| 超限 | N > 200 按类目分批，记 `degraded` |
| 算法 | 新 run `hybrid-attribution-llm-v1`；旧 run 读取不变 |
| UI | 第 5 步标题来自根因描述，不再复制第一个成员标题 |

**验证基线**：见 PR 描述；本地 `pnpm test:api` 2355 passed / 27 skipped，覆盖率 91.50%。

## §2 架构导览

### 2.1 读取投影（`attributions.py:211`、`:568`）

`ClusterableProbe` 把 `(probe_id, attribute_type, bad_case_id, probe_description)` 作为不可变记录返回。原先调用方要拿标题必须额外读 `bad_cases`，现在一次查询就拿到分组信号。`non_target` 仍被 `conclusion == "attributed"` 过滤。

### 2.2 分组层（`cluster.py:135`）

`build_attribution_drafts` 对每条唯一 probe 生成一个 `ClusterDraft`，按 `TYPE_ORDER` + `probe_id` 排序。`_attribution_description` 把结论空白归一化并截断到 240 字符；结论为空时用 `probe_id` 生成唯一兜底文本，避免“空文本”把无关 probe 合并。旧的 `cluster_probes` 保留，供无 agent 的测试/离线路径使用。

### 2.3 审查层（`cluster_llm.py:427`、`:888`）

- `build_review_request(grouping="attribution")` 的摘要直接取 draft 描述（即归因结论），每块仍只有 1 条样本；规则 7 明确禁止用实例名、数据集前缀、标题模板、类目当共同根因。
- `enhance_clusters(grouping="attribution")` 返回 `hybrid-attribution-llm-v1`；review 失败时 `_fallback_groups`（`:1357`）按类目合并成员，描述由 `attribution_fallback_description` 生成。
- 超过 200 个 draft 时 `_review_batched`（`:1157`）按类目分批，每批 `validate_review_partition` 独立校验，最后按全局 draft 索引合并；批次事实在成功后写一条 `degraded`。
- `_merged_stats` 在 attribution 下不再从标题重算 `signature_overlap`，保留 0 作为占位。

### 2.4 持久化与读模型（`prepare.py:505`、`stages.py:1084`）

- 无 agent：保持旧词法路径、旧 hash、旧 `similarityThreshold` payload。
- 有 agent：每个 attributed probe 一个 draft；`clusters_created` 记录 `draftCount` / `draftSummaryMaxChars` / `grouping`。
- 第 5 步 `StepCluster.title` 由 `probe_cluster_description` 生成，描述仍是完整根因归纳；`cases[0].title` 只留在来源 case 表。

## §3 数据流走查

生产 run（20 条 attributed，13 条同模板标题）：

1. 归因阶段写 `probe_reports.probe_description`；prepare 调 `list_clusterable_probes` 拿到 20 条 `ClusterableProbe`。
2. `build_attribution_drafts` 产出 20 个单 probe draft（13 prompt / 6 flow / 1 error），D1..D20 的摘要逐条不同。
3. `cluster.review` 收到 20 个结论摘要 + 每 draft 1 条样本；模型按“同一处修改可覆盖”合并，例如把“回归门禁缺失”与“行为保持证据缺失”合并、把“429 恢复分支缺失”单独成簇。
4. 校验器确认每个 D 键恰好出现一次、无跨类目合并；代码按 `from` 展开成员并落 `probe_cluster_probes`。
5. 两次评分调用仍各一次，按最终簇批量评分；`probe_clusters` 写入根因 title/description、confidence、severity、rank。
6. 第 5 步读 `probe_cluster_description` 生成簇标题；来源 case 表仍显示真实 bad case 标题。

若 review 失败：第 3 步改为按 `prompt` / `flow` / `error` 生成 3 个兜底簇，描述为 `prompt 类问题 · 13 条归因（聚类降级）`，并写 `degraded`；strict 下直接失败且不落簇。

## §6 讨论点

### 6.1 200 draft 上限只约束条数，不直接约束字符数

- **位置**：`cluster_llm.py:82`、`:1223`
- **现象**：`ATTRIBUTION_REVIEW_MAX_DRAFTS = 200` 限制单次 review 的 draft 数，但每个 draft 的摘要 240 字符 + 最多 3 条样本（约 360 字符/条）仍可能让 prompt 超过 60k 字符。
- **问题**：issue 的成本段写的是“N ≤ 200 或输入 ≤ 60k 字符”，当前满足前者，不满足最坏情况下的后者。
- **预判**：20 条生产数据的 prompt 约 6k tokens，远低于上限；200 条属于极端情况，且仍被条数截断，模型上下文可承受。可接受为已知边界，后续若要严格按字符限流再加估算器。
- **结论**：暂不修，记入 §7 分流与 PR 的 material limitations。

### 6.2 `signatureOverlap=0.00` 仍进入评分 prompt

- **位置**：`cluster_llm.py` 的 `_render_cluster_header`
- **现象**：归因分组下该统计量不再从标题计算，评分 prompt 仍渲染 `signatureOverlap=0.00`。
- **问题**：模型可能把 0 误读为“成员完全不相似”，而实际只是该统计量不适用。
- **预判**：评分任务是给簇打分，不依赖紧密度；现有 prompt 已把成员数、时间跨度作为主统计量。保留 0 不影响正确性，删除会改动评分 prompt 契约与既有测试。
- **结论**：暂不修，作为后续清理项。

### 6.3 降级文案的 N 是 probe 数，不是 distinct case 数

- **位置**：`cluster.py:179`、`cluster_llm.py:1357`
- **现象**：`{N} 条归因` 取 draft 数；若一个 probe 被多个 bad case 复用，UI 的 `caseCount` 可能大于 N。
- **问题**：两个数字并排时可能让人误以为少了成员。
- **预判**：文案明确写“条归因”，成员表按 case 展开；本 run 是 1:1。若未来复用普遍，可在文案里改用 case 数或同时展示。
- **结论**：暂不修，记录口径。

### 6.5 集成冒烟发现：簇标题重复完整描述

- **位置**：`apps/api/app/service/evolution/stages.py:1100`
- **现象**：第一版实现把整条 `probe_cluster_description`（含 review 写的 summary）作为簇标题，标题在 1408px 下换行并挤占严重度/置信度，视觉上比原型更重。
- **问题**：标题应回答“这个簇是什么根因”，不是重复展开区的完整描述。
- **预判**：描述格式固定为 `{type} 类问题 · {title} · {summary}`，标题只取前两段；legacy 描述没有 summary 时保持整条。已在冒烟后修复，并补 stages 断言。
- **结论**：已修（2026-11-24，冒烟截图刷新）。

### 6.4 修复 main 上的 `bugfix-45` 撞号

- **位置**：`.agents/flow/issues/bugfix-attribution-skill-admin-style*`
- **现象**：PR #565 新增的 issue 使用 `bugfix-45`，与 #552 的既有 issue 冲突，`main` 上 `verify:flow` 红。
- **问题**：不在 #587 的功能范围内，但不修则本 PR 的 flow 门禁无法通过。
- **预判**：把较新的 `bugfix-attribution-skill-admin-style` 改为 `bugfix-52`，保留先到的 `bugfix-45`；只改 flow 规划编号，不改 GitHub 编号与实现。
- **结论**：已修（commit `4564de17`），PR 描述已说明。
