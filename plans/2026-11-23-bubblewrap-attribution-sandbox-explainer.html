1bubblewrap 是什么

先建立正确的直觉：它是一条命令、一个按次启动的进程包装器，而不是一个需要“维护状态”的服务。

一句话

bubblewrap（命令名 bwrap）是 Linux 上的轻量沙箱工具，最初为 Flatpak 而生。它用命名空间（namespace）和 bind mount 为一条命令构造一个“最小文件系统视图”，然后执行目标程序。

在本项目里，目标程序就是 Claude Code CLI；它被允许看到系统运行时（只读）和一个 本次归因专属的可写目录，看不到其他工作区、.env、SSH 私钥或宿主机上的其他数据。

容易误解
  • 不是 Docker/虚拟机：没有镜像、没有守护进程、没有常驻容器；每次调用就是一个进程树。
  • 不是网络防火墙：这里用 --share-net 共享宿主网络，因为 CLI 要访问模型 API。出站控制是另一层的事。
  • 不是密钥保险箱：凭据通过环境变量传入，不 bind 进沙箱；日志侧还有脱敏。
  • 通常不需要 root：依赖非特权 user namespace；是否需要 setuid 取决于发行版与内核策略，bwrap 探针就是用来验证这一点的。
关键区分：“沙箱”是进程级、按次的；bubblewrap 是系统级、长期安装的软件包。归因结束时删除的是前者，不是后者。

2为什么归因需要它

归因不是“读一条日志”那么简单：它把仓库内容、Session trace、Skill Prompt 交给一个会调用工具的模型进程。

威胁模型

Skill 执行时，Claude Code 在 --permission-mode bypassPermissions 下运行，模型可以调用 Bash/Read/Write 等工具。输入里包含来自目标仓库和线上 Session 的不可信文本；如果模型被内容诱导（prompt injection）去读取或写入宿主机文件，直接以 harness 账号运行就会越权。

bwrap 的作用不是“让模型更听话”，而是即使模型被诱导，它也只能在单间里活动：系统目录只读，唯一可写的是本次 attempt 目录。

宿主 / harness

沙箱外

  • /opt/harness/shared/.env
  • HE_DATA_DIR 下其他工作区
  • SSH 私钥、共享 settings、数据库
  • 其他归因 attempt 的目录
bwrap · 每次调用

沙箱内（Claude Code 能看到的世界）

  • 只读：/usr、/bin、/lib*、/etc/ssl、DNS 与 locale 等运行时文件，以及 Claude 二进制本身
  • 可写的宿主目录：仅 attribute_output/<batch>/<case>/attempt-<random>（另有 /proc、/dev 合成挂载）
  • 共享：网络（--share-net），用于模型 API
  • 隔离：mount / user / pid / ipc / uts / cgroup 命名空间
为什么不用 chroot 或容器？ 这里需要的是“每条命令、无 root、低开销、按次启动”的隔离。bwrap 正好提供了这个粒度；容器更适合长期服务，反而更重。

3一次归因的 9 步：从一个 Badcase 到一份报告

用一个具体例子走一遍。假设批次是 01M83TWE…，case 是 case-01，本次 attempt 随机名是 a1b2c3。

触发：保存绑定，或向导关闭缓存重算

LocalAttribution.attribute(item) 被调用；批次 ID 是绑定代际或本次 Run ID。

准备输出目录

创建 HE_DATA_DIR/attribute/<workspace>/attribute_output/<batch>/<case>/；后续报告与日志都落在这里。

开一个临时 attempt 目录

tempfile.TemporaryDirectory(prefix="attempt-", dir=output) → attempt-a1b2c3/。它既是工作目录，也是 bwrap 里唯一可写的宿主目录。

在 attempt 内铺好冻结输入

写入 .claude/skills/<skill>/（以及兼容入口 .cac/skills）、.platform/make_probe_report.py、input_badcase.json，并创建独立的 home/ 与 tmp/。

在内存里拼出 bwrap 命令

claude_skill._sandbox(directory, executable) 生成 argv；注意它不创建任何持久对象，只是拼参数。

bwrap 启动 Claude Code

--unshare-all --share-net --die-with-parent --new-session，把系统目录只读 bind 进来，把 attempt 目录读写 bind 进去，然后 --chdir 到 attempt 并 exec CLI。

模型在单间里工作

Claude 读取五个冻结输入、执行 Skill、调用 make_probe_report.py，把 probe_report.json 与 .platform/receipt.json 写回 attempt 目录。它看不到宿主机的其他数据。

沙箱外校验、发布报告

CLI 退出后，平台读取 receipt、校验 sha256，再用可信 writer在沙箱外按原始输入重跑一遍，确认报告不可被篡改；随后发布 probe_report.json，把本次日志写到 logs/a1b2c3/attribute_log.json。

清理 attempt，保留证据

TemporaryDirectory 退出 → 删除 attempt-a1b2c3/（含独立 HOME）。probe_report.json、logs/、attribute_log.json 都在 attempt 外，继续保留。

目录在“执行前 / 执行后”长什么样

# 执行期间
attribute_output/01M83TWE.../case-01/
├── attempt-a1b2c3/           # 唯一可写；结束后删除
│   ├── .claude/skills/...
│   ├── .cac/skills/... -> ...
│   ├── .platform/make_probe_report.py
│   ├── input_badcase.json
│   ├── home/                # 独立 HOME
│   ├── tmp/                 # TMPDIR
│   └── probe_report.json    # Skill 在沙箱内写
├── logs/a1b2c3/attribute_log.json  # 保留
├── attribute_log.json              # 保留：最近一次
└── probe_report.json               # 保留：最终报告

# 执行结束后
attribute_output/01M83TWE.../case-01/
├── logs/a1b2c3/attribute_log.json
├── attribute_log.json
└── probe_report.json
# attempt-a1b2c3/ 已被 TemporaryDirectory 删除

真实运行时，bwrap 收到的命令（简化）

# 示例用变量让长路径可读；实际参数由 _sandbox() 直接生成 argv 数组
CLAUDE=/opt/harness/shared/claude-code/current/usr/bin/claude
ATTEMPT=.../attribute_output/<batch>/<case>/attempt-a1b2c3

bwrap \
  --unshare-all          # user/mount/pid/net/ipc/uts/cgroup 命名空间
  --share-net            # 网络仍用宿主：CLI 要访问模型 API
  --die-with-parent      # API 进程退出，沙箱子进程跟着死
  --new-session          # 防止 TIOCSTI 终端注入
  --ro-bind /usr /usr \
  --ro-bind /bin /bin \
  --ro-bind /lib /lib \
  --ro-bind /lib64 /lib64 \
  --ro-bind /etc/ssl /etc/ssl \
  --ro-bind /etc/resolv.conf /etc/resolv.conf \
  --ro-bind /etc/hosts /etc/hosts \
  --ro-bind /etc/ld.so.cache /etc/ld.so.cache \
  --ro-bind /etc/nsswitch.conf /etc/nsswitch.conf \
  --ro-bind /etc/localtime /etc/localtime \
  --ro-bind "$CLAUDE" "$CLAUDE" \
  --proc /proc --dev /dev \
  --bind "$ATTEMPT" "$ATTEMPT" \
  --chdir "$ATTEMPT" \
  -- "$CLAUDE" -p --output-format json --bare \
     --session-id <uuid> --permission-mode bypassPermissions \
     --allow-dangerously-skip-permissions \
     "/attribute-badcases input_badcase.json，请分析并生成归因报告"

说明：只有存在的系统路径才会被 ro-bind；二进制按 resolve() 后的真实路径 bind。沙箱不 bind 共享 settings 文件，模型凭据通过环境变量传入。

注意：上面的命令没有 --clearenv，环境是平台构造后显式传入的；也没有把 HE_DATA_DIR 整体挂进去。bwrap 隔离的是文件系统视图，不是环境变量或网络。

4创建、维护、删除：到底删了什么？

把“bubblewrap”拆成四个层次看，就不会混淆“软件包”和“沙箱”。

长期

bubblewrap 软件包

生命周期：系统级 / 长期

由 bootstrap 的 apt-get install ... bubblewrap 安装；旧主机手工安装。升级走 apt。归因不会删除它。

一次调用

bwrap 沙箱进程

生命周期：一次 Claude CLI 调用

没有常驻守护进程，也没有“容器”需要停止。CLI 退出（或 --die-with-parent 触发）后，命名空间随进程消失。

一次归因尝试

attempt 临时目录

生命周期：一次 attempt

TemporaryDirectory 创建；正常结束（成功/异常）时删除。报告和日志在它外面，不会被一起删掉。

对照表

对象谁创建生命周期归因结束会删吗？
bubblewrap 包 / bwrap 二进制deploy/bootstrap-server.sh（旧主机手工 apt）系统级，长期不会
bwrap 沙箱（命名空间 + 进程）每次 run_skill 调用一次 CLI 调用进程退出即消失
attempt-<random>/tempfile.TemporaryDirectory一次归因尝试正常路径删除
attempt/home/、attempt/tmp/claude_skill._environment()在 attempt 内随 attempt 删除
logs/<attempt>/attribute_log.jsonLocalAttribution._write_log()每次尝试保留不会
attribute_log.json最近一次尝试的发布覆盖更新不会
probe_report.json校验通过后发布长期（报告）不会
输入归档 / Skill 快照CaseInputArchive / 快照发布长期；重试复用不会
“每次归因完就会删除吗？” 删除的是临时 attempt 目录和它里面的独立 HOME；不删除 bubblewrap 包，也不删除报告/日志/快照。
硬杀边界：如果进程被 SIGKILL，TemporaryDirectory 的清理逻辑不会执行，可能残留一个 attempt-* 目录；目前没有自动 sweeper（截至本说明），可以人工清理。由于报告和日志都在 attempt 外，残留不会影响已产出的证据。

维护方式

  • 安装：新主机由 deploy/bootstrap-server.sh 的 apt 列表安装；旧主机执行一次 sudo apt-get install -y bubblewrap，或在 root 下重跑 bootstrap（幂等）。
  • 升级：跟随系统 apt；应用本身不下载、不编译、不维护 bwrap。
  • 健康检查：API 启动与每次发布都会跑一次只读探针；探针不创建沙箱、不写盘、不需要清理。
  • 清理：旧报告目前没有按次数自动清理的机制；需要时按工作空间保留数据库与共享快照，再清理 attribute_output 中不再引用的批次。

5探针、失败码与部署门

为什么“只是缺一个包”会让整个发布在迁移前停住。

探针（只读，不建沙箱）

bwrap --unshare-all --share-net --die-with-parent \
  --ro-bind / / -- /bin/true

把整个根目录只读 bind 进来，执行 /bin/true。能退出 0，说明当前账号能创建命名空间、能完成 mount；它不启动 Claude，也不产生持久对象。

在哪跑

  • API 启动：main.py 调 skill_preflight_error()，日志 attribution.preflight；失败则 runtime_enabled=false，绑定 worker 不启动，页面显示“归因未运行”。
  • 发布：release.sh 在 Alembic 迁移与切换 current 之前，用候选 API 跑 app.third_party_api.ai_agent.preflight；失败立即中止并恢复 .env。
错误码含义典型处置
ATTRIBUTION_BWRAP_MISSINGshutil.which("bwrap") 找不到二进制；包没装或 PATH 不可见安装 bubblewrap；用 deploy/harness 账号复跑探针
ATTRIBUTION_BWRAP_UNUSABLE找到了二进制，但命名空间探针非 0（权限/内核策略/AppArmor 限制）检查 unprivileged user namespace、AppArmor、服务账号权限
ATTRIBUTION_PROVIDER_UNSUPPORTED当前 Provider 不实现 Skill 能力切到支持 Skill 的 Provider
ATTRIBUTION_CONFIG_INVALIDSettings 校验失败（不打印环境值）检查 AI_AGENT_PROVIDER 等配置
为什么当前部署会失败？ AI_AGENT_PROVIDER=claude-code，发布预检要求 bwrap；这台机器是 11-09 初始化的旧主机，早于 PR #421 把 bubblewrap 加进 bootstrap，因此从未装过。PR #543 只是把“缺失”从运行时问题提前成了发布门，让旧版本继续服务，而不是带病切换。
修复顺序：root 安装 → 用 deploy（发布预检账号）和 harness（服务账号）分别跑探针 → 重跑 Deploy。若明确只要“仅缓存”部署，可把 Provider 设为 fake，预检会以 cache_only=True 放行，但不会执行真实归因。

一页总结

bubblewrap 是“按次进程沙箱”：每次归因执行 Claude Code 时，把系统目录只读挂入、把 attempt 目录读写挂入，再执行 CLI；不是常驻容器。

删的是 attempt：正常结束删除 attempt-<random> 与独立 HOME；probe_report.json、logs/、attribute_log.json 保留。bwrap 包本身由 apt 长期维护。

当前阻塞是主机缺包：PR #543 的发布预检在迁移前拦截；装一次 bubblewrap，用 deploy/harness 验证探针，再重跑 Deploy。
