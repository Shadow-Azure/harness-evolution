## 1. 一页速览

一句话：这是给会话树装一排“体检仪表”，不是换发动机——只把执行闭环、关系置信度、对象 revision、定义指纹和文件读取证据变成可存储、可返回的稳定字段，真正填表留给 M9-02/M9-03/M9-04。

比喻：以前的 `session_families.status` 像“体检报告上只有一个总评”；这次新增的 `execution_outcome` 是单独一栏“这次任务到底跑完没有”，两者不能互相覆盖。证据字段则像化验单上的项目和条码，只存编号与哈希，不存化验原液（消息、工具输出、定义正文）。

| 交付块 | 内容 | 风险 |
|---|---|---|
| 数据库 | 0016 加列、默认 `legacy_unknown`、可空证据列、SQLite/MySQL 双方言、列级重试守卫 | 加列在 MySQL 大表上会有 DDL 成本 |
| API 契约 | `runtimeKey`、`executionOutcome`、`endReason`、`agentDefinitionHash`、`definitionSource`、事件证据字段 | 新增必填字段是破坏性增量 |
| 封闭状态 | `Literal` 声明，服务层用 `get_args` 派生校验集合 | 脏数据会让整页 500（见 §6 讨论点 1） |
| 测试 | 迁移回填/重跑/部分 DDL、DTO 字段与非法值 | MySQL 回填只在 CI mysql lane 间接覆盖 |

验证基线（本 PR 实际执行）：

## 2. 架构导览

### 2.1 迁移：只在缺失时加列

`0016_trace_evidence_contract.py:51-73` 先 `inspect` 目标表已有列，再对缺失列执行 `op.add_column`。这比直接 `op.add_column` 多了一层保护：MySQL 的 DDL 会自动提交，若迁移在加完一部分列后失败，Alembic 版本号仍停在 0015，下次重跑会从 0016 开始；没有守卫就会在已存在的列上重复加列而失败。

`execution_outcome` 用 `NOT NULL + server_default='legacy_unknown'`（`0016:23-31`、`0016:33-40`），SQLite 与 MySQL 都会用默认值填充已有行，因此不需要额外的 `UPDATE`。可空的 `end_reason`、hash、`read_complete`、`relation_confidence` 对存量保持 NULL。`runtime_key` 与 `parser_version` 完全没动，符合 m9-01 的“不重复建 runtime 表”。

降级同样按存在性过滤（`0016:78-95`），SQLite 走 batch 重建，MySQL 直接 drop。

### 2.2 读模型：三张表到三个 Record

`apps/api/app/db/crud/sessions.py:26-82` 的 `SessionRecord / AgentRecord / EventRecord` 各增加对应字段，`_session_record`、`_agent_record`、`_event_record` 从 `select(table)` 的全列映射里取值。因为查询本来就是 `select(session_families)` / `select(agents)` / `select(agent_events)`，新增列不需要改 SQL，只需要改 Record 和映射；`ProblemRepository` 复用同一组 mapper，也不会漏字段。

### 2.3 API 契约：封闭枚举 + 按需返回

`apps/api/app/service/sessions/schemas.py:14-33` 用 `Literal` 定义四个状态集合，并用 `get_args` 生成 `frozenset` 给服务层校验，避免枚举值在 schema 与 service 各写一份后漂移。

- 列表项新增 `runtimeKey`、`executionOutcome`（`schemas.py:63-68`）。
- Agent 节点新增 `executionOutcome`、`endReason`、`agentDefinitionHash`、`definitionSource`（`schemas.py:148-159`）。
- 事件可选返回 `objectRevision`、`definitionHash`、`fileReadHash`、`readComplete`、`relationConfidence`（`schemas.py:93-130`），全部用 `exclude_if=_missing`，未记录时不序列化，符合 05 API 设计“只在存在时返回”。

`SessionTree` 根级补 `runtimeKey`（`schemas.py:200`），与 05 §3.2 的示例一致。

### 2.4 服务：映射与封闭校验

`apps/api/app/service/sessions/service.py:121-139` 的 `_closed` / `_optional_closed` 把数据库字符串收窄到 DTO 的封闭集合；`_list_item`（`service.py:69-100`）和 `_agent`（`service.py:141-210`）分别映射 Session 与 Agent/事件。`SessionTree` 的 `runtime_key` 来自 `snapshot.session.runtime_key`（`service.py:338`）。

这是“读时校验”而不是“写时约束”：数据库列仍是 `VARCHAR`，没有 CHECK；非法值会在读取时变成 500（`_closed` 抛 `AppError`），这是有意的 fail-closed，代价见 §6 讨论点 1。

### 2.5 边界：不解析新证据

本 PR 没有改 `service/acquisition/**`、parser 或 replay。所有新列在归一化写入前保持默认值/NULL。也就是说，升级后现有会话会显示 `executionOutcome=legacy_unknown`，前端必须把它当“未知”，不能当“完成”。

## 3. 数据流走查

剧本：升级数据库 → 归一化写会话 → 读列表/树 → 生成契约。

1. 应用启动调用 `upgrade_database`（`apps/api/app/db/migrate.py:17`），Alembic 从 0015 走到 0016；已有 `session_families`、`agents`、`agent_events` 行由加列默认值得到 `legacy_unknown`/NULL。
2. 归一化沿用现有写入路径（本 PR 不碰）：插入 `session_families` 时没有提供新列，SQLAlchemy 让数据库 server default 生效；因此新会话同样是 `legacy_unknown`。
3. `GET /api/sessions` 走 `SessionRepository.list_sessions` → `select(session_families)` 全列 → `_session_record` → `_list_item`。响应多出 `runtimeKey` 与 `executionOutcome`，其余统计与既有字段不变。
4. `GET /api/sessions/{id}/tree` 走 `tree_snapshot` → `AgentRecord`/`EventRecord` → `_agent`。Agent 返回执行闭环字段；事件证据字段为 NULL 时不出现。
5. `pnpm contract:generate` 从 FastAPI 导出 OpenAPI，再生成 `api.d.ts`；Web 只做类型同步，不改变任何页面行为。

真实例子：升级后打开一个旧 Session，列表卡会显示“解析状态 ok、执行闭环 legacy_unknown”；事件卡不会凭空出现 revision 或关系置信度，因为还没有写入方。这正是 m9-01 的交付边界。

## 6. 讨论点

### 讨论点 1：一条脏枚举值会让整个会话列表 500

- **位置**：`apps/api/app/service/sessions/service.py:121-139`
- **现象**：`_closed` 对数据库里的字符串做封闭集合校验，非法值抛 `AppError(500)`；列表页只要有一行 `execution_outcome` 被外部写坏，整页就不可用。
- **问题**：读路径应该 fail-closed 还是降级为 `legacy_unknown` 并告警？现有 `_task_kind` 也是 fail-closed（`service.py:107-119`），但列表页的爆炸半径比单棵树大。
- **预判**：当前写法能最快暴露数据漂移，且新列写入方还没上线，短期风险低；若 M10 之后出现多写入方，建议改为“记录 warning + 回退 legacy_unknown”，避免一个坏行拖垮整页。
- **结论**：

### 讨论点 2：证据字段先于写入方进入公开契约

- **位置**：`apps/api/app/service/sessions/schemas.py:93-130`
- **现象**：事件证据字段在 m9-01 就出现在 OpenAPI/TS 里，但 m9-02/M9-04 才会写；当前所有响应都不会返回它们。
- **问题**：是否应该等写入方就绪再暴露字段？先暴露的好处是前端和契约一次到位，坏处是“字段存在但永远为空”的窗口期。
- **预判**：m9-01 的职责就是契约先行，且字段是可选的（不出现），对现有消费者无影响；保留。
- **结论**：

### 讨论点 3：文件读取的 path/range 没有落库

- **位置**：`apps/api/alembic/versions/0016_trace_evidence_contract.py:42-47`；`plans/fullstack-design/06-database-design.md:269-270`
- **现象**：本 PR 只落 `file_read_hash` 与 `read_complete`，没有 path/range 列；m9-01 issue 的目标段落提到 path/range。
- **问题**：是设计遗漏，还是有意分给后续 issue？06 只定义 hash/complete；m9-05 才定义知识文档的 `source_path`。
- **预判**：按“实现冲突以链接设计章节为准”，0016 不应自造列；M9-02 的 parser 证据可以先把 path/range 放在证据结构里，等 M9-05 需要查询时再建列。
- **结论**：

### 讨论点 4：部分 DDL 守卫最初只处理“列缺失”（已加固）

- **位置**：`apps/api/alembic/versions/0016_trace_evidence_contract.py:51-62`
- **现象**：初版守卫只检查列名；复核时用一个临时 SQLite 探针手工预建了可空的 `session_families.execution_outcome`，再升级到 head，迁移会静默成功，但该列保持可空/无默认值，读路径随后会 500。
- **问题**：是否需要校验列的 nullability/default，而不只是存在性？
- **预判**：真实半成品只会是“部分列已加、部分没加”（单条 `ADD COLUMN` 原子），但手工热修/带外迁移可能留下错误定义；让迁移直接报错比让读路径 500 更可控。
- **结论**：已决（2026-11-16）：`_add_columns` 现在校验已存在列的 nullability，定义漂移抛 `RuntimeError`；新增 `test_evidence_migration_rejects_wrong_existing_definition` 覆盖。

## 9. 文件级代码分析

### 9.1 `apps/api/alembic/versions/0016_trace_evidence_contract.py`（A）

职责：一次迁移把 M9 需要的 12 个列加上，并保证双方言可重跑。

变更思路：

```python
# 之前：没有这个 revision，0015 的 head 直接结束
# 现在：先 inspect 现有列，只加缺失列
existing = _column_names(table)
for column in columns:
    if column.name not in existing:
        op.add_column(table, column)
```

为什么这么写：MySQL 的 DDL 自动提交，失败重试是真实运维场景；`op.add_column` 本身不幂等，所以幂等性要由迁移代码提供，而不能只依赖 `alembic_version`。

检视发现：初版只复核列存在性；复核后已增加 nullability 校验，定义漂移会直接报错（见讨论点 4）。

### 9.2 `apps/api/app/db/models/domain.py`（M）

职责：让 SQLAlchemy 元数据与 06 表设计一致。

```python
# 之前：session_families 只有 status / skill_names ...
# 现在：status 后插入 execution_outcome（NOT NULL default legacy_unknown）和 end_reason
```

`agents`、`agent_events` 同样按 06 的列顺序补；没有新索引，因为设计没有要求。风险：`execution_outcome` 的 server default 会让所有新写入默认 `legacy_unknown`，直到 M9-02 显式写入。

### 9.3 `apps/api/app/db/crud/sessions.py`（M）

职责：把新列带进读模型，不改变查询。

```python
# 之前：SessionRecord 没有 runtime_key/execution_outcome
# 现在：Record 增字段，_session_record 从 row 取值
```

因为查询是 `select(table)` 全列，新增字段对 SQL 零改动；`ProblemRepository` 复用 mapper，自动获得新字段。

### 9.4 `apps/api/app/service/sessions/schemas.py`（M）

职责：公开契约的封闭枚举与可选证据字段。

```python
ExecutionOutcome = Literal["completed", "interrupted", "failed", "legacy_unknown"]
EXECUTION_OUTCOMES: frozenset[str] = frozenset(cast(tuple[str, ...], get_args(ExecutionOutcome)))
```

`exclude_if=_missing` 让未记录的证据不出现在 JSON 中，避免“字段存在但全 null”的噪声；代价是字段在 OpenAPI 中是可选的，前端需要按可选处理。

### 9.5 `apps/api/app/service/sessions/service.py`（M）

职责：Record → DTO，并把数据库字符串收窄到封闭集合。

```python

# 现在：execution_outcome/end_reason/agent_definition_hash/definition_source + 事件证据
```

`_closed` 的 500 行为见讨论点 1；`runtime_key` 从 `snapshot.session` 取，避免树根重复查询。
