## §1 一页速览

一句话：把生产登录页从“前台小窗口”升级成原型里的“门厅导览牌 + 前台登记台”——左边告诉你这栋楼能做什么（工作空间隔离、归因、默认 10 个 Session），右边才是登记的地方（用户名/密码）。

比喻里最关键的一刀：原型右栏那排账号按钮像“把全体员工工牌挂在门厅”，谁路过都能点名；本 PR 只搬信息层级，不搬工牌，生产页面对账号目录一无所知。

| 交付块 | 内容 |
| --- | --- |
| 布局 | 桌面 `min(920px, 100%)` 双栏（1.02fr / 0.98fr），≤760px 单列 |
| 左栏 | 品牌锁排 + 三条产品事实 + 内部部署页脚；无焦点元素、无用户数据请求 |
| 右栏 | 登录标题、`LoginForm`、首次改密提示；错误仍为内联 `role=alert` |
| 安全边界 | 不渲染账号、邮箱或可点选账号；不读取用户目录；登录 API/Cookie/改密/守卫不变 |
| 视觉 | 背景、圆角、边框、间距来自 `tokens.css`；新增大卡片阴影 token |
| 验证 | 组件测试 5 例、E2E 3 例、m1 回归 5 例、类型/lint/style/build/bundle/docs/flow 全绿 |

## §2 架构导览

### 2.1 入口与布局归属

`/login` 路由带 `authLayout` 元信息，`App.vue` 据此不渲染顶栏，把 `Index.vue` 放进 `main.auth-main`。本 PR 只改 `Index.vue`，不动 `App.vue`、路由守卫和 `LoginForm`（`apps/web/src/pages/login/Index.vue:1-86`）。

### 2.2 左栏：静态产品事实

左栏是 `<section aria-labelledby="login-brand-title">`，标题 `工作空间 · 归因 · 进化`（`Index.vue:28-35`），下面三条 `<li>` 分别对应 issue 要求的工作空间隔离、对象级归因、默认 10 个 Session（`Index.vue:36-61`）。文案全是静态字符串，没有任何 composable、store 或 API 调用；这是“无账号枚举”的结构性保证，而不是靠 CSS 隐藏。

移动端只隐藏长说明和页脚（`Index.vue:270-273`），品牌、标题、摘要仍保留，和 issue 的“压缩为品牌与简短能力摘要”一致。

### 2.3 右栏：复用登录状态机

右栏把原有 `LoginForm` 原样放进 `form-body`（`Index.vue:77-79`），自身只负责标题、说明与首次改密页脚。`LoginForm.vue` 的 `useLogin`、错误码映射、禁用/加载态、自动补全属性一行未改，因此提交、错误、强制改密回跳的语义仍由既有实现负责。

### 2.4 视觉与 token

卡片阴影 `--shadow-auth-card` 落在 `tokens.css:58`，值是原型的 `0 22px 70px rgb(24 35 55 / 12%)`。其余背景/边框/圆角/间距都用既有 token；`verify:web-style` 通过说明 Vue 组件内没有新增字面色值。左侧渐变用 `color-mix` 混合 `var(--blue)`/`var(--purple)` 与 `var(--bg-card)`，没有引入第二套颜色。

### 2.5 测试分层

- 组件层 `Index.test.ts:68-103`：断言双栏区域、可访问标题、能力文案、无账号/邮箱、焦点顺序。
- E2E 层 `m12-11-login-v2-layout.test.mjs`：真实 API + Vite proxy + headless Chrome，覆盖 1408px 双栏、390px 单列、无横向溢出、无账号目录、Tab 顺序与可见焦点、错误凭据的内联播报。

## §3 数据流走查

一条登录主线的实际路径（本 PR 只改第 2 步的渲染）：

1. 浏览器打开 `/login`。路由守卫探测会话，调用 `GET /api/auth/session`（未登录时 refresh 返回 401，属于预期噪声）。
2. 渲染 `Index.vue`：左栏静态文案 + 右栏 `LoginForm`。这一步不请求 `/users` 或 `/members`，E2E 用 `Network.requestWillBeSent` 断言过。
3. 用户按 Tab：左栏无 focusable → 用户名 → 密码 → 登录按钮；输入获得 EP 的 `is-focus` 阴影，按钮获得 `:focus-visible` outline。
4. 提交：`LoginForm` 调 `useLogin`；失败时 `AUTH_INVALID` 映射成 `用户名或密码错误`，由 `role=alert` + `aria-live=polite` 播报。
5. 成功：既有逻辑恢复 `auth/session`、写 `stores/auth`、跳 `redirect ?? 最近空间总览`；本 PR 未改这条链。

## §6 讨论点

### 6.1 issue 状态停在 `ready` 而不是 `in-progress`

- **位置**：`.agents/flow/issues/m12-11-login-v2-layout.md:12`
- **现象**：本 PR 把 m12-11 从 `backlog` 推进到 `ready`，没有标 `in-progress`。PR 描述里也写明了原因。
- **问题**：m12 的 P1 档仍有 2 个未 done 的 issue（m12-09、m12-10）；m12-08 已在本 PR 对齐为 done。`verify-flow` 的优先级推进规则只允许 P2 在“最高未清档仅剩 1 个未 done”时进入 `in-progress`/`done`。若标 `in-progress`，CI 的 `verify-flow --diff` 会红。
- **预判**：保持 `ready` 能合法挂 PR；等 m12-09/m12-10 收尾、P1 只剩 1 个后，再用独立 close PR 标 `done`。代价是 issue 状态与实际开发进度有一段可见偏差，需要维护者接受。
- **结论**：

### 6.2 1440px 出现纵向滚动条

- **位置**：`apps/web/src/pages/login/Index.vue:90` 与 `apps/web/src/App.vue:105-112`（`main` 的 `padding: 20px 0 64px`）
- **现象**：1440×900 截图右侧有纵向滚动条；`.auth-page` 是 `min-height: 100vh`，外层 `main` 还留 64px 下内边距，两者相加超过视口。
- **问题**：视觉上不如原型的整屏留白干净；但横向无溢出，功能无影响，且 main 分支的旧登录页同样存在。
- **预判**：这是既有布局问题，不是本 PR 引入；`App.vue` 不在本 issue 的 scope 内，强行改会把登录页改动扩成全局布局改动。建议单独修 `main.auth-main` 的下内边距（或给 auth 布局去掉 `main` 的默认 padding），本 PR 不动。
- **结论**：

### 6.3 E2E 用固定宽度区间锁双栏

- **位置**：`tests/e2e/m12-11-login-v2-layout.test.mjs:201`
- **现象**：断言 1408px 下卡片宽度落在 900–940px，左右栏宽都大于 400px。
- **问题**：如果将来设计决定调整卡片宽度（例如 960px），测试会先红；这是“把原型基线钉进测试”的代价。
- **预判**：可接受。双栏比例和卡片宽度是本 issue 的核心验收对象，锁住它比松散的“左右不重叠”更能防止回退；调整设计时同步改常量即可。
- **结论**：

## §9 文件级代码分析

### 9.1 `apps/web/src/pages/login/Index.vue`

职责：登录路由的唯一页面壳，负责双栏结构与静态产品文案，登录行为委托给 `LoginForm`。变更形态：重写模板与样式，脚本部分未变。

旧模板（`origin/main`）是一个 420px 的 `article.auth-card`，从上到下堆品牌、`SESSION` 眉题、`登录` 标题、`LoginForm`、页脚；没有左右分栏，也没有能力说明。

新模板把同一张卡拆成两个命名区域：左栏用 `<section aria-labelledby="login-brand-title">` 承载品牌、`h1` 和三条 `<li>`；右栏用 `<section aria-labelledby="login-form-title">` 承载 `h2`、说明、`LoginForm` 与页脚。两栏各自有可访问名称，读屏可以先听到“区域名”再进入内容。

样式上，桌面用 `grid-template-columns: 1.02fr 0.98fr` 接近原型的 1.02/0.98 比例（`Index.vue:108-117`）；左栏渐变与原型一致（`Index.vue:119-129`）；`≤760px` 单列并隐藏长说明（`Index.vue:259-278`），`≤420px` 收窄页面内边距（`Index.vue:280-284`）。无动画，不涉及 `prefers-reduced-motion`。

实现思路总结：结构语义化、文案静态化、视觉 token 化；登录行为完全不动。

检视发现：无阻断项。已知弱点见 §6.2（外层 padding 造成的纵向滚动）。

### 9.2 `apps/web/src/pages/login/Index.test.ts`

职责：组件级回归。新增三例——双栏区域与 `h1` 唯一性、无账号/邮箱/演示账号文本、DOM 焦点顺序；保留原有错误凭据与成功回跳两例。

关键点：焦点顺序断言直接查询 `input, button` 的 DOM 顺序，而不是模拟 Tab；真实 Tab 行为交给 E2E。这样组件测试不依赖浏览器焦点实现，E2E 负责浏览器语义。

检视发现：无。

### 9.3 `tests/e2e/m12-11-login-v2-layout.test.mjs`

职责：真实 API + Vite proxy + headless Chrome 的跨栈验收。三个测试各自启动/关闭独立 Chrome，共享一套 API/Web 夹具。

关键点：

- 桌面场景断言卡片宽度、左右栏边界、能力文案、账号数为 0、按钮只有登录、输入只有 username/password，并用 `Network.requestWillBeSent` 确认没有 `/users` 或 `/members` 请求（`test:186-233`）。
- 390px 场景断言单列、卡片不越界、长说明 `display: none`、无横向溢出（`test:235-256`）。
- 键盘场景先填值让提交按钮可用，再按 Tab 三次并读取 `document.activeElement`；随后检查输入框 `is-focus` + `box-shadow`、按钮 `outlineStyle/outlineWidth`（`test:270-359`）。
- `expectedLogEntry` 只放过 `/api/auth/refresh` 与 `/api/auth/login` 的预期 401，其它 console/网络错误仍会让测试失败。
