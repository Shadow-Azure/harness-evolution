## §1 一页速览

一句话：给工作空间加四块只读总览数据——指标条（summary）、时间趋势（trend）、来源分布（sources）与可筛选分页列表（bad-cases）；四者共用一套 Asia/Shanghai 闭区间时间窗、一套对象多选解析和一套窗口/粒度错误码，趋势的“哪些桶存在、每个桶怎么算”收敛到纯函数。

一个比喻：这套接口像同一个检票口的四台闸机。summary 是门口的计数器，trend 是按天/周/月排好的连续货架（没货也要留空格），sources 是按来源分好的堆，list 是能按条件翻的明细单。四台闸机必须认同一张车票（同一个 `window`），否则会出现“封面写 6 件、货架摆 5 件、明细 7 行”的自相矛盾；`objects` 多选则像“只看这几条通道”，但通道牌（`objects` 选项）不能因为你看了一条就消失。

## §2 架构导览

### 2.1 四个端点、一个查询对象

四个 handler 都声明 `wid: WorkspaceId`、`access: Annotated[WorkspaceAccess, Depends(require_workspace_role("viewer"))]`，并把 `access.workspace_id`（而不是路径里的 `wid`）传给服务层（`apps/api/app/api/overview.py:113-121`、`:139-148`、`:167-175`、`:193-204`）。这和 m7/m8 的读路径一致：空间作用域由授权依赖解析出来，handler 只消费结果。

参数别名集中在模块顶部：`from`/`to`（`date | None`）、`range`（`int | None`，OpenAPI 用 `json_schema_extra` 声明 7/30/90）、`objects`（`list[str] | None`）、`grain`（`Grain = Literal["day","week","month"]`）、`badCaseType`（`Literal["all","self","discovery"]`）、`page`/`pageSize`（修复后见 `apps/api/app/api/overview.py`）。`_query()` 把原始参数装成冻结的 `OverviewQuery`，其中 `objects` 已由 `parse_object_filter()` 解析为元组；列表端点额外把 `BadCaseListQuery(window=…, bad_case_type=…, page=…, page_size=…)` 交给服务。

代价是参数校验时机不统一：`range`/窗口组合在服务层报专用错误码；`grain` 由 FastAPI 按 `Literal` 校验，但 `OverviewRoute` 把它映射回 `GRAIN_INVALID`；`page`/`pageSize`/`badCaseType` 由 FastAPI 直接报通用 `VALIDATION_INVALID`。读契约的人要知道 422 有两条来源（见 §6.6，修复后 `grain` 仍保持专用码）。

### 2.2 窗口是纯函数，边界规则只有一份

`resolve_window()`（`window.py:99-145`）顺序做七件事：校验 `grain` → 校验 `from > to` → 校验“单边界必须带 range” → 解析 range → 解析边界 → 校验跨度 → 决定有效粒度。边界规则（`:76-96`）：

```python
if date_from is not None and date_to is not None:
    return date_from, date_to
if date_from is not None:
    return date_from, date_from + timedelta(days=range_days - 1)
if date_to is not None:
    return date_to - timedelta(days=range_days - 1), date_to
return today - timedelta(days=range_days - 1), today
```

这个顺序把“显式双边界优先于 range”和“单边界必须显式 range”同时表达出来。实测：`from=2026-11-01&range=7` → `[11-01, 11-07]`；`to=2026-11-01&range=7` → `[10-26, 11-01]`；只给 `from` 不给 range → `422 WINDOW_INVALID`（`reason` 明确写“a single boundary requires an explicit range”）。默认窗口 `[today-89, today]`，与 05 §3.10 的示例窗口 2026-08-13..2026-11-10（正好 90 天）一致。

粒度降级只有一行（`:142-144`）：`grain == "day" and span_days > 92 → week`；92 天保持日粒度，93 天降级。周/月永不降级。响应里的 `grain` 是 `window.grain`（`service.py:191-204`），不是请求值。

### 2.3 桶 walker：只返回相交桶，标签随粒度

`bucket_start()` 把任意本地日映射到桶首：日=原日、周=`day - weekday()`（ISO 周一）、月=`day.replace(day=1)`（`window.py:148-154`）。`bucket_starts()` 对日粒度直接铺 `span+1` 天；对周/月粒度从“包含 start 的桶”开始按 7 天/下月 1 日推进，直到桶首超过 end（`:166-176`）。因此首桶可以早于 `window.start`（窗口从周三开始时，首桶是周一），这是“与窗口相交”而不是“落在窗口内”。

`bucket_label()` 日/周输出 `MM-DD`，月输出 `YYYY-MM`（`:179-183`）。`bucket` 字段仍是完整 ISO 日期，所以跨年周的 `12-29` 不会失去年份信息。§1 的 105,198 窗口性质测试覆盖了闰日、月末、跨年、跨月、周日夜/周一凌晨等边界，没有发现空桶、重复桶、漏日或“末桶之后仍相交”的情况。

### 2.4 聚合在一条 SQL 行里出，分桶在 Python 里做

`OverviewRepository.counts()`（`crud/overview.py:130-179`）用一条 `SELECT` 同时取五件事：

```python
select(
    func.count().label("bad_cases"),
    func.coalesce(func.sum(_flag(bad_cases.c.bad_case_type, "self")), 0).label("self_cases"),
    func.coalesce(func.sum(_flag(bad_cases.c.bad_case_type, "discovery")), 0).label("discovery_cases"),
    func.count(func.distinct(bad_cases.c.bad_case_session_id)).label("sessions"),
    func.count(func.distinct(bad_cases.c.object_name)).label("sources"),
)
```

条件由 `_case_conditions()` 统一构造（`:86-104`）：`workspace_id == :wid`、`created_at >= day_start(start)`、`created_at < day_start(end+1)`、可选的 `object_name IN (...)` 与 `bad_case_type == ...`。`_flag()` 用 `CASE WHEN … THEN 1 ELSE 0 END` 而不是 `FILTER (WHERE …)`，是为 SQLite/MySQL 双方言交集做的取舍（Note Alternatives 第 1 条）。

`sources()` 复用同一组条件，按 `object_name` 分组，排序 `total DESC, object_name ASC`（`:269-316`）。趋势只取窗口内的 `(created_at, bad_case_type)` 行（`:233-267`），由 `OverviewService.trend()` 在 Python 里落桶并补零（`service.py:177-204`）。列表的 `count_cases()` 与 `page_cases()` 复用同一条件构造器（`:318-396`），结构上保证 `total` 与 `items` 的分母一致。

### 2.5 对象多选解析：一次 split + 一次去重

`parse_object_filter()`（`service.py:73-98`）先展开每个参数里的逗号，再 `strip()`、丢空、按首次出现去重，最后对“去重后的数量”判 50 上限：

```python
for raw in values:
    for part in raw.split(","):
        name = part.strip()
        if not name or name in seen:
            continue
        seen.add(name)
        selected.append(name)
if len(selected) > MAX_OBJECTS:  # 50
    raise AppError(422, ErrorCode.OBJECT_FILTER_TOO_LARGE, ...)
```

这解释了为什么 `?objects=a&objects=a,a` 合法（去重后 1 个），而 51 个不同名字才 422。`objects` 为空元组时 `_case_conditions()` 不加任何对象谓词，等价“全部”。

### 2.6 DTO 与 camelCase：`from`/`to`、`self`/`discovery` 是显式别名

所有 DTO 继承 `IdentityModel`（`alias_generator=to_camel, populate_by_name=True, extra="forbid"`，`apps/api/app/service/identity/schemas.py:11-13`），所以 `bad_cases → badCases`、`page_size → pageSize` 自动完成；三个会撞 Python 关键字的字段用显式别名：

```python
date_from: date = Field(validation_alias="from", serialization_alias="from", ...)
date_to: date = Field(validation_alias="to", serialization_alias="to", ...)
self_cases: int = Field(validation_alias="self", serialization_alias="self", ge=0)
```

（`schemas.py:17-26`、`:33-38`、`:66-71`、`:93-98`）。实测响应确实是 `{"window":{"from":…,"to":…}}` 与 `totals.self`/`buckets[].discovery`，不是 `dateFrom`/`selfCases`。

### 2.7 外部表探测：一次探测、进程级缓存

`_table_present()` 用 `inspect(connection).has_table(name)` 探测外部表，结果缓存在 repository 实例的 `_presence` 字典里（`crud/overview.py:113-128`）。三个读路径入口短路：`counts()`/`object_options()`/`trend_points()`/`sources()`/`count_cases()`/`page_cases()` 在 `bad_cases` 缺失时返回 0/空；`_attribution_counts()` 在 `bad_case_analysis` 或 `probe_reports` 缺失时返回空字典（`:398-405`）。这与 m8-02 的 `_scoped_reads_available` 同构。

缓存是进程级的，`OverviewService`/`OverviewRepository` 只在 `create_app()` 时构造一次（`main.py:236`、`:473`），所以“运行中建表/删表”要重启才会重新探测（§6.7）。

### 2.8 契约生成与错误码

`main.py` 只加三行：导入、`OverviewService(OverviewRepository(...))` 装配、`app.include_router(overview_router)`（`:25`、`:41`、`:103`、`:236`、`:473`、`:523`）。`errors.py` 只加三个 StrEnum 成员（`:90-92`）。`packages/contracts/openapi.json` 与 `api.d.ts` 由 `pnpm contract:generate` 生成，`pnpm contract:check` 通过说明生成物与 FastAPI 源一致。

## §3 数据流走查


## §6 讨论点

### 6.1 `bad_case_type` 的值域没有在写入侧收紧：列表 500、summary/trend 口径自相矛盾（bug / P2）

- **位置**：`apps/api/app/service/overview/schemas.py:114`（`bad_case_type: BadCaseType`，`BadCaseType = Literal["self","discovery"]`）；`apps/api/app/service/overview/service.py:123`（`cast(BadCaseType, row.bad_case_type)`）与 `:106-108`（`_label` 对未知类型会回退成原名，但随后的 DTO 校验会先失败，fallback 救不了响应）；`apps/api/app/db/crud/overview.py:150-158`（`badCases` 数全部行，`self`/`discovery` 只数两类）；`apps/api/app/service/overview/service.py:187-190`（未知类型既不进 `self` 也不进 `discovery`，`total` 只由二者相加）；写入侧 `apps/api/app/third_party_api/bad_case_query/models.py:18`（`bad_case_type: str`，仅长度约束）与 `apps/api/app/service/acquisition/bad_case_catalog_sync.py:67`（原样写库）。
- **现象**：我在临时库插入 `self` / `regression` / `SELF` 三条同空间 case，实测 summary 返回 `badCases=3, self=1, discovery=0`，trend 的 `Σ total=1`，而 `GET …/bad-cases` 直接抛 `pydantic.ValidationError`（`bad_case_type` 不是 self/discovery），HTTP 层 500。44 条 API 用例只覆盖 `self`/`discovery`（`test_overview_api.py:1349` 只验证查询参数里的非法值，不验证库里的行）。
- **问题**：DTO 把“上报协议里的闭集”当成“数据库里的闭集”。`bad_case_type` 列只有 `String(16) NOT NULL`，没有 CHECK；ingest 路由确实用 `Literal` 校验（`apps/api/app/service/workspaces/ingest.py:37`），但 legacy 目录同步是另一条写入路径，上游模型只限长度。结果是：一条 malformed 行就让整个空间的总览列表不可用；即使不 500，summary 的 `badCases` 也不等于 `self + discovery`，trend 的柱子和指标条对不上，08 §6.1 的六格 StatStrip 会显示“3 / 1 / 0”，与设计示例的“总数 = 两类之和”矛盾。代码库里同类字段已有降级先例：`apps/api/app/service/bad_cases/service.py:48-50` 的 `_literal()` 把越界值变成 `None` 并挂 `EXTERNAL_FIELD_INVALID` 警告，overview 却选择了硬失败；`sessions/service.py:172` 也是同样的 `cast` 写法，说明这是既有模式的复制而不是新发明。
- **预判**：两个方向，二选一或都做：写入侧在 catalog sync 里用 `_literal`/白名单把越界类型归一或拒绝（并对存量行做一次排查），读取侧至少让列表不 500——`bad_case_type: str` + `_label` fallback 返回原名，或复用 V1 的降级警告；同时明确“未知类型是否计入 `badCases`/`sessions`/`sources`”，否则指标条仍然自相矛盾。补一条“插入未知类型仍 200、且数字口径有定义”的用例。当前 catalog sync 默认关闭、前端未落地，故不是合并阻塞，但在 m8-04 接页面之前应定稿。
- **结论**：2026-11-16 已修：`_case_conditions()` 增加共享谓词 `bad_case_type IN ('self','discovery')`，summary/trend/sources/object options/list 一致排除越界类型，`used` 仍数空间全部行；新增 `test_unknown_bad_case_type_rows_are_excluded_consistently`（直插 `regression` 行后 list 200、summary `badCases=6=self+discovery`、trend 总和 6、`used=8`）。排除规则写进 Note 与 05 §3.10/§4.18、06 §7.5。写入侧归一仍留给后续（legacy 目录同步默认停用），本次只保证读取侧不再 500、口径不再分叉。

### 6.2 极端日期触发未捕获的 `OverflowError`：三种合法参数组合直接 500（bug / P2）

- **位置**：`apps/api/app/service/overview/window.py:92-95`（`date_from + timedelta(days=range_days - 1)` 与 `date_to - timedelta(...)`）；`apps/api/app/db/crud/overview.py:98`（`day_start(end + timedelta(days=1))`）；跨度校验在 `window.py:135-141`。
- **现象**：实测 `?from=9999-12-31&range=7`、`?to=0001-01-01&range=7`、`?from=9999-01-01&to=9999-12-31` 都在窗口解析或首条 SQL 前抛 `OverflowError: date value out of range`，ASGI 层未捕获，表现为 500；`?from=0001-01-01&range=90` 正常 200。365 天的 9999 年窗口能通过“≤366 天”校验，随后死在 `end + 1 day`，所以跨度上限并不能兜住。
- **问题**：用户输入把 422 变成 500，违反本 PR 自己建立的“不可用窗口 → `WINDOW_INVALID` 422”契约；FastAPI 的 `date` 解析接受 1..9999 年，没有任何一层把日期钳在业务可表达范围。虽然需要登录且输入荒谬，但这是一个确定性的崩溃类，未来任何“按窗口循环/加一天”的代码都会复制同一个坑。
- **预判**：在 `resolve_window()` 里加显式日期范围（如 `MIN_DATE=1970-01-01`、`MAX_DATE=2999-12-31`，或至少 `date.max - 1`）并返回 `WINDOW_INVALID`，或在 `day_start(end + 1)` 处捕获 `OverflowError` 转 422；补三条用例（最大年、最小年、单边界跨年）。成本约五行，建议本 PR 顺手修。
- **结论**：2026-11-16 已修：`resolve_window()` 把边界收敛到 `1970-01-01..2999-12-31`，并把 `_resolve_bounds` 的 `OverflowError` 转成 `422 WINDOW_INVALID`；`from=9999-12-31&range=7`、`to=0001-01-01&range=7`、`from=9999-01-01&to=9999-12-31` 三条均 422，新增窗口单测与 API 参数化用例。上界同时挡住 `end + 1 day` 与周/月桶推进的溢出。

### 6.3 `sessions` 含 pending 根，与 06 §7.5 的“空间 Session 集合”和 Session 页数字不同构，OpenAPI 也未说明（decision + fact / P2）

- **位置**：`apps/api/app/db/crud/overview.py:157`（`COUNT(DISTINCT bad_case_session_id)`，不 JOIN `session_families`）；`apps/api/app/service/overview/schemas.py:39`（`sessions` 的 OpenAPI 描述只有 “Distinct root sessions in the window.”）；设计 [06 §7.5](fullstack-design/06-database-design.md) `:848`（“空间 Session 集合 = … 与 `session_families` 的 JOIN；未命中的计入待轨迹同步，不进列表”）；[08 §6.1](fullstack-design/08-frontend-implementation.md) `:482`（StatStrip 第二格叫“关联 Session”）；Note `:52`（声称“已写进 note 与 OpenAPI 描述”）；用例 `test_overview_api.py:415-423`（`sessions=3`；fixture 没有 seed 任何 `session_families` 行，`PENDING_ROOT` 只是命名上的 pending——若实现改成 JOIN，`sessions` 会变 0、测试会红，所以“不 JOIN”这个选择有测试承重）。
- **现象**：overview 把“窗口内被上报的根”都算进 `sessions`，包括没有归一化轨迹的 pending 根；06 §7.5 给“空间 Session 集合”的定义是 JOIN 后的集合，未命中“不进列表”；08 的页面文案叫“关联 Session”。这不算错——Note 的 Alternatives 明确拒绝了 JOIN 方案——但 Note 说“已写进 OpenAPI 描述”不成立：`sessions` 的 description 只有一句 “Distinct root sessions in the window.”，没有“含 pending、不是 Session 页 total”的说明；05 §3.10/§4.18 也没有写。
- **问题**：同一个空间、同一段时间，总览的“关联 Session”和 Session 页的 `total`/`pendingSessions` 会是三个不同的数，且不能相加。设计页把“空间 Session 集合”定义成 JOIN 口径，后续 m8-04 接页面时很容易按 06 §7.5 理解而把 pending 从总览里减掉，或者把三个数拼成一句话。OpenAPI 是外部调用方唯一能读到的口径，缺这句会放大误读。
- **预判**：保留现语义（窗口内被上报的根，含 pending；这正是 Note 的理由），但补三处事实：06 §7.5 增加“overview 的 `sessions` 是上报根口径，不是本表的 Join 集合”；05 §3.10/§4.18 增加一句公式；`schemas.py:39` 的 description 补 “includes roots without a normalized trace; not the Session page total”。08 的“关联 Session”可作为文案备选。非阻塞。
- **结论**：2026-11-16 已修：06 §7.5 增加「总览 `sessions`」行，05 §3.10/§4.18 写明「窗口内上报根、含 pending、不是 JOIN 集合、不等于 Session 页 `total`、不能与 `pendingSessions` 相加」，`OverviewTotals.sessions` 的 OpenAPI 描述同步并由 `test_openapi.py` 钉住；无行为变更。

### 6.4 MySQL lane 并不执行 overview 仓储，PR 与 Note 的“MySQL 已验证”声明不成立（testing + fact / P2）

- **位置**：`scripts/run-api.mjs:19`（`db-mysql` 只跑 `tests/test_database.py -m mysql`）；`package.json:17`；`apps/api/tests/test_database.py:1707` 等 MySQL 用例；Note `:58`（“MySQL 侧只在 CI 的 mysql lane 验证语义”）；PR 描述 Known limitations 同句。

### 6.5 `triggerAt == createdAt` 只在 OpenAPI/Note 说明，05 §3.10 的 DTO 例子仍暗示真实触发时刻（fact / 中低）

### 6.6 `grain`/`range` 在 OpenAPI 里不是枚举，与 05 §4.18 的 `day|week|month`、`7|30|90` 不一致（contract + fact / 低）

- **位置**：`apps/api/app/api/overview.py:37-46`（`RangeDays = Annotated[int | None, Query(...)]`，类型是任意 int）；`:57-66`（`TrendGrainQuery = Annotated[str, Query(...)]`）；`packages/contracts/openapi.json` 的 trend `grain` schema（`type: string`，只有 description/default）；`packages/contracts/src/generated/api.d.ts:8109` 段（`grain?: string`、`range?: number`）；`apps/api/tests/test_openapi.py:488-494`；设计 05 §4.18 `:1182`（`grain=day|week|month`、`range=7|30|90`）。
- **现象**：响应里的 `TrendResponse.grain` 是 enum（`openapi.json` components 里有 `["day","week","month"]`），请求参数却不是；`range` 连 description 之外的约束都没有。`test_openapi.py` 因此只断言了 `grain` 的默认值和描述、`badCaseType` 的 enum，没有断言请求 `grain`/`range` 的 enum；PR 描述“test_openapi.py pins … enums”只对了一半。
- **问题**：这是有意的取舍——若把 `grain` 声明成 `Literal`、`range` 声明成 `enum`，FastAPI 会在进入 handler 前抛通用 `VALIDATION_INVALID`，就违背本 PR 承诺的 `GRAIN_INVALID`/`WINDOW_INVALID`。代价是生成的 TS 客户端对 `grain` 只有 `string`，IDE 不会提示合法值，外部调用方只能读 description。设计页写“枚举”，契约里没有，读者会以为漏生成。
- **预判**：保留专用错误码优先；如果要在契约里体现枚举，需要给 `grain` 增加一层 `RequestValidationError` 到 `GRAIN_INVALID` 的映射（或自定义 `openapi_extra` 的 enum），并补断言；否则至少在 05 §4.18 与 Note 里写明“枚举只体现在 description，不用 JSON Schema enum 是为了保留专用错误码”。非阻塞。
- **结论**：2026-11-16 已修：路由 `grain` 改为 `Literal["day","week","month"]`，OpenAPI 暴露 enum、生成的 TS 客户端得到联合类型；`OverviewRoute` 把 `grain` 的 `RequestValidationError` 映射回 `422 GRAIN_INVALID`，其余校验错误仍走 `VALIDATION_INVALID`。`range` 因 §6.10 需要接受显式双边界下被忽略的任意残留值，保留 `int | None` 校验，用 `json_schema_extra` 在 OpenAPI/TS 暴露 `7|30|90`；`test_openapi.py` 断言两个 enum，API 用例断言非法 `grain` 仍是专用码。

### 6.7 表存在性探测是进程级缓存：运行中删表/建表会 500 或长期零值，PR 的 “No 500s” 只对首次探测成立（fact / 低）

- **位置**：`apps/api/app/db/crud/overview.py:113-128`（`_presence` 缓存）；用例 `test_overview_api.py:1365-1417`（先 `DROP TABLE` 再请求）与 `:1420-1440`；Note `:28`（“探测结果在 repository 生命周期内缓存”）；PR 描述 “No 500s”。
- **现象**：在同一个 app 进程里先成功 list（此时 `bad_case_analysis`、`probe_reports`、`bad_cases` 都被缓存为存在），再 `DROP TABLE bad_case_analysis`，下一次 list 直接 `OperationalError` 500；再 `DROP TABLE bad_cases`，summary/trend 也 500。两条降级用例能绿，是因为 `overview` fixture 每个用例新建 app，第一次探测时表已经不在。反过来，如果外部 bootstrap 晚于进程启动，overview 会一直返回零，直到重启。
- **问题**：Note 已写了缓存与重启要求，所以这不是隐瞒；但 PR 的“No 500s”与 Note 的“外部表缺失一律降级不 500”在字面上覆盖了运行中缺失，而实际只有“首次探测即缺失”被验证。测试也没法区分“缓存正确”与“降级正确”。
- **预判**：保留缓存（与 m8-02 一致），把 PR/Note 的措辞改成“首次探测时缺失则降级；运行中建/删表需重启”；可选地只缓存“存在”不缓存“不存在”（负结果过期重探），避免“先启动后 bootstrap”长期零值。非阻塞。
- **结论**：2026-11-16 已修（措辞，无行为变更）：Note 中/英与 PR 口径改成「首次探测缺失才降级；探测按进程缓存，运行中建/删表需重启，可能长期零值或在下次查询抛数据库错误」，删除绝对「no 500s」表述；缓存策略保持与 m8-02 一致。

### 6.8 `objects` 选项的跨空间隔离没有测试能证伪（testing / 低）

- **位置**：`apps/api/app/db/crud/overview.py:205-231`（`object_options` 的 `_case_conditions(workspace_id=…)`）；A/B 语料 `test_overview_api.py:199-214`（B 的两个对象名与 A 相同：`deep-research`、`Explore`）；隔离断言 `:1125-1171` 只覆盖 list 行与 summary 的 404，`summary.objects` 没有跨空间断言。

### 6.9 `attributionCount` 的“对象·版本”在 05/06/07 有三套定义，overview 选了 probe 三元组（decision + fact / 低）

- **位置**：`apps/api/app/db/crud/overview.py:406-422`（`(bad_case_analysis.bad_case_id, probe_reports.probe_type, probe_reports.probe_object, probe_reports.object_version)` 去重）；[05 §3.4](fullstack-design/05-api-design.md) `:866`（“去重 `(object_type, object_name, object_version)` 行数”）；[05 §4.18](fullstack-design/05-api-design.md) `:1185`（“去重对象·版本数”）；[06 §4.2.1](fullstack-design/06-database-design.md) `:465`（`COUNT(DISTINCT probe_type, probe_object, object_version)`）；[07 §4.1](fullstack-design/07-backend-implementation.md) `:311`（`COUNT(DISTINCT object_type, object_name, object_version)`）。
- **现象**：overview 选择 06 的口径（归因对象/版本，来自 `probe_reports`），而 07 与 05 §3.4 写的是 bad case 自身的 `object_*`。今天 `bad_case_analysis` 还是 `UNIQUE(bad_case_id)`（`apps/api/app/db/models/domain.py:312`），一个 case 至多一条归因，两种定义数值相同；m10 扩成一 case 多归因后，二者会分叉：按 probe 三元组可能 >1，按 case 自身对象永远是 1。

- **结论**：2026-11-16 已修：以 06 §4.2.1 的 `COUNT(DISTINCT probe_type, probe_object, object_version)` 为唯一口径，写进 05 §3.10 并由 §4.18 引用；05 §3.4、§4.7 与 07 §4.1 改成引用同一定义（不再用 case 自身的 `object_*` 表述）；06 §7.5 增加一行索引。

### 6.10 显式 `from/to` 下仍校验 `range`，且设计表未写默认 90 与列表接受 `range`（simplification + fact / 低）

- **位置**：`apps/api/app/service/overview/window.py:126-128`（先判单边界，再无条件 `_resolve_range(range_days)`）；`test_window.py:85-95`（用例注释“range value is ignored but still validated”）；设计 05 §4.18 `:1185`（列表行只列 `from/to`，没有 `range`）与 `:1182`（summary 行写 `from/to` 或 `range`）。
- **现象**：`?from=…&to=…&range=14` → 422 `WINDOW_INVALID`，尽管双边界已经完整、range 被忽略；`?from=…&to=…&range=7` → 200。列表端点实际接受 `range`，但 05 §4.18 的列表行没写；默认 90 只在 OpenAPI description 与 Note 里，05 表没写（§3.10 的示例窗口恰好是 90 天，可作旁证）；周/月桶的 `label` 格式（`MM-DD` / `YYYY-MM`）也只在 `TrendBucket.label` 的 description 里，05 §3.10 只给了日桶示例。
- **问题**：如果前端把“7/30/90”放在 URL 里、用户又自定义了起止日期，客户端可能仍带着 `range`；range 合法时没事，任何非 7/30/90 的残留值（或未来新增的快捷选项）会在自定义区间时突然 422。更常见的是文档读者按 05 表实现列表，不知道可以传 `range`，也不知道默认窗口是 90 天。

- **结论**：2026-11-16 已修：显式 `from/to` 时不再调用 `_resolve_range`，`range=0/7/14` 一律忽略（API 用例覆盖 0/7/14，窗口单测覆盖 0）；只有无边界或单边界推导时才要求 7/30/90。05 §4.18 表补上列表也接受 `range`、默认 90、`pageSize` 1..50、桶 label 格式与「显式双边界忽略 range」规则；Note 同步。

### 6.11 `attributionCount` 的去重路径在 m10 之前无法被集成测试证伪（testing / 低）

- **位置**：`apps/api/tests/m8-03-workspace-overview/test_overview_api.py:1030-1071`（三个 case 各接一个 probe，断言 1/1/1/0/0/0）；`apps/api/app/db/models/domain.py:312`（`UniqueConstraint("bad_case_id", name="uq_bad_case_analysis_case")`）；Note Consequences 第 5 条（“真正的多归因去重路径要等 m10”）。
