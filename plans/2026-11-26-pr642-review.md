## 1 一页速览

一句话：把“一条配置 = 一个对象”改成“一条配置 = 同仓多个成员”，共享仓库、基线、测试工程、主指标与归因 Skill，一次 run 一起 patch、一起评测。

比喻：原来的配置像一张只写一个收件人的快递单；现在一张单可以写同一地址的多个收件人，地址、邮资、时效只填一次，包裹按每个收件人的门牌分别投递。

## 2 架构导览

- **两层身份**：`evolution_targets` 继续承载共享字段和 V1 兼容旧列；`evolution_target_members`（`domain.py:564`）承载成员身份与冻结定义。旧列仍写首个成员，历史读路径可回退。
- **全局唯一**：成员表 `(workspace_id, object_type, object_name)` 唯一索引 + 服务层 `find_all` 预检（`targets.py:791`）。冲突返回 `409 MEMBER_ALREADY_CONFIGURED` 并定位 `members[i].objectName`。
- **写路径**：保存只做一次 `ls-remote`，随后逐成员 `TargetDefinitions.freeze`；仓储 insert/update 同事务写 1 行配置 + N 行成员（`crud/evolution_targets.py:471,531`）。
- **读路径**：`_load_members` 批量读后由 `_record` 组装；无成员行的历史配置合成单成员，避免读路径分叉。
- **匹配**：`MatchCondition.targets[]`（`potential.py:362`）让关联按成员并集、每个 case 用自身对象的 Session 入口点；`object_entries` 保存每个成员的首个触发点。
- **归因**：绑定快照存 `members[]`，`AttributionRunner` 为每个 case 选择其所属成员的类型/名称/revision；单成员路径的 manifest 身份不变。
- **run**：启动冻结 `evolution_run_targets`；prepare 逐成员 `cat-file`，patch/eval 从 run targets 派生目录集合。
- **投影**：一条配置一行；成员 chip 与 case 成员列来自 `object_name`，run 详情显示共享测试工程与 `workspace.subDirs`。

## 3 数据流走查

1. 管理员在配置弹窗填共享块 + 两个成员 → `POST /api/evolution/targets` 带 `members[2]`。
2. 服务逐成员校验/去重、一次 `ls-remote`、逐成员读定义并冻结 → 仓储同事务写配置与成员。
3. 向导选择该配置 → 请求带 `targetId`；`enabled_config_by_id` 返回配置 + 成员。
4. `launch` 逐成员解析 revision，写 run + 2 行 `evolution_run_targets`，旧列写首个成员。
5. prepare 用 `MatchCondition.targets[]` 关联并集；candidate 记录命中成员；逐成员 `cat-file` 验证目录。
6. patch 的 `allowed_paths` 覆盖两个目录；评测 launch 的 `asset_paths` 列出两个成员资产。
7. run 详情/总览读取 `targets[]`/`members[]`，前端渲染成员 chip 与成员列。

## 6 讨论点

### 6.1 总览成员版本标签合并

- **位置**：`apps/api/app/service/overview/targets.py:1260`
- **现象**：同一配置的成员分析按 `version` 键合并，后一个成员的 `TargetVersionLabel` 会覆盖前一个；如果两个成员在同一 ref 下解析出不同 digest，标签的 aliases 只保留最后一个成员。
- **问题**：可能少算/错配历史 attributed 报告，尤其成员定义不同 digest 时。
- **预判**：当前设计共享 ref、成员 digest 独立；本轮测试场景两个成员同为同 ref 且报告按各自对象写入，未复现少算。建议后续把 aliases 做并集、digest/commit 以成员为维度展示。
- **结论**：待维护者拍板；无实害但属于已知边界。

### 6.2 归因上下文仍是“每 case 单目标”

- **位置**：`apps/api/app/service/evolution/attribution.py`（`contexts` 分组）与 `attribution_context.py`
- **现象**：设计 §5.2 写“上下文 `targets[]`”，实现按 case 所属成员分别构建 bundle，而不是一个 bundle 内列全部成员。
- **问题**：多成员 Session 的上下文不包含其他成员的 occurrence；归因 Skill 看到的是本 case 对象。
- **预判**：这是刻意的取舍：单成员 bundle 哈希逐字不变，且归因结论按 case 自身对象更准确；但需要维护者确认是否接受与设计文字的偏差。
- **结论**：待维护者拍板；若要求严格 `targets[]`，需扩展 context schema 并接受多成员哈希变化。

### 6.3 run 详情共享测试工程由前端回查配置

- **位置**：`apps/web/src/pages/evolution/RunDetail.vue` / `runDetail.ts`
- **现象**：run 详情没有 `validationProjectId/testProjectId/primaryMetricKey`，前端用首个成员匹配 `GET evolution/targets` 后展示；配置被删或请求失败时该行省略。
- **问题**：多一次请求，且配置删除后无法展示历史共享测试工程。
- **预判**：不影响核心流程；后续可在 run card/detail 直接暴露这三个字段。
- **结论**：待维护者拍板；当前为可用降级。

### 6.4 flow 状态无法置 done

- **位置**：`.agents/flow/issues/m28-01-multi-member-evolution-target.*`
- **现象**：`verify:flow` 要求 P1 跨 milestone 串行，`m18-git-egress-proxy` 与 `m25-session-level-agent-link` 未 done，因此本 issue 不能置 `in-progress/done`。
- **问题**：PR 合并后 issue 仍保持 open/ready；闭环需要先完成两个更高优先级 issue，或由维护者调整优先级规则。
- **预判**：这是流程策略问题，不是本 PR 代码缺陷；PR 描述已声明。
- **结论**：待维护者拍板；不影响 PR 代码合并，影响 issue 闭环。

## 9 文件级代码分析

本轮重点通读服务与数据层；前端只读关键段并依赖组件测试与 E2E。逐文件结论：

- `db/models/domain.py`：成员表字段、双唯一约束与全局索引与设计一致；旧列 nullable 只改变新库 DDL，历史库由 0035 放宽。
- `db/models/evolution.py`：run 成员快照记录、candidate 三列与记录默认值；旧构造点因默认值不受影响。
- `db/crud/evolution_targets.py`：成员批量读、同事务替换、成员冲突分类；`_member_unique_violation` 依赖数据库错误文本，SQLite/MySQL 都包含表名，CI 双方言已验。
- `service/evolution/targets.py`：legacy single 兼容与成员写模型；`legacy_single` 用 `SkipJsonSchema` 隐藏，OpenAPI 不泄露；重复成员先服务预检、再靠唯一索引兜底。
- `service/evolution/potential.py`：并集关联与按成员入口点；单成员分支仍走同一 `entry_for`，行为等价。
- `binding_worker.py`：成员快照、按成员分组查最新报告、BindingBatch targets；单成员 batch 的 definition/revision 与旧路径一致。
- `attribution.py`：per-case 目标选择与 revision 优先级；单成员 manifest 身份不变，历史 run 回退到 legacy revision。
- `launch.py`：targetId/对象双入口、逐成员 revision、run targets 与 subDirs；旧请求体仍可用。
- `prepare.py`：condition targets、candidate 成员列、逐成员 cat-file；历史 run 无 targets 时回退旧列。
- `patch_source.py` / `git_candidate.py`：多目录 allowed_paths、成员提示词、提交 scope；placeholder 仍写首成员目录。
- `eval_poller.py` / `ai_eval_platform.py`：多资产一次提交，asset_types 多 key；单成员路径不变。
- `overview/targets.py`：成员分析合并、members 投影、case 成员列；合并边界见 §6.1。
- `TargetFormDialog.vue` / `TargetTable.vue`：成员行、chip、错误定位、删除确认；前端测试覆盖。
- `LaunchWizard.vue`：配置单选、成员只读面板、targetId 请求；未逐行通读，依赖组件测试与 E2E。
- `RunDetail.vue` / `StepRange.vue`：成员 chip、subDirs、共享测试工程；未逐行通读，依赖组件测试与 E2E。
