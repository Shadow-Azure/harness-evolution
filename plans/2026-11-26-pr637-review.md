## §1 一页速览

一句话：给 agent 进化对象加一个默认关闭的 `.env` 开关，开启后「关联」按名称、而不是按 `AGENT.md` 正文摘要。

比喻：正文摘要像指纹，能精确区分同名不同版本；名称像门牌号，找得到人但分不清同住的兄弟姐妹。这个 PR 让部署者显式选择「按门牌号找人」，默认仍按指纹。

| 交付块 | 内容 |
| --- | --- |
| 开关 | `HE_AGENT_MATCH_BY_NAME`，布尔，默认 `false`，启动读取 |
| 匹配 | agent 目标忽略 `observed_revisions`，按类型+名称关联 |
| 总览 | agent 目标折叠为 `defaultRef` 单版本行；历史报告按别名挂回 |
| 边界 | 报告缓存、`targetRevision`、第 4 步统计、启动门、绑定去重仍按 body hash |
| 验证 | 166 个聚焦用例、lint/typecheck/docs/flow/contract/gates 全过；浏览器 before/after 待补 |

## §2 架构导览

- **注入**：`Settings.agent_match_by_name`（`apps/api/app/config.py:216`）在 `create_app` 里传给两处 `PotentialMatcher` 和 `TargetOverviewService`（`apps/api/app/main.py:379-400`）。这样预览、启动、绑定与总览共享同一个匹配器实例的开关。
- **匹配器**：`PotentialMatcher.__init__` 新增 `agent_match_by_name`（`apps/api/app/service/evolution/potential.py:596`）；`associated_sessions` 在开关开启且目标类型为 agent 时置 `match_by_presence`（`:637`），绕开 `observed_revisions` 的摘要过滤，其余分支原样。
- **总览**：`_analyse_target` 在 agent + 开关时走新分支（`apps/api/app/service/overview/targets.py:901`），否则走原 `_build_version_labels` 路径。
- **单行版本**：`_analyse_agent_by_name`（`:981`）以 `defaultRef` 为唯一版本键，解析成功时记录 digest/commit，失败时 `resolve_legacy_target_version` 给出 `tag:<ref>` 兜底（`:999-1027`）。
- **历史报告**：别名集合包含配置 ref、解析 revision、裸 hash 与 **该对象窗口内历史报告的 `object_version`**（`:1006-1017`），使 `_newest_link_by_case`（`:1049`）仍能按 case 选中旧报告；这解决了「折叠版本后 attributed/nonTarget 归零」的直接风险。
- **统计**：`entries` 由历史报告 case 与本次 potential 的并集生成（`:1060`），`session_ids` 同时包含关联 Session 与报告 case 的 Session（`:1053-1058`）。

## §3 数据流走查

1. 浏览器请求 `GET /overview/targets/{id}/detail`。
2. `TargetOverviewService._analyse_target` 先取窗口 case、run、报告链接；若目标是 agent 且开关开启，进入 `_analyse_agent_by_name`。
3. 单版本行：`defaultRef` → resolver（fake 或真实 git）→ `digest`；失败则 `tag:<ref>` 兜底，`unresolvedVersions` 保持空。
4. `PotentialMatcher.associated_sessions(condition)`：开关开启 + agent → 忽略版本过滤，返回窗口内包含该名称的 Session。
5. `_newest_link_by_case(links, aliases)`：历史报告版本作为别名命中，取每个 case 最新报告；attributed/nonTarget 因此保留。
6. DTO：`versions=[ref]`、`versionOptions=[ref]`、`byVersion=[同一行]`、`stats.versions=1`；case 列表的 `objectVersion` 显示 `ref`。

## §6 讨论点

### D1 名称模式的别名只来自窗口内历史报告

- **位置**：`apps/api/app/service/overview/targets.py:1006-1017`
- **现象**：`aliases` 从本次 `list_attributions(case_ids=窗口 case)` 的 `object_version` 构造，窗口外报告不进入别名。
- **问题**：如果窗口外有同一 agent 的历史报告，名称模式不会把它们挂到当前唯一版本行。
- **预判**：这是总览窗口契约的自然结果，不是名称模式独有；窗口外报告本来就不应出现在当前窗口的统计里，建议保持。
- **结论**：待维护者确认（无代码改动建议）。

### D2 开关是进程级，预览/启动/绑定也持有同一个 matcher

- **位置**：`apps/api/app/main.py:379-400`、`apps/api/app/service/evolution/potential.py:637`
- **现象**：开关同时作用于 overview、preview、launch、binding 的 matcher；这些路径当前不传 `observed_revisions`，所以行为不变。
- **问题**：未来若有路径重新对 agent 引入 revision 过滤，会被这个全局开关静默绕过。
- **预判**：当前无实害；这是有意的「进程级匹配策略」，若未来收紧应改成语义显式的参数并补测试。
- **结论**：待维护者确认。

### D3 内容解析失败时版本行显示 ref，但 digest 为空

- **位置**：`apps/api/app/service/overview/targets.py:999-1027`
- **现象**：resolver 失败时用 `resolve_legacy_target_version(ref)` 兜底，`match_by_presence` 仍能关联；这一行没有 digest/commit；`unresolvedVersions` 为空。
- **问题**：用户看到的是一个「已解析」的 ref 行，尽管内容实际读不到。
- **预判**：这是 issue 明确要求的行为（名称匹配不依赖内容）；风险是用户误以为内容可用，启动时仍会报 `TARGET_CONTENT_UNRESOLVED`。当前无实害，建议保留。
- **结论**：待维护者确认。
