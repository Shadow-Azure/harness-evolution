## §1 一页速览

**一句话**：把 parser 从“一次只解析一份 transcript 的无状态工具”升级为“按 root 会话构造、用 `can_parse` 按轨迹内容选型、在子类内用父 `toolUseResult.agentId` ↔ 子 JSONL `agentId` 补 derived 父子链接”的会话级组件；`agent_tree` 只在缺少 authoritative 父调用时应用链接，从而把生产 session `226504ab` 的三个子 Agent 从 `synthetic-agent` 挂回真实的 `call_…` 触发点。

**比喻**：旧路径像把一整车乘客分别送到终点，再在出口靠名字猜谁和谁是一家人；新路径像进站前先核对整列车次（`can_parse`），上车时就把每节车厢按真实挂钩接好（会话内 derived 链接），出站只做最后的编组检查（`agent_tree` 应用链接）。

| 交付块 | 内容 | 用户可感知结果 |
|---|---|---|
| 会话级 parser | `__init__(payloads)` 校验同 root/同 runtime/恰一 main；`normalize_session()` 一次产出 transcripts + links（`parsers/base.py:539-592`） | 同一 root 的主/子轨迹在归一化阶段互相可见 |
| 轨迹选型 | `for_trace(payloads)` 遍历 `can_parse` 唯一命中；零命中 `UnsupportedTraceRuntime`，多命中 `AmbiguousTraceRuntime`（`parsers/factory.py:49-61`） | 不再只凭 `runtime_key` 选 parser |
| derived 链接 | 父 `toolUseResult.agentId` ↔ 子顶层 `agentId`，仅唯一、未与 authoritative 冲突时生成（`parsers/claude_code.py:602-640`） | 缺 envelope `toolUseId` 时仍能挂到真实 spawn 调用 |
| 组装器只应用 | 仅当 `transcript.parent_tool_use_id is None` 时用 link；标记 `derived`；子节点写真实 `tool_use_id`（`agent_tree.py:732-735, 797-806`） | 结构树/lane DAG 从真实 `call_…` 起跑，synthetic 兜底保留 |
| 版本与回填 | `parser_version` 6→7（`claude_code.py:426`），replay 按 runtime 版本重放存量 root | 生产 226504ab 部署后重放即可修正 |

## §2 架构导览

### 2.1 会话契约：值对象与构造校验

`AgentLink` 只带 `child_agent_id`、`parent_tool_use_id`、`confidence`（`parsers/base.py:163-169`）；`SessionParseResult` 把 transcripts 与 links 一起返回（`base.py:225-231`）。`BaseTraceParser.__init__` 校验非空、同 root、同 runtime、恰一个 main，并把 `payloads/main/subagents` 存为成员（`base.py:539-561`）。`normalize_session` 只是逐 payload 调 `normalize`，再调子类 `link_transcripts`（`base.py:586-592`）；基类默认无链接（`base.py:594-599`），Claude 子类才有实现。这层把“会话成员”和“单 transcript 模板”分开，`normalize` 的 JSONL 帧、坏行、计数、finalize 全部保持原样（`base.py:601-617`）。

**关键取舍**：`main` 的注解是 `TracePayload | None`（`base.py:558`），虽然构造已保证恰一个 main；`for_single_payload` 用 `__new__` 绕过构造校验，专门服务单 payload 兼容入口（`base.py:563-575`）。前者是类型上的小妥协，后者是刻意的兼容缝：它让旧 `extract_evidence` / 单条 normalize 调用不需要伪造一个 main。代价是子类若未来在 `__init__` 里加缓存，单 payload 路径不会执行它——当前没有这种子类。

### 2.2 选型：内容优先，但身份仍参与持久化

`for_trace` 完全不看 `runtime_key`，只遍历注册子类的 `can_parse`（`parsers/factory.py:49-61`）；`create(runtime_key, payloads)` 保留为显式/测试入口（`factory.py:63-74`），`for_payload` 服务单 payload（`factory.py:76-87`），`version` 不再实例化 parser（`factory.py:89-95`）。Claude 的 `can_parse` 只读每条 payload 的首个 JSON 对象，要求 `type` 加任一 Claude 形态标记，最多看 10 个非空行（`claude_code.py:64-92, 429-451`）。这套机制确实实现了“不依赖 runtime_key 也能选型”，`test_for_trace_selects_by_content_not_runtime_key` 覆盖；但它也把“身份”和“内容”拆成了两个事实源——选型看内容，`source_records` 仍按 payload 的 `runtime_key` 存取，二者不一致时的路径没有系统测试（见 D3/D4）。

### 2.3 Claude 的 derived 证据

解析每条 record 时，顶层 `agentId` 被记入 `ctx.native_agent_id`（`claude_code.py:460-462`）；工具结果 record 的顶层 `toolUseResult.agentId` 按 `tool_use_id` 记入 `ctx.agent_result_ids`（`claude_code.py:549-555`）。finalize 把两者落到 `ParsedTranscript.native_agent_id` 与 `agent_result_ids`（`base.py:704-705`）。`link_transcripts` 先按 native id 建“唯一子 transcript”索引，再让每个父的 result id 去认领；同一 child 被多个 tool id 认领、或 native id 命中多个 child，都不生成链接；已有 `parent_tool_use_id` 的 child 直接跳过（`claude_code.py:602-640`）。这是“宁可 synthetic，也不乱挂”的保守策略。

### 2.4 组装器：链接只是兜底，authoritative 优先

`_derived_parent_tools` 再次按 child 去重，保留唯一 parent tool（`agent_tree.py:450-461`）。组装时先走原有 `parent_tool = transcript.parent_tool_use_id`；只有它是 None 且存在 derived tool 时才替换（`agent_tree.py:732-735`）。命中父事件后，`link_applied` 为真则强制 `derived`，否则沿用旧的 `returned_tool_ids` 判断（`agent_tree.py:797-799`）；并把 child 节点的 `tool_use_id` 写成真实父调用（`agent_tree.py:801-806`）。这正好是 UI 需要的两个字段：`SessionAgent.toolUseId` 与父事件 `relationConfidence`（`service/sessions/service.py:153, 180`）。

### 2.5 三条入口与幂等

`replay` 先按 `(runtime_key, root_session_id)` 取待处理，再用 `list_root_payloads` 取齐整 root，校验 main 数，`for_trace` 后 `normalize_session`，把 `{root: links}` 交给 `assemble_agent_trees`，最后 `replace_normalized_root` 原子重写（`replay.py:177-306`）。`local_sessions._normalize_corpus` 按 root 分组、构造 `TracePayload`、选型、归一化（`local_sessions.py:481-510`）；`assemble_local_sessions` 直接使用 links（`local_sessions.py:531-539`）。`normalize.normalize_payloads` 提供同构 helper（`normalize.py:61-68`），但生产调用方实际直接走 factory。**没有发现 double normalize**：`normalize_session` 对每个 payload 只调一次 `normalize`，`extract_evidence` 在生产路径无调用方；local 的两条入口各自扫描一次，但不会对同一批 transcript 重复归一化。

## §3 数据流走查

以生产 `226504ab` 的部署后 replay 为主线：

1. **触发**：`replay_pending_payloads` 用 `TraceParserFactory.versions()`（Claude=7）查 pending（`replay.py:115`）；parser_version 6 的存量 payload 全部进入待重放集合。
2. **按 root 取齐**：pending 按 `(runtime_key, root_session_id)` 分组（`replay.py:127-129`），每个 root 用 `list_root_payloads` 取全部 payload，而不是只取 pending 的单条（`replay.py:189-197`）。这是会话级归一化的前提。
3. **main 校验**：`main_count != 1` 时写 `MISSING_MAIN_AGENT` / `DUPLICATE_MAIN_AGENT` 并把该 root 标 failed（`replay.py:198-219`），避免把构造异常升级成整批异常。
4. **选型**：`for_trace(session_payloads)` 逐个 parser 跑 `can_parse`；Claude 读首记录判定形态（`factory.py:49-61`、`claude_code.py:429-451`）；零命中/多命中分别走 `UNSUPPORTED_RUNTIME` / `AMBIGUOUS_RUNTIME`（`replay.py:220-255`）。
5. **构造会话**：parser 拿到 main + 3 个 subagent，校验同 root/同 runtime/恰一 main（`base.py:539-561`）。
6. **归一化**：`normalize_session` 逐 payload 归一化（`base.py:586-592`）；main 的 assistant record 里三次 `Agent` 工具调用成为 `agent` 事件；子 transcript 首条 record 的 `agentId` 被记下（`claude_code.py:460-462`）。
7. **取反证**：main 的三条 tool result record 各带 `toolUseResult.agentId`，按 tool_use_id 记录（`claude_code.py:549-555`）。以一条为例：`call_A` ↔ `native_A`，子 transcript 的 `native_agent_id = native_A`。
8. **生成链接**：`link_transcripts` 得到 `AgentLink(child=A, parent_tool_use_id=call_A, confidence=derived)`；若 child 已有 envelope `toolUseId`，跳过（`claude_code.py:602-640`）。
9. **组装**：child 的 `parent_tool_use_id` 为空，组装器采用 `call_A`，在 main 的事件表里找到同 id 的 `agent` 事件，把 child 的 `parent_agent_id` 指向 main、`tool_use_id` 写成 `call_A`、事件置信度标 `derived`（`agent_tree.py:732-806`）。若链接缺失/歧义，仍走原有 synthetic 分支（`agent_tree.py:736-795`）。
10. **持久化与读模型**：`replace_normalized_root` 删除并重建该 root 的五张表行，`agents.tool_use_id` 写真实调用 id，`agent_events.relation_confidence=derived`（`crud/acquisition_replay.py:681-800`）；API 原样投影（`service/sessions/service.py:153, 180`）。
11. **UI 数据形状**：结构树用 child 的 `toolUseId` 在父事件中找 `agentEventIndex`（`apps/web/src/components/agent-tree/tree/layout.ts:224-235`），lane 用同一 id 找 `triggerLineOf`（`lane/laneModel.ts:361-369`），因此子 lane 从真实 spawn 行（如 L1028）起跑；父事件 `derived` 不再被当成 synthetic（`layout.ts:195-205`）。**这一层的数据形状是正确的**，但同一套数据会触发 D2 的“未返回最终报告”误报。

### D2 derived 链接触发前端“未返回最终报告”误报

- **位置**：`apps/api/app/service/acquisition/agent_tree.py:797-799`（新逻辑把链接边标 `derived`）与 `apps/web/src/components/agent-tree/tree/layout.ts:258-267`（`relation === "derived"` 直接返回 `MISSING_REPORT_WARNING`）。
- **现象**：旧代码里 `derived` 的含义是“父工具事件存在、但父 transcript 里没有该调用的 tool_result”（`agent_tree.py:166-172` + 旧 `confidence` 判断），所以 UI 用 `derived` 推断“未返回最终报告”在当时说得通。新代码的 `derived` 恰恰相反：链接证据就是父 transcript 里一条真实的 `toolUseResult.agentId`（`claude_code.py:549-555, 602-640`），说明结果已经回来了。本次用真实本地会话做只读探针：抹掉 `meta.toolUseId` 后 5 个子 Agent 全部 `execution_outcome=completed`、`end_reason=end_turn`，但按现有 UI 代码都会显示“未返回最终报告”（`layout.ts:265-267` 不看 `executionOutcome`；`layout.test.ts:125-160` 也把 derived 与 warning 绑在一起）。生产 226504ab 的三个子 Agent 一旦由 synthetic 变 derived，同样会命中。
- **问题**：同一个置信度值承载了两种相反的证据语义，且这次是批量翻转（v7 replay 会把所有缺 envelope `toolUseId` 的存量会话的子 Agent 都变成 derived），影响面不止 226504ab。这不是数据错误（父子关系、tool_use_id 都是对的），但直接违背“UI 与原型一致、不出现新的异常标签”的验收语境。
- **预判**：应在前端修，而不是回退后端：`completionWarningOf` 删除 `relation === "derived"` 分支，只按 `executionOutcome/endReason` 判断“未返回最终报告”；`derived` 继续只作为关系证据标签（“派生”）。这不需要改共享契约，属于纯 UI 跟随数据语义。若维护者更希望保留“derived=结果未回”的旧语义，则必须给新链接引入另一个枚举值，那会改契约，不建议在本 PR 做。
- **结论**：

### D3 `can_parse` 形态标记过宽，非 Claude 轨迹可能被静默当作 Claude

- **位置**：`apps/api/app/service/acquisition/parsers/claude_code.py:64-73`（标记含泛化的 `message`）、`claude_code.py:429-451`（`type` + 任一标记即接受）、`parsers/factory.py:49-61`（完全不看 `runtime_key`）。
- **现象**：构造一条 `{"type":"message","message":{"role":"assistant","content":"hello"}}`、`runtime_key="codex"` 的 payload，`for_trace` 实际选中 `claude-code`，`normalize` 返回 1 条 transcript、`runtime_key=claude-code`、0 个 issue（本次实测）。而 `plans/fullstack-design/04-backend-architecture.md:119` 与 `06-database-design.md:156` 仍写“未知/歧义选型产生稳定错误，不能 fallback 到 Claude”。
- **问题**：`type + message` 是很多 agent 日志的通用形状，不足以证明“Claude Code 轨迹”。当前只有 Claude 一个生产 parser，没有立即的数据污染；但一旦新增 runtime，错误轨迹会被 Claude normalizer 静默吃掉，且 `ParsedTranscript.runtime_key` 会被改成 `claude-code`，身份与内容不一致。这与文档承诺的 fail-fast 相反。
- **预判**：把标记收紧到 Claude 特有的组合（至少要求 `sessionId`/`uuid`/`parentUuid`/`isSidechain`/`toolUseResult`/`agentId` 之一，不能只靠 `message`），并对“选中的 parser.runtime_key 与 payload.runtime_key 不同”记一条稳定诊断（不是静默）；是否失败由维护者定。当前 125 个真实本地 JSONL 的首记录探针 0 失败，说明收紧不会误伤现有 Claude 形态。
- **结论**：

### D4 `runtime_key` 内容选型与持久化身份不一致的路径未实现文档承诺

- **位置**：`apps/api/app/service/acquisition/replay.py:195-221`（会话 payload 保留 DB 的 `runtime_key`）、`apps/api/app/db/crud/acquisition_replay.py:608-648`（`_ensure_sources` 按 `payloads[0].runtime_key`）、`acquisition_replay.py:693-701, 741`（随后按 `tree.runtime_key` 查/取 `source_ids`）；文档 `plans/fullstack-design/05-api-design.md:1509`（“不一致只记诊断”）。
- **现象**：`for_trace` 按内容可能选出与 payload `runtime_key` 不同的 parser；归一化后的 transcript/tree 用 parser 的 `runtime_key`（`base.py:663`、`agent_tree.py:879`），但 `_ensure_sources` 与 `source_ids` 用 payload 的 key。两者不一致时，`source_rows` 可能为空、`source_ids[(tree.runtime_key, ...)]` 会 KeyError，外层 `except Exception` 记 `ROOT_REPLAY_FAILED`，root 反复失败；没有任何“不一致”诊断。该路径未在本次实际跑 DB，结论来自代码推导。
- **问题**：设计说 `runtime_key` 是身份提示、选型看内容、不一致只记诊断；代码却在持久化层把两个身份混用。对于 `script` 直接写入 `trajectory_payloads` 的错标行，这是可触发的；对 HTTP envelope 路径，未知 runtime 在 adapter 层已失败，触发面小。
- **预判**：需要二选一并写进 Note/文档：A）持久化继续以 payload `runtime_key` 为身份，选型只做校验并记录不一致；B）以选中的 parser `runtime_key` 为规范身份，回写/对齐 `source_records`。A 改动小、符合“身份不出现第二个 home”；B 更彻底但要考虑跨 runtime 重标。当前无生产数据证据，建议作为后续小 PR，不在本 PR 扩大范围。
- **结论**：

### D5 单条 record 批量 tool_result 时，derived 链接会被误判为“多父认领”而丢弃

- **位置**：`apps/api/app/service/acquisition/parsers/claude_code.py:549-555`（record 里每个 `tool_use_id` 都写入同一个 `result_agent_id`）、`claude_code.py:619-637`（同一 child 收到两个 tool id 即不生成链接）。
- **现象**：构造一条 user record，同时包含 Agent 调用与 Bash 调用的两个 tool_result，顶层 `toolUseResult.agentId` 为子 Agent id；实测 `link_transcripts` 返回空，因为 Bash 的 tool id 也被写入了 `agent_result_ids`，child 被两个 tool id 认领，触发“歧义丢弃”。若按 tool 名只把 Agent/Task 调用写入 `agent_result_ids`，该 child 本可正确挂到 Agent 调用。现有 `test_link_resolution_ignores_multiply_claimed_child` 锁定了这种丢弃。
- **问题**：Claude Code 通常一条 user record 只放一个 tool_result（本次 125 个真实文件与上游 schema 文档一致），所以当前无实害；但格式允许多个，且 parser 自己已有批量结果的测试形状。一旦上游批量返回，正确的 derived 链接会退化成 synthetic，且没有 issue 解释原因。
- **预判**：低优先级、低成本：在 `tool_results` 循环里用已有的 `tool_name` 判断，只对 Agent（或历史 `Task`）调用记录 `agent_result_ids`；若一条 record 有多个 Agent 结果，保持“歧义不链接”。补一个批量 record 的测试即可。不建议在 `agent_tree` 侧兜底，因为那里看不到 tool 名。
- **结论**：

## §9 文件级代码分析

### 9.1 `parsers/base.py`

**职责**：会话级 parser 模板与共享值对象；变更形态 M。**依赖解读**：纯标准库（`abc`、`dataclasses`、`types.MappingProxyType`），没有第三方包；模板方法把 JSONL 帧、坏行、隐私边界、计数、finalize 固定在基类，子类只实现 record/meta。

**旧代码**（origin/main）：`normalize(payload)` 直接建 `ParseContext`，循环解码并 finalize；parser 没有构造参数，也没有会话成员。

**新代码**（`parsers/base.py:539-592`）：

```python
def __init__(self, payloads: Sequence[TracePayload]) -> None:
    ...
    mains = tuple(payload for payload in payloads if payload.agent_kind == "main")
    if len(mains) != 1:
        raise ValueError("trace parser session must contain exactly one main payload")
    self.payloads = tuple(payloads)
    self.main = mains[0]
    self.subagents = tuple(...)

def normalize_session(self) -> SessionParseResult:
    transcripts = tuple(self.normalize(payload) for payload in self.payloads)
    return SessionParseResult(transcripts, tuple(self.link_transcripts(transcripts)))
```

**在做什么**：构造即绑定整个 root，`normalize_session` 一次返回全部 transcript 与链接；`link_transcripts` 默认空，Claude 子类覆盖。**为什么这么写**：用户要求“创建子类时把整会话初始化到成员变量”，同时保留单 payload `normalize` 作为兼容入口；把校验放在基类，避免每个子类重复同 root/同 runtime/恰一 main 的检查。**检视发现**：`main` 注解为 `TracePayload | None`（`:558`）而构造已保证非空，属于类型上的小妥协；`for_single_payload` 用 `__new__` 绕过 `__init__`（`:563-575`），未来子类若在 `__init__` 里加状态会静默缺失，当前无此子类，记录为兼容缝的边界。

### 9.2 `parsers/factory.py`

**职责**：注册表与选型入口；变更形态 M。**旧代码**：`create(runtime_key)` 直接按 key 实例化，`version` 也实例化一个 parser。**新代码**（`:49-95`）：

```python
matches = [p for p in cls._parsers.values() if p.can_parse(payloads)]
if not matches: raise UnsupportedTraceRuntime(payloads[0].runtime_key if payloads else "unknown")
if len(matches) > 1: raise AmbiguousTraceRuntime([p.runtime_key for p in matches])
return matches[0](payloads)
...
return cls._parsers[runtime_key].parser_version
```

**在做什么**：按内容唯一选型，显式入口保留，版本读类属性不实例化。**为什么这么写**：避免按注册顺序静默选；`can_parse` 是类方法，选型不需要构造实例。**检视发现**：`for_trace` 完全忽略 `runtime_key`（D3/D4 的根），且没有隔离某个 `can_parse` 抛出的异常（一个子类 probe 抛错会中断整个选型）；当前只有 Claude，无实害，但契约上“can_parse 必须廉价且不抛”没有强制。

### 9.3 `parsers/claude_code.py`

**职责**：Claude record/meta 解释与会话链接；变更形态 M。**旧代码**：`parser_version = 6`，无 `can_parse`、无链接，`normalize` 一次只处理一个 payload。**新代码**：版本 7（`:426`）；`can_parse` 前缀探测（`:429-451`）；`agentId` 与 `toolUseResult.agentId` 捕获（`:460-462, 549-555`）；`link_transcripts`（`:602-640`）。

```python

    matches = children_by_native.get(native_agent_id, [])
    if len(matches) != 1: continue
    child = matches[0]
    if child.parent_tool_use_id is not None: continue
    claims.setdefault(child.agent_id, set()).add(tool_use_id)
...
if len(tool_use_ids) != 1: continue
```

**在做什么**：唯一 native id → 唯一 child，唯一 tool id → 唯一链接；authoritative 优先，歧义丢弃。**为什么这么写**：把“宁可不挂也不乱挂”固化在 parser，`agent_tree` 只负责兜底。**检视发现**：D3（标记过宽）、D5（批量 tool_result 误丢）；此外 D4 中“父 result 与子的配对”完全依赖 `agentId` 精确相等，若上游改写 agentId 大小写/编码，链接会静默退化，当前无证据。

### 9.4 `agent_tree.py`

**职责**：把 transcripts + links 组装成树/事件；变更形态 M。**旧代码**：`assemble_agent_trees(transcripts)`，置信度只按 `parent_tool in returned_tool_ids` 分为 authoritative/derived。**新代码**（`:450-461, 732-735, 797-806`）：

```python
derived_parent_tool = derived_parent_tools.get(transcript.agent_id)
link_applied = parent_tool is None and derived_parent_tool is not None
if link_applied: parent_tool = derived_parent_tool
...
confidence = "derived"
if not link_applied and parent_tool in returned_tool_ids.get(owner_id, frozenset()):
    confidence = "authoritative"
...
nodes[transcript.agent_id] = replace(..., tool_use_id=parent_tool, description=event.description)
```

**在做什么**：derived 只填补缺失的 parent tool；成功挂接后写真实 tool id，供 UI 定位；synthetic/resolved 分支完全保留。**为什么这么写**：authoritative 是 envelope 的强证据，不能被内容推断覆盖；UI 的 lane 起点依赖 child tool id，必须在组装期写入。**检视发现**：D2 的置信度语义碰撞；`AgentLink.confidence` 字段被完全忽略（`_derived_parent_tools` 只看 `parent_tool_use_id`，无论传 authoritative 还是 derived 都按 derived 应用），这是一个只在未来 parser 扩展时才咬人的契约小坑。`assemble_agent_trees(transcripts, links)` 对 links 的 key 静默兜底（key 不匹配就当作无链接），本次检视自测时就踩过一次；生产三处调用 key 正确，但建议在 `SessionParseResult` 里带上 root id 或加断言。
