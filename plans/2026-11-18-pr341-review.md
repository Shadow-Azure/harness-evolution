## §1 一页速览

**一句话：** 第五步聚类不再“数好卡片硬劈两半”，而是把标题字面相近的问题卡片放进同一叠；每叠的标题和算法参数都留痕。

**比喻：** 旧算法像按人数把一桌人从中间切开，左边未必是一家人；新算法先看每个人衣服上的共同关键词，共同词占比够高才坐一桌，桌数和每桌人数由内容决定。

## §2 架构导览

### 2.1 纯函数层：`service/evolution/cluster.py`

旧文件只有一个 `simple_cluster`：按 `attribute_type` 分组、按 `probe_id` 排序、`(n+1)//2` 分半。新文件保留 `ClusterDraft` / `cluster_severity` / `cluster_hash`，把组合逻辑换成四步（`cluster.py:74-120`）：

1. 按 `probe_id` 去重：同一 probe 的重复输入不会让成员重复（`cluster.py:88-95`）；
2. 每个类型独立取组并按 `probe_id` 排序（`cluster.py:97-102`）；
3. `_tokens` 把文本转成 ASCII 词元 + CJK 字符二元组（`cluster.py:167-183`）；
4. 用 token → probe 的倒排表只比较“至少共享一个词元”的 pair，Jaccard ≥ 0.3 即 union（`cluster.py:123-164`）。

`_connected_components` 用并查集把相似边连成连通分量，成员索引排序后返回；`cluster_probes` 再按分量顺序生成 `ClusterDraft`。因此结果只依赖 `probe_id` 与文本，不依赖数据库行序。

### 2.2 编排层：`prepare.py`

`_build_clusters` 的输入没有变：仍是 `list_clusterable_probes` 返回的 `(probe_id, attribute_type, bad_case_id)`。变化是新增一次只读的 `load_bad_case_evidence`，按 probe 取标题（`prepare.py:344-350`），再把标题传给 `ProbeForCluster.text`（`prepare.py:352-360`）。

评分与落库路径未动：仍按 `cluster_severity` 算 severity，按 `(-severity, -reportCount, type)` 排序，然后 `replace_prepared_clusters` 在同一事务里写 `probe_clusters` + `probe_cluster_probes` 并推进游标（`prepare.py:362-400`）。

`clusters_created` 事件新增三个 payload 键（`prepare.py:286-296`），值来自 `_build_clusters` 返回的 `fingerprint = cluster_hash(drafts)`（`prepare.py:400-401`）。

### 2.3 测试与门禁

`test_cluster.py` 用短标题直接断言簇成员与描述；`test_prepare.py` 用共享 harness 造 3 个 self-report case，跑完整 `EvolutionPrepareService.handle`，断言两张表、成员顺序、severity/rank 和事件 payload。`pyproject.toml` 把新 hyphen 目录的 `conftest.py` 排除出 mypy，理由与既有两处相同。

## §3 数据流走查

场景：cluster-only run，3 个 self report，标题分别是「检索索引读取失败 / 检索索引读取超时 / 工具调用超时」。

1. 启动：`POST /cluster-previews` 建 run，prepare job 从 unit 0 跑到 unit 3（Session、潜在、归因）。
2. unit 4：`_build_clusters` 调 `list_clusterable_probes`，得到 3 条 attributed 探针（`prepare.py:339`）。
3. 标题：`load_bad_case_evidence` 按 case id 读 `bad_cases`，`title_by_probe` 把 probe → 标题（`prepare.py:344-350`）。
4. 聚类：`cluster_probes` 在 prompt 类型内得到两条：`(检索索引读取失败, 检索索引读取超时)` 与 `(工具调用超时)`；前者代表标题是「检索索引读取失败」，后者是「工具调用超时」（`cluster.py:74-120`）。
5. 评分：两条 severity 分别 5.7 / 5.2，rank 1 / 2（沿用 `cluster_severity`）。
6. 落库：`replace_prepared_clusters` 写 2 行 `probe_clusters` + 3 行 `probe_cluster_probes`，游标 4 → 5。
7. 事件：`clusters_created` payload = `{clusters: 2, algorithm: "lexical-jaccard-v1", similarityThreshold: 0.3, clusterHash: <64 hex>}`。
8. cluster-only 收口：`mark_prepared(status="completed")`，前端轮询到 completed 后展示簇列表。

## §6 讨论点

### D1 单链接的传递闭包会放大“链式相似”

- **位置**：`apps/api/app/service/evolution/cluster.py:123-164`
- **现象**：A 与 B、B 与 C 各有一条 ≥ 0.3 的边时，A 与 C 即使不相似也会进同一簇；`test_single_link_merges_a_transitive_chain` 已把这个行为固定下来。
- **问题**：标题很短或共享高频词时，链式合并可能把一批不同问题并成一个大簇，severity 的 reportCount 随之变大。
- **预判**：0.3 的阈值下需要两条较强边才会链起来，演示与当前 fixture 规模可接受；若真实数据出现大簇，再考虑 complete-link 或簇直径上限。
- **结论**：

### D2 簇数增加会放大迭代轮次

- **位置**：`apps/api/app/service/evolution/cluster.py:74-120`；`prepare.py:384-400`
- **现象**：旧算法每类最多 2 簇，新算法按内容合簇，簇数可以接近 case 数；`build_rounds` 是一簇一轮。
- **问题**：完整自进化 run 的 patch/eval 次数可能显著增加，成本和耗时随数据规模上升。
- **预判**：这是“更细粒度聚类”的自然后果，不属于本 issue 的验收范围；需要限制轮次时应另立调度策略 issue，而不是在聚类里重新硬合并。
- **结论**：

### D3 聚类步新增一次外部表读取，失败语义仍是 job 失败

- **位置**：`apps/api/app/service/evolution/prepare.py:344-345`
- **现象**：`load_bad_case_evidence` 从 `bad_cases` 读标题；归因阶段也读同一张表，但归因失败会转成 `blocked(attribution)`，聚类步没有对应的 `blocked(cluster)` 包装。
- **问题**：如果 table 在归因成功后、聚类时不可读（例如连接瞬断），prepare job 会以普通异常失败，而不是 blocked 可重试。
- **预判**：同一次 prepare 里归因刚成功读过该表，窗口极小；且旧代码的 `list_clusterable_probes` 失败也有同样语义，本次没有恶化。若要补齐，应统一抽象 external read 失败映射，而不是只包这一处。
- **结论**：

### D4 阈值 0.3 来自样例校准，没有数据集回归

- **位置**：`apps/api/app/service/evolution/cluster.py:18`
- **现象**：0.3 由“检索索引读取失败/超时”“模型输出格式错误/不符合要求”等样例与“共享词元但不相关”的反例定出；测试固定了这些样例。
- **问题**：不同业务标题长度、语言混排、模板化标题可能表现不同，阈值缺少真实数据集上的分布证据。
- **预判**：本 issue 明确不承诺诊断准确性；先把阈值与算法版本写进 run 事件，后续有真实数据再评估是否调整，不在本 PR 拍板。
- **结论**：

### D5 一条 probe 关联多个 case 时代表标题取最小 case id

- **位置**：`apps/api/app/service/evolution/prepare.py:346-350`
- **现象**：`min(probe_case_ids)` 选最小 case id 的标题作代表；正常归因路径一个 probe 只对应一个 case。
- **问题**：缓存复用或异常数据可能让一个 probe 关联多个 case，代表标题就是任意（但确定）的一个。
- **预判**：当前数据模型下不会触发；若以后允许多 case 复用，可改为“公共标题/最长公共子串”，无需现在处理。
- **结论**：

### D6 `docs/architecture.md` 的“真实评测与 patch”仍是未具备

- **位置**：`docs/architecture.md:63`
- **现象**：m12-03 已合入真实 patch/评测接缝，但状态行仍把“真实评测与 patch”列为缺失；本 PR 只移除了“真实聚类算法”。
- **问题**：现状文档与已合入能力不一致。
- **预判**：属于 m12-03 的文档欠账，不应塞进本 PR；建议在 m12-03 的 follow-up 或下一个触及该行的 PR 一起修正。
- **结论**：

## §9 文件级代码分析

### `apps/api/app/service/evolution/cluster.py`（M，+180/-36）

**职责：** 纯函数聚类器，输入 attributed probe（id、类型、标题），输出有序 `ClusterDraft`。

**旧代码 vs 新代码：**

- 旧 `simple_cluster` 的“排序 → 分半 → 生成描述”全删；`ClusterDraft`、`cluster_severity`、`cluster_hash` 保留。
- 新 `CLUSTER_ALGORITHM` / `SIMILARITY_THRESHOLD` / `TYPE_ORDER` 是唯一口径常量（`cluster.py:15-21`），测试与事件 payload 共用，避免文档、实现、测试三处各写一个 0.3。
- `ProbeForCluster.text` 带默认空串（`cluster.py:27-33`）：旧调用点/测试可以只给 id 和类型；prepare 始终传标题。
- 分词不使用第三方库，避免为一次聚类引入依赖；CJK 二元组对中文短标题比整词切分更稳，ASCII 词元覆盖英文/数字。
- 倒排表把 pair 枚举限制在“共享词元”的候选集，600 条共享一个词元的测试仍在毫秒级完成。
- 描述生成把标题空白折叠并截断到 120 字符（`cluster.py:204-238`），避免超长标题撑破列表/详情；空标题回退为成员条数。

**检视发现：** `_TOKEN_PATTERN` 只覆盖 CJK 基本区与扩展 A，扩展 B 及兼容区字符会被忽略；当前产品标题以常用汉字为主，无实害。`TYPE_ORDER` 与 `TYPE_CONFIDENCE` 的键没有机械同步测试，但两者都来自封闭集合，新增类型时测试会先红。
