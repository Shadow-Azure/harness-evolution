## §1 一页速览

一句话：把“解析哪种 agent 的轨迹”从散落在 normalizer 里的隐含假设，变成数据库、replay 和 parser 都认的一个 `runtime_key`。

比喻：原来的 `normalize.py` 像一个只会说 Claude 方言的翻译员；现在前台先看工牌（runtime_key），再叫对应语种的翻译员。新语种只需新增一个翻译员并登记，不用改前台流程。

| 交付块 | 内容 | 验收 |
|---|---|---|
| 扩展点 | `BaseTraceParser` + 工厂 + 自动发现 | 新 runtime 只加子类；重复 key 失败 |
| 身份 | 四表 runtime_key + 复合主键/唯一键 | 存量回填 claude-code；同 root/agent 可按 runtime 并存 |
| 版本 | per-runtime parser_version | 升级 fake runtime 只重放 fake root |
| 失败语义 | 未知 runtime `UNSUPPORTED_RUNTIME` | 不进入 Claude parser，不写业务树 |
| 文档 | Agent Note + 架构现状 + scope | 双语配对、flow、docs 门禁 |

验证基线（本地实测）：`pnpm lint:api`、`pnpm typecheck`、`pnpm typecheck:api`、`pnpm test:api`（1039 passed / 16 skipped，覆盖率 91%）、`pnpm test:db`（20 passed）、`pnpm build`、`pnpm contract:check`、`pnpm fixtures:check` + `fixtures:seed`、`pnpm verify:docs`、`pnpm verify:flow` 均通过。MySQL 与 E2E 由 CI lane 执行。

## §2 架构导览

### 2.1 模板方法与子类边界

`BaseTraceParser.normalize()`（`parsers/base.py:329`）只做三件事：拆物理行、解码 JSON、把 record 交给 `consume_record`。坏行、非对象 JSON、空对象都在 `decode_record`（`base.py:346` 附近）变成稳定 issue，后续行继续解析。

`ParseContext`（`base.py:161`）是“公共计数器 + 隐私边界”：子类只能通过 `record_user_turn`、`record_assistant_message`、`record_tool_use`、`record_block` 等方法提交结构化事实，最终 `finalize`（`base.py:372`）统一生成 `ParsedTranscript`。这样消息正文、工具输出不会因为新增 runtime 而意外进入公共字段。

Claude 子类（`claude_code.py:74`）保留原有 `assistant/user/attachment`、`isMeta`、`content`、usage 去重、Agent/Skill/Workflow 事件命名规则；`parse_agent_meta`（`claude_code.py:165`）只投影公共 facts。`extract_evidence()`（`base.py:425`、`claude_code.py:181`）当前返回空元组，是 M9-02/M9-04 的接口占位。

### 2.2 工厂与发现

`TraceParserFactory.register`（`factory.py:25`）在重复 `runtime_key` 时直接抛 `RuntimeError`，不静默覆盖；`create`（`factory.py:39`）找不到时抛 `UnsupportedTraceRuntime`（`factory.py:10`），没有 `get(..., Claude)` 这种回退。`parsers/__init__.py` 用 `pkgutil.iter_modules` 导入同目录模块，因此新增 `parsers/<runtime>.py` 不需要改工厂。

`normalize.py` 的 `CURRENT_PARSER_VERSION` 来自 `TraceParserFactory.create("claude-code").parser_version`，这让“自动发现”成为导入期硬依赖，而不是可选项。

### 2.3 replay 查询与写入

`_pending_condition`（`acquisition_replay.py:173`）由四部分组成：source 不存在、hash 为空、hash 变化、parser_version 为空，或该行 runtime 的版本落后。`_processed_condition`（`:191`）要求 hash 相同且属于已注册 runtime 且版本不落后；未知 runtime 不会被算成 processed。

`list_root_payloads`（`:230`）按 runtime + root 取全部 agent 原文；`replace_normalized_root`（`:615`）在同一事务里删旧树、写 `session_families`/`agents`/事件/用户轮次，并按 runtime 推进 source cursor。`agents` 与 `session_families` 都写入根 runtime。

### 2.4 迁移

`0015` 对 SQLite 采用“临时表 + 复制 + 替换 + 改名”，因为 SQLite 不能直接改复合主键；对 MySQL 直接 `ADD COLUMN`、`DROP PRIMARY KEY, ADD PRIMARY KEY`、替换唯一键与索引。存量行统一 `server_default='claude-code'` 回填，`agents`/`session_families` 同样补列。

## §3 数据流走查

1. 外部脚本写 `trajectory_payloads`，或 local/upstream 路径写 payload；新行带 `runtime_key`，老行/未显式写入的行由默认值成为 `claude-code`。
2. scheduler 或 admin 触发 sync；`sync.py` 用 `TraceParserFactory.versions()` 生成 per-runtime 版本表。
3. `list_pending_payloads` 按 `(runtime_key, root, agent)` 找出待处理 identity，未知 runtime 也会被列出。
4. replay 按 `(runtime, root)` 分组；factory 选择 parser；该 root 的全部 payload 被 normalize 成 `ParsedTranscript`。
5. `assemble_agent_trees` 校验同一 root 只有一个 main、无重复 agent、runtime 不混用，生成 Session/Agent 树。
6. `replace_normalized_root` 在一个事务里重写业务表，并只推进当前 runtime 的 source cursor；另一个 runtime 的 cursor/Session 保持不变。
7. 未知 runtime 在 factory 处被截住，写 `UNSUPPORTED_RUNTIME`，不进入 Claude parser，也不产生业务行。

## §6 讨论点

### 6.1 未知 runtime 会持续保持 pending

- **位置**：`apps/api/service/acquisition/replay.py:183`
- **现象**：未知 runtime 只写 `UNSUPPORTED_RUNTIME` 并计为 failed，不推进 source cursor；调度器下一轮仍会看到它。
- **问题**：如果上游误写一个未知 runtime，sync 每 60 秒创建一次任务，直到补 parser 或人工清理 payload；日志/任务列表会持续有失败记录。
- **预判**：与现有“结构损坏 root 保持 pending”一致，是有意暴露而非静默吞掉；当前单实例、低频接入可接受。若要改善，应增加“终止性诊断 cursor”而不是在 replay 里回退 Claude。
- **结论**：

### 6.2 Session DTO 暂未暴露 runtimeKey

- **位置**：`apps/api/app/service/sessions/schemas.py`（本 PR 未改）
- **现象**：数据库已有 `session_families.runtime_key`，但 `SessionListItem` / `SessionTree` 还没有 `runtimeKey` 字段；`plans/fullstack-design/05-api-design.md` §3.1 的示例包含该字段。
- **问题**：前端暂时拿不到 runtime；如果 M9-01 在改 Session DTO 时遗漏，该字段会继续缺失。
- **预判**：本 issue 明确“不改前端展示”，且 M9-01 的实现内容包含“更新 OpenAPI、契约快照与证据 DTO”，由 M9-01 统一补 runtimeKey 可以避免和 executionOutcome 的契约变更拆成两次。
- **结论**：

### 6.3 SQLite 迁移依赖 Alembic 连接默认关闭外键

- **位置**：`apps/api/alembic/versions/0015_runtime_identity.py:134`
- **现象**：`source_records` 重建时直接 drop 旧表；`session_families` / `agents` 有指向它的外键。当前 Alembic 的独立 SQLite 连接默认 `foreign_keys=OFF`，所以测试通过。
- **问题**：如果未来有人用 `foreign_keys=ON` 的连接执行迁移，`DROP TABLE source_records` 可能失败或留下不一致引用。
- **预判**：本地/测试 SQLite 的迁移路径由 `app/db/migrate.py` 控制，生产是 MySQL；当前无实害。可在迁移里显式临时关闭外键或改 batch，但会增加跨方言复杂度。
- **结论**：

### 6.4 同一 root session id 不能跨 runtime 共存

- **位置**：`apps/api/app/db/models/domain.py`（`session_families.id` 仍是单列主键）
- **现象**：payload/source 的 identity 已带 runtime，但 Session 表仍以 root id 为全局主键。
- **问题**：若两个 runtime 恰好产生同一个 root session id，后处理的 Session 会替换先处理的 Session，留下另一 runtime 的 source cursor。
- **预判**：真实 agent 的 root id 是 UUID/ULID，碰撞概率可忽略；设计 06 也把 `session_families.id` 定为单主键。保持现状，出现真实碰撞再评估复合键。
- **结论**：

### 6.5 未知 runtime 诊断包含 runtime key（已修）

- **位置**：`apps/api/app/service/acquisition/replay.py:183` 附近
- **现象**：初版 `sync_runs.errors.message` 只写 “Trace payload runtime is not supported”，运维无法从批次错误直接看出是哪个 runtime。
- **问题**：诊断码稳定，但排障需要再查 payload 行。
- **预判**：`runtime_key` 不是正文/隐私内容，且列宽 32，直接放进 message 安全；HTTP status 仍只映射通用文案。
- **结论**：已修复，message 改为 `Unsupported trace runtime: <runtime_key>`，测试覆盖。

## §9 文件级代码分析

### `parsers/base.py`

- **职责**：runtime 无关的模板方法与公共结果类型（A）。
- **关键依赖**：仅标准库与 `app.utils.time`；不导入任何 provider 模块，避免 base 反向依赖具体 runtime。
- **变更块**：`ParsedTranscript` 增加 `runtime_key`；新增 `TracePayload` / `AgentMetaFacts` / `TraceEvidence` / `ParseContext`；`normalize`/`decode_record`/`finalize` 承接原 `normalize.py` 的帧与计数逻辑。
- **实现思路**：把“解析协议”和“解释记录”分开；子类只改解释层。
- **检视发现**：`extract_evidence` 默认空元组，覆盖 M9-02 之前的所有 runtime。

### `parsers/factory.py` + `parsers/__init__.py`

- **职责**：注册表、版本表、自动发现（A）。
- **变更块**：重复 key 抛错；未知 key 抛 `UnsupportedTraceRuntime`；`versions()` 返回按 runtime 的版本；包导入时 import 子模块。
- **检视发现**：无。注册发生在导入期，无并发写；测试用 fake runtime 验证“只注册即可用”。

### `parsers/claude_code.py`

- **职责**：Claude 专有 record/meta 解释（A）。
- **变更块**：原 `normalize.py` 主体搬入 `consume_record`；`parse_agent_meta` 投影 `agentType/taskKind/teamName/name/skillName/model/toolUseId/parentAgentId/spawnDepth`；事件命名与 usage 去重保持原行为。
- **检视发现**：`extract_evidence` 为空是 issue 明确的接口占位。

### `service/acquisition/normalize.py`

- **职责**：公共 facade（M，−522/+约 20）。
- **变更块**：类型定义迁到 `parsers/base.py`；`normalize_transcript` 增加 `runtime_key` 默认值并走 factory；`aggregate_transcripts` 保留。
- **检视发现**：`CURRENT_PARSER_VERSION` 通过 factory 创建 Claude parser 获取，导入期即验证自动发现。

### `replay.py`

- **职责**：按 runtime root 原子 replay（M）。
- **变更块**：pending 查询传版本表；分组键改为 `(runtime, root)`；factory 选择 parser；未知 runtime 走独立错误分支；`replace_normalized_root` 传 parser 版本。
- **检视发现**：§6.1/§6.5。

### `db/crud/acquisition_replay.py`

- **职责**：payload/source 存储原语（M）。
- **变更块**：`PendingPayload`/`RootPayload`/`MissingPayloadSource` 增加 runtime；join 三列；per-runtime pending/processed 条件；source 插入/更新按 runtime；Session/Agent 插入带 runtime。
- **检视发现**：`_pending_condition`/`_processed_condition` 是纯 SQL 表达式，便于双方言复用；未知 runtime 不计 processed。

### `alembic/versions/0015_runtime_identity.py`

- **职责**：runtime identity 迁移（A）。
- **变更块**：SQLite 重建 `trajectory_payloads`/`source_records`，MySQL 改主键/唯一键/索引；三个表 + agents 增加列；downgrade 对称恢复。
- **检视发现**：§6.3/§6.4。

### 测试与文档

- **新增测试**：factory 契约、fake runtime normalize、fake runtime replay、per-runtime 版本升级、未知 runtime、0015 回填与复合 identity。
- **文档**：Agent Note 记录取舍；`docs/architecture.*` 更新 payload identity 与 parser 选择；issue scope 增补测试/文档/检视路径。
- **检视发现**：无额外问题；MySQL 迁移的实际执行由 CI 覆盖。
