## §1 一页速览

**一句话：** 这个 PR 把自进化首页从“未来会接入”的 Vue Flow 占位页，换成了真正读取持久 run 的两组运行卡片；浏览器负责显示，后端负责决定哪条 run 属于哪组、阶段是什么、进度和接纳数是多少。

**比喻：** 后端像档案室的登记员，已经按“正在办理/历史归档”分好文件并写好每份文件的进度标签；前端只是把文件放进原型里的卡片盒，不再自己猜另一套排序和百分比。

## §2 架构导览

### 2.1 HTTP 层只提供一个只读入口

`GET /api/evolution/runs` 通过共享 `BEARER_AUTH` 保护，返回 `EvolutionRunList`（`api/evolution_runs.py:19-29`）。前端约定 401 是未登录，403 仍可能表示必须先改密；创建、编辑、重试等写动作不在本端点。

这个端点的输入为空，输出已经被后端分为两个数组。调用方拿到 `running` 与 `history` 后只按数组顺序渲染，不需要再写“若 status 在 [...] 则放进某组”的第二套规则。

### 2.2 服务层把数据库事实翻译成卡片

`EvolutionRunService` 是“登记员”：它从 repository 拿到带聚合事实的 summary，再用 `_card()` 转成公开契约（`service/evolution/runs.py:208-241`）。六个状态在 05 §4.10 中固定：

```text
preparing / running / blocked → running
completed / failed / interrupted → history
```

`_progress()` 是唯一的进度计算点（`:158-178`）。它根据持久化 `progress_unit` 与真实 cluster 数生成总单元、half-up 百分比、阶段文案、已完成轮次和接纳数。前端不再有例如 `Math.round(unit / clusters)` 的逻辑。

生成出的 `stage_label` 保留原型文案“LLM 归因置信度”，而不是复用详情页的“归因确认”；这让列表文案和原型一致，而详情页仍可沿用既有六步标题。

### 2.3 统计和创建人来自同一次批量读取

`list_summaries()` 先读取全部 run 和创建人，再对这批 run 做三次集合查询：cluster 数、accepted round 数、final（`db/crud/evolution.py:104-178`）。这像先把一叠档案编号收集好，再一次性查询每个档案对应的附件，不会逐张卡发请求。

`_stats()` 只接受定义的统计字段并补零；`usedProbes` 根据 `model + prompt + error` 派生（`service/evolution/runs.py:136-155`）。这是任务要求的“用于进化”口径：非问题和未分析不算进去，即使旧的 `stats.usedProbes` 值过期也不会污染列表。

### 2.4 运行卡是纯投影，不是执行状态机

`RunCard.vue` 使用 backend 已给出的 `status` 生成显示 badge，使用 backend 已给出的 `percent` 设置宽度，使用 backend 已给出的 `stageLabel` 显示进度文案（`RunCard.vue:9-72,124-168`）。

它能处理两个容易误报的场景：

- `completed` 且 `final=null`：显示“已完成 · 终评未知”，不把缺失 final 推断成“无收益”（`:21-25,36-39`）；
- `blocked/failed/interrupted`：错误说明只挂在状态 badge 的 `title`/`aria-label`，不把 `eval`、`push` 等内部阶段码直接排成额外错误行（`:83-89`；`:146-168`）。

### 2.5 共享页面框架负责原型的 1080px 几何

M5-03 的配置页和 M5-04 的运行列表共用 `.evolution-page-frame`（`styles/main.css:41-55`）。它用父容器推导的 `width` 与相对定位保持 24px 视口 gutter，不使用会劫持 fixed 弹窗的 `transform`；因此运行列表继承配置页的桌面/中等/手机宽度，而 M5-03 的弹窗遮罩仍覆盖整个 viewport。

### 2.6 E2E 使用真实 SQLite、FastAPI、Vite 和 Chrome

`m5-run-list.test.mjs` 起动真实服务，先断言两个空组，再插入七个 run，检查 3 个 running + 4 个 history 的顺序、creator meta、紫色 target chip、青色 model chip、状态背景、6px 进度条、无内部 stage 泄漏、无假 hover 和 390px 页面无横向溢出（`:223-402`）。

截图写到临时目录，测试结束后清理，避免 E2E 修改仓库中的报告资产（`:137-143,146-149,399-401`）。

## §3 数据流走查

### 场景 A：首次进入 `/evolution`

1. `Index.vue` 挂载 `useEvolutionRuns()`，读取固定 query key（`Index.vue:12-14`）。
2. 请求 pending 时显示 4 行骨架（`:46-50`）。
3. API 返回两个空数组时，两个 `RunGroup` 都进入自己的空态；running 文案是“当前没有正在执行的自进化”，history 是“暂无历史记录”（`RunGroup.vue:41-48`）。
4. 页面标题、说明和禁用 Launch 按钮仍在，不会把整个页面替换成空白（`Index.vue:26-44`）。

### 场景 B：运行库中存在六种状态

1. repository 一次读取所有 run 并按 `created_at DESC, id DESC` 排序（`db/crud/evolution.py:120-124`）。
2. service 统计真实 cluster/accepted/final，计算每个卡片的 `progress`（`service/evolution/runs.py:136-178`）。
3. 六种 status 被固定分入 running/history；每个数组保持 repository 原始相对顺序（`:244-257`）。
4. `RunGroup` 只按数组渲染，不调用 `sort` 或再分组（`RunGroup.vue:31-40`）。
5. E2E 直接验证 running `[running, blocked, preparing]` 与 history `[completed-effective, failed, interrupted, completed-no-benefit]` 的顺序（`m5-run-list.test.mjs:245-270`）。

### 场景 C：失败的 run 只有内部 error 摘要

1. repository 返回 `error.stage=eval`、`error.message=...`（契约见 05 §3.5）。
2. `RunCard` 状态 badge 的 `title` 和 `aria-label` 使用 message；页面正文不显示 `eval · ...`（`RunCard.vue:83-89`）。
3. 用户能通过视觉/辅助技术看到“失败/已中断”和错误摘要；组件测试锁住无 `.run-error` 额外行（`RunCard.test.ts:161-225`）。

### 场景 D：完成但没有 final

1. `status=completed`，但 repository 没有 final 行。
2. status 文案变成“已完成 · 终评未知”，class 是中性 `done-pending`（`RunCard.vue:21-25,36-39`）。
3. 卡片底部只显示“终评数据暂不可用”，不显示 `best vs 初始`（`:146-167`）。
4. 这条路径由组件回归覆盖（`RunCard.test.ts:145-159`）。

### 场景 E：读取失败

1. `Index.vue` 收到 query error 后显示页级 `ErrorState`，标题、说明、齿轮入口仍在（`Index.vue:26-56`）。
2. 点击重试调用 `refetch`；成功后重新显示两个运行组（`:16-18`，`Index.test.ts:165-185`）。

### 场景 F：从 M5-03 配置页回到自进化

1. 运行列表和配置页共用 `.evolution-page-frame`，不改变顶层页面宽度。
2. M5-03 测试在真实浏览器里继续验证 target 页的 1080/800/390 几何、全视口 overlay 和齿轮导航（`m5-target-config.test.mjs:338-356,809-855`）。
3. 本 PR 没有把 target 页的行为替换为运行列表逻辑，只把页面容器类抽到共享 CSS。

## §6 讨论点

### D1 仓库内预览截图仍是修复前的 UI

**位置：** `reports/2026-10-27/m5-04-run-list/screenshots/01-desktop-1408.png`、`02-mobile-390.png`；当前 UI 代码见 `RunCard.vue:83-97,146-168`。

**现象：** 两张 tracked 截图仍显示可见的 `eval · 评测队列暂停` / `eval · 评测执行失败…` 错误行。当前 `RunCard.vue` 已删除 `.run-error` 行，错误只进入状态 badge 的 title/aria-label；E2E 也断言页面正文不含 `eval ·`。`git log --follow` 显示两张图来自 `07900bc`，后续修复提交没有更新它们。

**问题：** PR 中的 `reports/` 是用户会当作验收证据查看的目录。现在的截图会把已修复的旧 UI 呈现成当前事实，误导 reviewer，也违反 smoke 报告的“证据是 source of truth”原则。

**预判：** 在 `computer-use-smoke-reporting` 阶段重新生成修复后的截图并用官方 renderer 输出最终报告；或在最终 smoke 前移除这两张预览图。不要让 E2E 每次重写 tracked 文件，当前临时目录策略保留。

**结论：** 成立。旧预览图已从 PR 删除；最终验收必须以随后生成的 smoke 报告截图为准。

### D2 失败/阻塞错误摘要只在不可聚焦的 title 中

**位置：** `RunCard.vue:83-89`、`RunCard.test.ts:161-225`。

**现象：** 状态 badge 是普通 `<span>`，错误消息通过 `title` 与 `aria-label` 暴露。鼠标悬停可看到浏览器原生 title，但 span 不可聚焦，触屏设备没有可靠 hover；有视觉需求但不能用鼠标的用户无法查看错误摘要。设计 08 §8 要求 failed/interrupted 的 `error.message` 摘要 tooltip，而原型也把它作为可查看的状态附加信息。

**问题：** 屏幕阅读器能读 aria-label，但“看得见的人”在移动端或键盘场景里只能看到“失败/已阻塞”，无法知道原因。错误摘要的状态从“tooltip”退化成只对鼠标有效。

**预判：** 为仅在有 error 时的 badge 提供键盘/触屏可用的轻量 tooltip（例如可聚焦的 `ElTooltip` 或 `aria-describedby` + focus/hover 视觉提示），保持不新增常驻错误行；补组件断言和 390px E2E。不要在可见区泄漏 `eval/push` 阶段码。

**结论：** 成立。错误 badge 已改为可聚焦、可点击 trigger，通过 `aria-describedby` 与 `role=tooltip` 暴露摘要；组件和真实 Chrome 均覆盖。

### D3 E2E 对六种状态只锁排序，未锁全部状态文案

**位置：** `m5-run-list.test.mjs:245-270,322-349`；组件 `RunCard.test.ts:51-225`。

**现象：** 浏览器 E2E 验证七个 run 的 ID 顺序、running 卡样式和 failed/interrupted tooltip，也验证没有内部 stage；但它没有直接断言 `preparing → 准备中`、`completed no benefit → 已完成 · 无收益`、`completed final=null → 已完成 · 终评未知`。组件测试覆盖了 running/completed/blocked/failed/interrupted，其中 preparing 的文案仍主要依赖 status mapping 实现。

**问题：** 后端分组正确时，如果前端准备态文案回退为“未知状态”，E2E 仍可能通过。这个风险较小，但 M5-04 的验收明确要求六种状态。

**预判：** 在组件测试补 preparing 文案，并在 E2E 对七张卡的状态 badge 文案做一次映射断言；仍保持后端负责 status，不把测试变成第二套状态机。

**结论：** 成立。组件测试补 `准备中`；E2E fixture 增加 `completed + final=null`，并锁定八张卡的全部状态文案。
