## §1 一页速览

一句话：把「一个 bad case 的多条对象·版本归因」从两张既有表里按稳定顺序读出来，并让每条归因能用一个 `attributionId` 深链打开，同时不破坏旧的 probe/analysis 读法。

一个比喻：**像便利店的取货柜**——柜门（case）先验证是不是你的；柜门里每个格子贴着一张取货单（attributionId），按放进去的时间从新到旧排；格子上写着它属于哪个对象/版本、走没走缓存、放单子的那次班次（run）；如果单子上缺版本号或触发点对不上，就贴一张固定格式的“信息不全”便签（warning），而不是猜。

| 交付块 | 内容 | 证据 |
|---|---|---|
| 分页列表 | `GET …/attributions?page&pageSize`，newest-first，total/page/pageSize | 新 suite 的 paging / beyond-page 用例 |
| 详情深链 | `GET …/attributions/{attributionId}`，触发点对照 + warnings | detail / warning / coordinate 用例 |
| 归属校验 | 未知或跨空间 case → 404 BAD_CASE_NOT_FOUND；跨 case id → 404 ATTRIBUTION_NOT_FOUND | cross-case / unowned / outsider 用例 |
| 计数 | `BadCase.attributionCount/hasAttribution` = distinct object·version | count 用例；既有 m4-02 精确 DTO 用例 |
| 兼容 | `/analysis`、`/sessions/{sid}/probes`、`/probes/{id}` 不动 | legacy 用例 |
| 契约 | FastAPI OpenAPI 重新生成，TS 类型同步 | `contract:generate` + `contract:check` |

## §2 架构导览

### 2.1 HTTP 层只做三件事

`apps/api/app/api/problems.py:215` 与 `:245` 分别是列表和详情端点。它们只做参数绑定（`page` 默认 1、`pageSize` 默认 2/上限 50、id 单段路径上限 64）、复用既有 `require_workspace_role(viewer)` 依赖，然后把 `WorkspaceReadScope.for_workspace(...)` 交给服务层。公共 DTO 直接作为返回类型，所以 OpenAPI 自动生成，不需要手写序列化。

依赖注入走 `request.app.state.attribution_read`（`problems.py:45`），与现有 `problems_from` 同构；装配点只有 `main.py:256` 一处。

### 2.2 服务层拥有两条领域规则

`AttributionReadService`（`apps/api/app/service/bad_cases/attribution.py:29`）把「case 先可读」和「attributionId 必须仍挂在这个 case」放在服务层，而不是塞进 repository：

```python
# 列表：先验证 case，再取 total 与当页
await self._require_case(case_id, scope)
total = await self._attributions.count_links(case_id)
rows = await self._attributions.list_attributions(case_id, offset=..., limit=...)
```

```python
# 详情：先验证 case，再查 link；link 不存在就是 404 ATTRIBUTION_NOT_FOUND
record = await self._attributions.get_attribution(case_id, attribution_id)
if record is None:
    raise AppError(404, ErrorCode.ATTRIBUTION_NOT_FOUND, ...)
```

这样 repository 只回答「表里有没有行」，服务层回答「这次请求能不能看」。`case_visible`（`db/crud/problems.py:124`）复用 `bad_cases` 的空间条件，只做一次存在性查询，不加载 Session 树。

### 2.3 计数口径放在外部读边界

`BadCase.attributionCount` 的唯一口径是 06 §4.2.1 的 distinct `(probe_type, probe_object, object_version)`。实现没有加列、没有额外 SQL，而是在 `service/bad_cases/service.py:123` 用快照里已有的 analysis/probe 行做去重：

```python
triples.setdefault(row.bad_case_id, set()).add(
    (probe.probe_type, probe.probe_object, probe.object_version),
)
```

这保持与 SQL 版 `attribution_count()` 同语义，也让 `get_case` / `list_for_session` 两条旧路径顺带拿到计数；`BadCase.has_attribution` 只是 `count > 0` 的派生。

### 2.4 triggerCompare：候选快照是唯一证据源

`latest_candidate_trigger`（`db/crud/attributions.py:813`）取该 probe 最新一条 `evolution_run_candidates`，同时 outer join 两个触发点的 agent 取 `tree_index`。服务层 `_trigger_order`（`attribution.py:180`）按设计顺序判定：

1. 两侧都有 `triggered_at` → 比时间，相等为 `same`，否则 `before/after`；
2. 否则四元坐标齐全 → 按 `(tree_index, event_index)` 字典序；
3. 候选 `order_state != comparable` 或缺坐标 → `unknown`。

`versionState` 只看 `probe_reports.object_version` 是否为空：新 run 一定 pin 版本，历史空值不伪造。`warnings`（`attribution.py:139`）把版本未知、触发点不可比、legacy import、run 来源缺失四类证据缺口固定成 code/message，文案不插值外部字段。

### 2.5 契约与生成物

`AttributionItem/AttributionDetail/AttributionTriggerCompare/AttributionWarning/AttributionPage` 定义在 `service/bad_cases/attribution_schemas.py`，继承 `IdentityModel`（camelCase、`extra=forbid`）。`pnpm contract:generate` 重写 `packages/contracts/openapi.json` 与 `api.d.ts`；`test_openapi.py` 的路径集合与鉴权清单同步增加两个路径。

## §3 数据流走查

主线剧本：错误详情左栏选中 case → 拉第 1 页归因 → 点第一条 → 深链详情。

1. 浏览器请求 `GET /api/workspaces/ws-a/bad-cases/bc-1/attributions?page=1&pageSize=2`。
2. `require_workspace_role("viewer")` 解析 `ws-a` 的成员角色；失败时 404/403 在进入服务前就结束。
3. `AttributionReadService.page`：`case_visible` 查 `bad_cases` 的 `workspace_id`，不在 `ws-a` → `404 BAD_CASE_NOT_FOUND`。
4. `count_links` 用 `bad_case_analysis JOIN probe_reports` 数出可投影行数（无 probe 的 V1 兼容行不计）；`list_attributions` 按 `probe_reports.updated_at DESC, probe_id DESC` 取 offset/limit。
5. 每行经 `_item` 投影：`probe_id → attributionId`、`last_reused_run_id ?? created_run_id → runId`、`last_reused_run_id 存在 → isCached`。
6. 用户点击第一条 → `GET …/attributions/probe-123`。`_require_case` 再次校验 case；`get_attribution` 同时按 `bad_case_id + probe_id` 查 link，跨 case 直接 `404 ATTRIBUTION_NOT_FOUND`。
7. `latest_candidate_trigger("probe-123")` 取最新候选，`_trigger_order` 得出 `after`；`versionState` 由 `object_version` 给出；`_evidence_warnings` 产出空数组或固定 code。
8. 返回 `AttributionDetail`（camelCase JSON），前端用 `triggerCompare` 渲染「对象进入点 vs case 触发点」。

## §6 讨论点

### D1 `total` 与当页项来自两个数据库会话

- **位置**：`apps/api/app/service/bad_cases/attribution.py:54-60`；`db/crud/attributions.py:798`
- **现象**：先 `count_links` 再 `list_attributions`，各自开一个 `database.session()`。
- **问题**：并发写入时可能出现 total 与 items 来自不同快照（例如 total=4 但第 2 页只有 1 条）。
- **预判**：只影响瞬时展示，不影响深链或归属校验；合并成单会话也挡不住 MySQL 的默认隔离级别差异，收益有限，本 PR 不改。
- **结论**：（留空）

### D2 外部行字段漂移会 500 而非降级

- **位置**：`apps/api/app/service/bad_cases/attribution.py:96-111`
- **现象**：`probe_type`、`conclusion`、`attribute_type` 直接 `cast` 后交给 Pydantic 的 `Literal` 校验。
- **问题**：如果外部写入方把 `conclusion` 写成闭集外的值，列表/详情会 500；旧 `service/bad_cases` 对同类漂移采用 warning + 降级。
- **预判**：V2 写入由本服务 `ProbeWrite` 强制闭集，m10 迁移也回填了结论，现实风险低；若未来接外部直写，应在这里补 `_literal` + 降级 warning。
- **结论**：（留空）

### D3 `versionState` 只由 object_version 是否为空推导

- **位置**：`apps/api/app/service/bad_cases/attribution.py:119-123`
- **现象**：`versionState = exact` 当且仅当 `probe_reports.object_version` 非空。
- **问题**：设计说「历史 legacy 行可为 unknown」，但没有额外版本匹配状态；当前实现把所有有版本的归因都当 exact，包括假设存在的「历史行自带版本」。
- **预判**：迁移不回填历史版本，V2 新 run 一律 pin 版本，该近似与现有数据一致；若未来引入版本回填，需要改成按候选的版本解析状态。
- **结论**：（留空）

### D4 `BadCase.analysis` 暂时与计数并存

- **位置**：`apps/api/app/service/problems/schemas.py:141-151`
- **现象**：V2 设计说「BadCase 不再内联单条 analysis」，本 PR 仍保留它，同时新增计数。
- **问题**：客户端会看到两套归因摘要；文档与实现存在阶段性差异。
- **预判**：m11-02 前端切换完成前删除会破坏当前错误页；这是有意的兼容窗口，m11-06 退役旧字段，已写入 owning Note 的 Consequences。
- **结论**：（留空）

### D5 `pageSize` 默认 2 是 UI 约定而非设计明文

- **位置**：`apps/api/app/api/problems.py:224`
- **现象**：§4.19 只给了 `pageSize=2` 的示例，没有规定默认值；端点默认 2。
- **问题**：默认值属于契约，未来 UI 想要不同默认页大小需要改客户端或显式传参。
- **预判**：issue 明确「归因按 2 条分页」，m11-02 的 `useAttributions` 也按 2 条设计；把它固化为默认值是合理的。
- **结论**：（留空）

### D6 CI 的 `docs-flow` 与 `flow-online` 被 #301 阻塞

- **位置**：`.agents/flow/issues/m10-04-seven-step-prepare.md`（本 PR 未改）
- **现象**：`verify-flow` 报「m10 尚有 1 个同档 issue 未 done（m10-04-seven-step-prepare）」；GitHub 侧 #213 已 CLOSED，本地仍是 in-progress。
