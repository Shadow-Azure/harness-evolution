## 1. 一页速览

一句话：这个 PR 给真实 candidate 加了一名“值班传话员”——`eval_poller` 按数据库里的时间表替 JobRunner 去问评测平台，拿到结果后把下一道 apply/finalize 工单放回持久队列。

比喻里最重要的不是传话员本人，而是它的“值班簿”：`eval_next_poll_at`、`eval_external_id`、completed result 和轮次终态都在数据库。进程重启后，换一个传话员也能照值班簿继续，不依赖上一名传话员的记忆。

| 交付块 | 结果 |
|---|---|
| Gateway | `submit/get_status/get_result` 稳定协议；Fake gateway 由 run 创建期配置确定 |
| 提交评测 | 真实 push 成功后才提交；external id、状态、attempt、起止与下次轮询持久化 |
| 轮询 | queued/running 延后 5 分钟；completed 保存一次结果；failed/timeout/坏数据进入 `blocked(eval)` |
| 自动续链 | completed → apply → accept/reject → 下一轮或 finalize，不新增人工 advance API |
| 终评 | 写 `evolution_finals`、校验/发布 run 分支，最后才把 run 置 completed |
| 恢复边界 | poller 自身定时状态可从 DB 恢复；自动退避、崩溃 job 与 SSE 重连仍归 m5-11 |

## 2. 架构导览

### 2.1 Gateway 是稳定插座，Fake 是可复现插头

[contracts.py:103](../../../apps/api/app/service/evolution/engine/contracts.py#L103) 把 `eval_config` 深冻结成 `EvalGatewayConfig`。提交、状态和结果是三个独立 DTO；[contracts.py:130](../../../apps/api/app/service/evolution/engine/contracts.py#L130) 的 Protocol 只暴露稳定业务语义，不泄露 HTTP 平台字段。

`FakeEvalGateway` 的关键设计是**不保存内存任务**：`eval_id` 由 run、round、candidate commit 推导，状态和分数由配置决定（[contracts.py:239](../../../apps/api/app/service/evolution/engine/contracts.py#L239)）。所以新进程拿到旧 `eval_id` 后仍能解释同一结果，像用订单号从公告板取回结果，不需要柜台职员记得昨天说过什么。

### 2.2 持久状态是轮询事实源

[evolution.py:973](../../../apps/api/app/db/crud/evolution.py#L973) 在一个事务里保存 external id、`evaluating`、attempt、start、next poll 与 run 聚合状态；[evolution.py:1156](../../../apps/api/app/db/crud/evolution.py#L1156) 只允许第一次写入结果，并同步 `eval_current/eval_candidate` UI 投影。

结果落库后并不立刻变成内存回调：completed result 本身成为后续扫描的 durable marker，[evolution.py:1063](../../../apps/api/app/db/crud/evolution.py#L1063) 会持续找到尚未 apply 的轮次。这样即使“结果已落库、工单还没建好”之间进程退出，重启后仍能补工单。

### 2.3 Poller 只做 DB + external HTTP

[eval_poller.py:173](../../../apps/api/app/service/evolution/eval_poller.py#L173) 的循环不占 JobRunner 全局 worker，也不执行 git。一次扫描依次处理：

1. 到期的 evaluating 轮次；
2. completed 但尚未 apply 的轮次；
3. 全部轮次已终态但仍 running 的 run，补 next advance 或 finalize。

[eval_poller.py:326](../../../apps/api/app/service/evolution/eval_poller.py#L326) 在问 gateway 前先检查 run、mode、status、push skipped 与 timeout。异常只隔离当前轮次，不终止整批扫描（[eval_poller.py:239](../../../apps/api/app/service/evolution/eval_poller.py#L239)）。

### 2.4 Apply 复用真实 Git 边界

[apply_final.py:43](../../../apps/api/app/service/evolution/apply_final.py#L43) 不直接写“accepted”；它从持久 result 和 cluster/probe 证据重建 trace，再调用 m5-09 的真实 `accept`/`reject`。所以 external verdict 只决定方向，amend、candidate force-with-lease、run 分支 fast-forward 与 candidate 清理仍由同一个 Git 边界负责。

### 2.5 Finalize 先形成终评事实，再发布 run

[apply_final.py:153](../../../apps/api/app/service/evolution/apply_final.py#L153) 先确认所有轮次都是 accepted/rejected/skipped，再写 `evolution_finals`、校验并发布 run 分支，最后 `complete_run`。这条顺序保证 UI 不会在看到 completed 后才发现终评 row 不存在。

## 3. 数据流走查

示例：run `evo-42` 的第 2 轮 candidate 已真实 push。

1. advance job 把轮次切到 `evaluating`，`EvolutionEvalSubmitter.submit()` 调 gateway 得到 `fake:evo-42:r2:<commit>`，并把 next poll 设为 5 分钟后（[eval_poller.py:62](../../../apps/api/app/service/evolution/eval_poller.py#L62)）。
2. 30 秒一次的 poller 扫描只取 `next_poll_at<=now` 的行；不到 5 分钟时什么都不做。
3. gateway 返回 running：只把下一次 deadline 再推后 5 分钟，不重复 submit。
4. gateway 返回 completed：poller 取结果、脱敏、只保存一次，并更新 run/round 的分数投影（[eval_poller.py:370](../../../apps/api/app/service/evolution/eval_poller.py#L370)）。
5. 下一段扫描看到 durable completed result，确保存在一个 `evolution_apply` job；JobRunner 的 active-stage 约束防止同一 run 并发进入下一阶段。
6. apply 用 external verdict 接纳或拒绝；accept/reject 在同一 DB 事务推进 `progress_unit`。
7. terminal hook 发现还有 pending round 就排 advance，否则排 finalize。
8. finalize 写终评、发布最终 run 分支，最后将 run 置 completed。

## 5. 人工验收清单

- [ ] 启动一条 full run，确认 candidate 真实 push 后才出现 `eval_submitted`。
- [ ] 将 next poll 提前到当前时间，确认 running 时只推进 deadline。
- [ ] 让 gateway 返回 completed，确认 Run Detail 的 current/candidate 分数与 DB 一致。
- [ ] 确认只生成一个 apply job；重复扫描与进程重启不重复 accept/reject。
- [ ] 两轮 run 中第一轮 accept/reject 后自动进入第二轮，不出现跳轮。
- [ ] 全部轮次结束后自动写 final、发布 run 分支并转 completed。
- [ ] `HE_GIT_PUSH=false` 的 skipped 轮次不进入评测，仍能形成本地终态。
- [ ] gateway failed/timeout/异常时 run 进入 `blocked(eval)`，恢复后不自动重提。
- [ ] 刷新详情页后仍能从 REST/DB 看到完整轮次与最终结果。

## 6. 讨论点

### D1 Important — 到期查询先 `LIMIT` 再过滤 run 资格，坏行可饿死健康 run

- **位置**：`apps/api/app/db/crud/evolution.py:1029-1061`；`apps/api/app/service/evolution/eval_poller.py:239-269`
- **现象**：`list_eval_due()` 只过滤 round，不 join run 的 `mode/status`，然后按 `limit` 截断；`_poll_round()` 拿到 batch 后才判断 run 不活跃并返回 false。
- **问题**：若 100 条 inactive/failed/blocked run 的旧 `evaluating` 行排在前，后面的 running run 永远进不了 batch。最小复现用 `batch_size=1`、一条 blocked 旧行和一条 running 新行，连续 3 次 `run_once()` 都返回 0，健康行从未被访问。
- **预判**：把 run 资格（full + running，必要时 push 非 skipped）下推到 due query，并用“inactive 前置 + healthy 后置”回归；同步检查 `list_running_full_runs()` 的同类早截断风险。
- **结论**：✅ 2026-10-28 修复。`list_eval_due()` 在 `ORDER BY / LIMIT` 前 JOIN run 并按 `mode=full/status=running` 过滤；新增 blocked 旧行 + running 新行、`batch_size=1` 回归。`list_running_full_runs()` 已直接按 full/running 查询，无同类早截断。

### D2 Important — final 写入/工作区准备失败仍会把 run 变成不可恢复的 failed

- **位置**：`apps/api/app/service/evolution/apply_final.py:205-227`；`apps/api/app/service/jobs.py:274-292`；`apps/api/app/service/evolution/events.py:315-341`
- **现象**：只有 `publish_run_branch()` 的 `GitOperationError` 被转成 blocked；`write_final()` 与 `_prepared_workspace()` 的异常直接冒出。JobRunner 的通用异常路径随后调用 `record_failed()`，把 run 置 `failed`。
- **问题**：这与 PR 的“最终写失败仍可恢复，不得伪造 completed”不一致。实际复现中 `write_final()` 抛一次可重试异常，job 变为 failed，run 同时变为 `failed/final`，poller 不会再处理这条 running run。
- **预判**：给 final 阶段的非 Git 临时失败定义可恢复 disposition；至少新增“write_final 异常后 run 不被终态化，恢复后 finalize 可重试”的回归，并明确该状态应留在 running 还是走受控 blocked。
- **结论**：✅ 2026-10-28 修复。`write_final()` 与 workspace 重建异常统一转为 `RunBlocked(stage=push, error_stage=final)`，run 进入可恢复 blocked；测试覆盖失败后 resume、重试 finalize 并完成。

### D3 Important — 布尔分数仍可作为合法评测结果进入 1.0 投影

- **位置**：`apps/api/app/service/evolution/engine/contracts.py:191-194,262-282`
- **现象**：`EvalResult.from_payload()` 已拒绝 bool，但 `EvalResult.__post_init__()` 与 `FakeEvalGateway.get_result()` 仍把 bool 当数值。实测 `EvalResult(current_score=True, ...)` 保留 bool；Fake gateway 返回的 `current_score` 变成浮点 `1.0`。
- **问题**：外部 JSON 的 `true` 可以伪装成 0–1 区间的合法分数；之后 DB/UI 无法区分真实 `1.0` 与错误输入。
- **预判**：抽一个 strict numeric helper，在 `EvalResult` 构造、Fake gateway 和 persisted payload 三处共用；增加 bool/字符串/非有限值 table test。
- **结论**：✅ 2026-10-28 修复。构造器、Fake gateway、persisted payload 共用严格 score validator；bool、字符串、非有限值均有回归。

### D4 后续义务 — 提交评测的 crash window 归 m5-11，但必须显式纳入恢复测试

- **位置**：`apps/api/app/service/evolution/advance.py:149-165`；`apps/api/app/service/evolution/eval_poller.py:62-139`
- **现象**：轮次先在 DB 变为 `evaluating/pending`，之后才调用 gateway 并保存 external id。若进程死在这两步之间，当前 m5-10 的 due query 找不到 external id，advance 重试又会因“earlier round is evaluating”提前返回。
- **问题**：这不是本 PR 内必须补的完整崩溃恢复，但 m5-11 必须覆盖“evaluating + external id 为空”的继续提交，且依赖 gateway idempotency key 避免外部重复。
- **预判**：在 m5-11 recovery 设计中加入该状态和无内存重启测试；本 PR 只需保留 idempotency key 与失败边界。
- **结论**：m5-11 必须覆盖；本 PR 保留 idempotency key。

### D5 当前部署约束 — poller 没有跨进程 claim

- **位置**：`apps/api/app/service/evolution/eval_poller.py:173-309`；`apps/api/app/service/jobs.py:123-152`
- **现象**：单进程内 `start()` 幂等，JobRunner 有内存 `submit_lock`；DB due/follow-up 查询本身没有 claim，`job_runs` 也没有对应唯一约束。
- **问题**：当前“单 worker”架构下无实害；若未来横向扩容多个 API 进程，多个 poller 可能同时查状态，并在极窄窗口重复建 apply job。
- **预判**：保持单进程承诺即可；扩容前必须增加 DB lease/claim 或唯一任务键。此项不作为本 PR 阻断。
- **结论**：单进程部署无当前实害；扩容前增加 DB lease/claim。

## 9. 文件级代码分析

### 9.1 `engine/contracts.py`（M）

职责是把评测平台差异收在一个稳定协议后面。变更新增 `EvalRequest/EvalSubmission/EvalStatus/EvalResult`、Fake gateway 与默认 factory；`EngineDeps.gateway_factory` 让测试可注入别家实现。

关键依赖：Pydantic 只负责外层配置；这里使用 dataclass、MappingProxyType 和 tuple 做运行时冻结。比喻上，它像把用户写好的评测配置装进一次性封条袋：后续轮询只能读，不会因为进程中的其他请求改袋内内容。

旧行为只有惰性 `DefaultEvalGateway.config`；新行为具备完整三步协议与确定性结果。Fake id 是 run/round/commit 的函数，所以重启后仍是同一订单。

发现：D3。bool 在 Python 是 `int` 子类，当前 finite 检查不能挡住。

### 9.2 `eval_poller.py`（A）

职责是提交、轮询和补投任务。它不执行 git，也不拿 JobRunner worker lock。`now`、poll/scan/timeout 均可注入，使测试能确定时间。

关键依赖全在项目内部：SQLAlchemy repository、JobRunner、Event service。它是“值班传话员”，但把每次承诺都写进 DB 值班簿，而不是记在脑子里。

旧代码没有该文件。新逻辑分为 submit、due poll、follow-up scan、running-run scan、failure isolation 五段；completed 与失败各只落一次终态，事件写入 best effort，避免日志失败掩盖主事实。

发现：D1、D4。D1 是查询顺序导致的事实饥饿；D4 是明确留给 m5-11 的崩溃窗口。

### 9.3 `apply_final.py`（A）

职责是 consumption side：从持久 result 决策，再构造 placeholder final。它没有直接改 Git，而是调用 `EvolutionCandidateService` 与 `Workspace.publish_run_branch()`，保证 m5-09 的真实候选边界仍是唯一 Git 写入者。

关键依赖是 candidate service 和 frozen `EvalResult`。比喻上，评测结果只是“裁判纸条”，真正改仓库仍要找原来的施工队。

旧代码无 apply/finalize；新代码将 accept/reject 的吸收态复用、final metrics 汇总、最终 push 与 complete 顺序连起来。final push failure 被转换为 blocked 并保留 final。

发现：D2。非 Git 的 final 写入/工作区准备异常没有覆盖。

### 9.4 `db/crud/evolution.py`（M）

职责是评测状态的事实源。新增 `mark_eval_submitted`、waiting/due/followup 查询、result/failed transition、run progress 与 push skipped 事务。

关键设计是把“外部世界已返回”变成可重启解释的投影：external id、result、scores、next poll 同表。事务边界让 round 与 aggregate run 不会只更新一半。

旧代码到 candidate 终态为止；新代码继续推进 evaluation/deciding/accepted/rejected。失败/超时会同时写 round 与 run blocked。

发现：D1。due 查询缺少 run 资格下推。

### 9.5 `advance.py`（M）

职责是候选 publish 后提交评测，并在 job terminal 后决定 next round/finalize。

关键依赖是 candidate service、gateway submitter 与持久 rounds。它把“terminal hook 失败也不丢后续”交给 poller 再扫描，不再把一次内存回调当成唯一机会。

旧代码只 publish candidate；新代码在 `status=evaluating && external id 为空` 时 submit，并把 terminal lifecycle 扩展到 advance/apply。

发现：D4 的状态窗口需要 m5-11 负责 job crash 后继续 submit。

### 9.6 `main.py` / `config.py`（M）

职责是生产组合与运行参数。main 注册 apply/finalize handler、构造 poller、在 lifespan 启动/停止；config 增加 scan/poll/timeout 秒数。

关键依赖是 FastAPI lifespan。它像总闸：DB、job recovery、queued job 先恢复，再启动定时器；退出反向关闭定时器、scheduler、job、HTTP client 与 DB。

旧代码只注册 prepare/advance；新代码把自动闭环的 handler 全部接上。未新增 manual advance/push 路由。

发现：无新增阻断；组合根缺少真实 lifespan smoke 属于后续 Computer Use 验证。

### 9.7 `workspace.py`（M）

职责是提供 finalize 可调用的 `publish_run_branch()`，内部复用完整 `validate_for_push()` 与 fast-forward-only push。

关键约束是 candidate 可 force-with-lease，run branch 永不 force。final 发布因此只是对既有 run 分支做最后一次守卫。

旧代码只有各阶段单独调用校验；新入口把 final validation 与 push 组成一个明确 API。

发现：无。Git 边界本身已由 m5-09 审阅。

### 9.8 测试（A、M）

`test_gateway_poller.py` 用真实迁移 SQLite、fake clock 与 job capture 覆盖 due、completed、重启、malformed 隔离、timeout 与配置解析。`test_apply_final.py` 覆盖 submit、exactly-once apply、lifecycle、final、push 失败与决策文案。`test_app_wiring.py` 验证生产 handler 和“无人工 advance/push API”。

测试质量总体偏向真实 DB 状态，而非 mock call-count。缺口是 D1 的 batch 早截断、D2 的 final persist failure、D3 的 bool direct constructor；三者都需要新增真实行为断言。

Note 清楚记录为什么使用 DB 定时器、为什么 Fake gateway 不保存内存，以及哪些恢复能力留给 m5-11。中英 issue 只更新 scope、状态和 owning Note，没有复制第二套设计。architecture 文档把“占位评测闭环”移入已具备，并保留“真实评测”未具备。
