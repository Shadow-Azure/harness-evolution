## §1 一页速览

一句话：把「工作空间总览」做成空间默认落地页——一个只用 URL 记状态的只读页面，把 m8-03 的 summary / trend / sources / bad-cases 四个端点拼成统计条、堆叠趋势、来源分布和可分页列表，并让 bad case ID 新窗口下钻到错误详情的问题描述 Tab。

一个比喻：这页像体检中心的报告首页。统计条、趋势图、来源分布、列表是四台各自插电的仪器（四个独立 `useQuery`），任何一台断电（500）另外三台照常工作；墙上只有一块白板（URL）记录「这次查哪段时间、哪个来源、哪一页」，所有人改条件都写在白板上，仪器只认白板。图表不是买来的成品仪器，而是一把自制的刻度尺（`chartGeometry.ts` 的纯函数）：给定柱数、宽度、最大值，算出每根柱子的位置与高度，所以能单独拿尺子做实验，不用起浏览器。

## §2 架构导览

### 2.1 URL 是唯一状态源

页面不持有第二份筛选状态：`parseOverviewQuery(route.query)` 每次从 URL 算出 `OverviewUrlState`（`Index.vue:42-45`），所有交互都走 `replaceState()` 把 patch 合并后 `router.replace`（`Index.vue:115-118`）。规范化也在同一个 watcher 里：与 `overviewQuery(state)` 不一致时 replace（`Index.vue:208-212`），所以「刷新恢复」「分享链接」「手改 URL」走的是同一条解析路径。

`overviewUrl.ts` 的解析是「先校验、再决定优先级」：`range=custom` 必须 from/to 都存在、格式合法、`from <= to`（`:88-103`）；没有 `range` 但给了合法 from/to 时反推成 custom（`:101`）；`range=7/30/90` 优先于残留的 from/to（`:97-100`）；`page` 只接受 ≥1 的安全整数（`:72-76`）；`objects` trim、去空、按首次出现去重（`:78-86`）。这解释了为什么 `?range=365` 会静默回落 90 天、`?from=2026-02-31` 会被判非法。

### 2.2 四个查询与缓存键

四个 composable 各自 `useQuery`（`useOverview.ts:20-88`），key 的第一段是 `["ws", wid, "overview", <端点>, filters]`（`queryKeys.ts:55-64`）。wid 在最外层，因此不存在「A 空间的缓存被 B 空间复用」；`WorkspacePicker` 切空间时还会整树失效旧 wid（`WorkspacePicker.vue:63-70`）。

筛选键按端点裁剪：summary/sources 只吃窗口 + objects；trend 额外吃 grain；cases 额外吃 `badCaseType`/`page`/`pageSize`（`Index.vue:47-57`）。因此改粒度只重拉趋势，改类型/翻页只重拉列表——这是「图表与列表互不阻塞」之外的另一层节制。

没有 `AbortSignal`：`api/overview.ts` 的四个函数不接收 signal，`request` 虽然支持（`http.test.ts:266-274`）但未传入。TanStack 的默认行为是「同 key 去重、不同 key 各发各的」，旧请求不会被取消，也不会覆盖新 key 的缓存。这是全仓现状（其它 api 模块同样不传 signal），不是本 PR 新增的退步；后果只是筛选快速切换时多几个在途请求。

### 2.3 图表几何是纯函数

`chartGeometry.ts` 只依赖数字：`niceStep` 用 10 的幂 + 1/2/5 残差（`:59-64`），`niceTicks` 从 0 累加并保证最后一个刻度 ≥ max（`:73-91`），`barLayout` 算槽宽与柱宽（`:99-109`），`stackY` 把 self/discovery 堆到基线上并夹到坐标区高度（`:120-147`），`percent` 做占比（`:155-166`）。`StackedBucketChart` 用固定 `viewBox 0 0 720 220`、`preserveAspectRatio="none"` 拉伸到容器宽，轴标签与 tooltip 用 DOM 覆盖层（`StackedBucketChart.vue:16-18,89-118,165-257`）。

实测：`niceTicks(6,4) = [0,2,4,6]`（截图里就是 0/2/4/6）；`niceTicks(11,4) = [0,5,10,15]`；`barLayout(14,720) = {slot:51.43, barWidth:28, dense:false}`；`stackY(1,0,0,220,1e9)` 仍给 3px 最小可见高度。几何层没有除零：`axisMax` 取最后一个刻度且最小为 1（`StackedBucketChart.vue:56`），`percent(0,0)` 返回 `{0,0}`。

### 2.4 组件分工与三态

页面只做编排与 URL 写入；展示组件通过 props 拿数据、通过 emit 表达意图（`Index.vue:270-345`）。三态的顺序在每个区块里一致：`loading` → `error` → `empty`/内容（`StatStrip.vue:78-90`、`StackedBucketChart.vue:132-160`、`BadCaseTable.vue:129-174`、`SourceBars.vue:63-83`）。四个查询各自 `isPending` 驱动骨架，所以统计条 500 时趋势与列表仍在（E2E 实测：`statstrip` 消失、列表 8 行、图表仍在，`m8-04-overview.test.mjs:634-707`）。

### 2.5 默认落地与旧链接

`DEFAULT_WORKSPACE_PATH` 从 `sessions` 改为 `overview`（`router/workspace.ts:6-10`），根路由 `""` 重定向到 overview（`router/index.ts:44-53`），登录后的 `safeRedirect` 与空间选择共用 `defaultLandingPath`（`router/workspace.ts:89-99`；`Chooser.vue:44`）。旧链接做了显式分流：`/` → overview，`/sessions`、`/errors` → sessions（`router/workspace.ts:131-139`），`isLegacyWorkspacePath` 仍认 `/sessions/**`、`/evolution/**`（`:146-155`）。顶栏 brand 从 sessionsPath 改为 overviewPath（`TopNav.vue:318-321`），并新增「总览」项（`:334-346`）。

实测：`/workspaces/ws-default` 在浏览器里落到 `/workspaces/ws-default/overview?tab=cases&range=90&grain=week`（E2E 第一条，`m8-04-overview.test.mjs:372-434`）；`m1-shell` 仍停在 `/sessions` 并暴露 4 个顶栏链接（`m1-shell.test.mjs:347-354`）。

### 2.6 契约：再导出，不改 API

## §3 数据流走查

一条主线（viewer 从空间根进入、改筛选、点桶、下钻）：

```text
GET /workspaces/ws-default
  → 路由守卫：isLegacyWorkspacePath? 否 → auth.workspaceById(ws-default) 可见（router/index.ts:154-164）
  → 子路由 "" redirect → workspacePath(wid, "overview")（router/index.ts:44-48）
  → 懒加载 pages/overview/Index.vue（:49-53）
  → setup：parseOverviewQuery({}) → DEFAULT_OVERVIEW_STATE（overviewUrl.ts:110-152）
  → watcher(immediate, post)：URL 缺 tab/range/grain → replace 成
       ?tab=cases&range=90&grain=week（Index.vue:208-212；Index.test.ts:151-159）
  → 四个 useQuery 并行：
       /api/workspaces/ws-default/overview/summary?range=90
       /api/workspaces/ws-default/overview/trend?range=90&grain=week
       /api/workspaces/ws-default/overview/sources?range=90

  → summary → 6 格；trend → 14 个周桶 + 轴；sources → top6；cases → 8 行
```

实测请求形状（临时探针 + `Index.test.ts:199-222`）：summary/sources 不带 `grain`；trend 带 `grain=day`；cases 带 `page=2&pageSize=8&badCaseType=self`；`objects` 为空时**不出现** `objects=`（`api/overview.ts:49-57`；`overview.test.ts:86-107`），多选时是一条逗号串 `objects=deep-research,workflow`。

交互到 URL 的对照（E2E 实测数字，语料为独立空间写入的 11 条「今天/昨天」case，`m8-04-overview.test.mjs:189-301`）：

## §6 讨论点

### 6.1 桶点击用「请求粒度」而不是「服务端实际粒度」：降级成周后点周桶只筛一天（bug / P2）

- **位置**：`apps/web/src/pages/overview/Index.vue:313-321`（`<StackedBucketChart :grain="state.grain">`）与 `:303-305`（副标题 `grainLabels[state.grain]`）；`components/StackedBucketChart.vue:82`（`bucketWindow(bucket.bucket, props.grain)`）；`overviewUrl.ts:225-247`（`bucketWindow` 只信传入 grain）；`FilterBar.vue:62-66,177-182`（页面已经知道实际粒度并提示「已按周展示」）；Note `:14`（「日桶当天、周桶周一到周日、月桶整月」）。
- **现象**：服务端在日粒度窗口 >92 天时降级为周并回传 `grain: "week"`（08 §6.2/`:506`）。此时页面 `state.grain` 仍是 `"day"`，图表把服务端返回的周桶按日粒度换算窗口。临时探针：URL `range=custom&from=2026-08-01&to=2026-11-16&grain=day`，trend 返回 `grain=week`、桶 `2026-08-17`；图表副标题显示「按日聚合」，点击该桶后 URL 变成 `from=2026-08-17&to=2026-08-17`——列表只查周一当天，而柱子和 tooltip 表达的是整周（08-17..08-23）。同一时刻筛选条显示「已按周展示」，两个控件对「桶」的解释互相矛盾。
- **问题**：`grainEffective` 已经算好（`Index.vue:73-75`），却只传给 `FilterBar`，没有传给图表。结果是「图表画的是周、点击筛的是日」：例如某根柱子按周显示 3 条，点进去列表只剩周一当天的 1 条，且 URL 会被分享成错误的一日窗口。现有测试无法证伪：`StackedBucketChart.test.ts:20-24,44-65` 直接给组件传 `grain`，绕过了页面的接线；`Index.test.ts` 全部用例的 trend 都是 `grain: "week"` 且 URL `grain=week`（`:40-47`），没有「请求 day、响应 week」的组合。
- **预判**：`Index.vue:316` 改传 `:grain="grainEffective ?? state.grain"`，副标题也改用实际粒度；补一条页面级用例（URL `grain=day`、trend 返回 `week`、点周桶断言 `to=周一+6`），再补一条组件用例（props grain=week、桶是周一）。一行改动 + 两条用例，建议本 PR 修完再合并。
- **结论**：2026-11-16 已修：`Index.vue` 新增 `activeGrain = grainEffective ?? state.grain`，图表 `:grain` 与副标题都用它；`selectBucket` 在页面层用 `bucketWindow(bucket, activeGrain)` 重算闭区间，不再信任请求粒度。新增页面用例（日请求/周响应 → 点周桶断言 `from=周一`、`to=周一+6`）与 E2E（>92 天 + `grain=day`，点周桶筛整周、列表条数按周计算）。

### 6.2 切换空间时先用旧筛选向新空间发一轮请求（bug / P3）

- **位置**：`apps/web/src/pages/overview/Index.vue:195-215`（同一个 watcher 负责规范化与空间重置，`flush: "post"`）；`components/layout/WorkspacePicker.vue:44-79`（切空间保留 `route.query`）；`composables/useOverview.ts:24-88`（四个 query 的 key 直接吃 filters）；Note `:17`（「合并后重置优先并跳过本轮规范化」）。
- **现象**：临时探针在 A 空间打开 `?range=7&objects=deep-research&type=self`，切到 B 后记录到 B 的 8 个请求：前 4 个是 `summary/trend/sources/bad-cases?range=7&objects=deep-research`（cases 还带 `badCaseType=self`），后 4 个才是 `range=90` 的默认请求。也就是重置导航确实发生了，但它发生在首屏查询之后；B 空间会先按 A 的筛选渲染一次（若 B 恰好有同名来源，还会短暂显示「被筛过」的统计与列表），随后跳回默认。
- **问题**：Note 说「重置优先」，实际是「重置在导航层优先，但查询已经用旧 state 起跑」。键里带 wid 保证了不会拿到 A 的数据，所以不是跨空间泄漏；代价是每次切换多 4 个请求、一次可见的闪烁，以及一个用户无法解释的「数字先变小再变回」。单测 `Index.test.ts:345-367` 只断言最终 query 是默认值，没有断言切换期间请求过什么，因此这条路径没有测试承重。
- **预判**：三选一——（a）在 `WorkspacePicker` 切空间时去掉 overview 的筛选 query（只保留 section），从源头不产生旧筛选；（b）让查询用的 filters 在 `wid` 变化的那一帧直接取默认值（例如 `effectiveState = wid !== lastWorkspaceId ? DEFAULT : state`），URL 稍后对齐；（c）接受多一轮请求，但在单测里把「切空间只发默认请求」钉住。推荐（b）+ 用例，改动集中在一个 computed。
- **结论**：2026-11-16 已修：采用（a）的变体——空间选择器切到总览时用 `overviewQuery(DEFAULT_OVERVIEW_STATE)` 导航（不再携带旧 query），页面 watcher 只做规范化、不再按 `wid` 重置。新增 `WorkspacePicker` 用例（切到 B 的 URL 为默认值）、页面请求日志用例（B 的四个请求无旧 `range/objects/badCaseType`）与 E2E（A 带筛选切 B，记录网络请求并逐条断言）。

### 6.3 越界 `page` 显示「这个空间还没有 bad case」，分页条消失（bug / P3）

- **位置**：`apps/web/src/pages/overview/overviewUrl.ts:72-76`（`parsePage` 只校验 ≥1 的安全整数，无上界）；`Index.vue:52-57`（page 原样进请求）；`components/BadCaseTable.vue:55-70`（`pages`/`currentPage` 被夹取，但空态只看 `items.length` 与 `filtered`）、`:153-173`（空态）、`:241-263`（分页条只在 `items.length > 0` 时渲染）。
- **现象**：探针让服务端返回 `total=3, items=[]`（按 m8-03 的 count/page 实现，越界页 items 为空、total 仍为过滤后的权威值，`apps/api/app/db/crud/overview.py:318-396`），URL 为 `?page=99`：列表显示「这个空间还没有 bad case / 上报 bad case 后……」，分页条整块消失，`currentPage` 逻辑上已被夹到 1，但没有任何提示「第 99 页不存在」。`filtered` 只看 objects/type/range（`Index.vue:82-87`），不看 page，所以也不会落到「筛选没命中」的文案。
- **问题**：这是 URL 可构造的状态（手改、旧书签、数据变少后的前进/后退），页面却用「空间没有数据」来解释，且把用户唯一能回到有效页的分页条藏掉。`BadCaseTable` 的 `pages` 与 `currentPage` 已经算出来了，但页面没有用它来纠正 URL，形成「组件知道真相、URL 不知道」的分叉。
- **预判**：在 cases 查询成功后，若 `state.page > pages && items.length === 0`，用 `router.replace` 把 page 收到 `pages`（或 1）；同时把 `filtered` 加上 `page > 1`，让空态至少说「当前页没有数据」。补一条越界页用例。非阻塞，但这是列表最容易被分享坏的状态之一。
- **结论**：2026-11-16 已修：cases 成功后把越界 `page` 夹到 `ceil(total/pageSize)`（`router.replace`），夹取列表前 `BadCaseTable` 显示独立的「第 N 页没有数据」状态并保留分页条，不再误用「空间没有 bad case」。新增 `BadCaseTable` 用例、页面用例（`page=99` → `page=3` 且渲染有效页）与 E2E（11 条数据 `page=99` → `page=2`、3 行、分页条可见）。

### 6.4 跨空间后退会丢掉旧筛选并改写历史条目（bug / P3）

- **位置**：`Index.vue:195-215`（watcher 只比较 `wid !== lastWorkspaceId`，不区分「选择器切换」与「历史前进/后退」）；`WorkspacePicker.vue:63-79`（切空间是 `router.push`，历史里保留 A 的带筛选条目）。
- **现象**：探针在 A 打开 `?range=7&objects=deep-research`，切到 B（被重置为默认），再 `router.back()`：地址栏回到 A 的路径，但 query 已被改写成 `tab=cases&range=90&grain=week`。用户按「后退」期望回到刚才的 7 天 + 来源筛选，实际回到默认总览，且原来的历史条目被就地替换（再前进也找不回）。
- **问题**：08 §6.2 只说「切换空间重置到 `tab=cases`」，没有说「后退也重置」。现在的实现把任何 wid 变化都当成切换空间，导致后退/前进这种「恢复历史」的语义被覆盖。对只看单空间的用户无影响；对多空间用户，这是一次静默的状态丢失。测试也没有覆盖（`Index.test.ts:345-367` 只覆盖 push 切换）。
- **预判**：若产品接受「跨空间一律重置」，应在 08 §6.2 写明并接受历史被改写；若希望后退恢复，则给重置加条件（例如选择器切换时带一个一次性标记，或比较 `history.state.position`/导航方向），或者让 workspace 切换只重置 `objects/type`（空间相关），保留时间窗与粒度（用户真正的观察上下文）。建议先定语义再改代码。
- **结论**：2026-11-16 已修：规范化仍走 `replace`，但不再在 `wid` 变化时重置筛选；默认查询由选择器导航写入，历史里 A 的筛选条目保持原样，因此 Back 恢复 A 的 URL 与列表。新增页面用例（A 带筛选 → B → `router.back()` 后 query 与 cases 请求都回到 A 的筛选）与 E2E（A→B→back，行数恢复 4）。

### 6.5 1440 顶栏换行：与原型单行不一致，新增项加剧但非根因（visual/IA + fact / P3）

### 6.7 图表 dense 阈值 26 与设计 08 的 >60 不一致（fact / P3）

### 6.8 404 未整页跳空间选择，区块错误用的是固定伪错误码（fact / P3）

- **位置**：`StatStrip.vue:78-83`（`code="OVERVIEW_SUMMARY_UNAVAILABLE"`）、`StackedBucketChart.vue:138-144`（`OVERVIEW_TREND_UNAVAILABLE`）、`BadCaseTable.vue:145-152`（`OVERVIEW_CASES_UNAVAILABLE`）；`api/http.ts:12-25`（`ApiError` 带真实 `code`/`status`）；设计 08 `:522`（「区块级 `ErrorState`（错误码 + 重试）；`404 WORKSPACE_NOT_FOUND` 整页跳空间选择」）。
- **现象**：三处 `ErrorState` 的 `code` 都是页面自造的字符串，没有把 `ApiError.code` 传下去；所以用户看不到 `WORKSPACE_NOT_FOUND`/`INTERNAL`/`OBJECT_FILTER_TOO_LARGE` 这些真实错误码，只看到固定的「OVERVIEW_*_UNAVAILABLE」。全仓 `apps/web/src` 没有任何 `WORKSPACE_NOT_FOUND` 处理（grep 0 命中）：若会话里的空间已被删除/移出（auth store 还留着），守卫放行，四个请求同时 404，页面显示四块「加载失败 + 重试」，重试永远 404，也不会跳回空间选择。
- **问题**：08 §6.4 把 404 当成整页状态处理，实现只做了区块级；在正常刷新/切换路径上守卫兜住了 wid，所以平时不可见，但「权限被收回/空间被删」正是最需要引导的场景。真实错误码丢失还让「重试」按钮在 422（如 objects >50、窗口 >366 天）上同样无效——PR 的已知缺口也承认前端没做预校验，那至少应该把服务端 422 的码显示出来。
- **预判**：给四个区块传 `error.code`（把 `ErrorState` 的 code 从常量改为 `error.code ?? 常量`），并在 cases/summary 的错误处理里识别 404 → `router.replace('/workspaces?reason=forbidden')`（复用守卫的既有 query 约定，`router/index.ts:156-161`）。404 分支需要一条用例；错误码透传是纯展示改动。非阻塞。
- **结论**：2026-11-16 已修：四个区块（statstrip / chart / sources / cases）新增 `code` prop，`Index.vue` 用 `blockErrorCode(error, fallback)` 透传 `ApiError.code`；任一查询返回 404 或 `WORKSPACE_NOT_FOUND` 时整页 `router.replace('/workspaces?reason=forbidden')`，不再渲染四块永远失败的重试。新增页面用例（四端点 404 → 路由到 chooser；summary 422 显示 `OBJECT_FILTER_TOO_LARGE` 而非伪码）、组件真码用例与 E2E（500 区块显示 `INTERNAL`、不出现 `OVERVIEW_SUMMARY_UNAVAILABLE`）。

### 6.10 从「近 7/30 天」点自定义会跳到最近 90 天，而不是当前窗口（bug / P3）

- **结论**：2026-11-16 已修：`setRange("custom")` 去掉「仅默认 range 才用 summary.window」的条件，存在 `summary.window` 就直接预填当前窗口，仅在窗口缺失时回落 `defaultCustomWindow()`。新增页面用例（`range=7` 点自定义，断言 `from/to` 等于 summary 的 7 天窗口而不是 today-89..today）。

```ts
export function overviewQuery(state) {
  const query = { tab: "cases", range: state.range === "custom" ? "custom" : String(state.range), grain: state.grain };
  if (state.range === "custom" && state.from && state.to) { query.from = state.from; query.to = state.to; }
  if (state.objects.length > 0) query.objects = state.objects.join(",");
  if (state.type !== "all") query.type = state.type;
  if (state.page > 1) query.page = String(state.page);

```

这在做什么：第一段把优先级写成显式分支（显式 custom 优先于数字 range；数字 range 优先于残留 from/to；都不合法落默认）；第二段只写「非默认值」，所以默认 URL 就是三个键，分享链接不会带一堆空参数。`sanitized` 用 `sameOverviewQuery` 比较键集合与值，避免仅因键序不同就重导航（`:196-209`）。

### 9.3 `apps/web/src/pages/overview/chartGeometry.ts`（A，166 行）

职责：图表纯几何——刻度、柱布局、堆叠高度、占比。新增文件。

关键依赖：只有 `Math` 与 `Number`。它像**刻度尺与积木**：不关心数据从哪来，只把「柱数 / 宽度 / 最大值 / 两段值」变成像素与百分比，因此能在 Node 里单独扫描（§1）。

关键代码块：

```ts
function niceStep(rawStep, minStep) {
  const magnitude = 10 ** Math.floor(Math.log10(rawStep));
  const residual = rawStep / magnitude;
  const scaled = residual <= 1 ? 1 : residual <= 2 ? 2 : residual <= 5 ? 5 : 10;
  return Math.max(minStep, scaled * magnitude);
}
```

```ts
export function stackY(self, discovery, top, height, max) {
  const safeSelf = Number.isFinite(self) && self > 0 ? self : 0;
  const safeDiscovery = Number.isFinite(discovery) && discovery > 0 ? discovery : 0;
  const total = safeSelf + safeDiscovery;
  if (total <= 0 || !Number.isFinite(height) || height <= 0 || !Number.isFinite(max) || max <= 0) { /* 全 0 几何 */ }
  const scaled = Math.min(height, (total / max) * height);
  const totalHeight = Math.max(MIN_BAR_HEIGHT, scaled);
  const selfHeight = (totalHeight * safeSelf) / total;
  return { y: top + height - totalHeight, totalHeight, selfHeight, discoveryHeight: totalHeight - selfHeight };
}
```

这在做什么：第一段把任意步长归一到 1/2/5×10ⁿ，`minStep` 保证计数轴不出现小数；第二段先清洗非有限/负数，再对「总值为 0」「高度/轴上限非法」短路，最后用 `Math.min(height, …)` 夹住超过轴上限的柱（轴刻度覆盖 max 时不会发生，但保留防御）。

扫描结论：`niceTicks` 对 0/NaN/Infinity 返回 `[0,1]`；对 0..200 的每个 max 与 count 1/2/3/4/5/10，首项为 0、严格递增、全整数、末项 ≥ max、数量受 guard 限制；1e6..1e300 也成立。`barLayout` 对 -2..120 桶：非正数返回空布局，正数 `barWidth ≤ min(28, slot)`。`stackY`/`percent` 对 NaN/Infinity/负数/1e9 都输出有限数；唯一 `NaN` 是 `top=NaN`（页面恒传 0，不可达）。

检视发现：dense 阈值 26 与 08 的 60 分叉（§6.7）；`decimalsFor` 对 `String(step)` 含指数形式（如 1e-7）有专门分支，实测 0.9/3 的组合输出 `[0,0.5,1]`，无浮点噪声；`MIN_BAR_HEIGHT=3` 让「1 条」在 1e9 轴上仍可见，这是有意的可视化选择（也意味着 0 与 1 的高度差不代表真实比例，属设计取舍）。无功能缺陷。
