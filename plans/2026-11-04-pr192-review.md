## §1 一页速览

一句话：这个 PR 给接口错误加了一层“翻译台”，把机器信封翻译成“哪里错了 + 怎么改”。

比喻：后端原来递来一张写着编号和英文代码的故障单；前端现在先看编号和字段位置，再按场景说出“密码格式不对，请修改后再试”，而不是把故障单原样贴到屏幕上。

| 交付块 | 用户效果 | 证据 |
|---|---|---|
| 共享格式化器 | 422 显示字段级原因；网络/权限/服务错误给出下一步。 | `apps/web/src/app/apiError.ts:128` |
| 登录与改密 | 后端校验落到字段文案，内部英文短语不外显。 | `apps/web/src/pages/login/LoginForm.vue:28` |
| 同步与向导 | 立即同步、条件查询和启动失败显示可执行建议。 | `apps/web/src/components/layout/TopNav.vue:254` |
| Run 重试 | 保留状态类业务文案，同时兜底字段级校验。 | `apps/web/src/pages/evolution/RunDetail.vue:329` |
| API 测试 | 确认 422 details 的安全字段集。 | `apps/api/tests/test_app.py:520` |

## §2 架构导览

### 翻译台

`ApiError` 是前端共享传输层抛出的统一错误对象；`formatApiError` 在 `apps/web/src/app/apiError.ts:128` 接收它。422 时先调用 `formatValidationDetails`（`apiError.ts:73`），读取后端 `_safe_validation_errors` 保留的 `loc/msg/type`（`apps/api/app/errors.py:198`）。字段路径的最后一段（`apiError.ts:54`）映射成中文标签，校验类型映射成原因和建议（`apiError.ts:27`）。

非 422 失败走 `stableMessage`（`apiError.ts:98`）：网络、权限、服务、任务冲突、零命中分别给出动作；未知错误只允许中文消息原样透传，否则回到调用方场景兜底（`apiError.ts:147`）。这样“内部服务短语”不再成为 UI 文案。

### 场景优先

登录/改密先保留 `AUTH_INVALID`、限流等稳定业务文案，再用字段错误或共享消息兜底（`LoginForm.vue:15`、`ChangePasswordCard.vue:12`）。Run 重试先保留 `RUN_NOT_RETRYABLE` 和 `RUN_NOT_FOUND`，否则交给共享层（`RunDetail.vue:323`）。这个顺序避免把领域语义稀释成通用提示。

### API 边界

后端行为不在本 PR 中改变；测试只固化已有信封契约：`details.errors` 白名单为 `loc/msg/type`（`test_app.py:527`），缺失参数与非法数字分别产生 `missing` 和 `int_parsing`（`test_app.py:525`、`test_app.py:531`），错误输入值不出现在 `msg`（`test_app.py:533`）。

## §3 数据流走查

1. 用户在登录表单提交用户名和密码，请求返回 422。传输层把响应信封转成 `ApiError`。
2. `LoginForm` 的 computed 调 `formatApiError(error, "登录失败")`（`LoginForm.vue:28`）。
3. `formatValidationDetails` 读取 `loc=["body","password"]`、`type="string_pattern_mismatch"`，生成“密码格式不正确，请按字段要求修改后再试。”（`apiError.ts:84`）。
4. 登录页优先返回 `fieldErrors.password`，提示直接渲染在原错误位（`LoginForm.vue:28`）；测试断言不包含 `String should match pattern`。
5. 若响应没有 details，共享层返回“登录失败，请检查输入后重试。”（`apiError.ts:113`），仍保留场景。

## §6 讨论点

### 6.1 未知 body 字段被统一称为“查询参数”

- 位置：`apps/web/src/app/apiError.ts:60`
- 现象：`fieldLabel` 的兜底硬编码为“查询参数”；`loc=["body","unknownField"]` 也会显示“查询参数”。
- 问题：字段位置语义不准确，用户可能去检查 URL/query，而错误实际在提交体。
- 预判：应根据 `loc` 的位置段区分 body/query/path，未登记字段用“请求体字段 / 查询参数”，避免误导。
- 结论：按授权修复。

### 6.2 目标保存仍保留裸错误回退

- 位置：`apps/web/src/pages/evolution/targets/Index.vue:126`
- 现象：`REPO_INVALID/TARGET_EXISTS/PROJECT_ID_INVALID` 有专项文案，但其他 API 错误返回 `errorValue.message`；普通 `Error` 也返回 `message`。
- 问题：例如 `request validation failed` 或内部英文异常仍可能进入保存表单。
- 预判：专项码优先；其余调用 `formatApiError(errorValue, "保存配置失败")`，字段错误可先进入表单汇总。
- 结论：按授权修复。

### 6.3 issue 的全局兜底表述宽于实现

- 位置：`.agents/flow/issues/m6-actionable-validation-errors.md` 实现内容第二条
- 现象：issue 说“全局 query fallback 不再只处理 409”，实现实际选择页面级接入，避免 Vue Query cache 错误与页面 catch 重复通知。
- 问题：契约表述与实现策略不一致，后续维护者可能误以为 `main.ts` 已改。
- 预判：把契约改成“已有定制文案的业务页优先，页面内联 catch 使用共享解释层；不引入无去重机制的全局二次弹层”，同步英文侧。
- 结论：按授权修复。

## §9 文件级代码分析

### `apps/web/src/app/apiError.ts`

职责：共享错误解释层。变更为新增 155 行能力，同时保留 `presentConflict`。

旧逻辑只有 409 冲突展示；页面各自决定是否显示 `error.message`。新逻辑先判断 `ApiError`，再区分字段级 422 与稳定错误码。关键块是 `formatValidationDetails` 把数组归约为 keyed field errors；`formatApiError` 把多条字段错误合并成一条总提示，同时保留字段锚点数据。

实现思路：机器详情只用于解释，不直接展示；场景兜底由调用方传入。未知消息默认隐藏，避免把英文诊断当 UI。

发现：见 §6.1。

### 页面接入文件

职责：把解释层插入已有交互状态。所有页面改动都保持既有 loading、inline alert 和错误码优先级，只替换最后兜底。

旧代码示例：`previewError.value = error instanceof Error ? error.message : String(error)`；新代码是 `previewError.value = formatApiError(error, "查询命中结果失败").message`。登录/改密额外读取字段错误，确保 422 能指向字段。

实现思路：领域分支优先，通用解释兜底。测试以 MSW 返回真实 422 信封，锁住文案质量。

发现：目标配置页没有接入，见 §6.2。

### `apps/api/tests/test_app.py`

职责：固化安全校验信封。新增断言不改生产代码，验证 details 白名单和输入值不回显。

旧测试只检查 `loc`。新测试分别请求缺失参数和非法数字，检查 `missing`、`int_parsing`，并断言错误值不在 `msg`。

实现思路：前端解释只消费 `type/loc`，后端契约测试保证可依赖的最小字段集。

发现：无。
