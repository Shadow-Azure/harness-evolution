## §1 一页速览

一句话：把“模型直接改文件”换成“模型交一张施工单，代码当施工队照单施工”，让第三路 patch 生成（`agent-edit`）真的能产出候选，同时把施工单、施工结果和真正的 git diff 一起留档。

一个比喻：模型是只看图纸的工长，不能自己动墙；它把“这里换一根梁”写在施工单（`edits.json5`）上。`AgentEditPatchSource` 是施工队，先在一块**临时样板间**（scratch mirror）里照单施工——样板间塌了也不影响真房子；确认成品后，才把新墙纸尺寸（整文件内容）交给 git 去真仓库贴。

## §2 架构导览

### 2.1 两张“接缝”分别负责什么

- **AI 能力面**：`AIAgentProvider.edit_workspace`（`contracts.py:105`）只负责“看 + 交施工单”。它拿 `EditRequest`（工作区、提示、允许范围、可选的 `session_id` / `feedback`），回 `EditResult`（`contracts.py:138`），其中新增的 `plan` 是唯一可审计的意图。
- **patch 生成面**：`PatchSource.build_bundle`（`patch_source.py:154`）负责“把意图变成可提交的字节”。`agent-edit` 实现（`patch_source.py:390`）在这层完成确定性施工与整文件打包。

这种切法的好处是后端换模型只动 provider，换 patch 策略只动 source；代价是 `edit_workspace` 的语义从设计文档写的“应用”变成了“只出计划”，见 §6.2。

### 2.2 临时样板间怎么来的

`_apply_on_scratch`（`patch_source.py:514`）先建临时目录，`_mirror_plan_files`（`patch_source.py:532`）只把施工单点名的文件按相对路径复制过去，然后 `apply_edit_plan` 在临时目录里跑。因此：

- 越界路径在 applier 的 `allowed_paths` 处被拒（`allowed=<sub_dir>/**`），真仓库没被写过；
- 锚点缺失/多义只会在临时目录留下半成品，下一次重试重新镜像，不会叠加；
- 真仓库唯一的写入点是 `create_candidate_bundle` 的 commit，天然就是安全闸，不需要 `git checkout -- .`。

### 2.3 多文件候选如何保持旧哈希兼容

`PatchBundle.sha256`（`patch_source.py:77` 起）保持既有规则：单文件直接复用 `Patch.sha256`，多文件按排序后的 `(path, content)` 逐段喂 SHA-256。publish 用 `bundle.sha256` 写 `Harness-Patch-Hash`，旧的 placeholder / minimal-config 单文件 trailer 逐字节不变，因此历史 run 的幂等重放不受影响。

### 2.4 审计信息落哪

`_audit_payload`（`git_candidate.py:1206`）把 `files`、`patchHash`，以及（仅 agent 计划）`intent`、逐条 `report`、`sessionId`、有界 `unifiedDiff` 放进 `candidate_committed` 事件。`unifiedDiff` 来自 `CandidateWorkspace.unified_diff`，即候选 commit 与父提交的真实 `git diff`——这是“声明 vs 实际”的对照物。

## §3 数据流走查（一条主线）

1. **prepare 之后**：run 有 `workspace_path`、run 分支与基线；`patchMode=agent-edit` 冻结在 `eval_config`。
2. **advance → publish**（`git_candidate.py:209`）：round 进入 `patching`，若没有已存 bundle，就取 patch 源。
3. **工厂选择**（`patch_source.py:656`）：run 快照的 `patchMode` 优先，否则 `HE_PATCH_SOURCE_MODE`；`agent-edit` 需要注入 provider，否则 `ConfigError`。
4. **同簇反馈**（`git_candidate.py:723`）：查同簇更早的 `rejected` round；有则把分差、失败原因、上一份 plan 的摘要与逐条状态、`sessionId` 组成 `PatchFeedback`。
5. **施工单**（`patch_source.py:436`）：provider 以只读工具探索，写 `.harness-evolution/edits.json5`；provider 解析并校验成 `EditPlan` 后回传。
6. **样板间施工**：镜像目标文件 → `apply_edit_plan`；若一条都没成功，带具体错误 `--resume` 追问一次（`patch_source.py:204` 的测试锁住该行为）。
7. **打包**：把实际变化的文件读成整文件 `Patch(overwrite=True)`，连同 `intent`、`report`、`sessionId` 组成 `PatchBundle`。
8. **持久化**：`_stored_patch`（`git_candidate.py:1156`）写入 round 的 `patch` JSON；单文件同时保留旧 `file/lines/overwrite` 键，多文件写 `files`。
9. **提交**：`create_candidate_bundle` 在 run 分支上建候选分支、写文件、`git add`、commit，并回填真实 diff。
10. **事件**：`candidate_committed` 落审计 payload；随后走既有 push → eval。
11. **下一轮（若存在）**：同簇的下一轮 publish 读到上一轮的 `sessionId` 与 buffer，`--resume` 同一会话继续，而不是从零开始。

## §6 讨论点

### 6.1 评测 reject 后没有“自动下一轮”

- **位置**：`apps/api/app/service/evolution/git_candidate.py:723`（反馈构造已就绪）；`apps/api/app/service/evolution/prepare.py` 的 `_build_rounds`（每簇恰好一轮，未在本 PR 改动）。
- **现象**：源级能力与 e2e 都证明“只要存在同簇下一轮，就能 resume + 带缓冲”；但生产流程在 eval reject 后直接把该 round 标为 `rejected`，没有创建下一轮的调度器，`eval_poller` 随后看到所有 round 终止就进入 finalize。
- **问题**：issue 的验收项“reject 后下一轮携带反馈与拒绝缓冲；轮次上限生效”在生产路径上不可达。
- **预判**：实现它需要新增 round 的插入/跳过与进度游标语义（`db/crud`、`total_units`、UI 的 round 列表与进度），属于跨模块的 round 生命周期改造。按本 issue 的 scope（不含 `db/**`、前端）不宜在本 PR 硬塞；建议单开 follow-up issue，本 PR 保留 source 能力与测试。
- **结论**：

### 6.2 `edit_workspace` 只出计划，应用放在 patch source

- **位置**：`apps/api/app/third_party_api/ai_agent/claude_code.py:358`；`apps/api/app/service/evolution/patch_source.py:436`。
- **现象**：设计 §5.5.1 写的是 `edit_workspace(...) -> EditResult` “产出编辑计划并确定性应用”；实现里 provider 只回 plan，`AgentEditPatchSource` 才应用。
- **问题**：契约注释与设计文档不一致，未来换 provider 时“谁负责写盘”会有歧义。
- **预判**：当前切法更安全（真仓库零写入、重试天然幂等），但需要在设计文档或 owning Note 里把“应用归 patch source、provider 只产意图”写成现状；若坚持设计原文，则要把 scratch mirror 与回滚策略下沉进 provider，收益不大。
- **结论**：

### 6.3 整文件覆盖补丁可能丢文件模式位

- **位置**：`patch_source.py:551` 的 `_patch_from_content` 与 `third_party_api/git/workspace.py` 的 `_write_patch`。
- **现象**：Patch 只携带路径与行，`overwrite` 写入时按默认权限创建/覆盖；若 agent 修改了可执行脚本，候选提交可能丢 `+x`。
- **问题**：当前目标对象是技能/配置文档，风险低；但 `allowed_paths` 并不排除脚本。
- **预判**：可接受为已知弱点，在 Note/PR 明示；彻底修复需要 `Patch` 增加 mode 或改为直接收 git diff（改动面大）。
- **结论**：

### 6.4 部分成功时选择“更干净”还是“改得更多”

- **位置**：`patch_source.py:490` 的 `_application_rank`。
- **现象**：一次计划部分失败、重试后干净但文件更少时，排序优先“全部应用”，其次文件数。
- **问题**：这是产品取舍——宁要小而干净，还是大而带错？当前取“干净优先”，并把逐条 report 落审计。
- **预判**：合理默认；若后续真实 case 表明需要“尽量多改”，再调 rank 即可。
- **结论**：

### 6.5 事件里的是有界 diff 与完整 intent

- **位置**：`git_candidate.py:1206`。
- **现象**：`intent` 全量落事件，`unifiedDiff` 截断到 20k 字符。
- **问题**：与 issue“diff + intent + report 全量落 run events”的字面要求存在一处取舍——diff 超长时只留头部并标注截断。
- **预判**：事件行是 DB 文本，不设上限会放大存储与 SSE 负载；保留完整 intent + 截断 diff 是可审计与可用性的平衡。若验收坚持全量 diff，应改为对象存储引用而不是行内 payload。
- **结论**：

## §9 文件级代码分析

### `apps/api/app/service/evolution/patch_source.py`（M，核心）

- **职责**：新增第三种 patch source，把 agent 的 `EditPlan` 变成多文件 `PatchBundle`；同时扩展 `PatchSource` 协议与工厂。
- **关键依赖**：`apply_edit_plan` 是仓库内确定性应用器（纯文本、原子写）；`tempfile`/`shutil` 只用于样板间，不引入新第三方依赖。
- **变更代码块**：
  - 旧：`build()` → 单文件 `Patch`；`agent-edit` 直接 `ConfigError` 保留。
  - 新：`build_bundle(feedback=...)`（`patch_source.py:436`）负责 prompt、重试、镜像、打包；`default_patch_source_factory(provider=...)`（`patch_source.py:656`）注入 provider。
  - 为什么：保持旧 source 零改动（`_DefaultBundleSource` 包装），新能力只加子类；反馈参数即使旧 source 不用也兼容。
- **检视发现**：见 §6.2、§6.3、§6.4。

### `apps/api/app/service/evolution/git_candidate.py`（M，核心）

- **职责**：publish 从“单 Patch”升级为“bundle”，持久化审计信息，并把 provider 失败分成终态失败与可重试 blocked。
- **关键依赖**：`EvalResult.from_payload` 读既有评测快照；`asdict` 只序列化既有 dataclass；无新依赖。
- **变更代码块**：
  - 旧：`if saved file/lines → Patch`；`create_candidate(patch=...)`；payload 只有 `files`/`patchHash`。
  - 新：`_stored_bundle`（`git_candidate.py:1069`）兼容旧单文件与新 `files` 数组；`create_candidate_bundle` 统一提交；`_audit_payload`（`git_candidate.py:1206`）补 intent/report/session/diff；`_handle_provider_failure`（`git_candidate.py:770`）对 retryable 失败落 `blocked(stage=patch)`。
  - 为什么：不新增 DB 列即可承载多文件与会话；“声明 vs diff”成为可审计信号。
- **检视发现**：`_patch_feedback` 每次 publish 多一次 `list_rounds` 查询；round 数量级很小，可接受。终态失败复用 `_fail_patch_generation`，错误语义与旧 ConfigError 路径一致。

### `apps/api/app/third_party_api/ai_agent/contracts.py`（M）

- **变更代码块**：`EditRequest` 增 `session_id` / `feedback` 并校验非空；`EditResult` 增 `plan` / `report` 并校验 `summary == plan.summary`。
- **检视发现**：`contracts` 反向依赖 `edits` 模块（同包、无环），类型上合理；若未来抽独立包需拆分，但当前不值得。

### `apps/api/app/third_party_api/ai_agent/claude_code.py`（M）

- **职责**：把 `EditRequest` 的新字段翻译成 CLI 参数。
- **变更代码块**：`--resume <session>`（`claude_code.py:547` 起）与 `--max-turns 40`（`claude_code.py:81`）；`edit_workspace` 回传 `plan`。
- **检视发现**：真实 CLI 的 `--resume` 只对持久化会话有效；edit 路径没有 `--no-session-persistence`，所以语义成立，但本 PR 未加真实 CLI e2e（需要部署凭据），属于既有测试边界。
