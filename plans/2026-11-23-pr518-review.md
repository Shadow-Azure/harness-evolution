## §1 一页速览

一句话：把“模型直接改文件”换成“模型交一张施工单，代码当施工队照单施工”，让第三路 patch 生成（`agent-edit`）产出可审计的多文件候选。

一个比喻：模型是只看图纸的工长，不能自己动墙；它把“这里换一根梁”写在施工单（`edits.json5`）上。`AgentEditPatchSource` 是施工队，先在**临时样板间**（scratch mirror）里照单施工——样板间塌了也不影响真房子；确认成品后，才把新墙纸尺寸（整文件内容）交给 git 去真仓库贴。

## §2 架构导览

### 2.1 两张接缝

- **AI 能力面**：`AIAgentProvider.edit_workspace` 只负责“看 + 交施工单”。它拿 `EditRequest`（工作区、提示、允许范围），回 `EditResult`（新增 `plan` 字段承载可审计意图）。
- **patch 生成面**：`PatchSource.build_bundle` 负责“把意图变成可提交的字节”。`agent-edit` 实现在这层完成确定性施工与整文件打包。

这种切法让换模型只动 provider、换 patch 策略只动 source。代价是 `edit_workspace` 的语义从设计文档写的“应用”变成了“只出计划”，已在 §5.5.1/§5.5.4 同步。

### 2.2 临时样板间

`_apply_on_scratch` 建临时目录，`_mirror_plan_files` 只把施工单点名的文件按相对路径复制过去，然后 `apply_edit_plan` 在临时目录里跑。因此：

- 越界路径在 applier 的 `allowed_paths` 处被拒（`<sub_dir>/**`），真仓库没被写过；
- 锚点缺失/多义只会在临时目录留下半成品，不影响仓库；
- 真仓库唯一的写入点是 `create_candidate_bundle` 的 commit，天然就是安全闸，不需要 `git checkout -- .`。

### 2.3 多文件候选与旧哈希兼容

`PatchBundle.sha256` 保持既有规则：单文件直接复用 `Patch.sha256`，多文件按排序后的 `(path, content)` 逐段喂 SHA-256。publish 用 `bundle.sha256` 写 `Harness-Patch-Hash`，旧的 placeholder / minimal-config 单文件 trailer 逐字节不变。

### 2.4 审计信息落哪

`_audit_payload` 把 `files`、`patchHash`，以及（仅 agent 计划）`intent`、逐条 `report`、有界 `unifiedDiff` 放进 `candidate_committed` 事件。`unifiedDiff` 来自 `CandidateWorkspace.unified_diff`，即候选 commit 与父提交的真实 `git diff`——这是“声明 vs 实际”的对照物。

## §3 数据流走查

1. **prepare 之后**：run 有 `workspace_path`、run 分支与基线；`patchMode=agent-edit` 冻结在 `eval_config`。
2. **advance → publish**：round 进入 `patching`，若没有已存 bundle，就取 patch 源。
3. **工厂选择**：run 快照的 `patchMode` 优先，否则 `HE_PATCH_SOURCE_MODE`；`agent-edit` 需要注入 provider，否则 `ConfigError`。
4. **施工单**：provider 以只读工具探索，写 `.harness-evolution/edits.json5`；provider 解析并校验成 `EditPlan` 后回传。
5. **样板间施工**：镜像目标文件 → `apply_edit_plan`；一条都没成功就本轮失败，不做第二次模型调用。
6. **打包**：把实际变化的文件读成整文件 `Patch(overwrite=True)`，连同 `intent`、`report` 组成 `PatchBundle`。
7. **持久化**：round 的 `patch` JSON 写 `files` / `intent` / `report`，单文件同时保留旧 `file/lines/overwrite` 键。
8. **提交**：`create_candidate_bundle` 建候选分支、写文件、`git add`、commit，并回填真实 diff。
9. **事件与后续**：`candidate_committed` 落审计 payload；随后走既有 push → eval；评测 reject 沿用既有拒绝逻辑结束该轮。

## §6 讨论点

### 6.1 自动 round 重试：已决定不做

- **位置**：原 `git_candidate._patch_feedback` / `AgentEditPatchSource` 的重试循环。
- **现象**：初版曾实现“同簇下一轮 resume + 拒绝缓冲”，但 run 状态机每簇只建一轮，要让它可达必须改 round 生命周期、进度游标与前端展示。
- **问题**：维护者 2026-11-23 明确：先不做重试，失败即拒绝，不要过度设计。
- **预判**：本轮已删除 `PatchFeedback`、`--resume`、拒绝缓冲与二次编辑调用；issue #488、设计文档、Agent Note 同步改写成“单轮 + 失败即拒绝”。
- **结论**：✅ 已决（2026-11-23，维护者）。

### 6.2 `edit_workspace` 只出计划，应用放在 patch source

- **位置**：`claude_code.py` 的 `edit_workspace`；`patch_source.py` 的 `AgentEditPatchSource`。
- **现象**：设计 §5.5.1 原文是 provider “产出编辑计划并确定性应用”，实现改为 patch source 在临时镜像上应用。
- **问题**：契约注释与设计文档需一致。
- **预判**：当前切法更安全（真仓库零写入、无需回滚）。
- **处置**：设计 §5.5.1/§5.5.4 已同步；base 契约注释同步。
- **结论**：✅ 已决（2026-11-23）。

### 6.3 整文件覆盖补丁可能丢文件模式位

- **位置**：`_patch_from_content` 与 `third_party_api/git/workspace.py` 的 `_write_patch`。
- **现象**：Patch 只携带路径与行，`overwrite` 写入时按默认权限创建/覆盖；若 agent 修改可执行脚本，候选提交可能丢 `+x`。
- **问题**：当前目标对象是技能/配置文档，风险低；`allowed_paths` 并不排除脚本。
- **预判**：接受为已知弱点，在 PR 描述明示；彻底修复需要 `Patch` 增加 mode 或改为直接收 git diff（改动面大）。
- **结论**：

### 6.4 事件里的 diff 有界

- **位置**：`_audit_payload`。
- **现象**：`intent` 全量落事件，`unifiedDiff` 截断到 20k 字符。
- **问题**：与“diff + intent + report 全量落 run events”的字面要求存在取舍。
- **预判**：事件行是 DB 文本，不设上限会放大存储与 SSE 负载；完整 intent + 截断 diff 是可审计与可用性的平衡。设计文档已写明截断。

## §9 文件级代码分析

### `apps/api/app/service/evolution/patch_source.py`（M，核心）

- **职责**：新增第三种 patch source，把 agent 的 `EditPlan` 变成多文件 `PatchBundle`；扩展 `PatchSource` 协议与工厂。
- **关键依赖**：`apply_edit_plan` 是仓库内确定性应用器（纯文本、原子写）；`tempfile`/`shutil` 只用于样板间，不引入新第三方依赖。
- **变更代码块**：
  - 旧：`build()` → 单文件 `Patch`；`agent-edit` 直接 `ConfigError` 保留。
  - 新：`build_bundle()` 负责 prompt、镜像、应用、打包；工厂接受 provider。
  - 为什么：保持旧 source 零改动（`_DefaultBundleSource` 包装），新能力只加子类。
- **检视发现**：见 §6.2、§6.3、§6.4。

### `apps/api/app/service/evolution/git_candidate.py`（M，核心）

- **职责**：publish 从“单 Patch”升级为“bundle”，持久化审计信息，并把 provider 失败分成终态失败与可重试 blocked。
- **关键依赖**：`asdict` 只序列化既有 dataclass；无新依赖。
- **变更代码块**：
  - 旧：`if saved file/lines → Patch`；`create_candidate(patch=...)`；payload 只有 `files`/`patchHash`。
  - 新：`_stored_bundle` 兼容旧单文件与新 `files` 数组；`create_candidate_bundle` 统一提交；`_audit_payload` 补 intent/report/diff；`_handle_provider_failure` 对 retryable 失败落 `blocked(stage=patch)`。
  - 为什么：不新增 DB 列即可承载多文件；“声明 vs diff”成为可审计信号。
- **检视发现**：provider 可重试失败会 blocked，可由人工重试；这不是 round 级自动重试，符合“失败即拒绝”。

### `apps/api/app/third_party_api/ai_agent/contracts.py`（M）

- **职责**：`EditResult` 增加 `plan`，把可审计意图从 provider 传给 patch source。
- **变更代码块**：`plan` 可选字段 + `summary == plan.summary` 校验；`EditRequest` 保持原样。
- **检视发现**：`contracts` 反向依赖 `edits` 模块（同包、无环），类型上合理。

### `apps/api/app/third_party_api/ai_agent/claude_code.py`（M）

- **职责**：编辑调用回传 `plan`，新增 `--max-turns 40` 花费闸。
- **检视发现**：不再传 `--resume`；真实 CLI 编辑的单次调用边界由 turn cap + 超时共同约束。
