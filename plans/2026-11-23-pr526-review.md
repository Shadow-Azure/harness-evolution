## §2 架构导览

### 2.1 策略落在配置边界，而不是散在业务分支

`Settings.ai_agent_failure_policy` 是 `Literal["strict","degrade"] | None`，`derive_ai_agent_failure_policy` 在 provider 校验后推导；`main.py` 只把 `effective_ai_agent_failure_policy` 交给 prepare。业务侧的 `cluster_llm` 不读环境变量，只接收一个 `Literal` 参数——策略可测试、可回放。

### 2.2 strict 的失败路径

`enhance_clusters` 把 policy 传给 `_review` / `_score_confidences` / `_score_severities`。每个任务在 provider 异常或契约异常时：

1. 先 `note_call` 写 `ai_agent_call`（provider 异常 `outcome=error`；strict 契约异常也记 `error`）；
2. strict 时抛 `ClusterAIFailure(task, reason)`，不再 `note_degraded`、不返回 fallback；
3. `prepare._build_clusters` 不执行到 `replace_prepared_clusters`，因此 DB 里没有兜底簇；
4. job 层因为 `ClusterAIFailure.stage == "cluster"` 把 run 标 `failed`、`error_stage=cluster`，并写 `run_failed` 事件。

degrade 分支保留原有三条 fallback，并把任务键写进 `run.stats.clusterDegraded` 与 `clusters_created.payload.degraded`。

### 2.3 失败步骤可读

`step_states` 新增 `error_stage`：当 `run_status == "failed"` 且 `error_stage == "cluster"` 时，第 5 步从 `pending` 变 `active` 且 `clickable`。`stages.py` 在 `/steps/clusters` 读取 `clusterFailurePolicy` / `clusterDegraded` / `clusterAlgorithm`，并在失败时把 `run.error_message` 作为 `failure` 返回。UI 用同一 DTO 显示回退列表或严格失败原因。

### 2.4 部署资产的服务级化

`install-claude-code.py` 在版本目录旁创建相对软链 `current`，把共享 settings 写到 `<prefix>/config/settings.json`（0644、无 `apiKeyHelper`/密钥），并在切换 `current` 前检查二进制 other-execute、settings other-read、prefix/config other-traverse。`deploy.yml` 只在安装步骤启用时注入稳定 `HE_AI_AGENT_CLAUDE_BIN`、`HE_AI_AGENT_CLAUDE_SETTINGS`、`CLAUDE_CONFIG_DIR` 与 `ANTHROPIC_API_KEY`（值复用 `CLAUDE_CODE_API_KEY`，base64/stdin），并加了一步服务器侧共享资产预检。

## §3 数据流走查

生产失败场景：

1. Deploy 安装 CLI → 写 `current` + 共享 settings → 注入 `.env` → preflight 通过 → 切换 release。
2. systemd 以 `harness` 启动 API，`EnvironmentFile` 提供 `HE_AI_AGENT_CLAUDE_BIN=.../current/usr/bin/claude`、`HE_AI_AGENT_CLAUDE_SETTINGS=.../config/settings.json`、`CLAUDE_CONFIG_DIR=.../config`、`ANTHROPIC_API_KEY`。
3. prepare 进入聚类：`write_stats` 先落 `clusterFailurePolicy=strict`；`cluster_llm` 调 `claude --bare -p ... --settings ...`。
4. 若 CLI 无法启动：`AgentProviderError` → `ai_agent_call(outcome=error)` → `ClusterAIFailure("cluster.review", "AgentProviderError: claude-code analysis call could not start")`。
5. job 层 `record_failed`：`run.status=failed`、`error_stage=cluster`、`error_message=...`。
6. `/steps/clusters`：`step_states(..., error_stage="cluster")` 第 5 步 active；payload 返回 `failurePolicy=strict`、`failure=...`、空 clusters。
7. `RunDetail` 显示失败徽标 + 顶部错误 + 第 5 步可点击；`StepClusters` 显示“真实 AI 聚类失败，运行已显式中止”。

降级场景：

1. `HE_AI_AGENT_FAILURE_POLICY=degrade`（或 `fake` 默认）。
2. 三次调用任一失败 → `degraded` 事件 + 确定性值；`run.stats.clusterDegraded` 落任务键。
3. `RunCard` 的 `degraded` 来自 stats；徽标显示“已完成 · 聚类降级”；`StepFinal` 显示降级提示，不再显示“自进化有效”。

## §6 讨论点

### 6.1 历史 run 的降级标记

- **位置**：`apps/api/app/service/evolution/runs.py:259` / `stages.py:695`
- **现象**：`degraded` 只从 `run.stats.clusterDegraded` 读取；本 PR 之前创建的 run 没有这个 stats 键，即使 `clusters_created.payload.degraded` 存在。
- **问题**：生产 run `01M834EBAY3C9BB3TM8V85VHQN` 属于历史 run，页面仍会显示旧徽标。
- **预判**：新增 run 的语义正确；历史 run 回填需要从 events 批量读 `clusters_created.payload.degraded`，属于额外的读模型改造，不在本 issue 的“严格失败”交付边界内。
- **结论**：记录为已知限制；生产验证用新 run。

### 6.2 生产验证依赖合并与 Deploy

- **位置**：`.github/workflows/deploy.yml`
- **现象**：本地只能验证安装脚本单测、fixture 页面与 API 契约；真实 CLI/settings/凭据的端到端行为要等 merge 后 Deploy。
- **问题**：如果真实 CLI 在共享 config 目录仍写缓存，`harness` 只读目录可能暴露新的失败。
- **预判**：`--no-session-persistence` 已覆盖 analyze/edit 的会话写入；首次部署 smoke 若发现其他缓存写入，再补可写 state 子目录或 ACL。
- **结论**：PR 不声称生产已通过；合并后由 Deploy + 一次真实 run 验收。

### 6.3 文档预算上调

- **位置**：`scripts/doc-budgets.manifest.json`
- **现象**：`docs/ai-agent.md` 700→850，`docs/claude-code.md` 500→520。
- **问题**：常驻文档预算门禁要求先搬层/压缩；本 PR 已压缩两轮，剩余内容是失败契约与共享资产的操作事实。
- **预判**：这两页是各自事实的唯一 home；拆到部署页会让配置语义与 CLI 操作分离。
- **结论**：接受上调，PR 说明已记录理由。

## §9 文件级代码分析

### `apps/api/app/service/evolution/cluster_llm.py`

- **职责**：三层聚类的 review/score/severity 编排与降级。
- **变更形态**：M；旧版三条 `except` 一律 fallback。
- **关键依赖**：Pydantic v2 做输出契约；provider 异常统一折叠成 `AgentProviderError`。
- **变更块**：新增 `ClusterAIFailure`（task + bounded reason），三个任务各自在 `except` 后先记 call、strict 直接 raise、degrade 才 `note_degraded`。`_result_record` 的 outcome 扩到 `error`，让 strict 契约失败也有正确的观测值。
- **实现思路**：把“是否允许回退”收口为参数，而不是让每个任务自己判断配置。
- **检视发现**：无阻断问题；strict 失败仍保留 `ai_agent_call`，满足可诊断要求。

### `apps/api/app/service/evolution/prepare.py`

- **职责**：七步 prepare 编排。
- **变更形态**：M。
- **变更块**：构造器新增 `failure_policy`；聚类前先写 `clusterFailurePolicy`，成功时写 `clusterAlgorithm` / `clusterDegraded`；`enhance_clusters` 透传策略。
- **实现思路**：失败 run 也能从 stats 解释策略；strict 异常自然跳过 `replace_prepared_clusters`。
- **检视发现**：在失败路径上只写 policy、不写 degraded，语义正确。

### `apps/api/app/service/evolution/state.py` / `stages.py` / `runs.py`

- **职责**：七步状态机与投影。
- **变更形态**：M。
- **变更块**：`step_states`/`ensure_step_readable` 增加 `error_stage`；失败聚类步骤 active；clusters payload 增加四个审计字段；run card 增加 `degraded`。
- **实现思路**：状态机只对 `cluster` 失败开可读口，避免把其他失败阶段误标成可读。
- **检视发现**：`_FAILURE_STEP_INDEX` 目前只有 cluster，未来可按需扩展。

### `deploy/install-claude-code.py`

- **职责**：deploy 用户安装/配置 Claude Code。
- **变更形态**：M。
- **变更块**：`build_shared_settings`、`configure_shared`、`switch_current`、`preflight_shared_access`；`write_atomic` 支持父目录权限；主流程在切换 current 前 preflight。
- **实现思路**：把“用户级 CLI”变成“服务级资产”，同时不引入 root/ACL。
- **检视发现**：preflight 只检查 other 位，不能模拟 ACL；当前部署拓扑没有 ACL，足够。

### `apps/web/src/pages/evolution/components/StepClusters.vue`

- **职责**：第 5 步聚类卡片。
- **变更形态**：M。
- **变更块**：算法/策略行、degraded 警告、failure alert；空簇文案在 failure 时不再显示。
- **实现思路**：复用现有 `.card/.cluster` 与颜色 token，不新造布局。
- **检视发现**：`:degraded` 与 `failure` 都是可选字段，旧 API 响应安全。

### `apps/web/src/pages/evolution/components/StepFinal.vue` / `RunCard.vue` / `RunDetail.vue`

- **职责**：终评与运行卡片状态。
- **变更形态**：M。
- **变更块**：`degraded` 时改徽标/终评文案并显示警告；statusClass 用 `pending`（灰）而不是 `accepted`（绿）。
- **实现思路**：不在前端推断降级，只消费后端 `degraded` 布尔。
- **检视发现**：无阻断问题。

- **覆盖**：strict 三任务、strict contract、degrade 保持、prepare 无落库、失败步骤可读、degraded 徽标/终评、installer preflight、provider settings 优先级、edit argv、OpenAPI 字段集。
