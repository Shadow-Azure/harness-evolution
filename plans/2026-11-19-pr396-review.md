## §1 一页速览

一句话：把「为了看一页书，把整座图书馆搬回家」改成「只让快递送那一页所在的单行本，且只取需要的一页」。

原来的读取路径是 `git clone --mirror`：把目标仓库全部历史、分支和 tag 都拉到本地，再 `git show` 一个文件。生产冷缓存下，这一步在 20 秒内容预算内完不成。现在按「仓库 + ref」缓存一个浅仓库，只 fetch 那一个 ref，文件内容由 partial clone 在 `git show` 时按需拉一个 blob。

| 交付块 | 内容 |
|---|---|
| 单 ref 缓存 | 每（仓库, ref）一个目录，进程内锁串行 |
| tag/分支 | `clone --depth 1 --single-branch --filter=blob:none --branch <ref>`，后续只 fetch 同 ref |
| 完整 SHA | `git init` + promisor remote + `git fetch --depth 1 --filter=blob:none origin <sha>` |
| 读取 | `git show <commit>:<path>`，懒拉一个 blob |
| 错误 | 保持既有分类，新增 `ref_invalid` |

验证基线：`pnpm test:api` 通过（整体覆盖率 91%），`pnpm typecheck:api`、`pnpm lint:api`、`pnpm lint:docs`、`pnpm verify:flow`、`pnpm test:gates`、`pnpm contract:check` 均通过。

## §2 架构导览

`TargetContentResolver` 只依赖 `read_file(repo_url, sub_dir, ref, file_name)`；本 PR 没有改接口，因此 service 层与 `target_content.py` 不动。

- `content.py:98` `read_file`：先校验路径与 ref，再算缓存路径并加锁；锁覆盖“确保 ref”和 `git show` 两步。
- `content.py:120` `_cache_path`：`<repo_hash>/<ref_hash>`，ref hash 的输入包含 URL，避免不同仓库同名 ref 碰撞。
- `content.py:135` `_ensure_commit`：完整 SHA 走 bare repo + 单 ref fetch；其它 ref 走 clone/fetch + `HEAD`/`FETCH_HEAD` 解析。
- `content.py:180` `_clone_ref`：唯一出现 `--single-branch` 的地方；失败按 stderr 区分 ref 缺失与仓库不可达并清理目录。
- `content.py:205` `_init_bare`：为完整 SHA 建立 promisor remote，后续 `git show` 才能懒拉 blob。
- `content.py:228` `_fetch_ref`：依次尝试 `refs/heads/<ref>` 与 `refs/tags/<ref>`，只接受“ref 不存在”类错误继续尝试。
- `content.py:267` `_git`：`asyncio.wait_for` 单次上限，取消时由 `_run_process` 杀掉进程组。
- `content.py:292` `_checked_ref`：拒绝选项式 ref 与控制字符，返回 `ref_invalid`。

## §3 数据流走查

1. 启动向导调用 `preview/sessions` → `TargetContentResolver.resolve` → `SubprocessGitContent.read_file`（`content.py:98`）。
2. `_cache_path` 算出 `<data>/target-content/<repo>/<ref>`，同 ref 的并发请求在 `_cache_lock` 排队。
3. 首次 tag 读取：`_clone_ref` 执行单分支浅克隆（`content.py:180`），`HEAD` 解析成 commit。
4. 已缓存 tag：`_fetch_ref` 只 fetch 该 ref（`content.py:228`）；分支因此保持最新，完整 SHA 直接跳过网络。
5. `_git` 执行 `git show <commit>:<path>`：本地没有该文件 blob 时，promisor remote 按需拉取，失败按“文件缺失/网络”分类（`content.py:333`）。
6. 返回文件正文；resolver 继续算 body hash，调用方无感知。

## §6 讨论点

1. **位置**：`apps/api/app/third_party_api/git/content.py:135`
   **现象**：只有 40 位完整 SHA 走对象直达；缩写 SHA 会被当作分支/tag，最终 `ref_not_found`。
   **问题**：旧实现在完整 mirror 里能解析缩写 SHA，这里存在行为收窄。
   **预判**：接受，UI 文案写「commit id」，后续可经 GitHub API 补全缩写；如实际有人使用再补。
   **结论**：

2. **位置**：`apps/api/app/third_party_api/git/content.py:228`
   **现象**：tag 每次读取都会执行一次小 fetch，即使 tag 不可变。
   **问题**：省了全量历史，但重复读取仍有一次网络往返。
   **预判**：单 ref fetch 很轻，换取 tag 被 force-move 时也能刷新；若冷读频繁，可后续按 ref 类型缓存 TTL。
   **结论**：

3. **位置**：`apps/api/app/third_party_api/git/content.py:120`
   **现象**：每个新 ref（尤其分支/commit）都会留下一个浅仓库目录，没有清理策略。
   **问题**：长期多 ref 会累积磁盘占用。
   **预判**：当前写入门槛低、目标仓库数量有限，先观察；需要时加 LRU/部署清理。
   **结论**：

4. **位置**：`apps/api/app/third_party_api/git/content.py:113`
   **现象**：锁是进程内的，多进程/多实例会各自 clone 同一 ref。
   **问题**：m16 明确单实例，当前无实害；扩多实例时需要考虑跨进程锁。
   **预判**：无实害，记录为扩展期事项。

## §9 文件级代码分析

### `apps/api/app/third_party_api/git/content.py`（M）

职责：只读目标内容，按 ref 缓存并执行 `git show`；进程边界与错误分类也在这里。

旧代码（`origin/main`）：`_ensure_mirror` 对每个仓库执行 `git clone --mirror --no-hardlinks`，缓存键只有仓库；`_resolve_commit` 在 full mirror 上 `rev-parse`；`git show` 不需要额外网络。

新代码：缓存键扩展到 ref；tag/分支用单分支浅克隆，完整 SHA 用 bare + promisor fetch；`_fetch_ref` 只刷新同一 ref；`_show_failure` 把“文件不存在”和“懒拉 blob 失败”分开。

实现思路（≤3 行）：

1. 用“仓库 + ref”把不可变输入变成一个可复用的小仓库。
2. 只下载目标 ref 的 commit/tree，文件 blob 交给 promisor 按需拉取。
3. 失败时清理半成品目录，保持旧错误分类。

检视发现：见 §6；无阻塞缺陷。已知弱点：短 SHA、缓存清理、跨进程锁，均已记录并接受。
