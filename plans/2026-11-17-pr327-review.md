## §1 一页速览

一句话：把“仓库或 ref 无效”这一条糊在一起的错误，拆成“哪个字段、什么原因、怎么改、git 说了什么”。

比喻：以前的错误像医院前台只说“你不舒服”，现在分诊台告诉你挂哪个科（`field`）、初步判断（`reason`）、建议（前端文案），必要时附上检查单（`command`/`output`）。

## §2 架构导览

### 2.1 失败分类在 adapter 边界完成

`remote.py:14` 把远端失败原因收敛为四个字面量；`remote.py:22` 的 `RepoInvalid` 同时携带退出码与 stderr，但 `str(exc)` 仍是稳定通用句。`remote.py:102` 的 `_run` 用 `ref_check` 区分 `git ls-remote --exit-code`（退出码 2 = ref 不存在）与 `list_tags`（退出码 2 只能是仓库不可达）。这样 service 不需要理解 git argv。

### 2.2 service 拥有字段/原因封闭集合

`targets.py:25` 定义 `TargetField`；`targets.py:26` 起定义 `TargetReason`，其中远端原因复用 adapter 的 `RepoFailureReason`。`targets.py:151` 的 `_repo_invalid(field, reason, command, output)` 只在两者都有值时填充 `details`，`versions` 继续调用无参版本保持空 details。`targets.py:180` 的 `_remote_invalid` 把 `ref_not_found` 落到 `defaultRef`，其他远端失败落到 `repoUrl`。

### 2.3 输出脱敏复用既有链路

`redaction.py:169` 的 `redact_command_output` 先走 `redact_text`（token/Bearer/userinfo/私钥/provider key），再用单个交替正则一次性区分远端 URL/SCP、UNC、Windows、POSIX 路径：远端路径保留，本机绝对路径替换为 `<path>`，避免二次扫描误伤 URL 路径。最后按末 40 行与 4096 字节截断（`redaction.py:199`）。

### 2.4 前端把错误当作数据而非字符串

`targetErrors.ts:39` 是 reason → `{message, suggestion}` 的文案表；`targetErrors.ts:116` 只接受合法 `field`/已知 reason，否则回退；`targetErrors.ts:147` 是唯一入口，`PROJECT_ID_INVALID` 也复用字段锚点。`TargetFormDialog.vue:69` 用 `visibleServerError` + `serverErrorDismissed` 表达“错误仍在但用户已修改字段”，`TargetFormDialog.vue:127` 在输入时清除。`TargetFormDialog.vue:454` 起渲染汇总与原生 `<details>` 输出块。

## §3 数据流走查

1. 管理员在浮窗提交 → `Index.vue:131` 捕获 `ApiError`。
2. `targetServerError` 读 `code`：`REPO_INVALID` → 解析 `details`；`PROJECT_ID_INVALID` → 解析字段；其他 → `formatApiError`。
3. 对话框 `watch props.serverError`：清空 dismissed、`nextTick` 后按 `[name=field]` 聚焦。
4. 字段渲染 `aria-invalid` / `aria-describedby`，字段下显示原因与建议；有 `command`/`output` 时渲染可展开块。
5. 用户修改该字段 → `onFieldInput` 置 dismissed，汇总与字段错误一起消失。
6. 后端路径：`_normalize_write` 逐字段抛 `_repo_invalid(field, reason)`；`_validate_remote` 捕获 `RepoInvalid` 后组装 `{command:{name,exitCode}, output}`，`output` 已脱敏截断。

## §6 讨论点

### 讨论点 1：超长字段的错误码从 `VALIDATION_INVALID` 变为 `REPO_INVALID`

**位置**：`apps/api/app/service/evolution/targets.py:37`

**现象**：四个可编辑字段移除 `Field(max_length=...)`，超长输入现在由 service 返回 `REPO_INVALID` + 字段细节；此前 Pydantic 先返回 `VALIDATION_INVALID`。`openapi.json` 同步删除对应 `maxLength`。

**问题**：这是否属于本 issue 的“只改错误明细、不改错误码集合”边界？对 API 客户端是可见变化，虽然更符合 issue 中“对象名超长也落到 objectName”的文字。

**预判**：为使 `object_name_invalid` 覆盖超长并让前端字段锚点生效，这个调整是必要的；工程 ID 仍保留 `VALIDATION_INVALID`。若维护者更看重既有错误码分类，可保留 maxLength 并让前端把 `VALIDATION_INVALID.errors` 也映射到字段。

**结论**：（留空）

### 讨论点 2：字段错误只在修改“被锚定字段”时清除

**位置**：`TargetFormDialog.vue:127`

**现象**：服务端错误锚定 `repoUrl` 时，修改 `objectName` 不会清除错误；修改 `repoUrl` 才清除。

**问题**：用户可能先改别的字段，汇总错误仍在；这是“保持错误直到修复点被触碰”的设计，还是应该任何输入都清除？

**预判**：保留当前行为更符合“错误跟着字段走”，避免用户改无关字段导致错误消失后误以为已修复。无实害。

**结论**：（留空）

### 讨论点 3：脱敏以正则黑名单为主

**位置**：`redaction.py:169`

**现象**：`redact_text` 覆盖常见凭据形态；本机路径用单个交替正则替换。未知格式的密钥（例如自定义 header）仍可能出现在 `output`。

**问题**：在 admin-only、4096 字节、末 40 行的边界内，黑名单是否足够？是否需要正向白名单（只保留 git 常见文本）？

**预判**：复用运行日志链路是本 issue 的明确要求；当前边界可接受。若未来输出面向 member 或更广用户，需要正向白名单。

**结论**：（留空）

### 讨论点 4：`output` 对 `list_tags` 不返回，但 `versions` 仍可能暴露原因给 member

**位置**：`targets.py:481`

**现象**：`versions` 捕获 `RepoInvalid` 后仍返回 `_repo_invalid()`（无 details），不区分超时/不可达/ref 不存在；符合“读接口不含诊断”。

**问题**：member 看到的仍是通用文案，是否需要至少区分超时与不可达？issue 非目标明确不向 member 返回 git 原始输出，但未禁止 reason；当前选择最小暴露。

**预判**：保持现状，避免扩大读接口契约。

**结论**：（留空）

## §9 文件级代码分析

### `remote.py`（M）

职责：把 `git ls-remote` 的进程结果翻译成稳定异常。旧代码把所有失败压成一个无信息的 `RepoInvalid`；新代码保留通用 message，但附带 `reason`、`exit_code`、`stderr`。`_run(ref_check=True)` 只有 validate 使用，因此 `list_tags` 的退出码 2 不会被误判为 ref 不存在。实现思路：分类在 adapter、展示在 service、脱敏在 utils，三层各管一件事。

检视发现：无可执行缺陷；`RuntimeError` 仍归入 `git_unavailable`，与旧行为一致。

### `targets.py`（M）

职责：字段校验、封闭集合、details 组装。每个本地规则显式传入 `(field, reason)`；`_repo_invalid` 只在两者都存在时带 details，保证 versions 无诊断。`_validate_repo_url` 先判 password 再判端口，保证“带凭据且端口非法”优先报凭据问题。实现思路：保持 422 / 通用 message 不变，增量 details 由调用点决定。

检视发现：见讨论点 1。

### `redaction.py`（M）

职责：命令输出的有界脱敏。用一次交替匹配避免 URL 路径被路径规则二次替换；尾截断保留最接近失败点的字节。实现思路：先凭据、再路径、再控制字符、最后行/字节预算。

检视发现：见讨论点 3；单测覆盖 URL 路径保留、POSIX/Windows 路径替换、控制字符与截断边界。

### `targetErrors.ts`（A）

职责：把 `ApiError` 变成 UI 可直接渲染的结构。`structuredError` 对 `field`/`reason` 做白名单校验，未知值回退；`PROJECT_ID_INVALID` 复用同一字段通道。实现思路：错误文案集中在表里，组件只负责布局。

检视发现：无。

### `TargetFormDialog.vue`（M）

职责：字段错误渲染、聚焦、清除、git 输出块。`visibleServerError` 与 `serverErrorDismissed` 把“props 错误”与“用户已开始修复”分开；`aria-describedby` 指向字段错误 id。实现思路：不引入新弹层，沿用现有 Element Plus 表单与 token。

检视发现：见讨论点 2；输出块使用原生 `<details>`，键盘可展开。

### `Index.vue` / `TargetsOverview.vue`（M）

职责：把保存失败统一交给 `targetServerError`。总览页此前直接把 `Error.message` 当文案，现在与配置页共用字段锚点，避免两套行为。检视发现：无。

### 测试与文档（M）

API 测试按“本地规则/远端分类/脱敏/HTTP 边界”分组；Web 测试覆盖字段锚点、聚焦、清除、输出块、回退；E2E 使用确定性 remote 覆盖不可达与缺失 ref。文档把 details 形状、admin-only 与子目录校验时机写进 05/08；Agent Note 把安全边界从“不含 stderr”改为“admin 有界脱敏输出”。
