## §1 一页速览

**一句话：** 这个 PR 把 M5-02 的 target API 接到了真正可操作的管理页面：成员能查看启用/停用配置，admin 能新增、编辑、启停和删除，向导候选则继续只消费 enabled-only catalog。

**比喻：** 配置页像公司前台登记表。成员可以查看“谁已登记”，管理员才能改表；后端门禁决定仓库和 ref 是否真的可用；全局 toast 是大厅广播，表单内错误是柜台小票，同一次失败只应在正确的层级出现一次。

## §2 架构导览

### 2.1 路由层只负责进入受保护的页面

`/evolution/targets` 使用懒加载并落到 `TargetConfigPage`（`router/index.ts:50-57`）。它没有标记 `public`，因此走统一的 `beforeEach`：先恢复登录态，未登录跳 `/login?redirect=...`，强制改密再跳改密页（`router/index.ts:69-88`）。

页面角色只在 UI 层决定按钮是否可见：

```text
auth.user.role === "admin"
  → canWrite=true
  → 新增、编辑、启停、删除可见

auth.user.role === "member"
  → canWrite=false
  → 列表只读
```

证据是 `Index.vue:32-33`、`TargetTable.vue:52-152`。真正的安全边界仍在 M5-02 的中间件；前端隐藏按钮只负责体验，不承担授权。

### 2.2 数据层把配置事实和向导候选分开

这是这个 PR 最重要的业务边界：

- `/api/evolution/targets` 返回所有配置，包括停用项，供配置页查看和重新启用；
- `/api/catalogs/targets` 只返回启用项，供后续启动向导选择；
- `/api/catalogs/models` 同样复用 catalog 失效边界。

证据是 `evolutionTargets.ts:10-16`、`catalogs.ts:5-18`。如果把两者合并，用户停用对象后要么看不到它、无法重新启用，要么会在向导里选到停用对象。

### 2.3 mutation 成功才刷新，失败保留现状

三类 mutation 共用 `invalidateTargetDependents()`（`useEvolutionTargets.ts:14-20`）：

```text
create/update/delete 成功
  → 失效 ["evolution","targets"] 整棵前缀
  → 失效 ["catalogs"] 整棵前缀

任一请求失败
  → 不执行 onSuccess
  → 列表和 catalog 保持原状
```

`["evolution","targets"]` 同时覆盖配置列表和 `${targetId}/versions`；`["catalogs"]` 同时覆盖 target 与 model catalog（`queryKeys.ts:22-27`）。这里用前缀失效而不是手动改缓存，避免同一对象在列表、版本和向导候选之间出现三种状态。

### 2.4 页面把“表单内错误”和“列表上下文错误”分开

页面维护两类持久错误：

- `formError`：`REPO_INVALID`、`TARGET_EXISTS` 等保存失败留在打开的表单中，输入不清空；
- `operationError`：`TARGET_IN_USE` 和启停失败留在列表上方，被操作的行不消失。

证据是 `Index.vue:34-38`、`:70-138`、`:158-164`。这比只用 toast 更适合复杂表单，因为用户可以修改出错字段后直接重试。

### 2.5 表单状态由打开事件重置，编辑时加载版本

`TargetFormDialog` 的本地 form 是一次可修改副本（`TargetFormDialog.vue:34-41`）。父组件打开新增/编辑时设置 `target + modelValue`，子组件 watch 到打开状态后从 target 或默认值重置（`:52-99`）。

编辑态把 target id 传给 `useEvolutionTargetVersions`，只有选中 target 时才请求 tags（`useEvolutionTargets.ts:70-80`）。版本选项包含：

1. 远端 tag；
2. 当前 target 的 `defaultRef`；
3. 用户手工输入的 ref。

因此分支名不需要伪装成 tag，也能保留在 select 中；`allow-create + filterable` 正是这个作用（`TargetFormDialog.vue:177-214`）。

### 2.6 视觉复用原型 token，不引入第二套主题

共享 token 已与原型亮色系一致：`bg/bg-panel/bg-card/border/text/blue/green/red/purple` 等值直接对应 `plans/14-15-ui-prototype/harness-evolution.html:8-15` 与 `apps/web/src/styles/tokens.css:1-17`。

配置页使用原型 `.wrap` 的 1080px 上限和相对视口 24px 横向 gutter，在中等宽度与 390px 下不会重复叠加外层页面的留白；页头使用 `.page-head`/`.page-note` 层级：18px 标题、12px faint 说明（`targets/Index.vue:141-240`）。白色卡片、12px 圆角、1px 边框和 compact typography 与原型一致；对象类型和启用状态分别采用紫色 kind chip 与绿/灰 tinted badge（`TargetTable.vue:241-274`）。新增表单使用 720px modal、14px 圆角、15px 标题、14px/18px header、18px body 与 66vh 滚动区、13px/18px footer 和 footer 面板底色（`TargetFormDialog.vue:102-296`），没有另造暗色或独立视觉系统。

### 2.7 E2E 使用真实栈，只替换外部 git

浏览器测试启动真实 `vite`、FastAPI、SQLite 和 Chrome（`m5-target-config.test.mjs:204-275`），只注入确定性 `DeterministicGitRemote`（`m5_target_server.py:14-24`），避免测试依赖公网 git。

测试仍走真实：

- HTTP 路由、鉴权、数据库；
- 前端 query、表单、Element Plus dialog/message-box；
- 浏览器 DOM、cookie 和 390px viewport。

active run 由测试工具直接写入真实 `evolution_runs` 表（`m5_target_run_tool.py:26-64`），因此 `TARGET_IN_USE` 是 repository 真实判定，而非前端 mock。

## §3 数据流走查

### 场景 A：admin 新建有效 target

1. 点击“新增配置”，`openCreate()` 清空旧错误并打开表单（`targets/Index.vue:43-49`）。
2. 用户填写名称、仓库、子目录、基线，选择 enabled（`TargetFormDialog.vue:112-223`）。
3. 提交前 trim 并检查四个必填字段（`:72-91`）。
4. `POST /api/evolution/targets`（`evolutionTargets.ts:23-30`）。
5. 成功后 mutation 失效 target 和 catalog 前缀（`useEvolutionTargets.ts:33-36`）。
6. 页面关闭表单并清空编辑对象（`targets/Index.vue:122-137`）。
7. 列表重新读取，新行出现；未来向导通过 catalog 看到 enabled-only 结果。

### 场景 B：远端或 ref 无效

1. 表单提交后，后端返回 `422 REPO_INVALID`。
2. 页面 catch 后映射成“仓库或 ref 无效，请检查地址、子目录与基线”（`targets/Index.vue:107-115,133-134`）。
3. `serverError` 渲染在仍打开的 dialog 内（`TargetFormDialog.vue:225-231`）。
4. 所有已填值仍保留，用户可以只改错误字段再提交。
5. 请求失败不触发 query invalidation，列表不被错误数据替换。

### 场景 C：编辑 target 并选择版本

1. 点击行“编辑”，设置 `editingTarget` 并打开 dialog（`targets/Index.vue:51-57`）。
2. `editingTargetId` 驱动 `GET /targets/{id}/versions`（`:39-41`）。
3. 版本结果与 target defaultRef 去重、排序后作为 select 选项（`TargetFormDialog.vue:44-50`）。
4. 用户可从 tag 选择，也可输入分支名（`:177-195`）。
5. 提交完整 PUT body，而不是只发送变化字段（`targets/Index.vue:59-68`、`evolutionTargets.ts:38-49`）。

### 场景 D：启停

1. 表格把当前 target 克隆并翻转 `enabled` 后 emit（`TargetTable.vue:32-37`）。
2. 页面用完整对象生成 PUT body（`targets/Index.vue:97-105`）。
3. 成功后失效配置与 catalog；停用行仍在配置列表，但不再进入 catalog。
4. 失败时行保持原状态，列表上方显示持久错误。

### 场景 E：删除被进行中 run 引用的 target

1. 点击删除先弹出含“有进行中 run 时不可删除”的确认框（`targets/Index.vue:70-85`）。
2. 后端 repository 在行锁事务中发现 active run，返回 `409 TARGET_IN_USE`。
3. 页面把错误显示在列表上下文中，被引用行继续存在（`:86-94`、`:158-164`）。
4. 全局 `presentConflict` 不重复弹 toast，因为 `TARGET_IN_USE` 已被登记为 page-handled（`app/apiError.ts:3-25`）。

### 场景 F：成员查看

1. 路由守卫确认成员已登录。
2. 页面 `canWrite=false`，不渲染新增按钮和整列操作（`targets/Index.vue:32`、`TargetTable.vue:52-57,91-94,127-152`）。
3. 即使伪造前端调用，后端仍会拒绝写请求。
4. 390px viewport 下页面本体无横向溢出，表格由 `.target-table-scroll` 内部滚动（`TargetTable.vue:205-218`）。

### 场景 G：从自进化页进入配置

1. `/evolution` 页头渲染 icon-only 齿轮（`pages/evolution/Index.vue:13-21`）。
2. Link 的可见文本为空，但 `aria-label/title` 都是“配置进化对象”（`TargetConfigEntry.vue:6-23`）。
3. 点击进入 `/evolution/targets`；返回后因写入已触发前缀失效，已有 catalog observer 会重新取数。

## §6 讨论点

### D1 `TARGET_EXISTS` 会同时触发全局 toast 和表单内错误

**位置：** `apps/web/src/app/apiError.ts:3-6`、`apps/web/src/main.ts:27-30`、`apps/web/src/pages/evolution/targets/Index.vue:107-134`。

**现象：** 页面明确把 `TARGET_EXISTS` 映射进打开的表单，但全局 page-handled 集合只登记了 `BAD_CASE_SESSION_MISMATCH` 和 `TARGET_IN_USE`。后端返回重复对象对时，用户会同时看到“同类型的对象名称已经配置”的表单错误和一条 `target already exists` 的全局错误 toast。

**问题：** 设计要求 422/409 作为可复核的页面错误呈现；同一次失败出现两种措辞、两个位置，会让用户误以为发生了两次失败，也破坏了“列表错误/表单错误/全局通知”三者的单一归属。

**预判：** 应把 `TARGET_EXISTS` 加入 page-handled 409 集合，并增加一条直接回归，防止后续再次由全局 toast 抢走表单错误。框架行为已实测：`node_modules/.pnpm/@tanstack+query-core@5.104.5/node_modules/@tanstack/query-core/build/modern/mutation.js:202-227` 会先调用 cache-level `onError`，再调用 mutation observation 的 `onError`，最后向 `mutateAsync` 调用方重新抛出错误，所以两条反馈路径都会执行。

**结论：** 应修复。这是明确的双重错误反馈缺陷，不属于风格偏好。**处理结果：** `TARGET_EXISTS` 已加入 page-handled 409，并新增“不触发全局 notify”的回归测试。

### D2 成员看到空配置页时被提示去执行无权操作

**位置：** `apps/web/src/pages/evolution/targets/components/TargetTable.vue:73-76`。

**现象：** 空态描述固定为“新增一个 skill 或 agent，启动向导才会显示候选对象”，但成员模式下新增按钮和操作列均已隐藏。

**问题：** 当成员第一次进入且数据库没有 target 时，页面会给出一条成员无法执行的指令。这不是安全漏洞，而是角色状态与文案状态不一致；用户会寻找一个不存在的按钮。

**预判：** 空态应根据 `canWrite` 分支：admin 显示新增引导，成员显示“当前暂无配置，请联系管理员添加或启用对象”。补一条成员空列表组件测试即可锁住。

**结论：** 应修复。角色权限已经按设计实现，但空态仍泄露了 admin-only 操作语气。**处理结果：** 空态描述已按 `canWrite` 分支，成员只得到联系管理员提示。

### D3 Issue 与 Agent Note 的权限/职责事实和 fullstack-design 冲突

**位置：** `.agents/flow/issues/m5-03-target-config-ui.md:80-82`、`.agents/flow/issues/m5-03-target-config-ui.en.md:116-118`、`.agents/notes/implemented/feature/2026-10-27-target-config-ui.md:13`。

**现象：** 中文 Issue 的“非目标”仍写“不做权限分级”，英文同节却写“No scope creep beyond…”，中英并不等价；fullstack-design、代码和测试都明确要求成员只读、admin 可写。Agent Note 又写“Only the backend `GitRemote` decides whether a repository, ref, and subdirectory are valid”，但实际 subDir 由 service 的 `_validate_sub_dir()` 校验，`GitRemote` 只校验 repo/ref（`apps/api/app/service/evolution/targets.py:117-175,287-292`）。

**问题：** `.i18n.yaml` 只记录 pair 的 blob hash，不会发现语义不一致。后续实现者若把中文“非目标”当权威，可能撤销本 PR 已完成的角色视图；若按 Note 理解 subDir 校验，也会错误归责到 git adapter。

**预判：** 删除或改写“不做权限分级”，中文改成与英文一致的“不扩大本 Issue 已声明边界”；Agent Note 改成“后端 service 负责 repo/ref/subDir 语法规则，GitRemote 负责远端与 ref 可达性”。随后重录三件套。

**结论：** 应修复。设计文档和测试已经给出权威答案，这里不是待拍板的取舍，而是过时事实。**处理结果：** 中英文 Issue 的非目标已等价，Agent Note 已区分 target service 的语法/路径校验与 `GitRemote` 的远端/ref 校验，并重录两组 i18n。

### D4 新页面的语义色与原型 chip/badge 仍有偏差

**位置：** 原型 `plans/14-15-ui-prototype/harness-evolution.html:388-401`；实现 `apps/web/src/pages/evolution/targets/components/TargetTable.vue:241-262`。

**现象：** 原型把 kind chip 定义为紫色文字、紫色淡边框和紫色淡背景；当前 `kind-chip` 使用蓝色文字且没有背景。原型 enabled/disabled badge 都有与状态色对应的淡背景；当前状态 chip 只有文字和边框色。配置页的其他尺寸、卡片、边框和排版已对齐，但这两个最常扫读的语义标记仍像另一套“资源标签”而非原型 badge。

**问题：** 用户明确提出前端应按 `harness-evolution.html` 设计。虽然 F19 没有现成截图，Agent Note 也把原型定为唯一视觉基准，语义标记的颜色漂移会让 skill/agent 和启用状态与已有页面看起来不属于同一套设计语言。

**预判：** 最小修法是让 kind chip 使用 purple 的 35%/9% color-mix，enabled/disabled 使用 green/text-faint 的 tinted background；不新增 token，不复制整页样式。入口位置还应留给 M5-05 的 Step1 名称选择器，本 PR 在 `/evolution` 页头的临时入口可作为提前可发现性，但 M5-05 合入时必须把齿轮放到设计指定位置并做集成复测。

**结论：** 颜色部分建议在本 PR 修复；入口位置作为 M5-05 明确交付，不在本 PR 伪装成最终定位。**处理结果：** kind chip 已改为原型紫色体系，enabled/disabled badge 已加入对应浅底；真实 Chrome 断言通过。M5-05 最终入口位置已写入 Agent Note。

### D5 移动端测试没有真正证明表格发生了横向溢出

**位置：** `tests/e2e/m5-target-config.test.mjs:505-518`、`TargetTable.vue:212-218`。

**现象：** E2E 断言 `scroller.scrollWidth >= scroller.clientWidth`。因为没有内容时两者也相等，这个条件不能证明内部滚动被触发。

**问题：** 当前 CSS 的 `min-width: 820px` 在 390px viewport 下实际上会溢出，所以产品行为大概率正确；但回归断言偏松，未来如果把 `min-width` 删掉，测试仍可能通过。

**预判：** 改成 `scrollWidth > clientWidth`，并可同时断言 `.target-table-scroll` 能滚动且 `document.documentElement` 不溢出。

**结论：** 小问题，不阻塞功能；若本 PR 修改 E2E 或响应式 CSS，应顺手收紧断言。**处理结果：** 已严格断言内部 `scrollWidth > clientWidth` 且两侧宽度大于零，并通过临时移除内部滚动的变异确认测试会红。

### D6 配置页缺原型 1080px 容器与安静页头层级

**位置：** 原型 `plans/14-15-ui-prototype/harness-evolution.html:376,411-415`；实现 `apps/web/src/pages/evolution/targets/Index.vue:141-242`。

**现象：** 全局 workspace 最大宽度是 1280px，配置页原先没有自己的 1080px 容器；页头使用 `EVOLUTION` eyebrow、17px 标题和 12px dim lede，而原型是 18px 标题加 12px faint note，没有 eyebrow。

**问题：** 配置页在大屏上比原型内容更散，标题区域多一级视觉信息；token 相同不足以证明页面骨架相同。

**预判：** 在配置页自身收口 1080px 居中容器与 24px 横向留白，保留全局 20px/64px 纵向节奏，避免影响 Session/Errors workspace；页头改成 `page-head/page-note` 语义。

**结论：** 属于用户明确要求的原型一致性缺陷。**处理结果：** 页面以 1080px 上限和父容器推导宽度逃逸外层 gutter，再用相对定位把页面居中，保持自身 24px 横向 padding；该实现不使用 `transform`，不会把 fixed 弹窗遮罩限制在页面容器内。E2E 在 1408px 断言外框 1080px、内容区 1032px 和居中，在 800px 断言内容区 752px，在 390px 断言内容区 342px，三档均无页面横向溢出；打开弹窗后还必须断言 `.el-overlay` 覆盖完整 viewport。标题字号/字重、note 字号/颜色及无 eyebrow/lede 也已锁定。

### D7 配置弹窗宽度与分区偏离原型

**位置：** 原型 `plans/14-15-ui-prototype/harness-evolution.html:530-538`；实现 `apps/web/src/pages/evolution/targets/components/TargetFormDialog.vue:102-285`。

**现象：** 原实现为 560px 宽，footer 只是 body 内的一段按钮，没有原型 modal 的独立 footer 面板；Element Plus 默认 header/body padding 也覆盖了预期节奏。

**问题：** 配置字段较多，560px 让表单局促；头和操作区在视觉上未与内容分区，不符合原型 modal 的阅读顺序。

**预判：** 使用 720px 宽度、14px 圆角和 Element Plus 的 `header-class/body-class/footer-class` 明确三区；标题 15px/700，header 14px/18px，body 18px 且限制 66vh 后内部滚动，footer 13px/18px 并使用 `--bg-panel`；提交按钮通过 `form` 属性保留原生表单提交语义。

**结论：** 属于原型一致性缺陷。**处理结果：** 组件测试锁定移动端宽度表达式和三区结构；真实 Chrome 锁定 720px 计算宽度、14px 圆角、15px/700 标题、header/body/footer padding、66vh body 滚动区、footer 背景，以及 390px 下 358px modal 与两侧 16px gutter。局部圆角选择器从错误的后代选择器修正为 `.el-dialog.target-form-dialog` 根节点选择器。
