## §1 一页速览

一句话：把「先有 probe 再聚类」的 V1 准备链，换成「bad case → Session → 潜在 → 归因 → 聚类」的 V2 七步链，同时让旧 run 不需要数据迁移也能被七步页面读懂。

比喻：旧链像先拿到一份已经批改过的作业清单再分组；新链像先按「这个对象版本是否在 Session 里出现」筛出相关作业，逐份判定是否真是该对象的问题，再把确认的作业按类型装订成册。旧 run 没有这些新册子，服务端就把旧清单重新贴成七步目录，而不是把旧数据改写成假的新证据。

交付块：

| 块 | 内容 |
|---|---|
| 状态机 | 七步键、`5+M+1`、prepared=5、cluster_only 终态 |
| prepare | matcher + 候选批量 upsert + 归因复用 + attributed 聚类 |
| 读取 | 七端点共享 `build_step_payload` |
| 历史 | `legacy-probe-import` 游标只读投影 + probe 兼容分支 |
| UI | 七步详情、V2 stats、sessions/potential 服务端分页 |

验证基线：`pnpm test:api` 1275 passed / 18 skipped；`pnpm test:web` 574 passed；run-detail E2E、integration、gates、contract、flow、docs 通过；真实浏览器 6 个冒烟场景 PASS。

## §2 架构导览

### 2.1 状态机是唯一事实源

`state.py:94` 的 `legacy_unit` 只回答「旧游标等于七步的哪一格」，不改写 `progress_unit`；`state.py:118` 的 `effective_unit` 在读取入口统一套用。`step_states` 仍只做纯函数投影，`appendable` 的七键由 `ensure_step_readable` 统一 404 语义。这样 run shell、step 端点、进度百分比都从同一个游标出发，不会出现「列表说第 6 步、详情说第 5 步」。

### 2.2 prepare 是一条可重入流水线

`prepare.py:122` 的 `handle` 按游标分段：每段先完成自己的写入，再推进一个 unit。候选段用 `upsert_many` 单事务写全量（含 excluded）；归因段从候选表重建 included 行，`AttributionRunner` 用候选 `probe_id` 跳过已完成项；聚类段只读 `list_clusterable_probes`（`prepare.py:325`），因此 `non_target` 永远进不了簇。失败时 `blocked(attribution)` 只抛 `RunBlocked`，由 jobs 层落状态；重试重新入队 prepare，从游标继续。

### 2.3 读取只有一个 builder

`stages.py:502` 的 `build_step_payload` 接收一个 `_RunFacts`（run + clusters + candidates + attributions + probes），七个 builder 按 key 取对应事实。V2 与 legacy 的差异集中在 `_RunFacts.legacy` 和三个兼容函数（`_v2_session_rows:767`、`_legacy_potential_rows:857`、`_legacy_potential/attribution` 分支），而不是复制七个端点。

### 2.4 写入守卫与游标同事务

`db/crud/evolution.py` 新增 `replace_prepared_clusters`：在同一事务里校验 expected=4、写 cluster/link、推进到 5。`insert_rounds` 与 `write_final` 的 expected 从旧的 4 / 4+M 改为 5 / 5+M；`mark_prepared` 固定 unit 5。这保证「簇存在」与「游标已 prepared」不会分裂。

## §3 数据流走查

1. 启动：`launch.py` 先解析 target/policy/window，`_require_potential` 用共享 matcher 判 `NO_ASSOCIATED_SESSIONS` / `NO_POTENTIAL_MATCHED`，再把 `potential_policy/cache_enabled/attribution_engine` 固化进 run 快照。
2. prepare unit 0→1：记录 `prepare_started`，进入 range 完成态。
3. unit 1→2：`associated_sessions`，把 Session 分区与行快照写进 stats，记 `sessions_linked`。
4. unit 2→3：`potential_cases`，候选全量 upsert，记 `potential_computed`。
5. unit 3→4：从候选重建 included 行，`AttributionRunner` 缓存复用/重算，批量记 `attribution_created/reused`。
6. unit 4→5：只取 attributed 候选聚类，写 confidence/severity/rank；full 再准备 workspace、建 rounds，最后 `mark_prepared(5)`。
7. 读取：run shell 用 `effective_unit` 得到七步状态；`GET /steps/{key}` 过 readiness 后由同一 builder 取 payload；legacy run 走 probe 兼容分支。
8. iteration/final：沿用既有 rounds/final 表，只把 DTO 的 `probes/probeCount/type` 改为 `cases/caseCount/category`。

## §6 讨论点

### D1. 本 PR 同时改了后端与运行详情 UI，跨了 m10-04/m10-06 的切片

- **位置**：`apps/web/src/pages/evolution/**`（本 PR 18 个前端文件）
- **现象**：issue m10-04 的 scope 原本只有后端/契约；但七步 DTO 一旦替换，旧六步页面会 typecheck 与运行同时失败。
- **问题**：这是一个「后端契约切换必须带着消费端一起切换」的原子变更；拆成两个 PR 会让 main 在中间态不可用。
- **预判**：接受本次合并；m10-06 仍需补 2–4 步分页、SSE、non_target 展示与 blocked attribution 的自动重试交互，不应把本 PR 视为 m10-06 已完成。
- **结论**：（留空）

### D2. 历史 run 的 sessions/potential 行是合成数据，可能被误读

- **位置**：`stages.py:857`（legacy potential）、`stages.py:767`（session 行）、`state.py:94`
- **现象**：V1 没有 sessions/potential 的持久化行；兼容分支用 probe 与 source case 合成，`title` 可能为空、`orderState` 固定 `unknown`、触发点可能缺失。
- **问题**：页面会把合成行当作「历史 run 当时确实这样筛过」；但 V1 并没有这些阶段。
- **预判**：接受只读投影，但建议在 DTO/文档明确「历史合成」语义；若后续要做历史 run 的审计级回放，应另建快照而不是继续从 probe 推断。
- **结论**：（留空）

### D3. prepare 仍是单 job，workspace 准备失败后的重试可能重复建分支

- **位置**：`prepare.py:384`（workspace）、`state.py:122`（游标）
- **现象**：聚类与 rounds 之间的 workspace 失败会留下 unit=5；重试 prepare 会再次 `workspaces.prepare(run)`。
- **问题**：Git workspace 实现是否对「同一 run 分支已存在」幂等，取决于实现细节；当前测试用 fake workspace，未覆盖真实 git 重启。
- **预判**：本次沿用旧 prepare 的重试形态，未新增风险；建议 m10-06/恢复专项补一个真实 git 的「prepared 中途失败」测试。
- **结论**：（留空）

### D4. launch 同步跑一次全量 matcher，prepare 再跑一次

- **位置**：`launch.py:_require_potential`、`prepare.py:122`
- **现象**：启动前为快速 409 先做一次 `associated_sessions + potential_cases`，成功后 prepare 再从 unit 1 做一次。
- **问题**：大空间下启动请求会承担一次全量匹配成本；设计明确要求启动判 409，但两次计算没有共享快照。
- **预判**：当前数据量下无实害；若预览/启动成本成为瓶颈，可在 launch 时持久化 matcher 快照供 prepare 复用，而不是重复查询。
- **结论**：（留空）

### D5. `attribution_list_run` 的「每 case 一条主归因」依赖排序

- **位置**：`db/crud/attributions.py:list_run_attributions`、`stages.py:_RunFacts.attribution_by_case`
- **现象**：一个 case 可关联多条归因；读取按 `updated_at desc, probe_id` 排序后 `setdefault` 取第一条。
- **问题**：这是「展示主归因」的隐式规则，未在 DTO 暴露「还有哪些归因」；多归因详情属于 m11 的范围。
- **预判**：接受当前排序作为稳定主归因；m11 多归因页面应显式给出完整列表，而不是依赖第一条。
- **结论**：（留空）

### D6. 删除了旧六步快照与真实 git prepare 测试

- **位置**：`apps/api/tests/m5-06-six-step-api/snapshots/**`（13 删）、`m5-09-git-candidate/test_prepare_service.py`
- **现象**：行为已替换，snapshot 不再有意义；真实 git prepare 测试随旧 service 删除。
- **问题**：新 prepare 的真实 git 集成覆盖下降；目前 workspace 用 fake。
- **预判**：建议后续补一个「真实 git + 七步 prepare」的恢复测试；这是覆盖欠账，不是本 PR 的阻断项。
- **结论**：（留空）

## §9 文件级代码分析

### `state.py`

职责：七步游标与 V1 只读投影。旧版是六键、`4+M+1`；新版阈值 `(1,2,3,4,5,5+M,6+M)`，`legacy_unit` 把 V1 的 2–4 折叠到 prepared 5。`ensure_step_readable` 只额外隐藏 cluster_only 的 iteration/final。

### `prepare.py`

职责：七段 prepare。核心是「先写后推进」与「从游标恢复」：候选批量 upsert 用唯一键幂等；归因用候选 probe 指针断点；聚类只读 attributed。`_run_policy` 直接读 resolve 后的快照，避免 default preset 携带 switches 被二次校验拒绝。

### `stages.py`

职责：七步 DTO。`build_step_payload` 是唯一入口；V2 与 legacy 的分叉集中在 `_RunFacts` 的 `legacy` 标记和合成行函数。clusters/iteration 的 case 表由 cluster links + probe/candidate 关系统一生成。

### `runs.py`

职责：run shell。`_stats` 把 V2 stats 与 legacy probe 统计统一；`_progress` 用 `effective_unit` 计算百分比与阶段文案；`_detail_steps` 输出七键。

### `launch.py`

职责：启动预检与快照。把旧的 `NO_PROBES_MATCHED` 预检替换为 matcher 的 `NO_ASSOCIATED_SESSIONS`/`NO_POTENTIAL_MATCHED`，并把 policy/cache/engine 固化进 run。

### 前端

`RunDetail.vue` 增加 page 状态与七步 stats；`RunStepContent.vue` 按 key 分派七个组件；`StepSessions/StepPotential` 走服务端分页；`StepClusters/StepIterations` 改用 case 表；`StepFinal` 的 `type` 改 `category`。
