## §1 一页速览

一句话：把“谁有资格证明你是谁”从 `IdentityService` 里拆出来，装成一个可替换的插座；密码登录原样从插座走，Cookie/SSO 将来只换插头。

比喻：登录像进门查证件。`AuthProvider` 是墙上统一的插座规格——只问“这张证件能不能验过”，不关心是密码还是外部工牌；`ProviderRegistry` 是配电箱，启动时只允许插 `password` 这一种插头，插 `cookie`/`oidc` 直接跳闸（进程启动失败）；`SessionBridge` 是前台登记员，拿验过的证件去名册里找对应的人，找不到就说“没有你的登记”（403），绝不在现场给人补办一张新证；`CallbackService` 是预留的“外部证件窗口”，设备还没到，所以先挂“暂未开放”（501），但取号、核对、失败原因（400/401/403/502）都已经装好，接上设备即可用。

| 密码回归 | 原 `login` 里的 argon2 校验与 dummy 抹平移入 `PasswordProvider`，错误码不变 | `apps/api/app/service/identity/password.py:22`、`apps/api/app/service/identity/service.py:51` |

## §2 架构导览

### 2.1 一张协议只问“验没验过”

`AuthProvider` 只有一个方法 `authenticate(Credentials) -> ProviderIdentity | None`（`apps/api/app/service/identity/providers.py:36`–`:43`）：返回身份表示验过，返回 `None` 表示拒绝，抛 `AuthProviderError` 表示“提供方本身坏了”（`:14`–`:15`）。三个中性类型各管一段：`Credentials` 是入参口袋（`username`/`password`/`code`，`:18`–`:24`），`ProviderIdentity` 是“验过的身份 + 来源 + 可选邮箱”（`:27`–`:33`），`ProviderRegistry` 是启动期唯一的装配与选择点（`:46`–`:69`）。

关键取舍是“拒绝”和“故障”分开：调用方拿到 `None` 走 401（用户错），拿到 `AuthProviderError` 走 502（提供方错）。这决定了 §3 剧本 C 里 401 与 502 的分流，也是将来接 OIDC 时区分“code 无效”和“IdP 超时”的唯一依据。

### 2.2 注册表：启动即跳闸

`ProviderRegistry.from_settings` 只在 `settings.auth_provider is PASSWORD` 时构造 `PasswordProvider`（`providers.py:59`–`:69`），`cookie`/`oidc` 直接抛 `AuthProviderConfigurationError`，消息明确写“reserved and not implemented”，不静默回退。`password` 属性在未配置时也抛同一异常（`:71`–`:76`），是给“注册表被手工组装漏了 provider”兜底的失败关闭。

装配点在 `IdentityService.__init__`（`apps/api/app/service/identity/service.py:32`–`:34`），而 `IdentityService` 在 `create_app` 里构造（`apps/api/app/main.py:126`），所以非法值在任何请求被接收之前就让 `create_app` 抛异常——这正是测试 `test_reserved_providers_fail_startup`（`apps/api/tests/identity/test_auth_provider_seam.py:128`–`:136`）断言的行为。设计 07 §8.2.1（:1241）写的是“在 `main.py` 装配时按 env 选实现”，实际是“`main.py` 构造服务、服务内部选实现”；语义等价，位置差一层，见 §7。

### 2.3 密码提供方：把原来的字节搬进插座

`PasswordProvider` 复刻了原 `IdentityService.login` 的校验逻辑（`apps/api/app/service/identity/password.py:22`–`:37`）：按用户名取行，取不到就用构造时预生成的 dummy hash（`:20`），`verify` 失败统一 `None`，成功返回 `ProviderIdentity(provider=PASSWORD, subject=user.id)`。两处细节值得记：

- 异常从 `VerifyMismatchError` 放宽成 `VerificationError`（`:33`）。旧代码遇到库里的坏 hash 会冒到 500，现在归为一次普通拒绝（401）——行为有变化，方向是变稳。
- dummy hash 仍只算一次，但实例化位置从 `IdentityService` 挪到了 provider；`IdentityService` 自己还留着一个 `PasswordHasher`（`service.py:30`）给改密/建号用，于是启动时多算了一次 argon2（约几十毫秒）。无实害，见 §7。

### 2.4 会话桥：找名册，不建号

`SessionBridge.resolve` 是“身份 → 用户行”的唯一通道（`apps/api/app/service/identity/session_bridge.py:31`–`:58`）：password 身份用 `get_by_id(identity.subject)`，失败给 401 `AUTH_INVALID`（与密码错同码，避免把“用户不存在”暴露成另一种信号）；外部身份用新仓储方法 `get_by_provider_subject(provider, subject)`（`apps/api/app/db/crud/users.py:40`–`:62`），失败给 403 `AUTH_NO_MAPPING`。最后统一判 `is_active`，停用给 403 `FORBIDDEN`（`:52`–`:57`）。

`complete_login` 先 `touch_last_login` 再 `issue`（`:60`–`:75`），签出的 access/refresh 与密码登录完全同构：`sub` 用内部 id、`role` 用库里的角色、`mcp` 带强制改密标记。桥不写任何用户行，`get_by_provider_subject` 在空 subject 时提前返回 `None`（`crud/users.py:47`–`:48`），避免用空串去匹配一堆 `external_subject IS NULL` 的行。

### 2.5 回调：两条锁，一次交换

`CallbackService.complete` 的顺序被刻意固定（`apps/api/app/service/identity/callback.py:134`–`:171`）：先看有没有外部 provider（没有 → 501，`:142`–`:148`），再验 state（`:149`），再看 code（`:150`–`:155`），再换身份（`:156`–`:169`），再映射用户（`:170`），最后 `302` 回 `HE_WEB_BASE_URL`（`:171`）。

state 是两道锁：`CallbackStateStore.issue` 生成 HS256 JWT，载荷只有 `typ=state`、24 字节随机 `nonce`、`iat`、`exp=now+600`（`:57`–`:69`）；`verify` 要求查询串的 state 与 cookie 逐字节相等（`hmac.compare_digest`，`:77`），再验签与过期（`:79`–`:89`），任何一类失败都收成同一个 400 `AUTH_STATE_INVALID`（`:91`–`:98`）。实测确认：`exp` 由 PyJWT 自动校验，缺 `typ` 会抛 `MissingRequiredClaimError`；非 ASCII 的 state 若直接进 `compare_digest` 会抛 `TypeError`，`:75` 的 `isascii()` 守卫是必需的，不是装饰；同一个 state JWT 拿去当 Bearer 会被 `TokenService.decode_access_token` 的 `typ` 检查拒掉（返回 `AUTH_REQUIRED`），不存在 typ 混淆。

HTTP 适配层只做三件事（`apps/api/app/api/auth.py:114`–`:134`）：把 `code`/`state`/`cookie` 交给服务、把 refresh cookie 按既有约定写入（`set_refresh_cookie`，`:126`）、成功后清掉 state cookie（`:127`–`:133`）。注意：服务返回的 `AuthenticationResult.access_token` 在这里被丢弃，前端拿到 302 后要照常调 `POST /api/auth/refresh` 换 access——与“刷新/重进页面以 refresh 为准”的既有契约一致，代价是多签一次 JWT。

### 2.6 装配与配置：预留旋钮

`config.py` 新增一个封闭枚举 `AuthProviderName`（`:60`–`:64`）和六个字段（`:125`–`:130`）。`HE_SESSION_COOKIE_NAME` 用 RFC 6265 token 字符集校验（`:187`–`:192`），`HE_OIDC_ISSUER` 复用既有的 HTTP(S) URL 校验（`:195`–`:199`），`HE_OIDC_CLIENT_SECRET_ENV` 只允许环境变量名、拒绝任何像密钥的字面值（`:201`–`:210`）——这是“secret 只存引用名”的执行点。`oidc_configured` 把三个开关聚成一个布尔（`:246`–`:249`），但目前没有任何消费者。

对照设计 04 §9（:385–387）：`cookie`/`oidc` 是预留值、`HE_SESSION_*` 在 password 模式不读取、`HE_OIDC_*` 仅 oidc 模式必填——实现的字段、默认值、校验强度与设计一致；区别只在“预留字段当前不产生行为”，这是设计明说的。

### 2.7 公开路径与共享限流

callback 加进 `_PUBLIC_API_PATHS`（`apps/api/app/middleware/auth.py:12`–`:18`，回调在 `:16`），因此不带 Bearer 也能到路由；`docs/architecture.md:27` 同步了这句话。限流中间件把判断从单点改成集合（`apps/api/app/middleware/rate_limit.py:60`–`:64`），`GET /api/auth/callback` 与 `POST /api/auth/login` 共用同一个 `LoginRateLimiter`，键只有客户端 IP（`:65`–`:66`），窗口 10 次/60 秒，超限返回 429 + `Retry-After`（`:67`–`:73`）。

顺序上，限流中间件在 `AuthMiddleware` 之内（`apps/api/app/main.py:481`–`:482`，后加的在外层）：认证中间件先放行公开路径，限流再记账，所以“公开 + 限流”同时成立。实测：连续 10 次 `GET /api/auth/callback` 后，同一 IP 的第 11 次登录请求直接 429（`RATE_LIMITED`）——两个端点共享一个预算，这是设计 07 §8.2.1（:1242）“callback 纳入登录限流键”的直接后果。

### 2.8 唯一管理员的两道 if

`create_user` 先拒绝 `role == "admin"`（`apps/api/app/service/identity/service.py:141`–`:146`），再拒绝不在 `{admin, member}` 的值（`:147`–`:152`）。第二道在当前契约下不可达（`CreateUserRequest.role` 是 `Literal["admin","member"]`，见 `apps/api/app/service/identity/schemas.py:60`；而 admin 已被第一道拦掉），属于防御性冗余，见 §7。真正造管理员的地方只剩 `seed_admin_if_empty`（`service.py:36`–`:49`），且它只在 `users` 表为空时动手（`:38`）。测试 `test_only_the_seeded_administrator_can_hold_the_admin_role`（`test_auth_provider_seam.py:458`–`:501`）同时验证了“建第二个 admin 得 422 `ROLE_INVALID`”和“列表里 admin 只有一个”。

## §3 数据流走查

### 剧本 A：用户用密码登录（回归主线）

1. `POST /api/auth/login` 带 `{"username":"admin","password":"initial-password"}` → 中间件放行公开路径 → 限流记一次（`middleware/rate_limit.py:60`）。
2. 路由把密码交给 `IdentityService.login`（`api/auth.py:72`–`:75`）；`login` 不再自己查库，而是 `providers.password.authenticate(Credentials(...))`（`service.py:53`–`:55`）。
3. `PasswordProvider` 按用户名取行、`verify` argon2id、成功返回 `ProviderIdentity(PASSWORD, <user.id>)`（`password.py:28`–`:37`）。
4. `bridge.resolve` 用 `get_by_id` 再读一次用户行（`session_bridge.py:34`），判 `is_active`；停用则 403 `FORBIDDEN`。
5. `complete_login` 更新 `last_login_at` 并签 access/refresh（`:60`–`:63`）；路由写 refresh cookie、返回 `{accessToken, expiresIn, user}`（`api/auth.py:76`–`:81`）。
6. 误差：这一步比改动前多一次 `SELECT users WHERE id = ?`；密码错/用户不存在仍是一次 dummy 校验 + 401 `AUTH_INVALID`，耗时不因“用户是否存在”而分叉。

### 剧本 B：没有配 IdP 时的回调（生产默认路径）

1. 浏览器（或任何人）`GET /api/auth/callback?code=x&state=y` → 公开表放行 → 限流记一次（实测第 11 次 429）。
2. 路由调 `callback.complete`，`registry.external` 为 `None`，在验 state 之前直接 501 `AUTH_PROVIDER_NOT_CONFIGURED`（`callback.py:142`–`:148`）。
3. 响应是 JSON 错误信封，不建用户、不读 state cookie；测试断言 `users.count()` 不变（`test_auth_provider_seam.py:196`–`:215`）。
4. 这就是当前生产环境的全部行为：回调永远 501，`HE_AUTH_PROVIDER` 改 `cookie`/`oidc` 则连启动都过不了。占位语义清晰，代价是“回调路径在真接入前不可用”。

### 剧本 C：注入 provider 后的回调矩阵（测试与探针实测）

| 输入（按判定顺序） | 输出 |
|---|---|
| 无外部 provider | 501 `AUTH_PROVIDER_NOT_CONFIGURED`（不碰 state） |
| 有 provider，缺 state cookie | 400 `AUTH_STATE_INVALID` |
| state 与 cookie 不相等 / 非 JWT / 非 ASCII | 400 `AUTH_STATE_INVALID` |
| state 过期（`exp` 已过） | 400 `AUTH_STATE_INVALID` |
| 有 provider + 有效 state，缺 code | 401 `AUTH_INVALID` |
| provider 返回 `None`（拒绝 code） | 401 `AUTH_INVALID` |
| provider 抛 `AuthProviderError` | 502 `AUTH_PROVIDER_ERROR` |
| 身份有效但 `(oidc, sub)` 无映射 | 403 `AUTH_NO_MAPPING`，用户数不变 |
| 映射到停用账号 | 403 `FORBIDDEN` |
| 映射到启用账号 | 302 到 `HE_WEB_BASE_URL`，Set-Cookie refresh + 删除 state cookie，`last_login_at` 更新 |

本机探针补充确认了成功分支的完整输出：`location: https://harness.example`、`refresh_token=…; HttpOnly; Max-Age=1209600; Path=/api/auth; SameSite=strict`、以及一条 `he_oidc_state=""; Max-Age=0; Path=/api/auth; SameSite=lax`。

### 剧本 D：限流预算被共享

1. 同一 IP 连打 10 次 `GET /api/auth/callback` → 10 次 501，预算用满（`rate_limit.py:40`–`:43`）。
2. 此时 `POST /api/auth/login`（正确密码）→ 429 `RATE_LIMITED`，`Retry-After` 为窗口剩余秒数（实测）。
3. 相反方向同样成立：10 次登录尝试后，回调请求会先被 429，到不了路由。
4. 这是“一个预算两个入口”的必然结果；改动前攻击者也能用 10 次空登录锁住 IP，所以不构成新增攻击面，只是把“共享”从隐式变成显式（见 §6.5 的方法维度问题）。

## §6 讨论点

> 每条给预判不给结论；结论栏留空，待维护者拍板。

### 6.1 state cookie 的契约缺 `path`，删除路径写死

- **位置**：`apps/api/app/service/identity/callback.py:125`–`:132`（`state_challenge()` 返回的字段）与 `apps/api/app/api/auth.py:127`–`:133`（删除时写死 `path="/api/auth"`）
- **现象**：`CallbackStateChallenge` 只带 `value/cookie_name/max_age/secure/samesite`，没有 `path`；回调成功删除 state cookie 时固定用 `/api/auth`。测试 helper 也只能手工补 `path="/api/auth"` 才与实现对齐（`apps/api/tests/identity/test_auth_provider_seam.py:79`–`:87`）。本机探针：把 state cookie 写在 `path="/"` 后走成功回调，响应里只有一条 `Path=/api/auth` 的删除头，浏览器不会删掉 `path="/"` 的那份（探针中 cookie jar 仍保留该 cookie）。
- **问题**：`state_challenge()` 是“交给未来写入方的契约”，但它没说明 cookie 该写在哪条路径；写入方若按 Starlette 默认（`path="/"`）落 cookie，回调成功后 state cookie 会残留到 10 分钟 TTL。写入与删除的路径知识分散在两个文件、两种字面量里，未来很容易配错而不自知（403/400 不会出现，只是 cookie 没清）。
- **预判**：把 `path` 加进 `CallbackStateChallenge`（或直接给 `set/clear` 一对方法），让写入方和回调共用同一个常量；顺手补一条“成功后浏览器真的删掉 cookie”的断言。当前没有生产写入方（`state_challenge()` 只被测试调用），所以无实害，属于下一 PR 落地前的契约收口。
- **结论**：2026-11-15 已修复。`CallbackStateChallenge` 增加 `path` 字段并固定为 `/api/auth`，写入与删除共用 `CALLBACK_STATE_PATH`；成功回调测试改为断言浏览器 cookie jar 中的 state cookie 真正消失。

### 6.2 `auth_provider` 不参与密码登录判定

- **位置**：`apps/api/app/service/identity/password.py:28`（只按 username 查）与 `apps/api/app/service/identity/session_bridge.py:33`–`:40`
- **现象**：本机探针把 seeded admin 的 `auth_provider` 改成 `oidc`、并映射了 `external_subject`，随后用初始密码 `POST /api/auth/login` 仍返回 200 和 access token。`auth_provider` 列只被外部身份的 `get_by_provider_subject` 读取（`crud/users.py:53`–`:56`）；`UserRecord` 甚至不携带这两列（`apps/api/app/db/models/users.py:51`–`:66`），密码路径在类型上就看不到它。
- **问题**：如果 `auth_provider` 的语义是“这个用户的身份来源/唯一允许的登录方式”，那么“外部映射用户仍可用本地密码”就绕过了 SSO 策略；如果它只是“这个用户是从哪个 IdP 导入的”，那当前行为没问题。设计 07 §8.2.1（:1236）的措辞“password 用户默认 provider=password……只回填映射”更像记录来源，但没有把语义写死。
- **预判**：先定语义再动代码。若定为“禁止混用”，在 `SessionBridge.resolve` 的 password 分支加一次 `user.auth_provider == PASSWORD` 判定即可（代价是 `UserRecord` 多两列或在仓储层暴露一个布尔），错误码沿用 401 以免泄露账号存在性；若定为“记录来源”，建议在 Agent Note 的 Decision 里明写“不限制登录方式”，避免下一轮重新讨论。当前没有管理入口能写这两列（只能改库），属潜在问题。
- **结论**：2026-11-15 已决定并落地。password 登录只接受 `auth_provider=password` 的账号；外部映射用户不能回退到本地密码，`SessionBridge` 与 `PasswordProvider` 双重校验，补了映射后密码登录 401 的回归测试。

### 6.3 state 复用 `HE_JWT_SECRET`，且不是一次性

- **位置**：`apps/api/app/service/identity/callback.py:116`–`:118`（`CallbackStateStore(settings.jwt_secret.get_secret_value())`）、`:57`–`:69`（签发）、`:71`–`:98`（校验）
- **现象**：state 是 HS256 JWT，签名密钥与 access/refresh 完全同一把；state 值出现在回调 URL 查询串里（浏览器历史、反代访问日志、Referer 都可能记录）。校验只做“签名有效 + 未过期 + 与 cookie 相等”，nonce 不落任何存储，因此同一份 state 在 10 分钟内理论上可重放（实际被 IdP 的一次性 authorization code 挡住，但那是外部保证）。另一个已确认的边界：typ 隔离成立，state JWT 当 Bearer 使用会被拒（`AUTH_REQUIRED`）。
- **问题**：(a) 将来真正开放登录跳转端点后，任何拿到一份 state JWT 的人都能拿它做 HS256 已知明文的离线爆破；`HE_JWT_SECRET` 目前只要求非空（`config.py:153`–`:157` 的 `require_jwt_secret`），弱密钥会直接威胁 access token 的签发权。(b) “state 一次性”依赖外部 IdP 的 code 语义，不是本服务自己保证的。
- **预判**：当前无生产签发方（`state_challenge()` 只被测试调用，且无 provider 时回调在验 state 前就 501），无实害。接入跳转端点时建议二选一：给 state 派生独立密钥（如 `HMAC(secret, "state")`）并把“≥32 字节”纳入 Settings 校验；或把 nonce 放进短 TTL 的一次性集合。属于下一 PR 的安全设计点，现在写进 Note 的 Consequences 比之后补更省事。
- **结论**：2026-11-15 已处理。state 使用从 `HE_JWT_SECRET` 派生的独立签名键，降低跨用途密钥复用风险；一次性仍依赖 IdP 的 authorization code，已写入 Agent Note 的 Consequences，接真实 provider 前复核。

### 6.4 设计写“sub/email 匹配”，实现只按 sub

- **位置**：`apps/api/app/service/identity/session_bridge.py:42`–`:45`；对照设计 `plans/fullstack-design/07-backend-implementation.md:1226` 与 `05-api-design.md:1315`
- **现象**：`ProviderIdentity.email` 被定义（`providers.py:27`–`:33`）也由测试塞了值（`test_auth_provider_seam.py:254`–`:256`），但桥只查 `(auth_provider, external_subject)`；email 从未参与映射。设计两处写的是“sub/email 匹配”，05 §8 错误码表也写“按 sub/email 匹配不到用户”。
- **问题**：实现与设计文本不一致，读者按设计实现或排障时会找错方向；更关键的是“按 email 自动关联本地账号”本身有安全争议——邮箱未验证或被 IdP 侧篡改时，等于把账号接管能力交给 IdP 的 email 字段。
- **预判**：只按 sub 是更安全的默认，建议保留实现、改设计措辞（把 email 标为“仅展示/审计，不参与匹配”），并在 Agent Note 的 Decision 里显式加一句“不按 email 自动关联”。若确实需要 email 兜底，必须同时要求 `email_verified` 且限定企业域名，作为独立决策记录。
- **结论**：2026-11-15 已修正设计措辞。07 §8.2.1、05 §4.16/§8、09 §4 与设计 README 统一为“按 sub 匹配，email 仅展示、不参与自动关联”；实现保持只按 sub，避免未验证邮箱导致账号接管。

### 6.5 限流键是 `(method, path)`，POST 回调绕过限流

- **位置**：`apps/api/app/middleware/rate_limit.py:60`–`:64`
- **现象**：只有 `("GET", "/api/auth/callback")` 会进限流。本机探针：连续 12 次 `POST /api/auth/callback` 全部 405 `METHOD_NOT_ALLOWED`，第 11 次也没有 429；同一窗口内 `GET` 第 11 次是 429。另有一条已被测试固化的行为：`GET` 回调与登录共享同一 IP 预算（10 次回调后登录 429）。
- **问题**：如果将来接入的 IdP 使用 `form_post` 响应模式（POST 回调），新路由要么先撞 405、要么在放宽方法后静默绕过限流；限流键把方法写死，扩展点是一个容易漏的字符串集合。
- **预判**：本轮只有 GET 回调，无实害；接入 provider 时把判定改成“路径属于认证尝试”（忽略方法）或显式补 POST 分支，并把共享预算的取舍写进设计。顺带确认一下“callback 与 login 共享预算”在 NAT 场景下是否可接受（办公网多人共用出口 IP 时，10 次回调会让登录排队），这是设计 07 §8.2.1（:1242）的既定选择，不是实现偏差。
- **结论**：2026-11-15 已修复。回调限流改为按路径判定、忽略 HTTP 方法，POST 回调同样消耗登录预算；补了 10 次 405 后第 11 次 429 的测试。

### 6.6 `POST /api/users` 的 422 描述没有跟上新语义

- **位置**：`apps/api/app/api/users.py:35`；生成物 `packages/contracts/openapi.json` 中 `/api/users` POST 的 422 描述
- **现象**：该 422 仍写 “Request validation failed”，但本 PR 让同一状态码多了 `ROLE_INVALID` 业务错误（`service.py:141`–`:146`，测试 `test_auth_provider_seam.py:498`–`:499` 断言 422 + `ROLE_INVALID`）。OpenAPI 与生成类型的描述现在与真实语义不符。

- **预判**：一行改动即可：描述改为“请求校验失败或角色非法（`ROLE_INVALID`）”，重跑 `pnpm contract:generate`，`test_openapi` 无需改。无行为风险，建议在本 PR 收口（否则生成物会一直带着旧描述）。
- **结论**：2026-11-15 已修复。`POST /api/users` 的 422 描述改为“请求校验失败或角色非法”，并重新生成 OpenAPI/TS 契约。

## §9 文件级代码分析

### 9.1 `apps/api/app/service/identity/providers.py`（A）

职责：把“验证身份”抽象成一张协议，并提供启动期的唯一选择点。

新代码的核心是三个小类型 + 一个注册表：

```python
@dataclass(frozen=True, slots=True)
class ProviderIdentity:
    provider: AuthProviderName
    subject: str
    email: str | None = None

class AuthProvider(Protocol):
    name: AuthProviderName
    async def authenticate(self, credentials: Credentials) -> ProviderIdentity | None: ...

@classmethod
def from_settings(cls, settings: Settings, users: UserRepository) -> "ProviderRegistry":
    if settings.auth_provider is AuthProviderName.PASSWORD:
        from app.service.identity.password import PasswordProvider
        return cls(password=PasswordProvider(users))
    raise AuthProviderConfigurationError(...)
```

为什么这么写：协议只留一个方法，未来的 Cookie/OIDC 提供方不需要知道用户表、token、HTTP；`Credentials` 是“所有 provider 入参的并集”，代价是每种 provider 只消费其中一部分字段（`code` 目前只给外部回调用）。`from_settings` 里延迟导入 `PasswordProvider`，避免 `password.py` ↔ `providers.py` 的循环导入（`password.py:8` 要导 `Credentials/ProviderIdentity`）。

### 9.4 `apps/api/app/service/identity/callback.py`（A）

职责：回调编排 + state 挑战，provider 无关。

旧代码：无。新代码的两段关键逻辑：

```python
def issue(self) -> str:
    now = int(self._clock())
    return jwt.encode({"typ": "state", "nonce": secrets.token_urlsafe(24),
                       "iat": now, "exp": now + self._ttl_seconds},
                      self._secret, algorithm="HS256")          # :60–:69

def verify(self, *, value, cookie) -> None:
    if not value or not cookie: raise self._invalid()
    if not value.isascii() or not cookie.isascii(): raise self._invalid()
    if not hmac.compare_digest(value, cookie): raise self._invalid()
    try:
        claims = jwt.decode(value, self._secret, algorithms=["HS256"],
                            options={"require": ["exp", "typ"]})
    except jwt.PyJWTError as exc: raise self._invalid() from exc
    if claims.get("typ") != "state" or not claims.get("nonce"): raise self._invalid()
```

为什么这么写：所有失败收成一个 `400 AUTH_STATE_INVALID`，攻击者无法区分“没带 cookie / 伪造 / 过期”，减少探测面；`isascii()` 是 `hmac.compare_digest` 的硬前提（实测非 ASCII 会抛 `TypeError`）；`options={"require": [...]}` 把 `typ` 缺失也变成 400，避免空载荷 JWT 混过。`CallbackStateChallenge`（`:26`–`:34`）是给未来写入方的“参数清单”，`samesite` 用 `Literal["lax"]` 锁死，防止有人把 state cookie 写成 Strict 导致跨站回调丢 cookie。

检视发现：契约缺 `path` 见 §6.1；密钥复用与一次性见 §6.3；`web_base_url` 为空时回退 `"/"`（`:171`）见 §6.7；`state_challenge()` 当前没有生产调用方（只被测试 `:218`–`:242` 使用），是本 PR 明确留下的钩子。
