## §2 架构导览

**页面壳与页头。** `RunDetail.vue` 仍是单文件页面，数据入口是 `useEvolutionRunDetail`（`RunDetail.vue:43-51`）。页头从“标题 + 状态 + 创建人 · 时间”改为“标题 + 状态 + 空间 badge”（`RunDetail.vue:521-533`）；空间名来自 `useAuthStore().workspaceById`，未加载时显示 `—`（`RunDetail.vue:273-275`）。这是“展示层只读现有会话数据”，不新增接口。

**infoPanel 的两类数据。** 统计数字仍在 `run.stats`（`sessions` / `badCases` / `potential` / `attributed` / `reused` / `byCategory`）。原型要求但 `run.stats` 没有的三个事实——策略/缓存开关、非该对象、本次新增——分别来自已经存在的 step payload：range step 的 `condition.policy` / `condition.cacheEnabled`，attribution step 的 `rows`（`category` 为空即非该对象，`source` 区分 cached / fresh；本次新增只计可归因的 fresh 行）（`RunDetail.vue:189-203`、`282-377`）。两个 step 查询与当前选中 step 共用 query key（`queryKeys.evolutionRunStep`），所以打开 range/attribution 步骤时不会重复请求；切到日志页签时不再请求（`activeTab === "steps"` 门控，`RunDetail.vue:190/196`）。

**工作区折叠。** 原来的 `workspace-panel` 独立 article 被删掉，`workspace-grid` 原样搬进 infoPanel 内 `<details data-testid="run-workspace">`（`RunDetail.vue:781-870`）。分支复制按钮、推送错误、本地路径的嵌套 details 都保留；流程进度 article 紧跟 infoPanel（`RunDetail.vue:881`）。

**分布图。** 类型条分母在完成态用 attribution rows 总数、未完成态用 `stats.potential`（`RunDetail.vue:373-377`），非该对象与「未归因」作为灰色段追加（`RunDetail.vue:346-371`）；图例保留 error/prompt/model，并补“＝ 归因 · 复用缓存 · 本次新增”（`RunDetail.vue:735-766`）。

**原型。** `evInfoPanel` 增加工作区折叠（`harness-evolution.html:5110/5143`），`evRenderDetail` 增加页签与空间 badge（`5423`），`evLogPanel` 提供日志页签内容（`5380-5410`），`EV-20261119-05` 提供准备中示例（`4943`）。原型的 `evDisplayModel` 在准备中时把统计归零（`4988`），`evStageActive` 把第 1 步置为 active（`5030` 附近）。

## §3 数据流走查

**完成态（`run-v2-completed`）。** 打开 `/workspaces/ws-default/evolution/runs/run-v2-completed` → `useEvolutionRunDetail` 拿 run shell 与七步 → `selectedKey` 默认最后一个 done（final）→ 并行请求 `steps/range` 与 `steps/attribution`（infoPanel 需要）→ infoPanel 用 `stats` + range condition + attribution rows 渲染 → 流程进度与 final 步骤产出。E2E 用 `compareDocumentPosition` 确认 info 在 progress 之前，且 `.workspace-panel` 不存在。

**准备中。** `run.status=preparing` → 页头 badge“准备中” → 七步详情无 ready step，`range` 为 active/clickable → infoPanel 显示 0 统计、策略/缓存、非该对象 `—` → 准备中文案 → 第 1 步内容。E2E 新增 `run-v2-preparing` 断言这些点。

**执行日志。** `?tab=logs` → `activeTab='logs'`，infoPanel 的 range/attribution 查询被门控关闭 → `RunLogPanel` 走原有 REST 分页与 SSE 逻辑。切回步骤时再请求 infoPanel 数据。

## §6 讨论点

### D1（已修）日志页签仍会为隐藏的 infoPanel 发两个 step 请求

- **位置**：`RunDetail.vue:189-203`。
- **现象**：range/attribution 查询只按 `clickable` 启用，没有看当前页签；`?tab=logs` 时 infoPanel 不渲染，但仍会请求两个 step。
- **问题**：日志页签是只读排障场景，多两个请求没有收益，且在慢网下会拖慢日志首屏。
- **预判**：应把两个查询限制在 `activeTab === "steps"`；日志页签不需要策略/缓存/非该对象。
- **结论**：本 PR 已修（2026-11-19）。`activeTab` 门控后，切回步骤时按需请求，query key 与选中 step 共享缓存；design doc §10.2 与 composable JSDoc 同步说明这两个 info 读取。

### D2（已修）新增准备中示例运行导致 `EV_RUNS[1]` 指向错位

- **位置**：原型 `harness-evolution.html:4970`。
- **现象**：原代码用 `EV_RUNS[1]` 把“无收益”示例改成全部拒绝；把准备中运行插到数组第 0 位后，`EV_RUNS[1]` 变成 `EV-20261109-01`，错误地改写了默认演示运行。
- **问题**：原型列表/详情会少一个“未产生收益”示例，且默认演示运行的 cluster 被错误改写；这是新增示例数据的连带回归。
- **预判**：用稳定 id 查目标 run，不用数组下标。
- **结论**：本 PR 已修（2026-11-19），改为 `EV_RUNS.find(r => r.id === 'EV-20261106-02')`；确认没有剩余 `EV_RUNS[<index>]` 访问，`#/run/EV-20261109-01` 深链仍可解析，向导创建的 run 也经 `evMakeRun` 获得 worktree。

### D3（已修）准备中示例仍保留按真实 window 算出的 cluster 数

- **位置**：原型 `harness-evolution.html:4935`。
- **现象**：`evMakeRun` 先按 window 算 clusters，准备中示例虽然把统计归零，但 `evTotal`/stepper 的「迭代优化（N 轮）」仍可能显示非零轮数。
- **问题**：准备中的页面不该出现已经算好的迭代轮数；当前示例窗口恰好是 0 轮，属于“碰巧正确”。
- **预判**：准备中时把 clusters 清空，让轮数与统计一致。
- **结论**：本 PR 已修（2026-11-19），`if (cfg.preparing) run.clusters = []`。

### D4（已修）归因未完成时“可归因/非该对象/复用缓存/本次新增”口径不一致

- **位置**：`RunDetail.vue:297-377`。
- **现象**：非该对象只在 attribution step `done` 时显示，但复用缓存/本次新增无条件读 summary，归因进行中会显示半截数字；同时分布条用 `stats.potential` 作分母，归因未完成时条会空一截。
- **问题**：同一个不完整快照里有的数显示、有的数隐藏，读起来像统计错误；分布条标题说 N 条，条却不满。
- **预判**：要么全按最终值门控，要么全按行级中间态显示，不能混。
- **结论**：本 PR 已修（2026-11-19）。归因未完成时复用缓存/本次新增显示 `—`，分布条追加灰色「未归因」余量（`pendingCount`）补满；归因完成后全部改为行级最终值。blocked-at-attribution 单测断言 `16 / —` 与「未归因 12」。

### D5（保留）关联 Session 仍显示「已关联 / 版本未知」

- **位置**：`RunDetail.vue:690-696`。
- **现象**：原型显示「5 / 7」（已关联/总数），生产契约只有 `sessions` 与 `versionUnresolvedSessions`，没有窗口内 Session 总数。
- **问题**：如果为了对齐原型新增 `sessionsTotal`，会违反 issue 的“不改 API 契约”。
- **预判**：保留现有两段口径，并在 PR/Note 里写明限制；不伪造总数。
- **结论**：保留（2026-11-19）。后续若产品确需总数，另开契约变更。

### D6（已修）「本次新增」改用原型公式（只计可归因 fresh 行）

- **位置**：`RunDetail.vue:356-372`。
- **现象**：原实现直接用 attribution summary 的 `fresh`，后端是 `potential - reused`，把 fresh 的非该对象行也算进“本次新增”；原型是 `attributed - reused`，只统计可归因行。
- **问题**：有 fresh 非该对象时“本次新增”会虚高；E2E 的 `run-v2-completed` 原断言 4（6−2）就是错的，按原型应为 3（5 个可归因中 2 个 cached）。
- **预判**：用已取回的 attribution rows 做行级统计，不新增接口。
- **结论**：本 PR 已修（2026-11-19）：`fresh = rows.filter(category !== null && source === "fresh").length`；E2E 断言改为「本次新增 3」，单测改为「本次新增 7」（16 个可归因中 9 个 cached）。

### D7（已修）「可归因 / 非该对象」在 legacy run 上会重复计数

- **位置**：`RunDetail.vue:306-327`。
- **现象**：原实现 “可归因” 用 `run.stats.attributed`，“非该对象” 用 summary.nonTarget；legacy 分支把 `attributed` 设成 `potential`，同时把 attribute_type 为空的 probe 计入 nonTarget，于是同一行会在两个数里各出现一次。
- **问题**：legacy run 的 `可归因 + 非该对象` 可能大于 potential，图例的“＝ 归因 N”也包含非该对象。
- **预判**：可归因与非该对象都从 attribution rows 的 `category` 是否为空推导，不混用 run.stats。
- **结论**：本 PR 已修（2026-11-19）。新增 legacy 单测：stats.attributed=3、rows 为 2 个有类别 + 1 个空类别时，显示 `2 / 1`，不再显示 `3 / 1`。

### D8（保留）类型条里非该对象排在最后

- **位置**：`RunDetail.vue:346-371`。
- **现象**：原型示例的图例顺序由 `Object.entries` 的首次出现顺序决定，不固定；生产把非该对象追加在 error/prompt/model 之后。
- **问题**：纯视觉顺序差异，不影响统计或可读性；强行按原型截图排序会把顺序绑到示例数据。
- **预判**：保留“类型在前、非该对象在后”的稳定顺序。
- **结论**：保留（2026-11-19）。如产品要求固定顺序，另开微调。

### D9（保留）roadmap 预算上调 870 → 900

- **位置**：`scripts/doc-budgets.manifest.json`。
- **现象**：新增 M21 milestone 必须增加一行 roadmap 序列和一行说明；main 的 roadmap 预算 930 装不下这一行，本 PR 提到 970，并登记 m21-milestone 预算。
