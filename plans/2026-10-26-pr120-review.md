## §1 一页速览

一句话：这个 PR 把“错误详情”从一个占位页变成可分享的三栏审案台——左边列出问题，中间只保留当前问题的执行流，下面按问题描述或归因分析解释证据。

一个比喻：页面像法庭案卷台。左栏是案卷目录，执行流是证据链，双 Tab 是“事发经过”和“归因结论”；URL 是案卷编号，刷新后仍能回到同一页。

## §2 架构导览

### 2.1 路由与 URL 是唯一选择状态

`/sessions/:sessionId/errors` 懒加载错误页，`/errors` 保留为无 Session 时的入口空态（`router/index.ts:27-30`、`:55-57`）。错误页从 `route.params` 与 `route.query` 派生 `case`、`tab`，没有另造可漂移的本地选择状态（`Index.vue:46-64`）。`parseSessionDeepLink(..., "error")` 只接受安全字符和长度范围，并将 `tab=attr` 规范化条件限定为“存在 case”（`deepLink.ts:147-197`）。

这样做的好处是浏览器刷新、前进后退和复制链接都走同一条路径；代价是每次切换都要经过 router push，组件必须容忍短暂的查询切换。

### 2.2 数据读取分成四条独立链

页面并行读取 Session 概要、执行流、问题列表；选中后再读取问题详情和分析状态，只有归因页签且状态为 `analyzed_issue` 才读取 probe（`Index.vue:66-89`）。这避免左栏为每个问题逐条发 probe 请求，也避免在问题描述页签提前拉归因正文。

查询键把 `badCaseId` 与 `sessionId` 一起编码（`queryKeys.ts:15-20`），从缓存层阻止同一 bad-case 在不同 Session 路由间复用。这是正确的数据隔离边界，尤其覆盖了“浏览器内先打开正确会话，再改 URL 到错误会话”的场景。

### 2.3 归属校验由后端作权威

前端把 `sessionId` 作为查询参数传给详情与分析接口（`badCases.ts:9-45`）。后端若发现 case 不属于该 Session，返回 `409 BAD_CASE_SESSION_MISMATCH`；页面将其提升为整页不可重试错误（`Index.vue:148-180`）。前端没有依据 ID 前缀猜归属，符合设计。

### 2.4 执行流过滤复用既有 AgentTree

`flowTree` 只过滤 `SessionTree.badCases`，保留 Agent/Skill 拓扑（`Index.vue:112-121`）；`flowProblems` 为画布提供与之一致的详情（`:122-126`）。“全部错误”删除 `case` 和 `tab`，两个 computed 随之恢复全图（`:206-211`）。选择问题时清空展开集，再由 anchor 的祖先链重新展开（`:197-204`、`:252-278`）。

### 2.5 Markdown 的信任边界

MarkdownIt 以 `html:false`、`breaks:true`、`linkify:true` 初始化，并对所有链接加 `target="_blank"`、`rel="noopener noreferrer"`（`markdown.ts:4-34`）。实测依赖为 `markdown-it@14.1.0`、MIT、6 个运行期依赖；其默认 `validateLink()` 拒绝 `javascript:`、`vbscript:`、`file:` 等协议。组件也只把 `probeAnalysis` 走 Markdown，`probeDescription` 保持纯文本和 `pre-wrap`（`AttributionReport.vue:158-174`）。

### 2.6 状态分层

页面级错误与组件级错误分开：

- 跨 Session 409、问题 404、非法 URL：整页错误，避免局部继续显示不可信详情（`Index.vue:148-180`）。
- 问题列表失败：只在左栏重试（`ErrorSidebar.vue:61-70`）。
- 执行流失败：只在图上重试（`Index.vue:374-380`）。
- 分析/probe 失败：只在归因区重试（`AttributionReport.vue:63-80`）。

## §3 数据流走查

以 URL `/sessions/S/errors?case=C&tab=attr` 为例：

1. Router 进入 error 路由；页面解析出 `sessionId=S`、`selectedBadCaseId=C`、`activeTab=attr`（`Index.vue:46-64`）。
2. 四个首屏查询同时开始；问题详情与分析请求附带 `sessionId=S`（`badCases.ts:9-45`）。
3. 左栏先用问题列表渲染全部卡片；详情返回后用 `detailQuery.data` 作为选中问题（`Index.vue:91-108`）。
4. 执行流先用 `C` 过滤树中 bad-case 节点，再把单问题详情传入 AgentTree（`Index.vue:112-126`）。点击画布问题卡同样调用 `selectBadCase()`，因此路由成为双向联动共同真值（`:197-204`、`:389`）。
5. 分析状态为 `analyzed_issue` 且页签为 attr 时，`probeId` 才从查询变为非空，触发 probe 请求（`Index.vue:83-89`）。
6. probe 返回后，归因组件渲染结论、分类/根因对象、问题描述、Markdown 推导和来源问题链接（`AttributionReport.vue:92-194`）。
7. 若后端判定 case 与 `S` 不符，详情或分析请求返回 409；页面不再渲染侧栏、流图或详情，只显示归属错误（`Index.vue:148-180`、`:308-316`）。
8. 用户点击“全部错误”后，router 生成无 query 的 canonical URL；选择状态归零，执行流恢复全量 bad-case 节点（`Index.vue:206-211`）。

## §6 讨论点

### D1 [Important] 归因信息在结论横幅和正文重复，破坏固定渲染顺序

**位置**：`apps/web/src/pages/errors/components/AttributionReport.vue:101-117`、`:120-156`。

**现象**：`analyzed_nonissue` 的 `result.reason` 在结论横幅显示一次（`:105-108`），紧接着“非问题的分析原因”又显示一次（`:120-128`）。`analyzed_issue` 的 `issueCategory` 与 `rootObject` 在结论横幅显示一次（`:114-117`），随后分类/根对象区再次显示同样内容（`:145-156`）。

**问题**：fullstack design §7.3 要求固定顺序是“结论 → 非问题原因或分类+根因对象 → 问题描述 → 推导 → 来源”；原型结论横幅只承担结论和状态，不重复正文（`plans/14-15-ui-prototype/harness-evolution.html:2024-2082`）。当前实现把第二步内容提前塞进第一步，页面更长、信息重复，也降低了与原型的一致性。现有测试反而把 `Explore @ v1.0.0` 出现在 `.conclusion` 固化成期望（`Index.test.ts:232-241`），会掩盖该偏差。

**预判**：应让结论横幅只保留 `结论 + 问题/非问题/未分析`；分类、根因对象、非问题原因只在下一条正文块出现。测试应断言这些文案在结论区内不存在且页面各只出现一次。

**结论**：—（待维护者拍板）

### D2 [Important] 真实 ID 的截短与新窗口深链交互未按设计与原型落地

**位置**：`apps/web/src/pages/errors/components/ProblemDescription.vue:30-36`、`apps/web/src/pages/errors/components/AttributionReport.vue:177-193`、`apps/web/src/components/bad-cases/BadCaseList.vue:101-133`。

**现象**：问题描述和来源问题均取 ID 前 12 位（`ProblemDescription.vue:35`、`AttributionReport.vue:190`），但同一页面左栏和画布取前 8 位（`BadCaseList.vue:118/131`、`agent-tree/layout.ts:507/545/567`）。问题描述 ID 是不可点击的 `span`；来源问题使用当前窗口的 `RouterLink`；左栏 ID 也包在整张选择按钮里，不能独立打开新窗口。

**问题**：ID 策略明确要求“UI 显示取前 8 位 + tooltip 展示全量”（`plans/fullstack-design/05-api-design.md:948`），review 指南要求真实 ID 点击深链使用新窗口、指定 tab（`plans/fullstack-design/09-review-guide.md:14-15`、`:44`）。原型中问题 ID 和归因 tab 报告入口均是 `target="_blank" rel="noopener"`（`plans/14-15-ui-prototype/harness-evolution.html:2000-2008`、`:2060-2066`）。当前行为既造成同页 ID 长度不一致，也无法从详情快速开新页对照。

**预判**：抽取统一的短 ID 展示函数固定为 8 位；ID 独立渲染为可访问链接，保留卡片主体的“选择/定位”点击，避免把 `<a>` 嵌套进 `<button>`；问题描述 ID 开 `desc`，归因报告/来源 ID 按目标 tab 开新窗口并加安全 `rel`。

**结论**：—（待维护者拍板）

### D3 [Nit] 问题描述标题和正文重复同一 `reason`

**位置**：`apps/web/src/pages/errors/components/ProblemDescription.vue:37-56`。

**现象**：标题行用 `problem.reason`（`:37-40`），正文第一段再次输出同一个字段（`:54-56`）。

**问题**：原型标题是短标题，正文是独立的 detail（`plans/14-15-ui-prototype/harness-evolution.html:2000-2021`）。API 没有独立 detail 字段，重复同一 reason 会让用户误以为有标题与说明两层信息。设计只要求展示 reason + metadata，未要求重复。

**预判**：保留标题区 reason，正文从 facts/关联对象开始；若需要强调原因，可由布局或摘要 chip 承担，而不是原文重复。

**结论**：—（待维护者拍板）

### D4 [Nit] 未分析空态文案偏离原型

**位置**：`apps/web/src/pages/errors/components/AttributionReport.vue:92-100`。

**现象**：当前结论横幅下写“外部归因系统尚未写入结果”；原型写“该错误还没有归因分析，尚不能判断是否为问题。”（`plans/14-15-ui-prototype/harness-evolution.html:2026-2034`）。

**问题**：两句话含义相近，但前者偏系统实现术语，后者更直接解释用户为何还看不到结论；在“严格按原型”的目标下属于可见文案差异。

**预判**：采用面向用户的“尚未分析/还不能判断是否为问题”文案，同时保留现有未分析状态 chip。

**结论**：—（待维护者拍板）

## §9 文件级代码分析

### 9.1 `apps/web/src/pages/errors/Index.vue`

职责是用 URL 派生选择状态并编排四条读链。主要变更从占位页变成完整工作台：新增 `useSessionBadCases/useSessionSummary/useSessionTree`、详情/分析/probe 查询、过滤树、祖先展开和两类错误边界。

关键点：

- `deepLink` 是唯一选择来源（`:49-64`），比多个 `ref` 互相监听更稳定。
- `flowTree` 只过滤 badCases，不重算 Agent/Skill 拓扑（`:112-121`），与设计“保留相关 agent 节点与触发点”一致。
- `routeFatalError` 将 409/404 提升为页级错误，避免局部组件继续消费不匹配数据（`:148-180`）。
- `watch([selectedProblem, sessionTree])` 自动展开 anchor 的祖先（`:252-278`），覆盖折叠节点中的问题卡。

风险与接受理由：

- Session/树自身的 404 仍落在各自组件错误态，而不是整页 Session-not-found；当前没有把 stale session URL 视为安全边界，不构成数据泄露，但视觉上会比 case 404 更碎片化。无实害，暂不阻塞。
- 页面有两处 `h1`（左栏“错误”和主区“错误详情”），与原型视觉一致，阅读器层级可后续统一。当前无功能实害。

### 9.2 `apps/web/src/pages/errors/components/AttributionReport.vue`

职责是把分析状态在三个互斥分支中展示。`analysis.status` 控制结论，`probe.attributeType` 控制模型/prompt/错误 tone 与标签，`probe` 只在 analyzed issue 下提供对象、描述和推导。

做得好的部分：

- `probeDescription` 保持纯文本，`probeAnalysis` 才走 Markdown（`:158-174`）。
- 来源链接用真实 `badCaseId` 构造错误详情 URL（`:181-190`）。
- probe 失败和分析失败分别落在独立 `ErrorState`（`:69-80`）。

设计偏差见 D1、D2、D4。另一个无实害点是内部来源链接也被 Markdown 的统一规则以外的方式渲染为普通 RouterLink，当前导航可用；改用新窗口后需同时加 `rel="noopener noreferrer"`。

### 9.3 `apps/web/src/pages/errors/components/ProblemDescription.vue`

职责是按原型阅读顺序展示问题身份、状态和事实。`badCaseFactEntries()` 把 metadata 限制为前三项并截断长值；上报对象区分主 Agent 与子 Agent ID。

实现思路正确：外部字段全部走 Vue 文本插值，没有 `v-html`。需要注意的偏差是 ID 取 12 位且不可点击（D2），以及 reason 标题/正文重复（D3）。

### 9.4 `apps/web/src/components/bad-cases/BadCaseList.vue`

本次为错误页增加 `compact` 模式：隐藏内部标题、卡片改为两行，活动色从红色改成蓝色，与错误详情原型的左栏选择语义一致。普通 Session 概览模式保持原结构。

列表活动状态仍通过 `aria-pressed` 暴露，滚动由 `scrollToProblem()` 在 active ID 变化后执行（`:39-55`）。缺点是把整张卡片做成按钮后，ID 无法成为独立的新窗口链接（D2）。若要同时保留卡片选择与 ID 深链，应将卡片拆成容器 + 独立选择按钮/ID 链接，不能嵌套交互元素。

### 9.5 API、composables 与 query keys

`ownedBadCasePath()` 对 badCaseId 编码，并在存在 Session 时追加 `sessionId`（`badCases.ts:9-17`）。详情和分析共享这一路径策略，减少归属参数漏传。

三个 query 的 enabled 条件都以 ID 非空为前提；probe 还允许外层增加 tab 条件（`useBadCases.ts:17-75`）。`queryKeys.badCase*` 将 `sessionId ?? "unscoped"` 纳入 key（`queryKeys.ts:15-18`），避免跨 Session 缓存串线。未发现 stale-data 或竞态问题。

### 9.6 Router 与 deep link

`/sessions/:sessionId/errors` 懒加载并受全局 auth/password guard 保护（`router/index.ts:27-30`、`:65-85`）。`/errors` 仍是顶层入口，无 Session 时显示选择提示。

deep-link parser 对 Session、case、agent、evidence、tab 的类型和长度做校验；canonical query 不保留无意义的 `tab=desc`，确保“全部错误”得到干净 URL（`deepLink.ts:147-197`）。没有发现 URL 注入或开放重定向问题。

### 9.7 Markdown 与依赖

新增依赖是 `markdown-it@14.1.0`（固定版本）与对应类型。实测其许可证为 MIT，运行期依赖为 `argparse/entities/linkify-it/mdurl/punycode.js/uc.micro`，都可在 Vite 构建期打包。

安全依赖面正确：`html:false` 阻断原始 HTML；默认 `validateLink()` 阻断 `javascript:`、`vbscript:`、`file:`；组件测试确认 `<img>`/`<script>` 不会原样输出。建议视为已满足设计的安全边界。

### 9.8 Session 概览入口

`SessionOverview.vue:196-204` 把原来的本地 CTA 变成 `/sessions/{sid}/errors` 的 `RouterLink`，与设计“只保留打开错误详情”一致。单元测试同时断言元素是 `<a>`、href 和文案（`pages/sessions/Index.test.ts:200-209`）。
