## §2 架构导览

### 2.1 为什么提示行链接比齿轮好：从"图标猜谜"到"文字直说"

旧齿轮按钮的全部可供性只有三个字号的属性：13px、`--text-faint` 灰、裸字符 `⚙`，无边框无底色（旧版样式，本 PR 已删）；提示文案还要求用户"点击齿轮前往配置页"，把动作对象指向一个视觉上几乎融进表单背景的图形字符（flow issue `m6-wizard-config-link.md:31-37` 的背景与现象段）。这不是审美问题，是任务链路断点：向导第一步的对象下拉只列**已配置且启用**的对象（`LaunchWizard.vue:93`），没配置过的用户看到空列表，「下一步」直接禁用（`LaunchWizard.vue:635`，`!selectedTarget` 即禁用）——此时唯一的出路就是那个找不到的齿轮，向导就卡死在第一步。

新入口的三个设计选择都有明确理由：

- **动作对象写进文案**：提示行现在是"未配置的进化对象不会出现在列表中；点击配置页前往。"（`LaunchWizard.vue:537`），可点的就是「配置页」三个字，认知路径最短——用户本来就是被告知"去配置页"，而不是被告知"去找齿轮"。
- **颜色借用全站已建立的语义**：`--blue` 在向导里已经是"可点/当前"色（步骤指示器 `LaunchWizard.vue:755-758`、报告 ID 链接 `.linklike :1000-1007` 同色），提示链接复用同一语言，不需要用户学新规则。
- **用原生 `button` 而非 `a`**：`type="button"` + `:focus-visible` outline（`LaunchWizard.vue:858-877`）——键盘 Tab 可达、焦点环可见，这是 `router-link`/`a` 之外的第三种合理选择，因为它触发的不是纯导航而是"关向导 + 导航"的组合动作（`goTargetConfig` 先 `emit("close")` 再 `router.push`，`LaunchWizard.vue:263-267`）。

### 2.2 失效链路为什么一行不用改：换的是"触发器"，不是数据边界

这是本 PR 最值得理解的设计判断。向导读的对象列表来自 catalog query（`LaunchWizard.vue:87`，key 为 `queryKeys.targetCatalog` = `["catalogs","targets"]`，`queryKeys.ts:33`）。配置页每次写入成功（新增/编辑/启停/删除）统一失效两个**父前缀** `["evolution","targets"]` 与 `["catalogs"]`（`useEvolutionTargets.ts:14-21`，三个 mutation 的 `onSuccess` 分别挂在 `:35`、`:45`、`:49`）。TanStack Query 的失效是前缀匹配：失效 `["catalogs"]` 会覆盖其下所有子键，包括向导在用的 `["catalogs","targets"]` 和模型列表 `["catalogs","models"]`（`queryKeys.ts:32-34`）；向导版本下拉用的 `["evolution","targets",id,"versions"]`（`queryKeys.ts:30-31`）同理被 `["evolution","targets"]` 覆盖。

于是"在配置页保存 → 返回 → 重开向导看到新对象"整条刷新链路完全活在写入侧，向导侧只需在挂载时正常发起 query——query 被 invalidate 标记为 stale，重开向导（组件重挂载）时自动重取。本 PR 把**触发这次跳转的 UI**从齿轮换成提示链接，跳转本身（`goTargetConfig`）一字未动，数据边界自然也不用动。设计文档同步时也只改了入口形态描述、保留"返回后失效语义不变"（`plans/fullstack-design/08-frontend-implementation.md:479`）。

### 2.3 `--blue-deep` 的来历：门禁把字面色赶进 token home

hover 想要的"加深"色在原型里写作字面色 `color-mix(in srgb, var(--blue) 72%, #000)`（`harness-evolution.html:618`）。但 `verify:web-style` 门禁禁止 `.vue` 文件出现字面色——`COLOR_PATTERN = /#[0-9a-f]{3,8}\b|rgba?\(/i` 会命中其中的 `#000`（`scripts/verify-web-style.mjs:4`），只有 `tokens.css` 被豁免（`:13`）。所以同一个 color-mix 必须收进 `tokens.css:12` 成为 `--blue-deep`，组件里引用 `var(--blue-deep)`（`LaunchWizard.vue:870`）。这不是新增一种颜色，而是给既有 hover 语义一个门禁合规的 home；命名与 `--blue` 相邻直白，当前全库唯一消费者就是这条链接（`--blue-deep` 仅出现两处：定义处与 `LaunchWizard.vue:870`）。

### 2.4 入口全景：向导内链接上线，页头齿轮去留未决

改动后"进配置页"共有两个入口：`/evolution` 页头的齿轮形 `RouterLink`（`TargetConfigEntry.vue:6-11`，本 PR **未动**）与向导第一步提示行链接。flow issue 明确把页头齿轮列为非目标："是否保留由后续反馈决定"（`m6-wizard-config-link.md:125`）；owning Note 的 Decision 段也把"最终入口"指向向导提示链接，页头齿轮只作为可发现性入口（`2026-10-27-target-config-ui.md:13`）。也就是说"页面上有两个入口、其中一个是齿轮"是**当前有意保留的现状**，不是遗漏。

## §3 数据流走查

端到端剧本（登录 → 开向导 → 点提示链接 → 配置对象 → 返回重开），每步带锚点：

1. **登录后进入 `/evolution`**。路由注册于 `router/index.ts:51-52`；页面头部并排放着齿轮形 `TargetConfigEntry`（`Index.vue:62`）和「＋ 启动自进化」按钮（`Index.vue:63-70`）。
2. **点「＋ 启动自进化」**，`wizardOpen = true`（`Index.vue:67`），`LaunchWizard` 挂载（`Index.vue:103-107`），第一步渲染对象类型分段、对象下拉、版本下拉（`LaunchWizard.vue:462-518`）。catalog query 同时发起（`:87`）。
3. **看提示行**。对象行下方是 `p.f-note`："未配置的进化对象不会出现在列表中；点击配置页前往。"，其中「配置页」是 `button.cfg-link`（`LaunchWizard.vue:536-543`）。两种现实场景：对象列表正常时它是旁路入口；catalog 请求 422（如本地 fixture 的假域名，§6-7）时下拉为空且无错误提示（模板只给 versions 配了错误块 `:520-535`，catalogs 没有），提示链接是唯一可走的出路。
4. **点「配置页」**。`goTargetConfig()` 先 `emit("close")`——父组件把 `wizardOpen` 置回 false（`Index.vue:105`）——再 `router.push("/evolution/targets")`（`LaunchWizard.vue:263-267`），路由落在配置页（`router/index.ts:63-64`）。键盘路径：Tab 聚焦出现 outline（`:874-877`），Enter 原生触发 click。
5. **配置对象**。新增/编辑成功后，写入 mutation 统一失效 `["evolution","targets"]` 与 `["catalogs"]`（`useEvolutionTargets.ts:14-21`）。
6. **返回重开**。回到 `/evolution` 再开向导，catalog query 重新挂载；因刚被失效，TanStack 自动重取，新对象出现在下拉里（`LaunchWizard.vue:87`、`:93`）。这条链路本 PR 零改动，见 §2.2。
7. **自动化证据**。E2E 把上述主线走了一遍：`pushState` 回 `/evolution` → 断言页头齿轮入口仍在（`m5-target-config.test.mjs:840-843`）→ 点 `open-launch-wizard`（`:844-847`）→ 等提示链接出现（`:848-852`）→ 点击（`:853-856`）→ 等落配置页并断言 `pathname === "/evolution/targets"`（`:857-865`）。组件单测则断言齿轮不存在、链接文案、close 事件与路由（`LaunchWizard.test.ts:120-136`）。

## §6 讨论点

### 6-1 [P2] 22 个脚本的 POSIX-only main 守卫：Windows 本地门禁全部静默假绿

**位置**：`scripts/` 下 22 个文件的 `if (import.meta.url === \`file://${process.argv[1]}\`)` 守卫（如 `verify-web-style.mjs:20`、`run-gates.mjs:66`、`verify-flow.mjs:129`、`verify-bundle.mjs:146` 等；另有 `contract.mjs:259`、`performance-report.mjs:73` 已用 `pathToFileURL(...).href` 安全写法，带守卫脚本合计 24 个）。

**现象**：实测本机 Windows——`node scripts/verify-web-style.mjs` 直接跑**无任何输出、exit 0**（守卫恒假：`import.meta.url` 是三斜杠正斜杠 URL，模板串拼出的是两斜杠反斜杠路径）；经 `.tmp/run-gate.mjs`（把 `argv[1]` 重写成三斜杠 URL，`run-gate.mjs:14`）才真正执行。也就是说 Windows 上 `pnpm verify:web-style`、`pnpm verify:docs` 等一律 exit 0 但什么都没验——本地"全绿"里有一批是假绿。CI 全部 `runs-on: ubuntu-latest`（如 `ci.yml:18`），守卫在 Linux 上成立，所以 CI 结果不受影响。

**问题**：`m6-windows-dev-entry`（m6-05，GitHub #118）当年就记录了这个守卫缺陷并承诺"另立 issue"，其非目标明确写着"不为 flow-new-issue.mjs / 其他 import.meta.url 入口判断做 Windows 兼容（另行立 issue）"（`m6-windows-dev-entry.md:25`、`:52`、`:83`），但至今没有任何 issue 落地（`.agents/flow/issues/` 下 Windows 相关只有这一个）。本地假绿会让人把"我在本地跑过门禁"当成验证证据——本 PR 描述里的 `pnpm verify:web-style：绿` 就属于这种无法自证的证据。

**预判**：兑现 m6-05 承诺，立一个 m6 process issue：统一把守卫改成 `import.meta.url === pathToFileURL(process.argv[1]).href`（仓库内已有两处范本），或抽一个公共 `isMain()` 工具；可顺带把 `.tmp/run-gate.mjs` 转正。工作量小、风险低（改守卫不改门禁逻辑，`pnpm test:gates` 兜底）。

**结论**：已决 2026-10-29——兑现 m6-05 承诺：本 PR 新建 flow issue m6-11（GitHub #163）承接守卫统一改造；守卫代码改动不入本 PR，避免门禁脚本改动与功能变更混车。

### 6-2 [P2] `verify-web-style.mjs:28` 在 Windows 上直接抛 `ERR_INVALID_URL_SCHEME`

**位置**：`scripts/verify-web-style.mjs:22-28`（`sourceRoot = new URL("../apps/web/src", import.meta.url)`；`readFile(new URL(path, sourceRoot), "utf8")`）。

**现象**：经 `.tmp/run-gate.mjs` 在 Windows 实测，主块执行到 `:28` 抛 `TypeError [ERR_INVALID_URL_SCHEME]: The URL must be of scheme file`（栈指向 `verify-web-style.mjs:28`）。根因：`readdir(recursive, withFileTypes)` 在 Windows 给出的 `entry.parentPath` 是带反斜杠的**绝对路径**（`D:\...\apps\web\src\pages\...`），拼进 `new URL(path, sourceRoot)` 后，以 `D:` 开头的字符串被 URL 解析器当成 `d:` 协议（单字母是合法 scheme），结果不是 `file:` URL，fs 拒绝。

**问题**：与 §6-1 同根但更糟一层：即便用 runner 修好入口，这个门禁脚本在 Windows 上依然跑不起来。目前它的实际保护范围 = 只在 CI（ubuntu）生效；Windows 开发者在本地改组件里的字面色时，`pnpm lint` 系（eslint）不查 CSS 字面色，唯一防线形同缺席。

**预判**：把 `:27-28` 改成 `pathToFileURL(path.join(entry.parentPath, entry.name))`（或 `resolve` 后再转 URL），一行修复；修法应并入 §6-1 的同一个 process issue，避免两个 PR 打架。

**结论**：已决 2026-10-29——并入 m6-11（GitHub #163）：修法为 pathToFileURL(path.join(entry.parentPath, entry.name)) 一行，随该 issue 落地。

### 6-3 [P3] eslint-disable 区间豁免，换取「点击配置页前往。」紧邻渲染

**位置**：`LaunchWizard.vue:537`（disable 注释）与 `:542`（enable 注释），豁免规则 `vue/multiline-html-element-content-newline`。

**现象**：该规则属于 eslint-plugin-vue 的 strongly-recommended 类（规则源码 meta `categories: ["vue3-strongly-recommended"]`，由 `eslint.config.js:9` 的 `pluginVue.configs["flat/recommended"]` 启用），要求多行元素的内容前后换行；`button` 不在规则默认豁免的 inline-non-void 清单里（实测 `eslint-plugin-vue/dist/utils/inline-non-void-elements.js`，36 个元素无 `button`）。若照规则换行写，@vue/compiler-dom 3.5.44 实测渲染输出会变成 `_createTextVNode("点击 ")` 与 `_createTextVNode(" 前往。")`——「配置页」两侧各多一个可见空格；紧邻写法则是无空格的 `"点击"`/`"前往。"`。所以这不是偷懒，是用一处区间豁免保住中文句内的排版正确性。

**问题**：豁免带着中文理由注释、范围收在单行模板区间内，属于规范用法；但它开了"本文件可以禁用模板排版规则"的先例，后续类似场景可能照抄而不权衡。

**预判**：可接受。若想更保守，可以把该禁用写成 eslint 配置里的按文件覆盖并附同样理由，但收益不大；不建议为规则妥协渲染出空格。

**结论**：已决 2026-10-29——接受区间豁免：中文理由注释+单行模板单点范围+仓库先例（AttributionReport.vue 等）；不为规则妥协渲染出空格，后续同类场景须个案权衡。

### 6-4 [P3] `--blue-deep` 新 token：门禁约束下的正解，命名与归位合理

**位置**：`tokens.css:12`（定义）、`LaunchWizard.vue:870`（唯一消费者）；原型对应字面色 `harness-evolution.html:618`。

**现象**：门禁 `verify-web-style` 只允许 `tokens.css` 持有字面色（`scripts/verify-web-style.mjs:4`、`:13-16`），hover 加深色里的 `#000` 在 `.vue` 里必红。PR 把原型 hover 值 `color-mix(in srgb, var(--blue) 72%, #000)` 原式收进 token home，组件引用 `var(--blue-deep)`，渲染值与原型逐字一致。

**问题**：唯一可议的是命名——`--blue-deep` 表达"hover 加深"靠约定而非语义（比如 `--blue-hover`），且目前全库只有一处消费者，有人会问为什么不用 `color-mix` 直接算在组件里（答案：门禁禁 `#000` 字面色）。

**预判**：归位正确（token home 是唯一合规去处）、命名可接受（与 `--blue` 相邻、直白）。属"无发现"级确认项，放进来是为了留档门禁约束的因果，供未来同类 hover 色照此办理。

**结论**：已决 2026-10-29——接受：token home 是唯一合规去处，命名与 --blue 相邻直白；留档门禁因果供未来同类 hover 色照此办理。

### 6-5 [P3] 应用 `.f-note`（margin 6px）与原型 `.wz-note`（margin-top 8px + line-height 1.55）的微差

**位置**：应用 `LaunchWizard.vue:813-816`（`.f-note { margin: 6px 0 0; font-size: 11.5px; }`，无 line-height）；原型 `harness-evolution.html:616`（`.wz-note { margin-top: 8px; …; line-height: 1.55; }`）。

**现象**：PR 描述称"应用 UI 与原型逐属性一致"——对链接本身（`.cfg-link`）成立（逐属性对照一致，含 hover）；但提示行**容器**用的是应用既有的共享类 `.f-note`，与原型新建的 `.wz-note` 差 2px margin-top 和一个 line-height。且 `.f-note` 是双消费者的共享类（对象行提示 `:536-543` 与"下一步"提示 `:590-592` 共用），原型 `.wz-note` 只对应前者；若硬改成 8px + 1.55 会波及第二处提示行。

**问题**：2px 与行高的差异在真实界面里几乎不可感知，但它使"逐属性一致"的表述不严格成立；检视者日后拿原型做像素对照时会撞上这处已知偏差，没有留档的话容易被当成回归。

**预判**：三选一——(a) 接受现状，在 owning Note 或本检视文档留档即可；(b) 应用侧给这一处提示行加独立修饰类对齐原型；(c) 反向改原型为 6px。倾向 (a)：复用共享类比像素一致更重要，原型 `.wz-note` 的 8px/1.55 更像原型自有的排版选择。

**结论**：已决 2026-10-29——采纳预判 (a)：接受现状并在本文档留档。.f-note 共享类服务两处提示行，复用优先于像素一致；2px+line-height 差异无实害。

### 6-6 [P3] `run-e2e --pattern` 匹配的是测试名：flow issue 里的命令会 "no tests matched"

**位置**：`scripts/run-e2e.mjs:13`（取第一个非 `-` 参数为 pattern）、`:16-18`（`testTitles()` 用正则从源码抽 `test()/it()` 标题）、`:29-35`（按"标题是否匹配"过滤文件，零命中直接 exit 2）、`:40`（透传 `--test-name-pattern`）；flow issue 两处写法 `m6-wizard-config-link.md:98`、`:119`。

**结论**：已决 2026-10-29——本 PR 修复：m6-10 中英两处命令改为 pnpm test:e2e --pattern "target config" 并重录 yaml；run-e2e 对文件名 pattern 的提示优化不做。

### 6-7 [P3] fixtures 假域名 `example.invalid` 使 `/api/catalogs/targets` 422、向导对象列表恒空（非本 PR 引入）

**结论**：已决 2026-10-29——仅记录不行动：既有设计事实，本 PR 未改变未恶化；种子域名与逐 target 容错两个方向留里程碑 backlog，由用户定优先级。

**结论**：已决 2026-10-29——无需行动：平台分支无 CI 覆盖是常态；若 m6-11 立项，顺带在正文登记"Windows 本机 e2e 冒烟"为该环境已知验证方式。（已登记：该句已写入 m6-11（GitHub #163）非目标段。）

## §9 文件级代码分析

### 9.1 `apps/web/src/pages/evolution/components/LaunchWizard.vue`

**职责与变更**：M；启动向导组件（两步弹窗）。本 PR 只动入口形态：删齿轮按钮与 `.gear` 样式，提示行内嵌 `button.cfg-link`，新增链接三态样式；`goTargetConfig()` 与其余约 1050 行零改动。

```vue
<!-- 旧（94c21f0）：对象下拉右侧的裸字符按钮，样式只有 13px 灰字 -->
```
