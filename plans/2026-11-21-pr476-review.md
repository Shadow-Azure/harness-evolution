## §1 一页速览

**一句话**：给每个本地 job 一张会过期的“酒店房卡”（租约 + 心跳），重启后沿着数据库里的“接力棒”（检查点）继续跑；如果推送其实已经到了远端，就先对账再决定是否真的失败。

交付块：

| 块 | 交付 |
|---|---|
| 租约 | `claim` 原子领取、`renew` 续租、`release` 清租；历史空租约按过期处理 |
| 重启恢复 | 残留 `running` → `interrupted` + `run_interrupted` + `job_recovered` → 同阶段重新入队 |
| 阶段恢复 | prepare 复用 workspace；advance 复用 candidate/eval；apply/final/retry 按现场事实继续 |
| 推送幂等 | 推送前落 workspace/push 目标；push 非零后 `ls-remote` 对账，远端等于目标即成功 |
| 停机 | 停止接单 → 有界等待 → 取消并释放租约；systemd 先 SIGTERM 主进程 |
| 可观测 | Git stderr 进 `error_detail`；UI 说明自动恢复并轮询；日志显示 `job_recovered` |

验证基线：本 PR 的 CI + 本地 `test:api` 103 项、`test:db` 21 项、`test:web`、`typecheck`、`lint:docs`、`verify:flow`、`contract:check`、`test:gates` 全绿；真实浏览器冒烟截图见 PR 描述。

## §2 架构导览

### 2.1 数据层：租约是“谁在跑”的唯一持久事实

`apps/api/app/db/models/jobs.py:49` 增加三列：`lease_owner`（实例/worker）、`lease_expires_at`、`heartbeat_at`，并在 `:56` 建 `(status, lease_expires_at)` 索引。迁移 `0025` 是幂等的：先反射列和索引，缺什么补什么（`apps/api/alembic/versions/0025_job_lease_heartbeat.py:47`），SQLite 走 `batch_alter_table`，MySQL 同样可加列/索引；历史行三列皆空，`claim` 把空租约视为过期。

`JobRepository.claim`（`apps/api/app/db/crud/jobs.py:184`）把“queued 或租约过期的 running”放进同一条 `UPDATE ... WHERE`，以 `rowcount == 1` 作为领取成功；`renew`（`:236`）只在 `status=running AND lease_owner=owner` 时续租；`release`（`:266`）只清租约、不改状态。`complete/fail/interrupt` 都通过 `_LEASE_CLEARED` 清租，避免终态行还挂着有效租约。

### 2.2 执行层：心跳与“有界排水”

`JobRunner._run`（`apps/api/app/service/jobs.py:279`）领取成功后启动心跳任务（`:393`）：每个 `heartbeat_seconds` 调一次 `renew`；续租失败说明本进程已不是 owner，直接取消本地 handler。handler 结束的 `finally` 会取消心跳并清掉 `_active_task`。

`JobRunner.recover`（`:125`）先 `mark_running_interrupted`，再对每个残留 job 写 `run_interrupted`；`sync` 保持“新 ref 重试”，evolution job 则用同 kind、同 payload 重新入队（`evolution_retry` 加 `recovery: true` 标记），并写 `job_recovered` 事件。这样恢复入口不需要在 runner 里知道七个阶段的业务细节。

`JobRunner.close`（`:254`）先置 `_closed` 停止接单，再只等当前持有全局锁的 handler，最多 `drain_timeout_seconds`；超时取消剩余任务，`_run` 的 `CancelledError` 分支把 job 标 `interrupted` 并释放租约。`main.py` 从 `Settings` 传入三个时间参数；systemd 单元用 `KillMode=mixed` + `TimeoutStopSec=45`（`deploy/harness-api.service:21`）保证主进程先收到 SIGTERM。

### 2.3 Git 层：推送前检查点 + 推送后对账

`GitWorkspaceManager.prepare_with_checkpoint`（`apps/api/app/third_party_api/git/workspace.py:181`）在 `validate_for_push` 之后、真正 push 之前调用一次回调。`EvolutionPrepareService` 的回调把 `repo_path/base_ref/base_commit/branch_name/workspace_path/push_repo_url` 写进 run（`apps/api/app/service/evolution/prepare.py:518`、`db/crud/evolution.py:324`），所以即使进程在 push 中被杀，下一次 prepare 也能从持久 workspace 继续。

`_push_run_branch`（`workspace.py:741`）先读远端 ref：已等于本地 HEAD 就直接返回，不再 push；push 返回非零时再读一次远端，等于 HEAD 就视为“server 收下了、client 被杀了”，否则抛原错误（`:805`）。`push_candidate`（`:353`）也做了同样的 tag 对账。`GitOperationError` 新增 `detail`，由 `_error_from_result` 填入脱敏后的 stderr，最终进入 blocked 事件的 `error_detail` 与 run 的 `error_message`。

### 2.4 阶段恢复：只重入能证明下一步的阶段

- prepare：`prepare.py:144` 把 interrupted 拉回 running；`_already_prepared` 与 `progress_unit` 保证已完成步骤不重跑。
- advance：`advance.py:109` 对 `patching/pushing` 优先 `repush_existing`，只有 candidate 检查点缺失才 `publish`；`evaluating` 只补交缺失的 eval id。
- apply/final：`apply_final.py` 在进入业务前 `mark_recovered`，随后仍按“round 已决策 / final 已落库”早返回。
- retry：`retry.py:271` 的 `_recover_running` 从 final、已评测未决策 round、活动 round、pending round 依次推导，复用既有 `_finalize/_apply/_republish_push/_schedule_next`。
- UI：`RunDetail.vue:589` 说明“系统将自动恢复”；`useEvolutionRunDetail.ts:39` 对 interrupted 每 5 秒轮询；`EventList.vue:37` 给 `job_recovered` 一个 ↩ 图标。

## §3 数据流走查：一次部署重启

1. 部署在 run 的 prepare/push 阶段重启。进程被 SIGTERM：`close` 停止接单，等 handler 到 drain 窗口；若 push 正在收尾，系统给 handler 一个窗口，超时则取消。job 行被 `interrupt` 标 `interrupted` 并清租。
2. 若进程被直接杀掉，job 行仍是 `running`；下次启动 `recover` 先把它标 `interrupted`。
3. `recover` 写 `run_interrupted` 事件，把 run 标 `interrupted`，再插入同 kind 的新 queued job，并写 `job_recovered`（payload 带 `previousJobId`）。
4. `start_queued` 调度新 job；handler 入口看到 `run.status == interrupted`，调 `mark_recovered` 回到 running。
5. prepare 复用 workspace 与已落库的 push 目标；`_push_run_branch` 先 `ls-remote`。远端已是目标 commit 就直接继续，不重复 push、不重复建分支。
6. 如果中断发生在 advance：`advance` 找到 `pushing` round，复用 `candidate_ref/candidate_commit` 走 `repush_existing`；如果 candidate 还没落库，才从 trace 重建。eval 已提交就复用，未提交才补交。
7. 如果中断发生在 apply/final：apply 从已完成的 eval 继续；final 从已落库的 final 行继续，最后再对账推送 run 分支。
8. UI：run 详情在 interrupted 时每 5 秒拉一次 REST；恢复后状态变 running，横幅消失，日志里留下 `job_recovered` 与恢复前的 `run_interrupted`。

## §6 讨论点

### D1：`record_recovered` 的事件与状态转移是两步

- 位置：`apps/api/app/service/evolution/events.py:400`、`prepare.py:144`
- 现象：`record_recovered` 只写事件，真正把 run 拉回 running 的是各阶段 handler 入口。
- 问题：如果 `record_recovered` 写事件失败，run 仍是 interrupted，但重新入队的 job 仍会跑；handler 的 `mark_recovered` 是兜底。反过来，如果 handler 一直没被调度，run 会保持 interrupted。
- 预判：这是有意的“先留证据、再在真正执行时改状态”；单实例串行 worker 下 queued job 会被 `start_queued` 调度，窗口很短。
- 结论：留空。

### D2：中断的 `evolution_retry` 只能从现场推导阶段

- 位置：`apps/api/app/service/evolution/retry.py:271`
- 现象：原 retry job 的 payload 只有 `runId/automatic`，恢复时没有显式 stage。
- 问题：`_recover_running` 用 final/round 状态推导，能覆盖 push/eval/apply/final；如果中断发生在 patch 生成中且 candidate 未落库，会走 `_regenerate_round` 重新生成。
- 预判：语义正确，代价是极端情况下可能多生成一次 patch；这是“不重复调用模型/评测”边界内可接受的。
- 结论：留空。

### D3：`claim` 已支持过期接管，但终结写入不校验 owner

- 位置：`apps/api/app/db/crud/jobs.py:184`、`:287` 附近
- 现象：`claim` 能接管过期 running 行；`complete/fail` 只按 job id 更新，不校验 `lease_owner`。
- 问题：多实例下旧 worker 若在租约过期后恢复执行并写入，可能覆盖新 owner 的终态。
- 预判：本 issue 明确单实例部署假设，多实例 leader election 不在范围；当前租约字段为后续演进保留。
- 结论：留空，等真正多实例化时补 owner 条件。

## §9 文件级代码分析

### 9.1 `apps/api/app/db/crud/jobs.py`

**职责**：job 行的全部持久化操作；本 PR 新增租约生命周期。变更形态：M。

**关键依赖**：SQLAlchemy 2.x Core `update/select`，通过 `Database.transaction()` 共享会话；不需要额外库。这里的“租约”就像共享办公桌的占座牌：坐下时写名字和到期时间，干活期间续时，走时把牌子拿走。

**旧代码**：

```python
async def claim(self, job_id: str) -> JobRunRecord:
    await session.execute(
        update(job_runs)
        .where(job_runs.c.id == job_id, job_runs.c.status == "queued")
        .values(status="running", started_at=now, attempt=job_runs.c.attempt + 1, updated_at=now)
    )
    claimed = await self.get(job_id)
    if claimed is None:
        raise RuntimeError("claimed job disappeared before execution")
    return claimed
```

**新代码**：

```python
result = await session.execute(
    update(job_runs)
    .where(
        job_runs.c.id == job_id,
        or_(
            job_runs.c.status == "queued",
            and_(
                job_runs.c.status == "running",
                or_(job_runs.c.lease_expires_at.is_(None), job_runs.c.lease_expires_at < now),
            ),
        ),
    )
    .values(status="running", ..., lease_owner=owner, lease_expires_at=now + lease, heartbeat_at=now)
)
if result.rowcount != 1:
    return None
```

**在做什么**：把“领取”和“接管过期 running”合成一条条件更新，用 `rowcount` 判定唯一赢家；返回 `None` 让 runner 安静退出，而不是抛“claimed job disappeared”。**为什么**：单实例启动恢复仍以 `mark_running_interrupted` 为主，但租约字段为未来多实例和异常检测保留，不应只做装饰。

**实现思路总结**：条件更新保证原子性；清租集中在 `_LEASE_CLEARED`，避免终态行残留有效期。

**检视发现**：`complete/fail` 不校验 owner，见 §6 D3；单实例范围内接受。

### 9.2 `apps/api/app/service/jobs.py`

**职责**：串行 worker、恢复、排水。变更形态：M。

**关键依赖**：`asyncio` 任务与 `asyncio.wait`；没有引入外部队列。心跳像“定时给前台打电话确认房间还在用”。

**旧代码**：

```python
async def close(self) -> None:
    self._closed = True
    for _job_id, task in list(self._tasks.items()):
        task.cancel()
    await asyncio.gather(..., return_exceptions=True)
```

**新代码**：

```python
self._draining = True
self._closed = True
try:
    await self._drain_and_cancel()
finally:
    self._draining = False
```

`submit()` 在 `_draining` 期间仍可落 queued 行，但不调度；这样 handler 在窗口内完成时，terminal hook 仍能把下一阶段写入队列，由下次启动的 `start_queued()` 接续。

**在做什么**：先只等持有全局锁的 handler，窗口外取消；启动恢复把可恢复 kind 重新入队，并写 `job_recovered`。**为什么**：部署不能在 SIGTERM 后无限等待，也不能把正在收尾的 push 直接砍掉；把阶段语义留给阶段 service，runner 只负责“同 kind 重排”。

**实现思路总结**：`_closed` 同时阻断新提交与调度；`_active_task` 区分“在跑”与“排队等锁”。

**检视发现**：若 `record_recovered` 失败，handler 的 `mark_recovered` 仍是兜底；见 §6 D1。

### 9.3 `apps/api/app/third_party_api/git/workspace.py`

**职责**：隔离 workspace、candidate、run branch 发布。变更形态：M。

**关键依赖**：`git` 子进程；`remote_ref_commit` 用 `ls-remote` 只读对账。像寄快递：快递员说“失败了”，但先查一下收件人其实已签收，就不重复寄。

**旧代码**：

```python
remote_commit = await self.remote_ref_commit(...)
head = ...
if remote_commit is not None and remote_commit != head:
    ...  # 只处理非快进
await self._push_checked(workspace_path, ("git", "push", remote, f"{head}:refs/heads/{branch}"))
```

**新代码**：

```python
if remote_commit == head:
    return
...
try:
    await self._push_checked(...)
except GitOperationError as exc:
    if await self._remote_branch_matches(workspace_path, remote, branch, head):
        return
    raise exc
```

**在做什么**：push 前 already-up-to-date 直接返回；push 非零后只读对账一次，命中才吞错。**为什么**：这正是事故形态（远端已写入、client 被杀），但真实 403/非快进不能被吞掉。

**实现思路总结**：对账只读、只比较精确 commit；失败仍抛原错误并带脱敏 stderr。

**检视发现**：`_remote_branch_matches` 在对账查询自身失败时返回 False，从而保留原错误，不会把网络错误误判成成功；正确。

### 9.4 `apps/api/app/service/evolution/advance.py`

**职责**：推进一轮 candidate；本 PR 增加中断恢复。变更形态：M。

**旧代码**：首个非终态 round 只要不是 `pending` 就返回 no-op（`earlier round is pushing`），恢复后 run 会卡住。

**新代码**：`patching/pushing` 走 `repush_existing`（有 candidate）或 `publish`（无 candidate）；`evaluating` 只补交缺失 eval id。

**在做什么**：把“同一个 round 的现场”当成幂等键；已提交 candidate 不重新 commit，已提交 eval 不重复 submit。**为什么**：issue 要求“不重复调用模型或评测”，而 round 状态就是最可靠的持久键。

**实现思路总结**：先读 round.status，再选唯一动作；`_trace` 只在需要重建 candidate 时使用。

**检视发现**：`pushing` 分支会先重建 trace 再判断是否真的需要，属于可忽略的计算浪费；无功能影响。

### 9.5 UI：`RunDetail.vue` + `useEvolutionRunDetail.ts`

**旧**：中断 banner 只说“可查看最后事件”；interrupted 不轮询，恢复后页面不会自己回来。
**新**：banner 说明“系统将自动恢复”；interrupted 每 5 秒轮询；日志给 `job_recovered` 图标。

**为什么**：后端现在会自己恢复，前端不能继续把 interrupted 当永久终态。轮询是 SSE 在中断后被关闭的兜底。

**检视发现**：UI 只在 interrupted 状态显示“将自动恢复”；如果 recovery job 长时间排队，文案仍然成立（尚未开始执行），没有误导。

## §10 检视修复轮

首轮结构化检视和独立复检发现 7 个需要修的实际缺陷，已全部在本 PR 内修复并补回归测试：

1. **排水期无法排下一阶段**（高）：`close()` 先置 `_closed`，handler 在窗口内完成时 terminal hook 的 `submit` 被拒，prepare 完成后 run 会停在 running 且没有后续 job。修法：增加 `_draining`，排水期 `submit` 只落 queued、不调度，重启后由 `start_queued` 接续；新增 `test_drain_allows_terminal_hook_to_queue_followup`。
2. **心跳误杀终态写入**（高）：`fail()` 清租后 `renew()` 返回 False，下一次心跳会取消仍在写 blocked 事件的 handler。修法：续租失败先重读 job，终态安静返回，只有另一个 owner 持有 running 行才取消；新增 `test_heartbeat_does_not_cancel_terminal_bookkeeping`。
3. **租约接管后旧 worker 覆盖终态**（高，多实例）：`complete/fail/interrupt` 增加可选 `owner` 条件，runner 传入自己的 owner；新增 `test_terminal_writes_are_owner_scoped`。
4. **eval retry 恢复复用陈旧 external id**（高）：round 仍是 evaluating、`eval_status=failed` 或 poll 截止为空时，恢复会把 stale round reset 后重新 submit。修法：`retry._stale_eval_round` 与 `advance` 的 evaluating 分支共用同一判断；新增 `test_stale_evaluating_round_is_reset_and_resubmitted`。
5. **patching 恢复遇到脏 workspace**（中）：崩溃可能留下 candidate 分支、已 stage 的 patch 或未跟踪文件，`create_candidate` 的 `_require_clean` 会把它变成 failed。修法：恢复路径 `reset_workspace=True`，先 `git switch --force` 回 run 分支并 `git clean -fd`；新增 `test_candidate_resume_resets_a_half_finished_workspace`。
6. **重推失败丢 stderr**（中）：`_handle_git_failure` 的 `RunBlocked` 没带 `detail`。修法：透传 `error.detail`，由 job 层写进 `run_blocked` 的 `error_detail` 与 run 的 `error_message`。
7. **单个恢复事件失败中断整轮 recover**（中）：`recover()` 的 interruption/terminal/requeue 已拆成独立 try/except；事件写失败仍会落 queued 行。新增 `test_recovery_isolates_a_failing_event_write`。

未修的低风险项：终态 run 的残留 running job 仍可能被插一条同阶段 queued 行，后续 handler 会安全 no-op；只有审计噪声和 attempt 递增，没有卡死路径。多实例真正并发仍不在本 issue 范围。

修复后重新执行：`tests/bugfix-11-durable-jobs`（12 项）、`tests/bugfix-11-prepare-resume`（10 项）、`tests/m5-11-evolution-recovery`、`typecheck:api`、`lint:api` 全绿。
