## 1. 一页速览

一句话：把“平台返回什么 verdict 就信什么”改成“平台只报测量值，HE 自己拿基线做严格更优判定”，并让基线、逐轮候选和测试集终评共用同一条 durable 轮询链路。

比喻：平台像体温计，只报度数；这个 PR 把“是否发烧”的判断从体温计厂商手里收回，改由医生按同一个体温计读数与就诊时基线比较。

## 2. 架构导览

### 2.1 选择层

`EvalGatewayFactory`（`apps/api/app/third_party_api/eval_gateway/factory.py:34`）在构造时注册 `fake` 与 `ai-eval-platform`；`create`（`:75`）先看 run 快照的 `mode`，再回退 `HE_EVAL_MODE`，未知值抛 `EvalGatewayConfigError`。`config.py` 的 `eval_mode` 校验从同一注册表取合法值，避免“settings 允许但工厂不认识”。

`BaseEvalGateway`（`base.py:46`）把 Bearer 头、30s 超时、JSON 解析、4xx/5xx 分类收在一处；平台子类只实现 `submit`/`get_status`/`get_result`。错误消息带 HTTP 状态和平台错误码，但保留 `retryable` 与 `platform_code` 两个结构化字段供 poller 消费。

### 2.2 平台适配

`AiEvalPlatformGateway`（`ai_eval_platform.py:41`）的 `submit`（`:50`）把候选 commit、ref、subDir/asset_types 与 lineage 映射到平台 `asset_override`；提交后断言 `asset.resolved_commit` 等于候选 commit。`get_status`（`:97`）把 11 态折到 HE 5 态；`partial` 低于 50% 完成率判失败，`paused_budget` 直接失败。`get_result`（`:130`）只返回 `EvalMeasurement`，主指标缺失时显式失败而不是当 0 分。

### 2.3 存储与轮询

新表 `evolution_evaluations`（`db/models/evolution.py:309`）用 `UNIQUE(run_id, kind)` 保证每种运行级评测一行；`ensure_run_evaluation`（`db/crud/evolution.py:1644`）幂等创建，`save_run_eval_result`（`:1802`）只写一次完成态。poller 的 `_poll_run_evaluation`（`eval_poller.py:656`）与轮次轮询同构，可重试错误只推迟 `next_poll_at`，最终失败统一 `blocked(stage=eval)`。

### 2.4 裁决与终评

`gate_measurement`（`eval_gate.py:29`）只做三件事：校验有限分数、按方向调用 `strictly_better`（`:63`）、把基线分与候选分装进 `EvalResult`。`EvolutionApplyService._validation_baseline`（`apply_final.py:166`）先找最近已接纳轮，再回退验证集基线；基线未完成时 apply 返回未应用，不提前裁决。`_test_final_values`（`:494`）用测试集基线与终评分别写 `init_score`/`best_score`，并把主指标投影成前端 `{name, init, best, delta}` 行。

## 3. 数据流走查

1. 管理员保存 target：`primary_metric_key` 经 `_validate_primary_metric_key` 校验后入库。
2. 启动 run：`_snapshot_eval` 把两个模板 ID、主指标 key、subDir 写入 `eval_config`；真实模式缺字段返回 422。
3. `evolution_advance` 在发布第 1 轮前调用 `submit_baselines`（`eval_poller.py:173`），两条基线各自拿独立幂等键。
4. 第 1 轮 candidate 发布并提交；poller 同时轮询三条评测。验证集基线完成后，apply 才按基线裁决。
5. 接纳 -> run 分支快进、基线顺延；拒绝 -> run 分支不动、基线不动。
6. 所有轮次终态后，finalize 调用 `submit_test_final`（`:185`）；测试集终评完成后写 `evolution_finals`，并在 `StepFinal` 显示“测试集对比”。

## 6. 讨论点

### 6.1 `partial` 最低完成率阈值固定 50%

- 位置：`apps/api/app/third_party_api/eval_gateway/ai_eval_platform.py:33`
- 现象：`PARTIAL_MIN_COMPLETION_PERCENT = 50` 是常量。
- 问题：不同数据集对“可消费的部分结果”容忍度不同；50% 是 issue P3 的默认值，不是平台契约。
- 预判：第一期按默认值落地可接受；真实评测后若 partial 误判，再提升为对象级或环境级配置。
- 结论：留待需求方在真实运行后拍板。

### 6.2 幂等键的 attempt 语义

- 位置：`apps/api/app/service/evolution/eval_poller.py:73`、`:219`
- 现象：`eval_attempts` 只在平台返回 202 后递增；传输失败（丢弃响应）时保持原值，`/retry` 复用同一个 `Idempotency-Key`。确认平台终态失败后再重试才会递增到新键。
- 问题：若把传输重试也当成新 attempt，平台已创建 run 但 202 丢失时会被重复评测；反过来若终态失败也复用旧键，平台可能拒绝或重放旧结果。
- 预判：当前实现按“已接受提交计数”区分两者；新增 `test_submission_attempts.py` 覆盖“丢响应复用键”与“确认失败换新键”两个负例。
- 结论：符合 issue 讨论与平台幂等契约；若平台不能幂等重试，应在平台侧错误码上显式判未知，而不是本地推断未创建。

### 6.3 `HE_GIT_PUSH=false` 时仍会提交基线

- 位置：`apps/api/app/service/evolution/eval_poller.py:173`
- 现象：`submit_baselines` 只检查 mode/status，不检查 push 是否能发生；dev 关闭 push 时会多花两次平台调用（真实平台可能计费）。
- 问题：基线对不评测的 run 没有决策价值。
- 预判：可接受；`HE_GIT_PUSH=false` 是本地开发配置，默认 CI/fake 不产生真实费用。
- 结论：留作后续优化，未在本 PR 扩 scope。

## 9. 文件级分析

### `eval_gate.py`

职责：平台无关的严格更优门控。变更形态：A。关键依赖：无第三方包，仅 `math` 与 contracts。旧代码把 `external_verdict == "accept"` 当结论；新代码只接收 `EvalMeasurement` 与基线分，按 `direction` 比较，平票拒绝。实现思路：把“比较”与“落库结构”放在同一函数，避免 apply 与 final 各写一套。

### `eval_poller.py`

职责：轮次与运行级评测的统一 durable 轮询。变更形态：M。新增 `submit_baselines`/`submit_test_final`/`_poll_run_evaluation`；`run_once` 先处理运行级评测，再处理轮次 follow-up，最后做 run 级终态扫描。关键依赖：`EvolutionRepository` 的行锁与 `EvalGateway` 接口。风险：基线失败与轮次失败共用 `blocked(stage=eval)`，错误信息必须能区分；当前用 `kind` 与平台码区分。

### `apply_final.py`

职责：把评测结果变成 git 结论与终评行。变更形态：M。`_validation_baseline` 优先已接纳轮、再回退验证集基线；legacy payload 仍按 `externalVerdict` 兼容。`_test_final_values` 输出前端可读的单行主指标对比。风险：`best_score` 语义从“各轮最高验证分”变为“测试集终评分”，需要需求方知悉。

### `TargetFormDialog.vue` / `TargetTable.vue`

职责：对象配置表单与列表。变更形态：M。新字段与两个工程 ID 同组、单行跨两列，帮助文案说明“平台 results 的 metric_key”；列表在“测试工程”列追加“主指标”行。风险：历史行 `primaryMetricKey` 为空时显示“未填写”，保存时必须补齐；与迁移默认空串一致。
