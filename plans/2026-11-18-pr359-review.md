## §1 一页速览

一句话：这个 PR 把无轨迹 bad case 详情从“整页换成一纸状态说明”改回“错误详情页里换掉执行流和详情 tab”，侧栏与头部重新出现。

比喻：原来的错误详情页像一套两居室，左厢房列 case，中间是执行流和双 tab。m12-07 遇到“Session 还没落库”时，把整套房子拆掉只剩院子中央一块告示牌；#357 要求只把中间客厅换成告示牌，左厢房和门厅继续保留。

| 交付块 | 内容 |
| --- | --- |
| 布局 | 340px 侧栏 + `error-head` + 主区；trace 分支只替换主区执行流/双 tab |
| 侧栏 | 无 Session 时展示当前 case 标题、短 ID、对象名、`syncStatus` 徽标、归因空态/计数 |
| 头部 | 上报时间、根会话 ID、对象名、`1 个 bad case`、归因计数 |
| 返回入口 | Session 可读时是链接；不可读时是 `aria-disabled` 的禁用态 |
| 数据 | 不新增端点；503 `details` + 路由 `sid` + attributions `total` |
| 测试 | 组件测试 20 条（含 3 条新增/改写）+ `m12-07` E2E 壳层断言 |

## §2 架构导览

### 2.1 路由与数据源

`Index.vue:64-116` 从路由解析 `sessionId` 和 `case`，然后并行发起五个读取：

- `useSessionBadCases`、`useSessionSummary`、`useSessionTree`：Session 维度的列表/摘要/执行流；Session 未落库时返回 404。
- `useBadCase`：case 详情；case 存在但 Session 未就绪时返回 409/503，错误 `details` 带轨迹状态。
- `useAttributions`：case 的归因列表；无 Session 时返回 200 空列表，正好用来渲染空态和计数。

`traceDetails`（`Index.vue:202-213`）只接受 `ApiError` 且 code 为 `BAD_CASE_SESSION_PENDING` / `BAD_CASE_SESSION_UNAVAILABLE` 的错误，再用 `parseTraceStatusDetails` 把 `details` 转成 `TraceStatusDetails`。`traceStatus`（`:214-226`）额外拒绝 `details.sessionId` 与路由 `sid` 不一致的响应，避免跨 Session 状态污染页面。

`routeFatalError`（`:227-279`）保留原有优先级：深链解析失败、case 归属不符、真正 404 仍走整页错误态；只有 `traceStatus` 存在时才进入状态壳层。

### 2.2 模板分层

`Index.vue:479-725` 的新结构：

```text
section.errors-workspace
├── ErrorState (routeFatalError)
└── template (正常)
    ├── ErrorSidebar (始终渲染；trace 时进入 case 作用域分支)
    └── main.error-main
        └── header.error-head
            ├── trace 时：createdAt / root sid / objectName / 1 个 bad case / 归因数
            └── 非 trace：原开始时间 / repo / 问题数 / 已归因数
        ├── TraceStatusPanel (trace)
        └── template (非 trace)：flow-panel + detail-panel
```

关键点是 `ErrorSidebar` 和 `error-head` 不再放在 `v-else` 里；trace 分支只包住主区内容。`ErrorSidebar` 的 trace 入参在 `Index.vue:494-512`，头部分支在 `:528-544`，禁用返回入口在 `:564-579`。

### 2.3 侧栏的两种模式

`ErrorSidebar.vue:146-266` 用一个 `v-if="trace"` 切换：

- 有 trace：标题取 `trace.title`，数量固定 1；列表区渲染 `trace-case`，包含短 ID、对象名、状态徽标、归因标题、加载/错误/空态/计数。
- 无 trace：保留原来的筛选 chips、“全部 bad case”、`CaseGroup` 列表与启动入口。

`trace` 为 null 时行为与改前完全一致；`trace` 非 null 时不再渲染筛选和“全部 bad case”，避免把“只有一条当前 case”伪装成完整会话列表。

### 2.4 共享状态文案

`traceStatus.ts:27-42` 新增 `TRACE_STATUS_LABELS` 与 `traceStatusLabel`，把“就绪/未同步/同步中/同步失败/无可用轨迹”从 `TraceStatusPanel.vue` 抽出来，侧栏和面板共用，避免两处漂移。`TraceStatusPanel.vue:22` 改为调用共享 helper。

## §3 数据流走查

以 `m12-07-unavailable` 为例：

1. 总览点击“查看”进入 `/workspaces/ws-default/sessions/30000000-...104/errors?case=m12-07-unavailable&tab=desc`（`Index.vue:64-94`）。
2. `problemsQuery` / `summaryQuery` / `treeQuery` 对未落库 Session 返回 404；`detailQuery` 返回 503 `BAD_CASE_SESSION_UNAVAILABLE`，`details` 含 `title/objectName/createdAt/syncStatus/lastError/retryable/lastAttemptAt`；`attributionsQuery` 返回 200 空列表。
3. `traceDetails` 解析 `details`（`:202-213`），`traceStatus` 校验 session 归属后返回状态对象（`:214-226`）；`routeFatalError` 不再把 503 当成整页错误（`:227-279`）。
4. 模板渲染：`ErrorSidebar` 收到 `trace` 和 `traceAttributionCount`（`:494-512`），头部用 `traceStatus.createdAt` / `objectName` / `1 个 bad case` / 计数（`:528-544`），主区渲染 `TraceStatusPanel`（`:582-590`）。
5. `traceAttributionCount` 来自 `allAttributions.length`（`:133-136`），也就是 `useAttributions` 翻完所有页后的 total；空列表时侧栏显示“暂无归因。尚未进入自进化。”，头部显示 `0 个归因`。
6. 点击“刷新状态”调用 `refreshTraceStatus`（`:392-399`）重新拉取 detail/problems/summary/tree；同步状态入口仍派发 `hev:open-sync-status`（`:401-403`）。
7. 无 Session 时 `session` 为 null，头部和侧栏的返回入口都走 `aria-disabled` 的 span（`Index.vue:564-579`、`ErrorSidebar.vue:170-185`），不会导航到 404。

## §6 讨论点

### 讨论点 1：无 Session 时侧栏不列同根兄弟 case

- **位置**：`apps/web/src/pages/errors/components/ErrorSidebar.vue:45-53`、`:220-266`
- **现象**：trace 模式侧栏只展示当前 case；原型在有 Session 时会列出同根其它 case。
- **问题**：用户从状态页无法确认相邻 case 的情况，需要回总览再找。
- **预判**：issue #357 明确把“同根兄弟 case”列为需要新 case 级读模型的后续能力；本 PR 只渲染 503 `details` 能证明的当前 case，不伪造列表。代价是侧栏信息密度低于原型。
- **结论**：

### 讨论点 2：归因接口失败时头部仍显示 0 个归因

- **位置**：`apps/web/src/pages/errors/Index.vue:543`、`apps/web/src/pages/errors/components/ErrorSidebar.vue:245-258`
- **现象**：`traceAttributionCount` 直接取 `allAttributions.length`；接口 pending 或 error 时是 0，头部显示 `0 个归因`，侧栏则显示加载骨架或错误态。
- **问题**：接口失败时“0”可能被读成“确实没有归因”，而实际是未知。
- **预判**：未就绪 case 的 attributions 端点当前返回 200 空列表，失败是异常路径；若要更严谨，可在 `attributionsQuery.error` 时把头部计数显示为 `—`，但这会多一个展示分支。当前无实害，先记录。
- **结论**：

### 讨论点 3：`trace-mode` 类现在只作状态标记

- **位置**：`apps/web/src/pages/errors/Index.vue:482`
- **现象**：单栏/居中样式已删除，`trace-mode` 没有对应 CSS，仅保留在根节点上，组件测试断言其存在。
- **问题**：读代码时可能误以为它还有布局作用。
- **预判**：保留它作为“当前是轨迹状态分支”的显式状态钩子，后续若要做 trace 专属视觉或 E2E 定位可直接使用；也可以删除并让测试只断言面板/侧栏/头部共存。当前无行为影响。
- **结论**：

### 讨论点 4：禁用返回入口用 span 而不是 button

- **位置**：`apps/web/src/pages/errors/Index.vue:571-579`、`apps/web/src/pages/errors/components/ErrorSidebar.vue:170-185`
- **现象**：无 Session 时返回入口是带 `aria-disabled="true"` 的 span，不是可聚焦的 button。
- **问题**：键盘用户不会聚焦到一个“不可用但存在”的控件；屏幕阅读器对 span 的 disabled 语义支持也不如原生 button。
- **预判**：它不是交互控件，作为纯文本禁用态可以接受；若要更严格的无障碍语义，可改成 `<button disabled>` 并保留同样样式。当前无实害。
- **结论**：

## §9 文件级代码分析

### `apps/web/src/pages/errors/Index.vue`（M）

职责：错误详情页的查询编排、深链派生、三态渲染（正常/轨迹状态/整页错误）。本 PR 的核心是把“轨迹状态”从整页分支降为 `<main>` 内的内容分支。

旧代码（`git show origin/main:apps/web/src/pages/errors/Index.vue` 对应段）：

```vue
<main v-if="traceStatus" class="error-main trace-main">
  <TraceStatusPanel ... />
</main>
<ErrorState v-else-if="routeFatalError" ... />
<template v-else>
  <ErrorSidebar ... />
  <main class="error-main">
    <header class="error-head">...</header>
    <section class="flow-panel">...</section>
    <section class="detail-panel">...</section>
  </main>
</template>
```

新代码：

```vue
<ErrorState v-if="routeFatalError" ... />
<template v-else>
  <ErrorSidebar ... :trace="traceStatus" ... />
  <main class="error-main">
    <header class="error-head">
      <template v-if="traceStatus">...上报时间/对象/1 个 bad case/归因数...</template>
      <template v-else>...原开始时间/repo/问题数/已归因数...</template>
      <RouterLink v-if="!traceStatus || session" ...>返回 Session</RouterLink>
      <span v-else ... aria-disabled="true">返回 Session</span>
    </header>
    <TraceStatusPanel v-if="traceStatus" ... />
    <template v-else>
      <section class="flow-panel">...</section>
      <section class="detail-panel">...</section>
    </template>
  </main>
</template>
```

为什么这么写：壳层（侧栏 + 头部）与内容分支解耦；状态面板只接管它真正替代的区域。`traceAttributionCount` 用 `allAttributions.length` 而不是再发请求，因为 `useAttributions` 已经把分页翻完并缓存。

检视发现：无逻辑缺陷。`trace-mode` 类保留但无 CSS，见 §6.3；归因计数在接口失败时显示 0，见 §6.2。

### `apps/web/src/pages/errors/components/ErrorSidebar.vue`（M）

职责：错误详情左栏。改前只有“完整会话 case 列表”一种模式；改后新增“当前 case”模式。

旧代码：数量固定 `problems.length`，标题固定 `session?.title ?? problems[0]?.sessionTitle ?? sessionId`，返回入口永远渲染 `<RouterLink>`。

新代码（`ErrorSidebar.vue:42-53`）：

```ts
const traceLabel = computed(() => props.trace ? traceStatusLabel(props.trace.syncStatus) : "");
const sidebarTitle = computed(() => props.trace?.title || props.session?.title || props.problems[0]?.sessionTitle || props.sessionId);
const sidebarCount = computed(() => props.trace ? 1 : props.problems.length);
```

模板（`:146-266`）把筛选 chips、全部 case、`CaseGroup` 放进 `v-else`；trace 分支渲染 `trace-case`，归因区域按 `traceAttributionLoading/Error/Count` 三态展示。返回入口在 `:170-185` 按 `!trace || session` 切换链接/禁用 span。

为什么这么写：同一组件承载两种数据形态，避免再拆一个只用于异常态的侧栏组件；props 明确 `trace: TraceStatusDetails | null`，null 时保持旧行为。

检视发现：无逻辑缺陷。无 Session 时没有 `canStart` 入口，符合“不伪造兄弟 case”的边界；若未来要支持从状态页启动进化，需要先有 case 级读模型。见 §6.1。
