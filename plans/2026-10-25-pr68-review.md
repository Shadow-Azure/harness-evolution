## 1. 一页速览

一句话：这个 PR 给后续所有业务装上一只“可换插头”的数据库配电箱——同一条业务线路既能接生产 MySQL 8，也能接本地 SQLite，同时保证断电时 API 仍能报出是哪一端出了问题。

生活化比喻：`Database` 像电源插座标准，SQLite 和 MySQL 是两个插头，repository 与业务只认插座；`health` 是配电箱上的双色指示灯，一盏表示 API 是否活着，另一盏表示数据库是否真正可查询。

交付块：

| 交付块 | 维护者能看到什么 |
|---|---|
| 统一连接边界 | 业务只拿 session/transaction，不自行创建 engine。 |
| 双方言适配 | SQLite 带固定 pragma，MySQL 带生产 pool 与上海时区。 |
| 迁移基座 | 空 SQLite/MySQL 库都可幂等升级到 revision `0001`。 |
| 可解释的故障 | DB 故障不拖垮 API；health 返回 503 和稳定脱敏摘要。 |
| 双库门禁 | CI 用真实 MySQL 8.4 service 跑同一套 repository contract。 |
| 跨栈测试 | Web 经真实 Vite proxy 请求真实 FastAPI + SQLite。 |

## 2. 架构导览

### 2.1 配置与唯一选择点

`apps/api/app/config.py:19-56` 把 dialect、URL、pool、data dir 放进 `HE_` 命名空间。未显式提供 URL 时，SQLite 派生 `data/harness.db`，MySQL 派生 credential-free 的本地 URL。

`apps/api/app/db/factory.py:9-13` 是唯一分派点：SQLite 枚举值走 `SqliteDatabase`，其余已校验的枚举走 `MySqlDatabase`。Pydantic 的封闭枚举会在未知 `HE_DB_DIALECT` 值进入工厂前拒绝配置。

### 2.2 Database 插座

`apps/api/app/db/base.py:20-42` 定义 `dialect`、engine、start/dispose、session/transaction、health。`session()` 只负责关闭，不作隐式提交；`transaction()` 才拥有 commit/rollback 语义。

`apps/api/app/db/database.py:44-62` 延迟创建 engine，避免应用 import 时连接数据库。`transaction()` 在 `database.py:70-79` 对 `BaseException` 统一 rollback 后重抛，因此业务异常与任务取消都不会留下半提交写入。

已知边界：protocol 仍暴露 `engine`。本 issue 的 issue 正文要求 SQLAlchemy engine 经 Database 暴露，因此这里记录为接口面，而非本 PR 新缺陷；后续 repository 实现应优先使用 session，测试外的业务仍不得自行建 engine。

### 2.3 两个插头

`apps/api/app/db/sqlite.py:21-40` 在每一个 DBAPI 连接上设置 WAL、foreign keys、5000ms busy timeout 与 NORMAL synchronous。测试在 `apps/api/tests/test_database.py:111-129` 查询真实连接状态，而不是只断言方法被调用。

`apps/api/app/db/mysql.py:21-40` 配置 pool size、overflow、30 分钟 recycle、pre-ping，并在每个新连接上设置 `+08:00`。CI 与 `test_database.py:279-289` 都通过真实 MySQL 查询 `@@session.time_zone`。

### 2.4 启动、迁移与释放

`apps/api/app/main.py:22-48` 是应用组装根。lifespan 依次 start、迁移、yield、dispose；start 或 migration 失败只写日志并把应用标记为 DB unhealthy，API 仍可监听。

`apps/api/app/db/migrate.py:13-25` 把 Alembic 放到 worker thread，因为 Alembic env 内部要 `asyncio.run()`；`apps/api/alembic/env.py:33-54` 使用 async connection 执行同步迁移接口。`render_as_batch=True` 为后续 SQLite ALTER 做准备。

### 2.5 Health 的两盏灯

`apps/api/app/api/health.py:15-45` 定义数据库摘要与完整 health DTO；`latencyMs` 用 alias 对齐 TS camelCase。`health.py:48-73` 每次实际执行 `SELECT 1`；失败时仅返回异常类型与固定 unavailable 文案，并把 HTTP 状态改为 503。

`packages/contracts/src/index.ts:14-35` 同步声明双方言、数据库健康与版本字段。`apps/web/src/App.tsx:35-57` 区分加载、API 不可达、DB 异常和健康四态。

## 6. 讨论点

### D1. 注入 Database 与迁移 URL 可能指向两个不同的库

**位置**：`apps/api/app/main.py:22-37`、`apps/api/app/db/migrate.py:13-25`。

**现象**：`create_app()` 允许调用方注入 Database，lifespan 也启动这个对象；但 `upgrade_database(_database, settings)` 完全忽略 `_database`，用 `settings.effective_db_url` 另建 Alembic engine。实测 settings 指向临时库 B、注入 `SqliteDatabase` 指向临时库 A，启动结束后只有 B 出现 `harness.db`，A 未被迁移。

**问题**：这是明确的双目标错误。后续 health 查询 A 时会说数据库可达，但 schema 迁移实际落在 B；测试注入、未来依赖替换或测试库切换都可能得到“healthy but uninitialized”的实例。当前测试只用匹配 settings 与 Database，或 mock 迁移函数，没有覆盖这个错配。

**预判**：应为本 PR 修复。让迁移配置从被启动的同一个 Database 取 URL，或把 Settings/Database 绑定成不可分离的单一组合对象；补一条双临时 SQLite 路径的回归测试，证明迁移目标始终是注入对象。

**结论**：已修复（2026-10-25）。`upgrade_database()` 现在只从实际启动的 `Database.url` 构造 Alembic 配置；双 SQLite 回归测试证明注入库被迁移、Settings 指向的另一库不会被创建。

### D2. 原始数据库异常会被完整写进日志，可能泄漏凭据或基础设施信息

**位置**：`apps/api/app/db/database.py:87-91`、`apps/api/app/main.py:38-45`；相关测试在 `apps/api/tests/test_database.py:151-169`、`apps/api/tests/test_app.py:238`、`test_app.py:270`。

**现象**：公共 health 已正确脱敏，但 `logger.exception()` 会把原始异常文本写进服务端日志。测试还主动构造了包含 `ops:super-secret@db.internal` 和私有路径的异常，并断言这些内容出现在 `caplog` 中。

**问题**：数据库 URL、驱动错误或迁移异常可能包含用户名、密码、主机、库名、路径甚至 SQL 参数。日志通常比 health 更持久、更容易被集中采集；把凭据锁在公共接口外、却完整写进日志，没有真正兑现密钥卫生。当前 Owning Note 选择记录原始诊断异常，因此修复后也应同步该决策。

**预判**：应保留 `phase`、`dialect`、异常类型和可操作摘要，同时对 URL userinfo、密码字段、SQL 参数与敏感路径做统一脱敏；若需要完整堆栈，可记录不携带异常字符串的 frame，而不是直接 `logger.exception()`。补“同一异常可诊断但秘密不在日志”的测试。

**结论**：已修复（2026-10-25）。应用与 health 日志改为稳定结构化字段 `phase/dialect/error_type`，不再调用 `logger.exception()`；含 DSN、密码、主机和路径的回归异常只保留在测试输入中，不会进入公共响应或日志。

### D3. 数据库已确认异常时，hero 区仍显示“连接状态检查中”

**位置**：`apps/web/src/App.tsx:49-57`、`apps/web/src/App.tsx:90`。

**现象**：health 503 后顶部状态正确显示“数据库异常”，但 hero meta 使用 `health?.db.ok ? "已连接" : "连接状态检查中"`，于是同一个页面同时说“异常”和“检查中”。加载阶段 `databaseLabel` 还会先默认显示 SQLite，即使目标环境是 MySQL。

**问题**：这是用户可见的状态矛盾，会让人误以为检查尚未完成，而不是数据库已经失败。失败状态正是本 PR health 增量的核心，现有单测只断言顶部 pill，没有锁住 meta 文案。

**预判**：应把数据库展示收敛为 `unknown / connected / failed` 三态：无 health 时显示“数据库 / 检查中”，成功后显示实际 dialect，“已连接”，失败后显示实际 dialect，“连接异常”。前端单测同时覆盖失败态不存在“检查中”和加载态不冒充 SQLite。

**结论**：已修复（2026-10-25）。前端改为未知/已连接/连接异常三态：加载显示“数据库 · 检查中”，失败显示实际方言 + “连接异常”，单测锁定失败态不再出现“检查中”。

### D4. 跨栈集成只走 health 成功态，真实 503 链路依赖两侧 mock 对齐

**位置**：`tests/integration/web-api-proxy.test.mjs:136-162`；对照 `apps/api/tests/test_app.py:121-146`、`apps/web/src/App.test.tsx:72-98`。

**现象**：后端单测构造 unhealthy Database 得到真实 503 body，前端单测 mock 同样形状的 503；真实跨栈集成只验证 200 health 和 401 envelope。

**问题**：当前没有一条真实 `Web → Vite → FastAPI → DB failure → 503` 的链路。若 backend alias/status/content-type 或 frontend 503 解析发生漂移，两侧各自 mock 的测试仍可能互相“配合错误”。

**预判**：建议在本 PR 或最迟 health 壳收尾 issue 增补一个第二 API 实例，使用不可写 SQLite 路径或不可达 DB URL，经真实 Vite proxy 断言 503 health DTO。当前成功态集成已覆盖主接线，因此列为测试缺口而非运行时阻塞。

**结论**：已修复（2026-10-25）。跨栈集成新增第二个不可连接 SQLite + FastAPI + Vite 实例，真实断言代理返回 503、`ok=false`、`db.ok=false`，且响应与 API 日志都不含临时数据库路径或凭据。

## 9. 文件级代码分析

### 9.1 `apps/api/app/config.py`（M）

职责是把数据库选择变成环境配置。新增 `DatabaseDialect`、data dir、URL、pool 与 echo；`effective_db_url` 提供双方言默认值。

旧版本只有 host/port/phase/CORS/docs/log。新版本仍不把真实凭据存进仓，默认 MySQL URL 不含 user/password；生产必须通过 `HE_DB_URL` 注入。

发现：D1 不在本文件，但与 Database/Settings 双来源相关。未发现其他缺陷。

### 9.2 `apps/api/app/db/base.py`（A）

职责是定义业务可依赖的协议和公开健康结果。`DBHealth` 是 frozen dataclass，避免调用方修改检查结果；`Database` 固定生命周期、session、transaction、health。

实现思路：接口只表达业务所需能力，具体驱动由 adapter 吸收。未发现缺陷。

### 9.3 `apps/api/app/db/database.py`（A）

职责是共享 SQLAlchemy 生命周期。start 延迟建 engine，session 关闭，transaction 统一 commit/rollback，health 用 `SELECT 1` 计时并返回稳定错误摘要。

事务处理采用“异常统一 rollback 后再抛”的守卫形状；这比在业务层逐个处理异常更不容易漏写。发现：D2 的原始日志；未发现事务残留缺陷。

### 9.4 `apps/api/app/db/sqlite.py`（A）

职责是构造本地 SQLite engine。默认 URL 时先建 data dir，连接时设置四项设计 pragma。

关键依赖 `aiosqlite` 是 SQLAlchemy 的 async DBAPI 驱动。测试直接查询 PRAGMA，能抓住配置被删除或恢复到不同连接的问题。未发现缺陷。

### 9.5 `apps/api/app/db/mysql.py`（A）

职责是生产 MySQL engine。pool/overflow 来自 Settings，recycle/pre-ping 固定为设计值，每次连接设置上海时区。

CI 真实 MySQL 8.4 和 repository contract 证明这套配置不只是属性赋值。未发现运行时缺陷；私有 pool 属性测试较脆但不阻塞。

### 9.6 `apps/api/app/db/factory.py`（A）

职责是唯一适配器分派。Pydantic 枚举负责非法值 fail-fast，工厂本身保持短小。

未发现缺陷。

### 9.7 `apps/api/app/db/migrate.py` 与 `apps/api/alembic/**`（A）

职责是让 Alembic 与 FastAPI 的 async SQLAlchemy 技术栈协作。程序化入口在 worker thread 调 Alembic，env 内再创建 NullPool async engine；日志配置可被应用入口关闭，避免覆盖 uvicorn logging。

旧仓库没有迁移，新代码建立单树基线。`render_as_batch` 与 `compare_type` 为后续双方言 schema 演进准备。发现：D1 的 URL 来源错配。

### 9.8 `apps/api/app/main.py`（M）

职责是应用 composition root。新增 lifespan，把数据库启动、迁移和释放放进 FastAPI 生命周期；初始化失败转成可通过 health 观察的状态。

旧版本只组装 middleware/routes。新版本增加 `database` 注入缝和启动错误状态，符合“DB 故障不崩 API”的决策。

发现：D1、D2。

### 9.9 `apps/api/app/api/health.py`（M）

职责是把 API/Database 两盏灯合成公开 health。成功 200，DB 失败 503；异常字符串先经过 adapter 的稳定摘要，不会直接透传驱动文本。

旧版本只有 `ok/service/phase`。新增 `version/db`，OpenAPI 的 `latencyMs` alias 与 TS 契约一致。未发现本文件直接缺陷。

### 9.10 `packages/contracts/src/index.ts`（M）

职责是同步 health 契约。新增 dialect 常量、DatabaseHealth 与 version/db。

实现仍是手写契约，m1-04 才会改为 OpenAPI 生成；本 PR 通过后端字符串对账测试锁住关键字段。未发现缺陷。

### 9.11 `apps/web/src/App.tsx` 与 `App.test.tsx`（M）

职责是消费 health 并展示连接状态。成功、API 不可达、DB 503 与加载四态均有测试，覆盖率由 V8 80% 阈值强制。

旧版本只按 HTTP 200 判断是否连接。新版本接受 503 health body，区分 DB 异常。发现：D3。

### 9.12 `apps/api/tests/test_database.py`（A）

职责是数据库行为契约。覆盖 URL 派生、工厂、SQLite pragma、事务回滚、health 脱敏、MySQL pool、空库迁移、双方言 repository 与 MySQL 时区。

实现思路：SQLite 与 MySQL 共享同一个 `RepositoryContract` 类，MySQL 用例由 marker 和 CI service 强制执行。发现：D1、D2 的测试期望需同步修正；未发现假测试。

### 9.13 `apps/api/tests/test_app.py`（M）

职责是 FastAPI 行为测试。新增 lifespan 启动/失败、health 200/503、迁移失败、启动失败脱敏、DB URL 配置和跨语言契约对账。

测试直接驱动真实 FastAPI app 或真实 lifespan，不用 mock 替代被审查的 HTTP 层。发现：D2 的日志断言与 D1 的注入错配未覆盖。

### 9.14 `tests/integration/web-api-proxy.test.mjs`（M）

职责是用真实子进程启动 FastAPI 与 Vite。动态分配端口、等待 readiness、捕获日志、POSIX 进程组清理，成功态与 401 都经真实 proxy。

实现思路：把浏览器网络层的代理行为从两个单元测试域中单独拿出来验证。发现：D4。

### 9.15 `.github/workflows/ci.yml`、脚本与门禁（M）

职责是让 SQLite、前后端覆盖率、跨栈集成和 MySQL 8 都成为真正会执行的检查。MySQL job 设置 `HE_REQUIRE_MYSQL=1`，缺服务直接失败；`test:gates` 钉住命令与 80% 阈值存在。

实测 MySQL 日志为 3 passed，而不是 skipped。未发现 CI 旁路。

### 9.16 文档、Agent Note 与 flow（A/M）

职责是同步当前数据库现状、开发命令和决策理由。Agent Note 明确单接口、双 adapter、空迁移、health 降级与 CI 双库；issue scope 覆盖新增的根命令、契约、Web 与跨栈测试目录。

发现：D2 修复后需更新 Note 中的“原始诊断异常只进入日志”这一事实。其余双语/预算/链接门禁通过。
