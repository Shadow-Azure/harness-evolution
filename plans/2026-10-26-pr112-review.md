## §1 一页速览

一句话：这个 PR 给外部问题三表装了一层“只读翻译器”，把症状、归因状态和根因报告拼成页面可直接消费的五种展示状态，并尽量把上游坏数据降级成可诊断 warning，而不是把整页打成 500。

生活化比喻：外部系统像三个各自记账的档案柜，本服务只能隔着玻璃看。这个 PR 不是把柜子搬走，而是新增一位档案员：同一案件的“问题卡、分析结论、根因报告”一起核对；对不上号时贴上“未分析”标签并留下可追踪的告警码。

## §2 架构导览

### 2.1 Repository 是只读数据库适配层

`BadCaseRepository` 对 `bad_cases`、`bad_case_analysis`、`probe_reports` 分别提供按会话、按 ID 和批量查询，全部使用 SQLAlchemy `select()`。`BadCaseRepositoryProtocol` 只声明读操作，service 不依赖 `Database` 本身，也不能通过公开 repository 方法发起写入。位置：`apps/api/app/db/crud/bad_cases.py:71-103`、`:155-263`。

批量读取是这里的关键：列表先取 cases，再对当前页 case ids 各做一次 analysis/probe 批量查询，避免“每张问题卡再回一次表”的 N+1。命名虽然简单，但边界是对的：外部 schema 细节停留在 repository，业务判断不碰 SQL。

### 2.2 Service 做关系校验，而不是无条件相信外键

`BadCaseService` 将三表组装成 `BadCaseReadModel`。它没有因为数据库有外键就假设数据一定一致，而是再次验证：

- `analyzed_issue` 必须恰有一个 probe；其余状态不得挂 probe。
- probe 必须存在且与 bad case 属于同一根会话。
- `attribute_type` 必须是 `model|prompt|error` 的闭集。
- bad case 的 `type/object type`、`analysis_result` 形状都做防御式校验。

位置：`apps/api/app/service/bad_cases/service.py:284-387`。

### 2.3 漂移被折叠成两种结果

身份字段缺失时，service 不制造空 ID 模型，而是跳过该行并返回 warning；非身份字段异常时，尽量保留可展示对象，并以空值或安全占位降级。warning 只包含稳定 code、字段名和追踪 ID，不包含上游原文。位置：`apps/api/app/service/bad_cases/service.py:153-282`、`:389-463`。

## §3 数据流走查

### 场景 A：读取一个会话的问题列表

1. `BadCaseService.list_for_session(sid)` 调 repository 按 `created_at, bad_case_id` 取全部 case。
2. service 收集当前批次的 case ids，一次查 analysis，一次查被引用的 probe。
3. 每个 case 单独归并，但数据已预加载，不会逐卡回表。
4. `analyzed_issue + model/prompt/error` 映射为三种问题展示态；`analyzed_nonissue` 与缺失/坏分析降级为另外两态。

入口：`apps/api/app/service/bad_cases/service.py:128-213`。

### 场景 B：probe 报告反查来源问题

1. repository 以外连接读取 `bad_case_analysis → bad_cases → probe_reports`。
2. service 只接受 `analyzed_issue`，且 case session 与 probe session 完全一致的反向链接。
3. 重复 case id 去重，最终输出 `fromBadCases` 与总数；坏链接只产生脱敏 warning。

入口：`apps/api/app/db/crud/bad_cases.py:228-263`、`apps/api/app/service/bad_cases/service.py:389-463`。

### 场景 C：外部字段坏掉

1. case/analysis/probe 主键或 session 缺失：不构造伪造模型。
2. analysis 与 probe 关系矛盾：返回 canonical `unanalyzed`。
3. `analysis_result` 不符合当前状态：保留状态，清空 result，并产生 `ANALYSIS_RESULT_INVALID`。
4. 非身份字段类型错误：页面可继续渲染，但该字段降级为 `None`、空串或空映射。

## §6 讨论点

### D1 应用启动仍通过 Alembic 创建外部三表

**位置**：`apps/api/app/main.py:90-96`、`apps/api/alembic/versions/0004_domain_fixtures.py:240-323`

**现象**：应用每次启动都执行 `upgrade_database()`；历史 migration `0004` 会无条件创建 `bad_cases`、`probe_reports`、`bad_case_analysis`。PR 描述却写明 “avoids runtime writes/migrations”，issue 的实施步骤也要求“确保 Alembic 不写外部表”。

**问题**：如果生产连接使用只读业务账号，启动 migration 可能直接失败；如果上游已经预建同名表，应用 migration 也可能与外部 schema 所有权冲突。这是架构契约问题，不是本次新增 repository 造成的，但仍是本 issue 的未完成验收。

**预判**：P1。应在合并前明确拆开“外部 schema bootstrap”和“应用自有表 migration”：CI/dev 可通过独立 fixture bootstrap 建表，生产应用 migration 不应取得外部表 DDL 所有权。修改历史 migration 前需要维护者确认存量环境迁移策略。

**结论**：已修复（2026-10-26）。应用启动以 `bootstrap_external_tables=False` 升级本服务自有表；开发 fixture 在迁移后显式创建外部三表，并覆盖“应用先启动、fixture 后 seed”的顺序。

### D2 外部业务时间没有规范成 Asia/Shanghai

**位置**：`apps/api/app/db/crud/bad_cases.py:110-152`、`apps/api/app/service/bad_cases/schemas.py:46-60,79-95`

**现象**：实际用 SQLite fixture 调用 read model，`created_at` 返回 `2026-10-20T09:03:00`，`tzinfo=None`；测试的 MySQL 输入是 UTC，也没有断言 read model 的时区。设计要求 API 时间统一为 `+08:00`，而现有 `as_shanghai()` 未被使用。

**问题**：m4-02 若直接把 dataclass 映射到 Pydantic 响应，时间会是无时区字符串，前端无法判断 09:03 是上海还是 UTC；若 serializer 假设 UTC，会再偏 8 小时。时间字段类型漂移也没有 warning。

**预判**：P2，建议在 repository 边界校验 `datetime` 并调用 `as_shanghai()`，或在 service 构造 read model 时统一转换；补 SQLite/MySQL read-model 时区断言。

**结论**：已修复（2026-10-26）。repository 在出站 DTO 边界统一调用 `as_shanghai()`，SQLite/MySQL 时间均带 `+08:00`。

### D3 Probe 展示文本为空时静默输出空串

**位置**：`apps/api/app/service/bad_cases/service.py:448-456`

**现象**：实测构造 `probe_object=''`、`probe_description=''`、`probe_analysis=''` 的 probe，service 返回三个空字符串且 `warnings=[]`。这些列在设计中均为 NOT NULL；外部 schema 漂移或空串写入时页面会出现一张无可读内容的归因卡。

**问题**：身份字段缺失有诊断，但同类展示字段缺失没有；这不满足“外部字段漂移不会崩溃且日志可定位”的可观测性目标。

**预判**：P2，建议对必填展示文本做非空校验，保留安全占位但产生稳定的 `EXTERNAL_FIELD_MISSING/INVALID` warning；不要把上游原文写进 warning。

**结论**：已修复（2026-10-26）。三个必填展示文本为空时保留安全占位，并产生稳定、脱敏的 `EXTERNAL_FIELD_MISSING` warning。

### D4 列表与 probe 反查不是同一数据库快照

**位置**：`apps/api/app/db/crud/bad_cases.py:162-263`、`apps/api/app/service/bad_cases/service.py:128-151`

**现象**：`list_for_session()` 依次使用三个独立 session 读取 cases、analyses、probes；`get_probe_result()` 也分两个 session 读取 probe 与反向来源。外部系统在两次查询之间更新时，可能读到旧 case 加新 analysis，或 probe 已变化但来源仍是旧状态。

**问题**：单次响应可能不是一致快照。当前 refresh 会自愈，因此不是数据损坏；但 m4-02 的错误详情可能短暂显示互相矛盾的结论。

**预判**：P2/P3，建议提供 repository 的“单会话批量快照”方法；如果接受最终一致，应在 Agent Note 写明该窗口与刷新策略。

**结论**：已修复（2026-10-26）。列表、单 case 和 probe 反查均改为单数据库 session 快照方法，并有 session 打开次数回归。

### D5 只读门禁只检查方法名，没有覆盖所有 SQL 路径

**位置**：`apps/api/tests/m4-01-external-read-models/test_external_read_models.py:329-354,502-506`

**现象**：测试捕获了一次列表读取的三条 `SELECT`，另有测试只检查 repository 公开方法名中不含 insert/update/delete。若未来在某方法中直接 `session.execute(text("UPDATE ..."))`，这两条测试未必能拦住。

**问题**：只读边界是 issue 的硬约束，当前测试与代码事实一致，但门禁表达不够强。

**预判**：P3，建议对 repository 的所有公开查询逐一捕获 statement，并断言只包含 SELECT；或者抽出统一只读执行方法，由结构测试保证没有直接 DML。当前无实害。

**结论**：已修复（2026-10-26）。测试逐一执行全部公开 repository 路径，并断言所有实际 SQL 首关键字仅为 `SELECT`。

## §9 文件级代码分析

### `apps/api/app/db/crud/bad_cases.py`（A）

职责：把外部三表的数据库行收窄成只读 boundary DTO，并提供按会话/ID/批次的查询。

关键依赖：SQLAlchemy Core 的 `select()` 构造参数化 SQL；这里的 repository 不接管事务写入，只通过 `Database.session()` 获取读连接。

变更核心：批量 case → 批量 analysis → 批量 probe 是这条路径的性能基础；probe 反查使用 outer join 暴露 case/probe 身份，让 service 能识别坏链接。

实现思路：repository 是“只读档案柜的取件窗口”，返回 dataclass 而不是 SQLAlchemy Row，避免数据库列名越过边界。

检视发现：时间原样读出，未统一时区；多次查询使用独立 session，见 D2/D4。

### `apps/api/app/service/bad_cases/schemas.py`（A）

职责：让问题列表、分析状态和 probe 结论拥有稳定的内部 read model。

变更核心：`DisplayState` 将三种 problem attribute 展开成原型的五态；warning 只携带 code、field 和外部稳定 ID。

实现思路：先建立闭集类型，再把“最多有点漂移”与“身份不可用”区分为可展示模型和 lookup 诊断。

检视发现：datetime 字段只是注解，不负责校验或时区转换，见 D2。

### `apps/api/app/service/bad_cases/service.py`（A）

职责：合并外部三表并执行关系/形状校验。

变更核心：批量预取避免 N+1；状态与 probe 关系以“要么合法、要么 unanalyzed”处理；probe 反查只接受同会话 analyzed issue。

实现思路：外键是数据库的承诺，service 再做一次“入口核对”，像机场安检不会只看身份证是否过期。

检视发现：必填 probe 文本空串漏诊断；多次 repository 调用跨 session，见 D3/D4。

### `apps/api/tests/m4-01-external-read-models/test_external_read_models.py`（A）

职责：覆盖五态、坏字段、坏链接、反向来源、查询次数与只读方法面。

检视发现：主场景和降级路径覆盖充分；没有时态规范化、probe 文本空值、全 SQL 路径只读断言，见 D2/D3/D5。

### `apps/api/tests/test_database.py`（M）

职责：新增真实 MySQL 的五态读模型合同。

检视发现：实际验证了跨库合并和反向来源，但没有断言输出时间带 `+08:00`。MySQL 测试使用直接 DML 建夹具并在 `finally` 清理，属于测试设施，不是运行时写路径。

### `fixtures/m2-synthetic/corpus.json`（M）

职责：加入第五种展示态所需的 `model` 归因数据。

检视发现：夹具与五态测试一致；没有引入本机轨迹正文或本地路径。

### issue、架构文档与 Agent Note（M/A）

职责：同步现状、边界和决策。

检视发现：Note 准确说明“运行时 repository 无写方法”，但没有明确应用 migration 仍会创建外部表；PR 描述中的 “avoids runtime writes/migrations” 因此过强，见 D1。
