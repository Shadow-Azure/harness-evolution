## 1. 一页速览

一句话：启动向导点“下一步”后不再只把按钮置灰，而是显示“正在准备第 N 步 + 当前阶段 + 已等待秒数”，表单保留但锁住；失败若属于目标文件超时，就在同一张卡里给出原因、“不是 Session 数据为空”、重试和返回修改条件；取消或迟到的响应不会推进步骤。

一个比喻：像查快递物流。页面只把**已经发生**的“已揽收”标为进行中，后面的“运输中/派送中”老实保持灰色，不假装快递已经到下一站；如果超时就亮“物流异常”，给你“重试/改地址”，而不是只把查询按钮变灰。

## 2. 架构导览

### 2.1 状态与“锁住谁”

向导仍是单一 SFC 的四步状态机，新增的核心状态是一个对象而不是一个布尔：

- `previewBusy: PreviewBusy | null`（`LaunchWizard.vue:142`）保存 `fromStep`、`failed`、`elapsed`、`timeoutMessage`；`previewInFlight = previewBusy && !failed`（`LaunchWizard.vue:381-383`），`formLocked` 直接等于它（`:384`）。
- 旧的 `pending` 继续表示“有请求在跑”，既包括前进预览，也包括步骤内分页、第 4 步缓存刷新和启动（`LaunchWizard.vue:141`、`937`、`1003`、`1057`、`1078`）。`isBusy = pending !== ""`（`:380`）仍是所有按钮的总开关。
- `nextButtonTestId` 根据 `fromStep` 返回 `wizard-step2-next` / `wizard-step3-next` / `wizard-next`（`:385-394`），所以等待中 footer 的禁用主按钮能沿用既有 E2E test id。

锁的边界是这次模板改造最值得看的地方：

- 进度卡在 `.wz-form` **之前**渲染（`LaunchWizard.vue:1242-1322`），`.wz-form` 只包住四个步骤模板（`:1324-1329`），footer 在 `.wz-form` 之外（`:2073`）。因此 `inert` 只作用于表单，卡片、取消、header 关闭都仍然可操作——没有把进度卡误锁进去。
- `.wz-form.locked` 只是 `opacity: .55; pointer-events: none; user-select: none`（`LaunchWizard.vue:2305-2309`），真正的键盘/无障碍锁定来自 `:inert="formLocked || undefined"`（`:1327`）。真实浏览器 smoke 用 `.wz-form.inert === true` 验证过（`tests/e2e/smoke-waiting.test.mjs:460-462`，该文件不在 PR 内）。
- 超时后 `failed=true`，`previewInFlight` 为 false，表单自动解锁；此时 footer 回到第 1 步普通按钮，但“下一步”因 `contentUnresolved` 被禁用（`LaunchWizard.vue:2101`），用户改版本/点卡片里的“返回修改条件/重试解析”才能继续。这是一个有意的“失败后恢复编辑”状态。

### 2.2 请求代际与计时器

- `previewGeneration` 是组件的普通 `let`（`LaunchWizard.vue:167`），只被 `beginPreview`（`:801-802`）、`cancelPreview`（`:835-836`）、`returnToEditing`（`:883-884`）和 `onBeforeUnmount`（`:217`）递增。响应返回后先在 try/catch 里比较代际，再决定是否写状态。
- `finishPreview(generation)`（`:823-832`）是统一的收尾：代际不匹配直接返回；匹配则清 `pending`、停表，并在卡片未失败时清空卡片。超时失败卡会被保留（`!previewBusy.value.failed` 的判断）。
- `beginPreview`（`:801-815`）重置 `previewBusy` 和 `elapsed`，设置 `pending`，启动 1 秒一次的 `setInterval`（`:786-793`）。`stopElapsedTimer` 在成功/普通错误（`finishPreview`）、取消、超时（`handleContentUnresolved`）、返回编辑、版本修改（`clearContentUnresolved`）和卸载路径上都会被调用；本次逐条走查没有发现泄漏。
- 没有改 `http.ts`、没有 AbortController：取消只是前端“不再认领结果”，服务端请求可能继续。这与 PR 的边界声明一致，也避免了把一次共享 transport 的改造塞进 UI PR。

### 2.3 超时分类与字段红态

- `contentFailureReason`（`LaunchWizard.vue:736-745`）只从 `ApiError.details.reason` 取稳定 reason；`isContentTimeout`（`:751-757`）要求 code 为 `TARGET_CONTENT_UNRESOLVED` 且 reason 为 `content_timeout` 或 `timeout`。
- `handleContentUnresolved`（`:848-873`）在 `previewBusy !== null` 且是超时 reason 时才启用失败卡：把 `step` 拉回 1、`contentUnresolved=true`、`contentError` 写成可操作文案、`fieldErrors.version=false`（改用 `contentUnresolved` 维持红色，见 `:1405`、`:1413`）、清空下游 preview，再把 `previewBusy.fromStep=1`、`failed=true`、冻结计时器。
- 非超时内容错误（`content_not_found`、`ref_not_found`、`repo_unreachable` 等）仍走原来的字段级红字（`:1454-1471`），既有测试 `LaunchWizard.test.ts:878-921` 继续覆盖。
- `retryContentResolution`（`:876-880`）先清卡片再跑 `goToSessions`；`returnToEditing`（`:883-892`）直接清卡片、回第 1 步并解除红态。两者都保留已填条件。

### 2.4 原型与“诚实降级”

原型在 `harness-evolution.html` 里新增了 `evWzStartBusy`（`:5515-5540`）、`evWzBusyCard`（`:5542-5589`）、`__evWzSimulate`（`:5866`）和 `wzsim` 参数入口（`:7413`）。原型为了演示会：

- 第 2 秒把阶段自动推进到下一行，第 4 秒自动进入下一步（`harness-evolution.html:5527-5534`）；
- 第 1 步第 20 秒自动变超时（`:5528`）；
- 用 `wzsim=loading|timeout` 冻结状态截图（`:5866-5875`）。

生产没有伪造这些推进：`PREVIEW_CURRENT_STAGE = 0`（`LaunchWizard.vue:175`），`previewStageRows` 里 `index < 0` 永远不成立，所以“已完成 ✓”分支实际是死代码，第 1 步永远只有“读取目标版本=进行中、关联 Session=等待”。这与 Note 的“服务端未上报子阶段，不伪造完成”一致，是对的设计取舍。原型和生产的两处差异（原型会推进阶段、超时文案用真实 elapsed 而不是 20 秒）在 §6-9、§6-1 分别记录。

## 3. 数据流走查

主线剧本（第 1 步点击“下一步”，成功/超时/取消三条结局）：

1. 用户点 `[data-testid=wizard-next]`，触发 `goToSessions`（`LaunchWizard.vue:895-899`）。`validateStep1`（`:691-709`）先做本地校验：版本格式、必填、时间段、策略；失败则只写字段错误，不发请求。
2. 校验通过后 `beginPreview(1, "sessions")`（`:901`）：`previewGeneration++`、建 `previewBusy{fromStep:1, failed:false, elapsed:0}`、`pending="sessions"`、启动计时器（`:801-815`）。
3. 同一时刻 Vue 渲染进度卡（`LaunchWizard.vue:1242-1322`）：标题“正在准备第 2 步 · 读取目标版本”、阶段行“读取目标版本（进行中）/ 关联 Session（等待）”、`已等待 0 秒`；footer 换成“取消等待 + 禁用主按钮（正在读取目标版本…）”（`:2074-2095`）；`.wz-form` 加上 `inert` 和 `locked`（`:1324-1329`）。
4. `previewSessions`（`:903-907`）发出 `POST …/preview/sessions`。服务端在匹配 Session 前先 `TargetContentResolver.resolve`（`apps/api/app/service/evolution/target_content.py:162-168`），对冷缓存执行 `git clone --mirror`（`apps/api/app/third_party_api/git/content.py:78`、`:102-125`）。
5. 服务端读目标文件与 git 子进程各有一道 20 秒上限（`target_content.py:33`、`:262`；`git/content.py:56`、`:147-151`），超时映射为 `TARGET_CONTENT_UNRESOLVED` + `content_timeout`/`timeout`。
6. **成功**：响应回来后 `if (generation !== previewGeneration) return`（`:908`），写 `sessionPreview`、`sessionPage`、清空下游、`step=2`（`:909-915`）；`finally` 里的 `finishPreview` 清 `pending`、停表、移除卡片（`:928`、`:823-832`）。footer 变成第 2 步按钮。
7. **超时失败**：catch 先做同样的代际检查（`:917`），`handleContentUnresolved` 识别 timeout reason 并建失败卡（`:918`、`:848-873`）；`finally` 仍会 `finishPreview`，但因为 `failed=true` 保留卡片、只清 `pending`（`:827-831`）。用户看到“读取目标版本超时 + 不是 Session 数据为空 + 重试解析 / 返回修改条件”，版本输入保持红框，`elapsed` 冻结。
8. **取消**：`cancelPreview` 递增代际、停表、清卡片和 `pending`（`:835-840`），步骤和输入不变。之后迟到的成功/失败响应在 try/catch 与 `finishPreview` 两处都被代际拦住（`:908`、`:917`、`:824`），不会推进步骤，也不会清掉下一次请求的状态。
9. **非超时内容错误**：`handleContentUnresolved` 仍把 `step=1`、`fieldErrors.version=true`，显示字段级红字和既有“重试解析”链接（`:1454-1471`）；卡片在 `finally` 被清掉（未失败）。
10. **未套卡片的路径**：步骤内分页 `changeSessionPage`/`changePotentialPage`（`:933-953`、`:999-1020`）、第 4 步缓存刷新 `refreshAttribution`（`:1053-1071`）和 `launch`（`:1074-1100`）仍只用 `pending` 禁用按钮。这是 PR 明确声明的范围，不是遗漏。

## 6. 讨论点

### 6-1 “20–40 秒”与“20 秒上限”互相矛盾，失败卡又硬编码 20 秒

**位置**：等待文案 `LaunchWizard.vue:447-449`；失败文案 `LaunchWizard.vue:444-446`；同样的承诺在 Agent Note `.md:17`、`.en.md:17`、`design-v2.md:238`；服务端上限 `apps/api/app/service/evolution/target_content.py:33`、`:262`，git 子进程上限 `apps/api/app/third_party_api/git/content.py:56`、`:147-151`。

**现象**：等待卡告诉用户“通常 2–5 秒；首次读取该仓库可能需要 20–40 秒”，但服务端把一次 `read_file`（含冷 clone）包在 20 秒 `asyncio.wait_for` 里，git 子进程本身还有一道 20 秒；超过 20 秒的首次读取不会“等到 30 秒后成功”，而是直接变成 `content_timeout`/`timeout` 并显示失败卡。失败卡又说“服务端在 20 秒内没有读完”，这个 20 是写死的，不是用卡片上的 `elapsed`；如果超时上限将来变更、或测试/代理提前返回 422，同一张卡会出现“已等待 N 秒”与“20 秒内”并排。连原型自己的演示也会在第 20 秒切成 failed（`harness-evolution.html:5528`），和它同一张卡上的“20–40 秒”文案互相打脸。

**问题**：这是 PR 要解决的那个场景的核心预期管理：用户被引导接受最长 40 秒，实际 20 秒就会失败；文案没有告诉用户“冷 clone 必须在 20 秒内完成，否则会超时”。同时，写死 20 秒让文案与真实 elapsed、未来可配置的超时脱钩。

**预判**：把等待文案改成“通常 2–5 秒；冷缓存需要先 clone，服务端读取上限 20 秒，超时会给出重试；首次成功后会缓存 mirror”；失败卡的“20 秒”改用 `formatElapsed(previewBusy.elapsed)` 或与后端常量同源，至少不要与卡片上的 elapsed 自相矛盾。Note/design 的 20–40 秒一并改掉。这是文案/文档缺陷，不是请求逻辑缺陷（服务端上限本身按设计工作）。

**结论**：

### 6-2 `design-v2` 说 `repo_unreachable` 也走超时卡，生产与 Note 说不

**位置**：`plans/ui-prototype-v2/design-v2.md:239`；生产 `LaunchWizard.vue:751-757`；Agent Note `.md:40`（`repo_unreachable` 仍走字段红字）；已修正的 `plans/fullstack-design/08-frontend-implementation.md:682`。

**现象**：`design-v2 §7.5` 写“超时：`TARGET_CONTENT_UNRESOLVED`（`content_timeout` / `repo_unreachable`）……显示在进度卡内”；生产只把 `content_timeout`/`timeout` 判为超时卡，`repo_unreachable` 会落到 `fieldErrors.version` 的字段红字。`460a318` 把 08 的同一句从 `content_timeout / repo_unreachable` 改成了 `content_timeout / timeout`，却漏改 design-v2，说明这是收尾遗漏，不是有意的设计分歧。

**问题**：验收人按 design-v2 构造一个仓库不可达场景，会期待失败卡，实际只看到版本字段红字；反过来，如果团队决定 `repo_unreachable` 也应该卡片，那生产实现就漏了。两种解释必须选一个并让文档一致。当前生产的“只把真正的超时叫超时”是合理的（`repo_unreachable` 往往是 DNS/权限/地址错误，立刻返回），所以更可能应改文档。

**预判**：把 `design-v2.md:239` 改成 `content_timeout` / `timeout`，并补一句“其他内容 reason 仍保留字段级红字”；如果产品希望 `repo_unreachable` 也卡片，另开修复 PR 同时改 `isContentTimeout` 与 Note，不要只改文档。

**结论**：

### 6-3 每秒变化的 `elapsed` 在 `aria-live=polite` 区域内，且失败卡的 `role=alert` 被 `aria-live=polite` 覆盖

**位置**：`LaunchWizard.vue:1242-1249`（`role` 绑定与 `aria-live="polite"`）、`:1265-1268`（秒表文本）；声明在 `plans/fullstack-design/08-frontend-implementation.md:684`。

**现象**：进度卡整体是一个 `aria-live="polite"` 区域，里面的“已等待 N 秒”每秒变化；失败时同一个节点把 `role` 切成 `alert`，但 `aria-live` 仍是 `polite`。按 ARIA 语义，显式的 `aria-live="polite"` 会覆盖 `role=alert` 隐含的 assertive，所以“超时”并不会以告警优先级播报；而等待期间读屏器可能每秒播报一次 elapsed。卡片还是用 `v-if` 整体插入的，插入时 live region 可能不播报；成功/取消后整块移除，也没有“已完成、进入第 2 步”的播报或焦点安置。

**问题**：PR 在 08/Note 中把 `role=status`/`role=alert` 当作可访问性交付，但实际语义被 `aria-live` 削弱；秒表放在 live region 里制造持续噪音。这是真实的无障碍缺陷，不是“可以后续再说”的细枝末节，因为等待 20 秒正是读屏用户最需要安静、清楚状态的场景。

**预判**：不要给整张卡加 live region。保留一个稳定的、只承载状态文字的 `role=status` 区域（或给标题/阶段变化单独 `aria-live`）；`elapsed` 加 `aria-hidden="true"`（视觉用户看，读屏用户不需要每秒听）；失败卡用 `role="alert"` 时去掉 `aria-live`（或显式 `assertive`）；成功/超时切换时把焦点移到新步骤标题或失败卡的重试按钮。补一个 accessibility 断言/浏览器检查。

**结论**：

### 6-4 超时态版本输入是 `aria-invalid`，但 `aria-describedby` 指向的 `wizard-version-error` 没有渲染

**位置**：版本输入 `LaunchWizard.vue:1402-1418`（红色 `:1405`、`aria-invalid` `:1413`、`aria-describedby="wizard-version-error"` `:1414`）；字段错误节点 `LaunchWizard.vue:1454-1471` 只在 `fieldErrors.version` 为真时渲染。

**现象**：超时卡分支把 `fieldErrors.version` 设为 `false`，用 `contentUnresolved` 维持红框；因此 `aria-invalid="true"` 生效，但 `id="wizard-version-error"` 的 `<p>` 不存在，`aria-describedby` 悬空。错误文案只出现在上方的失败卡里，没有和输入框建立程序化关联。

**问题**：读屏用户聚焦版本输入时只会听到“无效”，听不到“读取目标文件超时、不是 Session 数据为空”。普通无错误状态下 `aria-describedby` 也指向不存在的节点（既有问题），但这次新增了“确实 invalid 却没有描述”的状态，影响更具体。

**预判**：给失败卡一个稳定的 `id`，超时态把 `aria-describedby` 指向卡片；或渲染一个视觉隐藏、内容为 `contentError` 的描述节点；或保留字段级错误节点但用 `<p>` 显示与卡片相同的文案（注意避免重复 test id）。这属于小改，可与 6-3 一起做。

**结论**：

### 6-5 前端没有自己的超时兜底，等待卡可能无限转

**位置**：`beginPreview`/计时器 `LaunchWizard.vue:786-815`；footer 取消 `:2074-2095`；服务端超时 `target_content.py:262`。

**现象**：前端没有 `setTimeout` 或 AbortController，`previewBusy` 只在请求 resolve/reject、手动取消、返回编辑或卸载时结束。若代理挂住连接、请求永不 settle，或后端卡在 Session 查询/数据库而没有内容读取之外的超时保护，进度卡会一直显示、表单一直锁着、计时器一直跑；用户只能点“取消等待”，超时卡永远不会出现。若只是返回 504/非 JSON，请求会 settle，卡片会消失并落到通用 `requestError`，也不会出现超时卡。

**问题**：PR 的“20 秒反馈”只覆盖服务端内容读取层的超时，完全依赖它返回 422；传输层/代理层/后续 Session 查询的失败不在覆盖范围。用户遇到的是“等待卡永远不结束”，比原来的“按钮置灰 20 秒”更难判断。当前 PR 明确说不改 `http.ts`、不引入 AbortController，所以这不是实现违约，而是需要明确记录的边界。

**预判**：至少有两条路：一是在 UI 加一个 watchdog（比如 25 秒后把卡片切成“仍在等待/可能网络异常”，提供取消和重试，不强行 abort 也可），二是明确写入 Note/文档“只有服务端 20 秒超时会被卡片化，代理/网络挂起时用取消”。考虑到 #394 会改后端读取路径，建议本 PR 先补文档 + 一个“请求永不返回”的测试，避免把前端 watchdog 做成新的语义。

**结论**：

### 6-6 秒表与 `finishPreview` 代际守卫没有测试，现有取消用例会“为对的理由通过、为错的实现也通过”

**位置**：`LaunchWizard.test.ts:923-979`（只断言“已等待 0 秒”）、`:1099-1139`（取消后直接 release，没有新请求）；被测逻辑 `LaunchWizard.vue:786-832`。

**现象**：全文件没有 fake timers，所有测试在毫秒级结束，所以“已等待 0 秒”既是初始值也是唯一被断言的 elapsed；把 `startElapsedTimer` 删掉、把 tick 改成永不递增、或让 interval 永不停止，28 个测试仍会全绿。取消测试在取消后没有发起第二个预览，旧请求 release 时 `previewBusy` 已经是 null、`pending` 已经是空，所以即使 `finishPreview` 不检查代际、直接清 `pending`/卡片，测试也看不出差别——它只覆盖了 try/catch 里的代际检查，没有覆盖 `finishPreview` 的守卫。

**问题**：PR 把“每秒计时器 + 请求代际”作为核心机制写进标题和 Note，但这两个机制恰恰是测试最薄弱的地方。取消后马上重试、旧响应迟到，是这套设计最容易回归的路径；没有测试就无法防止未来把 `finishPreview` 改成无条件清理。

**预判**：加 fake-timer 用例验证 0→1→60 秒格式、成功/普通错误/取消/卸载后 interval 不再 tick；再加一个“hold 旧请求 → 取消 → 立即发起新请求 → release 旧请求”的用例，断言新请求的卡片和 `pending` 不被清掉、步骤不被旧结果推进。这样 6-1 的 elapsed 文案、6-5 的 watchdog 也才有测试落点。

**结论**：

### 6-7 进度卡在滚动容器顶部，长表单/后几步可能看不到卡和重试按钮（未实测）

**位置**：卡片在 `.modal-body` 内 `LaunchWizard.vue:1231-1322`；`.modal-body` 是 `max-height: 66vh; overflow-y: auto`（`:2227-2231`）；footer `:2073`。

**现象**：卡片插在 `.modal-body` 的可滚动内容最上方，没有 `scrollIntoView`/焦点移动。用户在第 2/3 步（或已经滚到第 1 步下方）点 footer 的下一步时，滚动位置不变；进度卡和超时卡的“重试解析/返回修改条件”可能落在视口上方，用户只看到 footer 按钮变成禁用的阶段文案。超时后 footer 回到普通第 1 步按钮（且被 `contentUnresolved` 禁用），如果卡片在视口外，用户可能以为“点了没反应”。

**问题**：footer 的阶段文案和取消仍然给了基本反馈，所以不是完全无反馈；但“超时卡 + 重试/返回”是 PR 的主要交付，如果它出现在视口外，核心场景就退化。smoke 只在第 1 步、未滚动的情况下验证，未覆盖这个状态。

**预判**：在卡片出现/变为 failed 时 `scrollIntoView({block:'nearest'})` 并把焦点移到卡片标题或重试按钮；或者把状态/操作固定在 `.modal-foot`（至少失败操作）。建议在真浏览器补一个“滚到第 1 步底部再点下一步”和“第 3 步点下一步”的用例。当前无证据表明一定发生，先作为设计观察。

**结论**：

### 6-8 新增 test id 有重复，阶段行共用同一个 id

**位置**：`wizard-content-retry` 在卡片 `LaunchWizard.vue:1305` 和字段错误 `:1466` 各一处；阶段行 `wizard-progress-stage` 在 `:1278` 每行重复。

**现象**：正常流程下两个 retry 不会同时渲染（超时卡时 `fieldErrors.version=false`，字段错误节点不渲染；而 `contentUnresolved` 又让 footer 的下一步禁用，用户无法在卡片仍显示时触发 `validateStep1` 把它变回 true），阶段行则本来就该有多行，测试用 `findAll`。但源码层面存在同名 id，`getByTestId` 严格模式或未来分支改动可能直接抛错。

**问题**：这是测试可读性/稳健性问题，不是用户可见 bug；仓库里已有 `wizard-error`/`wizard-back` 等互斥分支重复 id 的先例，所以不是本 PR 新引入的模式。但新卡片的 retry 与旧字段错误链接同名，容易让后来者误以为只有一个入口。

**预判**：给卡片按钮改 `wizard-card-retry`（或反之），阶段行改用 `wizard-progress-stage-${index}` 或在列表上用 `data-testid="wizard-progress-stages"` + `li`；如果坚持共用，至少在测试里用 `findAll` 并断言数量，避免将来误用 `get`。

**结论**：

### 6-9 文档/证据措辞把“本地 fixture + 注入 422”说得像真实 20 秒后端超时

**位置**：Agent Note `.md:37`、`:42`、`.en.md:37`、`:42`；PR 的 Verification 与 Boundaries；原型 reduced-motion 声明。

**现象**：Note 写“生产实现已落地并通过真实浏览器冒烟：等待卡、阶段按钮、表单锁定、取消、20 秒超时卡、重试/返回都可用”，又写“生产证据来自真实浏览器冒烟（等待卡、20 秒超时、取消、重试）和部署日志”。实际 smoke（`tests/e2e/smoke-waiting.test.mjs:411-427`）用的是本地 SQLite fixture + 本地 bare git 仓库，超时态是 CDP `Fetch` 拦截请求、等 20 秒后**注入**一个 422 `content_timeout`，不是真实后端超时，也不是真实 GitHub 延迟；PR 正文在 Verification/Boundaries 里明确说了这一点，Note 没有。PR 正文另称“Scoped CSS matches the prototype, including reduced-motion spinner handling”，但原型 `harness-evolution.html` 没有 `prefers-reduced-motion`，生产才新增了这段 CSS。

**问题**：证据本身是有效的 UI 状态验证（真实浏览器、真实组件、真实 DOM/inert），但 Note 的措辞会让后来者把它当成“20 秒真实后端超时已验证”或“真实 GitHub 慢链路已验证”。同理，reduced-motion 是生产新增、原型未实现，不能写成“和原型一致”。

**预判**：在 Note 的 Consequences 补一句“smoke 使用本地 fixture，并以 CDP 注入 422 模拟 20 秒超时；不覆盖真实 GitHub 延迟与后端真实超时”，正文把“matches the prototype, including reduced-motion”改成“按原型层级实现，生产另补 reduced-motion”。这不会削弱证据，反而让后续重评估有准确起点。

**结论**：

### 6-10 有意的差异与一段死代码：阶段推进、分页/缓存刷新不套卡、`done` 分支

**位置**：`PREVIEW_CURRENT_STAGE=0` 与 `previewStageRows` `LaunchWizard.vue:175`、`:460-484`；`changeSessionPage`/`changePotentialPage`/`refreshAttribution` `:933-1071`；原型推进 `harness-evolution.html:5527-5534`。

**现象**：原型第 2 秒推进到“关联 Session/已完成”，生产永远把第一行标为进行中、第二行等待；`done` 状态分支在 `PREVIEW_CURRENT_STAGE=0` 下不可达。分页、第 4 步缓存刷新和启动都没有进度卡。Note 与 08 已明确说这是“服务端未上报子阶段，不伪造完成”的诚实降级。

**问题**：这些差异本身是合理的，不应该在验收时当作缺陷；但 `design-v2 §7.5` 的“已完成阶段打勾”是原型行为，生产永远看不到，文档读者容易误判。生产保留 `done` 分支/CSS 是为了和原型共享结构，代价是一段死代码。

**预判**：接受差异，并在 design-v2 的“已完成阶段打勾”旁注明“原型演示用；生产因服务端无子阶段不会出现 done”；`done` 分支可以保留（结构对齐）或在生产删掉并让原型自行保留。分页、缓存刷新、启动不套卡也建议在 §7.5 明写，避免下一轮验收再问。

**结论**：

### 9.1 `apps/web/src/pages/evolution/components/LaunchWizard.vue`（M，`+1277/−679`，`-w` 后 `+616/−18`）

**职责**：四步启动向导；本 PR 为三个前进预览（sessions / potential / attribution）增加等待卡、阶段/耗时、取消、超时卡和表单 `inert` 锁，其余路径保持原样。
**变更形态**：大量模板行只是包 `.wz-form` 造成的缩进；逻辑集中在 `<script setup>`（约 280 行新增）、卡片/footer/模板（约 110 行）和约 230 行 CSS。
**依赖**：Vue 3 `ref/computed/watch`、TanStack Query（版本建议）、既有 `api/evolutionRuns` 与 `ApiError`；没有新依赖。进度卡是本地 DOM + scoped CSS，spinner 是纯 CSS 动画，不引入组件库。

**旧代码 vs 新代码（脚本）**：

```text
旧：pending 单状态；goToSessions 直接 pending="sessions"；finally 无条件 pending=""
    handleContentUnresolved 一律 step=1 + fieldErrors.version=true
    内容错误文案在一个 helper 里先取 reason 再拼 copy
新：previewBusy + previewGeneration + elapsedTimer
    beginPreview / finishPreview / cancelPreview / returnToEditing 四个状态入口
    contentFailureReason + isContentTimeout 分离“超时”与“其他内容错误”
    超时且 previewBusy 存在：失败卡、fromStep=1、fieldErrors.version=false 但 contentUnresolved 保持红框
```

**为什么这么写**：三个 `preview/*` 仍是同步契约，无法从服务端拿百分比；前端能诚实展示的只有“第几步、哪个阶段、等了多久、能不能取消”。代际是共享 transport 没有 abort 时的最小替代：不取消服务端请求，只拒绝迟到结果，避免“取消后仍推进步骤”。`inert` + `locked` 的选择是把“保留输入但禁止改条件”做成一件事，而不是清空表单或整窗 spinner。

**实现思路（≤3 行）**：用一个 `previewBusy` 对象承载“等待/失败”两种卡态，用请求代际隔离迟到响应，用 `pending` 继续兼容既有按钮禁用；超时只在 reason 命中时升级成卡片，其他错误保持原字段红字。

**检视发现**：代际、取消、`finishPreview`、计时器清理、`inert` 作用域逐条走查**没有发现功能性错误**；发现集中在文案/文档（6-1、6-2、6-9）、无障碍（6-3、6-4）、测试缺口（6-6）、滚动可见性（6-7）和 test id（6-8）。CSS 新增的 `white` 字面量（`:2521`）沿用了既有 `.btn.primary { color: white }` 的写法，`verify:web-style` 的正则只拦 `#hex`/`rgba()`，所以门禁会绿；这是既有例外，不建议在本 PR 扩面。`@media (prefers-reduced-motion: reduce)` 同时补了 `.switch` 的 transition 关闭（`:2524-2534`），属于顺带修复，无副作用。
