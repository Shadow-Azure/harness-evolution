## §1 一页速览

**一句话**：把问题卡上的「标题」和「正文」拆成两个字段——短标题 `title` 进错误详情页标题行、问题列表卡、执行流图问题卡；长描述统一叫「描述正文」，真实列名从 `reason` 改为 `bad_case_description`，对外 DTO 字段仍叫 `reason`。

**一个比喻**：以前的 `bad_cases` 像一张只有背面的快递面单——背面写满详细说明，前台却只能把整段说明贴到本该写大字收件人的位置；现在面单正面有了一行大字（`title`），背面继续放详细说明（`bad_case_description`），前台按两级排版。

## §2 架构导览

### 2.1 数据层：一次改名 + 一次加列

`bad_cases` 是外部写入、本服务只读的表（[06 §4.1](fullstack-design/06-database-design.md#L322-L343)）。本次同时做两件事：

1. 新增 `title VARCHAR(255) NOT NULL`（`domain.py:236`）——短标题，外部上报必填；
2. `reason` 列改名 `bad_case_description TEXT NOT NULL`（`domain.py:237`）——语义仍是描述正文，列名统一 `bad_case_` 前缀，对齐 `probe_reports.probe_description / probe_analysis`。

对外 DTO 字段名保持 `reason`，映射发生在仓储边界：`_row_bad_case` 把 `mapping["bad_case_description"]` 装进 `BadCaseRow.reason`（`crud/bad_cases.py`），`BadCaseRecord` 同理（`crud/sessions.py`）。这样契约、前端与 issue 验收里的 `reason` 语义都不动，只有存储层改名。

### 2.2 迁移：先改名、再补列、后收紧

`0010_bad_case_title.py`：

- `upgrade()`（`0010:24-53`）：`inspect().has_table("bad_cases")` 守卫（运行时可能不建外部表）→ batch 改名（显式带 `existing_nullable=False, nullable=False`，否则 MySQL 的 `CHANGE COLUMN` 会把列改成可空）→ batch 加可空 `title` → `UPDATE … SET title = SUBSTR(bad_case_description,1,255)` → batch 置 `NOT NULL`。
- `downgrade()`（`0010:57-76`）：删 `title`、把列名改回 `reason`；描述正文无损，只丢派生出来的短标题（docstring 已说明）。

### 2.3 读模型：外部坏数据也要有可读题名

`derive_title()`（`title.py:33-57`）三层兜底：

1. 外部 `title` 非空 → 去空白、截 255 直接使用；
2. 否则取描述首句（CJK `。！？!?；;`、换行、拉丁句点后跟空白/行尾，`title.py:9`），截 255；
3. 两者都不可用 → `未命名问题`。

降级信号沿用现有机制：`BadCaseService._case_model` 在派生时追加 `EXTERNAL_FIELD_MISSING`（`field="title"`，`service.py:266-272`），`ProblemService` 把它并入 `degraded` 与 `diagnosticCode`（`problems/service.py:136-147`），前端显示「数据降级」chip。`SessionBadCase`（会话树/图上卡）没有 degraded 字段，只派生标题——[06 §4.1](fullstack-design/06-database-design.md#L341) 已写明这层边界。

### 2.4 Web：三级卡片统一主文本

- 详情页 `ProblemDescription.vue`：标题行渲染 `title`（`:53-56`），新增正文块 `.problem-detail` 渲染 `reason`（`:85-90`），样式对齐原型 `.ed-detail`：`margin-top:9px / 12.5px / line-height:1.7 / var(--text-dim)`（`:134-139`）；间距按原型重排（heading `gap:9px`、facts 6px、association 8px）。
- 列表卡 `BadCaseList.vue`：compact 与非 compact 的标题位置都改用 `problem.title`（`:127`、`:200`），aria-label 同步（`:169`）。
- 图上卡：`types.ts` 把 `BadCaseLayoutNodeData.reason` 改名为 `title`；`layout.ts` 用 `${shortId} ${title}` 测量宽度（`layout.ts:449-463`），三条挂载路径都 `detail?.title ?? item.title`（`:523`、`:565`、`:590`），150–400px 钳制不变；`BadCaseNode.vue` 渲染 `data.title`（`.finding-reason` → `.finding-title`）。
- 执行流说明行 `pages/errors/Index.vue:138` 改用 `title`。

## §3 数据流走查（端到端一条主线）

1. **上游上报**：外部系统往 `bad_cases` 写一行，带 `title` 与 `bad_case_description`。
2. **迁移/seed**：`pnpm fixtures:seed` 经 `crud/fixtures.py` 写新列；老库经 `0010` 回填 `title = SUBSTR(description,1,255)`。
3. **查询**：`BadCaseRepository.list_snapshot` / `SessionRepository` 读 `bad_cases`，行映射在 `crud/bad_cases.py::_row_bad_case` 把 `bad_case_description` 装进 `reason`。
4. **派生**：`BadCaseService._case_model` 调 `derive_title(row.title, row.reason)`；缺 title 时追加 warning。
5. **组装**：`ProblemService._public_cases` 把 `title` 写进 `BadCase` DTO，并按 warning 计算 `degraded`；`SessionService` 组装树上的 `SessionBadCase.title`。
6. **契约**：FastAPI OpenAPI → `pnpm contract:generate` → `openapi.json` + `api.d.ts`。
7. **前端**：错误页取 `useSessionBadCases` / `useBadCase`；详情页标题行 = `title`、正文块 = `reason`；左栏与图上卡主文本 = `title`。
8. **证据**：`collect-smoke.mjs` 在真实前后端上断言标题与正文两段文本、三态、窄屏与 console，产出 `assertions.json` 与 `smoke-report.html`。

## §6 讨论点

> 每条给预判不给结论；结论栏留空，供逐条拍板。

### 6-1 DTO 字段名 `reason` 与列名 `bad_case_description` 不对称

- **位置**：`apps/api/app/db/crud/bad_cases.py:149`、`plans/fullstack-design/05-api-design.md` §3.4。
- **现象**：存储列叫 `bad_case_description`，对外 JSON 仍叫 `reason`，需要在仓储层做一次「名字转换」。
- **问题**：两套命名长期并存，读代码的人容易以为 `reason` 是另一份数据；也让「reason 语义收敛为描述正文」只能靠文档维持。
- **预判**：保持现状更稳。`reason` 已是外部契约与前端既有字段，改名是破坏性变更；列名带前缀是本表约定（`probe_reports` 同理）。文档已在 05 §3.4 / 06 §4.1 写明一一映射。
- **结论**：

### 6-2 `SessionBadCase` 没有 `degraded`，图上卡降级只在详情加载后才出现

- **位置**：`apps/api/app/service/sessions/schemas.py:95-105`、`apps/web/src/components/agent-tree/layout.ts:534`。
- **现象**：会话树上的 `SessionBadCase` 只有派生后的 `title`，没有降级标记；图上卡片的 `data.degraded` 取自 `BadCase` 列表项（`AgentTree` 的 `problems` prop → `layout.ts:534`），列表查询返回后就会显示，不需要单条详情；只有「仅树数据」的路径无法表达降级。
- **问题**：同一行坏数据在详情页显示「数据降级」，在只有树数据时图上卡不显示，观感不一致。
- **预判**：可接受。树接口是轻量读模型，加字段要动契约且会扩大每次树查询的载荷；`BadCase.degraded` 已覆盖详情/列表路径。已在 06 §4.1 写明边界，并补了 `layout.ts` 的 degraded 透传断言与图上卡降级 chip 断言（§7）；若将来图上卡需要独立降级提示，再单独评审加字段。
- **结论**：

### 6-3 读时派生的「首句」规则对长英文/无标点文本的表现

- **位置**：`apps/api/app/service/bad_cases/title.py:9-30`。
- **现象**：首句终止符对 CJK 标点、换行、`". "`/行尾句点生效；无标点时整段截 255 字符，可能在词中间截断。
- **问题**：极端英文描述会得到一个 255 字符、词尾被切的标题。
- **预判**：无实害。这是异常数据的兜底路径，正常上报必须带 `title`；255 字符也远超卡片可见宽度（图上卡会 ellipsis，列表卡单行省略）。回填同样按 255 字符处理，行为一致。
- **结论**：

### 6-4 `degraded` 语义被扩大

- **位置**：`apps/api/app/service/problems/service.py:136-147`。
- **现象**：以前 `degraded=true` 只表示 `bad_case_type / object_type` 非法；现在缺 `title` 也会置真。
- **问题**：前端「数据降级」chip 与 `diagnosticCode` 的含义从「身份字段坏了」扩到「展示字段缺失」；更关键的是，`degraded` 同时被用来选择「占位锚点」分支，若把它直接当成锚点降级条件，只有 title 缺失的行会丢掉真实上报人锚点（`main/-1`），与树读模型给出的锚点不一致。
- **预判**：信号扩大正确且成本低——这正是 issue 要求的「降级展示沿用现有 degraded 机制」；但锚点分支必须只看身份字段（`identity_degraded`）。已在 `problems/service.py` 拆成两个变量修复，并补锚点回归断言（§7）。
- **结论**：

### 6-5 迁移在 MySQL 上的锁表成本

- **位置**：`apps/api/alembic/versions/0010_bad_case_title.py:47-53`。
- **现象**：`title` 先可空、UPDATE 回填、再 `MODIFY … NOT NULL`；MySQL 8 的 `ADD COLUMN` 可 instant，但 `MODIFY NOT NULL` 通常要重建表。
- **问题**：`bad_cases` 规划量级 10³–10⁴（06 §5），重建表仍是秒级；但这是外部写入的表，迁移窗口会短暂阻塞上游写入。
- **预判**：当前量级可接受，且 issue 已约定存量由上游重灌为权威路径；若未来行数上到 10⁶，应改成「先加可空列 + 后台回填 + 单独收紧」的三步迁移。
- **结论**：

### 6-6 报告与截图入库

- **位置**：`reports/2026-10-29/issue-165-bad-case-title/**`（10 张 PNG + 1 个 HTML + 2 个采集脚本）。
- **现象**：PR 体积的大部分来自证据文件；`collect-before.mjs` 用 `git archive f37010d` 生成「修复前」快照，`collect-smoke.mjs` 在真实前后端上跑三态与窄屏。
- **问题**：仓库会持续变大；脚本与历史报告有维护成本。
- **预判**：沿用了 #150/#153 的既有做法，且这类真实浏览器证据无法由单元测试替代；脚本已参数化（临时数据目录、动态端口），可复跑。
- **结论**：

## §9 文件级代码分析

### 9.1 `apps/api/alembic/versions/0010_bad_case_title.py`（A，迁移）

职责：把 `bad_cases.reason` 改名 `bad_case_description`，新增 `title` 并回填。关键依赖：Alembic `batch_alter_table`（SQLite 不能原地改列/加 NOT NULL 列，batch 先建新表再拷贝）。

旧代码（`0004` 中的列定义）：

```python
sa.Column("reason", sa.Text(), nullable=False),
```

新代码（`0009 → 0010` 的增量）：

```python
with op.batch_alter_table("bad_cases") as batch_op:
    batch_op.alter_column(
        "reason",
        new_column_name="bad_case_description",
        existing_type=sa.Text(),
        existing_nullable=False,
        nullable=False,
    )
with op.batch_alter_table("bad_cases") as batch_op:
    batch_op.add_column(sa.Column("title", sa.String(255), nullable=True))
op.execute("UPDATE bad_cases SET title = SUBSTR(bad_case_description, 1, 255)")
with op.batch_alter_table("bad_cases") as batch_op:
    batch_op.alter_column("title", existing_type=sa.String(255), nullable=False)
```

为什么这么写：MySQL 的 `CHANGE COLUMN` 不带 `NULL/NOT NULL` 时默认把列改成可空——这是 CI `mysql` lane 真实抓到的缺陷，故改名时显式带 `existing_nullable=False` 与 `nullable=False`；SQLite 走 batch 重建表，同样吃到这两个参数。`has_table` 守卫保证运行时不创建外部表的部署不会被迁移弄坏。实现思路总结：**改名保语义、加列走可空 → 回填 → 收紧，双向可逆**。

检视发现：回填取「前 255 字符」而非「首句」，与 issue 原描述不一致 → 已在 issue 双语正文改为「前 255 字符」并记录在 §7。

### 9.2 `apps/api/app/service/bad_cases/title.py`（A，派生标题）

职责：给低质量外部数据一个可显示的短标题。依赖：标准库 `re`。

```python
_SENTENCE_END = re.compile(r"[。！？!?；;\n]|\.(?=\s|$)")  # noqa: RUF001

def derive_title(title: object, description: object) -> tuple[str, bool]:
    external = _usable_title(title)
    if external is not None:
        return external[:TITLE_MAX_LENGTH], False
    sentence = _first_sentence(description)
    if sentence is None:
        return UNNAMED_TITLE, True
    return sentence[:TITLE_MAX_LENGTH], True
```

为什么这么写：返回 `(title, derived)` 二元组，调用方无需再判断 warning；`object` 入参允许数据库边界传来 `None`/非字符串而不抛错（外部表结构漂移的既有防御风格）。正则里 `\.` 用前瞻避免把 `v1.0`、`e.g` 当句末。实现思路总结：**外部值优先、描述首句兜底、未命名问题保底，255 截断与列宽一致**。

检视发现：无。`derive_title` 同时被 problems 与 sessions 两条读路径复用，避免了 `SessionBadCase` 自己实现一遍。

### 9.3 `apps/api/app/service/problems/service.py`（M，降级判定）

旧：

```python
degraded = item.bad_case_type is None or item.object_type is None
```

新：

```python
title_degraded = any(
    warning.code == "EXTERNAL_FIELD_MISSING" and warning.field == "title"
    for warning in item.warnings
)
identity_degraded = item.bad_case_type is None or item.object_type is None
degraded = identity_degraded or title_degraded
...
# 只有身份字段坏了才回退到 main 占位锚点；派生标题必须保留真实上报人锚点。
if identity_degraded:
    anchor = resolve_problem_anchor(bad_case_type=None, object_type=None, bad_case_agent_id=None, …)
else:
    anchor = resolve_problem_anchor(bad_case_type=item.bad_case_type, object_type=item.object_type, …)
```

为什么这么写：降级信号统一从 warning 列表推导，不新增读模型字段；`diagnostic_code` 的候选字段集合同步加 `title`，且保持「bad_case_type → object_type → title」的旧优先级。**锚点分支与展示降级必须分离**：review 阶段实测发现，若用合并后的 `degraded` 选择占位锚点，只有 title 缺失的行会被挂到 `main/-1`，与树读模型的真实上报人锚点不一致（`m4-02` 已补锚点回归断言）。实现思路总结：**warning 是唯一事实源；降级展示可以扩，锚点输入不能扩**。

检视发现：见 §6-4（`degraded` 语义扩大，展示可接受、锚点分支已修正）。

### 9.4 `apps/web/src/pages/errors/components/ProblemDescription.vue`（M，两级渲染）

旧：

```html
<span id="problem-description-title" class="problem-title">{{ problem.reason }}</span>
...
<div v-if="facts.length"><div class="facts">…</div></div>
```

新：

```html
<span id="problem-description-title" class="problem-title">{{ problem.title }}</span>
...
<div class="problem-detail" data-testid="problem-detail">{{ problem.reason }}</div>
<div v-if="facts.length" class="facts-block"><div class="facts">…</div></div>
```

样式：`.description` 从 `gap: 9px` 改为 `gap: 0`，各块显式 margin（detail 9px、facts 6px、association 8px、diagnostic 8px、heading `gap: 9px`），与原型 `.ed-detail/.fi-facts/.ed-meta/.ed-head` 一一对应。为什么这么写：原型给正文块的是 `margin-top` 而不是父级 gap，直接用 gap 会双重间距；显式 margin 让每块间距可分别对照原型。实现思路总结：**结构对齐原型、间距逐块对齐、类名保留现有测试选择器**。

检视发现：`.problem-detail` 没做空值保护——若后端 `reason` 为空会渲染一个空 div。后端已保证 `reason` 非空字符串（`reason or ""` 只在该字段非法时出现，同时会置 degraded），空 div 高度为 0，无实害；若未来要隐藏，可加 `v-if="problem.reason"`。

### 9.5 `apps/web/src/components/agent-tree/{types.ts,layout.ts,nodes/BadCaseNode.vue}`（M，图上问题卡）

旧：布局数据字段叫 `reason`，宽度按 `${shortId} ${reason}` 测量。
