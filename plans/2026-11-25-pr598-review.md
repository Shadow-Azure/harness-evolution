## §1 一页速览

一句话：把「站点叫什么」从 Web 源码搬到服务器 `.env`，由 API 在启动时读入并开一个公开只读端点，Web 在首屏挂载前取一次写进 Pinia，让顶栏、登录页、强制改密卡与浏览器标题共用同一份品牌文案。

一个比喻：API 像物业值班室，启动时从服务器抽屉里取出这次部署定制的门牌；浏览器每次开门前先派一个人去值班室抄门牌，抄不到就挂上出厂自带的那块。门牌只换字，不换门框（布局、导航、标记图形、favicon 都不动）。

| 交付块 | 用户可见结果 |
|---|---|
| API 配置 | `HE_BRAND_NAME` / `HE_BRAND_SUBTITLE` 可覆盖；未设置、`None`、空串、纯空白一律回落当前文案；真实值 trim 后使用 |
| 公开端点 | `GET /api/app-config` 无 token 返回 `{"brand":{"name","subtitle"}}`；`extra="forbid"`；不写库、不审计 |
| 契约链 | OpenAPI 快照、生成 TS 类型与 `AppConfigResponse` 导出一致，`contract:check` 无 diff |
| Web 装配 | `bootstrapApp` 在 `app.use(pinia)` 后、mount 前加载一次；失败/非法响应回落默认且不抛错；`document.title` 随品牌名 |
| 四个品牌面 | 顶栏（含 `aria-label`）、登录左栏、改密卡品牌名、浏览器标题读同一 store |
| 长品牌名 | 顶栏 ≤640px 只留标记；登录页与顶栏在 1408/390 用省略号截断，无横向溢出 |
| 文档与记录 | `.env.example`、05/08、Agent Note 三件套、flow issue scope/adr 同步 |

## §2 架构导览

### 2.1 配置层：默认值与归一化都在 `Settings`

`config.py:25-26` 定义 `DEFAULT_BRAND_NAME` / `DEFAULT_BRAND_SUBTITLE`，`config.py:179-180` 把它们设为字段默认值，因此 `HE_` 前缀自动得到 `HE_BRAND_NAME` / `HE_BRAND_SUBTITLE`。真正让「空串不产生空品牌」的是 `config.py:241-256` 的 before 校验器：`None` 直接回落，字符串先 `strip()`，空结果再回落；非字符串原样交给 Pydantic 报类型错误。默认值不是在校验器里再写一遍字面量，而是从 `cls.model_fields[field_name].default` 取，避免同一文件内出现第二份文案。

### 2.2 HTTP 层：一个模型、一条路由、一个公开例外

`app_config.py:9-15` 与 `18-23` 定义 `AppConfigBrand` / `AppConfigResponse`，都设 `extra="forbid"`；`app_config.py:26-35` 的路由没有额外依赖，直接从 `request.app.state.settings` 读两个字段（`app.state.settings` 在 `main.py:689` 注入，和 `/api/health` 的取法一致）。返回注解 `-> AppConfigResponse` 让 FastAPI 自动生成 response schema，`main.py:757` 把它注册在 auth 路由之前。

公开边界在 `middleware/auth.py:66-68`：`_PUBLIC_API_PATHS`（`auth.py:15`）精确匹配后直接 `call_next`，因此无 token 的 GET 不会被 `AUTH_REQUIRED` 拦下。这个集合是精确字符串匹配，`/api/app-config/` 会先被 FastAPI 307 到无斜杠路径，和既有 `/api/health` 行为一致。

### 2.3 契约层：生成链是唯一事实源

`openapi.json:110` / `130` 是两个 schema，`openapi.json:11060` 是 path；`api.d.ts:2115` / `2125` 是生成类型，`api.d.ts:6690` 是 path 的响应引用；`index.ts:30` 只做对外导出并带 JSDoc。`contract:check` 本机实测无 diff，说明生成链没有被手改。

### 2.4 Web 客户端：严格的运行时校验

`api/appConfig.ts:6-9` 是构建期兜底常量；`14-26` 的 `isRecord` / `isBrand` 要求 `brand` 是对象、`name` 与 `subtitle` 都是 trim 后非空字符串；`28-37` 不合法时抛 `ApiError(status, "INVALID_RESPONSE")`；`43-47` 复用 `http.ts:196-202` 的 `request`，把校验函数挂在 `options.validate` 上（`http.ts:183-185`）。这层校验是必要的：服务端会归一化，但代理返回 HTML 或旧版 API 时，浏览器不能把 `undefined` 渲染成空品牌。

### 2.5 Store：单飞 promise、永不抛错、finally 写标题

`stores/appConfig.ts:13-16` 用 `ref` 保存品牌与 `isLoaded`，闭包变量 `loadPromise` 做单飞；`18-29` 成功覆盖、失败回落、`finally` 写 `document.title`；`38-41` 的 `load()` 用 `loadPromise ??= loadOnce()` 保证并发/重复调用只发一次请求。`document` 有 `typeof` 守卫（`6-10`），所以非浏览器测试环境不会炸。

### 2.6 装配顺序：品牌在路由与鉴权恢复之前

`bootstrap.ts:31-33` 的顺序是 `app.use(pinia)` → 取 store → `await load()`，然后才 `app.use(VueQueryPlugin)`、`installAuthRuntime`、`app.use(router)`，最后恢复登录态并 mount（`34-41`）。这保证任何品牌面首次渲染时 store 已经是最终值，不会先闪一下默认文案。注入缝 `loadAppConfig`（`bootstrap.ts:13`）让单测可以证明「加载发生在 mount 前」而不必真的打网络。

### 2.7 四个品牌面与截断

顶栏 `TopNav.vue:333` 的 `aria-label`、`342-343` 的 `<strong>` / `<small>` 读 store；CSS 在 `555-568` 给 `.brand-copy` 加 `min-width: 0`、`max-width: 220px` 与两行省略号，`823-895` 的断点全部保留（1700 隐藏 `.tn-note`、1500 隐藏 `.tn-sub`、1100 隐藏副标题、640 隐藏整块文字只留标记）。登录页 `Index.vue:27-28` 读 store，`140-151` 补同样的截断；改密卡 `ChangePasswordCard.vue:76` 只换品牌名，`158-168` 补截断，`77` 的 `首次登录` 逐字未动。`index.html:7` 保留 `Harness Evolution` 作为 JS 执行前的标题兜底。

## §3 数据流走查

以「部署方在服务器 `.env` 写了 `HE_BRAND_NAME=Acme Diagnostics`，重启 `harness-api`，用户打开登录页」为主线：

1. `harness-api` 启动，`Settings()` 从 `HE_` 环境读值；`normalize_brand_text` 把 `" Acme Diagnostics "` strip 成 `Acme Diagnostics`，未设置的副标题保留默认（`config.py:241-256`）。
2. `create_app` 把 settings 放进 `app.state.settings`（`main.py:689`），并注册 app-config 路由（`main.py:757`）。
3. 浏览器先拿到 `index.html`，`<title>` 暂时是 `Harness Evolution`（`index.html:7`）；`main.ts` 调 `bootstrapApp`。
4. `bootstrapApp` `app.use(pinia)` 后立即 `useAppConfigStore(pinia).load()`（`bootstrap.ts:31-33`）。
5. `load()` → `loadOnce()` → `fetchAppConfig()` → `request("/api/app-config")`（`stores/appConfig.ts:18-21`、`api/appConfig.ts:43-46`），实际发出 `GET /api/app-config`。
6. API 侧 `AuthMiddleware` 命中公开集合直接放行（`auth.py:66-68`），路由从 settings 构造 `AppConfigResponse`（`app_config.py:26-35`），返回 `{"brand":{"name":"Acme Diagnostics","subtitle":"轨迹诊断与自进化"}}`。
7. 浏览器 `request` 解析 JSON 并调用 `decodeAppConfig`；`isBrand` 通过后返回 payload（`http.ts:183-185`、`apps/web/src/api/appConfig.ts:28-37`）。
8. store 写 `brand.value`、`isLoaded = true`，`finally` 把 `document.title` 设为 `Acme Diagnostics`（`stores/appConfig.ts:20-28`）。
9. `bootstrapApp` 继续安装 VueQuery、auth runtime、router，恢复登录态后 mount（`bootstrap.ts:34-41`）。首次渲染时顶栏 `aria-label` / 品牌文字、登录左栏、改密卡品牌名、标题都已是配置值。
10. 长品牌名在顶栏被 `max-width: 220px` 与省略号收住（`TopNav.vue:555-568`），在登录页被列宽与省略号收住（`Index.vue:140-151`）；≤640px 顶栏只画标记（`TopNav.vue:854-866`），390px 无横向溢出。
11. 失败分支：网络错误、非 2xx、非法 JSON、字段不合法都会在 `loadOnce` 的 `catch` 里落到 `DEFAULT_BRAND`，`finally` 仍写默认标题，然后照常 mount（`stores/appConfig.ts:23-28`）。

## §6 讨论点

### D1 常驻架构文档的「公开端点」清单已经过期

- **位置**：`docs/architecture.md:27`、`docs/architecture.en.md:27`（同族：`plans/fullstack-design/04-backend-architecture.md:279`、`plans/fullstack-design/07-backend-implementation.md:1502`）

### D2 挂载被 app-config 请求串行阻塞，且请求没有超时

- **位置**：`apps/web/src/bootstrap.ts:31-33`、`apps/web/src/stores/appConfig.ts:18-29`、`apps/web/src/api/appConfig.ts:43-47`
- **现象**：`bootstrapApp` 在 `app.use(pinia)` 之后 `await` 品牌加载，成功或失败都完成之后才继续装 router 与 mount；`fetchAppConfig` 走 `request`，`fetch` 没有 `AbortSignal`，`http.ts:142` 会一直等到底层网络栈超时。
- **问题**：issue 验收标准 4 要求「接口异常或响应不合法时应用仍可加载」；「异常」如果是网络挂起（网关黑洞、API 不接受连接但不 RST、移动网络半开），promise 既不 resolve 也不 reject，页面会停在白屏，默认文案也不会出现。当前只覆盖了「快速失败」和「响应不合法」，没有覆盖「慢/挂起」。这与其他页面的数据请求不同：那些请求发生在 mount 之后，慢只会让局部 loading，不会挡住整个应用。
- **预判**：两种修法都合理：给 app-config 单独加 2-3s `AbortSignal.timeout`（`request` 已接受 `RequestInit`，只需在 `fetchAppConfig` 传入 signal，超时后走 `NETWORK_ERROR` 回落），或者在 Note 里显式承认「首帧与 API 可用性绑定」并记录取舍。前者改动小、与验收 4 更一致；代价是多一个魔法数字。无实害的前提是 API 与 Web 同源且同时可用，生产重启窗口内首屏白屏的风险真实存在但短暂。
- **结论**：

### D3 默认品牌存在三份副本，Note 对「测试防漂移」的表述过强

- **位置**：`apps/api/app/config.py:25-26`、`apps/web/src/api/appConfig.ts:6-9`、`apps/web/index.html:7`、`.agents/notes/implemented/feature/2026-11-25-brand-env-config.md:24`（英文侧同义）

- **结论**：

### D4 E2E 的 Windows 专用数据目录把 SQLite 写进仓库根目录

### D5 首次加载失败后整个 SPA 生命周期不再重试品牌

- **位置**：`apps/web/src/stores/appConfig.ts:16`、`38-41`
- **现象**：`loadPromise` 在第一次调用时被赋值并永久保留；失败时 `loadOnce` 内部 catch 后正常 resolve，因此后续 `load()` 直接复用已完成的 promise，不会再次请求。
- **问题**：如果用户正好在 API 重启的几秒内打开页面，品牌会在整个会话里停在默认值，即使 API 随后恢复；刷新页面才能拿到配置品牌。对「配置品牌」的部署，这等于一次瞬时故障放大成整段会话的品牌错误。
- **预判**：单次加载是 issue 的明确要求（「在挂载前拉取一次」），所以这不是验收违规；但「一次」指成功路径更合理。可在 `catch` 里把 `loadPromise = null` 允许后续调用重试（当前没有调用方会重试，所以实际仍需某个重试触发点），或者 Accepted 并在 Note 里写明「失败即本次会话使用默认」。当前无实害（品牌是展示层），属边缘可用性。
- **结论**：

### D6 公开端点没有缓存头，每次页面加载都会打一次 API

- **位置**：`apps/api/app/api/app_config.py:26-35`
- **现象**：响应没有 `Cache-Control` / `ETag`，浏览器每个新页面加载都会重新 `GET /api/app-config`。
- **问题**：品牌配置只在 API 启动时变化，天然适合 `Cache-Control: public, max-age=…` 或至少 `no-cache` 语义；当前默认依赖浏览器启发式，行为不确定。若未来在 nginx 前加缓存层，没有显式头的 200 JSON 可能被缓存到重启之后，出现「后端已换品牌、浏览器仍旧名」。另一方面，公开端点被高频请求也无鉴权成本，当前量级无实害。
- **预判**：本轮可不改；如果改，给 `Cache-Control: no-cache`（每次复用前校验）或 `public, max-age=300` 并在部署文档说明重启后最多 5 分钟旧名。属设计取舍，建议记在 Note 或后续 ticket，而不是阻塞本 PR。
- **结论**：

### 9.1 `apps/api/app/config.py`（M）

职责：环境变量 → `Settings` 的唯一入口。变更形态：在 `web_base_url` 与 `auth_provider` 之间插入两个品牌字段，新增两个模块常量与一个 before 校验器。

关键依赖：`pydantic-settings` 的 `env_prefix="HE_"` 负责把字段名映射成环境变量，`BeforeValidator` / `field_validator(mode="before")` 在类型校验之前拿到原始字符串；`cls.model_fields[...]` 是 Pydantic v2 的字段元数据，用来复用默认值而不复制文案。

旧代码（`main`）：

```python

    web_base_url: str | None = None
    auth_provider: AuthProviderName = AuthProviderName.PASSWORD
```

新代码（节选，`...` 表示省略的相邻字段与校验器）：

```python
DEFAULT_BRAND_NAME = "Harness Evolution"
DEFAULT_BRAND_SUBTITLE = "轨迹诊断与自进化"

...
    brand_name: str = DEFAULT_BRAND_NAME
    brand_subtitle: str = DEFAULT_BRAND_SUBTITLE

...
    @field_validator("brand_name", "brand_subtitle", mode="before")
    @classmethod
    def normalize_brand_text(cls, value: object, info: ValidationInfo) -> object:
        """Treat blank brand overrides as unset and trim configured text."""
        field_name = info.field_name
        default = (
            cls.model_fields[field_name].default
            if field_name is not None and field_name in cls.model_fields
            else ""
        )
        if value is None:
            return default
        if isinstance(value, str):
            normalized = value.strip()
            return normalized or default
        return value
```

这在做什么：`HE_BRAND_NAME=""`、`HE_BRAND_NAME="   "` 与字段缺省最终都得到默认文案；正常值两侧空白被去掉。为什么这么写：把「空」的判定收在一处，API、测试与未来调用方共享同一语义，同时不在校验器里再写一遍默认文案。

实现思路总结：字段默认值提供兜底，before 校验器只做「归一化 + trim」，类型错误仍交给 Pydantic。

检视发现：无长度上限（D7）；默认值仍是 API/Web 双份（D3）。

### 9.6 `apps/web/src/stores/appConfig.ts`（A）

职责：品牌状态的唯一 owner，负责加载、回落与标题。变更形态：新文件，44 行。

关键依赖：Pinia setup store（`defineStore("appConfig", () => …)`）；`ref` 自动解包，组件里写 `appConfig.brand.name`；`document` 用 `typeof` 守卫。

新代码：

```ts
const brand = ref<Brand>({ ...DEFAULT_BRAND });
const isLoaded = ref(false);
let loadPromise: Promise<void> | null = null;

async function loadOnce(): Promise<void> {
  try {
    const response = await fetchAppConfig();
    brand.value = response.brand;
    isLoaded.value = true;
  } catch {
    brand.value = { ...DEFAULT_BRAND };
    isLoaded.value = true;
  } finally {
    applyDocumentTitle(brand.value.name);
  }
}

async function load(): Promise<void> {
  loadPromise ??= loadOnce();
  await loadPromise;
}
```

这在做什么：第一次 `load()` 发请求，后续调用复用同一个 promise；成功覆盖、失败回落；无论哪种都写标题。为什么这么写：品牌是全局单例，不应在四个组件里各发一次请求；`finally` 保证「失败也有标题」，避免标题停在 `index.html` 的旧值。

实现思路总结：单飞 + 全捕获 + `finally` 收尾，组件只读状态。

检视发现：失败后不重试（D5）；`isLoaded` 目前只被测试读取，生产无消费者（nit）；无超时（D2）。
