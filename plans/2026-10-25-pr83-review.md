## §2 架构导览

### 2.1 从事实源到数据库

`fixture_corpus.py:299-409` 先解析 manifest，再逐 agent 读取 JSONL。payload 文件必须位于 corpus 根目录内，单项 32 KiB、总 payload 128 KiB 有上限，内容哈希与行数由字节推导，不接受手写冗余值。

`fixtures_seed.py:126-130` 把整个 corpus 写库放在一个事务里；先 payload 与 `source_records`，再 `session_families`，然后按深度写 `agents`，最后写事件、用户轮次、问题和目标。这个顺序满足外键依赖，任一写入异常会整体回滚。

生活化比喻：先把“原始录音带”入库，再建立索引卡、会话树和争议记录；不是先拼一棵只在内存里成立的假树。

### 2.2 稳定键 upsert

`fixtures.py:48-74` 明确每张表的稳定键，并把运行态字段标成 insert-only：

- `source_records.processed_* / last_sync_run_id` 只能在首次插入，重跑 seed 不覆盖。
- `evolution_targets.created_by` 只在目标首次出现时赋值。
- 其他 fixture-owned 字段在内容变化时原位更新，主键不变。

这解决了一个真实风险：后续归一化已经把 payload 标成处理完成后，演示 seed 再跑一次不能把进度清空。

### 2.3 冻结迁移

`0004_domain_fixtures.py` 在 revision 内显式创建 11 张表、索引与 FK，不遍历当前 Python 模型 metadata。以后领域模型增加字段时必须新增 revision，旧库升级和新库建库才不会得到不同 schema。

### 2.4 测试分层

`test_fixture_corpus.py` 的主要价值不是“有 12 个测试”，而是把五种故障放在该层：

```text
静态 corpus  → schema/未知字段/路径/大小/JSONL
SQLite 真库  → 事务、幂等、变更新增、运行态保留
schema 反射  → FK、ULID 类型、迁移 head
CLI          → 确定性 JSON 输出、单行失败
GitHub CI    → MySQL 8.4 再跑同一约定
```

## §3 数据流走查

### 场景 A：CI 从空库 seed

1. `pnpm fixtures:check` 调 Node bridge，再调 `python -m app.cli fixtures-check`。
2. loader 读取 `corpus.json` 和 7 份 JSONL，拒绝未知文件与超限内容。
3. `pnpm fixtures:seed` 在 runner 临时目录创建 SQLite 文件。
4. CLI 识别 `scope=m2-synthetic`，升级到 `0004`。
5. 单事务写入 44 行，二次执行返回 `0 inserted / 0 changed`。
6. `test:api` 和 MySQL job 再验证 repository 与 schema，而不是只看退出码。

### 场景 B：归一化后再次 seed

1. 归一化把 `source_records.processed_at/processed_hash/parser_version/last_sync_run_id` 填好。
2. fixtures 再次执行，`_INSERT_ONLY_COLUMNS` 让这四个字段不进入 update payload。
3. 结果应为 `changed=0`，处理后状态保留。

### 场景 C：fixture 内容变化

1. 修改 manifest 的会话标题。
2. 稳定键命中原行，只更新 fixture-owned 字段。
3. 主键、会话内 agent 关系和归一化处理态保持；结果报告 `changed>0`。

### 场景 D：异常输入

1. 未知字段由 Pydantic `extra=forbid` 拒绝。
2. payload 路径逃逸、未登记文件、非法 JSONL、超预算内容在开库写入前失败。
3. 生产环境或 `phase=live` 在打开数据库前失败。

## §6 讨论点

### D1（P1）数据卫生门禁只识别少数本地路径和密钥形态

**位置**：`apps/api/app/fixture_corpus.py:20-24,305-306,359-362`；`fixtures/m2-synthetic/corpus.json:417`

**现象**：`PRIVATE_MARKER` 只匹配 `/Users/`、`claude-code-sessions`、`.claude/`、`sk-ant-`、Bearer 和几个 `HE_*` 名字。我把 fixture 的 project path 改成 `/home/alice/private`，把 `repoUrl` 改成 `https://user:secret@example.invalid/...`，`load_fixture_corpus()` 两次都接受。Windows 用户目录和常见 URL 凭据同样不在门禁内；`repo_url` 模型也只校验长度。

**问题**：PR 声称拒绝真实路径和密钥，但覆盖范围不足。演示 fixture 一旦被误改成 Linux/Windows 本地数据或带凭据的仓库地址，`fixtures:check` 会放行并最终进入提交与 CI 日志。

**预判**：应在 schema 层限制 `projectPath` 为固定 synthetic 根，例如 `/workspace/`，并拒绝任何 URL userinfo、query secret 和所有常见用户目录（`/home/`、`C:\Users\`）。这是数据卫生缺陷，建议合入前修。

**结论**：

D1 已修复（2026-10-25）：项目路径限定为合成 `/workspace/` 根，常见 Linux/Windows/UNC 本地路径与 URL 凭据在 loader/schema 层拒绝；安全合成 URL 仍通过。

### D2（P2）JSONL 只验证“是对象”，没有绑定 session/agent，也不拒绝重复键

**位置**：`apps/api/app/fixture_corpus.py:285-291`

**现象**：loader 对每行只做 `json.loads` 和 `isinstance(dict)`。我把主会话 payload 的 `sessionId` 改成另一个合法 UUID，检查仍通过；把同一行写成两个 `sessionId` 键，Python 静默采用最后一个，检查也通过。PR body 却声称会拒绝 duplicate keys。

**问题**：manifest 说 payload 属于 agent X，内容却可声称来自 session Y。seed 会按 manifest 建关联，后续归一化首次读 payload 才发现不一致或更糟地产生错配数据。重复键则让人工审阅看到的 JSON 与解析结果可能不同。

**预判**：在 `_load_payload` 接收期望的 root/agent id，使用 `object_pairs_hook` 拒绝重复 JSON 键，并逐行验证 `sessionId` 与可选 `agentId`；未知/缺少身份字段也应失败。应补真实 JSONL 回归，而不是只测重复业务 ID。

**结论**：

D2 已修复（2026-10-25）：JSONL 使用嵌套 `object_pairs_hook` 拒绝重复键，每行 `sessionId` 必须匹配 manifest，子 Agent 还必须声明匹配的 `agentId`。

### D3（P2）两条主 agent bad case 使用了非 null 锚点

**位置**：`fixtures/m2-synthetic/corpus.json:325,340`；设计 `plans/fullstack-design/06-database-design.md:335`

**现象**：`badcase-synthetic-0003` 和 `0004` 的 `badCaseAgentId` 分别是主 agent id，设计了锚点：主 agent 应为 `null`，只有子 agent 使用真实 `agentId`。loader 的 `all_agent_id_set` 校验反而把主 id 当成合法值。

**问题**：fixture 数据与 API 的锚点契约不一致。后续 M4 直接消费这些行时，会把 `null → main` 的默认路径替换为显式主 agent 路径，导致测试掩盖真实装配分支或产生不同卡片宿主。

**预判**：将这两条改为 `null`，并在 loader 中禁止 `badCaseAgentId == badCaseSessionId`；测试应明确覆盖“主 agent 不重复写 root id”。

**结论**：

D3 已修复（2026-10-25）：两条主 Agent 问题的 `badCaseAgentId` 改为 `null`；loader 拒绝主 Agent 或跨会话子 Agent 锚点。

### D4（P2）re-seed 会改写 source_records.received_at

**位置**：`apps/api/app/db/crud/fixtures.py:64-74,152-165`

**现象**：`received_at` 未列入 insert-only。我先把一条 `source_records.received_at` 改成 2025-01-01，再跑同一 corpus，结果 `changed=1` 且时间被覆盖回 fixture 的 `importedAt`（2026-10-20）。

**问题**：设计把 `received_at` 定义为“首次发现该 payload 的时间”，这是审计事实。即使 manifest 改了 `importedAt`，重跑 seed 也不应改写已经发生的首次接收时间。

**预判**：把 `received_at` 加入 `_INSERT_ONLY_COLUMNS`，新增“修改 received_at 后 reseed 保留”的回归。其他运行态字段已用同样方式保护，修改很小。

**结论**：

D4 已修复（2026-10-25）：`received_at` 进入 insert-only 集合，已有首次发现时间在重复 seed 后保持不变。

### D5（P3）CI 的 fixture seed 没有重复执行

**位置**：`.github/workflows/ci.yml:39-45`

**现象**：CI 只执行一次 `fixtures:seed`。测试代码覆盖了二次执行，但部署命令行本身的连续调用依赖 test:api，不是 CI step。

**问题**：无实害；当前已有真实 pytest 覆盖，重复 command smoke 主要是多一层接线证据。

**预判**：无需单独修；若后续改动 Node bridge/环境缓存，可在同一 CI step 再跑第二次并断言 `noop`。

**结论**：

无需修（2026-10-25）：真实 pytest 已连续 seed 两次并断言第二次零写入；CI 的同一条命令链路不提供更多状态覆盖，保留现有更接近存储层的断言。

## §9 文件级代码分析

### `fixtures/m2-synthetic/corpus.json`（A）

职责：描述四根会话、8 个节点、4 个问题、4 条归因状态、2 份 probe 与 1 个进化目标。

实现思路：所有时间固定为 Asia/Shanghai，project path 使用 `/workspace/*`，payload 以显式文件路径关联。四棵树分别覆盖普通子任务、workflow+worker、forked skill 和最小主会话。

检视发现：D1、D3。另有一个正向设计：workflow 节点声明无 payload 且四项统计为 0，符合合成节点口径。

### `fixtures/m2-synthetic/payloads/*.jsonl`（A）

职责：保存 7 个有转录 agent 的原始 JSONL。

实现思路：内容是最小 Claude-like 事件序列，足以让后续解析器练习 user、assistant、usage、tool_use、tool_result、Skill/Workflow 触发；不存真实 prompt 或本机路径。

检视发现：D2。文件体积总计 2,841 bytes，远低于预算；会话统计与 JSONL 当前手工一致，但 loader 尚无自动交叉校验。

### `apps/api/app/fixture_corpus.py`（A）

职责：manifest schema、关系校验、JSONL 读取、容量限制与数据卫生检查。

关键依赖：Pydantic v2 提供 alias、`extra=forbid` 和嵌套模型验证；`pathlib.Path` resolve/is_relative_to 阻止路径逃逸；SHA-256 给 payload 稳定身份。

实现思路：先验证 manifest，再逐文件装载 payload，最后验证问题/归因/目标之间的交叉引用。错误在数据库打开前抛出，因此 CLI 可以给单行诊断。

检视发现：D1、D2。正向点是错误路径和未登记文件都 fail-closed，且四个 root 与 agent id 的唯一性有检查。

### `apps/api/app/fixtures_seed.py`（A）

职责：只暴露 seed facade，不把 CLI 细节泄漏给业务模块。

实现思路：小型 `__all__` 门面让 CLI 依赖稳定接口，未来 scheduler/test helper 也能复用同一 seed 能力。

检视发现：无。

### `apps/api/app/db/models/domain.py`（A）

实现思路：SQLAlchemy Core Table 而非 ORM 类，显式列、JSON、BigInteger SQLite variant、LONGTEXT MySQL variant、FK 和索引。它适合 repository 直接构造表达式，也减少 ORM 隐式加载。

检视发现：D4 指向 `source_records` 的 upsert 语义，不是列本身；schema 字段、FK 与索引整体符合设计。
