## §1 一页速览

**一句话**：给「读知识文档」这件事补上证据链——只有配置过的知识根目录内、或白名单 MCP 知识工具返回的文档，才会变成一条 `kind=knowledge` 的事件；事件只记书名、版本、书架号（id/revision/path/scope），不抄内容。

**一个比喻**：知识根像图书馆的「在册分馆平面图」。只有从登记在册的分馆书架上拿的书，才算一次「知识借阅」（`Read` 命中 roots）；馆外大厅里随手翻的源码不算（普通 `Read` 不产事件）；从馆际互借单（MCP `search/retrieve`）上列来的书直接算借阅。系统只在借阅台账上登记「哪本书、第几版、在哪个分馆的哪个架位」，正文一个字不抄——所以台账可以给审计看，不能给盗版商看。

## §2 架构导览

这一层讲「零件怎么拼起来」。整体是五段式：**配置 → 识别 → 证据落库 → 重放取范围 → 查询暴露**，每段之间只通过一个数据形状交接（`tuple[str, ...]` 的 roots、`ParsedEvent`、`agent_events` 行、`SessionEvent` DTO）。

### 2.1 配置层：知识根是空间的一个字段，不是一张新表

根被刻意塞进已有的 `workspaces` 行（`db/models/workspace.py:30`，`JSON NULL`），而不是独立表：这样复用现成的 `PUT /api/workspaces/{wid}` 权限模型和迁移，不用新端点、不用新外键。代价是 roots 只能整组读写，无法按根做行级审计。

归一化的唯一入口是 `utils/knowledge_paths.py:54`：

- **规范形式**（`_canonical_root`，`knowledge_paths.py:35`）：绝对路径、反斜杠转正斜杠、折叠重复斜杠、去尾斜杠、拒绝 NUL 与 `..` 段；`/` 单独保留（`:51` 的 `rstrip("/") or "/"`）。
- **数量/长度**（`:15-22`）：每空间 ≤20 条、每条 ≤512 字符；去重在归一化后做（`:62`），所以 `"/kb"` 与 `"/kb/"` 只算一条。
- **匹配**（`match_knowledge_root`，`:80-99`）：先规范化候选路径，再按**段边界**比：`/kb` 命中 `/kb/a.md`，不命中 `/kb2/a.md`（`:96`）；多个命中取最长（`:97`），支持嵌套根 `/kb` + `/kb/team`。
- **文档身份**（`knowledge_document_id`，`:102`）：`doc:` + sha256(根相对路径)[:32]，只吃路径不吃内容，所以正文永远不落库。

配置写入走 `WorkspaceService`（`service/workspaces/service.py:196` 建空间、`:240` 改空间），校验失败统一抛 `422 KNOWLEDGE_ROOTS_INVALID`，details 只有 `{"reason": ...}`（`:481-486`）——不回显路径是刻意的隐私选择，值得保留。

**读的路径**：`WorkspaceRecord.knowledge_roots` 在 `_workspace_from_row` 里由 `_knowledge_roots`（`crud/workspaces.py:133`）把 JSON 解成 `tuple[str, ...]`；`_workspace_dto`（`service/workspaces/service.py:512`）再把它原样塞回 API 响应。

### 2.2 识别层一：Read 的「门禁」在 parser 里，不在采集器里

关键设计：**不是**在采集/入库时判断路径，而是在 parser 解析 JSONL 时判断。`TracePayload.knowledge_roots`（`parsers/base.py:125`）随 payload 进入解析器，`finalize` 后事件已经带上坐标，落库时不需要回查任何配置。这保证「同一份 payload + 同一份 roots ⇒ 同一批事件」，重放可复现。

`Read` 的判定链（`claude_code.py:478-494`）：

1. 结果记录里每个 `tool_result` block 先入队（`:463-469`），并关闭 open tool；
2. 若该记录有 `toolUseResult`，`_file_evidence`（`:301`）抽出 `filePath / content / startLine / numLines / totalLines`；
3. 只有 `tool_name == "Read"` 才进 `_record_file_knowledge`（`:491-492`）；
4. `_record_file_knowledge`（`:528-546`）用 `match_knowledge_root` 判命中；命中才产事件：`retrieval_kind=file_read`、`retrieval_scope=命中的根`、完整读 `document_revision=digest:<sha256(content)>`、不完整或内容缺失 `unknown`（`:536-537`）。

`Edit` / `Bash` 在 `:491` 这一层就被 `tool_name == "Read"` 挡掉，所以「普通源码 Read、Edit、Bash 不产生事件」不是靠路径判断，而是靠**工具名 + 根匹配两道闸**。

坐标的巧处：事件是在**结果行**（可能晚很多行）才 Append 的，但坐标必须取**调用行**。`record_tool_use` 在调用时把 `ToolCallPosition`（`base.py:96-102`）存进 `tool_call_positions`（`:335-339`），结果到达时 `record_knowledge_event` 按 `tool_use_id` 取回（`:474`）。这就是为什么测试里「先发 skill 调用、后发 Read 结果」仍然得到 `knowledge` 在前（`test_knowledge_read.py:364-397`）。

### 2.3 识别层二：MCP 是显式白名单，不做「名字里有 knowledge 就算」

`knowledge.py` 的存在理由是「不同 Provider 的工具命名没有统一约定，模糊匹配会误判」。所以：

- 白名单是 6 个**精确字符串**（`knowledge.py:98-105`），映射表在 `:108-110`，查询函数 `knowledge_adapter_for`（`:113`）只做 dict 精确命中；
- `mcp__knowledge__search` / `mcp__kb__retrieve` 分成两个 adapter，用 `retrieval_kind` 区分 `mcp_search` / `mcp_retrieve`（`:84-95`）；
- 结果解析器 `McpKnowledgeAdapter.parse`（`:54-70`）容忍三种形状：单 JSON 对象、`{documents|results|items: [...]}` 信封、NDJSON（`:120-155`）；字段别名覆盖 `id/documentId`、`path/sourcePath`、`revision/version/digest/contentHash`、`title/name`、`collection/collectionId`（`:26-31`）；
- 只读身份字段，正文键（`content`/`text`）从不碰；坏 JSON、空结果、非对象记录一律返回空 tuple，不抛异常、不产 issue（测试 `test_knowledge_mcp.py:213-224`、`:336-347`）。

**为什么每条文档一条事件**：一次 `search` 可能返回 20 篇文档；若合成一条，后续归因无法指向具体文档。代价是同一个 `tool_use_id` 对应多条事件，这会撞上 `agent_tree` 的「tool id 唯一」bookkeeping（`agent_tree.py:523-542` 用 `tool_events` 检测 `DUPLICATE_TOOL_USE_ID`），所以那里显式 `continue` 跳过 knowledge——这是本 PR 里最容易看漏、但必须存在的一行（`:527-530`）。

### 2.4 证据层：5 个可空列，不新建表

选择加列而不是建 `knowledge_events` 表，理由是「事件已经是触发点的统一形状，按 kind 分表会让 Session tree 的读取路径分叉」。代价是 `agent_events` 变宽、且知识专属字段对其它 kind 恒为 NULL（`models/domain.py:252-256`）。

索引 `(agent_id, kind, document_id)`（`:262-267`）支撑「某 agent 读过哪些文档」的最左前缀查询；`agent_id` 在最左，所以不会拖慢既有的按 agent 读事件。

迁移 0019（`alembic/versions/0019_knowledge_document_triggers.py`）沿用 0016/0018 的**列存在性守卫**：

```python
# 旧：0018 之前直接 op.add_column（迁移中途失败后重跑会撞「列已存在」）
# 新：0019 先反射、只补缺失，并校验 nullability
existing = _existing_columns("agent_events")
current = existing.get(str(column.name))
if current is None:
    op.add_column(table, column)
elif bool(current["nullable"]) != bool(column.nullable):
    raise RuntimeError(...)
```

`:39-57` 的守卫让「MySQL DDL 自动提交、上次迁移中途失败」的场景可以重跑只补缺失列；nullability 不符时**大声失败**而不是留下半坏表（测试 `test_knowledge_migration.py:218-235`）。`:98-102` 在 SQLite 上用 `batch_alter_table` 重建表来 drop，规避 SQLite 不支持直接 drop 列。

### 2.5 重放层：roots 是「会话被谁上报」的函数

这是全 PR 最需要想清楚的一段。`list_workspace_knowledge_roots`（`crud/acquisition_replay.py:298-327`）的口径是：

```
bad_cases WHERE bad_case_session_id = :root
   → DISTINCT（workspace id + knowledge_roots）
   → workspaces.knowledge_roots 并集
   → normalize_knowledge_roots()
```

为什么取并集而不是「主空间」：一个根会话可能被多个空间上报，各自配置不同根；只取一个会漏证据（Agent Note 已把这条写进 Alternatives）。代价是**证据范围与会话绑定、而不是与空间绑定**——`agent_events` 没有 workspace 列，所以同一批 knowledge 事件对所有能看见该会话的空间都可见（§6 D4）。

`replay.py:206-211` 对每个 root 只查一次 roots，再传给该 root 的全部 payload，保证一次重放内配置一致（不会出现父 agent 用旧 roots、子 agent 用新 roots）。失败兜底是 `replay.py:259-269` 的 `except Exception → ROOT_REPLAY_FAILED`。

### 2.6 暴露层与前端

`SessionEvent`（`service/sessions/schemas.py:93`）新增 5 个 `exclude_if=_missing` 的可选字段（`:130-159`）；`kind` 枚举加 `knowledge`（`:12`）。`exclude_if=_missing` 意味着非知识事件的响应体字节不变——这是旧客户端兼容的关键，不是装饰。

前端**没有任何业务代码改动**：`SessionEvent["kind"]` 被 `ChainItem`（`components/agent-tree/types.ts:16-29`）直接当作联合类型，`layout.ts:193-200` 用 `kind` 做 pill 的 class，`AgentNode.vue:85-99` 用同一个字符串渲染 `<span class="rf-cnode knowledge">`。所以「未知 kind 通用渲染」在**功能**上成立；但样式表只给 `.skill/.agent/.workflow` 上了色（`AgentNode.vue:281-299`），图例也只有三项（`SessionOverview.vue:278-286`），知识 pill 会是「无色无边框的裸 pill」——功能能看，视觉上是缺口（§6 D8）。

## §6 讨论点

> 每条固定五段：位置 / 现象 / 问题 / 预判（供拍砖）/ 结论（留空给维护者）。

### D1 合法配置的根长度 512 与存储/DTO 的 255 冲突

- **位置**：`apps/api/app/utils/knowledge_paths.py:18`（`MAX_KNOWLEDGE_ROOT_LENGTH = 512`）→ `apps/api/app/service/acquisition/parsers/claude_code.py:545`（`retrieval_scope=root`）→ `apps/api/app/db/models/domain.py:256`（`retrieval_scope VARCHAR(255)`）→ `apps/api/app/service/sessions/schemas.py:154-159`（`max_length=255`）
- **现象**：配置一个 304 字符的绝对路径根（`≤512`，校验通过）。`retrieval_kind=file_read` 的事件把**根**写进 `retrieval_scope`。实测（`apps/api/.venv` 内直接构造）：`SessionEvent(..., retrievalScope=root)` 抛 `ValidationError: String should have at most 255 characters`；而 SQLite 对 `VARCHAR(255)` 不做长度校验（实测插入 304 字符成功）。
- **问题**：两条真实后果——① MySQL 严格模式下 `INSERT` 报 `Data too long`，`replace_normalized_root` 抛错 → 该 root 整根重放失败（`ROOT_REPLAY_FAILED`）；② SQLite 上静默存进 304 字符，随后 `GET /api/sessions/{id}/tree` 在 `_agent()` 里构造 `SessionEvent` 时就抛 `ValidationError` → 未捕获 → **500**。也就是说同一份合法配置，在两种方言上给出两种坏结果。`source_path`（列 1024 / DTO 1024）对超长绝对路径也是同类问题，只是更难触发（Linux `PATH_MAX=4096`，macOS 1024）。
- **预判**：这是本 PR 唯一的「合法输入直接打断读接口/重放」的实质缺陷，修复面很小，建议合并前处理。三种修法任选：a) 把 `MAX_KNOWLEDGE_ROOT_LENGTH` 降到 255（但 512 是设计文档写死的）；b) 把 `retrieval_scope` 列与 DTO 一起放宽到 512；c) 写入前截断 scope 到 255（会丢证据完整性）。我倾向 b（配置限制与存储一致），若担心索引/宽度则 a 并同步 05/06/07 与 Agent Note。
- **结论**：已拍板：把 `retrieval_scope` 列与 DTO 一起放宽到 512（配置上限与存储一致），补 304 字符合法根的 replay + `GET /sessions/{id}/tree` 回读测试；否决降到 255 与写入前截断。

### D2 配置变更不会触发重放，且 PR 点名的补数命令补不上

- **位置**：`apps/api/app/db/crud/acquisition_replay.py:176-191`（`_pending_condition`：只认「无 cursor / hash 变 / parser_version 旧」）→ `apps/api/app/service/acquisition/replay.py:308-321`（`replay_local_payloads` = 先 import 再 `replay_pending_payloads`）→ `apps/api/app/service/workspaces/service.py:240-257`（改 roots 只 update `workspaces` 行，不触碰 `source_records`）
- **现象**：会话在 parser 5 下已经归一化过一次（`processed_hash == payload.content_hash`、`parser_version == 5`）。此时管理员把 `/kb` 加进 roots：`source_records` 没有任何变化，`_pending_condition` 为假，该 root 永远不是 pending。`pnpm data:replay:sessions`（`scripts/local-sessions.mjs` → `replay-local`）先 import 本地文件，内容未变 → hash 不变 → 仍然 pending 为空。PR 的「已知限制」写「需 `pnpm data:replay:sessions` 或下一次归一化」，对 parser-4 存量成立，对 **parser-5 且 payload 未变** 的会话不成立。
- **问题**：最自然的操作顺序（先导入历史会话 → 再发现并配置知识根）下，知识事件**永远不会**出现，而且没有任何报错或状态提示。这不是「重放慢」，是「没有入口」。对首次上线尤其明显：升级后 replay 会把 parser-4 全量补一遍，但补的时候 roots 还没配（新字段），补完即定型。
- **预判**：功能可用性上的实质缺口，接近 Blocker 但不是数据损坏。最小成本是「改一行 + 写一条 runbook」：在 `update_workspace` 里当 `knowledge_roots` 变化时把该空间的 `source_records` 标记为 stale（例如把该空间上报根的 `parser_version` 置回 `None`/旧值，或加一个 `needs_replay` 标志），或者在 07 里明确写「先配 roots，后入库」并把 PR 的已知限制改准。若本 issue 不想扩范围，至少要把那句错误的补数指引改掉，否则运维会照着做然后以为功能坏了。
- **结论**：已拍板：`update_workspace` 在 roots 集合实际变化时把该空间上报根的 `source_records.parser_version` 置 NULL（repository 负责，缺 `bad_cases` 表时安全跳过）；roots 未变（含仅顺序变化）不触发；同步改准 07/Note/PR 已知限制。

### D3 `object_revision` 的词汇被 MCP 原始 revision 打破

- **位置**：`apps/api/app/service/acquisition/parsers/base.py:486`（`object_revision=document_revision`）→ `apps/api/app/service/acquisition/knowledge.py:183`（`revision = … or "unknown"`，不做前缀归一）→ 文档冲突：`plans/fullstack-design/05-api-design.md:188`（`objectRevision` = `tag:<tag>` / `digest:<hash>` / `unknown`）、`plans/fullstack-design/06-database-design.md:268`（同）；而 `plans/fullstack-design/07-backend-implementation.md:162` 写「`object_revision` 同步为文档 revision」
- **现象**：M9-04 里 `object_revision` 是所有 kind 共享的**封闭词汇**：skill/agent 显式 tag → `tag:<...>`，body hash → `digest:<...>`，缺失 → `unknown`。M9-05 让 knowledge 事件直接复用 `document_revision`：文件读是 `digest:...`（合规）、partial 是 `unknown`（合规）、但 MCP 的 provider revision 是原样值——测试明确断言 `event.object_revision == "r7"`（`test_knowledge_mcp.py:285-286`）、`"v3"`/`"abc123"` 同理（`:181-188`）。
- **问题**：同一个字段在 DB/API 里有两种词汇。当前仓内没有按前缀解析 `object_revision` 的消费方（`_apply_agent_revisions` 只对 `kind=agent` 做 `startswith("tag:")`），M10 的 PotentialMatcher 也只按 `object_type=skill|agent` 过滤，所以**今天无实害**。但它把「`object_revision` 是封闭前缀词汇」这条契约悄悄破坏了，而 05/06 仍在承诺旧词汇——后续做「knowledge 成为可进化对象」的切片时会撞上。
- **预判**：不需要改行为，需要二选一并写清：a) 承认 knowledge 的 `object_revision` 是「provider 原始 revision」，把 05:188 与 06:268 改成 `tag:/digest:/provider-revision/unknown`（并在 `SessionEvent.object_revision` 描述里写明 knowledge 例外）；b) 让知识事件把 provider revision 归一成 `provider:<value>`，`document_revision` 保留原值。b 更干净但要重跑一条测试断言；a 更省。无论选哪个，建议别让 `object_revision` 和 `document_revision` 无条件同值——两个字段同时存在，本就表达了「语义不同」。
- **结论**：已拍板：取方案 b——`document_revision` 保留 Provider 原始 revision，`object_revision` 归一为 `provider:<value>`（文件读仍 `digest:`/`unknown`）；补两字段语义区分的测试与 05/06/07/Note 文案。

### D4 roots 并集 + 全局事件 → 共享根会话的跨空间可见（M10 承接）

- **位置**：`apps/api/app/db/crud/acquisition_replay.py:298-327`（并集）→ `apps/api/app/service/acquisition/replay.py:208`；可见性侧：`apps/api/app/db/crud/sessions.py:398-413`（会话按 scope 过滤）、`:436-449`（`agent_events` 无空间过滤）、`:455-460`（`bad_cases` 有空间过滤）
- **现象**：root 会话被空间 A（roots=`/kb-a`）与 B（roots=`/kb-b`）同时上报。重放时并集 `{/kb-a, /kb-b}` 生效，产生两组 knowledge 事件。B 的成员打开该会话 tree，能看到 `sourcePath=/kb-a/…`；A 的成员同理看到 `/kb-b/…`。这是 `agent_events` 无 workspace 列的结构性结果，不是实现疏漏。
- **问题**：泄露的不是正文，是**另一空间的知识库路径与文档存在性**；配合 `retrievalScope`，等于暴露了 A 的知识库目录结构。Agent Note 与 06 §7.5 已把这个口径写进决策（「查询层裁剪留 M10」），但文档只说「会带出多空间的知识证据」，没说「B 会看到 A 的路径」，验收方容易低估。

- **结论**：已拍板：接受本切片口径，M10 承接查询层裁剪；06 §7.5 与 Agent Note 明确写出「共享根会话的其他空间成员可见 sourcePath/scope（不含正文）」。

### D6 `document_id` 未用规范化路径，同一文档可能有两个身份

- **现象**：匹配阶段把路径规范化了（反斜杠→正斜杠、折叠重复斜杠、去尾斜杠），但派生 id 时用的是**未规范化**的原串。实测同一文件：

  ```
  "\kb\guides\a.md"        → doc:21496f55…   （匹配仍返回 "/kb"）

  "/kb//guides/a.md"       → doc:6e242b58…   （重复斜杠恰好被 lstrip 吸收）
  ```

- **问题**：`document_id` 的契约是「稳定文档身份」，但它对路径拼写敏感。Windows 风格 `filePath`（Claude Code 在 Windows 上会给反斜杠）会让**所有**文件读的文档 id 与 macOS/Linux 不同；带尾斜杠的路径会额外制造一个「假新文档」。对后续「按 document_id 聚合某文档被读了多少次」或「knowledge 成为对象」都是噪声。
- **预判**：Minor 但修起来极简：`_record_file_knowledge` 里对 `path` 先过 `_canonical_document_path`，或用 `match_knowledge_root` 返回的规范候选；同时 `source_path` 也建议存规范形式（现在存原串，可能出现同一文档两种 path 写法）。补一个「反斜杠/尾斜杠归一后 id 相同」的用例即可锁住。
- **结论**：已拍板：新增公开 `canonical_knowledge_path`，`knowledge_document_id`、`source_path` 与事件名统一基于规范路径；补反斜杠/重复斜杠/尾斜杠同一 id 与 >1024 字符截断测试。

### D7 知识根的两个校验边界：并集 20 上限与 `/` 根

- **位置**：`apps/api/app/utils/knowledge_paths.py:54-67`（`normalize_knowledge_roots` 在**并集**上再次执行 `MAX_KNOWLEDGE_ROOTS=20` 的检查，`too_many` 抛错）→ `crud/acquisition_replay.py:327`（并集直接调它）→ `replay.py:259-269`（`except Exception` → 整根失败）；`/` 根：`knowledge_paths.py:51`、`:93-94`、测试 `test_knowledge_read.py:141-144`
- **现象（并集超限）**：空间 A 配 11 条根、空间 B 配 11 条根，同一 root 会话被两者上报 → 并集 22 条 → `normalize_knowledge_roots` 在 index 20 抛 `KnowledgeRootError("too_many")`（实测复现）。该异常在 `replay.py:206` 的 try 内被 `except Exception` 吞成 `ROOT_REPLAY_FAILED`，**该 root 的 skill/agent/knowledge 事件全部不落库**，且错误信息不指向 roots 配置。
- **现象（`/` 根）**：`/` 被显式支持（`match_knowledge_root` 对 `root == "/"` 单独分支，测试断言 `normalize_knowledge_roots(["/"]) == ("/",)`）。一个空间管理员把 `/` 配成知识根，该会话里**所有** `Read` 都成为 knowledge 事件（源码、配置、`.env` 路径……）。路径会进 `source_path`，并因 D4 的并集口径可能被共享根会话的其他空间看到。
- **问题**：①「每空间最多 20 条」的约束被错误地施加在**跨空间并集**上，一个纯配置组合就能让重放整体失败，且失败原因不可诊断；②`/` 根是「全盘皆知识」的开关，校验层没有防呆（也没在 05 里说明这是允许的）。
- **预判**：①是实质缺陷，建议把「读路径的归一化」与「配置写入的限额校验」拆成两个函数（例如 `normalize_union` 不查数量，或超限时截断并记 issue），至少不要让一次配置把整根重放打死；错误码也应给出 `KNOWLEDGE_ROOTS_INVALID`/明确 issue 而不是通用 `ROOT_REPLAY_FAILED`。②建议在 05/Agent Note 里显式声明 `/` 的语义与风险，或在校验里拒绝 `/`（要求至少两级，如 `/kb`）——这属于产品取舍，需要维护者拍。
- **结论**：已拍板：读侧并集改用 `merge_knowledge_roots`（逐项归一化、去重、忽略非法项、不套 20 条上限），写侧仍保留 20 条；`/` 根在校验层拒绝，reason `too_broad`；补「两空间各 11 条根、并集 22 条 replay 成功」测试。

### D9 MySQL 验证声明与实际门禁覆盖不符

- **位置**：`scripts/run-api.mjs:18-19`（`db` = `tests/test_database.py -m "not mysql"`；`db-mysql` = `tests/test_database.py -m mysql`）→ `.github/workflows/ci.yml:190-223`（mysql lane 只跑 `pnpm test:db:mysql`）→ `apps/api/tests/test_database.py:1234-1320`（mysql 用例只断言 head=0019 与 `users`/`job_runs`/`sync_*` 的列与索引，**没有** `agent_events` 的 5 个新列、没有 `ix_agent_events_knowledge_document`、没有 `workspaces.knowledge_roots`）
- **现象**：PR 写「`pnpm test:db:mysql` 留给 CI mysql lane 验证（含 0019 的 JSON 列与索引）」「CI … mysql … 全部通过」。实际 CI 的 mysql lane 只会迁移到 head 并检查与 0019 无关的表；`test_knowledge_migration.py` 四个用例全部只跑 SQLite；`list_workspace_knowledge_roots` 的 SQL（`SELECT DISTINCT` 里含 **JSON 列**）从未在 MySQL 上执行过。
- **问题**：两个具体风险都没被覆盖：①`SELECT DISTINCT id, knowledge_roots … ORDER BY id` —— MySQL 对 JSON 列参与 `DISTINCT` 的历史行为与普通列不同（是否报错/如何比较取决于版本，本机无 MySQL，**未实测**，所以我只把它列为待验证项而不是缺陷断言）；②`workspaces.knowledge_roots` 是 MySQL `JSON` 类型，`list_workspace_knowledge_roots` 只接受 `isinstance(roots, list)`（`acquisition_replay.py:325`），而 `crud/workspaces.py:133-143` 的读者**同时兼容 str**——两处读取口径不一致，一旦 MySQL 驱动在该路径返回 JSON 文本，replay 会静默得到空 roots（不报错、不产事件），这是比报错更难查的失败模式。
- **预判**：这是「验证故事」的实质薄弱点，不一定是代码 bug。建议合并前至少做一件事：a) 在 `test_database.py` 的 mysql 用例里补 0019 的列/索引断言；b) 给 m9-05 replay 用例加 `@pytest.mark.mysql` 并在 CI mysql lane 跑它（`db-mysql` 的目标文件需要改，或新增 lane）；c) 若不想扩 CI，就在 PR 里把「MySQL 未验证 DISTINCT-JSON 路径」写进已知限制，并把 `list_workspace_knowledge_roots` 改成复用 `_knowledge_roots` 的读取口径。
- **结论**：已拍板：`list_workspace_knowledge_roots` 去掉 `SELECT DISTINCT`（SQL 只选 id+roots，Python 按 workspace id 去重），统一用 `decode_knowledge_roots`；`test_database.py` 的 mysql 用例补 `agent_events` 五列 + 索引 + `workspaces.knowledge_roots` 断言。

### D10 重放新增 `bad_cases` 硬依赖，失败码不指向根因

- **位置**：`apps/api/app/db/crud/acquisition_replay.py:307-315`（`bad_cases.join(workspaces)` 无条件执行）→ `replay.py:208`；失败兜底 `replay.py:259-267`（`ROOT_REPLAY_FAILED`）；测试侧代价见 `tests/m2-07-*`、`tests/m2-08-*` 的 `ensure_fixture_external_tables`
- **现象**：归一化以前只碰内部表；现在每个 root 都要 join `bad_cases`。在「外部问题侧表未建」的环境（`main.py:396` 启动迁移显式 `bootstrap_external_tables=False`，0004 迁移是按开关跳建 `bad_cases` 的），replay 会对每个 root 抛 `OperationalError: no such table: bad_cases`，被兜成通用的 `ROOT_REPLAY_FAILED`，看起来像「解析失败」，实际是 schema 缺失。这也是 m2-07/m2-08 两个测试必须补 bootstrap 的原因。
- **问题**：①归一化是全局管线，突然多了一个「问题侧 schema」依赖；②错误码不带原因，排障成本高；③同一份 roots 有两种读取实现（`crud/workspaces.py:133` 兼容 str，`acquisition_replay.py:325` 只认 list），长期会漂。
- **预判**：Minor（生产上 `bad_cases` 通常存在，因为空间额度/会话树也查它）。建议：查不到表/列时降级为「空 roots + 一条明确 issue」，而不是整根失败；把 roots 读取收敛到 `utils/knowledge_paths.py` 或复用 crud 的 `_knowledge_roots`；`ROOT_REPLAY_FAILED` 的 message 至少带异常类别（不含 SQL 文本）。
- **结论**：已拍板：replay 先探测 `bad_cases` 表并传入 roots 查询，缺失时降级空 roots（不让整根失败）；回退 m2-07/m2-08 不再需要的 bootstrap 补丁。

### D11 文档与实现的三处偏差（含 07 的路径优先级写反）

## §9 文件级代码分析

> 每个文件：职责一句 + 变更形态 + 关键依赖 + 变更块（旧 vs 新）+ 检视发现。M 文件前身用 `git show origin/main:<path>` 对照。

### 9.1 `apps/api/app/utils/knowledge_paths.py`（A，107 行）

**职责**：知识根的唯一定义处——规范形式、匹配、文档 id。被配置写入、parser、重放三方共用，保证「写进去的根」与「匹配用的根」是同一套规则。

**关键依赖**：只用标准库 `hashlib`/`re`；无第三方。比喻：它是图书馆的「书架编号规则手册」，配置员、借阅台、审计员都翻同一本。

**变更块**：整文件新增。四段结构清晰：`_canonical_root`（`:35-51`）→ `normalize_knowledge_roots`（`:54-67`）→ `match_knowledge_root`（`:80-99`）→ `knowledge_document_id`（`:102-107`）。写法上刻意「校验即归一化」：`_canonical_root` 一边拒绝（`..`/NUL/相对）一边改写（反斜杠/重复斜杠/尾斜杠），返回值就是落库值，避免「校验通过但存了另一种写法」。

**检视发现**：

1. **id 派生没复用规范化结果**（D6）：`knowledge_document_id` 拿原始 `path` 切片，与 `match_knowledge_root` 内部的 `_canonical_document_path` 不一致；尾斜杠/反斜杠会分叉身份。修法：让匹配函数返回 `(root, canonical_path)` 或对外暴露 `canonical_document_path`。
2. **数量上限施加在并集上**（D7）：`normalize_knowledge_roots` 同时承担「写配置的限额」与「读并集的归一化」，重放侧调用就会因跨空间并集超限而抛错。
3. `/` 根被显式支持（`:51`、`:93-94`），语义是「全盘皆知识」；是否允许属产品决定（D7）。
4. Windows 盘符路径（`C:/kb`）会被判 `not_absolute`，`_canonical_document_path` 同样拒绝——若将来在 Windows 跑 Claude Code，知识识别会整体失效。当前仓库部署目标是 macOS/Linux，无实害，建议在 docstring 写明「POSIX 语义」。

### 9.2 `apps/api/app/service/acquisition/knowledge.py`（A，202 行）

**职责**：MCP 知识工具的白名单与结果解析器。把「provider 返回的一段文本」压成 `tuple[KnowledgeDocument, ...]`，只保留身份字段。

**关键依赖**：标准库 `json`/`hashlib`/`dataclasses`。无第三方、无网络。比喻：它是「馆际互借单的读单员」——只抄单子上的书名/版次/馆藏号，书本身翻都不翻。

**变更块**（全新）：

```
旧：无
新：KnowledgeRetrievalKind(15) / KnowledgeDocument(34) / McpKnowledgeAdapter(46)
    _decode_documents(120) 单 JSON→信封→NDJSON 三级降级
    parse(54) 是唯一入口 → 去重排序 tuple
```

设计上有三个「不」值得记：不做模糊匹配（`:113` dict 精确命中）、不读正文键（`_document` 只取 id/path/revision/title/collection）、不抛异常（坏输入统一空 tuple）。

**检视发现**：

1. 去重键是 `(document_id, source_path or "", revision)`（`:67`）：同一 `id` 但一条带 path、一条不带，会被当成两篇文档（两条事件）。provider 混返两种形状时会产生重复证据，建议在 key 里把「path 缺失」与「path 存在」折叠（例如都按 `document_id` 优先）。
2. NDJSON 是「全有或全无」：任一坏行丢弃整批（`:150-151`）；而 JSON 数组里坏元素是逐个跳过（`:134`、`:137`）。两种策略并存本身没错，但值得在 docstring 里点明，避免调用方以为「坏行只是跳过」。
3. 无输入长度上限：`_tool_result_text` 把整个 MCP 响应读成字符串后才解析，100 条上限在解析之后。超大 provider 响应的内存峰值由上游决定；当前无实害，记一笔。
