## §1 一页速览

**一句话：** 这个 PR 给自进化 run 开了六个只读取件窗口（筛选/聚类/归因/排序/迭代/终评），每个窗口只回答"这一步现在能不能看、能看的话里面是什么"；能不能看不由窗口自己判断，而由 m5-01 那块唯一的进度牌（`progress_unit` 游标）统一决定。

**比喻：** 像档案馆的六个取件窗口加门口一块翻页进度牌。牌子没翻到的窗口直接说"还没到"（`404 STEP_NOT_READY`）；牌子已经翻过、窗口正在办事的，可以先看一眼屋里（`status=active`），但屋里可能还没有文件（终评未写入时四个结论字段是 `null`，见 D1）。六个窗口背后是同一个库管员（`build_step_payload`），他不会自己再算一遍分数，只把库里已经写好的数字取出来。

## §2 架构导览

### 2.1 HTTP 层只加六个薄壳

六个路由都长一个样：`Security(BEARER_AUTH)` + `responses=STEP_RESPONSES` + 一行 `stages_from(request).step(run_id, key)`，返回体用 `cast` 钉到具体模型（`apps/api/app/api/evolution_runs.py:91-157`）。`STEP_RESPONSES` 复用启动路由的 401/403 说明并补 404（`:47-54`），所以六个端点在 OpenAPI 里各自带 `401/403/404`（外加 FastAPI 自动补的 `422`）。

路由里没有任何状态判断、没有 payload 拼装，甚至没有 `if key ==`——key 是写死在各函数上的常量（例如 `:98` 的 `"input"`、`:157` 的 `"final"`）。**好处**：六个端点的 OpenAPI 形状由返回类型直接生成，不会出现"动态 key 一个 schema 装六种 payload"的退化；这正是 Note 里记的被否方案（动态路由）。

一个细节：`:37-39` 的 `stages_from()` 和既有的 `runs_from()`/`launch_from()` 完全同构，都从 `request.app.state` 取装配好的单例（`main.py:119,199`）。限流意义上的"每个请求一份"不存在，服务无状态。

### 2.2 唯一的进度牌：unit 游标状态机

`step_states(progress_unit, cluster_count, run_status)` 是六步状态的唯一来源（`apps/api/app/service/evolution/state.py:135-166`）。它按阈值表把六步分成 done / active / pending：

| 步 | 阈值（unit ≥ 阈值即 done） |
|---|---|
| 0 筛选输入 | 1 |
| 1 问题聚类 | 2 |
| 2 归因确认 | 3 |
| 3 严重程度排序 | 4 |
| 4 迭代优化 | 4 + M（M = 簇数） |
| 5 测试集终评 | 5 + M |

阈值由 `_thresholds()` 从 `total_units = 4 + M + 1` 推出来（`state.py:67-82`），与 07 §5.1 的表格逐字对应。**active** 赋给"第一个未 done 的步"，只有当 run 处于 `preparing|running|blocked` 时才会出现（`:22,152-156`）；终态（`completed|failed|interrupted`）的 run 没有 active 步，只有 done 和 pending。

于是 404 矩阵不用写特判，直接从表里读出来：

| run 状态 / 位置 | input | clusters | attribution | severity | iteration | final |
|---|---|---|---|---|---|---|
| `preparing`，unit 0 | **active 200**（准备态） | 404 | 404 | 404 | 404 | 404 |
| `preparing`，unit 1 | done | **active 200**（空簇） | 404 | 404 | 404 | 404 |
| `running`，unit 3 | done | done | done | **active 200** | 404 | 404 |
| `blocked`，unit 4（3 簇） | done | done | done | done | **active 200**（带"第 x/y 轮"） | 404 |
| `running`，unit 4+M | done | done | done | done | done | **active 200（结论字段为 null，见 D1）** |
| `completed`，unit 5+M | done | done | done | done | done | done |
| `failed` / `interrupted`，unit 3 | done | done | done | 404 | 404 | 404 |
| `cluster_only` + `completed`，unit 2 | done | done | 404 | 404 | 404 | 404 |
| `cluster_only` + `running`，unit 2 | done | done | 404 | 404 | 404 | 404（D4 守卫，不再依赖终态） |

`ensure_step_readable()`（`:170-196`）把两件事翻译成 `StepNotReady`：pending 步，以及 cluster_only run 的 `attribution/severity/iteration/final`（05 §4.12 的"一律"在 readiness 入口拦下，不进入 `step_states`）；`stages.py:308-316` 再翻译成 `404 STEP_NOT_READY`（`details={"key": key}`）。也就是说"404 矩阵"是同一张表加一条 mode 守卫的两处投影，没有第二套 if 链。

### 2.3 一次 step 请求读四次库

`step()` 的顺序是：`get_run`（`:300`）→ `list_clusters`（`:307`，既给 readiness 的 M，也给 payload 的簇）→ `list_cluster_probes`（`:335`）→ `list_rows_by_ids`（`:337`）。四次都是点查/批量查，没有 N+1：簇→probe 是一次 join（`db/crud/evolution.py:312-333`，按 `probe_clusters.seq, probe_cluster_probes.id` 排序），probe→案卷/session 是一次 `IN` 查询（`db/crud/probe_query.py:132-153`）。`_iteration`/`_final` 各自再读一次 rounds，`_final` 多读一次 finals。

比喻：库管员先去目录室拿这卷档案的索引（run），再看有多少个子卷（clusters），一次调出所有子卷的附件清单（links），再一次性把附件正文搬过来（rows）——不是每翻一页跑一趟库房。

### 2.4 一个共享组装，按 key 分派

`build_step_payload(run, clusters, key)`（`stages.py:319-355`）先统一预备三份读时索引：`cluster_of_probe`（probe → 簇）、`probes_of_cluster`（簇 → probe 列表，保持 link 顺序）、`grouped`（probe → 关联行）。然后用一个 `builders` 字典把 key 映射到六个私有组装函数（`:342-354`），一行 `builders[key]()` 收口。

**为什么这样而不是 if/elif**：字典让"六步都必须实现"变成类型/运行时的硬约束（缺 key 直接 KeyError，而不是静默返回某个分支）；也让新增步骤时必须同时补 DTO、builder、路由三处，不会漏。

**与设计签名的差异**：07 §5.10 和实现计划原先写的都是 `build_step_payload(run, key)`，实现是 `(run, clusters, key)`。我的独立判断是**不构成偏离**（详见 D5）：设计那句话的规范内容是"六个端点共享同一组装、不复制业务逻辑"（05 §3.6 原句），`clusters` 是调用方为了算就绪度本来就要读的数据，把它传进来只减少一次重复读；修复轮已把 07 §5.10 的示意签名对齐成 `(run, clusters, key)`，歧义消除。

### 2.5 分数只读：不重算 confidence / impact / severity / rank

四个分数列直接来自 `probe_clusters` 的落库值（`stages.py:108-121,544-545,617-630`），service 里没有第二处乘 `impact`、算 `reportWeight` 或 `round(..., 1)` 的代码——这与 07 §5.10「接口只读这些列，不再占位计算」和 09 R11（占位逻辑集中、单测锁定）一致。读时只派生两个计数：

- `probe_count` = 该簇的 link 数（`stages.py:543,622,704`）；
- `report_count` = 该簇 probe 反查到的 distinct `bad_case_id` 数（`stages.py:406-424`）。

severity 排序（`stages.py:633-639`）的键是 `(severity 是否为空, -severity, rank 或 len+1)`：有分的按分降序，同分按落库 rank，没分的垫底。这符合 05 §3.6「按落库 severity 降序」，也解释了为什么 `rank` 仍然是契约字段却几乎不参与排序。

### 2.6 契约：六个 key 判别 schema，生成物零漂移

六个响应模型都继承同一个 `EvolutionStepShell`（`stages.py:216-223`：index/title/status/clickable/detail），各自把 `key` 钉成 `Literal[...]` 常量并声明自己的 `payload`（`:226-275`）。生成的 OpenAPI 里因此是六个独立 schema，`status` 是 `enum done|active|pending`，`key` 是 `const "input"` 且有默认值；生成的 TS 是 `key: "input"` 必填常量（`packages/contracts/src/generated/api.d.ts:1247-1268`）。

我对生成物做了结构化比对（不是看行数）：基线与 head 的 **共享 schema 顺序完全一致**，只有 `ErrorCode` 的枚举值多了两个；新增 6 条 path、24 个 schema；删除了 0。`openapi.json` 那 2544 行 diff 的大头是字母序插入造成的行位移，不是契约内容变动——这点值得记住，否则很容易把"生成物 diff 很大"误读成"改了旧契约"。

### 2.7 支撑性改动：让行里带上归因文本

第 2 步要输出 `analysis`（设计写的是"在对象逻辑中复现并确认索引未校验"），但 `ProbeHitRow` 原本没有 `probe_analysis` 字段。本 PR 把它加进 select 与行 DTO（`db/crud/probe_query.py:24,107,202`），并把向导用的 `_item_of` 公开成 `probe_row_of`（`service/evolution/probe_query.py:192-217`）给 stage 复用。这是"一个事实一个 home"的正例：ProbeRow 的渲染只有一份实现，向导与六步读同一份。

## §3 数据流走查

### 场景 A：刚启动的 run，用户点开第 0 步

1. `POST /api/evolution/runs` 返回 202 与 `runId`，run 行 `status=preparing`、`progress_unit=0`、`models/窗口/目标版本` 已在建行时快照（`launch.py:158-175`）。
2. 前端跳到详情页（m5-07 未实现，当前是占位落地页），请求 `GET /api/evolution/runs/{rid}/steps/input`。
3. `step()` 读到 run 与空簇列表（`stages.py:300-307`），`list_cluster_probes` 返回 `()`（`crud/probe_query.py:144-145` 的空集短路在 rows 侧；links 侧由 SQL 直接给空）。
4. `step_states(0, 0, "preparing")` 把第 0 步判成 `active`，`ensure_step_readable` 放行（`state.py:178-180`）。

### 场景 B：一个跑完的 run，用户从第 0 步点到第 5 步

1. 六次 GET，每次都走 `step()`，前四步读到同一组链接与行。

3. 第 1 步：簇列表 + 每簇 `probes`（`stages.py:534-554`）。

### 场景 C：run 阻塞在评测（`status=blocked`，`blocked_stage=eval`）

### 场景 D：cluster_only run 的读法

### 场景 E：输错 run id / 点到未来步骤 / 手拼路径

### 场景 F：同一 GET 连点两次

1. 服务端每条路径都只读（`get_run/list_clusters/list_cluster_probes/list_rows_by_ids/list_rounds/get_final`），没有任何 `insert/update/delete`。

### 场景 G：前端（m5-07）将来怎么用

1. 拿到六步外壳后，`status` 决定 stepper 的三种态，`clickable` 决定能不能点（`clickable = status != "pending"`，`:222`）。
2. 前端不需要"如果 unit >= 4 则…"这类推算，也不需要自己算 `第几轮`——`detail` 由后端给（`:395-397`）。

## §6 讨论点

### D1 终评进行中会返回一份"零值终评"

**位置：** `apps/api/app/service/evolution/stages.py:784-802`（占位 payload 分支）、`state.py:79-82`（final 阈值 `5+M`）；对照 `07 §5.1` 的 `S4 --> S5: 全部轮次完成（unit=4+M）`。

**现象：** 当 `progress_unit = 4+M`（所有轮次完成、终评刚提交、`evolution_finals` 行还没写）且 run 仍是 `running`/`blocked` 时，第 5 步按状态机是 `active` → 可读，但 `get_final()` 返回 `None`，于是接口返回 `verdict=false, bestVersion="", bestScore=0.0, initScore=0.0, metrics=[]`（`changes` 仍按已接纳轮次给出）。这不是边角状态：按 07 §5.1 的状态图，每个 run 都会经过 unit 4+M 这一格。

**问题：** 伪造的"verdict=false + 0 分"与真实的"终评不通过、得分 0"在结构上完全同形，只有 `status` 能区分。m5-07 详情页如果按 payload 直接渲染"终评不通过 / 最佳 0.0"，用户会把"还没出结果"读成"结果很差"；而设计 05 §3.6/§3.6.1 只给了 done 态样例，没有定义 active 态该返回什么，这个决定是本次实现自己补的，写进了 Note 的 Consequences 之外（Note 只写了"零值 hits 是空态"，没写零值终评）。当前也没有测试覆盖该分支（`coverage` 对三元表达式的两个分支无法区分，`stages.py` 报缺行只有 472/579）。

**预判：** 两条路二选一——(a) 契约层表达"无结果"：`verdict: bool | None`、`bestVersion/bestScore/initScore` 改可空，或把 `payload` 整体可空，active 时返回 null 字段；(b) 保持零值但把它明确成契约语义，并在 05 §3.6 补一句"active 的 final 返回零值占位，消费方必须按 status 渲染"，同时在 Note 与测试里钉住。倾向 (a)，因为"0 分"是个有业务含义的数；但 (a) 要改契约并让 m5-07 处理 null，成本更高。

**结论：** 已决（2026-10-27）：选 (a) 可空。`StepFinalPayload` 的 `verdict/bestVersion/bestScore/initScore` 改为可空；`_final` 在 `evolution_finals` 无行时返回 `null` 字段（`metrics` 仍 `[]`、`changes` 仍按已接纳轮次），不再伪造 false/""/0.0。05 §3.6 补 null 口径句，Note 记取舍，服务层与 API 层各补 unit=4+M 用例与 `step-final-active` 快照，契约重新生成。

### D2 「真实 prepare 编排」的归属从 m5-06 改成一个区间，但没有任何 issue 认领它

**位置：** `.agents/notes/implemented/feature/2026-10-27-six-step-api.md:18`、`.agents/notes/implemented/feature/2026-10-27-launch-wizard-admission.md:16-17`、`apps/api/app/service/evolution/prepare.py:17-18,35`；对照 `.agents/flow/issues/m5-09-git-candidate.md:44`、`m5-10-placeholder-eval.md:44`、`m5-11-evolution-recovery.md:44` 与已关闭的 `m5-12-launch-hit-scope.md:36,65`。

**现象：** 本 PR 把 m5-05 Note、占位 handler 与配套断言里的"prepare 编排由 m5-06 提供"统一改成"由引擎切片 m5-09–m5-11 提供"。但翻三个引擎切片的「实现内容」：m5-09 是临时 workspace/clone/分支/candidate/push 重试，m5-10 是 eval gateway/占位评分/poller，m5-11 是 sweeper/retry/恢复与 E2E 闭环——**没有一条写着"evolution_prepare 真实编排：筛选 → 占位聚类 → 落簇 → 推进到 unit 2"**。已关闭的 m5-12 仍写着「六步 prepare 的真实编排（m5-06）、`ENGINE_INVALID` 引擎注册表（m5-06）」。

**问题：** 归属从"一个具体切片"退化成"一个区间"，读者据此无法回答"谁交付 prepare"。更实际的风险是：m5-09/10/11 各自按自己的「实现内容」收尾，prepare 编排既不属于任何人的验收，又必然被 m5-11 的 E2E（「准备→候选→评测→接纳/拒绝」）需要，结果要么被动塞进 m5-11 让它膨胀，要么在验收时才发现没人做。`ENGINE_INVALID` 同理（m5-09..m5-11 都没有提）。这是"一个事实一个 home"在流程层的缺口，不是代码缺陷。

**预判：** 在 m5-09（或新开一个 m5 切片）的「实现内容」里显式加一行认领 prepare 编排与 `ENGINE_INVALID`，把本 PR Note 的区间表述改成指向该 issue；m5-12 属已关闭的历史工作稿，可以不动，但如果真动 prepare 时顺手把两处旧表述改掉，避免下一个人再追一次。这是流程 PR 的事，不必回改本 PR。

**结论：** 已决（2026-10-27）：由 m5-09 认领。m5-09「实现内容」补一行——接通 `evolution_prepare` 真实编排（workspace/ref 校验、筛选、聚类、状态推进）与引擎注册表校验（`engine_key` → 422 `ENGINE_INVALID`）；六步 Note 的区间表述改为指向 m5-09。m5-12 已关闭，不动。

### D3 第 0 步的 hits 由"落簇结果"反推，而设计写的是按条件计数

**位置：** `apps/api/app/service/evolution/stages.py:467-514`（`_input` 从 `grouped` 反推 sessions/badCases/analyzed/probes）；对照 `07 §5.10` 第 0 行「数据来源：`probe_reports` + `session_families` + `bad_cases`/`bad_case_analysis`（命中计数）」与 `service/evolution/probe_query.py:252-293`（向导 preview 的真实计数）。

**现象：** 实现里第 0 步的所有数字都来自本 run 已落的簇↔probe 关联，而不是按 `run.window_from/to + models` 重查一次。preparing 时因此恒为零值（设计允许）；但如果 prepare 丢掉任何一个命中的 probe，第 0 步的数字就会小于向导预览。现在最可能的落差来源是 `probe_reports.attribute_type` 是 `String(16)` 无 CHECK 约束（`db/models/domain.py:255`）：向导侧 `badCases/sessions/analyzed` 按**全部**命中行计数、`probes` 只数三种已知属性（`service/evolution/probe_query.py:272-281`），六步侧则四个数都只覆盖"进了簇的行"——一条属性值脏的 probe 就会让两边对不上。

**问题：** "筛选输入"这一步的语义是"我当初用这个条件筛出了什么"，用户在向导里已经看过一次数字，进详情页看到另一个数字会怀疑启动条件被悄悄改了。当前 V1 占位聚类是全量落簇，所以差异不会出现；但这层假设没有任何门禁或测试，要等 m5-09+ 真接上 prepare 才能验证。

**预判：** 保留"落簇即事实"的单一口径（它更符合只读、可审计、不重跑查询的取向），但把这层含义写进 05 §3.6 或 07 §5.10 一句话：「第 0 步的计数按落簇结果，不按条件重查；preparing 时为零值」。等 prepare 真接上，补一条"命中 N / 落簇 M"的对账断言（若 prepare 会过滤，就要求 N=M 或显式记录差量）。

**结论：** 已决（2026-10-27）：保留"落簇即事实"单一口径，补设计句。05 §3.6 与 07 §5.10 各加一句"第 0 步 `hits` 按已落簇的 probe 计数、不按条件重查，`preparing` 时为零值"；Note 记理由（只读、可审计、不重跑查询）与欠账（prepare 接上后补"命中 N / 落簇 M"对账测试，留给后续切片）。代码不变。

### D4 cluster_only「一律 404」依赖一个没写死的引擎状态前提

**位置：** `apps/api/app/service/evolution/stages.py:308-317`（readiness 只问状态机）、`state.py:22-23,152-156`；测试构造 `test_steps_api.py:186`（直接把 `status` 写成 `completed`）、`test_steps_service.py:185`。

**现象：** 05 §4.12/§869 要求 cluster_only 的 run 请求 `attribution/severity/iteration/final` **一律** 404。实现没有 mode 特判，靠的是"cluster_only run 一定在 unit 2 处于终态"这一前提：unit 2 时 input/clusters 已 done，若 run 是终态 → 四步 pending → 404。测试把 status 写死成 `completed`，于是恰好满足。若将来引擎在准备期间把 cluster_only run 标成 `running`（先 running、落簇后再终态是很自然的写法），同样的 unit 2 下 attribution 会变成 **active → 200**，payload 是空 `items`。

**问题：** 设计要求的是"一律"，实现给出的是"只要引擎那样写就一律"。这条不变量既不在门禁里，也不在测试里，只写在 Note 的 Consequences 之外的一句判断（"cluster_only run 以终态停在 unit 2"）。它今天是安全的（cluster_only 的 prepare handler 还没接，`engine/cluster_only.py:15-20` 仍会因 deps 缺失抛 `ConfigError`），但它是本 PR 唯一一处"语义正确性外包给未来代码"的地方。

**预判：** 先补一条测试把当前行为钉住（`status=running` + `unit=2` + `mode=cluster_only` → 当前实现返回 200 active），再决定要哪边：要么状态机/服务加一条"cluster_only 不产生 active 步"的约束（代价是 mode 进入状态判定），要么把设计口径改成"cluster_only 终态时后四步 404"，并说明进行中允许看归因空表。倾向后者 + 测试锁定，因为前者会把 mode 混进 R4 想保持纯净的状态机。

**结论：** 已决（2026-10-27）：按设计修实现。`ensure_step_readable` 增加 `mode` 参数，cluster_only run 的 `attribution/severity/iteration/final` 在 readiness 入口一律 `404 STEP_NOT_READY`（details 带 key），`step_states` 仍是纯游标状态机；补 `status=running + unit=2 + mode=cluster_only` 的服务/API 用例，既有终态用例保持绿；Note 改写被否方案与被推翻的前提。

### D5 `build_step_payload(run, clusters, key)` 与设计 `(run, key)` 的差异复核

**位置：** `apps/api/app/service/evolution/stages.py:319-324`；设计 `plans/fullstack-design/07-backend-implementation.md:954`（"共享 `build_step_payload(run, key)`"）、`05-api-design.md:334`（"服务端只复用同一个 `build_step_payload`"）；实现计划 `.superpowers/sdd/m5-06-six-step-api-plan.md:7`。

**现象：** 设计两处都写 `(run, key)`，计划也照抄；实现多一个 `clusters` 参数，并在 commit message 与 Note 里显式写成 `(run, clusters, key)`。`clusters` 是 `step()` 为了算 M 本来就要 `list_clusters` 的数据（`:307`），传进组装函数避免同一请求内读两次；`build_step_payload` 自己不查库、不判就绪，仍是"纯组装 + 一次按 key 分派"。

**问题：** 需要判断的是"设计那句话是契约还是示意"。如果把 `(run, key)` 当契约，这就是偏离；当示意，则这是实现细节的合理细化。判据在于设计**规范的是行为还是形参**：05 §3.6 与 07 §5.10 的规范句都是"共享同一组装、不复制业务逻辑"，没有一条命令式要求函数只能有 N 个参数；而 05 §3.6.1 的返回示例才是可执行的契约，本 PR 的六份快照与它逐字段一致（见 §9）。

**预判：** 不构成偏离，无需改动。若要消除歧义，可以把 07 §5.10 的示意签名补成 `(run, clusters, key)`，或在设计里改成"一个共享组装函数（入参以实现为准）"；这属于设计文档措辞，不是代码修复。另外注意 `build_step_payload` 没加下划线前缀（是公开方法），但它离开 DB 读出的 `clusters` 就没法用——如果真要把它当长期 seam（例如引擎或 m5-07 复用），更合适的形态是一个"已加载的一步上下文"入参；目前只有一个调用方，保持现状即可。

**结论：** 已决（2026-10-27）：不是偏离，不改代码；只把 07 §5.10 的示意签名补成 `(run, clusters, key)`，让设计措辞与实现对齐。
