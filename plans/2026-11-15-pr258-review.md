## §1 一页速览

**一句话**：把“进化对象、运行、事件、SSE 票据”从全局资源改成“某个空间里的资源”，并给前端补上带空间前缀的 V2 接口。

**一个比喻**：以前所有房间共用一把总钥匙，谁捡到写着 run id 的纸条都能进；现在每层楼有自己的门禁，纸条（事件 topic）还必须配上本楼的门禁卡（workspaceId + 成员关系），楼里的资料柜（target/run/event）也按楼编号。

**交付块**

| 能力 | 结果 |
|---|---|
| target 空间化 | 唯一键含 workspace；V2 增删改查限本空间；旧读按可见空间过滤 |
| run 空间化 | 创建写 workspace；列表/详情/步骤/重试按空间；旧路由过滤 |
| event/SSE | 事件继承 run 空间；ticket 可带 workspaceId，逐 topic 校验 |
| 写权限 | V2 写与旧 launch/retry 均要求 space_admin；viewer 只读 |
| 清单 | 旧/V2 targets、models 均按空间投影 |
| 兼容 | 旧无前缀路径保留一个版本；旧 target 写仍限全局管理员 |

**验证基线**：`test:api` 860 passed / 11 skipped；E2E 19 passed；integration 6 passed；lint/typecheck/contract/gates/docs/flow/bundle 全绿。MySQL 仅 CI 覆盖。

## §2 架构导览

### 2.1 空间解析只有一处入口

`WorkspaceService.visible_ids`（`apps/api/app/service/workspaces/service.py:114`）把“我是全局管理员”与“我有哪些成员行”收敛成 `None | tuple[str, ...]`：`None` 表示显式全局，空元组表示什么都看不到。`app/api/deps.py:20` 的 `visible_workspace_ids` 只做请求层适配，`app/api/deps.py:30` 的 `authorize_workspace` 复用同一套 404/403 语义。这样旧路由不必各写一遍“管理员直通”。

### 2.2 V2 路由是一层薄壳

`apps/api/app/api/evolution_workspace.py` 不复制业务规则：每个 handler 解析 `{wid}` 后把 `(wid,)` 传给既有 service。读路由挂 `viewer`、写路由挂 `space_admin`，全局管理员由依赖直通。路由层只多做两件事：把 service 的 `None` 映射成 `RUN_NOT_FOUND` / `STEP_NOT_READY`，以及把 path 空间作为唯一过滤条件。

### 2.3 服务层把“空间”当过滤参数，不另建上下文对象

targets、runs、events、retry、stages 的 service 签名都增加可选 `workspace_ids`。未传时保持旧的全局行为（仅管理员或后台任务使用），传入时拼到 SQL 的 `workspace_id IN (...)`。这避免为每个 service 构造一个 `WorkspaceScope` 对象，也让旧调用点的兼容成本可见。

### 2.4 写入链由 run 快照决定空间

`EvolutionTargetService.enabled_config`（`service/evolution/targets.py:411`）在可见空间内找唯一启用配置；多条时优先默认空间，否则 409。launch 用它解析出的 `config.workspace_id` 同时写入 run 快照和 probe 查询（`launch.py:142`），prepare 再用 `run.workspace_id` 重建查询（`prepare.py:413`）。事件 append 不信调用方，直接从 run 行取空间（`db/crud/run_events.py:125`）。

### 2.5 SSE 票据是“空间证明 + 资源证明”

`EvolutionRunTopicAuthorizer`（`service/evolution/events.py:486`）先证明 `workspaceId` 的成员关系，再要求每个 topic run 属于该空间；未带 `workspaceId` 的旧客户端逐个 run 校验成员关系。所有失败统一 `TICKET_INVALID`，避免通过 ticket 响应枚举空间或 run。

## §3 数据流走查

**场景：空间 A 的空间管理员通过 V2 启动一次 run，前端订阅 SSE。**

1. `POST /api/workspaces/ws-a/evolution/runs`（`evolution_workspace.py:326`）→ `require_workspace_role("space_admin")` 读 `ws-a` 成员行；不满足 403，不可见 404。
2. `EvolutionLaunchService.request_run(..., workspace_ids=(ws-a,))` → `enabled_config` 只在 `ws-a` 找 target；找不到 409 `TARGET_NOT_CONFIGURED`。
3. `normalized_query` 带 `(ws-a,)` → `ProbeQueryRepository.list_hit_rows` 在 `bad_cases.workspace_id` 上过滤；别的空间 bad case 不会进入本次 run。
4. `EvolutionRepository.create_run` 写入 `evolution_run.workspace_id = ws-a`；事件 append 从该行继承空间。
5. 前端 `POST /api/events/ticket {topics:["run:..."], workspaceId:"ws-a"}` → 授权器先查 `ws-a` 成员关系，再查 run 活跃且属于 `ws-a`；任一步失败 401。
6. `GET /api/workspaces/ws-a/evolution/runs/{rid}/events` → `EvolutionRunEventService.list` 用 `(ws-a,)` 取 run；跨空间 404。

旧无前缀路径走同一套 service，只是把 `workspace_ids` 换成 `visible_workspace_ids(request)`；旧 launch/retry 额外用 `authorize_workspace` 检查目标/run 所属空间的 `space_admin`。

## §6 讨论点

### D1 旧 retry 路由读两遍 run

- **位置**：`apps/api/app/api/evolution_runs.py:214-223`
- **现象**：先用 `EvolutionRunService.detail` 判断可见性，再用 `_run_workspace` 从 repository 取一次 run 拿 workspace。
- **问题**：两次查询、两次 seq/max 计算；如果两次之间 run 被删，`_run_workspace` 会再走 404，行为仍一致。
- **预判**：无实害；更彻底的做法是让 detail 暴露所属空间，或直接在路由用 repository 取 run 再做可见性判断。
- **结论**：

### D2 旧 target create 固定落默认空间

- **位置**：`apps/api/app/api/evolution_targets.py:64-70`
- **现象**：旧 `POST /api/evolution/targets` 不接收空间，统一写 `ws-default`。
- **问题**：多空间部署下，全局管理员从旧页面创建对象时可能以为在“当前空间”，实际进了默认空间。
- **预判**：兼容期的可接受折中；V2 页面应按 `{wid}` 写入，旧入口可在 V1 退役时删除。
- **结论**：

### D3 visible_ids 没有上限

- **位置**：`apps/api/app/service/workspaces/service.py:114`
- **现象**：可见空间全量返回，旧路由把它直接拼进 `IN (...)`。
- **问题**：极端多空间用户会撞 SQLite 参数上限（默认 999），查询整体失败而非降级。
- **预判**：当前单组织空间数远低于此；若空间数上量，可复用 `auth/session` 的 200 上限并显式拒绝/截断。
- **结论**：

### D4 事件表空间列靠写入路径维护

- **位置**：`apps/api/app/db/crud/run_events.py:125`
- **现象**：append 从 `evolution_runs` 读 `workspace_id` 写入事件；模型层没有 `evolution_run_events.workspace_id -> workspaces.id` 外键。
- **问题**：绕过 store 直接 SQL 写入时，事件空间可能与 run 空间不一致；当前应用内没有第二条写路径。
- **预判**：无实害；若要数据库级保证，需要补外键/触发器，属于迁移决策，不宜在本 PR 顺手加。
- **结论**：

### D5 V2 七步路由用一个 union 响应

- **位置**：`apps/api/app/api/evolution_workspace.py:299`
- **现象**：`/runs/{run_id}/steps/{key}` 返回 `EvolutionStep` 联合类型，契约增加约 1.1k 行。
- **问题**：OpenAPI 体积变大；前端消费时仍需按 `key` 收窄。
- **预判**：运行时无成本，等 m10 七步重排时再决定拆成独立端点或判别联合。
- **结论**：

### D6 workspaceId 在 ticket 上仍是可选

- **位置**：`apps/api/app/service/identity/schemas.py:69`
- **现象**：旧客户端不带 `workspaceId`，授权器逐个 run 校验；新客户端应始终带。
- **问题**：可选字段意味着长期存在两条授权路径，测试面更大。
- **预判**：m7-08 前端切到 V2 后应收紧为必填；当前保留是为兼容一个版本。
- **结论**：

### D7 MySQL 方言只由 CI 覆盖

- **位置**：`apps/api/app/db/crud/evolution_targets.py`、`run_events.py`
- **现象**：本地只跑 SQLite；`IN (...)`、`with_for_update`、`select` 子查询在 MySQL 上的行为由 CI `mysql` lane 验证。
- **问题**：若 MySQL 对空 `IN` 或子查询优化不同，可能出现本地绿、CI 红。
- **预判**：SQLAlchemy 生成的是标准表达式；等 CI 结果再决定是否调整。
- **结论**：

## §9 文件级代码分析

### `apps/api/app/api/evolution_workspace.py`（A）

职责：把既有 service 暴露成 `/api/workspaces/{wid}/evolution/**`，不承载业务规则。

变更要点：每个 handler 先由 `require_workspace_role` 拿到 `WorkspaceAccess`，再把 `wid` 原样传给 service。读用 `viewer`，写用 `space_admin`；`read_run` / `read_step` 把 `None` 映射为 404。catalog 路由是同一文件的第二个 router，路径为 `/api/workspaces/{wid}/catalogs/**`。

实现思路：路由层只做“身份 → 空间 → service 参数”的转换，跨空间资源统一按 404，避免枚举。

### `apps/api/app/service/evolution/targets.py`（M）

新增 `enabled_config` 是 launch 与 preview 的共同入口：按可见空间找启用配置，多条时优先 `ws-default`，否则 409。`create/update/delete/versions` 全部接受 `workspace_ids`，唯一性检查先按空间过滤再交给数据库约束兜底；`_is_unique_violation` 补上新约束名，重复对象不再落到 500。

### `apps/api/app/api/evolution_runs.py`（M）

旧列表/详情/事件/步骤都传 `visible_workspace_ids`；旧 launch 先用 `enabled_config` 解析目标空间并 `authorize_workspace(..., "space_admin")`，再委托 launch service；旧 retry 先判可见再判空间管理员。代价是旧路由多了几行编排，但写权限不再依赖全局管理员规则。

### `apps/api/app/service/evolution/events.py`（M）

`list` 先按 `workspace_ids` 取 run，再读事件页，跨空间 404。`EvolutionRunTopicAuthorizer` 现在强制注入 `WorkspaceService`：带 `workspaceId` 时先证明成员关系并校验 run 空间；不带时逐 run 证明。作者原本允许 `workspaces=None` 以便单测，那会让“忘记注入”变成静默放行，本 PR 已改为必填。

### `apps/api/app/db/crud/run_events.py`（M）

`append` 在写入事务里先查 run 的 `workspace_id`，再写事件；事件空间永远由 run 派生。

### `apps/api/app/service/catalogs.py`（M）

`targets/models` 接受可见空间：targets 直接过滤 `evolution_targets`；models 先取该空间 bad case 的 `bad_case_session_id`，再聚合 `agents.model`，因此模型清单不再跨空间。

### `packages/contracts/**`（M，生成物）

`pnpm contract:generate` 重新导出 OpenAPI 与 TS；新增 V2 路径、`TicketRequest.workspaceId`、steps union。禁止手改，`contract:check` 已验证当前一致。
