## §1 一页速览

一句话：把两条链路上原本「各记一半」的 AI 调用信息，收成一张统一的出站小票——每次 `analyze` / `edit_workspace` 都开一张，失败也开，票面上同时有任务、模型、token、成本、耗时、结果和提交通道的「行李标签」。

一个比喻：以前的 cluster 路径像在登机牌背面手写几个数字，agent-edit 路径干脆没有票；现在 `ai_observability.py` 是唯一一台打票机，`AgentCallTrace` 是副券，写着这趟飞了几段、第几段才把行李（`result.json5` / `edits.json5`）送到、行李是不是被修补过。`git_candidate` 和 `prepare` 是两个登机口，各自把票打出来贴到同一本事件簿上。

## §2 架构导览

### 2.1 打票机：`AiAgentCall`

`AiAgentCall` 是 `service/evolution` 下的 frozen slots dataclass（`ai_observability.py:26-38`），三个构造入口：

- `from_edit(task, result)`（`:41-54`）：成功返回 `EditResult` 时，从 `result.usage` / `result.latency_ms` / `result.trace` 生成记录，`outcome="ok"`。
- `failed(task, error)`（`:57-69`）：provider 抛 `AgentProviderError` 时，用 `error.provider_id` / `error.trace` 生成记录，`model="unknown"`、tokens/cost/latency 全 0（见 §6.1）。
- cluster 路径没有用类方法，而是在 `prepare.py:595-608` 把 `CallRecord` 逐字段搬进 `AiAgentCall`。

`payload()`（`:71-98`）只做序列化：固定 16 个键，`totalTokens` 由 `input_tokens + output_tokens` 现算。它是 cluster 与 candidate 两条链路的共同出口，读者只要看这一个函数就能知道事件长什么样。

### 2.2 副券：`AgentCallTrace`

`AgentCallTrace`（`contracts.py:69-116`）是 5 个字段的值对象（3 个计数 + `parsed_by`/`repaired`）：`attempts`、`submission_parse_failures`、`submission_validation_failures`、`parsed_by`、`repaired`；`feedback_retries` / `submission_failures` 是派生属性。`__post_init__` 拒绝负数、`attempts < 1`、两类失败合计超过 attempts、以及 `repaired=True` 但 `parsed_by != "repair"`。

它被挂在 `AnalysisResult`（`:149`）、`EditResult`（`:196`）和 `AgentProviderError`（`:238`、`:253`）上。这样 provider 失败也能把「跑了几次、提交坏在哪」带到事件层，而不需要存储原始模型输出。

### 2.3 两个登机口

- **cluster**：`prepare.py:590-609` 的 `record_call` 把 `CallRecord` 转成 `AiAgentCall` 后调用 `self._events.record(...)`，`stage="cluster"`、`step_index=4`。
- **candidate**：`git_candidate.py:738-755` 的 `_record_ai_call` 用 `stage="candidate"`、`step_index=5`；调用点在 `publish` 的 `except AgentProviderError` / `except ConfigError` / `else` 三个分支（`:233-257`）。

`git_candidate` 的 `_record` 已在本次新增可选 `step_index` 参数（`:710`、`:725`），其余事件不受影响。

### 2.4 失败也要开票

`AgentEditPatchSource` 新增 `last_ai_call` 属性（`patch_source.py:363-373`），`build_bundle` 在开头把它重置为 `None`（`:407`）；provider 成功返回后立即写 `from_edit`（`:423`），provider 抛错时写 `failed`（`:421`）再 re-raise。`git_candidate._last_ai_call`（`:1059-1069`）用 `getattr` + `isinstance` 读取，只有真正发生 provider 调用才记事件；placeholder / minimal-config 不产生事件。

失败顺序是：`_record_ai_call` → `_handle_provider_failure` / `_fail_patch_generation` → `run_blocked` 或 `run_failed`。也就是说事件流里先看到 AI 调用票，再看到 run 的阻断/失败结论。

resume 不重复：`publish` 在 `round_.candidate_commit` 存在时直接 `repush_existing`（`:222-223`）；否则 `_stored_bundle(saved)` 非空就跳过 `build_bundle`（`:229-231`），因此不会重新调用 provider。代码路径成立，但没有测试守卫（见 §6.4）。

### 2.5 脱敏器与小票字段

`events.py:276` 在落库前对 payload 调 `sanitize_value`；`redaction.is_sensitive_key`（`redaction.py:102-110`）先把键归一成小写字母数字，再按前缀/后缀/敏感集合判断。实测：

- `tokens` → 归一 `tokens`，命中前缀 `token` → `<redacted>`；
- `totalTokens` → 归一 `totaltokens`，既不以 `token` 开头也不以 `token` 结尾（结尾是 `tokens`）→ 保留；
- `inputTokens` / `outputTokens` / `costUsd` / `latencyMs` / `sessionId` / `attempts` / `feedbackRetries` / 四个 `submission*` 键全部保留；
- `sanitize_value({"tokens": 15, "totalTokens": 15})` 返回 `{"tokens": "<redacted>", "totalTokens": 15}`。

所以已知问题 1 的修法（改名 `totalTokens`）与所有新键都正确；集成测试又用真实持久化事件断言了 `totalTokens` / `inputTokens` / `outputTokens` / `costUsd` / `latencyMs`，覆盖了「落库后仍保留」这一层。

### 2.6 配置校验

`config.py:318-327` 把 `HE_PATCH_SOURCE_MODE` 的合法集合从硬编码的 `{"placeholder", "minimal-config"}` 改成 `PATCH_SOURCE_MODES`（`patch_source.py:41` 的 `("placeholder", "minimal-config", "agent-edit")`），并在错误信息里列出合法集合；`test_patch_sources.py:224-233` 新增 `agent-edit` 通过的断言，非法值仍抛异常。函数内延迟 import 规避了 `config` ↔ `patch_source` 的加载顺序问题，lint/typecheck 均通过。

## §3 数据流走查

以一次带 agent 的 cluster-only prepare 为例：

1. **准备阶段**：`prepare.py:495-524` 从归因行构造 `drafts`；`agent` 非空时进入 `_enhance_clusters`（`:517-524`）。
2. **review 调用**：`cluster_llm._review` 发一次 `analyze(task="cluster.review")`。provider 在 `claude_code._analyze_with`（`:308-367`）里跑第一次 CLI，写入 `result.json5`，`collect` 做 strict → JSON5 → repair → Pydantic 校验。
3. **首轮非法**：若 `collect` 返回 `is_ok=False`，`feedback_prompt` 生成具体字段/约束，拼回 prompt，**无 `--resume`** 地重跑一次（`:337-347`）；重跑期间不恢复第一轮会话，因为 analyze 用 `--no-session-persistence`。
4. **trace 汇总**：两轮各产生一个 `SubmissionOutcome`；`_call_trace(outcomes)`（`:893-916`）算 `attempts=2`、首轮 parse 或 validation 失败计数、并取最后一轮的 `parsed_by` / `repaired`。成功返回 `AnalysisResult(trace=…)`；失败抛 `AgentProviderError(trace=…)`。
5. **事件落库**：`prepare.record_call` 把 `CallRecord`（含 `trace`）搬进 `AiAgentCall`，`EvolutionRunEventService.record` 先校验 `stage` / `step_index` / `event_type`，再 `sanitize_value` payload，最后写 `run_events` 并推 SSE。
6. **评分两次**：同样各一次 `analyze`（`cluster.score`、`severity.score`），同样记录；任何一次 provider 失败或输出违反契约都会另记 `degraded` warn 事件，并降级到确定性值。
7. **agent-edit 路径**：`publish` 无已存 patch 时创建 `AgentEditPatchSource`，`build_bundle` 调一次 `edit_workspace`；成功后立刻 `last_ai_call = from_edit`，再在临时镜像上 `apply_edit_plan`。
8. **应用失败**：镜像里一条都没应用 → `ConfigError`；`publish` 的 `except ConfigError` 先记 `ai_agent_call`（`outcome=ok`，因为 provider 调用本身成功），再 `_fail_patch_generation` 记 `run_failed`。
9. **provider 失败**：`build_bundle` 内 `except AgentProviderError` 把错误记录为 `failed` 并 re-raise；`publish` 的 `except AgentProviderError` 先记 `ai_agent_call`（`outcome=error`），再 `_handle_provider_failure` → 可重试则 `run_blocked`，不可重试则 `run_failed`。
10. **resume**：已有 `candidate_commit` 或已存 patch 时跳过 `build_bundle`，因此不会产生第二条 `ai_agent_call`。
11. **retry CLI 失败**：首轮提交非法、第二轮 CLI 直接非零退出时，`_call` 抛错；`claude_code.py:343-347` 用 `replace(_call_trace(outcomes), attempts=len(outcomes)+1)` 把两次调用计数留下，但 provenance 仍来自首轮（见 §6.2）。

## §6 讨论点

### 6.1 失败调用的 usage / model / latency 全为 0

- **位置**：`apps/api/app/service/evolution/ai_observability.py:57-69`（`failed` 硬编码 `model="unknown"`、tokens/cost/latency 全 0）；`apps/api/app/third_party_api/ai_agent/claude_code.py:353-360`（`parsed` 里的 usage 在抛错时被丢弃）；`apps/api/app/service/evolution/cluster_llm.py:1253-1276`（`_failure_record` 同样清零 usage / model，latency 有测量）；`apps/api/app/service/evolution/patch_source.py:418-421`（注释称失败也「cost-attributable」）。
- **现象**：用只读脚本让两次 analyze 都返回 `usage={input_tokens:100, output_tokens:20}`、`total_cost_usd=0.05` 的校验失败提交，最终 error payload 是 `inputTokens=0`、`outputTokens=0`、`totalTokens=0`、`costUsd=0`、`model="unknown"`；`AiAgentCall.failed` 的 `latencyMs` 固定 0（candidate provider 失败即如此，cluster 失败则用 `_failure_record` 的实测 elapsed）。
- **问题**：`ai_observability.py:3-5` 的模块 docstring 说 cost、latency 等可从事件流单独聚合；但最需要成本归因的失败调用反而没有 usage/model，candidate 失败连 latency 也是 0。`patch_source.py:419-420` 的「failure is cost-attributable」在当前 payload 下不成立（只能归因「发生了一次调用」，不能归因花了多少）。这与 PR 的「failed one 也记一条」在数量上成立，在成本语义上不成立。
- **预判**：若接受为已知边界，最省事的是改注释与 docs：失败事件只保证 `attempts` / 失败计数 / provider / task，usage 与 latency 可能是 0；同时把模块头那句「cost can be aggregated」限定为成功调用。若要在本 PR 补齐，给 `AgentProviderError` 加可选 `usage` / `latency_ms`（仍是 additive，不改 `AIAgentProvider` 方法签名），`AiAgentCall.failed` 接收并透传；`_analyze_with` 在 `collect` 失败时把当前 `parsed.usage` 带上，`AgentEditPatchSource` 把 provider 调用前后的 elapsed 带上。
- **结论**：2026-11-23 采纳「补齐可归因成本」：`AgentProviderError` 增加可选 `usage` / `latency_ms`，`claude_code` 在校验失败时传入已解析的 usage，`AiAgentCall.failed` 与 `cluster_llm._failure_record` 透传；解析前的进程级失败仍为 0/unknown 并在 docs 写明。回归见 `test_agent_edit_source.py`、`test_ai_agent_claude_code.py`、`test_clustering_three_layers.py`（`4f21df99`）。

### 6.2 失败轮次的 `submissionParsedBy` / `submissionRepaired` 语义

- **位置**：`apps/api/app/third_party_api/ai_agent/claude_code.py:911-912`（`parsed_by=last.parsed_by`、`repaired=last.parsed_by == "repair"`，不判断 `last.is_ok`）；`apps/api/app/third_party_api/ai_agent/contracts.py:23`（`SubmissionParsedBy` 的 doc「produced the accepted literal」）与 `claude_code.py:893-901`（`_call_trace` doc「the document the caller actually consumed」）；`apps/api/app/service/evolution/ai_observability.py:94-95`（payload 直接落这两个值）。
- **现象**：两轮都写入 `[1,2]`（顶层是 list，非 object）时，`collect` 返回 `status="invalid"` + `parse_error` + `parsed_by="strict"`；`_call_trace` 得到 `AgentCallTrace(attempts=2, parse_failures=2, parsed_by="strict")`，事件 `outcome=error` 但 `submissionParsedBy="strict"`。首轮校验失败、重试 CLI 非零退出时（`claude_code.py:343-347`），trace 的 `parsed_by` 来自首轮那个**已被拒绝**的字面量；若首轮是 repair 档，`submissionRepaired=true` 也会出现在 error 事件上。
- **问题**：契约与 `_call_trace` 的 docstring 都把 `parsed_by` 定义成「被接受/被消费的文档由哪一档产生」，失败时并不存在这样的文档；而 payload 的消费方若按 `submissionRepaired` 统计「抢救率」、按 `parsed_by` 统计「哪一档产出成功文档」，会把失败也算进去。`AgentCallTrace.__post_init__` 也没有拒绝「所有轮次都失败但 `parsed_by` 非空」的组合。
- **预判**：先把语义钉死。若以「accepted document」为准，最小修法是 `parsed_by=last.parsed_by if last.is_ok else None`、`repaired=last.is_ok and last.parsed_by == "repair"`；这样 retry CLI 失败的 `parsedBy` 也会是 null（因为最后一轮没有提交）。若确实想保留「最后一次提交尝试的档位」，就改 contracts / `_call_trace` 的 docstring，并另加一个 `acceptedParsedBy` 或 `lastSubmissionParsedBy` 字段区分。无论哪种，都应补一个「顶层非 object」和「首轮非法 + 重试 CLI 失败」的 trace 测试——现有 `test_missing_submission_keeps_parse_failure_provenance` 只覆盖了 missing。
- **结论**：2026-11-23 采用「最后一次提交尝试的档位」语义：`submissionParsedBy` / `submissionRepaired` 描述最后一轮解析，即使该文档随后校验失败；成功信号仍是 `outcome`。contracts / `_call_trace` docstring 与新常驻页已统一措辞，不新增 `acceptedParsedBy`（`4f21df99`）。

### 6.3 「解析失败率 = submissionParseFailures / attempts」的分母

- **位置**：`docs/ai-agent.md:39` / `docs/ai-agent.en.md:39`；`apps/api/app/third_party_api/ai_agent/claude_code.py:337-347`；`apps/api/app/service/evolution/cluster_llm.py:1265-1275`；payload 字段在 `ai_observability.py:92-97`。
- **现象**：`attempts` 计的是模型调用数，不是「实际收集到提交的轮数」。第一次 CLI 就启动失败（如 binary 不存在）时，`AgentProviderError` 的默认 trace 是 `attempts=1, parse_failures=0, parsed_by=None`；按文档公式得到 `0/1 = 0%`，但这一轮根本没进提交通道。首轮校验失败 + 重试 CLI 失败时 `attempts=2, validation_failures=1`，只收集了 1 轮；按文档的 parse 失败率公式分母仍是 2，而真正可解析的提交只有 1 轮。事件里没有 `submissionRounds` 之类的字段，消费方只能靠 `outcome` / 失败计数做非显式推导。
- **问题**：文档把 `failures / attempts` 称为「提交文件解析失败率」，但分母把「没有提交可解析」的调用也算进去了，率会偏低；这与设计 07 §5.5.3 层 5 想看的「提交文件解析失败率」不是同一个数。PR 描述「parse failure rate is therefore derivable from the event stream alone」在简单公式层面不成立。
- **预判**：在 trace/payload 里加 `submissionRounds`（实际 `collect` 过的轮数），把率定义为 `submissionParseFailures / submissionRounds`；这也能让 retry CLI 失败与成功重试不再只靠 `outcome` 区分。若不想加字段，至少在 docs 把分母写成「模型调用数」，说明它是上界而不是精确的提交解析失败率，并在 Note 记录。
- **结论**：2026-11-23 采纳加字段方案：trace/payload 增加 `submissionRounds`（实际 `collect` 轮数），解析失败率改为 `submissionParseFailures / submissionRounds`；`AgentCallTrace` 校验轮数不超过模型调用数。docs / Note 已同步（`4f21df99`）。

## §9 文件级代码分析

### `apps/api/app/service/evolution/ai_observability.py`（A，观测核心）

- **职责**：把一次 provider 调用的归一化字段（task/provider/model/usage/cost/latency/outcome/session + trace）序列化成 `ai_agent_call` payload；不读取业务状态、不发事件。
- **变更形态**：新增（无旧代码）。旧代码是 `prepare.py` 里手写的 9 键 dict，agent-edit 路径完全没有 payload。
- **关键依赖**：只依赖 `third_party_api.ai_agent.contracts` 的 `AgentCallTrace` / `AgentProviderError` / `EditResult`，没有新增第三方包；`frozen=True, slots=True` 让记录不可变，`field(default_factory=AgentCallTrace)` 给 cluster 的 `CallRecord` 提供默认 trace。
- **变更代码块**：新增内容就是 `AiAgentCall` + `payload()`（`:26-98`）。`payload()` 的关键选择是把 `totalTokens` 现算而不是存字段（避免与 `input/output` 漂移），并显式在任何字符串值进事件前依赖统一脱敏器。
- **检视发现**：`failed()` 的零 usage / 零 latency 与模块头「cost 可聚合」冲突，见 §6.1；其余无发现。

### `apps/api/app/third_party_api/ai_agent/contracts.py`（M，契约）

- **职责**：新增 `AgentCallTrace` / `SubmissionParsedBy`，把 trace 挂到 `AnalysisResult`、`EditResult`、`AgentProviderError`。
- **变更形态**：M；旧 `AnalysisResult` / `EditResult` 只有 usage/latency/session/retryable，旧 `AgentProviderError` 只有 retryable/provider_id/detail。
- **关键依赖**：同包 `edits.EditPlan`，无新依赖。
- **变更代码块**：
  - 旧：`AgentProviderError(message, retryable, provider_id, detail)`；结果对象无 trace。
  - 新：`AgentCallTrace` 带 `__post_init__` 不变量（`:87-104`）、`feedback_retries` / `submission_failures` 派生属性（`:106-116`）；三个对象各加一个带默认值的 `trace` 字段（`:149`、`:196`、`:238`、`:253`）。
  - 为什么：错误也携带 provenance，避免失败调用在事件里只剩 detail。
- **检视发现**：不变量没有约束「所有轮次失败但 `parsed_by` 非空」，与 §6.2 相关；`SubmissionParsedBy` 与 `submission._ParsedBy` 重复，见 §6.10。

### `apps/api/app/third_party_api/ai_agent/claude_code.py`（M，数据源）

- **职责**：真实 Claude Code provider 现在把 analyze 的两轮提交、edit 的单轮提交汇总成 `AgentCallTrace`；retry CLI 失败时保留首轮失败计数并补上第二次调用。
- **变更形态**：M；旧 `_analyze_with` 只有一个 `outcome` 变量，旧 `edit_workspace` 不产出 trace。
- **关键依赖**：`StructuredSubmission.collect`（仓库内第一方，解析阶梯）和 `submission.SubmissionOutcome`；`dataclasses.replace` 用来在 retry 失败时改 attempts。
- **变更代码块**：
  - 旧：`outcome = collect(...); if not outcome.is_ok: retry; outcome = collect(...)`。
  - 新：`outcomes: list[SubmissionOutcome]` 收集每轮；retry 的 `_call` 抛错时 `exc.trace = replace(_call_trace(outcomes), attempts=len(outcomes)+1)`（`:343-347`）；成功/失败都把 `_call_trace(outcomes)` 挂到结果/错误（`:353-360`）。
  - 为什么：`attempts` 要等于真实模型调用数，且第二次调用即使没有提交也要计数。
- **检视发现**：`_call_trace` 的 `parsed_by` / `repaired` 取最后一轮但不判断 `is_ok`，见 §6.2；retry 失败分支无测试，见 §6.4；失败时丢弃 `parsed.usage`，见 §6.1。

### `apps/api/app/service/evolution/cluster_llm.py`（M，cluster 路径）

- **职责**：`CallRecord` 增加 `trace`；失败记录从 `AgentProviderError.trace` 取计数（并在 provider error 时改用 `error.provider_id`），结果记录透传 `result.trace`。
- **变更形态**：M；旧 `_failure_record(task, agent, elapsed_ms)` 没有 error 参数，trace 不存在。
- **关键依赖**：只依赖 `contracts.AgentCallTrace`；`_failure_record` / `_result_record` 是纯数据装配。
- **变更代码块**：
