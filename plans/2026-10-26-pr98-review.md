## §1 一页速览

一句话：这个 PR 给“导入后的原始 payload”装上定时清扫器，用一条数据库锁保证 scheduler 和 admin 手动操作永远不会同时启动两次同步，并把真实 pending 状态安静地放进原型顶栏。

生活化比喻：`sync_lock` 像办公室门口唯一的一把钥匙。定时清扫员和管理员都想进去工作，但只有拿到钥匙的人能创建任务；任务结束、崩溃恢复或锁已指向终态任务时，钥匙才被归还或重配。顶栏只是门口的进度牌，不是另一套任务真相。

## §2 架构导览

### 2.1 共享 trigger 把“检查、落任务、落锁”串成一条路

`SyncCoordinator.trigger()` 先用进程内 `asyncio.Lock` 缩小单进程竞争，再检查 durable lock、活跃 job 和 pending 数；只有三项都表明可以新建时，才调用 `SyncLockRepository.create_job()`。该 repository 在同一事务里写 `job_runs` 和 `sync_lock`，所以插入锁失败不会留下孤儿 job（`apps/api/app/db/crud/sync.py:60-96`）。

### 2.2 scheduler 只触发同一入口

`_scheduler_loop()` 每轮等待 interval，再调用 `run_once()`；`run_once()` 没有另一套任务创建逻辑，而是直接调用 `trigger("scheduler", None)`（`apps/api/app/service/acquisition/sync.py:199-243`）。这让手动和定时任务共享所有去重规则，代价是 scheduler 错误只能通过 durable status 观察，而不能靠 SSE 推送。

### 2.3 JobRunner 的 terminal hook 释放锁

`JobRunner._run()` 在 success、failure、cancel 后都进入 `finally`，读取最新 job 并调用 terminal hook（`apps/api/app/service/jobs.py:238-283`）。`SyncCoordinator.release_terminal_job()` 先终结异常 sync audit，再按 jobId 删除匹配锁（`apps/api/app/service/acquisition/sync.py:179-197`）。这避免“任务已完成但锁永远占着”。

### 2.4 API 与 UI 都读 durable truth

`GET /api/acquisition/status` 从 source cursor、active job 和 latest sync batch 组合状态（`apps/api/app/service/acquisition/sync.py:161-177`）；顶栏只调用这个接口和 `/jobs/{id}`，不会自行推测 pending。admin 动作通过中央 middleware 的 `/api/acquisition/sync` 管理路径做角色限制（`apps/api/app/middleware/auth.py:19,51-60`）。

## §3 数据流走查

### 场景 A：scheduler 正常发现 pending

1. lifespan 完成 migration、identity seed 和 `jobs.start()` 后启动 scheduler（`apps/api/app/main.py:67-76`）。
2. 60 秒 tick 调共享 `trigger`。
3. trigger 发现 pending > 0，在同一事务创建 queued sync job 和 `sync_lock`。
4. JobRunner 串行 claim job，SyncCoordinator 调 root replay，并把进度写入 `job_runs`。
5. replay 完成 sync audit；runner 完 job 后 terminal hook 删锁。
6. 顶栏下一次 15 秒 status 轮询看到 processed 增加、pending 归零。

### 场景 B：管理员点“立即处理”

1. 顶栏对 authenticated user 显示 pending 摘要。
2. admin 打开用户菜单看到“立即处理”，member 不渲染该按钮（`TopNav.vue:174-205`）。
3. 前端 POST trigger；queued/reused 时以 500ms 轮询 job，idle 时直接失效 status。
4. terminal 后同时失效 acquisition status 与 `["sessions"]`（`TopNav.vue:74-105`）。
5. sync 不建立 SSE；页面导航与其他查询不被阻塞。

### 场景 C：进程在 sync 中途崩溃

1. 重启后 `JobRunner.start()` 将所有 running job 标 interrupted。
2. 旧 sync audit 被终结，旧锁释放；sync job 以新 replay id 重排。
3. scheduler 启动时修复活跃 job 缺失的锁。
4. 新 job 再次 replay pending payload，旧审计仍可查询。

## §6 讨论点

### D1 status 错误消息原样回显，可泄漏 token 和本地路径

**位置**：`apps/api/app/api/acquisition.py:54-69,87-88`

**现象**：`SyncStatusError.message` 直接取数据库中 `sync_runs.errors[].message`，只检查类型，没有脱敏或长度上限。我用一条合法结构的错误记录写入 `token=must-not-leak /private/local/path` 后调用 `/api/acquisition/status`，响应原样包含整段内容。

复现结果：

```text
assert "must-not-leak" not in response.text
AssertionError: response contains token=must-not-leak /private/local/path
```

**问题**：当前正常生产者确实只写稳定消息，但 API 把“历史/外部写入已可信”当作前提；旧版本、手工修复或未来 replay 错误一旦带路径/秘密，会直接进入所有登录用户可见的响应。这违反“status 返回脱敏错误”的契约。

**预判**：这是跨层安全边界，应在出站 DTO 构造时统一 `sanitize_job_error`/等价的稳定 message 映射并限制长度，而不是只依赖所有 producer 永远正确。建议 P1。

**结论**：已修复（2026-10-26）。status 出站层只接受稳定 code 闭集，并按 code 映射固定文案；未知 code 返回 `SYNC_ISSUE` 通用摘要。回归注入 token/绝对路径后响应与日志均不包含原值。

### D2 scheduler 异常使用 `logger.exception`，可能把数据库路径或驱动上下文写日志

**位置**：`apps/api/app/service/acquisition/sync.py:240-243`

**现象**：定时 trigger 失败时直接记录完整异常和 traceback；其他 job 路径只记录 `error_type` 和安全摘要。

**问题**：连接错误、SQLite 文件错误或驱动异常可能含本地绝对路径、DSN 片段或输入参数，与“同步错误只保留稳定 code/message，不写本地路径”的边界不一致。

**预判**：改成稳定 `error_type`/安全 code，并另加低基数指标；完整异常是否可写应在受控 debug 路径明确开关。建议 P2。

**结论**：已修复（2026-10-26）。scheduler 失败只记录固定事件名、异常类型和稳定 code，不再记录 traceback 或异常正文；caplog 回归覆盖 DSN、本地路径和 token。

### D3 admin 手动 job 进入 failed/interrupted 时没有可见反馈

**位置**：`apps/web/src/components/layout/TopNav.vue:86-105`

**现象**：轮询看到 terminal 状态后直接跳出循环，只失效查询；没有读取 job.error，也没有设置 `actionError`。现有 UI 测试只覆盖 running→completed。

**问题**：若 job 在创建 sync audit 前失败，status 的最新 errors 仍为空；用户看到按钮从“处理中”恢复为“立即处理”，不知道任务失败。即使已有 sync audit，错误也只藏在另一个 hover 区域。

**预判**：应在 failed/interrupted 分支把 job.error 转成统一、脱敏的用户文案，并补失败状态的组件测试。建议 P2。

**结论**：已修复（2026-10-26）。manual job 进入 failed/interrupted 后，顶栏显示固定脱敏提示并停止轮询；组件测试验证自由文本不进入 DOM。

### D4 restart recovery 的 job 调度与锁补建不是原子顺序

**位置**：`apps/api/app/main.py:73-76`、`apps/api/app/service/jobs.py:125-142`、`apps/api/app/service/acquisition/sync.py:81-88`

**现象**：`jobs.start()` 先恢复并重排 sync job，并且 `_schedule()` 已创建 asyncio task；之后 lifespan 才调用 `sync.start_scheduler()` 补建/认领锁。worker 在两次 await 之间存在先进入 handler 的调度窗口。

**问题**：替换 job 在极短时间内可能以 running 状态存在而 durable lock 尚未关联。当前单进程 V1 下复现依赖事件循环/数据库时序，测试没有直接断言 handler 首行必须看到锁，但该不变量没有被代码结构保证。

**预判**：把“恢复/重排”与“开始调度”拆开，先补锁再放行 sync worker，或由 coordinator 在 job 调度前完成 adoption。建议 P2，需确定性回归。

**结论**：已修复（2026-10-26）。启动流程拆为 recover、lock adoption、dispatch 三阶段；replacement job 在 lock adoption 前保持 queued，确定性回归验证 dispatch 时锁已存在。

### D5 status 的 active state 与 latest batch numbers 可能来自不同批次

**位置**：`apps/api/app/service/acquisition/sync.py:161-177`

**现象**：active job 和 latest sync batch 分别查询；job 刚 queued、尚未创建本轮 `sync_runs` 时，status 已经显示 `queued`，但 imported/skipped/errors 仍来自上一批。

**问题**：顶栏 hover 会把两个时间点的数据拼成一句话，短窗口内产生误导；目前没有直接安全或一致性损害。

**预判**：非阻断，可在 status DTO 中明确 `latestBatch`，或按 active job 的 `ref_id` 优先取对应 batch，只有 idle 时回退 latest。建议 P3。

**结论**：已修复（2026-10-26）。status 的 pending、processed、active job 与对应 batch 在同一数据库快照读取；active job 有 `ref_id` 时只读取其批次，缺失时返回零批次而不是借用最新批次。
