## §1 一页速览

一句话：这个 PR 把 M1 的“能登录的空白应用”收口成可演示的产品壳，统一了加载、空、错误和 409 反馈，并提供不造领域数据的 seed 与真实浏览器 E2E。

生活化比喻：页面三态像交通信号灯，health 是总闸，各业务页面不再各装一套灯泡；seed 像新房交付时只放钥匙和门禁卡，不摆假家具；E2E 则是每次装修完真的开门走一遍，而不是只看电路图。

| 交付块 | 结论 |
|---|---|
| Sessions / Errors / Evolution 导航 | 实现完整，active 状态和鉴权边界成立 |
| health loading/error/retry | 已接入真实 query，shell 与导航保留 |
| 404、409、全局未捕获错误 | UI 语义成立，真实 Chrome 已覆盖 409 toast |
| demo 角标 | 只由 `phase=demo` 驱动，scaffold/live 单测覆盖 |
| fixtures seed | 只走迁移和既有管理员播种，无领域假数据 |
| 真实 Chrome E2E | 2/2 本地通过，CI build lane 已实际执行 |

## §2 架构导览

### 2.1 启动与全局壳

浏览器启动仍由既有 `bootstrapApp` 完成 Pinia、Vue Query、鉴权和 router 初始化，再挂载 `App.vue`。`App.vue:13-20` 根据路由 `authLayout` 决定是否查询 health：登录和强制改密页不请求受保护壳依赖，业务页使用共享 `["health"]` query。

`App.vue:76-115` 的模板关系是：

```text
shell
├── TopNav（非 auth layout）
├── health loading → LoadingSkeleton
├── health failure → ErrorState + retry
└── health success / 409 conflict → RouterView
```

这意味着后端 health 首次加载和数据库 503 都使用真实请求结果，不存在运行时 stub 分支；错误时 TopNav 仍保留，用户不会只剩一张白页。

### 2.2 导航与演示状态

`TopNav.vue:35-45` 固定展示 Sessions、Errors、Evolution 三个入口。Router 在 `router/index.ts:26-38` 注册对应路由，其中 `/errors` 是懒加载且没有 `public` meta，因此仍受既有鉴权守卫保护。

`App.vue:78-81` 只把 `data.phase === "demo"` 传给顶栏；`TopNav.vue:46-53` 据此决定角标。演示标志和业务数据分离，scaffold/live 不会因为“开发环境”或“有管理员账号”而误显示角标。

390px 规则集中在 `TopNav.vue:198-243`：1100px 隐藏副标题，640px 进一步隐藏品牌文字、压缩导航和用户名。真实 E2E 在 390×844 下同时保留三门导航与用户入口。

### 2.3 共享三态

三个 UI 组件均为无业务语义的表现层：

- `LoadingSkeleton.vue:14-28` 提供 `role=status`、`aria-live=polite` 和一个屏幕阅读器标签。
- `EmptyState.vue:14-30` 承载标题、说明与可选 action slot。
- `ErrorState.vue:28-47` 承载 code、message、可选 retry；404 传 `retryable=false`。

页面只提供领域文案：Sessions 明确“后续 milestone 接入”，Errors 明确“不展示模拟问题”，Evolution 保留 Vue Flow 画布，不把空壳伪装成真实运行。

### 2.4 全局错误与 409

`createAppQueryClient()` 在 QueryCache 和 MutationCache 上安装同一个 `onError` 接缝（`queryClient.ts:18-23`）。`presentConflict()` 只接管 `ApiError(409)`，通过注入的 `notify` 显示服务端安全消息，不替换页面（`apiError.ts:9-17`）。

`installGlobalErrorHandler()` 捕获 Vue 渲染/事件处理中的未处理异常，控制台上报一次，用户侧只显示固定通用文案（`globalError.ts:13-16`）。`main.ts:3-5,16-30` 将真实 `ElMessage` 和其 base/message CSS 注入两条错误路径。

### 2.5 Seed 边界

`fixtures/m1-shell.json` 只有 `version/scope/actions` 三个字段，`app/cli.py:24-31` 用 `extra="forbid"`、闭集 action 和固定 scope 拒绝扩展字段。`_ensure_seed_environment()` 在打开数据库前拒绝 `production` 与 `phase=live`。

`_seed()` 只运行迁移并调用既有 `IdentityService.seed_admin_if_empty()`（`cli.py:59-78`），没有创建 session、bad case、probe、run 或任何前端假数据。没有管理员环境变量时返回诚实的 `noop`。

### 2.6 E2E 与共享运行时

`tests/support/runtime.mjs` 把端口分配、子进程清理、Chrome/CDP 连接、DOM 等待和浏览器错误收集抽成共享能力。Integration 与 E2E 共用这套实现，避免两份 CDP 协议分叉。

`tests/e2e/m1-shell.test.mjs:73-136` 启动真实 FastAPI、临时 SQLite 和 Vite；测试用 refresh cookie 进入已鉴权页，验证三种导航、demo 角标、Errors/Evolution 占位和 390px 布局。第二个场景拦截 health 并返回 409，验证 Message 固定定位、导航和页面均保留。

## §3 数据流走查

### 场景 A：登录后进入演示壳

1. `bootstrapApp` 恢复会话，路由就绪后挂载 App。
2. `App.vue:16-20` 查询 `/api/health`。
3. 响应 `phase=demo` → `TopNav` 显示“演示数据”。
4. RouterView 渲染 Sessions 空态；用户点击 Errors 或 Evolution 时只替换 RouterView。
5. health 状态 pill 显示协议中的数据库方言，页面数据仍来自真实表。

### 场景 B：health 加载与失败

1. 初次 pending 时，shell 与导航已存在，RouterView 暂时由骨架替代（`App.vue:98-106`）。
2. 503 或网络错误时，`healthFailure` 变为 true，显示 `ErrorState`（`App.vue:107-112`）。
3. 用户点击重试，`retryHealth()` 触发同一 query 的 refetch；成功后 RouterView 恢复，失败则错误态继续保留。
4. 单测用 pending handler 和 503→200 两段响应证明该状态切换。

### 场景 C：409 非阻塞提示

1. health 或任意 Query/Mutation 抛 `ApiError(409)`。
2. QueryClient cache 调到 `presentConflict()`。
3. `ElMessage.error()` 显示后端消息。
4. App 把 health 409 识别为 conflict，不进入整页 `ErrorState`；当前 RouterView 与 TopNav 保持。
5. 真实 E2E 拦截 health 请求，断言 toast 文案、fixed 定位、导航、页面，以及无整页错误态。

### 场景 D：开发/演示 seed

1. `pnpm fixtures:seed` 加载 `fixtures/m1-shell.json`，并转发给 API venv。
2. `app.cli` 先校验 manifest 和环境，再打开数据库。
3. 迁移到 head，调用既有管理员播种。
4. 有管理员凭据且空库时创建一名强制改密 admin；否则返回 `noop`。
5. 第二次执行仍保持单用户，不产生领域表或重复行。

### 场景 E：真实浏览器 E2E

1. Node test 启动 API、Vite 和临时数据目录。
2. `createBrowserPage()` 启动隔离 headless Chrome，启用 Page/Runtime/Log。
3. 测试写入 refresh cookie，导航到 `/sessions`。
4. CDP DOM 断言读取导航、角标、空态、路径与 390px 边界。
5. 浏览器 warning/error/exception 汇总后断言为空；测试结束关闭 Chrome 并终止进程树。

## §6 讨论点

### D1 新 E2E 门禁没有接入仓库的元门禁与“全测试”入口

**位置**：`.github/workflows/ci.yml:54-55`、`package.json:20-22`、`scripts/gates.spec.mjs:290-336`、`scripts/route-gates.mjs:28-68`、`AGENTS.md:60`、`docs/development.md:30`。

**现象**：PR 在 CI 增加 `pnpm test:e2e`，但 `test:all` 仍是原来的 `test:web + test:api + test:db:mysql + test:integration`；`scripts/gates.spec.mjs` 没有断言 `test:e2e` 脚本存在或 CI 真的调用它；`route-gates` 对 `tests/e2e/**` 没有路由项，实际运行 `node scripts/route-gates.mjs --base origin/main` 的建议列表里也没有 `pnpm test:e2e`。新增的 `fixtures:seed` 同样没有进入命令清单或门禁自测。

**问题**：根 `AGENTS.md:60` 明确要求门禁脚本改动同步更新 AGENTS 与 `scripts/gates.spec.mjs`，本 PR 修改了 CI 门禁却未做。于是 CI YAML 中一行删除就能让 E2E 静默消失，现有 gate self-test 仍会全绿；开发者按文档运行 `test:all` 也会误以为已经跑过新的真实浏览器测试。

**预判**：这是应在合并前修复的流程缺口，不是产品运行缺陷。建议把 `test:e2e` 加入 `test:all`，在 gate spec 中钉住 package script、CI step 与 route recommendation，同步 AGENTS/development 中英命令清单，并把 `AGENTS.md` 加入 issue scope。

**结论**：
已修复（2026-10-25）。`test:all` 纳入 `test:e2e`；CI 增加 E2E 与 fixtures seed 清单冒烟；`scripts/gates.spec.mjs` 钉住 package scripts、CI step、route-gates 推荐和零匹配行为；AGENTS 与中英文开发指南同步命令清单，m1-09 scope 纳入 `AGENTS.md`。

### D2 浏览器错误门禁存在可漏报的通道

**位置**：`tests/support/runtime.mjs:285-293`、`tests/e2e/m1-shell.test.mjs:226-303`。

**现象**：浏览器 helper 把所有来源的 `401` 和 `404` 网络错误都当成预期 auth probe 忽略，而不是只忽略具体端点或具体测试声明的期望错误；第二个 409 E2E 创建了 `violations` 和 `window.__e2eErrors`，却只断言 toast/nav/page，没有断言这两个错误集合为空。

**问题**：缺失脚本、样式或动态路由 chunk 的 404 不会让 E2E 失败；409 分支即使伴随 Vue warning、runtime exception 或未处理 rejection，也仍可通过。验收标准写的是“无控制台错误”，当前门禁只能证明部分通道为空。

**预判**：应让 `browserViolations()` 接受测试级 expected-failure 谓词，默认不吞 404；409 场景在 toast 出现并稳定后断言 `violations=[]` 与 `runtimeErrors=[]`。这不会扩大产品范围，只是让现有浏览器证据可信。

**结论**：
已修复（2026-10-25）。浏览器日志默认不再吞任何 401/404；测试只能用精确 URL/status 谓词声明预期网络失败。409 场景单独声明 `/api/health` 409，并在 toast 出现后断言 browser violations 与 runtime errors 均为空。严格门禁还捕获了缺少 favicon 造成的一个真实 404，已补站点图标而非隐藏错误。

### D3 E2E 过滤零匹配会挂起，并绕过子进程清理

**位置**：`scripts/run-e2e.mjs:13-18`、`tests/e2e/m1-shell.test.mjs:73-136`、`tests/support/runtime.mjs:85-112`。

**现象**：实际执行 `pnpm test:e2e -- definitely-not-a-real-test` 后，进程超过 90 秒仍不退出；手动中断后，本次启动的 FastAPI、Vite 和 Python 子进程仍在运行，只能额外按进程组终止。匹配测试名的 `pnpm test:e2e -- m1-shell` 则能正常 2/2 通过并清理。

**问题**：runner 把任意非 flag 参数直接变成 test-name-pattern，却没有零匹配预检或总超时；Node 仍执行文件级 `before` 启动真实服务，零测试时没有正常走到 `after`。模式拼错会让开发者卡住，并可能污染下一轮端口、数据库和 Chrome 测试。

**预判**：建议在启动服务前识别未匹配测试并立即失败，或给 E2E runner 增加有界总超时与信号清理兜底。CI 当前不带 pattern，因此这不是现存 CI 红灯，但会让 issue 指定的局部 E2E 命令不可靠。

**结论**：
已修复（2026-10-25）。E2E runner 在启动 Node 测试文件前静态提取测试名并检查 pattern；零匹配立即以退出码 2 失败。runner 增加 180 秒上限；测试运行时增加 SIGINT/SIGTERM 清理与 before 失败兜底，确保 FastAPI、Vite、SQLite 和临时目录被回收。
