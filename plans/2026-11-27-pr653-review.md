## §1 一页速览

**一句话**：把两个 shallow 缓存从“目录像仓库就可复用”改成“由文件锁串行、由生命周期标记判定可复用、坏缓存删除重建”，让 SIGKILL 或重启残留的 `shallow.lock` 最多造成一次自动重建。

**一个比喻**：缓存像一间共享工具房。以前只看门有没有锁孔就认为工具齐全，谁把半成品留在里面都没人知道；现在进门前先在门外的登记本上拿号（`flock`），使用时在门上挂“施工中”（`incomplete`），收工挂“可用”（`complete`）。停过电的房间（SIGKILL）一定挂着“施工中”，下一个人直接清空重摆，而不是继续在半成品上修。

**交付块**

| 块 | 内容 | 验证 |
|---|---|---|
| 所有权 | `<cache-root>/.locks/` 下的跨进程 `flock`，进程死亡自动释放 | 并发共用一次 clone；SIGKILL 后能重新拿锁 |
| 生命周期 | 缓存目录旁 `<ref-key>.state.json`，`incomplete`/`complete` 原子写 + fsync | 半成品重建；旧缓存补写 complete 沿用 |
| 自愈 | flock 内清理 git 锁、锁冲突清理重试一次、坏缓存删除重建 | 残留锁恢复；持久冲突分类为 `cache_stale_lock` |
| 启动兜底 | job recovery 前清扫两个缓存根 | 启动清扫用例 |
| 失败分类 | 内容读取新增 `cache_stale_lock`；workspace 保持可重试 fetch 失败 | m19/m24 回归全绿 |

## §2 架构导览

### 2.1 共用缓存层 `cache.py`

- **跨进程锁**：`cache_flock`（cache.py:285）在缓存根的 `.locks/` 下按 cache key 哈希出稳定锁文件，`_await_flock`（cache.py:427）用非阻塞 `fcntl.flock(LOCK_EX|LOCK_NB)` 每 50ms 重试。非阻塞循环而不是 `to_thread(flock)`，是为了让等待中的协程可取消：取消时关闭 fd，不会把锁泄漏到进程重启。
- **状态标记**：`write_state`（cache.py:137）写临时文件、`fsync`、`os.replace`，再 fsync 目录；`read_state`（cache.py:106）把损坏/缺字段当成“无标记”，交给重建。标记是缓存目录的**兄弟文件**，因为 `git clone` 要求目标目录为空。
- **git 锁清理**：`git_lock_files` 覆盖裸仓与 `.git` 两种形态，清理 `shallow.lock`、`index.lock`、`HEAD.lock`、`config.lock`、`packed-refs.lock` 与 `refs/**/*.lock`；`clean_git_locks`（cache.py:220）只在持有 flock 时调用。
- **冲突识别**：`is_lock_conflict`（cache.py:234）只认 `Unable to create ... .lock` 与 `Another git process seems to be running`，避免把网络失败误判为锁。
- **启动清扫**：`sweep_cache_root`（cache.py:308）对每个缓存先拿非阻塞 flock；拿不到说明有活跃操作，跳过。拿到后删除 `incomplete` 缓存、删除带锁的无标记旧缓存、清理其余遗留锁。删除动作在锁内，避免清扫踩到另一个进程的 fetch。

### 2.2 目标内容读取 `content.py`

`read_file_at_commit`（content.py:126）把整段读取包在“进程内 `asyncio.Lock` → 跨进程 `flock`”里，再执行 `_ensure_commit`（content.py:166）和 `git show`。`_ensure_commit` 分两条路：

- **可复用**：`_reusable`（content.py:250）要求结构可用，且 `complete` 标记匹配，或旧缓存无标记且无 git 锁。清理锁 → 写 `incomplete` → `_refresh`（content.py:215）→ 写 `complete`。
- **重建**：删除目录与标记 → 写 `incomplete` → clone/init → fetch → 写 `complete`。

失败处置：取消时清理锁并保持 `incomplete`；普通 git 失败若缓存里出现锁（说明 fetch 被中断、对象库可能半成品）也保持 `incomplete` 让下次重建；否则恢复 `complete`，保住“网络抖动不丢完整对象”。

### 2.3 run 准备 `workspace.py`

`_ensure_ref_cache`（workspace.py:1221）同样用进程内锁 + flock，把规则收在 `_ensure_ref_cache_locked`（workspace.py:1233）：

- 可复用条件 = 结构可用 +（`complete` 标记匹配，或无标记且无锁）；随后再校验 `git remote get-url origin` 与当前 `repo_url` 一致。
- 可复用：清锁 → 记录 `previous` commit（完整 commit 看对象是否存在，分支/tag 看 `refs/heads/harness-target`）→ `incomplete` → `_fetch_ref`（workspace.py:1331）→ `complete`。
- 不可复用：`_build_ref_cache`（workspace.py:1306）先写 `incomplete` 再 `git init --bare`，失败删除目录与标记；成功 fetch 后写 `complete`。

`_fetch_with_lock_retry`（workspace.py:1377）对同一 argv 在锁冲突时清理并重试一次；`_fetch_error`（workspace.py:1389）在仍冲突时写 `git.cache.stale_lock` 日志，并保留原有的可重试分类与失败文案。

### 2.4 启动兜底 `main.py:619`

lifespan 在 `identity-seed` 之后、`jobs.recover()` 之前调用 `sweep_cache_roots(target-content, repos)`。清扫失败只记 `git.cache.sweep_failed` 警告，不阻断启动；两个根都不存在时是空操作。

## §3 数据流走查

**场景 A：残留 `shallow.lock` 的内容读取**

1. 读取同一 `(repo_url, ref)`，缓存目录与 `complete` 标记都在。
2. `cache_flock` 拿到锁；`_reusable` 因标记匹配返回真。
3. 清理 `.git/shallow.lock`；写 `incomplete`。
4. `git fetch --depth 1 ...` 成功；解析 `FETCH_HEAD`。
5. 写 `complete`；`git show` 返回文件；调用方看不到 `repo_unreachable`。
6. 若 fetch 仍报锁冲突：清理后重试一次，仍失败 → `cache_stale_lock` + `git.cache.stale_lock` 日志，缓存恢复 `complete` 供下次重试。

**场景 B：进程在 fetch 中被 SIGKILL**

1. 缓存旁留下 `incomplete`，仓库里有 `shallow.lock`，flock 随进程死亡被内核释放。
2. 下一次读取拿到 flock，`_reusable` 因 `incomplete` 返回假。
3. 删除缓存目录与标记，按单 ref 重新 clone/fetch；成功后写 `complete`。重建只影响这一对 `(repo_url, ref)`。

**场景 C：启动清扫**

1. lifespan 在 job recovery 前遍历两个根的两级缓存目录。
2. 对每个目录尝试非阻塞 flock；活跃缓存跳过。
3. `incomplete` 缓存与带锁旧缓存删除；其余清理遗留锁。
4. `git.cache.sweep` 记录删除/清理数量；随后 job recovery 看到的是可复用或待重建的缓存。

**场景 D：并发读取同一 cache key**

进程 A 拿 flock 开始 clone；进程 B 的协程在 `_await_flock` 里等待（可取消）。A 写 `complete` 释放锁；B 拿到锁看到 complete，只做一次刷新，不再 clone。测试断言 clone 恰好一次。

## §6 讨论点

### 6.1 启动清扫与第二个进程的竞争

- **位置**：`apps/api/app/third_party_api/git/cache.py:308`
- **现象**：清扫会对每个缓存目录删除 `incomplete` 缓存。
- **问题**：如果同机还有第二个 API 实例正在 clone/fetch，这个缓存正被活跃操作持有；无锁删除会踩坏它。
- **预判**：单实例部署是当前前提，但 issue 明确要求同机多进程安全。清扫应先拿同一把非阻塞 flock，拿不到就跳过。
- **结论**：已按此修复（2026-11-27）：清扫在 `_try_flock` 内评估与删除，活跃缓存跳过。

### 6.2 刷新失败何时恢复 `complete`

- **位置**：`content.py:166`、`workspace.py:1233`
- **现象**：普通 git 失败后，若缓存里没有 git 锁就恢复 `complete`；有锁则保持 `incomplete`。
- **问题**：用“失败后是否留下锁”推断缓存是否完整，是一次启发式判断；若 git 在退出前自行删掉了锁但对象库仍不完整，会错误复用。
- **预判**：git fetch 的 pack 是原子落盘，优雅退出会清理锁；真正的中断（SIGKILL/进程组被杀）会留下锁。启发式成立，且下一次 `git show`/fetch 失败仍会触发重建，不会永久卡死。
- **结论**：

### 6.3 完整 commit 冷缓存的失败语义

- **位置**：`content.py:166`、`workspace.py:1306`
- **现象**：完整 40 位 commit 冷缓存首次 fetch 失败会删除目录；旧行为也是删除半成品。
- **问题**：真实网络失败与不可达仍按 `repo_unreachable` / 可重试失败上报，是否有行为变化？
- **预判**：冷缓存本来就没有可保留的完整对象，删除半成品保持原语义；可复用缓存的刷新失败才保留。

## §9 文件级代码分析

### 9.1 `third_party_api/git/cache.py`（A，480 行）

**职责**：两个 shallow 缓存共用的所有权、生命周期与启动恢复。**变更形态**：新增。

**关键依赖**：标准库 `fcntl`（POSIX 文件锁，内核在进程退出时释放）、`msvcrt`（Windows 分支，经 `importlib` 延迟导入避免非 Windows 类型检查问题）、`os.replace` + `fsync`（原子标记）。没有第三方依赖。

**实现思路**：

- 锁文件放在缓存根 `.locks/`，哈希 cache key 后命名；重建删除的是缓存目录，不会让等待者锁住失效 inode。
- 标记是目录的兄弟文件，`phase/repo_url/ref/started_at/commit` 五个字段；`read_state` 对坏文件返回 `None`，等价于“需要重建”。
- 清理 git 锁前必须先持有 flock；因此 `clean_git_locks` 的调用点都在 `cache_flock` 内。
- 清扫对所有目录先 `_try_flock`，拿不到就跳过；这同时满足“启动阶段无需竞争”和“同机多进程不互相踩”。
- 日志只写 cacheKey（相对路径）、repoHost（URL host）、refHash（sha256 前 16 位）。

**检视发现**：初版清扫在拿锁前删除未完成缓存，已修复（§6.1）；其余无发现。

### 9.2 `third_party_api/git/content.py`（M，+179/−40）

**职责**：目标内容读取的单 ref 缓存。**变更形态**：修改既有 `SubprocessGitContent`。

**关键依赖**：沿用原有 `_git` 进程 seam 与 20s 超时；新增依赖仅为本地 `cache` 模块。

**变更块**：

- `read_file_at_commit` 把 `flock` 与进程内锁并列，`git show` 的懒 blob fetch 若报锁冲突则清理重试一次。
- `_ensure_commit` 从“分支/完整 commit 两个 if”改为“可复用/重建两条路”，每条都写完整生命周期标记。
- `_fetch_ref` 的候选循环改为调用 `_fetch_with_lock_retry`，只有非 missing-ref 失败才抛分类错误。
- `_fetch_failure`/`_show_failure` 优先识别锁冲突，返回新 reason `cache_stale_lock`。

**实现思路总结**：把“缓存是否可信”从结构判断换成标记 + 锁证据；失败路径区分“可保住的完整缓存”和“必须重建的半成品”。

**检视发现**：无新发现；与 issue 的失败分类要求一致。

### 9.3 `third_party_api/git/workspace.py`（M，+134/−30）

**职责**：run 准备的裸缓存与工作区。**变更形态**：修改 `_ensure_ref_cache` 一段。

**关键依赖**：既有 `GitOperationError` 分类与 `GitPushProvider`；新增本地 `cache` 模块。

**变更块**：

- `_ensure_ref_cache` 只负责“进程内锁 + flock”，规则进 `_ensure_ref_cache_locked`。
- 可复用分支保留 `previous` commit，失败时恢复 `complete`；出现 git 锁说明 fetch 被中断，保持 `incomplete`。
- `_build_ref_cache` 在 `git init --bare` 前写 `incomplete`；`_remove_cache` 同时删标记。
- `_fetch_with_lock_retry` 与 `_fetch_error` 统一锁冲突重试与日志。
