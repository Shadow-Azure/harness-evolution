## §1 一页速览

一句话：给 agent 进化对象加一个默认关闭的 `.env` 例外，让“同名但正文 hash 不同”的 Session 在总览里合并成配置 ref 一行，同时把报告与缓存继续钉在 body hash 上。

比喻：body hash 像身份证号，名称像姓名。默认按身份证号索引，避免同名不同人混在一起；这个开关只在 agent 这个窗口允许按姓名索引，档案（报告）、缓存和启动用的原文仍按身份证号保存。

## §2 架构导览

### 2.1 配置层

`Settings` 是唯一的运行时配置入口，`HE_` 前缀由 `SettingsConfigDict` 统一处理。新字段 `agent_match_by_name: bool = False` 只是增加一个布尔项；非法值沿用 Pydantic 启动校验失败，不新增容错分支（`config.py:161`）。

`.env.example` 把它放在归因可选组附近，并写明“仅影响 agent 目标、默认关闭、改后重启 `harness-api`”。

### 2.2 共享匹配器

`PotentialMatcher` 继续是向导、启动前检查、绑定 worker 与总览共用的关联实现。开关在构造函数进入（`potential.py:592-600`），只改 `associated_sessions` 的一个谓词：

```python
ignore_revisions = self._agent_match_by_name and condition.target_type == "agent"
```

当且仅当对象类型是 agent 时，`observed_revisions` 的哈希过滤被跳过；`skill/knowledge` 仍走原 `isdisjoint(...)` 分支（`potential.py:637-648`）。没有传 `observed_revisions` 的调用（向导第 2/3 步、启动、绑定）本来就不受影响。

### 2.3 总览版本构建

`TargetOverviewService` 多了一个同名开关（`targets.py:661-670`）。`_analyse_target` 在 agent 名称模式下不再用 `_build_version_labels` 从事件 digest 累积版本，而是：

- 版本键 = 规范化后的 `defaultRef`，显示 ref 也是它；
- 内容解析只用于拿 revision/commit 证据；解析失败时 `resolved=None`；
- 别名集合 = `defaultRef` + 解析出的 version/revision + 裸 hash + 该对象所有历史报告的 `object_version`（`targets.py:570-600`）；
- 每个 case 用别名集合选最新报告（`_newest_link_by_case`），因此折叠后 attributed/nonTarget 不会归零；
- 解析失败时用一个占位 `ResolvedTargetVersion` 调匹配器，总览仍按名称关联（`targets.py:1000-1010`）；启动链路不经过这里，仍保留原显式错误。

skill/knowledge 完全走原 `_build_version_labels` 分支。

## §3 数据流走查

同一条 agent 目标 `Explore`、`defaultRef=main`、两条事件版本 v1.0.0 / v1.5.0 的剧本：

1. 总览列表进入 `_analyses` → `_analyse_target`（`targets.py:947`）。
2. 读窗口 case、事件版本、runs、attribution links（`targets.py:948-960`）。
3. `name_matched=true` 时走 `_name_matched_version`（`targets.py:1039`）：解析 `main` 内容，构造一个 label；即使解析失败也返回一个版本行。
4. 循环 `_newest_link_by_case(links, label.aliases)` 把历史报告挂到该行；再调 `_evaluate_resolved`，其 `associated_sessions` 因匹配器开关忽略 revision，按名称收进两个 Session。
5. `TargetAnalysis.versions=("main",)`；detail 的 `byVersion` 只有一行；`stats.sessions=2`、`potential=2`、`attributed=1`。
6. 关闭开关时同一步骤走旧 `_build_version_labels`：三行（v1.5.0、v1.0.0、main），main 行 0 Session，attributed 报告落在 v1.0.0。
7. 启动/向导不经过总览服务：`TargetContentResolver` 仍读 `AGENT.md`，缺失仍返回 `TARGET_CONTENT_UNRESOLVED`。

## §6 讨论点

### 讨论点 1：开关同时存在于服务与匹配器

- **位置**：`apps/api/app/main.py:381`、`apps/api/app/main.py:400`、`apps/api/app/service/overview/targets.py:661`
- **现象**：`PotentialMatcher` 与 `TargetOverviewService` 各持一份 `agent_match_by_name`，由 `main.py` 同时传入。
- **问题**：未来若有新的装配点只传一侧，总览可能“折叠了版本行但没放开关联过滤”（或相反），出现难排查的混合口径。
- **预判**：当前唯一生产装配点已同时传入，issue 也明确要求两处都改；可接受。长期可让服务读取 matcher 的能力位，或加启动断言。
- **结论**：2026-11-26 采用双重防护：名称行在 `_evaluate_resolved` 显式传 `observed_revisions=None`，不依赖 matcher 的第二份开关；新增服务级单测固定该调用。

### 讨论点 2：名称模式仍会尝试内容解析

- **位置**：`apps/api/app/service/overview/targets.py:1046-1048`
- **现象**：名称模式仍调用 `_resolve_version` 读取 `AGENT.md`，只为拿到 ref/commit 证据；失败时总览仍关联。
- **问题**：每次总览加载可能多一次有界内容读取；失败缓存 30 秒，首次仍可能等待超时。
- **预判**：版本行需要 commit 证据时这是必要成本；若后续确认总览不需要 commit，可跳过解析。当前保留与原型一致的 ref/commit 语义。
- **结论**：

### 讨论点 3：别名集合包含该对象全部历史报告版本

- **位置**：`apps/api/app/service/overview/targets.py:570-600`
- **现象**：名称模式把该对象所有历史报告的 `object_version` 都加入别名，`_newest_link_by_case` 按 case 取最新一条。
- **问题**：同名不同正文的历史报告会合并到同一行，counts 可能比 hash 模式更大；这是开关的预期代价。
- **预判**：issue 明确要求“历史报告仍挂在该行”，且按 case 取最新；不做按正文二次拆分。
- **结论**：

## §9 文件级代码分析

### `apps/api/app/config.py`

变更形态：M。职责：环境配置单一入口。新增一个布尔字段，不引入新 validator；Pydantic 的 bool 解析负责拒绝非法值。思路：把开关放归因配置附近，和它影响的匹配层放在同一阅读区。

### `apps/api/app/main.py`

变更形态：M。三处装配：预览 matcher、共享 matcher、总览服务。前两处让匹配器拥有同一开关；第三处让总览决定是否折叠版本行。思路：单一装配点同时传值，避免生产出现混合口径。

### `apps/api/app/service/evolution/potential.py`

变更形态：M。`associated_sessions` 是唯一改动的查询方法。新谓词 `ignore_revisions` 只在 agent 且开关开启时为真；其他分支、计数、排序不变。思路：把“是否按 revision 过滤”收在共享匹配器内，overview 之外未来若传 revision 也自然遵守。

### `apps/api/app/service/overview/targets.py`

变更形态：M。新增两个纯函数与一个服务方法：

- `_agent_name_aliases`：把配置 ref、解析 revision、裸 hash、历史报告版本折叠成别名集合；
- `_name_match_commit`：从最近 run 找 ref/revision 对应的短 commit；
- `_name_matched_version`：构造单行 label；
- `_analyse_target` 分支：名称模式走单行，普通模式保持旧路径；解析失败时用占位 revision 调匹配器。

思路：只在“选哪些版本行”和“每行接受哪些别名”两处特化，匹配器与报告范围不动。
