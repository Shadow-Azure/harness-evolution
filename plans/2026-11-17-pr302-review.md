## §2 架构导览

### 2.1 生产层：只补一个闭集分支

`RunDetail.vue:223` 的 `blockedStageLabel` 把 `run.blockedStage ?? run.error.stage` 映射为人类可读阶段。m10-04 已把契约的 closed set 扩到 `patch|push|eval|attribution`，但前端 switch 没有 attribution 分支，因此真实 blocked attribution run 落入 `default: 未知阶段`。本 PR 只增加 `case "attribution"`，不改变阶段来源、优先级或 banner 结构。

banner 本体在 `RunDetail.vue:420`：阶段、错误、`retryAttempts`、`nextRetryAt`、人工重试按钮都由 run 快照驱动；人工重试仍走既有 `retryEvolutionRun`，有受理去抖与自动恢复，不把“已提交”说成“已成功”。

### 2.2 E2E 层：用真实 API/SQLite 证明前端只消费后端事实

`m10-06-run-detail-v2.test.mjs` 不 mock HTTP，起真实 FastAPI + Vite proxy + headless Chrome，和 m5 详情 E2E 同样经 `installCookie` 使用真实 refresh cookie。

fixture `m10_06_run_detail_fixture.py` 直接写库，产出三个 run：

- `run-v2-completed`：`progress_unit=8`、2 簇，6 个候选（5 attributed + 1 non_target）、2 个簇、2 个轮次、6 条事件；
- `run-v2-blocked-attribution`：`progress_unit=3`、`blocked_stage=attribution`、`retry_attempts=2`，只到 step 4；
- `run-v2-legacy`：`attribution_engine=legacy-probe-import`、V1 `progress_unit=6`，验证历史 run 由后端投影成七步。

数据不是“造一个刚好能过的空壳”：Session 页有 5 个关联 Session，潜在页有 6 个 included 候选，Step 4 有 cached/fresh/non_target，Step 5 有 9.1 与 7.8 两个严重度、non_target 不在簇内。

### 2.3 为什么不在前端重算

E2E 的断言全部读 DOM 的最终事实：第 2 页只有 1 条、第 5 步首簇 `aria-expanded=true`、blocked run 的 `stepRequests` 只出现 attribution。它们没有从 `progress.unit` 反推，也没有在前端补簇；这保证 m10-04 的“后端唯一状态源”没有被测试绕过。

## §3 数据流走查

1. 登录改密后，`openRun` 全页导航到 `/workspaces/ws-default/evolution/runs/run-v2-completed`；详情页并行取 `GET /runs/{rid}` 和默认 step（completed 默认 final），`useEvolutionRunStep` 只在 `clickable` 时发请求。
2. 点击 stepper 的 sessions，URL query 改为 `?step=sessions`，只请求 `GET /steps/sessions?page=1&pageSize=4`；第 2 页点击后只把 `page=2` 重发同一个 step 端点。
3. 点击 potential/attribution/clusters，分别只请求对应 step；Step 4 渲染 `summary.potential/reused/fresh/nonTarget` 与每行 `source`；Step 5 直接使用后端 `clusters[]` 顺序，首簇默认展开。
4. blocked run 默认选中第一个 active（attribution），页面请求 `GET /steps/attribution`；banner 读取 `blockedStage`、`retryAttempts`、`nextRetryAt`，不请求 clusters/iteration/final。
5. 执行日志 tab 以 `GET /events?afterSeq=0&limit=100` 为事实源；事件带 `stepIndex` 时点击跳 step，带 `clusterId` 时跳到 clusters 并高亮，带 error 时展开脱敏 detail。

## §6 讨论点

### 6.1 Step 4 是否也要分页？

- **位置**：`StepAttribution.vue:14`、`05-api-design.md` §3.6 attribution payload。
- **现象**：issue 的实现内容写了“Step 2–4 使用分页表”，但 Step 4 的 API payload 没有 `total/page/pageSize`，设计 08 §10 也只给 Step 2/3 标了每页条数。
- **问题**：如果在浏览器私自切页，会与服务端行序、summary 和后续聚类脱节。
- **预判**：本 PR 保持 Step 4 一次展示服务端返回行，分页留给 API 演进。
- **结论**：保持现状；已在 PR 边界和 Note 记录。

### 6.2 前端是否需要防御性重排簇？

- **位置**：`StepClusters.vue:16`、`05-api-design.md` §3.6（`clusters[]` 按 severity 降序）。
- **现象**：组件直接使用后端数组顺序，首簇默认展开。
- **问题**：如果前端再排序，会与后端 rank、深链和轮次引用形成第二套规则。
- **预判**：排序是后端持久化事实，前端只渲染。
- **结论**：保持现状；E2E 断言首簇 9.1、次簇 7.8，覆盖顺序。

### 6.3 08 §10.1 的 infoPanel 策略/缓存 chip 为什么没加？

- **位置**：`RunDetail.vue` infoPanel、`05-api-design.md` §3.6 RunDetail 字段。
- **现象**：08 §10.1 的结构图提到策略/缓存 chip，但 RunDetail 契约没有 `potentialPolicy` / `cacheEnabled`，只有 Step 1 的 `condition` 有。
- **问题**：要加就必须扩展 API 或每页额外请求 range step；m10-06 scope 是 web/e2e，没有 API 变更授权。
- **预判**：本 PR 保持 Step 1 展示同一快照，PR 描述明确列为契约差异。
- **结论**：不扩 scope；后续如要 chip 常驻，应由 API 在 RunDetail 暴露快照。

### 6.4 E2E fixture 直接写库是否脆弱？

- **位置**：`m10_06_run_detail_fixture.py:34`。
- **现象**：fixture 直接 insert `evolution_run_candidates`、`probe_reports`、`probe_clusters`、`evolution_rounds`、`evolution_run_events`。
- **问题**：列名/表结构变化会立刻让 E2E 失败，维护成本高于使用 prepare 管线。
- **预判**：但 prepare 需要 git/引擎/工作区，不能稳定在 E2E 里跑；直接写库能控制七步 DTO 的每个边界。
- **结论**：保留；失败会明确指向 schema 漂移，属于可接受的测试成本。

## §9 文件级代码分析

### `apps/web/src/pages/evolution/RunDetail.vue`

职责一句话：运行详情壳，负责取 run/step、路由 query、blocked banner 与日志 tab。变更形态：M，新增 2 行。

关键依赖：`useEvolutionRunStep` 把 `page/pageSize` 放进 query key，未到达节点 `enabled=false`，因此“不请求未到达 step”不是 UI 隐藏，而是数据层禁用。比喻：电梯按钮只有在楼层存在时才通电。

旧代码：

```ts
case "eval":
  return "评测（eval）阶段";
default:
  return "未知阶段";
```

新代码：

```ts
case "eval":
  return "评测（eval）阶段";
case "attribution":
  return "归因（attribution）阶段";
default:
  return "未知阶段";
```

为什么：契约早已允许 attribution，前端 switch 是唯一漏掉的消费点；补分支比在模板里做字符串判断更集中。

实现思路总结：保持后端事实优先，只补展示映射。

检视发现：无。`blockedStage ?? error.stage` 的优先级正确；banner 的 `nextRetryAt` 与 `retryAttempts` 都来自 run，不前端估算。
