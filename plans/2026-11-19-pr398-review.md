## §1 一页速览

一句话：把「生产 git 读取 GitHub 慢/超时」的修复收进一个**只服务 git 子进程**的本地 Xray/VLESS 代理；代理坏了不重启 API，进程内熔断回直连。

比喻：代理像一条专用货运通道，只有 git 的货车能上；通道堵了，调度员在门口挂「暂停使用」牌子，货车改走普通道路，而不是把整个厂区关掉重开。

| 交付块 | 内容 |
|---|---|
| 配置入口 | GitHub Environment Secret `XRAY_CONFIG`（完整 Xray JSON） |
| 运行时开关 | `HE_GIT_PROXY` 只写本地地址，UUID/公钥不进 API |
| 回退 | 部署探测失败 → unset；运行中连续 3 次代理层失败 → 直连，后台探测恢复 |
| 表面 | 内容读取、`ls-remote`、工作区 clone/push；其它出网不变 |
| UI | 无变化 |

## §2 架构导览

**配置进不来 API。** `config.py:134` 只新增 `git_proxy`、探测间隔与超时；`config.py:219` 只接受无凭据的 http 地址。部署侧 `xray-config.py:42` 在 runner 与服务器两侧校验 JSON、回环入站和 VLESS 出站；`deploy.yml:70` 的步骤只在隧道探测通过后才让后续注入写 `HE_GIT_PROXY`，否则在 `deploy.yml:267` 生成 `--unset`。

**代理只在 git 子进程。** `main.py:159` 创建控制器和 runner；`main.py:295/300/339` 分别注入 `SubprocessGitRemote`、`SubprocessGitContent`、`GitWorkspaceManager`。`proxy.py:101` 设置 `HTTPS_PROXY`/`HTTP_PROXY`，并用 `GIT_CONFIG_*` 把 GitHub SSH 远端重写为 HTTPS；`proxy.py:411` 在直连时先 `strip_proxy_environment`，避免继承环境里的旧代理。

**回退是进程内状态机。** `proxy.py:192` 的控制器以 `closed → open → half_open → closed` 迁移；`proxy.py:273` 决定当前请求是否走代理；`proxy.py:301` 的后台探测在 `open` 冷却后尝试恢复。`proxy.py:411` 对代理层失败做一次直连重试，`proxy.py:118` 只把明确的代理错误算作熔断信号，GitHub 慢仍归内容超时。

**部署不依赖服务器访问 GitHub。** `fetch-xray.sh` 在 runner 下载固定版本与 SHA256，`bootstrap-server.sh:106` 只安装已在共享目录里的 unit；`harness-proxy.service` 以 `deploy` 用户运行，`ProtectSystem=strict`，只读配置与二进制。

## §3 数据流走查

1. 用户在 `production` Environment 配 `XRAY_CONFIG`。
2. Deploy 在 runner 执行 `xray-config.py --extract`，得到 `http://127.0.0.1:10808`；失败则后续 `--unset`，发布直连。
3. runner 下载 Xray，rsync 到 `/opt/harness/shared/proxy/bin/`，SSH 以 stdin + base64 写 `config.json`（0600）。
4. `sudo systemctl restart harness-proxy`，等待 active，再通过代理 `curl https://api.github.com/zen`；失败则停服务并直连。
5. 探测通过 → `inject-config.py` 写 `HE_GIT_PROXY`；API 重启后 `main.py:159` 装配 runner。
6. 第一次 git 读取：`endpoint()` 返回代理 → 子进程带代理环境 → 内容解析或 `ls-remote` 成功则 `report_success`；代理层失败则 `report_failure` + 本次直连重试。
7. 连续 3 次代理层失败 → `open`，请求直连；后台探测成功后回到 `closed`，无需重启 API。

## §6 讨论点

### D1 代理失败没有独立错误原因

- **位置**：`apps/api/app/third_party_api/git/proxy.py:411`、`apps/api/app/third_party_api/git/content.py` 的 `repo_unreachable` 映射
- **现象**：代理层失败后 runner 直接重试；若直连也失败，调用方仍看到 `repo_unreachable` 或 `content_timeout`，没有 `proxy_unreachable`。
- **问题**：#394 设计希望失败原因区分「代理不可用」与「仓库不可达」，前端可提示「已尝试代理」。当前只有 `git.proxy.retry_direct` 日志，没有稳定 reason。
- **预判**：不影响回退本身，属于可观测性增强；需要改 `GitContentUnavailable`/`RepoInvalid` 的 reason 传递，适合在 #394 后续切片做。
- **结论**：

### D2 环境里的 `GIT_CONFIG_COUNT` 会被覆盖

- **位置**：`apps/api/app/third_party_api/git/proxy.py:101`
- **现象**：代理启用时直接写 `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_n`，若进程环境已设置同名变量，原配置丢失。
- **问题**：生产 systemd 环境当前没有这些变量，风险低；但测试/CI 或未来运维可能设置。
- **预判**：可接受；若后续需要叠加配置，可先读取现有计数再追加。
- **结论**：

### D3 每次发布都会重启代理

- **位置**：`.github/workflows/deploy.yml:70`
- **现象**：即使 `XRAY_CONFIG` 未变，代理步骤仍重启 `harness-proxy`。
- **问题**：重启瞬间正在走的 git 请求会失败并触发直连重试；不影响正确性，但有一次抖动。
- **预判**：可接受；后续可按配置哈希决定是否重启。
- **结论**：

### D4 校验拒绝所有非回环入站

- **位置**：`deploy/xray-config.py:42`
- **现象**：任何 inbound 的 `listen` 不是 `127.0.0.1`/`localhost`/`::1` 都拒绝，包括用户有意暴露的独立 metrics/api 入站。
- **问题**：这是有意的安全默认，避免本机代理变成公网开放代理；但会限制高级配置。
- **预判**：保持现状并在文档说明；需要额外入站时另开受控配置。
- **结论**：

### D5 `localhost` 入站的地址族

- **位置**：`deploy/xray-config.py:64`
- **现象**：`listen: localhost` 时生成 `http://localhost:<port>`，由 git 解析地址族；Xray 若只绑定单栈，可能解析到另一栈。
- **问题**：概率低；推荐显式 `127.0.0.1`。
- **预判**：文档已推荐 `127.0.0.1`，保持现状。
- **结论**：

## §9 文件级代码分析

### `apps/api/app/third_party_api/git/proxy.py`（A）

职责：提供「是否走代理」的进程内状态机，以及把代理环境/SSH 重写注入 git 子进程的 runner。第三方依赖只有标准库 `asyncio`/`ssl`，没有新增包。

变更核心：

- `GitProxyController`：`closed` 默认走代理；`report_failure` 累计到阈值或 `half_open` 失败时 `_open()`；`probe_once` 成功时从 `open` 进 `half_open`，第二次成功回 `closed`。探测用 HTTP CONNECT 到 `github.com:443`，5 秒上限，不拉正文。
- `ProxyAwareGitRunner.run`：代理可用时设置环境并执行；returncode 为 0 记成功；stderr 命中 `is_proxy_failure` 才记失败并直连重试一次；非代理错误不熔断。
- `apply_proxy_environment`：用 `GIT_CONFIG_COUNT` 做 `git@github.com:`/`ssh://git@github.com/` → HTTPS 重写，避免改 argv 影响既有命令断言。

检视发现：初版只校验被选中的入站，未阻止同一配置里另有一个 `0.0.0.0` 入站；已在本 PR 修复（`22ce1a2`）。其余见 D1/D2。

### `deploy/xray-config.py`（A）

职责：runner 侧 `--extract` 校验并输出代理地址；服务器侧原子写 `0600` 配置；`--remove` 清理。关键约束：JSON 对象、至少一个回环 mixed/http 入站、至少一个 vless 出站、所有入站回环。检视发现：初版未校验“所有”入站，已修复并补测试；`localhost` 地址族见 D5。

### `.github/workflows/deploy.yml`（M）

职责：新增代理准备步骤与注入回退。每一步失败都 `exit 0` 并 `::warning::`，保证发布继续直连；配置经 base64 + stdin 传输，不进命令行/日志。检视发现：每次发布重启代理（D3），以及 `sudo` 依赖 bootstrap 的 sudoers（已在文档与流程中说明）。

### `apps/api/app/main.py`（M）

职责：把 runner 注入三个 git 接缝，并在 lifespan 启动/停止探测。检视发现：`cast(Any, ...)` 绕过 runner 的 nominal 类型差异，运行时只依赖 `returncode/stdout/stderr` 三个字段；这是为兼容三个模块各自的 `GitProcessResult` 类型所做的取舍，已有单测覆盖行为。
