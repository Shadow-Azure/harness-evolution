## §1 一页速览

**一句话**：把 `insert_after` 的锚点从「文件里包含这段文字的**那一行**」改成「文件里**唯一出现的一整段文字**，插在这段文字**末行**之后」，并让 prompt、设计文档、validator 说的是同一句话——起因是生产 run 因为一条**只活在 validator 里、没写进 prompt** 的「锚必须单行」规则整轮失败。

**一个比喻**：旧实现像「拿一句话当书签，夹在含这句话的那一页的页脚下面」；新实现像「拿整段引用当书签，贴在引用所指段落的末尾」。而这次事故的根因，是门口保安（validator）额外要求「书签只能是一个词」，说明书（prompt / 派生 schema / 设计文档）却只写了「书签要在书里独一无二」——模型交了合法书签，被保安当场撕票，而 edit 只有一次机会。

## §2 架构导览

### 2.1 契约层：Pydantic 是唯一事实源，但只能表达「字段级」约束

`edits.py` 的 `EditOp` 用一个 `mode="after"` 的模型级校验器把「哪个 op 允许/禁止哪个字段」收在一处（`edits.py:157-176`）。这次改动只做减法：不再检查 target 里有没有换行。

```python
# 旧（main）
elif self.op in _ANCHORED_OPS:
    target = _require_non_blank(self.target, field="target", op=self.op)
    if self.op == "insert_after" and ("\n" in target or "\r" in target):
        raise ValueError("target must be a single-line substring")
# 新（HEAD）
elif self.op in _ANCHORED_OPS:
    _require_non_blank(self.target, field="target", op=self.op)
```

理解这段的关键是：**Pydantic 只校验「形状与字面量」，不校验「与文件内容的关系」**。「锚是否存在、是否唯一」永远是应用器的事（它要读文件），所以这次事故的本质不是「校验太严」，而是「一条**依赖文件内容**的规则被写成了**形态规则**，而且没写进 prompt」。

### 2.2 应用层：`_apply_one` 只做计数，`_insert_after_text` 只做定位

- `_apply_one`（`edits.py:507-542`）：`text.count(target)` 为 0 → `skipped_anchor_missing`（`526`），>1 → 抛 `EditPlanError`「anchor is ambiguous」（`528-536`），==1 → 调 `_insert_after_text`（`542`）。删掉的是旧实现 `_apply_one` 里的同一段单行拒绝（diff 的 `-` 侧），计数与多义逻辑原样保留。
- `_insert_after_text`（`edits.py:465-504`）是纯函数：输入文件全文 + 唯一出现的 target + content，输出新全文。它按 **target 的结尾形态**分支：

| target 结尾 | 插入点 | 插入行换行 | 代码 |
|---|---|---|---|
| `\r\n` | 该 `\r\n` 之后 | `\r\n` | `478-479` |
| `\r` 且下一个字符是 `\n`（停在 CRLF 中间） | 补完这个 `\r\n` 之后 | `\r\n` | `480-484` |
| 其他 bare `\r` | 该 `\r` 之后 | `\n` | `485-487` |
| `\n` | 该 `\n` 之后 | `\n` | `488-489` |
| 无结尾换行 | 匹配末字符所在行的**下一个行终止符**之后；无终止符则 EOF 并补 `\n` | 该终止符风格（`\r\n`/`\n`） | `490-501` |

### 2.3 让「绕过模型」依然安全的第二道门：`_coerce_edit`

`apply_edit_plan` 对每一条编辑先调 `_coerce_edit`（`edits.py:650`），后者**不管传进来的是不是 `EditOp` 实例，都 `model_dump()` 后重新 `model_validate`**（`edits.py:300-320`）。这是讨论点里「删除 `_apply_one` 守卫后 `model_construct` 是否还安全」的答案：安全——空 target 会在这次重校验里被 `_require_non_blank` 拒掉，到不了 `_insert_after_text`。代价是 `_apply_one` 里 `target is required` / `content is required` 两处（`:518-519`、`:538-541`）变成纯防御分支。

### 2.4 模型可见面：prompt 与设计文档

- `_edit_prompt()`（`patch_source.py:511-548`）产出 edit 会话的唯一 goal prompt，`build_bundle()` 在 `patch_source.py:411-417` 调用它；锚点契约就在 `537-547` 的三行里，改动是第二行的一句：
  ```
  「锚文本必须存在且唯一。」→「锚文本必须是文件内唯一出现的文本片段，可跨行；insert_after 把 content 插到该片段末行之后。」
  ```
- 07 §5.5.4 是这条契约的设计 home：json5 示例注释（`07:842`）与执行流 bullet（`07:849`）各改一处，且 bullet 里「insert_after 行边界」改成「insert_after 块末行之后」。

### 2.5 支撑性基础件（无改动，但决定字节保真）

`_load_target` 用 `newline=""` 读（`edits.py:436-437`）、`_atomic_write` 用 `newline=""` 写（`:578`），`_apply_on_scratch`（`patch_source.py:458-473`）用 `shutil.copyfile` 镜像（`494`）+ `_read_text` 的 `newline=""`（`497-500`）——整条链路不做换行翻译，所以 `\r\n` 能一路保到 `PatchBundle`。**这是 PR 描述里「插入行沿用锚行风格」能成立的前提**，也被这次 `_write` 改成 `write_bytes` 的测试基建改动呼应（`test_edit_plan_applier.py:101-104`）。

## §3 数据流走查

剧本：生产 run 第 3/10 轮，计划第 7 条是 4 行块锚点的 `insert_after`。

1. **prompt 生成**（`patch_source.py:411-417`）：`_edit_prompt()` 把「锚文本必须是文件内唯一出现的文本片段，可跨行；insert_after 把 content 插到该片段末行之后」交给 CLI。
2. **agent 写提交文件**：`.harness-evolution/edits.json5`（json5，注释/尾逗号容错）。生产那次 `submissionParsedBy=json5`，说明这一步成功。
3. **提交校验**（`claude_code.py` 侧 `submission.collect(prep, EditPlan.model_validate)`）：`EditPlan.model_validate` → 每个 `EditOp._validate_op_fields`（`edits.py:157-176`）。**旧实现**在这里抛 `edits.6: target must be a single-line substring`，整轮失败；**新实现**放行。
4. **镜像与逐条应用**（`patch_source.py:427` → `458-473`）：
   - `_mirror_plan_files` 用 `shutil.copyfile` 把 plan 涉及的每个文件复制到临时目录（`476-494`）；
   - `apply_edit_plan` 在 scratch 上跑（`edits.py:591-718`）：每条先 `_coerce_edit` 重校验（`650`）→ `_load_target` 做 scope/符号链接/UTF-8 校验并 `newline=""` 读全文（`368-451`）→ `_apply_one` 计数（`507-542`）→ `_insert_after_text` 定位（`465-504`）→ 内容真变了才 `_atomic_write`（`664-665`）。
5. **字节结果示例**（合成样例，与新增用例同形）：文件 `l1\nl2\nl3\nl4\nl5\nl6\n`，target `l2\nl3\nl4\nl5\n`，content `NEW` → 输出 `l1\nl2\nl3\nl4\nl5\nNEW\nl6\n`（`test_edit_plan_applier.py:390-411`）。块末行的 `\n` 之后插入，不产生空行。
6. **回到 bundle**：`_read_text`（`newline=""`）取回改动文件全文 → `_patch_from_content` 按 `\n` 切行（`503-508`）→ `PatchBundle{files, unified_diff, note=summary, intent=plan, report}`（`432-437`）。
7. **下游**：candidate 提交 → push → eval；`report` 逐条 status 落 run events，`git diff` 是唯一真值。

**这次走查暴露的关键事实**：第 4 步 `_insert_after_text` 的「无结尾换行」分支（`edits.py:495-501`）在**文件末行没有换行符**时，会把 target 之后、末行结尾之前的内容**整段丢掉**（`prefix = f"{text[:match_end]}{ending}"`，`suffix` 置空）。走查见讨论点 1。

## §6 讨论点

### 讨论点 1：末行没有换行符时，`insert_after` 会静默吞掉锚点之后的字符

**位置**：`apps/api/app/third_party_api/ai_agent/edits.py:495-501`（新 `_insert_after_text` 的「无行终止符」分支）

**现象**：文件末行没有结尾换行、target 落在末行中间（不触到 EOF）时，插入结果会丢掉 target 之后到 EOF 的内容。公开入口实测（`apply_edit_plan`，报告都是 `applied`）：

| 文件 | target | content | 旧实现输出 | 新实现输出 |
|---|---|---|---|---|
| `one\ntwo` | `tw` | `x` | `one\ntwo\nx\n` | `one\ntw\nx\n`（丢了 `o`） |
| `{\n  "version": "1.0"}` | `"version"` | `"build": 7` | `{\n  "version": "1.0"}\n"build": 7\n` | `{\n  "version"\n"build": 7\n`（丢了 `"1.0"}`） |
| `alpha\nbeta gamma` | `beta` | `NEW` | `alpha\nbeta gamma\nNEW\n` | `alpha\nbeta\nNEW\n`（丢了 ` gamma`） |
| `# title\n\nlast line` | `last` | `NEW` | `# title\n\nlast line\nNEW\n` | `# title\n\nlast\nNEW\n` |

根因是一行 `prefix, suffix = f"{text[:match_end]}{ending}", ""`：既然 `match_end` 之后没有任何 `\r`/`\n`，那么「这一行的结尾」就等于 EOF，`prefix` 应当是 `text`（整段保留）而不是 `text[:match_end]`。旧实现用 `splitlines(keepends=True)` + 整行拼接，天然保留了尾巴，所以这是**本 PR 引入的行为回归**，而不是既有限制。

**问题**：这是静默数据丢失——`report` 是 `applied`、`git diff` 会把删掉的字符如实呈现，但 plan 与模型都不知道自己写坏了文件；如果被删的是 `SKILL.md` 结尾的半个句子或 JSON 的收尾括号，候选 patch 会变成语法错误文件，而失败会以「评测 reject」而不是「应用器 bug」的形式出现，归因成本很高。仓库里不带末尾换行的文件并不罕见（外部工具生成的 JSON、`.gitignore`、部分 fixture）。

**预判**：必修（bug，建议阻断合并）。修法很小：该分支改成 `prefix, suffix = f"{text}{ending}", ""`；同时补一条「末行无换行 + target 在行中/行首」的用例（这正是现有单行字节矩阵漏掉的那一格）。顺带把 docstring `edits.py:468-472`「否则插入点是匹配末字符所在行的结尾」与实现对不齐的地方一起对齐。

**结论**：已决 2026-11-25：成立且已修复（`01d3bd8c`）。该分支改为整段保留 `prefix=f"{text}{ending}"`，并新增「末行无换行 + target 在行中/行首」的字节回归（`test_insert_after_single_line_targets_reproduce_exact_bytes` 扩到 9 格）。

### 讨论点 2：多行 target 可以绕过「唯一」契约，而且单行等价只在 LF/CRLF/纯 CR 文件成立

**位置**：`apps/api/app/third_party_api/ai_agent/edits.py:522`（`text.count(target)`）、`Agent Note:19`（「多行 target 不绕过它」）、`edits.py:490-501`（`find("\n")` 定位）

**现象**：

1. **自重叠多行块漏判多义**：`text.count` 数的是**不重叠**出现次数。文件 `L\nL\nL\n`、target `L\nL` 实际出现 2 次（下标 0 与 2），`count` 得 1，于是按「唯一」放行、插在第一个块之后；`ab\nab\nab` 同理。单行 target 时代这个洞就存在（文件 `aaa` + target `aa`：`count` 得 1，实际重叠出现 2 次），但那时多行 target 在 validator 就被拒，所以**多行契约把这条洞从「不可达」变成「可达」，而 Note 明确写了「多行 target 不绕过它」**。结果仍然确定（总是第一个），但「唯一」这个审计承诺不再成立。
2. **单行等价的前提被夸大**：用旧实现等价物对 602 组「旧实现不报错」的单行 target 做差分，**154 组输出不同**：
   - **120 组**是讨论点 1 的丢字符；
   - **14 组**来自混合 bare `\r` 与 `\n` 的文件：`a\rb\n` + target `a`，旧实现插在 `a\r` 之后（`a\rx\nb\n`），新实现一路找到后面的 `\n`、插到 `b\n` 之后（`a\rb\nx\n`）；`a\rb\r\nc\n` 同理；
   - **20 组**来自 `str.splitlines()` 与 `find("\n")` 的分隔符集合不同：`str.splitlines()` 还切 `\v`、`\f`、`\x1c`–`\x1e`、`\x85`、`\u2028`、`\u2029`，`a\vb\n` + target `a` 在旧实现里 `a\v` 自成一「行」、新实现把它和 `b` 当同一行。仓库 `11-bad-case-session-sync.md:92` 恰好记过同类坑（「按 `\n` 分帧而不是 `splitlines`」），说明这是团队已知的语义分界。

**问题**：契约文字（prompt / 07 / Note）说的是「唯一出现的文本片段」，实现说的是「不重叠出现次数为 1」；两者在多行自重叠块上不等价。另外「单行输出逐字节不变」被写进了 Note 与实现计划，作为回归安全网的核心承诺，而它只在「文件只用 LF、CRLF 或纯 CR 一种换行风格」时成立。

**预判**：唯一性问题建议定为**正确性**（中低）：修法是把计数改成逐位推进的 `find` 循环（`count` 换成 `while (i := text.find(target, i)) != -1: i += 1`），或在 Note/07 里把「唯一」显式降级为「不重叠唯一」并说明理由——二选一，不要文字说一套代码做一套。混合换行与 `splitlines` 分隔符差异建议如实标注为已知边界（低，无实害：仓库内文本文件基本是 LF/CRLF），但 Note 与实现计划里的「逐字节一致」必须加上限定语。

**结论**：已决 2026-11-25：按 issue 契约保留 `text.count` 的不重叠计数，并在 Agent Note 与 07 §5.5.4 显式标注「不重叠唯一」；「逐字节一致」限定为 `\n` / `\r\n` / 纯 bare `\r` 文件，混合换行与 `splitlines` 的 Unicode 分隔符记为已知边界（无实害，不另开 issue）。

**变更代码块 1：validator 删掉单行拒绝**（`edits.py:157-176`）

这在做什么：把「锚不能跨行」从模型层移除；`append` 禁 target、`delete` 禁 content、content 非空等约束全部保留。为什么这么写：这条规则与 prompt/07 冲突，且模型无法从派生 schema 里看到它——留在这里只会继续制造「合法计划被拒」。**实现思路**：契约只保留「形状」类约束；「与文件内容的唯一性」交给应用器，这是本仓库一贯的分工（`_ANCHORED_OPS` 的 docstring 也是这么写的，`edits.py:68-69`）。

**变更代码块 2：`_insert_after_text` 重写**（`edits.py:465-504`）

```python

# 新（整段定位；节选无换行结尾分支）

...
newline = text.find("\n", match_end)
if newline != -1:
    ending = "\r\n" if newline > 0 and text[newline - 1] == "\r" else "\n"
    prefix, suffix = text[: newline + 1], text[newline + 1 :]
```

这在做什么：先按整段找到唯一匹配的末尾（`match_end`），再根据 target 自己是否带换行决定插入点；不带换行时，向后找「这一行的终止符」，插在终止符之后。为什么这么写：旧实现「第一个包含 target 的行」在多行 target 下无法定义；用 `index` + 五个结尾分支能把「块末行之后」写成显式规则，也顺手兼容了 CRLF。**实现思路**：把「插入点」抽象成 `(prefix, suffix, ending)` 三元组，最后一段 `f"{prefix}{body}{suffix}"` 统一拼装——比旧实现「改列表元素再 insert」更容易验证字节不变。

这是本文件里唯一有实质风险的重写，风险点就是讨论点 1 的 `text[:match_end]`、讨论点 2 的换行语义、以及 `481-487` 的零覆盖。
