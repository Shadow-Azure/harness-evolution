## §1 一页速览

**一句话**：把 Linux 归因的默认执行从“必须先启动 bubblewrap 命名空间”改成“默认只通过两个受限 MCP 工具读本条证据、写本条报告；bubblewrap 变成显式开关”，让 #544 那台没有 bwrap 的生产机也能把排队批次跑完。

**比喻**：旧路径像把 Claude 关进一间只放本条材料的房间，再把门窗锁死；新默认路径像在墙上开两个窗口——一个窗口按页递出五份冻结输入和绑定 Skill，另一个窗口只收结构化字段、由平台自己的脚本盖章。房间其余部分不打开，但也不再需要给 Claude 一间房。

## §2 架构导览

### 2.1 开关与预检链路

开关只有一个：`Settings.attribution_bwrap_enabled`（`config.py:195`，默认 `False`，env 前缀 `HE_`）。`ClaudeCodeProvider` 在构造时缓存它（`claude_code.py:162`），于是 `skill_preflight_error()` 只在开关为真时才调用 `sandbox_preflight_error()`（`claude_code.py:180-181`），再在 `run_skill` 时把同一个值传给 `claude_skill.run`（`claude_code.py:194`）。

结果在启动路径上分叉：`main.py:374-375` 用 `attribution_error is None` 计算 `attribution_enabled`；该布尔值同时控制默认包（`:382`）、预览能力（`:392`）、本地上报（`:402`）和绑定消费者是否启动（`:644-645`）。默认模式在 Linux 上不再因为缺 bwrap 变成不可用，而是照常领取。

发布侧是同一套语义：`preflight.py:18-27` 先把 `provider` 与 `bwrap_enabled` 拼进状态行，再按 `reason` 返回 0/1；`release.sh:142-143` 仍在迁移与切换 `current` 前调用它，失败时不切版本。

### 2.2 执行分支

`claude_skill.run`（`claude_skill.py:253-300`）只加了一个分支：

- Linux 且开关为假 → `executionMode="case-tools"`；`prefix=[]`；`cwd=home`；CLI 选项来自 `_case_tool_options(directory)`。
- 其余（显式启用 bwrap 的 Linux、macOS、其他平台）→ `executionMode` 为 `bubblewrap` 或 `seatbelt`；`prefix=_sandbox(...)`；`cwd=directory`；选项仍是 `bypassPermissions` + `--allow-dangerously-skip-permissions`。

这样改动面很小：旧沙箱路径的 argv 与工作目录原样保留，只有默认 Linux 分支换了选项和 cwd。`executionMode` 随后进入 `details`，最终写进 `attribute_log.json` 的 `execution` 字段。

### 2.3 两个 MCP 工具

`attribution_case_tools.py` 是一个独立的 stdio MCP server，只做两件事：

- `read_evidence`（`:65-82`）：不传 `path` 时列出可读文件；传了就按 16 KiB 读一页。文件清单是硬编码的五份输入（`:16-22`）加 `skill/` 下除 `make_probe_report.py` 外的普通文件（`:53-63`）。符号链接在构造时与每次读取时都被拒绝；分页用增量 UTF-8 解码器，跨页的多字节字符不会被截断。
- `write_probe_report`（`:84-124`）：只接收 `ReportFields`（`:26-41`，`extra="forbid"`、`strict`）。case ID、输入路径、输出路径、解释器都由平台决定；模型字段变成 `--flag=value` 追加到参数列表，不经过 shell。writer 在 `cwd=work`、`env={"PATH": os.defpath}`、`python -I` 下运行，超时 20s；失败时把 stderr 截断到 512 字节返回。

`ReportFields` 不接受 `bad_case_id`、`output`、`input_badcase`、`command` 等字段，`test_case_tools.py:92` 专门覆盖了这一点。

### 2.4 平台写入与报告核验

写入链路没有新代码，但默认模式把它变成了主路径：

1. `_stage_attempt`（`local_attribution.py:468-489`）把 Skill 文件写进 `.claude/skills/<name>/`；将冻结包里的 `make_probe_report.py`（平台 writer）移到 `.platform/`；再把 `writer_entrypoint.py` 的 shim 复制到 Skill 目录；最后写入五份输入。
2. 平台在冻结包时强制用 `writer_path` 覆盖同名文件（`attribution_skill_packages.py:399-404`），上传包不能替换 writer。
3. shim（`writer_entrypoint.py:8-33`）用 `sys.executable -I` 调 `.platform/make_probe_report.py`，成功后写 `.platform/receipt.json`（路径 + SHA-256）。
4. `_read_emission`（`local_attribution.py:491-512`）校验回执、路径、大小与 hash；`canonical_report`（`:654`）再用原始输入和冻结 skill 的 writer 重新生成报告，入库前完成二次校验。

所以“模型只填分析字段”不是约定，而是冻结包、shim、回执与二次生成四层共同保证的。

### 2.5 CLI 边界

默认模式的选项由 `_case_tool_options`（`claude_skill.py:167-210`）生成：

- `--restricted`：把文件工具限制在工作目录内；`cwd` 被设为 `home`，而证据在它的上级 `work`，所以即便未来误开文件工具，默认也读不到证据目录。
- `--disable-slash-commands`：Skill 不再以斜杠命令加载；完整 `SKILL.md` 通过 `--append-system-prompt-file` 作为文本注入。
- `--strict-mcp-config` + `--mcp-config`：只加载平台生成的 `attribution` server；server 命令是当前 API 解释器 + `-I` + `attribution_case_tools.py` + 本条目录。
- `--tools ""`：关闭全部内置工具；`--allowed-tools` 只放行两个 MCP 工具；`--permission-mode dontAsk` 让允许清单内的调用不弹问。
- `--bare` 保留：不读个人 hooks、插件、CLAUDE.md 与 keychain；凭据仍只来自 `_environment` 投影的变量。

`run` 的旧注释说“CLI 在逐次文件系统沙箱中运行”，现在改成“case tools 或文件系统沙箱”（`claude_skill.py:20-24`），与代码一致。

### 2.6 失败语义

- 预检失败：`attribution_enabled=False`，绑定消费者不启动，`runtimeEnabled=false`，`canRecompute=false`；已有绑定与历史报告保留。这是 #544 的原有语义，没变。
- 开关为假：不再有“缺 bwrap 就不 claim”的路径；如果 CLI 或 MCP 工具在 claim 后失败，按既有重试规则消耗尝试次数。见 §6 讨论点 1。
- writer 失败：工具返回 `ValueError("platform writer rejected the report: ...")`；模型可以重试。最终 `_read_emission` / `canonical_report` 仍会拒绝没有回执或被篡改的报告。
- 超时：单 case 超时仍是 `HE_ATTRIBUTION_TIMEOUT_SECONDS`（默认 600s，`config.py`）；writer 的 20s 是工具级预算。

## §3 数据流走查

1. **启动**：`Settings()` 读 `.env`（`HE_ATTRIBUTION_BWRAP_ENABLED` 默认 false）→ `build_agent_provider` 选公共 Provider → `skill_preflight_error()`。Linux 默认模式直接返回 `None`，于是 `attribution_enabled=True`，`main.py:610-613` 打一条 `attribution.preflight ... bwrap_enabled=False ready=True`，`:644` 启动绑定消费者。
2. **领取**：绑定 worker 找到 `attribution_due` 到期的 generation，按批次 claim；claim 前没有额外的 bwrap 检查（默认模式）。
3. **准备输入**：`_case_input`（`local_attribution.py:385-428`）把 Session 证据与**一条** Badcase 行组装成 `input_badcase.json`，连同 `session_tree.json`、`traces.json`、`trace_coverage.json`、`attribute_source.md` 写入归档并冻结。
4. **Stage**：`_stage_attempt` 写 Skill 文件、`.platform` 平台 writer、shim、五份输入；`.cac/skills` 只作为兼容别名。
5. **执行**：`claude_skill.run` 在 Linux 默认分支建 `home`、`tmp`，写 `home/attribution-instructions.md`（`SKILL.md` 原文 + 平台执行说明），生成 MCP 配置，然后以 `--restricted`、`--tools ""`、两个允许工具、`dontAsk` 启动 Claude。
6. **读证据**：模型先 `read_evidence` 列文件，再按页读 `input_badcase.json` 与需要的 `skill/` 资料；跨页按 `next_offset` 续读。
7. **写报告**：模型把分析字段交给 `write_probe_report`；工具用本条 `bad_case_id` 与固定输出路径调 shim；shim 调 `.platform/make_probe_report.py`，生成 `probe_report.json` 与 `.platform/receipt.json`。
8. **核验入库**：CLI 退出后，`_read_emission` 校验回执与 hash，`canonical_report` 用原始输入重新生成报告，`log` 写 `status=report_validated` 与 `execution.executionMode=case-tools`，报告入库；目标页与总览读同一套状态。
9. **显式沙箱**：把开关设为 true 并重启后，启动预检会跑 `bwrap --unshare-all ...`；失败则 `attribution_enabled=False`，不 claim，due 与重试次数保留；成功则回到旧命名空间路径，`executionMode=bubblewrap`。

## §6 讨论点

### 讨论点 1：默认模式依赖的 `--restricted` 能力没有进入预检

- **位置**：`apps/api/app/third_party_api/ai_agent/claude_skill.py:275-279`（默认分支）、`claude_code.py:180-181`、`preflight.py:20-27`
- **现象**：开关为 false 时，运行路径直接拼 `--restricted`；预检只判断 bwrap，不检查 Claude CLI 是否存在、版本是否支持该 flag。生产 Deploy 日志显示 2.1.325 已安装，且该版本二进制确实含 `--restricted`；但本机 2.1.179 对同一 flag 报 `unknown option`。Deploy 支持用 `vars.CLAUDE_CODE_VERSION` 固定旧版本，或在未配置 `CLAUDE_CODE_*` secrets 时跳过安装（`deploy.yml` 中 Claude 安装步骤会直接跳过）。
- **问题**：固定旧版本或跳过安装的部署，预检仍会输出 `ready=True`；第一批 claim 后每个 case 以 CLI 退出码失败，3 次重试后 `attribution_due` 被清空，回到 #544 的“绑定被消耗”形态——这次会留下 error 日志，但用户仍要重新绑定。触发条件是“旧 CLI + 默认模式”，不是所有部署。
- **预判**：在 `preflight.py` 增加一次廉价的能力探针（`claude --version` + 最小版本常量，或直接试跑 `--restricted --version`），失败返回新的 `ATTRIBUTION_CLI_UNSUPPORTED`，发布前拦下；同时在部署文档写明最低 Claude Code 版本。成本很小，能把“默认开启”的风险收回发布门禁。
- **结论**：

### 讨论点 2：默认模式把边界从内核沙箱降到了工具面

- **位置**：`claude_skill.py:275-279`、`attribution_case_tools.py:112-121`
- **现象**：默认模式只在 CLI 参数层限制模型：禁内置工具，只允许两个 MCP 工具；MCP server 与平台 writer 仍以 API 用户身份在宿主机运行，writer 只继承 `PATH`、以 `-I` 启动。旧 bwrap 模式把整个 CLI（包括它启动的 writer）关进命名空间。
- **问题**：模型能读的五份证据与上传 Skill 都来自不可信输入；当前 writer 由平台强制覆盖（`attribution_skill_packages.py:399-404`），模型改不了它的行为，但 writer/MCP server 自身或其依赖一旦有解析漏洞，影响面是 API 主机而不是沙箱。另一个差异是网络：默认模式没有 bwrap 的 `--unshare-all`，writer 与 CLI 的隔离只靠平台代码自律。
- **预判**：按当前代码，模型能做的只有“读五个文件 + 提交分析字段”，writer 只读 `input_badcase.json` 并写固定路径，短期无实害；但这是安全边界的实质变化，建议在 owning Note 中明确记录“默认模式不提供 OS 隔离”的取舍，并让需要强隔离的部署显式开回 bwrap。属于设计取舍，不应在未决前继续加宽默认工具面。
- **结论**：

### 讨论点 3：证据读取从“可检索文件”退化为 16 KiB 顺序分页

- **位置**：`attribution_case_tools.py:65-82`
- **现象**：`read_evidence` 只有“列文件/读一页”两种形态，页大小固定 16 KiB，没有 grep、摘要或按 JSON path 取子节点。大 `traces.json`、`attribute_source.md` 需要模型多轮续读。
- **问题**：生产批次的 trace 可能达到 MB 级；顺序读会消耗更多模型轮次与 token，极端情况下 600s 单 case 超时。旧 bwrap 模式有文件工具，模型可以选择性读片段。PR 描述用 22 条合成 Badcase 验证过流程，但没有给出每 case 的工具调用数/耗时对照。
- **预判**：先在生产 22 条上量一次每 case 的 tool call 数、token 与耗时；如果偏大，再加一个只读的 `search_evidence` 或按 JSON 路径读取的工具，或者把页大小做成配置。当前无实害证据，属于需要用真实数据拍板的取舍。
- **结论**：

### 讨论点 4：存量 bwrap 部署升级后会默认降级

- **位置**：`.env.example:308`、`docs/deployment.md:67`
- **现象**：开关默认 false，且没有“检测到主机已有 bwrap 就自动沿用”的逻辑；旧部署升级后，除非显式在 `/opt/harness/shared/.env` 写入 `HE_ATTRIBUTION_BWRAP_ENABLED=true` 并重启，否则执行方式从 `bubblewrap` 变成 `case-tools`。
- **问题**：对已经依赖命名空间隔离的部署，这是一次静默的行为变化；启动日志会打 `bwrap_enabled=False`，但部署文档没有一句“升级后要保留原沙箱需做什么”。运维可能以为隔离还在。
- **预判**：在部署文档或 Playbook 的升级步骤加一句显式迁移说明（设 true、重启、用 `journalctl` 看 `bwrap_enabled=True`），不需要改代码。无当前实害，属于交付说明缺口。
- **结论**：

### 讨论点 5：新增 `mcp` 运行时依赖的足迹

- **位置**：`apps/api/pyproject.toml:19`
- **现象**：`mcp>=2.2,<3` 本次实际安装 2.3.0，并带入 `mcp-types`、`httpx2`、`jsonschema`、`opentelemetry-api` 等传递依赖；服务只用到 stdio server、工具 schema 和客户端测试。
- **问题**：API 运行时多一组依赖与安全面；这项能力本质上是一个 136 行的 JSON-RPC over stdio 服务。官方 SDK 换来协议兼容与 schema 生成，但长期维护/漏洞响应成本也进入 API 镜像。
- **预判**：如果团队把 MCP 作为归因之后的长期协议，用官方 SDK 合理；如果只此一处使用，可评估用 stdlib 实现最小 JSON-RPC（initialize / tools/list / tools/call）来减依赖。无功能缺陷，属于依赖取舍。
- **结论**：

## §9 文件级代码分析

### `apps/api/app/third_party_api/ai_agent/attribution_case_tools.py`（A）

职责：Linux 默认模式下，把模型能触达的面收窄成“本条 case 的证据读取 + 平台 writer”；不启动 shell，不暴露工作目录。

**依赖**：`mcp`（官方 Model Context Protocol Python SDK，运行时从 PyPI 安装，不是构建期打包）提供 stdio server、工具 schema 与客户端测试；`pydantic` 已存在于 API 依赖。这个文件是 SDK 的第一方使用方，不是厂商代码 vendoring。

**关键变更块**：

```python
# 可读文件 = 五份固定输入 + 绑定 Skill 内除 writer 外的普通文件
self.files = {name: self.work / name for name in _EVIDENCE}
self.files.update(
    (f"skill/{path.relative_to(self.skill)}", path)
    for path in self.skill.rglob("*")
    if path.name != "make_probe_report.py" and not path.is_symlink() and path.is_file()
)
self.files = {
    name: path
    for name, path in self.files.items()
    if path.is_file() and path.resolve() == path
}
```

这里做的是“先枚举、再按真实路径过滤”：枚举阶段排除符号链接与 writer，过滤阶段再用 `resolve() == path` 防止父目录被替换。读文件时还会再校验一次（`:70`），所以 stage 之后被换成链接也会被拒绝。

```python
def write_probe_report(self, report: ReportFields) -> str:
    input_path = self.files["input_badcase.json"]
    writer = self.skill / "make_probe_report.py"
    output = self.work / "probe_report.json"
    ...
    (case,) = json.loads(input_path.read_bytes())["bad_cases"]
    args = [sys.executable, "-I", str(writer), "--input-badcase", str(input_path),
            f"--bad-case-id={case['bad_case_id']}", "--output", str(output)]
    for name, value in report.model_dump(exclude_none=True).items():
        flag = name if name in {"probe_type", "probe_object"} else name.replace("_", "-")
        args.append(f"--{flag}={value}")
```

模型只提供分析字段；case ID 从本条输入取，输出路径由平台写死，`probe_object`/`probe_type` 保留 writer 的 snake_case 参数名，其余用 kebab-case。`-I` + `env={"PATH": os.defpath}` 把 Python 的隔离模式与最小环境一起用上，避免模型通过环境变量影响 writer。

**实现思路**：白名单枚举 + 双层符号链接检查 + 固定参数拼装 + 最小环境子进程。

**检视发现**：

- `(case,) = ...["bad_cases"]` 假设输入永远只有一条 Badcase。当前 `_case_input`（`local_attribution.py:385-428`）确实只放一条，但这是隐式契约；若未来输入改成“整段 Session 的多条 Badcase”，这里会直接解包失败。建议在注释里写明这个前提，或让工具显式接收 `bad_case_id` 并 `next(...)` 选行。
- writer 超时 20s 是硬编码；对常规报告足够，但对超大输入没有留余量。属可接受的小风险。
- `read_evidence` 没有检索工具（见 §6 讨论点 3），这是默认模式与旧沙箱模式的主要能力差。
