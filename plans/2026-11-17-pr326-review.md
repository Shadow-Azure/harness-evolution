## §1 一页速览

一句话：把“bad case 行是否存在”和“它的 Session 轨迹是否就绪”拆成两件事，前者决定 404，后者决定 409/503 与状态面板。

比喻：上报的 bad case 像快递面单，Session 轨迹像包裹。旧实现看不到包裹就说“没有这个订单”；新实现保留面单，并告诉你是“运输中”“运输失败”还是“上游根本没有发货”。

## §2 架构导览

### 2.1 一个派生映射，两种消费面

`session_status.py:44-61` 是唯一的状态映射入口：

```python
trace = _derive_trace_status(sync_state, session_ready=session_ready)
if source_available or trace.status is READY:
    return trace
return replace(trace, retryable=False)
```

`_derive_trace_status` 先看 Session 是否存在（`:70`），再看 `bad_case_root_sync.status`（`:89-125`）。确定性失败与“synced 但 Session 丢了”都落到 `unavailable`。读服务只负责取事实，不重复拼状态。

### 2.2 详情：先存在性，后就绪度

`ProblemService.get_case`（`service.py:80-113`）先 `case_row`；只有 case 行为空才 404（`:93-98`）。随后 `case_snapshot` 为空时读取 root 状态并抛 409/503。这解决了旧实现把 `_family(session)` 的 `None` 和 case 的 `None` 混在一起的问题。

### 2.3 列表：按页批量，不做 N+1

`OverviewRepository.page_cases`（`overview.py:362-445`）在同一 DB session 内：

1. 取当前页 case 行；
2. 一次 `bad_case_root_sync ... in_(roots)`；
3. 一次 `session_families ... in_(roots)`。

随后 `OverviewService._item`（`service.py:112-144`）把三份事实交给同一个映射函数。页面大小 8，查询次数与页大小无关。

### 2.4 调度：失败也分“值不值得再试”

`bad_case_sync.py:30-40` 定义确定性错误集合；`:141-169` 把 `failed` 候选条件加上 `last_error not in (...)`。`reset_deterministic_failures`（`:293-326`）只在启动且存在可用 source 时把这些行复位为 `pending`，清空首次 claim 快照，允许重新选择 source。

### 2.5 前端：错误码是入口，details 是内容

`errors/Index.vue:201-211` 只认两个 code；`routeFatalError` 在 `:230` 提前返回，避免把 503 落到通用“读取失败”。`traceStatus.ts` 防御式解析 details，面板（`TraceStatusPanel.vue:70-130`）只消费解析后的类型。

## §3 数据流走查

主线：总览打开 → 列表补状态 → 点击“查看” → 详情 503 → 面板。

1. 用户打开 `/workspaces/ws-default/overview`；`OverviewService.list_cases`（`service.py:248-279`）先算 total，再取一页行。
2. `page_cases` 批量取 root-sync 与 Session 存在性（`overview.py:398-429`），把 `sync_state/session_present` 塞进 `BadCasePageRow`。
3. `_item`（`service.py:112-144`）输出 `syncStatus/sessionReady/lastError/retryable/nextRetryAt`。
4. `BadCaseTable.vue:234-260`：`traceReady` 为真才渲染 ID 深链；否则 ID 是普通文本，旁边是 `查看` 的 RouterLink。
5. 进入 `/sessions/<root>/errors?case=...&tab=desc`；`ProblemService.get_case` 先读 case 行（存在），再发现 `case_snapshot` 为空（`service.py:100-113`）。
6. 读取 `bad_case_root_sync` 与 source 可用性，映射为 `unavailable`，抛 `503 BAD_CASE_SESSION_UNAVAILABLE`，details 带 `lastError/retryable/lastAttemptAt`（`session_status.py:128-164`）。
7. `errors/Index.vue:201-211` 解析 details，模板 `:460-472` 渲染 `TraceStatusPanel`，不再渲染 404 的 `ErrorState`。
8. 用户点“查看同步状态”，`openSyncStatus` 派发 `hev:open-sync-status`；`TopNav.vue` 监听并固定同步弹层。点“刷新状态”会同时重取 detail、Session 列表、概览和树，轨迹补齐后自动回到正常错误详情。

## §6 讨论点

### 6.1 启动复位是“每次重启一次机会”，不是“配置变化监听”

- **位置**：`apps/api/app/db/crud/bad_case_sync.py:293-326`、`service/acquisition/bad_case_sync_coordinator.py:109-121`
- **现象**：确定性失败退出调度候选；每次进程启动且存在可用 source 时，这些行被复位为 pending，再走一次同步。
- **问题**：如果全局查询已配置但仍然不可用，每次部署/重启会多一轮失败与一条新日志；没有真正监听配置变化。
- **预判**：这是无迁移方案下最小可行的“重新触发入口”，代价是一次有界重试；若未来配置热更新，应改为配置变更事件触发。
- **结论**：待维护者拍板。

### 6.2 `failed` 与 `unavailable` 共用 503 `BAD_CASE_SESSION_UNAVAILABLE`

- **位置**：`apps/api/app/service/bad_cases/session_status.py:149-164`
- **现象**：transient failed 与确定性 unavailable 都返回 503，前端靠 `syncStatus` 区分。
- **问题**：如果第三方调用方只读 `code`，会把“会自愈的失败”和“配置问题”当成同一类。
- **预判**：契约只增加两个 code 是刻意控制错误码表面；details 已给稳定区分，前端不需要新 code。若外部集成增多，可再拆 `BAD_CASE_SESSION_SYNC_FAILED`。
- **结论**：待维护者拍板。

### 6.3 生产状态面板是全宽，原型保留左侧 case 列表

- **位置**：`apps/web/src/pages/errors/Index.vue:455-472`、`TraceStatusPanel.vue`
- **现象**：无 Session 时页面没有可渲染的 Session 侧栏，因此面板占满内容区；原型里该 case 仍有 Session 壳，所以保留侧栏。
- **问题**：这是原型与生产唯一明显的信息架构差异，评审需要确认是否接受“无 Session 就不假装有侧栏”。
- **预判**：接受。强行渲染空侧栏只会制造第二个错误态；面板已保留返回总览、同步入口和 case 身份。
- **结论**：待维护者拍板。

### 6.4 m8-04 E2E 的夹具从假 Session 改为真实 Session

- **位置**：`tests/e2e/m8-04-overview.test.mjs:299`、`:589`
- **现象**：m8-04 原来用 `m8-04-session-alpha/beta` 这类不存在的 Session 造 case；新列表会把这些行判为 pending，ID 不再是深链，原有“case deep link”断言超时。
- **问题**：这是新行为对既有测试的合理冲击，但也说明“无 Session 的 case 不再是深链”会影响所有依赖 ID 链接的脚本。
- **预判**：把 m8-04 改用 fixture 中真实存在的 Session，保留它验证 ready 行深链的原意；m12-07 专门验证未就绪行的“查看”行为。结论已按此修复（2026-11-17）。
- **结论**：已决。

## §9 文件级代码分析

### 9.1 `apps/api/app/service/bad_cases/session_status.py`（A）

职责：把持久化 sync state 与 Session 存在性翻译成公开五态；不碰 IO。

关键依赖：`BadCaseRootSyncRow` 是 db 边界 DTO，`AppError` 是统一错误壳；本文件不依赖 FastAPI。

变更代码块：

```python
trace = _derive_trace_status(sync_state, session_ready=session_ready)
if source_available or trace.status is READY:
    return trace
return replace(trace, retryable=False)
```

这段把“状态是什么”和“能否自动恢复”分开：`_derive` 只回答前者，source 探针只在后者上做减法。因此 pending 在没有任何 source 时也会诚实显示“不会自动重试”。

实现思路：先判 Session（ready 优先），再按 sync status 分支，最后统一覆盖 retryable；`trace_status_details` 与 `raise_trace_not_ready` 把同一份 TraceStatus 转成 HTTP details。

检视发现：无阻塞问题。`trace.status is READY` 用身份比较 StrEnum 成员，安全。

### 9.2 `apps/api/app/service/problems/service.py`（M）

旧行为：`case_snapshot` 一次返回 None 就直接 404。

新行为：`get_case`（`:80-125`）先 `case_row`，只有行缺失才 404；snapshot 为空时读取 sync state、source 可用性并抛 409/503。

实现思路：把“行存在”与“投影可读”拆成两个查询，代价是 ready 路径多一次 case 读；换来 404 不再被复用。`source_available` 作为可选注入，保持现有单测与旧调用方兼容。

检视发现：`merged.items` 为空时改为 500 INTERNAL；这是外部行字段损坏的防御分支，行为从“伪装成 404”改为“明确服务端异常”，可接受。

### 9.3 `apps/api/app/db/crud/bad_case_sync.py`（M）

新增：确定性错误集合、失败候选排除、启动复位。

```python
and_(
    bad_case_root_sync.c.status == _FAILED,
    or_(next_retry_at IS NULL, next_retry_at <= now),
    or_(last_error IS NULL, last_error NOT IN (...)),
)
```

`last_error IS NULL` 分支避免 SQL 三值逻辑把无错误码的 failed 行误排除。

检视发现：复位只清 `source_snapshot` 而不改 `synced_at`（该字段在 failed 行本来为空），无遗留状态；`agent_count` 保留，便于观察上次部分写入量。

### 9.4 `apps/api/app/db/crud/overview.py`（M）

`page_cases` 从“一次查 case + 一次查归因”变成“case + sync state + Session 存在性 + 归因”。三份查询都在同一 session 内，减少快照漂移。

检视发现：roots 用 `dict.fromkeys` 去重，保持页内顺序；`session_families` 查询没有 workspace 条件，但 roots 来自本空间已过滤的 case，Session id 全局唯一，不存在跨空间泄漏。

### 9.5 `apps/api/app/service/overview/service.py`（M）

`_item` 接收 `source_available`，`list_cases` 每页只解析一次 source 探针。

检视发现：source 探针在空的 page 上也会执行；当前实现先取 rows 再探针，若想省一次查询可在 `rows` 为空时跳过。页面大小 8、探针是一次索引查询，无实害。

### 9.6 `apps/web/src/pages/errors/traceStatus.ts`（A）

职责：防御式解析 `ApiError.details`，只接受五个合法 `syncStatus`；未知形状返回 null，页面回退原有错误态。

检视发现：字段缺失时给空串/null，面板用空值兜底；不会把任意 409 误认成轨迹错误。

### 9.7 `apps/web/src/pages/errors/Index.vue`（M）

旧行为：任意 404 一律“问题不存在或已删除”；任意 409 一律“问题不属于当前 Session”。

新行为：只有 `BAD_CASE_NOT_FOUND` 走 404 文案；两个轨迹 code 先解析 details，优先渲染面板；ownership mismatch 仍单独处理。

检视发现：`traceStatus` 优先于 `routeFatalError`，因此 detail 503 时不会先闪 404；刷新成功后 error 清空，页面自然回到正常详情。

### 9.8 `apps/web/src/components/TraceStatusPanel.vue`（A）

职责：纯展示轨迹状态、`lastError`、重试性、上次尝试、同步入口、复制 ID。

检视发现：复制使用可选链 `navigator.clipboard?.writeText`；无剪贴板时按钮不会报错但也不会提示失败。当前内部工具可接受，若需要可补 fallback。

### 9.9 `apps/web/src/pages/overview/components/BadCaseTable.vue`（M）

新列 `轨迹`；`traceReady` 为真才渲染 ID 链接，否则 ID 文本 + `查看` RouterLink。

检视发现：`min-width` 从 760 提到 860，列数增加后水平滚动仍可用；未就绪行的 `查看` 与 ID 文本同格，不会误触全行跳转。

### 9.10 测试与原型

- `test_trace_status.py`：五种状态、404、ownership、列表字段、调度排除与复位、无 source 时 retryable=false。
- `TraceStatusPanel.test.ts` / `Index.test.ts` / `BadCaseTable.test.ts`：面板文案、409/503 页面分支、轨迹列与“查看”。
- `m12-07-trace-state.test.mjs`：真实浏览器走完 ingest → overview → 查看 → 状态面板，并断言 404 文案缺席。
- 原型：新增 `轨迹` 列、`TraceStatusPanel` 同构信息架构、无轨迹 case 不生成归因占位。

检视发现：E2E 对无 Session 路由产生的 404 网络日志做了显式白名单，并注释了原因；这不是忽略代码错误，而是承认“会话资源不存在”是该场景的预期响应。
