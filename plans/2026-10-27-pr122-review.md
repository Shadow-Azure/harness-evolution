## §2 架构导览

### 2.1 数据库是状态的硬边界

五张表按依赖顺序建立：run → cluster/link → round → final。`progress_unit` 在 `evolution_runs` 上是唯一游标，不新增“当前 step”派生列，避免同一状态两个 home（`0006_evolution_state.py:78`, `models/evolution.py:81`）。

数据库层还固定了两类历史事实：`probe_clusters.seq` 是创建顺序，`rank` 是后续严重度排名；二者分离，重排不改变插入顺序（`models/evolution.py:118,128`）。`evolution_finals.run_id` 同时是 PK，天然保证一个 run 只有一条终评（`models/evolution.py:218-232`）。

### 2.2 repository 是唯一写入闸机

`advance_unit()` 用 `WHERE id=? AND progress_unit=expected` 做 compare-and-update；rowcount 不为 1 后重新读取，区分“run 不存在”和“游标已变化”（`crud/evolution.py:102-137`）。这就是数据库版的“拿旧票不能重复过闸”。

cluster 写入现在要求 unit=1，round 写入要求 unit=4，final 写入要求 unit=4+M 且 running；检查与写操作在同一事务内，stale prepare 无法通过 `ON DELETE CASCADE` 删除已有 rounds（`crud/evolution.py:172-202`, `:260-273`, `:300-318`, 回归 `test_repository.py:332-365`）。

### 2.3 六步状态由一个纯函数产出

`STEP_KEYS` 与中文标题都在服务端固定（`state.py:6-20`）。阈值表把 input/cluster/attribution/severity 固定在 1–4，iteration 是 `4+M`，final 是 `4+M+1`（`state.py:67-82`）。`preparing/running/blocked` 一律把首个未完成步骤标为 active；终态不伪造 active（`state.py:135-166`）。

这层的代价是不能通过“直接写一个 step status”绕过流程；收益是 M5-06 API、M5-07 UI 和事件日志都能消费同一结论。

### 2.4 聚类是明确标注的占位策略

先按固定类型顺序遍历，再按 `probe_id` 排序和 `(n+1)//2` 分半；描述中保留“占位聚类”，避免演示结果被误解为真实语义聚类（`cluster.py:35-65`）。hash 对类型、描述和 probe 顺序做 canonical JSON SHA-256，同输入必须同输出（`cluster.py:68-91`）。

`TYPE_IMPACT` 是不可变 `MappingProxyType`，repository 只保存调用方传入的 impact，不复制策略（`cluster.py:30`, `models/evolution.py:350-357`, `crud/evolution.py:148-163`）。

### 2.5 引擎只声明能力，不抢后续阶段的职责

`EvolutionEngine.handle()` 先验证 `job.kind ∈ stages()`，再从 `KIND_TO_METHOD` 找可调用方法；声明了阶段却没有方法也会 ConfigError（`base.py:28-48`）。factory 只认 run 创建时固化的 `engine_key`，未知 key 直接失败（`factory.py:15-30`）。

cluster-only 只声明 `evolution_prepare`，其他四种 job 在 dispatch 入口失败（`cluster_only.py:11-20`, 测试 `test_engine.py:142-166`）。full 声明五阶段，但把具体编排留给 M5-05/M5-09；这一范围取舍已写入 Agent Note，避免后续出现“没人负责”的空白（`2026-10-27-evolution-state.md:13,21`）。

gateway 配置在每次调用时从 run snapshot 深度冻结为 tuple/mapping proxy，因此创建后修改原字典不会污染历史 run（`contracts.py:60-101`, `base.py:50-53`, 测试 `test_engine.py:223-244`）。

## §3 数据流走查

1. 创建 run：调用方给出 target/repo/version/engine/eval 快照，repository 补默认状态 `preparing`、unit=0 并写行（`crud/evolution.py:40-86`）。
2. 筛选完成：只允许 `0→1`；重放同一 expected 会得到 409，错误里带当前 cursor（`state.py:111-132`, `crud/evolution.py:102-137`）。
3. 聚类写入：run 必须仍在 unit=1；repository 删除旧 cluster/links 后按调用方顺序插入，整个过程一个事务（`crud/evolution.py:139-202`）。
4. 聚类完成并进入归因/排序：继续单步推进到 unit=4；任何跳步或回退都在纯状态层被拒绝（`state.py:111-132`）。
5. 建 rounds：只允许 unit=4 且所有 round 属于同一 run，按 seq 查询稳定排序（`crud/evolution.py:220-288`）。
6. 迭代完成：调用方按 M 个 cluster 逐轮推进到 `4+M`；final 写入时 repository 再查实际 cluster count，防止调用方传错 M（`crud/evolution.py:290-318`）。
7. 终评：在合法 unit/status 下 insert-or-update 单行 final，保证重试可覆盖但不会产生第二行（`crud/evolution.py:319-348`）。
8. 引擎阶段：JobRunner 未来只按 run 的 `engine_key` 走 factory；cluster-only 收到 advance/apply/finalize/retry 会在入口 ConfigError（`factory.py:20-30`, `cluster_only.py:11-20`）。

## §6 讨论点

### D1 `insert_rounds()` 未校验 cluster 是否属于同一 run

**位置**：`apps/api/app/db/crud/evolution.py:220-273`

**现象**：方法会校验所有 round 的 `run_id` 相同，也会校验该 run 的 cursor，但没有确认每个 `probe_cluster_id` 来自这个 run。数据库 FK 只保证 cluster 存在，不保证与 round 的 run 相同。

**问题**：若未来 M5-09 装配时把 A run 的 round 错配到 B run 的 cluster，数据库会接受；M5-06 按 run 读取 rounds/clusters 时就会出现跨 run 的混合迭代。这个问题当前未暴露到 API，但 repository 正是用来守住跨表业务不变量的边界。

**预判**：应在同一事务内先查询这些 cluster 的 `run_id`，要求集合完整且全部等于 round 的 run；用 repository 回归覆盖“外来 cluster 被拒绝且不写 round”。

**结论**：✅ 2026-10-27 已修复（`1d1cece`）。`insert_rounds()` 在同一事务内批量读取 cluster 的 `run_id`，拒绝不存在或属于其他 run 的 cluster；回归同时验证失败后不写入任何 round，且两个 run 的 cluster 保持不变。数据库关系图把 rounds 同时归属 run 与 cluster，逻辑上二者必须同 run，不能只依赖调用方自觉。

### D2 full prepare 模板是否应在 M5-01 完成

**位置**：`apps/api/app/service/evolution/engine/base.py:16-53`, `full.py:10-52`, `cluster_only.py:8-20`

**现象**：本 PR 的 base 只有能力分发和 gateway，没有 fullstack-design §5.4 中完整的 prepare 模板与四个钩子；具体 stage handler 通过 `EngineDeps` 注入。

**问题**：若没有明确 ownership，后续 M5 可能把 prepare 重复实现在 API 或 JobRunner 中。

**预判**：M5-01 先锁定公开能力面，M5-05 实现 cluster-only prepare，M5-09 实现 full prepare/iteration；这种切片能让每期 PR 独立有效，代价是 M5-01 本身不能跑完整 run。

**结论**：✅ 2026-10-27 接受当前切片。Agent Note 已记录 M5-05/M5-09 的后续归属（`2026-10-27-evolution-state.md:21`）；本 PR 不越界实现 git/eval/patch。

### D3 为什么没有在 M5-01 增加 API 与前端

**位置**：`.agents/flow/issues/m5-01-evolution-state.md:43-56`

**现象**：本 PR 只落持久化、状态、聚类算法和引擎工厂，没有 `/runs`、step API 或页面。

**问题**：单看 PR 用户还不能点击或启动 run。

**预判**：M5-02 到 M5-07 分别负责 target/run/step/UI；先完成底座可避免前端按临时契约开发，再在后续改一遍。

**结论**：✅ 与 issue 交付边界一致，非缺失。

### D4 MySQL 是否真的执行相同迁移语义

**位置**：`apps/api/tests/test_database.py:693-827`, `:1391-1568`

**现象**：CI 的 mysql lane 既反射表结构，也执行 repository round-trip。

**问题**：如果只测 SQLite，MySQL 的 JSON、FK、索引或时间行为可能在合并后才暴露。

**预判**：共享 `assert_evolution_schema()` 锁住列/索引/FK/nullability；round-trip 锁住真实写入顺序。

**结论**：✅ 已覆盖；CI run `40374623580` 的 mysql job 通过。
