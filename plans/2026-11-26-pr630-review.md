## §1 一页速览

**一句话：** 表单不再要求用户决定「启用」这个全局状态；新增对象默认启用，编辑停用对象保持停用，停用/启用继续在能看到状态徽标的列表里操作。

**比喻：** 表单是对象的「身份证登记处」，启用状态是对象的「在职状态」。登记处不再顺便办入职/离职，入职/离职回到人事列表里办——那里能看见每个人当前的状态。

| 交付块 | 内容 |
| --- | --- |
| 表单 | 删除 `启用` 表单项、`ElSwitch` 和右侧文案 |
| 状态 | 新增 `enabled: true`；编辑保留 `props.target?.enabled` |
| 生命周期 | 列表 `停用/启用` 动作不变，仍是唯一状态入口 |
| 契约 | 后端、API、DB、启动/归因/总览均不改 |

**验证基线：** 59 个目标配置组件测试、全量 web 套件、目标配置 E2E（含停用后编辑）、50 项 gates、flow/docs 门禁均通过；实机 Before/After 与原型同视口截图见 PR 描述。

## §3 数据流走查

主剧本（新增）：

1. 用户点「新增配置」→ `Index.vue` 打开 `TargetFormDialog`，`target=null`。
2. `resetForm()` 设 `form.enabled = true`；表单渲染到「主指标 key」。
3. 提交 → `submit` 发 `enabled: true` → 后端 `EvolutionTargetWrite` 接收 → 列表刷新显示「已启用」。

编辑停用对象：

1. 列表行「编辑」→ `target.enabled=false`。
2. `resetForm()` 保留 `false`；表单不显示开关，用户看不到状态，但列表行仍可见「已停用」。
3. 保存 → 提交 `enabled: false` → 后端 record 仍停用 → 列表徽标仍为「已停用」。

## §6 讨论点

### F1 · E2E 只断言 API 停用，未断言列表 UI 仍停用

- **位置：** `tests/e2e/m5-target-config.test.mjs:924-939`
- **现象：** 初版新增用例在编辑停用对象后只查 API `enabled: false`；列表行可能因刷新延迟仍显示旧徽标。
- **问题：** 这是否足以证明用户看到的仍然是「已停用」？
- **预判：** 不够；已补 UI 行断言「已停用」。不需要产品决策。
- **结论：** （留空）

### F2 · 编辑弹窗不再显示对象当前状态

- **位置：** `TargetFormDialog.vue:158`、`plans/fullstack-design/08-frontend-implementation.md:751`
- **现象：** 表单不再显示开关，编辑停用对象时弹窗内没有任何「已停用」提示；用户只能从列表行确认。
- **问题：** 是否需要只读状态徽标或提示文案？
- **预判：** 按 #628 的决定，生命周期留在列表；当前不加提示可接受，但若后续出现「为什么保存后没进向导」的反馈，再考虑在弹窗头部显示只读状态。不阻塞本次合并。
- **结论：** （留空）

### F3 · 原型与生产的「归因 Skill」差异

- **预判：** 这是 #628 之前就存在的差异，本次只移除开关；补齐会扩大 UI 改动面，建议独立 issue。PR 已注明对照范围。
