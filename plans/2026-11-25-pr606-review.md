## §1 一页速览

一句话：上游 bad case 真实数据里出现了「`bad_case_type` 为 null」和「`title` 超过 255 字符」的条目，旧传输模型一票否决整页、游标卡死、同步永久停摆；本 PR 沿用 m6-17 的「传输放宽、写入归一」分层，让传输模型接受这两种真实形状，由写入映射统一落库——null/缺失 type 落 `self`、超长 title 截前 200 字符，命中归一化时记一条含 `badCaseId` 与字段名的 info 日志，不改表结构、不改读路径、不改游标语义。

一个比喻：传输模型原来是入库门卫，手里攥着本地仓库的规格书，上游每页货物必须逐件符合规格才放行，一件不合规格整批退回——而上游偏偏会送来「没贴类型标签」和「标签过长」的货，整批退回让补货线彻底停摆。本 PR 把门卫的差事一分为二：门卫只负责「看清来货长相」（接受 null 与超长标签），怎么入库由标签员（`_row` 写入映射）决定——补一张 `self` 标签、把超长标题剪到 200 字符，并且登记一笔「这批有 N 件被加工过」的流水（info 日志）。门卫自己不动手改货，其他规格（缺必填、超长 type、空标题）仍然整批退回。

| 交付块 | 用户可见结果 |
|---|---|
| 传输放宽 | `bad_case_type` 为 null 或缺失的页解析成功；300 字符 title 传输层保真；`extra="forbid"`、时间戳时区、页级排序/唯一/limit/total 校验全部不动 |
| 写入归一 | null/缺失 type 落库 `self`；title 超过 200 截前 200，200 以内原样；显式 `self` / `discovery` 与短标题不被改写 |
| 可观测性 | 归一化命中才记一条 `logger.info`，extra 带 `badCaseId` 与命中字段名；无命中无日志；不新增状态列 |
| 读路径统计 | 归一化后的行落进 `KNOWN_BAD_CASE_TYPES` 白名单，总览计数与列表不再静默漏行 |
| 同步恢复 | 坏页从 poison pill 变为正常页，游标继续推进，后续 bad case 恢复同步 |
| 文档与记录 | 12 章 §3.2/§3.3 与实现一致；Note 三件套记录分层理由与有损取舍 |

## §2 架构导览

### 2.1 传输层：`third_party_api/bad_case_query/`

`http.py` 是出站 HTTP 客户端 `HttpBadCaseCatalogSource`：`fetch_page`（http.py:34-49）用一把 `asyncio.Lock`（http.py:32）保证进程内不并发；`_request`（http.py:55-98）做有界重试——超时与传输错误退避重试（http.py:72-81），401/403 直接映射 `BAD_CASE_QUERY_UNAUTHORIZED`（http.py:83-88），429/5xx 重试（http.py:89-94），其余 ≥400 映射 `BAD_CASE_QUERY_REQUEST_FAILED`（http.py:95-96）。`_parse`（http.py:100-128）是页级校验三连：JSON 可解析（http.py:108-113）→ `BadCasePage.model_validate`（http.py:114-119）→ 回显 offset/limit 一致（http.py:120-123）+ 所有 id 严格大于请求游标（http.py:124-127）；任何一环失败都收敛为 `BAD_CASE_QUERY_INVALID_RESPONSE`（http.py:149-155）。

`models.py` 是严格模型：`BadCaseItem`（models.py:11-37）`extra="forbid"`（models.py:14），本 PR 改了两处——`bad_case_type: str | None = Field(default=None, min_length=1, max_length=16)`（models.py:18，原为必填 `str`）、`title` 去掉 `max_length=255` 保留 `min_length=1`（models.py:24，alias `bad_case_title`）。`BadCasePage`（models.py:40-62）的页级结构校验未动：`limit ≤ 200`（models.py:47），`consistent` 校验器拒绝超页、乱序、重 id、`total < len(items)`（models.py:50-62）。`BadCaseCatalogSource` Protocol（models.py:65-78）定义只读分页源契约。

### 2.2 服务层：`service/acquisition/bad_case_catalog_sync.py`

`_row`（bad_case_catalog_sync.py:61-91）是本 PR 的核心：先检测漂移（bad_case_catalog_sync.py:63-70，`bad_case_type is None` 与 `len(title) > 200` 两项），命中则记一条 `logger.info("upstream bad case normalized", extra={"badCaseId": ..., "fields": ...})`（bad_case_catalog_sync.py:71-75），再构造 `CatalogCaseRow`——`bad_case_type=item.bad_case_type or "self"`（bad_case_catalog_sync.py:79）、`title=item.title[:200]`（bad_case_catalog_sync.py:85），其余映射与 m6-17 的空值降级（`_object_name` bad_case_catalog_sync.py:53-58、`object_type or "skill"` bad_case_catalog_sync.py:81）保持不变。`BadCaseCatalogSyncService.run`（bad_case_catalog_sync.py:144-226）循环翻页：读游标（bad_case_catalog_sync.py:147-149）→ `mark_running`（bad_case_catalog_sync.py:161）→ 每页 `fetch_bad_case_page`（bad_case_catalog_sync.py:177-181）→ 空页即 exhausted（bad_case_catalog_sync.py:182-185）→ 游标不前进则报 502（bad_case_catalog_sync.py:186-192）→ `commit_page`（bad_case_catalog_sync.py:195-200）→ 推进游标与计数（bad_case_catalog_sync.py:201-206）→ 预算上限 `max_pages` / `deadline` 控制单轮规模（bad_case_catalog_sync.py:103-112、176）→ 收尾 `mark_idle`（bad_case_catalog_sync.py:210）或异常 `mark_failed` 后重抛（bad_case_catalog_sync.py:211-216）。

## §3 数据流走查

剧本：上游返回一页 2 条——id=101 `bad_case_type=null`、title 正常；id=102 `type="self"`、title 恰好 300 个字符。

1. 周期触发：coordinator `_scheduler_loop` 到点调 `run_once` → `trigger`（coordinator:101-103、77-99），提交 `KIND="bad_case_catalog_sync"` job；JobRunner 通过 main.py:312 注册的 handler 进入 `service.handle`（service:131-142）→ `run(owner=job.id)`。
2. 读游标与开工：`get_state` 拿 `last_bad_case_id`（service:147-149 → crud:128-142），`mark_running` 清上轮错误（service:161 → crud:186-198）。
3. 取页：`fetch_bad_case_page(after_id=cursor, offset=0, limit=page_size)`（service:177-181）→ `HttpBadCaseCatalogSource.fetch_page` 持锁发请求（http.py:34-49、42）→ `_parse` 校验。**修复前**：id=101 的 null type 在 `model_validate` 违反必填约束、id=102 的 300 字符 title 违反 255 上限，`ValidationError` → 整页 `BAD_CASE_QUERY_INVALID_RESPONSE`（http.py:114-119、149-155），游标卡死。**修复后**：models.py:18 与 :24 放行这两种形状，页通过；页级排序/唯一/limit/total 校验照常把关（models.py:50-62）。
4. 逐条归一化：`_row(item, page_now)`（service:195-200 → 61-91）。id=101 命中 `bad_case_type is None` → 日志 `fields="bad_case_type"`，落库 `bad_case_type="self"`（service:79）；id=102 命中 `len(title)=300 > 200` → 日志 `fields="title"`，落库 title 为前 200 字符（service:85）。若一条同时命中两项，`fields="bad_case_type,title"`（service:63-75）。
5. 原子落页：`commit_page`（crud:232-301）。101/102 都是 catalog 新 id → `begin_nested` 批量插入（crud:255-256）；`bad_case_type` 列 NOT NULL（domain.py:306）由第 4 步的 `self` 兜住；同事务把 `last_bad_case_id` 推到 102、`synced_count` 重算（crud:286-296）。
6. 游标推进与收尾：`pages+1`、`cursor=102`、`pending = total − len(items) = 0`（service:201-206、194）；本页 2 条 ≥ total 2 → `exhausted=True`（service:207-209）→ `mark_idle` 归零 attempts 与 last_error（service:210 → crud:214-230）。
7. 读路径统计：总览 `counts` 的 `_case_conditions` 用 `bad_case_type.in_(("self","discovery"))` 过滤（overview.py:114-132、119）——id=101 归一化后带 `self` 标签进入 `self_cases` 计数（overview.py:180-182），而不是被白名单静默排除；`page_cases` 列表展示 id=102 的截后 200 字符标题（overview.py:402、461），前端与同步浮层不需要任何感知。

反路径（未放宽的形状照旧拒绝）：空 session_id、37 字符 session_id、17 字符 type、空 title 任一出现，仍在第 3 步整页 `BAD_CASE_QUERY_INVALID_RESPONSE`，游标不动、`mark_failed` 记稳定错误码（service:211-216、crud:200-212）——页级原子性与「坏页不推进」的既有语义未被本 PR 触碰（test_bad_case_query_client.py:205-235 锁定）。

## §6 讨论点

### D1 `bad_case_type=""`（空字符串）形状未被测试覆盖

- **位置**：`apps/api/app/third_party_api/bad_case_query/models.py:18`（约束）、`apps/api/app/service/acquisition/bad_case_catalog_sync.py:79`（归一化）、`apps/api/tests/m6-16-bad-case-catalog-sync/test_bad_case_query_client.py:205-235`（非法形状参数化，含 17 字符 type 与空 title，无空串 type）
- **现象**：传输约束 `str | None = Field(default=None, min_length=1, max_length=16)` 对非 None 值生效——探针实测（pydantic 2.14.4）：空串被拒 `string_too_short`，null 与缺失放行。该 `min_length=1` 是 main 原样保留项，本 PR 只把类型改为可空。测试覆盖了 null、缺失、超长三种漂移形状，空串形状不在任何参数化列表里。
- **问题**：是否值得在本 PR 补一条参数化用例（把 `{"bad_case_type": ""}` 加进客户端非法形状列表），还是留给后续？
- **预判**：当前行为是自洽的：传输层拒绝空串，空串永远到不了 `_row`；即使将来放行，`or "self"`（falsy 兜底）也会把空串落成 `self`（见 D4 的漂移实例）。所以这是「防未来无意放宽」的回归锁，而非修复项：往现有 `pytest.mark.parametrize` 列表加一项的成本约一行，收益是把「传输层继续拒绝空串」这一 main 既有契约显式钉住。倾向本 PR 顺手补一条；若维护者认为该约束无需回归保护，留后续亦可——两种选择当前都无实害。
- **结论**：已决（2026-11-25，采纳并修复）：`test_fetch_page_still_rejects_illegal_shapes` 参数化列表补 `{"bad_case_type": ""}`，断言空串 type 仍整页 `BAD_CASE_QUERY_INVALID_RESPONSE`——传输层 `min_length=1` 拒绝空串是 main 既有契约（pydantic 探针已证实），用例钉住它防未来无意放宽。

### D2 归一化日志用 `logger.info` 的量级影响

- **位置**：`apps/api/app/service/acquisition/bad_case_catalog_sync.py:63-75`（配合 `page_size` 上限 200（service:110、models.py:47）与 `max_pages` 默认 100（service:103））
- **现象**：每条命中归一化的 item 记一条 info 日志，逐条携带 `badCaseId`。极端场景（上游全量漂移，如冷启动同步十万条、全部 title 超长）：单轮 run 理论上限 100 页 × 200 条 = 2 万条 info 日志。
- **问题**：上游大面积漂移时，info 级逐条日志的噪音与存储量是否可接受？要不要改成每页一条聚合、或降级/采样？
- **预判**：逐条 + 带 `badCaseId` 正是这条日志的设计意图——「区分上游漂移与本地逻辑错误」需要能定位到具体 case（Note Consequences 第 4 条已记录此取舍）；聚合会丢掉可定位性，采样会丢掉漂移规模。漂移量本身就是需要被看见的信号：万级漂移暴露的是上游数据治理问题，日志量只是它的影子，且 info 级别在常规日志管线下可控。倾向维持现状，无实害；真出现量级问题时再议采样，届时 owning Note 的 Consequences 是现成的重评估起点。
- **结论**：已决（2026-11-25，不改代码）：逐条带 `badCaseId` 的 info 日志正是「区分上游漂移与本地逻辑错误」的设计意图，极端量级（单轮至多 2 万条）是上游数据治理问题的影子且 info 级可控；真出现量级问题再议采样，owning Note Consequences 为现成重评起点。

### D3 `title[:200]` 的截断边界：Python 码点 vs 数据库 utf8mb4 字符宽度

- **位置**：`apps/api/app/service/acquisition/bad_case_catalog_sync.py:85`（截断）、`apps/api/app/db/models/domain.py:312`（`title` String(255)）、`apps/api/app/config.py:217`（默认连接串 `charset=utf8mb4`）
- **现象**：Python 字符串切片按 Unicode 码点截断（`len('😄') == 1`）；MySQL 官方手册 §13.3.1 明确「对字符字符串列（CHAR/VARCHAR/TEXT），长度规格按字符单位解释」「VARCHAR(M) 的 M 是最大字符数」，utf8mb4 下 BMP 之外的增补字符（如 emoji）同样计 1 字符。本表通过 utf8mb4 连接访问。
- **问题**：码点截断语义与数据库字符宽度语义是否一致？4 字节字符（emoji）会不会因「字节 vs 字符」错位导致截后仍超列宽？
- **预判**：一致，无风险。两端计数都是码点口径：Python `[:200]` 最多 200 个码点，MySQL utf8mb4 的 VARCHAR(255) 按 255 个字符（码点）计，200 ≤ 255 恒成立，写入永不触列宽。探针实测传输层放行 250 个 emoji 的 title 且 `len==250`（每 emoji 计 1 码点），佐证码点口径。SQLite 测试环境不强制 VARCHAR 长度，更无影响。检视侧未起本地 MySQL 实例做端到端写入实测（本机无 MySQL），依据为官方文档 + CI `mysql` lane 绿；组合字符（变音符等 grapheme cluster 拆成多码点）在两端都按码点计，口径同样一致。结论：无实害。
- **结论**：已决（2026-11-25，实测 + 官方文档）：无实害——Python `[:200]` 码点截断与 MySQL utf8mb4 字符宽度口径一致（手册 §13.3.1：字符列长度按字符单位解释），200 ≤ 255 恒成立，写入永不触列宽。

### D4 `_row` 里「归一化检测」与「实际归一化」是两处独立逻辑，存在漂移空间

- **位置**：`apps/api/app/service/acquisition/bad_case_catalog_sync.py:63-70`（检测：`is None` / `len > 200`）对照 `:79` / `:85`（改写：`or "self"` / `[:200]`）
- **现象**：检测表达式与改写表达式分处两段，靠人肉保持同步。对 None 与 `>200` 两者严格一致；对空串 `""` 两者不一致——`"" or "self"` 会归一落库，但 `"" is None` 不判漂移、不记日志。当前该不一致不可达：传输层 `min_length=1` 拒绝空串（探针实测 `string_too_short`）。
- **问题**：未来若有人放宽传输约束（例如允许空串表达「上游显式空」），只改一处不改另一处，会产生「落库 self 但无归一化日志」或反向的静默漂移；这个同步维护成本要不要现在收口？
- **预判**：风险真实但当前不可达，无实害。可选收口是先算归一值再与原值比较（把两处合成一处），但会牺牲现写法的直读性；m6-17 的 `object_name` / `object_type` 降级（service:53-58、81）一直没有日志，本 PR 的检测已是增强而非欠账。倾向本 PR 不改，约定「放宽传输约束的 PR 必须同时补空串用例」（与 D1 呼应），届时顺手收口；该约定可写进 owning Note 的 Consequences 一句话防遗忘。
- **结论**：已决（2026-11-25，不改代码）：空串被传输层拒绝，检测/改写不一致当前不可达；D1 用例已锁空串拒绝行为；约定未来任何放宽传输约束的 PR 必须补空串用例并同步收口 `_row` 检测与改写逻辑（约定记本文结论栏）。

### D5 存量 201–255 字符 title 行在下次 catalog 更新时会被被动截断（检视侧补充）

- **位置**：`apps/api/app/db/crud/bad_case_catalog_sync.py:25-39`（`_UPDATE_COLUMNS` 含 `title`）、`:265-278`（catalog 自有行 update）、`apps/api/app/service/acquisition/bad_case_catalog_sync.py:85`
- **现象**：修复前旧代码允许 201–255 字符 title 原样落库（列宽 255）。修复后，若这类存量行（origin=catalog）再次进入同步窗口，update 分支会用归一化后的值（截前 200）覆写 title。
- **问题**：issue 非目标写明「不回填或重写存量行」——这种被动截断是否越界？
- **预判**：不越界，影响面极小：游标只增（crud:286-296 仅在 commit_page 内推进，service:205），已推进过的 id 不会被重扫；只有冷启动（cursor 行不存在）或该 id 恰在未同步窗口内才会触发 update。且「下次同步按当前归一化规则写入」与主动回填是两回事——落库值本就应满足现行规则，与「上游该行本来就是超长 title」一致。无实害，无需行动；记录留档供将来追溯「为什么某行 title 从 230 字符变成 200」。
- **结论**：已决（2026-11-25，不改代码）：被动截断仅影响冷启动或恰在未同步窗口内的存量行（游标只增、已推进 id 不重扫），影响面极小；「下次同步按现行规则写入」与主动回填是两回事，本文留档供将来追溯。

### 9.1 `apps/api/app/third_party_api/bad_case_query/models.py`（M）

职责：上游 bad case 目录查询的传输模型与分页源 Protocol——把「上游响应长什么样」钉成代码。变更形态：M，±3 行两处字段签名 + docstring 一句。

关键依赖：`pydantic`（2.14.4，运行时校验库，社区第一方生态的核心件）：`Field` 的 `min_length` / `max_length` 对 `str | None` 只作用于非 None 值；`ConfigDict(extra="forbid")` 让多余字段整页拒绝。可把 pydantic 比作海关 X 光机——包裹形状不合规格当场拦下，本 PR 相当于把两种「上游真实会寄」的形状从违禁清单移到放行清单。

旧代码（`git show 907d3446:...`）：

```python
class BadCaseItem(BaseModel):
    """One upstream bad case shaped like the local bad_cases columns."""
    ...
    bad_case_type: str = Field(min_length=1, max_length=16)
    ...
    title: str = Field(alias="bad_case_title", min_length=1, max_length=255)
```

新代码：

```python
class BadCaseItem(BaseModel):
    """One upstream bad case; null type and overlong titles stay for write normalization."""
    ...
    bad_case_type: str | None = Field(default=None, min_length=1, max_length=16)
    ...
    title: str = Field(alias="bad_case_title", min_length=1)
```

这在做什么：把「上游数据已满足本地列约束」这个错误假设从模型里去掉——type 可以没有，title 可以很长；非空时的 1–16 长度与非空 title 保留。为什么这么写：`default=None` 让「字段缺失」与「显式 null」殊途同归（探针实测两者都得到 `None`），解析层保持忠实（不改写值），把「怎么落库」留给写入层——这正是 docstring 新句 `stay for write normalization` 的含义。`BadCasePage` 的 `consistent` 校验器与 `limit le=200` 一行未动，页级结构防线原样。

实现思路总结：类型层只放宽「形状」约束，语义归一全部下沉写入层；两处放宽与 12 §3.3「仅有的两处放宽」条款逐字对应。

检视发现：空串形状仍被拒（main 原样，未测，见 D1）；其余无发现。

### 9.2 `apps/api/app/service/acquisition/bad_case_catalog_sync.py`（M）

职责：游标式同步服务——把上游页翻译成本地行并原子落库。变更形态：M，`_row` 函数 +13/−2 行，类主体零变更。

新代码：

```python
def _row(item: BadCaseItem, fallback: datetime) -> CatalogCaseRow:
    """Map one upstream item to local columns, normalizing type and title."""
    normalized = [
        field
        for field, drifted in (
            ("bad_case_type", item.bad_case_type is None),
            ("title", len(item.title) > 200),
        )
        if drifted
    ]
    if normalized:
        logger.info(
            "upstream bad case normalized",
            extra={"badCaseId": item.bad_case_id, "fields": ",".join(normalized)},
        )
    return CatalogCaseRow(
        ...
        bad_case_type=item.bad_case_type or "self",
        ...
        title=item.title[:200],
        ...
    )
```

这在做什么：落库前先回答「这条要不要加工」，要则记一笔带 `badCaseId` 与命中字段名的流水，然后统一产出满足本地列约束的行。为什么这么写：`or "self"` 与 `[:200]` 都是无条件表达式，正常数据走过去值不变（`"self" or "self"` == `"self"`，10 字符 `[:200]` 原样），漂移数据被兜住——不需要 if/else 分支，两条规则对显式合法值天然幂等（`test_explicit_bad_case_type_and_short_title_stay_verbatim` 锁定）。检测列表与 200 口径来自归因侧既有预算（attribution.py:436、attribution_executor.py:118 均 `[:200]`），不是新发明。

实现思路总结：归一化 = 一条检测（可观测）+ 一条改写（兜底），写进唯一的写入映射函数；页级事务、游标、预算逻辑零接触。

检视发现：检测与改写对空串不一致（D4，当前不可达无实害）；逐条日志量级（D2，可接受）；存量行被动截断（D5，无实害）。
