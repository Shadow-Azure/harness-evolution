## §1 一页速览

**一句话**：总览页原来在一个 1180px 宽的盒子里自己滚动，滚动条就画在盒子右缘；现在让滚动容器铺满工作区，再用左右对称的内边距把内容列“顶”回中间，滚动条自然落到窗口右缘。

**比喻**：像把窗帘的滑轨从“窗框内的一根窄杆”换成“整面墙的轨道”——窗帘（内容列）还挂在原来的位置，但拉绳（滚动条）回到了墙边。

| 交付块 | 内容 |
|---|---|
| 行为 | 1500×837 常显滚动条下，滚动条 x=1485–1500（窗口右缘）；内容列 180–1305 不变 |
| 不变 | 1180px 内容列、卡片宽 1125px、筛选/列表交互、1024/640 断点 |
| 测试 | 新增 1 个 E2E 用例，覆盖右缘、滚动、横向溢出与断点 |
| 流程 | #362 → m12-16（in-progress），M12 active |

## §2 架构导览

### 2.1 工作区壳层没有动

`apps/web/src/App.vue:116-121` 的 `main.workspace-main` 仍是 `height: calc(100vh - 56px)` + `overflow: hidden`。这是刻意的：Session 列表、错误详情、自进化、空间管理都依赖各自的内滚动容器，贸然把壳层改成 `overflow: auto` 会给这些页面叠加第二条滚动条。PR 只改总览页自己的滚动子容器，影响面收敛在一个页面。

### 2.2 滚动容器与内容列的分离

`apps/web/src/pages/overview/Index.vue:597-605`：

```css
.overview-page {
  width: 100%;
  height: 100%;
  padding: 18px max(20px, calc((100% - 1180px) / 2 + 20px)) 64px;
  overflow-y: auto;
}
```

- `width: 100%` 让滚动容器与 `main.workspace-main` 同宽，滚动条画在容器右缘 = 窗口右缘。
- inline padding 的百分比与 `calc` 按包含块（`main`，1500px）解析；左右对称，所以内容列始终在滚动视口内居中。
- 公式 `(100% - 1180px) / 2 + 20px` 的含义：先让 1180px 盒子居中，再加回 20px 内边距——等价于以前的 `width: min(1180px, 100%) + margin: auto + padding: 20px`。
- 滚动条宽度从内容区扣除，但左右 padding 对称，内容列仍居中；右侧多出的滚动条宽度就是滚动条自己。

不同视口下的几何（实测）：

| 视口 | padding | 滚动条 | 内容列（`.ov-grid`） |
|---|---|---|---|
| 1500 | 180 | 15（1485–1500） | 180–1305（1125） |
| 1024 | 20 | 15 | 20–989（969） |
| 640 | 12（640 断点覆盖） | 文档滚动 | 12–628（616） |

Before 与 After 在 1500 下的内容列都是 180–1305（1125px），所以卡片/筛选/列表宽度没有变化。

## §6 讨论点

### 6.1 卡片宽度是否“不变”

- **位置**：`apps/web/src/pages/overview/Index.vue:597-605`
- **现象**：第一版用“内部 `.overview-column` 包一层 1180px”的方案，1500 下卡片内容宽从 Before 的 1125px 变成 1140px（多出滚动条腾出的 15px）。
- **问题**：issue 的验收要求“卡片、筛选、列表的宽度与交互不变”，多 15px 是否算变更？
- **预判**：用对称 inline padding 可以让内容宽严格保持 1125px；已改用该方案并实测 Before/After 的 `.ov-grid` 都是 180–1305。
- **结论**：已决（2026-11-18）。以 padding 方案为准，卡片宽度与 Before 逐像素一致；代价是 `.overview-page` 的“列宽”由内边距表达，而不是一个显式的 1180px 盒子，可读性靠注释补足。

### 6.2 滚动条起点是顶栏以下，而不是原型那种从窗口顶部开始

- **位置**：`apps/web/src/App.vue:116-121`、`Index.vue:601-604`
- **现象**：原型由文档整体滚动，滚动条从 y=0 开始；本实现滚动容器在 `main` 内，滚动条从 y=56（顶栏高度）开始。
- **问题**：这是否仍与原型不一致？
- **预判**：issue 的目标明确写“滚动条起点与原型一致（顶栏以下至窗口底部）”，当前的壳层语义就是工作区主体内滚动；把文档还给页面会牵动其它工作区页面，超出本 issue 的交付边界。
- **结论**：按 issue 定义接受。若未来要完全复刻原型的文档滚动，应作为壳层级 issue 统一评估。

### 6.3 内容列相对窗口几何中心有约 7.5px 偏移

- **位置**：`Index.vue:603`
- **现象**：经典滚动条占 15px，内容列在“滚动视口”（1485px）内居中，因此相对 1500px 窗口的几何中心左移 7.5px。
- **问题**：是否要为了视觉中心补偿半个滚动条？
- **预判**：不建议。补偿会让布局依赖滚动条宽度（覆盖式滚动条平台为 0），并且 Before 的内容列本来也在窗口中心（160–1340）；当前方案内容列与 Before 完全同位置，只是滚动条外移。用户感知的是滚动条位置，不是 7.5px 的列偏移。
- **结论**：已决（2026-11-18）。不补偿，保持与 Before 相同的内容列坐标。

### 6.4 合入后的流程收口

- **位置**：`m12-milestone.md:9`、`m12-16-overview-scroll-ownership.md` flow 围栏
- **现象**：PR 合入时 `m12-16` 仍是 in-progress、M12 仍是 active；GitHub 会因 `Closes #362` 关闭 issue，但本地流程树不会自动变 done。

## §9 文件级代码分析

### 9.1 `apps/web/src/pages/overview/Index.vue`（M）

职责：总览页的布局、请求区块与 URL 状态。本次只改 scoped style。

旧：

```css
.overview-page {
  width: min(1180px, 100%);
  height: 100%;
  margin: 0 auto;
  padding: 18px 20px 64px;
  overflow-y: auto;
}
```

新：

```css
.overview-page {
  width: 100%;
  height: 100%;
  padding: 18px max(20px, calc((100% - 1180px) / 2 + 20px)) 64px;
  overflow-y: auto;
}
```

为什么这么写：滚动条属于“滚动容器”而不是“内容列”。把容器拉满、用 padding 把内容“挤”回中间，既保住 1180px 列与卡片宽度，又让滚动条画在窗口边。`max(20px, …)` 保证 1180px 以下仍有 20px 呼吸空间；640 断点继续用原来的 `14px 12px 48px`，移动端行为不变。

实现思路总结（≤3 行）：容器全宽 → 滚动条到窗口边；对称 padding 代替 `margin:auto`；断点沿用原覆盖规则。

检视发现：无功能缺陷。可读性上，公式比显式 1180 盒子更难一眼看懂，已用注释解释。

### 9.2 `tests/e2e/m8-04-overview.test.mjs`（M）

- 1500×837：滚动容器 `getBoundingClientRect().right` 与 `innerWidth` 相差 ≤1px；`scrollHeight > clientHeight`；`.ov-grid` 宽 1000–1140；document/body 无横向溢出。
