## §1 一页速览

一句话：这个 PR 把每个 Agent 的原始 JSONL 变成可落库的统计、用户输入锚点和 Skill/Agent/Workflow 事件，同时让坏行变成安全 issue，消息与 thinking 文本只留在解析期。

生活化比喻：normalizer 像海关的计票员；它逐箱扫描记录、累计真正有效的票据、把私密信件留在过境区，只交出一张不含内容的统计单。某一行损坏时，它记下箱号，不把整船货退回去。

| 交付块 | 结论 |
|---|---|
| per-payload 纯解析 | 已按最后累计 usage 修正，真实 token 总量可追溯 |
| bad-line 隔离与隐私 | 标准坏 JSON 已隔离；合法 JSON 的非对象记录被静默忽略 |
| 用户轮次/事件 | 主 Agent 过滤、human attachment、事件顺序与偏移符合测试预期 |
| 结构 block | 基本符合；`tool_result` 未保留 `tool_use_id` 关联 |
| sync error 落库 | 只写稳定结构，不泄漏原始行或正文 |
| fixture golden 与本地聚合 | 测试与命令均可复现，但 golden oracle 同步固化了 usage 首片口径 |

## §3 数据流走查

### 场景：一份主 Agent payload 被导入后计算统计

1. 本地导入把原文按 `(root_session_id, agent_id)` 写入 `trajectory_payloads`，并留下未处理 source index。
2. `normalize_local_sessions()` 扫描语料，对每个 payload 调纯 parser。[local_sessions.py:449](/Users/zn-ice/2026/harness-evolution/apps/api/app/service/acquisition/local_sessions.py:449)
3. parser 逐行解析；坏行只生成脱敏 issue。
4. 主记录中的 cwd/branch/version/entrypoint 被复制进 RootMetadata；时间转 Asia/Shanghai。
5. user 记录与 human attachment 生成 `ParsedUserTurn`；assistant tool_use 生成 `ParsedEvent`。
6. assistant usage 按 message id 计一次；工具/error/模型统计写入 ParsedTranscript。
7. 本地命令仅输出 aggregate，不输出 prompt、message、thinking、tool result、路径或 issue 原文。
8. m2-04 之后才能使用这些结果组装树并写业务表；本 PR 不更新 `source_records.processed_*`。

## §6 讨论点

### D1 重复 message 的 usage 固定取首片，真实 token 总量少计

**位置**：`apps/api/app/service/acquisition/normalize.py:417-423`；测试固化在 `apps/api/tests/m2-03-jsonl-normalizer/test_normalize.py:105-154,203`

**现象**：同一 `message.id` 第一次出现时即标记 usage 已计入，之后的分片即使携带最终 usage 也不会再读。真实本地数据有 1,889 个重复 message id，其中 1,318 个首片 usage 为 0、后续才出现有效 usage；所有 1,889 个序列都单调不减。当前聚合计为 4,371,178 tokens，取每条 message 最后一个 usage 则为 9,743,423。

**问题**：设计要求“usage 按 message.id 去重后求和”，目的是同一消息不重复，而不是保留第一次出现的未完成分片。按当前行为，大多数使用流式分片的真实消息会少计 input/output，后续 `agents.tokens_total` 与会话总量都会失真。

**预判**：这是需要修复的数据正确性缺陷。聚合期应按 message id 保存“最终一条有效 usage”，或保持最后观测值；若遇到非单调下降，应判定 provider 数据异常而不是静默接受。现有“首片 positive、后续 999”测试只覆盖了相反方向，掩盖了真实数据的正常流式形态。

**结论**：已修复（2026-10-25）。同一 message id 以最后观测的累计 usage 覆盖先前分片；回归覆盖真实流式 `0 → 有效值` 形态。真实本地 token 聚合修正为 9,743,423，其余消息、工具、错误和轮次统计不变。

### D2 `tool_result` 丢失 `tool_use_id` 关联

**位置**：`apps/api/app/service/acquisition/normalize.py:391-405`；测试期望见 `test_normalize.py:384-428`

**现象**：`ParsedBlock` 一律从 `block.id` 取 `tool_use_id`，但 Claude 的 `tool_result` 使用 `tool_use_id` 字段。实测一条 `{type:"tool_result", tool_use_id:"tool-1"}` 得到 `ParsedBlock(kind="tool_result", tool_use_id=None)`。

**问题**：设计 §2.3 rule 3 明确要求 `tool_result` 按 `tool_use_id` 回填。当前结果无法把 tool result 与产生它的 tool_use 关联，后续树组装若消费结构 block，会丢失调用关系。

**预判**：无安全影响，但属于解析契约缺陷。最小修复是在 `tool_result` 分支优先读 `block.tool_use_id`，并补一个保留 id 的断言；现有测试应改为验证关联，而不是把 `None` 固化。

**结论**：已修复（2026-10-25）。`tool_result` 读取 `tool_use_id`，`tool_use` 继续读取 `id`；回归断言关联 id 为 `tool-1`。

### D3 合法 JSON 的非对象行被静默忽略

**位置**：`apps/api/app/service/acquisition/normalize.py:322-324`

**现象**：输入 `42\n` 被 `json.loads()` 接受，`_dict(42)` 变成空 dict，随后 `continue`；parser 返回 `lines=2`、`issues=[]`，同一 payload 后续 user turn 仍被读取。

**问题**：payload 契约的每一行是一个 JSON object。一个顶层 array、string、number 或 null 虽然语法合法，但不是 transcript record，无法产生任何统计；当前完全静默，违反“坏行写入 errors 并隔离”的可诊断目标。

**预判**：这是边界数据健壮性问题。应在继续前判定 `isinstance(raw, dict)`，否则生成稳定、脱敏的 `INVALID_JSONL_RECORD` issue；若产品决定把非对象行视为空记录，应在设计里明确，而不能靠实现偶然忽略。

**结论**：已修复（2026-10-25）。顶层标量、数组和 `null` 产生脱敏 `INVALID_TRANSCRIPT_RECORD`，不泄露原值，也不阻断后续记录。
