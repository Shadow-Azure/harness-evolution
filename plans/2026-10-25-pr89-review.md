## §1 一页速览

一句话：这个 PR 把一组互不相关的 Agent transcript 拼回一棵可回溯的会话树，并为 Workflow、forked skill、teammate 和异常父链提供统一规则。

生活化比喻：它像把一桌散落的接线端子和线缆按插头编号接回配电盘；普通子 Agent 靠 `toolUseId` 找插座，teammate 直接接主闸，Workflow 是新增的零负载汇流节点。

| 交付块 | 结论 |
|---|---|
| main/普通 subagent/teammate | 基本符合设计；本地 62 个 subagent 均可回溯 |
| Workflow/forked skill | 合成节点、零统计和 fork 名称规则已覆盖 |
| 缺父降级 | 节点会挂 main 并告警，但合成边锚点不完整，见 D1 |
| 排序/环检测/隐私 | 结构排序稳定，警告不含正文或路径 |
| 统计与状态 | 统计求和正确；`fail` 判定只覆盖零消息，见 D2 |
| fixture golden | 排除了 manifest 的 workflow 行，未发现节点 ID 漂移，见 D4 |

## §2 架构导览

### 2.1 纯函数边界

`agent_tree.py:305` 的 `_assemble_root` 只接收 m2-03 的 `ParsedTranscript`，不重新读取 JSONL 或数据库。这个边界把解析错误和树结构错误分开，也避免 m2-05 的事务职责提前渗入。

`agent_tree.py:53` 定义扁平 `AssembledSessionTree`，节点通过 `parent_agent_id` 表达层级。前端无需递归嵌套 JSON，与 `05-api-design.md:168-169` 的扁平 `agents[]` 契约一致。

### 2.2 父链与合成节点

`agent_tree.py:361-404` 先给 root 内每个 `toolUseId` 建索引，再从 Workflow 事件生成 `wf_` 节点。普通子 Agent 在 `agent_tree.py:509-533` 通过父事件匹配；teammate 在 `agent_tree.py:442-448` 直接挂 main。

缺父调用时，`agent_tree.py:430-436` 会向 main 追加合成 `agent` 事件并产生稳定警告。但这里没有同步更新子节点自身的 `toolUseId`，见 D1。

### 2.3 结构与确定性

`agent_tree.py:216-251` 做环检测和不可回溯检测，`agent_tree.py:254-270` 按结构深度、源位置和 id 排序。测试用反转输入验证树签名稳定，避免依赖 SQL 返回顺序。

### 2.4 统计与会话边界

节点统计直接复制规范化结果；`agent_tree.py:622-634` 对整棵树求 messages/tools/errors/tokens 总和，`spawnDepth` 保留 provider 值。Workflow 节点固定零统计。时间边界取所有 transcript 的有效首末时间。

## §3 数据流走查

### 场景 A：主 Agent 调用普通子 Agent

1. m2-03 从 assistant 的 `Agent` tool-use 生成 `kind=agent` 事件。
2. 子 transcript 的 `meta.toolUseId` 指向该调用。
3. assembler 在 root 内查到事件 owner，把 `parentAgentId` 设为 owner。
4. 节点描述取父事件 description，排序锚点也取父事件位置。
5. 页面或持久化层可用 `parentAgentId + toolUseId` 画出边。

### 场景 B：缺父调用

1. 子 transcript 没有 `meta.toolUseId`。
2. assembler 将节点降级挂 main，并写 `MISSING_PARENT_TOOL_USE_ID`。
3. assembler 向 main 追加合成 `agent` 事件。
4. 当前子节点仍保留 `toolUseId=null`，合成事件却使用 `synthetic-agent-...`；两者不能配对，见 D1。

### 场景 C：Workflow

1. main 的 `Workflow` tool-use 生成 Workflow 事件。
2. assembler 用 root id + tool-use id 生成稳定 `wf_<digest>` 节点。
3. Workflow 节点四项统计为 0，`toolUseId` 保留调用 id。
4. workflow-subagent 优先使用明确 workflow 元数据；否则在唯一 Workflow 下挂接。

### 场景 D：forked skill

1. 普通 Skill 事件只留在父节点的 events 中。
2. 有独立 transcript 的 forked skill 生成 `kind=subagent/taskKind=forked_skill` 节点。
3. 节点 `agentType` 与 `name` 清空，`skillName` 保留；优先按父 tool id，否则按 skill name 找唯一父事件。

## §6 讨论点

### D1 缺父合成事件没有和子节点形成可配对锚点

**位置**：`apps/api/app/service/acquisition/agent_tree.py:273-291`、`430-436`、`509-517`

**现象**：实测 main 无事件、普通 child 无 `meta.toolUseId` 时，main 得到 `synthetic-agent-a89a...` 事件，但 child 的公开 `toolUseId` 仍是 `None`。main 已有 2 条 assistant message 时，合成事件仍写 `messageOffset=0`。现有测试只断言 main 多了一个事件，没有断言 child 和新事件能配对。

**问题**：`05-api-design.md:169` 明确定义 `toolUseId` 是画布边的父调用锚点；`messageOffset` 是该触发点之前的 assistant 数。当前结构虽然能从 `parentAgentId` 回 root，但前端无法用 child 的 `toolUseId` 找到合成事件，且 `×N` 会错误地显示该边发生在第一条消息之前。本地恰好就有 1 个缺父普通 Agent，因此不是纯理论边界。

**预判**：这是本 PR 唯一直接影响真实数据展示的缺陷。修复时让 `append_missing_parent_event` 返回合成 tool id 和 offset，同时更新 child 的 `toolUseId`、排序锚点；offset 取该节点当前 unique assistant message 数。增加“child.toolUseId == main synthetic event.toolUseId”和“offset == main.messagesCount”的断言。

**结论**：已修复（2026-10-25）。缺失/未知父调用现在生成 root+child 稳定的合成 `toolUseId`，child 与 main 锚点共享该 id；`lineNo` 为父事件末尾后的确定性位置，`messageOffset` 等于 main 已有的 unique assistant 数。回归测试同时断言可配对与偏移。

### D2 `fail` 状态规则只实现了“主 Agent 零消息”

**位置**：`apps/api/app/service/acquisition/agent_tree.py:294-302`

**现象**：实测 main 记录顺序为 user → assistant → user，最后一条 assistant 缺失，messages_count=1，assembler 仍返回 `ok`。代码没有 provider fatal/未恢复错误的输入字段，也只把“零消息”视为 fail。

**问题**：`06-database-design.md:598-602` 规定 `fail` 为“最后一条 assistant 记录缺失或存在未恢复的致命错误”，`partial` 仅为 `is_error=true`。当前实现把“有 assistant 但会话未正常收尾”误判为正常；在会话列表和问题筛选中会出现错误状态。

**预判**：在规范化结果中增加隐私安全的 `ended_with_assistant` 或等价终态标记，由 assembler 统一判定；增加 user→assistant→user 和致命错误测试。若 provider 无法可靠表达“未恢复致命错误”，应在 Agent Note 明示能力边界，不能静默把规则缩成零消息。

**结论**：已修复（2026-10-25）。规范化结果记录最后会话角色与未恢复的 provider API 错误；assembler 在最后一条不是 assistant、或错误未被后续成功 assistant 恢复时判 `fail`，普通 `is_error` 仍判 `partial`。

### D3 重复父 tool-use id 会静默生成双胞胎边

**位置**：`apps/api/app/service/acquisition/agent_tree.py:361-379`、`509-533`

**现象**：构造 main 中两个事件共用 `dup`，两个 child 都声明 `toolUseId=dup` 时，assembler 只记录一条 `DUPLICATE_TOOL_USE_ID`，随后把两个 child 都挂到同一 owner，并都使用最后一次 `dup` 事件。两个 child 本身没有歧义警告。

**问题**：调用 id 本应唯一；一条父事件被两个 Agent 共同消费时，后端无法知道哪条边才是真实调用。数据库仍可接受结果，后续问题卡锚点 `eventIndex` 也可能落到错误兄弟。

**预判**：当前真实数据未复现，影响为 P2。最小方案是把重复 id 的事件索引标为 ambiguous，对依赖它的 child 发稳定警告并降级 main，或拒绝该 root；至少应记录 child id，而不只把警告记在事件 owner 上。

**结论**：已修复（2026-10-25）。重复父调用 id 被标记为 ambiguous；依赖该 id 的每个 child 分别降级到 main，并各自获得唯一合成锚点与 `AMBIGUOUS_PARENT_TOOL_USE_ID`，不再形成共享歧义边。

### D4 synthetic workflow 行的节点 ID 与 assembler 输出不一致

**位置**：`fixtures/m2-synthetic/corpus.json:134-146`、`apps/api/tests/m2-04-agent-tree/test_agent_tree.py:318-359`

**现象**：manifest 声明 Workflow 节点 `wf-s2-0001`，assembler 对同一 root/tool call 生成 `wf_9e88822acbfcd60c0837bf523793af78`。golden 测试在 `test_agent_tree.py:331` 主动排除 manifest 的所有 workflow 行，再只断言“Workflow 节点数为 1”，因此看起来通过。

**问题**：m2-01 的 seed 当前会把 `wf-s2-0001` 写入真实 `agents` 表，而 m2-04 的 canonical tree 会生成不同 ID。m2-05 做删除重写前，fixture、manifest 与 assembler 是三个不一致的事实源；测试名“reconciled”与实际断言不符。

**预判**：实际数据没有 workflow，所以不影响当前本地树；但会削弱 synthetic golden 对 Workflow 的结构保障。修复可让 manifest 不手写派生 workflow 行，或把 manifest 行视为输入并由 assembler 回填稳定 ID，同时断言节点 ID、parent 与 toolUseId 一致。

**结论**：已修复（2026-10-25）。synthetic manifest 改用 assembler 的稳定 Workflow id，worker parent 同步；golden 不再排除 Workflow 行，并逐项断言 id、parent、toolUseId。

## §9 文件级代码分析

### `apps/api/app/service/acquisition/agent_tree.py`（A）

职责：把归一化 transcript 投影为扁平 Agent 节点，解析父链，生成 Workflow 合成节点并聚合会话统计。

关键依赖：只依赖标准库与 m2-03 的只读结果，没有 FastAPI、数据库或文件系统耦合。这使树算法可在 CI 中用纯对象稳定测试。

实现思路：

```text
group by root
  → validate one main / unique node ids
  → index trigger tool ids
  → synthesize workflow nodes
  → attach transcript subagents
  → detect cycle/unreachable
  → canonical order
  → aggregate session stats
```

检视发现：D1、D2、D3。未发现消息正文泄漏；`agent_meta` 仅作为持久化契约保留，未进入告警或聚合 CLI。

### `apps/api/app/service/acquisition/normalize.py`（M）

职责：m2-03 normalizer 增加 transcript 首末有效时间，供树聚合会话时间。

变更核心：每条有效 JSON record 的时间戳进入 `observed_timestamps`，最后以 min/max 写入 `started_at/ended_at`。这样 assistant-only 会话仍有可落库边界。

检视发现：这个变更没有引入正文持久化；时间戳仍统一为 Asia/Shanghai。D2 的“最后 assistant”需要更明确终态事实，目前只靠 messages 数量无法判断。

### `apps/api/app/service/acquisition/local_sessions.py`（M）

职责：复用本地扫描和 normalizer 输出，提供 `assemble_local_sessions` 聚合入口。

实现思路：本地目录 → `ParsedTranscript[]` → `assemble_agent_trees` → `AgentTreeAggregate`，不写数据库、不输出路径或 prompt。

检视发现：本地实测 4 roots / 66 nodes / 62 subagents，与报告一致；聚合 CLI 不暴露具体标题或正文。

### `apps/api/app/cli.py`（M）

职责：增加 `tree-local` 子命令并输出 `asdict(AgentTreeAggregate)`。

检视发现：继续使用 `_absolute_path_without_resolving_symlinks`，避免 symlink source 被提前解析；错误仅输出稳定文本。

### `scripts/local-sessions.mjs`（M）

职责：把 `pnpm data:tree:sessions` 转发到 Python CLI。

检视发现：命令映射简单、退出码透传；没有 shell 拼接敏感参数。

### `apps/api/tests/m2-04-agent-tree/test_agent_tree.py`（A）

职责：覆盖 nested、Workflow、forked skill、teammate、缺父、环、确定性排序、隐私和 synthetic golden。

检视发现：测试只检查 synthetic 事件存在，没有检查 child 与新事件的配对和 offset，导致 D1 漏网；golden 排除 manifest workflow 行，导致 D4 漏网；状态只覆盖零消息 fail，未覆盖最后 assistant 缺失。测试注入的 `PRIVATE_*` 文本和告警脱敏断言有效。
