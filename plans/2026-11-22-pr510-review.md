## §1 一页速览

一句话：agent 不再直接改文件，而是交一张可审计的「点菜单」（`EditPlan`）——菜单说清改哪个文件、锚哪段文本、换成什么、为什么；一个确定性厨师（`apply_edit_plan`）按单、按序、每步重读食材下锅，失败就记一笔继续；最后用「出菜照片」（`git diff`）而不是菜单来证明菜真的变了；`PatchBundle` 是能一次端多盘菜的托盘，而 `Harness-Patch-Hash` 是托盘编号，单盘时沿用旧编号以保住幂等。

比喻：这像餐厅后厨的「点菜单 + 出菜照片」。服务员（agent）不进厨房，只在单子上写「宫保鸡丁：把 30 秒改成 120 秒，理由是该桌三次超时」；厨师（applier）按单子顺序做，每做一步都重新看一眼盘里现在是什么（所以第二步能看见第一步的结果）；改菜用「新盘子装好再替换旧盘子」（原子写），做坏一步不会留下半盘菜。店长验收不看单子，只看照片（`git diff`）——单子可以吹牛，照片不会。托盘（`PatchBundle`）允许一次端多盘，编号仍是旧托盘号，所以老订单还能对上。

## §2 架构导览

### 2.1 四层与依赖方向

这一层刻意做成四个可独立测试的同心环：

1. **契约层** `edits.py:118-197`：只依赖 `pydantic` 与 stdlib，import 面没有任何 `app.*`（`edits.py:24-43`）。因此 bugfix-21 的 agent-edit source、以及 submission 通道，都能直接复用它而不会把 service 层拖进来。
2. **应用层** `edits.py:558-681`：纯文本 + 文件系统，不认识 git、不认识 provider、不认识 bundle。它唯一的输出是 `EditApplication`（改了哪些文件 + 每条状态）。
3. **bundle 层** `patch_source.py:34-93`：service 层的值对象，依赖 `edits.EditPlan` 与 `workspace.Patch`。它把「一次改动的多文件」与「审计意图 + 逐条报告」装在一起。
4. **提交层** `workspace.py:347-488`：`third_party_api` 不知道 `PatchBundle` 的具体类型，只认识结构性 Protocol `CandidateBundle`（`workspace.py:124-140`，只要 `files` 与 `sha256`）。这避免了 `third_party_api → service` 的反向依赖，是本 PR 最值得记的结构决策。

`_SinglePatchBundle`（`workspace.py:143-156`）是让 legacy 路径复用新原语的适配器：它把单个 `Patch` 冒充成 bundle，`sha256` 直接委托给 `Patch.sha256`，所以旧 trailer 的字节序列不变。

产品接线的事实：`apply_edit_plan`、`build_bundle`、`create_candidate_bundle` 在 `apps/api/app` 里**都没有调用方**（只有 `__init__` 导出与测试）。引擎仍走 `patch_source.build()` → `git_candidate.py:258` 的 `create_candidate`。所以本 PR 交付的是「零件与接缝」，不是「已通电的回路」；这与 issue 的「只做机械组件」边界一致。

### 2.2 `EditOp` 的字段矩阵

四个 op 的必填/禁用关系全部压在 Pydantic 上（`edits.py:157-171`）：`append` 禁 `target`、要 `content`；`insert_after` / `replace` 要 `target` + `content`；`delete` 要 `target`、禁 `content`；`rationale` 一律非空。`content` 行数上限在字段校验器（`edits.py:149-155`），预算在计划校验器（`edits.py:190-197`）。这意味着「形状不对」在模型层就死掉，应用器只需要防「绕过模型构造」的路径（`_coerce_edit`，`edits.py:290-310`）——这个双重防御是刻意的，测试里 `model_construct` 的用例占了很大篇幅。

### 2.3 路径安全三道闸

第一道在模型里：`_safe_relative_path`（`edits.py:88-115`）拒绝空、首尾空白、NUL、反斜杠、盘符前缀、绝对路径、非规范 POSIX（`./a`、`a//b`）、`.`/`..`/空段，以及**任意段**命中 `.git` / `.harness-evolution`（大小写折叠，`edits.py:79-85`）。

第二道在应用时：`_load_target`（`edits.py:355-436`）重新调用同一个函数，所以 `model_construct` 出来的恶意 `EditOp` 也过不去；再加 `allowed_paths` 的词法匹配。

第三道在解析后：`destination.resolve()` 后要求仍在 workspace 内、且**解析后的相对路径**也不含保护目录、也满足 `allowed_paths`（`edits.py:375-411`）。这堵的是「工作区内的符号链接把写操作带出 scope」——测试 `test_symlink_escape_is_an_error`、`test_symlink_into_a_protected_directory_is_an_error`、`test_symlink_outside_allowed_paths_is_an_error` 三条各自钉住一种逃逸。

一个细节：写盘用的是解析后的 `resolved` 路径（`edits.py:614`、`:628`），所以「经符号链接编辑」是 write-through 语义（改的是链接目标），但报告里记的是 plan 里的词法路径（`edits.py:629`）。这在 git 眼里会出现「报告说改了 `alias.md`、diff 说改了 `real.md`」的错位，见 §9。

### 2.4 应用循环：三种状态与预算

`apply_edit_plan`（`edits.py:558-681`）的骨架是「先做四条全局闸，再逐条 try」：

- 全局闸：workspace 必须绝对路径且存在、`edit_budget` 非负（`edits.py:577-583`）；`limit = min(edit_budget, EDIT_BUDGET)`（`:584`），所以调用方只能收紧、不能放宽模块上限。
- 逐条：`_coerce_edit` → `_load_target` → `_apply_one` → 内容真的变了才 `_atomic_write` 并记入 `changed`（`:612-637`）。
- 状态映射：文件/锚不存在 → `skipped_anchor_missing`（`_AnchorMissing`，`:638-647`）；多义锚、越界、非法编辑、I/O 失败 → `error`（`:648-674`）；超出预算的条目在循环顶部直接记 `error` 并跳过（`:591-611`）。
- 聚合：`files` 是真正变了的文件排序元组，`skipped` 是所有非 `applied` 的条目（`:676-681`）。

注意「applied」不等于「文件变了」：`replace` 的 content 与 target 相同时仍报 `applied`，但不会进 `files`（测试 `:693-706`、我的独立探针）。这个区分对下游很重要——bugfix-21 若按 `files` 建 bundle，会得到空文件集。

### 2.5 `PatchBundle`：兼容 hash 与排序

`PatchBundle`（`patch_source.py:34-93`）是 frozen dataclass，`__post_init__` 做四件事：非空、note 非空、`note == intent.summary`（防止提交信息与审计意图漂移）、按路径排序并拒绝重复（`:59-72`）。

`sha256`（`:74-93`）分两支：单文件直接返回 `Patch.sha256`（`file + \0 + 换行连接的行`），多文件则对排序后的每个 `(path, content)` 依次 update `path \0 content \0`。排序保证与入参顺序无关，单文件分支保证旧 trailer 逐字节兼容。兼容是硬要求：`Harness-Patch-Hash` 是「worker 重启后复用已提交 commit」的幂等键（`workspace.py:402-425`），改了格式会让在途 run 断掉。

### 2.6 提交层：结构性接缝、保护路径与真值

`create_candidate_bundle`（`workspace.py:347-488`）把旧 `create_candidate` 的十步流程原样保留，只把「一个 patch」换成「一组 stageable 文件」：

- `_stageable_files`（`:490-520`）先排序、去重，再逐个过 `_validated_patch_path`（`:1790-1814`：规范相对 POSIX、无 NUL/反斜杠/盘符、非 `.git`），最后按 `allow_protected_paths` 决定 `.harness-evolution` 是放行还是报错——**不静默丢弃**是这里的设计要点：调用方请求了文件却因保护规则没进提交，是最难查的错。
- 一次 `git add -- <paths>`（`:446-454`）而不是逐个 add；commit 之后 `git rev-parse HEAD` 取真实提交。
- `_candidate_diff`（`:523-543`）用 `git diff --no-color --no-ext-diff --src-prefix=a/ --dst-prefix=b/ <commit>^ <commit>` 取真值，回填 `CandidateWorkspace.unified_diff`（`:120`）。
- 重放分支（`:395-431`）要求「同 parent + 同 message + 同 trailer hash」三者同时成立才复用，否则删掉旧候选分支重建。

`.git` 的拒绝是双层的：`_validated_patch_path` 在写盘前就拒绝（`:1808-1812`），`_stageable_files` 在 add 前再拒绝一次；而 `.harness-evolution` 只由 `_stageable_files` 管，`_write_patch` 本身不拦——因为 legacy placeholder 确实要写那个目录。

### 2.7 支撑件

- `_compile_glob`（`edits.py:313-335`）：手写 POSIX glob → regex，`**` 可跨 `/`、`*` 不跨、`?` 单个非 `/`，并 `lru_cache`。它只服务 `allowed_paths`，所以不需要完整 glob 语义（没有字符类、没有转义），这与「路径 scope 是 harness 侧约定」的定位一致。
- `_validation_detail`（`:268-274`）：只取 `loc` 与 `msg`，`include_input=False`，避免把 agent 写的内容回显进错误；总长 1000 字符封顶。
- `_io_detail`（`:277-279`）：只留 `strerror`，不泄露 workspace 绝对路径。
- `_FULL_DIGEST`（`workspace.py:1840`）：bundle hash 必须是 64 位小写 hex，防止自定义 `CandidateBundle` 把 `refs/...` 之类的字符串塞进 trailer。

## §3 数据流走查

一条主线（今天可达的部分实线，bugfix-21 的部分虚线）：

1. **agent 写计划**。按设计，agent 在 `<workspace>/.harness-evolution/edits.json5` 写下 `{summary, edits:[{op,file,target?,content?,rationale}]}`（07 §5.5.4）。这一步在本 PR 之外（submission 通道由 #508 提供）。
2. **收货与盖章**。通道把字面量解析成对象，交给 `EditPlan.model_validate`：四 op 字段矩阵、`summary` 非空、预算 ≤ 8、每条 `content` ≤ 400 行、路径必须是规范相对 POSIX 且不在保护目录（`edits.py:118-197`）。任何一条不满足，agent 拿到的是 Pydantic 的字段级错误，而不是应用器的文件级错误。
3. **应用**。`apply_edit_plan(plan, workspace=<绝对路径>, allowed_paths=(...))`（`edits.py:558`）。对第 i 条：重新校验 → 读当前文件（`:421-422`，`newline=""` 保留 CRLF）→ 作用域与保护目录复查 → 执行纯文本操作 → 变化才原子写。第 i+1 条看到的是第 i 条写后的文本（`:590-637`）。
4. **真实输入输出**。我用一个真实 git 仓库跑了四 op（见 §1）：`# Doc\n\nalpha\nbeta\n` 经 `insert_after alpha`、`delete beta\n`、`append tail` 变成 `# Doc\n\nalpha\ninserted\ntail\n`；`config.json` 的 `"timeout": 30` 被替换成 `120`。同一 plan 在另一个独立仓库重放，两者 `git diff` 都是 311 字节且逐字节相同。
5. **报告**。`EditApplication` 给出 `files=('config.json', 'docs/doc.md')`、每条 `applied`（`edits.py:676-681`）。若某条锚缺失，它记 `skipped_anchor_missing` 并继续；若锚多义，记 `error` 并继续；若写盘失败，记 `error` 并继续。整体没有「回滚到计划前」的语义——原子写只保证单文件不半写。
6. **组 bundle**。agent-edit source（bugfix-21）会把 `files` 的最终内容读成 `Patch`，连同 `plan` 与 `report` 装进 `PatchBundle(files=(...), note=plan.summary, intent=plan, report=application.report)`（`patch_source.py:34-57`）。`note == intent.summary` 由 `__post_init__` 强制（`:65-66`），所以提交信息与审计意图不能各说各话。
7. **提交**。`create_candidate_bundle`（`workspace.py:347`）校验 bundle hash 形如 64 hex、筛 stageable 文件、`git switch` 到 run 分支、建候选分支、逐文件 `_write_patch`（append 或 overwrite，`:1631-1652`）、一次 `git add`、commit、取 `git diff`。trailer 写 `Harness-Patch-Hash: sha256:<bundle.sha256>`。
8. **重放**。worker 重启后同 base + 同 message + 同 hash → 复用已有 commit（`:395-431`），并重新收集同一个 `unified_diff`。注意：复用判定读的是**新** message 的 trailer（`:410`），但因为上一行已经要求新旧 message 全等，这一步在逻辑上是冗余的。
9. **真值对照**。设计说「意图态与结果态合一」：`intent` 是计划、`report` 是逐条执行结果、`unified_diff` 是 git 真值。三者的差异（计划说改了 A，diff 只有 B）本身就是审计信号。本 PR 把三个字段都备好了，但还没有代码去比对它们——那是 bugfix-21 的闭环。

一个今天就能观察到的断点：`create_candidate`（legacy）现在也会收集 `unified_diff`，但引擎 `git_candidate.py:258` 只读 `candidate.ref/commit/message`，所以这份 diff 被原地丢弃；这就是 §6 点 5 的成本来源。

## §6 讨论点

> 本节保留检视时的现象与实测；每条的**结论**是 2026-11-22 维护者裁决。FIX 1-4 已随本 PR 的 fix 提交落地并带回归用例，其余以「推迟到 bugfix-21」或「记录」留档，不再重开。

### 讨论点 1：`Patch.sha256` 不覆盖 `overwrite`，单文件 bundle 原样继承

**位置**：`apps/api/app/third_party_api/git/workspace.py:94-101`（`Patch.sha256`）、`:154-155`（`_SinglePatchBundle.sha256`）、`apps/api/app/service/evolution/patch_source.py:85-86`（单文件分支）；写盘语义在 `workspace.py:1631-1652`

**现象**：实测 `Patch(file="a.md", lines=("b",), overwrite=False).sha256 == Patch(..., overwrite=True).sha256`（同为 `2e0d0bf2…`），但同一份基线文件 `existing\n` 上，append 写出 `existing\nb\n`、overwrite 写出 `b\n`。`PatchBundle` 单文件分支把这个 hash 原样当 bundle hash，`create_candidate_bundle` 再把它写进 `Harness-Patch-Hash` trailer。

**问题**：trailer 的用途是幂等复用——「同 base + 同 message + 同 hash 就复用已有 commit」（`workspace.py:395-431`）。hash 不区分 append/overwrite，意味着两个**内容不同**的 patch 会共享同一个身份；只要 message 也相同（source 从 append 切到 overwrite、但 note 文案未变，或 note 只描述文件与键），重放就会拿到旧 commit，候选内容与本次 patch 不一致。PR 把「单文件 hash 逐字节兼容」定为硬要求，所以这是明确的「兼容 vs 正确」取舍，不是疏忽。

**预判**：当前无实害——placeholder 与 minimal-config 的 message 由 run/trace/note 决定，要撞上需要同时满足同 base、同文件、同 lines、同 message；bugfix-21 预计固定 `overwrite=True`。建议把 `overwrite` 纳入**新格式**（多文件分支或 `sha256:2:` 前缀），单文件 legacy 分支保持原样，这样在途 run 的幂等不断、新路径身份完整。不建议直接改 `Patch.sha256`。

**结论**：已决 2026-11-22：推迟到 bugfix-21，本 PR 不改 `Patch.sha256`（单文件 `Harness-Patch-Hash` 必须与旧 trailer 逐字节兼容，改格式会断掉在途 run 的重放幂等；`overwrite` 碰撞记录为已知取舍，由 bugfix-21 用带版本的 hash 格式纳入）。

### 讨论点 2：单条失败后继续，部分应用只有逐条报告、没有整体失败信号

**位置**：`apps/api/app/third_party_api/ai_agent/edits.py:590-681`（循环与异常分支）、`:218-240`（`EditApplication`）

**现象**：实测 10 条编辑的 plan（绕过模型）前 8 条 `applied`、后 2 条 `error`，`a.md` 停在 `base\nn0…n7\n`；另一个混合 plan 产生 `error / skipped_anchor_missing / skipped_anchor_missing`。`EditApplication` 只有 `files`（真正变了的文件）、`report`（逐条）、`skipped`（非 applied）三个面，没有 `ok`/`failed` 聚合，也没有「这次计划整体成功率」字段。

**问题**：设计明确要求「逐条 status 报告、后续编辑的锚实时复查」，所以继续执行是对的。问题在调用方：bugfix-21 若按 `files` 组 bundle 直接提交，report 里的 `error` 会被静默带过，候选 diff 少了意图中的改动，而提交信息仍写着完整的 `intent.summary`。更细一层：`files` 只说明「变了的文件」，无法区分「这个文件被部分编辑（前一条改成功、后一条失败）」与「这个文件完全没动」——前一种恰恰是最需要回喂给模型的状态。

**预判**：不必在本 PR 改 applier；建议在 `EditApplication` 上加 `failed` 聚合属性（`errors` 已存在，再加一个语义明确的布尔或 `ok` 计数），并在 bugfix-21 的 bundle 构造处定一条硬规则「`report` 里有 `error` 就拒绝提交、把 `skipped` 回喂模型」。如果维护者认为「partial 是合法结果」，至少在 Note 里写清「applied ≠ 整体成功」，别让下游误读。

**结论**：已决 2026-11-22：推迟到 bugfix-21，本 PR 不改 applier（逐条继续是设计要求，整体失败信号属于调用方契约；bugfix-21 在 bundle 构造处拒绝含 `error` 的 report、把 `skipped` 回喂模型，并在 owning Note 里写清「applied ≠ 整体成功」）。

### 讨论点 3：legacy `create_candidate` 用 `allow_protected_paths=True`，宽度按调用者身份而不是文件用途

**位置**：`apps/api/app/third_party_api/git/workspace.py:317-345`（legacy 传 True）、`:490-521`（判据只看路径）；测试 `apps/api/tests/m5-09-git-candidate/test_git_workspace.py:350-383`（参数化里 `.harness-evolution/edits.json5` + True 期望放行）

**现象**：实测 legacy `create_candidate` 能提交 `.harness-evolution/candidate-r1.md`；同时 `_stageable_files(bundle, allow_protected_paths=True)` 对**任意** `.harness-evolution/**` 都放行——测试自身就把 `.harness-evolution/edits.json5` 当作合法输入钉住了。`.git/config` 在 True/False 下都被拒。

**问题**：placeholder 需要写 `.harness-evolution/candidate-r<seq>.md` 是事实，但实现把「placeholder 需要」放宽成了「所有 legacy 单文件 patch 都可以」。minimal-config 的路径由 `_config_path` 生成（`config/...`），今天不会撞上；但这是一个按「谁在调用」授权的开关，任何未来复用 `create_candidate` 的 source 都会自动继承这个宽度。设计里 `.harness-evolution/` 是「排除在 diff scope 外」的目录，legacy 全量放行与这句话的张力值得记录。

**预判**：更窄的做法有两种——把放行限定到 placeholder 的具体模式（`candidate-r<seq>.md`），或让 source 显式声明「允许受保护路径」而 `create_candidate` 默认 False、只有 placeholder 传 True。前者更安全（连 placeholder 也只能写自己的文档），后者更通用（未来若真有 source 需要写 scratch 目录）。成本都是给 `create_candidate` 加一个参数或一次路径比对。

**结论**：已决 2026-11-22：保持现状并记录（`allow_protected_paths=True` 是 legacy placeholder 的既有兼容宽度，`create_candidate` 的 docstring 已写明它只为 placeholder 的受保护文档放行、`.git/**` 永不放行；收窄会改动 placeholder 的提交契约，不在本 PR 调整）。

### 讨论点 4：`PatchBundle.__post_init__` 静默重排 `files`

**位置**：`apps/api/app/service/evolution/patch_source.py:59-72`

**现象**：实测 `PatchBundle(files=(b, a), note="n").files == (a, b)`，入参顺序被 `sorted(key=patch.file)` 覆盖，随后 `object.__setattr__` 写回。docstring 称 `files` 是 "ordered set"，但实际语义是「按路径排序的 tuple」。

**问题**：调用方传进来的顺序（例如按编辑顺序、或按「先配置后文档」的叙事顺序）被静默丢弃。今天无实害：`sha256` 明确与顺序无关（`:82-83`），`CandidateWorkspace` 也不暴露文件顺序，`git add` 接受任意顺序。但如果未来 message 生成、事件 payload 或 UI 展示依赖 bundle 顺序，就会得到一个「看起来有顺序、其实被重排」的字段。另一个角度：排序是确定性提交的必要条件，所以行为本身是对的，问题只在措辞与「静默」二字。

**预判**：保持排序；把 docstring 从 "ordered set" 改为 "path-sorted tuple（入参顺序不保留）"，并在 `__post_init__` 的 docstring 明说重排。若确实需要保留入参顺序，可以另加 `requested_order: tuple[str, ...]`，但不建议为假设需求扩字段。

**结论**：已决 2026-11-22：保持排序并记录（按路径排序是确定性提交与顺序无关 hash 的前提，入参顺序不保留是有意的契约；本 PR 不扩 `requested_order`，后续如需展示顺序另立需求）。

### 讨论点 5：`unified_diff` 每条 candidate 都收集，今天没有消费者

**位置**：`apps/api/app/third_party_api/git/workspace.py:523-543`（`_candidate_diff`）、`:425-431` 与 `:483-487`（两处 return 前调用）

**现象**：用计数 runner 实测，新建 candidate 共 **9 个 git 进程**：`status / switch / merge-base / rev-parse / switch / add / commit(-c ...) / rev-parse / diff`；重放路径同样 9 个、同样含 `diff`。而产品代码里唯一的调用方 `apps/api/app/service/evolution/git_candidate.py:258` 只读 `candidate.ref / commit / message`，`unified_diff` 被丢弃；`create_candidate` 的 legacy 签名也不把它交给任何人。

**问题**：每个 candidate 多一次 git 子进程，并把完整 unified diff 读进内存。小 patch 301 字节，但大改动的 diff 可能到 MB 级；在「每轮都要建 candidate」的引擎里，这是稳定的额外开销，换来的字段今天零消费者。PR 的意图是为 bugfix-21 铺路，方向可以理解，但成本落在了当下的每一条路径上。

**预判**：加 `collect_diff: bool = False`（或在 `CandidateWorkspace` 上做惰性 property），bugfix-21 需要时显式开启；legacy `create_candidate` 明确不需要，可以固定 False。若维护者认为「真值必须随候选一起产出」，就保留默认 True，但在 Note 里记下这条成本，避免以后误以为是免费字段。

**结论**：已决 2026-11-22：保留现状（issue 要求 `PatchBundle.unified_diff`，`git diff` 就是本层交付的「真值」；每候选多一次 `git diff` 子进程的成本由真值收益覆盖，不引入 `collect_diff` 开关）。

### 讨论点 6：`EditPlan.edits` 是冻结模型里的可变列表

**位置**：`apps/api/app/third_party_api/ai_agent/edits.py:174-197`（`frozen=True` + `edits: list[EditOp]`）

**现象**：实测 `plan.summary = "t"` 抛 `ValidationError`（Pydantic 的 frozen 生效），但 `plan.edits.append(...)` 成功、`len` 从 1 变 2；`hash(plan)` 抛 `TypeError: unhashable type: 'list'`。也就是说「frozen」只冻结字段绑定，不冻结列表内容。

**问题**：设计把 Pydantic 模型称为「单一事实源」，预算校验器只在构造时跑一次；构造后 append 一条新编辑可以绕过 `_validate_budget`（虽然 `apply_edit_plan` 的 `limit = min(...)` 会兜住，`_coerce_edit` 也会重新校验每一条）。所以没有安全后果，但「模型不可变」的直觉是错的，未来若有人把 `EditPlan` 当缓存键或跨线程共享，会在 `hash` 或并发修改上踩坑。

**预判**：改成 `edits: tuple[EditOp, ...]` 最直接——Pydantic 反序列化仍接受 JSON 数组并转 tuple，测试大多不用改；代价是调用方要写 tuple（或接受转换），且 `plan.edits[0] = ...` 从「静默改列表」变成「报错」。若要保持 `list`，就在 docstring 写明「frozen 是浅冻结」。

**结论**：已决 2026-11-22：接受（FIX 4），`EditPlan.edits` 改为 `tuple[EditOp, ...]`（理由：frozen 只冻结字段绑定，tuple 才让模型深度不可变、恢复可哈希并堵住构造后 append 绕过预算校验；`model_json_schema()` 仍是 JSON array，`model_validate` 仍接受列表）。回归用例见 `test_edit_plan_applier.py::test_edit_plan_edits_are_a_deeply_immutable_tuple`。

### 讨论点 7：`insert_after` 只支持单行锚，而 `replace` / `delete` 支持多行，且差异只在应用时暴露

**位置**：`apps/api/app/third_party_api/ai_agent/edits.py:157-171`（模型校验没有单行约束）、`:479-488`（应用时拒绝）、`:511-533`（`replace`/`delete` 的多行锚路径）

**现象**：实测 `EditOp(op="insert_after", target="line1\nline2", ...)` 通过 Pydantic；`apply_edit_plan` 返回 `error`「target must be a single-line substring」。同一份文件上，`replace` 的多行锚（`target="one\ntwo"`）正常 `applied`，文件变为 `ONE\nthree\n`。

**问题**：同一种「锚」在三个 op 里语义不同，但差异没有被写进模型；agent 交上来的 plan 在模型层「合法」，到应用时才被判死。设计说 Pydantic 是单一事实源，这条约束却只活在 applier（`:479-488`），与「防绕过」的防御代码混在一起。回喂给模型的是一条 `error`，而不是「`insert_after` 的 target 不能含换行」的字段级提示，重试成本更高。

**预判**：把单行检查搬进 `EditOp._validate_op_fields`（一行 `if self.op == "insert_after" and ("\n" in target or "\r" in target): raise`），applier 保留防御但变成真正的 `pragma: no cover`。另一条路是让 `insert_after` 支持多行锚，但那要重新定义「在匹配段之后」与行边界，成本明显更高，不建议为假设需求扩语义。

**结论**：已决 2026-11-22：接受（FIX 3），把单行锚约束搬进 `EditOp._validate_op_fields`（理由：同一种「锚」在三个 op 里的语义差必须在模型层暴露，坏计划在落盘前失败、回喂模型拿到字段级错误；applier 保留防御性检查，`model_construct` 绕过的路径仍记 `error`）。回归用例见 `test_insert_after_rejects_a_multiline_anchor_at_model_construction`。2026-11-25 更新：该决定已由 #599 反转——生产 run 因这条未写进 prompt 的隐藏单行规则在 patch 阶段整轮失败，锚点契约统一为「存在且唯一、可跨行」，插入点为块末行之后，上述回归用例已随之删除。

### 讨论点 8：bugfix-21 的 `.harness-evolution/edits.json5` scratch 会让 `_require_clean` 直接失败

**位置**：`apps/api/app/third_party_api/git/workspace.py:1173-1183`（`_require_clean` 用 `git status --porcelain --untracked-files=all`）；设计侧 `plans/fullstack-design/07-backend-implementation.md:838`

**现象**：在真实仓库里写 `.harness-evolution/edits.json5` 后，`git status --porcelain --untracked-files=all` 返回 `?? .harness-evolution/edits.json5`；`git check-ignore` 无输出（未忽略）；随后 `create_candidate` 在 `_require_clean` 处失败 `workspace is not clean`（stage=workspace）。注意 placeholder 的 `.harness-evolution/candidate-r1.md` 是**被提交的 tracked 文件**，不等于 scratch 会被忽略。

**问题**：按 07 §5.5.4，agent 的编辑阶段就是「在工作区里写 `edits.json5`」，然后才走 candidate 提交。本 PR 的 applier 与 stager 都排除了 `.harness-evolution`，但工作区清洁检查没有排除，三者语义不一致。结果是 bugfix-21 接上真实调用方的那一天，candidate 永远建不出来——这是本 PR 交付的接缝上的一个真实阻塞项，只是今天还没有调用方所以没暴露。

**预判**：三条修法：① `_require_clean` 加排除 pathspec（`git status --porcelain --untracked-files=all -- . **结论**：已决 2026-11-22：接受（FIX 1），`_require_clean` 过滤 `git status --porcelain --untracked-files=all` 里的 `.harness-evolution/**` 条目（理由：该目录是 agent scratch，`create_candidate_bundle` 的常规路径从不 stage 它，计入脏检查会让 bugfix-21 的编辑阶段永远建不出候选；其余任何 tracked/untracked 脏路径仍然报 `workspace is not clean`，rename 只有两侧都在 scratch 内才忽略）。回归用例见 `test_git_workspace.py::test_untracked_harness_evolution_scratch_does_not_block_a_candidate` 与 `test_modified_tracked_file_still_blocks_a_candidate`。

### 讨论点 9：`allowed_paths` 缺省是「不限制」，不是「拒绝」

**位置**：`apps/api/app/third_party_api/ai_agent/edits.py:338-352`（`:340-341 if not allowed_paths: return True`）、`:558-564`（参数默认 `()`）

**现象**：实测不传 `allowed_paths` 时，`README.md` 的编辑被 `applied`；传 `("skills/**",)` 同一条变 `error`；传 `("",)` 也 `error`（空 pattern 被跳过、无命中）。`apply_edit_plan` 的签名默认是 `()`。

**问题**：设计写「`file ∈ allowed_paths`」，实现把「不传」解释成「不限制」。这是 fail-open 默认：bugfix-21 的调用方漏传一个参数，agent 的可写面就从 `skills/**` 扩到整个工作区（只剩 `.git` 与 `.harness-evolution` 被拦）。工作区本身是隔离克隆，最坏后果是候选 diff 越界、仍会进 eval 与审计，所以不是数据安全事故；但「安全闸默认最宽」与直觉相反，而且和 `_load_target` 里两道 scope 检查的严肃程度不匹配。

**预判**：不建议直接把默认改成「拒绝一切」（大量测试与现有调用以「不传=全工作区」为前提，改动面大）。更干净的是把参数改成 `allowed_paths: tuple[str, ...] | None = None`：`None` = 显式不限制，`()` = 拒绝一切；这样语义自解释，调用方也能被类型检查提醒。退一步，至少在 docstring 里把「空 = 不限制」写成显式契约，并在 bugfix-21 的 source 里固定传入 scope。

**结论**：已决 2026-11-22：接受（FIX 2），签名改为 `allowed_paths: tuple[str, ...] | None = None`（理由：`None` = 调用方显式不收窄、`()` = 拒绝一切，scope 计算为空时 fail-closed，避免漏传参数把可写面悄悄扩到整个工作区；非空元组的 glob 语义不变）。回归用例见 `test_allowed_paths_none_means_no_narrowing_and_empty_denies` 与更新后的 `test_allowed_paths_use_posix_globs`。

## §9 文件级代码分析

### `apps/api/app/third_party_api/ai_agent/edits.py`

**职责**：把「agent 想改什么」变成 Pydantic 契约，再把契约确定性地应用到工作区文件上，产出逐条状态。**变更形态**：A，纯新增，无旧侧（`git show origin/main:…` 不存在该文件）。

**关键依赖解读**：只依赖 `pydantic` 与 stdlib（`os`、`re`、`stat`、`tempfile`、`pathlib`、`dataclasses`、`functools`、`typing`）。Pydantic 在这里是「单一事实源」：op 枚举、跨字段必填/禁用、内容行数、路径规范全部由它执行，所以 submission 通道只要 `model_validate` 就能在落盘前挡住坏计划。`tempfile.mkstemp` 与 `os.replace` 是原子写的两个原语——同一目录建临时文件，写完 `fsync`，再原子替换；比喻是「新盘子装好菜再换下旧盘子」，中途打翻也不会留下半盘。

**变更代码块分析**（纯新增，逐块讲「在做什么、为什么这么写」）：

- **常量与保护目录**（`:45-69`）。`EDIT_BUDGET=8`、`MAX_CONTENT_LINES=400`、`_PROTECTED_DIRS={".git",".harness-evolution"}` 以及折叠版。折叠是为了 macOS 的默认大小写不敏感文件系统：`.GIT` 和 `.git` 在磁盘上是同一个目录，只比对原文会漏。
- **路径校验函数**（`:72-115`）。`_require_non_blank` 只做跨字段的「非空白」；`_safe_relative_path` 是模型与 applier 共用的唯一路径判据——先拒空/空白/NUL/反斜杠/盘符，再要求 `PurePosixPath.as_posix()` 与原文逐字相等（这一条同时干掉 `./a`、`a//b`、`a/../b`、尾斜杠），最后拒保护目录。把它做成模块级函数而不是 `EditOp` 的私有方法，是为了让 `_load_target` 能对 `model_construct` 出来的对象复用同一套规则（`:363`）。
- **`EditOp`**（`:118-171`）。`extra="forbid"` 让 agent 多写字段直接失败；`file`、`rationale`、`content` 三个字段校验器，加一个 `model_validator(mode="after")` 管 op 级字段矩阵。为什么字段矩阵不拆成四个子模型：设计要的是「一个封闭集合、一处可读的规则表」，四个子类会让 `EditPlan.edits` 的联合类型与错误定位复杂化。
- **`EditPlan`**（`:174-197`）。`summary` 非空 + `edits` 列表 + 预算 validator。预算只在构造时检查；运行时的 `min(edit_budget, EDIT_BUDGET)` 是第二道，专门兜 `model_construct`。
- **状态与结果类型**（`:200-240`）。`EditStatus` 用 `__post_init__` 拒绝负 index 与未知 status（frozen dataclass 的校验放这里）；`EditApplication` 三个字段 + 两个便捷 property。为什么不是 Pydantic：这层刻意不引入第二套校验语义，保持「值对象只装数据」的边界，测试 `:488-498` 用 `ValueError` 钉住。
- **错误类型**（`:243-260`）。`EditPlanError` 的 message 格式在 docstring 里钉死为 `edits[<index>] (file=<file>, op=<op>): <constraint>`——这是回喂模型时「可定位、不回显计划内容」的关键；`_AnchorMissing` 是它的子类，只用来把「锚/文件不存在」映射到 `skipped_anchor_missing` 而不是 `error`。
- **错误渲染**（`:263-287`）。`_validation_detail` 不回声输入、按 `loc: msg` 拼、1000 字符封顶；`_io_detail` 只留 `strerror` 不泄露绝对路径；`_raw_field` 兜住「连字段都取不到」的坏对象。
- **`_coerce_edit`**（`:290-310`）。`isinstance(raw, EditOp)` 时不直接信任，而是 `model_dump()` 后重新 `model_validate`——因为 `model_construct` 出来的实例绕过了所有校验器。这是「Pydantic 是事实源」在运行时的补丁，测试 `:720-746` 用未知 op 与空 content 两条钉住。
- **glob 与 scope**（`:313-352`）。`_compile_glob` 手写翻译，`**` 跨分隔符、`*` 不跨、`?` 单个非 `/`；`_matches_allowed` 去掉 `./` 前缀、空 pattern 跳过、`x/**` 额外匹配目录 `x` 本身，最后 `fullmatch`。没有复用 `fnmatch`，因为它的 `*` 会跨 `/`；手写翻译让「`**` 跨、`*` 不跨」完全由本文件定义。
- **`_load_target`**（`:355-436`）。四段：词法路径 + 词法 scope → `resolve()` 并 `relative_to(root)` → 解析后保护目录 + 解析后 scope → 存在性、regular file、UTF-8 读取。`newline=""` 是刻意的：保留 CRLF，避免 Python 的换行翻译把文件悄悄改写。所有异常都折成带 index/file/op 的 `EditPlanError`。
- **文本操作**（`:439-533`）。`_append_text` 保留原字节、在边界补一个 `\n`、把 content 自己的尾随换行折成一个；`_insert_after_text` 用 `splitlines(keepends=True)` 找唯一一行、继承该行的行尾（CRLF 或 LF）、必要时先给末行补行尾；`_apply_one` 先做 op 分派，再统一做「occurrences == 0 → skip、> 1 → error」的锚检查。`insert_after` 额外拒多行 target（见讨论点 7）。
- **`_atomic_write`**（`:536-555`）。同目录 `mkstemp` → 写入 → `flush` → `fsync` → 复制原文件 mode → `os.replace`；任何异常都先删临时文件。为什么复制 mode：配置/脚本类文件的执行位与权限不该被一次编辑悄悄改成 `0600`（`mkstemp` 的默认）。
- **`apply_edit_plan`**（`:558-681`）。全局闸 → `limit` → 逐条 try → 三条 except 映射 → 聚合。实现思路三行：**先窄后宽**（模型能挡的绝不留到运行时，运行时能挡的绝不留给 git）；**每条重读**（顺序语义的唯一实现方式）；**单文件原子、整体不回滚**（失败条目记录后继续，文件停在上一次一致状态）。

**检视发现**：

1. **`allowed_paths` 默认 fail-open**（中，`:340-341`、`:562`）：见讨论点 9。修法：`None` 与 `()` 分开语义，或在 docstring 显式化。
2. **`insert_after` 单行约束只活在 applier**（低，`:479-488` vs `:157-171`）：见讨论点 7。修法：一行校验器搬进模型。（2026-11-25 更新：#599 已删除该约束本身，见讨论点 7 结论。）
3. **「已应用但无改动」没有下游表示**（低，前瞻，`:627-637`、`:676-681`）：实测 content == target 时 `applied`、`files=()`；`PatchBundle` 拒绝空 `files`，把这种文件塞进非空 bundle 也会让 `git commit` 失败（我的独立探针）。bugfix-21 需要一个「本轮无改动」分支（跳过提交 / 记 `noop` 状态），否则「已经修好了」会被当成系统错误。
4. **符号链接 write-through 的路径错位**（低，`:614`、`:628-629`）：写盘用解析后的 `resolved`、`changed` 与报告用词法 `edit.file`；实测 `alias.md -> real.md` 编辑后 `files=('alias.md',)` 而内容变的是 `real.md`。对 `git diff` 无影响（git 看到真实文件），但审计时「报告路径」与「diff 路径」会不一致。若认为这是问题，修法是报告解析后的相对路径，或显式拒绝符号链接目标。
5. **无实害但值得知道**：`EditPlan` 的 frozen 是浅冻结（讨论点 6）；`_validation_detail` 截断可能切在错误条目中间（1000 字符、影响小）；`insert_after` 的 `text.count(target)` 与逐行查找在「同一行出现两次」时会判多义（实测 `x\nx\n` 正确判 ambiguous），语义自洽。

### `apps/api/app/service/evolution/patch_source.py`

**职责**：把「一次候选改动」从单个 `Patch` 升级成 `PatchBundle`，并给旧 source 一个零改动的 `build_bundle()` 默认实现。**变更形态**：M，+127/−4；旧侧是「只有 `Patch`、没有 bundle 概念」的版本。

**变更代码块分析**：

- **新增 `PatchBundle`**（`:34-93`）。旧侧完全没有这个类型；新类型把 `files / note / intent / report / unified_diff` 装在一起，`__post_init__` 做四道形状校验 + 排序，`sha256` 做兼容哈希。为什么 `note == intent.summary` 要硬校验：提交信息是给人看的「改动」段，`intent.summary` 是审计意图；两者允许各写各的，就会出现「提交说 A、计划说 B」的漂移。
- **`PatchSource` 协议加 `build_bundle`**（`:96-125`）。旧侧只有 `build/change_note`；新方法默认由 `_DefaultBundleSource` 提供，所以既有实现不需要改一行。
- **`_PatchBuilder` + `build_default_bundle` + `_DefaultBundleSource`**（`:128-168`）。三件套的分工：Protocol 描述「旧 source 有什么」，函数做「调用两次旧方法并包成 bundle」，mixin 把函数挂成方法。为什么用 mixin 而不是给 `PatchSource` 加默认实现：Protocol 不能有实现，而让每个 source 自己写一遍 `build_bundle` 就是重复。
- **两个旧 source 的基类变化**（`:171`、`:230`）。`class PlaceholderPatchSource:` → `class PlaceholderPatchSource(_DefaultBundleSource):`，`MinimalConfigPatchSource` 同理；方法体一字未动。这是「零改动」在 diff 上的样子。
- **工厂加保留分支**（`:339-342`）。旧侧是「未知 mode 一律 `ConfigError`」；新侧先识别 `agent-edit` 并给出指向 bugfix-21 的明确信息，其余未知 mode 仍走原错误。

**检视发现**：

1. **`PatchBundle.sha256` 单文件分支继承 `Patch.sha256` 的 `overwrite` 盲区**（中，`:85-86`）：见讨论点 1。
2. **`PATCH_SOURCE_MODES` 不是模式校验的事实源**（低，`:26` vs `apps/api/app/config.py:322`）：`config.py` 的 `validate_patch_source_mode` 仍写着 `{"placeholder", "minimal-config"}`，所以 `HE_PATCH_SOURCE_MODE=agent-edit` 在 Settings 层就报「must be placeholder or minimal-config」，到不了工厂那句「reserved for bugfix-21」。run 级 `eval_config["patchMode"]` 与测试里的 `fallback_mode=` 能到工厂。bugfix-21 落地时必须同时改 `config.py`，否则新模式的 env 路由永远打不开；在那之前，两处列表的漂移是一个「谁会先改」的隐患。
3. **`PatchBundle` 的 `report` 与 `unified_diff` 没有交叉校验**（无实害，`:56-57`）：bundle 可以带一份 `report` 说 8 条 applied、`files` 却只有一个；这层不做一致性检查是合理的（真值由 git 给），但审计方要自己比对。
4. **无实害**：`build_default_bundle` 调用 `build()` 与 `change_note()` 两次，minimal-config 的 `_derive_change` 会被算两次（纯函数，成本可忽略）；`_DefaultBundleSource` 只提供 `build_bundle`，`isinstance(source, PatchSource)` 依赖子类同时继承 `build/change_note`，测试 `:868` 钉住了。

### `apps/api/app/third_party_api/git/workspace.py`

**职责**：在隔离工作区里创建候选提交；本 PR 把「单文件 patch」升级为「多文件 bundle」，并把真实 `git diff` 回填到候选快照。**变更形态**：M，+207/−11。

**旧 vs 新对照（`create_candidate`）**：

旧（`origin/main:apps/api/app/third_party_api/git/workspace.py`，`create_candidate` 主体，节选）：

```python

            if (
```

新（`workspace.py:317-345`）：

```python
    async def create_candidate(self, prepared, *, run_branch, candidate_ref, patch, message, ...):
        """Create one candidate commit from a single patch.

        Delegates to :meth:`create_candidate_bundle` with a one-file bundle so
        the multi-file and single-file paths share commit, trailer, reuse, and
        diff logic. Only ``.harness-evolution/**`` stays stageable here because
        the legacy placeholder source intentionally commits a document under
        that directory; ``.git/**`` is never stageable, even on this path.
        """
        return await self.create_candidate_bundle(
            prepared,
            run_branch=run_branch,
            candidate_ref=candidate_ref,
            bundle=_SinglePatchBundle(patch),
            message=message,
            expected_run_id=expected_run_id,
            reset_workspace=reset_workspace,
            allow_protected_paths=True,
        )
```

读法：旧方法是「一份完整流程，只有一个 patch」，新方法是「把 patch 装进适配器，交给 bundle 流程」。收益是提交、trailer、复用、diff 四条逻辑只有一份实现；代价是 legacy 路径现在也会收集 diff（讨论点 5），并且 `allow_protected_paths=True` 的宽度问题被固化（讨论点 3）。

**新增 `create_candidate_bundle`**（`:347-488`）：十步流程与旧方法一一对应，差异只有三处——`files = self._stageable_files(...)`、`for patch in files: self._write_patch(...)`、`("git", "add", "--", *(patch.file for patch in files))`。`patch_hash` 在筛选文件与创建候选分支之前先做 `_FULL_DIGEST` 校验（`:389-391`），这是防止自定义 `CandidateBundle` 把任意字符串写进 trailer 的闸。

**新增 `_stageable_files`**（`:490-520`）：排序 → 去重 → 逐路径 `_validated_patch_path` → 保护路径判定（`.harness-evolution` 只在 `allow_protected_paths` 时放行，`.git` 永不放行）→ 返回 tuple。为什么「报错而不是丢弃」：调用方请求了文件，若因保护规则被静默过滤，它会以为提交成功；报错至少让调用方看见。

**新增 `_candidate_diff`**（`:523-543`）：`git diff --no-color --no-ext-diff --src-prefix=a/ --dst-prefix=b/ <commit>^ <commit>`。`--no-ext-diff` 禁用外部 diff 驱动（目标仓库可能配了会卡住的工具），两个 prefix 保证输出与常规 patch 一致。

**新增路径校验**（`:1790-1828`）：`_validated_patch_path` 是 `_write_patch` 与 `_stageable_files` 共用的判据，覆盖 NUL、反斜杠、盘符、非规范 POSIX、绝对路径、`.`/`..`/空段、`.git`；`_is_git_path` / `_is_harness_evolution_path` 都按段折叠比对。

**检视发现**：

1. **legacy 全量放行 `.harness-evolution`**（中，`:344` / `:512-519`）：见讨论点 3。
2. **`unified_diff` 无条件收集**（低，`:425-431`、`:483-487`）：见讨论点 5；实测每候选 9 个 git 进程，含 `diff`。
3. **`_stageable_files` 在切分支之后才校验**（低，`:390-393`）：`files = ...` 位于 `git switch run_branch` 之后，所以一个非法 bundle 会先切换分支再报错。无数据损坏（工作区无改动），但失败路径留下了「分支已切」的副作用；若想更干净，可以把 `patch_hash` 与 `_stageable_files` 提到所有 git 操作之前。
4. **无实害**：复用分支的 trailer 检查（`:410`）在「新旧 message 全等」的前提下是冗余的；`CandidateWorkspace.unified_diff` 的默认空串让旧构造继续可用（`:120`）；`_write_patch` 的 `_validated_patch_path` 替换了原来的内联检查（`:1631-1652`），行为只增不减。
