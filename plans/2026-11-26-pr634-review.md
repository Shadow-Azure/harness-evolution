## 2. 架构导览

### 2.1 服务端：列表响应多一条只读通道

`TargetOverviewDisabledItem`（`apps/api/app/service/overview/target_schemas.py:90`）只有 `targetId/objectType/objectName/attributionSkillName/defaultRef`，没有统计字段；`TargetOverviewListResponse.disabled`（`:110`）默认空列表，因此旧捕获和旧客户端仍能解析。

`TargetOverviewService.list_targets()`（`apps/api/app/service/overview/targets.py:627`）仍是原流程：`_analyses()` 只取启用对象、算汇总、排序分页。新增的 `_disabled_targets()`（`:672`）用同一仓储再读一次同空间全部对象，过滤 `enabled=false` 后按对象名、类型、id 排序。它不调用 matcher、不解析版本、不读内容，因此不会把停用对象带进趋势或潜在 case 计算。

关键点：`disabled` 与分页解耦，每页都返回该空间全量停用对象；`summary`、`items`、`total` 完全没改口径。

### 2.2 Web：两条数据通道而不是一份合并列表

`TargetsOverview` 从查询结果分出 `disabledItems`（`apps/web/src/pages/overview/components/TargetsOverview.vue:99`），只传给 `TargetSideList`，不并入 `targetItems`。因此所有消费 `targetItems` 的地方——筛选选项、趋势、两块分布、`TargetDetailCard`、`PotentialCaseTable`——天然看不到停用对象，无需逐个加过滤。

`TargetSideList` 把两类行折成同一种 `SideRow`（`TargetSideList.vue:16`、`:78`）：启用行带统计字段，停用行统计字段为 0；`rows` 顺序固定为“启用行在前、停用行在后”，共同按 5 条分页。分页文案由 `pagerInfo`（`:120`）生成，显示总数与“N 个已停用”。`showsDisabledDivider()`（`:131`）只在可见页里第一张停用行走过时插入分组标题。

### 2.3 启用：复用既有写入，不在前端拼新协议

`enableTarget()`（`TargetsOverview.vue:397`）先从 `useEvolutionTargets()` 的配置集合按 id 找完整 `EvolutionTarget`；配置查询尚未完成时先 `refetch()`，避免用户刚进页面点启用得到“配置未加载”。随后用当前配置组装 `EvolutionTargetWrite`（`enabled=true`，`attributionPackageId` 原样带上），调用既有 `updateTarget`。服务端仍执行仓库/ref 校验和 `enabled` 绑定副作用；成功后 `invalidateOverview()` 并回到第 1 页，失败只显示服务端错误，不做本地乐观删除。

## 3. 数据流走查

1. 浏览器请求 `GET /api/workspaces/ws-default/overview/targets?from=…&to=…&page=1&pageSize=50`。
2. `list_targets()` 用启用对象跑 matcher，得到 `summary/items/total`；再读同空间停用对象，写 `disabled`。
3. `TargetsOverview` 渲染统计条、趋势、分布和详情卡时只读 `targetItems`；右栏拿到 `items` 与 `disabled`。
4. 右栏第 2 页：第一行是最后一个启用对象，随后出现“已停用对象 · 仅展示，不参与统计”与灰色卡片；卡片没有选中按钮，只有启用/编辑/移除。
5. 点击启用：前端组装完整写入 → `PUT /api/evolution/targets/{id}` → 服务端校验并置 `enabled=true` → 前端失效总览查询 → 统计对象数 +1、停用分组消失、对象按可进化顺序回到启用列表。
6. 编辑沿用 `TargetFormDialog`；移除沿用既有确认框与删除 API。

## 6. 讨论点

### 6.1 右栏分页总数包含停用对象，而顶部统计与 API `total` 不含

- 位置：`apps/web/src/pages/overview/components/TargetSideList.vue:120`、`apps/api/app/service/overview/targets.py:672`
- 现象：`pagerInfo` 用 `rows.length`（启用 + 停用），页面文案会显示“共 7 个 · 1 个已停用”，而顶部统计与 `TargetOverviewListResponse.total` 仍是 6。
- 问题：两个“总数”并存，用户可能误读；但 issue 明确允许“右栏分页计数可以包含停用对象”，且“1 个已停用”在文案里做了拆分。
- 预判：符合 issue 交付边界；如果后续希望两个数字完全一致，应把停用对象从右栏分页中拆出为折叠区，而不是改 API `total` 口径。
- 结论：留待需求方拍板；当前按 issue 原文实现。

### 6.2 历史停用对象缺少 `primary_metric_key` 时，“启用”会返回 422

- 位置：`apps/web/src/pages/overview/components/TargetsOverview.vue:397`、`apps/api/app/service/evolution/targets.py:238`
- 现象：启用复用的是整对象 `PUT`，当前服务端要求 `primary_metric_key` 非空。migration 0033 给旧行补的空字符串不会自动变成合法 key；E2E fixture 也必须显式写 `resolved_rate` 才能启用。
- 问题：管理员面对一个 #620 之前创建、一直停用的对象，点“启用”会看到“primary metric key is required”，需要先点“编辑”填 key 再保存/启用。
- 预判：这是 #620 校验与 #626 复用写入共同作用的已知路径，不是本 PR 引入的新破坏；issue 原文也写明“失败显示服务端错误”。可在后续 issue 让启用动作检测空 key 时直接打开编辑表单，减少一次报错。
- 结论：接受现状并在 PR 描述中说明；若需求方认为必须先编辑，再开小 issue 处理。

### 6.3 停用行动作行位置与原型不同

- 位置：`apps/web/src/pages/overview/components/TargetSideList.vue:271`
- 现象：原型把“启用/编辑/移除”放在标题行右侧，本 PR 放在卡片右下（与既有启用行动作行一致）。应用右栏在 1500 视口下约 350 CSS px，标题行并排会挤得“已停用”徽标换行。
- 问题：这是视觉与原型的已知差异，但不是功能缺失；分组标题、灰度、徽标、归因 Skill、说明与按钮集合都一致。
- 预判：保持现状更符合现有右栏密度；如果要求逐像素复刻原型，需要连同启用行动作行一起重排，属于视觉重构而非本 issue 的可见性修复。
- 结论：记录为有意的响应式适配，供人工验收确认。

### 6.4 每次列表多一次数据库查询

- 位置：`apps/api/app/service/overview/targets.py:672`
- 现象：`_analyses()` 与 `_disabled_targets()` 各读一次对象配置；后者只做过滤和排序，不读 case、不跑 matcher。
- 问题：对象总览本来就有多次聚合查询，多一条小表查询的代价可忽略；换来的是两条统计口径物理隔离，不需要在 `_analyses()` 里加参数。
- 预判：保持现状；若未来对象数量上千，可让仓储一次返回启用/停用两组。
- 结论：无实害，接受。

## 9. 文件级代码分析

### 9.1 `apps/api/app/service/overview/targets.py`

职责：把启用对象配置、case facts 与归因链接投影成对象总览 DTO；本次只在列表读路径新增停用对象元数据。

```python
# 旧
async def list_targets(...):
    analyses = await self._analyses(workspace_id, query.window, ())
    ...
    items=[_overview_item(analysis) for analysis in page],
    total=len(ordered),
```

```python
# 新
async def list_targets(...):
    analyses = await self._analyses(workspace_id, query.window, ())
    disabled = await self._disabled_targets(workspace_id)
    ...
    disabled=[TargetOverviewDisabledItem(...) for target in disabled],
    total=len(ordered),
```

实现思路：先保持启用对象的分析路径原样，再追加一条只读查询；两条路径在返回 DTO 处汇合，统计字段不共享。`_disabled_targets()` 用 `casefold()` 排序，保证中英文对象名都有稳定顺序；id 兜底避免同名对象抖动。

检视发现：无阻塞问题。查询范围固定为路径 workspace，不会跨空间泄漏；停用对象不触发 matcher，成本与对象数量线性。

### 9.2 `apps/web/src/pages/overview/components/TargetSideList.vue`

职责：对象总览右栏的排序、分页、选择与增编删入口。

```vue
<!-- 旧：只有启用行，分页按 items.length 计算 -->
<div v-for="item in visible" :key="item.targetId" class="side-item">
  <button class="select" @click="emit('toggle', item.targetId)">…</button>
</div>
<span class="info">共 {{ items.length }} 个 · 第 {{ safePage }} / {{ pages }} 页</span>
```

```vue
<!-- 新：启用行 + 停用行合并为 rows；停用行没有 .select -->
<template v-for="(row, index) in visible" :key="`${row.kind}-${row.id}`">
  <div v-if="showsDisabledDivider(index)" class="side-group">已停用对象 · 仅展示，不参与统计</div>
  <div v-if="row.kind === 'enabled'" class="side-item">…</div>
  <div v-else class="side-item is-disabled">
    <span class="badge off">已停用</span>
    <button class="btn enable" @click.stop="emit('enable', row.item)">启用</button>
  </div>
</template>
<span class="info">{{ pagerInfo }}</span>
```

实现思路：把两类对象折成字段完整的展示行，模板不依赖联合类型收窄；停用行用普通 `div`，从结构上保证不可选中。分组标题由“可见页内第一张停用行”决定，翻页后不会重复显示。

检视发现：无阻塞问题。停用行的统计字段固定为 0，仅用于模板占位，不会进入任何计算；`rows` 每次 props 变化重算，对象量级下开销可忽略。

### 9.3 `apps/web/src/pages/overview/components/TargetsOverview.vue`

职责：对象总览的数据装配、筛选、详情与配置 CRUD。

```ts
// 旧：只有 targetItems；新增/编辑/移除
const targetItems = computed(() => targetsQuery.data.value?.items ?? []);
```

```ts
// 新：disabled 独立通道；新增 enableTarget
const disabledItems = computed(() => targetsQuery.data.value?.disabled ?? []);

  let target = evolutionTargetsData.value?.items.find(...);
```
