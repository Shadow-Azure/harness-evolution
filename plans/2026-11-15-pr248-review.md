## 1. 一页速览

一句话：给 V1 的四张业务表贴上“属于哪个空间”的标签，并把空间、成员、上报凭据三张新表的骨架立起来；这一版不开放任何空间业务端点。

一个比喻：这像给一栋老楼换门牌系统——先在每户门口钉上“默认楼栋”的临时门牌，保证今天还能正常进出；等新的门禁前台（m7-03）上线后，再由每个写入方报出自己的真实楼栋。

| 交付块 | 内容 | 证据 |
|---|---|---|
| 契约 | `SessionPayload`、`Workspace`、`WorkspaceMember`、`WorkspaceCredential` 等显式 TS 类型 | `pnpm typecheck` |
| 表结构 | `workspaces` / `workspace_members` / `workspace_ingest_credentials` | 迁移测试 |
| 存量兼容 | 四张表 `workspace_id` 回填 `ws-default`，用户全部以 viewer 入默认空间 | 迁移测试 |

| 迁移验证 | SQLite 升级/重复升级/回填；MySQL 空库升级 | `test:db`、CI mysql lane |

## 2. 架构导览

### 2.1 契约层是“提前画好的插座”

`packages/contracts/src/workspaces.ts:12` 定义 `WorkspaceRole`，`:24` 定义 `Workspace`，`:48` 定义 `WorkspaceMember`，`:59` 定义 `WorkspaceCredential`，`:75` 定义 `SessionPayload`。字段与 05 §3.7 的 JSON 示例一一对应。为什么手写而不生成？因为本 issue 不开放 `/api/workspaces` 端点，FastAPI OpenAPI 里还没有这些 schema；先手写是为了让后续 UI 与 API 切片共用同一组字段名，m7-03 接入端点后再替换成生成类型。`packages/contracts/src/index.ts` 只做汇总导出，不引入运行时依赖。

### 2.2 迁移层是“一次性搬家清单”

`apps/api/alembic/versions/0014_v2_workspaces.py:342` 的 `upgrade()` 按固定顺序执行：

1. `:150` 给 users 加 `auth_provider` / `external_subject` 与唯一索引；
2. `:65` 建空间三表；
3. `:173` 幂等插入默认空间，`quota = COUNT(bad_cases) + 50`；
4. `:204` 为每张业务表加 `workspace_id` 并回填；
5. `:300` 把 `evolution_targets` 的唯一键改成空间内唯一；
6. `:329` 把存量用户写成默认空间的 viewer。

`:379` 的 `downgrade()` 严格反序，并在删除列前按名称确认外键是否存在。

### 2.3 双方言差异是“能安全施工才施工”

SQLite 不支持直接给已有表加外键；用 Alembic batch 重建父表会在 `PRAGMA foreign_keys=ON` 下触发子表的 `SET NULL`/`CASCADE`，把 run 快照或 analysis 行静默改掉。因此 `:255` 只给 MySQL 加三张业务表的 workspace 外键，SQLite 保留 `NOT NULL`、默认值与索引。`evolution_run_events.workspace_id` 按 06 §5.7 只是审计冗余列，不挂外键。

### 2.4 默认值是“临时门牌”，不是隔离

`:204` 在 SQLite 上直接以 `NOT NULL DEFAULT 'ws-default'` 加列，在 MySQL 上先可空、回填、再收紧。原因是 SQLite 不能用 `ALTER COLUMN` 收紧空值；两种路径的最终语义一致：存量无 NULL，新写入未带空间时落默认空间。这个默认值让 V1 目录同步和 fixture 在 m7-03 之前继续工作，但也意味着漏传空间不会报错；本地 `test_v2_workspace_foundation_backfills_default_workspace` 明确验证了这一点。

## 3. 数据流走查

以“空库升级 + 一条存量 bad case + 一个新 run”为主线：

1. 空库从 head 升到 `0013`，插入两个用户、两条 bad case、一个 target、一个 run 与一条 run event（`apps/api/tests/test_database.py:695`）。
2. 升级到 head：users 先得到 provider 字段（`0014_v2_workspaces.py:150`），空间三表建立（`:65`），默认空间以 `quota=52` 插入（`:173`）。
3. 四张表加列并回填 `ws-default`（`:204`）；evolution_targets 的唯一键重建（`:300`），在此之前 `_backup_run_targets()` 保存了 run 的 `target_config_id`，重建后恢复，避免 SQLite 的 `SET NULL` 改写 run 快照。
4. 两个用户写入 `workspace_members(role=viewer)`（`:329`）。
5. 测试断言版本 `0014`、无 NULL workspace、默认空间 quota、成员行、索引名，并插入一条不带 `workspace_id` 的 bad case 验证数据库默认值；再插一次跨空间同名 target 验证唯一键已按空间生效。

## 6. 讨论点

### 6.1 SQLite 不追加 workspace 外键

- **位置**：`apps/api/alembic/versions/0014_v2_workspaces.py:255`
- **现象**：MySQL 为 bad_cases / targets / runs 加外键，SQLite 只加 NOT NULL、默认值和索引。
- **问题**：SQLite 本地库缺少数据库级引用完整性，误写 `workspace_id` 不会被数据库拒绝。
- **预判**：接受。SQLite 仅测试/本地；在 `PRAGMA foreign_keys=ON` 下重建父表会级联改写子表，风险大于收益。应用层空间服务本来就要做不可见空间判定。
- **结论**：（留待维护者）

### 6.2 `ws-default` 过渡默认值何时撤

- **位置**：`apps/api/alembic/versions/0014_v2_workspaces.py:204`、`apps/api/app/db/models/domain.py:233`
- **现象**：`workspace_id` 带数据库默认 `ws-default`，V1 写入不传空间也会成功。
- **问题**：m7-03 之后如果某条写路径漏传空间，数据会静默进入默认空间，而不是报错。
- **预判**：本 PR 需要它保证 V1 兼容；m7-03 完成显式空间写入后，应另起迁移删除默认值并把缺失空间变为显式错误。
- **结论**：（留待维护者）

### 6.3 bad_cases 模型不声明 workspace 外键

- **位置**：`apps/api/app/db/models/domain.py:226`
- **现象**：迁移在 MySQL 上加外键，ORM 模型只声明列与索引。
- **问题**：模型与迁移的约束信息不一致，读模型时看不到外键关系。
- **预判**：接受。`bad_cases` 在 fixture 路径由模型 metadata `create_all` 引导，跨 MetaData 的 workspace 外键无法解析；迁移是约束事实源。等 V2 上报端点让 bad_cases 完全归本服务所有后，再统一模型与迁移。
- **结论**：（留待维护者）

### 6.4 targets 重建期间的 run 快照恢复

- **位置**：`apps/api/alembic/versions/0014_v2_workspaces.py:268`
- **现象**：SQLite 重建 targets 前把 `evolution_runs.target_config_id` 复制到临时表，重建后写回。
- **问题**：临时表与恢复语句增加迁移复杂度；如果恢复失败，run 快照会退回 NULL。
- **预判**：必要且已由测试覆盖。没有备份时 SQLite 的 `SET NULL` 会静默把 run 与 target 解绑，比多十几行代码危险得多。
- **结论**：（留待维护者）

## 9. 文件级代码分析

### 9.1 `apps/api/alembic/versions/0014_v2_workspaces.py`（A）

职责：一次迁移完成空间三表、用户 provider 字段、四张业务表空间列与存量回填。

- 旧状态：空间概念不存在，所有 bad case 与自进化对象都是全局的；`evolution_targets` 按 `(object_type, object_name)` 全局唯一。
- 新逻辑：`:342` 固定顺序；`:173` 以 Python 查询保证默认空间只插一次；`:300` 在 SQLite 上备份 run 的 target 引用后重建唯一键。
- 实现思路：能用 `ALTER TABLE ADD COLUMN ... DEFAULT` 的地方不在 SQLite 重建整表；必须重建的唯一一处显式保护子表快照。

检视发现：无阻塞缺陷。风险是默认空间名称被占用时唯一键冲突，属于迁移前置状态异常，未额外处理。

### 9.2 `apps/api/app/db/models/workspace.py`（A）

职责：空间三表的查询模型。`workspaces`（`:21`）含 quota/status/时间戳；`workspace_members`（`:40`）联合主键与 user 索引；`workspace_ingest_credentials`（`:61`）哈希唯一与 `(workspace_id, revoked_at)` 索引。

检视发现：模型不负责建表（迁移是事实源），因此没有把三表塞进其他 MetaData；`DEFAULT_WORKSPACE_ID` 作为常量供后续服务复用。

### 9.3 `users.py` / `domain.py` / `evolution.py` / `run_events.py`（M）

四份模型只加列、索引与约束，不改查询投影。`users.py:37` 起是 provider 字段；`domain.py:233` 是 bad_cases 的空间列与四个 workspace-leading 索引；`domain.py:388` 把 targets 唯一键改为含空间；`evolution.py:38` 与 `run_events.py:42` 是 run/event 的空间列。既有记录 dataclass 不增加必填字段，避免影响所有构造点。

检视发现：模型中的 workspace 外键有意缺省，原因见 §6.3。

### 9.4 `packages/contracts/src/workspaces.ts`（A）

职责：在 OpenAPI 生成物出现前，固定空间与 auth/session 的字段名。`SessionPayload` 复用既有 `PublicUser`，避免重复定义用户字段。

检视发现：`sessionWorkspace.role` 同时容纳 `global_admin` 与三个空间角色，和 05 §3.7 的“当前用户有效角色”一致。

### 9.5 `apps/api/tests/test_database.py`（M）

职责：用真实 SQLite 连接验证迁移结果，而不是只测常量。新增测试从 `0013` 插入存量行再升级，覆盖默认空间、回填、成员、索引、数据库默认值、跨空间唯一键与用户映射唯一性。既有的空库升级测试与 MySQL 空库测试同步 head 与列集合断言。

检视发现：MySQL 分支只做空库 schema 验收，回填逻辑由 SQLite 覆盖；两者共享同一迁移代码，CI mysql lane 仍会真实执行 DDL。
