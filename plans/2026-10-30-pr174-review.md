## §1 一页速览

**一句话：** 让 bad_cases 里的每个根会话自动补齐主 agent 与全部 subagent 的原始轨迹，并用一张状态表回答“总共有多少、同步了多少、还差多少”。

**一个比喻：** `bad_cases` 是前台收到的“问题工单”，`bad_case_root_sync` 是工单处理台账；定时任务像一名不厌其烦的档案员，按台账逐张工单去问两个窗口——“这个 agent 还叫了谁？”（接口 1）、“把这个 agent 的轨迹给我”（接口 2）——把档案按 `(root_session_id, agent_id)` 放进 `trajectory_payloads`，最后交给现有归一化流水线装订成可浏览的会话树。档案员一次只处理有限几张工单；上一批没做完，下一次打卡就先跳过，等下一轮再从台账继续。

| 交付块 | 内容 |
|---|---|
| 状态表 | `bad_case_root_sync`：claim/lease、attempts、last_error、agent_count、next_retry_at |
| 定时任务 | `bad_case_root_sync` job；活跃批次跳过；批量/时间预算/深度/agent 上限可配 |
| 外部客户端 | 接口 1 裸数组；接口 2 NDJSON；接口 2 进程内串行；响应体/行上限 |
| 树组装 | subagent `agent_meta={"parentAgentId": ...}`；无 toolUseId 时挂父 agent 节点 |
| 状态 API | `GET /api/acquisition/status` 的 `badCaseSync` 块 |
| 前端 | 顶栏“数据同步”浮层：总数/已同步/未同步/同步中/失败，running/failed 文案 |
| 冒烟 | 真实 SQLite + API + Vite + headless Chrome + mock 查询服务 |

## §2 架构导览

### 2.1 状态表是“可验证的完整”，不是缓存

`bad_case_root_sync` 由服务自己拥有，`root_session_id` 主键，`status` 四态（`pending/syncing/synced/failed`）。候选查询从 `bad_cases` 的 distinct root 做 LEFT JOIN，所以“没有状态行”本身就是新 root 的正常形态；反过来，状态行对应的 root 从 bad_cases 消失后只留审计、不进统计。对应实现：`apps/api/app/db/crud/bad_case_sync.py:160-184`、`:330-360`。

### 2.2 claim/lease 把“谁在跑”写进数据库

claim 在一个事务里先查后写，`synced` 拒绝，未过期 `syncing` 拒绝，未到期 `failed` 拒绝；成功时 `attempts += 1`、写 lease。每个 agent 写完后 `renew_lease` 续期，租约长度至少覆盖单 root 时间预算。这样进程崩溃后，过期 lease 可被下一次 tick 重新 claim。对应：`crud:186-260`、`service:227-232`。

### 2.3 两个外部接口是两种完全不同的形状

接口 1 返回 `["child-a", "child-b"]` 裸数组；接口 2 返回 NDJSON，一行一个 object，没有 `agent_meta`。客户端用严格 Pydantic 校验接口 1，用自写 NDJSON 解析器处理接口 2；接口 2 的整段调用包在 `asyncio.Lock` 里，保证进程内不重叠。响应体 64 MiB、单行 1 MiB、行数 1,000,000 上限。对应：`apps/api/app/third_party_api/session_query/http.py:26-143`。

### 2.4 BFS + 逐 agent 写入

服务从 root 开始队列遍历，`visited` 防环；每个 agent 取到轨迹后立即写一行 `trajectory_payloads`，而不是整棵树取完再写。这样中途失败时已抓到的 payload 不会丢，`agent_count` 也是真实行数；重试按主键幂等覆盖。对应：`apps/api/app/service/acquisition/bad_case_sync.py:235-302`。

### 2.5 单飞在 job 层，调度器只负责“要不要提交”

调度器每 `HE_BAD_CASE_SYNC_INTERVAL_SECONDS` 触发一次；发现已有活跃 `bad_case_root_sync` job 就返回 `skipped`，没有候选就 `idle`，有候选才 `JobRunner.submit(ref_id=KIND)`。`JobRunner` 本身串行执行 handler，所以不会出现两个批次同时跑。对应：`bad_case_sync_coordinator.py:73-121`。

### 2.6 状态 API 与前端是“同一块数据的两种投影”

`SyncCoordinator.status()` 仍返回归一化统计；`BadCaseRootSyncCoordinator.status()` 返回 bad-case 统计；路由把两者合成 `AcquisitionStatusResponse`。前端只多读一个嵌套对象，不新增轮询端点。对应：`api/acquisition.py:51-84,175-180`、`TopNav.vue:77-100,205-240`。

## §3 数据流走查

1. **启动**：lifespan 迁移到 0011，构造 `BadCaseRootSyncService` 与 `Coordinator`，注册 `bad_case_root_sync` handler，`await bad_case_sync.start()`。
2. **tick**：`trigger("scheduler")` 检查 `session_query_configured` → 查活跃 job → 查候选数 → `submit`。
3. **claim**：服务按批取候选，逐个 `claim`；失败/租约被占则跳过。
4. **遍历**：`_sync_root` 取 root 轨迹 → 写 main 行 → 取直接子 → 写 subagent 行（`parentAgentId`）→ 续 lease → 继续队列；超深度/agent 上限或时间预算则抛稳定错误。
5. **成功**：`mark_synced(agent_count=实际行数)`；同一批所有 root 完成后调用一次 `replay_pending_payloads`。
6. **失败**：`mark_failed(error=稳定 code, next_retry_at=1/5/15/1h, agent_count=已写行数)`；已写 payload 保留，下一 tick 重试。
7. **状态**：`GET /api/acquisition/status` 返回 `badCaseSync`；前端顶栏浮层展示总数/已同步/未同步/同步中/失败，running 显示“补齐中”，failed 显示稳定错误文案。
8. **查询**：重放把 payload 归一化成 `session_families/agents/...`，`GET /api/sessions` 即可看到会话与问题卡。

## §6 讨论点

> 本节保留检视时的判断过程；Critical/Important 已在同 PR `9ea5e19` 修复，结论栏记录实测与代价。

### D1 MySQL 缺表异常被漏捕（Critical，已修复）

- **位置**：`apps/api/app/db/crud/bad_case_sync.py:132-134,166-170,179-183,325-329`
- **现象**：只捕 `OperationalError`；MySQL 缺表经 SQLAlchemy 归一为 `ProgrammingError`（asyncmy 1146）。
- **问题**：MySQL 部署缺 external 表时 `/api/acquisition/status` 500，整个顶栏同步不可用。
- **预判**：SQLite 测试通过形成假绿，必须同时捕 `ProgrammingError`。
- **结论**：已修复（`9ea5e19`）：`_missing_bad_cases` 接受两类异常，`list_candidates/count_candidates/stats/last_run_at/last_error` 都容错；新增 `ProgrammingError(1146)` 单测。

### D2 单 root 遍历不受时间预算约束、租约会缩短（Important，已修复）

- **位置**：`bad_case_sync.py:133,163,235-302`
- **现象**：预算只在候选间检查；单 root 最坏 200 agent×3×60s，期间持有全局 worker lock；晚 claim 的 lease 从批开始时间算。
- **问题**：一个慢 root 可阻塞 sync/pull/evolution 数小时；崩溃后 lease 过早过期，可能重复 claim。
- **预判**：应在 `_sync_root` 每个 agent 前检查 deadline，并按 root 实际 claim 时间 + 续期设置 lease。
- **结论**：已修复（`9ea5e19`）：每 agent 前检查 deadline，超限记 `BAD_CASE_SYNC_TIME_BUDGET`；claim 用 root 实际时间，lease 至少覆盖时间预算，每 agent `renew_lease`。

### D3 失败 root 丢弃已抓 payload（Important，已修复）

- **位置**：`bad_case_sync.py:162-176,178-187`
- **现象**：先收集整棵 payload 再写库；失败时整批不写，`agent_count=0`。
- **问题**：与设计“已写入 payload 保留、失败记录部分行数”冲突，重试重复串行拉取。
- **预判**：改为每个 agent 取到即写，失败保留。
- **结论**：已修复（`9ea5e19`）：逐 agent 单行事务写入，`RootSyncProgress` 记录实际行数，失败 `mark_failed(agent_count=progress.agent_count)`；测试断言失败 root 保留 1 行。

### D4 NDJSON 无上限且 splitlines 会切 U+2028（Important，已修复）

- **位置**：`session_query/http.py:105-143`
- **现象**：原先无 body/line 上限，`splitlines()` 把 U+2028/U+2029 当换行。
- **问题**：超大响应打爆内存；合法 JSON 字符串被切断后 root 反复失败。
- **预判**：按 `\n` 分帧，加上 64 MiB / 1 MiB / 1,000,000 行上限。
- **结论**：已修复（`9ea5e19`）；新增 U+2028 保留与超长行拒绝测试。

### D5 前端忽略 running/failed/lastError（Important，已修复）

- **位置**：`TopNav.vue:205-240`
- **现象**：只处理 unavailable 与计数，running 显示静态数字，failed 没有原因。
- **问题**：用户看不到“正在补”与“为什么失败”。
- **预判**：补 `badCaseSyncStatusLabel` / `badCaseSyncErrorLabel`，浮层按状态切换。
- **结论**：已修复（`9ea5e19`）；新增 failed 状态组件测试与文案单测。

### D6 统计边界与 orphan 行（Minor，已修一半）

- **位置**：`crud:362-405`
- **现象**：`last_run_at/last_error` 可能取 orphan 状态行；`total` 与 grouped 两条查询非同一快照。
- **问题**：统计展示可能自相矛盾（synced > total 时 unsynced 被 max(0) 截断）。
- **预判**：last_run/error 改成 join 当前 roots；快照问题在单实例低并发下无实害。
- **结论**：`last_run_at/last_error` 已改为 join 当前 roots（`9ea5e19`）；两条查询合并为单快照留作后续优化，当前单实例无实害。

### D7 agent_count 语义（Minor，已对齐设计）

- **位置**：`service:174`、`crud:254-330`
- **现象**：原为“本次 payload 数”，失败固定 0。
- **问题**：与设计“该 root 在 payload 表的实际行数”不完全一致。
- **预判**：逐 agent 写入后按实际行数记录。
- **结论**：已随 D3 修复；`agent_count` 现在等于实际写入行数（含 main），仍只作诊断，不参与已同步统计。

### D8 父节点锚点与诊断（Minor，部分修复）

- **位置**：`agent_tree.py:540-551`
- **现象**：原取父节点 anchor（首事件），未记录 `PARENT_ANCHORED_BY_AGENT`。
- **问题**：排序可能不在父节点最后事件附近；诊断码缺失。
- **预判**：锚点取父节点最后一个事件；诊断码可选。
- **结论**：锚点已改为父节点最后事件（`9ea5e19`）；诊断码未加，避免新增公开 warning 面，留作后续。

### D9 job result 键（Minor，留档）

- **位置**：`service:109-122`
- **现象**：返回 `rootsSkipped/skipped`，设计 §8 写 `skippedTicks`。
- **问题**：键名与设计不完全一致；`skippedTicks` 是调度器概念，handler 不知道。
- **结论**：保留实现键，设计 §8 以 `rootsSkipped` 为准（待下一轮文档同步）。

### D10 迁移/测试薄弱（Minor，部分补强）

## §9 文件级代码分析

### `apps/api/app/db/crud/bad_case_sync.py`（A）

**职责：** 状态表的唯一读写入口：候选、claim、续租、成功/失败、统计、最近运行/错误。

**关键依赖：** SQLAlchemy Core + `Database`；没有 ORM 关系，靠 `(root_session_id)` 逻辑关联 external `bad_cases`。比喻：它是台账管理员，只认编号，不认工单内容。
