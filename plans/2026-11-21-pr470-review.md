## §2 架构导览

### 2.1 后端：可见进度是状态机的一部分

`state.py` 仍是七步游标规则的唯一 home：`total_units()` 给出完整 run 的 5+M+1 个游标，`_CLUSTER_ONLY_HIDDEN` 已声明 cluster_only 不进入 iteration/final。新增 `progress_total(mode, cluster_count)`（`state.py:83`）只回答「这个 mode 对外展示多少步」：cluster_only 固定 5，其余走 `total_units()`。这样 `runs.py` 不再自己判断 mode 的可见步数，避免第二份事实源。

`runs.py` 的 `_progress()`（`runs.py:293`）先按原有规则校验游标，再在 `run.mode == "cluster_only"` 时（`runs.py:303`）把 unit 截到 5、用 /5 标签、`doneRounds=0`、`accepted=0`，完成态为 `_CLUSTER_ONLY_DONE_LABEL`（`runs.py:67`）。完整 run 的分支原样保留。

### 2.2 前端：页面是编排者，簇卡是复用件

`ClusterPreview.vue` 在 run completed 后并行读三个 step（`ClusterPreview.vue:43` / `:49` / `:50`）：

- `range`：持久条件快照，用于「启动自进化」的同一条件。
- `clusters`：页面主体数据。
- `attribution`：`badCaseId → sessionId` 映射，只用于来源表深链，不向 `steps/clusters` 契约加字段。

`StepClusters.vue` 只增加可选 `title/subtitle/caseSessions` props（`StepClusters.vue:13`），默认标题仍是运行详情第 5 步的「第 5 步 · 聚类与严重度」（`StepClusters.vue:89`），因此不会复制一套簇卡。`StepCaseTable.vue` 在拿到 `wid + caseSessions` 时把 ID 渲染为错误详情链接（`StepCaseTable.vue:26` / `:62`），否则保持纯文本；运行详情与迭代步骤的默认行为不变。

### 2.3 列表卡片：按 mode 收口

`RunCard.vue` 的 completed 分支先看 mode（`RunCard.vue:32`）：cluster_only 显示「✓ 已完成 · 仅聚类」，不再落入「终评未知」。统计条把「已跑轮次」替换为「聚类」（`RunCard.vue:210`），底部说明未执行 patch / 评测（`RunCard.vue:262`）。完整 run 的 final / delta 逻辑未动。

## §3 数据流走查

1. 用户在向导第 4 步点「仅聚类」→ `POST …/evolution/cluster-previews` → 202 → 路由 `/evolution/cluster/:runId`。
2. `ClusterPreview.vue` 用 `useEvolutionRunDetail` 读 run shell；`preparing/running` 时只轮询，不请求 step。
3. run 变成 `completed` 后，三个 step 查询被 enabled；页面渲染「问题聚类结果」、输入概况、簇卡与来源表。
4. 用户点「以这批问题启动自进化」→ `launchFullRun()`（`ClusterPreview.vue:163`）用 `rangeCondition` 重建 body：target / version / window / policy / cache / models，`mode="full"` → `POST …/runs` → 失效运行列表查询 → 跳运行详情。
5. 列表页的 `RunCard` 读同一 run 的卡片 DTO；cluster_only completed 走新的徽标 / 聚类数 / 底部说明。
6. 详情页（run detail）仍按共享七步契约渲染；cluster_only 的 iteration/final 是 pending，但仅聚类页不渲染这两个节点。

## §6 讨论点

### D1 启动后是否让运行列表失效

- **位置**：`apps/web/src/pages/evolution/ClusterPreview.vue:182`
- **现象**：点「启动自进化」后直接跳运行详情；运行列表查询原本由向导出口负责失效。
- **问题**：30s staleTime 内返回列表可能看到旧卡片，用户会以为新 run 没创建。
- **预判**：补 `invalidateQueries(evolutionRuns)` 与向导一致；无额外请求，只标记 stale。
- **结论**：本 PR 内已补（2026-11-21），并保留该讨论点供维护者复核。

### D2 仅聚类完成卡是否应使用绿色成功徽标

- **位置**：`apps/web/src/pages/evolution/components/RunCard.vue:48`
- **现象**：cluster_only completed 返回 `done-ok`（绿色）。
- **问题**：仅聚类没有「自进化有效」结论，绿色是否会被误读为「产生收益」。
- **预判**：徽标文案已明确「仅聚类」，绿色只表达「运行完成」；若产品希望中性色，可改用 `done-pending`，代价是完成态与失败态更接近。
- **结论**：留空待维护者判断。

### D3 深链依赖 attribution 是否有额外成本

- **位置**：`apps/web/src/pages/evolution/ClusterPreview.vue:50`
- **现象**：页面为来源表深链多读一个 `steps/attribution`。
- **问题**：多一个请求；若该 step 失败，ID 退化为纯文本。
- **预判**：只在 completed 后触发，与 clusters 并行；契约不新增字段，失败可降级，成本可接受。若未来 `StepClusterCase` 增加 sessionId，可删掉这条查询。
- **结论**：留空待维护者判断。

### D4 run detail 仍返回七个 step 节点

- **位置**：`apps/api/app/service/evolution/runs.py:383`（`_detail_steps`）
- **现象**：cluster_only 的详情仍返回 iteration/final pending。
- **问题**：共享七 key 契约下是否应隐藏这两个节点。
- **预判**：本 PR 的入口不渲染它们；改契约会波及运行详情、E2E 和深链，超出本 issue。保持现状并在 Note 记录。
- **结论**：留空待维护者判断。

### D5 E2E 列表卡片断言从 stageLabel 改为徽标

- **位置**：`tests/e2e/m11-05-v2-cross-stack.test.mjs:792`
- **现象**：历史卡片不渲染 `stageLabel`，首版断言误以为会显示「第 5/5 步」。
- **问题**：断言会超时，且说明 issue 描述里「列表卡片显示错误步骤」只对进行中卡片成立。
- **预判**：断言改为徽标「✓ 已完成 · 仅聚类」+ 不出现「已跑轮次」「第 6/7」，覆盖真实渲染路径。
- **结论**：本 PR 内已修（2026-11-21）。

## §9 文件级代码分析

### 9.1 `apps/api/app/service/evolution/state.py`

职责：七步游标与可见性规则的唯一 home。变更形态：M，新增 `progress_total()`。

变更块：

```python
def progress_total(mode: str, cluster_count: int) -> int:
    if mode == "cluster_only":
        return PREPARE_COMPLETE_UNIT
    return total_units(cluster_count)
```

旧的 `total_units()` 同时承担「游标上限」和「对外总步数」两个语义；cluster_only 的游标上限仍是 5+M+1（为了兼容持久化与校验），但对外只应展示 5。拆出 `progress_total()` 后，`_progress()` 不再自己写 mode 判断，规则仍集中在 state.py。代价：新增一个公开函数，需要单测覆盖两种 mode；已补。

检视发现：无阻塞问题。`mode: str` 没有用 Literal；与现有 `step_states` 的 `run_status: str` 风格一致，暂不收紧。

### 9.2 `apps/api/app/service/evolution/runs.py`

职责：run 列表 / 详情投影。变更形态：M，`_progress()` 增加 cluster_only 分支。

变更块：

```python
if run.mode == "cluster_only":
    total = progress_total(run.mode, cluster_count)
    unit = min(unit, total)
    stage_label = (
        _CLUSTER_ONLY_DONE_LABEL if unit >= total else _CLUSTER_ONLY_STAGE_LABELS[unit]
    )
    return EvolutionRunProgress(... done_rounds=0, accepted=0)
```

旧的代码对所有 mode 都算 `total_units()` 与七步标签，cluster_only 完成态 unit=5 落入「第 6/7 步 · 迭代优化」。新分支把可见总步数、标签、轮次、接纳数一起收口。`unit = min(unit, total)` 是防御性截断：历史/异常游标大于 5 时也不会显示 6/5。

检视发现：`accepted=0` 对 cluster_only 是正确的语义，但如果未来 cluster_only 支持接纳（当前不支持），这里需要同步。已由 Note 的 Consequences 记录。
