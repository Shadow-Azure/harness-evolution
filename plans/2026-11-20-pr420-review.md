## §1 一页速览

## §2 架构导览

**三个标签的数据本来就在库里。** 启动时 `EvolutionLaunchService._run_values()` 把 `policy.snapshot()` 与 `body.cache_enabled` 写进 run 行（`apps/api/app/service/evolution/launch.py:269-270`）；`ResolvedPolicy.snapshot()` 固定产出 `{preset, includeSelfReport, includeAfterObject, sameObjectOnly}`（`apps/api/app/service/evolution/potential.py:126-133`），所以 `potential_policy` 里始终有 `preset`。列定义是 `potential_policy JSON NULL`、`cache_enabled BOOLEAN NOT NULL DEFAULT false`（`apps/api/app/db/models/evolution.py:48-49`、`:359-360`、`:582-583`）。缺的只是列表服务没有把它们投影进卡片，这正是 issue #414 说的“投影缺口而不是新需求”。

**后端投影。** `_policy()` 只认 `custom`，其余一律 `default`（`runs.py:337-341`）；`_card()` 在同一处把两项塞进 DTO（`runs.py:361-362`），DTO 字段在 `runs.py:140-157`。`EvolutionRunDetail` 直接继承 `EvolutionRunCard`（`runs.py:195-204`），`_detail()` 又用 `**card.model_dump()` 展开（`runs.py:476-503`），所以详情接口自动获得同样的两个字段；这是“单一快照”的实现方式，也意味着契约面比 PR 描述里写的“卡片”更大（见 D3）。举一个真实例子：`run-completed-effective` 行的 `potential_policy={"preset":"custom",...}`、`cache_enabled=true`，列表 JSON 就是 `policy: {preset: "custom"}`、`cacheEnabled: true`（`test_runs_api.py:204-211` 断言）；没有策略的旧行 `potential_policy=None` 得到 `{preset: "default"}`（`test_runs_service.py:238-260`）。

**工作空间名为什么不进 DTO。** 页面读的是 workspace-scoped 路由 `/api/workspaces/{wid}/evolution/runs`（`apps/web/src/api/evolutionRuns.ts:22-37`），服务端 `list_runs` 把 `workspace_ids=(wid,)` 传给服务（`apps/api/app/api/evolution_workspace.py:324-331`），所以一次响应里的卡片必然同属一个空间，DTO 再逐卡重复空间名是冗余。页面从 `auth.workspaceById(workspaceId.value)?.name` 取名字（`Index.vue:22-26`），`workspaceById` 在可见空间列表里查找（`apps/web/src/stores/auth.ts:74-76`）；路由守卫在进入页面之前就要求该空间可见，否则跳回空间选择（`apps/web/src/router/index.ts:156-162`），因此正常导航下名字在首帧就存在。名字为空时卡片不渲染空间 chip（`RunCard.vue:178-182`），而不是伪造一个名字——设计文档 08 明确写了这条（`08-frontend-implementation.md:610-614`）。对照之下，旧的全局接口 `/api/evolution/runs` 会返回所有可见空间的 run（`apps/api/app/api/evolution_runs.py:109-113`），那一类消费方不能直接复用这个单名 prop；当前 Web 没用它，所以无实害。

**契约变化。** 卡片新增两个必填字段并进入 `required`（`packages/contracts/openapi.json:1919-1920`）；新的 `EvolutionRunPolicy` 只含 `preset`，枚举 `default|custom`，默认 `default`（`openapi.json:2449-2465`）；详情继承后同样进入 required（`openapi.json:2092-2093`），生成的 `api.d.ts` 在卡片段 `:2365-2384`、详情段 `:2405-2432`、策略类型 `:2566-2576`。生成物没有手改，`pnpm contract:check` 独立通过。

**旧数据语义已核对，不是“顺手编一个默认值”。** `_policy()` 把 `None` 归一为 `default`，而执行侧的 `_run_policy()` 对 `None` 也返回 `resolve_policy(None)`，即 self-report + after-object + 非 same-object 的默认开关（`apps/api/app/service/evolution/prepare.py:634-644`），所以“默认潜在策略”对旧行是真实语义。`cache_enabled` 的旧行值为 `false`（迁移 0021 加列时 `server_default=false`，`apps/api/alembic/versions/0021_attribution_run_snapshot.py:24-31`），引擎读的是 run 行上的 `run.cache_enabled`（`prepare.py:252`），且 false 时 `reused` 恒为 0（`potential.py:789-795`）；缓存开关与快照持久化是 #296 / #298 两个相邻提交（`b698cc1`、`f8752d2`），在快照落库之前创建的 run 本来就不会复用缓存，因此旧卡显示“不复用缓存”没有篡改历史。这个结论把 `test_m10_03_migration.py:106-107` 的迁移断言和当前执行链对齐了。

**前端渲染。** 三枚标签都是轻量 computed：策略只看 `preset`，缓存只看 `cacheEnabled`（`RunCard.vue:56-68`）；模板在时间窗之后依次插 space / policy / cache，再走到模型 chip（`RunCard.vue:175-199`）；缓存开启时加 `is-on` 类（`:187-191`），样式复用 cyan token（`:441-450`）。空间名由 `Index.vue:133-147` 传给两个 RunGroup，再由 `RunGroup.vue:7-12`、`:41-48` 透传给每张卡；`workspaceName` 是必填 prop，所有挂载点都在同一条链上。

**测试与证据。** 组件层覆盖 default / custom、cache true / false、时间只剩纯时间、空间名来源（`RunCard.test.ts:79-98`、`:130-153`）；页面层覆盖 auth store → RunGroup 的传递（`Index.test.ts:252-268`）；API 层覆盖投影与旧数据归一；E2E 用真实 Chrome 断言三枚标签文本、时间不再含 `Administrator`、页面无横向溢出（`tests/e2e/m5-run-list.test.mjs:308-317`、`:362-367`、`:339-340`）。注意 E2E 视口是 1408×960（`:228-231`），PR 里的 1500×837 截图是外部证据、不是这条测试的产物；截图检视时未打开，修复后 worker 已核对。

## §3 数据流走查

以一条 `completed` 且 `policy=自定义 + cache=true` 的 run（E2E fixture 的 `run-completed-effective`）为主角：

1. 用户在向导里选自定义策略、打开缓存，点启动。`EvolutionLaunchService._run_values()` 写入 `potential_policy=policy.snapshot()`、`cache_enabled=body.cache_enabled`（`apps/api/app/service/evolution/launch.py:269-270`）；`resolve_policy()` 保证 custom 一定带全三条开关（`potential.py:147-185`）。
2. 行落库：`potential_policy` 存 JSON，`cache_enabled` 存 bool（`apps/api/app/db/models/evolution.py:48-49`）。
3. 浏览器打开 `/{wid}/evolution`，`useEvolutionRuns(workspaceId)` 用 workspace-scoped 路径请求（`apps/web/src/composables/useEvolutionRuns.ts:11-18`、`apps/web/src/api/evolutionRuns.ts:22-37`）。
4. FastAPI `list_runs(wid)` 校验 viewer 角色后调 `EvolutionRunService.list(workspace_ids=(wid,))`（`apps/api/app/api/evolution_workspace.py:324-331`）。
5. `list()` 对每条 summary 调 `_card()`（`runs.py:444-458`）；`_card()` 组装 `EvolutionRunCard`，其中 `policy=_policy(summary)`、`cache_enabled=run.cache_enabled`（`runs.py:344-380`）。
6. `_policy()` 读 `summary.run.potential_policy["preset"]`，`custom` 原样保留，其余（含 None、未知值）归一为 `default`（`runs.py:337-341`）。
7. 响应序列化为 camelCase：`policy: {preset: "custom"}`、`cacheEnabled: true`，并受 `EvolutionRunCard` 的 required 约束（`openapi.json:1919-1920`）。
8. 前端 `Index.vue` 同时算 `workspaceName`（`auth.workspaceById`，`Index.vue:22-26`），把两组 run 和三枚 prop 交给 RunGroup（`:133-147`）。
9. RunGroup 逐卡透传 `wid` / `workspaceName` / `run`（`RunGroup.vue:41-48`）；RunCard 渲染：右上 `createdAtLabel` 只输出时间（`RunCard.vue:172`），第二行依次输出空间名、`自定义潜在策略`、`复用缓存`（`:175-199`）。
10. 点卡片走 `detailPath`（`RunCard.vue:74-81`），详情接口同样由 `_detail()` 从 `**card.model_dump()` 得到 `policy` / `cacheEnabled`（`runs.py:476-503`），但详情页当前不展示它们，属于契约预留。

反例链路：旧行 `potential_policy=None` → 第 6 步归一 `default` → 显示“默认潜在策略”；旧行 `cache_enabled=false` → 显示“不复用缓存”，与 `prepare` 读到的执行语义一致。缺失 auth 空间名 → 第 9 步 `v-if` 不渲染空间 chip，卡片其余标签照常。

## §6 讨论点

### D1 新前端直接解引用 `run.policy.preset`，与 Note 的兼容性描述不符

- **位置**：`apps/web/src/pages/evolution/components/RunCard.vue:60-68`（`props.run.policy.preset === "default"`、`props.run.cacheEnabled`）；`.agents/notes/implemented/bug-fix/2026-11-20-run-list-prototype-alignment.md:28`（英文配对 `.en.md:28`）；部署侧 `deploy/release.sh:144-158`、`deploy/nginx-harness.conf:9,17`、`deploy/harness-api.service:14`、`.github/workflows/deploy.yml:64-68`。
- **现象**：新后端 → 旧前端是安全的（多出的字段被忽略）；反过来，新前端遇到旧后端响应时，`cacheEnabled` 缺失只是 falsy，会显示“不复用缓存”，但 `run.policy` 是 `undefined`，再取 `.preset` 会抛 `TypeError`，整张卡（很可能整页）渲染失败，而不是 Note 写的“读 `undefined`”。生产常态下 API 与 Web 同属一个 release、`current` 软链原子切换（`release.sh:144-146`），nginx 的 root 与 API 代理都指向 `current`（`nginx-harness.conf:9,17`），所以正常发布不会混版本；但健康检查失败时 `rollback()` 会把 `current` 切回上一 release（`release.sh:150-158`），已经在浏览器里加载了新 bundle 的标签页下一次刷新列表就会撞上旧 API，这个窗口是真实存在的。
- **问题**：这是一条“新增必填嵌套字段”的兼容性边界，与仓库既有做法不一致：上一个同类变更在 PR #406 用 `item.short || item.title` 给旧响应留了兜底。当前 Note 用“同版本部署”合理化“不做降级”，但把崩溃机制写成了“读 undefined”，描述与代码行为不符；将来若有人照着 Note 做版本错配排查，会被误导。
- **预判**：两条路二选一。要兜底就把 `policyLabel` 改成 `props.run.policy?.preset === "custom" ? "自定义潜在策略" : "默认潜在策略"`（一行，语义不变），顺手让 `cacheEnabled` 在类型上也接受 `undefined`；不兜底就明确写“缺 `policy` 会渲染报错，回滚窗口内需刷新页面”，并接受该限制。我倾向前者：成本一行，和 #406 的先例一致，还能顺带覆盖“浏览器缓存了旧 JS 但 API 已回滚”的场景。
- **结论**：已按预判兜底：`policyLabel` 改为 `props.run.policy?.preset === "custom"`，缺 `policy` 时回落默认策略；Agent Note 的兼容性表述同步更正，并补旧 payload 回归测试。2026-11-20

### D2 “顺序与原型一致”是首要验收，但自动化只断言文本、没有断言顺序

- **位置**：`tests/e2e/m5-run-list.test.mjs:308-317`（按 testid 逐个取文本）、`:362-367`（逐个 `assert.equal`）；`apps/web/src/pages/evolution/components/RunCard.test.ts:85-98`；验收原文 `.agents/flow/milestones/m23-milestone.md:25`、`.agents/flow/issues/m23-run-list-prototype-alignment.md:36`。

### `apps/api/app/service/evolution/runs.py`（M）

职责：把 run 仓储 summary 投影为列表 / 详情 DTO。没有新增第三方依赖，只用了已有的 Pydantic `IdentityModel` 与 `collections.abc.Mapping`。
