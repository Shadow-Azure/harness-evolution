## §1 一页速览

一句话：给 `bad_cases` 配了一个“带书签的采购员”——书签记录已经取到哪个 id，每次只取比书签大的新书；遇到书架上已有的同名书，就换成新版而不是再摆一本。

| 交付块 | 用户能看到什么 | 验证基线 |
|---|---|---|
| 目录同步 | `bad_cases` 自动出现上游数据，无需外部直写 | 单测 + E2E + 冒烟：3 条 mock 数据落库，游标到 3 |
| 四段浮层 | 问题数量 / 问题轨迹 / 会话归一化 / 归因分析 | 组件测试 + 冒烟截图 |
| 幂等更新 | 同一 id 重复同步不增行，标题等字段被更新 | 仓储测试 + MySQL 测试 |
| 失败可见 | 页失败回滚、游标不动、状态 failed + 稳定错误码 | 服务测试 |
| 降级 | 未配置或外部表未就绪时状态可用，不 500 | 状态 API 测试 |

## §3 数据流走查

1. **启动**：lifespan 迁移 → `jobs.recover()` → `bad_case_sync.start()` → `catalog_sync.start()`。协调器先复位残留 `running`，再提交一次 job。
2. **第一页**：服务读状态表；无行则初始化 cursor=0；`mark_running`；请求 `?bad_case_id=0&offset=0&limit=200`。
3. **落库**：客户端解析并校验 items；服务映射为 `CatalogCaseRow`（时间戳缺失用本次时间）；仓储在一个事务内 upsert 整页、`COUNT(bad_cases)`、写游标与剩余量。
4. **翻页**：cursor=本页最大 id；`total == len(items)` 或空页时结束；预算/页数上限时保留 `pending` 留给下个 tick。
5. **展示**：`GET /api/acquisition/status` 返回 `synced`（COUNT）、`unsynced`（上游剩余）、归因聚合；浮层四段按序渲染。
6. **失败**：任一页异常 → 整页回滚、`mark_failed` 写稳定码；前端显示“同步失败 + 文案”，下一 tick 重试。

## §6 讨论点

### 6.1 `meta_data` 只接受对象，可能误拒上游数组/标量

- **位置**：`app/third_party_api/bad_case_query/models.py:25`
- **现象**：`meta_data` 声明为 `dict[str, Any] | None`，`extra="forbid"` 下数组或标量会整页判非法。
- **问题**：`bad_cases.meta_data` 是通用 JSON 列，06 §4.1 明确“结构不统一”；上游返回数组并不违反表契约。
- **预判**：真实联调时只要有一条 `meta_data` 为数组，整页同步失败，且错误只显示 `BAD_CASE_QUERY_INVALID_RESPONSE`，排查成本高。
- **结论**：**已修复**。改为 `Any | None`，仓储不再 `dict(...)` 强转；客户端与仓储各补一条数组用例。

### 6.2 MySQL 方言 upsert 缺自动化覆盖

- **位置**：`app/db/crud/bad_case_catalog_sync.py:292`、`tests/test_database.py`
- **现象**：仓储单测只跑 SQLite；`mysql` lane 原先只跑 `test_database.py`，不经过 `commit_page`。
- **问题**：`on_duplicate_key_update` 的写法与 SQLite 不同，CI 绿不代表 MySQL 路径可用。
- **预判**：若 MySQL 分支写错，只有生产首次同步才暴露。
- **结论**：**已修复**。在 `test_database.py` 增加 `@pytest.mark.mysql` 用例，真实 MySQL 上跑“插入 → 同 id 更新 → 行数仍为 1”。

### 6.3 status 轮询每次做 3 次 COUNT

- **位置**：`bad_case_catalog_sync_coordinator.py:149`、`crud/bad_cases.py:251`
- **现象**：每次 `/api/acquisition/status` 都 `COUNT(bad_cases)`，归因再两条 COUNT。
- **问题**：`bad_cases` 很大时，15s 轮询的成本随行数增长；设计 §6.2 明确 `synced=COUNT`。
- **预判**：当前规模可接受；数据量上来后可能成为数据库热点。
- **结论**：保留设计口径，记录为后续优化点（可改读状态表 `synced_count`，并接受外部直写造成的轻微漂移）。

### 6.4 第一页失败时 `unsynced` 仍为 0

- **位置**：`service/acquisition/bad_case_catalog_sync.py:117`
- **现象**：首轮页请求失败时状态表尚未写入 `pending_count`，前端显示“未同步 0 + 同步失败”。
- **问题**：数字与失败态并列时略有误导，但 `status=failed` 已明确表达失败。
- **预判**：上游不可用时用户可能误以为“没有剩余数据”。
- **结论**：暂不修复；失败态文案优先，后续可把 `pending_count` 改为 nullable 表示“未知”。

### 6.5 E2E 的串行断言弱于冒烟

- **位置**：`tests/e2e/m6-16-bad-case-catalog-sync.test.mjs`
- **现象**：E2E 断言 `maxActive <= 1`，0 也通过；冒烟断言 `maxActive == 1`。
- **问题**：单看该断言无法证明“确实调用了 API 2”。
- **预判**：同一测试已断言 `trajectoryCalls >= 3`，组合后可排除 0 调用。
- **结论**：接受；保留轻量 E2E，严格串行证据由冒烟报告承担。
