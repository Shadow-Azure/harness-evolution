## §1 一页速览

一句话：把 `AI_AGENT_PROVIDER`、`HE_AI_AGENT_CLAUDE_BIN`、`HE_PATCH_SOURCE_MODE` 三个运行配置从 GitHub Secrets 经既有 base64 + stdin 通道写进服务器 `.env`；Secret 缺失或为空时显式 `--unset`，让「删掉 Secret」不再留下继续生效的旧值。

比喻：这是一条**报关通道**。三个 Secret 是货主填的申报单，workflow 是报关员——把每件货装进密封袋（base64），贴上品名（键名），走同一条已经验过货的通道（SSH stdin）送到服务器；`inject-config.py` 是仓库管理员，开袋、核对品名、把货放上货架（`.env`），货主撤回申报时就按 `--unset` 把对应货位清空。日志是回执，只写「今天送了几件」，不写袋子里是什么。§6 点 1 要问的是：当一件货的包装破了（值里带换行），管理员拒收并喊了一声警告，但回执仍然写「3/3 已送达」——货架上留着上一批的旧货。

## §2 架构导览

### 2.1 一条已经存在的通道，三个新货位

服务器 `.env` 的写入不是本 PR 新建的：`Deploy` 早已把 `HE_DATA_DIR`、`HE_GIT_PUSH_PROVIDER`、`GIT_ASKPASS`、可选的评测三键、`HE_GIT_PROXY` 与 `HE_GIT_PUSH_TOKEN` 经同一条通道送进 `/opt/harness/shared/.env`（`.github/workflows/deploy.yml:296-314`）。`inject-config.py` 的合并语义是「stdin 里出现的键替换或追加，没出现的键原样保留」（`deploy/inject-config.py:72-85`）；`--unset` 是唯一的删除入口（`:99-105`、`:76-77`）。

这三个 AI 键的特殊性不在传输，而在**「缺失」必须被解释成删除**。旧语义下，Secret 被删除时 workflow 不发对应的行，服务器上的旧值继续生效；从 `agent-edit` 切回 `placeholder` 时，`.env` 里仍写着 `agent-edit`，服务重启后依旧按旧值走。本 PR 把「缺失」翻译成 `--unset KEY`，因此每次发布后 `.env` 的三键状态与 Secrets 一一对应（`.github/workflows/deploy.yml:316-332`）。这是 PR 的核心设计，Note 的 Problem/Decision 两段讲得最清楚（`.agents/notes/implemented/process/2026-11-22-ai-agent-secret-injection.md:9-13`）。

### 2.2 条件组装：`if` 而不是 `&&`

三个键都用 `if [ -n "${KEY:-}" ]` 而不是 `[ -n ... ] && ENTRIES+=...`（`.github/workflows/deploy.yml:318-332`）。这个选择在 `set -euo pipefail`（`:273`）下是稳妥的：`if` 的条件失败不会触发 errexit；`${KEY:-}` 也让未定义的 Secret 不会撞上 `set -u`。值经 `printf '%s' | base64 | tr -d '\n'` 压成单行（`:319`、`:324`、`:329`），既避开了 `&`/`$`/反引号/引号在 SSH 命令行里的展开，也避开了 base64 的 76 列换行。

`ENTRIES` 是数组（`:296-298`），`UNSET_ARGS` 是空格连接的字符串（`:303`、`:307`、`:314`、`:321`、`:326`、`:331`）。这种不对称不是疏忽：`ENTRIES` 以 `printf '%s\n' "${ENTRIES[@]}"` 逐行喂给 stdin（`:338`），数组天然按元素分行；`UNSET_ARGS` 最终被拼进远端命令行 `python3 ... $UNSET_ARGS`（`:339`），字符串直接展开即可。代价是 `$UNSET_ARGS` 未加引号、按空白分词，且远端命令是一个双引号字符串——今天拼接进来的只有三组固定字面量（键名是 `[A-Za-z_][A-Za-z0-9_]*`），没有用户输入，所以安全；未来若把键名或值动态拼进去，就会多一个 shell 注入面（点 3）。

### 2.3 服务器侧落盘：解码、校验、跳过、原子替换

`inject-config.py` 的 `decode_entries`（`deploy/inject-config.py:29-48`）逐行 `partition(" ")`，先校验键名（`:36-38`），再 `base64.b64decode(..., validate=True)` 并按 UTF-8 解码（`:39-43`），最后拒绝含 `\n` 或 `\r` 的值（`:44-46`）。三类失败都只打 `::warning::` 并 `continue`，注释写明「保持服务器现状」——这正是点 1 的来源：对一个**显式存在**的 Secret，跳过等于把旧值留在服务器上。

写入走 `rewrite_env`（`:64-92`）：读旧文件、按 `=` 前的名字替换或删除、把新键追加到末尾、用同目录临时文件 `fsync` 后 `os.replace` 原子替换（`:86-92`），临时文件 `chmod 0600`（`:91`）；workflow 事后再次 `chmod 600` 并 `stat` 校验（`.github/workflows/deploy.yml:342-347`）。`--backup` 在写入前把旧文件复制到 `.env.bak.<sha>` 并 `chmod 0600`（`deploy/inject-config.py:51-61`），`release.sh` 在探活失败时用它恢复（`docs/deployment.md:61`）。实测落盘文件与备份都是 `600`（§3.3 场景 7）。

### 2.4 日志与可观测性

步骤末尾的日志（`.github/workflows/deploy.yml:350-354`）只输出 `${#ENTRIES[@]}`、`$DATA_DIR`、`$GIT_PROXY_URL`、`$GIT_PUSH_PROVIDER`、token 状态与 `AI_AGENT_COUNT/3`，没有任何 AI 值。`AI_AGENT_COUNT` 是三个 `[ -n "${KEY:-}" ]` 的加和（`:350-353`），因此它数的是「Secret 是否存在」，不是「键是否真的落盘」。当值含换行时，`inject-config.py` 跳过该键，但 workflow 仍数到 3/3，同一轮里 inject-config 自报的 `injected N config entries` 又比 `${#ENTRIES[@]}` 少一（§3.3 场景 5 的 5 vs 6）。这是点 2 的核心：日志能证明「没有泄露值」，但不能证明「配置已经生效」。

日志里的其余字段是既有行为：`$DATA_DIR` 来自 `vars.HE_DATA_DIR`（`:274`），`$GIT_PROXY_URL` 是本机回环代理（`:304`），`$GIT_PUSH_PROVIDER` 是 `github|gitlab` 枚举（`:286-290`）；这些都不是本 PR 新增的泄漏面。`$DATA_DIR，`、`$TOKEN_STATE，` 这类「变量后紧跟全角标点」的写法在 macOS bash 3.2 上会被误解析成变量名的一部分（本机实测 `DATA_DIR�: unbound variable`），Linux runner 的 bash 5 不会；新加的 `$AI_AGENT_COUNT/3` 因为后面是 ASCII `/`，在两种 bash 下都安全。这一点不影响本 PR，但值得在改这段日志时知道。

### 2.5 文档与模板：同一条事实的多个 home

三键的默认值与合法值现在至少出现在四处：`apps/api/app/config.py:158-162`（Settings 定义）、`deploy/env.production.example:82-90`（模板示例）、`docs/deployment.md:49-51`（部署说明）、Note 的 Consequences（`.agents/notes/implemented/process/2026-11-22-ai-agent-secret-injection.md:21`）；另有 `.github/workflows/deploy.yml:11-14` 的头注释与 flow issue 的复述。这些位置的措辞基本一致，但「默认 `~/.local/bin/claude`」在 `harness` 用户下不可用（点 4）；模板第 3 行「所有变量带 HE_ 前缀」也被无前缀的 `AI_AGENT_PROVIDER` 打破（`deploy/env.production.example:3`、`:88`）。文档小节本身是准确的「存在写入 / 缺失 unset / 回退 Settings 默认值 / #488 前置」，但它把「回退默认值」写成了一条可用的退路，而默认值在 API 用户的 home 下并不成立。

### 2.6 测试与门禁

`test_inject_config.py` 新增了一个种子函数与四个用例（`apps/api/tests/deploy/test_inject_config.py:30-38`、`:69-101`、`:128-136`）：三键全写、三键全 unset、部分写入 + 其余 unset、workflow 静态接线。落盘端的行为由既有 `rewrite_env` 用例覆盖；workflow 侧没有 YAML 解析，也没有 `bash -n`，只有一个以步骤名为锚点的正则（`:130`）。`pnpm test:gates`（44 pass）与 `verify:docs`（14 叶）都不解析 `deploy.yml` 的 YAML 结构，因此「测试通过」不等于「workflow 结构合法」——这次实测解析通过，但测试本身没有这个保证（点 7）。

### 2.7 合并面：本分支缺 #514

本分支的 merge-base 是 `fc5d460e`，`origin/main` 已到 `1e394620`，中间 9 个提交包含 #514 的真实 `ClaudeCodeProvider`。分支上的 `factory.py` 仍是 `_PendingClaudeCodeProvider`（`apps/api/app/third_party_api/ai_agent/factory.py:26`、`:58-61`），合并后的树会换成 `origin/main` 的 `ClaudeCodeProvider`（`origin/main:apps/api/app/third_party_api/ai_agent/factory.py:13`、`:20-24`）。因此：本 PR 的 CI 测的是「占位 provider + 注入接线」，而合并后的真实行为是「真实 provider 读取注入的三键」；`HE_AI_AGENT_CLAUDE_BIN` 在分支上是惰性的，在合并后的树中会被 `_binary()` 消费（`origin/main:apps/api/app/third_party_api/ai_agent/claude_code.py:553-557`）。这正是点 9 要讨论的验证缺口，也是点 4 为什么重要。

## §3 数据流走查

### 3.1 主线剧本（Secret → .env → Settings）

1. `Deploy` 被 main 的 CI 完成事件或手动触发（`.github/workflows/deploy.yml:17-25`），job 使用 `production` 环境（`:33`），因此 Environment 级与仓库级 Secrets 都可用。
2. 注入步骤把三键从 `secrets` 上下文取进 step `env`（`:268-270`）；未定义的 Secret 展开为空串。
3. 校验既有配置：`HE_DATA_DIR` 必须绝对、无空白/`..`、不在发布目录（`:274-285`）；`HE_GIT_PUSH_PROVIDER` 只接受 `github|gitlab`（`:286-290`）。这三键没有值校验，只有非空判断（`:318-332`）。

5. 三个 AI 键各自二选一：非空 → `ENTRIES+=("KEY base64(value)")`；空 → `UNSET_ARGS="$UNSET_ARGS --unset KEY"`（`:318-332`）。
6. `printf '%s\n' "${ENTRIES[@]}"` 通过 stdin 送到远端，命令行只出现 `--backup '$BACKUP' $UNSET_ARGS`（`:337-339`）；值不进 argv。

### 3.4 失败与回滚

值非法（例如 `HE_PATCH_SOURCE_MODE=agent-edit` 或 `gpt`）不会在注入步骤被拦截，服务重启时由 Settings 校验抛 `ValidationError`，`release.sh` 探活失败后恢复 `.env` 与上一 release（`docs/deployment.md:61`）。也就是说，非法值是「部署失败 + 回滚」，不是「静默生效」；而换行值是「跳过 + 保留旧值 + 回执 3/3」，是静默的。两者在文档里被同一句「解码失败告警跳过，写盘失败中止发布」概括（`docs/deployment.md:47`），但后果完全不同。

### 讨论点 1：值含换行时 `inject-config.py` 静默跳过，陈旧值继续生效，回执仍写 3/3

**位置**：`deploy/inject-config.py:44-46`（解码结果含 `\n`/`\r` → `::warning::` + `continue`）、`.github/workflows/deploy.yml:318-332`（只判断非空就把值放进 `ENTRIES`，没有换行校验）、`.github/workflows/deploy.yml:350-354`（计数只看 env 是否存在）、`docs/deployment.md:47`（只写「解码失败告警跳过」）与 `:51`（新小节未提换行）。

**现象**：本地用真实 `inject-config.py` + workflow 原样组装逻辑跑了场景 5：预置 `.env` 为 `HE_PATCH_SOURCE_MODE=agent-edit`，把 Secret 设成 `$'minimal-config\n'`（模拟 `gh secret set -f` 或复制粘贴带尾随换行）。结果 `HE_PATCH_SOURCE_MODE=agent-edit` 原样留在 `.env`，日志打 `::warning::HE_PATCH_SOURCE_MODE 解码结果含换行，跳过该键（保持服务器现状）`，`inject-config.py` 自报 `injected 5 config entries`，workflow 回执却是 `已注入 6 个配置变量（… AI Agent Secret：3/3）`，步骤退出码 0。也就是说：运维看到「3/3、部署成功」，服务器上却是旧值。`\r` 同理（Windows 行尾）；值含 `\n` 的 `AI_AGENT_PROVIDER` 或 `HE_AI_AGENT_CLAUDE_BIN` 也一样。

**问题**：PR 的核心承诺是「Secret 是唯一事实源，缺失即删除」。换行值既不是「缺失」，也没有被写入，落进了一个第三种状态：**Secret 存在、键未更新、旧值继续生效**。这与 PR 的动机（避免陈旧值残留）正面冲突。`inject-config.py` 的跳过策略本身有合理理由——单个坏键不应阻塞整次发布（`:11-12` 的 docstring 写明），且这个行为在 PR 之前就存在；但本 PR 把三键抬成「生产配置的唯一通道」后，这个旧策略的后果从「一个可选键没更新」升级为「AI Agent 配置静默漂移」。文档只写「解码失败告警跳过」（`docs/deployment.md:47`），没有写「含换行也会跳过」「跳过会保留旧值」，更没有写「回执仍按 Secret 数计数」。

**预判**：在 workflow 组装阶段加一道**换行/回车拒绝**，把「坏值」变成 `::error::` 并 `exit 1`（在写 `ENTRIES` 之前，对三个值统一 `case "$v" in *$'\n'*|*$'\r'*)`）。这比让 inject-config 改语义更小：它只影响本 workflow，且「显式设置了一个坏 Secret」本来就是运维需要立刻知道的事，失败比静默漂移安全。若不想让坏键阻塞整次发布，退一步：给 `inject-config.py` 加 `--strict`（或 `--fail-on-skip`），三键走 strict、其余走宽松；同时让脚本输出 `applied=`/`skipped=` 计数，workflow 用 `applied` 而不是 `ENTRIES` 长度做回执。无论选哪条，都应把「换行跳过会保留旧值」写进 `docs/deployment.md` 的注入段，并在 Note 的 Consequences 里补一句「跳过不是删除」。

**结论**：（留空，待维护者拍板）

### 讨论点 2：`AI_AGENT_COUNT/3` 只报数量，不报键名与写入/移除，且数的是「Secret 存在」而不是「已生效」

**位置**：`.github/workflows/deploy.yml:350-354`（`AI_AGENT_COUNT` 由三个 `[ -n "${KEY:-}" ]` 加和，回执拼在「已注入 N 个配置变量」后）、`deploy/inject-config.py:118-121`（脚本只输出总数，不输出逐键状态）。

**现象**：场景 1 回执 `AI Agent Secret：3/3`，场景 2 `0/3`，场景 3 `1/3`，场景 5 仍是 `3/3`（但其中一键被跳过）。回执没有告诉运维**哪一键**是 3 里的哪一个；在「全配」与「三键里有一键应被 unset」之间，`3/3` 与 `3/3` 可以对应完全不同的 `.env`。同一轮里，inject-config 输出 `injected 5 config entries`，workflow 输出 `已注入 6 个配置变量`，两个数字不一致，运维需要自己推断差额来自跳过。另一方面，日志确实没有泄露任何值（本检视对 `claude-code`、真实路径、`minimal-config` 与特殊字符串做了扫描，全部 clean），这是设计想要的效果。

**问题**：这个日志的用途是「让运维确认本次发布把哪三键设成了什么状态」。只给计数，无法回答「`HE_PATCH_SOURCE_MODE` 现在是不是 `placeholder`」「`HE_AI_AGENT_CLAUDE_BIN` 到底有没有被写入」；在点 1 的换行场景里，它还会给出与事实相反的印象。反过来，把完整值打进日志又违背「值不落日志」的边界（`AI_AGENT_PROVIDER`/`HE_PATCH_SOURCE_MODE` 是枚举，不敏感；`HE_AI_AGENT_CLAUDE_BIN` 是路径，也不敏感；但三键都被当作 Secret 管理，统一不打印是更稳的边界）。需要的是「键名 + 状态」而不是「值」。

**预判**：回执改成逐键状态，例如 `AI Agent：AI_AGENT_PROVIDER=已写入，HE_AI_AGENT_CLAUDE_BIN=已写入，HE_PATCH_SOURCE_MODE=已移除`；状态只取 `已写入`/`已移除`/`已跳过` 三个枚举，不出现值。`已跳过` 来自 inject-config 的逐键输出（建议脚本打印 `applied=KEY1,KEY2 skipped=KEY3` 到 stdout，workflow 捕获后重排），这样点 1 的静默漂移也会在回执上可见。若不想改 inject-config，至少把 `AI Agent Secret：$AI_AGENT_COUNT/3` 改成「三个键名 + 是/否」的布尔列表（`AI_AGENT_PROVIDER=set` 等），它仍然不泄露值。

**结论**：（留空，待维护者拍板）

### 讨论点 3：`UNSET_ARGS` 是空格字符串且未加引号展开；今天安全，明天是注入面

**位置**：`.github/workflows/deploy.yml:303`（`UNSET_ARGS=""`）、`:307`、`:314`、`:321`、`:326`、`:331`（字符串追加）、`:338-339`（`printf ... | $SSH_CMD ... "python3 ... $UNSET_ARGS"`）；`deploy/inject-config.py:99-105`（`--unset` 是 `action="append"`）。

**现象**：`UNSET_ARGS` 被拼成 `--unset A --unset B` 这样的字符串，最终嵌进远端命令的双引号里，由远端 bash 按空白分词。当前拼进去的只有 `HE_GIT_PROXY`、`HE_GIT_PUSH_TOKEN` 与三个 AI 键名，都是固定字面量且符合 `_ENV_NAME`，所以没有分词或注入风险；本地场景 1（单键）、场景 2/6（多键）与补测（`UNSET_ARGS` 为空串、`removed 0 keys`、退出 0）覆盖了 argc 的三种形态。`set -euo pipefail` 下，`[ -n ... ]` 作为 `if` 条件（`:318` 等）不会触发 errexit；`:351-353` 的 `[ -n ... ] && AI_AGENT_COUNT=...` 作为非末尾的 `&&` 列表也不会触发，本地全空场景退出码 0 已证实。反过来，如果未来有人把「动态键名」或「带空格的值」拼进 `UNSET_ARGS`，未加引号的展开会让它按空白拆成多个参数；远端命令字符串也会多一个 shell 注入面。

**问题**：这是一个「当前无实害、但把危险姿势固化」的维护性问题。PR 沿用了既有模式（`:303-314` 的代理/token 先例），所以不是本 PR 引入的缺陷；但本 PR 把 `UNSET_ARGS` 从 2 个键扩到 5 个键，复制这个模式的成本在上升。另一个细节是：`:351-353` 的 `&&` 写法依赖「后面还有 echo」这个位置事实；如果未来有人把 echo 删掉或把某条计数挪到末尾，最后一条失败的 `[ -n ]` 会让 `set -e` 以非零退出，而作者可能以为它和 `if` 一样安全。

**预判**：保持字符串也可以，但加两道护栏：① 在追加前对键名做一次 `case "$KEY" in *[!A-Za-z0-9_]*) echo "::error::..." ; exit 1;; esac`（或者干脆只允许常量集合），把「动态键名」挡在门外；② 用 `shellcheck` 或 `bash -n` 做 CI 检查，并在注释里写明「`UNSET_ARGS` 只允许固定键名，禁止拼值」。更彻底的做法是两边都用数组，远端用 `printf '%q '` 拼成安全的命令字符串，但这会改变远端命令的构造方式，收益（当前没有动态输入）不抵成本。计数行建议改回 `if [ -n ... ]; then AI_AGENT_COUNT=$((...)); fi`，把「位置依赖」去掉。

**结论**：（留空，待维护者拍板）

**位置**：`apps/api/app/config.py:162`（默认 `~/.local/bin/claude`）、`deploy/env.production.example:84-85`（默认值与「若与部署用户不同请填绝对路径」）、`docs/deployment.md:51`（「`~` 不展开，路径不同请设为绝对路径」）、`deploy/bootstrap-server.sh:36`（`useradd --system --no-create-home`）、`deploy/harness-api.service:12`、`:15`（`User=harness` + `EnvironmentFile`）、`deploy/install-claude-code.py:245-247`（`.claude` 目录 0700）、`.github/workflows/deploy.yml:257`（安装脚本以 `$SSH_USER` 即 `deploy` 运行）。

**关键依赖解读**：Agent Notes 的骨架是固定四段（Problem → Decision → Alternatives considered → Consequences），`process` 类目覆盖「发布/工具/流程」。这条 Note 的 Alternatives 段是本层最有价值的部分：Variables、workflow_dispatch inputs、让 inject-config 缺行即删、写死模板，四条都被否并给了理由。

**变更代码块分析**（纯新增，按四段讲）：

- Problem（`:7-9`）：把「inject-config 保留旧值」的既有语义与「删 Secret 后旧值仍生效」的后果写清楚；例子是 `agent-edit` → `placeholder` 的切换。
- Decision（`:11-13`）：三键同名、存在写/缺失 unset、base64 + stdin、日志只报计数；并明确 `agent-edit` 不在本 issue 扩展。
- Alternatives（`:15-17`）：四条被否方案；「让 inject-config 缺行即删」被否的理由（无法区分「没打算注入」与「Secret 被删除」）尤其关键，它解释了为什么意图必须留在 workflow 层。
- Consequences（`:19-21`）：每次发布显式设置/移除、删 Secret 后回退默认、注入通道不校验值、新增同源配置沿用该模式。

**检视发现**：

1. Consequences 写「删除 Secret 后重启即回退 Settings 默认值（`claude-code` / `~/.local/bin/claude` / `placeholder`）」，但没有写「`~/.local/bin/claude` 在 harness 下不可用」「默认 `claude-code` 在合并后的树里需要 CLI + settings」。这是决策记录里最容易误导后续维护者的一句（点 4）。中。
2. Decision 写「日志只报计数与状态，不出现值」；实际只报计数，没有逐键状态（点 2）。措辞略宽。低。
3. Consequences 写「注入通道不校验取值，非法值仍由服务启动校验拦截」——对非法枚举成立，但对含换行的值，注入通道是「跳过」而不是「交给服务校验」，旧值会留下（点 1）。建议补一句「跳过不是删除」。中。
4. 四段骨架、双语、配对 hash 都合规；`process` 类目选择合理（发布接线属于流程/发布）。无问题。

### `apps/api/app/config.py`（未变更，作为消费端通读）

**职责**：Pydantic Settings 的三键定义与校验。**变更形态**：未变更。

**关键依赖解读**：`pydantic-settings` 从环境/`.env` 读入，`AliasChoices` 让 `AI_AGENT_PROVIDER` 与 `HE_AI_AGENT_PROVIDER` 都能命中同一字段；`field_validator` 在构造 `Settings` 时执行，因此非法值是**启动失败**而不是运行期失败；systemd 的 `EnvironmentFile` 把 `.env` 注入进程环境，是这条链的最后一公里。

**变更代码块分析**：无 diff；需要对照的是三个字段与三个校验器：

```python
patch_source_mode: str = "placeholder"
ai_agent_provider: str = Field(
    default="claude-code",
    validation_alias=AliasChoices("AI_AGENT_PROVIDER", "HE_AI_AGENT_PROVIDER"),
)
ai_agent_claude_bin: str = "~/.local/bin/claude"
...
if value not in {"placeholder", "minimal-config"}:   # patch_source_mode，不 strip
...
normalized = value.strip().lower()                    # ai_agent_provider，strip+lower
...
normalized = value.strip()                            # ai_agent_claude_bin，strip
```

**检视发现**：

1. `patch_source_mode` 不 `strip`，`" minimal-config "` 会启动失败；provider/bin 会 strip，三者不一致。低（点 5）。
2. `ai_agent_claude_bin` 只校验非空，不校验绝对路径/存在性；默认值 `~/.local/bin/claude` 在 harness 下不可用（点 4）。中。
3. `ai_agent_claude_bin` 在合并后的树里由 `claude_code.py` 消费；本分支没有消费者，故本 PR 的测试无法覆盖「注入的值真的被 provider 用上」（点 9）。记录。
