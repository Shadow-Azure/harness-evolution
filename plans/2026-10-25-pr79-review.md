## §1 一页速览

一句话：这个 PR 给后续同步和自进化功能补上一本可恢复的任务账本，以及一套“数据库回放 + 内存广播”的实时通知系统；任务 JSON 仍是事实源，SSE 只是按一次一票的门铃通知页面刷新。

生活化比喻：`job_runs` 像办事大厅的排队号与办理记录，重启后仍能知道谁没办完；`evolution_run_events` 是每笔业务的流水账；EventBus 像大厅广播，慢听众可能漏掉“正在办理”的播报，但还能从流水账补读；一次性 ticket 则是只允许进门一次、60 秒失效的访客条。

| 交付块 | 结论 |
|---|---|
| job_runs 与双方言迁移 | 字段、索引、状态机基本完整；MySQL CI 实际通过 |
| 串行 JobRunner | 串行、去重、异常脱敏、queued 恢复和主要 cancel 路径成立 |
| 中断事件 | 启动恢复会落库，但 stage/job 关联语义有偏差；优雅停机未落库 |
| EventBus/replay | 分页 replay/live 去重与断线清理成立；多 topic 游标和队列丢事件存在边界 |

## §2 架构导览

### 2.1 组合根与生命周期

`apps/api/app/main.py:45-50` 先构造 EventBus、SQL event store 和 JobRunner，再在 `main.py:49-76` 的 lifespan 中按 database → migration → identity seed → job recovery → serve → cancel jobs → close bus → dispose database 的顺序运行。

任务状态的真实来源是 `job_runs`。事件历史另有 `evolution_run_events`，SSE 不保存第二套长期历史，只在每个连接中保存有界通知队列。

### 2.2 任务持久层

`apps/api/app/db/models/jobs.py:25-56` 定义设计要求的 job 字段，并用 `created_at DESC` 的 `(kind, created_at)` 索引支持最近任务查询。`apps/api/app/db/models/run_events.py:19-52` 对齐设计的事件列，包含 `(run_id, seq)` 唯一约束。

`0003_jobs.py:18-104` 建立两张表；`job_runs.created_by` 有真实用户外键，`evolution_run_events.run_id` 因 evolution 父表属于 m5-08 暂不建外键。这个边界在 Agent Note `2026-10-25-jobs-sse.md:13-21` 明确记录，不是静默漏项。

### 2.3 串行 runner

`apps/api/app/service/jobs.py:141-170` 在进程内 submit lock 内查重、落 queued 行并调度。`jobs.py:235-254` 再用全局 worker lock 保证串行 claim/执行/完成。

去重规则分两层：

```text
sync / evolution_retry
  同 kind + 同 ref 已有 queued/running → 复用已有 job

evolution_prepare / advance / apply / finalize
  同 run 任一步已有 queued/running → 409 RUN_BUSY
```

`apps/api/app/db/crud/jobs.py:77-103` 为所有 evolution kind 构造跨 kind 的 active 查询，避免同一 run 的 prepare 与 advance 并行。

### 2.4 重启与关闭

启动时 `jobs.py:106-139` 先把残留 running 标为 interrupted；evolution 任务先写 `run_interrupted` 事件，再向 run topic 发带 eventSeq 的通知；sync 另建一条 queued 审计记录重试。

关闭时 `jobs.py:223-247` 取消内存 task，活动 handler 捕获 `CancelledError` 并把对应 job 行标为 interrupted。queued 但尚未 claim 的 task 保持 queued，下一次启动可继续调度。

### 2.5 EventBus 与 replay

`apps/api/app/service/events.py:101-178` 为每个连接建一个跨多个 topic 的共享队列，容量默认 100；`publish()` 不做 I/O，队列满时同步丢最旧项并记录 warning。

`stream_events()` 在 `events.py:181-253` 先建立实时订阅，再从持久 replay 分页读取，使用每个 topic 的游标过滤回放期间已经入队的重复事件。回放耗尽后进入 live queue，空闲发 ping，最后在 generator 结束或断开时移除订阅。

`apps/api/app/db/crud/run_events.py:34-89` 用 `seq > cursor`、`created_at,id` 和 `limit + 1` 分页；`record_interrupted()` 在 `run_events.py:91-129` 以当前最大 seq 加一写入中断事件。

### 2.6 ticket 与 HTTP

`apps/api/app/api/events.py:46-77` 只允许 `run:{rid}` 形状，经可注入 `RunTopicAuthorizer` 后把当前用户、topics 和 cursor 封进一次性 ticket。SSE 入口 `events.py:113-160` 只接受 query ticket；URL 上的 topic 参数会稳定返回 401。

`Last-Event-ID` 优先于 ticket cursor；非法游标返回 422，而且 parse 发生在 ticket consume 之前，错误请求不会烧掉票据。`apps/api/app/api/jobs.py:59-74` 提供受 Bearer 保护的 job REST 真值。

## §3 数据流走查

### 场景 A：提交两个同步任务

1. 调用方进入 `JobRunner.submit()`；`service/jobs.py:150-166` 先查同 kind/ref 的活跃任务。
2. 无重复时插入 queued 行，payload 先经 `sanitize_job_payload()` 递归脱敏。
3. `_schedule()` 创建内存 task；两个 task 可以同时存在，但真正执行都要先取得 `_worker_lock`。
4. handler 成功后 `complete()` 写 completed、progress=1、finished_at；失败则只持久化截断并脱敏后的 error。
5. 调用方通过 `GET /api/jobs/{jobId}` 从数据库重读真值，不依赖内存 task 是否仍在。

### 场景 B：进程重启恢复

1. 上次进程在 running 时消失。
2. 新进程 lifespan 调 `jobs.start()`。
3. `mark_running_interrupted()` 把 residual running 标为 interrupted。
4. evolution 任务通过 `SqlRunEventStore.record_interrupted()` 写一条事件，再发 `run.interrupted`。
5. sync 任务复制 payload/ref/creator 新建 queued 行，旧行仍保留 interrupted 审计。
6. `list_queued()` 重新调度所有 queued 行。

### 场景 C：SSE 首连与断线补发

1. 登录用户 POST `/api/events/ticket`，提交 run topic 和 cursor。
2. 服务端校验 topic 形状与可注入资源授权，返回 60 秒一次性 ticket。
3. EventSource 连接 GET `/api/events?ticket=…`；服务端先消费 ticket。
4. `stream_events()` 先订阅 EventBus，再分页读取 `seq > cursor` 的持久事件。
5. 回放期间新到的 live 通知已在队列中；按 eventSeq 比较可去掉重复。
6. 回放耗尽后持续输出 live queue；无消息超过心跳间隔时发 `event: ping`。
7. 浏览器断线重连时带 `Last-Event-ID`，服务端用新 ticket 和 header cursor 重放缺口。
8. generator 结束或客户端断开时，subscription 从所有 topic 反向索引移除。

### 场景 D：票据重放与非法 topic

1. ticket store 使用 HMAC 保护随机 id 和绝对过期时间。
2. GET stream 的第一次 consume 成功即从内存 grant 表删除。
3. 第二次 GET 得到 `401 TICKET_INVALID`；超过 60 秒得到 `TICKET_EXPIRED`。
4. URL 附带 `topics=` 不会扩大权限，而是直接拒绝。

## §6 讨论点

### D1 重启中断事件不符合事件字段语义，并丢失 job 关联

**位置**：`apps/api/app/service/jobs.py:109-129`、`apps/api/app/db/crud/run_events.py:91-127`、`plans/fullstack-design/06-database-design.md:535-539`

**现象**：实测插入并 claim `evolution_prepare` 后启动 runner，写出的行是 `event_stage=evolution_prepare event_job_id=None`。设计中的 stage 闭集是 `prepare/cluster/step/candidate/push/eval/apply/final`，`run_interrupted.job_id` 应与被中断的 `job_runs` 行关联。

**问题**：前端和 `/runs/{rid}/events` 按 stage 筛选、按 jobId 跳转任务详情时会失配；恢复事件成为无法回链到原执行任务的历史孤点。

**预判**：Priority P1。建议 `RunEventRecorder.record_interrupted()` 接收 job_id，并由 runner 按 kind 映射合法 stage（或由未来 evolution 服务提供 stage），补一条读取持久行并断言 stage/job_id 的回归测试。

**结论**：已修复（2026-10-25）。中断恢复按 job kind 映射到合法 `stage`，`RunEventRecorder` 接收并持久化原 `job_id`；回归测试覆盖 prepare→`prepare`、advance→`step` 以及持久行字段。

### D2 优雅停机只改 job 状态，不写 run_interrupted 历史

**位置**：`apps/api/app/service/jobs.py:223-247`、`apps/api/tests/jobs/test_jobs.py:393-413`

**现象**：实测启动一个阻塞的 `evolution_advance` 后调用 `runner.close()`，job 变为 interrupted，但 `evolution_run_events` 行数是 0。启动恢复路径会写事件，优雅关闭路径不会。

**问题**：同一个 interrupt 状态因退出方式不同产生不同历史；刷新 run 事件页时，正常重启看不到中断原因，也收不到可回放的 run.interrupted。

**预判**：Priority P1/P2。关闭路径应复用持久中断写入与发布逻辑，且先落库、后尽力发布；进程马上关闭时发布可以丢，但库中历史不能丢。补 shutdown 持久事件测试。

**结论**：已修复（2026-10-25）。启动恢复与优雅停机共用先持久化、后发布的 helper；shutdown 回归测试验证 job 状态、合法 stage、jobId 与持久事件序号一致。

### D3 多 topic 重连复用单个 Last-Event-ID 会跳过低序号 run 的事件

**位置**：`apps/api/app/service/identity/schemas.py:69-73`、`apps/api/app/api/events.py:148-158`、`apps/api/app/db/crud/run_events.py:43-48`、`apps/api/app/service/events.py:181-199`

**现象**：ticket 允许最多 32 个 topics，但 cursor 是单个整数；SSE id 又只是每个 run 自己的 `seq`。实测同一连接订阅 run:A 与 run:B、A 最后 id=100、B 仅有 1/2 时，重连头 `Last-Event-ID: 100` 会被同时当作两个 run 的游标，B 的事件全部跳过。

**问题**：当前前端只订阅一个 run，所以暂未触发；但公开 API 和内部 replay 已声明支持多 topic。任何复用这个能力的新页面都会静默丢历史，而且不会收到 reset。

**预判**：Priority P2。短期可把 M1 ticket 限制为恰好一个 run topic；若要保留多 topic，需要复合事件 id（例如带 topic）或把 ticket 扩展为按 topic 的 cursor map，不能用单整数广播给所有 topic。

**结论**：已修复（2026-10-25）。M1 ticket 契约收紧为恰好一个 `run:{rid}`，Schema 与 TicketStore 双层校验；多 topic 请求稳定拒绝。未来如需多 topic，必须设计按 topic 的复合游标，不能广播一个整数。

### D4 有界队列会丢弃“持久且关键”的完成事件，而不只是 progress

**位置**：`apps/api/app/service/events.py:130-161`

**现象**：实测 queue capacity=1 时先发 `run.completed`、再发一次 `run.progress`，最旧的 completed 被无条件丢掉，队列只剩 progress。设计说明的是进度事件可丢，不可阻塞；当前实现没有区分事件类型。

**问题**：慢页面可能错过会改变页面生命周期的 completed/failed/blocked 通知，连接仍保持，因此浏览器不会自动重连补发，只会在静默错误的旧状态上停留。

**预判**：Priority P2。建议区分“可合并 progress”和“不可静默丢失的状态事件”：保留最重要事件、对 progress 做 latest-wins，或在溢出时关闭连接并让客户端重连/走 reset。

**结论**：已修复（2026-10-25）。队列满时只淘汰最旧 `run.progress`；若无 progress 可淘汰，则保留已排队的关键事件并关闭慢连接，由浏览器重连后的持久 replay 补齐，不阻塞 producer。

### D5 当前状态文档仍声称“未具备真实 replay adapter”

**位置**：`docs/architecture.md:81-82`、`docs/architecture.en.md:81-82`、`apps/api/app/db/crud/run_events.py:15-89`

**现象**：中文和英文当前状态都写“未具备真实 event replay adapter”，但本 PR 已默认装配 `SqlRunEventStore`，并执行真实 SQLite 分页回放。

**问题**：维护者会得到相互矛盾的现状；文档门禁只能校验格式和链接，无法发现这种语义漂移。

**预判**：Priority P2 fact，不涉及运行逻辑。应删除“真实 adapter 未具备”，仅保留真正尚未具备的 m5 resource authorizer、外键和 evolution 业务。

**结论**：已修复（2026-10-25）。中英文架构现状改为 SQL replay 已具备，仅列 m5 父表关系与真实资源授权等真实缺口。

### D6 应用层 ping 与 EventSourceResponse 自带 ping 叠加

**位置**：`apps/api/app/api/events.py:152-160`、`apps/api/app/service/events.py:234-241`、`apps/api/.venv/lib/python3.14/site-packages/sse_starlette/sse.py:321,456-477`

**现象**：应用在自己的 stream 中每 `HE_SSE_HEARTBEAT_SECONDS` 发 `event: ping`；构造 `EventSourceResponse` 时没有传 `ping=0`，第三方库默认还会另起定时器，每 15 秒发一条 comment ping。实际安装版本为 sse-starlette 3.5.1。

**问题**：同一连接最多会有两套心跳；当配置不是 15 秒时还会出现两个频率。浏览器忽略 comment，所以功能不坏，但代理流量、日志和连接保活行为变得难以解释。

**预判**：Priority P3。要么关闭库自带 ping 并使用应用统一事件，要么交回库做心跳并从服务 stream 删除 ping 分支，只保留一套机制。

**结论**：已修复（2026-10-25）。保留应用层可配置 named ping，并以 `ping=0` 关闭 sse-starlette 内建 comment ping，连接只存在一套心跳。

### 已知非阻塞边界

- 默认 `ShapeRunTopicAuthorizer` 不校验 run 是否存在或已完成；单组织模型下没有跨用户数据隔离问题，但 m5 必须接真实 authorizer 才能阻止对不存在/结束 run 的订阅。
- `evolution_run_events.run_id` 暂无外键；m5 父表落地后必须补关系约束。
- SQL store 当前不产生 `stale_topics`，reset 分支只有编排测试，真实 retention/history deletion 属于后续阶段。

## §9 文件级代码分析

### `apps/api/app/service/jobs.py`（A）

职责：任务提交、全局串行执行、恢复、关闭和错误脱敏。

关键依赖：asyncio 提供单进程锁和 task；repository 隔离 SQL；EventBus 与 RunEventRecorder 通过构造参数注入，避免 runner 知道 SSE 或 evolution 表细节。

变更核心：`submit` 使用 submit lock 串行化“查重 + 插入”；`_run` 使用 worker lock 串行化实际 handler；`close` 取消所有 task，活动 handler 在 CancelledError 中写 interrupted。

检视发现：D1、D2。另有一个非阻塞健壮性点：`JobRepository.claim()` 未检查 UPDATE rowcount；正常路径由 `_schedule()` 防重，但内部重复调用会拿到未真正 claim 的 row。

### `apps/api/app/service/events.py`（A）

职责：定义 replay/recorder/authorizer 协议、连接级有界 EventBus，以及 replay → live 的 stream 编排。

变更核心：先 subscribe 再 replay，避免交接窗口丢通知；每个 topic 维护 highest event 去重；queue 满时 drop-oldest。

检视发现：D3、D4、D6。单首页面、单 topic 场景的核心逻辑正确，现有测试对分页、重复抑制、heartbeat 和 unsubscribe 有真实覆盖。

### `apps/api/app/db/crud/jobs.py`（A）

职责：job_runs 的 insert/get/active 查询和状态迁移。

变更核心：跨 evolution kind 查询活跃 ref；时间戳使用应用侧 Asia/Shanghai；claim 只接受 queued 行。

检视发现：没有直接业务缺陷。`mark_running_interrupted()` 的 docstring 说 atomically，但实现是先查 id 再逐条更新；在单进程启动阶段可接受，未来多 worker 需改成单条 UPDATE RETURNING/等价事务。

### `apps/api/app/db/crud/run_events.py`（A）

职责：真实 SQL 事件回放和 restart interruption 追加。

变更核心：按每个 topic 的 cursor 建 OR 条件，`limit + 1` 判断下一页；事件 wire object 与 `/runs/{rid}/events` 对齐；中断写入使用 max(seq)+1。

检视发现：D1、D3。max+1 在单进程单 run 顺序写时成立，m5 若允许同 run 并发 append，应改数据库序列/retry unique conflict。

### `apps/api/app/api/events.py`（M）

职责：签票与 SSE 传输适配。

变更核心：topics 形状校验、注入 authorizer、一次性 ticket consume、Last-Event-ID 优先、sse-starlette 序列化。

检视发现：D3、D6；缺失 ticket 已稳定返回 401，URL topics 注入不会扩大权限。

### `apps/api/app/api/jobs.py`（A）

职责：job REST 状态读模型。

变更核心：DB record 转 camelCase DTO；path 参数公开名为 jobId；稳定 404。

检视发现：无。响应字段与 05 §4.1 示例一致，`result/payload` 不跨越非必要 API 边界。

### `apps/api/app/main.py`（M）

职责：装配与 lifespan。

变更核心：构造 bus/store/runner，启动恢复，停机 cancel/close/dispose，挂载 jobs/events router。

检视发现：装配顺序清晰；D2 的修复应优先放进 JobRunner，而不是在组合根补特殊分支。

### `apps/api/app/middleware/auth.py`（M）

职责：将 `/api/events` 从 Bearer 公共路径例外交给 ticket 端点自己校验。

检视发现：exact-path 匹配不会误放行 `/api/events/ticket` 或其他子路径，行为正确。

### `apps/api/app/db/models/jobs.py` / `run_events.py`（A）

职责：最终 SQL schema 映射与记录转换。

检视发现：字段、唯一约束、索引与设计主体一致；run-event `run_id` 外键作为显式 m5 欠账记录。

### `apps/api/alembic/versions/0003_jobs.py`（A）

职责：双方言创建 job 与 run-event projection。

检视发现：DESC 索引和唯一约束已由 SQLite/MySQL schema 测试实际验证。m5-08 必须做 alter-FK 而不是重建同名表，否则会冲突。

### `apps/api/app/config.py`、`errors.py`、`service/identity/schemas.py`（M）

职责：增加 SSE 参数、任务错误码和 ticket input 契约。

检视发现：配置边界合理；`JOB_NOT_FOUND/RUN_BUSY` 进入 OpenAPI enum。ticket 输入允许 32 topics，见 D3。

### `apps/api/tests/jobs/**`（A）

职责：锁定串行、去重、脱敏、重启、关闭和 HTTP job state。

检视发现：主行为覆盖扎实；关闭测试只检查 job 行，没有检查持久 run event，正好遗漏 D2。没有 claim rowcount 的破坏性测试。
