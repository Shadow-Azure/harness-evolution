## §1 一页速览

一句话：把目标配置页借给 8 列表格的那段页宽还回去——它不再被 1080px 的共享阅读列锁住，而是像 V2 原型一样在 1720px 处封顶。

比喻：共享页宽像一件所有人共穿的外套，列表与管理页穿 1080px 合身；目标配置页因为多了两列，被这件外套勒住了手臂。这个 PR 只给它单独改了一只袖长，没有把全家的衣服一起改大。

| 交付块 | 内容 | 验证 |
|---|---|---|
| 页宽 | 共享规则用 `min(var(--evolution-page-max-width, 1080px), 100%)`，目标页把变量设为 1720px | 1408 下 frame 1408、内容 1360；1920 下 frame 1720、内容 1672 |
| 表格 | 8 列自然宽度回到可视宽度内，操作列不再被 scroller 裁切 | 1408 下 table `scrollWidth === clientWidth`，所有行的操作列右缘都在 scroller 内 |
| 回归 | E2E 固定 1408×788/1920×1080/1024×768，并锁住列表与管理页 1080px | `m5-target-config`、`m5-run-list`、`m7-09-workspace-admin` 通过 |
| 决策 | Note 记录“只放开单页、其余页保持 1080px” | `pnpm lint:docs` 通过 |

验证基线：基线 `53ff8532` 下 1408×788、DPR 2 测得 frame 1080、内容 1032、table 1129/996、操作列不可见；PR head 测得 1408/1360、1324/1324、操作列可见。数值来自本地真实浏览器 smoke，截图见 PR 描述。

## §2 架构导览

### 2.1 共享页宽层

`apps/web/src/styles/main.css:60-65` 的 `.workspace-main .evolution-page-frame` 是工作区壳层的共享内容列：`left: 0` 抵消 V1 的居中补偿，`width: min(var(--evolution-page-max-width, 1080px), 100%)` 与 `padding: 20px 24px 64px` 提供阅读宽度与留白。自进化列表（`apps/web/src/pages/evolution/Index.vue`）、空间管理（`apps/web/src/pages/workspaces/Admin.vue`）和目标配置（`apps/web/src/pages/evolution/targets/Index.vue`）都挂在这个 frame 上。

### 2.2 页面级修饰

新规则在 `apps/web/src/styles/main.css:67-73`：

```css
.workspace-main .evolution-page-frame.target-config-page {
  --evolution-page-max-width: 1720px;
}
```

选择器只设置自定义属性，共享规则读取它决定页宽上限：默认 1080px，目标配置页 1720px。这样改变宽度上限不需要提高选择器优先级，也不会让 ≤640px 的 `width: 100%` 媒体规则失效——媒体规则与共享规则 specificity 相同且位于后面，仍会覆盖宽度。`target-config-page` 已经是目标页根节点的既有类（`apps/web/src/pages/evolution/targets/Index.vue:140`），E2E 也在用它定位页面。

### 2.3 表格侧

`TargetTable.vue` 的 `.target-table-scroll` 是 `overflow-x: auto` 的滚动容器，`.target-table` 是 `width: 100%; min-width: 980px`（`apps/web/src/pages/evolution/targets/components/TargetTable.vue:233-243`）。本 PR 没有改它：当上游 frame 给出 1360px 内容面板时，表格自然宽 1324px，scroller 的 `clientWidth` 也是 1324px，溢出自然消失；1024 下 frame 只有 976px 内容，表格继续由这层滚动容器兜底。

### 2.4 E2E 层

`tests/e2e/m5-target-config.test.mjs:371-431` 在 1408×788 下读取 frame、内容宽、table scroller 与全部 `.row-actions` 的几何；`:439-475` 在 1920 下断言 1720/1672；`:483-509` 在 1024 下断言页面不横向溢出、表格仍可横向滚动。等待函数（`:130-139`）现在要求至少一行目标渲染完成，避免在 `LoadingSkeleton` 阶段读取 `null`。`tests/e2e/m7-09-workspace-admin.test.mjs:163` 与 `:358-362` 增加空间管理页宽度 1080px 的断言；`tests/e2e/m5-run-list.test.mjs:341` 继续锁住列表页 1080px。

## §3 数据流走查

1. 浏览器打开 `/workspaces/ws-default/evolution/targets`，Vue 路由挂载 `targets/Index.vue`，根节点带 `evolution-page-frame target-config-page`。
2. CSS 层叠：共享规则读取 `--evolution-page-max-width`；目标页把它设为 1720px，其他页没有设置，回落到 1080px。`padding` 与 `margin: 0 auto` 始终不变。
3. 在 1408 视口，frame 宽 1408、内容宽 1360；`.target-table-panel` 的 16px 内边距与 1px 边框内，scroller 可用宽度 1324px。
4. 8 列表格按 `width: 100%` 铺到 1324px，`scrollWidth === clientWidth`，所有行的操作列右缘都落在 scroller 内，横向滚动条消失。
5. 在 1920 视口，frame 在 1720px 封顶并居中，左右各 100px；在 1024 视口，frame 回到 100% 宽，内容 976px，表格重新出现横向滚动兜底。
6. 页面级 `document.scrollingElement.scrollWidth === clientWidth` 始终成立，说明放宽的是内容列而不是把文档撑宽。

## §6 讨论点

### 讨论点 1：为什么只放开目标配置页，而不是把共享 1080px 一起改成 1720px

- **位置**：`apps/web/src/styles/main.css:60-73`。
- **现象**：共享规则默认仍是 1080px，只有 `.target-config-page` 把上限变量设为 1720px。
- **问题**：issue 的根因描述把共享页宽称作上游原因；只改单页是否治标不治本？
- **预判**：issue 的影响面只描述目标配置页，且前一 bugfix（#423）的 Note 明确记录“列表/配置/管理页统一到 1720px 需要独立 issue 与产品确认”。一次性改三个页面会把本 PR 变成跨页面布局改版，超出 bugfix scope；把上限做成变量后，后续统一只需给其他页设置同一个变量，不需要重写规则。结论留给维护者。
- **结论**：（待维护者确认）

### 讨论点 2：1024 仍保留表格横向滚动是否可接受

- **位置**：`tests/e2e/m5-target-config.test.mjs:483-509`。
- **现象**：1024 下 frame 回到 100%，内容 976px，表格 `scrollWidth 1129 > clientWidth 940`，仍要横向滚动。
- **问题**：是否应该继续压缩列宽或改为卡片布局，让 1024 也不横向滚动？
- **预判**：issue 明确把 1024 下保留横向滚动列为预期兜底，且改列宽/卡片布局会改变信息结构。当前行为与验收口径一致。结论留给维护者。
- **结论**：（待维护者确认）

### 讨论点 3：E2E 把 1360/1672 内容宽写死，是否过于耦合

- **位置**：`tests/e2e/m5-target-config.test.mjs:413`、`:468`。
- **现象**：断言直接写 1360 与 1672，等于把“frame 宽 − 2×24px padding”固化进测试。
- **问题**：如果设计 token 或 frame 内边距调整，测试会先红。
- **预判**：这两个数字就是 08 §9.5 与原型当前页宽契约的体现；写死能在 padding 被误改时立即暴露偏差，属于有意的回归锚点。结论留给维护者。
- **结论**：（待维护者确认）

### 讨论点 4：表格无溢出与操作列可见是否重复断言

- **位置**：`tests/e2e/m5-target-config.test.mjs:430-431`、`:474-475`。
- **现象**：`tableScrollWidth === tableClientWidth` 成立时，最后一个单元格通常不可能被裁切；`actionsFullyVisible` 看起来冗余。
- **问题**：保留两条断言是否增加维护成本？
- **预判**：两条分别对应验收里的“无横向滚动条”和“操作列完整可见”；操作列检查改为遍历所有行，能独立暴露定位/溢出类回归（例如 sticky/absolute 或 padding 异常），保留更有诊断价值。结论留给维护者。
- **结论**：（待维护者确认）

## §9 文件级代码分析

### 9.1 `apps/web/src/styles/main.css`

职责：工作区壳层的共享页宽与页面级修饰。变更形态：M，共享规则改 1 行，新增 6 行。

旧代码：

```css
.workspace-main .evolution-page-frame {
  left: 0;
  width: min(1080px, 100%);
  margin: 0 auto;
  padding: 20px 24px 64px;
}
```

新代码：

```css
.workspace-main .evolution-page-frame {
  left: 0;
  width: min(var(--evolution-page-max-width, 1080px), 100%);
  margin: 0 auto;
  padding: 20px 24px 64px;
}

.workspace-main .evolution-page-frame.target-config-page {
  --evolution-page-max-width: 1720px;
}
```

为什么这么写：共享规则是所有工作区页面的默认值，直接改它会把列表、管理页一起变成 1720px；把上限做成自定义属性后，目标页只改一个变量，其他页继续拿默认 1080px。`min(..., 100%)` 保证 1408 下铺满、1920 下封顶、1024 下回落；≤640px 的 `width: 100%` 媒体规则与共享规则 specificity 相同且在后，因此仍然生效。实现思路总结：共享规则参数化，目标页只提供参数值。

检视发现：无。已知边界：变量名只在 `main.css` 与目标页根类名之间形成约定，改类名需同步。

### 9.2 `tests/e2e/m5-target-config.test.mjs`

职责：目标配置页的真实浏览器回归。变更形态：M，新增约 95 行。

旧断言：1408 下 frame 宽 1080、内容宽 1032、只检查页面不横向溢出。

新断言：1408×788 下 frame 1408、内容 1360、table `scrollWidth === clientWidth`、所有 `.row-actions` 的右缘不超出 scroller；1920 下 1720/1672、table 不溢出、操作列可见；1024 下 frame 1024、内容 976、table 仍横向滚动、页面不溢出。等待函数在测量前要求至少一行渲染完成，避免在加载骨架阶段解引用 null。

为什么这么写：不只断言“页面宽度变了”，而是把 issue 的三个用户可见结果——8 列可见、操作列不被裁切、宽视口不浪费页宽——分别锚定到几何量上；1024 的断言防止为了“任何视口都不溢出”而误删表格自己的滚动兜底。

检视发现：无。已知弱点：内容宽写死为 1360/1672，padding 调整时会红；这是有意的契约锚点，见讨论点 3。
