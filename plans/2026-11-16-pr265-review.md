## §1 一页速览

一句话：给空间机器上报开一条只认 `whk_` 凭据的专用入口，把额度、`badCaseId` 归属与根会话待同步标记收进同一个事务，让同一 ID 的重报成为不占额度的 upsert。

一个比喻：这个端点像小区的快递柜。凭据是一张只能开当前空间柜门的卡；额度是柜格总数；同一个快递单号重复投递只更新柜里那个包裹，不占新格；别人家的单号不能塞进这个柜子，也不能把已入柜的包裹搬走。门禁只认得这张卡，拿它去开单元门、车库门一律无效。

## §2 架构导览

### 2.1 认证边界：只给一条路由开门

中间件先拿 `request.url.path` 做精确判断：公开路径与文档路径放行，非 `/api/` 放行，然后是新加的 `_is_credential_route`（`apps/api/app/middleware/auth.py:48-55`）。这个函数要求方法严格等于 `POST`、路径匹配模块级锚定正则 `^/api/workspaces/[^/]+/bad-cases$`（`auth.py:34`）；命中就 `call_next`，完全不碰 JWT（`auth.py:70-71`）。其余请求继续走原来的 bearer 解码、`must_change_password` 与管理员路由判断（`auth.py:73-95`）。

这条豁免的设计意图是“凭据不映射用户主体”：`WorkspaceService.verify_credential` 只把 token 的 SHA-256 与 `workspace_ingest_credentials` 中未撤销的行比对，返回 `WorkspaceCredentialAccess(workspace_id, credential_id)`（`apps/api/app/service/workspaces/service.py:431-442`）。因此它不能成为任何 `request.state.principal` 的消费者。

我用 ASGI 测试客户端补了几条 PR 测试矩阵没覆盖的边：`GET` / `PUT` / `DELETE` 同一路径 → 401 `AUTH_REQUIRED`；尾斜杠 → 401；`//api/...` → 404；`.../bad-cases%2F` → 401。编码斜杠不会造成“中间件看到 A、路由器看到 B”的错位：uvicorn 的 `h11_impl.py:205` 在写 scope 前 `unquote`，Starlette 的 `URL(scope=...)` 消费同一个 `scope["path"]`（`starlette/datastructures.py:39`），中间件与路由器不会对同一次请求得出两套路径。`/api/workspaces/{wid}%2Fbad-cases` 在 ASGI 测试客户端里被归一成同一路由（201），但这取决于客户端先解码，不能单独当作 uvicorn 证据；真正的结论是两者始终读同一个已解码路径。

### 2.2 请求与响应契约

请求模型 `BadCaseIngest` 在 `apps/api/app/service/workspaces/ingest.py:25-46`：`alias_generator=to_camel` + `extra="forbid"`，没有 `populate_by_name`，所以只认 `badCaseId` 这类别名；字段长度逐项对齐 `bad_cases` 列（`bad_case_id` 64、`session_id` 36、`object_name` 128、`title` 255、`object_version`/`bad_case_agent_id`/`source` 64）。`meta_data` 是 `dict[str, Any] | None`，不是任意 JSON。

响应模型 `BadCaseIngestResponse` 继承共享的 `WorkspaceModel`（`service/workspaces/schemas.py:12-15`），因此受 `extra="forbid"` + camelCase 约束；响应体只有 `badCaseId` 与 `workspaceUsed`（`service/workspaces/ingest.py:49-53`）。路由声明默认 201，更新路径把注入的 `Response.status_code` 改成 200（`apps/api/app/api/ingest.py:99-102`），并始终写 `X-HE-Workspace-Used`。

值得一提的是，凭据依赖比 body 校验先执行：FastAPI 的 `solve_dependencies` 先递归解依赖（`fastapi/dependencies/utils.py:676`），再处理 body（同文件 `:758`）。所以“凭据错误 + body 也错误”返回 401 而不是 422——这是正确的安全顺序。

### 2.3 单事务写路径

核心在 `apps/api/app/db/crud/bad_case_ingest.py:152-189`，顺序固定：

1. `_lock_workspace`（`:191-212`）：MySQL 用 `SELECT quota ... FOR UPDATE`；SQLite 先执行 `UPDATE workspaces SET updated_at = updated_at WHERE id = :wid`。后者不是装饰：SQLite 没有行锁，这条写语句取得数据库写锁，把后续的读-判-写串行化。我实测 `with_for_update()` 在 SQLite 方言下被整个省略，而这条自赋值 UPDATE 会挡住第二个连接的写（直到 `busy_timeout=5000` 耗尽）。
2. `_existing_owner`（`:214-220`）：按 `bad_case_id` 主键读归属，读在锁之后，锁顺序 workspace → case。
3. 归属优先于额度：他空间 → `BadCaseIdConflict`；本空间 → 更新；只有新 ID 才 `_used` 与 `quota` 比较（`:167-170`）。
4. `_insert` / `_update`（`:222-271`）：`_update` 只写 `_UPSTREAM_COLUMNS`，不碰 `workspace_id`；`created_at` 与其余上游字段一起被替换。
5. 写后再次 `_used`（`:175`），作为响应体与响应头来源。
6. `insert_pending_root`（`bad_case_sync.py:139-182`）：先 `SELECT` 再 `INSERT`，撞唯一键就吞掉；`synced` 与 `failed` 行保持原状（`test_ingest_root_sync.py:40/64`）。

事务边界由 `SqlAlchemyDatabase.transaction()` 负责：正常提交，任何异常回滚（`apps/api/app/db/database.py:76-84`）。因此额度失败不会留下半条 case，root-sync 插入失败也会连同 case 一起回滚。

### 2.4 错误矩阵与 200/201

服务层把三种仓储异常翻成 `AppError`：`WorkspaceMissing → 404 WORKSPACE_NOT_FOUND`、`BadCaseIdConflict → 409 BAD_CASE_ID_CONFLICT`（`details:{badCaseId}`）、`QuotaExceeded → 409 QUOTA_EXCEEDED`（`details:{quota,used}`）（`service/workspaces/ingest.py:101-118`）。凭据缺失/未知/撤销 → 401 `CREDENTIAL_INVALID`；凭据有效但空间不匹配 → 先查空间存在性，存在 403、不存在 404（`:88-93`）。

`created` 布尔值只决定 200/201；OpenAPI 在 `apps/api/app/api/ingest.py:27-38` 同时声明两个成功响应与 `X-HE-Workspace-Used` 头，生成物见 `packages/contracts/openapi.json` 的 `/api/workspaces/{wid}/bad-cases`。`test_openapi.py:251-284` 把“无 security、两个成功响应、header integer、请求体属性集合、`additionalProperties:false`”都钉住了。

### 2.5 凭据使用记录

`last_used_at` 是诊断字段：`touch_credential` 在写事务提交之后执行，60 秒窗口内不重复写（`service/workspaces/service.py:54-58`、`:444-462`；仓储 `db/crud/workspaces.py:766-787`）。失败被吞掉，不会把已提交的上报变成 500。代价是日志里没有异常原因（见 §6.10）。

### 2.6 装配、错误码与文档

`main.py` 构造 `BadCaseIngestService`（`apps/api/app/main.py:234-238`），挂到 `app.state.bad_case_ingest`（`:470`），并注册 router（`:512`）。`errors.py:88-89` 新增两个错误码，进入共享 `ErrorCode` 枚举与 OpenAPI。文档侧 `docs/architecture.md:53` / `.en.md:53` 把数据层条目改成“凭据上报幂等 upsert，目录任务限默认空间，归因只读”；目录任务确实只写默认空间（插入省略 `workspace_id` 走 server default，更新列不含 `workspace_id`，见 `db/crud/bad_case_catalog_sync.py:24-37`、`:96-111`）。

## §3 数据流走查

一条完整主线（以“第一次上报”为例）：

```text
POST /api/workspaces/ws_1/bad-cases
Authorization: Bearer whk_...
{"badCaseId":"BC-HC-021", "sessionId":"...", "badCaseType":"self", ...}
  → AuthMiddleware 命中锚定正则，跳过 JWT（auth.py:70-71）
  → 路由依赖 credential_access（api/ingest.py:69-74）
  → bearer_credential 解析 scheme/token（api/ingest.py:60-66）
  → verify_credential 做 SHA-256 查询，未撤销才返回（service.py:431-442）
  → 凭据空间 == URL 空间？不等则 403/404（ingest.py:88-93）
  → body 校验：别名 + extra=forbid（ingest.py:25-46）
  → BadCaseIngestService.ingest（ingest.py:95-126）
  → repository.ingest 单事务（bad_case_ingest.py:152-189）
      锁空间 → 读归属 → 额度 → insert/update → 计数 → insert pending root
  → 提交后 touch_credential（60s 节流，失败只记日志）
  → 201（或 200）+ X-HE-Workspace-Used（api/ingest.py:99-102）
```

分支与实测证据：

| 条件 | 状态 | 响应 | 测试 |
|---|---|---|---|
| 新 ID，`used < quota` | 201 | `{badCaseId, workspaceUsed}` + header | `test_ingest_api.py:19` |
| 同空间同 ID | 200 | 同上，`used` 不增 | `test_ingest_api.py:48`、`test_ingest_quota.py:49` |
| 新 ID，`used >= quota` | 409 | `QUOTA_EXCEEDED`，`details:{quota,used}` | `test_ingest_quota.py:17` |
| 他空间已拥有该 ID | 409 | `BAD_CASE_ID_CONFLICT`，不搬移 | `test_ingest_conflict.py:17` |
| 凭据缺失/未知/撤销/JWT/错误 scheme | 401 | `CREDENTIAL_INVALID` | `test_ingest_auth.py:41/74/91` |
| 凭据有效、URL 为另一已存在空间 | 403 | `WORKSPACE_FORBIDDEN` | `test_ingest_auth.py:112` |
| 凭据有效、URL 空间不存在 | 404 | `WORKSPACE_NOT_FOUND` | `test_ingest_auth.py:128` |
| body 违约（额外字段/枚举/超长/snake_case） | 422 | `VALIDATION_INVALID` | `test_ingest_api.py:101` |
| 凭据用在其它路由 | 401 | `AUTH_REQUIRED` | `test_ingest_auth.py:152` |
| 尾斜杠 POST | 401 | `AUTH_REQUIRED` | `test_ingest_auth.py:162` |

我另外实测了 `GET` / `PUT` / `DELETE` 同一路径与 `.../bad-cases%2F`：全部 401；`//api/...`：404；这些不是 PR 测试矩阵的既有行（见 §6.11）。

并发语义：

- 同空间不同 ID：SQLite 由自赋值 UPDATE 的写锁串行；MySQL 由 `FOR UPDATE` 行锁串行。实测去掉 SQLite 锁后 8 并发全部 201（quota=3），加回锁后恰好 3×201 + 5×409。
- 同空间同 ID：串行后第二个请求在归属读阶段看到行，走 200，不会撞主键。
- 跨空间同 ID：SQLite 仍被全局写锁串行，第二个请求在归属读阶段看到行 → 409；MySQL 下两个事务锁的是不同空间行，会真正并发到主键，见 §6.1 的快照问题。
- 跨空间同 root：SQLite 由全局写锁串行，第二个事务在插入前就能看到已提交的 root 行；MySQL 跨空间并发时 `insert_pending_root` 的 select-then-insert 会撞唯一键，被它自己的兜底吞掉。但 `claim()` 一侧没有同样的兜底，见 §6.2。

## §5 人工验收清单

PR 描述只给了命令级验证表，没有逐条人工验收清单；下面按交付承诺、错误矩阵与设计 §4.17 整理，供本地/预发逐条勾选。

- [ ] 用空间管理员创建 `whk_` 凭据，再以 `Authorization: Bearer <credential>` 上报一条新 ID：201，body 为 `{badCaseId, workspaceUsed}`，头为 `X-HE-Workspace-Used`。
- [ ] 同一 ID 再报一次（改标题/描述/`createdAt`）：200，`used` 不变，数据库行被更新且 `workspace_id` 不变。
- [ ] 把 `quota` 调到 `used`：新 ID 409 `QUOTA_EXCEEDED`，`details` 为 `{quota, used}`；已有 ID 仍 200。

- [ ] 把凭据发到 `GET /api/workspaces`、`GET /api/workspaces/{wid}/sessions`、`POST /api/workspaces/{wid}/credentials`：全部 401 `AUTH_REQUIRED`。
- [ ] body 加 `workspaceId`、把字段改成 snake_case、把 `badCaseType` 改成非法值：均 422 `VALIDATION_INVALID`。
- [ ] 数据库里确认 `bad_case_root_sync` 出现该 root 的 `pending` 行；把它改成 `synced`/`failed` 后再上报，状态、`synced_at`、`next_retry_at` 不被重置。
- [ ] 并发压测：quota=3 发 8 个不同 ID，恰好 3 个 201、5 个 409，`COUNT(*) = 3`；MySQL lane 跑同一场景。

## §6 讨论点

### 6.1 MySQL REPEATABLE READ 下跨空间同 ID 并发的重读会读到旧快照（bug / 疑似 P1）

- **位置**：`apps/api/app/db/crud/bad_case_ingest.py:245-254`（重读在 `:248`，普通 `SELECT` 在 `:214-220`）。
- **现象**：`_insert` 捕获 `IntegrityError` 后再调 `_existing_owner` 重读。MySQL 默认隔离级别是 REPEATABLE READ；手册明确事务内所有一致性读共用“第一次一致性读”建立的快照（锁定读不是一致性读）。事务的第一次一致性读是插入前的 `_existing_owner`（`:164`），发生在竞争方提交之前；竞争方提交后本方的 `INSERT` 才因主键冲突失败，此时重读仍用旧快照，看不到赢家的行，`owner is None` 走到 `:250` 重新抛出 —— 调用方拿到 500 INTERNAL，而不是 200/409。
- **问题**：生产方言是 MySQL，而“撞主键退化为 upsert / 异空间升级为冲突”正是设计 §4.17 与 Agent Note 的核心承诺。SQLite 路径恰好不会触发：自赋值 `UPDATE` 在归属读之前就把写事务串行化；去掉锁后 SQLite 的 select 是 autocommit，重读能看见赢家（我实测 4 同 ID 在无锁下仍为 3×200）。因此这个兜底只在 MySQL 跨空间并发时可达，而 MySQL 测试没有同 ID 并发用例；覆盖率为 0（`:245-254` 零执行）。
- **预判**：这是真 bug，不是理论风险；触发条件是“两个空间几乎同时上报同一个新 `badCaseId`”。影响是偶发 500 + 客户端重试，不损坏数据。修法：把冲突后的重读改成锁定读（`.with_for_update()`，当前读能看到最新提交），或改用 `INSERT ... ON DUPLICATE KEY` + 锁定读；并在 MySQL lane 加一条跨空间同 ID 并发用例。建议合并前处理。
- **结论**：

### 6.2 `claim()` 仍假设自己是 root-sync 的唯一写入方（bug / P2，SQLite 实证）

- **位置**：`apps/api/app/db/crud/bad_case_sync.py:259-287`（无 row 时 `:271-287` 直接 `INSERT`）与新增的 `:139-182`（`insert_pending_root`）。
- **现象**：本 PR 给 `bad_case_root_sync` 增加了第二个写入方。`claim()` 仍是“先 `SELECT` 查不到再 `INSERT`”，且这段 `INSERT` 没有 `try/except`。在 SQLite 上 `with_for_update()` 是空操作（我编译确认），`claim` 的 `SELECT` 不会锁住不存在的行；如果此时上报事务插入了同一个 root 的 pending 行并提交，`claim` 的 `INSERT` 会拿到 `UNIQUE constraint failed`（我用同形的两个 SQLAlchemy session 做了最小复现）。`claim` 的调用点在 `apps/api/app/service/acquisition/bad_case_sync.py:160-165`，位于逐 root 的 `try` 之外，异常会冒出 `run()` 并让本次 job 失败；下一次 tick 再重试。
- **问题**：这是 PR 新引入的跨写入方竞态。触发前提是 root 已经在 `bad_cases` 里可见（目录任务、历史数据或更早的上报）但还没有状态行，同时有人在同一 root 下上报新 case。设计 §5.2 明确说“`pending` 可以不落库，扫描时把无状态行视为 pending”，也就是说显式 pending 写入并非必需；一旦引入，就必须和 `claim` 共用“insert-if-absent”语义。MySQL 的 RR gap lock 很可能让 `claim` 的 `SELECT ... FOR UPDATE` 挡住这个插入（未实测），但这属于方言巧合，不能作为正确性依据。
- **预判**：在 `claim` 里捕获 unique violation 并返回 `False`（让下一 tick 重新看到 pending），或让 `claim` 复用 `insert_pending_root` 的 insert-if-absent，或直接用方言 upsert；并补一条“claim 与 ingest 并发”的测试。影响限于一次同步 job tick，数据不丢。建议同 PR 修。
- **结论**：

### 6.3 两个 `IntegrityError` 兜底分支没有任何测试执行（test / P1–P2）

- **位置**：`apps/api/app/db/crud/bad_case_ingest.py:245-254`、`apps/api/app/db/crud/bad_case_sync.py:178-181`；相关用例 `tests/ingest/test_ingest_quota.py:94`、`tests/ingest/test_ingest_conflict.py:74`。
- **现象**：只跑 51 条 ingest 用例的覆盖率显示，上述两个 `except IntegrityError` 块零执行。更强的反证：我用测试插件把 `_insert` 替换成完全不捕获 `IntegrityError` 的实现，`test_concurrent_identical_reports_create_one_row` 与 `test_concurrent_cross_workspace_reports_keep_one_owner` 仍然全绿——因为 SQLite 写锁在归属读之前就串行化了，两个用例根本没走到主键冲突。MySQL 的两条用例一条是顺序的额度/冲突/幂等，一条是不同 ID 并发，没有同 ID 并发。
- **问题**：PR 最核心的并发承诺（撞主键 → 200/409、root-sync 竞争 → 保留状态）没有任何测试真正证明；测试证明的是锁，不是兜底逻辑。若按 6.1 修复，还需要一条能稳定进入该分支的用例。
- **预判**：补两类测试：仓储层用两个 session + 明确屏障强制“读到 None → 对方提交 → 插入冲突”的交错；MySQL lane 加跨空间同 ID 并发。根 sync 侧同理，让 claim 与 ingest 并发。否则这条代码路径会一直是覆盖率盲区。
- **结论**：

### 6.4 SQLite 自赋值 `UPDATE` 锁有效且承重，但把写路径变成全局串行（decision / 无实害）

- **位置**：`apps/api/app/db/crud/bad_case_ingest.py:191-212`；SQLite pragma 在 `apps/api/app/db/sqlite.py:19-40`（`busy_timeout=5000`）。
- **现象**：`UPDATE workspaces SET updated_at = updated_at` 确实取得数据库写锁（raw sqlite3 实测第二个连接被挡住）；去掉它后 8 并发 quota=3 全部 201，加回后 3×201 + 5×409。代价是每次上报把“读归属 → 判额度 → 写 → 计数 → root-sync”整段串行化，且锁等待超过 5 秒会变成 500。
- **问题**：本地/测试可接受，生产 MySQL 不受影响；这是方言固有权衡，Agent Note 已记录。需要确认的是 5 秒 `busy_timeout` 在突发上报下是否会把排队变成 500。
- **预判**：保留现状；建议把“SQLite 写锁等待上限 5s，超过会 500 而非无限排队”写进 Note 或开发文档；如果未来本地吞吐成为问题，可评估 `BEGIN IMMEDIATE`（语义相同但更直白）。不是合并阻塞项。
- **结论**：

### 6.5 `metaData` 从 JSON 收窄为 object（decision / 低）

- **位置**：`apps/api/app/service/workspaces/ingest.py:44`；列定义 `apps/api/app/db/models/domain.py:246`；目录任务 `apps/api/app/db/crud/bad_case_catalog_sync.py:53`（`meta_data: Any | None`）。
- **现象**：数据库列是 JSON，设计 §4.1 说“上报打点数据，结构不统一”，目录任务接受任意 JSON；新端点只接受 object 或 null，数组/标量直接 422。`BadCase` DTO 与 problems 侧也一直是 `dict`，所以这是“与现有读模型一致、与写入列/legacy 路径不一致”的收窄。
- **问题**：如果上游某天把 `metaData` 发成数组或字符串，上报会 422，而同样数据走目录任务能入库。需要确认这是有意的契约收窄。
- **预判**：我倾向保留 object（读模型和 TS 类型都已是 `Record<string, unknown>`），但应在 05 §3.8 明写“`metaData` 必须是 JSON object”，并在 Note 记一句；否则就改为 `Any`/JSON 值以对齐列类型。
- **结论**：

### 6.6 无时区偏移的 `createdAt` 被默认当作 Asia/Shanghai（decision / P2）

- **位置**：`apps/api/app/service/workspaces/ingest.py:46`；`apps/api/app/db/crud/bad_case_ingest.py:107`；`apps/api/app/utils/time.py:11-16`。
- **现象**：Pydantic 接受 `2026-11-09T07:58:00`（无 offset）为 naive datetime；`as_shanghai` 对 naive 值直接 `replace(tzinfo=SHANGHAI)`。如果调用方按 UTC 发 naive 时间，会落库成 +08 的 07:58，整体偏移 8 小时。设计示例全部带 `+08:00`，但 OpenAPI 只写 `format: date-time`，没有测试覆盖 naive 输入。
- **问题**：`created_at` 会参与向导时间窗（05 §4.9）和排序，静默偏移很难被发现；而且“naive = +08”是本服务内部约定，外部调用方无从得知。
- **预判**：二选一并写进契约：拒绝 naive（422，最安全）或在 05 §3.8 明写“无 offset 按 +08 解释”。我倾向拒绝；无论哪种都补一条测试。
- **结论**：

### 6.7 顺序重报也返回 200，与设计 §4.17 的措辞不一致（decision / 低）

- **位置**：`apps/api/app/api/ingest.py:100`；设计 [05 §4.17](fullstack-design/05-api-design.md)（“同一 `badCaseId` 并发插入撞主键时退化为 upsert，返回 `200`”）。
- **现象**：实现对所有“已存在且属于本空间”的重报都返回 200；设计只把 200 写在并发撞主键的场景，幂等段没有说顺序重报的状态码。
- **问题**：客户端可能把 200 理解成“发生了并发竞争”，从而做多余的告警；契约读者也会疑惑。
- **预判**：200 用于所有 upsert 更自然；建议把 05 §4.17 改成“同空间同 ID 重报（无论是否并发）→ 200”，并在 Note 同步一句。
- **结论**：

### 6.8 设计写“异步标记”，实现是同一事务同步写（fact / 低）

- **位置**：`apps/api/app/db/crud/bad_case_ingest.py:176`；设计 [05 §4.17](fullstack-design/05-api-design.md)（“写入成功后异步标记该 `sessionId` 待补轨迹”）。
- **现象**：实现在写 case 的同一事务里 `insert_pending_root`，提交前完成；这比“异步标记”更强（不会出现已提交 case 缺 root 标记的窗口），Agent Note 的 Alternatives 也解释了为什么拒绝独立事务。
- **问题**：设计文字与实现机制不一致；后续读者可能以为有 outbox/异步任务的预留。
- **预判**：设计文字改为“同一事务 insert-if-absent 标记”，并引用 11 §5.2 允许显式 pending 行；这是文档对齐，不是实现问题。
- **结论**：

### 6.9 403/404 区分让持凭据者可枚举空间（security decision / 低，已被 Note 记录）

- **位置**：`apps/api/app/service/workspaces/ingest.py:88-93`；Note 的 Consequences。
- **现象**：凭据有效但 URL 空间不匹配时，空间存在 → 403、不存在 → 404；任何有效凭据持有者都能探测任意空间 id。未认证调用仍是统一 401（凭据先校验）。
- **问题**：这是设计 §4.17 明确要求的错误矩阵，不是实现漂移；但它确实提供了存在性 oracle。若空间 id 可猜（fixtures 用 `ws-harness` 这类短 id），枚举成本很低。
- **预判**：按设计保留；如果未来在意枚举，可改为“mismatch 一律 404”（需要改设计）或加按凭据的速率限制。建议把“无速率限制、无请求体上限”一并写进 Note 的欠账。
- **结论**：

### 6.10 `touch_credential` 失败只记 warning，异常原因丢失（bug / 低，可观测性）

- **位置**：`apps/api/app/service/workspaces/service.py:458-462`。
- **现象**：`except Exception:` 只输出 `"workspace credential last-used update failed"` 与 `credential_id`，没有 `exc_info=True`，也没有 `str(exc)`；数据库异常的原因被丢弃。这段在事务提交后执行，吞异常本身是对的，但排障时看不到为什么失败。
- **问题**：恰好在数据库不健康时最需要这条信息；只记一个没有原因的 warning。
- **预判**：加 `exc_info=True`（或 `error=str(exc)`），不影响响应；可再加一个计数器。属于小修。
- **结论**：

### 6.11 “凭据不到别处”与 body 拒收的测试矩阵有缺口（test / 中低）

- **位置**：`apps/api/tests/ingest/test_ingest_auth.py:152-179`、`apps/api/tests/ingest/test_ingest_api.py:101-143`。
- **现象**：(a) 越权矩阵只有 `POST .../bad-cases/` 一条同路径负例，没有 `GET` / `PUT` / `DELETE` 同路径（我实测都是 401，但没被测试钉住）；(b) snake_case 参数把 camelCase 必填字段全部拿掉，失败原因同时包含“缺少别名”和“多余字段”，没有单独证明“在合法 camelCase body 上多带一个 `workspace_id` 会被拒”；(c) 没有“凭据缺失 + body 也非法 → 401（凭据先于 body）”的顺序断言；(d) 节流测试直接给仓储传 `not_before`，没有钉住 service 的 `CREDENTIAL_TOUCH_SECONDS = 60`——把它改成 0 或 3600 该测试仍绿；(e) 200 更新路径没有断言 `workspace_id` 不变（只在冲突用例里断言了 owner 行未被覆盖）。
- **问题**：这些不是当前行为的缺陷（行为正确），而是回归保护不足；未来改中间件正则或模型配置时可能悄悄放宽。
- **预判**：补三行矩阵（GET/PUT/DELETE 同路径）、一个“合法 body + `workspace_id` 额外字段”的参数、一个“坏 body + 缺凭据 → 401”、一个“改标题/时间戳的 200 重报后 `workspace_id` 仍等于原空间”的断言；节流用例改为通过 service 调两次并断言第二次返回 False。成本很低。
- **结论**：

### 6.12 重复的上游列清单、测试专用仓储入口与 bearer 解析（simplification / 低）

- **位置**：`apps/api/app/db/crud/bad_case_ingest.py:24-36` 与 `apps/api/app/db/crud/bad_case_catalog_sync.py:24-37`；`apps/api/app/db/crud/bad_case_sync.py:208-220`；`apps/api/app/api/ingest.py:60-66` 与 `apps/api/app/middleware/auth.py:73-75`。
- **现象**：两条写入路径各自维护“全部上游字段”清单（一个含 `updated_at`、一个不含），新增列时容易只改一边；`ensure_pending` 只有测试调用，却作为生产仓储方法存在；bearer 解析在中间件与端点各写了一遍。
- **问题**：`_UPSTREAM_COLUMNS` 漂移会直接破坏“重报更新全部上游字段”的契约；另外两处是小维护成本。
- **预判**：抽一个共享的 `UPSTREAM_BAD_CASE_COLUMNS`（或从表列减去 server-owned 推导），两条写入路径复用；`ensure_pending` 要么接入生产路径，要么改成测试 helper；bearer 解析抽到共享函数。都不影响当前行为。
- **结论**：

### 6.13 响应头在 OpenAPI / 生成类型中声明为 number，运行时是字符串（fact / 低）

- **位置**：`apps/api/app/api/ingest.py:22-25`；`packages/contracts/openapi.json` 的 200/201 header；`packages/contracts/src/generated/api.d.ts:6087` 与 `:6098`。
- **现象**：`_USED_HEADER_SCHEMA` 的 `schema.type` 是 `integer`；运行时 `response.headers[...] = str(...)`，测试也断言 `response.headers["x-he-workspace-used"] == "1"`；openapi-typescript 因此把 `"X-HE-Workspace-Used"` 生成为 `number`。HTTP 头值在线上永远是字符串。
- **问题**：生成类型说 number、实际拿到 string；严格按类型使用的调用方可能直接做数值运算而踩空。`test_openapi.py:259` 反而把 integer 钉住了。
- **预判**：改成 `type: string` 并在描述里写“十进制整数”（或加 `pattern: ^[0-9]+$`）；若坚持 integer，则应在契约说明里写清“工具需自行解析”。无数据风险，属契约精度问题。
- **结论**：

### 6.14 配额只约束凭据上报，目录任务仍可把默认空间推过 quota（fact/decision / 低）

- **位置**：`apps/api/app/db/crud/bad_case_catalog_sync.py:292-301`（目录 upsert）与 `apps/api/app/db/crud/bad_case_ingest.py:167-170`（ingest 额度判定）；设计 [06 §4.1](fullstack-design/06-database-design.md) 只写“目录任务限默认空间”。
- **现象**：目录任务按主键 upsert `bad_cases`，不查 `workspace.quota`；插入省略 `workspace_id`，落到 server default 的默认空间。ingest 的 `used` 是 `COUNT(workspace_id)`，因此默认空间可以被目录任务推到超过 quota，`workspaceUsed` 也会如实返回大于 quota 的数。两者也不共享 workspace 行锁，默认空间上并发的 ingest 可能读到目录任务提交前的计数。
- **问题**：`quota` 的实际语义是“凭据上报的准入上限”，不是“空间容量的硬上限”。这一点在 05/06 没有明写，容易被读成后者。
- **预判**：设计已限定目录任务只写默认空间，大概率是有意为之；建议在 06 §4.1 或 architecture 里写清“quota 只约束 ingest，legacy 目录任务不受其约束”，并在启用目录同步时确认默认空间超限可接受。不是本 PR 的回归，也不是合并阻塞项。
- **结论**：

### 9.8 `apps/api/app/db/crud/integrity.py`（A）

职责：跨方言识别 `IntegrityError` 是否为唯一键冲突。新增文件。

关键依赖：SQLAlchemy `IntegrityError.orig`（底层驱动异常）。它相当于一个“错误文案翻译层”，因为 SQLite/MySQL 没有共享错误码。

变更块：

```python

    message = str(error.orig).lower()
    return any(marker in message for marker in _UNIQUE_MARKERS)
```

这在做什么：把 SQLite 的 `UNIQUE constraint failed` 与 MySQL 的 `Duplicate entry` 归一成布尔值，供四个仓储模块共用。
