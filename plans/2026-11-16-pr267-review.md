## §1 一页速览

一句话：把空间 Session 列表从“默认最多 100 条、按标题/ID 子串猜”改成“默认最近 10 条、输入完整 root ID 精确命中”，并在同一响应里给出两个服务端口径的数：当前筛选下匹配多少条（`total`）和空间里还有多少根会话没归一化轨迹（`pendingSessions`）。

一个比喻：这个端点像图书馆的借阅台。以前它把整排书架推到你面前，让你在书名里猜；现在只递最近上架的十本，另配一个索书号检索窗——索书号必须写全，大小写和首尾空格不管，但写半截或写书名都借不到。`total` 是这一排（已上架）的总册数，`pendingSessions` 是还在编目、只报数不借出的书；两者不是同一批书，所以不能直接相加。

## §2 架构导览

### 2.1 两个端点、一条服务路径

V1 `GET /api/sessions` 与 V2 `GET /api/workspaces/{wid}/sessions` 共用 `SessionService.list` 和 `SessionListResponse`，差异被压缩成两个开关：`exact_query` 与 `limit`。V1 的 handler 显式传 `exact_query=False`、默认 `limit=100`（`apps/api/app/api/sessions.py:53-70`）；V2 的 handler 把 `q` 先 `strip()`，默认 `limit=10`，显式 `exact_query=True`（`apps/api/app/api/sessions.py:119-138`）。V2 的 workspace 作用域由 `require_workspace_role("viewer")` 授权后构造 `WorkspaceReadScope.for_workspace(access.workspace_id)`（`:137`），因此“能读哪个空间”不落在 SQL 文案里，而落在 scope 对象里。

这个设计把“两个端点的检索语义不互相污染”变成显式参数，而不是靠两个 handler 各拼一套 SQL；代价是 `SessionFilters` 多了一个布尔位，且默认值 `False` 对 V2 是危险默认（见 §6.10）。

### 2.2 谓词唯一来源：`_session_conditions`

列表和计数共用同一个谓词构造器 `_session_conditions`（`apps/api/app/db/crud/sessions.py:201-226`），顺序固定：作用域 → `q` → `status`。`q` 有两个分支：精确模式下 `func.lower(session_families.c.id) == exact.lower()`（`:210-213`），模糊模式下沿用旧的 `search_text LIKE` 或 `lower(id) LIKE`，并复用 `_escape_like`（`:214-221`）；`status=problem` 展开为 `partial`/`fail` 的 `IN`（`:222-223`）。列表（`:243-281`）和 `count_sessions`（`:283-307`）都只消费这个列表，因此 `total` 与 `items` 的筛选口径在结构上不会漂移——这是本 PR 最值得肯定的实现选择。

`count_sessions` 只是 `select(func.count()).select_from(session_families).where(*conditions)`，没有 `limit`、没有 `order by`，所以 `total` 天然忽略分页（`:294-305`）。

### 2.3 作用域的组合方式：半连接而不是 join

`WorkspaceReadScope.session_condition()` 返回 `session_families.id IN (SELECT bad_cases.bad_case_session_id FROM bad_cases WHERE <workspace predicate>)`（`apps/api/app/db/crud/read_scope.py:58-64`），workspace 谓词本身是 `column == workspace_id`，用户作用域则是 `column IN (SELECT workspace_id FROM workspace_members WHERE user_id = …)`（`:46-56`）。

这里用 `IN` 子查询而不是 join 是关键：同一个 root 在一个空间里可能被上报多条 bad case（corpus 的 session 1 就有 `badcase-synthetic-0001` 与 `0005` 两条）。join 会让该 root 在 `items` 里出现两次、让 `total` 多算；`IN` 是半连接，天然去重。我在临时库里构造“同一 root 在 A 有 2 条 case、在 B 有 1 条”后实测：A 的 `items` 各出现一次、`total=4`（不是 5）、卡片 `stats.badCases` 分别按空间是 2 和 1；精确 `q` 也只返回一行。跨空间隔离因此是“按空间投影”，不是“root 独占一个空间”：共享 root 在两个空间都可见，但每个空间只看到自己的 case 计数与 tree（既有用例 `tests/m7-06-session-workspace-scope/test_session_scope.py:237-279` 已钉住 tree/bad-cases，本 PR 新增的 total/pending 没有在这里加断言，见 §6.3）。

### 2.4 两个计数器

`total` 是“当前筛选下已归一化根的数量”，`pendingSessions` 是“当前空间里被 bad case 提到、但 `session_families` 还没有对应行的根的数量”。后者没有复用 `session_condition()`，而是直接从 `bad_cases` 出发：`scope.condition(bad_cases.c.workspace_id)` + `NOT EXISTS (SELECT session_families.id WHERE session_families.id = bad_cases.bad_case_session_id)`，再 `COUNT(DISTINCT bad_case_session_id)`（`apps/api/app/db/crud/sessions.py:309-324`）。

三个细节值得记住：第一，`NOT EXISTS` 只按 id 关联、不再按空间过滤，这是正确的——families 是全局读模型，没有“空间归属”；第二，`DISTINCT` 保证同一根的多条 case 只算一次；第三，pending 完全不接收 `query`/`status`，所以搜索无结果时角标仍然显示（Note 的 `Consequences` 明确说这是有意的）。实测：A 空间 12 条已归一化根 + 1 条 pending 根（给了 2 条 case）时，`total=12`、`pendingSessions=1`。

### 2.5 服务装配与响应

`SessionService.list` 先取当前页 `records`，再用当前页 id 做一次 `bad_case_counts`，然后 `count_sessions`、`count_pending_sessions`，最后组装 `SessionListResponse(items=…, total=…, pending_sessions=…)`（`apps/api/app/service/sessions/service.py:195-225`）。响应模型 `SessionListResponse` 在 `IdentityModel` 之上增加两个 `Field(ge=0)`（`apps/api/app/service/sessions/schemas.py:45-50`），序列化仍走共享的 camelCase 别名，所以 JSON 是 `total` 与 `pendingSessions`。

装配处 `app.state.sessions = SessionService(SessionRepository(...))` 只在应用创建时执行一次（`apps/api/app/main.py:232`、`:468`），因此 repository 上的 `_bad_cases_ready` 探测缓存是进程级缓存，而不是请求级。

### 2.6 契约生成

`apps/api/app/api/sessions.py:21` 的 `SessionQuery = Annotated[str, Query(max_length=512)]` 被两个端点共用；V2 handler 的默认值 `10` 进入 OpenAPI 参数 schema。`packages/contracts/openapi.json` 里 `SessionListResponse` 的 `properties` 增加 `total`/`pendingSessions`，`required` 变为三项；`api.d.ts` 同步为必填 number。`test_openapi.py:293-313` 与 `test_latest_ten.py:453-479` 两处都断言了字段集合、required 和两个 `limit` 默认值——重复但有效。

契约里没有变的是 `q`：两个端点的 `q` schema 完全相同（`default: ""`、`maxLength: 512`、无 description），读者无法从 OpenAPI 分辨 V1 模糊与 V2 精确（见 §6.6）。

### 2.7 缺表降级与缓存

`_scoped_reads_available` 用 `inspect(connection).has_table("bad_cases")` 探测外部表，结果缓存在 repository 实例上（`apps/api/app/db/crud/sessions.py:237-241`；探测实现 `apps/api/app/db/crud/read_scope.py:67-82`）。三个读路径（list/count/pending）都在入口处短路返回空或 0，所以新安装在 `bad_cases` 未 bootstrap 时不会 500。代价是进程启动后表才被创建/删除时需要重启才会重新探测；Note 的 `Consequences` 已记录，这是既有读路径的行为，不是本 PR 新增。

### 2.8 现有 Web 消费者：两个 headline 变化都还没落到页面

`apps/web/src/pages/sessions/Index.vue:65-77` 的过滤器写死 `limit: 100`，所以“默认 10 条”对现有页面不生效；`components/SearchBox.vue:31-33` 的 placeholder/aria-label 仍写“搜索标题、仓库或根会话 ID”，而 `Index.vue` 的 300ms 防抖会把任意输入原样作为 `q` 发给 V2。本 PR 把 V2 `q` 改成完整 ID 精确后，页面上的标题/仓库搜索会得到空结果；同分支的 `eec017d` 把 e2e 从 `example-repo` 改成完整 root ID（`tests/e2e/m3-session-browser.test.mjs:449-470`），CI 绿了，但页面行为没变。m8-05 之前这是 main 上的过渡期错位（§6.1）。

## §3 数据流走查

一条完整主线（“用户在空间 A 粘贴一个完整 root ID 回车”）：

```text
GET /api/workspaces/ws-a/sessions?q=10000000-0000-4000-8000-000000000001&status=all
  → AuthMiddleware 解 JWT（sessions 路由不在凭据豁免名单）
  → require_workspace_role("viewer") 授权并返回 WorkspaceAccess（api/sessions.py:122）
  → handler：q.strip()、limit=10、exact_query=True（api/sessions.py:126-136）
  → WorkspaceReadScope.for_workspace(access.workspace_id)（api/sessions.py:137）
  → SessionService.list：再 strip 一次（service.py:201）
  → repository.list_sessions（crud/sessions.py:243-281）
      _session_conditions：scope IN 子查询 + lower(id)=lower(q) + status
      ORDER BY started_at DESC, id ASC LIMIT 10
  → repository.bad_case_counts(当前页 id, scope)（crud/sessions.py:427-448）
  → repository.count_sessions(同一谓词, 无 limit)（crud/sessions.py:283-307）
  → repository.count_pending_sessions(scope)（crud/sessions.py:309-324）
  → SessionListResponse(items, total, pendingSessions) 按 camelCase 序列化
```

用测试 fixture 的真实数字（`tests/workspaces/latest_ten_support.py:14-18`）：A 空间有 12 条已归一化根（session 1 带 2 条 case），另有 1 条没有 families 行的 `PENDING_ROOT`。于是：

| 请求 | `items` | `total` | `pendingSessions` |
|---|---|---|---|
| 无 `q` | 最新 10 条（`LATEST_TEN`） | 12 | 1 |
| `limit=5` | 前 5 条 | 12 | 1 |
| `q=<最老根的完整 ID>` | 只该根 | 1 | 1 |
| `q=<该 ID 的前 24 位>` | `[]` | 0 | 1 |
| `q="示例会话"`（标题） | `[]` | 0 | 1 |
| `q="   "`（全空白） | 最新 10 条 | 12 | 1 |
| `q=<只在 B 的 root>` | `[]` | 0 | 1 |
| 删掉 `bad_cases` 表 | `[]` | 0 | 0 |

分支与实测证据：

| 条件 | 结果 | 测试 |
|---|---|---|
| V2 默认（无 q） | 10 条 + total 12 + pending 1，pending 根不在 items | `test_latest_ten.py:164-180` |
| `limit=5` | items 5、total 仍 12 | `:183-199` |
| 完整 ID、大小写混合、首尾空格、不在最新 10 内 | 命中 1 条，total 1 | `:202-221` |
| 部分 ID / 标题片段 | items `[]`、total 0，pending 不变 | `:224-248` |
| 他空间 root | A 查不到；B 查得到；B 默认页只有它 | `:251-281` |
| `q` + `status` 组合 | ok 0 / partial 1 / problem 1 / fail 0 | `:284-327` |
| 只有 pending 的 root 作 `q` | items `[]`、total 0、pending 1 | `:330-347` |
| 全空白 `q` | 等同无 q | `:350-367` |
| `started_at` 相同 | 按 id 升序 | `:370-395` |
| 外部表缺失 | 200 + 全零 | `:398-410` |
| V1 | 模糊标题/ID、13 条、total 13、默认页大小 100 | `:413-450` |
| 现有 Web 搜索框输入 `example-repo` / 标题片段 | `items=[]`、total 0（页面仍承诺可搜标题/仓库） | `eec017d`；`SearchBox.vue:31-33` |

并发/快照语义：这四个读查询各自 `async with self._database.session()`（`crud/sessions.py:279`、`:306`、`:323`），因此 `items`/`total`/`pending` 不是同一快照；`replay` 或上报恰好落在两次查询之间时，可能出现 `total < len(items)` 或 pending 与页内数据不一致。它不影响正确性口径，但和 tree 路径“一个读事务”的既有约定不一致（见 §6.7）。

### 6.4 V1 冻结端点被共享 DTO 改形，设计文字仍写 `{items}`（decision + fact / P2）

- **位置**：`apps/api/app/service/sessions/schemas.py:45-50`；`apps/api/app/api/sessions.py:53-70`；设计 [05 §4.2](fullstack-design/05-api-design.md)（响应 `{ "items": [SessionListItem] }`）、[05 §4.18](fullstack-design/05-api-design.md)（“V1 无前缀的 `GET /api/sessions` 冻结保留一个版本”）、[13 §5](fullstack-design/13-root-session-id.md)（“不改 `GET /api/sessions` 的请求/响应模型”）。
- **现象**：`SessionListResponse` 被 V1/V2 共用，新增两个必填字段后 V1 也返回 `total`/`pendingSessions`；`api.d.ts` 把两字段标成 required。V1 的 `pendingSessions` 是“当前用户全部可见空间按根去重”的全局数，而 V2 是单空间角标——同一个字段名，两种集合。设计 05 §4.2 与 13 §5 没有同步，OpenAPI 的 DTO 描述“workspace-wide counters”在 V1 上也不准确。
- **问题**：这是 additive 契约变化（严格校验封闭响应体的旧客户端会看到多余字段），但“冻结端点”至少应在设计文档里同步，否则“冻结”二字名不副实；同时两个端点共享一个 DTO 让 V1 被迫计算两个它未必需要的聚合查询。
- **预判**：我倾向保留 additive（Note 已记录，仓库内没有构造该响应的消费者），但补 05 §4.2 与 13 §5 的说明，并把 DTO 描述改成中性表述；若维护者要严格冻结，则给 V1 单独一个只含 `items` 的响应模型，代价是契约与前端类型分叉。非合并阻塞项。
- **结论**：2026-11-16 已修：保留 additive；05 §4.2 与 13 §5 写明 V1 新增 `total`/`pendingSessions`（V1 pending 为可见空间并集去重，V2 为单空间根数）；`SessionListResponse` docstring 改为中性的 "One current page plus counters"。

### 6.5 `total` 只数已归一化根、不含 pending，这个口径没有写成公式（decision / 低）

- **位置**：`apps/api/app/db/crud/sessions.py:283-307`；`apps/api/app/service/sessions/service.py:214-225`；设计 [06 §7.5](fullstack-design/06-database-design.md)、[08 §5.2.1](fullstack-design/08-frontend-implementation.md)。
- **现象**：A 空间有 12 条已归一化根 + 1 条 pending 根，响应是 `total=12`、`pendingSessions=1`。08 §5.2.1 说标题区显示“最新 10 / 总数 N”，并在 `pendingSessions>0` 时追加“N 个待同步”；读者容易把“总数”理解成 13（含 pending 的全部上报根）。
- **问题**：`total` 与 `pendingSessions` 不是同一集合的划分：pending 不受 `q`/`status` 影响，`total` 受；两者不能直接相加得到“全部根”。设计没有把这句话写成公式，UI 与后续 m8-05 很容易按“total+pending”做展示。
- **预判**：保留 `total` = 当前筛选下已归一化匹配数，并在 08 §5.2.1 / 05 §4.18 / Note 明写“`total` 不含 pending，pending 与 `q`/`status` 无关，二者不可相加”；若产品要“全部根”语义，应新增字段（如 `reportedSessions`）而不是改 `total`。
- **结论**：2026-11-16 已修：05 §4.18、08 §5.2.1 与 owning Note 写明公式——`total` 只数当前 `q`/`status` 下已归一化的根且不含 pending，`pendingSessions` 与 `q`/`status` 无关，二者不可相加。

### 6.6 `q` 的精确语义在 OpenAPI 中没有 description，两个端点的 `q` 在契约里无法区分（fact / 中低）

- **位置**：`apps/api/app/api/sessions.py:21`；`packages/contracts/openapi.json` 的 `/api/sessions` 与 `/api/workspaces/{wid}/sessions` 的 `q` 参数；`packages/contracts/src/generated/api.d.ts:2847-2857`。
- **现象**：两个 `q` 的 schema 完全相同（`default: ""`、`maxLength: 512`、无 description）；实际语义相反：V1 是 `search_text` + `id` 子串模糊，V2 是完整 root ID 精确（`lower(id)=lower(trim(q))`，大小写不敏感）。`total`/`pendingSessions` 也没有 description，生成类型只有 `/** Total */` 与 `/** Pendingsessions */`。
- **问题**：前端/外部只看 OpenAPI 无法知道“V2 传子串会得到空结果”，也无法知道 trim 与大小写规则；设计 05 §3.10 写了精确查询，但契约没有落。这个参数是本次行为变化的核心，契约描述缺失会让 m8-05 或外部调用方按旧习惯传片段。
- **预判**：给 V2 的 `q` 加 `description`（“完整 root session ID；trim 后大小写不敏感精确匹配；子串/标题不命中”），给 `total`/`pendingSessions` 加一句口径说明，重跑 `pnpm contract:generate`；低成本、无行为变化。
- **结论**：2026-11-16 已修：V2 `q` 与 `total`/`pendingSessions` 增加 OpenAPI `description`，`pnpm contract:generate` 重生成 `openapi.json` 与 `api.d.ts`；`test_openapi.py` 增加 description 断言，V1 `q` 保持无 description。

### 6.7 列表响应由 4 个独立数据库会话拼成，不是单一快照（decision / 低）

- **位置**：`apps/api/app/service/sessions/service.py:202-220`；`apps/api/app/db/crud/sessions.py:279`、`:306`、`:323`；既有约定 `apps/api/tests/m2-06-session-query-api/test_sessions_api.py:426-449`（tree 必须只开一个 repository session）；会删 `session_families` 的重放路径 `apps/api/app/db/crud/acquisition_replay.py:596-602`。
- **现象**：`items`、当前页 case 计数、`total`、`pendingSessions` 各开一个 `database.session()`。并发 replay 会在 `_delete_root_tree` 里 `delete(session_families)` 再重建（`acquisition_replay.py:596-602`），恰好落在两次查询之间时可能出现 `total < len(items)`，或 pending 与页内/总数口径短暂不一致。tree 路径已经用单 session 修过同样的“混合快照”问题，并有测试钉住。
- **问题**：响应把 `total` 当“权威值”，但没有快照保证；读多写少、窗口毫秒级，当前无实害，但与仓库已有的“一个读事务”约定不一致，且新增的两个聚合查询放大了窗口。
- **预判**：可接受现状并在 Note 的 Consequences 写明“这几个数来自不同快照”；若追求严格一致，把四个查询收进一个 session（像 `tree_snapshot` 那样），并加一条“只开一个 session”的计数测试。不是合并阻塞项。
- **结论**：2026-11-16 已修（仅文档）：owning Note 的 Consequences 记录 `items`/当前页 case 计数/`total`/`pendingSessions` 来自不同读会话、不是单一快照，并引用 tree 路径 `tree_snapshot` 先例与重放删除重建的毫秒级窗口；按决定不新增快照机制。

### 6.8 索引/查询计划只有说明没有验证，Note 对 `lower(id)` 的判断比实测更悲观（testing + fact / 低）

- **位置**：`apps/api/app/db/crud/sessions.py:309-324`；索引 `apps/api/alembic/versions/0014_v2_workspaces.py:36-40`；Note `Consequences` 第 2 条（`2026-11-16-workspace-session-latest-ten.md:36`）。
- **现象**：我用临时 SQLite 库实测：pending 查询走 `SEARCH bad_cases USING COVERING INDEX ix_bad_cases_workspace_session (workspace_id=?)` + `SEARCH session_families USING COVERING INDEX sqlite_autoindex_session_families_1 (id=?)`；精确列表走 `SEARCH session_families USING INDEX sqlite_autoindex_session_families_1 (id=?)` + `LIST SUBQUERY` + `USE TEMP B-TREE FOR ORDER BY`。也就是说，`IN` 子查询仍然把 `session_families` 主键用上了；Note 写的“`lower(id)=lower(q)` 让精确搜索无法直接使用主键最左前缀”对 SQLite 过于绝对。MySQL 本地无服务，计划未验证。

### 9.4 `apps/api/app/db/crud/sessions.py`（M）

职责：Session 读模型仓储；本 PR 抽出 `_session_conditions`，新增 `count_sessions` 与 `count_pending_sessions`。修改文件。

关键依赖：SQLAlchemy Core 的 `select`/`func.count`/`func.distinct`/`exists()`。它在这里相当于“方言翻译器”：同一段 `IN (SELECT …)` 与 `NOT EXISTS` 在 SQLite/MySQL 上生成不同计划，但语义相同；`func.lower` 则是为了抹平两个方言的大小写敏感性差异。

旧代码（列表内联谓词）：

```python
conditions = [scope.session_condition()]
if query:
    pattern = f"%{_escape_like(query.lower())}%"
    conditions.append(or_(session_families.c.search_text.like(pattern, escape="\\"),
                          func.lower(session_families.c.id).like(pattern, escape="\\")))
if status == "problem":
    conditions.append(session_families.c.status.in_(("partial", "fail")))
elif status != "all":
    conditions.append(session_families.c.status == status)
```

新代码（共享构造器 + 两个计数）：

```python
def _session_conditions(*, query, status, exact_query, scope) -> list[ColumnElement[bool]]:
    conditions = [scope.session_condition()]
    if exact_query:
        exact = query.strip()
        if exact:
            conditions.append(func.lower(session_families.c.id) == exact.lower())
    elif query:
        ...  # 旧的 LIKE 分支原样保留
    if status == "problem": ...
    return conditions

async def count_sessions(...):
    statement = select(func.count()).select_from(session_families).where(*_session_conditions(...))

async def count_pending_sessions(scope):
    statement = select(func.count(func.distinct(bad_cases.c.bad_case_session_id))).select_from(bad_cases).where(
        scope.condition(bad_cases.c.workspace_id),
        ~select(session_families.c.id).where(
            session_families.c.id == bad_cases.c.bad_case_session_id).exists(),
    )
```

这在做什么：把“作用域 + q + status”收敛成一个函数，列表与 `total` 共用；pending 走另一条从 `bad_cases` 出发的半连接，用 `NOT EXISTS` 表达“没有 families 行”。`IN` 与 `NOT EXISTS` 都避免 join 膨胀，这是本 PR 在正确性上最关键的两处写法。

检视发现：`COUNT(DISTINCT)` 的语义没有测试承重（§6.2）；共享根的 pending 口径未文档化（§6.3）；`lower(id)` 的计划判断在 Note 中偏悲观（§6.8）；新增段覆盖率 100%，无未执行分支。索引 `ix_bad_cases_workspace_session` 在 migration 0014 中存在，实测 SQLite 计划命中它。
