## §1 一页速览

一句话：把「deploy 能执行、所以部署检查通过」改成「harness 能穿越目录、所以部署检查通过」，并在重跑 Deploy 时主动修复线上已经存在的 0700 版本目录。

比喻：旧预检像**用房东的钥匙试门**——deploy 是房东，门当然能开；真正要进门的是租客 harness。现在检查的是门锁本身是否允许租客通过（other 位），并且在发现旧门被房东反锁（0700）时，重跑一次就换回公共锁（0755）。

## §2 架构导览

### 2.1 权限修复收敛到两个入口

`version_directory()` 把「二进制在 `<prefix>/<version>/usr/bin/claude`」这条路径假设收口成一次校验（`install-claude-code.py:191`）。`repair_service_access()` 只做一件事：把 `prefix`、`<version>`、`usr`、`usr/bin` 设为 0755，并把二进制恢复为 0755（`:203`）。

调用点有三个，覆盖了所有部署形态：

1. 新解包：`dpkg-deb -x` 后、`os.replace()` 前，显式设置 staging 及 `usr`、`usr/bin`（`:249` 附近），再在改名后调用 `repair_service_access()`（`:269` 附近）。
2. 同版本重装：`binary.exists()` 且 `--version` 成功时，先修复再早返回（`:237`）。
3. 仅配置路径：`need_install=false` 时根本不进入 `install_from_deb()`，所以在 `main()` 里解析出 `active_binary` 后单独调用修复（`:533` 附近）。这一条是 #531 指出的「只改 preflight 不够」的关键。

### 2.2 预检从 prefix 走到二进制

`preflight_shared_access()` 现在收集 `prefix`、`<version>`、`usr`、`usr/bin`、`settings.parent` 五个目录，逐个检查 other-traverse；二进制 separately 检查 other-execute，settings 检查 other-read（`install-claude-code.py:421-461`）。任何缺失目录都会显式报 `directory is missing`，不再像旧版那样只检查 `prefix` 和 `config`，从而漏掉真正导致 EACCES 的版本目录。

### 2.3 Deploy 侧的第二道检查

`deploy.yml` 的预检不再用 `test -x`（deploy 是属主，必然通过），而是把目录链和 settings 交给远程 bash 的 `require_other()`，用 `stat -c '%a'` 取 other 位（`.github/workflows/deploy.yml:259-307`）。如果 deploy 恰好有 `sudo -u harness` 权限，就执行 `claude --version`；没有则打印 warning 并依赖 other 位检查。这与 bootstrap 只授予 deploy `systemctl` 权限的现状一致，不扩大 sudo 面。

### 2.4 测试与文档

测试用 `seed_shared_assets()` 构造一条完整 0755 链（`test_install_claude_code.py:296`），再按需把某一级改回 0700；旧的三个 preflight 测试也改用同一个构造器，修掉了「夹具先手动 chmod 0755、掩盖真实缺陷」的问题。文档把版本目录 0755、重跑修复、harness 视角验收写进现状说明。

## §3 数据流走查

生产部署（`need_install=false`）：

1. Deploy 把 `deploy/` 同步到 `/opt/harness/shared/config/`，通过 stdin 把 Secret 交给 `install-claude-code.py`。
2. `main()` 读取 `~/.local/bin/claude --version` 得到目标版本；`active_binary = launcher.resolve()` 指向 `<prefix>/<version>/usr/bin/claude`。
3. `repair_service_access()` 把 `prefix`、版本目录、`usr`、`usr/bin` 设 0755；历史 0700 目录在这一步被修复。
4. `configure()` / `configure_shared()` 写 deploy 的 `~/.claude`、共享 settings 与 0600 `.env` 注入值。
5. `preflight_shared_access()` 从 `prefix` 走到二进制逐级检查；失败在 `switch_current()` 之前抛出，旧 release 继续服务。
6. `switch_current()` 原子切换 `current` 软链；随后以 stable 路径执行 `claude --version` 自检。
7. Deploy 的第二步预检用 `stat` 复核 other 位；有权限时再以 harness 身份执行 `--version`。
8. 合并后的 Deploy 重启 `harness-api`；真实 run 的 `cluster.review` 以 `outcome=ok`、tokens>0、model 非 `unknown` 作为最终验收。

新解包（`need_install=true`）：

1. `mkdtemp()` 建 0700 staging；`dpkg-deb -x` 解包。
2. 显式设置 staging、`usr`、`usr/bin` 为 0755；执行 candidate `--version`。
3. `os.replace(staging, target)` 改名，目标目录保持 0755；再调用一次修复函数兜底。
4. 之后的 preflight / `switch_current` 与上面相同。

## §6 讨论点

### 6.1 Deploy 无法以 harness 身份执行，流水线只能证明 other 位

- **位置**：`.github/workflows/deploy.yml:299` / `deploy/bootstrap-server.sh:126`
- **现象**：bootstrap 只给 deploy `systemctl` 的 NOPASSWD 权限，`sudo -n -u harness true` 在线上会失败，预检走 warning 分支。
- **问题**：other 位正确等价于「非属主可穿越」，但无法证明 harness 的补充组、ACL 或后续 mount 选项没有别的问题；线上最终仍要人工执行一次 harness 视角命令或看真实 run。
- **预判**：这是当前最小权限模型的合理边界。给 deploy 加 `sudo -u harness` 会扩大部署账号横向权限，且需要 root 改 sudoers，超出本 issue「纯流水线」的范围。
- **结论**：（留空给维护者）是否在后续 issue 中评估只读的执行冒烟方案。

### 6.2 `repair_service_access()` 把 prefix 也强制为 0755

- **位置**：`deploy/install-claude-code.py:212-221`
- **现象**：修复函数不只改版本目录，也把 `prefix` 本身设为 0755。
- **问题**：如果未来有人刻意把 prefix 设为更严格（如 0750），部署会被静默改回 0755。
- **预判**：prefix 是服务级 CLI 根，0755 是设计值；当前无实害，且与 `preflight` 的 other-traverse 要求一致。
- **结论**：（留空给维护者）是否要在文档里把 prefix 0755 也写成契约。

### 6.3 preflight 不检查 prefix 的父目录

- **位置**：`deploy/install-claude-code.py:443`
- **现象**：检查链从 `prefix` 开始，`/opt/harness/shared` 不在检查范围。
- **问题**：如果 `/opt/harness/shared` 被改成 0750，harness 仍然无法穿越，但预检会通过。
- **预判**：bootstrap 以默认 umask 创建该目录（0755），当前无实害；把父目录纳入检查会越过「prefix 是安装器边界」的职责，需要维护者决定。
- **结论**：（留空给维护者）。

## §9 文件级代码分析

### 9.1 `deploy/install-claude-code.py`（M）

职责：以 deploy 身份解包、配置、切换 Claude Code 的服务级共享资产。前身的关键缺陷是 `mkdtemp()` 的 0700 被 `os.replace()` 原样带入版本目录；旧 preflight 只检查 `prefix` 和 `config`。

变更代码块对照：

```text
旧：if existing.returncode == 0: return binary
新：if existing.returncode == 0:
        repair_service_access(binary, prefix)
        return binary
```

早返回是「同版本重装」的最高频路径，修复必须放在返回之前；否则重跑 Deploy 仍然保留 0700。

```text
旧：os.replace(staging, target)
新：对 staging / usr / usr/bin 显式 chmod 0755
    os.replace(staging, target)
    repair_service_access(binary, prefix)
```

`dpkg-deb -x` 不会把 staging 根目录的权限改回 0755，必须在改名之前显式设置；改名后再兜底一次，防止未来有人改动解包实现。

```text
旧：for directory in (prefix, settings.parent)
新：directories = [prefix, version_dir, version_dir/"usr", version_dir/"usr/bin", settings.parent]
```

预检的检查面从两个目录扩到完整链条；任何一级缺 other-traverse 都会在 `switch_current` 之前失败。

实现思路总结：用「一个路径校验 + 一个权限修复函数」覆盖新装、重装、仅配置三条路径；预检只读、修复只写，两者在 `switch_current` 前串行。

检视发现：无阻塞缺陷。`repair_service_access` 对 prefix 的强制 0755 见 §6.2。

### 9.2 `.github/workflows/deploy.yml`（M）

职责：在 Deploy 中安装/配置 CLI，并在发布前做服务用户视角的预检。旧实现用 `test -x`，以 deploy 身份执行，deploy 是属主，必然通过。

变更代码块分析：

```text
旧：test -x "$BIN" && test -r "$SETTINGS"
新：远程 bash + require_other 逐级检查
```

`require_other` 用 `stat -c '%a'` 取权限，`10#$mode % 10` 取 other 位，再按 `mask` 判断 exec/read。它避免了 `test -x` 的 effective-uid 陷阱。

```text
if sudo -n -u harness true; then
  sudo -n -u harness "$BIN" --version
else
  echo "::warning::..."
fi
```

有权限时做真实执行冒烟；没权限时只告警，不阻断发布。这是对 bootstrap sudoers 现状的兼容，不是遗漏。

实现思路总结：把「deploy 视角」换成「other 位视角」，并把 harness 冒烟做成可选增强。

检视发现：无阻塞缺陷。sudo 边界见 §6.1。

### 9.3 `apps/api/tests/deploy/test_install_claude_code.py`（M）

职责：安装器纯函数测试。新增 `seed_shared_assets()` 统一构造完整 0755 链，覆盖：

- 0700 的 version / usr / usr/bin 三档分别让 preflight 失败（`:319`）；
- `repair_service_access()` 修复已有目录后 preflight 通过（`:332`）；
- `install_from_deb()` 早返回修复（`:346`）；
- 新解包后版本目录 0755（`:358`）；
- 仅配置路径 `main()` 修复历史 0700（`:388`）。

旧夹具在 preflight 前手动 chmod 0755，只覆盖部分目录；新夹具通过 `seed_shared_assets()` 一次性设好整链，再针对性地改坏某一级，避免「测试自己掩盖缺陷」。

检视发现：无阻塞缺陷。
