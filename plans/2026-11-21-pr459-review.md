## §1 一页速览

**一句话**：把“GitHub 专用 + 一个全局 push URL”改成“按部署选择 provider、按 run 选 push/eval 目标”，让 PAT/Secrets 下发与新增 GitLab 子类成为同一套设计。

| 交付块 | 内容 |
|---|---|
| 配置 | `HE_GIT_PUSH_PROVIDER`（github/gitlab）+ `HE_GIT_PUSH_TOKEN`（PAT，Secret 注入）；可选 API/base/username 覆盖 |
| 抽象 | `GitPushProvider` 父类 + `GitHubProvider` / `GitLabProvider` 子类 + 工厂；新增平台只加子类 |
| 目标 | target/run 的 `pushRepoUrl` / `evalRepoUrl`；空值回退 provider fork / `HE_GIT_PUSH_URL` / `repoUrl` |
| 凭据 | `GIT_ASKPASS` 从 env 取值；token 不进 URL/DB/事件/日志 |
| 兼容 | `HE_GIT_PUSH` / `HE_GIT_PUSH_URL` 保留；未配置新字段时行为不变 |

## §2 架构导览

### 2.1 配置与工厂

`HE_GIT_PUSH_PROVIDER` 是部署级选择器，默认 `github`；未知值启动失败，不静默回退。`HE_GIT_PUSH_TOKEN` 只从 Secrets / 服务器 `.env` 注入，和 `GIT_ASKPASS` 配套；`HE_GIT_PUSH_API_URL` / `HE_GIT_PUSH_BASE_URL` / `HE_GIT_PUSH_USERNAME` 只在自托管/企业版覆盖。工厂在 composition root 构造一次，业务层只依赖父类。

### 2.2 父类与子类

父类定义 `remote_url` / `auth_environment` / `ensure_fork` / `open_pull_request` 以及公共 `push_ref` / `remote_ref`；GitHub 子类负责 `api.github.com`、`Bearer`、`x-access-token`、`POST /repos/{owner}/{repo}/forks`；GitLab 子类负责 `/api/v4`、`PRIVATE-TOKEN`、`oauth2`、`POST /projects/{encoded}/fork`。新增平台只加子类 + registry，不改 prepare/candidate/final 状态机。

### 2.3 目标与评测同源

target/run 快照 `pushRepoUrl` / `evalRepoUrl`；prepare/candidate/final 用 per-run push 目标，评测用 per-run eval 目标。设计文档明确“推 fork、评上游”会把 `blocked(push)` 变成 `blocked(eval)`，因此 push 与 eval 必须指向同一个可 fetch 的仓。

### 2.4 凭据

`GIT_ASKPASS` 脚本读 `HE_GIT_PUSH_USERNAME` / `HE_GIT_PUSH_TOKEN`；`harness` 用户无 home，脚本用绝对路径。token 不进入 URL、数据库、事件或日志；个人 PAT 是过渡，专用账号/App 留给后续切片。

## §3 数据流走查

1. 部署：`production` Secrets 写入 `.env`，`GIT_ASKPASS` 注入后重启。
2. target 配置：可填 `pushRepoUrl` / `evalRepoUrl`；空值由 provider 推导 fork 并回退。
3. 创建 run：快照 provider、push/eval 目标与凭据引用；运行中不读 target 当前值。
4. prepare：读上游；按 per-run push 目标推送 run 分支。
5. candidate：推 candidate tag 到同一 push 目标。
6. eval：用 per-run eval 目标 + candidate commit；评测侧能 fetch。
7. 接纳/终评：仍回同一目标；失败进入既有 blocked。

## §6 讨论点

### D1：M26 vs M25

- **位置**：`.agents/flow/roadmap.md`、`.agents/flow/milestones/m26-git-push-provider.md`
- **现象**：main 已有 M25（轨迹父子关系会话级链接）；本 PR 的 provider 切片最初创建为 M25，冲突后改为 M26。
- **问题**：GitHub milestone #36 的标题已改为 M26，但 issue #457 标题不含里程碑号，历史里可能看到“原 M25”的记录。
- **预判**：M26 是正确编号；GitHub 侧已同步改名，后续以 #457 + #36 为准。
- **结论**：

### D2：provider 只按部署选择

- **位置**：`plans/fullstack-design/04-backend-architecture.md` 配置表
- **现象**：`HE_GIT_PUSH_PROVIDER` 是部署级，不是 target 级。
- **问题**：同一部署内如果同时有 GitHub 与 GitLab target，需要切换部署或后续加 per-target override。
- **预判**：当前诉求是“换部署时换平台”，部署级足够；per-target 明确列为非目标，避免首版扩大状态机与测试面。
- **结论**：

### D3：retry 自阻塞仍未修

- **位置**：issue #457 背景
- **现象**：provider 修好后，push 失败仍可能因 retry 调度缺陷停在 running。
- **问题**：本 PR 是 docs-only，没有修 retry；上线前必须单独修。
- **预判**：provider 与 retry 分开验收，避免把两个独立缺陷捆在一个 PR；retry 修复应有独立 issue。
- **结论**：

### D4：预算提高

- **位置**：`scripts/doc-budgets.manifest.json`
- **现象**：`docs/git-workspace.md` 700→950、roadmap 1100→1200、m26 milestone 600。
- **问题**：预算提高会降低未来压缩压力。
- **预判**：新增 provider/凭据/per-target 说明是常驻事实，搬层会让文档找不到 home；压缩到 700 会丢掉关键约束。PR 已写明理由，接受本次提高。
- **结论**：
