## §1 一页速览

**一句话**：把「一个 bad case 只能挂一条归因状态」改成「一个 case 可以挂多条归因」，给归因报告补上空间、结论、缓存指纹与复用计数，并新建一张「这次 run 里每个 case 进没进潜在、为什么」的候选台账；只动 schema 与 repository，不碰 API、service 与前端。

**一个比喻**：V1 的 `bad_case_analysis` 像**一张病历卡**——一个病人（case）卡上只允许写一条会诊结论，想换结论只能擦掉重写。V2 把它换成**会诊记录册**：同一个病人可以有多条会诊记录，每条记录指向一份检查报告（`probe_reports`）。同时给每份报告加了三样东西：① **条形码**（`cache_key`，七项身份拼成的指纹），同样的七项身份再来一次，直接复用上次那份报告，不重新化验；② **复用台账**（`reused_count` / `last_reused_run_id`），记「这份报告被第几次 run 借去用过」；③ **挂号台账**（`evolution_run_candidates`），记这次 run 里每个 case **有没有进潜在集、被哪条策略挡掉、两个触发点分别在事件流的哪个位置**——被挡掉的也要留档，否则没人能解释「为什么它没进」。

## §2 架构导览

这一层的核心是三个决定：**在哪张表上扩展**、**用什么当身份**、**谁拥有 schema**。

### 2.1 为什么原位演进而不新建平行表

V1 的归因真相分散在四张表：`bad_cases`（case 本身）、`bad_case_analysis`（case ↔ 归因状态，1:1）、`probe_reports`（归因明细）、`probe_cluster_probes`（簇 ↔ 归因）。所有对外读路径都以 `probe_id` 为关节：`GET /api/probes/{probeId}`、簇成员、旧 bad-case 详情都靠它。

如果新建一张 `v2_attributions`，就会出现两套归因 ID、两套簇成员口径，`probe_id` 兼容链直接断掉。所以 PR 选择「原位演进」：`bad_case_analysis` 只是把唯一键从 `(bad_case_id)` 换成 `(bad_case_id, probe_id)`（`0020:456-510`），语义从「case 的状态行」变成「case ↔ probe 的关联行」；`probe_reports` 加列而不是新表（`0020:29-69`）。代价写在 PR 描述的「已知限制」里：所有旧读取方都必须容忍「一个 case 多行」和「状态列可空」，本 PR 只改了 `bad_cases` 读链，其余留给 m11（见 §6 D2）。

### 2.2 三层身份：`probe_id` 是名字，`cache_key` 是指纹，候选是快照

| 身份 | 是什么 | 谁生成 | 稳定性 |
|---|---|---|---|
| `probe_id` | 一条归因明细的稳定 ID，对外就是 `attributionId` | 调用方传入（`ProbeWrite.probe_id`，`attributions.py:81`） | 永不变；缓存命中时以已有行为准 |
| `cache_key` | 七元组指纹 `sha256(workspace_id + bad_case_id + probe_type + probe_object + object_version + policy_version + attribution_engine)` | 由 `ProbeWrite` 从落库字段现算（`attributions.py:99-110`） | 任一身份字段变化即变 |
| 候选行 | `(run_id, bad_case_id)` 的一次快照 | `CandidateWrite.id` 由调用方生成 | 重跑 prepare 时按 `(run, case)` 覆盖，`id`/`created_at` 保留 |

一个具体例子：同一个 case `bc-1`、同一个 skill `deep-research`，第一次用 `policy_version=v1` 跑出 `prompt` 归因，第二次用 `policy_version=v2` 再跑。两次的 `cache_key` 不同（policy 在键里），所以落成 **两条** `probe_reports`；但两次的 `(probe_type, probe_object, object_version)` 相同，所以 `attribution_count` 只算 **1**（`attributions.py:368-383`，与 06 §4.2 的 `COUNT(DISTINCT …)` 一致），而 `list_attributions` 返回 **2 条**。这个「计数按对象身份、列表按行」的差别被 `test_attribution_count_distincts_the_object_identity` 钉住（`test_attribution_repository.py:267-278`）。

### 2.3 迁移的「可重试」是怎么做到的：三道守卫

MySQL 的 DDL 不是事务性的：0020 跑到一半失败，Alembic 不会盖章，重跑会**再执行一遍 upgrade()**。所以每一个动作都必须能「做第二遍不炸」。PR 用三道守卫：

1. **表存在性**（`_has_table`，`0020:107-109`）：`probe_reports`/`bad_case_analysis`/`bad_cases` 都是外部服务拥有的表，内部部署可能压根没有。缺表就跳过对应演进（`0020:513-532` 的 upgrade 主体就是按这个顺序串起来的一组带守卫调用）。
2. **列/索引/唯一键/外键逐个判定**（`_existing_columns`/`_existing_indexes`/`_existing_uniques`/`_existing_foreign_keys`，`0020:112-141`）：`_add_columns`（`:144-157`）只补缺失列；如果列已存在但**可空性与预期不符**，它选择**抛错而不是静默修**（错误信息直接告诉你「先修列再重试」），这是刻意的：静默修会让「半途的错列」永远没人发现。
3. **回填只看 NULL 或默认值**：`_backfill_workspace` 的 `WHERE workspace_id IS NULL OR workspace_id = 'ws-default'`（`0020:284`）、`_backfill_conclusion` 的 `WHERE conclusion = 'attributed'`（`0020:300`）、`_backfill_cache_keys` 的 `WHERE cache_key IS NULL`（`0020:335`）。这样重跑不会把已经算对的值再改一遍。

三道守卫带来的一个副作用值得知道：`_backfill_conclusion` 用「等于默认值」当作「尚未回填」的标记。如果某条 probe 的结论真的是 `attributed`，又恰好关联到一条 `analyzed_nonissue` 的旧行，重跑 upgrade 会把它改成 `non_target`。正常流程里 0020 只跑一次（之后 Alembic 直接跳过），只有「半途失败重试」才可能落到这个窗口，属于可接受的近似。

### 2.4 双方言的两个分叉点

**分叉一：SQLite 用 batch 重建，MySQL 用 ALTER。** SQLite 不支持 `ALTER COLUMN`/`DROP CONSTRAINT`，SQLAlchemy 的 `batch_alter_table` 做法是「建影子表 → 拷数据 → 删原表 → 改名 → 重建索引」。所以任何一次 batch 都可能**顺带重建索引**，顺序很关键：0020 在 `probe_reports` 上先 `_add_columns` → 再 `_make_attribute_type_nullable`（`:224-242`，一次 batch）→ **然后**才 `_create_indexes`（`:524`）→ 最后 `_create_foreign_keys`（`:525`，SQLite 上又是一次 batch）。先放宽列、后建索引，避免 batch 重建时把刚建好的唯一索引丢掉。测试 `test_attribution_migration_backfills_legacy_rows_and_evolves_schema` 的 `:305-311` 就是在钉这件事。

**分叉二：MySQL 删唯一键前必须先有替身索引。** InnoDB 要求外键列上有索引；`bad_case_analysis.bad_case_id` 的 FK 一直靠 `uq_bad_case_analysis_case` 这个唯一索引支撑。如果先 `DROP INDEX uq_bad_case_analysis_case`，MySQL 会报「Cannot drop index … needed in a foreign key constraint」。`52692ad` 这个修正 commit 的做法是：进函数就先建 `ix_bad_case_analysis_case_updated (bad_case_id, updated_at)`（`0020:463-466`），再按 `add_link → drop_legacy → relax_status` 的顺序改（`:472-510`）；降级时对称地「先建回 `uq_bad_case_analysis_case`，再删 `uq_bad_case_analysis_case_probe`」（`:632-670`），最后才删辅助索引（`:671-674`）。注释写在 `0020:460-462`。

这个修正的**正确性只能由真实 MySQL 证明**，而本机没有 MySQL；SQLite 不校验「删索引会不会打断 FK」，所以 SQLite 用例无论怎么改顺序都会绿。它目前是「读代码 + MySQL 语义推理」的结果，不是「跑出来的结果」。

### 2.5 旧读链的三种兼容手法

旧接口只知道「一个 case 一条状态」，PR 用三种手法让它在一 case 多行时继续能跑：

1. **取最新行**：`get_analysis` 从 `one_or_none()` 改成 `ORDER BY updated_at DESC, id DESC LIMIT 1`（`bad_cases.py:347-370`）。不这么改，一 case 两行会直接抛 `MultipleResultsFound`（500）。
2. **升序让 map 保留最新**：`list_snapshot` / `get_case_snapshot` / `analyses_by_case_ids` 全部改成 `ORDER BY bad_case_id, updated_at, id` 升序（`bad_cases.py:334-343`、`:443-450`）。消费方是一句字典推导：`analyses = {row.bad_case_id: row for row in analysis_rows}`（`service/bad_cases/service.py:187`）——**后写覆盖**，所以升序返回等价于「保留最新」。这是个很巧的复用：不改 service 一行，只改 SQL 的排序方向。
3. **边界默认值**：`ProbeReportRow` 新增 7 个带默认值的字段（`bad_cases.py:70-76`），`_row_probe` 用 `mapping.get(...) or 默认值` 兜底（`:212-218`），所以任何「只 select 了旧列」的调用点不会因为缺键炸掉。

### 2.6 ORM 与迁移的分工：外键归迁移，ORM 只描述可查的列

`probe_reports.workspace_id/created_run_id/last_reused_run_id` 在 ORM 里是**普通字符串列**，外键只在迁移里建（`models/domain.py:334-365` 的注释 + `0020:78-97`）。原因很实在：`ensure_fixture_external_tables` 只拿问题侧 metadata 建三张表（`fixtures.py:88-100`），如果 ORM 声明了「`probe_reports.workspace_id → workspaces.id`」这种跨 metadata 外键，`create_all` 在排序表时会因为找不到 `workspaces` 而抛 `NoReferencedTableError`。

但候选表是**反例**：`models/evolution.py:135-159` 明确声明了 `bad_case_id → bad_cases`、`probe_id → probe_reports` 两个跨 metadata 外键，而 Agent Note（`.md:18`）写的是「候选表的空间与问题列在 ORM 里保持普通字符串」。这条 Note 与代码不符（见 §6 D8）。好在这条路径没有实害：全仓没有 `EVOLUTION_METADATA.create_all()`（`grep "create_all"` 只命中 `fixtures.py:93` 与两份测试里的临时 metadata），而 `probe_cluster_probes` 早就是这个写法（`models/evolution.py:220`），候选表只是跟它一致。

## §3 数据流走查

一条端到端主线：**启动迁移 → 存量回填 → V2 写入 → 候选快照 → 旧接口读回**。用迁移测试里的那批假数据当例子（`test_attribution_migration.py:85-163`）：workspace `ws-attribution-legacy`，三个 case，四个 probe，其中 `probe-legacy-orphan` 没有任何 case 关联。

### 3.1 启动迁移：库里已有 V1 数据（`bootstrap_external_tables=True`）

`upgrade_database` → Alembic `upgrade head` → 0004 在空库上用开关建外部三表 → … → 0019 → **0020**。0020 的 `upgrade()`（`0020:513-532`）按固定顺序做七件事：

```
_add_columns(probe_reports)      ← 9 个新列，全部带 server_default，存量行自动拿默认值
_make_attribute_type_nullable()  ← attribute_type NOT NULL → NULL
_create_indexes(probe_reports)   ← 4 个索引，含 uq_probe_reports_cache_key
_create_foreign_keys(probe_reports) ← workspace / created_run / last_reused_run
_normalize_reused_count()        ← 兜底 NULL → 0
_evolve_bad_case_analysis()      ← 先建 FK 索引，再「加新唯一 → 删旧唯一 → 放宽 status」
_回填四段 + 建候选表
```

注意「加列带 `server_default`」这个细节：`workspace_id NOT NULL DEFAULT 'ws-default'`（`0020:30-35`）让存量行立刻有值，MySQL 才肯加这一列；随后 `_backfill_workspace` 再把「能关联到 case」的行改到 case 所在空间（`0020:275-286`）。

### 3.2 回填：四个字段各自从哪来

| 字段 | 依据 | 例子（测试数据） | 锚点 |
|---|---|---|---|
| `workspace_id` | 关联 case 的 `workspace_id`，取最新链接；关联不上就留默认 | `probe-legacy-issue` → `ws-attribution-legacy`；`probe-legacy-orphan` → `ws-default` | `0020:267-286` |
| `conclusion` | 最新链接的 `analysis_status`：`analyzed_nonissue → non_target`，其余（含 NULL / `unanalyzed`）→ `attributed` | `probe-legacy-nonissue` → `non_target` | `0020:289-304` |
| `attribute_type` | 字面量 `nonissue`、空串 → NULL | 两条历史行变 NULL | `0020:307-316` |
| `cache_key` | 在 Python 里用七元组重算（SQLite 没有 `sha256`） | `probe-legacy-issue` 的键 = `sha256("ws-attribution-legacy"+"bc-legacy-issue"+"skill"+"deep-research"+"v2.0.0"+"v1"+"legacy-probe-import")` | `0020:319-365` |

`_backfill_cache_keys` 是唯一一个「必须逐行算」的：SQLite 无内建 sha256，MySQL 有 `SHA2()` 但两方言无法共用一条 SQL（Agent Note `.md:27` 记了这个取舍）。实现是「一次 SELECT 出所有 `cache_key IS NULL` 的 probe → Python 逐行算 → 逐行 UPDATE」。三个细节值得注意：

- **只算有 case 关联的**：`if bad_case_id is None: continue`（`0020:343-345`），孤立 probe 永远 NULL。这是有意的（算不出 case 维度的键），代价是这些 probe 永远不可能命中缓存（Note `.md:36` 已声明）。
- **同键只算第一条**：`seen` 集合（`0020:341`、`:356-358`）跳过重复键，否则第二条 UPDATE 会撞唯一索引。副作用见 §6 D4。
- **多 case 关联时只取最新一条**：子查询 `ORDER BY updated_at DESC, id DESC LIMIT 1`（`0020:331-334`）。V1 的唯一键是 `(bad_case_id)`，一个 probe 理论上可以被多个 case 关联（`probe_id` 上没有唯一约束），回填只能挑一个。

### 3.3 V2 写入：一次「算过」和一次「复用」

**首次算出一个归因**：

```
ProbeWrite(probe_id="probe-a", workspace="ws-default", case="bc-a",
           type="skill", object="deep-research", version="v2.0.0",
           policy="v1", engine="engine-a", ...)
  → upsert_probe()：SQLite ON CONFLICT(cache_key) / MySQL ON DUPLICATE KEY
  → 新行落库，created_run_id=RUN_ID，reused_count=0
  → 返回 probe_id（upsert 后按 cache_key 反查，attributions.py:255-263）
  → upsert_link(case, probe)：插一行 bad_case_analysis，analysis_status=NULL
```

**第二次同样的七元组**（例如 `cache_enabled=false` 强制重算）走同一个 `upsert_probe`：冲突命中，`updates` 只刷 `attribute_type/conclusion/confidence/probe_description/probe_analysis/policy_version/attribution_engine/updated_at` + `created_run_id`（`attributions.py:240-251`），**`probe_id` 与 `created_at` 保留**（不在 `updates` 里），所以返回的还是 `probe-a`。测试 `test_cache_upsert_reuses_the_existing_probe_id` 断言了 5 件事（`:194-225`）：行数 1、id 仍是 `probe-first`、结论被刷新、`created_run_id` 变成新 run、`created_at` 没变。

**真正的缓存命中**应该走 `reuse()`（`attributions.py:336-348`）：只 `reused_count = reused_count + 1`、写 `last_reused_run_id`、刷 `updated_at`，不插行。注意这两条路径是**两个不同的 API**，调用方自己选；repository 不做「先查再决定」，因为那会在并发下退化成先查后写。

### 3.4 候选快照：被排除的也要留档

`EvolutionRunCandidateRepository.upsert`（`attributions.py:427-476`）的冲突目标是 `(run_id, bad_case_id)`，冲突时刷新除 `id`/`run_id`/`created_at` 之外的全部列（`:448-450`）。所以「重跑 prepare」等价于「就地更新同一行」，`id` 不变——测试 `test_candidate_upsert_is_idempotent_per_run_and_case` 断言了 `record.id == "candidate-a"`（`:195`）。

`included=false` 的行**没有**被过滤掉：`upsert` 只是把 `write.included` 原样写进 `values`（`:442`），`list` 也不带 `included` 条件（`:478-487`）。测试用 `policy_excluded + order_state=unknown` 那一行证明（`test_candidate_repository.py:139-162`）。这是「运行详情可解释」的前提：用户问「我这个 case 为什么没进潜在集」时，答案必须已经在库里。

### 3.5 旧接口读回：一个 case 两行时会发生什么（实测）

这是本 PR 最需要看懂的一段。构造：case `bc-drift`，`probe-legacy`（旧分析 `analyzed_issue`，`updated_at=NOW`）+ `probe-v2`（V2 行 `analysis_status=NULL`，`updated_at=NOW+1h`），两条 `bad_case_analysis`。实测输出：

```
get_analysis -> probe-v2 None                    # 取到最新那行，状态是 NULL
merge_snapshot items: 1
  analysis.status = unanalyzed  probe_id = None   # 旧 DTO 降级成「未分析」
  warnings = [('INVALID_ANALYSIS_STATUS', 'analysis_status')]   # 外加一条「外部数据非法」告警
```

链路是：`get_case_snapshot` 升序返回两行 → `dict` 保留最后一行（V2）→ `_analysis_model` 拿 `status=None` → 走「非法状态」分支，返回空分析并附 `INVALID_ANALYSIS_STATUS`（`service/bad_cases/service.py:325-339`）。

也就是说旧接口不是「少显示一点信息」，而是**把一个合法的新数据判成脏数据**。这一点 PR 的「已知限制」只写了「按空状态降级」，没有写会附带一条数据质量告警（见 §6 D2）。

## §6 讨论点

> 每条固定五段：位置 / 现象 / 问题 / 预判（供拍砖）/ 结论（留空给维护者）。

### D1 删掉 `UNIQUE(bad_case_id)` 是跨服务语义变更，外部写入方可能悄悄退化成「每次插新行」

- **位置**：`apps/api/alembic/versions/0020_v2_attribution_schema.py:469-503`（`drop_legacy`/`add_link` 执行 `DROP CONSTRAINT uq_bad_case_analysis_case`）；表的归属声明见 `apps/api/app/db/migrate.py:22-28`（「External problem/attribution/probe tables are owned outside this service」）与 `apps/api/app/db/crud/fixtures.py:88-100`
- **现象**：`bad_case_analysis` 被明确标注为外部服务拥有的表，本仓只有读路径 + 开发用播种写入。V1 的唯一键 `UNIQUE(bad_case_id)` 正是外部写入方做「一个 case 一条状态」upsert 时最自然的冲突目标。0020 把它删掉后，同一条 `ON DUPLICATE KEY UPDATE` / `ON CONFLICT` 语句不再有冲突目标，只会一直插新行。
- **问题**：这不是「多归因」本身的问题，而是**上线顺序**的问题：0020 先上、外部写入方后切，中间窗口里外部服务每写一次就多一行，而旧读接口只取最新一行、`analysis_progress` 按行计数（`bad_cases.py:301-307`），所以症状是「统计数字慢慢变怪」而不是报错。本仓无法验证外部写入方的 SQL（不在仓库内），因此这条只能作为**发布协调项**提出，不能断言它一定会发生。
- **预判**：设计文档已经把这个变更写成既定决策（06 §9、15 §6.1），所以不建议在本 PR 里改方案；建议在 PR 描述或 06 §9 的「回滚」段落里补一句上线约束：**0020 必须与外部写入方切到 `(bad_case_id, probe_id)` 键同批发布**，并在切换前确认外部写入方不依赖 case 唯一键。如果外部写入方暂时改不了，也可以考虑让 0020 在「外部表存在」时保留一个过渡期的告警期（例如先只加新唯一键、不删旧键——但那会直接阻止多归因写入，所以只能二选一）。
- **结论**：

### D2 `analysis_status` / `attribute_type` 可空只兼容了一半：旧读模型把合法 V2 行判成脏数据

- **位置**：`apps/api/app/db/crud/bad_cases.py:192`（`analysis_status=_text(...)`）、`:207`（`attribute_type=_text(...)`）→ 消费方 `apps/api/app/service/bad_cases/service.py:325-339`（`status is None` → `INVALID_ANALYSIS_STATUS` + `_empty_analysis()`）、`apps/api/app/db/crud/bad_cases.py:301-307`（按 status 分桶计数）；另一条链 `apps/api/app/db/crud/probe_query.py:198`、`:204`（`str(row[...])`）→ `apps/api/app/service/evolution/probe_query.py:195-199`（`_attribute_of` 过滤未知值，`probe_row_of` 返回 `None`）
- **现象**（实测，见 §3.5）：一 case 挂了「旧 `analyzed_issue` 行 + 新 V2 行」后，`GET /api/problems/{id}/analysis` 返回 `status=unanalyzed`，并附带 `INVALID_ANALYSIS_STATUS` 告警。另一条链上，`ProbeHitRow.attribute_type` 由 `str(None)` 变成**字符串 `'None'`**，`_attribute_of` 认不出 → `probe_row_of` 返回 `None` → 该 probe 在进化向导的预览里直接消失。
- **问题**：PR 把「可空」定义成兼容例外，并在 Note 里写「V2 repository 写入时强制非空」，但那只约束了**写**；**读**侧有两条链路仍假设「非空 + 封闭枚举」，且失败方式是「静默降级成脏数据」而不是报错。PR 描述里「旧 bad-case 读接口会按空状态降级」只覆盖了其中一条，没提告警和 probe 预览丢行。今天无实害（没有任何 service 调用新 repository，所以生产不会产生 V2 行），但它是 m11-01 接线当天的第一颗地雷。
- **预判**：建议在本 PR（不留到 m11）做一件低成本的事：给 `_analysis_model` 加一条「`analysis_status is None` 且有 probe 关联 → 按 probe 结论映射为 `analyzed_issue`/`analyzed_nonissue`」的兼容分支，或退一步「不产生 `INVALID_ANALYSIS_STATUS` 告警」（新增一个更准确的 warning 码）；同时把 `_row_hit` 的 `str(...)` 改成 `_text(...)` 风格的 `str | None`，让 `_attribute_of` 收到 `None` 而不是 `'None'`。两处都不改对外契约（`AnalysisStatus` 仍是三值），改的是「合法 V2 行别被判成脏」。若维护者认为 m11 会整体替换这两条读链，也可以只把「会冒出 `INVALID_ANALYSIS_STATUS`、probe 预览会丢 V2 行」写进 Note 与 06 §4.2 的兼容例外，把修法挂到 m11-01。
- **结论**：

### D3 `created_run_id` 的语义在同一份设计文档里自相矛盾

- **位置**：`plans/fullstack-design/06-database-design.md:522`（`created_run_id` = 「首次生成该结论的 run」）对照 `plans/fullstack-design/06-database-design.md:745`（「`cache_enabled=false`：…重算并 upsert 同 `cache_key` 行（`created_run_id` 更新）」）与实现 `apps/api/app/db/crud/attributions.py:250-251`（`if write.created_run_id is not None: updates["created_run_id"] = ...`）；Agent Note `.md:15` 写「刷新结论、描述、引擎、`created_run_id` 与 `updated_at`」
- **现象**：同一个字段在两处被赋予两种含义：§4.2 表格说「首次生成」，§5.8 与代码说「最新写入」。测试 `test_cache_upsert_reuses_the_existing_probe_id` 断言 `row["created_run_id"] == OTHER_RUN_ID`（`test_attribution_repository.py:223`），即把「最新写入」固化成契约。
- **问题**：两个字段的职责就此重叠——`last_reused_run_id` 表示「最近复用的 run」，`created_run_id` 又表示「最近写入的 run」，而「首次生成」这个信息**彻底丢失**（没有任何列保存它）。将来想回答「这个结论最初是哪个 run 算出来的」时，只能靠 `run_events` 反推。另外，`reuse()`（`:336-348`）不改 `created_run_id`，所以「命中走 reuse」和「命中走 upsert」两种调用方式会让这个字段含义不同。
- **预判**：需要拍一个口径，二选一并把另一处改掉：a) 承认它就是「最近一次生成该结论的 run」，把 §4.2 表格的「首次生成」改成「最近生成」，并说明「首次」有意不保留；b) 让它真的是「首次」，upsert 冲突时**不**更新它（只由 insert 决定），把「最近一次」的职责完全交给 `last_reused_run_id`（那就需要接受「upsert 命中」不算复用、不计 `reused_count`）。我倾向 a：语义简单、与已落地的测试一致，代价只是丢一个可推导的信息。
- **结论**：

### D4 回填时重复 `cache_key` 的第二行被静默留成 NULL，缓存从此永不命中

- **位置**：`apps/api/alembic/versions/0020_v2_attribution_schema.py:341`（`seen: set[str] = set()`）、`:356-358`（`if cache_key in seen: continue`）、`:359-365`（逐行 UPDATE 且带 `cache_key IS NULL` 守卫）
- **现象**：同一 case 下有两条 probe 身份完全相同（V1 允许：`probe_id` 上没有唯一约束，同一对象·版本被重复分析过就会这样），回填时第一条拿到键、第二条因为 `seen` 命中被跳过，保持 NULL。之后：① 这两条 probe 的 `cache_key` 一条有、一条没有；② 下一次真正写入同七元组时，唯一索引只在「非 NULL」上冲突，所以会再插一条新行（V2 行），历史那条 NULL 行永远留在库里、永远不会被复用；③ 没有任何日志或计数告诉你跳过了几条。
- **问题**：数据层面这是「用一个唯一索引的 NULL 语义兜住历史脏数据」，本身可以接受；问题在于**无声**：迁移跑完后没人知道有多少条 probe 因此永久失去缓存能力，也没法在事后区分「孤立 probe」和「重复身份 probe」。对「开发库与 fixtures；生产无数据」的定位来说影响很小，但如果哪天要评估缓存命中率，这批 NULL 会被误算成「孤立 probe」。
- **预判**：Minor。两个低成本改法任选：a) 迁移里对 `seen` 命中的行记一条 logger 计数日志（或在结束时写一条「跳过 N 条重复身份 probe」的汇总日志），让运维能看见「跳过 N 条重复身份 probe」；b) 接受现状，但在 Note `.md:36` 那一句「孤立历史 probe 的 `cache_key` 永远为 NULL」后面补上「以及身份重复、被跳过的 probe」，把口径写全。
- **结论**：

### D5 MySQL 的原子 upsert 分支在任何门禁里都没有被执行过；「并发收敛」也只是 SQLite 串行

- **位置**：`apps/api/app/db/crud/attributions.py:266-290`（`_probe_upsert_statement` 的 mysql 分支 `:282-289`）、`:311-332`（`upsert_link` 的 mysql 分支）、`:451-474`（候选 upsert 的 mysql 分支）；测试侧：`apps/api/tests/m10-01-attribution-schema/*` 全部用 `Settings(db_dialect=DatabaseDialect.SQLITE, …)`；`scripts/run-api.mjs:19`（`db-mysql` 只跑 `tests/test_database.py -m mysql`）；`apps/api/tests/test_database.py:1235`（mysql 用例只断言 `head=0020` 与 `users`/`job_runs` 的列）
- **现象**：`grep AttributionRepository|EvolutionRunCandidateRepository` 在 `apps/api/tests` 下除本 PR 的 4 个文件外**零命中**。也就是说：MySQL 的 `on_duplicate_key_update(**updates)` 从未被编译过、更没被执行过；`test_concurrent_cache_upserts_converge_on_one_probe`（`test_attribution_repository.py:228-248`）跑在 SQLite 上，aiosqlite 是单写者，4 个 `asyncio.gather` 实际被串行化，证明的是「不会重复插入」，不是「并发下收敛」。
- **问题**：PR 描述写「MySQL 原子 upsert 分支只由 CI 的 `test:db:mysql`（迁移与既有 repository contract）间接覆盖」——这句话的实际含义是**零覆盖**，既有 repository contract 与这两个新仓储无关。MySQL 分支的风险不是理论上的：`on_duplicate_key_update(**updates)` 的键来自 Python dict，列名写错、`updated_at` 传 `text()` 之类的差异只会在真实方言编译时暴露；而「FK 索引顺序」那个修正（`52692ad`）同样只有 MySQL 能证明。
- **预判**：不必在本 PR 造 MySQL 环境，但建议做一件低成本的事：给 `test_database.py` 的 mysql 用例或一个**双方言参数化**的用例加「建 1 条 run + 1 个 case + 用 `AttributionRepository.upsert_probe` 写两次同键、断言只有一行且 id 相同」，这样 CI 的 mysql lane 会真的执行 MySQL 分支；同时把 PR 描述的这句改成「MySQL upsert 分支无自动化覆盖，仅由迁移用例间接验证 DDL」。如果维护者接受「m11 接 service 时统一补双方言 contract」，那就把这句话写进已知限制，别写成「已被间接覆盖」。
- **结论**：

### D6 `reuse()` 不可重入：重跑同一个 run 会把 `reused_count` 重复累加

- **位置**：`apps/api/app/db/crud/attributions.py:336-348`（纯 `reused_count + 1`，不校验 `last_reused_run_id`、不做幂等）
- **现象**：候选表的幂等语义是「重跑 prepare 只更新同一行」（`UNIQUE(run_id, bad_case_id)`，测试 `test_candidate_upsert_is_idempotent_per_run_and_case`）。但 `reuse()` 是**累加**：同一个 run 因为重试/重放再次命中同一份 probe，`reused_count` 会 +2、`last_reused_run_id` 不变。于是同一张台账里，「候选幂等」与「复用计数不幂等」并存。
- **问题**：`reused_count` 的文档定位是「缓存命中的审计计数，不表示 run 数」（Note `.md:34`），所以「+2」在字面上没违约；但它与候选行的 `UNIQUE(run, case)` 放在一起会被读成「一次 run 一次命中」。将来做「缓存命中率 = 命中数 / (命中数 + 重算数)」时，重试会污染分子。另外 `reuse()` 对不存在的 `probe_id` 是静默 no-op（UPDATE 影响 0 行，不抛错），调用方无法发现「我以为命中了，其实 probe 已不在」。
- **预判**：Minor，但有两条值得现在定：a) 给 `reuse()` 加幂等条件（只有该 probe 的 `last_reused_run_id` 不等于本次 run 时才 +1）（代价是「同一 run 多次命中」不再可数，但那本来也不该数）；b) 或保持累加，但在文档里把「一次命中」定义为「一次调用」而不是「一个 run」，并让 `reuse()` 返回受影响行数（`result.rowcount`），让调用方能察觉 probe 不存在。我倾向 a + 返回 rowcount。
- **结论**：

### D7 降级会删行，但没有文档承诺的「导出文件」；`attribute_type` 一律变 `nonissue`

- **位置**：`plans/fullstack-design/06-database-design.md:968`（「若已存在一 case 多归因，降级前只保留 `updated_at` 最新的一行并**记录导出文件**」）对照 `apps/api/alembic/versions/0020_v2_attribution_schema.py:593-618`（`_dedupe_analysis_links` 直接 `DELETE`，不写任何文件/表）；`attribute_type` 还原见 `0020:535-561`（`UPDATE probe_reports SET attribute_type = 'nonissue' WHERE attribute_type IS NULL`）
- **现象**：降级会把一 case 的多行裁到最新一行，被删的行**没有任何留档**；同时所有 `attribute_type IS NULL` 的 probe（包括 V2 的 `non_target` 行）统一变成 `'nonissue'`。测试 `test_attribution_migration_downgrade_restores_v1_shape` 明确断言了 `attribute_type == "nonissue"`（`:498`），也就是说这是有意的映射。
- **问题**：两个都是「文档与实现不一致」：① 文档写「记录导出文件」，代码没有；② 文档写降级「不是无损回放」，但没说 `attribute_type` 的 NULL 会被折成 `nonissue` 这个具体损失。降级在生产上大概率不会被用（PR 自己说「生产回滚以回退应用版本 + 保留新结构为主」），但 migration 的 downgrade 是**可执行的**，一旦有人执行，被删的归因链接不可恢复，而且没有任何证据留下。
- **预判**：Minor。二选一：a) 让 `_dedupe_analysis_links` 在删除前把被删行写成一个 JSON 导出（放 `op.get_context().config.attributes` 指定的路径，或至少 `logger.warning` 打印被删的 `(case, probe)` 清单）；b) 改文档：把「记录导出文件」删掉，改成「降级丢弃最新一行之外的关联，无留档；生产回滚请走版本回退」。我更倾向 b（改动小、诚实），但若维护者认为 downgrade 是给开发库用的安全阀，a 也只是十几行。
- **结论**：

### D8 几处小语义缝隙（合并成一条，逐项可单独拍）

- **位置与现象**：
  1. **Note 关于候选表外键的描述与代码相反**：`Agent Note .md:18` 说「候选表的空间与问题列在 ORM 里保持普通字符串」，但 `models/evolution.py:135-159` 明确声明了 `bad_case_id → bad_cases` 与 `probe_id → probe_reports` 两个跨 metadata 外键。真实约定应该只是「**`probe_reports` 新增列**的外键放迁移里」。
  2. **空串与 NULL 版本的键相同、计数不同**：`attribution_cache_key` 把 `None` 折成 `""`（`attributions.py:70`），所以 `object_version=None` 与 `""` 命中同一行缓存；但 `attribution_count` 的 `COUNT(DISTINCT probe_type, probe_object, object_version)`（`:368-383`）会把 NULL 与 `""` 算成两个。`ProbeWrite.object_version` 是自由 `str | None`，没有归一化。
  3. **`attribution_count` 与 `list_attributions` 的分页不自洽**：前者数「对象身份」（distinct 三元组），后者按行分页；测试里就出现了 `count == 1` 而 `list` 返回 2 条（`test_attribution_repository.py:267-278`）。如果 m11 直接用 `count` 当分页 total，页码会算错。
  4. **候选表对 `bad_cases` 是 `ON DELETE CASCADE`**：删一个 case 会把历史 run 里解释「它为什么被排除」的候选行一起删掉，审计链被切断。06 §5.9 只写「FK → `bad_cases`」，没写删除策略。
  5. **`CACHE_KEY_FIELDS` 是死代码**：`attributions.py:38-46` 定义了七字段元组但全仓无引用（`grep` 只命中定义处），而真正决定顺序的是 `attribution_cache_key` 的函数体。
  6. **`server_default` 与 ORM 的双写**：同一套 server_default（`'attributed'` / `0.8` / `'v1'` / `'legacy-probe-import'` / `0`）在迁移的 `PROBE_ADDED_COLUMNS`（`0020:29-69`）和 ORM（`models/domain.py:348-365`）里各写一遍，未来改默认值要改两处。
- **问题**：都不影响今天的正确性，但它们是「下一个人读文档/读 DDL 会读错」的那类债务，且其中 2、3 会在 m11 做「多归因列表 + 分页」时变成真问题。
- **预判**：Minor。建议：① 改 Note 那句为「`probe_reports` 新增列的外键只放在迁移里；候选表沿用既有的跨 metadata 外键写法」；② 在 `ProbeWrite.__post_init__` 里把 `""` 归一成 `None`（一行），或在 `attribution_count` 里用 `coalesce(object_version, '')`；③ 文档里明确「`attribution_count` 是对象身份数，不是行数，不能当分页 total」；④ 候选表 `bad_case_id` 的删除策略二选一（保留 `CASCADE` 就别在 06 里暗示它是审计事实，或改成 `RESTRICT`/`SET NULL` 前先想清楚 case 被删时 run 详情怎么渲染）；⑤ 删掉 `CACHE_KEY_FIELDS` 或让它成为唯一的顺序来源；⑥ 双写默认值本身也可以接受，但值得在 ORM 那侧加一行注释指向迁移。
- **结论**：

### D9 「候选全量保存」目前只是仓储能力，缺一个「全量」的守卫

- **位置**：`apps/api/app/db/crud/attributions.py:427-476`（`upsert` 逐条写，没有批量、没有「本次 run 应有多少条」的概念）、`:478-487`（`list` 全量返回）；06 §5.9 的承诺「全量落库（含被策略排除的行）」
- **现象**：repository 只能保证「你给我一条我写一条」。如果 m11 的 prepare 在循环里 `continue` 掉一条被排除的候选（这很自然：被排除的 case 通常不会继续往下走），候选表就少一行，而没有任何东西会报错。`UNIQUE(run_id, bad_case_id)` 只保证「不重复」，不保证「不缺失」。
- **问题**：这是「全量保存」这条设计承诺的落地缺口。它不在本 PR 的范围内（本 PR 只做 repository），但本 PR 是唯一能低成本加守卫的地方——比如让 `EvolutionRunCandidateRepository` 暴露一个 `replace_run(run_id, writes)`（先按 run 删/或对账）或一个 `count(run_id)`，让 prepare 在收尾时对比「本次候选数 vs 已写行数」。
- **预判**：Minor / decision。如果维护者认为「全量」由调用方的测试来保证（m11 的 prepare 测试断言 `len(list(run_id)) == 期望`），那就保持现状，但建议在 06 §5.9 或 Note 里把「全量由调用方保证，repository 不做对账」写明，避免后来者以为写了 `upsert` 就自动全量。若希望现在就加一道保险，`count(run_id)` 是最小改动。
- **结论**：

## §9 文件级代码分析

> 每个文件：职责一句 + 变更形态 + 关键依赖 + 变更块（旧 vs 新）+ 检视发现。M 文件前身用 `git diff origin/main...HEAD` 对照。

### 9.1 `apps/api/alembic/versions/0020_v2_attribution_schema.py`（A，721 行）

**职责**：把 V1 的归因 1:1 结构原位演进成「一 case 多归因 + 缓存 + 候选快照」，并保证 SQLite/MySQL 双方言、可重试、可降级。

**关键依赖**：`alembic.op`（DDL 执行器）+ `sqlalchemy.inspect`（反射当前 schema）+ 标准库 `hashlib`（回填缓存键）。没有第三方迁移工具，也没有把 sha256 交给数据库——这是本文件最重要的一个取舍（SQLite 无 `sha256()`，两方言无法共用一条回填 SQL）。比喻：它是**装修队**，不是设计师——设计图纸在 06 §4.2/§9，它只负责「哪里缺就补哪里、缺表就跳过、拆墙前先装临时支撑」。

**9.1.1 常量与声明（`:18-104`）**

新/旧：整段新增。声明式地把「要加什么」写成元组：`PROBE_ADDED_COLUMNS`（9 列）、`PROBE_INDEXES`（4 个，含唯一缓存键）、`PROBE_FOREIGN_KEYS`（3 个）、`CANDIDATE_INDEXES`（4 个）。这么写的好处是 upgrade 与 downgrade 共用同一份清单——downgrade 的 `_drop_probe_columns`（`:677-713`）就是遍历 `PROBE_ADDED_COLUMNS` 决定删哪些列，不会出现「加了 9 列、降级只删 8 列」。

**9.1.2 反射守卫（`:107-212`）**

新：`_has_table` / `_existing_columns` / `_existing_indexes` / `_existing_uniques` / `_existing_foreign_keys` 五个小函数，每次调用都重新反射（不是缓存）。`_add_columns`（`:144-157`）是本文件唯一的「强硬」处：列已存在但可空性不符 → `RuntimeError` 并提示「先修列再重试」。`_create_foreign_keys`（`:180-212`）在 SQLite 上开 `batch_alter_table` 并整体跳过不存在的被引用表——注意它是在 `missing` 非空时才开 batch，所以「所有被引用表都缺」的情况下仍会走一次空 batch（无实害，只是白重建一次表）。

**9.1.3 回填（`:245-374`）**

新：四个 `_backfill_*`，顺序固定为 workspace → conclusion → attribute_type → cache_key，因为后一步依赖前一步的最终值（cache key 里含 workspace 与 policy/engine）。`_backfill_workspace` 用一条相关子查询带 `ORDER BY updated_at DESC, id DESC LIMIT 1` 取最新链接，`COALESCE(..., 'ws-default')` 兜孤立 probe。`_backfill_cache_keys` 是唯一「拉全表到 Python」的地方：先 `SELECT … WHERE cache_key IS NULL`，再逐行 UPDATE。

### 9.2 `apps/api/app/db/crud/attributions.py`（A，487 行）

**职责**：V2 归因与候选的唯一写入口 + 一 case 多归因的读接口；把「方言原子 upsert」这件事收在一个地方。

**关键依赖**：`sqlalchemy.dialects.sqlite.insert` / `mysql.insert`（方言 upsert 构造器）+ 项目内的 `Database`（事务/会话壳）与 ORM 表定义。这两个 dialect insert 是 SQLAlchemy 官方的方言扩展，不是第三方包；它们**在构造 SQL 时**就决定了用哪条语句，所以 repository 必须知道方言名字——`self._database.dialect`（`:272`、`:311`、`:451`）。

比喻：它是**同一台收银机上的两个按键**。SQLite 走「先查会员号（`cache_key`），有就改、没有就开新卡」；MySQL 走「按会员号自动查重，重复就覆盖」。按哪个键由「店在哪个国家（方言）」决定，但收据格式（返回值、字段刷新规则）对外一致。

**9.2.1 缓存键（`:38-74`）**

新：`CACHE_KEY_FIELDS` 常量 + `attribution_cache_key` 函数。公式是七段字符串**直接拼接**后 sha256，`object_version or ""` 折空。docstring（`:58-64`）解释「没有分隔符也不会碰撞，因为调用方都用落库列构造」——这个论证偏松（见检视发现 1）。

**9.2.2 `ProbeWrite` / `AttributionRecord` / `CandidateWrite`（`:77-168`）**

新：三个 frozen dataclass。`ProbeWrite.cache_key` 是 `@property`（`:99-110`），**不存字段**——避免调用方传一个和七元组不一致的键。`CandidateWrite.__post_init__`（`:163-168`）在编译 SQL 之前就拒绝非法 `order_state`/`included_reason`，所以「封闭枚举」的保护在 Python 层而不是 DB 层（DB 没有 CHECK）。

**9.2.3 `upsert_probe`（`:211-264`）与方言语句（`:266-290`）**

旧：无（新文件）。新：先拼 `values`（含 `last_reused_run_id=None`、`reused_count=0`，只在 insert 生效）与 `updates`（8 个可变列 + 条件性的 `created_run_id`），再按方言构造语句，最后在同一事务里 upsert + 按 `cache_key` 反查 `probe_id`。

**为什么这么写**：冲突目标必须是 `cache_key`（而不是 `probe_id`），因为「同一次归因重算」会带来一个新的 `probe_id`，我们想让**旧 ID 赢**。SQLite 能显式指定冲突目标（`index_elements=[cache_key]`），MySQL 的 `ON DUPLICATE KEY UPDATE` 不能指定，只能「任何唯一键冲突都走更新」——这就埋了那个 PK 冲突的坑（见检视发现 2）。

**9.2.4 `upsert_link` / `reuse`（`:292-348`）**

新：`upsert_link` 的冲突时 `set_={"updated_at": now}`——**只刷时间**，故意不刷 `analysis_status`/`analysis_result`，这样一条 V1 行被 V2 重新关联时，历史状态仍然可读（docstring `:298-303` 写明了）。`reuse` 用 SQL 表达式 `reused_count + 1` 而不是「读出来加一」，所以并发下不会丢计数。

**9.2.5 读接口（`:350-417`）**

新：`list_attributions` 按 `probe_reports.updated_at DESC, probe_id` 排序并分页；`attribution_count` 用 `COUNT(DISTINCT probe_type, probe_object, object_version)`；`get_attribution` 只在该 probe 仍关联该 case 时返回。`_attribution_join` 是**内连接**，所以 `probe_id IS NULL` 的 V1 兼容行天然不出现在多归因列表里——这是对的（它们没有归因明细）。

**9.2.6 候选仓储（`:420-487`）**

新：`upsert` 的冲突目标 `(run_id, bad_case_id)`，`updates` 排除 `id`/`run_id`/`created_at`（`:448-450`）；`list` 按 `bad_case_id` 排序返回全部行。

**检视发现**：

1. **键公式无分隔符**：`"".join(parts)`（`:74`）。当前 `probe_type` 只可能是 `skill`/`agent`（都是 5 字符）而其余字段是 ID/名称/版本，构造不出真实的跨字段歧义，所以**今天无实害**；但 docstring 的论证（「调用方都用落库列构造」）并不能排除「字段值本身跨过边界」的情况，而 `probe_type` 在 DB/仓储层**没有任何校验**（`ProbeWrite.probe_type` 是自由字符串）。建议：要么在 `ProbeWrite.__post_init__` 收窄 `probe_type`，要么在键里加 `\x00`/长度前缀（一次性改会换掉所有历史键，需与回填同批）。属 Minor。
2. **PK 冲突路径在两种方言下都坏**：若调用方复用一个已存在的 `probe_id` 但改了 `object_version`/`policy_version`/`attribution_engine`（键变了），SQLite 会在 `ON CONFLICT(cache_key)` 上插一条新行 → 撞 PK → `IntegrityError`；MySQL 会命中 PK → 更新可变列但**不更新 `cache_key`**（不在 `updates` 里）→ 随后按新键反查 `scalar_one()` 抛 `NoResultFound`。两者都是 500，但 MySQL 还会留下一条「描述/时间被别的身份覆盖、键还是旧键」的脏行。触发条件是调用方复用 ID，当前无调用方，属 Minor；修法是把 `cache_key` 也放进 `updates`（让 MySQL 与 SQLite 的「新键新行」语义靠拢），或显式先按 `probe_id` 检查冲突并给出明确错误。
3. **`CACHE_KEY_FIELDS` 是死代码**（D8-5）：`:38-46`，全仓无引用。
4. **`reuse()` 不幂等、静默 no-op**（D6）：`:336-348`。
5. **`upsert_probe` 的「写后读」多一次往返**（`:255-263`）：可以用 `RETURNING`（SQLite 支持、MySQL 不支持）或 MySQL 的 `LAST_INSERT_ID` 优化，但当前写法简单且两方言一致，不值得动。
