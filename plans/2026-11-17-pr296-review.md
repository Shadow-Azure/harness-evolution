## §1 一页速览

**一句话：** 给每个进入潜在集合的 bad case 按「对象 · revision」发一张可复用的体检报告；命中缓存就复用旧报告并记账，未命中才调用纯规则引擎，再把报告、case 关联和 run 候选指针一次写进库。

**一个比喻：** 引擎像化验室，只根据送来的样本出结论，不碰档案柜；runner 像前台，先查档案柜里有没有同编号的旧报告，没有才送检，最后把报告号同时登记到问题卡和本次 run 的候选清单上。

## §2 架构导览

### 2.1 引擎层：只吃证据，不碰数据库

`AttributionInput`（`attribution.py:64`）把 runner 能拿到的所有事实收成一个不可变输入：bad case 标题/描述/元数据、命中原因、两个触发点、knowledge 证据、目标 revision。`AttributionEngine`（`:44`）只有一个 `attribute()`，`RuleBasedEngine`（`:123`）用确定性模板实现四类结论。`AttributionResult.__post_init__`（`:109`）在进入数据库前拒绝非法结论/分类/置信度，避免脏值落到 `probe_reports`。

注册表是显式字典（`:262`），`resolve_attribution_engine`（`:267`）对未知 key 抛 `ConfigError`；`create_app` 在启动时调用它（`main.py:140`），未知 `HE_ATTRIBUTION_ENGINE` 直接失败。这保证缓存键里的 `attribution_engine` 一定对应真实实现。

### 2.2 runner：缓存、复用、恢复

`AttributionRunner.run`（`attribution.py:343`）按 included 过滤，先从 repository 取本 run 已关联的候选（`linked_probe_ids`），跳过它们；剩余候选分批加载 bad case 证据和 knowledge 证据，再逐条：

1. 计算 `targetRevision` 为 `object_version` 分量（`:399`）；
2. `cache_enabled` 时按七元组键查既有 probe；命中则 `reuse_probe_and_link` 并继续，不调引擎（`:409`）；
3. 未命中才调引擎，构造 `ProbeWrite`（revision 为 version）并 `write_probe_and_link`（`:427`）；
4. `RunBlocked` 原样上抛；`ValueError`/`ConfigError` 放行给 failed 分支；其它异常转成 `RunBlocked(stage="attribution", error_stage="prepare")`（`:452`），已完成行保持。

“只补未完成项”不是靠内存游标，而是靠候选行上已落库的 `probe_id`；因此进程重启/重试都成立。

### 2.3 repository：一次事务写三张表

`write_probe_and_link`（`attributions.py:324`）在一个事务里执行：方言原子 probe upsert → 按 cache key 读回稳定 `probe_id` → upsert `bad_case_analysis` → update 候选 `probe_id/is_cached=false`。候选行不存在时 `_require_candidate` 抛 `LookupError`，整个事务回滚，避免“有 probe 没有候选指针”的半截状态。

`reuse_probe_and_link`（`:366`）同样在一个事务里做复用计数、case 关联和候选 `is_cached=true`。`reused_count` 的更新条件是 `last_reused_run_id IS NULL OR != 当前 run`，同一 run 重复命中不重复计数；判断候选是否真的不存在只在 update rowcount 为 0 时补一次 select，兼容 MySQL 的 matched/changed rowcount 差异。

### 2.4 模式与 blocked

`0021`（`0021:67`）把 `probe_reports.object_version` 从 64 扩到 96，`digest:<sha256>` 的 71 字符不会再被截断/哈希；同时补 `evolution_runs.potential_policy/cache_enabled/attribution_engine`，旧 run 取 `NULL/false/legacy-probe-import`。两处都按存在性守卫，SQLite 用 batch、MySQL 用 alter。

`blocked_stage` 的封闭集合在 contracts、events、jobs、retry、runs 五处同步加入 `attribution`；`retry._dispatch` 对 attribution 没有迭代现场可恢复，自然落到“无 rounds → 重新入队 `evolution_prepare`”，由 m10-04 的 prepare 重入时跳过已关联候选。

### 2.5 知识证据

`load_knowledge_evidence`（`attributions.py:470`）按根 Session 批量查 `kind=knowledge` 的 document/path/revision/retrieval kind，按 `(document_id, revision, source_path)` 去重；runner 把它映射成 `KnowledgeEvidence` 传给引擎。`_knowledge_lines`（`attribution.py:240`）只渲染元数据，不读文档正文。

## §3 数据流走查

一条端到端主线（离线测试环境，真实表）：

1. `seed_session` 建根会话与主 Agent；`seed_case` 写两条 bad case（一条带 `metaData.error`，一条 discovery）。
2. `seed_run` 写 `evolution_runs`，`potential_policy`/`cache_enabled`/`attribution_engine=rule-v1` 落快照。
3. `seed_candidate` 写 `evolution_run_candidates`，候选行此时 `probe_id=NULL`。
4. 第一次 `runner.run(run, cases, cache_enabled=True)`：
   - `linked_probe_ids` 为空；
   - 批量读 bad case 与 knowledge 证据；
   - 引擎出 `attributed/error/0.8` 与 `non_target`；
   - `write_probe_and_link` 一次事务写 probe、link、候选指针；
   - `list_clusterable_probe_ids` 只返回 attributed 的那条。
5. 第二个 run 对同一 case 再跑：cache key 命中，`reuse_probe_and_link` 复用同一 `probe_id`，`reused_count` 加一，候选 `is_cached=true`。
6. 第三个 run 开 `cache_enabled=False`：跳过读，引擎重算并覆盖同键行，`created_run_id` 更新，`reused_count` 不清零。
7. 模拟引擎在第二条失败：第一条已落库，抛 `RunBlocked(stage=attribution)`；再次 run 时第一条被 `linked_probe_ids` 跳过，只补第二条，第一条 `updated_at` 不变。

## §6 讨论点

### D1. knowledge 证据没有按 case 触发点做时间窗

- **位置**：`db/crud/attributions.py:470`、`service/evolution/attribution.py:240`
- **现象**：`load_knowledge_evidence` 读取根 Session 内全部 `kind=knowledge` 事件；只要存在文档证据，无错误字段的自身上报就会按 `prompt` 归类并写入 reasoning，即使该文档是在 bad case 触发之后才被读取。
- **问题**：归因因果性上，事后读取的文档不应支持“事前”结论；占位规则下可能把无关文档算成证据。
- **预判**：属于低风险占位行为，真实 LLM 归因接入时应按 `(tree_index, event_index)` 或 `triggered_at` 截断到 case 触发点之前；当前不阻塞 m10-03。
- **结论**：留空给用户拍板。

### D2. runner 把所有异常都转成 blocked，可能掩盖编程错误

- **位置**：`service/evolution/attribution.py:452`
- **现象**：`ProbeWrite` 的 `ValueError`（例如目标类型非法）、`AttributionResult` 的校验错误、内存/序列化错误都会被包成 `RunBlocked(stage=attribution)`，而不是 `failed`。
- **问题**：配置/代码错误被当成可恢复失败，会停在 blocked 等人工 retry；虽然不会自动重试（sweeper 只自动推 push），但会延迟暴露 bug。
- **预判**：应把 `ValueError`/`ConfigError` 这类校验错误放行给 JobRunner 的 failed 分支，只把引擎执行与 DB 瞬时错误转 blocked；改动很小。
- **结论**：已在 `attribution.py` 的 per-item 异常分支放行 `ValueError`/`ConfigError`，并新增 `test_invalid_engine_result_fails_instead_of_blocking`；`RunBlocked` 与其它异常仍按原语义处理。

### D3. `reused_count` 的“每 run 一次”只防连续重复

- **位置**：`db/crud/attributions.py:366`、`_reuse_statement`
- **现象**：`last_reused_run_id != run_id` 只能阻止“同一 run 连续命中”；如果 run A 命中 → run B 命中 → run A 再次命中，run A 会第二次加计数。
- **问题**：严格语义“每 run 只加一次”需要独立的 run×probe 复用记录；当前依赖 runner 的 `linked_probe_ids` 跳过已完成候选，正常流程不会触发交叉重复。
- **预判**：继承 m10-01 的既有语义，本切片没有引入新的交叉场景；不扩表，留给真实多 run 并发需求再评估。
- **结论**：留空给用户拍板。
