## §1 一页速览

一句话：这个 PR 把“原始 payload → 规范化 Agent 树”的写入做成可按 root 重放、可跳过未变化输入、失败不污染其他会话的批次。

生活化比喻：一次 root 重放像做一张对账表。系统先把整张表算完，再拉下旧账桌（事务内删除），铺上新账表并盖“已处理”章；一个 payload 算错时整张 root 账表撤回，别的 root 继续结账。

| 交付块 | 结论 |
|---|---|
| pending 与 hash/parser 版本判定 | 主判定正确；root 内未变 sibling 的游标会在兄弟重放时被误刷新 |
| root 原子删除/重写 | FK 顺序和事务边界正确；payload 被删后又发生 root 重建时会丢失旧节点 |
| 失败隔离与错误脱敏 | 结构失败本身会保留旧库状态；progress 回调失败绕过该边界并可污染批次结果 |
| sync_runs 审计 | 生命周期存在；失败 root 未计入 `records_done`，完成批次进度可能低于 100% |
| 真实与双方言验证 | SQLite/本地 4 roots / 66 payload 通过；MySQL contract 据 CI 报告通过，本地未执行 |

## §2 架构导览

### 2.1 pending 不是水位线

`list_pending_payloads()` 以 payload 与 source record 的 outer join 查询待处理项：source 缺失、`processed_hash` 为空、hash 不符、parser 版本为空或落后五类都进入候选（`acquisition_replay.py:100-145`）。

白话解释：游标挂在每个 `(root_session_id, agent_id)` 上，而不是全库一根进度线；像每本书的借阅卡，而不是图书馆统一门禁时间。

### 2.2 root 是事务原子单位

service 先把 pending 按 root 分组（`replay.py:115-117`），再读取该 root 的全部现存 payload（`replay.py:127`），完成 normalize 和 assemble 后才调用写仓储（`replay.py:128-168`）。

仓储在一个事务里先补 source index，再按 `agent_events → agents → user_turns → session_families` 删除旧树（`acquisition_replay.py:280-301`），随后写 family、nodes、events、turns 和 source 游标（`acquisition_replay.py:320-443`）。

### 2.3 canonical 输出

`session_families` 保存 root 级聚合和主 source 指针；`agents` 保持扁平节点；`agent_events` 保存 Skill/Agent/Workflow 触发点；`user_turns.id` 由 `(root, seq)` 的 SHA-256 前缀确定性生成（`acquisition_replay.py:231-235`）。

### 2.4 批次审计

每批先插 running `sync_runs`，结束后统一写 completed、done、imported、skipped 和脱敏 errors（`replay.py:105-113,190-208`）。这里没有 scheduler、sync lock、HTTP 或 SSE，符合 m2-05 边界。

## §3 数据流走查

### 场景 A：首次导入并重放四条根会话

1. 本地 importer 写 66 条 `trajectory_payloads` 和未处理 source rows。
2. `replay_pending_payloads()` 找到全部 pending 并按 4 个 root 分组。
3. 每个 root 全量解析和组装；普通坏行形成脱敏 issue，但不阻止剩余树。
4. 单 root 事务内删除旧派生行，写 4 families、66 nodes、53 main turns 与 source 游标。
5. 第二次运行全部 hash/version 未变，结果为 `0 imported / 66 skipped`，业务数据和游标时间不变。

### 场景 B：一个子 payload 变化

1. pending 查询只返回变化的 child。
2. service 读取同一 root 的全部 payload，重算整棵树。
3. 删除并重写该 root 的会话视图。
4. 预期只有变化 child 的 processed 游标刷新；当前实现还会刷新未变 main 的 `processed_at/last_sync_run_id`（D2）。

### 场景 C：root 结构失败

1. normalizer 仍隔离坏行，但缺 main、重复 main、环等由 assembler 返回 root 级错误。
2. 失败发生在删除事务之前，旧树与旧 source 游标保留。
3. service 写稳定 `ROOT_*` 或 assembler code，并继续下一个 root。

### 场景 D：progress 回调

1. m2-06 可通过 `on_progress(done, total)` 接任务进度。
2. root 事务提交后，service 才调用回调。
3. 当前回调抛异常会进入“root 重放失败”分支，甚至在同一失败分支再次调用回调，导致“库已提交、结果记失败/批次中断”（D1）。

## §6 讨论点

### D1 progress 回调失败会把“已提交成功”记成失败，并可能中止整批

**位置**：`apps/api/app/service/acquisition/replay.py:126-181`，尤其 `161-169` 的事务提交与异常捕获、`180-181` 的失败分支回调。

**现象**：用一个第一次调用抛 `RuntimeError` 的 `on_progress` 实测：canonical root 已完成事务提交，但异常落入 `except Exception`，root 被计为 failed；失败分支再次调用同一回调后，异常继续冒泡，批次没有执行 `finish_sync_run`。

**问题**：progress 是 m2-05 显式提供的外部注入缝，不应反向决定 canonical 写入成功与否。当前还可能把同一 root 的 `failed` 与 `processed_candidates` 增两次，并在下一次运行因游标已推进而永久跳过这个“失败”root。

**预判**：这是先修为妙的批次一致性缺陷。建议把 progress 回调移出 root 事务失败判定范围，并明确定义回调异常策略：要么作为非致命观测错误记录一次，要么以独立 `SYNC_PROGRESS_FAILED` 结束批次，但绝不能回滚标签与已提交数据相反，也不能重复计数。

**结论**：已修复（2026-10-25）。progress 回调位于 root 结果判定之外；首次异常只追加 `SYNC_PROGRESS_FAILED` 并停止后续回调，已提交 root 仍计成功，批次继续完成。

### D2 root 内一个 payload 变化会误刷新未变 sibling 的 processed 游标

**位置**：`apps/api/app/db/crud/acquisition_replay.py:427-441`；调用处 `apps/api/app/service/acquisition/replay.py:161-168`。

**现象**：root 含 main + child，先重放，再只改 child 并重放；实测 main 的 `processed_at` 从 `21:51:53.171514` 被刷新到 `21:51:53.179446`，main 的 `last_sync_run_id` 也会改成新批次。

**问题**：06 §3.1 把 `processed_at` 定义为该 payload “最近一次归一化完成时间”，并要求 hash/parser 未变时跳过。为了重算 root 聚合而重写 sibling 的 canonical 行可以理解，但把 sibling 的 source 游标写成新批次会让审计误报它被重新规范化，也违反 Agent Note 中“未变输入不产生伪写入”的承诺。

**预判**：应在 root 重建时只推进本次 pending 的 source identities；parser 升级时所有对应 payload 本来都会 pending，因此自然全部推进。需要补“只改 child，main processed_at/last_sync_run_id 不变”的回归。

**结论**：已修复（2026-10-25）。重建 root 时仅推进本批 pending source；未变化 sibling 保留 `processed_at/last_sync_run_id`，变化 source 的 `line_count/kind/source_type` 在同事务更新。

### D3 payload 删除后，同 root 再次重建会丢失原业务节点，也没有删除日志

**位置**：`apps/api/app/service/acquisition/replay.py:127` 只加载当前 payload；`apps/api/app/db/crud/acquisition_replay.py:326` 删除整个 root；设计规则见 `plans/fullstack-design/06-database-design.md:147`。

**现象**：root 首次重放后有 main + child；删除 child payload，再修改 main 触发 root 重建，重放后 `agents` 只剩 main。纯删除、没有其他 pending 时不会立刻丢树，但下一次 parser 升级或 sibling 变化会丢。

**问题**：设计明确要求 payload 侧删除首版保留业务数据并记日志。当前只在“没有其他变化”时偶然保留；触发 root 重建就会级联掉已消失 payload 的 Agent/Event，且 errors 为空，审计无法发现。

**预判**：这是数据保留缺陷。最小方向有两种：重建前检测该 root 是否存在无当前 payload 的 source identity，保留其旧 canonical 子树；或 fail-closed 该 root 并记稳定 code，避免部分删除。无论哪种，都应补“删除 child 后 main 变化”的实测。

**结论**：已修复（2026-10-25）。payload 消失的 source 会生成 `MISSING_PAYLOAD_SOURCE`；受影响 root fail-closed，不执行删除重写，旧 Agent/Event/Turn 与会话保持完整。

### D4 失败 root 不影响 `records_done`，completed 批次进度会低报

**位置**：`apps/api/app/service/acquisition/replay.py:190-198`。

**现象**：结构失败测试有 3 个候选：2 个成功、1 个失败；批次写 `records_done=imported+skipped=2`，而所有候选都已被尝试。

**问题**：`records_total/records_done` 是批次进度。若 failed 不计 done，completed 批次会显示 2/3，像仍在运行；若把 failed 视为仍需重试，也应通过状态/剩余量明确表达，而不是让 completed 与进度互相矛盾。

**预判**：需先明确 done 的定义。通常 `done=imported+skipped+failed`，错误单独从 errors/failed 统计表达；若平台确实只把成功计入 done，则字段命名和 UI 语义应改，当前没有文档解释。

**结论**：已修复（2026-10-25）。completed 批次的 `records_done=imported+skipped+failed`，失败尝试不再留下永久低于总量的进度。

### D5 payload 消失没有批次级审计

**位置**：`apps/api/app/service/acquisition/replay.py:103-190`；pending 只从当前 payload 出发，source 中多出的身份不会被检查。

**现象**：删除 payload 后单独重放，结果为 0 imported / 剩余 payload skipped，`sync_runs.errors=[]`。

**问题**：06 §3.1 要求“保留业务数据并记日志”。当前保留是事实现象，不是受测保证；且同步批次没有记录哪些 payload 已从上游消失，后续诊断无法知道业务树为何包含“无源节点”。

**预判**：若 D3 采用保留旧子树方案，这个 warning 应同批写入；若采用 fail-closed，也应输出稳定 code。可以和 D3 在同一修复中处理。

**结论**：已修复（2026-10-25）。每次 replay 都审计无 payload 的 source identities；独立删除也会写入稳定脱敏 warning。

### `apps/api/app/service/acquisition/replay.py`（A）

### `apps/api/app/cli.py`（M）

职责：新增 `replay-local` 子命令，把本地 session import 和 pending replay 串起来，输出 aggregate-only JSON。入口继续复用无 symlink 的路径规范化，符合本地数据隐私约束。

检视发现：无。命令输出不包含 payload 正文或绝对路径。

### `apps/api/tests/m2-05-idempotent-replay/test_replay_service.py`（A）
