## §1 一页速览

**一句话：** 这个 PR 在自进化列表页装了一个"挂号台"——第一步选对象/时间/模型，第二步先把"这次会抽到多少份问题报告"的统计与明细（6 列、每页 8 条）摆给用户看，确认后可以选择"启动自进化"或"只做聚类分析"；两张票都只返回 `202 {runId, jobId, status:"preparing"}`，真正干活留给后台。

**比喻：** 向导像体检中心的挂号窗口：Step1 是填单子，Step2 是"本次预计抽几管血"的预检清单（命中统计 + 分页明细），确认后窗口只给你一张**受理单**（202），并不是"已经检查完"。普通号（full）去 `/evolution/runs/:id`，只做影像检查的号（cluster_only）去 `/evolution/cluster/:id`，两个房间当前都只挂"准备中"的牌子——因为后台诊室（`evolution_prepare` handler）要到 m5-06 才开张。

## §2 架构导览

### 2.1 HTTP 层：三个新入口，全部走共享 Bearer 鉴权

`POST /api/evolution/probes/query`、`POST /api/evolution/runs`、`POST /api/evolution/cluster-previews` 都挂了 `dependencies=[Security(BEARER_AUTH)]`（`api/evolution_launch.py:50,69`、`api/evolution_runs.py:44`），并在 OpenAPI 里显式声明 401/403/409/422（`api/evolution_launch.py:40-45`）。没有 admin 限制：05 §4.10 只对 retry 说"所有登录用户可调用"，启动同样对登录用户开放，前端入口也不分角色。

HTTP 层只做三件事：取 app-scoped service、把 body 交给 service、把异常交给统一 envelope（`errors.py:138-147`）。分组的复杂性没有渗进路由。

### 2.2 服务层：同步校验的顺序就是文档列的顺序

`EvolutionLaunchService.request_run` 的骨架（`service/evolution/launch.py:96-118`）：

```python
if body.mode != expected_mode: 422 VALIDATION_INVALID
config = await targets.find(...)          # 未配置/停用 → 409 TARGET_NOT_CONFIGURED
query = normalized_query(body, default_ref) # 版本兜底 + 窗口倒挂 → 422
await self._require_hits(query)           # 零命中 → 409 NO_PROBES_MATCHED
run = await self._runs.create_run(...)    # 先落 preparing 行
job = await self._jobs.submit("evolution_prepare", ...)
return RunAccepted(run_id, job_id, "preparing")
```

这条顺序保证了"校验失败不写库"：`test_start_run_rejects_window_and_empty_hits` 在两次失败后断言 `running == []`（`tests/m5-05-launch-wizard/test_launch_api.py:402-420`），实测成立。

### 2.3 一个请求两种校验路径

预览和启动各自实现了一遍"什么算命中"：

- 预览：`ProbeQueryService.preview` → `list_hit_rows` → 分组 → 只保留 `attribute_type ∈ {model,prompt,error}` 的项，`probes == 0` 时 409（`service/evolution/probe_query.py:218-254`）。
- 启动：`EvolutionLaunchService._require_hits` → 同一个 `list_hit_rows` → 只要存在 `probe_id is not None and analysis_status == "analyzed_issue"` 就放行（`service/evolution/launch.py:120-137`）。

两处的过滤条件不是同一份代码，也不是同一个谓词（一处看 attribute_type，一处不看）。在当前数据分布下结论一致；一旦上游写入 `attribute_type` 的第四种取值，就会出现"启动放行、预览 409"的分叉。这是本 PR 最值得收口的结构点：口径只有一份，实现却有两份。

### 2.4 仓储层：一次 join，两次查询，过滤在 Python 侧

`list_hit_rows` 以 `bad_cases` 为主表，左连 `bad_case_analysis`（按 bad_case_id）、`probe_reports`（按 probe_id）、probe 会话、上报会话与上报 agent，取出展示所需字段（`db/crud/probe_query.py:102-146`）。

```text
bad_cases ──1:1── bad_case_analysis ──0:1── probe_reports ──1:1── session_families(probe)
    └──1:1── session_families(case)        └──0:1── agents(case_agent)
```

时间窗与模型过滤不写进 SQL：窗口用 `probe 会话启动时间，缺失时回退上报会话启动时间` 在 Python 里逐行判断（`:150`、`:194-201`）；模型先用 `agents.root_session_id` 反查"该会话树里出现过哪些模型"（`:64-90`），再对**有 probe 会话的行**做交集（`:151-161`）。好处是语义写得清楚、方言无关；代价是全表拉取后在内存过滤，`bad_cases` 变大后需要把窗口/模型下推到 SQL（见 §6 D2）。

### 2.5 快照：启动那一刻把"运行期不再读配置"的东西全写死

`_run_values`（`service/evolution/launch.py:139-171`）把 `target_type/name/version`、`repo_url`、`sub_dir`、`base_ref`、`window_from/to`、`models`、`engine_key`、`eval_config`、`status=preparing` 一次性写进 `evolution_runs`。这正是 07 §5.3 的"两个创建期快照决定运行期行为"：运行期不再看配置表当前值。

实测确认这些列确实落入（`test_launch_api.py:437-457` 断言 target_config_id/repo_url/sub_dir/window/models）。但 `created_by` 没在这份 values 里（`db/crud/evolution.py:79` 取 `values.get("created_by")`）——这是 §6 D3 的证据来源。

### 2.6 作业层：202 之后立刻发生的事

`JobRunner.submit` 在插入 queued 行后立刻 `_schedule(job.id)`（`service/jobs.py:174-181`），`_run` 先在全局锁里取到 job，再查 handler 表；没有 handler 就 `RuntimeError`，被 catch 成 `repository.fail(...)`（`service/jobs.py:246-279`）。本 PR 没有 `jobs.register_handler("evolution_prepare", ...)`（`app/main.py:97-105` 只注册了 `pull`），于是：

```text
POST /runs → 202(preparing) → 10ms 内 job=failed("no handler registered for job kind evolution_prepare")
                             → terminal hook 只处理 sync（service/acquisition/sync.py:release_terminal_job）
                             → run 永远停在 preparing
```

本 PR 的 Note 把"run 停在 preparing"记为预期占位，但没说"每次启动都会留下一条 failed job"。§6 D5 讨论这一点。

### 2.7 前端数据层与路由

三个客户端函数在 `api/evolutionRuns.ts:12-60`，其中两个 POST 显式传 `acceptedStatuses: [200, 202]`——`request` 的默认白名单是 `[200,201,204]`，不传就会把 202 当错误（`api/http.ts:142-145`）。这是个容易踩的坑，PR 处理正确，且组件测试用 202 的 mock 覆盖了。

路由新增两条（`router/index.ts:54-61`），挂在 `/evolution` 之后、`/evolution/targets` 之前；没有新增 layout meta，与既有 `/evolution` 一致。

### 2.8 向导组件：一个组件同时装"表单"和"结果页"

`LaunchWizard.vue` 用 `step: 1|2` 控制两套模板（`:240`/`:375`），共享一个 `.modal` 外壳和 footer（`:508-547`）。状态机只有五个关键字段：`targetType/targetId/targetVersion/window*/selectedModels` + `preview`；`resetPreview()` 把 step/preview/page 一起清零（`:101-106`），任何条件变更都回到 Step1。

`preview` 是唯一的"结果事实"：统计、分布条、表格、分页信息全部从 `ProbeQueryResult` 读（`:262-267`、`:299-345`、`:346-364`），前端不做二次统计——这一点与 M5-04 的运行列表一脉相承。

### 2.9 落地页：以运行列表当"单条查询"用

`RunDetail.vue` 和 `ClusterPreview.vue` 都 `useEvolutionRuns()`，再从 `running/history` 里按 `runId` 找一条（`RunDetail.vue:13-25`、`ClusterPreview.vue:14-26`）。这是明确的占位：独立 `GET /runs/{rid}` 与 SSE 在 m5-07（Note 的 Consequences 已记录）。好处是跳转后立刻能显示"准备中"；代价是非 preparing 状态只能显示列表卡片的字段，而且状态文案没有共享映射（`RunDetail.vue:27-38` 只翻译了 preparing/running，其余直接回显 `status` 原值）。

## §3 数据流走查

### 场景 A：打开向导（实机截图见 `.tmp/wizard-390/01-step1-desktop.png`）

1. `Index.vue` 点"＋ 启动自进化" → `wizardOpen = true`（`Index.vue:54-61`），`LaunchWizard` 挂载。
2. 并行发 `GET /api/catalogs/targets` 与 `GET /api/catalogs/models`（`LaunchWizard.vue:56-57`）；`catalogs` 只含"已配置且启用"的对象（`service/catalogs.py:63-69` `list(enabled_only=True)`）。
3. `targetId` 初值为 `null`，所以名称下拉显示禁用占位"选择对象"；但 skill/agent 分段按钮一点就会自动选该类型第一个对象（`:74-82`）。
4. 版本下拉在 `versions` 查询 pending 时显示"读取版本…"（`:210-212`），**不会自动选中任何版本**；「下一步」按钮条件是 `!selectedTarget || !targetVersion || windowInvalid()`（`:541`），因此必须手动选版本才能继续。实测打开向导后：`target=synthetic-review, version=读取版本…, nextDisabled=true`。

### 场景 B：下一步 → 命中确认（实机截图 `.tmp/wizard-390/02-step2-desktop.png`）

1. `runQuery()` 组 body（`:108-120`：`targetType/targetName/targetVersion/from/to/models/page=1/pageSize=8/mode=full`）→ `POST /api/evolution/probes/query`。
2. 后端 `list_hit_rows` 取该对象 pair 的全部 bad case → 窗口过滤 → 模型过滤 → 分组 → 统计。
3. 200 时 `preview` 落地、`step = 2`（`:133-135`）；409 时留在 Step1，把 `error.message` 原样放进 `.wizard-error`（`:136-139`）——实测后端消息是英文 `"no analyzed probe matches the wizard condition"`，直接显示给用户。
4. Step2 渲染：条件摘要条（`:241-259`）、5 个统计（命中 session/问题报告/已分析/未分析/「是问题」进入聚类，`:261-267`）、分布条与图例（`:268-292`）、未分析提示（`:293-298`）、6 列 probe 表（`:299-345`）、分页（`:346-364`）。
5. 分页是"整页重查"：`changePage(next)` 改 `page` 后重新 POST（`:143-153`），后端从全量结果里切片（`service/evolution/probe_query.py:254-266`）。`total` 是命中 probe 数，不是坏例数。

### 场景 C：仅聚类出口（E2E 覆盖）

1. 点"启动问题聚类分析"→ `launch("cluster_only")` → `POST /api/evolution/cluster-previews`（`:155-171`）。
2. 后端 `expected_mode="cluster_only"`，落一行 `mode=cluster_only`、`engine_key=cluster_only` 的 preparing run，入队 `evolution_prepare`，202（`api/evolution_launch.py:75-84`、`service/evolution/launch.py:111-118`）。
3. 前端 `emit("launched","cluster_only",runId)` → `Index.onLaunched` 失效 `queryKeys.evolutionRuns` 后 `router.push('/evolution/cluster/:id')`（`Index.vue:32-41`）。
4. 落地页从运行列表找到该 run，显示"准备中"（E2E 断言 `landing.status.includes("准备中")`，`tests/e2e/m5-05-launch-wizard.test.mjs:314-331`）。

### 场景 D：完整自进化出口（本次实测）

1. 点"启动自进化 →"→ `POST /api/evolution/runs` → 202。
2. 落地 `/evolution/runs/:id`，实测渲染：标题 `synthetic-review synthetic-1 自进化`，状态徽标 `准备中` + "已受理，正在准备筛选与聚类，完成后此处展示六步进度。"，info 面板 4 行（对象/时间窗口/模型/模式）。
3. 后端在同一时刻：`evolution_runs.status=preparing`；`job_runs` 里这条 prepare job 状态 `failed`，`error="no handler registered for job kind evolution_prepare"`（实测，见 §6 D5）。
4. 运行列表里能看到这条 run（`createdBy: null`，见 §6 D3），状态准备中，进度 `total=5, percent=0`（沿用 m5-04 的六步投影）。

### 场景 E：对象未配置/已停用

- 前端：这类对象根本不进 `catalogs`，所以不出现在下拉里（E2E 断言 `Explore` 不在选项内，`:251-254`）。"禁用"落地为"不出现"，与 08 §9.2 一致，与 issue 文案"禁用未配置对象"是两种表述。

## §6 讨论点

### D1 probe 命中口径：按"上报对象"还是按"根因对象"

**位置：** `db/crud/probe_query.py:140-144`（`where bad_cases.object_type/object_name/object_version`）、`service/evolution/probe_query.py:179-190`（`probeObject` 只用于展示）；对照 `plans/fullstack-design/05-api-design.md:212`、`:242`、`:746`。

**现象：** 命中集合的过滤条件是 **上报问题时的对象**（`bad_cases.object_*`）；根因对象（`probe_reports.probe_object/object_version`）只进入展示字段，而启动快照里的"目标"又来自第三个来源——用户选中的 target 配置（`service/evolution/launch.py:102-108`）。05 §3.4 明确写着 `objectName/objectType/objectVersion` 是"上报者/发现者，不是根因"，并且"`probeObject @ objectVersion` 是自进化 target 的**唯一来源**"；§4.9 又断言"命中的 probe 必然属于该 target（`probeObject @ objectVersion`），所以 `usedProbes = probes`"。三句话与实现不是同一口径。

**问题：** 一旦"上报对象 ≠ 根因对象"，就会出现两个方向的错配。举 05 §3.4 自己的例子：bad case 上报对象是 `deep-research`，归因后 probe 是 `Explore@v1.0.1`。当前实现下：选 `Explore` 查不到这条命中（因为 bad case 的 object 是 deep-research）；选 `deep-research` 能命中，但界面"根因对象@"列会显示 `Explore@v1.0.1`，而启动的 run 快照 `target_*`/`repo_url`/`sub_dir`/`base_ref` 全部来自 deep-research 的配置——等于用 A 的仓库去跑 B 的根因聚类。文档自身也不自洽：§3.4 的例子说同一个 `pr-050b-03` 的 probeObject 是 Explore，§4.9 的示例响应却把它的 `probeObject` 写成 deep-research。现有 fixture 里每个 case 的上报对象与 probe 根因对象**刚好一一对齐**（`fixtures/m2-synthetic/corpus.json:292-410`），所以测试无法暴露错位。还有一个同源的小口径：`bad_cases.object_version` 为 NULL 的报告永远匹配不到任何版本（`fixtures/m2-synthetic/corpus.json` 里的 `badcase-synthetic-0004` 就是这种，没写 version），需要一句定性——是"版本必须精确匹配"的有意行为，还是历史数据被静默漏掉。

**预判：** 建议以 §3.4 为准：命中口径 = `probe_reports.probe_object/object_version`（`bad_cases.object_*` 可作为"上报对象"附加筛选），启动快照的目标也取自 probe 对象；另一种同样自洽的选择是"以用户选择的上报对象为准"，那就需要修订 §3.4/§4.9 的表述并把表格列名从"根因对象@"改成"上报对象@"。无论选哪边，都应该补一个"上报对象与根因对象不同"的后端用例，否则这条口径永远没有回归。

**结论：**（留空）

### D2 命中统计的三个口径细节：models 漏未分析、sessions 定义、analyzed 分母

**位置：** `db/crud/probe_query.py:150-161`、`service/evolution/probe_query.py:229-245`、`:256-265`；对照 `05-api-design.md:739-745`。

**现象：** 三个可验证的口径都值得定稿。(1) 模型过滤只对有 probe 会话的行生效，未分析行被无条件保留——实测 `models=["glm-5.3-flash"]` 时 `unanalyzed=1` 来自只跑过 `glm-5.3` 的会话；(2) `sessions` 只统计"有 probe 的会话"（`probe_session_id is not None`），实测 `badCases=2` 却 `sessions=1`，而 05 §4.9 的示例是 `sessions:130 / badCases:1`，两者不可能同时成立；(3) `analyzed` 是"按 bad_case 行计数、包含 `analyzed_nonissue`"，`usedProbes = probes` 只算"是问题"——与 `05-api-design.md:305` 的 `usedProbes = model+prompt+error` 一致，但与原型 `used = analyzed - notProblem` 的推导顺序不同（结果相同）。

**问题：** 向导 Step1 的文案对用户承诺"只纳入这些模型跑出的报告"，未分析计数却不遵守，用户会看到"过滤了模型但它还是把别人的未分析报告算进来"；`sessions` 没有文档定义，导致 05 §4.9 的示例与实现互相矛盾，未来做 M5-07 详情统计时容易出现第二套解释。

**预判：** 未分析行改用上报会话/上报 agent 的模型过滤（`_CASE_SESSION` 与 `_CASE_AGENT` 已经 join 进来，只差取 `model`）；在 05 §4.9 增补 `sessions` 的定义（建议"命中报告涉及的会话数，含未分析"）并把示例数字改自洽；三个统计各补一条"混合 analyzed/unanalyzed + 模型过滤"的用例。

**结论：**（留空）

### D3 启动的 run 没有创建人

**位置：** `service/evolution/launch.py:139-171`（`_run_values` 无 `created_by`）、`db/crud/evolution.py:79`。

**现象：** `request_run` 把 `created_by` 只传给了 `jobs.submit`（`:112-117`），没有传给 `create_run`；`create_run` 用 `values.get("created_by")` 取到 `None`。实测：登录 admin 启动后 `GET /api/evolution/runs` 返回 `createdBy: null`，而同一时刻 job 行的 `createdBy` 是真实用户 id。

**问题：** M5-04 交付的"创建人 + 创建时间" meta（`RunCard.vue:50-52`）在 M5-05 新流程上永远只剩时间；05 §3.5 明确要求"`createdBy` 是创建人的可空显示名，删除用户后为 null"。这不是可空语义，而是**所有新 run 都为空**，等于把上一刀的能力在本刀接回去时丢了。

**预判：** `request_run` 把 `created_by` 一并交给 `_run_values`（或直接 `values["created_by"] = created_by`），并在 `test_start_run_accepts_and_snapshots_query` 里断言 `row["created_by"]` 与卡片 `createdBy` 非空。改动约 3 行。

**结论：**（留空）

### D4 eval 配置明文入库、engineKey 未校验

**位置：** `service/evolution/launch.py:157-159`（`"eval_config": body.eval or {}`）、`:174-194`（job payload 里的 eval）、`service/jobs.py:50-61`（`sanitize_job_payload`）；对照 `05-api-design.md:775`、`errors.py:19-50`。

**现象：** 用 `eval:{"apiKey":"sk-live-abc123","provider":"x"}`、`engineKey:"nope-not-registered"` 调 `POST /runs`，实测返回 **202**；随后数据库里 `evolution_runs.eval_config = {"apiKey": "sk-live-abc123", "provider": "x"}`（明文），而同一份条件进入 job payload 时被 `sanitize_job_payload` 打成 `"apiKey": "<redacted>"`。也就是说同一份数据在 job 表被脱敏、在 run 表被原样留存。`engine_key` 也原样落库为未注册值，没有 `422 ENGINE_INVALID`（该错误码在 `ErrorCode` 里根本不存在）。

**问题：** 05 §4.10 明确"密钥用 env 引用名，不落库"，§8 也定义 `ENGINE_INVALID`（422）用于"engineKey 未注册或 eval 非法"。当前实现把两个校验都推迟了，但**快照已经落库**：即使 m5-06 在引擎工厂处补校验，明文密钥已经写进 DB/备份，事后失败也只是把 run 变 failed。仓库对 job payload 有脱敏策略，说明这是有意识的安全面；run 快照漏掉同一条策略，属于不一致。

**预判：** 本 PR 至少做两件事之一：(a) 对 `eval` 落库前复用 `sanitize_job_payload`（或只允许 `{"<键>Env": "HE_EVAL_..."}` 这种引用名形状，拒绝疑似密钥）；(b) 把"engineKey/eval 校验与 ENGINE_INVALID 推迟到 m5-06 引擎注册表"写进 Note 的 Consequences（当前 Note 反而说"共用同一套校验"）。两者都做则最稳。

**结论：**（留空）

### D5 202 受理之后 prepare job 立刻 failed

**位置：** `service/evolution/launch.py:112-117`、`service/jobs.py:246-279`、`app/main.py:97-105`（只注册 `pull`）。

**现象：** 实测 202 返回后约 10ms，`GET /api/jobs/{jobId}` 显示 `status: "failed"`，`error: "no handler registered for job kind evolution_prepare"`；`GET /api/evolution/runs` 仍显示该 run `preparing`（terminal hook 只处理 `sync`，`service/acquisition/sync.py:release_terminal_job`）。连续两次启动会留下两条 failed job 与两条 preparing run。

**问题：** Note 把边界写成"本切片不注册 handler → run 停在 preparing，是预期占位而非缺陷"，这句话对 run 成立，但对 job 不成立：每次正常启动都会写一条**失败**的内部作业记录，并把内部实现错误串持久化。05 §4.10 的状态机里没有"preparing 但作业已失败"这种组合；等 m5-06 接 handler 时，这些历史 failed job 需要额外的清理/兼容，`GET /api/jobs/{id}` 也会把 `no handler registered` 暴露给任何调用方（现在前端没调，但接口存在）。

**预判：** 二选一并写进 Note：(a) 注册一个占位 handler（例如只记一条 progress 事件后正常结束），让 job 成功、run 继续停在 preparing；(b) 保留失败并显式说明"接线前每次启动都会产生 failed job，m5-06 首个任务负责处理存量"。若选 (a)，改动只有一个函数 + 一行注册。

**结论：**（留空）

### D6 版本不默认选中，版本列表失败时无提示死锁

**位置：** `components/LaunchWizard.vue:66-71`、`:210-212`、`:427-445`、`:541`；对照 `08-frontend-implementation.md:477`。

**现象：** 实测打开向导：对象已自动选中 `synthetic-review`，版本停在占位"读取版本…"，「下一步」`disabled=true`；必须手动点版本才能继续。08 §9.2 要求"版本：`useTargetVersions(targetId)` 拉 tag 列表；**默认选中 `defaultRef` 对应项**"。另外 `useEvolutionTargetVersions` 是 `retry: false`（`composables/useEvolutionTargets.ts:70-81`），仓库不可用（`422 REPO_INVALID`）时 `versions` 进入 error，而 `versionOptions` 会回退到 `catalog` 里的 `versions`；若两者都为空，版本下拉只剩一个 disabled 占位，用户永远无法进入下一步，页面上也没有任何错误提示（版本查询的 error 没有渲染）。

**结论：**（留空）

### D9 向导自研弹层：与 08 §12.3 的 Element Plus 分工不一致，且缺对话框语义

### D10 重复提交无幂等，run 与 job 不在同一事务

### D12 同一份 body，两个端点对 targetVersion 的接受度不同

**位置：** `service/evolution/probe_query.py:132-138`（`normalized_query` 无默认版本时 422）、`service/evolution/launch.py:102-109`（用 `config.default_ref` 兜底）。
