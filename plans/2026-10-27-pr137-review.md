## §1 一页速览

**一句话：** 这个 PR 把“运行列表里的一张卡”延伸到一张可深链、可读六步产物的运行详情页；页面先拿一个后端算好的外壳，再按用户当前选中的节点懒加载该步内容。

**比喻：** 详情壳像火车站的总调度牌，哪一步已到站、哪一步正在开、哪一步还没到，都由后端翻牌；六个 step 端点像六个站台取件口，前端只在牌子允许时走到对应口取一份产出。前端不拿秒表自己猜列车位置，因此刷新、深链和运行中状态都读同一块调度牌。

## §2 架构导览

### 2.1 后端用一个详情壳复用列表事实

`EvolutionRunDetail` 直接继承 `EvolutionRunCard`，再加上 `blockedStage`、重试上下文、`evalStatus`、workspace、`lastEventSeq` 与六步数组（`apps/api/app/service/evolution/runs.py:168-177`）。

仓储层把原列表专用的 `list_summaries()` 抽成 `_summaries(run_id=None)`；详情调用 `get_summary(run_id)`，仍然一次批量取 creator、cluster count、accepted count 和 final，不按 step 做 N+1（`apps/api/app/db/crud/evolution.py:106-201`）。

HTTP 层只增加一条薄路由：取 service.detail，`None` 映射为稳定的 `RUN_NOT_FOUND`（`apps/api/app/api/evolution_runs.py:74-92`）。六个 step 路径沿用 m5-06 的既有实现。

### 2.2 六步状态仍只有一个来源

`step_states(progress_unit, cluster_count, run_status)` 是唯一状态机；`_detail_steps()` 只是把它的 `StepState` 投影成 API DTO，并给 active 的 iteration 补“第 x/y 轮”展示文案（`apps/api/app/service/evolution/runs.py:312-351`）。

这不增加第二套前端规则。前端 `defaultRunStepKey()` 只在已有 `status` 上选“第一个 active，否则最后一个 done，否则 input”（`apps/web/src/pages/evolution/runDetail.ts:11-16`），`resolveRunStepKey()` 只接受后端 `clickable` 的节点（`:24-30`）。

### 2.3 前端先取壳，再取当前一站

`RunDetail.vue` 同时建立两个 query：

```text
GET /api/evolution/runs/{rid}
        │
        ├─ steps / workspace / blocked / error
        │
        └─ selectedKey ─► GET /api/evolution/runs/{rid}/steps/{key}
```

第二个 query 的 `enabled` 是 `selectedStep.clickable === true`（`RunDetail.vue:27-46`），因此未到达节点不会用 404 做探测。点击已完成/进行中的节点只 `router.replace({ query: { step } })`（`:138-146`）。

### 2.4 六种 step 是同一详情壳下的独立取件口

`RunStepContent.vue:43-74` 按 key 分派六种组件，统一处理 loading、unreached、cluster missing 事件。这样六个 DTO 保持 key-discriminated，而页面只有一个壳。

`DiffView` 不解析 unified diff，直接按行首 `+/-/@@` 着色（`DiffView.vue:8-12`）。`EvalCompare` 用 `max(cur,cand)*1.06` 归一，并用 accepted 而不是“分数变大”决定是否宣称提升（`EvalCompare.vue:11-48`）。这两点与 08 §10.3 及原型一致。

### 2.5 深链、错误和状态交集都有专门测试

页面测试覆盖 failed-before-step-1、preparing、单步请求、query 切换、无效 cluster、completed final、blocked 上下文、run 读取失败和 RUN_NOT_FOUND（`RunDetail.test.ts:254-673`）。

conformance 测试覆盖真实状态交集：`pushing + push.failed`、`evaluating + eval.failed`、`patching + blockedStage=patch`，并覆盖 rejetected/accepted/failed/timeout 的评测文案（`RunDetailConformance.test.ts:221-343`）。

E2E 用一个真实 API + Vite 的组合走列表 → running iteration → cluster 深链 → blocked → completed → 390px 移动布局，并断言横向溢出为 0（`tests/e2e/m5-run-detail.test.mjs:226-422`）。

## §3 数据流走查

### 场景 A：用户从运行列表进入正在迭代的 run

1. 运行卡根据 `run.mode` 生成详情路径，阻止原生跳转后交给 router（`RunCard.vue:59-70,96-104`）。
2. 详情请求返回 `steps=[done,done,done,done,active,pending]`；`defaultRunStepKey()` 选中 iteration。
3. 页面只请求 `steps/iteration`，stepper 的 final 节点 disabled。
4. `StepIterations` 默认展开第一个非终态 round，展示 candidate ref/commit、推送状态、EvalCompare 与下一次轮询时间。
5. 用户点 clusters 后 query 变成 `?step=clusters`，第二步被请求；切换到其它非 cluster 步骤时删除 `cluster=`（`RunDetail.vue:138-146`）。

### 场景 B：cluster commit message 深链到具体簇

1. URL 带 `?step=clusters&cluster={id}`。
2. Step 2 数据到达后，`StepClusters` 找目标 id；存在时展开、高亮并 `scrollIntoView`。
3. 不存在时显示“目标簇已不存在”，同时通知父页删除失效 query（`StepClusters.vue:32-53`；`RunDetail.vue:167-172`）。
4. 删除 query 后组件保留 notice，避免用户只看到“参数消失但不知道原因”。

### 场景 C：run 停在 eval 失败

1. 详情壳返回 `status=blocked`、`blockedStage=eval`、`evalStatus=failed`、错误摘要与重试时间。
2. 页面顶部 blocked banner 先给阶段、错误、retry attempts、next retry 和时间（`RunDetail.vue:215-233`）。
3. 当前 iteration step 仍可读。round 可以停在 design-valid 的 `evaluating`，再由 `eval.status=failed` 推导为“评测失败”，而不是依赖不存在的 `round.status=blocked`（`StepIterations.vue:53-100`）。
4. 本轮 patch/push 中间状态仍保留，便于恢复切片接过。

### 场景 D：completed run 的终评

1. 六步全部 done，默认选 final。
2. final payload 给出 verdict、best/init score、结构化 metrics 和 accepted changes。
3. workspace 同时把最终 push status 和 pushedAt 传入终评组件（`RunStepContent.vue:68-74`）。
4. 页面展示 verdict 横幅、修改点、指标对比与最终 push 时间（`StepFinal.vue:84-173`）。

## §6 讨论点

### D1：来源问题深链没有遵循“新窗口 + 短 ID”契约

**位置：** `apps/web/src/pages/evolution/components/ProbeSourceTable.vue:10-15,51-59`

**现象：** 报告 ID 与来源问题 ID 都用同窗 `RouterLink`；两者都显示完整 `probeId` / `badCaseId`。原型使用 `target="_blank" rel="noopener"`；全局 F2 还要求 UI 显示短 ID。

**问题：** 用户在运行详情里点一个来源问题会被导航离开详情，失去当前 step、展开卡和簇高亮；真实 UUID 也可能撑宽六列表格。设计给出的“报告 ID 落归因 tab、问题 ID 落问题描述 tab”本身正确，但恢复方式不完整。

**预判：** 这是一个用户可见的行为缺陷，应在本 PR 修；复用 `badCaseDeepLink()` 与 `shortBadCaseId()`，改成显式 `<a target="_blank" rel="noopener noreferrer">`，并补一条断言新窗口与短 ID 的组件测试。

**结论：** ✅ 2026-10-27 已修复。来源表复用 canonical deep-link/short-ID 工具，报告与问题分别打开 `attr`/`desc` tab；测试覆盖短文本、完整 `title`、安全新窗口属性和两个目标 URL。

### D2：`lastEventSeq` 当前固定为 0，与 API 契约字面不一致

**位置：** `apps/api/app/service/evolution/runs.py:176,398`

**现象：** 05 §3.5 `:306` 定义 `lastEventSeq` 为 DB 当前最大事件序号，实现固定返回 0；Agent Note 明确把事件表与分页/SSE 留给 m5-08。

**问题：** 当前详情页不消费该字段，因此无用户实害；但任何外部消费者若信任契约，会误判 run 没有任何事件。事件表和查询适配器已经存在（`apps/api/app/db/crud/run_events.py`），只是没有 run 级“当前最大 seq”读接口。

**预判：** 这是有意的切片边界而非本 PR 应立即扩容的功能。建议在 m5-08 接入真实 max seq，并把本 PR Note 中“当前为 0”的欠账保留为明确前置依赖；若坚持本 PR 自洽，则应把它改为 `null` 并在 contract 中显式表达“尚未接入”。

**结论：** ✅ 2026-10-27 裁定保留为 m5-08 交付。当前页面不消费该字段，事件持久化属于 m5-08；该切片必须把 0 替换为 run 的实际最大 event seq，并使用非空事件表测试。本 PR 不扩成跨切片事件读取。

### D3：已接纳轮次没有显式标出评测时的 commit

**位置：** `apps/web/src/pages/evolution/components/StepIterations.vue:194-248`

**现象：** 页面同时展示 candidate ref/commit 和 amend 后 final commit，但没有 08 §10.3 `:567` 要求的 `Harness-Evaluated-Commit` 标签。

**问题：** candidate commit 已在上一段可见，用户仍可追溯“评测的是哪个 commit”；缺的是明确语义标签，审计时要把 candidate 与 final 的对应关系自己推断。API 的 `StepRound` 已同时包含 `candidate.commit` 与 `finalCommit.hash`，无需改契约。

**预判：** 低成本的文档/UI 语义修复：在 accepted 卡中把原 `candidate.commit` 标成“评测 commit / Harness-Evaluated-Commit”，final commit 保持“amend 后 commit”。若不修，应在 Note 记录接受理由。

**结论：** ✅ 2026-10-27 已修复。accepted 卡显式展示 `Harness-Evaluated-Commit` 与 candidate hash，再展示 amend 后 final commit；测试同时断言两个 hash 与标签。

### D4：原型迭代展开卡里的 LLM 归因摘要在实现中不存在
