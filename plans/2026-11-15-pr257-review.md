## §1 一页速览

一句话：把“Session 与 bad case 能不能读”从“数据库里有没有这行”改成“调用者能不能看见它所属的空间”，并且给 V2 前端一套显式的 `/workspaces/{wid}/…` 读路径。

比喻：轨迹库是全公司共享的档案室，`session_families` 是档案本身；每个空间只有权看自己提交的 bad case。以前前端拿着任意档案编号就能调阅，现在门口多了一张“你属于哪些空间”的名单：档案要出现在名单里，才能在列表里看到；直接报编号也会被当成“没有这份档案”。同一个档案被两个空间同时引用时，每个空间只翻到自己那叠问题卡。

| 交付块 | 内容 | 关键位置 |
|---|---|---|
| 可见性口径 | 固定空间 / 用户成员空间 / 全局管理员全部；无默认构造 | `apps/api/app/db/crud/read_scope.py:16` |
| 空间投影 | 会话集合 = 空间 bad case 根会话 ∩ `session_families` | `apps/api/app/db/crud/read_scope.py:58` |
| V2 路由 | sessions / detail / tree / bad-cases | `apps/api/app/api/sessions.py:118`、`apps/api/app/api/problems.py:157` |

## §2 架构导览

### 2.1 一个 scope 对象，三种来源

`WorkspaceReadScope`（`apps/api/app/db/crud/read_scope.py:16`）只有 `workspace_id` 与 `user_id` 两个字段，三个构造入口：

- `for_workspace(wid)`：已由 `require_workspace_role` 授权的空间路由使用，SQL 条件退化为 `column = wid`。
- `for_user(user_id, role)`：V1 端点使用；普通用户展开为 `workspace_members` 子查询，`role=admin` 直接转成 `all_workspaces()`。
- `all_workspaces()`：只有全局管理员；条件为 `true()`。

没有默认构造，是刻意的：新增读路径必须显式选一种，漏传 scope 不会静默变成“全部可见”。`condition(column)` 只负责生成谓词，`session_condition()` 把同一谓词套到 `bad_cases.workspace_id` 再投影 `session_families.id`，两处读路径共用一份口径。

### 2.2 路由只做三件事

`apps/api/app/api/sessions.py` 与 `apps/api/app/api/problems.py` 的处理函数保持统一形状：声明 Bearer、声明最低空间角色、把 `WorkspaceReadScope` 交给 service。

- 旧端点在函数内用 `read_scope(request)` 从 `request.state.principal` 取用户与角色（`sessions.py:38`、`problems.py:39`）。中间件已验签，这里只读已验证声明。
- 空间路由直接用依赖返回的 `WorkspaceAccess.workspace_id`（`sessions.py:118`、`problems.py:157`）；`require_workspace_role` 已把不可见空间翻译成 `404 WORKSPACE_NOT_FOUND`。
- 路由不做任何行级过滤或兜底 404，避免“HTTP 层一套、service 一套”的口径漂移。

### 2.3 仓储负责投影与存储细节

`SessionRepository`（`apps/api/app/db/crud/sessions.py`）的列表、概览、树、计数统一先过 `scope.session_condition()`：

- 列表把投影条件放进 `conditions[0]`，与原有 q/status/sort 条件合取（`:215`）；排序、limit 仍在 SQL 里。
- 概览与树在同一个 `session_families` 查询上加投影（`:261`、`:284`）；树里的 `bad_cases` 再按同一个 scope 过滤（`:333` 附近），所以共享 Session 的树只返回本空间的问题卡。
- `bad_case_counts` 同时按 scope 过滤，列表上的 `stats.badCases` 不会把别的空间数量算进来（`:362`）。

`ProblemRepository`（`apps/api/app/db/crud/problems.py`）在快照读上做同样的事：`session_snapshot/case_snapshot/session_probes` 先确认 Session 在投影内，再按 scope 读 bad case（`:76`、`:99`、`:124`）。

### 2.4 外部表的“空投影”退化

`bad_cases` 是外部引导表：应用迁移只建内部表，首次上报或 fixture seed 才创建它。初版实现直接在 `/api/sessions` 的 SQL 里引用 `bad_cases`，在全新数据库上会 500；m1-shell E2E 立刻抓到了这个回归。

修复方式是在仓储实例上做一次存在性探测（`bad_cases_table_present`，`read_scope.py:67`），缺失时返回空投影（列表 `[]`、概览/树 `None`、计数 `{}`），存在后缓存 `True` 不再重复查元数据。代价是“表尚未创建”期间每次读多一条 `has_table` 查询；真实部署在首次上报后只付一次。

### 2.5 探针：没有空间列时的最小边界

`probe_reports` 还没有 `workspace_id`（0015 归因迁移未落地），所以探针无法直接按空间过滤。实现分两层：

- 会话内探针列表：只保留“关联到可见 bad case”的探针，或完全没有归因关联的探针（`problems.py:136` 附近）。后者没有空间归属，继续随 Session 可读。
- 单条探针详情：先确认 Session 可见，再看是否存在可见的归因关联；有关联但都不可见 → 404（`problems.py:184`）。

这样修掉了初版的真实泄漏：同一根 Session 被 A/B 两个空间上报时，B 空间不能读到 A 空间 case 产出的探针。等 0015 给 `probe_reports` 加列后，可改为直接读空间列。

## §3 数据流走查

### 剧本 A：Alice 打开空间 A 的 Session 列表

1. `GET /api/workspaces/ws-a/sessions` 带 Bearer。
2. 中间件验签并写入 `request.state.principal`。
3. `require_workspace_role("viewer")` 查 `workspace_members`；Alice 是 viewer → 通过；不是成员 → 404 `WORKSPACE_NOT_FOUND`。
4. 路由用 `WorkspaceReadScope.for_workspace("ws-a")` 调 `SessionService.list`（`sessions.py:118`）。
5. 仓储生成 `id IN (SELECT bad_case_session_id FROM bad_cases WHERE workspace_id = 'ws-a')`，叠加 q/status/sort/limit（`crud/sessions.py:215`）。
6. `bad_case_counts` 用同一 scope 聚合，Session 1 的 `stats.badCases` 只算空间 A 的 1 条。
7. 响应 `SessionListResponse`；本轮仍是 `{items}`。

### 剧本 B：同一个 Session 被两个空间上报

1. `GET /api/workspaces/ws-a/sessions/{sid}/tree` 与 `/api/workspaces/ws-b/...` 分别固定自己的空间。
2. 树查询先确认 `sid` 在自己的投影里；两边都命中。
3. `bad_cases` 查询带各自 scope，Alice 只拿到 A 的卡，Bob 只拿到 B 的卡（`crud/sessions.py:333` 附近）。
4. 若 Alice 直连 B 的 Session 但 A 没有上报过它 → 404 `SESSION_NOT_FOUND`；若 B 空间本身不可见 → 先 404 `WORKSPACE_NOT_FOUND`。

### 剧本 C：V1 深链仍然可用

1. 浏览器旧页面调用 `GET /api/sessions`、`/api/sessions/{sid}`、`/tree`、`/bad-cases`、`/api/bad-cases/{id}`。
2. 路由把 principal 转成 `WorkspaceReadScope.for_user`，SQL 展开为 `workspace_id IN (SELECT workspace_id FROM workspace_members WHERE user_id = ?)`；全局管理员走 `true()`。
3. 任何越界 Session/bad case 返回 `404 SESSION_NOT_FOUND`/`BAD_CASE_NOT_FOUND`，与“空间不可见”保持同一状态码。
4. 旧页面的 DTO 完全不变，E2E 19/19 证明布局、深链和错误态没有回归。

### 剧本 D：探针详情

1. `GET /api/probes/{probeId}` → 先读 probe 行（`BadCaseService.get_probe_result`）。
2. `ProblemRepository.probe_visible` 确认 probe 的 Session 可见（`problems.py:184`）。
3. probe 没有任何 `bad_case_analysis` 关联 → 允许（没有空间归属）。
4. 有关联 → 必须至少一条关联的 `bad_cases.workspace_id` 在 scope 内；否则 404 `PROBE_NOT_FOUND`。

## §6 讨论点

### 讨论点 1：共享 Session 的探针边界（已修复）

**位置**：`apps/api/app/db/crud/problems.py:184`、`:124`。
**现象**：初版只按“Session 可见”放行探针；`probe_reports` 没有 `workspace_id`。
**问题**：同一根 Session 被 A/B 两个空间上报时，B 空间能读到 A 空间 case 产出的探针内容，与“所有读路径过 workspace 限制”的验收不符。
**预判**：这是真实的跨空间信息泄漏，但只存在于 V1 探针兼容端点；V2 归因端点不在本 issue。
**结论**：已在本 PR 修复（commit `29cdd84`）：探针至少要求一条可见的归因关联；无关联探针保持 Session 级可见。回归测试与真实服务冒烟均覆盖。

### 讨论点 2：没有 bad case 的 Session 从 V1 列表消失

**位置**：`apps/api/app/db/crud/read_scope.py:58`。
**现象**：`session_families` 里存在、但没有任何 workspace bad case 的 Session，不再出现在 `/api/sessions`，直连 404。
**问题**：这是设计“空间 Session 集合 = 空间 bad case 根会话投影”的直接后果，但对既有运维习惯（先导轨迹、后补 bad case）是一次可见行为变化。
**预判**：符合 06 §7.5；如果运维需要“先看轨迹再补 bad case”，应在同步/上报流程里给出待同步提示，而不是放宽读权限。
**结论**：留待维护者确认是否需要在部署/接入文档中显式说明。

### 讨论点 3：空间 Session 列表响应未带 total/pendingSessions

**位置**：`apps/api/app/api/sessions.py:118`。
**现象**：`GET /api/workspaces/{wid}/sessions` 返回 `{items}`，与 05 §4.18 的 `{items,total,pendingSessions}` 目标态不同。
**问题**：m8-02 的验收要求默认 limit=10、root-id 精确搜索与待同步计数；本 issue 的非目标明确把“最新 10 条交互”留给后续。
**预判**：这是切片边界而非遗漏；若在 m7-06 提前加字段，会与 m8-02 的搜索语义重复。
**结论**：按 issue 非目标保留，m8-02 扩展该路由。

### 讨论点 4：`bad_cases` 缺失时的探测成本

**位置**：`apps/api/app/db/crud/read_scope.py:67`。
**现象**：表不存在时，每个读请求都会有一次 `has_table` 元数据查询；表存在后只查一次并缓存。
**问题**：全新安装若长期不接上报，Session 页每次刷新多一次元数据查询。
**预判**：无实害；真实部署一旦首次上报就不再有成本。若要优化，可给负结果加短 TTL。
**结论**：观察即可，暂不引入 TTL 复杂度。

### 讨论点 5：管理员判定使用 JWT role 声明

**位置**：`apps/api/app/db/crud/read_scope.py:40`。
**现象**：`for_user` 用 principal 的 `role` 决定是否放开全部空间；角色变更要等 token 刷新。
**问题**：与 m7-03/m7-05 的既有中间件行为一致，但不是实时数据库角色。
**预判**：访问 token 短生命周期，现有系统已接受该窗口；若要实时，应在中间件统一改，而不是只改读路径。
**结论**：维持现状，不在本 PR 单独收紧。

## §8 文件级分析

- `read_scope.py`：新增 82 行。scope 值对象 + 两个条件生成 + 外部表探测；无 I/O 副作用（探测除外）。无默认构造是有意的 fail-closed 设计。

- `test_database.py`：MySQL lane 用例调整为先插入 bad case 再读列表，符合新投影语义；其余断言不变。
- `openapi.json` / `api.d.ts`：5 条新 path 的生成结果；手写契约源码未改。
