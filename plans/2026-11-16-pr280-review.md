## 1. 一页速览

一句话：把“文件能解析”和“任务真的做完了”拆成两条轴，并把 Agent/Skill 定义与文件读取变成只含指纹的证据。

比喻：以前的导入器像只看快递外箱有没有破的收货员；现在多了一位验收员，箱子里“有没有回执、文件读全了没有、技能和 Agent 是不是同一版本”都由指纹记录，但**不看正文**。

交付块：

| 块 | 内容 |
|---|---|
| 元数据容错 | 已知字段严格校验；未知标量脱敏、截断、去凭据后入 `agents.meta`；未知对象/数组丢弃 |
| 完成状态 | 只认显式 `stop_reason`；`TOOL_USE_OPEN` / `MISSING_FINAL_REPORT` / `TASK_SNAPSHOT_PENDING` |
| 定义证据 | agent 定义 body hash、Skill path + body hash、文件 path/range/complete/content hash |
| 落库 | 会话/节点完成度、Agent 定义 hash/source、Skill 事件 `definition_hash` |
| 版本 | `claude-code` parser_version 1 → 2，触发本 runtime 重放 |

验证基线：`pnpm test:api`（91% 覆盖）、`test:db`、`test:gates`、`test:integration`、`verify:docs`、`contract:check`、`fixtures:check` 均通过；MySQL 与浏览器 E2E 由 CI 覆盖。

## 2. 架构导览

### 2.1 已知严格、未知降级（`local_sessions.py:51`、`_claude_meta.py:11`）

`ClaudeSubagentMeta` 从 `extra="forbid"` 改为 `extra="allow"`。已知字段仍是 Pydantic 的强类型与长度约束，未知字段不会让整棵树失败。`isBuiltIn` 的 camelCase 与默认别名生成结果不一致，因此单独写了 `Field(alias="isBuiltIn")`；不写这条，`isBuiltIn=false` 会被当成未知字段。

未知字段的落库面在 `sanitize_unknown_metadata`（`_claude_meta.py:63`）：

1. 只接受安全键名；
2. 敏感键（token/apiKey 等）直接丢弃；
3. 只接受标量，字符串走 `redact_text`、去控制字符、截断到 256；
4. 最多 32 个字段。

这保证“漂移不丢树”的同时不把任意嵌套对象或凭据灌进 `agents.meta`。

### 2.2 完成状态只从显式证据推导（`base.py:594`）

```text
fatal API error                         → failed / external_failed
stop_reason=end_turn                    → completed / end_turn
stop_reason=interrupted|user_interrupt  → interrupted / external_interrupted
stop_reason=tool_use + 有未配对 tool_use → interrupted / tool_use_open
stop_reason=tool_use + 无未配对 tool_use → interrupted / missing_report
没有 stop_reason                         → legacy_unknown / NULL
```

关键取舍：没有 `stop_reason` 的旧载荷不猜 completed。旧数据只能表达“未知”，不能表达“完成”；这与 M9-01 Note 的 legacy 口径一致。

诊断码在两个位置出现：

- `TOOL_USE_OPEN`：`end_reason=tool_use_open` 时记录未返回调用数；
- `MISSING_FINAL_REPORT`：`missing_report`，或子 Agent 停在 `tool_use_open`；后者意味着“既有未返回工具，也没有最终报告”；
- `TASK_SNAPSHOT_PENDING`：最后一次 `task_reminder` / `toolUseResult.task` 仍有 pending/in-progress。

### 2.3 证据 hook 与隐私边界（`claude_code.py:117`、`:199`、`:371`）

- Agent 定义：`prompt_snapshot.systemPrompt[0]` 优先，`api-request-shape.system` 兜底；`## Subagent Permissions`、`## Notes`、`Token budget` 等通用后缀在 hash 前裁掉。`isBuiltIn=true` 时只记 `builtin`，不产生 body hash。
- Skill：`isMeta=true` 且带 `sourceToolUseID` 的注入消息，提取 `Base directory for this skill:` 路径与正文 hash。
- 文件：Read/Edit 的 `toolUseResult` 提供 path、1-based range、complete、内容 hash；Bash 只有结果显式带文件结构时才记。所有 `TraceEvidence` 只有 hash/路径/范围/来源，没有正文。
- 模型：`requested_model` 与 `reported_model` 并存；只有两个“具体模型 id”不一致时才发 `MODEL_EVIDENCE_CONFLICT`，且不覆盖任一字段。`sonnet` 这类别名不误报。

### 2.4 树级聚合与落库（`agent_tree.py:357`、`acquisition_replay.py:677`）

会话完成度聚合顺序：任一 failed → failed；任一 interrupted → interrupted；任一 legacy_unknown → legacy_unknown；否则 completed。workflow 合成节点不参与，因为它没有独立执行证据。`end_reason` 优先主 Agent 的原因。

落库只写既有列：

- `session_families.execution_outcome/end_reason`
- `agents.execution_outcome/end_reason/agent_definition_hash/definition_source`
- `agent_events.definition_hash`（Skill 事件）

文件读取的 path/range 没有列，因此只保留在 parser 证据结构里；`file_read_hash/read_complete` 留给 M9-05 的知识事件。

## 3. 数据流走查

以脱敏 fixture 为例：

1. `scan_local_sessions` 读取根/子 JSONL 与 meta；未知字段 `futureFlag` 保留为标量，`futureNested`/`futureList` 丢弃，`apiKey` 丢弃（`local_sessions.py:264`）。
2. 根 JSONL 的 Read 调用 → assistant tool_use 进入 `open_tool_uses`；tool_result 记录 `toolUseResult.file` → `file_read` 证据（path、1-1、complete=true、sha256）。
3. Skill 调用 → `agent_events(kind=skill)`；后续 `isMeta+sourceToolUseID` 注入 → `skill_definition` 证据（path + body hash）。
4. 根最后一条 assistant 的 `stop_reason=tool_use`，`tool-agent-1` 没有 result → `interrupted/tool_use_open`，并产生 `TOOL_USE_OPEN`；任务快照仍有 1 in-progress + 1 pending → `TASK_SNAPSHOT_PENDING`。
5. 子 Agent `prompt_snapshot` → 定义 hash（裁掉 Subagent Permissions 后缀）；最后一条 assistant 是 `tool_use` 且工具都已返回 → `interrupted/missing_report`，产生 `MISSING_FINAL_REPORT`；`pickedEffortModel` 与实际上报模型不同 → `MODEL_EVIDENCE_CONFLICT`。
6. `assemble_agent_trees` 把 Skill 证据按 `tool_use_id` 挂回事件，会话完成度取 main 的 `tool_use_open`。
7. `replace_normalized_root` 写入完成度、定义 hash/source 与 Skill `definition_hash`；`sync_runs.errors` 保留诊断码。

## 6. 讨论点

### 讨论点 1：文件读取的 path/range 仍未落库

- **位置**：`apps/api/app/service/acquisition/parsers/claude_code.py:199`；`plans/fullstack-design/06-database-design.md` §3.4
- **现象**：TraceEvidence 有 path/startLine/endLine/complete，但 `agent_events` 没有对应列；落库只写 `definition_hash`。
- **问题**：本 issue 的目标是“提取文件 path、range、complete 与 content hash”，但 M9-05 才定义知识文档 `source_path`。现在保留在内存证据里是否足够？
- **预判**：足够。按 PR #279 的结论，M9-02 先把 path/range 放在 parser 证据结构，M9-05 需要查询时再加列，避免提前固化知识库口径。
- **结论**：留待 M9-05；本 PR 在 Note 与描述中如实标注。

### 讨论点 2：Bash 没有可靠文件身份

- **位置**：`claude_code.py:199`
- **现象**：只对 Read/Edit 的 `toolUseResult` 生成文件证据；Bash 仅在其结果显式携带 `file` 结构时记录。
- **问题**：issue 背景写了 Read/Bash/Edit，Bash 是否被漏掉？
- **预判**：Bash 的实际结果只有 stdout/stderr，没有路径；从命令文本猜路径会制造假证据。拒绝猜测比凑齐三种工具名更重要。
- **结论**：接受该限制，写入 Note；如果 M9-05 需要 Bash 知识读取，应由 adapter 白名单提供路径。

### 讨论点 3：历史载荷仍是 legacy_unknown

- **位置**：`base.py:594`
- **现象**：没有 `stop_reason` 的载荷不产生 completed/interrupted。
- **问题**：部署后存量会话在重放前仍显示 legacy_unknown，是否会被误读为“未完成”？
- **预判**：`legacy_unknown` 是独立枚举，客户端应显示“未知”，不能当 completed 也不能当 failed。M9-04 的 revision 重放会补齐定义证据，但不会凭空补 `stop_reason`。
- **结论**：保持现状；需要真实数据验证时以新导出的显式 `stop_reason` 为准。

### 讨论点 4：parser_version 1 → 2 的重放成本

- **位置**：`claude_code.py:265`；`source_records.parser_version`
- **现象**：所有 claude-code 源在一次同步内重放。
- **问题**：是否应该等到 M9-04 一起升级，减少一次全量重放？
- **预判**：解析语义已经变化，不 bump 会让存量真实会话永远拿不到完成度与定义证据；一次重放优于长期双口径。
- **结论**：接受；重放是幂等的，失败按现有 per-root 隔离。

### 讨论点 5：未知元数据保留的隐私面（已加固）

- **位置**：`_claude_meta.py:63`
- **现象**：未知标量会进入 `agents.meta`，可能携带凭据或私有路径。
- **问题**：仅长度截断是否足够？
- **预判**：不够。已加 `is_sensitive_key` 丢弃与 `redact_text` 脱敏；路径仍可能保留，因为 agent 定义/文件证据本身需要路径。
- **结论**：已决（2026-11-16）：敏感键丢弃，字符串凭据脱敏，嵌套对象/数组丢弃，单字段 256 字符、最多 32 个字段；测试覆盖 `apiKey` 与 `Bearer` 值。

## 9. 文件级代码分析

### 9.1 `apps/api/app/service/acquisition/parsers/base.py`（M）

职责：runtime 无关的解析模板、共享上下文、完成度与证据结构。

关键依赖：`hashlib` 标准库用于定义/文件指纹；`re` 只用于通用后缀识别；不引入第三方依赖。

旧：

```python
@dataclass(frozen=True, slots=True)
class ParsedTranscript:
    ...
    ended_with_assistant: bool
    fatal_error_unrecovered: bool
    parent_agent_id: str | None = None
```

新：

```python
@dataclass(frozen=True, slots=True)
class ParsedTranscript:
    ...
    execution_outcome: ExecutionOutcome = "legacy_unknown"
    end_reason: EndReason | None = None
    agent_definition_hash: str | None = None
    definition_source: DefinitionSource | None = None
    evidence: tuple[TraceEvidence, ...] = ()
```

为什么这样写：新增字段都有默认值，旧构造点与旧测试无需改；`execution_outcome` 是独立轴，不覆盖 `status`。

旧：

```python
def mark_assistant_record(self, *, fatal_error_unrecovered: bool) -> None:
    self.ended_with_assistant = True
    self.fatal_error_unrecovered = fatal_error_unrecovered
```

新：

```python
def mark_assistant_record(
    self,
    *,
    fatal_error_unrecovered: bool,
    stop_reason: str | None = None,
) -> None:
    self.ended_with_assistant = True
    self.fatal_error_unrecovered = fatal_error_unrecovered
    self.last_stop_reason = stop_reason
```

实现思路：把显式停止原因带进上下文，完成度推导集中到 `_execution_state`；模板方法保持单一出口。

检视发现：`normalize_definition_body` 会裁掉任何以 `Notes` 开头的行；如果某个 Agent 定义正文本身包含同名小节，会被误裁。当前按设计“Notes 是通用后缀”接受，M9-04 若发现真实定义冲突再收紧。

### 9.2 `apps/api/app/service/acquisition/parsers/claude_code.py`（M）

职责：Claude record 解释、证据 hook、模型分离。

关键依赖：`_claude_meta` 提供键集合与脱敏，`base` 提供 hash 与上下文。

旧：

```python
def extract_evidence(self, payload: TracePayload) -> tuple[TraceEvidence, ...]:
    """Claude evidence hooks land in M9-02/M9-04; none are emitted yet."""
    return ()
```

新：

```python
def extract_evidence(self, payload: TracePayload) -> tuple[TraceEvidence, ...]:
    """Return the M9 evidence identities discovered in one payload."""
    return self.normalize(payload).evidence
```

为什么这样写：evidence 的产生与 normalize 共用同一条 record 消费路径，避免两套字段解释漂移；代价是如果调用方同时 normalize + extract_evidence 会重复解析一次，M9-04 接入时应直接用 `ParsedTranscript.evidence`。

检视发现：Bash 只在结果带 `file` 时记录，已作为限制写入 Note；这不是遗漏，是拒绝猜测。

### 9.3 `apps/api/app/service/acquisition/parsers/_claude_meta.py`（A）

职责：Claude 元数据已知键集合与未知标量脱敏。

旧：无此文件；封闭 schema 在 `local_sessions.py`。

新：

```python
def sanitize_unknown_metadata(meta: Mapping[str, object]) -> dict[str, object]:
    result: dict[str, object] = {}
    for key in unknown_metadata_fields(meta):
        if is_sensitive_key(key):
            continue
        value = _scalar(meta[key])
        if value is _DROP:
            continue
        result[key] = value
```

实现思路：先按已知集合筛未知键，再做敏感键过滤与标量归一；不递归、不保留嵌套，保证落库面有界。

检视发现：`_Drop` 哨兵类只用于区分“丢弃”与合法的 `None`；`_scalar` 对 `None` 直接丢弃。可读性一般，但没有行为歧义。

model_config = ConfigDict(alias_generator=to_camel, extra="allow", populate_by_name=True)
