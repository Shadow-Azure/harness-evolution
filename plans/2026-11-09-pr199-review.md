# PR #199 检视：阿里云 ECS 部署流水线（#198）

分支 `deploy/m6-22-aliyun` → `main`，8 个提交，纯新增（无既有文件行为变更，除预算清单与文档地图各一行登记）。

## 一页速览

- **解决什么**：服务只有本地入口与质量门禁，没有交付通道；把 push main 之后的发布变成零人工动作，落到阿里云单机。
- **怎么解决**：CI 全绿 → `workflow_run` 触发 Deploy → 前端构建产物 + API 源码 rsync 到 ECS release 目录 → 服务器脚本做迁移、软链原子切换、systemd 重启、60 秒探活 → 失败回滚上一 release。
- **代价**：回滚不自动降级数据库（Alembic downgrade 不在自动流程）；单机无水平扩展；HTTPS 未做（无域名）；deploy 用户私钥即生产权限。

## 架构导览

目标形态即 `plans/fullstack-design/01-architecture.md` §6 的"现在"列：公网只开 nginx（80，后续 443），静态文件从 `/opt/harness/current/web` 直出，`/api` 反代 `127.0.0.1:8787` 的 uvicorn（systemd 常驻，`harness` 系统用户），MySQL 8 同机自建。流水线与服务器职责分离：CI 只管构建与上传，服务器侧 `release.sh` 拥有全部状态变更（迁移/切换/重启/回滚），GitHub 侧只有三样权限：SSH 私钥、两个 Secret、一个端口 Variable。

## 数据流走查

1. push main → 既有 CI（`ci-ok` 聚合）→ 成功后 `workflow_run` 触发 Deploy（分支过滤 main；`workflow_dispatch` 可手动）。
2. Deploy job（`environment: production` 保护）：checkout CI 同一 commit → `pnpm build` → ssh-keyscan 收录主机指纹 → rsync 三路：web dist → `releases/<sha>/web`、api 源码 → `releases/<sha>/api`、deploy 模板 → `shared/config`。
3. 远程 `release.sh <release>`：source `.env` → `pip install <release>/api`（依赖进共享 venv，代码经 `python -m app` 的 cwd 优先从 release 目录解析）→ 复制 `alembic.ini` 副本并注入 `HE_DB_URL` 执行 `upgrade head` → `ln -sfn` + `mv -T` 原子切 current → `sudo systemctl restart harness-api`（sudoers 仅限 restart/start）→ curl `/api/health` 最长 60 秒。
4. 探活失败：软链退回切换前目标（首次部署无前序则仅重启）→ 再重启 → exit 1 让 job 红。
5. 清理：`releases` 只留最近 5 版。

## 讨论点

1. **位置**：`deploy/release.sh:31`（`pip install --quiet "$API_DIR"`）
   **现象**：全部 release 共用一个 venv，依赖按最新 release 安装。
   **问题**：回滚到旧 release 时依赖可能比旧代码声明的新。
   **预判**：`pyproject.toml` 依赖全是宽范围（`>=x,<y`），近期无破坏性升级，风险低；真出问题改 per-release venv，代价是每次发布多 1–2 分钟。结论留维护者。
2. **位置**：`.github/workflows/deploy.yml` SSH 配置段（`ssh-keyscan`）
   **现象**：每次部署 TOFU 式收录主机指纹，未固定。
   **问题**：理论上存在中间人替换指纹的窗口。
   **预判**：单机演示可接受；绑域名后把 `ssh-keyscan -H <host>` 输出固定成 repo Variable 更稳。结论留维护者。
3. **位置**：`deploy/bootstrap-server.sh` nginx 安装段
   **现象**：nginx 站点只在 bootstrap 安装一次，后续模板变更不自动生效。
   **问题**：改 `deploy/nginx-harness.conf` 后需要手工 root SSH 同步。
   **预判**：频率低、变更需谨慎，手工可接受；若要自动化需给 deploy 用户加 `cp` 到 sites-available 的 sudo 白名单，扩大攻击面。结论留维护者。
