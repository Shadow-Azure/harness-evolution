## §1 一页速览

**一句话**：把总览页从“只看 bad case”扩展成“bad case / 进化对象”双视角，并让对象视角的统计、趋势、分布、侧栏、单对象卡与潜在 case 列表共享同一个时间窗，同时各自保留需要的独立筛选。

**一个比喻**：总览页像一间有两块白板的作战室。左边白板按“问题来源”贴 bad case，右边白板按“进化对象”贴潜在 case。两块白板共用同一扇窗（时间范围与粒度），但右边白板旁边另有一张可单独调焦的放大镜（单对象卡），调焦不改变白板的窗。

## §2 架构导览

### 2.1 入口：双 Tab 与查询开关

`Index.vue:359` 用 `v-if="state.tab === 'cases'"` 渲染原有 case 视角，`v-else` 渲染 `TargetsOverview`。`casesTabActive`（`Index.vue:63`）被传给 trend/sources/cases 的 composable，切到对象视角后这些请求被禁用，避免继续算坏 case 聚合；summary 始终请求，因为它同时提供共享窗口和来源选项。`setTab`（`Index.vue:162`）只改 `tab` 并重置 `page`，所以切 Tab 不重置时间窗/粒度。

### 2.2 URL 是唯一状态源

`OverviewUrlState` 扩成一份联合状态：case 视角继续用 `objects/type/page`，对象视角新增 `targets/states/tpage`、列表 `ctarget/csource/cstate/cfrom/cto/page` 与详情 `dtarget/dversions/dfrom/dto/dlimit`。`parseOverviewQuery`（`overviewUrl.ts:187`）逐项校验，`overviewQuery`（`overviewUrl.ts:257`）只输出非默认键；case 视角的规范形保持 `tab/range/grain` 不变，避免旧链接和既有测试被无意改写。`overviewSharedWindow`（`:415`）、`overviewCaseWindow`（`:431`）、`overviewDetailWindow`（`:447`）区分“共享窗 / 列表独立窗 / 卡片独立窗”，缺省时回落到共享窗。

### 2.3 数据层：一个完整对象集合 + 三个独立读

`listAllOverviewTargets`（`api/overview.ts:266`）先取 `pageSize=50`，再按 `total` 补页；页面在客户端按 5 条切片。原因是对象多选、侧栏和详情选择器都需要完整 evolvable 排序，而列表端点单页最多 50。趋势（`:300`）、潜在 case 列表（`:322`）和详情（`:345`）各自独立请求，保留 m11-03 的四端点语义；query key 全部以 `["ws", wid, "overview", ...]` 开头，切空间不会复用旧空间缓存。

### 2.4 趋势：服务端给完整桶，客户端管显示

`TargetTrendChart` 不把 `states` 传给服务端，而是保留完整三态桶，再按所选状态求和（`TargetTrendChart.vue:104`）。这样 chip 上的数字始终是当前对象与时间窗内该状态的总数；若交给服务端过滤，点掉“未分析”后该 chip 会变成 0，无法再点回来。列表的 `cstate` 仍是服务端筛选，二者独立。

### 2.5 详情卡：独立窗口与版本作用域

`TargetDetailCard` 的版本菜单来自 `detail.target.versions`，无显式选择时用 `dlimit` 映射 `5|10|20|0(全部)`；日期缺省显示共享窗，设置后显示“跟随总览”（`TargetDetailCard.vue:87`–`160`）。父容器把 `dversions/dfrom/dto/dlimit` 单独组成 detail query key，因此卡片变化不会带动趋势和列表。

### 2.6 CRUD 与失败态

对象维护复用 `TargetFormDialog` 与 `useEvolutionTargets`（`TargetsOverview.vue:292`–`375`），权限用空间角色 `canManageWorkspace`。删除后立即从 URL 清理 `targets/ctarget/dtarget`，再失效 overview 前缀，避免详情持续 404。自检后新增加载失败横幅（`ov-target-load-error`），区分“没有对象”和“对象聚合失败”。

## §3 数据流走查：打开 `?tab=targets`

1. 入口解析 URL：`parseOverviewQuery` 合法化 `tab/range/grain/targets/states/...`，Index 把 `sharedFilters` 传给目标列表，把 `trendFilters` 传给趋势，把 `caseFilters` 传给潜在列表。
2. 页面并行请求：`/overview/targets?pageSize=50`（必要时补页）、`/overview/targets/trend`、`/overview/targets/cases`、`/overview/targets/{targetId}/detail`，外加始终存在的 `/overview/summary`。
3. 统计条取列表响应的 `summary`；侧栏取补齐后的 `items`，按 5 条切片；趋势画三态堆叠；两块分布分别从 `items.sessions` 与 `trend.buckets[].byTarget` 推导。
4. 用户点趋势 chip：只改 URL `states`，趋势在客户端重算，列表请求不变。
5. 用户点时间桶：写 `cfrom/cto`，只重置潜在列表的窗口，共享 `range` 与趋势不动。
6. 用户改单对象卡的版本/日期：只写 `dversions/dfrom/dto`，只有 detail query 重新请求。
7. 用户新增/编辑/移除对象：复用 target 表单；成功后失效 overview 前缀；移除时同时修正 URL，避免悬空 id。
8. 页面内容高于视口时：`.overview-page` 自身滚动（`Index.vue:455`），详情卡和列表可达；E2E 用滚动断言守住。

## §6 讨论点

### 6.1 数据契约缺口：描述字段与 defaultRef

- **位置**：`apps/web/src/pages/overview/components/PotentialCaseTable.vue:129`、`TargetSideList.vue`（版本显示 `versions[0]`）
- **现象**：原型列表末列是“问题现象/描述”，侧栏显示配置的 defaultRef；API 的 `TargetCaseItem` 没有描述字段，`TargetOverviewItem` 也不单独返回 `defaultRef`。
- **问题**：页面只能在“最后一列用归因分类”和“侧栏显示最高已观测版本”之间做近似；这会让读者以为视觉实现漏了，而不是数据边界。
- **预判**：当前保持诚实展示（分类/最高版本），在 PR 描述与 Agent Note 明确标注；若后续要完全对齐原型，应由数据契约扩展（m11-03 或后续 issue）补齐描述与 defaultRef，而不是前端伪造。
- **结论**：待产品/维护者拍板是否需要在本里程碑补契约。

### 6.2 完整对象集合的补页成本

- **位置**：`apps/web/src/api/overview.ts:266`
- **现象**：为让对象多选、侧栏与详情共用一套 evolvable 排序，前端一次拉全量（每页 50，按 total 补页），再由客户端切 5 条。
- **问题**：对象数超过 50 时会多发请求；超大空间的首屏成本随对象数增长。
- **预判**：当前空间对象是人工配置的小集合，补页通常 0–1 次；保留“一个排序源”比提前做服务端分页 + 选项端点更简单。若未来单空间对象数上百，应拆成 options 端点或让侧栏回到服务端分页。
- **结论**：待维护者判断是否需要提前设阈值告警。

### 6.3 趋势 chip 的客户端过滤

- **位置**：`TargetTrendChart.vue:104`、`TargetsOverview.vue:211`
- **现象**：`states` 不传给趋势端点，chip 在客户端切换；`states` 空表示全选，全选时回写空以保持 URL canonical。
- **问题**：趋势柱高之和与潜在列表总数不一致（列表还有来源/状态/独立时间筛选），可能被误读为 bug。
- **预判**：这是保留 chip 总数可用性的必要取舍；页面已用“柱高为所选信息之和”的文案说明。若更看重“两个数字恒等”，可以改成服务端过滤，但会牺牲 chip 的可逆性。
- **结论**：待维护者确认文案是否足够。

### 6.4 概览页自身滚动的影响面

- **位置**：`Index.vue:455`
- **现象**：`.overview-page` 增加 `height:100%; overflow-y:auto`，因为工作空间壳的 `main` 固定高度且 `overflow:hidden`。
- **问题**：这是页面级布局行为，会影响 bad case 视角与所有总览筛选；移动端已回退为文档流。
- **预判**：这是最小且局部的修复；更彻底的做法是让工作空间壳对所有页面统一可滚动，但那会影响 Session、错误详情等已有页面，超出本 issue。E2E 已加滚动断言。
- **结论**：待维护者确认是否接受局部修复。

### 6.5 未加入原型页头的“启动自进化”

- **位置**：`Index.vue:316` 页头
- **现象**：原型页头有“启动自进化”主按钮，本 PR 只加了“+ 新增进化对象”。
- **问题**：严格视觉对照会认为少一个按钮。
- **预判**：启动向导需要 target/version 预填与运行创建，属于自进化流程；本 issue 的交付边界是对象总览，直接在页头放一个不带预填的入口可能误导。若维护者要求，可后续单独接目标快照预填。
- **结论**：待维护者决定是否需要补。

## §9 文件级代码分析

### 9.1 `overviewUrl.ts`（M，+217/-?）

职责：把 URL 变成唯一状态源。变更前只理解 `tab: "cases"`，`tab=targets` 被标记为“请求了 M11 但降级”；变更后 `tab` 是二值联合，目标视角的 12 个键全部进入解析/序列化。

关键依赖：无第三方；纯函数，便于单测。就像收银台的价签：所有筛选先在这里换算成统一格式，页面和 API 只认这一份价签。

变更块：

```ts
// 旧：类型里 tab 只有 cases，targetsRequested 只是提示
export type OverviewUrlState = { tab: "cases"; ... };

// 新：tab 二值 + 目标视角键
export type OverviewUrlState = {
  tab: OverviewTab;
  ...
  targets: string[];
  states: TargetState[];
  targetPage: number;
  caseTarget: string;
  ...
};
```

为什么这么写：页面切换、刷新恢复、浏览器后退都依赖同一份状态；如果目标筛选放在组件本地，刷新会丢。`parseOverviewQuery` 的默认值回退保证非法 URL 不会让页面报错，`overviewQuery` 只输出非默认键保证链接短且稳定。

检视发现：无新的正确性问题；`states` 空表示全选，与 API 语义一致，已在注记中记录。

### 9.2 `api/overview.ts`（M）

职责：把 URL 状态编码成四个目标端点。变更前只有 summary/trend/sources/cases；变更后新增 target 列表（含补页）、趋势、case 列表、详情。
