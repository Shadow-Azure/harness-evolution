## §1 一页速览

一句话：这个 PR 给 Vue 壳装上“内存门禁卡 + cookie 续卡器”，用户从登录页进入业务页，访问令牌过期时自动换卡一次，首登用户则被门卫领到改密页。

生活化比喻：Pinia 是前台的临时卡盒，刷新页面就会清空；httpOnly refresh cookie 是锁在浏览器保险盒里的续卡凭据，JavaScript 看不到。`http.ts` 是唯一门卫，发现 401 时排队换一次卡，再把原请求原样递回去。

| 交付块 | 结论 |
|---|---|
| 登录、退出、当前用户与强制改密 | 主链路完整，页面和守卫均有真实测试 |
| 401 单飞刷新与请求重放 | 并发单飞、body/method 保留、公开 auth 请求不递归刷新已覆盖 |
| 启动、安全回跳与状态生命周期 | 启动顺序与常见开放重定向有测试；发现 URL 规范化旁路 |
| Element Plus 按需加载 | 自动导入生效，vendor JS 58.47 kB，未退化为整包 915 kB |
| 测试与 CI | 修复后本地 84 passed / 1 skipped；初始 CI 三条 lane 全绿 |

## §2 架构导览

### 2.1 启动顺序

`apps/web/src/bootstrap.ts:27-36` 的顺序是：

```text
Pinia → Vue Query → 注册 auth runtime → Router
  → await tryRefresh()
  → await router.isReady()
  → mount
```

这样导航守卫和显式恢复共享 `apps/web/src/stores/auth.ts:78-91` 的 `bootstrapPromise`，避免已登录用户在首屏先闪到登录页。测试 `apps/web/src/bootstrap.test.ts:10-48` 直接断言后三个动作的顺序。

### 2.2 传输层与身份装配

`apps/web/src/api/http.ts:27-79` 保存四类注入缝：当前 token、refresh、会话过期、强制改密。

`apps/web/src/auth/runtime.ts:19-35` 把 token 读取接到 `stores/auth`，并把 401/403 的恢复导航接到 router。传输层因此不 import Router、Store 或 Pinia，避免循环依赖。

请求首次执行位于 `http.ts:124-152`。并发 401 会在 `http.ts:114-122` 共享同一个 `refreshPromise`；成功后用最新 token 递归执行一次，并保留原 `RequestInit`。`http.ts:88-98` 每次重新构造 Headers，调用方自定义头不会被丢掉。

### 2.3 身份状态机

`apps/web/src/stores/auth.ts:21-26` 只把 access token 和 public user 放在内存。主要转移是：

| 输入 | 状态变化 |
|---|---|
| 登录成功 | 写 token/user，标记已 bootstrapped |
| 启动 refresh 成功 | 写 token，再请求 `/me` 写 user |
| refresh 失败 | 清 token/user，仍标记已 bootstrapped |
| 改密成功 | change-password → refresh → me |
| 登出 | 调后端，无论成败都清内存和 Query cache |

### 2.4 路由守卫

`apps/web/src/router/index.ts:38-61` 的优先级是：

```text
未 bootstrapped → await tryRefresh
未登录且不是 /login → /login?redirect=当前路径
已登录且是 /login → 安全 redirect 或 /sessions
mustChangePassword 且不是 /login|/change-password
  → /change-password?redirect=当前路径
```

`safeRedirect` 在 `apps/web/src/router/safeRedirect.ts:8-21` 要求字符串以 `/` 开头，拒绝 `//`、反斜杠和跨 origin 的 URL。正常 deep link、query 和 hash 可以保留。

### 2.5 页面组件

`apps/web/src/App.vue:10-17,44-60` 根据 `meta.authLayout` 隐藏 TopNav 和 health 查询。登录页和改密页因此是独立居中布局。

`LoginForm.vue:8-48` 负责本地空值校验、登录 mutation 和 inline 文案；AUTH_INVALID 映射成“用户名或密码错误”。`ChangePasswordCard.vue:8-57` 负责三次输入、mismatch、新旧密码相同、最小长度和提交。两者都使用 `role="alert"`，没有原生 alert。

`TopNav.vue:4-13,36-52` 从 Pinia 读取当前用户，退出 mutation 结束时导航到 `/login`。

### 2.6 自动导入与 bundle

`apps/web/vite.config.ts:9-37` 将 `ElButton`、`ElInput` 映射到 Element Plus 的组件目录，再交给 auto-import 与 component resolver。构建产物为独立 `vendor-element-plus` 58.47 kB JS / 38.87 kB CSS，未拉入整库 915 kB。

Element Plus、unplugin-auto-import、unplugin-vue-components 都来自其官方 GitHub 仓库并采用 MIT 许可证；lockfile 已固定解析版本。

## §3 数据流走查

### 场景 A：首次进入 `/sessions`

1. `main.ts` 创建 Pinia、QueryClient、Router 并调用 `bootstrapApp`。
2. `bootstrap.ts:34` 在 router ready 前执行 `tryRefresh()`。
3. `stores/auth.ts:94` 先调用 `/api/auth/refresh`；有效 cookie 下写 access token。
4. `stores/auth.ts:100` 调 `/api/auth/me` 恢复 public user。
5. 守卫看到用户正常，放行 `/sessions`；TopNav 显示 displayName。

### 场景 B：业务请求遇到过期 access token

1. `http.ts:132` 带旧 Bearer 发请求。
2. `http.ts:138-141` 命中 401，多个并发请求共享一个 refresh。
3. 新 token 进入 Header 后重放一次。
4. refresh 失败时，`auth/runtime.ts:23-28` 清 store 并回 `/login?redirect=原路径`。

已实测的正常路径：两个并发 401 产生一次 refresh，两个原请求均以原 method/body 重放成功。

### 场景 C：首登强制改密

1. 登录响应中的 `user.mustChangePassword=true` 写入 store。
2. 登录后的 `/sessions` 导航被 `router/index.ts:52-60` 改到改密页，并保存原目标。
3. 提交后 `stores/auth.ts:125-130` 依次执行 change-password、refresh、me。
4. 页面在成功后读取安全 redirect 并导航。

异常路径待讨论：change-password 返回 204 后，refresh 若 401，当前页面会停在 `/change-password`。

### 场景 D：令牌过期的当前用户请求

1. `useCurrentUser().refetch()` 调用 `stores/auth.ts:114-118`。
2. `/api/auth/me` 与业务 API 一样需要 Bearer，但 `http.ts:137` 把所有 `/api/auth/` 都当成无需刷新的 auth 请求。
3. 过期 token 直接抛 AUTH_EXPIRED，既没有 refresh，也没有触发过期回调。

### 场景 E：从 `/login?redirect=...` 回跳

1. 已登录用户访问 `/login` 时，守卫读取 `redirect`。
2. `safeRedirect` 解析 URL 并返回 app-relative 结果。
3. 常见 `https://`、`//host`、反斜杠输入都回退 `/sessions`。
4. 编码点段输入可在 URL 规范化后产生新的 `//...`，绕过入口检查。

## §6 讨论点

### D1 私有 `/api/auth/*` 请求不会触发 refresh

**位置**：`apps/web/src/api/http.ts:137-143`

**现象**：所有以 `/api/auth/` 开头的请求都被视为 auth 请求。实测 access token 过期后请求 `/api/auth/me`，fetch 收到 401 AUTH_EXPIRED，refresh 调用次数仍为 0，promise 直接拒绝。临时复现测试预期 2 次 fetch、1 次 refresh，实际只执行 1 次 fetch。

**问题**：`/api/auth/me` 是受 Bearer 保护的私有端点；`POST /api/auth/change-password` 和 `logout` 也需登录。只有 login 与 refresh 是公开端点（见 `plans/fullstack-design/05-api-design.md:525`）。当前分支判断把“路径以 auth 开头”误当成“公开端点”，导致 refresh 恢复能力在私有 auth API 上缺失。

**预判**：这是身份状态机缺陷。应按错误码而不是路径前缀决定是否刷新，或至少仅把 login/refresh 排除；同时保留 change-password 的 AUTH_INVALID 为表单错误，不能因 401 就把它误判为过期。

**结论**：已修复（2026-10-25）。login 与 refresh 精确识别为公开端点；受保护 auth 端点的 401 按 AUTH_INVALID/其他错误区分，非凭据错误只 refresh 并重放一次；刷新成功但重放仍 401 时也清态回登录。AUTH_INVALID 保留表单语义，既不 refresh，也不触发会话过期跳转。HTTP 回归测试覆盖 `/api/auth/me` 恢复、公开端点不递归、凭据错误不刷新/不跳转和重放终态。

### D2 改密后 refresh 失败会停留在已失效的改密页

**位置**：`apps/web/src/stores/auth.ts:125-130`、`apps/web/src/composables/useAuth.ts:86-102`

**现象**：实测 change-password 返回 204、refresh 返回 401 后，store 清空 token/user，mutation 抛错；当前路由仍是 `/change-password`，没有进入 `/login`。设计约定 refresh 失败时清态并跳登录（`plans/fullstack-design/08-frontend-implementation.md:88`）。

**问题**：401 自动恢复只覆盖由 `http.ts` 的 `refreshOnce()` 发起的 refresh。`changePassword()` 直接调用 store 的 `refresh()`，失败时只返回 false，没有复用 `authExpiredHandler` 的导航和 cache 清理路径。用户会被留在无有效会话的受保护页面。

**预判**：这是用户可见的状态机缺口。应让显式 refresh 与 401 refresh 共用失败恢复入口；若选择让表单显示“会话已过期”，至少立即导航登录并保留改密前目标。

**结论**：已修复（2026-10-25）。改密 mutation 在 refresh 失败、store 已清态时清空 query cache，并回到带安全 `redirect` 的登录页；回归测试覆盖 `/change-password?redirect=/sessions` 的失败恢复。

### D3 安全回跳可被 URL 规范化重新变成多斜杠路径

**位置**：`apps/web/src/router/safeRedirect.ts:8-21`

**现象**：`safeRedirect("/%2e%2e//evil.example")` 返回 `//evil.example`。在已登录路由复现中，`/login?redirect=/%2e%2e//evil.example` 最终使 `router.currentRoute.fullPath === "//evil.example"`，Vue Router 同时警告“resolved location cannot start with multiple slashes”。

**问题**：函数在规范化前只检查原始输入，规范化后的 `url.pathname` 未再次验证。返回值违背“只接受 app-relative 路径”的函数契约；在 Web history 下多斜杠 URL 还可能被浏览器或代理按不同语义解释，并至少会把用户送进异常 catch-all 路径。

**预判**：这是安全边界缺陷，但当前实测未证明跨 origin 自动跳转。最小修复是检查最终 pathname 仍以单个 `/` 开头，并把编码点段加入回归测试。

**结论**：已修复（2026-10-25）。规范化后的 decoded pathname 会再次重建 URL 并检查单斜杠、反斜杠和控制字符，最多处理四层编码，超限直接回退；编码点段、编码斜杠、反斜杠和双重编码均有测试。

### D4 `useCurrentUser` 的失败不进入统一请求状态

**位置**：`apps/web/src/composables/useAuth.ts:71-79`

**现象**：实测 `/api/auth/me` 返回 500 时，`refetch()` 正确 reject，但 `isError.value` 仍为 false，`error.value` 仍为 null。现有测试只检查五个键存在，没有检查失败语义。

**问题**：设计要求所有 composable 返回可消费的 `{data,isLoading,isError,error,refetch}`（`plans/fullstack-design/08-frontend-implementation.md:187`）。当前实现满足形状而不满足含义，未来 TopNav 或用户区调用 refetch 时无法渲染错误或重试态。

**预判**：当前没有业务页面主动调用该 refetch，因此无直接事故；但这是会复制的状态接口模板。建议用 Vue Query 包装 `/me`，或在 composable 内显式维护 pending/error refs。

**结论**：已修复（2026-10-25）。current-user composable 显式维护 pending/error refs，refetch 失败写入统一错误状态，重试成功后清空；回归测试验证完整 `{data,isLoading,isError,error,refetch}` 语义而不只是键集合。

### D5 TopNav hover 选择器与模板 class 不一致

**位置**：`apps/web/src/components/layout/TopNav.vue:36-52,156-159`

**现象**：模板根节点 class 是 `user-menu`，hover 样式却写 `.user-area button:hover`，选择器永远不命中。

**问题**：退出按钮缺少设计的 hover 反馈；功能和键盘可达性不受影响。

**预判**：无需阻塞；若本轮顺带修 D1–D4，可把选择器改为 `.user-menu button:hover`。

**结论**：已修复（2026-10-25）。hover selector 对齐实际 `.user-popover` 容器，并用 SFC source 断言防止选择器再次漂移。

## §9 文件级代码分析

### `apps/web/src/api/http.ts`（M）

职责：唯一的 JSON 传输层，集中 Bearer、错误解码、401 恢复和取消传递。

变更对照：旧实现只有 fetch、`response.ok` 与 JSON decode；新实现增加可注入身份回调、单飞 refresh、一次重放、201/204、统一 ErrorResponse 以及 403 改密导航。

实现思路：门卫先发原请求；401 时只开一个换卡窗口，成功就带新卡重放，失败就交给 runtime 清态回登录。`headersFor` 在每次重放时重建 Headers，避免旧 token 和调用方 header 被覆盖。

检视发现：D1 已修复。公开 login/refresh 不递归，认证凭据错误保持表单语义，受保护请求的其它 401 只共享一次 refresh；刷新成功但重放仍 401 时进入清态恢复。

### `apps/web/src/api/auth.ts`（A）

职责：五个身份 HTTP 操作的类型化薄封装。

变更核心：login/refresh/logout 显式 `credentials: "include"`，改密和 me 依靠同源默认凭据。所有函数只组请求，不写 store 或 router。

检视发现：无独立问题；D1 的路径分类发生在公共 transport。

### `apps/web/src/stores/auth.ts`（A）

职责：内存身份状态与 session 状态转移。

变更核心：`bootstrapPromise` 合并启动恢复；`refresh` 失败清态；`changePassword` 严格三步；logout 在 finally 中清态与 cache。

检视发现：D2 已修复。显式 refresh 失败后的 mutation 恢复会清 query cache 并回到带原安全目标登录页；登录与启动行为保持原测试。

### `apps/web/src/auth/runtime.ts`（A）

职责：组合根适配器，把传输层端口接到 Pinia 与 Router。

变更核心：注册 token provider、refresh、expired、forced-change 四个回调；导航参数再次经过 `safeRedirect`。

检视发现：D3 已由共享 `safeRedirect` 修复，因此 expired/forced-change 回跳也获得同一防护。

### `apps/web/src/composables/useAuth.ts`（A）

职责：页面使用的四个 auth composable。

变更核心：login/logout/change-password 使用 Vue Query mutation；currentUser 从 store computed；统一暴露五个状态键。

检视发现：D2、D4 已修复。改密失败恢复与 currentUser pending/error 状态都有真实失败回归。

### `apps/web/src/bootstrap.ts`（A）

职责：可测试的浏览器启动编排。

变更核心：注入 app/pinia/query/router/restore，先恢复认证再等待路由 ready 后挂载。

检视发现：无。测试直接锁定 `tryRefresh → isReady → mount`，这是本 PR 最关键的防闪屏顺序。

### `apps/web/src/main.ts`（M）

职责：真实浏览器组合根。

变更核心：从直接 mount 改成调用 bootstrap，并加载全局及 Element Plus token overrides。

检视发现：无。

### `apps/web/src/router/index.ts`（M）

职责：路由表和认证守卫。

变更核心：新增 login/change-password/404；守卫先等恢复，再处理未登录、已登录 login、强制改密三种改道。

检视发现：守卫分支本身清晰；D1 与 D3 已在传输/净化层修复，守卫继续复用统一边界。

### `apps/web/src/router/safeRedirect.ts`（A）

职责：把用户 query 收窄成应用内路径。

变更核心：拒绝非 `/` 开头、双斜杠、反斜杠及不同 origin，再返回 pathname/query/hash。

检视发现：D3 已修复，编码规范化后仍只返回单斜杠应用内路径。

### `apps/web/src/pages/login/Index.vue` 与 `LoginForm.vue`（A）

职责：登录布局和真实表单。

变更核心：页面只排版；表单负责空值、loading、AUTH_INVALID/限流文案与登录成功回跳。

检视发现：无独立问题。测试覆盖空提交、错误凭证、成功回跳；真实 Chrome 视觉仍需后续冒烟。

### `apps/web/src/pages/login/ChangePassword.vue` 与 `ChangePasswordCard.vue`（A）

职责：首登强制改密的布局和表单状态机。

变更核心：页面只排版；卡片负责 mismatch、同密码、最小长度和提交。

检视发现：D2 已修复；正常三步顺序与 refresh 失败回登录均有测试。

### `apps/web/src/components/layout/TopNav.vue`（M）

职责：业务页全局导航与当前用户区。

变更核心：读取 currentUser；logout mutation 后清态和 cache；只有存在 user 时显示 details。

检视发现：D5 已修复。退出失败仍是 best-effort，后端失败仍清本地态，符合设计。

### `apps/web/src/App.vue`（M）

职责：核心壳、health pill 与 auth layout 切换。

变更核心：authLayout 时隐藏 TopNav、health query 和 pill；main 宽度改为全屏。

检视发现：无。auth route 不请求 health，避免公开登录页混入业务状态。

### `apps/web/src/pages/NotFound.vue`（A）

职责：未匹配路由的安全兜底。

变更核心：显示 404 与回 sessions 链接；由于 catch-all 本身在守卫后，未登录用户先回登录。

检视发现：无独立问题；D3 的多斜杠路径会落在这个兜底，但根因在净化函数。

### `apps/web/vite.config.ts`（M）

职责：开发代理、测试环境、生产 chunk 和 Element Plus 解析。

变更核心：加入两个 unplugin；自定义具体组件目录为 input/button；将 Element Plus 单独成 vendor。

检视发现：构建实测输出 58.47 kB EP JS，未把整库同步打包。

### `apps/web/package.json`、`pnpm-lock.yaml`、自动声明（M/A）

职责：固定 Element Plus 与自动导入工具链。

变更核心：Element Plus 2.14.7；unplugin-auto-import 21.1.0；unplugin-vue-components 32.1.0；生成两个 d.ts。

检视发现：三者均 MIT、维护仓库明确；lockfile 完整，未引入原生运行时依赖。

### `packages/contracts/src/index.ts`（M）

职责：向 Web 暴露从 OpenAPI 生成的共享类型。

变更核心：新增 LoginRequest/Response、RefreshResponse、ChangePasswordRequest、PublicUser。

检视发现：`contract:check` 通过；无手改生成 schema。

### `apps/web/src/styles/tokens.css` 与 `element-overrides.css`（M/A）

职责：业务 token 与 Element Plus 表单控件视觉桥接。

变更核心：补 text-secondary、brand-accent、border-strong、shadow-card；把 Element Plus 主色、填充、文本映射回业务 token。

检视发现：web-style 门禁通过；D5 是组件内 selector 拼写，不涉及颜色源。

### Web 测试（A/M）

职责：证明身份状态机与页面行为，而不是断言 mock 调用。

变更核心：HTTP 使用真实 fetch contract；router/store/composable/component 使用 MSW 驱动；bootstrap 用可观测调用顺序；TopNav 连真实 QueryClient 验证 cache 清理。

检视发现：新增测试质量整体良好，但没有覆盖 D1–D4 的上述反例。D1 的测试标题“never refreshes public auth requests”只传 login，暴露了“公开 auth”与“所有 auth 路径”的语义混淆。

### 流程与文档（M/A）

职责：记录 in-progress 状态、设计权威、验证命令、身份恢复决策及当前架构。

变更核心：issue 扩到 plans/reports/lockfile；Agent Note 记录内存态、注入、单飞、自动导入等取舍；architecture 记录启动与恢复现状。

检视发现：i18n、Agent Note、预算、链接与导出文档门禁均通过。D1–D4 修复后 owning Note 的 Consequences 应补私有 auth endpoint 与 explicit refresh failure 的恢复语义。
