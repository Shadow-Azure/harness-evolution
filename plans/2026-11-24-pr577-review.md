## §3 数据流走查

1. 浏览器打开 `.../runs/run-v2-completed?step=clusters`，`useEvolutionRunStep` 请求 `steps/clusters`。
2. 路由进入 `EvolutionStageService.step()`；run 与 cluster 快照先按 workspace 过滤（`stages.py:497-504`）。
3. `_facts()` 读候选与归因；候选存在时 `case_ids` 取 `candidates[].bad_case_id`，否则回退 legacy probe 行（`stages.py:536-546`）。
4. 一次 `titles_by_ids(case_ids)` 返回 `{case-id: 短标题}`；未知 id 不在字典里。
5. `build_step_payload(..., "clusters")` 调 `_clusters()` → `_cluster_item()` → `_cluster_cases()`；每个 case 的 `title` 来自字典，缺失时用 `bad_case_id`。
6. DTO 序列化为 `StepClusterCase`；前端表格渲染短标题，`object_name`/类型/触发点/上报时间回到同一行可读。
7. 第 6 步 `steps/iteration` 复用同一次 facts 与同一个 `_cluster_cases()`，因此同步恢复；第 4 步 `steps/attribution` 走 `_v2_attribution_rows()`/`_legacy_attribution_rows()`，`description` 仍是 `probe_description`。

真实响应核对（同一份数据、同一浏览器视口 1500×900，before 用 `main` 的 API，after 用本分支的 API）：

- before：`clusters[0].cases[0].title` 是 800 字归因摘要；after 是「检索索引读取越界」。
- before/after 的 `attribution.rows[0].description` 都是同一段 800 字摘要，逐字相同。

## §6 讨论点

### 6.1 簇标题的取值仍是「第一条 case」，不是设计写的「最高频 case」

- **位置：** `apps/api/app/service/evolution/stages.py:1089`（`_cluster_item` 的 `title=cases[0].title`）。
- **现象：** 05 §3.6 写「簇标题取簇内最高频 bad case 的 `title`」，实现一直取 `cases[0].title`。本次修复后卡头从「长归因摘要」变成「第一条 case 的短标题」，语义更接近设计，但「最高频」仍未兑现。
- **问题：** 如果簇内第一条 case 不是最高频的那条，卡头会显示一个代表性较弱的标题；这是既有偏差，不是本 PR 引入。
- **预判：** 不属于 #570 的交付边界（issue 明确「不改簇标题算法」）；留后续 issue 用 `caseCount`/频次重算更合适。
- **结论：** 留后续。

### 6.2 新增读取让 `bad_cases` 外部表成为 V2 步骤的硬依赖

- **位置：** `apps/api/app/service/evolution/stages.py:546`、`apps/api/app/db/crud/bad_cases.py:275`。
- **现象：** 以前 `steps/clusters` 在 V2 路径只读候选与归因，不碰 `bad_cases`；现在每次七步请求都会读一次该表。表缺失或被拒时，`@read_only_guard("bad_cases")` 会把错误翻译成 503（`app/db/external_contract.py:426`）。
- **问题：** 新失败面。理论上不可能触发：V2 的 `evolution_run_candidates.bad_case_id` 有指向 `bad_cases` 的外键，legacy 的 `ProbeQueryRepository._hit_selection()` 本来就 join `bad_cases`（`probe_query.py:121`）；任何有来源 case 的 run 都意味着表存在。只有「候选和 probe 都为空」的 run 才会走 `titles_by_ids(())`，而它在碰数据库前就返回空字典。
- **预判：** 无实害，且错误码是仓库既定口径（503 + 可诊断 code），不建议在这里吞异常降级为空标题，否则真实的外部表故障会被静默掩盖。
- **结论：** 维持现状。

### 6.3 `_facts()` 仍然两次调用 `list_cluster_probes()`

- **位置：** `apps/api/app/service/evolution/stages.py:541`、`apps/api/app/service/evolution/stages.py:547`。
- **现象：** legacy 分支为了拿 probe id 调一次，构建 `cluster_links` 又调一次；同一请求两条 SQL。这是本次改动之前就存在的形态。
- **问题：** 多一次无谓查询，且读者会误以为是本次引入。
- **预判：** 顺手合并成一次读取能省一条 SQL；本 PR 已在 facts 层新增一条查询，混入无关优化会扩大 diff，但这条就在同一函数里、只搬一行。
- **结论：** ✅ 已修（2026-11-24 检视阶段）：`links` 提前到分支前只读一次，legacy 路径从两条 SQL 降到一条，V2 路径查询数不变；`pytest tests/evolution tests/m5-10-placeholder-eval` 与 `ruff` 复跑通过。

### 6.4 空标题回退到 `bad_case_id` 会让标题列出现内部 ID

- **位置：** `apps/api/app/service/evolution/stages.py:1052`、`apps/api/app/service/evolution/stages.py:1068`。
- **现象：** `bad_cases.title` 是 NOT NULL，但异常空串（或外部表行被删）时，回退值是 `v2-case-1` 这类内部 ID。
- **问题：** 可读性差；但它是稳定、可对照排查的标识，不会把长文重新带进标题列。
- **预判：** 与 issue「仅对异常空值保留可诊断行为」一致；比回退 `probe_description` 或前端截断更符合边界。测试已覆盖该分支（空串 → `bad_case_id`）。
- **结论：** 接受。

## §9 文件级代码分析

### `apps/api/app/db/crud/bad_cases.py`（M，+21）

职责：外部问题表的只读仓储。变更形态：在 `get_case()` 前插入一个批量标题读取。

关键依赖：`@read_only_guard("bad_cases")` 是仓库统一的外部表错误边界（`app/db/external_contract.py:426`），把 `OperationalError`/`ProgrammingError`/`DBAPIError` 翻译成 503 + 稳定 code；`select(bad_cases.c.bad_case_id, bad_cases.c.title)` 只投影两列，不把 `bad_case_description` 这类长文本带进内存。

变更块：

```python
unique = tuple(dict.fromkeys(case_ids))
if not unique:
    return {}
statement = select(bad_cases.c.bad_case_id, bad_cases.c.title).where(
    bad_cases.c.bad_case_id.in_(unique),
)
async with self._database.session() as session:
    rows = (await session.execute(statement)).all()
return {str(row[0]): str(row[1]) for row in rows}
```

`dict.fromkeys` 保序去重，与 `_facts()` 的入参构造重复但便宜；`str()` 包一层是因为 SQLite/MySQL 驱动对 VARCHAR 的返回类型都可能是 `str`，这里防御性收口。实现思路：一次 IN、只读两列、缺失自然缺席。

检视发现：无。已知取舍：外部表缺失时 503（见 §6.2）。

### `apps/api/app/service/evolution/stages.py`（M，+32/-15）

职责：七步只读投影。变更形态：`_RunFacts` 增字段、服务增依赖、`_facts()` 增一次批量读、`_cluster_cases()` 两个分支换取值。

关键依赖：`EvolutionRunCandidateRecord`（V2 候选快照）与 `ProbeHitRow`（legacy 探针行）是两条数据通路的边界记录；`Mapping` 来自 `collections.abc`，只读语义。

变更块（facts）：

```python
if candidates:
    probes: Sequence[ProbeHitRow] = ()
    case_ids = tuple(dict.fromkeys(candidate.bad_case_id for candidate in candidates))
else:
    links = await self._runs.list_cluster_probes(run.id)
    probe_ids = tuple(dict.fromkeys(link.probe_id for link in links))
    probes = await self._probes.list_rows_by_ids(probe_ids) if probe_ids else ()
    case_ids = tuple(dict.fromkeys(row.bad_case_id for row in probes))
case_titles = await self._bad_cases.titles_by_ids(case_ids)
```

先按本次 run 的事实来源收口 case id，再统一读一次；两条路径的 id 集合互斥，不会重复读。

变更块（投影）：

```python
title=facts.case_titles.get(row.bad_case_id) or row.bad_case_id,          # legacy
title=facts.case_titles.get(candidate.bad_case_id) or candidate.bad_case_id,  # V2
```
