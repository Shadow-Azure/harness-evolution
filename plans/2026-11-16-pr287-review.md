## 1. 一页速览

**一句话**：给每个显式 Skill/Agent 触发点发一张“身份证 + 座位号”——身份证是 `object_revision`，座位号是 `triggered_at` 与 DFS `tree_index`；存量会话重放一次后，后续 PotentialMatcher 才能真正比较“对象版本是否出现过、触发点谁先谁后”。

**一个比喻**：原来的事件表像一张只写了“某人来过”的签到表；现在补上了“哪一版的某人”和“第几排第几座”。只看名字会认错人，只看版本号会漏掉没有版本号、只有内容指纹的对象。

**交付块**：

| 块 | 结果 |
|---|---|
| 数据 | 0017 迁移，新增 3 列 + 2 索引 |
| 解析 | tag / body digest / listing digest / unknown 四态 |
| 组装 | 父 Agent 事件拿到子定义 hash 与 revision；DFS 坐标 |
| 重放 | claude-code parser version 4，只重放该 runtime |
| 测试 | revision 17 例、迁移 2 例、重放 3 例，另更新受影响的旧断言 |

**验证基线**：`pnpm test:api` 1092 passed / 16 skipped；`pnpm test:db` 20 passed；`pnpm lint:api`、`pnpm typecheck:api`、`pnpm contract:check`、`pnpm test:gates`、`pnpm verify:docs`、`pnpm verify:flow --diff origin/main` 均通过。

## 2. 架构导览

### 2.1 解析层：先收集证据，再在 finalize 统一发身份证

`BaseTraceParser.finalize` 在构造 `ParsedTranscript` 前调用 `_resolve_event_revisions(...)`（`base.py:495`）。这一步像“收卷后统一阅卷”：事件在扫记录时只记下显式版本/时间，Skill body 注入可能晚于 Skill 调用，所以不能在 `record_tool_use` 时就定 revision。

- `_tag_revision`（`base.py:614`）：`tag:<tag>`，空值返回 `None`。
- `_skill_revision`（`base.py:621`）：`sha256(path + "\0" + normalized body hash)`，路径参与身份但不落库。
- `_agent_revision`（`base.py:629`）：`sha256(agentType + "\0" + builtin/custom + "\0" + body hash)`；内置 Agent 没有 body，但仍保留类型与 builtin 标记。
- `_resolve_event_revisions`（`base.py:642`）：按 `tool_use_id` 把注入证据绑回原事件；tag 优先，其次 body，其次 16 位 listing digest，最后 `unknown`。

Claude 子类负责“哪些原始字段算证据”：`_object_version`/`_object_tag`（`claude_code.py:65`、`:77`）只读显式元数据，`_skill_listing_digests`（`:98`）只认 `skill_listing` 的已知形状；`parser_version = 4`（`:348`）让存量 claude-code 载荷重放。

### 2.2 组装层：父事件拿子定义，DFS 发座位号

`_apply_agent_revisions`（`agent_tree.py:302`）在父子关系确定后，按 `child.tool_use_id` 找到父节点的 `kind=agent` 事件，把子 transcript 的 `agent_definition_hash` 与 `agent_revision` 写回父事件。这解决了一个跨文件时序问题：Agent 定义 body 在子 transcript 里，但事件属于父 transcript。

`_assign_tree_indices`（`:346`）在 `_canonical_order` 之后按 `parent_agent_id` 建树，兄弟按 `sort_key` 排序，DFS 先序赋 0..N。主 Agent 是 0；父先于子；工作流/合成节点也占号。

### 2.3 持久化与迁移

迁移 0017（`0017_trigger_coordinates.py:81`）只加三列与两个索引，沿用 0016 的“列存在性 + nullability 守卫”，MySQL 部分 DDL 失败后可重跑；SQLite 降级用 batch（`:116`）。重放写入点分别在 `acquisition_replay.py:724`（tree_index）、`:737`（object_version）、`:738`（object_revision）、`:742`（triggered_at）。

## 3. 数据流走查

以一个真实 Session 的两个触发点为例：

1. 解析主 transcript，遇到 `Skill` 调用：`record_tool_use` 先记下 `object_version`（若有）与 assistant 记录时间；此时 revision 可能还未知。
2. 后续 `isMeta + sourceToolUseID` 注入到达：Claude parser 把 path 与归一化 body hash 存入 `ctx.evidence`；`skill_listing` attachment 把 16 位 digest 存入 `ctx.skill_digests`。
3. `finalize`：`_resolve_event_revisions` 按 tool-use 身份绑定 body，生成 `digest:`；没有 body 但有 listing digest 才用 fallback；都没有则 `unknown`。
4. 解析子 transcript：`prompt_snapshot` 生成 `agent_definition_hash` 与 `agent_revision`；子 meta 的 `toolUseId` 指向父 Agent 调用。
5. `_assemble_root`：先把子挂到父，`_apply_agent_revisions` 把子定义 hash/revision 写回父的 agent 事件；随后 `_canonical_order` 排序，`_assign_tree_indices` 赋 DFS 坐标。
6. 重放写库：事件行得到 `object_revision/object_version/triggered_at`，Agent 行得到 `tree_index`；下次 `data:replay:sessions` 只重放 parser version < 4 的 claude-code。

## 6. 讨论点

### 讨论点 1：组合 digest 把 path 藏进 hash，路径缺失时会改变 revision

- **位置**：`apps/api/app/service/acquisition/parsers/base.py:621`
- **现象**：Skill revision = `sha256(source_path + "\0" + body_hash)`；如果一次注入带 `Base directory for this skill:` 行、另一次没有，同一 body 会得到两个 revision。
- **问题**：这是“path + body hash”的设计选择，但 schema 没有 `source_path` 列；消费方无法从 revision 反推路径，也无法区分“路径缺失”与“路径不同”。跨机器/跨仓库复制同一 Skill 时，路径不同会被视为不同对象。
- **预判**：当前符合设计原文，且同一 workspace 的 Skill 路径通常稳定；真正需要跨路径匹配时，应由 M10 在比较层处理，而不是把 path 从身份里拿掉。无立即实害。
- **结论**：待维护者确认；若要求“同 body 跨路径也匹配”，需改设计而非只改代码。

### 讨论点 2：`attributionSkill` 只解析、不落独立列

- **位置**：`apps/api/app/service/acquisition/parsers/claude_code.py:377`、`base.py:189`
- **现象**：`attributionSkill` 被收进 `ParsedTranscript.attribution_skills`，但数据库没有对应列，也不生成事件；原始载荷仍在 `trajectory_payloads`。
- **问题**：符合“补充证据、不能替代显式触发”的设计；但如果 M10 要按归因标记统计，当前只能重新解析原始载荷。
- **预判**：本 issue 不发明无设计的列是正确取舍；M10 需要时再补迁移。无立即实害。
- **结论**：待维护者确认是否接受“raw payload 即存储”。

### 讨论点 3：未重放的存量行 `tree_index=0` 与主 Agent 坐标不可区分

- **位置**：`apps/api/alembic/versions/0017_trigger_coordinates.py:22`（默认 0）、`agent_tree.py:346`
- **现象**：迁移把存量 Agent 的 `tree_index` 设为 0；重放后才变成 DFS 序。主 Agent 也是 0。
- **问题**：如果 M10 在重放完成前消费坐标，会把所有旧节点当成“主 Agent 同序”，无法区分“未重放”与“真的是第 0 个”。
- **预判**：设计明确“重放补齐”，且 `triggered_at` 为 NULL 可作为未重放信号；但 `tree_index` 本身没有 sentinel。消费方必须以 `triggered_at IS NULL` 或 parser version 判断。
- **结论**：待维护者决定是否在 M10 前增加“coordinates known”布尔列；本 PR 不扩大 schema。

### 讨论点 4：语义版本被当作 tag

- **位置**：`claude_code.py:469`
- **现象**：`version`/`skillVersion`/`agentVersion` 都生成 `tag:<value>`；没有单独的 `version:` revision 形态。
- **问题**：如果未来出现“version 是语义版本、tag 是发布标签”的 provider，二者会被压成同一种 revision。
- **预判**：当前设计只定义 `tag:` / `digest:` / `unknown`，把显式版本当 tag 是最小实现；M10 若需要区分，应扩形态并迁移。
- **结论**：待维护者确认。

### 讨论点 5：listing content 行解析对畸形文本可能错配

- **位置**：`claude_code.py:137`（content 行循环）
- **现象**：遇到 `- ` 开头行就更新 current name，后续行只要出现 16 位 `digest:` 就挂到该 name；没有校验行结构。
- **问题**：畸形 listing 可能把一个 digest 挂到错误的 skill 名，导致 fallback revision 串名。
- **预判**：listing digest 本就是“算法未确认”的不透明 fallback，且 body 优先；错配不会覆盖明确证据，但会让 fallback 不可靠。可接受，若 M10 启用 digest 匹配前应加更严格结构校验。
- **结论**：待维护者决定是否现在收紧。

### 9.1 `apps/api/alembic/versions/0017_trigger_coordinates.py`（A）

```python
def _add_columns(table, columns):
    existing = _existing_columns(table)
    for column in columns:
        current = existing.get(str(column.name))
        if current is None:
            op.add_column(table, column)
            continue
        if bool(current["nullable"]) != bool(column.nullable):
            raise RuntimeError(...)
```

旧代码没有 0017；新代码把“列已存在但 nullability 不符”从静默通过改成显式失败，避免半套 DDL 被当成完整迁移。索引同理先反射再创建。降级先删索引再删列，SQLite 走 batch。

### 9.3 `apps/api/app/service/acquisition/parsers/base.py`（M）

职责：定义“事件长什么样”和“怎么从证据算 revision”。

旧代码的 `ParsedEvent` 只有 `definition_hash` 和 `relation_confidence`；`finalize` 直接 `events=tuple(ctx.events)`。新代码在构造 transcript 前统一解析：

`_resolve_event_revisions` 先建 `tool_use_id -> skill_definition` 映射，再按“tag → body → listing digest → unknown”的决定顺序处理；Agent 事件的 revision 先留 `unknown`，由组装层用子 transcript 覆盖。

### 9.4 `apps/api/app/service/acquisition/parsers/claude_code.py`（M）

旧代码 parser version 3，没有版本或 listing 逻辑。新代码：

### 9.5 `apps/api/app/service/acquisition/agent_tree.py`（M）

职责：把子 Agent 的 revision 挂到父事件，并给每个节点发 DFS 坐标。

旧代码在 `_transcript_node` 里用 `_skill_definition_hashes` 把 Skill body hash 写进事件；新代码把这个职责下移到 parser，`agent_tree` 只负责跨 transcript 的 Agent revision 关联与坐标。

```python
nodes = _apply_agent_revisions(nodes, transcripts)
ordered_nodes = _canonical_order(nodes, anchors, depths, main_id)
tree_indices = _assign_tree_indices({node.id: node for node in ordered_nodes}, main_id)
ordered_nodes = tuple(replace(node, tree_index=tree_indices[node.id]) for node in ordered_nodes)
```

检视发现：`_assign_tree_indices` 在不可达时抛 `ValueError`，但 `_depths` 已经先校验；这是双保险，不是新失败面。
