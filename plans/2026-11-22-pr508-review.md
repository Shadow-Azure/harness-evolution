## §1 一页速览

一句话：给「模型回话」修了一间收发室——子进程把结论写进一次性目录里的 `result.json5`，通道用三层递进的宽容解析把它读成对象、交给调用方的 Pydantic 模型盖章，失败就生成一张「哪个字段违反了哪条约束、请重写」的回话稿，让子类拿回去 `--resume` 重试一轮。

比喻：像考场收卷。`prepare` 给每位考生发一张一次性答题纸（任务目录）和一份题面说明（`schema.json`），只准他往纸上写（唯一工具白名单）；`collect` 是收卷人，先按标准格式读，读不懂按「宽松字迹」（JSON5）读，再读不懂上修复液（json-repair）抢救；最后交给阅卷老师（调用方 `model_validate`）判分，判错就写一张「第几题错在哪」的纸条（`feedback_prompt`）让考生重写一次。收卷人不命题、不判分、不喊考生——这就是 PR 强调的「四不做」边界。

## §2 架构导览

### 2.1 通道在「四不做」边界里的位置

`submission.py:15-32` 的 import 面只有 stdlib + 三个第三方包，没有任何 `app.*` 引用：它不认识 `AIAgentProvider`（`base.py:34-66`）、不认识 `AnalysisRequest`（`contracts.py:63-83`）、不认识工厂（`factory.py:58-98`）。对比 `fake.py:16-27` 直接依赖 contracts 与 base——fake 是「provider 的一个实现」，而 submission 是「provider 实现们共用的一个工具」，这条依赖方向决定了它可以被 bugfix-17 的 Claude Code 子类、bugfix-21 的 edit 路径同时复用，而不引入业务分支。

依赖三角各有分工：`pydantic` 是 schema 的唯一事实源（`prepare` 用 `model_json_schema()` 派生 `schema.json`，`submission.py:126-129`）；`json5` 只负责「读宽松字面量」；`json_repair` 只负责「读不懂时抢救」。通道自己不写业务规则、不发模型调用、不感知后端——这是 07 §5.5.3 的层 0/层 1 分工。

### 2.2 三个数据结构与一个类

`SubmissionPrep`（`submission.py:52-66`）是「一份已发下去的答题纸」：`directory`、`result_path`、`schema_path`、`prompt_addendum`、`allowed_tools`，全部 frozen+slots。`SubmissionOutcome`（`:69-88`）是「收卷结果」：`status` 三态 + `payload` + `validated` + 两类错误文本，`is_ok` 只是一个便捷属性（`:85-88`）。`StructuredSubmission`（`:91-213`）只做三件事：发卷、收卷、写回话稿。三个类型都是值对象，测试 `:329-335` 钉住了「调用方分支后不可被改写」。

`allowed_tools` 在 dataclass 上有默认值 `SUBMISSION_TOOLS`（`:66`），`prepare` 又显式传了一遍（`:136`）——重复但无害，好处是「常量改了不会悄悄影响已构造的 prep」这种语义并不存在，实际只是冗余；测试 `:267-268` 把两者都断言了。

### 2.3 `prepare`：先校验，再落盘

`submission.py:118-122` 先拒空 key 与非 Pydantic 模型，且都发生在建目录之前——这条顺序是刻意的：调用方写错参数时不会在磁盘上留下半个任务目录。之后 `_new_task_directory`（`:195-204`）分两条路：无 root 走 `tempfile.mkdtemp(prefix="he-ai-submission-")` 并记账到 `self._temp_directories`（`:197-200`）；有 root 就 `mkdir(parents=True, exist_ok=True)` 后在下面建 `{安全 key}-{uuid4}`（`:201-204`），caller 的 root 不会被当成一次性目录。`_safe_task_key`（`:216-219`）把非安全字符折成 `-`、去掉首尾 `-._`、截 48 字符，测试 `:250` 用 `"../escape"` 钉住了「任务键不能穿出 root」。

`schema.json` 的写法是 `json.dumps(model_json_schema(), ensure_ascii=False, indent=2)` 加一个换行（`:126-129`）——注意它落的是**标准 JSON**，宽容只在收货侧，命题侧不宽容。最后 `_prompt_addendum`（`:206-213`）生成三段指令：只写 `./result.json5`、形状看 `./schema.json`、JSON5 的四种宽松之处。这段文案是「层 1 防线」对模型说话的唯一入口，值得逐字读。

### 2.4 解析阶梯与「非映射短路」

`_parse_document`（`:241-266`）把三层 loader 装进一个元组（`:249-253`），循环里逐层 `try`：抛异常就把 `层名: 描述` 记进 `errors` 继续下一层（`:254-259`）；一旦某层返回**非 Mapping**，立刻带着「前序错误」返回 `invalid`（`:260-264`），不再往下一层走。三层都没成功才把累积的错误拼成一条文本（`:266`）。

这个短路的理由写在 docstring 里：`list` 或标量是「调用方给了错形状」，不是「语法坏了」，不该用修复液去救。实测也印证了短路的经济性——对 `[{"confidence": 0.7},]` 这种「严格 JSON 因尾逗号拒收、JSON5 读出 list」的输入，第三层 `json_repair` 同样会返回 list，继续往下走不可能救出对象。

### 2.5 三态终局：错误落在哪个字段

`collect`（`:139-171`）的骨架是三个 try/return：

- 读失败 → `missing`，`parse_error` 写「文件不可读：…」（`:151-157`）；
- 解析失败或顶层非对象 → `invalid`，只带 `parse_error`，`payload=None`（`:159-161`）；
- `validate` 抛任何异常 → `invalid`，带 `payload` 与 `validation_error`（`:163-170`）；
- 全通过 → `ok`，`payload` + `validated`（`:171`）。

「任何异常」是真的任何：`except Exception` 把非 Pydantic 的 validator 失败（比如跨字段一致性检查）也折进来，测试 `:202-215` 用一个直接 `raise RuntimeError` 的 validator 钉住。`_describe`（`:228-230`）负责把异常变成非空文本，`_bounded`（`:233-238`）再把文本压到 4000 字符以内——两个小工具的存在理由是「outcome 要能安全落日志/落盘」。

### 2.6 回喂文案：三种措辞，一个出口

`feedback_prompt`（`:173-193`）先对 `ok` 返回空串（`:181-182`）——这是给调用方的明确信号：拿到 validated 就不要再 `--resume`。非 ok 时先拼一段公共尾巴「未通过校验，请修正后重新写入（JSON5 宽松格式，形状见 schema.json）」（`:183-186`），然后按状态选前缀：`missing` 说「不存在或不可读」（`:187-189`），有 `validation_error` 说「字段违反约束」（`:190-191`），否则说「解析失败」（`:192-193`）。文案里带 `./result.json5` 与 `./schema.json` 两个相对路径，是因为回喂时子进程的 cwd 必须仍是任务目录——`prepare` 只给相对路径，绑定 cwd 是子类的责任；bugfix-17 的 CLI 参数也用了相对路径 `./result.json5`（`bugfix-claude-code-provider.md:34`）。

### 2.7 支撑基础件

- 常量区（`:34-49`）：两个文件名、白名单、4000 字符上限、48 字符 key 上限、一个不安全字符正则。全部 `Final`，作为「通道契约」的最小可见面。
- `_discard_directories`（`:222-225`）：`shutil.rmtree(..., ignore_errors=True)` 逐个删，吞掉竞态与权限错误——清理失败不该盖过业务结果。
- `weakref.finalize(self, _discard_directories, self._temp_directories)`（`:105-109`）：把「实例回收」当清理触发点，finalizer 持的是**列表对象**而不是 `self`，所以不会把实例钉住不死；列表是就地 append 的，finalizer 看到的是最终内容。
- `_bounded`（`:233-238`）：先 strip，超限就切 4000 字符再补 `…[truncated]`。它保护的是日志，不是模型——回喂给模型的文本同样走这条路径，所以「截断会不会伤到关键约束」是一个真问题（见 §6 讨论点 5）。

## §3 数据流走查

一条主线：调用方准备 → `prepare` 发卷 → 子进程写文件 → `collect` 收卷 → 调用方校验 → 失败回喂 → `--resume` 重写 → 再收一次。

1. **调用方准备**。未来的 `ClaudeCodeProvider.analyze` 拿到 `AnalysisRequest`（`contracts.py:63-83`，含 `task`/`prompt`/`output_model`），把 `task` 与 `output_model` 交给通道。此刻还没有任何文件。
2. **发卷**。`prepare(task_key, output_model)`（`submission.py:111-137`）先校验参数（`:118-122`），再建一次性目录（`:195-204`），写入由调用方模型派生的 `schema.json`（`:126-129`），返回含 `result_path` 与 `prompt_addendum` 的 `SubmissionPrep`（`:130-137`）。
3. **子进程写文件**。子类把 `prompt + prompt_addendum` 拼成 CLI 提示，以 `--allowed-tools "Write(./result.json5)"` 起子进程（`bugfix-claude-code-provider.md:34`）；agent 只被允许写这一个文件。注意「当前目录」这件事不在本组件里保证——`prepare` 只返回目录，子类必须把子进程 cwd 设成 `prep.directory`，否则相对路径写不到一次性目录里。
4. **收卷**。子进程退出（正常/非零/超时由子类处理）后，子类调 `collect(prep, OutputModel.model_validate)`（`:139-171`）。`read_text` 失败（不存在、无权限、非法 UTF-8）→ `missing`（`:151-157`）。
5. **解析**。`_parse_document`（`:159` → `:241-266`）按严格 JSON → JSON5 → json-repair 逐层尝试，每层先看是否 Mapping，非 Mapping 立即 `invalid`（`:260-264`）。
6. **校验**。payload 交调用方 validator（`:163-170`）：Pydantic 的字段/约束/别名/嵌套校验都发生在这里；任何异常变成 `validation_error`，状态 `invalid`。
7. **回喂**。调用方看 `status`：`ok` 直接用 `validated`，不 resume；否则 `feedback_prompt(outcome)`（`:173-193`）拿到一句可定位的文案，经 `--resume` 回灌同一会话重写 `result.json5`（预算 ≤1 轮归 bugfix-17）。
8. **终局与清理**。同一 `prep` 再 `collect` 一次即得第二轮结果（测试 `:114-131` 的「修正后重写」等价场景）；任务目录不会在 `collect` 后消失，只等实例回收时 `_discard_directories` 清理（`:105-109`、`:222-225`）。

真实输入输出（实测，`ScoreOutput{confidence∈[0,1], summary: str}`）：

| 模型写了什么 | collect 结果 | 说明 |
| --- | --- | --- |
| `{"confidence": 0.5, "summary": "ok"}` | `ok` | 第一层严格 JSON |
| `// 注释\n{confidence: 0.5, ...}` | `ok` | 第二层 JSON5（四类宽松各有用例） |
| `{"confidence": 0.7, "summary": "salvaged"`（缺右括号） | `ok` | 第三层 json-repair 救回 |
| `{"confidence": 0.7, "summary": }` | `ok`，`summary=""` | **修复液补了一个空串**（讨论点 1） |
| `{"confidence": 0.7, "summary": "salv`（截断在字符串中） | `ok`，`summary="salv"` | 截断内容被静默接受 |
| `[{...}]` 数组包一层 | `invalid`，不调 validator | 非映射短路（讨论点 3） |
| 两个对象首尾相接 | `ok`，取**后**一个 | json-repair 的 last-wins |
| 空文件 / 纯文本 / `[1,2,3]` | `invalid` | 测试 `:218-242` |
| 非法 UTF-8 字节 | `missing` | 讨论点 2 |
| 没写文件 | `missing` | 测试 `:183-199` |

这张表的证据来自本地探针：`json5.loads` 对注释、块注释、尾逗号、单引号、裸键五个用例全部接受（另测 `NaN`/`+0.5`/`0x1`/行继续也接受，超出宣传面）；`json_repair.loads` 对空串与纯文本返回 `''`、对 `null` 返回 `None`、对 `42` 返回 `int`——**会**返回非 Mapping，所以第 6 步前的类型检查不是多余防御。

## §6 讨论点

### 讨论点 1：json-repair 会「补值」，而 outcome 不记出处

**位置**：`apps/api/app/third_party_api/ai_agent/submission.py:249-265`、`:79-83`

**现象**：实测 `{"confidence": 0.7, "summary": }` 经第三层变成 `summary: ""` 并返回 `ok`；`{"confidence": 0.7, "summary": "salv` 变成 `"salv"` 也 `ok`；markdown 围栏、对象前的散文都被静默救回。但 `SubmissionOutcome` 只有 `status/payload/validated/parse_error/validation_error`，调用方无法区分「干净解析」与「修复液抢救」，更看不到修复器补过什么。

**问题**：07 §5.5.3 的层 5 要求「提交文件解析失败率、回喂重试次数入 `ai_agent_call` 事件」，层 4 要求「不静默落库半成品」。失败率能从 `status` 推出来，但「抢救率」推不出来；而被修复器补出的空串只要过得了 schema，就会以 `ok` 身份进入业务，属于层 4 想防的那种半成品。另一边，层 1 的卖点恰恰是宽容，收紧太多会削弱通道价值。

**预判**：建议在 outcome 上加 `parsed_by: Literal["strict","json5","repair"]`（或再加一个有界 `repair_log`）。成本很低：`json_repair.loads(text, logging=True)` 实测返回 `(obj, [{'text': 'While parsing an object value we found a stray }, ignoring it', 'context': 'summary": }'}])`，天然可做审计、可做「repair 档只接受闭合类修复、补值类升级为 invalid」的策略；调用方与 `ai_agent_call` 事件也能据此打标。是否本轮就加由维护者定：不加也能跑，只是层 5 的指标要等子类再包一层。

**结论**：已决 2026-11-22：接受，`SubmissionOutcome` 增加 `parsed_by` 与有界 `repair_log`（理由：层 4/5 需要区分「干净解析」与「修复液抢救」，而 repair 仅兜底与宽容契约不变；产物照收，只把出处记下来，不在本轮收紧 leniency）。见后续 fix commit。

### 讨论点 2：非法 UTF-8 归 `missing`，把「没交卷」和「交了乱码」混成一态

**位置**：`apps/api/app/third_party_api/ai_agent/submission.py:151-157`（对照 `tests/test_ai_agent_submission.py:224`）

**现象**：`read_text` 抛 `FileNotFoundError` 与抛 `UnicodeDecodeError` 走同一个 `except`，都返回 `missing`，`parse_error` 文案为「result.json5 不可读：…」。PR 正文把这条列为「可接受的实现选择（非差异）」。

**问题**：三态的直觉分工是「没写 / 写了但不可用 / 成功」。非法字节属于「写了但不可用」，语义上更接近 `invalid`。上层若按 `missing` 做「agent 没交卷 → 重开一轮」而按 `invalid` 做「回喂重写」，畸形的字节流会被送进错误的处理路径；即使两者都只是回喂，指标上「空交卷率」也会被乱码污染。

**预判**：更干净的做法是把 `except` 拆成两个分支：`UnicodeDecodeError` → `invalid`（读到字节，但解不成文本），`OSError` → `missing`。代价是改测试 `:224` 的期望值，并同步 docstring 里 `missing (no readable file)` 的说法（`:79-83` 目前其实已经写成「不可读」，所以这条更像「状态命名与调用方直觉不符」而非实现错误）。若决定保留现状，建议在 docstring 里写清「`missing` = 无法读出文本」，让调用方别把它当成「文件不存在」的同义词。

**结论**：已决 2026-11-22：接受，拆分读错误——`UnicodeDecodeError` → `invalid`，`OSError`/`FileNotFoundError` → `missing`（理由：三态按「没写 / 写了但不可用 / 成功」分工，乱码属于「写了但不可用」，否则会污染「空交卷率」并让上层走错重试路径）。见后续 fix commit。

### 讨论点 3：顶层非映射短路，是通道的一条隐含契约

**位置**：`apps/api/app/third_party_api/ai_agent/submission.py:260-264`（配合 `:142` 的 `Callable[[Mapping[str, Any]], BaseModel]`）

**现象**：`[{"confidence": 0.7, "summary": "wrapped"}]` 在严格 JSON 层就拿到 list，直接 `invalid`，**完全不会调用调用方 validator**；`[{"confidence": 0.7},]`（严格 JSON 因尾逗号拒收）走 JSON5 层拿到 list，同样短路，`parse_error` 形如「JSON5 解析结果不是 JSON 对象：list（前序错误：strict JSON: Illegal trailing comma…）」。

**问题**：这条短路等于给通道加了一条契约——「顶层必须是 JSON 对象」。它与 `_prompt_addendum` 的「单个 JSON5 对象」（`:210`）自洽，但没有写进类型签名或 `collect` 的 docstring。将来若出现 `RootModel[list[...]]` 形态的输出模型，通道会一律判 `invalid`，而且错误文案会指向「解析结果不是对象」而不是「你的模型要的是数组」。换个角度：把 list 直接交给 `model_validate`，Pydantic 会给出「Input should be a valid dictionary…」，信息量未必更差，还能让自定义 validator 自己决定接不接受。

**预判**：保持短路是对的——宽进严出、错误更早更清楚，而且继续往下走也救不出对象（实测 `json_repair` 对 `[{...}]` 同样返回 list）。建议把「顶层必须是对象」提升为显式契约（docstring + 讨论点 3 留档），这样未来接列表型输出模型时是有意扩类型，而不是撞上一个隐性限制。

**结论**：已决 2026-11-22：接受为文档化契约，在模块与 `collect` docstring 写明「顶层必须是 JSON 对象」，非映射直接 `invalid` 且不调用调用方 validator；列表型 `RootModel` 视为需要显式扩展通道（理由：短路本身正确——宽进严出、错误更早更清楚，且修复器也救不出对象——代价只是把隐性限制说清楚）。见后续 fix commit。

### 讨论点 4：`weakref.finalize` 清理策略在长生命周期进程里的行为

**位置**：`apps/api/app/third_party_api/ai_agent/submission.py:105-109`、`:195-204`、`:222-225`

**现象**：无 root 时每次 `prepare` 都 `mkdtemp` 并 append 进 `self._temp_directories`；只有实例被回收时 finalizer 才 `rmtree`。目录里是 `schema.json` + `result.json5`，`collect` 读取后不删除。

**问题**：如果通道随 provider 在启动时装配成单例（bugfix-17 最自然的写法：provider 持有一个 `StructuredSubmission`），进程活多久，`/tmp/he-ai-submission-*` 就攒多久，`_temp_directories` 列表本身也无界增长。测试不暴露这一点，因为实例随测试结束被回收。

**预判**：取决于调用方生命周期，当前**无实害**（还没有真实调用方）。建议给一个显式释放点：或在 `collect` 终局后删除（但 `--resume` 需要重读同一目录，所以更适合由调用方在「不再重试」时调 `discard(prep)`），或提供上下文管理器，或干脆约定「每次 analyze 新建一个通道实例」。前两种要把「谁拥有目录」写进 docstring（现在 `:93-99` 只说了「实例回收时删除」）。

**结论**：已决 2026-11-22：接受，新增幂等 `discard(prep)` 显式释放点，并在类 docstring 记录生命周期（理由：长生命周期实例会攒临时目录；`collect` 不自动删，因为层 5 原始证据可能仍要用，调用方在不再重试时释放即可）。见后续 fix commit。

### 讨论点 5：`_bounded` 按字符截断，可能切在错误条目中间

**位置**：`apps/api/app/third_party_api/ai_agent/submission.py:233-238`（作用于 `:166-170` 的 `validation_error`）

**现象**：实测 150 个越界的簇 → Pydantic 错误文本 30669 字符 → `_bounded` 在 4000 字符处切断，末尾是 `...input_value=99, i…[truncated]`，最后一条错误只留半行。4000 字符大约够 20 条错误。

**问题**：回喂给模型的是「半条错误 + `[truncated]`」。约束文本本身在本次实测里保住了（切点落在 `input_value` 尾部），但切点位置随字段名与消息长度浮动，不保证永远不切在「less than or equal to 1」中间。聚类与编辑计划都是列表型 schema，一次错很多条是常态，而不是极端情况。

**预判**：低危，但值得顺手改。按条目边界截断（例如 `splitlines` 分组、保留完整条目 + 显式写「还有 N 条未展示」）比按字符切更符合回喂场景；或者只取前 5 条 + 总数，模型反而更容易聚焦。当前单条错误场景完全够用，不必为它阻塞合并。

**结论**：已决 2026-11-22：接受，错误文本按行边界截断并保留「…（还有 N 行未展示）」标记，4000 字符仅作单行病理兜底，`validation_error` 与解析错误同走一条路径（理由：回喂的是完整错误行而不是半条，模型更容易聚焦；聚类与编辑计划一次错很多条是常态）。见后续 fix commit。

### 讨论点 6：`StructuredSubmission` 没从 `ai_agent/__init__.py` 导出

**位置**：`apps/api/app/third_party_api/ai_agent/__init__.py:20-32`（对照 `submission.py:269-276` 的 `__all__`）

**现象**：包的 `__init__` 导出面包含 base/contracts/factory/fake 的全部公共名，唯独没有 submission 的四个名字；测试与未来的子类只能 `from app.third_party_api.ai_agent.submission import ...`。PR 正文的对照表把「imports 仅 stdlib + json5/json_repair/pydantic」当作边界证据，但没有讨论包导出面。

**问题**：仓库把 `ai_agent/__init__.py` 当作「这个接缝的公共 API」，两种导入风格并存会让这个约定失效；bugfix-17 的作者若按包级习惯写 `from app.third_party_api.ai_agent import StructuredSubmission` 会直接 ImportError，而且报错发生在写子类时，不在本 PR 的测试里。

**预判**：建议补进包导出（一行 import + 四个 `__all__` 项），保持「包级导出面 = 公共 API」的一致性；或者反过来在 `__init__.py` docstring 里写明「submission 是子模块，按子模块导入」。前者更符合现状（其它四个模块都导出了），代价是 `__init__` 变长一点、未来若拆走 submission 要多改一处。

**结论**：已决 2026-11-22：接受，`RESULT_FILENAME`、`SCHEMA_FILENAME`、`SUBMISSION_TOOLS`、`StructuredSubmission`、`SubmissionOutcome`、`SubmissionPrep` 全部进 `ai_agent/__init__.py` 导出面（理由：`__init__.py` 是本接缝的公共 API，两种导入风格并存会让约定失效，子类作者会在写子类时才撞 ImportError）。见后续 fix commit。

### 讨论点 7：文件名与工具白名单是模块常量，`edits.json5` 路径无法直接复用

**位置**：`apps/api/app/third_party_api/ai_agent/submission.py:34`、`:40`、`:210`（下游：`bugfix-agent-edit-iteration.md:34`、07 §5.5.4）

**现象**：`RESULT_FILENAME` 与 `SUBMISSION_TOOLS` 写死为 `result.json5` / `Write(./result.json5)`，`prepare` 没有「文件名」参数；而 07 §5.5.4 与 bugfix-21 要求 edit 阶段的 `edits.json5` 也经这条通道收货（工具面 `Write(./.harness-evolution/edits.json5)`）。

**问题**：bugfix-20/21 只有三条路：把 EditPlan 写进 `result.json5`（与设计里的文件名不符）、在本文件加参数（改通道）、或复制一份通道（两份解析阶梯要同步维护）。另外 `Write(...)` 是 Claude Code 的工具语法，放在一个自称「不感知任何后端」的组件里，OpenCode 类子类需要不同的工具标识。

**预判**：现在加一个可选 `filename: str = RESULT_FILENAME`（`result_path`、`prompt_addendum`、`allowed_tools` 都由它派生）成本很小，能把「一条通道服务两种提交物」留在通道内部；也可以等 bugfix-20 再改，代价是届时同时改通道、子类、测试三处。工具语法那条无法在本层彻底解决（它是后端词汇），合理做法是明确标注「Claude Code 方言，子类可覆盖 `allowed_tools`」，或把常量移进子类；至少不要让模块 docstring 的「never branches on a backend」与常量里的 `Write(...)` 互相打脸。

**结论**：已决 2026-11-22：推迟到 bugfix-21（agent-edit 源码），本轮不参数化结果文件名与工具白名单（理由：`edits.json5` 同时需要文件名/路径参数与后端特定工具覆盖，等真实调用方落地时一次改对，避免为假设需求提前扩通道；决策与理由已写入 owning Note 的 Consequences）。

### 讨论点 8：「0 处真实差异」与 07/ADR 里仍在的快路径

**位置**：PR 正文「设计对齐」表；`plans/fullstack-design/07-backend-implementation.md:811`、`:831`；owning Note 的 `Decision`（`note:15`、`note:21`）；下游 `bugfix-claude-code-provider.md:38`、`:76`

**现象**：PR 正文称逐条对照 07 §5.5.3 后「0 处真实差异」，但对照表没有覆盖 07 明确保留的 `HE_AI_AGENT_NATIVE_SCHEMA` 快路径，也没有覆盖层 2（服务端校验）、层 4（有限重试与降级）、层 5（可观测）——这些被归到子类。与此同时，bugfix-17 已把「不实现 `--json-schema` 快路径、submission 是默认且唯一路径」写成了决定，而 07 §5.5.3 与 ADR 的 Decision 仍写「降为可选快路径、默认关」。

**问题**：同一件事在三个 home 里说法不一致：07/ADR 说「有开关，默认关」，bugfix-17 与本 PR 说「没有开关，唯一路径」。后续读者从 07 出发会以为存在一个配置项，配置文档、Settings 与测试都会跟着漂。这不是实现缺陷，是「决策留档」的归属问题。

**预判**：不必在本 PR 改 07（它属设计与事实层，改它要同步 04/ADR/双语与预算），但应在 owning Note 的 Consequences 里把「快路径已决定不做（或推迟到有真实需求时）」记下来——那正是决策记录该住的地方；PR 正文的「0 差异」建议改成「通道机制与 §5.5.3 一致；层 2/4/5 与 native 快路径归后续 issue」，避免给维护者一个过强的结论。

**结论**：已决 2026-11-22：接受，在 owning Note 的 Consequences 记录：提交通道是当前默认且唯一路径；`HE_AI_AGENT_NATIVE_SCHEMA` / `--json-schema` 仅是设计文档选项、刻意不实现，待真实需求出现再评估；`parsed_by`/`repair_log` 是层 5 出处字段；文件名参数化推迟到 bugfix-21（理由：07/ADR 与 bugfix-17 的说法漂移应在决策记录层收敛，07 事实层不在本 PR 改）。见后续 fix commit。

## §9 文件级代码分析

### `apps/api/app/third_party_api/ai_agent/submission.py`

**职责**：把「模型写的一个宽松字面量文件」变成「调用方 Pydantic 模型盖过章的结论，或一条可定位的回喂文案」——发卷、收卷、写回话稿，三件事之外什么都不做。**变更形态**：A，纯新增，无旧侧（`git show origin/main:…` 不存在该文件）。

**关键依赖解读**：

- `json5`（PyPI 社区包，纯 Python，运行时 import，无传递依赖，实测 0.17.3）：宽容字迹识别器——标准 JSON 只认双引号、精确逗号与无注释，它还能读注释、尾逗号、单引号、裸键。在本文件只做「把文本变成 Python 对象」，不做 schema 校验、不执行任何模型代码，这正是 07 §5.5.3 里「用 JS 生成 JSON 的价值是字面量容错 + 确定性序列化」的落点。
- `json-repair`（社区包，纯 Python，实测 0.64.9，运行时无依赖；`schema`/`pydantic` 只是 extra）：修复液 + 错别字纠正带——能把缺括号、缺引号、围栏、对象前的散文都「修」成合法对象。它在本文件是**唯一有写入语义的解析器**（可能补出空串、丢掉重复键、last-wins），所以它是讨论点 1 的主角。
- `pydantic`（第一方事实源）：阅卷老师。`prepare` 用 `model_json_schema()` 出题面（`:126-129`），`collect` 把 `model_validate` 交给调用方执行（`:163-170`）——通道自己不碰字段规则，因此业务校验的语义变化不会牵动通道。

比喻：`json5` 是宽容的字迹识别，`json-repair` 是修复液，`pydantic` 是阅卷老师；通道只是收发室，不替任何一方做决定。

**变更代码块分析**（纯新增，逐块讲「在做什么、为什么这么写」）：

- **常量与两个数据类**（`:34-88`）。两个文件名 + 一个白名单常量 + 两个上限 + 一个正则，全部 `Final`：它们是通道对外可断言的最小契约，测试 `:267-268`、`:256-257` 直接引用。`SubmissionPrep` 与 `SubmissionOutcome` 都 `frozen=True, slots=True`，`is_ok` 只做语法糖。为什么不是 Pydantic 模型：这层刻意不依赖 Pydantic 的校验语义，保持「通道只搬数据」的边界；测试 `:329-335` 用 `AttributeError` 钉住不可变。
- **`__init__` 与清理**（`:101-109`）。`weakref.finalize` 把「实例回收」当唯一的自动清理点，finalizer 的入参是列表对象而非 `self`，因此不会妨碍实例被回收；`_discard_directories`（`:222-225`）用 `ignore_errors=True` 吞掉竞态。为什么不在 `collect` 后删：`--resume` 需要同一目录重写重读，删除时机应属于调用方（讨论点 4）。
- **`prepare`**（`:111-137`）。先校验后落盘（`:118-122`）——失败不留下半成品目录；`_new_task_directory` 的两条路径（`:195-204`）把「一次性」与「caller 拥有 root」分开；`schema.json` 用 `ensure_ascii=False` 保证中文描述可读（Pydantic 的 field description 会原样落进去）；指令片段（`:206-213`）是给模型的唯一话术，包含「只写这个文件」「形状看 schema」「四种宽松」。
- **`collect`**（`:139-171`）。三个 return 把「读失败 / 解析失败 / 校验失败」拆成不同状态与不同错误字段，关键是**任何分支都不抛**：`except (OSError, UnicodeDecodeError)` 兜 IO，`except Exception` 兜 validator。为什么 validator 用注入的 callable 而不是 `type[BaseModel]`：调用方可能要跑跨字段语义校验（07 的层 0/层 2），Pydantic 的 `model_validate` 只是其中一种实现；测试 `:202-215` 用一个 `RuntimeError` validator 证明这条缝真的通用。
- **`feedback_prompt`**（`:173-193`）。状态 → 措辞的映射是 `ok` 返空串（明确「别再 resume」）、`missing` 说不可读、`validation_error` 说字段违约、其余说解析失败；尾巴统一指向 `./result.json5` 与 `./schema.json`。为什么返回 `str` 而不是结构化对象：回喂是「一句话塞回 CLI」，调用方不需要再拼装。
- **目录与工具**（`:195-225`）。`_safe_task_key` 用「白名单字符 + 截 48 + 兜底 task」防路径穿越（`:216-219`），测试 `:250` 用 `"../escape"` 验证父目录仍是 root。`_discard_directories` 见上。
- **文本工具**（`:228-238`）。`_describe` 保证错误文本非空（空消息的异常也有类型名兜底），`_bounded` 保证落盘/回喂的文本有上限——两者共同服务「outcome 可安全持久化」。
- **解析阶梯**（`:241-266`）。三层 loader 元组 + 逐层 try + 非映射短路 + 错误聚合，是本文件的心脏。实现思路三行：能严则严（标准 JSON 优先）→ 不能严就宽（JSON5）→ 宽也读不出才修（json-repair）；每一层都只接受「对象」，非对象立刻判死并附前序错误；三层全失败才返回聚合文本。

**检视发现**：

1. **json-repair 补值**（中，`:254-265`）：实测 `{"summary": }` → `summary=""` 且 `ok`，无出处记录；违反层 4「不静默落库半成品」的精神。修法见讨论点 1（`logging=True` 的 repair log 现成可用）。
2. **读取无上限**（低，`:152`）：`read_text` 一次性读全文，只捕获 `OSError`/`UnicodeDecodeError`；模型写出超大文件时 `MemoryError` 会逃出「collect never raises」。修法：读前 `stat().st_size` 判上限（建议 1 MiB）→ `invalid` + 明确文案。
3. **`missing` 文案重复**（低，`:156` + `:189`）：实测回喂文本为 `result.json5 不存在或不可读：result.json5 不可读：[Errno 2] No such file or directory: '/var/folders/…/result.json5'`——文件名与「不可读」各出现两次，并把绝对临时路径喂给模型。修法：`parse_error` 只存原因，前缀交给 `feedback_prompt`。
4. **`_bounded` 截断**（低，`:233-238`）：见讨论点 5，实测 30669 字符被切在条目中间。
5. **无实害但值得知道**：`allowed_tools` 在 dataclass 默认值与 `prepare` 实参里重复（`:66`、`:136`）；`__all__`（`:269-276`）完整但包级未导出（讨论点 6）；`# ruff: noqa: RUF001`（`:15`）应为文案里的全角标点触发了「歧义 Unicode 字符」规则，属于「中文文案进 Python 字符串」的既定代价，不是遗留问题。

### `apps/api/tests/test_ai_agent_submission.py`

**职责**：用 20 项测试钉住五件事——宽容矩阵、兜底只在必要时触发、三态终局、一次性目录、值对象不可变。**变更形态**：A，纯新增。

**关键依赖解读**：`pytest` 的 `tmp_path` 提供真实文件系统（不用 mock 文件系统，因为「真实写文件再读」正是通道的价值）；`monkeypatch` 用来给 `json_repair.loads` 装探针（`:53-63`），断言「兜底层有没有被叫到」。这个探针能生效的前提是 `submission.py` 在调用点做 `json_repair.loads(...)` 属性查找（`:252`）——若哪天有人改成 `from json_repair import loads`，探针会静默失效、测试仍然全绿但不再证明任何事。这是本文件最脆的一处，值得在测试注释里留一句。

**变更代码块分析**：

- **宽容矩阵**（`:66-111`）：五个用例覆盖行注释、块注释、尾逗号、单引号、裸键，每个都断言 `status=ok`、`payload` 精确相等、`validated` 是模型实例、两个错误字段为 None、回喂为空串——一条用例同时钉住「解析成功」与「不该回喂」。
- **兜底的两面**（`:114-154`）：一面证明「缺右括号会进 repair 且被救回」（`:114-131`），另一面证明「标准 JSON 与 JSON5 成功时 repair 完全不被调用」（`:134-154`，断言 `repairs == []`）。两面合起来才是 issue 的验收标准「仅作回退路径」。
- **三态**（`:157-242`）：`invalid` 断言 Pydantic 错误文本含 `1 validation error for ScoreOutput`、字段名、`less than or equal to 1`，且回喂含重写路径（`:157-180`）；`missing` 断言 `payload/validated` 为 None 且文案含「不存在」（`:183-199`）；畸形输入四例（空串、纯文本、数组、非法 UTF-8）只断言「终态且不抛」（`:218-242`）。
- **目录与准备**（`:245-300`）：两次 `prepare` 目录不同、`schema.json` 由调用方模型派生（含 `$defs` 里的 `from` 别名）、`../escape` 不能穿出 root、白名单恰为一条；空 key 与非 Pydantic 模型在**建目录前**被拒（`:293-300`）。
- **别名与嵌套**（`:303-326`）：`from` 别名 + 嵌套列表 + 注释/单引号/尾逗号混写，证明语义校验确实由 Pydantic 完成，而不是通道自己实现了一套。
- **冻结**（`:329-335`）：`AttributeError` 钉住 outcome 不可变。

**检视发现**：

1. **覆盖缺口**（process，低）：`_bounded` 的截断分支（`submission.py:238`）与「三层全失败」分支（`:266`）没有用例——后者实际上很难触达，因为 `json_repair.loads` 对字符串输入几乎不抛异常（实测空串/垃圾文本都返回 `''`），这条分支更像防御性兜底；前者补一个「超长错误被截断且带 `[truncated]`」的用例即可。
2. **未测的语义**（process，低）：没有用例断言「解析失败的 `invalid` 的 `payload is None`」；没有用例断言「JSON5 层返回非映射时同样短路且不叫 repair」（现有数组用例走的是严格 JSON 层）；没有用例覆盖 `missing` 文案的重复前缀（它就是被现状批准下来的）；也没有用例覆盖清理行为（`weakref.finalize` 只在实例回收时触发，测试天然看不到）。
3. **探针脆弱性**（process，低）：见上，`monkeypatch.setattr(json_repair, "loads", spy)` 依赖调用点的属性查找方式；建议加一行注释说明这个前提，或在 `submission.py` 里保留 `json_repair.loads` 的调用形态（现状即如此）。
4. **无外部依赖**：没有网络、没有子进程、没有时钟；`tmp_path` 隔离干净。PR 的「20 passed」本地实测可复现。
