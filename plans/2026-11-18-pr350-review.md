## §2 架构导览

### 2.1 页头动作仍由 Index.vue 拥有

issue 的“实现内容”写“在 `TargetsOverview` 的页头动作区”，但实际页头 `.page-head` 与其动作区一直由 `Index.vue` 拥有（`Index.vue:333-396`），`TargetsOverview.vue` 从模板第一行起就是统计条/筛选/图表（`TargetsOverview.vue:445` 起），没有自己的页头。把按钮塞进 `TargetsOverview` 反而会制造两个页头所有权，因此本次把动作留在共享页头，并按 `state.tab` 分派（`Index.vue:346-395`）。这是对 issue 文字的落地解释，不是范围扩张。

### 2.2 复用而不是复制向导

`openLaunchWizard`（`Index.vue:237-240`）只做一件事：`canManage` 时把 `wizardOpen` 置真。两个 tab 的按钮都调用同一个函数（`Index.vue:359`、`:384`），`LaunchWizard` 也只在页面底部挂载一次（`Index.vue:538-542`）。因此不存在第二份步骤状态、第二个 `open` 标志或重复的四步表单；切换 tab 不会新建向导实例。

### 2.3 权限判断只有一层来源

两个 tab 的按钮都包在 `v-if="canManage"` 里（`Index.vue:347`、`:371`），`canManage` 来自 `canManageWorkspace(workspace.role)`（`Index.vue:79-81`），与「+ 新增进化对象」、bad case 总览的写入口共用同一判断。`openLaunchWizard` 内再次检查 `canManage` 是纵深防御，不是第二套角色规则。

### 2.4 空配置守卫属于既有向导

按钮不预先判断“有没有启用对象”，点击后由 `LaunchWizard` 的 `hasAnyTarget` 分支决定显示四步表单还是配置守卫（`LaunchWizard.vue:146-153`、`:722-748`）。这正是 issue 要求的“不在前端重复判断目标是否可用”；配置链接 `goTargetConfig` 使用 `workspacePath(props.wid, "evolution/targets")`（`LaunchWizard.vue:367-371`），因此不会回到默认空间。

## §3 数据流走查

一条主线：进入对象总览 → 点启动 → 向导 → 空对象守卫 → 关闭/跳转。

1. 路由带 `?tab=targets`，`state.tab` 为 targets，页头走 `v-else` 分支（`Index.vue:370`）。
2. `canManage` 为真时渲染两个按钮（`:371-391`）；为假时渲染只读提示（`:392-395`）。
3. 点击「启动自进化」调用 `openLaunchWizard`（`:384`），`wizardOpen=true`（`:239`）。
4. `LaunchWizard` 挂载，读取 `/catalogs/targets`；无启用对象时渲染 `wizard-config-empty`（`LaunchWizard.vue:725-748`）。
5. 点「关闭」触发 `@close`，只把 `wizardOpen=false`（`Index.vue:541`），URL 的 `tab/range/grain/objects` 原样保留。
6. 点「前往配置 →」触发 `goTargetConfig`：先关向导，再 `router.push` 当前空间 `evolution/targets`（`LaunchWizard.vue:367-371`）。
7. 有启用对象时同一入口进入既有四步流程；本次未改向导步骤（E2E 使用空对象空间验证守卫路径，避免为测试伪造可联网的 git target）。

## §6 讨论点

### D1 页头动作落在 Index.vue，而非 issue 字面的 TargetsOverview

- **位置：** `apps/web/src/pages/overview/Index.vue:370-393`
- **现象：** issue 的实现内容写“在 `TargetsOverview` 的页头动作区增加”，但页头与动作区实际由 `Index.vue` 拥有；`TargetsOverview.vue` 没有页头。
- **问题：** 按字面把按钮搬进 `TargetsOverview` 会引入第二个页头所有权，或需要把页头整体下移，改动面与回归风险都大于收益。
- **预判：** 留在共享页头并按 tab 分派更符合现有结构；issue 文字可视为对“对象总览页头”的泛指。
- **结论：** （留空给维护者）

### D2 P2 issue 在 P1 尚未清档时被激活

- **位置：** `.agents/flow/issues/m12-12-target-overview-launch.md:14`
- **现象：** m12 仍有 P1 未 done（m12-09）时，本 issue 从 backlog 激活为 ready；若标 in-progress 会触发 `verify-flow` 的“P2 档未解锁”。
- **问题：** 当前用 ready 表达“已开始准备、等待 P1 清档”；若仓库要求严格串行，应在 P1 清档后再合并。
- **预判：** 本次由 ticket 明确指定开发 m12-12；保持 ready 可通过离线门禁，合并时机由维护者按优先级决定。
- **结论：** （留空给维护者）

### D3 E2E 只验证空配置守卫，不验证四步表单

- **位置：** `tests/e2e/m12-12-target-overview-launch.test.mjs:344-415`
- **现象：** 有对象的真实 target 种子指向 `example.invalid`，打开向导会等待远端 tag 读取；E2E 因此用空对象空间验证守卫、关闭和配置跳转，四步表单纯粹复用既有组件与测试。
- **问题：** “有对象时进入 Step1”没有真实浏览器断言，只有组件测试的向导挂载断言。
- **预判：** 本 issue 的边界是不改向导步骤；用既有向导的测试覆盖步骤，新增 E2E 聚焦入口与空态，是合理的成本取舍。
- **结论：** （留空给维护者）

## §9 文件级代码分析

### `apps/web/src/pages/overview/Index.vue`（M，+27/-8）

**职责：** 工作空间总览页壳：页头、tab、两个视图与启动向导的挂载点。

**旧代码：**

```vue
<template v-else>
  <button v-if="canManage" ... @click="targetsOverview?.openCreate()">+ 新增进化对象</button>
  <span v-else class="readonly">只读访问</span>
</template>
```

**新代码：**

```vue
<template v-else>
  <template v-if="canManage">
    <button ... @click="targetsOverview?.openCreate()">+ 新增进化对象</button>
    <button class="head-btn primary" data-testid="ov-target-launch" @click="openLaunchWizard">启动自进化</button>

  <span v-else class="readonly">只读访问</span>
</template>
```

**这在做什么：** 把原来的 `v-if` 从单个创建按钮提升到动作组，让创建和启动共享同一个 `canManage` 条件；启动按钮直接调用页面已有的 `openLaunchWizard`，没有新增状态或 API。主按钮样式与 bad case 总览一致，视觉层级与原型一致。
