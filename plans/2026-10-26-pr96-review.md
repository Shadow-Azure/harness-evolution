## §1 一页速览

一句话：这个 PR 把归一化后的会话、Agent、触发事件和外部问题组合成三个只读接口，让列表页、概览页和执行流图共享同一套后端真值。

生活化比喻：`session_families` 像一张已经算好总账的目录卡，`agents/agent_events` 是目录卡背后展开的家族关系图，外部 `bad_cases` 则像别人贴在图上的一次性便签；这个 PR 负责把三者按稳定规则装订成一份可直接翻阅的档案。

| 交付块 | 结论 |
|---|---|
| `GET /api/sessions` | 搜索、状态过滤、四种排序与 limit 均已实现 |
| `GET /api/sessions/{sessionId}` | 与列表项同构，404 使用统一 `SESSION_NOT_FOUND` |
| `GET /api/sessions/{sessionId}/tree` | 扁平 Agent、trigger、问题锚点和封闭枚举齐全 |
| 存储边界 | SQL 位于 `db/crud`，service 不拼 SQL；问题计数按页一次聚合 |
| OpenAPI/TS | 生成物同步，受保护 operation 与 422 外壳完整 |
| UI | 本 PR 无前端 diff；亮色原型壳保持不变 |

## §2 架构导览

### 2.1 HTTP 边界

`apps/api/app/api/sessions.py:29-49` 定义列表参数，`sessions.py:63-68` 与 `sessions.py:81-86` 分别提供概览和树。每个 operation 都声明 BearerAuth 以及 401/403/404/422 的统一 `ErrorResponse`；SQL 和业务映射没有进入路由。

参数约束与 `05-api-design.md:569-576` 对齐：`q <= 512`、`limit` 为 1–500，状态与排序使用闭集 Literal。

### 2.2 Service 编排

`service/sessions/service.py:209-219` 先读取当前页 session aggregates，再用一次 `bad_case_counts()` 聚合当前页问题数，避免按卡 N+1 查询。

列表 DTO 的密度计算集中在 `_density()`（`service.py:49-53`）；会话行、问题和树字段映射均集中在同一模块。主 Agent 固定显示“主会话”，其他节点按 `name → skillName → agentType → kind` 取标签（`service.py:82-89`）。

### 2.3 锚点计算

`service.py:141-199` 实现外部问题到执行流图的挂载：

- `self + agent`：上报 Agent 自身，`eventIndex=-1`。
- `self/discovery + skill`：上报 Agent 中同名 skill 的最后一次 trigger。
- `discovery + agent`：上报 Agent 的父节点中，用子 Agent `toolUseId` 匹配的 agent trigger。
- reporter 缺失或 trigger 缺失时记录脱敏 warning 并降级。

### 2.4 存储读路径

`db/crud/sessions.py:189-229` 完成列表搜索、状态、排序和 limit；`sessions.py:231-296` 分别读取 session、Agent、事件和问题。

问题计数使用 `GROUP BY bad_case_session_id`（`sessions.py:247-261`），对当前页 session id 只发一次查询。

### 2.5 共享契约

`packages/contracts/openapi.json` 已包含 `SessionListItem`、`SessionTree`、`SessionAgent`、`SessionEvent` 和 `SessionBadCase`。OpenAPI 测试额外锁定 three session operations 的 security、参数集合、闭集 `taskKind` 与统一 422 外壳。

## §3 数据流走查

### 场景 A：列表页分诊

1. Web 请求 `GET /api/sessions?status=problem&sort=agents`。
2. HTTP 层把 `status` alias 收窄为 Literal，service 建立 `SessionFilters`。
3. repository 先按 `partial/fail` 过滤 `session_families`，再按 agents 数倒序并用 session id 稳定破平。
4. 当前页 session id 一次分组查询 `bad_cases` 数量。
5. service 将聚合列和问题数映射成统一的 `SessionListItem`，密度由后端计算到一位小数。

### 场景 B：打开会话并绘制执行流

1. Web 请求 `GET /api/sessions/{sid}/tree`。
2. repository 读取 family、agents、events、bad-cases。
3. service 以 main Agent 为起点，将树整理成扁平节点与稳定 trigger 列表。
4. 外部问题先解析上报 Agent，再依据问题类型和对象类型寻找 host Agent 与 event index。
5. 前端只按 `parentAgentId/toolUseId/events/messageOffset` 绘制和计算节点间距，不重新做后端聚合。

### 场景 C：问题卡挂载

`discovery + agent` 卡片不只挂到上报子 Agent，而是回到父 Agent 中“调用该子 Agent”的 trigger。这样原型里的问题连线会落在实际分叉点，而不是浮在子节点旁边（设计见 `05-api-design.md:180-182`）。

## §6 讨论点

### D1 tree 读取跨多个数据库 snapshot，可能拼接两个版本

**位置**：`apps/api/app/service/sessions/service.py:236-248`、`apps/api/app/db/crud/sessions.py:231-296`

**现象**：`tree()` 依次调用 `get()`、`list_agents()`、`list_events()`、`list_bad_cases()`，每个 repository 方法都单独执行 `async with self._database.session()`。用临时回归在 `list_agents()` 返回后提交一次 canonical 更新，最终响应出现旧 `messagesCount=1` 加新 `concurrent-skill` 事件；数据库新状态实际是 `messagesCount=2` 且包含新事件。

**问题**：m2-05 的 replay 本来就是为了替换整棵树；用户打开页面时恰好遇到 replay，会在一次响应中看到新旧版本混合。parent/event/stats 不一致时，前端执行流图可能画错边、错算 `×N`，锚点也可能指向新版本才存在的事件。

**预判**：这是并发读取一致性缺陷。最小修复是在 repository 提供一个 tree snapshot 方法，让 family/agents/events/bad-cases 在同一个 `database.session()`/读事务中查询；不要让 service 跨 session 拼装同一棵树。

**结论**：已修复（2026-10-26）。repository 新增单次 `tree_snapshot()`，family、Agent、event 和 bad-case 在同一数据库 session 中读取；回归断言 tree 请求只打开一次 session。

### D2 anchor 暴露存储序号，而不是返回数组下标

**位置**：`apps/api/app/service/sessions/service.py:133-138`、`apps/api/app/service/sessions/service.py:171-173`

**现象**：`_last_skill()` 和 discovery-agent 分支直接返回数据库 `event_index`。把唯一一条 skill 事件的 `event_index` 设为 5 后，API 仍返回 `anchor.eventIndex=5`，但该 Agent 的 `events[]` 长度只有 1。

**问题**：设计明确规定 `anchor.eventIndex` 是目标 Agent `events[]` 的 0-based 下标，不是数据库主键或任意序号（`05-api-design.md:181`）。前端会按该值访问数组；非连续或历史数据会把问题卡锚到不存在的位置。

**预判**：当前 canonical assembler 正常生成连续序号，所以新 fixture 不会触发；但数据库约束只保证 `(agent_id,event_index)` 唯一，不保证连续。最小修复是按已排序 `events` 列表枚举得到真实下标，并为稀疏/乱序数据补回归。

**结论**：已修复（2026-10-26）。`anchor.eventIndex` 改由返回事件数组枚举得到；稀疏存储序号 5 在唯一返回事件上映射为 0。

### D3 未知 reporter 与 skill 组合仍借用 main 的 trigger

**位置**：`apps/api/app/service/sessions/service.py:149-161`

**现象**：把 `badcase-synthetic-0003` 的 `bad_case_agent_id` 改为不存在的 `missing-reporter` 后，接口记录了 warning，但返回 `anchor={agentId: main, eventIndex: 0}`，因为 fallback main 恰好有一个同名 skill。此前“未知 reporter 降级到根节点”的测试只覆盖了 `object_type=agent`，因此没有捕获。

**问题**：未知上报者意味着无法确认问题来源；main 中偶然出现的同名 skill 不应自动接管该问题。这会改变问题卡的视觉归属，可能把错误归到未参与上报的 skill。

**预判**：若“降级到根节点”按现有实现语义允许 root 内的同名 skill，需要把规则写进契约和测试；否则应在此组合下跳过 skill 匹配，直接返回 main + `eventIndex=-1`。

**结论**：已修复（2026-10-26）。未知 reporter 的 skill 问题不再搜索 main 的同名 trigger，固定锚到 main 自身且 `eventIndex=-1`。
