## §1 一页速览

**一句话**：第 4 步归因表过去像一张写着「报告编号」的索引卡，却不肯写这张卡放在哪个房间（Session）——现在 API 在每行补上房间号，前端把两列编号都变成门：来源 case 打开「问题描述」，报告 ID 打开「归因分析」并选中该行。

**比喻**：错误详情页是一栋按 Session 分房间的档案楼，深链是「房间号 + 案卷号 + 页签」的取件单；第 3 步一直带着房间号（`sessionId`）取件，第 4 步手里只有案卷号和报告号，所以只能停在楼门口。这个 PR 不是在前台再查一次房间（会引入第二事实源或绑定分页加载），而是让第 4 步的行数据本身随行携带房间号。

## §2 架构导览

### 2.1 契约层：Session 随行返回，而不是前端反查

错误详情深链的格式是 `/workspaces/:wid/sessions/:sid/errors?case=…&tab=…[&at=…]`，其中 `sid` 必须是 bad case 所属根会话（`badCaseId.ts:21-36`）。第 4 步的行只有 `badCaseId / attributionId`，拿不到 `sid`；组件即使把 ID 做成锚点，也只能拼出没有 Session 的链接。

PR 选择在响应 DTO 上增加必填 `session_id`（`stages.py:179-189`），而不是：

- 用 V2 原型的全局 `BAD_CASES` fixture 反查——生产前端没有这张表；
- 从第 3 步 potential rows 反查——第 3 步 5 条/页，第 4 步 6 行以上会查不到，还把两个步骤的加载顺序绑在一起；
- 新增按 `attributionId` 解析深链的接口——多一次往返，URL 仍要前端拼。

这些替代方案在 Agent Note 的 `## Alternatives considered` 里都有记录。契约层的实际差异只有三处：`openapi.json:5949` 与 `:5964`（属性与 required）、`api.d.ts:4016`（生成类型），以及 `contract:check` 已确认生成物与源码一致。`StepAttributionRow` 是响应模型，增加必填字段对旧客户端是「多一个可忽略字段」；生产发布是 api/web 同一 release 的原子切换（`docs/deployment.md:5`、`:20`），不存在新前端配旧 API 的窗口。

### 2.2 行内 Session 的来源：V2 与 legacy 各自真实来源

两条路径都从数据事实取 Session，没有前端推算：

- **V2**：`candidate.session_id`。候选行的 Session 由 `bad_cases.bad_case_session_id` 写入（`apps/api/app/db/crud/potential.py:147`、`apps/api/app/service/evolution/potential.py:750`、`apps/api/app/db/models/evolution.py:148`），也就是 bad case 的根会话。
- **legacy**：`first.probe_session_id`。来自 `probe_reports.session_id`（`apps/api/app/db/crud/probe_query.py:102`、`apps/api/app/db/models/domain.py:345`，列非空）。

这两个值指向同一个根会话，权威口径在 [13-root-session-id.md:8](fullstack-design/13-root-session-id.md)：「`bad_cases.bad_case_session_id`、`probe_reports.session_id`、`GET /api/sessions/{sid}` 的 `sid` 以及 Session 卡片的 `id` 都指向同一个值」。同一约定早已被第 3 步使用：potential 行的 `session_id` 分别取 `candidate.session_id` / `first.probe_session_id`（`stages.py:869`、`:891`），`StepPotential.vue:98` 已用同一个 helper 拼深链；第 4 步只是补齐同一条约定。

如果 Session 真的取错，错误详情页不会静默打开错误 case：`Index.vue:237-243` 会比较 `detail.sessionId` 与路由 `sid`，不一致直接显示 `BAD_CASE_SESSION_MISMATCH`。E2E 又把 6 行的 `session/case` 映射逐条固定（`m10-06:451-489`），因此「行与 Session 错配」在本 PR 内有测试兜底。**未发现 wrong-session 缺陷。**

### 2.3 深链格式与错误页解析

- URL 由唯一 helper `badCaseDeepLink` 生成（`badCaseId.ts:21-36`）：`URLSearchParams` 负责 `case/tab/at` 编码，path 参数分别 `encodeURIComponent`。
- 错误页由 `parseSessionDeepLink(..., "error")` 解析（`router/deepLink.ts:132-256`）：`case` 与 `at` 走同一套 SAFE_ID 校验（`at` 校验在 `:196-206`），`at` 缺少 `case` 会被判为 `DEEP_LINK_INVALID`。
- 页签与选中项由 `Index.vue` 的三个 computed 决定：`activeTab`（`:86-88`）、`requestedAttributionId`（`:90-91`）、`resolvedIndex`（`:137-155`）。`resolvedIndex` 先按 `at` 匹配，匹配不到再按 `obj`，最后回落到第一条——这与 [05 接口设计](fullstack-design/05-api-design.md) 第 1250 行的深链契约一致。
- `at` 在整页范围内加载：`useAttributions` 先取 50 条，再逐页读完全部归因（`useBadCases.ts:121-150`），不会因为归因分页而丢失 `at`。
- URL 里的 `tab=desc` 会保留：只有 sessions 列表页做 query canonicalization（`apps/web/src/pages/sessions/Index.vue:511`），错误页不做；因此 E2E 里 `/case=…&tab=desc$/` 的断言成立，不是碰巧。

### 2.4 渲染、样式与无障碍

`StepAttribution.vue` 的两个锚点：

- 来源列：`badCaseDeepLink(wid, row.sessionId, row.badCaseId, 'desc')`（`:79`），`aria-label="来源问题 <id>，在新窗口打开问题描述"`（`:81`），`title` 为完整 bad case ID（`:80`）。
- 报告列：`badCaseDeepLink(..., 'attr', row.attributionId)`（`:91-98`），`aria-label="归因报告 <id>，在新窗口打开归因分析"`（`:100`），`title="归因报告 ID · 打开归因分析"`（`:103`）。
- 两列都带 `target="_blank"` 与 `rel="noopener noreferrer"`（`:82-83`、`:101-102`）。

样式（`:229-256`）沿用 V2 原型 `.idlink` 的视觉语言：蓝色、1px 虚线下划线、hover 变实线、`focus-visible` 2px outline（原型定义见 `plans/ui-prototype-v2/harness-evolution.html:543-545`，第 4 步用法见 `:5344-5365`）。`td.id` 上原来的 `color: var(--blue)` 被移除（`:218-223`），颜色改由锚点承担——这正好消除了「蓝色但不可点」的误导。

无障碍方面，原生 `<a href>` 天然可聚焦、可回车打开；`aria-label` 覆盖可见的纯 ID 文本，补足动作语义；`title` 保留完整 ID。没有发现可访问性缺陷（12 个新 Tab 停靠点属于表格内正常链接密度）。

### 2.5 测试分层与各自的证明边界

- **组件**：`RunDetailConformance.test.ts:477-543` 逐字段断言两列锚点的 `href/target/rel/aria-label/title`；`StepContent.test.ts:419-433` 断言 href 含 `tab=desc` / `tab=attr&at=`。
- **API**：`test_m10_04_stages.py:84`（V2 行 `session-m10-04`）与 `:116-121`（legacy 行 `050b81ba-…c3`）。
- **E2E**：`m10-06:423-489` 锁 6 行 12 锚点、逐条 href、`reportLinks[0].focus()` 与 activeElement；`:646-712` 真的导航到报告/来源 href，断言落点页签与选中归因。
- **错误页深链解析**：`Index.test.ts:461` 用 4 条归因、`at=AT-0002` 断言落在 `2 / 4`——这是「多归因选中该行」的既有证据，正好补上新 E2E 没覆盖的那条分支（见 D3）。

## §3 数据流走查

1. 运行详情路由 `/workspaces/:wid/evolution/runs/:runId?step=attribution` 渲染 `RunDetail.vue`，它把路由里的 `workspaceId` 传给 `RunStepContent`（`RunDetail.vue:917-924`）。
2. `RunStepContent` 在 `step.key === 'attribution'` 分支把同一个 `wid` 传给 `StepAttribution`（`RunStepContent.vue:60-64`）。
3. 前端请求 `GET …/runs/:runId/steps/attribution`；服务端 `EvolutionStageService.step` 组装 `_RunFacts` 后经 `build_step_payload` 的 builder 表选择 `_attribution`（`stages.py:544-552`）。
4. V2 分支 `_v2_attribution_rows` 按候选行生成 `StepAttributionRow`，`session_id=candidate.session_id`（`stages.py:918`）；legacy 分支 `_legacy_attribution_rows` 按 probe id 分组，`session_id=first.probe_session_id`（`stages.py:942`）。
5. 响应 JSON 的每行因此带 `sessionId`；生成类型 `api.d.ts:4016` 与 OpenAPI `openapi.json:5949` 同步。
6. 模板为每行渲染两个锚点（`StepAttribution.vue:78-104`）：来源 href 是 `…/errors?case=<case>&tab=desc`，报告 href 是 `…/errors?case=<case>&tab=attr&at=<report>`。
7. 用户在新窗口打开报告链接；路由进入 `/sessions/:sid/errors`，`parseSessionDeepLink` 解析出 `case/tab=attr/at`（`deepLink.ts:196-206`），`useBadCase` 加载该 case 并校验 `detail.sessionId === sid`（`Index.vue:237-243`）。
8. `useAttributions` 读完全部归因页（`useBadCases.ts:135-147`），`resolvedIndex` 按 `at` 找到该行（`Index.vue:140-145`），`#attr-tab` 为 `aria-selected=true`（`Index.vue:652-665`），`AttributionReport` 渲染被选中的归因，`attribution-deep-link` 的 `title` 等于 `attributionId`（`AttributionReport.vue:163-173`）。
9. 来源链接跳过 `at`，只带 `tab=desc`：错误页进入「问题描述」页签，内容由 `ProblemDescription` 渲染；`at` 缺省时 `resolvedIndex` 回落 0，不影响描述页签。
10. legacy 运行走同一组件与同一深链；`at=probe_id` 仍能在该 bad case 的归因列表里命中，因为 `attributionId` 在 API 层就映射 `probe_reports.probe_id`（`plans/fullstack-design/05-api-design.md:564`、`bad_cases/attribution.py:100`）。
11. 没有行时渲染既有空态（`StepAttribution.vue:128-133`），本 PR 未改动。

### 9.2 `apps/api/app/service/evolution/stages.py`

**职责**：七步只读投影；本次给第 4 步行补 Session。变更形态 M。


**新代码**：

```python
class StepAttributionRow(IdentityModel):

    session_id: str
    attribution_id: str
```

两处构造器：

| 路径 | 旧 | 新 |
|---|---|---|
| V2 | 无 Session | `session_id=candidate.session_id`（`:918`） |
| legacy | 无 Session | `session_id=first.probe_session_id`（`:942`） |

**在做什么**：把「bad case 属于哪个根会话」从数据事实随行带给前端，而不是让前端按 case 反查。

**为什么这么写**：V2 的候选行本来就由 bad case 行生成（`potential.py:147`），Session 是它的固有属性；legacy 的 probe 行也持久化了根会话（`probe_reports.session_id`，非空），两者与 [13 号文档](fullstack-design/13-root-session-id.md) 的根会话口径一致。没有新增查询、缓存或数据库字段。

**实现思路总结**：字段随行返回；V2 与 legacy 各取自己已有的真实来源；前端只负责拼 URL。

**检视发现**：无代码缺陷。两点值得记录：

1. `StepAttributionRow` 的 docstring 说「rows without a Session cannot offer that link」，但字段是必填 `str`。V2 路径的 `probe_reports.session_id` 在 `ProbeWrite.__post_init__`（`attributions.py:106-108`）被拒绝为空；legacy 只有数据库列非空约束（`domain.py:345`），历史导入若写入空字符串，前端仍会拼出 `/sessions//errors`。当前未观测到这类数据，无实害（见 9.9）。
2. legacy 行取 `first = probe_rows[0]` 的 `bad_case_id` 与 `probe_session_id`；两者来自同一行，不会互相错配。若历史数据的 `probe_session_id` 与 `bad_case_session_id` 不同，第 3 步会先暴露出这个问题（同源），不属于本 PR 新增风险。
