## §1 一页速览

**一句话**：旧 analyze 把 `Write` 写进“允许清单”，却用 `--bare` 把工具集收窄到根本没有 `Write`；同时写权限规则用了 CLI 不匹配的 `Write(path)` 形式。本 PR 让工具集真实包含 `Write`，把唯一写权限按任务目录绝对路径配给 `Edit(//.../result.json5)`，并把“工具缺失/写被拒/超时”变成一次可诊断的失败，而不是第二次 300 秒重试。

**比喻**：旧实现像在门口贴了一张“允许进门”的清单，却把门焊死（`--bare` 移除了 `Write`）；即使门在，钥匙形状也不对（`Write(path)` 规则不参与文件写权限检查）。新实现先装回门（`--tools Read,Write`），再把钥匙只配给任务目录里那一把锁（`Edit(//<task>/result.json5)`）。

## §2 架构导览

### 2.1 适配层与提交契约的边界

提交通道（`submission.py`）仍负责“任务目录 + `schema.json` + `result.json5` + collect + 一次反馈重试”，本 PR 没有改它；改动全部收在 `ClaudeCodeProvider` 的 argv、规则与诊断层，符合 issue 的硬约束。

### 2.2 工具集不是允许列表

`claude_code.py:528-572` 的 `_analyze_argv()` 现在显式给 `--tools Read,Write`。这是本 PR 的关键认知：`--allowed-tools` 只能在已有工具集里做允许/拒绝，不能把被 `--bare` 移除的工具加回来。`ANALYZE_TOOLS`（`claude_code.py:86`）和 `SUBMISSION_TOOL`（`claude_code.py:95`）把这层约定固化成常量。

### 2.3 写权限由 `Edit(path)` 规则判定

`claude_code.py:546-551` 不再用 `Write(./result.json5)`，而是：
- `Read(//<task>/schema.json)`：让模型读 schema；
- `Edit(//<task>/result.json5)`：文件写检查实际读取的是 `Edit(path)` 规则，`Write(path)` 规则不参与匹配。

`_permission_rule_path()`（`claude_code.py:952`）用 `//` 锚到文件系统根；`_resolved_directory()`（`claude_code.py:947`）先解析任务目录，避免 macOS `/tmp -> /private/tmp` 这类软链让请求路径与规则路径不一致。

### 2.4 一次调用同时拿工具集与结果证据

analyze 改为 `--output-format stream-json --verbose`（`claude_code.py:559-561`）。`_parse_cli_stdout()`（`claude_code.py:705`）从 NDJSON 里取最后一个 `type=result`，同时记录 `system/init.tools`、`permission_denials`、`stop_reason`、`num_turns`。这些字段让 provider 能在同一轮结果里判断“工具在不在、写有没有被拒”，而不是再发一轮 prompt 试。

### 2.5 快速失败与取消诊断

`_ensure_submission_tool()`（`claude_code.py:316`）在工具集缺少 `Write` 时直接抛错；`_analyze_with()`（`claude_code.py:236-252`）在提交文件缺失且存在写拒绝时直接抛错，不再做第二次 300 秒调用。`_cancelled_error()`（`claude_code.py:496`）把有界 stderr 与结构化 CLI 证据写进 `detail`，替代原来的裸 `"cancelled"`。

## §3 数据流走查

1. `analyze()` 由提交通道创建一次性任务目录并写入 `schema.json`（`claude_code.py:190`）。
2. `_analyze_with()` 解析任务目录真实路径，作为 CLI 的 `cwd` 与权限规则锚点（`claude_code.py:218`）。
3. `_analyze_argv()` 生成 `--safe-mode --restricted --strict-mcp-config --tools Read,Write --allowed-tools Read(//...schema.json),Edit(//...result.json5)`（`claude_code.py:552-569`）。
4. CLI 以 stream-json 输出；`_call()` 解析 result 文档并记录 init 工具列表（`claude_code.py:440-494`）。
5. `_ensure_submission_tool()` 检查 `Write` 是否真的在工具集里；不在则立即失败。
6. `collect()` 读取 `result.json5`。若文件缺失且 result 里有写拒绝，立即以“submission write was denied”失败；若只是语法/字段问题，按原契约做一次反馈重试。
7. 成功时返回 `AnalysisResult`，usage/model/session 来自真实 CLI result；失败时 `AgentProviderError` 带 trace、usage、latency 与可诊断 detail。

## §6 讨论点

### 讨论点 1：`--restricted`/`--safe-mode` 把 CLI 版本耦合到 2.1.323

**位置**：`apps/api/app/third_party_api/ai_agent/claude_code.py:552-556`

**现象**：analyze argv 使用 `--safe-mode`、`--restricted`、`--strict-mcp-config`；这些 flag 在 2.1.323 上实测可用，但更老的 CLI 可能不识别 `--restricted`。

**问题**：升级/回滚 CLI 版本时，provider 可能在启动阶段直接失败，而不是像旧 argv 那样至少能跑一轮。

**预判**：当前部署固定 `CLAUDE_CODE_VERSION=2.1.323`，且 `docs/claude-code.md` 已记录工具面；这是可接受的版本耦合。若未来要支持更老版本，需要在 `ClaudeCodeProvider` 内做能力探测或版本回退，而不是把缺省行为改回 `--bare`。

**结论**：（留空）

### 讨论点 2：`stream-json --verbose` 放大了 stdout 体积

**位置**：`apps/api/app/third_party_api/ai_agent/claude_code.py:559-561`

**现象**：相比单 JSON，stream-json 会输出 init、thinking token、工具事件与最终 result；provider 仍然全量缓冲 stdout。

**问题**：极端长会话或大量工具轮次下，内存与解析成本高于旧格式；transport 目前只有超时约束，没有 stdout 上限。

**预判**：当前 analyze prompt 短、工具面只有 Read/Write，单轮输出远低于风险阈值；但“stdout 无上限”是既有边界，本 PR 没有恶化到需要在本 issue 处理。若要长期运行，应在 transport 或 provider 增加有界读取/截断。

**结论**：（留空）

### 讨论点 3：edit 通道仍用 `--bare`

**位置**：`apps/api/app/third_party_api/ai_agent/claude_code.py:574` 起

**现象**：`_edit_argv()` 仍保留 `--bare` 和 `Write(.harness-evolution/edits.json5)` 规则；它与 analyze 的旧缺陷同源。

**问题**：如果未来启用 `HE_PATCH_SOURCE_MODE=agent-edit`，编辑计划可能写不出来，重演本次故障。

**预判**：issue #537 的实现契约只覆盖 analyze，`edit` 不在交付边界内；但这是一个真实的潜在缺陷，应在启用 agent-edit 前单独开 issue 用同样的方式验证工具面与 `Edit(path)` 规则。

**结论**：（留空）

### 讨论点 4：写被拒的快速失败只在结果文件缺失时触发

**位置**：`apps/api/app/third_party_api/ai_agent/claude_code.py:236-252`

**现象**：只有 `SubmissionOutcome.status == "missing"` 且 result 里有 `permission_denials` 时才直接失败；如果模型写出了一个字段非法的 `result.json5`，即使同轮还有别的写拒绝，也会走一次反馈重试。

**问题**：这是刻意的：文件存在说明提交路径本身可用，非法字面量应按原契约得到一次修正机会；只有“文件根本不存在 + 有写拒绝”才能归因到权限面。

**预判**：行为与 issue 的“写被拒快速失败”一致；单测 `test_analyze_retries_an_invalid_literal_even_when_a_write_was_denied` 覆盖了这个边界。

**结论**：（留空）

## §9 文件级代码分析

### `apps/api/app/third_party_api/ai_agent/claude_code.py`

**职责**：Claude Code 适配层；把 analyze 的启动参数、权限规则、CLI 结果与失败诊断收在一个子类里，不碰提交通道与基类。

**变更块 1：常量与解析字段（86-128）**

新增 `ANALYZE_TOOLS=("Read","Write")`、`SUBMISSION_TOOL="Write"`；`_ParsedCliResult` 增加 tools/denials/stop_reason/num_turns。前者把“工具面只允许这两项”写成代码契约，后者让一次调用就能回答“工具在不在、写有没有被拒”。

**变更块 2：`_analyze_with` 的快速失败（203-314）**

任务目录只解析一次，同时作为 `cwd` 与规则锚点；首次调用后先检查工具集，再 collect；文件缺失且有写拒绝时直接失败。反馈重试仍是“一次、无状态、不带 `--resume`”，与原契约一致。

**变更块 3：`_analyze_argv`（528-572）**

去掉 `--bare`，用 `--safe-mode`/`--restricted`/`--strict-mcp-config` 保留上下文最小化，用 `--tools` 收敛内置工具，用绝对 `Edit(//...)` 规则授权唯一写目标。这里每个 flag 都有真实 CLI 实测支撑。

**变更块 4：结果解析与诊断（705-1010）**

NDJSON 解析记录 init 工具列表与 result 证据；`_cli_result_diagnostics()` 只输出工具名、拒绝目标、stop_reason、num_turns，不输出模型正文；`_cancelled_error()` 复用同一套诊断，因此取消不再是 `detail="cancelled"` 一句话。

### `apps/api/tests/test_ai_agent_claude_code.py`

**职责**：用 MockRunner 固定 argv/规则与失败路径，用 opt-in e2e 覆盖真实 CLI 的两个方向。

**变更块**：既有成功/重试断言改为新 argv；新增工具缺失、写被拒、非法字面量仍重试、重试后保留拒绝证据、取消诊断五个单测；新增越界写 e2e。覆盖点与讨论点 4 的边界一一对应。

### `docs/claude-code.md` 与 Agent Note

文档只写现状：analyze 的 flag、绝对规则、`stream-json` 证据与验收命令；Agent Note 记录为什么去掉 `--bare`、为什么 `Write(path)` 规则无效、为什么保留文件通道。两者分工符合 `docs/AGENTS.md` 的“现状进 docs、理由进 Note”。

**检视发现**：生产代码改动集中在单个模块，未发现阻塞性缺陷；遗留项是 edit 通道与 stdout 上限，已在 §6 讨论。
