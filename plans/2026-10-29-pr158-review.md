## §1 一页速览

**一句话**：这个 PR 把基线字段从“必须先选中一项的下拉框”改成“输入框就是最终值，仓库 tag 只是旁边的便签”，同时修掉了新增态没有请求却一直转圈的问题。

## §2 架构导览

### 2.1 表单值只由用户输入决定

`form.defaultRef` 仍是唯一提交值（`TargetFormDialog.vue:36-43`）。`ElAutocomplete` 在每次输入时发出 `update:modelValue`（Element Plus 2.14.7 实际源码 `autocomplete.vue_vue_type_script_setup_true_lang.mjs:91-103`），因此失焦只会关闭建议层，不再清空输入（同文件 `:123-131`）。这是本 PR 修复原始缺陷的核心。

### 2.2 tag 建议是可选派生数据

`versionOptions` 合并远端 tag 和已保存 target 的当前 `defaultRef`（`TargetFormDialog.vue:47-51`）。`fetchVersionSuggestions()` 无论当前输入是什么都返回完整列表（`:94-101`），所以当前基线是分支时，tag 建议仍可见；选择 suggestion 只是把同一个字符串写回输入框。

### 2.3 加载状态必须来自已保存 target

页面把 `editingTargetId` 作为 versions query 的启用条件（`Index.vue:39-47`）。新增态 id 为 null，不启用 query；loading 不是 query 的 `isPending`，而是 `editingTargetId && isFetching`。这把“query 被禁用”和“请求正在执行”区分开，避免新增态永久 loading。

### 2.4 草稿仓库与已保存仓库有不同事实来源

versions API 仍按 target id 查询已保存配置（`useEvolutionTargets.ts:70-80`），不会从浏览器探测草稿 `repoUrl`。当草稿 URL 变化时，帮助文案明确建议来自已保存配置（`TargetFormDialog.vue:52-63`）。这保住了后端作为仓库校验和远端访问的唯一权威。

## §3 数据流走查

1. 用户点击“新增配置”，`openCreate()` 将 `editingTarget` 置空（`Index.vue:49-55`）。
2. `editingTargetId` 为 null，因此 versions query 禁用；`versionsLoading` 明确为 false（`Index.vue:39-44`）。
3. 用户键入 `feature/foo`。`ElAutocomplete` 在每次 input 时更新 `form.defaultRef`，不要求 Enter 或 option（`TargetFormDialog.vue:217-230`）。
4. 用户失焦或点击“新增配置”。失焦只关闭 autocomplete popper；表单提交读取当前 `form.defaultRef.trim()`（`TargetFormDialog.vue:107-126`）。
5. `submitTarget()` 把完整字段提交到 create mutation（`Index.vue:128-144`）；后端仍按 `repo/ref/subDir` 返回 422 `REPO_INVALID`。
6. 编辑已有 target 时，id 启用 versions query；只有真实 fetch 进行时显示“正在读取仓库版本…”（`Index.vue:42-44`）。
7. versions 返回后，tag 与当前 `defaultRef` 共同成为建议（`TargetFormDialog.vue:47-51`）。
8. 用户在仓库地址中改值但尚未保存时，帮助文案指出建议来自已保存配置（`TargetFormDialog.vue:61-63`）。
9. 请求失败或没有 tag 时，输入框仍可编辑，提交仍使用用户文本（`TargetFormDialog.vue:65-71`）。

## §6 讨论点

### 6-1 [P2] 原型把当前应用的按钮式类型选择改成了圆点单选

**位置**：正式代码 `apps/web/src/pages/evolution/targets/components/TargetFormDialog.vue:156-164`；原型 `plans/14-15-ui-prototype/harness-evolution.html:577-580`、`:2817-2823`；用户确认截图对应的正式 UI 为蓝色 `Skill` / 白色 `Agent` 分段按钮。

**现象**：正式表单仍用 `ElRadioButton`，视觉上是一个连续分段选择器；PR 原型却新增 `kind-choice::before` 圆形选择点，把 `Skill` / `Agent` 画成普通 radio。审计报告称原型已对齐当前应用，但代码事实相反。

**问题**：用户明确要求“浮窗保持当前设计，只改基线下拉”。该原型变更扩大了视觉范围，使后续 UI 审查依据与正式页面不一致；如果后续继续按原型调整应用，会把用户明确保留的现有控件改掉。

**预判**：原型恢复与正式页面一致的 `ElRadioButton` 分段样式，保留新增的基线组合框与启用开关，不修改正式页面的对象类型控件。

**结论**：

不修（2026-10-29）：真实浏览器中 `ElRadioButton` 当前渲染为 `● Skill ○ Agent` 圆点单选，与原型一致；本 PR 没有修改对象类型控件。检视所称“蓝色分段按钮”与当前实际渲染不符。

### 6-2 [P2] 正式字段没有原型中的右侧下拉按钮，建议只能靠聚焦发现

**位置**：正式组件 `TargetFormDialog.vue:217-230`；原型 `harness-evolution.html:2839-2843`；Element Plus 实际模板 `node_modules/.pnpm/element-plus@2.14.7_vue@3.5.44_typescript@5.9.3_/node_modules/element-plus/es/components/autocomplete/src/autocomplete.vue_vue_type_script_setup_true_lang.mjs:368-411`。

**现象**：原型在输入框右侧画了独立的 `⌄` 按钮；正式组件使用 `ElAutocomplete`。该组件的 `show-arrow` 实际传给 Tooltip（源码 `:307`），控制 popper 的小三角，并不在 ElInput 内生成右侧展开按钮。正式页面只能通过点击/聚焦输入框触发建议。

**问题**：鼠标用户看到的仍像普通文本框，“这里还能展开 tag 列表”的提示弱于已确认原型。E2E 只验证直接输入，没有验证点击建议、键盘上下选择或 Enter 选择，所以当前成功 CI 不能证明“下拉框选择可以”这一半需求。

**预判**：若保留 `ElAutocomplete`，在输入框内增加一个可点击 suffix/独立 toggle 来触发 `focus()` 和建议列表；补真实 DOM 测试覆盖展开、选择与失焦。若产品接受“点击输入框即展开”，则应修改原型并明确该取舍，同时补 E2E。

**结论**：

已修复（2026-10-29）：基线组合框增加可访问的“展开标签建议”按钮，复用 `ElAutocomplete` 的 focus/建议层；补充真实 DOM 用例覆盖点击展开、点击建议回填、键盘 ArrowDown+Enter 选择。选中不再误把建议对象传入字符串表单。

### 6-3 [P2] 有缓存时后台重取失败不会显示“建议暂时不可用”

**位置**：`apps/web/src/pages/evolution/targets/Index.vue:45-47`；TanStack Query 实际语义 `node_modules/.pnpm/@tanstack+query-core@5.104.5/node_modules/@tanstack/query-core/build/modern/queryObserver.js:402`。

**现象**：`versionsError` 只看 `isError`。TanStack Query 在已有缓存、后台重取失败时保持 `hasData`，把失败标记为 `isRefetchError`，而 `isError` 为 false。此时界面仍显示上一次成功取得的 tag，帮助文案继续把它们当作当前建议。

**问题**：用户在编辑同一 target 且网络或后端临时失败时，会看到旧 tag 且没有“获取建议失败，可直接输入”的提示。直接手填仍可用，所以不是保存阻塞，但建议来源提示不真实，也可能诱导用户选择旧仓库的 tag。

**预判**：`versionsError` 同时考虑 `isError` 与 `isRefetchError`；有缓存时保留建议但标注过期/不可刷新，并补“成功缓存 + 重取失败”测试。

**结论**：

不修（2026-10-29）：用 TanStack Query v5 实际状态验证，已有 data 时后台重取失败会得到 `status: "error"`、`isError: true`、`isRefetchError: true`；现有 `isError` 条件已经覆盖，增加或条件不会改变行为。

### 6-4 [P3] 必填错误在键入第一个字符时可能仍停留

**位置**：`TargetFormDialog.vue:103-105`、`:228`；Element Plus input 事件顺序为 `emit(INPUT_EVENT)` 后再 `emit(UPDATE_MODEL_EVENT)`（autocomplete 实际源码 `:91-95`）。

**现象**：`@input="clearDefaultRefError"` 在组件发出 `update:modelValue` 之前运行。它读取的 `form.defaultRef` 仍是上一次的值；若此前因空值提交出现错误，用户键入单个字符时 helper 仍看到空字符串，不会删除错误。继续输入第二个字符后才会清除，或再次提交才清除。

**问题**：这不是保存失败，但会让用户在已输入合法 ref 时短暂看到陈旧错误；issue 曾特别关注旧错误提示不清除，现有测试没有覆盖“错误出现后仅输入一个字符”的路径。

**预判**：改为监听事件参数、使用 watcher 监听 `form.defaultRef`，或直接在该 input 事件中无条件删除 `errors.defaultRef`；补一条从空提交到单字符输入的测试。

**结论**：

已修复（2026-10-29）：基线输入改为由 `@update:model-value` 同时写入表单值并按新值清除错误；新增测试验证空提交后只输入一个字符，陈旧必填错误立即消失。

### 6-5 [P3] PR 描述没有包含用户要求的 UI 验证截图

**位置**：PR #158 描述；设计要求 `plans/fullstack-design/08-frontend-implementation.md:683`。

**现象**：PR 正文只有命令验证，没有新增/编辑浮窗、直接输入保存、建议失败兜底或与原型对照的截图。

**问题**：自动测试能证明请求体和主要 DOM 行为，但本次改动核心是交互与视觉对齐；评审者无法仅从 PR 复用用户已经看过的证据，也无法快速判断正式 UI 是否仍沿用当前设计。

**预判**：把最终正式 UI 与原型的关键截图加入 PR 描述，至少包含建议展开、直接输入保存、建议失败和 422 保留输入。

**结论**：

已修复（2026-10-29）：最终应用截图已存入 `reports/2026-10-29/issue153/` 并加入 PR 说明，覆盖建议展开、手填直接保存、建议失败与 422 输入保留。

## §9 文件级代码分析

### 9.1 `TargetFormDialog.vue`

**职责与变更**：M；表单输入、tag 建议、帮助文案与提交校验从 `ElSelect` 改为可直接编辑的 `ElAutocomplete`。

**关键依赖解读**：Element Plus 是本项目实际打包的 Vue UI 组件库，不是运行时外部脚本。`ElAutocomplete` 像“带便签栏的文本框”：输入值持续写回 v-model，文本框获得焦点时再向便签栏询问可选 tag。

**旧代码 vs 新代码**：

```vue
<!-- 旧：输入只是 select 的过滤文本 -->
<ElSelect v-model="form.defaultRef" filterable allow-create>
  <ElOption v-for="version in versionOptions" … />
</ElSelect>

<!-- 新：输入本身写入 form.defaultRef，建议由 callback 提供 -->
<ElAutocomplete
  v-model="form.defaultRef"
  :fetch-suggestions="fetchVersionSuggestions"
  trigger-on-focus
/>
```

旧实现的风险在于过滤文本与模型分离（原文件）；新实现直接使用输入事件更新模型。`versionOptions` 固定返回全部 tag 与已保存 ref，避免输入过滤把其他 tag 隐藏（`TargetFormDialog.vue:47-51`、`:94-101`）。帮助文案根据 create/edit、repo 草稿变化、loading、error 和空列表分层（`:57-72`），这部分方向清晰。

**实现思路总结**：输入是事实源；建议是附加数据；错误与 loading 只改变提示，不改变可编辑性。

**检视发现**：§6-2、§6-3、§6-4。

### 9.2 `Index.vue`

**职责与变更**：M；把 versions query 的 UI 状态从 `isPending` 改为“有 target id 且 `isFetching`”，同时传入 `isError`。

**旧代码 vs 新代码**：

```ts
// 旧：禁用 query 也可能是 pending
:versions-loading="versionsQuery.isPending.value"

// 新：没有 target id 必定不是 loading
const versionsLoading = computed(
  () => Boolean(editingTargetId.value) && versionsQuery.isFetching.value,
)
```

这一步直接修复新增态的永久 loading。`versionsError` 进一步把失败传给表单，但由于只读 `isError`，遗漏了缓存存在时的 refetch error（§6-3）。

**实现思路总结**：用当前 target 与真实 fetch 状态共同决定 loading，避免把 query disabled 状态当网络状态。

**检视发现**：§6-3。

### 9.3 `useEvolutionTargets.ts` 与 query cache

**职责与变更**：虽然没有出现在 PR diff 的文件列表里，但它是本次行为的上游依赖，必须纳入通读。

`updateMutation` 成功时调用 `invalidateTargetDependents()`（`useEvolutionTargets.ts:14-20`、`:37-45`）；该前缀 `["evolution","targets"]` 同时匹配 versions key `["evolution","targets",id,"versions"]`（`queryKeys.ts:29-31`）。因此保存新 repoUrl 后会失效旧 versions 缓存；30 秒 `staleTime`（`queryClient.ts:30`）不会阻止下一次编辑重取。此处无遗漏。

**实现思路总结**：target 集合是父前缀，保存配置同时使列表、catalog 与对应版本建议进入失效状态。

**检视发现**：无新增问题；缓存失效路径成立。

### 9.4 `TargetFormDialog.test.ts`

**职责与变更**：M；把旧测试中直接 `$emit("update:modelValue")` 的假入口改为真实 input DOM，并覆盖失焦、直接提交、建议失败和 repo 草稿变化。

**旧代码 vs 新代码**：

```ts
// 旧：测试自己制造一个成功事件，绕过了用户输入路径
wrapper.findComponent(ElSelect).vm.$emit("update:modelValue", "main")

// 新：从实际 input 输入，再触发 blur/submit
await wrapper.get('input[name="defaultRef"]').setValue("feature/direct-submit")
await input.trigger("blur")
await wrapper.get("form").trigger("submit")
```

这组测试直接覆盖原回归，质量显著高于此前。缺口是建议 callback 通过组件 prop 直接调用，没有走真实 popper 的点击和键盘路径；E2E 也只测直接输入。相关见 §6-2。

**实现思路总结**：测试入口前移到用户输入 DOM，而不是替组件声明成功。

**检视发现**：建议选择自动化覆盖不足，并入 §6-2。

### 9.5 `Index.test.ts`

**职责与变更**：M；页面级测试也改为真实 input，并增加新增态不请求 versions、不显示 loading 的断言。

旧测试的 `$emit` 同样绕过了组件内部过滤状态；新测试会经过 `TargetFormDialog` 的 v-model。`versionRequests === 0` 与“无 loading 文案”同时验证了请求和视图两端（`Index.test.ts:268-286`），证据完整。

**实现思路总结**：页面级测试验证从表单到 mutation 请求体的完整链路。

**检视发现**：无独立问题。

### 9.6 `m5-target-config.test.mjs`

**职责与变更**：M；删除“打开 select、输入、等待新建 option、点击 option”的 E2E 步骤，改为直接填写 `input[name='defaultRef']`；新增新增态无 loading 断言。

这使 E2E 与真实用户路径一致，并验证 422 后输入仍保留（`tests/e2e/m5-target-config.test.mjs:190-195`、`:500-523`）。但 `setInput` 是程序化设置值与派发事件，且保存通过 `.click()` 执行，不是真实的键盘焦点迁移；因此建议展开与真实 pointer blur 仍留为人工/后续 smoke 事项。

**实现思路总结**：E2E 从“选择新建 option 才能提交”改为普通文本提交。

**检视发现**：下拉选择与真实 blur 的自动化缺口并入 §6-2。

**实现思路总结**：保证生产构建和 jsdom 测试都能解析同一组件。

**检视发现**：无。

### 9.8 原型 `harness-evolution.html`

**职责与变更**：M；新增“进化对象配置”页、创建/编辑浮窗、可编辑 ref 组合框、建议展开、加载与失败状态。

基线核心交互与正式实现方向一致：输入即时同步（`:2793-2805`）、建议选择（`:2806-2815`）、直接保存（`:2878-2900`）。但对象类型被画成圆点（`:577-580`、`:2821-2822`），正式应用仍是 `ElRadioButton` 分段按钮；正式输入也没有原型中的独立下拉按钮（`:2841-2843`）。这两项使“原型与正式 UI 一致”的 PR 声明不成立（§6-1、§6-2）。

**实现思路总结**：原型已表达“输入优先 + 建议可选”，但控件细节扩大了用户确认的设计范围。

**检视发现**：§6-1、§6-2。
