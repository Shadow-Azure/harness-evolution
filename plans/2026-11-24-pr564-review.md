## §1 一页速览

一句话：把“主机缺部署前置”从合并后的 Deploy 事故，变成 PR 里先红后绿的安检门。

比喻：机场安检不再只看护照（代码单测），而是让旅客真的走过安检机（干净主机安装 + 服务账号探针 + 真实 preflight）；没带证件（缺 provisioning 路径）在登机前就被拦下。

| 单一来源 | `deploy/attribution-runtime-prerequisites.list` 记录运行时 OS 前置；bootstrap 安装、cloud-init 镜像、CI 断言 |
| 运行时门禁 | `deploy-contract` 在 `ubuntu:24.04` 容器先移除 bwrap 验证缺包负例，再真实安装、跑 `harness` 探针与 `attribution.preflight` |
| 静态门禁 | API 套件内断言清单一致、`release.sh` preflight 顺序、job 与 `ci-ok.needs` 接线 |

## §2 架构导览

三层防线，从“写清楚”到“跑起来”：

1. **清单层**：`deploy/attribution-runtime-prerequisites.list:1-10` 是唯一清单，当前只有 `bubblewrap`。`deploy/bootstrap-server.sh:16-28` 用 `SCRIPT_DIR` 找到清单，`mapfile` 读入后与基础包一起 `apt-get install`；清单缺失或为空直接失败，不静默跳过。`deploy/cloud-init.yaml:4-12` 是创建阶段的镜像，CI 保证两边不漂移。
2. **静态层**：`apps/api/tests/deploy/test_provisioning_contract.py:55-80` 校验清单、bootstrap、cloud-init 与 Provision 脚本一致；`:92-103` 用行号比较断言 preflight 在 `ln -sfn` 之前；`:106-118` 校验 `ci.yml` 的 job、容器镜像与 `ci-ok.needs`；`:140-157` 用真实 bash 计算脚本到仓库根的相对层级，防止再次出现 `../../..` 的 off-by-one。
3. **运行时层**：`apps/api/tests/deploy/verify_provisioning_contract.sh:32-40` 先移除预装 bwrap，`:42-51` 断言 `--check` 退出 10 且输出 `ATTRIBUTION_BWRAP_MISSING`；`:53-69` 创建 `harness` 后跑真实 `--install`，断言 `state=ready`、`bwrap --version`、服务账号命名空间探针；`:71-84` 以 `harness` 身份运行候选代码的 preflight，断言 `ready=True`。`.github/workflows/ci.yml:318-344` 把这个脚本放进一次性 `ubuntu:24.04` 容器；`:326-329` 的 seccomp/AppArmor 放开只服务 bwrap 的 userns 创建。

## §3 数据流走查

新增一个部署前置时，数据如何流动：

1. 开发者在 `deploy/attribution-runtime-prerequisites.list` 加包名。
2. `bootstrap-server.sh` 在下一次 bootstrap 时安装；`cloud-init.yaml` 需要同步镜像。
3. PR CI 的 API 套件先跑静态契约：若 cloud-init 没同步，`test_cloud_init_mirrors_every_runtime_prerequisite` 失败；若 bootstrap 又写死一份，`test_bootstrap_installs_every_runtime_prerequisite` 失败。
4. `deploy-contract` 在干净容器里跑运行时契约：负例证明“缺包会被识别”，正例证明“同一脚本能装好”，服务账号探针与 preflight 证明“装好之后归因运行时真的可用”。
5. `ci-ok` 聚合该 job；分支保护只要求 `ci-ok`，所以新增前置但漏 provisioning 的 PR 无法合并。

发布路径没有改变：`deploy/release.sh:142` 仍在切换 `current` 前跑 preflight，`deploy` 仍无 apt 权限；CI 只把同一契约前移。

## §6 讨论点

### D1 容器放开 seccomp/AppArmor 的边界

**位置**：`.github/workflows/ci.yml:326-329`

**现象**：`deploy-contract` 的容器带 `--security-opt seccomp=unconfined --security-opt apparmor=unconfined`。

**问题**：这两项放开会扩大容器内 PR 代码的内核攻击面；虽然容器不是 privileged、无 secret，仍应在代码里说明必要性。

**预判**：bwrap 创建 unprivileged user namespace 需要它们，GitHub Docker 默认策略会拒绝；一次性 runner 且无凭据可接受。

**结论**：已补注释说明用途与边界，未改成 privileged。

### D2 flow-online 与远端 issue 状态竞态

**位置**：`.agents/flow/issues/bugfix-attribution-provider-startup.md:11`、`.agents/flow/issues/bugfix-attribution-runtime-silent-hang.md:11`

**现象**：检视期间 #542/#544 在远端先关后开，`flow-online` 在两次 CI 中分别报“应为 CLOSED”和“应为 OPEN”。

**问题**：这是共享仓库的状态竞态，不应由本 PR 改主分支 flow 状态来“修”。

**预判**：远端 OPEN 与 main 的 `ready` 一致；保持本 PR 不碰这些文件即可通过。

**结论**：已回退这两处状态改动，本 PR 不再包含无关 flow 变更；后续由独立 flow sync 维护。

### D3 e2e 失败与 main 基线不一致

**位置**：`tests/e2e/m11-05-v2-cross-stack.test.mjs:649`、`tests/e2e/m4-problem-cards.test.mjs:1010`

**现象**：本 PR 两次 CI 的 e2e 分别失败于 target overview `potential=2`（期望 3）与问题卡 `pressed=true`（期望 false）；同 base 的 main CI（run 45306531947）e2e pass。

**问题**：本 PR 没有 app 代码差异，失败出现在时序敏感断言；需区分 flake 与真实回归。

**预判**：两次失败点不同、重跑可过，属 CI 负载下的 flake；若重跑仍红，再按真实回归处理。

**结论**：第三次重跑通过，确认为 runner 负载下的时序 flake；不在本 PR 改 e2e，必要时另开 issue 记录稳定性。

### D4 bootstrap 对清单文件的路径依赖

**位置**：`deploy/bootstrap-server.sh:16-21`

**现象**：bootstrap 现在要求同目录存在 `attribution-runtime-prerequisites.list`，否则退出。

**问题**：若有人只上传 `bootstrap-server.sh` 单文件，会失败。

**预判**：部署手册一直用 `scp deploy/*` 或 rsync 整个目录，清单会一起上传；显式失败比静默漏装安全。

**结论**：保留 fail-closed，并在错误文案中写明“把 deploy/ 下的清单与脚本一起上传”。

### D5 cloud-init 仍是静态镜像

**位置**：`deploy/cloud-init.yaml:11-12`

**现象**：cloud-init 的 `packages` 是静态列表，不直接读取清单文件。

**问题**：严格说不是“运行时单一来源”，新增包需要手动同步。

**预判**：cloud-init 在机器创建时执行，无法读取仓库文件；静态断言是本场景能做到的最强约束。

**结论**：保留；静态契约保证漂移必红。

## §9 文件级代码分析

### `deploy/attribution-runtime-prerequisites.list`

清单只有 `bubblewrap`，但注释定义了扩展顺序：改清单 → 同步 cloud-init/Provision → CI 验证。把“新增部署前置”从口头约定变成可执行契约。

### `deploy/bootstrap-server.sh`

`SCRIPT_DIR` 基于 `BASH_SOURCE`，因此从仓库目录或 `/opt/harness/shared/config` 执行都能找到清单；`mapfile` 在 Ubuntu 22.04 的 bash 5.1 可用；空数组在 `set -u` 下用 `"${RUNTIME_PACKAGES[@]}"` 展开安全（bash ≥4.4）。`sed` 去注释后仍有包名才继续，空清单 fail-closed。

### `deploy/cloud-init.yaml`

只改注释，保持 cloud-init 的 `packages` 静态可读；`runcmd` 仍做 `bwrap --version` 冒烟。

### `.github/workflows/ci.yml`

job 使用 `container` 而非 runner 预装环境；先安装 git 再 checkout，避免 ubuntu 基础镜像没有 git。静态测试先跑，运行时脚本后跑，失败点清晰。`ci-ok` 只加一个 needs 项，保持单点 required check。

### `apps/api/tests/deploy/verify_provisioning_contract.sh`

四个阶段各自输出稳定错误码；`set +e` 只包住预期失败的命令，避免 `set -e` 吞掉状态码。路径测试由 pytest 单独覆盖，防止父级数量回归。`DEBIAN_FRONTEND=noninteractive` 避免容器里 apt 交互。

### `apps/api/tests/deploy/test_provisioning_contract.py`

静态测试不 mock 关键路径，只读文件；`job_block` 用 YAML 顶层 job 缩进切块，避免匹配到其他 job；`ci_ok_needs` 解析 `needs` 列表；路径测试真实执行 bash 的 `cd` 表达式。

部署文档新增一节把门禁、顺序与排障收在一处，细节放手册；Agent Note 记录“为什么在 CI 真实跑而不是 mock”的取舍；flow issue 绑定 #552，依赖 bugfix-33（已随 #556 合并为 done）。
