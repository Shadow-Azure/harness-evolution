# PR 检视

[English](review.en.md) | 中文

> 类型：流程 | 层级：检视工程。目标是让维护者读懂 PR 在做什么、为什么这样做、代价是什么。

## 核心诉求

检视文档的第一使命是帮助理解，不是罗列事实：抽象机制配生活化比喻，术语首次出现给一句白话解释，论断跟着真实调用链与真实输入输出走。读者读完应能回答三个问题：解决什么问题、怎么解决、代价是什么。

## 工作流

1. 收集事实：`gh pr view` 拿标题、描述与规模；`git diff --name-status <base>...<head>` 拿逐文件状态；PR 描述里的验证声明原样提取。
2. 通读主线：按数据流从入口读到边界，行号锚点来自实际阅读，不估。
3. 产出文档：`plans/yyyy-mm-dd-pr<N>-review.md`，结构包含变更树、一页速览、架构导览、数据流走查、导读地图、人工验收、讨论点、分流表、文件级分析。
4. 需要逐文件注解时，用 `.agents/skills/pr-review/SKILL.md` 的体例；处理检视意见用 `.agents/skills/pr-review-fix/SKILL.md`。

## 证据要求

- 第三方或框架行为主张必须实测：查包源码、跑最小复现或给出官方文档出处。
- 未读完的文件在导读地图标 `◻`，不假装读过。
- 验证命令必须真实执行；未执行的项写"未验证"，不写成通过。
- 涉及安全、数据一致性、并发或状态机的风险，给出触发条件与建议归属阶段。

## 讨论点格式

每条讨论点固定五段：**位置**（file:line）、**现象**、**问题**、**预判**、**结论**。预判是供拍砖的初步看法，结论留空给维护者决定；已决事项记录日期、理由与实测数据。

## 分流表

| 发现 | 定性 | 去处 |
|---|---|---|
| 缺陷 | bug | 修复 PR 或 postmortem |
| 设计取舍 | decision | 更新 owning Agent Note |
| 使用步骤 | how-to | development.md |
| 现状偏差 | fact | 对应 docs 页 |
| 检视过程 | process | 本检视文档 |

检视报告本身不进 `.agents/notes/`：那是封闭的决策记录系统，类目、骨架与双语三件套不为过程记录设计。

## 纪律

- 不替维护者拍板：讨论点给预判不给结论。
- 不制造紧迫感：当前无实害的发现如实标注"无实害"。
- 不复述代码字面：讲意图、机制、边界与代价。
- 文档语言与仓库一致：常驻检视规范双语成对；单次检视记录用中文即可。
